# 能力路由

## 一句话判据

| 用户想要 | 原子 | 产物 |
|---|---|---|
| **重做一个**：照着这个网站/页面做出我的版本 | `clone` | 可构建的工程 |
| **看懂它**：它是怎么实现的、这段代码在干什么 | `reverse` | 分析报告 |
| **找洞**：我这个有没问题、能不能被打 | `redteam` | Findings + 复现步骤 |
| **防住**：让这个洞不再成立、怎么检测 | `blueteam` | 检测规则 + 加固 |

## 三种组合

| 场景 | 组合 | 为什么 |
|---|---|---|
| 站点复杂、直接抄容易踩坑 | `reverse` → `clone` | 先搞懂数据流再动手，省掉试错 |
| 刚复刻完，想验证安全性 | `clone` → `redteam` → `blueteam` | 红蓝的目标就是「我刚做出来的东西」 |
| 只想看自己有没有洞 | `redteam` 单独 | 不必先有复刻产物 |

**组合时靠目录交接**，不靠内存：
`reverse` 写 `analysis/`，`clone` 读它；`redteam` 写 `security/findings/`，`blueteam` 读它。
每一步都能单独跑，所以也能拆开用。

## 路由前必须确认的两件事

1. **目标是什么**：网址？本地文件？项目目录？跑起来的服务？
2. **归属**：是不是用户自己的东西？

第 2 条对 `redteam` / `blueteam` **是硬门槛**——不是自己的目标或不明确授权，
一律先引导到 `clone`（学习和重建），或者在动手前让用户明确声明授权范围。

## 判不准的时候

判不准就问一句，不要猜着开跑。最常见的三种歧义：

- **「帮我看看这个网站」** → 是看懂（`reverse`）还是做出来（`clone`）？
- **「这个能不能被打」** → 先确认目标归属；自己写的才走 `redteam`。
- **「把这个能力集成进来」** → 这是插件/技能开发，不是这四个原子的事，
  用 `plugin-development` 或 `skill-creator`。

## 别做的事

- 不为了「看起来完整」把四个原子全跑一遍。**能单条闭环就别组合**。
- 不在用户没确认目标的情况下直接开始复刻或测试。
- 不用 `reverse` 代替 `clone`（只分析不产出工程，用户会失望），
  也不用 `clone` 代替 `reverse`（建了一堆代码却答不出"它怎么做的"）。
