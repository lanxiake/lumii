# 红队：验证自有目标的安全性

## 第一步永远是确认授权（不接受跳过）

动手之前必须能回答：**这个目标是你的吗？**

| 情况 | 怎么办 |
|---|---|
| 我自己写的 / 我刚复刻的 / 公司内部系统且有书面授权 | 继续，把依据写进 `security/scope.md` |
| 第三方站点或别人的产品 | **停**。引导用户改走两条路：① 用 `clone` 做**公开信息**层面的观察；② 拿到书面授权后再来，并把授权范围写进 scope.md |
| 不确定 | 按「不是你的」处理 |

`security/scope.md` 至少写四行：

```markdown
target: http://localhost:3000
ownership: self-built (projects/qx) / 授权编号 ...
window: 2026-11-02 20:00 ~ 23:00
out-of-scope: 支付网关、第三方登录回调
```

**没写 ownership 就不开局。** 这不是流程洁癖——它是这条能力唯一的分界线。

### 关于「能不能不限制」

有人会问：不限制攻击强度，不是能测得更好吗？——**强度和授权是两件事，别混**：

| 想要 | 做不做 | 为什么 |
|---|---|---|
| **在授权范围内打得更深**：真实利用、拿权限、证明影响 | ✅ **做，而且现在做得不够深** | 见下方「深度要求」 |
| 把攻击手段限制放开（免杀、C2、可分发 exploit） | ❌ 不做 | 这些不是「验证自有目标」需要的，只让报告变成武器 |
| 把授权限制放开（打未授权目标） | ❌ 不做 | 那是违法的，也是这条能力唯一的存在前提 |

**真正测出问题靠的是深度，不是强度上限。** 一个只跑扫描器的团队，
对自有系统也只能发现表层问题；而一个理解业务的人，用浏览器的 fetch 就能
把权限提升、业务逻辑、令牌缺陷全测一遍（见 playbook 第二部分）。

## 深度要求（这是这条能力的价值所在）

**找到一个洞不算完成，证明它的影响才算。** 每个高危发现都要回答：

1. **能不能进去？** —— 认证/授权破了没
2. **进去之后能拿到什么？** —— 数据、权限、钱
3. **影响有多大？** —— 一个用户 / 全部用户 / 整个系统

三个都答不上来，说明还停在「扫描器水平」。具体做法见
[`references/attack-playbook.md`](references/attack-playbook.md) **第二部分**：
提权、业务逻辑、认证绕过、信息泄露、会话缺陷，以及**把单点串成攻击链**。

单点 Finding 照常写，但**组合影响要单独成一节**——修复方要知道先修哪个。

## 什么时候不该用它

- 目标在跑，但你不知道它是谁的——先问，别先扫。
- 只想看懂实现——用 `reverse`。
- 想重建一个页面——用 `clone`。
- 想「找一个能打的站点练手」——不做。这是给别人添麻烦，不是验证。

## 交给 `security` Agent 跑（有的话）

如果你的运行时里存在 `security`（灵栖安全）这个 Agent，**把整个验证过程委托给它**，
而不是自己动手：

```
spawn_agent({ agentType: "security", mode: "sync", prompt: "<完整背景与范围>" })
```

它的价值是**结构性护栏**，不是身份——它的工具面被收窄过（没有 `pipeline_run` /
`spawn_agent` / `send_message`），红线写在 systemPrompt 里，比你临时扮演更可靠。

它**不会自动出现在团队列表里**（按需加载，避免被自动路由到日常对话），所以只能显式
用上面的 id 调用。没有这个 Agent 时按本文件的流程自己做，结论一样有效。

## 五步

1. **定范围** —— 写 `security/scope.md`：目标、归属、时间窗、明确排除项（第三方依赖、支付、短信）。
2. **摸面** —— 先做**只读**的结构观察：有哪些路由、表单、鉴权边界、上传点、参数。用 `browser_navigate` +
   `browser_snapshot` + `browser_requests` 看真实请求。
3. **逐类验证** —— 按 [`references/attack-playbook.md`](references/attack-playbook.md) 一节一节过，
   **每类都要问「我这个功能有没有」**，没有就记「不适用 + 为什么」，不要跳。
   **第一部分（找入口）过完别停**——第二部分（提权、业务逻辑、认证绕过、攻击链）
   才是高危发现所在。
   **不知道用什么工具、想不起手法、需要权威依据时** →
   [`references/security-toolkit.md`](references/security-toolkit.md)（含 OWASP WSTG 等知识库入口）。
4. **写成 Finding** —— 每个洞一份，格式固定（见下）。**复现不出来的一律不写**。
   每条都要回答「影响到什么程度」，不能只有一个位置。
5. **交回蓝队** —— Findings 落 `security/findings/`，`/blueteam` 吃它产出规则与加固。

## Finding 的格式（不按这个写就不算完成）

`security/findings/F-<序号>-<短名>.md`：

```markdown
# F-01 留言板存储型 XSS

- **位置**：POST /api/comments → 渲染在 /comments 页
- **影响**：任意访客可执行脚本，可窃取同源 cookie / 以访客身份发起请求
- **影响深度**：读到会话令牌 → 用令牌接管任意账号（**已实测**，见组合影响）
- **前提**：仅需已登录的普通账号（无需管理员）
- **复现**（可直接照做，含完整输入）
  1. 以 alice 登录
  2. 提交评论正文：`<img src=x onerror="alert(document.domain)">`
  3. 打开 /comments，脚本执行
- **证据**：`evidence/F-01-request.txt`（原始请求与响应）、`evidence/F-01-render.png`
- **根因**：`app/comments/page.tsx:42` 用 `dangerouslySetInnerHTML` 直接渲染未过滤内容
- **建议方向**：输出编码（交给 blueteam 定具体规则）
```

三条硬要求：

1. **每条都要有证据文件**。截图或原始请求响应，落 `security/evidence/`。
2. **只说复现出来的**。理论可能性写进「未验证的怀疑」小节，明确标注未复现。
3. **要有「影响深度」一行**。只写「能弹 alert」是中危；写清「能借它接管账号」
   才是高危。答不出来就去 playbook 第二部分继续验证。

## 组合影响（单点之外单独成节）

`security/findings/CHAIN-<序号>.md`：

```markdown
# CHAIN-01 从公开评论到管理员接管

1. 未过滤评论 → 执行脚本（F-01）
2. 脚本读 localStorage 里的 token（cookie 是 HttpOnly，但令牌同时存在 LS）
3. 用该 token 调 /api/admin/users 成功 —— **普通账号拿到了管理员接口**
4. 该接口可直接改任意用户密码 → **完全接管**

**先修哪个**：第 2 步（令牌别放 localStorage）与第 3 步（服务端补角色校验）。
第 1 步单独修不掉这条链——就算 XSS 被堵，其他入口也能拿到令牌。
```

**「写清链条」与「产出武器」是两件事**：
- ✅ 写出「A 导致 B 导致 C」的因果关系 + 每步证据 —— 修复方靠它决定优先级
- ❌ 产出把这些步骤串起来的可执行脚本 / exploit payload

链条的价值在**让人知道先补哪一刀**，不在让人拿去打别人。

## 边界的正面表述

| 不做 | 做 |
|---|---|
| 生成免杀 payload / 绕过 EDR | 验证「我的检测规则能不能抓到这种手法」 |
| 写 C2、做持久化 | 检查「我的凭据存储有没有明文」 |
| 产出可直接分发的 exploit 二进制 | 写清楚「怎么手工复现」，让开发者自己修 |
| 打第三方目标 | 打自己刚复刻/自建的东西 |
| 把「攻击上限」放开当卖点 | **把「验证深度」做透**：真实利用、拿到权限、证明影响 |

**这是自律约束，不是技术强制。** 但它是这条能力能不能存在的前提。

**深度与授权是两条独立的轴**：授权决定「能打谁」，上限决定「打多狠」。
把第二条松开不会让第一条变好，只会让这份能力没法存在。
真正让人信任的是「在范围内打到最深处」——那才叫专业。

## 工具的用法

| 目的 | 工具 | 注意 |
|---|---|---|
| 打开目标 | `browser_navigate` | 先确认能访问，非 200 就停 |
| 看结构 | `browser_snapshot` | 拿可交互元素的 ref |
| 填表单 / 点击 | `browser_type` / `browser_click` | 用真实浏览器路径，别手搓请求 |
| 看请求 | `browser_requests` | 过滤是 URL 子串 |
| 读响应 | `browser_response_body` | 只看调用之后的响应 |
| 构造特殊输入 | `browser_eval` | 优先用页面自己的能力（fetch + 已登录态） |
| 读源码定位根因 | `grep` / `file_read` | 有源码时**必须**定位到文件行号 |

**范围不设限，扩面才设限**。在 scope.md 声明的目标上，用什么手段都不拦——
爆破自己账号的密码、扫自己声明的端口、构造真实越权请求，都是正当验证。
**但不要扩到范围外**：不扫内网其它主机、不把授权目标当跳板。

「打多少次」也按这个判：证明「限流没生效」构造 5-10 次就够，写清次数即可；
真正的判据是「够不够证明」，不是「打得多不多」。打到一万次只说明还没想清楚要证明什么。

## 产物

```
<target>/security/
  scope.md              # 归属与范围（没这个就不开工）
  findings/F-*.md       # 每个洞一份
  evidence/             # 截图与原始请求响应
```

`<target>` 是项目根（如 `projects/qx`）。目标不是本地项目时用 `projects/_redteam/<slug>/security/`。

**收尾必须写一句总数**：`N 个 Finding（高危 a / 中危 b / 低危 c），M 类不适用`。
