# Pixelorama 精灵图处理

把 AI 出的那张"看着像精灵图"的图，变成**真正能播的帧序列**。

## 一、先判断该不该用它

| 你的处境 | 用什么 |
| --- | --- |
| 要从零造一只桌宠（出图 + 打包 + 安装） | **pet-creator** |
| 手上已有一张图，要切成干净帧 | **本技能** |
| 只想出图，不处理 | `image_generate` |
| 想在 Pixelorama 界面里手工修 | 打开 Pixelorama GUI，本技能不管 |

`pet-creator` 自己的 `run.ts` 用 sharp 做像素处理；本技能是**同一步骤的更强替代**——
切片按真实内容边界而不是固定网格。两者不冲突。

## 二、前置（缺了会直接报错，报错里有安装指引）

- **Godot 4.7.x**（Pixelorama v1.2.3 要求 4.7.2，旧版打不开）
- **Pixelorama 源码目录**（含 `project.godot`），且**做过一次资源导入**：
  `godot --headless --path <目录> --import`

第一次跑之前**先 `probe`**，它会告诉你缺什么、去哪儿装。

## 三、标准流程

### 第 1 步：probe（别跳过）

```
execute_skill({ id: "pixelorama", params: { action: "probe" } })
```

返回 `ok: false` 时，把 `error` **原样转述给用户**——里面有下载地址和放置路径。
别自己编一个"环境已就绪"。

### 第 2 步：先看再切

```
execute_skill({ id: "pixelorama", params: { action: "analyze", file: "<图的绝对路径>" } })
```

看三个数：

| 字段 | 怎么读 |
| --- | --- |
| `has_alpha` | `false` ⇒ 必须抠底，否则切片一定不对 |
| `distinct_colors` | 几万 ⇒ 照片感。要像素画就加 `colors` |
| `box` | 等于整图尺寸 ⇒ 内容撑满了，角色很可能**越界** |

### 第 3 步：clean（常用的就这一个）

```
execute_skill({
  id: "pixelorama",
  params: {
    action: "clean",
    file: "<图的绝对路径>",
    outDir: "<输出目录>",
    colors: 24              // 可选：量化到 24 色
  }
})
```

参数全表：

| 参数 | 说明 |
| --- | --- |
| `file` | 输入图（**绝对路径**） |
| `outDir` | 输出目录（**绝对路径**） |
| `mode` | `auto`（默认，SmartSlicer）/ `grid` |
| `cols` / `rows` | `grid` 模式必给 |
| `colors` | 量化目标色数，建议 16–32。不给就保留原色 |
| `canvas` | `{w, h}`，指定输出画布；不给就按最大帧自适应 |
| `tol` | 抠底容差 0–765，默认 60 |
| `bg` | `[r,g,b]` 指定背景色；**默认自动估计，别乱传** |
| `prefix` | 输出文件名前缀，默认 `frame` |

## 四、怎么读结果（这里是判断力）

### `count` 不等于你预期的格数，通常**不是**工具的错

AI 出的图经常"角色撑破格子"，四格连成一片。这时 SmartSlicer 会如实报 `count: 1`
——它是**对的**，那张图真的只有一个连通区域。

**判据**：`count` 明显偏少、且 `source_rects[0]` 接近整图尺寸 ⇒ 角色连成一片。

处置顺序：

1. 先用 `mode: "grid"` + `cols/rows` 硬切，看每帧是不是残缺的
   （残缺 = 确认连成一片，硬切救不回来）
2. **重出那张图**，提示词里强调"四格之间必须有明显间隙、角色不得触碰格子边界"
3. **别在参数上硬凑**——切坏了比切不开更糟

### `removed_pct` 多少算正常

背景占比。2×2 四格通常 70–80%。

- **> 95%**：容差太大，把角色也吃掉了 → 调小 `tol`
- **< 40%**：背景没抠干净，或这图本来就不是"角色占小部分"的构图

**交叉验证**：`analyze` 报的 `content_pct` 应与 `100 - removed_pct` 很接近。
实测一组 27.53% vs 27.55%——两者算法独立（色距 vs 泛洪），吻合即为抠对了。

### `colors` 该给多少

实测一张 AI 出图：量化前 **17517 色**，`colors: 24` 之后 **24 色**，
而**包围盒一模一样**（446×370 @ (0,18)）——量化不啃轮廓。

- **16–32** 是像素画的常见区间。太少（< 8）会丢明暗层次，角色糊成一团。
- 返回的 `colors_after` 比 `colors` 略少是**正常的**（中位切分的空盒 + 取平均时撞色），不是失败。
- 调色板是**所有帧共用一套**的，帧间不会跳色。这是刻意设计，别改成逐帧量化。

## 五、失败怎么退

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| `找不到 Godot` | 没装或路径不对 | 照 `error` 里的地址下载，用 `PIXELORAMA_GODOT` 指过去 |
| `找不到 Pixelorama` | 没有源码目录 | git clone，**并做一次 `--import`** |
| `抠底后没找到任何内容` | 容差过大把角色也吃了 | 调小 `tol`；确实知道底色才传 `bg` |
| `Godot 没有返回结果标记` | 执行器编译失败 | 看 `godot_output_tail`，多半是执行器引用了带 autoload 的类 |
| `尺寸不能被 N×M 整除` | grid 模式硬要求 | 换 `mode: "auto"`，或用能整除的行列数 |

**绝不**为了让它"能跑通"而放宽判据或手改产物——切坏的帧比切不开更糟，
它会在客户端里一帧一帧地闪。

## 六、调用开销（影响你怎么组织步骤）

**每次调用 = Godot 冷启动约 3.7 秒**，而命令本身执行接近 0ms。

所以要连做几步时：

- ✅ `clean` 一次做完（抠底+切片+归一化+量化+导出）
- ❌ `cutout` → `slice` → 再导出（三次启动 ≈ 11 秒）

`probe` 的返回里有 `total_ms`（墙钟总时间，含启动）和 `elapsed_ms`（只算执行），
前者才是你要考虑的。
