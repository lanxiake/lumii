# 我让 AI 自己登录小红书发了篇长文，背后这套"操控浏览器"的技术值得说道说道

> 系列：《人人都能用AI写程序》番外·自动化篇
> 适合读者：好奇"自动发帖"怎么实现的普通人，以及想做浏览器自动化的开发者
> 阅读时间：约 14 分钟

---

<!-- IMAGE:01 type=cover prompt-ref=images/prompts.md#cover -->

先讲个我前两天真实干成的事。

我想把一篇几千字、配六张图的长文发到小红书。按平常的做法，得自己登录、点"写长文"、一段段贴文字、一张张传图、调封面、选排版模板……前后小半个小时，纯体力活。

这次我没动手。我让 AI 自己打开浏览器，自己登录小红书创作中心，自己把文字填进去，自己把六张图插到正确的段落之间，自己上传封面，最后停在发布按钮前等我点头。

全程我只做了两件事：把文章丢给它，最后确认一下预览。

做成之后我回过头想：这件事看起来像"外挂"，但它用的全是浏览器自己提供的、光明正大的能力。今天就借这篇文章，把"让程序操控浏览器"这件事讲清楚——**前半段给所有人看，后半段给想自己动手的开发者看**。

---

## 一、先破个误会：这不是"外挂"，是浏览器自带的"遥控接口"

很多人一听"程序自动操作浏览器"，第一反应是黑客、是外挂、是破解。

其实完全不是。

你每天用的 Chrome、Edge 浏览器，本身就内置了一个**给程序用的遥控接口**，官方名字叫 **CDP（Chrome DevTools Protocol，Chrome 开发者工具协议）**。

听着拗口，我用个类比你立刻就懂：

> 你家的智能电视，除了用遥控器按按钮，还能用手机 App 遥控对吧？手机 App 之所以能控制电视，是因为电视厂商**主动开放了一个遥控接口**。CDP 就是浏览器厂商开放的"遥控接口"——平时给程序员调试网页用，我们拿它来做自动化。

所以这套东西**不破解、不注入、不偷数据**，就是正大光明地用浏览器自己给的遥控器。你按 F12 打开的那个"开发者工具"，背后用的就是同一套协议。

<!-- IMAGE:02 type=concept prompt-ref=images/prompts.md#remote -->

![浏览器自带的遥控接口](images/02-remote.png)

明白这一点很重要：**自动化的第一原则，是尽量像真人一样用浏览器，而不是绕过它。** 后面你会看到，凡是想"抄近路"绕过浏览器的地方，几乎都会踩坑。

## 二、第一个坑：为什么"假装点击"打不开文件选择框

我先填文字，很顺利。但一到"插入图片"这一步，卡住了。

我的第一版思路很自然：在网页里找到那个"图片"按钮，用代码喊一声"点击！"。

结果——按钮确实有反应，但**该弹出来的"选择文件"对话框，死活不出来。**

我查了半天才搞明白原因，这背后是浏览器一条非常重要的安全规则：

> **只有真人亲手触发的点击，才被允许打开文件选择框、调用摄像头、申请通知权限这些敏感操作。**

浏览器内部给每一次点击都盖了个章，分两种：

- **真人点的**：盖"可信"章（业内叫 user activation，用户激活）
- **代码喊的**：盖"合成"章

代码用 `click()` 喊出来的点击，盖的是"合成"章。浏览器一看："哦，是程序自己喊的，不是人点的，那像'打开文件框'这种敏感操作，不准。"

这个设计其实是保护你的——不然任何一个网页都能在你不知情时偷偷弹窗让你传文件、开摄像头了。

<!-- IMAGE:03 type=concept prompt-ref=images/prompts.md#trusted -->

![真人点击才被盖上"可信"章](images/03-trusted.png)

那怎么办？答案是：**别假装点击，要让浏览器以为这是真人在点。**

CDP 提供了一个更底层的能力：直接告诉浏览器"鼠标移动到了这里、按下了、松开了"——模拟一套完整的真实鼠标动作。这套动作盖的是"可信"章。文件框，这就乖乖弹出来了。

**这是整件事最关键的一个认知：自动化不是"调用网页的函数"，而是"模拟一个真人的物理操作"。** 越往这个方向想，坑越少。

## 三、第二个坑：图片"塞"进去了，却显示不出来

文件框能打开了，我又遇到第二个怪事。

小红书的长文编辑器，用的是一种叫 **富文本编辑器**的东西（具体是 ProseMirror/TipTap 这一类）。你可以把它理解成一个"特别有脾气的文档区域"。

我一开始想抄近路：既然图片要显示在编辑器里，我直接用代码往那块区域里"塞"一个图片标签不就行了？

塞进去了。页面上**当时**也确实看到图了。但只要一保存、一刷新，图片就消失了，像没发生过一样。

为什么？因为这类编辑器**不认页面上的样子，只认它自己心里那本账。**

> 打个比方：你以为编辑器是块白板，谁都能上去画。其实它更像一个**有强迫症的记账员**——屏幕上显示什么，完全由他手里那本账本决定。你偷偷在白板上画了张图，他扭头一看账本上没这条记录，"唰"地就把你画的擦了。

所以正确做法不是去白板上画，而是**走记账员认可的正规流程**：像真人那样点工具栏的图片按钮、通过文件框选图、让编辑器自己把这张图记进账本。这样保存、刷新都还在。

这条经验可以推广到一句话：**碰到"现代网页应用"，别去直接改它显示的内容，要去触发它自己的操作流程。** React、Vue 这些框架做的页面，全是这个脾气。

## 四、第三个坑：图标按钮没有文字，怎么稳定地找到它

还有个细节挺有意思，顺手讲讲。

工具栏上那个"插入图片"的按钮，是个纯图标，没有任何文字。而且它的位置、顺序，平台随时可能调整。我要让程序每次都能准确找到它，不能靠"从左数第 8 个"这种脆弱的办法——平台一改顺序就废了。

我最后用的办法是：**认图标本身的"画法指纹"。**

每个图标其实是一段矢量绘图指令（SVG path），描述"先抬笔到哪、再画条线到哪"。这串指令对每个图标几乎是唯一的，就像指纹。我让程序去匹配这串指纹，不管按钮排第几、有没有文字，都能稳稳认出"这就是图片按钮"。

> 类比：在一群没戴工牌的人里找某个人，靠"站第几位"不靠谱（队形会变），靠"指纹"才靠谱。图标按钮也一样。

这种"靠稳定特征、不靠位置"的思路，是写自动化脚本能不能长期稳定运行的分水岭。

## 五、把图片放在"对的段落"，而不是全堆在结尾

到这里图能传上去了，但又有个体验问题：六张图全挤在文章最末尾，图文对不上。

我要的是——**第一张图在"谁该重启"那段后面，第二张在"定目标"那段后面**，各就各位。

解决思路也很朴素：**插图前，先把光标移动到目标段落，再插。** 就像你在 Word 里要在某句话后面贴图，得先把鼠标点到那句话后面一样。程序里我用"先定位到锚点文字、把光标移过去、再走插图流程"的方式，让每张图都落在它该在的段落。

我给每张图配了一个"锚点"——目标段落里的一小句话。程序找到这句话，把光标挪过去，再插图。图就乖乖待在对的位置了。

## 六、最后一个反直觉点：封面不在正文里

小红书长文有个容易踩的设计：**封面图不是正文的第一张图，而是要在"一键排版"那一页单独上传的。**

我一开始把封面也当成正文图插进去了，结果发布页的封面区还是空的。后来才发现，封面入口藏在排版页**最左边那张竖版预览**上——鼠标悬停上去，下面才浮出"从本地上传"按钮，走的是和正文插图同一套文件框流程。

这种"功能藏在 hover 浮层里"的设计，是 RPA（流程自动化）里最常见的硬骨头之一：**你不先模拟鼠标移上去，那个按钮根本不存在于页面上。** 又一次印证了前面那句话——尽量像真人一样操作。

## 七、给开发者：这套技术栈到底长什么样

前面是给所有人看的"原理版"。这一节往下挖一层，给想自己动手的同学。不想碰代码的读者可以直接跳到第八节。

**1. CDP 是怎么连上的**

CDP 本质是一套 **基于 WebSocket 的 JSON-RPC**。浏览器带 `--remote-debugging-port=9222` 启动后，访问 `http://127.0.0.1:9222/json` 能列出所有标签页，每个标签页给一个 WebSocket 地址。连上去之后，你发的每条消息长这样：

```json
{ "id": 1, "method": "Input.dispatchMouseEvent",
  "params": { "type": "mousePressed", "x": 100, "y": 200, "button": "left" } }
```

发一条带自增 `id` 的请求，浏览器回一条同 `id` 的响应，纯异步。整个自动化就是把这些原子命令编排起来。

**2. 可信点击：三个事件缺一不可**

打开文件框必须是带 user activation 的"可信"点击。用 `Input.dispatchMouseEvent` 依次派发 **mouseMoved → mousePressed → mouseReleased** 三个事件，模拟一次完整的真人点击。只发 pressed/released、不先 moved，部分页面也会判定异常。

**3. 文件选择器拦截三连**

这是插图的核心套路，记下来能少走很多弯路：

```
Page.setInterceptFileChooserDialog(enabled=true)   // 先开拦截
  → 可信点击触发 Page.fileChooserOpened 事件        // 拿到 backendNodeId
  → DOM.setFileInputFiles(backendNodeId, [本地路径]) // 直接喂文件
```

这样**不会弹出操作系统原生的文件对话框**（原生弹框 CDP 是控制不了的），整个过程全自动。上传成功后，图片在编辑器里表现为 `blob:` 开头的 URL。

**4. 为什么不能直接改 DOM**

ProseMirror/TipTap 这类编辑器维护一份自己的文档模型（document model / state），渲染出来的 DOM 只是这份 state 的投影。你直接 `appendChild` 改 DOM，下一次 state 重新渲染就把你的改动覆盖了。正确做法是触发它认可的输入路径（这里就是走工具栏 + 文件框），让改动进入它的 state。

**5. 按 SVG path 签名定位图标按钮**

图标按钮无文字、顺序不稳定，用文本或 nth-child 都脆。改为遍历候选按钮、读其内部 `<svg><path d="...">` 的 `d` 值做签名匹配（取一段唯一前缀即可），再用下标做兜底。这是长期稳定的关键。

**6. 锚点插图（in-flow placement）**

插图前用 `Range` + `Selection` 把光标定位到锚点文字所在的文本块（支持 top/before/after），再走插图流程，图片就落在对应段落而非全堆末尾。锚点用"目标段里的一小句原文"来匹配，比记录节点索引稳。

> 这套小红书长文发布的完整脚本（连接、可信点击、文件框拦截、锚点插图、封面上传）我已经沉淀成一个独立技能，关键经验也写进了项目记忆，换台电脑也能复现。

## 八、跳出细节：两种自动化范式，选哪个

做完小红书这套，我顺手对比了一下"发微信公众号"——这篇文章本身就是用程序发到公众号草稿箱的。但它走的是**完全不同的另一条路**，对比起来特别有启发：

<!-- IMAGE:06 type=infographic path=images/06-compare.png -->

![浏览器自动化 vs 官方API：两种范式](images/06-compare.png)

| 维度 | 浏览器自动化（小红书） | 官方 API（微信公众号） |
|------|----------------------|----------------------|
| 本质 | 模拟真人操作界面 | 直接调后台接口 |
| 前提 | 平台没开放接口，只能"用界面" | 平台开放了官方 API |
| 稳定性 | 页面一改版就可能失效 | 接口稳定，版本兼容好 |
| 维护成本 | 高，要盯着选择器 | 低，按文档来 |
| 适用场景 | 没有 API 的平台、个人自动化 | 有开放平台的正规对接 |

**结论很简单：有官方 API 就用 API，没有才退而求其次用浏览器自动化。**

浏览器自动化是"没有路时自己蹚出一条路"——强大，但脆弱，平台改个按钮你就得跟着改。官方 API 是"走平台修好的高速路"——稳，但你只能去平台允许你去的地方。

这两种范式背后是一个更大的判断：**做自动化前，先花十分钟确认对方有没有开放接口。** 这一步能帮你省下后面几天的维护成本。

## 九、开发者可复用要点（建议截图）

把这套踩坑浓缩成一张速查表：

1. **能用官方 API 就别用浏览器自动化**——先查有没有开放平台。
2. **把自动化想成"模拟真人物理操作"**，不是"调网页函数"。
3. **敏感操作（文件框/摄像头）必须用可信事件**——CDP 派发真实鼠标事件，别用合成 `click()`。
4. **文件上传记住三连**：开拦截 → 可信点击拿 backendNodeId → setFileInputFiles 喂文件。
5. **现代框架页面（React/Vue/ProseMirror）别直接改 DOM**，要触发它自己的输入流程。
6. **定位元素靠稳定特征**（SVG 签名、文本锚点），少靠位置下标。
7. **hover 才出现的按钮**，先模拟鼠标移上去再点。

## 本篇小结

三句话，可以截图保存：

1. **CDP 不是外挂，是浏览器自带的遥控接口**——光明正大地用。
2. **自动化的最高原则是"像真人一样操作"**——抄近路绕过浏览器的地方几乎都是坑。
3. **有 API 走 API，没 API 才浏览器自动化**——动手前先确认对方开没开接口。
