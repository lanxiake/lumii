# 数字处理

稿子里数字多的时候读这个。三层筛，按顺序过。

## 第一层：读者有没有感知？（先删）

**这一层最容易漏。** 不是所有精确数字都该念出来——**听了没法拿它做任何判断的，直接删掉。**

| 数字 | 有没有感知 | 处理 |
|---|---|---|
| `322 × 782`（面板像素） | ✗ 听完毫无概念，还打断节奏 | 删 |
| `237 × 132` | ✗ 同上 | 删 |
| `274 个文件` | ✗ 谁在意多少个文件 | 留图文层，别进旁白 |
| `110 个元素` | ◯ 有感知，但"元素"是内部说法 | 改说"一百一十项设置" |
| `43.5 s` / `16.7 s` | ✓ 能判断"快不快" | 保留 |
| `485 个 issue` | ✓ 能判断"维护活不活跃" | 保留 |
| `31,001★` | ✓ 能判断"有多少人认" | 保留 |

**判据：这个数字，读者听了能拿它做什么判断？答不出，就别念。**

**注意"感知度"和"精确度"是两件事。** `569ms → 936ms` 要精确（要被逐条核对），而 `322 × 782` 该删（读者无感）。两者不矛盾，不要因为它精确就舍不得删。

## 第二层：分精确层和口播层

**精确层**——表格、数据卡、元信息、许可证条款、测试数据：

> 一个数字都不许动。

**口播层**——念出来的旁白：

> 真人报数，该圆的圆、该简的简。

| 精确层 | 口播层 |
|---|---|
| `43.5 s` | 安装依赖四十三秒 |
| `16.7 s` | 构建十七秒 |
| `31,001★` | GitHub 三万一千星 |
| `485 个 open issue` | 仓库里还堆着四百八十五个待处理 issue |
| `25,873 行` | 两万六千行代码 |
| `0.53 MB` | 压缩之后只有 0.53 兆 |

**铁律：口播层每一个口语数字，必须能从精确层推出来。** 推不出来就是编。

**另一条约束：原稿已经念得顺的数字，别去动它。** 分层是用来解决"念不顺"的，不是把所有数字都模糊一遍。把"一点三八兆"改成"1.4 兆"是主动丢精度。

判断顺序：**先问"这个数字现在念得出来吗"。念得出来，就放过它。**

## 第三层：写法

| 类型 | 写法 | 例 |
|---|---|---|
| 带小数 | 阿拉伯数字 | `1.38 兆`、`0.53 兆`（不写"一点三八兆"） |
| 带英文单位／符号 | 阿拉伯 + 符号 | `569ms`、`936ms`、`57%` |
| 容量（兆 / KB） | 阿拉伯数字 | `源码包 37 兆`、`压缩之后只有 0.53 兆` |
| 整数秒 | 中文 | `安装依赖四十三秒`、`构建十七秒` |
| 个 / 项 / 行 / 星 | 中文 | `两万六千行`、`一百一十项`、`三万一千星` |

一句话：**小数和带符号的用阿拉伯，纯中文量词用中文。**

## 数字挂靠的对象也要准

数字对，但挂错了对象，一样是错。

| ✗ | ✓ | 为什么 |
|---|---|---|
| 三十七兆**代码** | **源码包** 37 兆 | 那是仓库拉取体积，不是代码本身的量 |
| 两万六千**行代码**（原值 2.6 万行） | 两万六千行代码 | 这个没问题；但若原值是 25,873，说"两万五千多行"更准 |
| 一百一十个**元素** | 一百一十**项设置** | "元素"是开发者说法，读者看到的是"能调的项" |

## 档位选择（要用户拍板）

这条会动数字精度，用之前问用户一句：

- 要发**严谨评测**、要能被人逐条核对 → **全精确档**，口播也念"43.5 秒"
- 要**口播流畅**、本来就是听个大概 → **分层档**，精确层一个不许动，且口语数字要能标出出处

**默认分层档。**

## 交付时怎么标

在交付文档里给出这两张表，让用户能核对：

1. **数字分层对照表** —— 精确层原值 ↔ 口播层写法 ↔ 出处段
2. **被删掉／弱化的数字** —— 原值 → 为什么念了没用

第二张表最容易被忽略，但它是"我删了东西"的交代，少了它用户会以为你漏了。
