## 实验 A：轻量事件去重（`event_dedup.py`）

### 它在复现什么

生产系统（GDELT / Event Registry / NewsBlur）的事件层最小骨架：

1. 标题归一化（去栏目前缀、去转载注记、去空白标点）
2. 集合相似度 + 双时间约束：文章与事件最近一条 **≤18h**、事件存活 **≤36h**
3. **两遍聚类**：模拟定时抓取，每轮 6 篇。第一遍拿新稿去比已有事件（只比事件侧**最近 3 篇**），第二遍把本轮剩下的两两建边取连通分量 → 新事件
4. 阈值扫描 + 三种相似度表示对照

### 数据长什么样

`news_sample.json` 里 45 条，每条带 `truth`（真实事件号）和 `expect`（`merge` / `miss-time` / `miss-local`）：

| 类型 | 例子 | 目的 |
|---|---|---|
| 同事件多来源变体 | `A01`~`A05`（GPT-5 发布）、`C01`~`C04`（央行降准） | 测召回 |
| 归一化后全等的转载 | `A01`↔`A02`、`E01`↔`E04` | 说明这是 **L1 文档层**的活，不靠事件层阈值 |
| 强本地语境稿（`miss-local`） | `B04`「出小区步行 8 分钟到地铁站」、`B05`「通勤缩短 25 分钟」 | 生产系统已知会漏，且**选择接受** |
| 晚到的后续稿（`miss-time`） | `A06` 晚一天、`A07` 晚 40 小时 | 让 18h / 36h 两个窗口各自被触发 |
| 同主题不同事件（干扰项） | 降准 vs 降准传闻澄清、台风登陆 vs 新台风将生成、财报 vs CEO 辞职、夺冠 vs 庆祝人群 | 测误并 |

C:/Users/75791/.lumii/runtimes/bin/python event_dedup.py --metric jac3

### 预期输出（本机实测）

```
阈值      事件数     应合并对     已合并     漏并      误并      召回率     pass1/2/新种       精确率
0.50     23       46         38       8        0        0.83     11/11/23         1.00
0.60     27       46         30       16       0        0.65     9/9/27           1.00
0.70     29       46         28       18       0        0.61     9/7/29           1.00
0.80     32       46         19       27       0        0.41     6/7/32           1.00

同一批数据、阈值都固定 0.70，只换相似度表示 —— 阈值是不可移植的
tok      29         28         0.61     1.00
jac3     43         2          0.04     1.00
ovl3     40         6          0.13     1.00
```

最后一列 `pass1/2/新种` = 第一遍吸收进已有事件的篇数 / 第二遍并进新种子的篇数 / 成为新事件种子的篇数，三者相加等于总篇数（45）。注意"新种"数恒等于事件数——每个新事件都由一颗种子开始。

### 你应该观察到什么

1. **同一份数据、同一个阈值 0.7，三种表示给出 29 / 43 / 40 个事件。** 这就是"0.7 是 NewsBlur 在它自己的英文表示上的存活值"的含义。别把任何阈值当常数。
2. **每个事件都挂着 N 个来源，没有任何一篇文章被删。** 看聚类明细那一节，`[事件 E002] 5 个来源 truth=G1`。
3. **漏并单调，误并不单调**：阈值 0.5→0.8，漏并从 8 涨到 27，误并一直是 0。想看到误并，直接跑 `--threshold 0.3`：汇总行给出 `合并 46，漏并 0，误并对 7`，明细里两个簇被点名——`E005 truth=D6/G7`（把另一品牌电池召回并进了车窗开关召回）、`E010 truth=D7/G6`（把庆祝人群并进了夺冠事件）。这就是**连通分量的传递闭包**（链式串并），也是生产系统为什么要"事件侧只比最近 3 篇 + 存活窗口"来掐断链条。
4. **设计内漏并是好事**：`B04/B05` 单列成两个单来源事件，`A06/A07` 被时间窗拦在 GPT-5 事件外。脚本会单独列一节解释每一条为什么合并不了。
5. **第一遍只吸收 20%**，远低于 NewsBlur 说的 70–80%。因为这份模拟每轮只来 6 篇、事件还没养肥。把脚本里 `round_size` 调大（比如 20），第一遍份额会明显上升——这就是稳态增量的样子。

### 已知偏差（不是 bug，是需要你知道的口径）

- **指标是"对"级**（pair-level）：46 个"应合并对"里有多少被合到一起，不是簇级 F1。
- **归一化去掉了所有空白**：中文没有词边界，保留空格会让 `GPT-5 发布` 和 `GPT-5发布` 变成两个分布；代价是英文词边界消失（`openai` 与 `AI open` 的 n-gram 会串味）。
- **`jac3` 模式在中文标题上会塌**（45 条只合出 2 对）——这是刻意的对照组，别当成"脚本坏了"。真实系统靠 embedding 把这一段差距补上，而 embedding 需要第三方库，所以离线实验里用 `tok`（词级重合系数）替代。
- **`tok` 模式有长度护栏**：少于 4 个 token 的标题没有投票权，否则「快讯」两个字能把半个 feed 吸走。
- **事件侧用"最近 3 篇里取最大相似度"**，是"对最近 3 篇做向量滑动平均"的零依赖替身，语义同向（旧稿失去投票权），但比滑动平均**略宽松**。

## 实验 B：规则引擎 + 命中集预览（`rule_engine.py`）

### 它在复现什么

用户偏好规则的**四件套** + 写操作的**四条不变式**（后者借自 Terraform plan/apply、CloudFormation change set、ArgoCD、Dependabot）：

| 件套 | 实现 |
|---|---|
| ① 规则对象化 | `{id, field, op, value, action, priority, log}` + 入库校验 |
| ② 命中集预览 | 每条规则命中**哪几条**资讯，纯计算、不写盘 |
| ③ 显式优先级链 | 按 `priority` 裁决；**同优先级动作相反时不自动裁决**，落兜底并上报 |
| ④ 规则日志 | 追加式 `rule_log.jsonl`，记 `plan_hash`／决策规则／裁决轨迹 |

| 不变式 | 实现 |
|---|---|
| 预览零副作用 | `preview` 一个字都不落盘 |
| 执行被审过的那一份 | `plan` 固化出带 `plan_hash` 的计划；`apply` 双重校验：**改一个字符**或**规则/数据漂移**都拒绝（退出码 2） |
| 结果写回同一条记录 | 日志按同一个 `plan_hash` 追加 |
| 可回滚或可追溯 | 日志里有完整裁决轨迹，能还原"这条为什么被静音" |

### 跑起来

```bash
C:/Users/75791/.lumii/runtimes/bin/python rule_engine.py              # 完整演示（校验→预览→计划→应用→日志→盲选对照）
C:/Users/75791/.lumii/runtimes/bin/python rule_engine.py preview      # 只看，不写盘
C:/Users/75791/.lumii/runtimes/bin/python rule_engine.py plan         # 生成 plan_preview.json
C:/Users/75791/.lumii/runtimes/bin/python rule_engine.py apply plan_preview.json
C:/Users/75791/.lumii/runtimes/bin/python rule_engine.py blind        # 没有预览的世界
C:/Users/75791/.lumii/runtimes/bin/python rule_engine.py demo-invalid # 坏规则怎么被挡在门外
C:/Users/75791/.lumii/runtimes/bin/python rule_engine.py log --tail 20
```

### 数据里的三处冲突

- **宽规则吞精确规则**：`R3 科技类静音(p30)` 2026-07-03 建，`R1 AI 垂直源直接推(p10)` 2026-08-11 建 → 优先级链让 R1 赢，插入顺序让 R3 赢。
- **平局**：`R4 医保必须推(p5)` 与 `R5 解读稿静音(p5)` 同时命中 `N22`，动作相反 → 程序**不猜**。
- **降权规则**：`R6 低质营销源静音(p40)` 命中 `N09/N12/N25`，最低优先级（谁都能覆盖它）。

### 预期输出（本机实测）

- 命中集：`R3` 7 条、`R2` 11 条、`R1` 4 条、`R4` 4 条、`R6` 3 条、`R5` 1 条。
- 冲突 7 条（`N01 N02 N03 N04 N06 N22 N29`），其中 6 条由优先级链裁决，**`N22` 平局未决**。
- 汇总：30 条 → 推 26 / 静音 4；10 条走兜底；`plan_hash=a1317e23fa046c21`。
- 篡改计划里一个字符 → `拒绝执行：计划文件本身被改动过（内容指纹对不上存好的 plan_hash）`，退出码 2。
- 只把 `R3` 的优先级从 30 改成 1 再 `apply` 旧计划 → `拒绝执行：规则或资讯池在计划生成后发生了变化（漂移）`，退出码 2。
- `blind`：同一份规则，30 条里 **6 条决策不同**（全是 R3 把 AI 稿静音），平局提示消失。
- `demo-invalid`：未知字段 `words`、拼错的 `startswidh`、非法动作 `hide`（外加 `in` 给了字符串）三条规则全部当场拒绝。

### 重点：没有预览，用户会怎样被"训歪"

`blind` 模式演示的就是市面上最常见的实现——规则按插入顺序、首条命中即生效，没有预览、没有冲突报告、没有日志。请照这个顺序看：

1. 用户 7 月加了「科技类静音」，8 月明确说「这几个 AI 源要推」。盲选实现里 **R1 一次都没生效**（被更早的 R3 吞掉）。用户在 feed 里看到的现象只是"AI 稿还是没几条"。
2. 用户能拿到的反馈信号只有**整体 feed 变好／变坏**——而整体分数是 6 条规则叠加的输出。一次只能改一条，改完看不出因果。于是他的合理反应是**再加一条更狠的**（所有科技稿一律静音），下个月再加一条反向的（OpenAI 的还是要推）。规则库越训越极端、互相打洞，最后没人敢删。
3. 平局资讯（`N22`）静默落进 feed。用户看到"我明明设了不看的还推给我"，代价是**对整个规则系统失去信任**——而它只需要一行"平局未决，请确认优先级"就能解释。

所以 `preview` 的价值不是"方便"，而是**让反馈信号和规则之间出现可归因的通路**：这条规则命中这 4 条、遮蔽在那里、和这条平局。有了这条通路，用户才可能做对一次修改；没有它，任何"从用户行为学习"的系统都会被训成规则的垃圾场。

## 三个扩展练习

1. **换上你自己的标题**：把 `news_sample.json` 换成你业务里 30~50 条真实标题（同 `id/title/source/published/truth/expect` 字段），重新跑阈值扫描。你会看到误并立刻出现——那一刻你才真正需要时间窗和实体一致性。
2. **给规则加"作用域"**：给规则加一个 `scope: "global" | "project:x" | "channel:weixin"` 字段，自己定覆盖顺序，然后回答：作用域链和优先级链冲突时谁赢？（这正是全局偏好 vs 项目偏好 vs 本次会话的真实难题。）
3. **把两遍聚类改成流式**：把 `round_size` 设为 1（每轮只来一篇），观察第一遍吸收比例和事件数怎么变。生产系统的 70–80% 是在这种"事件已经养肥"的稳态下得到的。
