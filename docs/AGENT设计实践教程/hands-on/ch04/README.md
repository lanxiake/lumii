## 实验 A：工具选择混淆离线实验

### 目标
用合成数据观察本章核心论断的两个侧面：
1. **语义干扰**——近似工具同时暴露时，选择错误集中在"同簇兄弟工具"之间；
2. **两个杠杆各管一段**——收敛（合并）治准确率，渐进披露治 token，互不替代。

### 运行

```bash
python tool_confusion_experiment.py            # 离线启发式模式（默认）
python tool_confusion_experiment.py --json out.json   # 另存机器可读结果
python tool_confusion_experiment.py --mode llm        # 真实模型模式（见下）
```

真实模型模式：设置环境变量 `LLM_API_KEY`（或 `OPENAI_API_KEY`；可选 `LLM_BASE_URL`，默认 OpenAI 官方；`LLM_MODEL`，默认 gpt-4o-mini）。脚本会把每个配置的工具目录 + 用户请求发给模型，要求返回 `{"tool": ...}`，统计 top-1。任何调用失败都记为该题错误并打印警告，不会中断。

### 数据集
`tools_dataset.json` 内置 40 个合成工具：9 个语义簇（搜索×5、文件读写×7、记忆×3、笔记×4、消息×4、日历×3、翻译×2、摘要×3）加 9 个正交工具（shell、生图、天气、TTS、列目录、glob、grep、计时器、deep_research）。30 条请求覆盖其中 30 个 gold 工具，其余 10 个纯作干扰项——这正是真实工具面的样子：多数工具在任一时刻都只是噪声。

三个配置：
- **full**：40 个全量暴露（对照组）；
- **converged**：按簇收敛到 18 个带 `action` 参数的工具。注意 `deep_research`（成本是普通搜索的 10–30 倍）和 `broadcast_message`（高风险，需独立确认闸门）刻意**不合并**——收敛不等于无脑归并；
- **lazy**：渐进披露模拟——高频工具常驻 + 每题按词面检索 top-6 注入，token 按"平均每题实际注入的工具块"估算。

### 预期输出（本机 Python 3.12.10 实跑值）

```
配置                             工具数   token   top-1      同簇混淆
full(40 全量暴露)                   40    1443     83%         3
converged(18 收敛后)               18    1478     87%         0
lazy(渐进披露)                      40     622     83%         3
```

### 你应该观察到
1. **同簇混淆 3 → 0**：合并消灭的是"选错双胞胎"这个故障类本身（`read_file_head` 选成 `read_file_tail`、`calendar_find_free_slot` 选成 `calendar_list_events` 这类）。
2. **converged 的 token 没降**（1,443→1,478，微升）：词面合并根本不是省 token 的手段。省 token 的是"不加载不用的定义"——看 lazy 列，−57%，与 Anthropic 报告的 85% 属同一机制（按需发现）。两个杠杆正交，生产上应同时使用。
3. **lazy 的准确率与 full 完全持平（83%）、混淆原样保留**：渐进披露不治语义干扰；而且 gold 若没被检索进候选就直接失败——这就是 ToolRet（arXiv:2503.01763）警告的检索层风险，也是"高频工具必须常驻"的原因。
4. **改一个参数复现"收敛有代价"**：把 `tool_confusion_experiment.py` 里 `_short_desc` 的 `lim=44` 改成 `24` 重跑——收敛工具的成员描述被压得太狠后，top-1 会从 87% 掉到约 70%（实测 70%）。合并后的描述必须保留每个 action 的可区分关键词，否则"该走哪个工具族"本身就会选错。

### 诚实拆解（务必读）
- **启发式选择器是对 LLM 行为的粗糙模拟**。TF-IDF 词面重叠只用于让"候选集里有近似兄弟时会混淆"这一结构性现象在无 GPU、无 API 的环境下可复现，**不用于复现任何论文的数字**（论文数字见章节 §四，均另有出处）。个别错误会是词面伪影而非语义错误，例如 `r21`（微信发消息）被 `set_timer` 抢走——因为"晚到十分钟"撞上了"倒计时提醒"的字面。换成 `--mode llm` 跑真实模型，混淆形态会更接近生产（同簇语义干扰占主导，词面伪影消失），具体数值取决于模型。
- **converged 的 +4pp 有机械成分**：合并后 gold 从"某个具体工具"变成"某个工具族"，族级选择天然更容易。真实的代价转移是"选错工具 → 传错 action 参数"，本脚本的启发式模式不评估参数级正确率；想看参数级误差请用 `--mode llm` 并扩展解析 `args.action`。
- token 估算：中文≈1 token/字、英文词≈1.3 token 的粗估，只用于配置间相对比较。

## 实验 B：工具描述重写工作坊

### 目标
把 §6.1 的描述模板变成可执行的 10 项 checklist：命名、何时用、何时不用＋点名兄弟工具、参数契约、枚举与默认值、格式/单位/时区、调用示例、可行动错误信息、无含糊话、返回与截断契约。

### 运行

```bash
python description_lint.py            # 坏版 vs 重写版逐项对照
python description_lint.py --bad-only # 只诊断坏版（先盲打分再对答案）
```

### 内置材料
3 个刻意写坏的 schema：`process_data`（"处理各种数据…之类的"，上帝工具）、`search_stuff`（描述只有"搜索。"，同族工具零指引）、`notify`（渠道不明＋"等等。"＋错误信息只有 `error`）；以及重写版 `transform_csv` / `search_web` / `send_im_message`。

### 预期输出（本机实跑值）

```
process_data → transform_csv：1/10 → 10/10
search_stuff → search_web：    2/10 → 10/10
notify → send_im_message：     1/10 → 10/10
合计：坏版本 4/30 → 重写版 30/30
```

### 练习建议
1. 先 `--bad-only` 自己盲打分，和脚本对答案，看哪几项你平时会漏（通常是 03 与 08）。
2. 删掉重写版 description 里"如需 X 请用 …"半句，观察同族错误隐患如何在静态层面显形（03 项塌掉）。
3. 把三个重写版喂给实验 A 的数据集（替换同名工具），跑 `--mode llm` 对比重写前后 top-1——这就是 Anthropic"用 Agent 重写工具描述换 −40% 任务时间"那篇里流程的最小复刻。

## 已知边界
- 合成数据、离线启发式，结论只有方向性；量自己系统的工具面请用真实请求日志替换 `requests` 段（格式照抄即可）。
- `--mode llm` 会产生 API 费用；30 题 × 2 配置 ≈ 60 次调用，用 gpt-4o-mini 级别模型成本 < $0.1。
- 脚本在临时嵌入式 Python 3.12.10 上验证通过；未做逐版本回归，但只用了保守的标准库用法（无第三方依赖、无新语法），3.8+ 应当可直接运行。
