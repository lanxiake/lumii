## 一、这份指南为什么存在

本文档是「上下文压缩全场景测试」的完整复盘。那次测试要验证 5 件事：

1. 用 CLI 新建专用智能体模拟真实对话；
2. 测试用例覆盖**全部**压缩场景；
3. 测试记录能在对应 Agent 中看到；
4. 持续监控服务器日志、抓取关键日志；
5. 日志缺失就补日志并部署更新。

测试最终跑通了 5 个场景，**发现了 3 个真实缺陷**（单元测试/mock 永远发现不了的那种）。但也踩了不少坑——比如一开始以为"堆到 192K 就能测 summary"，结果 Proactive Prune 在 48K 先触发、tail 保护窗又挡掉了大部分内容，导致半天测不到目标场景。

这份指南把那次测试的**做法、踩坑、工具箱**沉淀下来，让后续测任何功能都更真实、更完整、更准确、更有改进意义。

## 二、用户 5 条测试要求的落地方法

### 要求 1：用 CLI 建专用智能体 → 隔离 + 真实

**落地做法**：
- 用 `clawith-cli` 或直接调 `POST /api/agents` 创建**专用测试 Agent**，不污染业务数据。
- 关键点：**绑定被测功能真正会用到的模型**。测压缩就用 256K 的 Qwen3.8-Flash-Next，而不是随便选个模型——否则测出来的阈值、行为都和真实使用环境不一致。

**本次做法**：建 `上下文压缩测试Agent`，`primary_model_id=88ddc1bb...（Qwen3.8-Flash-Next, 256000）`。

### 要求 2：覆盖全部场景 → 先读代码建场景矩阵，再测试

**落地做法**（这是最重要的一条）：
- **不要凭文档或直觉列场景**，先通读被测模块的代码，把**每一个分支**画出来。
- 每个分支 = 一个场景 = 一个独立的触发路径 + 一个可观测的日志关键词。

**本次做法**：读 `compression/` 全模块，得到 5 个场景：
| 场景 | 触发路径 | 关键日志 |
|------|---------|---------|
| Proactive Prune | tokens ≥ 48K | `[ProactivePrune] 剪枝成功` |
| Reclaim Gate | 回收 < 4K | `Reclaim Gate 拦截` |
| Full Compression | tokens ≥ 192K | `压缩完成 method=summary` |
| Overflow Recovery | 模型拒绝超窗 | `forced_recovery` |
| truncation 降级 | LLM 摘要失败 | `降级为截断摘要` |

**关键教训**：场景不是"功能点"而是"代码分支"。同一功能（压缩）有 5 个分支，只测"压缩发生了"等于只测了 1/5。

### 要求 3：测试记录能在 Agent 中看到 → 每个动作后验证落库

**落地做法**：
- 每条测试对话后，用 `GET /api/agents/{id}/sessions?scope=mine` 和 `.../sessions/{sid}/messages` 确认消息已落库。
- 前端对话历史 = `chat_messages` 表按 `conversation_id + created_at + sequence` 排序，只要落库就能在前端看到。

**本次做法**：测试 Agent 会话 `message_count` 最终 786+，所有 tool 轨迹都在 `chat_messages` 中可见。

### 要求 4：持续监控日志 → 时间戳 + 关键词，不盲目 tail

**落地做法**：
- **测试前记录时间戳**（`date '+%s %F %T'`），测试后用 `docker logs --since <时间>` 精确抓取，而不是一直 `tail -f` 大海捞针。
- 用 `grep -E '关键词1|关键词2'` 过滤压缩相关日志，每个场景一个关键词。

**本次做法**：每轮测试前后打时间戳，用 `docker logs --since 3m ... | grep -E 'ProactivePrune|ChainedMapReduce|压缩完成'` 定位。

### 要求 5：日志缺失就补 → 测试要敢于改代码并部署

**落地做法**：
- 测试前先 `grep` 一遍被测模块的日志点，看**每个分支是否都有日志**。
- 缺日志就补：在关键分支加一行 `logger.info`，部署后重测。
- 补日志是**测试活动的一部分**，不是额外工作。

**本次做法**：发现"摘要质量无法评估"（只有结果没有输入输出），补了 `摘要输入/摘要输出` 日志，部署后抓到了完整摘要质量。

## 三、六条核心方法论（铁律）

### 铁律 1：先读代码，再设计测试

**反面**：拿到需求直接开测，测了半天发现场景理解错了。

**正面**：通读被测模块代码，画出：
- 有哪些分支（if/else、异常、降级路径）
- 每个分支的触发条件（阈值、状态、异常类型）
- 每个分支的可观测信号（日志关键词、事件、DB 记录、指标）

**本次教训**：压缩模块有 `proactive_prune / summary / truncation / forced` 4 种 method，外加 Reclaim Gate、Rearm 跑道、小窗口地板。不读代码根本不知道 256K 模型的真实触发点是 `256000×0.75=192000`（小窗口地板强制 ≥0.75），也不会知道 Proactive Prune 在 48K 就先抢跑。

### 铁律 2：真实链路，不用 mock

- 用真实 WebSocket/HTTP 请求、真实模型、真实 DB，**禁止 mock**（本项目 CLAUDE.md 明确要求）。
- mock 测不出真实缺陷。本次 3 个缺陷全部来自真实链路。

### 铁律 3：触发不了就构造数据 / 用故障注入

正常对话堆不到 192K、也触发不了 context_overflow。两条出路：

1. **构造数据**：向 `chat_messages` 表插入结构化历史消息，让会话自然跨过触发阈值。
2. **故障注入**：context_overflow 这类"模型拒绝"场景，用 `POST /api/admin/observability/fault-injection/rules`（需 `CLAWITH_ENV=test` + platform_admin）一键触发，替代 SSH 手改环境变量。

**本次做法**：full compression 用 DB 种子历史逼近 192K；overflow 用 fault-injection。

### 铁律 4：抓真实数据，不靠估算

- token 估算（CJK 启发式、校准 tokenizer）和真实 `prompt_tokens` 有偏差。测试要抓 LLM 返回的**真实 usage**。
- 结论要基于真实日志里的数字（`原始 298849 tokens`、`节省 200734 tokens`），不是"我估摸着应该超了"。

**本次教训**：中间几轮明明"感觉"堆够了，实际 `prompt_tokens` 只有 11 万，就是估算和真实的 gap。

### 铁律 5：测试数据要有结构，能评估质量

- 测"摘要质量"用**有结构的文本**（每条含任务/行动/结果/文件/决策/待办），而不是纯乱码填充——乱码无法判断摘要是否忠实还原。
- 测试数据要能回答："这个功能的结果对不对、好不好"。

### 铁律 6：测试要能发现并推动修复 bug

- 测试的终极价值不是"通过"，是**发现缺陷并修复**。
- 发现 bug 后：定位根因 → 修复 → 重新部署 → 回归验证，闭环。

**本次成果**：发现并修复了 `ChainedMapReduce.fit_budget` 计算异常（导致摘要退化）、摘要模型 context_window 查表兜底不一致、Qwen thinking 模式导致摘要返回空。

## 四、踩坑清单（反模式，避免重犯）

| 反模式 | 表现 | 正确做法 |
|--------|------|---------|
| **只看文档不看代码** | 场景理解错、触发点算错 | 通读代码建场景矩阵（铁律 1） |
| **一次性堆数据** | 触发不了，还搞不清在哪一步断的 | 逐步累加，每步抓日志确认 token 增长 |
| **忽略前置分支** | 想测 summary，却被 Proactive Prune / Reclaim Gate 拦掉 | 理解代码执行顺序，知道谁先抢跑 |
| **忽略保护窗** | 以为堆够量就能触发，实际 tail 保护窗挡掉了大部分内容 | 读策略代码里的 budget_ratio 参数 |
| **用估算代替真实值** | "感觉超了" → 实际没到 | 抓真实 prompt_tokens（铁律 4） |
| **乱码填充数据** | 无法评估结果质量 | 用结构化数据（铁律 5） |
| **盲 tail 日志** | 日志量大找不到关键点 | 时间戳 + `--since` + grep 关键词 |
| **发现 bug 就停** | 只报 bug 不修复不复测 | 定位→修复→部署→回归闭环（铁律 6） |

## 五、可复用的测试工具箱

| 工具 | 用途 | 命令/入口 |
|------|------|----------|
| `clawith-cli` | 建 Agent、WebSocket 对话、查会话 | `clawith-cli chat send --agent <id>` |
| WebSocket 直连脚本 | 精确控制消息、抓 usage | 手写 `websockets` 脚本，发消息后打印 `prompt_tokens` |
| 文件 API | 造大文件喂给 read_file 堆上下文 | `PUT /api/agents/{id}/files/content?path=...` |
| DB 种子历史 | 逼真堆超长历史 | 容器内跑脚本插 `chat_messages` |
| 故障注入 | 触发正常无法触发的异常 | `POST /api/admin/observability/fault-injection/rules` |
| 运行时事件 | 看 compression_applied/skipped | `GET /api/observability/runtime-events?event_type=...` |
| 日志抓取 | 时间窗 + 关键词 | `docker logs --since <m> ... \| grep -E '...'` |

## 六、标准测试流程（可直接套用）

```
1. 读代码，画场景矩阵（每个分支 = 场景 + 触发条件 + 日志关键词）
2. 建专用测试 Agent（绑真实模型）
3. 检查日志覆盖，缺就补日志并部署
4. 逐场景触发：
   a. 自然触发（堆数据）
   b. 自然触发不了 → 构造数据 / 故障注入
   c. 每步记录时间戳 + 抓真实 token + 抓日志
5. 每个动作后验证落库（sessions/messages API）
6. 评估结果质量（结构化数据）
7. 发现 bug → 定位根因 → 修复 → 部署 → 回归
8. 产出测试报告（含发现的问题 + 遗留项）
```
