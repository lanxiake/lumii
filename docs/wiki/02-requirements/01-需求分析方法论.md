# 需求分析方法论

---

## 一、通用需求分析流程

### 1.1 问题定义阶段

**目标**：明确要解决的核心问题，避免「为做功能而做功能」。

**步骤**：
1. 用一句话描述当前痛点或用户诉求
2. 验证问题真实性：是否有代码证据、用户反馈、数据分析支撑
3. 明确不做的范围（Non-Goals），防止范围蔓延
4. 输出：问题陈述 + 现状事实核查清单

**参考实践**：多设备同步分析中，先通过 `~/.lumii` 目录扫描（1.7GB 中 .mtbot-vcs 占 615MB）量化问题，而非凭感觉假设。

---

### 1.2 需求采集阶段

**目标**：从多维度收集真实需求，区分「用户说的」与「用户真正需要的」。

**采集渠道**：
- 代码现状核查：逐行阅读现有实现，确认哪些能力已具备、哪些缺口真实存在
- 用户故事：从具体使用场景反推功能（如「用户在多台设备使用，希望工作空间自动流转」）
- 业界参考：调研同类项目的成熟方案，提炼可借鉴点
- 约束条件：技术栈限制、架构边界（如 `packages/pet-core` 不得依赖 React/Electron）

**参考实践**：记忆 + Wiki 设计中，先盘点 8 项现有资产（LocalDatabase、agent_memories 表、MemoriesPage UI 等），再调研 12+ 开源项目，提炼 5 条核心方法论。

---

### 1.3 需求分类阶段

**目标**：把杂乱的需求条目结构化，便于后续排期与分工。

**分类维度**：
- 按价值维度：用户可见价值 / 架构价值 / 维护价值
- 按数据维度：参考「数据分类矩阵法」（见下节）
- 按架构分层：UI 层 / 服务层 / 数据层 / 跨层 IPC
- 按风险维度：低风险易做 / 高风险核心 / 有争议待验证

---

### 1.4 优先级评估阶段

**目标**：用统一标准排出 P0/P1/P2，避免主观拍脑袋。

**P0 标准（必须做，不做就无法交付）**：
- 核心价值闭环无法成立的能力
- 数据安全、隐私、合规相关的硬性要求
- 其他功能的前置依赖（如类型定义、数据库 Schema、抽象接口）
- 例：同步功能中「Profile（soul.md、user-memory.md）」「Agent 记忆」—— 用户内容核心，不做就不是同步

**P1 标准（应该做，本次迭代交付）**：
- 显著提升用户体验的能力
- 覆盖 80% 使用场景的能力
- 例：同步功能中「对话记录」「任务列表」「记忆宫殿」

**P2 标准（可以做，或留给后续迭代）**：
- 锦上添花、使用频率低的能力
- 高成本低收益的能力
- 例：同步功能中「MCP 服务器配置」「本地 Cron 任务」——设备差异大、冲突风险高

**评估技巧**：先做 P0，P0 通过后再启动 P1，避免同时摊大饼。

---

### 1.5 需求验证阶段

**目标**：在写代码前确认需求理解正确，减少返工。

**验证方法**：
1. 闭环验证：用一句话复述「用户做 X → 系统做 Y → 用户得到 Z」，若逻辑不通则回到问题定义
2. 设计评审：与熟悉代码库的人过一遍架构与文件落点
3. 非目标书面化：把「明确不做」的清单写进设计文档头部，防止中途被追加
4. 最小可行边界：MVP 只覆盖最核心路径，其余留接口

**参考实践**：录屏功能 MVP 明确不做系统声音、MP4 转码、时间线播放器，把范围收敛到「能录屏 + AI 可控 + 简易手动 UI」三件事。

## 二、从现有分析过程提炼的最佳实践

### 2.1 数据分类矩阵法

**来源**：`docs/analysis/2026-09-07-多设备数据同步策略分析.md` §2.1

**方法**：用一张矩阵表，从四个维度评估每类数据项，用于快速形成共识。

**矩阵模板**：

| 数据类型 / 功能项 | 应交付 / 应包含 | 冲突风险或实现复杂度 | 量级 / 成本 | 优先级 |
|------------------|----------------|---------------------|-------------|--------|
| 用户核心内容 | ✅ | 低 | 小 | 🔴 P0 |
| 重要配置 / 状态 | 部分 | 中 | 小 | 🟡 P1 |
| 衍生 / 可重建数据 | 部分 | 高 | 大 | 🟢 P2 |
| 缓存 / 日志 / 临时文件 | ❌ | - | 大 | - |

**使用步骤**：
1. 列出所有候选数据项或功能项
2. 逐格打分：「应交付」用 ✅/❌/⚠️；「风险」用 低/中/高；「成本」用量级数字或 小/中/大
3. 优先级列根据前三列自动推导：用户核心 + 低风险 + 小成本 = P0；反之降档
4. 把矩阵放在分析文档头部，作为后续设计/计划的锚点

**优势**：比纯自然语言讨论更高效，便于对比，也便于后续变更时追溯「为什么当时把 X 放 P2」。

---

### 2.2 P0/P1/P2 优先级划分标准（Lumii 实践版）

**判断顺序**（按权重从高到低）：
1. **是否是用户核心价值闭环**：没它就构不成「这个功能对用户有用」→ P0
2. **是否是其他模块的前置依赖**：类型、Schema、抽象接口 → 倾向 P0
3. **实现风险**：高复杂度 + 高不确定性 → 倾向从 P0 降到 P1/P2，或分阶段
4. **成本与收益**：实现成本 > 用户收益 → P2 或暂不做
5. **数据安全与隐私**：涉及密钥、用户隐私的机制 → 必须 P0

**判定示例（来自同步分析）**：
- soul.md（人格定义）：用户核心 + 低风险 + 1KB → P0
- provider.json（模型密钥）：设备特定 + 高冲突风险（各设备不同）→ ❌ 不同步
- conversations（对话）：重要但体积大 + 有冲突 → P1
- runtime_state（运行态）：可重建 + 高冲突 → ❌ 不同步

### 2.3 需求拆解模板结构

**一个完整的功能条目，从需求到交付应包含以下五段**，任何一段缺失都容易返工。

#### 第一段：设计文档（Design）
应覆盖：
- 标题、日期、状态（设计待评审 / 已确认 / 已废弃）
- 问题 / 背景分析（含代码事实核查或数据证据）
- 方案对比与选型（为什么选 A 不选 B/C）
- 核心设计（架构图、数据模型、关键流程）
- 范围（做 / 不做）
- 安全与风险
- 验收标准（可量化的通过条件）

#### 第二段：实施计划（Plan）
应覆盖：
- Goal：一句话目标
- Architecture：高层架构与模块边界
- Tech Stack：使用的技术与依赖（强调不引入什么）
- Global Constraints：不可违反的全局约束（如：不得改 `packages/pet-core`）
- File Map：新增 / 修改的文件清单与职责
- Task 分解：按依赖关系排序的子任务，每个子任务有独立的「做什么 + 验证命令」
- 里程碑与退出标准

#### 第三段：实施过程（Implementation）
应覆盖：
- 实际代码提交记录
- 过程中遇到的问题与绕过方式
- 与原设计的差异点及原因（设计 → 实际的一致性对比表）
- 重要 Bug 修复记录

#### 第四段：测试报告（Test Report）
应覆盖：
- 单元测试列表与通过率
- 集成测试 / E2E 场景
- CLI 证据（`evidence.jsonl`）与汇总表
- 性能指标（若涉及）
- 已知限制与后续补充验证项

#### 第五段：交付总结（Delivery Summary）
应覆盖：
- 完成的工作清单（设计 / 代码 / 测试 / 工具）
- 达成的目标（量化指标）
- 未完成 / 遗留项
- 关键成就与经验教训
- 下一步建议路线图
- 相关文档索引

## 三、需求与设计 / 实施的衔接方法

### 3.1 从需求到设计：先写「结论摘要表」

在设计文档头部放一张 4~6 行的结论摘要表，直接对应需求要点：

| 问题 | 结论 |
|------|------|
| 主目标 | A：…… ；B 留扩展位 |
| 范围 | 本期做 X、Y、Z；不做 A、B、C |
| 技术路线 | 方案 N（理由：……） |
| 最大风险 | ……（以及缓解方式） |

**价值**：评审时别人不必通读 10 页全文，2 分钟内即可抓住决策。

---

### 3.2 从设计到实施：写「全局约束（Global Constraints）」

在实施计划文档开头，用独立章节列出不可违反的硬约束，例如：
- 不引入新依赖（如 ML 框架、图表库）
- 不修改现有公共 API
- 所有数据库迁移必须提供 down 脚本
- 日志不得记录用户消息原文 / 密钥

**价值**：在漫长的编码过程中，开发者随时可以回查「我现在想做的这个小技巧是否越界」。

---

### 3.3 从实施到交付：写「与原设计对比表」

交付总结中必须有一张对比表：

| 目标 / 设计项 | 设计文档描述 | 实际实现 | 状态 | 差异原因 |
|--------------|-------------|---------|------|---------|
| 仅同步核心数据 | ✅ | ✅ | 符合 | - |
| Wiki 导出格式 | SQL dump + gzip | JSON | 差异 | better-sqlite3 易用性 |

**价值**：
- 防止「做完了但对不上当初的需求」
- 下次迭代时能看见当时的取舍，避免重新踩坑

---

### 3.4 跨层功能：先画「三处同步清单」

凡涉及 Electron 三层（主进程 / Preload / 渲染进程）的需求，设计阶段就列出一张「IPC 三处同步」清单：

| IPC 通道 / 能力 | 主进程 Handler | Preload `ElectronAPI` 类型与方法 | 渲染进程调用点 |
|----------------|---------------|----------------------------------|---------------|
| `cloudSync:getConfig` | ✅ | ✅ | ✅ |
| `cloudSync:testConnection` | ✅ | ✅ | ✅ |

缺一行就不要开工，开工后改一处就同步改三处。

---

### 3.5 收尾：交付文档索引表

每个功能收尾时，在交付总结附录放一张「相关文档索引」：

```
设计文档       → docs/design/XXX/YYYY-MM-DD-xxx-design.md
分析/反思文档   → docs/analysis/YYYY-MM-DD-xxx-reflection.md
实施记录       → docs/implementation/YYYY-MM-DD-xxx.md
修复文档       → docs/fix/YYYY-MM-DD-xxx-fix.md
测试报告       → docs/test/YYYY-MM-DD-xxx-test-summary.md
CLI 测试证据    → docs/test/lumii-cli/xxx-test-report.md
```

保证数月后回头看时，能从任意一篇文档顺藤摸到完整上下文。
