# 功能开发标准

## 1. 项目架构概览

### 1.1 三层进程架构

Lumii 采用标准 Electron 三层进程分离架构，各层职责边界不可逾越：

| 层级 | 进程 | 职责范围 | 核心能力 | 禁止事项 |
|------|------|----------|----------|----------|
| Main | 主进程（Node.js） | 系统资源访问、数据库、IPC 路由、生命周期管理 | 文件系统、SQLite、Git、TTS、托盘、更新、子进程执行 | 不可导入 React / 不可操作 DOM |
| Preload | 预加载沙箱 | 安全桥接层，窄暴露 Main 能力给 Renderer | contextBridge 白名单暴露、IPC 薄封装、类型声明 | 禁止暴露整个 ipcRenderer、禁止直接传递 Node API |
| Renderer | 渲染进程（Chromium） | UI 渲染、用户交互、状态管理 | React 组件树、CSS Modules、Context、Hooks、Services | 不可直接访问 fs / path / sqlite3 等 Node API |

## 2. IPC 三处同步铁律（核心约束）

### 2.1 通道命名规范

所有 IPC 通道必须使用 **`domain:action`** 两段式命名：

- 第一段：功能域（vcs / voice / agent / wiki / sync / settings / mcp / approval）
- 第二段：动作动词开头（get / list / create / update / delete / export / import）

正确示例：
- `vcs:getStatus`
- `wiki:listTopics`
- `sync:triggerExport`
- `approval:resolveRequest`

### 2.2 三处同步定义（缺一 CI 直接 FAIL）

新增或修改 IPC 必须在以下 **三处 100% 同步定义**，并通过 `ipc-contract.test.ts` 合约测试扫描门禁：

| 序号 | 位置 | 必须做 | 校验方式 |
|------|------|--------|----------|
| ① | **Main handler** `apps/windows/src/main/ipc/<domain>.ts` | `ipcMain.handle('domain:action', async (_e, args): ReturnType => { ... })`，args 必须 runtime 校验 | 合约测试扫描 `ipcMain.handle` 注册项 |
| ② | **Preload 桥** `apps/windows/src/preload/index.ts` + `electron-api.d.ts` | `contextBridge.exposeInMainWorld('electronAPI', { domainAction: (args) => ipcRenderer.invoke('domain:action', args) })` 薄封装；同步在 `Window.ElectronAPI` 接口声明入参和返回类型 | 合约测试 AST 解析 expose 项 + TS interface 项，与①做集合相等 |
| ③ | **Renderer 调用方** `apps/windows/src/renderer/services/<domain>.service.ts` | 导出 service 函数（如 `export async function getVcsStatus() { return window.electronAPI.vcsGetStatus(); }`），禁止业务组件直接调 `window.electronAPI` | 合约测试扫描 service 层 import + 调用关系 |

### 2.3 Preload 窄暴露（安全红线）

✅ 正确做法——薄封装单个通道：
```typescript
contextBridge.exposeInMainWorld('electronAPI', {
  vcsGetStatus: () => ipcRenderer.invoke('vcs:getStatus'),
  wikiListTopics: (opts) => ipcRenderer.invoke('wiki:listTopics', opts),
})
```

❌ 禁止做法——暴露整个 ipcRenderer（任意通道可调用，等于无安全边界）：
```typescript
contextBridge.exposeInMainWorld('electronAPI', {
  ipcRenderer: ipcRenderer,
})
```

### 2.4 Main Handler 输入校验

Main 侧 handler 必须在执行业务逻辑前做 **runtime 输入校验**（不能只靠 TS 类型，TS 编译后类型已擦除）：

```typescript
import { z } from 'zod';

const ListTopicsSchema = z.object({
  vaultId: z.string().uuid(),
  limit: z.number().int().min(1).max(200).optional().default(50),
  offset: z.number().int().min(0).optional().default(0),
});

ipcMain.handle('wiki:listTopics', async (_e, rawArgs) => {
  const args = ListTopicsSchema.parse(rawArgs);
  // ... 以下 args 类型安全
});
```

## 3. 文档五件套强制执行

每个跨层 Feature 必须产出以下 5 份 Markdown 文档，相互交叉引用相对路径：

| 序号 | 文档 | 存放目录 | 核心内容 | 验收要点 |
|------|------|----------|----------|----------|
| ① 设计文档 | `docs/design/<主题>/` | 目标、架构、数据流、边界、风险、方案对比 | 必须有 In-Scope / Out-of-Scope / Success Criteria（可量化） |
| ② 实施计划 | `docs/plans/<主题>/` | 分阶段里程碑、任务拆分（粒度≤0.5天）、验收命令、回滚方案 | 每个 P0/P1/P2 有明确 Done Definition |
| ③ 实施记录 | `docs/plans/<主题>/实施记录-*.md` 或内嵌代码注释 | 实际完成项、与计划偏差、关键决策 | 与计划 diff 的原因说明 |
| ④ 测试报告 | `docs/plans/<主题>/测试报告-*.md` 或 `*.test.ts` 附 Evidence.jsonl | CLI Suite / Vitest / Playwright 结果、截图、录屏 | 必须有 pass/fail 统计 + SKIP 原因 + 非确定性项标注 |
| ⑤ 交付总结 | `docs/plans/<主题>/交付总结.md` | 交付物清单、验证命令、已知限制、后续路线 | 必须含 Config/Windows 特殊要求 + 升级影响说明 |

**交叉引用规则**：设计文档底部链接计划；计划顶部引用设计；实施记录引用计划；测试报告引用实施记录；交付总结引用前 4 件。

## 4. 错误处理规范

### 4.1 四层分工模式

| 层级 | 位置 | 职责 | 反模式 |
|------|------|------|--------|
| L1 Model / Service 层 | `main/services/*` / `renderer/services/*` | 抛出**语义化错误对象**（NetworkError / ValidationError ...），带结构化 code + 调试数据 | 不做 UI 级 `alert()` / `toast()`；吞错 return null |
| L2 Custom Hook 层 | `renderer/hooks/**` | 捕获 L1 错误，转换为 UI 可消费状态（`{ error, isError }`）+ 降级数据 | 直接 throw 让组件崩；不区分可恢复/致命 |
| L3 UI 组件层 | `renderer/pages/*` / `components/*` | 显示 L2 传来的 error：`ErrorBanner` + 重试按钮 + 降级展示 | 再次 try/catch Service（重复分层） |
| L4 Global Boundary | `PageErrorBoundary`（路由级） | 兜底未预料异常：整页崩溃展示友好界面 + 重新加载按钮 | 不加区分全吞掉导致白屏无反馈 |

### 4.2 错误类型库（6 种）

```typescript
// apps/windows/src/renderer/errors/AppError.ts （Main 侧同构）
export class AppError extends Error {
  readonly code: string;
  readonly statusCode: number;
  readonly cause?: unknown;
  readonly debug?: Record<string, unknown>;

  constructor(params: {
    code: string;
    statusCode: number;
    message: string;
    cause?: unknown;
    debug?: Record<string, unknown>;
  }) {
    super(params.message);
    this.name = 'AppError';
    this.code = params.code;
    this.statusCode = params.statusCode;
    this.cause = params.cause;
    this.debug = params.debug;
  }
}

// 子类——code/statusCode 固定不可变
export class NetworkError    extends AppError { constructor(m: string, o = {}) { super({ code: 'NETWORK_ERROR',     statusCode: 503, message: m, ...o }); } }
export class ValidationError extends AppError { constructor(m: string, o = {}) { super({ code: 'VALIDATION_ERROR',  statusCode: 400, message: m, ...o }); } }
export class PermissionError extends AppError { constructor(m: string, o = {}) { super({ code: 'PERMISSION_DENIED', statusCode: 403, message: m, ...o }); } }
export class NotFoundError   extends AppError { constructor(m: string, o = {}) { super({ code: 'NOT_FOUND',         statusCode: 404, message: m, ...o }); } }
export class ConflictError   extends AppError { constructor(m: string, o = {}) { super({ code: 'CONFLICT',          statusCode: 409, message: m, ...o }); } }
```

### 4.3 三大错误处理模式

#### 模式一：错误包装（加语义信息不丢失 Cause）

```typescript
export async function loadWikiTopic(id: string) {
  try {
    return await window.electronAPI.wikiGetTopic(id);
  } catch (rawErr) {
    // 包装：加"是哪个 topic 失败"的语义，保留原始栈
    throw new AppError({
      code: 'WIKI_TOPIC_LOAD_FAILED',
      statusCode: 500,
      message: `加载 Wiki 主题 ${id} 失败`,
      cause: rawErr,
      debug: { topicId: id, at: Date.now() },
    });
  }
}
```

#### 模式二：降级模式（优先用历史数据不弹错）

```typescript
const { data: settings, error } = useSWR('settings', fetchSettings, {
  // 降级：即使本次网络失败，先返回上一份 localStorage 缓存
  fallbackData: () => {
    const cached = localStorage.getItem('settings-cache');
    return cached ? JSON.parse(cached) : DEFAULT_SETTINGS;
  },
  onErrorRetry: (err, key, config, revalidate, opts) => {
    if (err instanceof NetworkError) return; // 离线直接不重试，用缓存
    revalidate({ ...opts, retryCount: opts.retryCount + 1 });
  },
});
```

#### 模式三：边界模式（组件级崩溃不拖垮整页）

```tsx
// routes/index.tsx 中每个 <Route> 外层强制包：
<Route
  path="/wiki"
  element={
    <PageErrorBoundary pageName="Wiki 库">
      <WikiPage />
    </PageErrorBoundary>
  }
/>
```

## 5. 性能优化规范

### 5.1 memo 家族决策表

| 技术 | 适用场景 | 规避场景 | 成本评估 |
|------|----------|----------|----------|
| `React.memo(Component)` | 组件 props 引用稳定 + 子树重渲染开销大（>5ms） | 组件本身轻量（<2ms）；props 每次都是新对象 | 浅比较成本 ≈ 0.1ms，收益 > 10× 才值得用 |
| `useMemo(() => value, [deps])` | 计算开销大：数组排序/过滤、大对象构造、FTS 分词 | 简单字段访问、三元表达式、`{ a: 1 }` 字面量 | 依赖数组比较成本，避免为"避免 GC"过度使用 |
| `useCallback(fn, [deps])` | fn 传给 memo 子组件 props / fn 是 useEffect/SWR 依赖 | fn 只在当前组件 JSX onClick 用，不下传不进 deps | 依赖闭包失效是头号 Bug 源，宁可不加 |
| `React.lazy + Suspense` | 路由级页面、Modal 首次打开、低频二级面板 | 主工作区首屏必需组件（白屏 > 300ms 伤体验） | 分包体积 < 15KB 收益可忽略 |
| 虚拟列表 `react-window` | 列表项 > 200 条、每 DOM 复杂（>3 层嵌套） | < 50 条、每 item 纯文本 | 滚动防抖 + 骨架占位，处理跳跃回流 |

### 5.2 两大 Render 期陷阱

❌ 反模式 1：JSX 里 inline 新对象：
```tsx
<ExpensiveMemoChild options={{ theme: 'dark', density: 'compact' }} />
// options 每次 render 都是新引用，React.memo 全部失效 → 白写 memo
```

✅ 正确做法：提升到 `useMemo` 或 模块常量：
```tsx
const CHILD_OPTIONS = { theme: 'dark', density: 'compact' } as const;
const options = useMemo(() => ({ theme: curTheme, density: 'compact' }), [curTheme]);
<ExpensiveMemoChild options={options} />
```

❌ 反模式 2：JSX 里 inline 新函数：
```tsx
<MemoButton onClick={() => removeItem(id)}>删除</MemoButton>
// onClick 每次 render 新函数 → MemoButton memo 失效
```

✅ 正确做法：`useCallback` 或 父组件数据驱动：
```tsx
const handleRemove = useCallback(() => removeItem(id), [id, removeItem]);
<MemoButton onClick={handleRemove}>删除</MemoButton>
```

### 5.3 数据获取最佳实践

#### 5.3.1 去重 + 5 分钟软过期缓存

```typescript
import useSWR from 'swr';

const STALE_TIME = 5 * 60 * 1000; // 5 分钟内不重新请求

export function useWikiTopics(vaultId: string) {
  const key = vaultId ? ['wiki:topics', vaultId] : null;
  return useSWR(key, ([, id]) => window.electronAPI.wikiListTopics({ vaultId: id }), {
    staleTime: STALE_TIME,
    dedupingInterval: STALE_TIME, // 同 key 并发调用合并
    revalidateOnFocus: false,     // 切回窗口不自动打 IPC
    revalidateOnReconnect: true,  // 断线恢复才刷新
  });
}
```

#### 5.3.2 多级缓存（内存 → localStorage）

```typescript
function cachedFetcher<T>(key: string, rawFn: () => Promise<T>, ttl = 300_000): Promise<T> {
  const storageKey = `cache:${key}`;
  const cached = localStorage.getItem(storageKey);
  if (cached) {
    const { v, t } = JSON.parse(cached);
    if (Date.now() - t < ttl) return Promise.resolve(v as T);
  }
  return rawFn().then((v) => {
    localStorage.setItem(storageKey, JSON.stringify({ v, t: Date.now() }));
    return v;
  });
}
```

#### 5.3.3 分页 + 虚拟列表联合模板

```tsx
import { VariableSizeList as List } from 'react-window';

function TopicList({ items }: { items: Topic[] }) {
  const rowHeights = useRef<Record<number, number>>({});

  const getRowHeight = (idx: number) => rowHeights.current[idx] ?? 72;

  const setRowHeight = (idx: number, el: HTMLDivElement | null) => {
    if (el) rowHeights.current[idx] = el.getBoundingClientRect().height;
  };

  return (
    <List
      height={600}
      itemCount={items.length}
      estimatedItemSize={72}
      itemSize={getRowHeight}
      width="100%"
    >
      {({ index, style }) => (
        <div style={style}>
          <TopicRow
            ref={(el) => setRowHeight(index, el)}
            topic={items[index]}
          />
        </div>
      )}
    </List>
  );
}
```

## 6. Context 创建规范

### 6.1 五文件标准结构

每个业务 Context 必须按以下结构建目录，禁止把 types / reducer / hook 全塞一个 500+ 行文件：

```
renderer/contexts/
└── WikiPageContext/
    ├── types.ts       # WikiPageState / WikiPageAction（无 import 依赖）
    ├── Context.ts     # createContext<WikiPageState | null>(null)
    ├── Provider.tsx   # WikiPageProvider（reducer + init + 副作用）
    ├── useContext.ts  # export const useWikiPage = () => { const ctx = useContext( WikiPageContext ); if (!ctx) throw ... }
    └── index.ts       # 统一 re-export { WikiPageProvider, useWikiPage }
```

### 6.2 现有全局 Context 清单

| Context | 作用域 | 持久化 |
|---------|--------|--------|
| ThemeContext | 浅色/深色/跟随系统主题 | ✅ localStorage `theme` |
| SettingsContext | 用户偏好设置（语言、音量、TTS 引擎…） | ✅ SQLite `settings` 表 |
| GatewayConnectionContext | Gateway WebSocket 连接状态（双连接） | ❌ 内存 |
| PetStateContext | 桌宠运行时状态（情绪/动作/坐标） | ❌ 内存 |
| ApprovalContext | 自主进化审批队列 + 待办数 | ✅ SQLite `approval_*` |
| SyncStatusContext | 同步模块进度、冲突图标、最近一次时间 | ❌ 内存 |

## 7. Git 提交规范

### 7.1 Conventional Commit 格式

```
<type>(<scope>): <subject>
  │      │         │
  │      │         └─ 现在时祈使句，小写开头，无句号，≤50 字
  │      └─ 影响范围：agent-runtime / pet-core / windows / docs / sync / wiki / ui ...（可选）
  └─ 7 种类型之一
```

7 种类型：

| type | 使用场景 | 触发事项 |
|------|----------|----------|
| `feat` | 新增用户可见功能 | bump minor、生成 CHANGELOG |
| `fix` | 修复 Bug | bump patch、生成 CHANGELOG |
| `docs` | 仅文档变更（设计/计划/规范） | 不触发构建 |
| `style` | 格式：空格/缩进/分号/import 顺序，无逻辑变 | 不触发测试 |
| `refactor` | 代码重命名/拆分/提取，行为不变且非 Bug | 不触发 CHANGELOG |
| `test` | 补测试、修测试、加 fixture | 只跑相关测试 |
| `chore` | 升级依赖、改构建脚本、CI 配置 | 需注明是否破坏性 |

示例：
```
feat(agent-runtime): 新增 Elo Rating 能力元认知打分
fix(windows): 修复 IPC wiki:listTopics 入参未校验导致的崩溃
docs(standards): 补充功能开发标准 IPC 三处同步铁律
refactor(sync): 抽离 ConflictResolver 3 规则到独立函数
test(approval): 新增 L2 超时归档端到端测试
chore: 升级 electron-vite 至 2.3，保留 patches/vite-plugin-commonjs
```
