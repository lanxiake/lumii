# 01-代码风格指南

## 一、代码组织原则

### 1.1 单一职责原则

每个文件、函数、组件应该只负责一件事。

**单一职责违规及修复方案**

| 违规类型 | 问题描述 | 修复方案 |
| --- | --- | --- |
| UI+Logic 混用 | 组件同时包含 UI 渲染和业务逻辑 | 将业务逻辑移到自定义 hook 或服务层 |
| 数据获取+展示 | 组件既获取数据又负责展示 | 将数据获取移到容器组件或 hook，保持展示组件纯净 |
| 状态管理过多 | 组件管理过多局部状态 | 考虑使用 context 或状态管理库（Zustand、Jotai） |

### 1.2 文件大小限制

| 级别 | 行数 | 处理方式 |
| --- | --- | --- |
| 目标 | < 500 行 | — |
| 警告 | 500–700 行 | 需要审查，考虑拆分 |
| 最大 | > 700 行 | 强制拆分：子组件 / 自定义 Hooks / 工具函数 |

## 二、命名规范

### 2.1 文件命名

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 组件 | PascalCase.tsx | `DashboardPage.tsx` |
| Hook | camelCase.ts | `useDashboard.ts` |
| 类型定义 | camelCase.types.ts | `dashboard.types.ts` |
| 工具函数 | camelCase.ts | `formatDate.ts` |
| 样式文件（CSS Modules） | kebab-case.module.css | `dashboard-page.module.css` |
| 样式文件（全局） | kebab-case.css | `dashboard-page.css` |
| 常量文件 | UPPER_SNAKE_CASE.ts | `API_ENDPOINTS.ts` |
| 配置文件 | kebab-case.config.ts | `vite.config.ts` |

### 2.2 变量命名

- **常量**：`UPPER_SNAKE_CASE`，如 `MAX_RETRY_COUNT = 3`
- **变量**：`camelCase`，如 `userCount`、`isLoading`
- **布尔值**：`is` / `has` / `should` 前缀，如 `isActive`、`hasPermission`、`shouldRetry`
- **数组**：复数名词，如 `users`、`selectedItems`
- **函数**：动词开头，如 `fetchData`、`handleClick`、`validateInput`
- **回调函数**：`on` / `handle` 前缀，如 `onSubmit`、`handleChange`

### 2.3 组件命名

| 类别 | 规范 | 示例 |
| --- | --- | --- |
| 页面组件 | 以 Page 结尾 | `DashboardPage`、`SettingsPage` |
| UI 组件 | 描述功能 | `Button`、`Modal`、`DataTable` |
| 业务组件 | 领域 + 功能 | `DeviceCard`、`ConnectionStatus`、`SkillStoreView` |
| 高阶组件 | 以 with 开头 | `withAuth`、`withLoading` |
| Hook | 以 use 开头 | `useAuth`、`useDashboard` |

### 2.4 接口命名

- **Props 接口**：`ComponentName + Props`，如 `interface ButtonProps {}`
- **类型别名**：适合联合类型，如 `type ViewType = 'dashboard' | 'chat' | 'settings'`
- **枚举**：必要时使用字符串枚举，如 `enum ConnectionStatus { Disconnected = 'disconnected' }`
- **工具类型**：`Nullable<T>`、`Optional<T>` 等通用辅助类型

## 三、代码格式规范

### 3.1 缩进和空格

- 2 空格缩进
- 最大行长 100 字符
- 单引号
- 语句末尾分号

### 3.2 对象和数组格式

- 简单对象单行：`const user = { id: 1, name: 'John' };`
- 复杂对象多行（每项一行，尾逗号）
- 数组 > 3 项时多行，尾逗号
- 解构 > 2 项时多行，尾逗号

### 3.3 函数格式

- 简洁箭头函数：`const double = (x: number) => x * 2;`
- 带逻辑箭头函数用 `{ return }`
- 复杂逻辑使用 function 声明，参数多行对齐
- 异步函数：`async function fetchX(): Promise<X>`

## 四、TypeScript 规范

### 4.1 类型定义

| 规则 | 正确做法 | 错误做法 |
| --- | --- | --- |
| 公共 API 返回类型 | 显式声明 `: number` / `: User` | 依赖隐式推断 |
| 对象结构 | 优先 interface | 用 type alias 定义对象 |
| 联合/交叉类型 | 使用 type alias | interface 无法表达 |
| 禁止 any | 全部替换为 unknown + 类型守卫 | `data: any` |
| 类型导入 | `import type { User } from '...'` | 普通 import 导入只用到的类型 |

### 4.2 泛型使用

- 函数泛型：`function identity<T>(value: T): T`
- 接口泛型：`interface ApiResponse<T> { data: T }`
- 类型约束：`function findById<T extends HasId>(items: T[], id: string)`
- 默认泛型：`interface Container<T = string>`

### 4.3 枚举 vs 联合类型

- **优先联合类型**：如 `type ViewType = 'dashboard' | 'chat' | 'settings'`
- **必要时才用枚举**：需要反向映射或字符串常量集合的场景

## 五、React 规范

### 5.1 组件定义

- **函数组件 + 显式返回类型**：`export const Button: React.FC<ButtonProps> = ({ children }) => <button>{children}</button>`
- **forwardRef**：必须加 `displayName`，方便 DevTools 调试
- **React.memo**：仅用于纯净组件且渲染开销较大时，不要过度使用

### 5.2 Hooks 使用规范

| 规则 | 说明 |
| --- | --- |
| Hooks 顶置 | 所有 useState/useRef/useEffect 放在函数顶部，不在条件/循环中调用 |
| 派生状态 useMemo | 复杂计算（排序/过滤/映射大数组）用 useMemo，依赖数组正确 |
| 回调 useCallback | 作为 props 传给子组件的回调必须用 useCallback，避免子组件失效 memo |
| 副作用 useEffect | 副作用和清理成对出现；依赖数组精确，禁止空数组依赖有警告 |
| 提前 return | `if (loading) return <Loading />;` 必须在所有 Hooks 之后（避免 Hook 顺序变化） |

### 5.3 Props 处理

- 解构时直接写默认值：`{ showEmail = false }`
- 可选事件处理器加存在性判断：`{ onEdit && <button onClick={() => onEdit(user)}>编辑</button> }`
- className 用 `clsx` / `classnames` 合并条件类名

## 六、注释规范

### 6.1 文件头注释

```
/**
 * @file 文件简短描述
 * @description 详细描述文件功能和用途
 * @module 所属模块
 */
```

### 6.2 JSDoc 注释

公共 API 必须写完整 JSDoc：`@param` / `@returns` / `@throws` / `@example` 四项齐全。

### 6.3 行内注释

- ✅ 解释**为什么**而不是是什么（例：使用防抖避免频繁请求 API）
- ❌ 不写显而易见的注释（例：设置 count 为 0）
- TODO / FIXME 必须加可追踪 issue 或说明

### 6.4 类型注释

复杂类型、泛型参数需要加注释，说明字段的业务含义。

## 七、导入导出规范

### 7.1 导入顺序（从上到下严格排序）

1. React 导入（`import React`）
2. 第三方库（date-fns / lodash / @tanstack/react-query 等）
3. 绝对路径 UI 组件（`@/components/ui`）
4. 绝对路径业务组件（`@/components/business`）
5. 绝对路径 Hooks
6. 绝对路径 Services
7. 绝对路径 Types（必须 `import type`）
8. 绝对路径 Utils / Tools
9. 相对路径（`./SubComponent`、`../hooks/useLocalState`）
10. 样式文件（最后，CSS Modules 或全局）

### 7.2 导出规范

| 规则 | 说明 |
| --- | --- |
| 推荐命名导出 | `export const X = ...`，便于 tree-shaking 和查找引用 |
| 禁止默认导出 | 业务组件/函数一律 named export；只有页面/配置文件可例外 |
| index.ts 桶导出 | 统一 `export { Button } from './Button'`；类型也 `export type { ButtonProps }` |
| 类型独立导出 | `export type { X }` 与值导出分离 |

## 八、错误处理规范

### 8.1 错误类型定义

**AppError 基类体系**

```typescript
class AppError extends Error {
  constructor(
    message: string,
    public code: string,
    public statusCode?: number,
    public details?: Record<string, unknown>,
  ) {
    super(message);
    this.name = 'AppError';
  }
}

class ValidationError extends AppError { /* code=VALIDATION_ERROR status=400 */ }
class NetworkError    extends AppError { /* code=NETWORK_ERROR */ }
class PermissionError extends AppError { /* code=PERMISSION_DENIED status=403 */ }
class NotFoundError   extends AppError { /* code=NOT_FOUND status=404 */ }
class ConflictError   extends AppError { /* code=CONFLICT status=409 */ }
```

### 8.2 错误处理四层模式

| 层级 | 职责 | 处理方式 |
| --- | --- | --- |
| Service/Model 层 | 捕获底层错误 → 包装成具体 AppError 子类抛出 | `try/catch` + 包装 throw |
| Hook 层 | 接收 AppError → 存入 state → 重新抛给 UI 或吞掉 | useState<Error \| null> |
| UI 组件层 | 读取 error state → 渲染 ErrorBanner / Toast / 空态 | `if (error) return <ErrorBanner />;` |
| Global Boundary | React Error Boundary / 全局 uncaught promise | 兜底崩溃页面 + 日志上报 |

## 九、性能优化规范

### 9.1 性能优化决策表

| 优化技术 | 适用场景 | 何时避免使用 |
| --- | --- | --- |
| React.memo | 组件渲染开销大、props 变化不频繁 | 组件小、props 经常变（memo 比较成本 > 重渲染） |
| useMemo | 计算开销大（排序/过滤/大数据 map）、依赖变化不频繁 | O(1) 简单运算 |
| useCallback | 回调作为 props 传给 memo 子组件、依赖引用相等 | 回调不传子组件、子组件不 memo |
| React.lazy + Suspense | 路由级代码分割、大组件延迟加载（> 30KB） | 小组件 / 首屏必需组件 |

### 9.2 常见性能陷阱

- ❌ 禁止 render 期创建新对象 / 新数组：`items.map(i => ({ ...i }))` 每次 render 新引用，子组件全失效
- ✅ 用 useMemo 包裹派生对象创建
- ❌ 禁止 render 期创建新函数：`const onClick = () => props.onClick(x)`
- ✅ 用 useCallback 包裹，或提前把参数传进子组件用事件对象取 id
- ❌ 禁止 key=index：列表排序/增删后 React diff 错乱
- ✅ key 使用稳定 id（数据库主键 / 业务唯一 id）

### 9.3 数据获取优化

- 搜索输入 300ms 防抖，避免每字一请求
- 长列表分页：`useInfiniteQuery` + 游标 / offset
- 缓存策略：`staleTime: 5*60*1000` 用户相关数据 5 分钟新鲜
- 虚拟列表：> 200 条必须用 `react-virtuoso` 或等价，不要硬渲染全部 DOM

### 9.4 代码分割

- 路由级：所有非首屏 Page 都 `lazy(() => import(...))`
- 组件级：大图表 / 复杂对话框 / 配置面板按需懒加载
- Suspense fallback 用骨架屏 Skeleton 不是 Loading spinner

## 十、测试规范

### 10.1 测试文件组织

测试文件就近放置：

```
ComponentName/
├── ComponentName.tsx
├── ComponentName.module.css
├── ComponentName.test.tsx  ← 测试文件
└── index.ts
```

全局集成测试放 `src/test/__tests__/{components,hooks,pages,services}/`。

### 10.2 测试结构（四段式）

1. `describe('渲染')`：默认 / 加载 / 空 / 错误 四态
2. `describe('交互')`：点击 / 输入 / 选择 / 键盘
3. `describe('数据流')`：props 接收 / 回调触发 / 状态更新
4. `describe('边界情况')`：超长文本 / 空数组 / 非法输入 / 网络错误

### 10.3 Mock 策略

- Hook / Service mock 必须在 `import 组件` 之前声明（Vitest hoist 不生效场景）
- `beforeEach` 中 `vi.clearAllMocks()`，避免测试间污染
- mock 返回值结构 100% 与真实接口一致（不能缺字段导致类型断言掩盖 bug）

### 10.4 元素查询策略（优先顺序）

1. ✅ 角色查询 `screen.getByRole('button', { name: /提交/i })`（无障碍友好）
2. ✅ 标签文本 `screen.getByLabelText(/用户名/i)`
3. ✅ 占位符 `screen.getByPlaceholderText(/请输入/i)`
4. ✅ 测试 ID `screen.getByTestId('submit-button')`（无法语义查询时才用）
5. ❌ 绝对禁止：`getByClassName` / `getById` 等实现细节查询

### 10.5 用户行为模拟

- 全用 `@testing-library/user-event`：`userEvent.click` / `.type` / `.keyboard('[Enter]')` / `.selectOptions` / `.upload`
- 禁止用 `fireEvent`（除非 user-event 无法触发的极特殊场景）

### 10.6 异步测试

- 断言 UI 出现：优先 `await screen.findByText(...)`（自带重试）
- 复杂条件：`await waitFor(() => expect(mockFn).toHaveBeenCalled(), { timeout: 5000 })`
- 禁止 `await new Promise(r => setTimeout(r, 1000))` 这种固定等待（慢 + 不稳定 + 慢机器上 flaky）

### 10.7 覆盖率与质量标准

| 指标 | 目标值 |
| --- | --- |
| 行覆盖率 | > 80% |
| 函数覆盖率 | > 80% |
| 分支覆盖率 | > 70% |
| 语句覆盖率 | > 80% |

**测试质量检查清单**

- [ ] 所有公开函数/组件都有测试
- [ ] 边界情况 + 错误态 + 空态有测试
- [ ] 可独立运行，不依赖顺序
- [ ] 测试用例名描述行为不是实现
- [ ] 断言具体，不只测是否抛异常
- [ ] 不依赖类名/内部变量名
- [ ] 异步有等待机制，不是固定 sleep
- [ ] mock 每次重置，无测试间污染

## 附录：快速检查清单

- [ ] 命名清晰、描述性，不缩写难懂单词

- [ ] 无深层嵌套（if/for 嵌套 ≤ 3 层）
