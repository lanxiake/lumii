# 常见问题排查指南

本指南按用户最常遇到的问题域分类，给出标准化排查步骤和快速诊断命令清单，遵循「由浅入深、先环境后代码、先快速再深度」的顺序。

---

## 1. 启动类问题

| 现象 | 典型描述 |
|------|----------|
| 白屏 | 启动后窗口空白、无 UI、控制台报 404 / 500 |
| 闪退 | 打开后立即关闭、任务管理器进程瞬间消失 |
| 端口占用 | 启动日志报「address already in use :::xxxx」 |
| 权限不足 | 弹出「管理员权限才能运行」「拒绝访问」类提示 |

### 排查步骤

| 步骤 | 操作 | 通过标准 |
|------|------|----------|
| 1 | 检查进程是否真的启动 | `Get-Process | Where-Object { $_.ProcessName -like '*lumii*' -or $_.ProcessName -like '*electron*' }` 有结果 |
| 2 | 读取启动日志 | 打开 `~/.lumii/logs/` 下最新 `.log`，查最后 50 行有无 Error |
| 3 | 检查 DevTools（若窗口还在） | 按 F12 → Console 看是否有白屏堆栈 |
| 4 | 排查端口占用 | 见下方快速命令 |
| 5 | 清缓存重试 | 重命名 `~/.lumii` 为 `~/.lumii-backup` 再启动（相当于干净环境） |
| 6 | 开发者模式启动 | `pnpm dev:verbose` 看实时全量日志 |

### 快速诊断命令清单

```powershell
# [P1] 查端口占用（找被哪个 PID 占了）
netstat -ano | Select-String ':5173\|:3000\|:5174' | Select-Object -First 10
# 然后杀对应 PID（确认确实是异常残留进程再杀）
# Stop-Process -Id <PID> -Force

# [P1] 查僵尸 Electron（父 PID 已不存在的孤儿）
Get-WmiObject Win32_Process -Filter "name='electron.exe'" |
  Select-Object ProcessId, ParentProcessId, CommandLine |
  ForEach-Object {
    $parentAlive = Get-Process -Id $_.ParentProcessId -ErrorAction SilentlyContinue
    if (-not $parentAlive) { "ORPHAN ELECTRON PID=$($_.ProcessId) PPID=$($_.ParentProcessId)" }
  }

# [P2] 全量日志里找 ERROR（按时间倒序）
Get-Content ~/.lumii/logs/*.log -Tail 200 | Select-String 'ERROR|FATAL|Uncaught' -Context 3,3

# [P3] 清缓存（先备份用户数据！）
Copy-Item ~/.lumii ~/.lumii-backup-$(Get-Date -Format yyyyMMdd) -Recurse -Force
# Remove-Item ~/.lumii -Recurse -Force  # 仅确认数据已备份后执行
```

## 2. 连接类问题

| 现象 | 典型描述 |
|------|----------|
| 双连接断开 | 顶部状态栏显示「离线」「重连中」闪烁 |
| 网关超时 | 发送消息后长时间无响应，控制台报 `Gateway Timeout 504` |
| Token 失效 | 模型调用报 `401 Unauthorized` / `Invalid API Key` |
| 设备配对失败 | 多设备扫码后另一台显示未配对、数据不同步 |

### 排查步骤

| 步骤 | 操作 | 通过标准 |
|------|------|----------|
| 1 | 确认基础网络 | 浏览器正常访问百度/必应；能访问 `api.openai.com` 或对应模型域名 |
| 2 | 看状态栏双连接 | 设置页 → 网络，分别显示 WSS (Stream) + HTTPS (Request) 两条链路状态 |
| 3 | 重测 API Key | 设置 → 模型配置 → 点击「测试连接」按钮，看报错详情 |
| 4 | 重连双连接 | 状态栏右键 → 「断开并重连」 |
| 5 | 检查设备时间 | 本地时间与 UTC 偏差 > 5 分钟时，JWT Token 校验会失败 |
| 6 | 抓包验证 | 见下方快速命令里的 cURL 直连验证 |

### 快速诊断命令清单

```powershell
# [P1] 验证模型 API Key 是否有效（用 curl 直连绕开应用）
# 替换 <key> 为真实 Key，根据模型选对应 URL
curl -X POST "https://api.deepseek.com/chat/completions" `
  -H "Authorization: Bearer <your-key>" `
  -H "Content-Type: application/json" `
  -d '{"model":"deepseek-chat","messages":[{"role":"user","content":"hi"}],"max_tokens":5}'
# 预期：200 OK，含 choices 数组；任何 4xx 都是 Key/配置问题

# [P1] 检查本机时间同步（偏差 > 300s 会导致 JWT 失效）
w32tm /query /status
# 看「Last Successful Sync Time」和「Source」；若不对执行：
# w32tm /resync /force

# [P2] 测试 WebSocket 连通性
# 用 wscat 或 PowerShell 发 WS 握手请求（若装了 Node）
# npx wscat -c wss://<gateway-domain>/v1/stream

# [P3] 应用日志里的连接事件
Get-Content ~/.lumii/logs/*.log -Tail 500 |
  Select-String 'connected|disconnected|reconnect|401|504|timeout' -Context 2,2
```

## 3. Agent 类问题

| 现象 | 典型描述 |
|------|----------|
| 不回复 | 发了消息一直转圈、「正在思考」不结束 |
| 回复质量差 | 内容跑题、幻觉、编造工具结果 |
| 工具调用失败 | Tool 卡片显示红色失败、报错信息难以理解 |
| 子 Agent 异常 | spawn 后卡住、级联打断不生效、子结果没并到父消息 |

### 排查步骤

| 步骤 | 操作 | 通过标准 |
|------|------|----------|
| 1 | 复现最短用例 | 新建会话，发「只回复四个字：测试通过」排除上下文污染 |
| 2 | 区分模型 vs Agent 逻辑 | 判断是否「最简单的一句话回复都出问题」→ 大概率模型侧；「复杂任务用工具时才出」→ 大概率 Agent 逻辑 |
| 3 | 看工具调用日志 | 日志锚点 `[ToolRunner] → <tool>` + `← <tool>` 是否成对出现 |
| 4 | 原子 Agent 调度日志 | 查 `[SubagentBroker] registerRun / finalizeRun / acquire denied` |
| 5 | 查深度/并发护栏 | 是否命中 5 层深度 / 5 并发限制（日志有明确 deny 锚点） |
| 6 | 系统 Prompt 完整 | Debug 模式下看 `finalSystemPrompt` 长度是否异常（被截断/重复注入） |

### 快速诊断命令清单

```powershell
# [P1] 找某会话的完整工具调用链（会话 key 前 8 位）
$SESSION_PREFIX = "ada2720c"
Get-Content ~/.lumii/logs/*.log -Tail 2000 |
  Select-String $SESSION_PREFIX -Context 0,0 |
  ForEach-Object { $_.Line } |
  Select-String 'ToolRunner|SubagentBroker|spawn async|Aborted agent'

# [P1] 统计工具调用成功率（最后 1000 条日志）
Get-Content ~/.lumii/logs/*.log -Tail 1000 |
  Select-String '\[ToolRunner\]' |
  ForEach-Object { $_.Line } |
  Group-Object { if ($_ -match '← .*error|← .*fail') { 'FAIL' } else { 'OK' } }

# [P2] 检查护栏命中（并发/深度超限）
Get-Content ~/.lumii/logs/*.log -Tail 500 |
  Select-String 'denied|depth limit|concurrency|cascade'

# [P3] 验证模型本身没问题（和 2 类问题同方法，排除法）
# 若 curl 直连 OK 但应用内不回 → 问题在应用层而非模型侧
```

## 4. 记忆类问题

| 现象 | 典型描述 |
|------|----------|
| 不召回 | 明明问的是以前聊过的事，Agent 完全不记得 |
| 召回错误 | 调了完全不相关的记忆、张冠李戴 |
| 注入重复 | 同一段记忆在 System Prompt 里出现 2+ 次 |
| 提取遗漏 | 新聊过的重要信息没有被存进记忆（下次仍不记得） |

### 排查步骤

| 步骤 | 操作 | 通过标准 |
|------|------|----------|
| 1 | 直查 DB 确认数据存在 | 用 SQLite CLI 打开 `agent-runtime.db`，按关键词查 `memory_entries` 表 |
| 2 | 手动调用 `memory_search` | 新建会话 → 发「调用 memory_search 搜索 X 关键词」→ 看工具返回 |
| 3 | 看注入片段 | Debug 模式 `Show Final Prompt` 里搜 `### Memories:` 段，确认注入内容长度和条目数 |
| 4 | 检查提取时机 | 提取是会话结束触发 / 定期触发 / 手动触发？配置对不对 |
| 5 | 向量索引重建 | 执行 `wiki rebuild` CLI，可能是旧 embedding 维度不匹配 |
| 6 | 版本兼容 | 最近是否升级过 Schema？V29→V31 迁移是否有报错日志 |

### 快速诊断命令清单

```powershell
# 路径常量
$DB = "$env:USERPROFILE\.lumii\data\agent-runtime.db"

# [P1] 关键词直查记忆（绕过应用层，确认数据真的存在）
sqlite3 $DB @"
.headers on
.mode column
SELECT id, substr(content, 1, 80) AS preview, created_at
FROM memory_entries
WHERE content LIKE '%关键词%'
ORDER BY created_at DESC
LIMIT 20;
"@

# [P1] 检查重复注入（同一条记忆 ID 出现次数）
sqlite3 $DB @"
SELECT memory_id, COUNT(*) AS c
FROM (/* 模拟应用检索 SQL，根据 schema 调整 */
      SELECT id AS memory_id FROM memory_entries
      WHERE content LIKE '%某主题%' LIMIT 50)
GROUP BY memory_id
HAVING c > 1;
"@

# [P2] 触发向量索引重建 + 看耗时
# node apps/windows/resources/app-ui-cli/lumii-ui.mjs wiki rebuild
# 日志应有：rebuiltCount=N, backend=xxx

# [P3] 最近 24h 提取了多少条记忆
sqlite3 $DB @"
SELECT COUNT(*) AS extracted_last_24h
FROM memory_entries
WHERE created_at > datetime('now', '-24 hours');
"@
```

## 5. 同步类问题

| 现象 | 典型描述 |
|------|----------|
| 冲突 | 状态栏显示「有冲突待解决」「N 个文件冲突」 |
| 丢失数据 | 同步后某端的变更在另一端消失了 |
| 导入失败 | 导入 zip / 旧备份时「格式不对」「校验失败」 |
| Git 非快进 | push 报错 `! [rejected] master -> master (non-fast-forward)` |

### 排查步骤

| 步骤 | 操作 | 通过标准 |
|------|------|----------|
| 1 | 查看同步状态详情 | 设置 → 云同步 → 「查看详情」，列出 pending 文件列表 |
| 2 | 区分 Git 层 vs 应用层 | 直接 `git status` 看 `~/.lumii/workspace/.mtbot-vcs/repos/<workspace>/` 的真实状态 |
| 3 | 检查 adoptRemote 符号链接问题（案例库 2） | 日志搜 EPERM / symlink |
| 4 | 冲突时检查 Agent 目标 | `autonomous_goals` 表是否生成了冲突处理的高优先级目标（案例库 2 修复点） |
| 5 | 导入失败查校验 | 手动解压导入包，看 JSON 文件能否被 `jq .` 正常解析 |
| 6 | 非快进冲突策略 | 先 `git pull --rebase` 再 push；若仍冲突走 `adoptRemote` 人工决策 |

### 快速诊断命令清单

```powershell
# 常量
$SYNC_ROOT = "$env:USERPROFILE\.lumii\workspace\.mtbot-vcs\repos\lumii"

# [P1] 底层 Git 状态（比 UI 更权威）
Push-Location $SYNC_ROOT
git status --short        # 哪些文件改了
git log --oneline -5      # 本地 5 条提交
git remote -v             # remote 对不对
# git fetch origin        # 不做变更，只看远端有无新提交
Pop-Location

# [P1] 应用层同步日志（找 adoptRemote / conflict / EPERM）
Get-Content ~/.lumii/logs/*.log -Tail 300 |
  Select-String 'adoptRemote|enterConflict|EPERM|symlink|non-fast-forward|conflict' -Context 2,2

# [P2] 冲突时 Agent 目标是否生成
sqlite3 ~/.lumii/data/agent-runtime.db @"
.headers on
SELECT id, status, priority, substr(description, 1, 60) AS desc, created_at
FROM autonomous_goals
WHERE trigger_reason = 'cloud-sync-conflict'
ORDER BY created_at DESC LIMIT 10;
"@

# [P3] 备份完整性（MD5 比对确认备份不是复制同一份快照，案例库 3 的经验）
Get-ChildItem ~/.lumii/data/*.bak |
  ForEach-Object { Get-FileHash $_.FullName -Algorithm MD5 } |
  Select-Object Hash, Path |
  Format-Table -AutoSize
```

## 6. UI 类问题

| 现象 | 典型描述 |
|------|----------|
| 样式错乱 | 某个面板飞出屏幕、按钮叠在一起、长列表换行异常 |
| 主题切换异常 | 亮色/暗色/跟随系统切换后某块还是旧主题色 |
| 滚动卡顿 | 长对话/长列表滚动时掉帧、明显顿挫 |
| 输入法冲突 | 中文输入法输入到一半上屏消失、候选窗位置错位 |

### 排查步骤

| 步骤 | 操作 | 通过标准 |
|------|------|----------|
| 1 | 确认是否复现 | 刷新（Ctrl+R）后是否仍乱；清缓存刷新后是否仍乱 |
| 2 | 抓 DOM 看样式 | F12 → Elements，选异常元素，看 Computed 面板 height/width/position 是否计算异常 |
| 3 | 主题变量完整性 | DevTools Console 执行 `getComputedStyle(document.body).getPropertyValue('--bg-primary')`，主题切换前后应变化 |
| 4 | 虚拟列表配置 | 长对话/列表是否启用了虚拟滚动？itemSize 是否匹配真实行高 |
| 5 | IME（输入法）处理 | 检查是否用 `compositionstart/update/end` 事件在合成期间禁止状态更新 |
| 6 | 缩放/DPI | Windows 缩放率（100% / 125% / 150%）切换复现，锁定缩放是否仍异常 |

### 快速诊断命令清单

```powershell
# [P2] 快速检查本地缩放因子
Get-ItemProperty 'HKCU:\Control Panel\Desktop\WindowMetrics' |
  Select-Object AppliedDPI, LogPixels

# [P2] DevTools Console 里一键查虚拟列表问题（手动粘贴）
#   const scroller = document.querySelector('[data-testid="chat-message-list"]');
#   console.log('scrollHeight=', scroller.scrollHeight, 'clientHeight=', scroller.clientHeight);
#   const items = scroller.querySelectorAll('[role="row"]');
#   console.log('rows=', items.length, 'first height=', items[0]?.getBoundingClientRect().height);

# [P3] 强制刷新渲染缓存（Electron 特定）
# 应用内按 Ctrl+Shift+I 打开 DevTools → Ctrl+Shift+P → "Disable cache" 打勾 → Ctrl+R
# 若关闭 DevTools 问题消失 → 大概率是缓存 / 打包资源不一致

# [P3] 渲染层边界查看（手动操作）
# DevTools → 右上角三个点 → More tools → Layers → 查看是否产生了过多合成层（>20 层即有概率卡）
```

## 7. 性能类问题

| 现象 | 典型描述 |
|------|----------|
| 启动慢 | 双击应用到 UI 可交互 > 10s |
| 对话卡 | 发消息后 UI 冻结、打字一卡一卡 |
| diff 加载长 | 文件变更卡片 diff 显示要等 5+s 才渲染 |
| 内存泄漏 | 持续使用 2h+ 后内存从 300M 涨到 1.5G+、越来越卡 |

### 排查步骤

| 步骤 | 操作 | 通过标准 |
|------|------|----------|
| 1 | 阶段打标定位 | 看启动日志：splash → init main → load preload → mount renderer 各阶段耗时 |
| 2 | React 重渲染分析 | React DevTools → Profiler 录制一次操作，找被误标记为 render 的热点组件 |
| 3 | 长任务诊断 | DevTools Performance → Record 6s 操作 → Main 火焰图找 >50ms 的红条 |
| 4 | Heap 快照对比 | 1. 初始态 Snapshot 1 2. 跑 5 轮典型操作 3. Snapshot 2 → Compare 视图看 Detached DOM / 增长对象 Top 10 |
| 5 | 慢 SQL | 打开 SQLite `sqlite3` → `.timer on` → 手动执行可疑查询，看 `Run Time` |
| 6 | diff 大文件分块 | 变更的文件是否 >5MB？大 diff 应走「按需展开 + 截断超长安卓」策略 |

### 快速诊断命令清单

```powershell
# [P1] 进程级资源占用（实时刷新看哪个子进程涨）
# 开着应用跑一段时间，再执行：
Get-Process electron |
  Select-Object Id, CPU, WorkingSet64, PagedMemorySize64, StartTime |
  Sort-Object WorkingSet64 -Descending |
  Format-Table -AutoSize

# [P2] Performance.mark 埋点（若已启用，日志里搜 perf）
Get-Content ~/.lumii/logs/*.log -Tail 300 |
  Select-String '\[perf\]|performance|console\.time' |
  Select-Object -Last 30

# [P2] SQLite 慢查询（临时对当前 DB 打开统计）
# sqlite3 ~/.lumii/data/agent-runtime.db
#   sqlite> .timer on
#   sqlite> .explain
#   sqlite> EXPLAIN QUERY PLAN SELECT ...（你怀疑慢的 SQL）;
#   看 SCAN FULL TABLE（全表扫）是否出现；应出现 SEARCH + USING INDEX

# [P3] Heap 快照采集（生产环境安全触发）
# DevTools → Memory → Heap snapshot → Take snapshot
# 两次 snapshot 后，第二个选 "Comparison"，按 "# Delta" 列降序，定位 Retainers 路径切断源头
```

## 快速分流决策图

所有问题先在 30 秒内完成以下分流：

```
问题出现
   │
   ├─ 「刷新/重启应用后是否消失？」
   │      ├─ YES → 偶发（检查 flaky、并发、缓存）
   │      └─ NO  → 必现（继续往下）
   │
   ├─ 「换到干净的 ~/.lumii 目录是否消失？」
   │      ├─ YES → 数据态问题（DB 坏/配置错/缓存脏）
   │      └─ NO  → 代码态问题（继续往下）
   │
   ├─ 「是否最近一次升级后才出现？」
   │      ├─ YES → 回归（git bisect 定位引入 commit）
   │      └─ NO  → 环境/外部依赖（网络、权限、模型、系统升级）
   │
   └─ 「curl 直连模型 / SQLite 直查 DB 是否正常？」
          ├─ YES → 应用层 Bug（按上面对应域的步骤深入）
          └─ NO  → 外部依赖问题（模型服务 / DB 文件坏 / 网络 / 权限）
```

**遇到任何问题的黄金前三步**：
1. **看日志**（`~/.lumii/logs/` 最新文件）
2. **最小化复现**（新建空会话 / 清缓存 / 只跑 1 步操作）
3. **隔离依赖**（用 curl / sqlite3 直连绕开应用代码，定位是应用层 Bug 还是外部依赖问题）
