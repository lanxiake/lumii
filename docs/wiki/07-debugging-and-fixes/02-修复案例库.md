## 案例 1：消息乱序修复

**问题分类**：渲染 / 子 Agent UI
**修复日期**：2026-09-07
**影响范围**：所有含子 Agent 调用且主 Agent 继续输出的对话场景

### 1.1 问题描述

在对话中，主 Agent 先输出一段文本，再调用子 Agent，并且在子 Agent 运行期间继续输出后续文本时，界面上子 Agent 的内容必定出现在主 Agent 后续输出之前。用户感知到明显的「时间倒序」——先回复的内容在最下面，后回复的在前面。

典型用户报告：
> 子 Agent 任务完成的结果块，总是插在我看到主 Agent「等待中...」这句话之前，顺序完全是乱的。

### 1.2 根本原因分析

#### 代码层定位

`ChatContainer/mergeAssistantParts.ts` 中合并父子 parts 的算法逻辑错误：

```typescript
// 旧代码（错误实现）
function mergeAssistantParts(parentParts, childParts) {
  // ...
  let insertAt = parent.length
  while (insertAt > 0 && parent[insertAt - 1]?.type === 'text') insertAt--
  return [...parent.slice(0, insertAt), ...child, ...parent.slice(insertAt)]
  //                                                  ^^^^^^^^^^^^^^^^
  //  错误：向前扫描找到第一个非 text 后插入，把末尾连续 text 挤到子 parts 之后
}
```

#### 时序场景还原

| 时间 | 事件 | 主 Agent parts 状态 |
|------|------|---------------------|
| T1 | 主 Agent 输出「开始处理...」 | `[text_A]` |
| T2 | 主 Agent 调用子 Agent (tool_call) | `[text_A, tool_call]` |
| T3 | 主 Agent 继续输出「正在等待子任务...」 | `[text_A, tool_call, text_B]` |
| T4 | 子 Agent 返回结果 `child_text` | 合并时刻 |

合并时旧算法执行：
- `insertAt` 从 3 递减，检查 `parent[2] === text` → 减到 2
- 检查 `parent[1] === tool` 停住 → 在位置 2 插入 child
- **结果**：`[text_A, tool_call, child_text, text_B]` ❌
- 显示顺序：T1 → T2 → **T4 → T3**（时间倒序）

#### 5 Whys 收敛

| 层级 | 回答 |
|------|------|
| 为什么显示乱序？ | 子 Agent parts 被插入到末尾 text 之前而非之后 |
| 为什么这么写？ | 为了让「工具调用块」不全部落在终稿文字之后，视觉上更紧凑 |
| 为什么没考虑主 Agent 继续输出？ | 假设子 Agent 返回前主 Agent 不会再输出 text（设计时的隐含假设） |
| 为什么假设不成立？ | 真实实现里子 Agent 是 async 模式，父 Agent idle 时可继续流式输出 |
| 为什么没被测试发现？ | 原测试只覆盖了「无 trailing text」场景，缺「主 Agent 继续输出 text」用例 |

### 1.3 修复方案

将合并逻辑改为「直接追加到末尾」，严格保持时间顺序：

```typescript
export function mergeAssistantParts(
  parentParts: readonly AssistantPart[] | undefined,
  childParts: readonly AssistantPart[] | undefined,
): AssistantPart[] {
  const parent = [...(parentParts ?? [])]
  const child = [...(childParts ?? [])]
  if (child.length === 0) return parent
  return [...parent, ...child]
}
```

**受影响文件**：
1. `apps/windows/src/renderer/pages/ChatPage/components/ChatContainer/mergeAssistantParts.ts`
2. `apps/windows/src/renderer/pages/ChatPage/components/ChatContainer/mergeAssistantParts.test.ts`

### 1.4 验证方法

#### 单元测试

新增覆盖「主 Agent 继续输出 + trailing text」用例：

```typescript
it('子 Agent parts 追加到父消息末尾，保持时间顺序', () => {
  const parent: AssistantPart[] = [
    { type: 'thinking', id: 'th-1', text: 'plan', status: 'done' },
    { type: 'tool', id: 't1', name: 'Read', args: {}, status: 'done' },
    { type: 'text', id: 'tx1', text: 'partial', status: 'done' },
    { type: 'text', id: 'tx2', text: 'final', status: 'done' },
  ]
  const child: AssistantPart[] = [
    { type: 'tool', id: 't2', name: 'Write', args: {}, status: 'done' },
  ]
  const merged = mergeAssistantParts(parent, child)
  expect(merged.map((p) => p.id)).toEqual(['th-1', 't1', 'tx1', 'tx2', 't2'])
})
```

运行：

```bash
cd apps/windows
pnpm test src/renderer/pages/ChatPage/components/ChatContainer/mergeAssistantParts.test.ts --run
```

预期结果：4 个测试全部通过（含原有的「无 trailing text」「child 为空」「mergeFileChanges」用例）。

#### 集成验证

- 287 个渲染层集成测试全部通过
- 手动场景：主 Agent 调用子 Agent → 等待 3 秒（期间父 Agent 输出 2 段 text）→ 子 Agent 返回 → 检查时间戳顺序

### 1.5 经验总结

| 维度 | 经验 |
|------|------|
| **设计假设** | 所有涉及「重新排序」的算法，必须列出依赖的隐含假设清单；async 并发场景永远不要假设父/子顺序 |
| **测试边界** | 合并类算法至少覆盖：无前缀、有前缀、无后缀、有后缀、中间夹异类类型、空输入 6 种排列 |
| **权衡记录** | 当初为了「视觉紧凑」引入插入逻辑，文档中应记录权衡理由；当假设失效时可快速回退 |
| **回归防护** | 单测中显式验证 ID 顺序数组而非只验证长度，避免因「恰好长度对但顺序错」漏检 |

## 案例 2：云同步冲突检测修复

**问题分类**：数据同步 / Windows FS / Agent 联动
**修复日期**：2026-09-07
**影响范围**：Windows 平台所有包含符号链接的工作空间；所有冲突场景下 Agent 是否介入

### 2.1 问题描述

两个独立现象同时出现：

**现象一（符号链接崩溃）**：
用户在 Windows 11 上触发云同步 adoptRemote（无关历史 → 采用远端）时，备份阶段直接抛错退出，同步中断：

```
EPERM: operation not permitted, symlink 'C:\myself\projects\my\open-source\lumii' ->
'C:\Users\75791\.lumii\workspace.lumii-sync-backup-1788746268591\projects\lumii'
```

**现象二（冲突无处理）**：
当检测到真实冲突（两边改了同一个文件，无法自动合并）时，虽然 `enterConflict` 方法被调用并把状态设为 `conflict`，但 Agent 完全不知道这件事。设计文档要求「冲突交给 Agent 判定并落决」，实际没有任何介入机制。

### 2.2 根本原因分析

#### 根因 1：`cpSync` 默认复制符号链接

`sync-manager.ts` 的 `adoptRemote` 使用默认参数的 `fs.cpSync`：

```typescript
fs.cpSync(this.workspaceDir, backupDir, {
  recursive: true,
  filter: (src) => !src.includes('.mtbot-vcs'),
  // ← 缺 verbatimSymlinks，默认行为：遇到符号链接 → 尝试创建符号链接
})
```

Windows 默认安全策略下，创建符号链接需要：
- 管理员权限（以管理员运行），或
- 开发者模式（Settings → Privacy & security → For developers → Developer Mode）

默认两者都不满足时 `EPERM`。

#### 根因 2：冲突检测无回调机制

`enterConflict` 的实现只更新了内部状态：

```typescript
private enterConflict(...) {
  this.conflict = { ... }
  this.setState('conflict', `检测到 ${this.conflict.files.length} 个冲突文件`)
  // 此处应该触发外部介入，但实际没有
  return { success: false, state: 'conflict' }
}
```

虽然设计文档写了「冲突交给 Agent 判定」，但实现时忘记插入钩子，导致：
- 目标表 `autonomous_goals` 中不会出现冲突处理目标
- `collectTickSignals` 无法感知，心跳也不会调度
- 用户只能眼睁睁看到 `conflict` 状态却无人处理

#### 根因 3：备份失败阻断核心流程

备份只是「防止 adoptRemote 万一失败可回退」的保护措施，但代码直接写了 `fs.cpSync` 无 try-catch，备份失败时同步中断，导致本来能成功的 adoptRemote 也被阻断。

### 2.3 修复方案

#### 修复 1：符号链接跟随 + 容错备份

```typescript
try {
  fs.cpSync(this.workspaceDir, backupDir, {
    recursive: true,
    filter: (src) => !src.includes('.mtbot-vcs'),
    verbatimSymlinks: false, // 跟随符号链接 → 复制实际内容，不再创建 symlink
  })
  logger.warn(`[adoptRemote] 本地已备份到 ${backupDir}`)
} catch (err) {
  logger.warn(`[adoptRemote] 备份失败（将继续同步）: ${err.message}`)
  // 备份失败不应阻止同步进行
}
```

#### 修复 2：冲突检测回调 + Agent 主动目标创建

**Step 1**：`CloudSyncManager` 增加回调接口：

```typescript
export class CloudSyncManager extends EventEmitter {
  private onConflictDetected?: (conflict: ConflictInfo) => void

  setOnConflictDetected(callback: (conflict: ConflictInfo) => void): void {
    this.onConflictDetected = callback
  }
}
```

**Step 2**：`enterConflict` 中触发回调：

```typescript
private enterConflict(...): { success: false; state: 'conflict' } {
  this.conflict = { ... }
  this.setState('conflict', `检测到 ${this.conflict.files.length} 个冲突文件，等待 Agent 处理`)

  if (this.onConflictDetected) {
    try {
      this.onConflictDetected(this.conflict)
    } catch (err) {
      logger.warn('[enterConflict] 冲突回调失败:', err.message)
    }
  }
  return { success: false, state: 'conflict' }
}
```

**Step 3**：`main/index.ts` 注入回调，创建自主目标：

```typescript
cloudSyncManager.setOnConflictDetected((conflict) => {
  const db = agentRuntimeBridge.db
  const goalId = `goal-sync-conflict-${Date.now()}`
  const now = new Date().toISOString()
  db.prepare(
    `INSERT INTO autonomous_goals
     (id, agent_id, type, description, trigger_reason, status, priority, metadata, created_at, approved_at)
     VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)`,
  ).run(
    goalId, 'assistant', 'system-maintenance',
    `解决云同步冲突：${conflict.files.length} 个文件冲突（${conflict.files.slice(0, 3).join(', ')}...）`,
    'cloud-sync-conflict', 'executing', 0.9,
    JSON.stringify({ conflictFiles: conflict.files, localOid: conflict.localOid, remoteOid: conflict.remoteOid }),
    now, now,
  )
})
```

**修复后完整流程**：

```
检测到冲突 → enterConflict() → setState('conflict')
                 ↓
          onConflictDetected 回调
                 ↓
      autonomous_goals 插入 executing 状态高优先级目标
                 ↓
      collectTickSignals 收集到该目标 → 心跳调度
                 ↓
      Agent 调 cloud_sync_read_file 读三方内容
                 ↓
      Agent 调 resolve_sync_conflict 落决 → sync-manager 应用并推送远端
```

### 2.4 验证方法

| 验证项 | 方法 | 预期 |
|--------|------|------|
| 符号链接不崩溃 | 在工作空间创建 `mklink /D subdir ..\..\other`，然后触发无关历史 adoptRemote | 日志出「备份失败（将继续同步）」但远端历史 checkout 成功执行 |
| 冲突目标创建 | 人工制造冲突（两边改同一文件），触发 sync | DB `autonomous_goals` 表新增 1 行，status=executing，priority=0.9 |
| 心跳调度 | 等待下一个 tick（默认 60s 或手动触发） | 日志出现收集到该 goal + Agent 调度记录 |
| Agent 工具调用 | 观察 Agent 是否使用冲突处理工具 | ToolRunner 锚点出现 `cloud_sync_read_file` + `resolve_sync_conflict` |
| 编译 + 单测 | `npx tsc --noEmit -p apps/windows/tsconfig.json` + `vitest run sync-manager.test.ts` | 0 TS 错误，15 个单测全通过 |

### 2.5 经验总结

| 维度 | 经验 |
|------|------|
| **跨平台 FS** | Node `fs` 默认行为跨平台差异极大；任何涉及 symlink/hardlink 的 API 在 Windows 上默认不能直接用，必须显式设置 `verbatimSymlinks/dereference` 等参数 |
| **保护 vs 核心** | 备份、日志、上报等保护措施失败时，绝不能阻断核心流程；保护逻辑必须 try-catch 并降级 |
| **设计落地校验** | 设计文档中写了「X → Y 介入」但 Y 是另一个模块时，必须在 Y 侧加集成测试验证「X 是否真的触发了 Y」，否则极易漏接 |
| **回调注入模式** | 低层 Manager（如 sync-manager）不应直接依赖高层 Bridge（如 agentRuntimeBridge）；用「setOnXxx(callback)」模式解耦，测试时可注入空回调或 Mock |

## 案例 3：数据库锁误检测诊断

**问题分类**：存储 / SQLite 并发 / Windows 进程管理
**修复日期**：2026-08（持续诊断，多轮迭代）
**影响范围**：用户数据持久化完整性、会话创建/保存

### 3.1 问题描述

用户反馈：「新建的会话对话后，重启应用就没了」。历史上一直正常，是近期出现的回归。用户还观察到每次重启似乎都要「重建数据库」。

诊断时发现的直接证据链：
- `~/.lumii/data/` 目录下存在 **38 个** `agent-runtime.db.new-*` 轮转文件（日期跨度 8/7~8/13）
- 主路径 `agent-runtime.db` mtime 停在 8/11 19:16，超过 40 小时未更新
- 10 份 `.db.bak` 备份文件的 MD5 全部相同
- 任务管理器中有 **4 个** `electron.exe`（PID 152892 / 162428 / 166264 / 186788）父进程已不存在，从 8/12 起持续运行

### 3.2 根本原因分析

#### `isIoErr()` 误分类：两种本质不同的错误被归为同一类

`packages/agent-runtime/src/storage/local-database.ts` 打开数据库时的逻辑：

```
SQLite 抛 SQLITE_IOERR* / disk I/O error
     ↓
isIoErr() 判定 → 「IO 错误 = 数据库损坏」
     ↓
只重试 1 次（清 WAL 后再开一次）
     ↓
仍失败 → 进入 rotateCorruptedDb()
     ↓
     ├─ 能重命名被锁文件 → 轮转正常（但下次启动仍回主路径 → 遗弃）
     └─ 连重命名都 EBUSY → 铸造全新路径 agent-runtime.db.new-<timestamp>
                              + 从最近备份恢复
                              + 抛弃仍被锁的原文件（含新写入的会话！）
```

#### 为什么被锁？——僵尸进程

4 个孤儿 Electron helper 进程：
- 父 PID 在进程表中不存在（父进程已退出）
- 通过 WMI 拿 `CommandLine` 字段为空 → `scripts/stop-dev.ps1` 的清理过滤逻辑只按 `CommandLine` 匹配 → 直接跳过 → 从未清理成功
- 持续持有 `agent-runtime.db` 句柄 → Windows 下独占写锁 → 任何新进程打开时触发 IOERR

#### 孤儿轮转文件

锁解除时（某次重启碰巧僵尸被杀），应用退回主路径文件 → 上一次轮转出的 `.new-<ts>` 文件里已经保存了用户的新对话，但这个路径再也不会被打开 → 孤儿文件，用户感知为「会话丢了」。

**实锤证据**：
- 直接打开当天最新轮转文件 `agent-runtime.db.new-1786594297016`，找到了两条当天的新会话（「你叫什么名字」「你好呀」）
- 这两条在其他任何轮转文件里都不存在 → 用户对话确实被保存了，但存进了应用不会再打开的侧支文件

### 3.3 修复方案

#### 修复 1：打开失败增加退避重试（给瞬时锁自然解除窗口）

```typescript
const LOCK_RETRY_DELAYS_MS = [200, 500, 1000, 2000]
// 依次等待 200ms → 500ms → 1000ms → 2000ms 后重试打开
// 任何一次成功 → 正常返回；全部失败才判定损坏
```

#### 修复 2：轮转路径指针侧车文件

新增 `agent-runtime.db.active-path` 纯文本侧车文件：

```
启动时流程：
  1. 尝试打开主路径 agent-runtime.db
       ├─ 成功 → 正常用，写入 active-path = 主路径
       └─ 失败（锁/损坏）→ ↓
  2. 读取 agent-runtime.db.active-path
       ├─ 内容存在 → 尝试打开上次轮转到的路径
       │      ├─ 成功 → **继续沿用它，不再铸造新库**
       │      └─ 失败 → ↓
       └─ 不存在 → ↓
  3. 铸造新路径 + 从备份恢复
       └─ 写入新路径到 active-path，供下次启动继续使用
```

**关键代码位置**：`packages/agent-runtime/src/storage/local-database.ts:391-528`

### 3.4 验证方法

| 验证场景 | 操作方法 | 预期 |
|----------|----------|------|
| 瞬时锁重试 | 人工开一个 SQLite CLI 持有写锁，再启动应用 | 日志出现重试 4 次后（期间手动关闭 CLI）成功打开主库 |
| 持续锁走指针 | 启动 4 个模拟的「僵尸」进程持锁 → 重启应用 3 次 | 只铸造 1 个新路径；3 次重启 active-path 都指向同一路径；3 次写入的数据在重启后均可见 |
| 孤儿文件不再增长 | 修复前有 38 个 `.new-*`；修复后持续使用 2 天 | `.new-*` 文件数量不再增长（或仅 +0 / +1） |
| 真实用户验证 | 开发环境复现后观察日志 | 启动日志显示「主库路径持续被锁定，继续使用此前轮转路径」 |
| 单测 | `pnpm --filter ./packages/agent-runtime test local-database.test.ts` | 新增的重试与指针场景单测全通过 |

### 3.5 经验总结

| 维度 | 经验 |
|------|------|
| **错误分类必须精确** | 「IOERR」是包含几十种子错误的复合类；瞬时锁和真实损坏是本质不同的两类问题，绝不能合并处理；至少要区分：锁超时、权限不足、磁盘真实损坏 3 条路径 |
| **侧车指针文件** | 当「主路径可能不是当前在用文件」时，用一个轻量纯文本指针（< 50 字节）解决「下次启动找到当前在用文件」的问题，是一种通用范式 |
| **僵尸进程清理** | Windows 孤儿进程的 `CommandLine` 可能是空字符串；清理脚本除了按 `CommandLine` 过滤，必须再加一层「进程名 == electron.exe + 父 PID 已不存在 == 孤儿 == 直接杀」的兜底判断 |
| **备份有效性检查** | 定期（如启动时）比对近 10 份备份的哈希；若全部相同，意味着备份一直在复制同一个过期快照，是非常严重的信号，必须告警 |

## 案例 4：语音通话诊断与修复验证

**问题分类**：语音交互 / ASR 配置 / 音频路由
**诊断日期**：持续（含离线 Paraformer、流式切换、设备权限、TTS 通道）
**影响范围**：语音通话实时转写、ASR/TTS 全链路

### 4.1 问题描述

用户反馈：「对话中点击通话按钮后，我说话的时候界面上没有实时显示识别文字（只有我停止说话后才发送）」。用户期望：
1. 说话过程中实时显示中间识别结果（partial transcript）
2. 停止说话后自动把最终识别结果发送给 Agent

实际表现：第 1 点完全失效，第 2 点仍正常工作。

### 4.2 根本原因分析

#### 定位代码链路

实时转写推送路径：

```typescript
// voice-service.ts:518-530
if (isSpeaking && this.asrStream && this.stateMachine.isOneOf('listening', 'recognizing')) {
  const partial = this.asrStream.getPartialText()  // ← 读中间结果
  if (partial && partial !== this._lastPartial) {
    this._lastPartial = partial
    this.pushVoiceEvent({
      type: 'voice:transcript',
      callId: this.callId,
      text: partial,
      isFinal: false,  // ← 实时转写事件
    })
  }
}
```

前端接收：`useVoiceCall.ts:177-179` 监听 `isFinal=false` 更新 `partialTranscript` 状态。

#### 根因：当前 ASR Provider 不支持中间结果

配置为 `config.asr.provider = 'local-paraformer'`（离线 Paraformer），对应实现：

```typescript
// asr-engine.ts:190-192
class LocalOfflineParaformerAsr {
  getPartialText(): string {
    return ''  // 注释明确：「离线模式无中间结果」
  }
  resetAndGetResult(): string {
    // 整段结束后一次性返回
  }
}
```

`getPartialText()` 恒返回空字符串 → `if (partial && ...)` 永远 false → `voice:transcript (isFinal=false)` 事件永不推送 → 前端状态不更新。

#### 最终发送链路为何仍正常

VAD（Voice Activity Detection）检测到完整语音段结束后：
1. 调 `resetAndGetResult()` 获取最终文本（整段识别，离线模式可用）
2. 推 `voice:transcript (isFinal=true)` 事件
3. 调用 `submitToAgent()` 发送给 Agent

这条路径不依赖中间结果，所以正常工作。

## 案例 5：上下文压缩边缘案例修复

**问题分类**：算法边界 / Token 预算 / 去重策略
**诊断日期**：2026-08-21 ~ 2026-08-24（四轮测试迭代）
**影响范围**：长对话连续性、压缩后消息丢失 / 重复

### 5.1 问题描述

上下文压缩多层引擎在边界场景下出现 3 类异常：

| 异常 ID | 场景 | 用户感知 |
|---------|------|----------|
| E-1 截断位置错 | 在 JSON / Markdown 表格 / 代码块中间截断 | 后续渲染破版、JSON 解析报错、代码语法高亮失效 |
| E-2 Token 预算溢出 | 小 token 窗口下摘要自己占了 90%+ 预算 → 挤出用户关键消息 | 用户问「A」但压缩后上下文里完全没有「A 相关的原消息」，Agent 答非所问 |
| E-3 重复注入 | 同一消息同时出现在「保留的原消息区」和「摘要区」 | Agent 看到同一段内容两次，回复重复引用，统计 token 虚高 |

### 5.2 根本原因分析

#### E-1 截断位置错误

原实现按「消息条数 + 字符数」硬截断，不感知结构边界：

```
截断前最后一条消息（代码块）：
  ...
  ```typescript
  function foo() {
    return a +  ← 截到这里，后面被丢了！

压缩后：
  summary: "...（含半个未闭合的代码块）"
```

根因：截断策略里只有「数量阈值」没有「结构完整性检查」。Markdown 的结构单元（代码块、表格、列表、数学公式）可能跨几百行，简单按消息截断必然破坏完整性。

#### E-2 Token 预算溢出

原预算分配逻辑：

```
可用预算 = 当前 usage - 保留条数 × 平均单条 token
摘要生成 → 不感知剩余预算 → LLM 生成了一个极长的 4000 tokens 摘要
挤掉：原本应该保留的用户原消息（占 3500 tokens）
结果：摘要 4000 + 保留原消息 500 = 4500 用户有效上下文严重缩短
```

根因：摘要生成前未把「剩余可用 token 数」作为硬约束注入到 Prompt，也没有摘要后二次校验（摘要 token 数 / 预算总额 > 阈值时自动二次压缩）。

#### E-3 重复注入

去重判定的粒度是「整条消息 ID」，但摘要算法在抽取要点时可能：
1. 把一条已在「保留区」的消息的**部分内容**又写进摘要
2. 保留区消息 ID 和摘要区内容 ID 不同 → ID 级去重没命中
3. 最终用户同一段语义被 Agent 读两次

根因：缺「语义级相似度」二次校验。ID 去重只防「整条消息重复」，不防「摘要抽取了保留区的内容子集」。

### 5.3 修复方案

#### E-1 结构感知截断

在截断前增加「结构完整性回退」步骤：

```
候选截断点 = 按数量阈值计算的消息边界
  ↓
对候选截断点前最后 3 条消息做结构检查
  ├─ 代码块是否闭合（``` 对计数平衡）
  ├─ 表格是否有末行尾 |
  ├─ JSON 是否能被 JSON.parse 成功
  ├─ HTML 标签是否闭合（简单栈匹配）
  ↓
若有任何一项未闭合 → 截断点**向前回退一条消息**重新检查
  ↓（最多回退 3 条；回退 3 条仍不完整则用「移除该条不完整消息」兜底）
```

#### E-2 摘要预算硬约束 + 二次裁剪

1. **生成前**：把 `maxSummaryTokens = Math.floor(可用预算 * 0.25)` 注入到摘要 Prompt，明确要求 LLM 摘要长度不超过该值（加 token 计数 API 兜底）
2. **生成后**：若 `summaryTokens > maxSummaryTokens × 1.2`，触发二次压缩：
   - 再调一次摘要模型，输入 = 过长摘要本身，Prompt：「压缩到 N 字以内，保留 3 个核心要点」
   - 或本地启发式截断（取前 N 句 / 前 N 字符，配合句号切分）

#### E-3 保留区 vs 摘要区语义去重

在压缩提交事务前增加「内容级去重校验」：

```
S = 摘要文本集合（按句子切分，>50 字的）
R = 保留消息文本集合（按句子切分，>50 字的）

对每条 s ∈ S：
  sim = 最大相似度（与 r ∈ R 的 0~1 相似度，Jaccard 或 Embedding cosine）
  if sim > 0.75:
    s 从摘要中移除，附标记「该内容已在保留区」
```

默认采用词级 Jaccard（成本 O(n²) 但 n 不大）；可选 Embedding 余弦相似度（需调用模型但更准确）。

| 维度 | 经验 |
|------|------|
| **边界用例设计法** | 对任何「截断/裁剪/压缩」类算法，边缘用例设计先枚举结构单元矩阵（代码块/表格/JSON/HTML/数学公式），再分别构造，不要依赖真实用户碰运气暴露 |

| **真实用户日志抽取** | 边缘场景最高效来源是「从用户日志的失败案例」反推构造用例；真实触发过的 Case 1 个 > 凭空想 10 个 |
