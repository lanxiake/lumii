# 调试方法论

## 1. 科学调试六步法

科学调试是一个系统化的「假设驱动验证」过程，避免盲目试错。遵循以下六步循环，保证定位效率和可追溯性。

| 步骤 | 名称 | 核心动作 | 输出物 |
|------|------|----------|--------|
| ① | 现象定义 | 清晰记录「在什么条件下，发生了什么，期望是什么」 | 可复现步骤 + 截图/日志片段 |
| ② | 提出假设 | 基于代码结构和现象，列出 ≥2 个可能根因（按概率排序） | 假设清单 + 每假设的预测现象 |
| ③ | 插桩取证 | 增加日志、断点、探针，不修改业务逻辑 | 结构化日志 / 变量快照 / evidence |
| ④ | 稳定复现 | 按步骤 100% 复现，复现失败则回到 ① | 最小化复现脚本 / 用例 |
| ⑤ | 分析根因 | 比对证据与假设，排除错误假设，收敛到真因 | 根因分析文档（5 Whys / 鱼骨图） |
| ⑥ | 修复验证 | 最小改动修复，回归测试覆盖，修复前后 evidence 对比 | 修复 commit + 测试通过记录 |

**六步法循环图（文字版）**：

```
现象定义 ──→ 提出假设
   ↑              │
   │              ↓
修复验证 ←── 分析根因
   ↑              │
   │              ↓
稳定复现 ←── 插桩取证
```

**失败路径**：任何一步证据不足或结论矛盾 → 回退到上一步重新审视假设，禁止跳步直接改代码。

## 2. 根因分析技术

### 2.1 5 Whys 法

连续追问 5 次「为什么」，穿透症状直达根本原因。

**示例：新建会话丢失问题**

| 层级 | 问题 | 回答 |
|------|------|------|
| 第 1 层 | 为什么会话丢失？ | 数据被存进了一个 `.db.new-<ts>` 轮转文件，应用下次启动不再打开它 |
| 第 2 层 | 为什么存进轮转文件？ | 启动时判定主库损坏，执行了 `rotateCorruptedDb()` |
| 第 3 层 | 为什么误判损坏？ | `isIoErr()` 把瞬时文件锁和真实损坏都归为同一类错误，只重试 1 次就判损坏 |
| 第 4 层 | 为什么文件锁存在？ | 4 个僵尸 `electron.exe` 进程（PID 152892 等）父进程已退出但未清理，持续持有锁 |
| 第 5 层 | 为什么僵尸进程未被清理？ | `scripts/stop-dev.ps1` 的过滤依赖 `CommandLine` 字段，而孤儿 Electron helper 的该字段为空 |

**根因结论**：第 5 层是根源，但第 3 层是可以立即修复的系统性缺陷（增加退避重试 + 轮转指针）。

### 2.2 鱼骨图（因果图）

按大类梳理所有可能因素，避免被第一个想到的原因锁死思路。

```
                 [问题现象]
                     │
     ┌───────────────┼───────────────┐
     ↓               ↓               ↓
  [人员]          [流程]          [工具]
  ･操作不熟       ･缺少回归        ･类型检查漏跑
  ･假设不验证      ･审查不充分      ･日志级别不足
  
     ┌───────────────┼───────────────┐
     ↓               ↓               ↓
  [代码]          [数据]          [环境]
  ･并发时序       ･Schema 不一致   ･Node 版本
  ･边界条件       ･脏数据          ･Windows 权限
  ･错误路径       ･种子失效        ･网络/代理
```

**使用方式**：
1. 顶部写现象（必须具体，如「云同步 adoptRemote 抛 EPERM」而非「同步坏了」）
2. 六类下写具体怀疑点，每类至少写 2 条
3. 对每条从最容易验证的开始逐条排除（对比法 / 排除法）

### 2.3 对比法

找一个「工作正常的」对照组，逐项比对差异。

| 对比维度 | 示例 |
|----------|------|
| 时间 | 昨天能工作的代码版本 vs 今天失败的 HEAD |
| 环境 | 机器 A 正常 / 机器 B 失败 → 比对 Node 版本、.lumii 配置 |
| 输入 | 小文件成功 / 大文件失败 → 阈值/内存/分块逻辑 |
| 配置 | 默认 Provider 成功 / 自定义配置失败 → 比对 JSON diff |

**实施要点**：用 `git diff` 精确对比代码、用 JSON diff 对比配置、单变量每次只改一项。

### 2.4 排除法（二分法的通用版）

将可能因素对半分，逐次排除不可能的一半，直到收敛。

```
因素列表 [A, B, C, D, E, F, G, H]
   ├─ 禁用 [A,B,C,D] → 问题仍存在 → 排除左半，根因在 [E,F,G,H]
   │   ├─ 禁用 [E,F] → 问题消失 → 根因在 [E,F]
   │   │   ├─ 单独启用 E → 有问题 → 根因 = E
   │   │   └─ 否则 → 根因 = F
   └─ 若禁用 [A,B,C,D] 问题消失 → 对左半继续二分
```

## 3. 日志分析方法

### 3.1 结构化日志字段规范

所有生产日志必须包含以下字段，便于 grep / jq 过滤：

| 字段 | 示例 | 用途 |
|------|------|------|
| 时间戳 | `2026-09-07T03:21:45.123Z` | 时间线重建 |
| 模块前缀 | `[SubagentBroker]` `[compactContextAsync]` | 模块定位 |
| 实例标识 | `session=ada2720c…` `agent=assistant` | 区分多会话/多 Agent |
| 状态动词 | `started / ok / failed / rejected` | 条件过滤 |
| 关键数值 | `idle=312s/300s used=412K floor=390K` | 阈值判断 |

### 3.2 常用搜索过滤命令

```powershell
# 按模块前缀过滤
Select-String -Path .lumii-dev.log -Pattern '\[SubagentBroker\]'

# 按错误级别 + 关联上下文前后 5 行
Select-String -Path .lumii-dev.log -Pattern 'ERROR|WARN' -Context 5,5

# 按会话前缀关联完整链路（8 字符足够唯一）
Select-String -Path .lumii-dev.log -Pattern 'ada2720c'

# 用 jq 分析 JSONL evidence
Get-Content wiki-cli-evidence.jsonl | ForEach-Object { $_ | ConvertFrom-Json } |
  Group-Object status | ForEach-Object { "$($_.Name): $($_.Count)" }

# 时间窗口过滤（提取某小时的日志）
Select-String -Path .lumii-dev.log -Pattern '2026-09-07T03:'
```

### 3.3 时间线重建

复杂 Bug 往往是时序问题。按以下步骤重建事件序列：

1. **抽取锚点**：从报错栈或用户报告中取精确时间戳
2. **前后 2 分钟窗口**：将该时间点前后 2 分钟全部日志按时间升序排列
3. **分层标记**：为每行打标签（Main/Renderer/DB/Model/IPC）
4. **因果连线**：从请求 → 处理 → 响应 → 副作用 → 下一轮请求 串联箭头
5. **标记异常点**：在时间线上用 🔴 标记「缺少预期事件」「顺序颠倒」「数值异常」

**典型时间线异常模式**：
- 🔀 乱序：B 应该在 A 后但出现在前（如消息乱序子 Agent 插入位置错误）
- 🕳️ 空洞：预期的 `finalizeRun` 从未出现（投递链断裂）
- ⚡ 尖刺：10ms 内连续写入 DB 数千次（缺少事务合并）
- 💤 超长空闲：某步等待 30s 无进展（超时未触发，死锁）

## 4. Electron 应用调试技巧

Electron 三层架构（Main / Preload / Renderer）需要分别调试，各自有独立调试器。

### 4.1 三层独立调试表

| 层 | 启动方式 | 调试器入口 | 可观察对象 |
|----|----------|------------|------------|
| **Main 主进程** | `pnpm dev` 时加 `--inspect=9229` | Chrome 打开 `chrome://inspect` 或 VS Code Attach | `sync-manager`、`voice-service`、`local-database`、文件系统操作 |
| **Preload 预加载** | 继承主进程 inspect | 同上 | `ElectronAPI` 暴露、contextBridge 调用、序列化/反序列化 |
| **Renderer 渲染进程** | 应用启动后按 F12 或 Ctrl+Shift+I | Chromium DevTools | React 组件状态、Hooks、UI 事件、网络请求 |

### 4.2 主进程调试关键步骤

1. `set ELECTRON_ENABLE_LOGGING=1` + `set ELECTRON_ENABLE_STACK_DUMPING=1` 启动前开启原生日志
2. `console.log` 会同时输出到 DevTools Console 和终端 stdout
3. 断点调试：`debugger;` 语句或 VS Code `.vscode/launch.json` 的 Attach 配置
4. 崩溃定位：`*.dmp` 崩溃转储文件，使用 Electron symbol 文件解析

### 4.3 渲染进程 React 调试

| 工具 | 用途 |
|------|------|
| React DevTools 扩展 | 组件树、Props、Hooks、Context、重渲染高亮 |
| Performance 面板 | 长任务定位、帧分析、交互卡顿火焰图 |
| Memory 面板 | Heap Snapshot 对比、内存泄漏定位、Detached DOM 节点 |
| Network 面板 | IPC 之外的 HTTP / WebSocket 通道（模型 API、搜索等） |

## 5. Agent 运行时的状态快照

Agent 是复杂状态机，出问题时需要「拍片子」——导出核心状态做离线分析。

### 5.1 关键状态导出清单

| 状态 | 表/文件位置 | 导出方法 | 分析要点 |
|------|-------------|----------|----------|
| Goal 目标状态 | `autonomous_goals` 表 | `sqlite3 .dump` 或 CLI `autonomous goals list` | 是否卡在 pending、approved_at 是否填充、优先级是否合理 |
| 记忆状态 | `memory_entries`、`wiki_pages` | 按会话或时间窗口 select | 召回命中/遗漏、向量 embedding 是否生成、重复行 |
| Rating 满意度 | `autonomous_ratings` | `autonomous status --agent assistant` | 四维（能力/人格/记忆/行动）得分是否错位、时间窗口数据量是否足够 |
| 反思记录 | `autonomous_reflections` | JSON 列展开 | rootCause 是否合理、actionItem 是否可执行 |
| Prompt 变体 | `prompt_variants` | successRate 排序 | 是否 NaN 污染、基线是否优先排序 |
| 运行时配置 | `runtime_state` 表 | `SELECT * FROM runtime_state WHERE key LIKE 'compact%'` | 冷却键是否过期、flag 是否持久化正确 |

### 5.2 导出脚本标准流程

```bash
# 1. 安全复制（避免锁库）
cp ~/.lumii/data/agent-runtime.db /tmp/agent-runtime-snapshot-$(date +%s).db

# 2. 导出目标表（只读）
sqlite3 /tmp/agent-runtime-snapshot-*.db <<SQL
.headers on
.mode json
.output goals-snapshot.json
SELECT id, status, priority, created_at, approved_at, trigger_reason
FROM autonomous_goals ORDER BY created_at DESC LIMIT 50;
.output
SQL

# 3. 与代码基线版本一起归档，保证可离线回溯
git rev-parse HEAD > snapshot-git-commit.txt
```

## 6. 数据库问题排查

SQLite 是项目核心存储，问题集中在锁、慢查询、Schema 迁移三类。

### 6.1 SQLite WAL 与锁机制速查

| 现象 | 可能原因 | 诊断命令 |
|------|----------|----------|
| SQLITE_BUSY | 另一连接持有写锁未释放 | `PRAGMA busy_timeout = 5000;` 观察是否自愈 |
| WAL 文件巨大（>100MB） | checkpoint 长时间未触发 | `PRAGMA wal_checkpoint(TRUNCATE);` |
| 频繁 IOERR 但磁盘正常 | 僵尸进程持锁（Windows 常见） | 任务管理器查同目录 `agent-runtime.db` 多进程句柄 |
| 读得到旧数据 | 快照隔离 + 长事务未结束 | 确保所有 SELECT 均在自动提交模式短事务 |

**busy_timeout 最佳实践**：
- 所有 `new DatabaseSync()` 后立即执行 `PRAGMA busy_timeout = 5000`
- 重试退避：`200ms → 500ms → 1000ms → 2000ms`（如 `local-database.ts` 的 LOCK_RETRY_DELAYS_MS）

### 6.2 慢查询排查

```sql
-- 1. 启用慢查询日志（>500ms 记录）
PRAGMA profile = 500000;   -- 单位微秒

-- 2. EXPLAIN QUERY PLAN 分析可疑 SQL
EXPLAIN QUERY PLAN
SELECT * FROM memory_entries WHERE vector MATCH ? AND created_at > ?;

-- 3. 索引覆盖检查
PRAGMA index_list('memory_entries');
PRAGMA index_info('idx_memory_entries_created_at');

-- 4. 重建统计（统计陈旧导致选错执行计划）
ANALYZE;
```

### 6.3 .dump 数据导出与修复

```bash
# 1. 完整逻辑导出（即使 DB 部分损坏也能抢救可读数据）
sqlite3 agent-runtime.db .dump > agent-runtime-dump-$(date +%s).sql

# 2. 过滤仅导数据（不含 CREATE TABLE）做迁移核对
sqlite3 agent-runtime.db '.dump --data-only' > data-only.sql

# 3. 修复：从 dump 重建（解决页内 corruption、索引损坏）
mv agent-runtime.db agent-runtime-corrupted.db
sqlite3 agent-runtime.db < agent-runtime-dump-*.sql
ANALYZE;
```

### 6.4 锁问题诊断（数据库锁误检测案例经验）

- 孤儿轮转文件识别：`ls -la ~/.lumii/data/agent-runtime.db.new-*` 统计数量；>3 个就是锁问题反复触发
- 活跃指针文件：检查 `agent-runtime.db.active-path` 侧车文件内容是否指向当前真正打开的 DB
- 备份有效性：对 10 份 `.bak` 做 `md5sum`，若全部相同说明备份一直在复制过期快照，不是实时文件
- 僵尸句柄：Windows 下用「资源监视器 → CPU → 关联的句柄」搜索 `agent-runtime.db`，找到 PID 后再查其父进程是否已退出

## 7. 性能调试

性能问题的核心是「测量，不要猜」——先定量定位瓶颈，再动手优化。

### 7.1 三级定位法

| 层级 | 工具 | 输出 | 定位精度 |
|------|------|------|----------|
| 粗粒度 | `console.time('label')` + `console.timeEnd('label')` | label: 1234ms | 函数块/模块级 |
| 中粒度 | `performance.mark()` + `performance.measure()` | 结构化测量（可导出 PerformanceEntry 数组） | 子步骤级 |
| 细粒度 | Chrome DevTools Performance 面板 / `--cpu-prof` | 火焰图（C++/JS 全栈） | 单函数/单行级 |

### 7.2 性能 API 标准用法

```typescript
// 单次测量
console.time('ingest-docx')
await ingestDocx(path)
console.timeEnd('ingest-docx') // 输出：ingest-docx: 2341.52ms

// 结构化多点测量
performance.mark('compact:start')
performance.mark('compact:summary-gend')
performance.mark('compact:commit-done')

performance.measure('summary-phase', 'compact:start', 'compact:summary-gend')
performance.measure('commit-phase', 'compact:summary-gend', 'compact:commit-done')

const measures = performance.getEntriesByType('measure')
measures.forEach(m => logger?.perf?.('[compact]', `${m.name}=${Math.round(m.duration)}ms`))
performance.clearMarks()
performance.clearMeasures()
```

### 7.3 DevTools Performance 面板分析要点

- **Main 线程火焰图**：宽度 = 耗时，找最宽的横条；黄色 = JS 执行，紫色 = 样式/布局，绿色 = 绘制
- **长任务标记**：>50ms 的红色 RAIL 条，直接对应可感知卡顿
- **交互时间（INP）**：点击事件点到第一个视觉反馈帧之间的间隔，目标 < 200ms
- **内存趋势**：Performance 面板勾选 Memory，录完看 Heap 曲线是否锯齿上升（泄漏）

## 8. 二分定位法

当不知道「哪一个 commit / 哪一段代码 / 哪一半输入」引入了问题时，用二分法对数级缩小范围。

### 8.1 Git Bisect（代码版本二分）

```bash
# 1. 启动 bisect，标记两端
git bisect start
git bisect bad HEAD          # 当前版本坏
git bisect good v1.2.0       # 已知某旧版本好

# 2. Git 自动切到中点版本
#    → 运行测试 → 报告结果

git bisect bad               # 当前版本仍坏 → 说明问题更早引入
# 或
git bisect good              # 当前版本好 → 说明问题在之后

# 3. 约 ⌈log2(N)⌉ 步后，Git 输出：
#    <commit-hash> is the first bad commit

# 4. 结束 bisect，回到原分支
git bisect reset
```

**自动化**：如果有可脚本化的复现测试，用 `git bisect run ./repro-test.sh` 全自动跑完。

### 8.2 注释隔离法（代码块二分）

不知道 bug 在哪个函数时：

1. 把可疑文件的函数按上半/下半两组
2. 先注释上半组（stub 返回 mock 结果），看 bug 是否还存在
3. 若还存在 → 在下半组继续二分；消失 → 在上半组继续二分
4. 约 7 步可定位到单函数（100 函数规模）

### 8.3 半量输入法（输入规模二分）

输入规模大才复现的 bug：

1. 拿 10000 条输入复现 bug
2. 切前 5000 条测试：
   - 仍复现 → 继续对半
   - 不复现 → 切换到后 5000 条，或混合对半（交错二分）
3. 最终拿到最小可复现输入，通常只有几十行甚至几行，提交 issue 附带即可
