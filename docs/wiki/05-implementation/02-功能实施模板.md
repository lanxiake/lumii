# 功能实施模板

本文档提供四大标准模板：
- 标准设计文档结构（对应 `docs/design/**`）
- 标准实施计划结构（对应 `docs/plans/**`）
- 交付总结模板（对应 `docs/plans/**/交付总结.md` 与 `docs/implementation/**`）
- 问题修复文档模板（对应 `docs/fix/**`）

所有模板结构都提炼自现有设计 / 计划 / 交付文档的实际写法。

#### 1.2.1 现状事实核查

**必须有证据，不要空想痛点**。推荐三种写法：

| 现有资产 | 位置 | 说明 | 能直接用？ |
|---------|------|------|----------|

| MemoriesPage UI | `apps/windows` renderer | 记忆列表页 | ⚠️ 要加 Wiki Tab |

**写法 C：代码实勘结论**（例：子 Agent 计划 §0）

#### 1.4.3 核心流程

用「步骤编号 + 一句话」写出主流程。例：云同步 §6 同步主流程：

1. UI 触发 `syncNow()` → 调 main `cloudSync:syncNow`。
2. Handler 走加锁 `acquire(lockKey)`，防重入。
3. 读上次 HEAD → `git fetch --prune`。
4. 导出数据 → 写入工作区。
5. 冲突检测：双向合并。
6. `git add` + `git commit`（无变更就跳过）。
7. `git push` → 更新 HEAD 标记 → `send('cloudSync:status', state)` → 解锁。

### 2.2 Global Constraints（强制读）

**独立章节列出硬约束，参考自主进化 Agent P0 §全局约束（22 条范式）精简版**：

```markdown
## 全局约束（Global Constraints）

**任何代码不得违反。若确有必要违反，必须在 PR 中明确指出并说明原因 + 走评审。**

1. MVP 范围严格限定：本期不做 worktree、不做跨进程恢复、不做 MOA 多子树。
2. 用户审批必须：子 Agent 非自身权限一律走确认弹层；「始终允许」以 peerId 持久化。
3. 配置即代码：所有算法参数（并发帽、stall 阈值、VERDICT 保留率）写 `config.ts` 常量 + 注释，不散落代码。
4. 数据库 Schema 完整性：新增表/列必须提供 `_migration_xxx.up.sql` 和 `_migration_xxx.down.sql`；新列一律 DEFAULT NULL / 可空。
5. 算法一致性：列表（filter/sort/map）遍历顺序必须确定性（主键 / timestamp ASC），并发结果可复现。
6. 可观测性强制：每个关键编排步骤打 INFO 日志（subagentId + state）；异常必须带 code + stack。
7. 单元测试优先：算法/编排辅助类的测试覆盖率 ≥ 80%；先写失败测试再实现。
8. 集成测试必需：至少 2 个端到端闭环（成功投递 + 停滞检测中断）。
9. 隐私安全：日志不落用户消息原文 / token / context_token；敏感字段掩码。
10. 灰度发布支持：提供 `AGENT_SUBAGENT_ENABLED` 环境变量 killswitch。
11. 回滚预案：特性开关关闭时，父 Agent 仍按原有同步逻辑工作。
12. 不引入新依赖：保持现有 deps；如确需引入，先升级并跑 `pnpm audit`。
13. 不改变现有公共 API：`SessionOrchestrator.run()`、`ToolsBridge.runTools()` 签名不变。
14. 命名规则：通道 `domain:action`（kebab）；变量 camelCase；类型 PascalCase；文件名跟目录风格。
15. `packages/pet-core` 纯 TS：不得依赖 React / Electron / Pixi / DOM；如放类型必须纯数据无副作用。
```

### 2.3 §0 代码实勘结论（可选，但强烈推荐）

适合改现有模块的大功能。两张表：

**A. 现状锚点**

| 代码位置 | 当前状态 | 要怎么改 |
|---------|---------|---------|
| `orchestrator.run()` | 同步 return | 加 `hooks.onAsyncDone(subagentId, result)` 钩子位 |

3. SQLite 默认 WAL，activity 扩展大字段建议用 JSON TEXT，避免 BLOB 难查。

## 2. 根因分析

### 2.1 根本原因（Only ONE True Root Cause）
一句话点破。例：
> 主进程 handler 直接透传 renderer 传过来的 `accessToken`，但 keytar 读到的字段是 `accessTokenEncrypted`，导致两次来源不一致，触发 GitCode 401。

### 2.2 为什么之前没发现
- 单测用 fake keytar，fake 实现直接 return `accessToken`；真实 keytar 是加密字段。
- 手测只跑了「首次保存 → 立即同步」路径，没跑「重启 Lumii 后再同步」路径。

## 3. 修复方案

### 3.1 方案对比
| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：统一 keytar 侧字段名 | 把 fake 改对齐真实 | 改动最小 | 历史脏 token 仍无法用 |
| B：两处统一走 `getDecryptedAccessToken()` helper | 抽 helper + 双测 | 根治，兼容老库 | 多改 2 个文件 |

**选型**：B。理由：根治 + 兼容历史数据。

### 3.2 实际修改点
- 文件 1：`apps/windows/src/main/services/cloud-sync/keytar-helper.ts` → NEW，导出 `getDecryptedAccessToken()` 兼容迁移。
- 文件 2：`apps/windows/src/main/services/cloud-sync/manager.ts:281` → 调用上述 helper。

- `migrations/021_fix_cloud_sync_tokens.up.sql`：把旧字段改写到兼容列（幂等）。
