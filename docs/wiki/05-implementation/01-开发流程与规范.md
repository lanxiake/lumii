# 开发流程与规范

---

## 一、标准开发流程（需求 → 交付六段式）

所有跨功能/跨层的功能，严格按以下六步走，缺任何一步都不允许合并到主分支。

### 1.1 需求分析（Requirement）

**产出物**：问题陈述 + 数据证据 + 非目标清单。

**检查项**：
- 是否用代码事实 / 目录扫描 / 用户故事证明了问题真实存在？
- 是否明确了本期「不做什么」（Non-Goals），写在文档头部？
- 是否把需求条目按 P0/P1/P2 分层？
- 是否识别出跨层（main/preload/renderer）改动？如果有，进入 §二 额外流程。

**参考**：`docs/wiki/02-requirements/01-需求分析方法论.md`。

---

### 1.2 设计文档（Design）

**产出物**：`docs/design/<领域>/YYYY-MM-DD-<功能名>-design.md`。

**必填章节**（顺序不要改）：
1. 日期、状态（设计待评审 / 已确认 / 已废弃）、作用范围
2. 结论摘要表（4~6 行，覆盖主目标、范围、技术路线、最大风险）
3. 背景 + 代码事实核查
4. 方案对比与选型（至少 2~3 个方案，A/B/C 以及选择理由）
5. 核心设计（架构图、数据模型、关键流程）
6. 模块划分与文件落点
7. 安全 / 隐私 / 风险与缓解
8. 分期（P0/P1/P2 或 Phase 1/2/3）与每一期退出标准
9. 测试与验收（单测点 + 手测点 + 性能目标）

**评审通过后再进入下一步**：设计文档评审不通过的，不允许写任何实施代码。

---

### 1.3 实施计划（Plan）

**产出物**：`docs/plans/<领域>/YYYY-MM-DD-<功能名>-implementation-<阶段>.md`。

**必填章节**：
1. Goal（一句话目标，可验证）
2. Architecture（高层架构 + 模块边界）
3. Tech Stack（强调**不引入什么**依赖）
4. Global Constraints（不可违反的硬约束：如不改公共 API、不引入 ML 框架、日志不落用户消息）
5. File Map（新增 / 修改文件清单 + 职责）
6. Task 分解（按依赖关系排序，每个 Task 含：做什么、改哪些文件、验证命令）
7. 任务依赖图（ASCII 或列表式，明确先做哪几个 Task）
8. 工作量估计与里程碑
9. 风险与缓解
10. 验收标准清单（checkbox 形式，便于后续逐个打勾）

**TDD 约束（来自自主进化 Agent 等多个计划的共识）**：每个算法模块和核心编排模块**先写失败测试，再实现功能代码**。模块级测试覆盖率要求 ≥ 80%。

---

### 1.4 实施（Implementation）

**执行原则**：
1. 严格按 Task 顺序走，跳 Task 要在提交说明中解释原因。
2. 每个 Task 完成后**单独跑验证命令**，并在本 Task 下记录结果（失败要写原因 + 绕过时的额外代码）。
3. 每个 Task 单独一次 Commit，信息格式采用 Conventional Commit：
   ```
   feat(<scope>): <完成了什么>
   - <子项 1>
   - <子项 2>
   ```
   `<scope>` 示例：`agent-runtime`、`windows`、`compact`、`sync`。
4. 跨层功能必须遵守 §二 的「IPC 三处同步更新要求」。
5. 过程中发现设计偏差，先在实施文档补一张「与原设计差异表」，再继续，不要默默改方向。

---

### 1.5 测试（Test）

**分层测试要求**：

| 测试层 | 针对什么 | 放置位置 | 要求 |
|--------|---------|---------|------|
| 单元测试 | 算法、编排辅助类、纯函数 | 与被测文件同级 `__tests__/` 或 `*.test.ts` | 覆盖率 ≥ 80%；先写失败再实现 |
| 集成测试 | DB 迁移、Repo CRUD、跨模块闭环 | `apps/windows/src/**/__tests__/` 或就近 | 至少覆盖 P0 核心闭环 2 个端到端场景 |
| CLI / E2E | 从入口命令到输出的完整链路 | `docs/test/lumii-cli/` 或 `docs/test/自主进化Agent/` | 输出 `evidence.jsonl` + `test-report.md` 两张交付物 |
| 手工验收 | UI 交互、跨设备真实流转、权限弹窗 | 手工勾选 | 含深/浅主题、键盘 Esc/1/2/Ctrl+S 等快捷键 |

**每次发计划文档都必须有**：「验证命令」一节，明确写出跑哪些命令、在哪个包目录下跑。

**示例验证命令（必须可复制粘贴）**：
```bash
pnpm --filter ./packages/agent-runtime test -- src/agent/__tests__/subagent-broker.test.ts
cd apps/windows && npx vitest run src/main/agent-runtime/subagent-delivery.test.ts
pnpm typecheck
```

---

### 1.6 交付（Delivery）

**交付物 1：实施总结**（`docs/implementation/YYYY-MM-DD-<功能名>-implementation.md` 或独立章节）
- 代码实装状态：每个 Task 打勾
- 与设计文档的对比表：目标 / 设计 / 实际 / 状态 / 差异原因
- 已解决的问题列表：每个问题附根因 + 修复代码片段
- 文件清单：新增文件 + 修改文件，带行数估算
- 已知限制：测试环境限制、外部依赖、大文件跳过策略等
- 下一步工作：后续 Phase 列表

**交付物 2：测试报告**
- 测试套件清单、通过数 / 失败数 / 警告数
- 性能指标表：结果 / 目标 / 状态（示例：导出时间 <2s / <10s / ✅）
- 测试覆盖分栏表（环境检查 / 导出 / 导入 / Git / 完整流程）

**交付物 3：交付总结**（`docs/plans/<领域>/交付总结.md` 或实施文档末尾）
- 完成的工作（带分项 ✅）
- 达成的目标（量化指标）
- 未完成 / 遗留项
- 关键成就与经验
- 附录：相关文档索引（设计/分析/实施/修复/测试全部串起来）

## 二、跨层功能开发的 IPC 同步更新要求

**凡涉及 Electron 三层（主进程 / Preload / 渲染进程）的新能力，三处必须同时更新，缺一不可**。这是项目总纲 `AGENTS.md` 第 5 条明确规定。

### 2.1 三处同步的内容

| 层 | 要做的事 | 典型文件 |
|----|---------|---------|
| **① 主进程 Handler** | 用 `ipcMain.handle(...)` 注册通道；事件用 `ipcMain.on(...)`；输入做类型与安全校验 | `apps/windows/src/main/*/<feature>-ipc.ts` 或 `index.ts` |
| **② Preload `ElectronAPI`** | 用 `contextBridge.exposeInMainWorld('electronAPI', {...})` 暴露；类型写入 `ElectronAPI` interface | `apps/windows/src/preload/index.ts` + 对应的 `*.d.ts` |
| **③ 渲染进程调用方** | 从 `window.electronAPI.<domain>.<method>(...)` 调用；UI 侧处理 loading / error / success | `apps/windows/src/renderer/services/` 或 Page/Hook 内部 |

### 2.2 通道命名规范

命名格式：`<domain>:<action>`，全部小写 kebab-case。

示例：
```
cloudSync:getConfig / cloudSync:setConfig
cloudSync:testConnection
cloudSync:syncNow
channel:list / channel:send
vcs:diff / vcs:diffFile
voice:listProfiles / voice:saveProfile
```

**命名禁忌**：
- 动词开头写在左边（禁止 `getCloudSyncConfig` 无冒号）
- 驼峰混用（保持 kebab）
- 通道名过于泛化（如 `data:get`，谁也找不到）

### 2.3 三处同步的检查清单

在开始写代码前，先在设计或计划文档中填好下表：

| IPC 通道 | 主进程 Handler | Preload 暴露方法 + 类型 | 渲染进程调用点 |
|---------|---------------|------------------------|---------------|
| `cloudSync:getConfig` | ✅ | ✅ `electronAPI.cloudSync.getConfig()` | ✅ SettingsPage 区块 onMount |
| `cloudSync:testConnection` | ✅ | ✅ `electronAPI.cloudSync.testConnection()` | ✅ 「测试连接」按钮 onClick |
| `cloudSync:syncNow` | ✅ | ✅ `electronAPI.cloudSync.syncNow()` | ✅ 「立即同步」按钮 |
| 事件 `cloudSync:status` | ✅ `mainWindow.webContents.send` | ✅ `electronAPI.cloudSync.onStatus(cb)` | ✅ 设置页订阅状态行 |

表格任何一行有 ❌ → 该通道暂不做，后续补。

### 2.4 IPC 安全红线（来自 feature-development-standards）

1. **永远不要**把 `ipcRenderer` 整体暴露给渲染进程。
2. 传给主进程的参数：**Handler 层必须跑 typeof / schema 校验**，不可直接透传。
3. 回传给渲染进程的敏感字段（如 token）一律掩码（`ghp_****abcd`），不回传明文。
4. 日志中的 URL / token / context_token 做脱敏。

## 三、从现有实施计划提炼的实施方法

### 3.1 先写失败测试 → 实现 → 通过测试（TDD 三段式）

**适用场景**：算法模块（元认知、目标生成、Prompt 进化、Elo Rating、ProgressFence、SubagentBroker、compact policy 等）与纯编排辅助类。

**标准做法（来自自主进化 Agent P0 与 Subagent P0/P1）**：
1. `Step 1: 写失败单测`。文件名 `__tests__/<feature>.test.ts`，覆盖核心契约（超限返回 error、格式校验、边界返回空数组等）。**先跑一次，确认红色失败**。
2. `Step 2: 写最小实现`。实现刚好让上面测试变绿，不提前做未来优化。
3. `Step 3: 跑验证命令`。单独跑该文件测试，再记录到 Task 日志。
4. `Step 4: Commit`。测试与实现**尽量同一次提交**，防止出现「测试没被实际代码覆盖」的假象。

### 3.2 数据密集功能：先定义 Schema/类型，再做任何事

**适用场景**：云同步、渠道 Hub、Wiki、子 Agent Broker、录屏 Service 状态机。

**标准做法（来自云同步与子 Agent）**：
1. Task 1 固定是「类型与配置」。只产出 `types.ts`（接口/枚举/常量）与 `config.ts`（算法参数、默认值、killswitch）。
2. Task 1 要通过：类型检查 + 配置往返单测（token 加解密往返、配置项 clamp）。
3. 后续 Task 2/3/... 所有代码的参数 / 返回值严格引用 Task 1 的类型，禁止 inline `any`。

### 3.3 集成 / E2E：从真实入口调，不要 mock 全世界

**适用场景**：CLI 套件、云同步双设备流转、子 Agent 异步投递、录屏 MediaRecorder。

**标准做法（来自云同步与自主进化 CLI 套件）**：
1. 编写独立的 `run-<feature>-cli-suite.mjs` 脚本（Node 可直接跑），每一步 print PASS/FAIL。
2. 测试脚本实际写真实文件、起真实 SQLite 内存库、用两个本地临时 git 仓库互推模拟远程，**不 mock 网络层核心路径**。
3. 输出三份证据：
   - `*test-report.md`：人话总结
   - `*evidence.jsonl`：每一步结构化日志（{step,status,detail,timestamp}）
   - `*-summary.md`（若有）：高级汇总

### 3.4 大功能分多阶段：每阶段都要有独立的「退出标准」

**来自多层压缩引擎（Phase 1/2/3）与同步（Phase 1~5）的经验**：
- 每个 Phase 都写清：结束时必须满足哪些可量化条件（例：Phase 1 「48K→剪到 44K→加 5K→不抖动」通过 Rearm 单测）。
- 上阶段退出标准不满足，不允许开启下阶段。
- 每阶段结束在文档里打勾，并跑一次全量回归（确保旧阶段没被新阶段弄碎）。

## 四、文档交付清单（4+1）

每个功能在合并前，必须能在 docs 目录下指认出 **4 类文档 + 1 张索引**。缺一即视作「未完成」：

| # | 文档类型 | 典型路径 | 存在性检查 |
|---|---------|---------|-----------|
| 1 | 设计文档 | `docs/design/<领域>/YYYY-MM-DD-<功能>-design.md` | ✅ 含结论摘要表、方案对比、安全章节 |
| 2 | 实施计划（单阶段或多阶段） | `docs/plans/<领域>/YYYY-MM-DD-<功能>-implementation-<Px>.md` | ✅ 含 Goal / Architecture / Constraints / File Map / Tasks / 验收 |
| 3 | 测试报告 + 证据 | `docs/test/**/*-report.md` + `*evidence.jsonl` | ✅ 含通过率表、性能指标表 |
| 4 | 实施总结 / 交付总结 | `docs/implementation/*.md` 或 `docs/plans/*/交付总结.md` | ✅ 含「与原设计对比表」+「已解决问题」+「已知限制」 |
| +1 | 文档互相跳转索引 | 4 类文档的附录「相关文档索引」互相链接 | ✅ 能从任意一篇顺着跳到其余三篇 |

如果功能中间经历过紧急 Bug 修复，额外加：
- `docs/fix/YYYY-MM-DD-<功能>-<问题>-fix.md`：复现步骤 + 根因 + 修复代码 + 回归测试命令。

## 五、常见实施阶段的检查清单

### 5.1 开始编码前

- [ ] 设计文档已评审（含至少 1 名熟悉代码库的人过一遍）
- [ ] 实施计划已写：Goal / Constraints / File Map / Task 顺序 / 验证命令
- [ ] 涉及 IPC：三处同步表填完无 ❌
- [ ] 建分支：`feat/<功能>` 或 `fix/<bug>`（例：`feat/agent-subagent-p0p1`）
- [ ] 跑基线测试：记下当前的 `typecheck` + `lint` + 相关包测试的失败数，不允许越改越多

### 5.2 编码进行中（每 Task）

- [ ] 先写失败测试 → 再实现 → 单独跑该测试文件
- [ ] 该 Task 的改动文件集合是否落在计划 File Map 范围内？若超了，补差异记录
- [ ] 用 AGENTS.md 的命名规则：变量/函数 camelCase、类型/组件 PascalCase、2 空格缩进
- [ ] 跨层改动：Handler + Preload + Renderer 三处同步提交一次
- [ ] 单次 Commit 控制在单 Task 粒度，不要一次 commit 攒两个 Task

### 5.3 认为「做完了」，合并前

- [ ] 全量：`pnpm typecheck` 通过
- [ ] 相关包 lint 通过：`pnpm --filter ./apps/windows lint`
- [ ] 相关包测试通过：`pnpm --filter ./packages/agent-runtime test`、`pnpm --filter ./apps/windows test`
- [ ] 设计/计划/实施/测试/交付 4+1 文档存在且互相可跳转
- [ ] 手测清单逐项打勾：深/浅主题、Esc/1/2/Ctrl+S/快捷键、权限弹窗、toast 反馈
- [ ] 若改 DB Schema：正向迁移 + 回滚迁移都过一次；新字段 null 安全
- [ ] Killswitch / Feature flag：新能力是否可以一键关闭？（例：`AUTONOMOUS_ENABLED=false`、`compact.enableProactiveDedup=false`）
- [ ] 隐私合规：日志/Telemetry 不含用户消息原文、密钥、token 明文

### 5.4 提交合并说明（PR 描述模板）

至少包含四段：
1. **影响**：改了哪些模块、用户能感知到什么变化
2. **验证命令**：可复制粘贴的那三条（typecheck/lint/test）
3. **配置/Windows 特殊要求**：需要删什么缓存、装什么 native 模块、有没有只在 Windows 才生效的逻辑
4. **UI 改动附图/录屏**：只要 UI 长变了，必须附截图或者录屏链接（哪怕只有一行 CSS）
