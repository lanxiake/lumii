# 术语表

本术语表按 **6 大类**（架构类 / Agent 类 / 记忆类 / 同步类 / UI 类 / 测试类）组织。每条术语含：**中文名**、**英文名**、**定义**、**上下文说明**、**参考文档位置**。

## 2. Agent 类（17 项）

| 中文名 | 英文名 | 定义 | 上下文说明 | 参考文档位置 |
|--------|--------|------|------------|--------------|
| 自主性 / 自目的 | **Autotelic** | 一种 Agent 设计哲学：即使没有用户输入，Agent 也能自我设定目标并执行（如整理记忆、学习、设定新练习项）；与「纯响应式 Reactive」相对 | 自主进化 Agent 的 1 号设计理念：Lumii 不是一个「聊天框」，而是一个「有内在节奏的伙伴生命体」；因此心跳 / Cron 五档是基础骨架，不是锦上添花 | `docs/design/自主进化Agent/1-核心设计理念.md` / `docs/wiki/08-experience/02-技术攻克案例.md` §1 自主进化 |
| 意志性自主 | **Volitional Agency** | 在 Autotelic 之上再加强约束：Agent 的行动必须来自「内部生成的可解释 Goal/Plan/Action 链」，不能由随机数 + 硬编码规则伪装成自主 | 防止「伪自主」——每秒随机挑一个动作看起来很活，但无连贯性；Lumii 走 GPA（Goal → Plan → Action）三层拆分 + UCB1 选策略 | `docs/design/自主进化Agent/3-内在目标生成算法.md` |
| 元认知 | **Meta-cognition** | Agent「对自身能力的认知」：知道「自己哪些技能擅长、哪些不擅长、哪些需要练习、最近是否在进步」；是自主进化的基础闭环 | 在 Lumii 中用 Elo Rating 量化 8 维度能力（记忆/工具/规划/反思/写作/编码/沟通/学习）+ 置信度 λ=20 公式；避免「不知道自己不知道」而乱尝试 | `docs/design/自主进化Agent/2-元认知引擎算法.md` / `docs/wiki/08-experience/02-技术攻克案例.md` §1.1 Elo 置信度 |
| 埃洛等级分 | **Elo Rating** | 原为国际象棋选手相对水平的评分系统；Lumii 用于评估 Agent 在 8 个能力维度的相对水平：初始 1000 分，通过/失败一次 CLI 测试用例更新 R ± K×(实际−期望) | 参数调优结果 K=0.32 稳定不跳；置信度 `confidence = 1 − exp(−testCount/20)`，新维度测试 20 次后置信度 86%，权重平方放大 | 同上 2-元认知 / `packages/agent-runtime/src/storage/autonomous-repo.ts`（速查表 §3 Elo 核心） |
| 置信上限 | **UCB1（Upper Confidence Bound 1）** | 多臂老虎机问题经典算法：每轮选「`均值 + C × sqrt(ln(N)/n)`」最大的臂；用于在「探索新策略」与「利用已知好策略」之间平衡 | 内在目标生成模块中选下一策略：策略 = 「练习已知弱项」vs「探索未知能力」vs「巩固刚提升项」；C=2 偏探索 | `docs/design/自主进化Agent/3-内在目标生成算法.md` §2 多臂老虎机 |
| 汤普森采样 | **Thompson Sampling** | 贝叶斯版多臂老虎机：对每个臂的胜率建 Beta(α,β) 先验，采样一次选最大；在样本少时天然偏探索，样本多时收敛到最优臂 | 与 UCB1 双保险：关键决策（是否开启 L2 审批类工具）先过 Thompson 胜率 < 0.7 直接跳过，避免 Agent 在不确定时给用户添麻烦 | 同上 3-内在目标 §3 双保险策略 |
| 夏普利值 | **Shapley Value** | 合作博弈论中，「多个参与者共同产出一个收益时，每个参与者应分配的边际贡献」唯一满足四条公理的分配方法 | 多层进化协同归因：4 层（模型/编排/工具集/提示词）共同影响一次进化结果；Lumii 用 `fastCreditAssignment` 把 O(2⁴=16) 全组合降为 O(8) 仅变动层评估 | `docs/design/自主进化Agent/5-多层进化协同.md` / `docs/wiki/08-experience/02-技术攻克案例.md` §1.3 Shapley 简化归因 |
| 目标-计划-行动 | **GPA（Goal → Plan → Action）** | 内在动机的三层拆分粒度：Goal（做什么，≤30 字）→ Plan（分几步，≤5 步每步 ≤1 天）→ Action（可执行的工具调用序列，原子） | 防止目标过大无法验收；P0→P1 教训：如果目标不按 GPA 拆分，实施 6500 行还交付不了任何可验证项（砍到 1890 行才闭环） | `docs/wiki/08-experience/03-项目反思与改进.md` §2 过度设计收敛 |
| 心跳 | **Heartbeat** | 自主 Agent 的时间感知基础：以固定周期运行「情绪汇总 / 关注扫描 / 长程整理」三件事，让 Agent 有「生命节奏」而不是纯事件驱动 | Lumii 三档：30s（情绪 EMA + 桌面动作变化）/ 5min（用户最近关注项重排）/ 1h（学习 / 记忆 consolidate）；禁令 B1-B7 在每档入口硬编码拦截 | `docs/design/自主进化Agent/10-心跳与外部交互设计.md` / 速查表 §3 心跳驱动 |
| 情绪 / 心情 | **Mood** | Agent 在一段连续时间内的综合情感状态：平静/愉悦/焦虑/专注/无聊 5 档；来自最近 50 条消息的标签 EMA 平滑 | 桌宠 Pet State Machine 的表情选择来源；**禁令 B3：禁止无根据的情感投射**——Mood 必须来自带证据的 EMA 计算，不可随机变 | `packages/pet-core/src/state/petStateMachine.ts` / 禁令 B3：`docs/design/自主进化Agent/11-参数配置与生命感设计.md` §4 |
| 关注项 | **Concerns** | Agent 主动关心的 5~8 件事（用户的项目、健康、日程、宠物、最近学习的话题…），按最近交互频率加权排序 | 心跳 5min 档重新计算 Concerns 排序；用于下一次主动开口的话题候选（**B2：禁止机械重复关心**——同一 Concern 24h 内不主动触发第二次） | 同上 10-心跳 §3 关注项扫描 / 禁令 B2 |
| 大五人格 | **Big Five（OCEAN）** | 心理学经典五维人格模型：Openness 开放性 / Conscientiousness 尽责性 / Extraversion 外向性 / Agreeableness 宜人性 / Neuroticism 神经质 | Agent 人设参数，不随机但随用户反馈慢漂移；每日 EMA α=0.12 保证人格稳定；一天漂移 ≤ 0.02 防止变来变去精神分裂 | `docs/design/自主进化Agent/4-人格进化算法.md` / 速查表 §3 人格 Big Five |
| 指数移动平均 | **EMA（Exponential Moving Average）** | 时间序列平滑方法：`S_t = α·x_t + (1−α)·S_{t−1}`，旧数据指数衰减；相比普通平均更能反映近期趋势 | 三大用途：① 情绪 EMA 30s / ② 人格 EMA 日级 / ③ Shapley φ 归因跨轮 EMA 聚合；α 越小越稳，越大越敏感 | 以上 Agent 类各设计文档实现章节 |
| 多臂老虎机 | **Bandit（Multi-Armed Bandit）** | 经典强化学习问题设定：面对 N 个未知胜率的老虎机臂，如何通过试错最大化累计奖励；核心是探索-利用困境 | Agent 内在决策无处不在：UCB1 / Thompson Sampling 都是 Bandit 算法家族；在「选什么目标练习 / 选什么策略 / 调什么参数」时统一范式 | `docs/wiki/10-knowledge-index/03-术语表.md` 本条目关联 UCB1、Thompson 两条 |
| 离线审批三级风险 | **L0 / L1 / L2 Approval Tiers** | Lumii 给 Agent 工具调用分三级风险：L0 内部自治（读操作 / 无副作用，自动批准）/ L1 可见无副作用（截屏、查目录，超时拒绝）/ L2 有副作用（写文件、发消息，超时归档） | 护栏三道闸之二：每日 L1+L2 预算 5 条（北京时间 04:00 重置）；L1 15min 超时 = 拒绝（非默示同意）/ L2 超时 = 归档（不丢不执行） | `docs/wiki/08-experience/02-技术攻克案例.md` §1.2 三级审批矩阵 / 速查表 §3 审批队列 |
| 每日沟通预算 | **Daily Interaction Budget** | 为了不毁掉生命感（B6 禁令），Agent 每天主动发起的 L1+L2 审批请求设硬上限；默认 5 条，用户可在设置调到 2/5/10/无限 | 超预算后所有主动式 Cron 触发的 L1/L2 直接跳过；但用户发起的对话中产生的审批不受预算限制（毕竟是用户问的） | `docs/design/自主进化Agent/11-参数配置与生命感设计.md` §3 护栏参数 |
| 毁掉生命感的禁令（B1–B7） | **B1–B7 Vitality Guardrails** | 七条硬编码在心跳、审批、合成、元认知入口的**禁止项**，每条对应一个「AI 会立刻让用户觉得机械、被监控、或虚伪」的致命伤 | B1 禁止 OS 隐私数据（剪贴板/浏览历史等）/ B2 机械重复关心 / B3 无根据情感投射 / B4 监控暗示 / B5 心跳写聊天记录 / B6 无焦点弹通知 / B7 AI 静默写真相表 | 同上 11-参数配置 §4 禁令清单 + `docs/wiki/08-experience/04-工程实践最佳做法.md` §5 AI 护栏末尾 |

## 3. 记忆类（10 项）

| 中文名 | 英文名 | 定义 | 上下文说明 | 参考文档位置 |
|--------|--------|------|------------|--------------|
| 真相表 | **Truth Table** | 数据库中「用户输入的原始数据」所在表：用户消息、用户编辑过的 Wiki Topic、用户创建的 Vault、用户批准的审批请求…；AI 只能 read，**绝不能静默 write** | 与「派生表 Derived」成对出现；真相表一旦被 AI 静默写 = 监控暗示（禁令 B4+B7）= 用户信任感崩塌；代码层每笔 INSERT/UPDATE 走 TruthWriter API，源头强制要求 user_approved 标志 | `docs/wiki/08-experience/04-工程实践最佳做法.md` §2.2 真相表不动 |

| 合成综述 | **Synthesis** | 对一族强关联 Topic（5–20 个）自动生成的「综述页」：总结这簇知识在讲什么、关键论点、未解决问题、下一步可以怎么延伸 | 存放在 `wiki_synthesis` 真相表（用户可编辑覆盖，覆盖后 AI 不再重写）；**禁止合成产物反向覆盖原始 Topic**（否则就是 B7） | 速查表 §4.2 Synthesis / `wiki-summary.ts` |
| 知识库保险柜 | **Vault** | Wiki 顶层隔离单元：一个 Vault = 一个文件夹（Markdown 模式下）或一组带 vault_id 外键的表（SQLite 模式下）；Vault 之间检索默认不跨查 | 支持多 Vault：工作 / 个人 / 学习 / 项目 分开；Markdown 真相和 SQLite 真相之间可以双向零迁移切换（同路径下 SQLite 关 = Vault 从磁盘读 .md） | `docs/wiki/08-experience/03-项目反思与改进.md` §4 零迁移成本决策树 |

## 4. 同步类（8 项）

| 中文名 | 英文名 | 定义 | 上下文说明 | 参考文档位置 |
|--------|--------|------|------------|--------------|
| JSON 行格式 | **JSONL（JSON Lines）** | 每行一个 JSON 对象的纯文本格式：便于 grep / 追加 / 流处理 / Git diff；很多「AI 记忆导出」方案的默认格式 | 三大同步方案对比中 JSONL 排第一，但**复杂度被严重低估**：外键乱序、双写窗口、增量幻觉、删除要 tombstone、软链接跨平台、CHECK 历史兼容；最终 Phase0 弃 JSONL 走 SQLite 热备 + 每表 hash | `docs/design/数据同步功能/2026-09-07-同步策略反思.md` §2 JSONL 六大复杂度 |
| SQL 转储 / 数据库导出 | **SQL Dump** | 把整个库的表结构 + 数据导出成一个大 `.sql` 文件；恢复时用 `sqlite3 db.sqlite < dump.sql` 整库还原 | 三方案对比排第二；优点简单、缺点整库不支持增量；冷备份每月一次 OK，日常同步不行；可作为 JSONL ↔ SQLite 之间的兜底迁移手段 | 同上 §1 三方案长期路线 JSONL ↔ SQL Dump ↔ 事件溯源 |
| 预写日志 | **WAL（Write-Ahead Log）** | SQLite 等数据库的原子事务机制：修改先写 WAL 日志再写主文件；崩溃时用 WAL 重做保证 ACID；可被外部订阅做 CDC | 事件溯源 Event Sourcing 的底层灵感；Phase3（若做）会走「订阅 SQLite WAL → 产出事件流 → 多设备重放」路线；目前仅作内部 ACID 保障 | SQLite 官方文档 / 同步反思 §1.3 事件溯源条目 |
| 事件溯源 | **Event Sourcing（ES）** | 不存「当前状态」，只存按时间排序的「不可变事件流」：当前状态 = 事件流从 0 开始按顺序 apply 一次的结果；支持任意时间点回放审计 | 三方案长期路线的终局（Phase3+）；但复杂度最高，要求所有写入严格事件建模；P0/P1 直接跳 ES = 必死无疑，先走 Phase0 SQLite 热备 + 每表 hash 过渡 | 同上同步反思 §1 三方案长期路线结论 |
| 无冲突复制数据类型 | **CRDT（Conflict-free Replicated Data Type）** | 一组数学上证明过、不管多端怎么改/怎么乱序到达，只要最终所有事件都收齐，所有副本会收敛到相同状态的数据结构家族（LWW-Register / OR-Set / RGA…） | 传输层 4 方案对比（Git 文件 / CRDT / 中心化 / 三方融合）中 CRDT 理论最完美，但工程成本高：每条文本要带向量钟 + GC 墓碑；P2 评估引入文本类型 CRDT 替换 git merge-file 三路合并 | 同上同步反思 §3 传输层 4 方案取舍 |
| 乐观锁 | **Optimistic Lock** | 冲突检测的一种：假设冲突少，写之前不锁；写入时带版本号 `WHERE version = :expected`，匹配到的行数 = 0 说明被别人改了，报错让上层处理 | Lumii 冲突检测底层：每表 `updated_at + device_fingerprint` 做向量钟版乐观锁；比「单字段自增 version」更能识别并发改不同字段的可合并场景 | 速查表 §5 ConflictResolver 3 规则 |
| 非快进 | **Non-fast-forward（non-ff）** | Git push/pull 中「远程分支的最新 commit 不在本地历史链上」= 必须 rebase 或 merge 才能推进；Lumii 同步层一旦检测到 non-ff + 用户曾 `--squash`，极大概率已失联 | 同步策略反思最大教训：**Git Squash 在多设备场景是毁灭性的**——squash 会丢弃原 commit ID，两设备分别 squash 出两条不同 commit，互相 non-ff，再 force push = 对方全量冲突；Lumii Git Provider 硬拦截 `--squash` 与 `--force` | `docs/design/数据同步功能/2026-09-07-同步策略反思.md` §3.2 Git Squash 小节 |
| 压缩合并提交 | **Git Squash** | 把 N 个小 commit 合并成 1 个大 commit 再合入主干，表面干净、实际丢失了「哪个改动和哪个改动是一组」的因果链 | 单开发者 PR 到主干 OK；多设备同步用 Git + 每设备独立提交链 → 绝对禁止；Lumii 同步 PR 默认走 rebase 线性历史，不允许 squash 进入 `lumii-sync` 分支 | 同上 non-ff 条目关联 / 速查表 §5 Git Provider detectNonFastForward |
