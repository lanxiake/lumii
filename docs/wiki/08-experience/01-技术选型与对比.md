# 01-技术选型与对比

## 一、AI Agent 架构选型对比

### 1.1 Lumii Agent 架构 vs Hermes MOA 四层协作对照

| 协作层级 | Lumii Agent 现状 | Hermes MOA 架构 | 优劣分析 |
| --- | --- | --- | --- |
| L1 模型级 MOA | 单 Orchestrator 编排，主路径 `spawn_agent` | `conversation_compressor` + `turn_context` 双层语义清理，上下文模型与推理模型分离 | Lumii：实现简单、调试成本低；Hermes：语义污染隔离更彻底，但模型×2 成本高 |
| L2 任务委派同步 | 同步调用链：Tool Registry → Broker → Tool Execute | Subagent `plan` 阶段预生成子任务，异步派发后用 `StuckGuard` 监测停滞 | Lumii：一致性强、无状态丢失窗口；Hermes：任务可嵌套、专家子代理可 explore/plan/verify |
| L3 异步委派与结果投递 | 单层 await 等待，无异步结果队列 | `context_compressor.py:L1820-L1843` 异步结果队列 + 摘要护栏 + 并发帽 | Lumii：简单可控；Hermes：吞吐高，但需要超时/回滚/重放三机制 |
| L4 工作树隔离/扇出 MOA | 无隔离，共用目录状态 | 独立 worktree 目录沙箱 + MOA 扇出拓扑（explorer × planner × verifier） | Lumii：无沙箱成本；Hermes：多 Agent 并发无文件冲突，但实现复杂度指数级 |

### 1.2 单层编排 vs 多层协同的取舍

| 维度 | 单层编排（Lumii 现状） | 多层协同（P2 方向） | 取舍结论 |
| --- | --- | --- | --- |
| 复杂度 | 单 Orchestrator，<500ms 决策开销 | 四层独立进化：Prompt Bandit + Memory LTR + Skill 缺口 + Tool Thompson，需 Shapley Value 归因 | P0-P1 用单层，P2 仅在 4 层目标明确且有 1 个月使用数据后引入 |
| 可观测性 | 单日志流，单断点 | 需 `evolution_coordination_history` / `pareto_frontier` / `layer_performance_stats` 三表 | 多层必须先建全指标，否则黑盒不可控 |
| 回滚与安全 | 单版本回滚 | 层间冲突检测 3 条规则 + 兼容性矩阵 + 帕累托前沿多目标约束 | 多层必须保留"禁用该层"开关，保证降级到单层 |
| 工程投入 | <2 人周 | >3 人月，算法+数据+UI 三端 | 非核心路径，放在 Phase3 长期规划 |

### 1.3 同步调用 vs 异步投递的场景适配

| 场景 | 同步调用（await） | 异步投递（队列+回调） | 选择 |
| --- | --- | --- | --- |
| 读操作：记忆召回、设置查询、Wiki 检索 | 低延迟、失败直接抛错 | 无状态收益，额外引入队列开销 | 同步 |
| 写操作：SQLite Schema 迁移、IPC 跨层三处同步 | 需原子性，双写窗口零容忍 | 异步双写必然产生中间不一致 | 同步 + 事务 |
| LLM 长调用：元认知反思、综合摘要、页面编译 | 阻塞 >10s，UI 冻结 | 超时 + 取消 + 进度推送 + 重试 | 异步 + 状态机 |
| 能力测试：Elo Rating 批量评分 | 可重入，顺序无关 | 并发提高吞吐量，但 K-factor 一致性需锁 | 批量异步 + 单 agent 串行 |
| 后台心跳：情绪 EMA、关注 EMA、检查项 | 周期触发，失败不影响主链路 | 队列可积压，冷却重试 | 异步投递 |

### 2.2 Lumii 方案 A+ 选型结论

**语义 × 温度双轴架构**

| 轴 | 维度 | 实现方案 | 参考来源 |
| --- | --- | --- | --- |
| **语义轴** | 真相源 vs 派生索引（严格边界） | Wiki Markdown/原始附件为真相源；`wiki_pages` 记录元数据；`wiki_pages_fts`/`wiki_links`/`wiki_chunks` 三派生表可一键重建；保留 `rebuildWikiIndex()` 一等公民 | wiki0（最直接可迁移）、geronimo-iia（schema 驱动）、siyuan（三级分离） |
| **语义轴** | 关系模型 | `[[wikilink]]` 解析到 `wiki_links` 表（存 raw text/目标/alias/embed/resolved 状态）；反链仅查询该派生关系表；P2 再引入 ERO 实体观察关系表 | spences10 wiki0、chenly255、nvk |
| **语义轴** | 跨类型统一检索 | `wiki_search_fts` 统一索引 pages/chunks/raw 附件；FTS5 触发器适合增量但必须配显式 rebuild；损坏恢复/批量导入/迁移后统一走全量重建；chunk 输出 path/title/heading/line-range/snippet | studiomeyer-io、wiki0、YonasValentin |
| **语义轴** | 矛盾与替代策略 | 状态机 `active/outdated/disputed/archived`；重复/冲突/陈旧只能生成建议和标记，绝不静默覆盖用户资料；`archive` ≠ `supersede` 严格分离；P1 引入 compile run 候选审批流 | local-memory-mcp（tombstone supersede）、erickmbugua、nvk |
| **温度轴** | 热度与时效重排 | P1 纯标量排序：`use_count / (use_count + 5)` × 时效指数衰减（半衰期 30 天可配置）× 优先级；P3 叠加到 RRF | local-memory-mcp |
| **温度轴** | 生命周期归档 | 低访问→默认归档降权而非清除（尤其是用户手工笔记和上传资料）；`last_accessed`/`use_count`/`stability` 记录；P0 保留 P1 增加状态 | YonasValentin、memex（反模式，不采用物理 prune） |
| **温度轴** | 摄取失败可恢复 | P1 引入 `ingestion_jobs` 状态机（pending/running/succeeded/failed/cancelled）+ 源快照 + 安全重试；原文先落库，提取失败不丢不静默 | erickmbugua、memex |
| **可选增强层** | 向量 + RRF | P3 评估：中文/中英混合查询集金标达标 + Windows 首次下载冷启动可接受 + 包体可控；保留 fts/vector/hybrid 诊断模式和向量不可用降级 notice；模型 ID/维度/索引版本写入元数据 | YonasValentin、local-memory-mcp、memex |
| **可选增强层** | ERO 图谱 | P2 仅在多跳场景确实无法通过 wikilink/backlink 满足时引入；图谱检索必须 `useGraph` 开关；可视化放在实体>500 且链接密度足够后；`wiki_observations` 采用半开 `[valid_from, valid_to)` | aaronsb、local-memory-mcp |
| **绝对不做** | 物理删除低强度内容、自动合并相似实体、LLM 全量覆盖用户原文、无审批自动 supersede、依赖外部 MCP server 进程管理本地数据 | — | memex/consolidation/PruneKB、erickmbugua/write_pages 直接覆盖、MCP servers 集合 |

**演进路径（严格按序，不跳阶段）**

1. **P0 用户可见闭环**：`wiki_pages`/`wiki_links`/`wiki_chunks` + 两张 FTS5 + `wiki_index_meta`；CRUD/删除/重建/断链/中文查询测试；Markdown `[[wikilink]]` + backlinks；chunk 精确行范围定位
2. **P1 可信编译**：原始资料不可变引用 + 手动触发 triage/compile/cascade；`outdated/disputed/archived` 状态；compile log 可查看；ingestion job 状态机；候选修订带 base revision，展示 diff 用户确认后覆盖
3. **P2 事实和关系**：按需 `wiki_entities`/`wiki_observations`/`wiki_relations`；半开有效期 + tombstone supersede；先搜索结果关系解释，再评估图谱视图；无 LLM 争议标记+来源
4. **P3 智能检索**：Lumii 自有中文查询集验证 embedding/RRF/候选过取；模型不可用时保持完整 FTS5 功能；中文否定正则弃用，自建规则

## 三、同步方案对比

### 3.1 长期路线三方案：JSONL 导出 vs SQL Dump vs 事件溯源

| 维度 | JSONL 导出（当前思路） | SQL Dump | 事件溯源 Event Sourcing |
| --- | --- | --- | --- |
| **数据完整性** | ❌ 外键/CHECK 约束仅运行时校验，导出 JSONL 是无类型行；行顺序丢失，replay 不一定还原一致态 | ✅ `.dump` 含完整 CREATE TABLE + INSERT 顺序；`application_id`/`user_version` 绑定 schema 版本 | ✅ 事件不可变追加；状态可按事件 ID 精确 replay；每张真相表对应 event 表 |
| **一致性与 ACID** | ❌ 双写窗口：导出 JSONL 期间写操作产生"增量幻觉"；无事务边界；引用断裂（被引用行已导，引用行未导或反之） | ✅ `BEGIN IMMEDIATE` 快照导出；WAL checkpoint 可保证时间点一致；`sqlite3_backup_*` API 在线热备 | ✅ 事件追加单写者串行化；snapshot 可从任意事件 ID 重建；compaction 可验证 hash |
| **增量同步** | ❌ 基于 last_modified/mtime 不可靠；删除需 tombstone 追加；冲突无法自动合并 | ❌ 全量 dump 体积 O(GB)；需第三方 `sqldiff` 或自定义块级比对；版本冲突无语义 | ✅ 每个事件唯一 ID + 因果时钟；接收端幂等 apply；并发冲突在领域层有语义合并规则 |
| **查询性能与可用性** | ❌ 查询端需重新解析 JSONL 回写 SQLite；用户切到新设备必须等待"导入索引重建"；导出查询（搜索/排序/聚合）不可用 | ✅ dump 文件可直接 `sqlite3` 打开；新设备直接挂载 `.db`；无需重建 FTS/索引 | ⚠️ 冷启动需 replay 所有事件→必须配套 snapshot；snapshot 合并事件可按天/周 compaction |
| **迁移与演进** | ❌ 导出格式绑定代码版本；代码 V30 无法导入 V29 时代的 JSONL（列缺/列多）；零转换保证 | ✅ 同一个 `user_version` 可跨代码版本互导；向上迁移走现有 `migrateToVxx()` 管道 | ✅ 事件 schema version 入头部；旧事件 replay 走兼容适配器；新事件不影响既有 replay |
| **修复与审计** | ❌ 无差异对比工具；发现 JSONL 与 SQLite 不一致后无法定位"哪一行哪一步错了"；损坏只能整体重放 | ✅ `sqldiff` 二进制行级 diff；`.dump` 与原库 text 输出可 diff；损坏可 restore | ✅ 事件重放可单步；差异来自哪个事件 ID 100% 可定位；损坏可截断到最后一致事件 |
| **包体与传输** | ✅ 纯文本压缩率 ~65%；可单行 append 到 Git | ✅ SQLite 文件二进制；Git 历史膨胀（每次 1 字节改也重写整页） | ⚠️ 事件表通常比真相表大 2~3×；需按周期 snapshot + compaction |
| **人工可干预性** | ✅ 文本可手改、可 diff、可 grep；冲突可手工 merge | ❌ 二进制不可手改；冲突只能整体选一方；冲突 diff 不直观 | ⚠️ 事件文本可读但手改会破坏 hash chain；适合工具化冲突解决 |

**三阶段长期路线结论（Phase0~Phase4 共 11 周）**

1. **Phase0（1 周原型）**：放弃纯 JSONL 作为真相同步，改为「SQLite 在线热备（`sqlite3_backup_*`）+ 每表配套 SHA-256 行级 hash + 删除 tombstone」；JSONL 仅作为导出/导入**交换格式**而非同步真相
2. **Phase1（3 周核心同步）**：真相表事件化，每张真相表（agent_memories、wiki_pages、chat_messages）对应 `*_events` 表；单写者追加；消费端幂等 apply；删除事件与更新事件语义化
3. **Phase2（4 周增强优化）**：事件因果时钟（Lamport/Vector），冲突自动合并策略覆盖 80% 常见场景；剩下 20% 弹 UI 人工选择；每小时 snapshot compaction
4. **Phase3（3 周安全稳定）**：端到端加密事件包；设备注册/撤销只读权限；敏感数据正则 5 条扫描；同步状态托盘五色图标
5. **Phase4（长期高级）**：多人协作只读评论区；CRDT 评估；不做中心化服务（见下节）

### 3.2 传输层取舍：Git 文件同步 vs CRDT vs 中心化同步服务

| 维度 | Git 文件同步（当前思路） | CRDT 本地优先 | 中心化同步服务（不做） |
| --- | --- | --- | --- |
| **多设备一致性** | ❌ Git Squash 在多设备场景**破坏性**：设备 A `git reset --soft HEAD~3 && git commit --amend && git push --force` → 设备 B 的 refs 全部失联；`non-fast-forward` 需要用户懂 rebase；软链接跨 Windows/macOS 兼容差 | ✅ 操作交换而非状态交换；自动合并 commutative/associative/idempotent 操作；离线无限期写入，上线 converge；状态 CRDT + 文本 RGA（Yjs 成熟实现） | ✅ 服务器仲裁最后写入赢（LWW），实现简单；但完全依赖在线 |
| **冲突处理** | ⚠️ 文本 3-way merge 对 `.db` 二进制完全失效；JSONL 行级 merge 外键/约束语义丢失；用户被迫选 ours/theirs | ✅ 冲突域内自动收敛；"用户已编辑过的字段"保留优先，"Agent 自动生成字段"允许自动覆盖；无法收敛才降人工 | ✅ 服务器 LWW；但语义冲突（先撤销审批又通过）只能人工，LWW 可能错 |
| **用户体验** | ❌ 对话不同步问题：设备 A 聊 30 分钟关机→设备 B 打开看不到；降级体验 L1 摘要/L2 关键/L3 近期 7 天/L4 按需拉取；同步状态不透明→托盘五色图标方案 | ✅ 每文档状态独立 `[ok syncing offline conflict]`；同步失败保留本地操作，不阻塞编辑；不出现"导出中请稍候…"阻塞 UI | ✅ 实时类 Google Docs；但断网只读或禁止写入；不符合 Lumii 本地优先 |
| **部署与运维** | ⚠️ 需要 Git 仓库 URL、鉴权 token、用户懂 `--force` 恢复；GitHub 私有仓库免费但 2FA 门槛；LFS 大文件超配额要钱 | ✅ 点对点 WebRTC 同步 + 本地文件 USB 导入导出双路径；零服务器、零账号、零订阅；加密 key 本地导出备份 | ❌ 服务器开发 + 域名 + TLS + 运维监控 + 用户数据隐私合规 GDPR/PIPL；成本持续，单用户无商业模型 |
| **性能与体积** | ❌ `.db` 二进制每次 1 字节修改 Git 也重写整页 4KB→仓库大小 O(N 修改次数)；LFS 100MB 附件限流；多人协作 10 分钟 lock | ✅ 每同步消息 O(操作) 非 O(文档大小)；Yjs 文档 10 万字符 <200KB；弱网下增量推送字节 | ✅ 服务器端全量/增量都行；但弱网延迟直接反应用户 |
| **安全隐私** | ⚠️ Git 历史永久保留，即使删除也需 `filter-branch`；敏感内容误提交灾难；私有仓库是他人服务器 | ✅ 端到端加密；点对点无中继服务器可读；导出文件可选密码加密 | ❌ 服务器明文看所有数据；除非端到端加密但服务器又无法做冲突仲裁 |

**决策结论**

| 阶段 | 方案 | 条件 |
| --- | --- | --- |
| P0~P1 | Git 仅同步「`backup/` 目录下 SQLite 热备 .db 文件 + 每 500 次修改做一次 commit + 禁用 squash + force push 默认拒绝 + 提供一键 reset recovery 脚本」；附件走文件复制不用 LFS | 用户提供自己的 Git 私有仓库 URL + token；提示不做也可只靠 USB/局域网文件复制 |
| P2~P3 | 引入 Yjs CRDT 覆盖 chat_messages、wiki_pages 正文；agent_memories 等结构化表仍走事件溯源 apply；点对点 WebRTC + 文件双路径 | 有真实 3 设备用户长期使用反馈；中文输入 CJK 合并正确性建立测试集 |
| 永不做 | 中心化同步服务器 | 商业模型、隐私合规、运维成本三条都不支持；单用户桌面产品必须本地优先 |

## 四、渲染技术选型

### 4.1 PixiJS 桌宠 vs CSS 动画的场景划分

| 场景 | PixiJS WebGL 渲染 | CSS 动画（transform/transition/Web Animations API） | 选择 |
| --- | --- | --- | --- |
| 桌宠全身动作：走/跑/跳/呼吸/情绪变化 20+ 骨骼帧动画 | ✅ 骨骼动画成熟（Spine/DragonBones 导出）；单 draw call 批量 100+ 精灵；60fps 低功耗；像素完美缩放无锯齿 | ⚠️ 20+ 层 DOM absolute 合成，will-change 占 GPU 内存 200MB+；超过 10 层动画 Jank | PixiJS |
| 桌宠局部交互：点击脑袋反馈、拖拽反抗、鼠标悬浮表情 | ✅ 本地坐标命中测试精确；粒子反馈 50 颗 0 成本 | ✅ CSS 伪类 hover/active 无需 JS；transform 合成层不重排 | 简单：CSS；复杂粒子：PixiJS |
| 桌面多宠互动：碰撞检测、群体跟随、对话气泡轨迹 | ✅ 四叉树空间索引；50 宠 60fps；向量计算纯 JS 快 | ❌ DOM Element.getBoundingClientRect() 每帧强制回流 O(N²) | PixiJS |
| 工作台 UI：按钮/卡片/表单/页面/对话框/列表/虚拟滚动 | ❌ 文本渲染极差（无换行无省略号无换行断字）；无内置 accessibility；文本选中/复制/粘贴全手搓 | ✅ 浏览器原生语义标签；ARIA 原生键盘可达；长列表 10 万行 CSS contain: strict + 虚拟滚动 | CSS |
| 数据可视化：记忆温度热力图、能力雷达图、进化损失曲线、Wiki 关系力导向图 | ✅ WebGL 10 万节点 60fps；粒子过渡 | ⚠️ D3 SVG 1000 节点 OK；超过 5000 节点掉帧 | <1000 节点：SVG D3；>5000：PixiJS/Canvas；力导向图：d3-force + Canvas |
| 页面过渡/加载骨架/Toast 弹入/Modal 遮罩过渡 | ❌ 杀鸡用牛刀 | ✅ 10 行 CSS，prefers-reduced-motion 原生降级 | CSS |

**边界铁律**：`packages/pet-core`（桌宠动画、物理、行为决策）**纯 TS 不依赖 DOM**；`apps/windows/src/renderer/pet-overlay` 用 PixiJS 把核心渲染到 `<canvas>`；其余所有 UI 一律走 React + CSS Modules。不允许把 React 组件渲染到离屏 PixiJS 纹理。

### 4.2 CSS Modules vs CSS-in-JS 的决策

| 维度 | CSS Modules（已采用） | CSS-in-JS（styled-components/emotion/vanilla-extract） | 决策原因 |
| --- | --- | --- | --- |
| 包体与运行时 | ✅ 零运行时；编译期转换；`.module.css` 直接产出静态 class 名 | ❌ styled-components/emotion 注入样式 runtime：首屏 20KB JS + SSR 水合成本；vanilla-extract 零运行时但编译链复杂 | Electron 首屏冷启动对 100ms 敏感 |
| 主题切换 | ✅ 基于 `[data-theme]` 属性选择器 + CSS 变量；原子化令牌；<100 行实现深浅两套 | ✅ ThemeProvider React Context + 动态 CSS 变量；强类型主题 | 两者主题能力持平；CSS Modules 不依赖 React Context 失效 |
| 调试体验 | ✅ DevTools Elements 面板直接看 `.Button_button_abc123`；改样式立即生效；HMR CSS 不丢组件 state | ⚠️ emotion source maps 可用但默认关；styled HMR class hash 易变；动态样式改完经常整棵子树重渲染 | CSS Modules 调试链路最短 |
| 动态样式 | ⚠️ className 组合 `{[styles.active]: isActive}`；高频动态值（transform translate px）只能 inline style | ✅ 模板字符串插值 `${props.size}px` 直接生成原子 CSS；props 变化生成新规则 | Lumii 动态样式多通过内联 transform/宽度像素；CSS Modules + inline style 足够 |
| 类型安全 | ❌ class 名纯字符串，拼写错运行时无提示；`typescript-plugin-css-modules` 支持但需 IDE 插件 | ✅ styled/vanilla-extract 强类型；props 未传值 TypeScript 报错 | 项目已约定组件 class 命名规律 + lint；权衡后零运行时更重要 |
| 代码风格一致性 | ✅ `.module.css` 文件与 `.tsx` 就近放；样式与逻辑物理分文件便于设计/前端分工 | ⚠️ 样式 inline 在 tsx 文件，大组件 JS+CSS 混写超过 500 行违反单一职责 | AGENTS.md 500 行/文件上限；CSS Modules 强制样式抽文件 |
| 设计令牌复用 | ✅ tokens.css 定义 `--mt-surface-rgb` 等；可同时被 CSS、通过 `getComputedStyle(document.documentElement).getPropertyValue('--mt-...')` 读、也被 TS 令牌文件 colors.ts/spacing.ts 定义三倍复用 | ⚠️ TS 令牌 defineVars 一套；CSS 变量一套；容易双写漂移 | 现有 tokens.css + TS tokens/*.ts 双通道三倍复用已验证 |
| SSR/SSG（Electron 内用不上） | 中立 | 中立 | — |

**决策**：全项目统一 CSS Modules + 设计令牌 tokens.css + TS tokens 三重机制；禁止引入任何 CSS-in-JS 运行时库。动态像素（桌宠坐标、虚拟滚动偏移）用 inline style，其余语义颜色/间距/字号一律走 CSS 变量或 `.module.css` 中 class。

## 五、数据库选型：SQLite 本地优先 vs 云端数据库

| 维度 | SQLite 本地优先（已采用） | 云端数据库（PostgreSQL/Supabase/Firebase） | 决策结论 |
| --- | --- | --- | --- |
| **数据所有权与隐私** | ✅ `.db` 文件位于 `~/.lumii` 或 `%USERPROFILE%\.lumii`，用户完全拥有；可直接复制备份到 USB；进程外无任何出口，除非用户主动配置 | ❌ 数据在他人服务器；GDPR/PIPL 数据导出请求法律流程；供应商锁库，停服即用户数据丢失 | 单用户桌面 AI 伴侣核心就是数据本地化 |
| **启动延迟与可用性** | ✅ 0 ms 连接；`better-sqlite3` 同步 API 单次查询 <1ms；离线完全可用；断网、飞机模式 100% 功能不降级 | ❌ 首包 RTT 200ms 起；查询失败或超时需要全链路 fallback UI；断网只读或不保证一致（Firebase realtime 例外但存储模型不同） | Electron 冷启动 + Agent 思考已经慢；数据库必须零延迟 |
| **部署与成本** | ✅ 零运维；随安装包自动部署；无限用户量，每用户自带独立 DB；费用 0 | ❌ 每月 $25~$200 服务器；冷启动/超配额付费；DB 索引优化、VACUUM、备份、监控全做 | 开源无商业模型；承担不起服务器账单 |
| **Schema 迁移与演进** | ✅ 单向递增 V29/V30/V31 迁移；`user_version` pragma；CHECK 约束不 ALTER 则重建表；迁移 SQL 与代码同仓审查 | ✅ Supabase/Postgres 迁移工具成熟；ALTER 功能比 SQLite 强；Django ORM/SQLAlchemy 自动迁移 | 两者迁移能力相近；SQLite 已验证 31 版本无事故 |
| **多设备同步** | ⚠️ 需要实现（见上节：SQLite 热备 + 事件溯源 + CRDT 三阶段方案）；无内置；用户自己负责文件备份/传输 | ✅ 天然共享状态；多设备读写同一 DB；冲突服务端 LWW 解决；但 AI 伴侣数据跨设备一致性是核心需求 | 10 周方案补齐 SQLite 同步能力；不因此换云端 |
| **并发与规模** | ✅ 单用户单写者；WAL 模式读并发 100+ 连接；10GB 库 FTS5 查询 p95 <10ms；个人资料/聊天/Wiki 规模永远 <10GB | ✅ 多用户多写并发；TB 级；但单用户 1GB 以下云端反而比本地慢（网络往返） | 单用户场景 SQLite 性能是云端 100~1000× |
| **AI 功能本地计算** | ✅ embedding/sqlite-vec/FTS5 同进程；向量查询不跨网络；中文 embedding 模型本地跑 100ms 内；AI 记忆召回无出口 | ❌ embedding 发出去要花钱/要 API Key；向量数据库（Pinecone）超额度收费；中文 embedding 第三方不一定有 | 模型本地优先是核心产品诉求 |
| **破坏恢复与可移植性** | ✅ 单文件复制粘贴；`.db-wal`/`.db-shm` crash-safe；`sqlite3 .dump` 文本备份；损坏走 `PRAGMA integrity_check` 修复 | ⚠️ 云厂商导出功能各有差异；停机迁移；跨平台导出格式不统一；删除不保证真删 | 用户数据必须随时能脱离 Lumii |
| **Full-text Search 与向量** | ✅ FTS5 内置可重建 BM25；sqlite-vec 本地向量，与业务表同事务一致性 | ✅ Postgres pg_trgm + pgvector 更强；但跨网络语义查询延迟；同事务一致性难（向量库可能独立） | 当前 FTS5 足够；向量 P3 再评估 sqlite-vec 性能 |

**最终决策铁律**：`packages/pet-core`、`packages/agent-runtime`、`apps/windows/src/main/database` **所有业务数据一律落 SQLite**；不新增任何远程数据库依赖；远程只允许作为"可选的同步中继/备份目的地"，用户不配置就完全不启用；任何核心功能不得因网络缺失而降级。
