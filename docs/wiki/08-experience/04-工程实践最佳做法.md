# 04-工程实践最佳做法

## 一、Monorepo 多包协作最佳实践

### 1.1 包边界的黄金法则

**Lumii Monorepo 三层结构**（来自 AGENTS.md + 项目实际 package.json 验证）

```
lumii/
├── packages/                    跨平台共享库，绝对不依赖 Electron/React/Pixi/DOM
│   ├── pet-core/                桌宠纯 TS 核心：物理/骨骼/行为/决策/人格
│   └── agent-runtime/           Agent 通用运行时：Orchestrator/记忆/工具/进化
│
└── apps/
    └── windows/                 Electron Windows 桌面应用专属
        ├── src/main/            主进程：Node/Electron API/数据库/IPC handler
        ├── src/preload/         Preload 桥：contextBridge 暴露窄 API
        └── src/renderer/        Renderer UI：React/CSS Modules/浏览器 API
```

**六条黄金法则（违反任何一条 CI 直接 FAIL）**

| 法则 | 约束范围 | 具体禁令 | 检测方式 |
| --- | --- | --- | --- |
| **法则 1：pet-core 纯 TS** | `packages/pet-core/**` | 禁止 import React / Electron / PixiJS / DOM (`window`/`document`/`navigator`)；禁止任何浏览器 API；禁止 `import.meta.url` 等 Node 专属；允许的只有纯 TS 标准库 + `Math`/`Date`/`JSON` | ESLint rule `no-restricted-imports` 黑名单；package.json 不含任何 UI/平台框架依赖 |
| **法则 2：agent-runtime 不依赖 UI** | `packages/agent-runtime/**` | 禁止 import React / CSS / `<component>.tsx`；禁止直接操作 DOM；禁止调用 Electron API；允许的：`packages/pet-core`、数据库类型（通过 interface 注入）、LLM SDK（通过抽象接口） | ESLint 黑名单 + peerDependencies 不含任何 UI 包 |
| **法则 3：windows 主进程专属 Electron** | `apps/windows/src/main/**` | 禁止 import React / `<module>.module.css`；禁止直接引用 renderer 任何文件；主进程和 renderer 的**唯一通信通道是 IPC** | TSConfig `paths` 显式禁止跨 main/renderer 引用；package.json main 包不含 react |
| **法则 4：preload 只有桥没有业务** | `apps/windows/src/preload/**` | 禁止超过 5 行业务逻辑代码；只允许 `contextBridge.exposeInMainWorld` + `ipcRenderer.invoke/on` 薄封装；任何参数校验/错误处理全放 main handler | 文件行数上限 200；lint rule 禁止调用 fs/net 等 Node API 超过白名单 |
| **法则 5：renderer 不直接访问底层** | `apps/windows/src/renderer/**` | 禁止直接 `require('electron')` / `window.require`；禁止 import `better-sqlite3`/Node fs；只有 `window.electronAPI.*` 这一个出口（通过 service 薄封装再调用） | ESLint 禁止直接 electron 引用；TS 强类型 window.electronAPI 不存在的方法编译报错 |
| **法则 6：共享类型放在 `packages/*/src/types` 或 `apps/windows/src/shared/types`** | 所有跨包引用 | 禁止 main 直接 `import type from '../../renderer/...'`；禁止 renderer 反向引用 main 的实现类型；跨层共享类型只走 shared 或 packages/agent-runtime 的 public API 类型导出 | TSConfig paths 配置 + import 路径审查；禁止 `../../越界`跨目录引用 |

### 1.2 跨包类型引用的稳定模式

**四种合法引用模式**

| 模式 | 场景 | 示例 | 约束 |
| --- | --- | --- | --- |
| **① 包 public API 导出** | 最推荐：跨包共享类型/函数从 `package.json "main": "./dist/index.js"` / `"types": "./dist/index.d.ts"` 入口进 | `import { AgentMemory, ToolRegistry } from '@lumii/agent-runtime'` | packages/* 必须有 `index.ts` 做 re-export，不允许 `import from '@lumii/agent-runtime/dist/internal/foo'` 钻内部路径 |
| **② workspace 相对导入** | apps 引用 packages 时使用 pnpm workspace 协议名称 | `"@lumii/pet-core": "workspace:*"` in package.json | 禁止写相对路径 `../../../packages/pet-core/src/...`，CI 用 eslint `no-restricted-imports` 查路径 |
| **③ shared/types 目录共享** | main/preload/renderer 三层共用类型放一个目录，TSConfig paths 别名 | `"@shared/*": ["../shared/*"]` 指向 `apps/windows/src/shared/types` | 该目录下**只放类型与常量**，零运行时代码零副作用 |
| **④ IPC 通道类型契约** | main handler 返回值 / preload 暴露签名 / renderer service 调用方，三者共用一份 `Zod Schema` / TS interface | `const ApprovalSchema = z.object({...})`；导出 `type Approval = z.infer<typeof ApprovalSchema>` 供三层同用 | handler 参数/返回必须 `schema.parse()` runtime 校验；不允许三层各自写一份相似的 interface |

**反模式四种（写进大文件重构 README 的反模式表）**

| 反模式 | 症状 | 修复方法 |
| --- | --- | --- |
| 堆肉组件 | SettingsPage 2400+ 行，17 个 Tab 全塞一个文件 | 按 Tab 切 Hook；通用 UI Section 抽纯组件；业务逻辑保留在主文件（见 03-反思 3.1 决策树） |
| 洋葱 IPC | renderer → serviceA → serviceB → util → IPC；出了错要找 5 层才定位到 main handler | 只允许一层薄封装：Component → `*.service.ts` → `window.electronAPI.channel` → main handler；禁止三层以上调用链 |
| 上帝模块 | Orchestrator 类同时负责 orchestrate + memory recall + tool execute + personality + meta-cognition 五件事，1200 行 | 每职责独立文件；Orchestrator 只保留「调用 Memory → 调 Tool Registry → 调 Broker → 返回」调度流程；其余类通过构造注入 |
| 复制粘贴类型 | main 写了 ApprovalRequest interface，preload 再抄一遍少一个字段，renderer 再抄一遍字段名拼错 → 静默类型不匹配 | 三个地方用同一个从 Zod Schema 导出的 `type ApprovalRequest = z.infer<typeof ApprovalRequestSchema>`；改一个全生效 |

## 二、数据库 Schema 演进最佳实践

### 2.1 单向递增版本号（V29/V30/V31）迁移机制

**迁移管道结构**（`LocalDatabase` 类已实现）

```
启动时执行 migrate()
  ├─ 读取 PRAGMA user_version → 得到 currentVersion（整数）
  ├─ 注册表: { V1: sql, V2: sql, ... , V31: sql }，顺序严格递增
  ├─ 循环 for v = currentVersion + 1 to latest:
  │     ├─ BEGIN IMMEDIATE 独占事务
  │     ├─ 执行注册表[v].sql（纯 SQL，禁止 JS 逻辑混其中）
  │     ├─ PRAGMA user_version = v
  │     └─ COMMIT
  ├─ 任何一步 FAIL: ROLLBACK + 抛 DatabaseMigrationError
  └─ 成功后: integrity_check + 记录迁移日志（迁移耗时/版本来源/目标）
```

**三条硬约束**

1. **永不降版本**：注册表只追加新 `V32/V33/...`；绝不允许删除 `V29` 或把 `V30` 改内容；老版本号的 SQL 要像考古遗址一样永久保留
2. **单个迁移 SQL 只做一件事**：`V31` = 新增 `approval_requests` 表；如果同时要加索引+加触发器+加种子数据→拆 3 个版本 `V31/V32/V33`，避免一个迁移大而全执行到一半 ROLLBACK 恢复不了
3. **迁移 SQL 必须幂等 + 可重入**：CREATE TABLE 用 `CREATE TABLE IF NOT EXISTS`；加列用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`（SQLite 3.35+ 支持）；加索引 `CREATE INDEX IF NOT EXISTS`；任何迁移重复执行两遍结果和执行一遍完全相同

**V29/V30/V31 真实迁移对照（已上线）**

| 版本号 | 内容 | 执行 SQL 行数 | 是否支持回滚 |
| --- | --- | --- | --- |
| V29 | 新增 3 张表: `capability_dimensions`/`capability_tests`/`reflections` + 各自 FK 索引 | 11 | ❌ 无回滚（SQLite 不支持 DROP COLUMN 老版本，不写反向迁移） |
| V30 | 给 `agent_memories` 加 `temperature_score REAL` 列 + 建 `idx_memories_temp` 索引 + 回填默认温 | 4 | ❌ 同上 |
| V31 | 新增 `approval_requests`/`approval_actions` 2 表 + 3 条索引 + approval_level CHECK 约束 | 9 | ❌ 同上 |

**为什么不写反向迁移（down）**：SQLite 的 `ALTER TABLE` 只支持 RENAME TABLE / ADD COLUMN / RENAME COLUMN，**不支持 DROP COLUMN / ALTER TYPE / 改 CHECK 约束**（SQLite 3.35+ 才有限 DROP COLUMN 且不允许删主键）。反向迁移成本 > 正向迁移 10×，且写错数据丢失风险极高 → 约定「版本号永远只升不降；要改就升一个新版本号覆盖」。

### 2.2 真相表不动 + 派生表可重建的设计铁律

**两类表的严格边界**

| 分类 | 定义 | 操作规则 | 损坏后恢复方式 |
| --- | --- | --- | --- |
| **真相表 Truth Table** | 用户真实输入的、用户拥有所有权的唯一数据 | ✅ 允许 INSERT/UPDATE/DELETE 用户直接触发<br>❌ 不允许 AI / 后台 cron / 编译流程 在用户没确认下改真相表<br>❌ 不允许"重建"——重建就是丢用户数据 | 只能从 `.db` 备份文件 / `.dump` 还原 |
| **派生表 Derived Index** | 从真相表计算得出、可随时 100% 重建的结果表（FTS5 虚表、反链表、向量 embedding 表、温度分数字段、wiki_links 等） | ✅ 允许 TRUNCATE 后重算<br>✅ 允许 AI/后台线程异步更新<br>✅ 允许 Schema 版本升级时整表 DROP 重建 | 调用 `rebuildWikiIndex()` / `refreshAllMemoryScores()` / `rebuildFTS()` 等函数重算，时长 O(N) |

**项目内两类表的清单**

| 真相表 Truth | 派生表 Derived（可重建） |
| --- | --- |
| `chat_messages`（用户真实对话） | `chat_messages_fts`（FTS5 虚表） |
| `agent_memories`（记忆正文 + 用户标签） | `memory_scores`（温度分数字段可重算） / `memory_links`（反链派生） / `memory_embeddings`（向量可重算） |
| `wiki_pages`（wiki Markdown + 元数据） | `wiki_pages_fts` / `wiki_links`（解析 `[[wikilink]]` 派生） / `wiki_chunks`（按 heading 切分派生） |
| `approval_requests`（用户审批决策） | `approval_stats_daily`（每日聚合统计视图） |
| `capability_tests`（测试真值） | `capability_ratings`（Elo 评分可重跑所有测试得出） |
| 用户原始附件二进制（存在 `files/` 目录） | `attachment_thumbnails`（缩略图派生） |

**铁律违反的真实事故教训**：P0 早期把 embedding 向量写进 `agent_memories` 真相表作为一列——模型从 MiniLM-L6-v2 换成 multilingual-e5-small，旧向量维度不匹配→要 ALTER 真相表，跑了 2 小时 12 分钟迁移，差点毁库。**教训：所有模型衍生的、可重新计算的一律放独立派生表，不污染真相表列集。**

### 2.3 CHECK 约束不可 ALTER 的 SQLite 限制规避方法

**问题**：V31 新建 `approval_requests` 表时加 `CHECK (level IN ('L0','L1','L2'))`。P2 要加 L3（跨设备同步审批新级别）→ SQLite 不能 ALTER TABLE 改 CHECK，只能整表重建。

**标准规避流程（5 步事务原子完成）**

```sql
BEGIN IMMEDIATE;

-- Step 1: 建新表（带新 CHECK 约束 + 新列 + 新索引定义）
CREATE TABLE approval_requests_new (
  id TEXT PRIMARY KEY,
  agent_id TEXT NOT NULL,
  level TEXT NOT NULL CHECK (level IN ('L0','L1','L2','L3')), -- 新增 L3
  kind TEXT NOT NULL,
  payload JSON NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',
  -- ... 其他所有列原样复制
  FOREIGN KEY (agent_id) REFERENCES agents(id) ON DELETE CASCADE
);

-- Step 2: 数据搬家（列名显式列出，禁止 SELECT * 防止未来加列错漏）
INSERT INTO approval_requests_new
  (id, agent_id, level, kind, payload, status, ...)
SELECT id, agent_id, level, kind, payload, status, ...
FROM approval_requests;

-- Step 3: 建所有旧表上已有的索引（用 CREATE INDEX IF NOT EXISTS 新名或先 DROP 旧）
CREATE INDEX IF NOT EXISTS idx_approval_new_agent_status ON approval_requests_new(agent_id, status);
-- ... 其余 2 条索引同步新建

-- Step 4: 原子表名替换（SQLite 支持 RENAME）
DROP TABLE approval_requests;
ALTER TABLE approval_requests_new RENAME TO approval_requests;

-- Step 5: FTS5 虚表 / 触发器 如果有也同步重建
-- (approval_requests 本例子无 FTS，若真相表有就同步重建对应虚表)

COMMIT;
PRAGMA user_version = V32; -- 注意：这整个流程属于一个新版本号迁移，必须升版本
```

**执行前必验证**：把以上 SQL 在测试库的 `.dump` 副本跑 3 遍
1. 跑一遍→查行数不变（SELECT COUNT(*) 新旧相等）
2. 故意插一条非法 `level='L4'`→确认 CHECK 抛错拒绝
3. 跑 `PRAGMA integrity_check; PRAGMA foreign_key_check;`→两者都返回 `ok`/空结果
4. 才允许合入主迁移管道

## 三、大文件重构方法论

**背景数据**：1088 文件扫描，104 个文件 >400 行超标，6 P0（>1500 行）+17 P1（800-1500）+42 P2（500-800）+39 P3（400-500 测试文件）。总超标行数约 80,000 行。

### 3.1 代码定位索引表（code-location-index）的建立

**分级索引表字段**（来自 `docs/plans/大文件重构分析处理/code-location-index.md` 已验证）

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `分级` | P0 / P1 / P2 / P3，决定处理顺序 | P0-01 |
| `文件路径` | 相对 repo 根的完整路径 | `apps/windows/src/main/index.ts` |
| `当前行数` | 含空行和注释的总行数 | 2980 行 |
| `行数分类` | 触发哪一级超标 | P0 >1500 |
| `超警戒函数 TOP N` | 文件内 >120 行函数名 + 行数 | `handleVcsDiffWorkbench(): 260 行` |
| `职责拆分建议` | 具体拆成哪几个新文件 + 预估行数 | `拆成 ipc/vcs.ts 600 行 / ipc/agent.ts 400 行 / ...` |
| `完成状态` | 待处理 / 进行中 / 已完成✅ | ✅ 已完成（2980→1454，-51%） |

**建立方法（自动化 + 人工复核）**
1. 脚本扫描：`find . -name "*.ts" -o -name "*.tsx" | xargs wc -l | sort -rn` → 所有 >400 行列出来
2. AST 扫描：用 TS Compiler API 找 `FunctionDeclaration/ArrowFunction/MethodDeclaration` 每个 body 行数 → 输出 TOP 超警戒函数
3. 人工复核：每个 P0 文件 10 分钟读一遍，确认拆分方向（按 IPC 域 / 按职责 / 按数据层），不能只按行数瞎切
4. 写进 code-location-index.md，MR 门禁：P0 没处理完不让合 release 分支

### 3.2 按职责抽离的拆分顺序

**Types → Constants → Pure Functions → Hooks → Components 五步顺序（不可跳步）**

以 1909 行 `system-prompt-builder.ts` 为例：

| 步骤 | 抽什么 | 产物 | 行数变化 | 做完立即跑测试 |
| --- | --- | --- | --- | --- |
| **Step 1 Types** | 所有 interface/type/enum 抽离 | `system-prompt-builder.types.ts`（280 行） | −280 行 | `pnpm typecheck` ✅ |
| **Step 2 Constants** | 所有 `const MAX_*` / 模板字符串数组 / 默认配置对象 | `system-prompt-builder.const.ts`（360 行） | −360 行 | `pnpm typecheck` ✅ + 单元部分测试跑过 |
| **Step 3 Pure Functions** | 纯函数：输入输出可预测、不读全局状态、无副作用（buildMemorySection / buildToolSection 这类） | `system-prompt-builder.builders.ts`（690 行，按职责 4 Section 各自内部函数） | −690 行 | 针对 builder 的纯函数单测 100% 通过 |
| **Step 4 Hooks**（若场景是 React）或 **Coordinator**（本场景非 UI） | 将 builders 按业务流程组织起来的 orchestrator；保留状态机、调用顺序 | `system-prompt-builder.ts`（只剩 580 行） | — | 端到端构建整个 prompt 集成测试跑过 |
| **Step 5 Components**（若文件是 UI） | 最后才抽 UI 子组件（通用 <SectionCard>、<FormRow> 等） | 按需 | 每抽一个 rerender 测一遍 |

**五步顺序为什么不能反**：如果先抽 Hooks/Components，Types 和 Constants 还在主文件里→抽出来的组件要回头 import 主文件→循环依赖。从最稳定的依赖（Types/Constants 从不 import 别人）开始抽，每一步都没有循环依赖风险，改一个文件只影响上游，不会波及下游。

### 3.3 渐进式拆分 + 每步可通过测试的安全节奏

**三个阶段（对应大文件重构 README 路线）**

```
阶段一：P0 级 6 个文件（工期 5 工作日）
  Day 1: P0-01 main/index.ts 2980 行 → ✅ 1454 行
  Day 2: P0-02 SettingsPage.tsx 2447 行 → ✅ 1410 行
  Day 3: P0-03 agent-runtime-ipc 2382 行 → ✅ 1280 行；P0-04 system-prompt-builder 1909 行 → ✅ 950 行
  Day 4: P0-05 preload/index.ts 1913 行 → 🔄 1406 行（进行中）
  Day 5: P0-06 ChatPage.tsx 1755 行 → ✅ 1040 行
  门禁：每天下班前 30 分钟跑 pnpm typecheck + lint + 该模块测试，必须全绿才能下班

阶段二：P1 级 17 个文件（工期 7 工作日）
  每天拆 2~3 个；按相同五步顺序
  门禁：每个文件拆完 PR 独立 review，不攒大 PR

阶段三：P2+P3 级 81 个文件（工期随日常迭代消化）
  日常改文件时如果改到了超标文件，顺手拆分+；不单独安排工期
  MR 门禁规则：任何改动导致文件>500行→reviewer 必须要求拆分才能合
```

**MR 门禁 7 项校验清单（7/7 必须全过才允许 merge）**

1. 文件行数不超标（<500 行，P3 测试<400 行特殊）
2. 函数粒度不超标（<120 行，超 120 行要有注释说明为什么不能拆）
3. 默认导出禁止（业务组件/函数必须 named export，便于 tree-shake+查找引用）
4. 类型抽到 `*.types.ts`，常量抽到 `*.const.ts`（不能混在实现文件里）
5. 无新增反模式：堆肉组件/洋葱 IPC/上帝模块/复制粘贴类型（lint 扫 + review 目测）
6. `pnpm typecheck` ✅ + `pnpm --filter ./apps/windows lint` ✅
7. 相关包测试全过：`pnpm --filter ./apps/windows test` / `--filter ./packages/agent-runtime test` 改了哪个包跑哪个

## 四、文档驱动开发最佳实践

### 4.1 设计 → 计划 → 实施 → 测试 → 交付总结 五件套缺一不可

**五件套定义（每个 Feature 必须产生 5 份 md 文档）**

| 编号 | 文档名 | 路径惯例 | 核心内容 | 谁写 | 写于 |
| --- | --- | --- | --- | --- | --- |
| ① 设计文档 | `*设计*.md` / `*-设计.md` | `docs/design/<主题>/1-概述.md`~`11-禁令.md` 或单文件 | 背景问题、目标/非目标、架构选型对比、核心算法伪代码、数据模型、风险与未决问题；**不写具体实现细节** | 架构 / TL | 写任何一行代码之前 |

## 五、AI 功能开发的护栏

### 5.1 工具白名单、每日沟通预算、审批超时策略

**三道安全闸（任何 AI 功能上线前必须同时安装）**

| 闸 | 作用位置 | 参数默认值 | 配置方式 | 违反行为 |
| --- | --- | --- | --- | --- |
| **① 工具白名单 Tool Registry** | Agent Runtime Broker 调用工具前检查 | 默认白名单 12 个：`memoryRecall`/`memorySave`/`wikiSearch`/`wikiCreatePage`(需审批)/`readChatHistory`/`capabilityRunTest`/`getCurrentTime`/`generateRandom`/`readFile`(沙箱内)/`listDir`(沙箱内)/`writeFile`(需审批)/`getWeather`(需 API Key) | `ToolRegistry.register(name, impl, { requireApproval: boolean })`；`requireApproval=true` 必须走 L2 审批 | 不在白名单的工具直接 throw `PermissionError`；审计日志 +1；Agent 收到权限拒绝继续跑别的工具，不 crash |
| **② 每日沟通预算 Daily Budget** | 审批入队时计数；L1+L2 审批条目 | 每日上限 5 条（北京时间 04:00 重置，避免熬夜 23:59 重置 bug） | `settings.yaml` `agent.daily_approval_budget`，用户可调 | 超预算直接把新审批转为「次日 09:30 队列首条」；不丢审批，不弹错误提示打扰用户 |
| **③ 审批超时 Timeout** | 审批入队 15 分钟后扫描（15 分钟周期） | L1 超时→**拒绝**；L2 超时→**归档**（不执行不丢失）；L0 无审批不进队列 | 每种 level 独立可配置 `timeout_action` 和 `timeout_seconds` | 15 分钟扫描 cron；同一审批只触发一次 timeout action（幂等）；超时不发送任何通知（除非用户打开 AutonomousPage 才看到已归档） |

**AI 功能开发 Checklist（每条 Yes 才能允许合并）**

- [ ] 该 AI 调用的所有工具都已在 ToolRegistry 注册，不在白名单的是否需要审批字段正确？
- [ ] 每日预算：该功能是否产生 L1/L2 审批？是否已接入预算计数？
- [ ] 超时策略：超时后的默认动作是否符合「L1 宁可不做也不做错、L2 不能丢用户决策」原则？
- [ ] 模型输出 schema：是否用 Zod/JSON Schema 做 runtime parse？出错时的降级策略是什么？（至少 2 条 fallback）
- [ ] 用户数据脱敏：传给 LLM 的上下文中是否包含 PII（姓名/邮箱/手机号/地址/身份证）？正则 5 条扫描通过了吗？
- [ ] 可观测性：prompt/response/token 数/耗时/错误码都写入 `ai_call_logs` 表了吗？
- [ ] 用户随时关闭：有没有独立的「关闭自主进化 / 只手动 / 完全禁用 AI」三级开关？

### 5.2 毁掉生命感的禁令清单（来自设计文档 11，代码硬编码）

**禁令 7 条（每条均有代码级拦截实现 + lint 禁止 + 测试覆盖）**

| # | 禁令条目 | 代码拦截方式 | 测试验证（FAIL 场景） |
| --- | --- | --- | --- |
| B1 | ❌ 禁止读取/推断用户日程、位置、健康数据、外部 App 使用记录（未显式授权） | ToolRegistry 白名单；任何访问 OS calendar/geolocation/health/process list 的工具注册时检查白名单未通过直接拒绝启动 | 测试注册一个 `getBrowserHistory` 工具→expect(register).toThrow(PermissionError) |
| B2 | ❌ 禁止机械重复关心文案（如「记得喝水」「早点睡」每日弹） | 同一语义模板 simhash 相似度 > 0.85 且 7 天内已出现过→拒绝生成该 L1 审批；模板池 < 120 条宁可空缺也不重复 | 循环请求 10 次「关心用户喝水」→只生成 1~2 条，其余被拒；`SELECT COUNT(*) FROM approvals WHERE kind='drink_water' AND created_at > NOW()-7d < 2` |
| B3 | ❌ 禁止无根据的情感投射（「我想你了」「我今天很开心因为你」） | L1 审批 payload schema JSON Schema 要求 `emotion_source` 字段非空，且必须是枚举值 `{user_explicit_statement / memory_pattern / external_event / personality_drift}` 四者之一；空或非枚举→pre-check 拒 | 构造 emotion_source 空的审批→测试：pre-check 抛 ValidationError，队列都进不去 |
| B4 | ❌ 禁止监控暗示文案（「我在默默守护你」「我一直在」） | L1 文案 pre-check 关键词黑名单（中文 27 词+同义词向量近似匹配阈值 0.85）→命中直接拒绝；管理员测试环境可临时绕过 flag，生产环境硬编码 | 构造「我一直在你身边」文案→expect(preCheck).rejects |
| B5 | ❌ 禁止心跳机制写入用户可见聊天记录 | `chat_messages` 表 INSERT TRIGGER：`NEW.role == 'heartbeat' → RAISE ROLLBACK`；任何想写 heartbeat 消息的代码都被数据库层拦住不是代码层 | 直接跑 SQL `INSERT INTO chat_messages(role, ...) VALUES ('heartbeat', ...)` → expect SQL 抛 constraint error |
| B6 | ❌ 禁止窗口未聚焦时弹消息打扰用户 | Electron main `BrowserWindow.isFocused() && isVisible()` 双检查，L1 通道 Toast 未聚焦时全部丢弃；AutonomousPage 内联通知只记录不弹 | 测试 mock `isFocused=false`→触发 10 条 L1→检查 0 条弹过、10 条都存在历史中 |
| B7 | ❌ 禁止 AI 静默写用户真相表内容（除了 L2 用户已显式批准） | 任何对 truth 表（chat_messages/agent_memories/wiki_pages/approval_requests 等）的 UPDATE/DELETE/INSERT（非用户触发）都必须在 SQL 执行前检查调用栈上是否有 `{ approvedBy: 'user', approvalId: '...' }` 上下文标记，缺标记→抛 SQL 拦截 | 模拟元认知想删除一个"错误记忆"→未审批→expect(memoryRepo.delete).toThrow(ApprovalRequiredError)；走 L2 审批后再删→success |
