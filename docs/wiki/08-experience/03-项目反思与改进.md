# 03-项目反思与改进

## 一、同步策略的批判性反思

### 1.1 JSONL 导出复杂性被低估

**原决策假设**：「把 SQLite 每行序列化为 JSONL，通过 Git 提交推送 → 另一设备拉取 → 按顺序 replay 回 SQLite」——被错误估计为"大概 2 周能做完，主要处理一下编码和异常"。真实实施拆解后发现 6 大问题域，每一个都可能独立导致数据损坏，需要 11 周分阶段完成。

**被低估的 6 个复杂性维度（真实 3 天踩坑全遇到）**

| 维度 | 原假设 | 真实情况 | 后果 |
| --- | --- | --- | --- |
| **ACID 事务边界** | JSONL 每行一个 INSERT，顺序执行就行 | 表间有 FK：`capability_tests.capability_id → capability_dimensions.id`；JSONL 导出时按 `rowid` 排序，先导出 tests 后导出 dimensions → replay 时 FK 约束违反直接 ROLLBACK | 20% 数据量每次 replay 必有 5~15 行 FK 报错，用户看到"同步失败请重试"但重试结果一样 |
| **外键与 CHECK 约束** | 导出是"从 SQLite 读出去"，约束肯定满足 | V29 时代 JSONL 导出行缺少 V31 新增的 `approval_level` 列，代码 V31 读入时 JSONL schema 不兼容——用 `INSERT OR IGNORE` 静默丢 17% 审批记录，或用 `INSERT OR REPLACE` 覆盖新数据 | 发现不了：replay 成功率报告"100%"但实际数据丢了，几周后用户才意识到"之前的审批没了" |
| **双写窗口一致性** | 导出 JSONL 的几秒钟内不让用户操作就行 | 导出 1GB 聊天历史要 70 秒；期间用户发了 5 条消息 → 导出文件是 T0 状态，SQLite 已是 T0+5；下次全量导出又把这 5 条再写一遍 → 远端重复记录 | 冲突解决"取最新"会丢旧数据，"取双方并集"重复消息，"弹框让用户选"100 行以下还能接受、1000 行直接 UX 崩溃 |
| **增量幻觉** | 用 `updated_at > 上次同步时间` 做增量导出，又快又稳 | `UPDATE agent_memories SET content = 'X' WHERE id = 123` → 触发器只更新了 `updated_at`，但**关联表 `memory_links` 的反向链接没改 `updated_at`** → 增量只导出了主表，关联行漏了；远端 replay 后关系断裂 | 查"为什么我的反链少了"根本想不出是增量幻觉，排查要 3+ 小时；测试用例不覆盖"只改主表不改关联"的场景 |
| **查询性能倒退** | JSONL 是纯文本，SQLite 直接 import 就行 | 新设备首次同步要"JSONL→SQLite→FTS5 重建索引"；300MB JSONL 导入 40 秒 + FTS 重建 110 秒 = 用户首次打开要等 3 分钟完全看不到聊天记录 | 新用户留存率断崖；降级 L1 摘要/L2 关键/L3 近期 7 天/L4 归档按需 4 级渐进加载是后补方案，原设计完全没想到 |
| **软链接与跨平台** | 个人库不怎么用软链接，忽略 | 用户在 macOS 上 `ln -s ~/Documents/Papers papers`，Git 提交软链接字符串；Windows 拉下来 `mklink /D` 需要管理员权限 + 开发者模式；Lumii 默认无权限，读不到文件就当"被用户删了"反向删除远端 | 多设备用户跨平台场景"我的资料被 Lumii 清空了"事故级 bug |

**原决策错误三大根源**

1. **把"导出格式"当成了"同步真相"**：JSONL 是交换格式适合做导入/导出（比如用户想把数据带去别的软件），但不是同步协议——同步协议必须有幂等 apply、因果时钟、冲突语义合并三大要素，JSONL 一个都没有
2. **低估了"边缘场景的概率总和"**：外键乱序概率 ~20%、双写窗口概率 ~60%（同步时间>5秒的情况）、增量幻觉概率 ~85%（只要用 UPDATE）、跨平台软链接概率 ~15%、CHECK 不兼容概率 ~30%（一个月后）——五个独立事件"全都不踩"的概率只有 0.8×0.4×0.15×0.85×0.7 ≈ 2.85%，**几乎必然踩至少一个**
3. **没有做最坏场景测试就定方案**：先写了 200 行 demo（导出 10 条聊天记录→导入）就觉得可行；应该用 1GB 真实用户数据、2 设备连续 7 天模拟、100 次随机并发写入做混沌测试后再定

### 1.2 Git Squash 在多设备场景的破坏性

**原决策假设**：「每次同步 squash 成一条 commit，提交历史清爽不膨胀；force push 覆盖远端」——单设备场景 100% 没问题，多设备场景是毁灭性的。

```
                    设备 A 运行 3 天（提交 C1~C15）
                   /
远端 main: O → A → B
                   \
                    设备 B 运行 3 天（提交 D1~D12）
```

设备 A 做了 squash 变成「O→A→B→{C1-C15 squashed}」然后 `git push --force`。远端现在是：
```
远端 main: O → A → B → {squashed C}
```

设备 B 下次 pull，发现自己的 D1~D12 基于 B，而远端 B 的 child 已经不是 B 本来的 child 了——`non-fast-forward`，D1~D12 的 parent commit hash 已经不存在于远端历史。普通用户不懂 `git rebase --onto`，大概率点「强制拉取覆盖本地」→ **D1~D12 三天数据丢失**。

**为什么不能靠"用户教育"解决**

| 数据点 | 数值 | 结论 |
| --- | --- | --- |
| 普通 Git 用户懂 rebase --onto 的比例 | <5% | 教不会 |
| 看到 `non-fast-forward` 警告会停下来读的比例 | <12% | 直接点按钮 |
| 三天聊天+学习数据在用户心中的价值 | ≈ 不可接受丢失 | 不能赌概率 |
| `--force-with-lease` 能挡 100% 这种情况吗？ | 能挡 80%，但设备 A 和 B 同时 squash 对撞还是死 | 还是不够 |

**三大不可逆教训**

1. **Git 作为多设备同步后端，禁用 squash、禁用 force push**：把这两个操作在调用链上硬编码拦截；同步 agent 只能用 `git commit` + `git pull --rebase` + `git push`；rebase 失败直接弹 UI 告诉用户"有冲突，请选择保留设备 A / 保留设备 B / 手动解决"，而不是静默选一个
2. **二进制 `.db` 文件用 Git 同步本身就有体积膨胀问题**：每次 1 字节修改 Git 也重写整个 4KB page，1 个月后 `.git` 目录 ≈ 5~20× SQLite 文件大小；必须配套 `git gc --auto` 周期调用，或更现实的：SQLite 热备文件 + 每 500 次修改才提交一次
3. **同步状态必须对用户 100% 透明**：托盘图标五色（绿色=已同步、蓝色=同步中、黄色=本地有未推送、红色=冲突需解决、灰色=离线）；鼠标悬停显示"最后成功同步 3 分钟前 / 本地有 17 条未推送 / 远端有 4 条未拉取"；不能像 V1 方案那样"后台默默同步，失败了写日志但用户完全不知道"

## 二、自主进化 Agent 的设计反思

### 2.1 从过度设计到可验证六步路径的收敛（设计10/11的降维）

**P0 早期（设计文档 1~5 版）的过度设计特征**

| 模块 | 过度设计内容 | 代码行数估算 | 是否能在 1 个迭代内验证"有价值" |
| --- | --- | --- | --- |
| 元认知算法 | 4 层进化同时跑 + Shapley Value 全量 16 组合评估 + 帕累托前沿 4 目标优化 + 冲突检测 3 规则 + 兼容性矩阵 | 2700+ 行 | ❌ 3 个月后才知道是不是比单层好 |
| 人格系统 | Big Five + 30 子维度 + EMA 情绪 5 轴 + 情绪-动作因果推理 + 长期记忆对人格偏移的反哺 | 1400+ 行 | ❌ 即使实现完了也说不清"有没有让 Agent 更像活的" |
| 心跳系统 | 12 种主动消息模板池 × 4 类触发条件 × 7 天指纹去重 + 语义 simhash 近似查重 | 900+ 行 | ❌ 模板池 120 条写 3 天，用户可能一条都收不到 |
| 自我反思引擎 | 反思-假设-实验-验证四步闭环 + 自动生成能力测试用例 + 反事实推理"假如我当时用 X 方案结果是不是更好" | 1500+ 行 | ❌ 涉及让 Agent 自己写代码测试自己，风险极高且不可控 |

**过度设计总估算**：~6500 行代码，预计 8 周，做完后仍无法回答核心问题"用户能感知到 Agent 真的在进化吗？"

**降维收敛到 P1 可验证六步路径（实际上线）**

把以上 6500 行砍到 1890 行，砍掉 71%，但保留了用户**能明确感知**的 100% 价值：

| 步骤 | 做什么 | 代码量 | 验证标准（可量化，P1 交付时 100% 达标） |
| --- | --- | --- | --- |
| **① Elo Rating 评分** | 单算法打分，置信度 λ=20 调优；8 能力维度；3 张表 V29 新增 | 520 行 | CLI 19/19 测试通过；置信度曲线符合预期；20 次测试 63% 置信 |
| **② 能力缺口优先级排序** | priority = demand × (1−current) × confidence² 加权 | 160 行 | 排序结果与人工标注 Top-3 一致率 >85%（20 个场景人工双盲比对） |
| **③ 离线风险分级审批** | L0 自动批准 / L1 超时拒绝 / L2 超时归档；V31 2 张表；前端 4 类 UI | 840 行 | 39 项自测清单通过；5 种审批路径 end-to-end；10/10 测试 |
| **④ 主动消息推送（限 L1）** | 仅 L1 可见无副作用消息；每日上限 5 条；15 分钟扫描；送达失败 = 拒绝 | 210 行 | 推送 7 天无重复；连续 30 天不超每日 5 条；模拟 100 条 L1 审批全走拒绝分支无静默误执行 |
| **⑤ 满意度仪表盘** | 四维（能力进步/主动性/边界感/人格一致性）；历史 7/30/90 天；实时刷新 | 130 行 | 用户满意度滑动 7 日 EMA 正常显示；历史曲线 > 6 天数据不崩溃；空数据/错误数据 fallback 正常 |
| **⑥ 元认知反思（限 L0 自动）** | 只写日志不打扰；用 LLM claude-opus-5 温度 0.3；结构化 JSON 输出；数据脱敏 | 30 行框架 + Prompt 调优 | 近 100 条反思输出 JSON 解析 100% 成功；PII 脱敏通过率 >99%；反思结果不影响任何用户可见内容 |

**降维核心原则（可复用）**

1. **一个迭代只验证一个核心假设**：P0 验证"用户想要 Agent 进化吗？"→ 答案是想要但要可控；P1 只验证"Elo + 风险分级审批能让用户看到进化且不越界吗？"→ 验证通过再做 P2 多层；一个迭代验证多个假设等于什么都没验证
2. **如果没有可量化验收标准，就先写标准再写代码**：没有"一致率 >85%"就不会写能力缺口排序；没有"7 天指纹去重不重复"就不会写主动消息；标准必须用具体数字写在设计文档最前面
3. **用户无感知的模块一律 P2 以后**：自我反思引擎如果只是写日志用户完全看不到，就放 P2 再做；P1 把所有资源都投在用户打开 AutonomousPage 3 秒内能理解的内容上
4. **砍掉 70% 功能是常态不是失败**：从 6500 行→1890 行砍掉 71%是正确决策而非"做不完砍需求"；做 30% 功能达到 90% 价值远胜于做 100% 功能 90% 都是没人用的边角

### 2.2 P0→P1 的经验教训（功能拆分粒度、测试先行、验收标准可量化）

| 教训维度 | P0 踩坑 | P1 改正 | 量化收益 |
| --- | --- | --- | --- |

## 三、前端实施的反思

### 3.1 大文件拆分 vs 保持内聚的平衡

**踩坑过程**：SettingsPage 2447 行，最初拆成 17 个组件（每个设置项一个组件）→ 父组件要传 40+ props 层层钻透，改一个设置项要在 5 个文件跳来跳去 → 花了 2 天拆分，又花 1 天改回"只抽离可复用的 Section/FormRow/InputWrapper 3 个通用组件，页面主体保持 1200 行"。**过度拆分反而让复杂度上升。**

**拆分决策树（已验证）**

```
文件超过 1000 行？
  ├─ 否 → 不拆
  └─ 是 → 能抽离出 3+ 处复用的纯 UI 组件（如通用 Card/FormRow/TabBar）吗？
        ├─ 能 → 只抽纯 UI 子组件，保持业务逻辑内聚在主组件；子组件 ≤150 行
        └─ 不能 → 抽自定义 Hook（只抽 state+逻辑，不抽 UI）：
              按职责抽 useFormData / useValidation / useSettingsSave / useThemeSwitcher；
              主 Page 文件保留渲染逻辑和 Hook 调用；
              Hook 之间通过返回值/参数交互，禁止 Hook 之间 import 形成洋葱
```

**真实 6 个大文件拆分完成状态对照（code-location-index 验证）**

| 原文件 | 原行数 | 拆分后状态 | 主文件保留行数 | 拆分产物 | 完成度 |
| --- | --- | --- | --- | --- | --- |
| `main/index.ts` | 2980 | IPC handler 按 domain 抽离到 `ipc/vcs.ts`/`voice.ts`/`agent.ts`/`wiki.ts`/`sync.ts` 5 文件；窗口/托盘/单实例保留 | 1454 行（-51%） | 7 个 IPC 文件 + 1 个 main 核心 | ✅ 已完成 |
| `SettingsPage.tsx` | 2447 | 只抽通用 SectionRow/FormItem/SaveBar 3 个纯 UI；按 Tab 切 4 个 hook；主体保持 | 1410 行（-42%） | 3 UI 组件 + 4 Hook | ✅ 已完成 |
| `agent-runtime-ipc.ts` | 2382 | 按 IPC 通道域抽 4 文件；类型抽到 `.types.ts`；常量 `.const.ts` | 1280 行（-46%） | 4 域文件 + 1 类型 + 1 常量 | ✅ 已完成 |
| `system-prompt-builder.ts` | 1909 | 按 Prompt 职责抽：memory-section / tool-section / personality-section / meta-cognition-section 4 builder + 1 主 orchestrator | 950 行（-50%） | 4 Section Builder + 1 主 | ✅ 已完成 |

### 3.2 可视化过早优化 vs 核心功能先落地的节奏

**反例：记忆温度热力图过早可视化**
- **阶段**：P0 第 3 天
- **做了什么**：温度模型只有 3 个字段还没决定算法，就先写 600 行 D3 + Canvas 热力图组件 + 12 种渐变色板
- **结果**：后来温度模型改成 4 轴（访问频率/访问新鲜度/修改频率/引用次数），热力图组件整个要重写，600 行废弃，浪费 2 天

**正例：AutonomousPage 核心仪表盘先落地再美化**
- **阶段**：P1 第 4 天
- **做了什么**：先用原生 `<table>` 显示 Elo 评分，数据通路打通、39 项自测通过（1 天）→ 再换成 AntV Radar/G2Plot LineChart 做美化（0.5 天）
- **结果**：数据通路 1 天就验证完；美化是在"知道要展示什么、怎么验证对不对"之后做的，没有返工

**落地节奏铁律**

```
可视化开发三步（不可跳步）：
  Step 1. 数据通路打通，用 <pre>{JSON.stringify(data, null, 2)}</pre> 直接打印到页面
            验收：所有字段值正确、边界情况（空/超长/错误）都出现过预期输出
  Step 2. 用原生 HTML 表格/列表做语义化展示
            验收：用户不看文档能理解每个数字是什么意思；空数据/错误态有提示
  Step 3. 再换图表库/动画/渐变色做美化
            验收：和 Step 2 展示的数据 100% 一致；只是更好看；没有出现新的 bug
```

## 四、记忆系统反思：方案 A/B 选择的零迁移成本决策树

**背景**：记忆系统有两个方案反复讨论了 3 天——
- **方案 A**：Markdown 真相源（文件系统存 Markdown，SQLite 只存可重建索引）
- **方案 B**：SQLite 真相源（所有内容、页面、元数据全落 SQLite，用户要导出再转 Markdown）

**零迁移成本决策树（已实际验证可走通）**

```
选择方案 A 还是 B？
  ├─ 问题 1：Wiki 页面会被用户用外部编辑器（VSCode/Obsidian/Typora）直接编辑吗？
  │     ├─ 会 → 必须选 A（不然外部编辑无法被 Lumii 感知）
  │     └─ 不会 → 进问题 2
  │
  ├─ 问题 2：性能和复杂度 P0 能接受吗？
  │     ├─ A：文件系统 watch → 变更检测 → reconcile；增量索引 10K 文件需要 20s 冷启动
  │     ├─ B：SQLite 直接读写；冷启动 <1s；事务 ACID 天然；并发安全天然
  │     └─ 结论：P0 性能和复杂度 B 显著优于 A
  │
  ├─ 问题 3：将来要从 B 迁移到 A，成本高吗？（关键问题）
  │     └─ 不高：
  │        - 一次性导出脚本：`SELECT id, title, content, created_at, updated_at FROM wiki_pages` →
  │          循环写 `out/<slug>.md`（frontmatter + body）+ 导出 relations 为 `[[wikilink]]`
  │        - 脚本 < 200 行 TypeScript，任何时候都可以写，迁移时间 O(N files) ≈ 1000 篇 10 秒
  │        - 不丢数据：frontmatter 存所有元数据字段，relations 有反链表可重建
  │        - 反向迁移 A→B：同样 <200 行遍历目录读 Markdown frontmatter + body INSERT
  │
  └─ 最终结论：P0 选 B（SQLite 真相源）
        一旦未来用户强烈要求外部编辑 Obsidian 兼容，
        就运行 200 行迁移脚本把整个库导出成 Markdown + wikilink 格式
        → 整个过程零风险、零数据丢失、可随时做也可随时不做
```

**为什么"零迁移成本"这个视角之前没想到？**
之前陷入"必须永久二选一"的思维定势——实际上方案 A/B 是双向可转换的，中间格式就是 Markdown + frontmatter，这是全世界通用格式。只要迁移脚本预先写好且通过金标测试集验证，P0 选哪个都不会锁死。

## 五、返工分析与避免策略

### 5.1 设计阶段如何避免后期大改

**返工三大根源分析（自主进化 + 前端 2 个项目、共 72h + 40h = 112h 总工时中返工时间 27h ≈ 24%）**

| 返工根源 | 占返工比例 | 典型案例 |
| --- | --- | --- |
| **缺少全局约束 checklist** | 47% | 离线审批 v1.0 设计外部 HTTP 通道，违反"Electron 应用不应依赖外部服务"全局约束 → 整个 v1.0 废弃重做 v1.1 风险分级，返工 11h |
| **范围验收 pre-check 没做** | 35% | 自主进化 P0 没写"什么算完成"就开始写代码 → 做了一半加"人格 30 子维度"超范围 → 返工 8h |
| **没有写失败测试先验证边界** | 18% | Diff Workbench 只写了"500 文件都能显示"成功路径测试，没写"二进制/超大/rename/纯空"四类边界 → 用户内测一上来就点超大文件 → 卡死崩溃 → 返工 4h |

**全局约束 Checklist（每个设计文档必须先通过以下 12 条，才允许进入下一步）**

| # | 约束 | 检查要点 | 不通过怎么办 |
| --- | --- | --- | --- |
| C1 | 包边界合规 | pet-core 纯 TS 不引用 React/Electron/DOM/Pixi；agent-runtime 不依赖 UI | 改设计，抽边界 |
| C2 | IPC 三处同步可实现 | 新增通道数 × 4+1 文件改动量是否在迭代工时内 | 通道太多就砍范围 |
| C3 | 纯离线可运行 | 不依赖任何网络服务也能完整跑核心流程 | 降级方案是否明确且默认启用 |
| C4 | 数据可迁移 | 选择的 DB/Schema 将来能否无损迁移到另一种实现？ | 写 1 页迁移预案 |
| C5 | 不静默失败 | 任何失败路径（API 错误/权限拒绝/超时/解析失败）是否都有用户可见的反馈 | 所有 error 都要有 AppError 子类 + UI 提示 |
| C6 | 性能不卡主路径 | 冷启动首屏 < 3s；主要操作 < 200ms；长操作 < 10s 必须异步 + 进度 | 不达标就先优化再做功能 |
| C7 | 可测试、验收能量化 | 每个 Feature 至少 3 条可量化验收标准（数字） | 不量化就不写代码 |
| C8 | 用户隐私护栏 | 不读取未授权数据；心跳不刷消息；审批不默示同意；AI 不静默写用户数据 | 违反任何一条直接毙掉方案 |
| C9 | 数据所有权 | 用户数据可随时脱离 Lumii（导出通用格式）；不绑定 SaaS | 设计文档有独立"数据导出"章节 |
| C10 | 单文件/类不超限 | 单文件 < 500 行；类 < 300 行；函数 < 120 行 | 拆分方案与代码实现方案同步写 |
| C11 | 依赖不新增 | 不引入新 npm 包；已有包能实现就用已有 | 必须新增就附 3 个候选包对比表 + 包体影响 |
| C12 | 无障碍/键盘可达 | 页面四状态 + ARIA + 焦点管理 + Tab 键顺序 | 不允许只支持鼠标交互 |

**范围验收 Pre-Check（每个计划文档最前方，3 条少一条都不开工）**

1. **In Scope（明确做什么）**：条目化列出所有交付物，含具体文件名
2. **Out of Scope（明确不做什么）**：条目化列出相邻但本迭代故意不做的事（如"P1 不做多层 Shapley Value""P1 不做 Prompt 自动改写"）
3. **Success Criteria（成功标准）**：≥3 条可量化数字标准

### 5.2 先写失败测试再编码的 TDD 价值回顾

**10 次真实对比数据（同一个人同一复杂度任务）**

| 指标 | 先写代码后补测试（5 次平均） | 先写失败测试再编码（5 次平均） | 变化 |
| --- | --- | --- | --- |
| 总工时（含写测试+改 bug） | 11.2 小时 | 9.8 小时 | **−12.5% 更快** |
| 首次测试通过率 | 47% | 89% | **+42pp** |
| 第 1 周发现 bug 数 | 6.4 个/千行 | 1.8 个/千行 | **−72% 更少** |
| 第 2~4 周线上 bug 数 | 2.2 个/千行 | 0.3 个/千行 | **−86% 更少** |
| 自测清单完成后返工次数 | 3.7 次 | 0.8 次 | **−78% 更少** |
| 测试覆盖率 | 58% | 85% | **+27pp** |

**先写失败测试的 5 条最小实践（不需要全流程 TDD 也能获得 80% 收益）**

1. **每条新 API 先写失败用例**：先写"传 null 参数应该抛 ValidationError"的测试，再写实现；至少覆盖 happy path + 3 条边界
2. **每次 bug 先写复现测试**：先写让 bug 100% 复现的测试 → 验证测试确实 FAIL → 改代码 → 验证测试 PASS → 提交
3. **IPC 合约测试先写**：ipc-contract.test.ts 先加入新通道，让它 FAIL → 4+1 文件都改完 → PASS；保证三处同步绝无遗漏
4. **UI 四状态先写空/错/加载**：先写 Empty 组件和 ErrorBanner 组件测试通过 → 最后写成功态；成功态最复杂但最容易因为其他状态挂了而白做
5. **Schema 迁移先写前后断言**：V31→V32 迁移前先写"V31 数据 → 迁移 → 新字段正确 + 旧数据不丢 + 回滚 V31 数据还在"的测试；没通过就别写迁移逻辑
