# 测试策略与方法论

## 1. 测试金字塔在本项目中的落地

本项目采用分层测试金字塔策略，从下到上覆盖不同粒度，确保质量与效率的平衡。

| 层级 | 测试类型 | 技术栈 | 覆盖目标 | 占比建议 |
|------|----------|--------|----------|----------|
| 底层 | 单元测试 | Vitest | 函数/模块级逻辑正确性，核心算法 | ~60% |
| 中下层 | 集成测试 | Vitest + 真实依赖 | Agent 编排、IPC 桥接、数据库交互 | ~20% |
| 中层 | CLI E2E 测试 | Node 脚本 + JSONL evidence | 真实模型下 CLI 命令全链路 | ~12% |
| 中上层 | UI E2E 测试 | Playwright | 渲染进程界面交互、跨组件流程 | ~5% |
| 顶层 | 人工验证 | 功能可用性清单 | 用户体验、视觉效果、真实感受 | ~3% |

### 1.1 单元测试（Vitest）

- **目标**：100% 核心模块（`packages/pet-core`、`packages/agent-runtime` 核心算法）行覆盖率
- **范围**：纯函数、状态转换、工具类、数据访问层（SQLite 内存模式）
- **命名**：与被测文件同目录，`*.test.ts(x)`
- **示例位置**：
  - `packages/agent-runtime/src/storage/local-database.test.ts`
  - `packages/agent-runtime/src/compact/strategies/micro-compact-phase1.test.ts`
  - `apps/windows/src/renderer/pages/ChatPage/components/ChatContainer/mergeAssistantParts.test.ts`

### 1.2 集成测试

- **目标**：验证跨模块协作，重点测试 IPC 三层调用链
- **范围**：
  - Agent 编排（主 Agent + 子 Agent 调度）
  - IPC 桥接（main → preload → renderer 三层贯通）
  - 数据库 Schema 迁移
  - 上下文压缩引擎各阶段协同
- **工具**：Vitest + 真实 SQLite 文件（临时目录）+ 模拟 IPC 事件

### 1.3 CLI E2E 测试

- **目标**：真实应用运行环境下的完整可测路径验证
- **技术**：Node 脚本执行器 + JSONL evidence 留痕 + Markdown 报告三件套
- **执行方式**：`node docs/test/lumii-cli/run-*.mjs`
- **核心特性**：
  - 逐条运行、超时控制、PASS/FAIL 记录
  - 支持断点续跑（continue 模式）
  - SKIP 项单独分类补跑

### 1.4 UI E2E 测试

- **目标**：验证界面交互、视觉回归、用户操作流程
- **技术**：Playwright
- **范围**：核心页面渲染、主流程操作、主题切换适配

### 1.5 人工验证

- **目标**：补充自动化无法覆盖的体验维度
- **内容**：功能可用性清单（Checklist），覆盖：
  - 视觉效果与动画流畅度
  - 语音通话实际体验
  - 长对话卡顿感知
  - 桌面宠物交互手感

## 2. AI 功能的测试特点

AI 输出具有非确定性，传统断言方式无法直接套用。本项目采用以下多维验证策略：

| 验证维度 | 方法 | 适用场景 |
|----------|------|----------|
| **结构断言** | 校验输出 JSON Schema、字段完整性、类型正确性 | 工具调用参数、结构化答复 |
| **关键词匹配** | 必须包含/排除的关键词集合（支持 AND/OR 组合） | 指令遵循、内容主题确认 |
| **能力维度评估** | 分级评分（0/1/2）而非二元通过/失败 | 创意写作、代码质量、推理深度 |
| **证据链存在性** | 验证工具调用真实发生、中间过程日志存在 | 子 Agent 调度、工具链执行 |
| **多轮一致性** | 同一提示词 3 次运行，统计通过率 ≥ 2/3 | 核心功能稳定性验证 |
| **人工抽检** | 固定样本集定期人工评分（≥ 20% 抽样） | 回复质量、安全合规 |

### 2.1 非确定性测试的状态分类

| 状态 | 含义 | 处理方式 |
|------|------|----------|
| PASS | 全部断言满足 | 记入通过 |
| FAIL | 核心断言不满足 | 记录根因，进入修复流程 |
| SKIP | 环境不具备（模型未配置、工具禁用等） | 注明原因，分类补跑 |
| BLOCKED | 测试基础设施缺陷阻塞 | 单独跟踪，不纳入统计 |
| CONDITIONAL | 条件用例（成本过高，默认不执行） | 由单测覆盖或配置降阈值后执行 |

## 3. Vitest 测试规范

### 3.1 Mock 策略

```typescript
vi.mock('../../hooks/business/useFeature', () => ({
  useFeature: vi.fn(),
}));

beforeEach(() => {
  vi.clearAllMocks();
  (useFeature as any).mockReturnValue({
    data: mockData,
    loading: false,
    error: null,
  });
});
```

| 规则 | 说明 |
|------|------|
| Mock 时机 | 在导入被测组件前声明 `vi.mock()` |
| 重置策略 | `beforeEach` 中调用 `vi.clearAllMocks()`，避免跨用例污染 |
| 避免过度 Mock | 纯函数/工具类不 Mock，直接真实调用 |
| 数据库 Mock | 使用 SQLite 内存模式（`:memory:`）而非 Mock 整个 Repository |

### 3.2 元素查询策略（组件测试）

```typescript
screen.getByRole('button', { name: /提交/i });
screen.getByLabelText(/用户名/i);
screen.getByPlaceholderText(/请输入/i);
screen.getByTestId('submit-button');
```

| 优先级 | 查询方式 | 场景 |
|--------|----------|------|
| 1 | Role 查询（`getByRole`） | 无障碍友好，语义最稳定 |
| 2 | Label 文本（`getByLabelText`） | 表单输入框 |
| 3 | Placeholder（`getByPlaceholderText`） | 搜索框等 |
| 4 | Test ID（`getByTestId`） | 无法用语义查询的兜底 |
| - | ClassName / ID | 禁止使用（实现细节耦合） |

### 3.3 用户行为模拟

```typescript
import userEvent from '@testing-library/user-event';

await userEvent.click(button);
await userEvent.type(input, 'Hello World');
await userEvent.keyboard('[Enter]');
await userEvent.selectOptions(select, 'option value');
await userEvent.upload(fileInput, file);
```

**规则**：优先使用 `@testing-library/user-event` 模拟真实用户操作，避免直接 `fireEvent`。

### 3.4 异步等待策略

```typescript
await waitFor(() => {
  expect(screen.getByText('加载完成')).toBeInTheDocument();
});

await screen.findByText(/加载完成/i);

await waitFor(() => {
  expect(mockFunction).toHaveBeenCalled();
}, { timeout: 5000 });
```

| 策略 | 适用场景 |
|------|----------|
| `findBy*` 系列 | 自带重试机制，优先使用 |
| `waitFor` + 断言 | 非 DOM 状态变化（函数调用、变量） |
| 显式 timeout | 长操作（模型调用、文件 IO），默认 1000ms → 按需提升 |

## 4. 测试数据管理

### 4.1 数据分类与组织

| 数据类型 | 存放位置 | 生命周期 | 示例 |
|----------|----------|----------|------|
| 单元测试 Fixture | 与 `*.test.ts` 同目录 `__fixtures__/` | 随代码提交 | 小型 JSON、SQL 片段 |
| CLI 测试探针数据 | `docs/test/lumii-cli/测试材料/` | 随代码提交 | docx、mp4、PDF 真实文档 |
| 临时运行数据 | `os.tmpdir()` + 时间戳前缀 | 用例结束自动清理 | 临时 SQLite、导出文件 |
| Seed 播种数据 | 执行器内直接 SQL INSERT | 套件开始前播种，结束后清理 | `wiki_inbox` 探针、`autonomous_goals` 测试行 |

### 4.2 临时目录清理规范

```javascript
function makeTempDir() {
  const dir = fs.mkdtempSync(path.join(os.tmpdir(), 'lumii-test-'));
  afterAll(() => fs.rmSync(dir, { recursive: true, force: true }));
  return dir;
}
```

- 所有临时文件必须带唯一前缀（`lumii-test-<ts>-`）
- 套件 `afterAll` 钩子中递归删除，`force: true` 容忍部分失败
- 数据库测试优先使用内存模式，避免磁盘残留

## 6. 测试覆盖率标准与质量门禁

### 6.1 覆盖率指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 行覆盖率（Lines） | ≥ 80% | 核心模块（agent-runtime/pet-core）≥ 90% |
| 函数覆盖率（Functions） | ≥ 80% | 公开导出函数必须覆盖 |
| 分支覆盖率（Branches） | ≥ 70% | 错误路径、条件分支重点覆盖 |
| 语句覆盖率（Statements） | ≥ 80% | 与行覆盖率协同 |

### 6.2 质量门禁（提交前必过）

| 门禁 | 命令 | 失败后果 |
|------|------|----------|
| 类型检查 | `pnpm typecheck` | 阻止提交 |
| Lint | `pnpm --filter ./apps/windows lint` | 阻止提交 |
| 相关包测试 | `pnpm --filter <pkg> test` | 阻止提交 |
| 核心模块覆盖率 | CI 统计覆盖率下降 ≥ 2% | PR 评论告警 |

### 6.3 测试质量检查清单

- [ ] 所有公开的函数和组件都有测试覆盖
- [ ] 边界情况和错误状态都有测试
- [ ] 测试能够独立运行（不依赖测试顺序）
- [ ] 测试能够清晰描述所测试的行为
- [ ] 使用了适当的断言，不仅仅是测试是否抛出异常
- [ ] 测试不依赖实现细节（如类名、内部变量名）
- [ ] 异步测试有适当的等待机制
- [ ] Mock 被正确重置以避免测试间污染

## 7. Flaky 测试治理方法

Flaky 测试 = 相同代码在相同环境下多次运行结果不一致。

### 7.1 常见根因分类

| 类别 | 典型场景 | 修复方向 |
|------|----------|----------|
| **时序竞态** | 异步操作等待不足、并发调度顺序依赖 | 增加 `waitFor`、使用确定性调度、避免 sleep |
| **测试污染** | 用例间共享状态、Mock 未清理、全局变量残留 | 强制 `beforeEach` 重置、隔离单例 |
| **真实时间依赖** | `new Date()`、`setTimeout` 实际等待 | `vi.useFakeTimers()` 模拟时间 |
| **随机数据** | `Math.random()`、UUID 顺序敏感 | 固定种子或 Mock 随机源 |
| **外部资源** | 网络波动、文件系统锁、端口占用 | 重试 + 退避、资源池化、本地 Mock |
| **浮点精度** | 金额计算、向量相似度比较 | 近似断言（`toBeCloseTo`） |

### 7.2 治理流程

```
发现 Flaky
   ↓
标记为 .skip 并添加 FIXME（注明复现概率）
   ↓
3 次连续运行定位根因（3/3 通过或 2/3 通过 = Flaky）
   ↓
修复后移除 .skip，本地连跑 10 次验证
   ↓
记入 flaky-registry.md（如有），跟踪复发率
```

### 7.3 重试机制

- CLI E2E 执行器内置 `rate_limited` 自动退避重试（最多 6 次，5s/10s/15s... 指数退避）
- 单元测试不允许全局重试，必须确定性修复
- 允许部分 SKIP：对于环境强依赖的用例，明确跳过条件而非重试混过
