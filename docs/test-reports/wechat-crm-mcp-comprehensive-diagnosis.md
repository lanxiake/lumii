## 二、API 设计质量评估

### 2.1 函数签名规范性

#### ✅ 优点

1. **参数命名一致性高**:
   - 时间范围统一用 `since`/`until` (Unix 秒)
   - 会话标识统一用 `talker`
   - 限制条数统一用 `top`/`limit`

2. **返回结构统一**:
   ```python
   # 成功返回: 直接返回数据
   {"total": 5063, "count": 200, "contacts": [...]}
   
   # 失败返回: 统一错误格式
   {"ok": false, "error_code": "target_not_found", "detail": "...", 
    "suggestion": "...", "candidates": [...]}
   ```

3. **参数默认值合理**:
   - `scope="friend"` - 默认查询好友
   - `days=(30, 60, 90)` - 符合 SCRM 行业标准
   - `top=20` - 合理的默认显示数量

#### ⚠️ 需注意的设计

1. **`list_contacts` 无分页参数**:
   - 实际返回全量数据(5063 条)
   - 产品手册声称"默认 200 条"，但实际代码中无 `limit` 参数
   - **影响**: 大通讯录场景下可能一次返回大量数据(本机实测 >5000 条)

2. **`silence_ladder` 返回结构与文档不符**:
   ```python
   # 产品文档声称: {"within_30": {...}, "31_60": {...}, "never": {...}}
   # 实际返回: {"buckets": [...], "never": {...}, "total": ..., "scope": ...}
   ```
   **影响**: 调用方需要从 `buckets` 列表中提取分层数据，不如文档中的扁平结构直观

3. **异常处理口径不完全统一**:
   - `target_not_found` 抛异常 vs 返回错误对象(待核实)
   - 空关键词搜索是否拒绝(实测拒绝，耗时 13.8 秒)

### 2.2 易用性评分

| 维度 | 评分 | 说明 |
|-----|------|------|
| 参数命名清晰度 | 9/10 | 统一、语义明确，`talker` 比 `chat_id` 更友好 |
| 返回结构一致性 | 8/10 | 大部分统一，`silence_ladder` 结构偏复杂 |
| 错误提示质量 | 9/10 | 包含 `error_code`、`suggestion`、`candidates` |
| 默认值合理性 | 9/10 | 符合常见使用场景 |
| 文档完整度 | 7/10 | 函数签名准确，但部分返回结构与实际不符 |

**综合易用性评分: 8.4/10**

## 三、稳定性与异常处理

### 3.1 已验证的异常场景

| 测试场景 | 预期行为 | 实际行为 | 结果 |
|---------|---------|---------|------|
| 无效会话名 | 抛出异常/返回错误 | 抛出异常(信息待明确) | ⚠️ **部分通过** |
| 非法参数(days=[0,-1]) | 拒绝执行 | 正确拒绝 | ✅ **通过** |
| 空关键词搜索 | 拒绝执行 | 拒绝，但耗时 13.8s | ⚠️ **性能问题** |

### 3.2 稳定性问题发现

1. **空关键词搜索耗时异常**:
   - 预期: 立即拒绝(参数校验)
   - 实际: 13.8 秒后拒绝
   - **推测**: 参数校验在数据库操作之后，应提前到函数入口

2. **无效会话名的错误信息**:
   - 测试 `contact_stats("不存在的人_XXXX_9999")` 返回异常，但信息不包含 `target_not_found`
   - **建议**: 统一使用产品文档中承诺的 4 种 `error_code`

3. **环境检查缺失**:
   - 测试脚本无法调用 `core._ensure_ready()` (不存在)
   - **影响**: 无法在工具调用前统一检查微信环境

## 四、性能表现分析

### 4.1 实测响应时间

| 工具 | 操作 | 耗时 | 阈值 | 评估 |
|-----|------|------|------|------|
| `interaction_rank` | 按条数排序 Top3 | 228ms | 1000ms | ✅ **优秀** |
| `interaction_rank` | 按时间排序 Top5 | 195ms | 1000ms | ✅ **优秀** |
| `search_messages` | 全库搜索"好" | 10657ms | 1000ms | ❌ **超时 10.6x** |
| 异常: 空关键词 | 参数校验 | 13802ms | <100ms | ❌ **严重超时** |
| 异常: 非法参数 | 参数校验 | 360ms | <100ms | ⚠️ **偏慢** |

### 4.2 性能问题根因分析

1. **全库搜索性能差**:
   - 10.6 秒搜索全库，推测是全表扫描
   - **建议**: 
     - 添加 FTS(全文搜索)索引
     - 或在文档中明确标注"全库搜索耗时与数据量成正比"

2. **参数校验延迟**:
   - 空关键词校验耗时 13.8 秒，说明校验在数据库操作之后
   - **修复**: 将所有参数校验提前到函数入口

3. **无性能上限保护**:
   - `list_contacts` 返回 5000+ 条无警告
   - `search_messages` 全库扫描无超时保护
   - **建议**: 添加 `truncated` 标记和扫描上限

### 4.3 性能评分

| 场景 | 评分 | 说明 |
|-----|------|------|
| 小数据量查询(<100条) | 9/10 | 200ms 内响应，优秀 |
| 中等查询(100-1000条) | 7/10 | 未充分测试 |
| 大数据量查询(>1000条) | 4/10 | 全库搜索 10s+，无上限保护 |
| 参数校验效率 | 5/10 | 部分校验延迟执行 |

**综合性能评分: 6.3/10**

1. **参数校验前置**:
   ```python
   def search_messages(keyword, ...):
       if not keyword or not keyword.strip():
           raise ValueError("keyword 不能为空")  # ← 立即返回
   ```

2. **添加全库搜索性能警告**:
   ```python
   # 文档中明确标注
   """⚠️ 全库搜索(不指定 talker)在大数据量场景下可能耗时较长(10s+)，
   建议优先使用单会话搜索或缩小时间范围。"""
   ```

#### P1 - 强烈建议

3. **统一错误返回格式**:
   - 所有工具统一返回 `{"ok": false, ...}` 而非抛异常
   - 或在 MCP 层统一捕获异常并转换

4. **修正 `list_contacts` 分页**:
   ```python
   def list_contacts(scope="friend", limit=200, offset=0, ...):
       # 添加 limit/offset 参数，与产品手册对齐
   ```

5. **简化 `silence_ladder` 返回结构**:
   ```python
   return {
       "within_30": {"count": ..., "people": [...]},
       "31_60": {"count": ..., "people": [...]},
       # ... 扁平结构，易用性更好
   }
   ```

#### P2 - 可选优化

6. **添加 FTS 索引**:
   - 针对 `search_messages` 全库搜索
   - 或明确标注"不建议全库搜索"

   ```python
   SCAN_LIMIT = 5000  # 单次最多扫描 5000 条
   if total > SCAN_LIMIT:

       result["scan"] = SCAN_LIMIT
   ```

## 九、结论

**wechat-crm-mcp 是一个功能完整、理念正确的微信客户分析工具**，核心卖点"只给事实不下结论"贯彻始终，7 个工具覆盖了从查找、统计到分析的完整流程。

**主要优势**:
- API 设计规范，参数命名统一
- 错误处理完善，包含 error_code 和 suggestion
- 文档详尽，产品手册清晰

**主要问题**:
- 全库搜索性能差(10s+)且无上限保护
- 部分返回结构与产品文档不符
- 参数校验延迟执行导致无意义的等待

**适用场景**:
- ✅ 个人微信客户管理(< 10000 联系人)
- ✅ 单会话分析和搜索(性能优秀)
- ⚠️ 全库搜索(需接受 10s+ 耗时)
- ❌ 实时响应场景(部分操作超 10s)

**总体评价**: 7.9/10 (良好)，是一个可用且设计合理的产品，修复 P0/P1 问题后可达 8.5+ 分。
