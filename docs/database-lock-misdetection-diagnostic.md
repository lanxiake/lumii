# 新建会话丢失问题诊断与修复

## 问题描述

用户反馈:新建的会话进行对话后，重启应用会发现该会话丢失（历史上"以前都是正常保存的"，属于回归）。

## 根本原因

`packages/agent-runtime/src/storage/local-database.ts` 的 `isIoErr()` 把两种完全不同的情况判定为同一类错误：

1. **瞬时文件锁**：残留的僵尸 `electron.exe` 进程（父进程已退出但子进程未跟着退出，Windows 下常见）持有 `agent-runtime.db` 的文件锁。
2. **真正的磁盘损坏**：SQLite 文件本身损坏。

两者在 Windows 下都会抛出同样的 `SQLITE_IOERR*` / `disk I/O error`，代码原来只重试一次（清 WAL 后再开一次）就判定为"损坏"，进入 `rotateCorruptedDb()`：

- 若能重命名/删除被锁的文件 → 正常轮转；
- 若文件被锁到连"重命名/删除"都失败（`EBUSY`）→ 直接铸造一个全新路径 `agent-runtime.db.new-<timestamp>`，并从最近备份恢复数据，**把仍在被锁的原文件（及此后写入的新会话）整个抛弃**。

如果下次启动时锁碰巧解除，应用会退回使用原路径，于是上一次轮转出的 `.new-<ts>` 文件（及其中的新会话）就成了永远不会被再次打开的孤儿文件。这个过程在僵尸进程持续存在期间会反复发生，每次启动都可能铸造一个新的孤儿文件。

## 实锤证据（本次排查）

- 4 个确认孤儿的 `electron.exe` 进程（PID 152892 / 162428 / 166264 / 186788），父进程已不存在，从 8 月 12 日起持续运行，锁住 `agent-runtime.db`。
- 真正的 `agent-runtime.db` 文件 mtime 停在 8 月 11 日 19:16，40+ 小时未被成功打开写入。
- 同期 10 份 `.db.bak` 备份文件 MD5 完全相同 —— 备份其实一直在复制同一份已经过期的快照。
- 目录下累计 38 个 `.db.new-*` 轮转文件（8/7 ~ 8/13），说明这不是孤立事件。
- 直接读取当天最新轮转文件 `agent-runtime.db.new-1786594297016`，找到了两条当天的新会话（"你叫什么名字""你好呀"），这两条在其他任何轮转文件里都不存在 —— 证明用户的新对话确实被保存了，只是存进了一个应用不会再打开的侧支文件。

## 已实施的修复

1. **重试退避**（`local-database.ts` 打开失败后）：`200ms → 500ms → 1000ms → 2000ms` 依次重试，给瞬时锁一个自然解除的窗口，而不是一次失败就判损坏。
2. **轮转路径指针**（新增 `agent-runtime.db.active-path` 侧车文件）：若主库路径持续被锁定，启动时先检查上次轮转到的路径是否还能打开，能打开就**继续用它**，而不是再铸造一个新的空库——避免每次重启都遗弃上一次轮转路径里已经写入的数据。只有在没有可复用的轮转路径时，才会走原来"轮转 + 从备份恢复"的兜底逻辑。

代码位置：`packages/agent-runtime/src/storage/local-database.ts:391-528`（`isIoErr`、`LOCK_RETRY_DELAYS_MS`、`readActivePathPointer`/`writeActivePathPointer`）。单测：`packages/agent-runtime/src/storage/local-database.test.ts`。

已在真实环境验证：应用重启后，日志显示"主库路径持续被锁定，继续使用此前轮转路径"，没有再铸造新的孤儿文件。

## 如何保证后续不会出现同样问题

1. **不要在没有重试的情况下把 IOERR 当损坏处理**——任何修改 `openWithRecovery` 逻辑时，必须保留"先退避重试，确认不是瞬时锁"这一步，再考虑轮转。
2. **轮转前先看指针**——修改轮转逻辑时不要绕过 `readActivePathPointer`，否则又会退化成"每次重启铸造新孤儿文件"的老问题。
3. **根源仍未清除**：僵尸进程本身没有被杀掉（当前那 4 个 PID 一直因权限不足杀不掉）。真正杜绝这类问题需要让僵尸进程不再产生，或能被自动清理：
   - `scripts/stop-dev.ps1` 的 `Stop-OrphanDevProcesses` 目前按 `CommandLine` 过滤候选进程，但这类孤儿 Electron helper 进程通过 WMI 拿到的 `CommandLine` 是空的，导致过滤逻辑直接跳过它们，从未清理成功。**待办**：需要改成不依赖 `CommandLine`（例如结合进程名 + 父进程已不存在的判断），否则每次开发环境异常退出仍可能再产生新的僵尸锁。
   - 长期看，也可以考虑在应用自身的 `before-quit`/`performCleanup()` 流程里增加"确认所有子进程已退出"的等待或强杀步骤，而不是仅依赖开发脚本清理。
4. **定期检查孤儿轮转文件**：`~/.lumii/data/` 下如果堆积大量 `.db.new-*` 文件，说明锁问题在反复发生，应结合 `.active-path` 指针指向的文件确认当前真正在用哪一个，而不是想当然认为主路径 `agent-runtime.db` 就是最新数据。
