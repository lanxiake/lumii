# wechat-crm-mcp · 微信客户分析

> 详细安装与工具参数见
> [`../../apps/windows/resources/wechat-crm-mcp/README.md`](../../apps/windows/resources/wechat-crm-mcp/README.md)。
> 文末数字是 2026-10-14 在本机真机上跑这套 exe 的**原始输出**。

## 一句话

**把你微信里的通讯录和互动数据端上桌——只端数字，不下结论。**

---

## 一、它解决什么问题

### 1. 微信**从不帮你算账**

你的客户、合作方、群友，全都活在微信里。但微信不会回答任何一个真正有用的问题：

- 这个客户多久没联系了？——**没有"最后互动时间"这个视图**
- 这个群里到底有谁？——**群成员列表只在成员管理页里，翻不动也导不出**
- 我跟谁聊得最多？谁已经冷了半年？——**没有任何排行**
- 我发消息的时段集中在哪？——**没有**

### 2. 而"翻一翻"在量级上就是不成立的

本机通讯录 **2712** 个联系人、**35** 个群。手机上一屏 8 个人，
翻完一遍要点 340 屏，翻完也**记不住谁是谁、上次聊是什么时候**。
这不是"懒"，是**人力做不到的规模**。

### 3. 最容易被忽略的一层：**"没聊过的人"你看不见**

按"会话"来算，只有跟你私聊过的才有会话。而**绝大多数联系人一句话都没说过**——
他们在你的通讯录里，但**任何按会话排的榜都不会出现他们**。

本机实测的沉默分层：

| 桶 | 人数 |
|---|---|
| 30 天内有互动 | **117** |
| 31–60 天没互动 | **54** |
| 61–90 天没互动 | **0** |
| 90 天以上没互动 | **0** |
| **合计（通讯录总量）** | **2712** |

117 + 54 = 171，**剩下约 2540 人**——他们在你的通讯录里，
但**从没产生过一次互动**。微信永远不会告诉你这件事；
按会话统计的工具也**永远看不见他们**。

**wechat-crm-mcp 按「人」算，所以看得见。**

### 4. 它只端数字，不替你判断

清单和数字是**确定性的**（可复现、可核对），"这个客户值不值得跟"留给接入的 AI 或你自己。
**工具不发明"客户健康分"这种看着专业、实际是你猜我猜的数字。**

## 二、典型场景

### 场景 1：谁很久没联系了

```
你：哪些人很久没联系了？
AI：（silence_ladder(days=90)）
```

**本机实测**：30 天内 **117** 人、31–60 天 **54** 人、61 天以上 **0** 人，
而通讯录一共 **2712** 人——**其余约 2540 人从没互动过**。

⚠️ **"61–90 天 0 人"这个 0 是真的 0，不是查询失败**——
本工具**不会静默给 0**：名字对不上会给 `target_not_found` 和相近候选，
真为 0 才是"真没有"。这个区分在只看数字的报表里**看不见，但决定了你会不会做出错误决定**。

### 场景 2：客户画像的底料

```
你：我跟文件传输助手最近聊得怎么样？
AI：（contact_stats(talker="文件传输助手")）
```

**本机实测**：

| 指标 | 值 |
|---|---|
| 总条数 | **377** |
| 时间跨度 | 2026-08-21 → 2026-10-14，**54 天** |
| 最活跃的钟点 | **11 点（125 条）** |
| 最活跃的一天 | **2026-10-14（112 条）** |

这四个数字合起来就是一个**行为画像**：这是一个"上午 11 点集中处理、
最后一天爆发式使用"的对象，不是"每天都聊两句"的关系。
——**这种结论从聊天列表里是看不出来的**，因为列表只给你最后一条消息。

### 场景 3：互动排行

```
你：我最近跟谁聊得最多？
AI：（interaction_rank(top=20)）→ 614 / 511 / 497 / 445 / 377 ……
你：哪些人我很久没理了？
AI：（interaction_rank(sort="recent")）久未联系在前
```

本机实测榜首是 **614 / 511 / 497 / 445** 条——**头部极其集中**。
配合 `sort="recent"` 立刻反过来看"尾巴"，两个方向都是**同一个工具**。

### 场景 4：群里都有谁

```
你：我有那些客户群？
AI：（list_contacts(scope="group", keyword="客户")）→ 本机共 **35** 个群
你：XX企业群里都有谁？
AI：（list_contacts(room="XX企业群")）→ 成员清单，含 `name_in_room`（**群里的称呼**）
```

### 场景 5：离职 / 换号前，先把自己的人脉理一遍

这是**被市场验证过的最强触发场景**之一——"离职了，怎么备份导出微信里的客户列表到 Excel"
这类提问在社区里到处都是，因为**微信官方不提供联系人批量导出**。

用本工具的路径：

```
你：把我所有的群成员名单整理出来，我想知道平时都在跟哪些人打交道
AI：（list_contacts(scope="group") → 逐个 list_contacts(room=…)）
     或者：silence_ladder() 看哪些人已经很久没联系
```

⚠️ **但请先读 [`README.md` 的「风险与合规」](README.md#风险与合规必读不埋末尾)**：
把它用来**整理你自己的通讯录**是一回事，
用来**批量导出客户名单再群发**是另一回事——后者正是有人被罚 10 万的那条线。

### 场景 6：把它当"人脉体检"的输入

导出的数字可以直接喂给别的 AI 做分析，或者**每周跑一次看趋势**：
`silence_ladder` 的 31–60 天桶如果这个月比上个月大，说明你在**流失关系**——
这是一个**结构性的信号**，不是某条消息的内容。

## 三、它能读、能搜、能分析聊天记录吗？

这是最常被问的一个问题，也最容易被含糊过去。**直接给答案**：

| 问题 | 答案 |
|---|---|
| 读得到聊天记录吗？ | ✅ **读得到**，而且是**跨全部消息分片**的 |
| 读的是哪些字段？ | **只有两列：`create_time`（时间）和 `real_sender_id`（谁发的）** |
| 能**搜聊天内容**吗？ | ❌ **不能**。四个工具里**没有任何正文检索** |
| 那 `list_contacts(keyword=)` 搜的是什么？ | **通讯录**——显示名与 `username`，**不是聊天内容** |
| "分析"到底分析什么？ | **计数与时间分布**：条数 / 我发·对方发 / 活跃时段 / 活跃天 / 跨度 / 沉默天数 / 排行 / 分层 |

**关键的一条：正文（`content`）一个字节都不读。**

所有落到消息表上的 SQL 长这样（这是全部三处，没有第四处）：

```sql
select create_time, real_sender_id from [<会话表>]          -- 逐条扫
select real_sender_id, max(create_time), count(*) ... group by real_sender_id
select count(*), max(create_time) from [<会话表>]           -- 排行
```

**没有 `content`、没有 `message`、没有 `compress_content`**——
而 `list_contacts` 只在 `contact` 表上取 `username / remark / nick_name`。

### 为什么这样设计，而不是"顺手也读一下"

因为**通讯录和互动算术根本不需要正文**。而一旦不读，就多了一层**物理上的保证**：

> **即使有人拿到这个 exe 逐行审计，它也读不到"你说了什么"。**
> 不是"承诺不看"，是**代码里就没有那条 SQL**。

这和「只端数字，不下结论」是**同一件事的两面**：不读正文，就不可能替你下
"这个客户关系好不好"的结论——**它连判断的材料都没有**。

### 所以分工是清楚的

| 你要做的事 | 用哪个 |
|---|---|
| 读某段历史、搜一句话谁说过、总结一段对话、生成人物画像 | **`wechat-mcp`**（`read_history` / `search_messages` / `wechat_digest` / 画像） |
| 数通讯录有多少人、谁多久没联系、群里都有谁、跟谁聊得最多 | **本产品** |

⚠️ 顺带说明：它**确实要解密并打开**你的消息库（否则拿不到时间戳），所以它需要微信在运行、
需要扫到密钥。**"打开库"和"读正文"是两件事**——本产品打开库，只取时间与发送者两列。

## 四、功能详解（4 个工具）

### `list_contacts(scope?, room?, keyword?, include_deleted?, limit?, offset?)`

**做什么**：列通讯录；`room=` 时列**该群成员**。

**返回什么**：`username`（稳定 ID）、显示名、类型、`is_me`（群成员列表**包含你自己**——
否则"这个群几个人"跟微信里对不上）、`name_in_room`（群内称呼）、
`name_in_room_with`（**这一批里有几个是真有群昵称的**）。

**`name_in_room_with` 这个计数是防"静默稀疏"的**：群昵称来源本身只覆盖 9.6%，
如果只回一串空串，你会以为"查不到"；带上计数你才知道**是没设过，还是工具没读到**。

**`scope` 的取值**：`all` / `friend` / `group` / `official` / `open`（企业微信）。

**⚠️ 分类是按 `username` 后缀判的**（`@chatroom`＝群、`gh_`＝公众号、`@open`＝企业微信），
**不是按 `local_type`**——实测那个字段语义不干净（同为 `wxid_` 前缀却有两档取值）。
**可复现、可核对，不靠猜。**

**默认只回 200 条**——看返回里的 `total` 判断有没有被截断，用 `offset` 接着翻。
**别把"前 200 个"当成"一共 200 个"。** 本机 `total` 是 **2712**。

### `contact_stats(talker, since?, until?)`

**做什么**：算**单个会话**的互动数字。

**返回什么**：总条数 / 我发 vs 对方发 / **活跃时段分布** / **活跃天 Top** / 首末时间 / 跨度 / 沉默天数。

**为什么"活跃时段分布"值得单独说**：它把"什么时候能找这个人"从**感觉**变成**数字**。
本机那份 377 条的数据里，**11 点一个钟头占了 125 条（33%）**——
你在这个时段找他，回复概率是晚上的几十倍。

### `silence_ladder(scope?, days?, top?)`

**做什么**：**按人**分层——多久没互动 / 从没聊过的人。

**这是四个工具里唯一"按人"而非"按会话"的**，也是它看得见那 2540 个人的原因。

**它刻意不做的事**：**不给分**。不输出"客户健康度 72 分"这种数字——
那种分数看起来专业，实际上是**把工具的假设伪装成事实**。它给原始时间戳与条数。

### `interaction_rank(since?, until?, top?, sort?)`

**做什么**：**按会话**排行。`sort="recent"` 时久未联系在前。

**和 `silence_ladder` 的分工**：这个是"跟这个会话聊了多少"，那个是"跟这个人多久没说话"。
**两个视角都要**，因为群聊里的活跃成员可能在 `silence_ladder` 里是"从没私聊过"。

## 五、一轮完整回路

```
① list_contacts(scope="all")     → 2712 个联系人，看到 total
② silence_ladder()               → 117 / 54 / 0 / 0，其余约 2540 从没互动
③ interaction_rank(sorted)       → 头部 614/511/497/445 条，看出集中度
④ contact_stats(某个人)           → 377 条 / 54 天跨度 / 11 点峰值
⑤ 把 ②③④ 的数字交给 AI 或自己判断 → "该跟谁说话、该放下谁"
```

第 ⑤ 步**工具不参与**——这是刻意的分界线：
**工具负责让事实可核对，判断负责让事实有意义。**

| 调用 | 实测结果 |
|---|---|
| `list_contacts()` | **total = 2712**，本次返回 200（被 `limit` 截断，需 `offset` 翻页） |
| `list_contacts(scope="group")` | 群 **35** 个 |
| `contact_stats(talker)` | **377** 条，2026-08-21 → 2026-10-14，跨度 **54 天** |

| 由分层推出的"从没互动" | 约 **2540** 人 |
| `interaction_rank()` | 榜首 **614 / 511 / 497 / 445 / 377** 条 |

**最值得记住的一个数字是"2712 对比 171"**：

每一步都是**起真实 exe、走标准 MCP 协议**跑出来的。

## 七、企业侧怎么解决这件事，以及它们留下的空白

"我有哪些客户、谁很久没联系了"这个需求**不是新需求**——企业早就为它花了大钱。
值得看看那些钱花在哪、又漏掉了什么。

### 企业微信会话存档：唯一合规的正路，但它**只管企微**

| 项 | 事实 |
|---|---|
| 覆盖范围 | 企微之间、企微与外部客户个人微信的对话（**在企微窗口内**）、企微内外部群 |
| **个人微信** | **完全不在范围内**。企微与个人微信数据隔离，官方规则明确：**企业微信无法查看员工个人微信聊天记录** |
| 交付形态 | 原生**只提供加密数据接口**，后台看不到聊天内容——企业得自己把**拉密文 → 私钥解密 → 解析 → 落库 → 检索**整条链建起来 |
| 成本 | 官方接口费 2026-01-22 起调整为 **400 / 900 / 1800 元/人/年**（办公/服务/企业版），**还要再加第三方系统费**；自建解密检索系统，外包报价**二三十万**，且需长期维护 |
| 生效时点 | **只对开通之后的消息生效**，开通前追不回；私钥丢失则历史打不开 |
| 已知的坑 | 行业里最常见的一句话是「**开了存档却查不到**」 |

### 代价已经有人付过了

公开案例里，企业拿不出记录时的损失是这样的量级：

- 医疗器械代理的销售通过**个人微信**泄露标底 —— 损失约 **60 万佣金**并丢续约；
  另一名销售带走 **800 多个医院联系人**，次年产出 **90 多万**蒸发；
- 教培顾问用个人微信带走 **3000 多个家长联系方式**，流失生源 **40 多万**；
- 外贸业务员带走 **200 多个海外买家**，"三个平台记录一个都捞不着"，丢单 **超百万**。

**共同的失效点全都一样：客户在个人微信里，而所有合规手段都够不着个人微信。**

### 第三方 SCRM 的价格带

| 产品 | 参考价 |
|---|---|
| 企序通 SCRM | 标准版 **6800 元/年**含 10 席位；旗舰版 **8800 元/年**含 20 席位 |
| 一维助手 SCRM | 小微版约 **2300 元/年**（版本费 + 席位费） |
| 轻量 SCRM 一般区间 | **3k–1w / 年** |

### 有人已经因为"越界的那部分"被罚了

上面两类方案里，有一类是**明确违法**的——"破解微信数据库 + 上传云端 + 控制微信自动加好友"
的工作手机/聚合管理软件。2024 年 12 月，**北京尘锋**因这类软件被市场监管总局通报，
**罚款 10 万元**，认定妨碍微信正常运行、构成网络不正当竞争。
另有一家机构因为**批量导出客户手机号触发风控，整个企业账号被冻结 72 小时**，
当月退费投诉涨了 300%。

**所以"全本地、只读、不外传"在这个品类里不是一句好听的话，是一条画出来的线。**
拿用户的聊天记录和通讯录抄到云端，就是下一个被罚的位置。

### 为什么"沉默分层"这个设计是对的

企微侧的成熟 SCRM 早就在做同一件事，而且做法和我们的思路一致：

- 有产品按**"近期互动频次 / 是否长期未回复"**圈人群包；
- 有产品按 **30 / 60 / 90 / 180 天无互动**自动打"沉睡"标签。

**注意它们的分层刻度就是 30/60/90 天——和 `silence_ladder` 的桶完全一样。**
这说明"用时间桶表达关系冷热"是被市场验证过的模型，不是我们拍脑袋定的。
区别在于：**它们的数字来自企微的事件流，我们的数字来自你本机的库**——
所以它们**永远看不到个人微信**，而我们只看得到个人微信。

### ⚠️ 一条必须说清楚的界线

上面那些企业级方案，**合规前提是"提前告知员工、限定工作设备和工作场景"**——
公开资料里也写明：**无差别监控私人通讯、未告知存档可能违法**，
且第三方外挂普遍存在**封号风险**。

**wechat-crm-mcp 不是那个东西，也不该那样用。** 它的定位是：
**读你自己账号、你自己机器上、你自己的数据**——就像你翻自己的通讯录。
它没有任何"监控别人"的能力，也不该被拿去做那件事。

### 所以它补上的是哪一块

企业级方案**结构上够不到个人微信**——那是个人数据的范畴，不该由企业的接口去读。
而**你自己的个人微信**这一侧，市面上基本是空的：
没有会话存档、没有标签体系、没有客户分层报表。

`silence_ladder` 之所以有价值，恰恰因为它在这个空白上给出的是**确定性数字**——
**本机 2712 个联系人里，真正产生过互动的只有 171 个**。
这个数字，微信本身永远不会告诉你；企业级方案永远不会告诉你（它看不到）；
按"会话"统计的工具也说不全（群聊里说话的人不在私聊会话里）。

## 八、为什么值得

| 别人怎么做 | 本方案 |
|---|---|
| 手机上一个个翻（2712 人 ≈ 340 屏） | 一次查询拿到**完整清单**，还能 `offset` 翻页 |
| 按会话统计 | **按人**统计——看得见那约 2540 个"通讯录里有、从没说过话"的人 |

| 静默返回 0 | 名字对不上给 `target_not_found` + 相近候选，**真为 0 才是没聊过** |
| 按数据库字段猜类型 | 按 `username` 后缀判（`@chatroom`/`gh_`/`@open`），**确定性、可复现** |
| 群成员里漏掉你自己 | `is_me=true`，保证跟微信里数出来的人数一致 |

## 九、它做不到什么

- **不读聊天正文，所以搜不了消息内容**。它打开你的消息库，但 SQL 里只取
  `create_time` 和 `real_sender_id` 两列——**要搜某句话谁说过，用 `wechat-mcp`**。
  详见[第三节](#三它能读能搜能分析聊天记录吗)。
- **不出任何"判断"**：客户价值、关系好坏、情绪倾向——那是接入方 LLM 的事。
  本服务**只端数字**。
- **没有标签筛选**：本地库只有标签名，**没有**"好友 ↔ 标签"的映射表（需要逆向），
  所以没有按标签筛人的工具。**没有就是没有，不编一个近似的。**
- **群内称呼只对一部分人存在**：来源本身稀疏（**1980 行里只有 191 行非空，9.6%**），
  自己的办公群多、外部大群几乎没有。`name_in_room` 是空串就是"**这个群里没设过**"，
  **不是查不到**——所以**不拿全局名顶上**，也不能用它认人（**认人用 `username`**）。
- **默认只回 200 条**：看 `total`，别把"前 200 个"当成"一共 200 个"。
- **不会主动推送**：它是被调用的工具，不是常驻监控。"这个人三个月没联系了"
  这种提醒需要你在接入侧自己加定时。
- **读不了别人的账号**，也不上网——**全部本地处理**。
- ⚠️ 通讯录和互动数据含**他人**的隐私。只读、本地处理、不外传。
