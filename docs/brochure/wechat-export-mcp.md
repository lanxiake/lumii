# wechat-export-mcp · 微信导出与文件归档

> 详细安装、参数与体积实测见
> [`../../apps/windows/resources/wechat-export-mcp/README.md`](../../apps/windows/resources/wechat-export-mcp/README.md)。
> 文中体积与计数是 2026-10-14 在本机真机上跑这套 exe 的**原始输出**。
>
> 本产品**一个 exe 两个面**：**记录面**（聊天记录导出）与**文件面**（文件清单 / 占用 / 归档）。
> 原先的文件面是一个独立产品（`wechat-file-mcp`），2026-10-14 并入本产品——
> **两边共用同一套目录结构**，导记录与归档文件写进同一棵树。

## 一句话

**把一段聊天变成一个能发给别人的文件——图在里面，双击就像翻微信；
顺手把微信里的文件趁早搬出来，并告诉你哪些已经搬不动了。**

也是**一份能被 AI 直接拿去分析的数据**：导成 JSON，附一张统计报表，
而且能只说"把提到某件事的那些记录导出来"，不必整段搬。

## 一、它解决什么问题

### 1. 微信的导出是**残的**

| 你有什么办法 | 残在哪里 |
|---|---|
| 截屏 | 只有屏上那几屏，长记录要截几十张，还带你的头像和时间栏 |
| 逐条勾选转发 | 勾 500 条要点几百下；转发出去对方也还是"在微信里"，不成文档 |
| 微信自带的"导出聊天记录" | 出 txt——**图片没了、语音没了、引用没了、转账/合并转发/视频号全变成一行"未知消息"** |
| 第三方"备份"工具 | 大多要你登录、要上传、或者干脆解不开 4.x 的加密 |

**根本矛盾**：真实的导出需求几乎都是**"把这段发给人看"**（给律师、给同事、给审计、
给自己的另一个设备），而"给人看"这件事需要**媒体和结构**——恰恰是 txt 丢掉的东西。

### 2. 而"分享"这个动作，最容易毁掉的是**图**

只要图片是**外链**（指向本地某个 `files/` 目录），你把文件发给别人，
对方打开就是**一堆裂图**——因为你的相对路径在他的电脑上不存在。

wechat-export-mcp 的答案是**单个自包含 HTML**：**全部图片以 `data:` URI 内嵌在文件里**，
跨天的地方自动生成日期目录点了就跳。**一个文件，换台机器打开也不掉图。**

### 3. 社区里最常被抱怨的两件事，正好是这两件

翻这一类的求助帖，抱怨的分布很集中：

| 抱怨 | 根因 |
|---|---|
| **"导出的图片打不开"** | 图片是加密 `.dat`，**解密密钥没认出来**；或者图片早被清理、本地只剩碎片——**碎片即使解开也不是完整画面** |
| **"记录不完整"** | **电脑端没点开过的图/视频只加载了预览图**，导出后打不开。同类工具（仿微信 UI 的离线浏览器）也会踩这一条 |
| "导了半天，图还是裂的" | 导出目录里 HTML 引用旁边的 `_files/`——**HTML 单独发出去就掉图** |

第二条**不是工具的 bug，是微信的行为**：没下载过的东西，本地本来就没有完整版本。
**所以这类工具的正确做法不是"想办法修"，而是"如实告诉你有多少张没拿到"。**
本工具把它拆成 `image_no_key`（能修）和 `image_missing`（没救了）两笔账——
**这个区分，我们查过的同类工具里没有一家做。**

### 4. 微信里的**文件**会自己消失，而且不打招呼

文件不是"存着"的，是**缓存**。服务器只保留一段时间，过期后本地没下过的就**永久没了**：
点开只会看到一句"该文件已过期或已被清理"。这不是 bug，是设计。

要命的是**你自己不知道哪个快过期了**。你当时在群里点开看过一眼，
以为"在微信里"，一周后要用才发现打不开——**你没有任何预警**。

**时间窗只有 14 天**——聊天里的图片、视频、文件，微信官方的过期时限就是**两周**，
不是"很久以后"。微信设置里有开关「我 → 设置 → 通用 → 照片、视频、文件与通话 →
保留查看过的原图原视频」，**但它只保得住你看过的**；本工具告诉你的恰恰是
**你没点开、所以正在滑向过期**的那部分。

这不是假设的痛点。翻一圈公开的求助帖，形状高度一致：

- 有篇文章的标题就是**「救命！微信文件『已过期』差点让我当场去世」**；
- 工作群、客户合同、学生作业**「几天没点开就提示文件已过期或已被清理」**；
- 手机微信几十上百 G，**"不敢随便清理"**——因为怕清掉的正是不该清的；
- 还有一条很说明问题：**"把手机日期改到接收后 7 天内就能恢复过期文件"**传得很广，
  评论区一堆"亲测有效"——直到微信员工出来说**"假得有点离谱"**。

**谣言能被疯传，恰恰说明这件事上没有一个权威的、能自己查的入口。**

### 5. 「微信怎么这么占地方」没人答得上来

微信自带的"存储空间管理"只给你一个**总数**和几个大类，它不会告诉你
**这是哪个会话发的、是不是同一份文件被转发了十次、删了到底能省多少**。
而这些恰恰是"该不该清"的唯一依据。

### 6. 顺便说清楚：它不是"电子证据"

有律师的公开指引提到：**"第三方软件导出可能修改数据格式，反而失去证据原始性"**；
论坛上的原话更直白——**"备份给自己看可以，但打官司法院不认"**。
法院侧的指引则会提醒：**截图只能显示时分秒、没有年月日，"日后举证最好重截一次"**，
**"一键瘦身""垃圾清理"要慎用"**。

**这些提醒我们完全同意，而且要说在前面**：
本工具做的是**让你手上有一份完整、可读、能自己掌控的副本**——
**不是**给你一份"法院采信的证据"。需要法律效力时请走公证/鉴定，
并**保留原始设备**。把这句写在这里，比事后解释便宜得多。

## 二、典型场景

### 记录面

#### 场景 1：导出成文件给自己存档

```
你：我和「文件传输助手」的记录导出来
AI：（名字没把握先 list_sessions(query="文件") 拿确切会话名——本机实测命中 1 个）
     export_chat(talker="文件传输助手", out_dir="D:\\导出", format="md")
     → **53,816 字节，一个纯文本 md**
```

**本机实测**：`md` 是**单个 53 KB 文本文件**——最小的形态，只出文字，
适合喂给别的工具做分析、检索。

#### 场景 2：**带图**、发给别人看（记录面的核心场景）

```
你：把这个群上个月的记录弄成能发给别人看的样子
AI：export_chat(…, format="html", media="images", since=…, until=…)
     → D:\导出\<会话>\chat.html（单文件，图全在内嵌里）
```

**本机实测**：

| 形态 | 体积 | 说明 |
|---|---|---|
| `format="md"` | **53,816 B** | 纯文字 |
| `format="html", media="images"` | **796,701 B** | **单个自包含文件，12 张图片内嵌（538,964 B 的 base64）** |
| `format="html", media="all"` | html 主体 **1,831,684 B** + 附件 **325,071,131 B** | 见下 |

第二行是最该被理解的一个数字：**同一个会话，加上 12 张图，文件从 53 KB 长到 797 KB
——但仍然是「一个文件」**。这 797 KB 可以直接拖进微信发给别人，对方双击就能看，
**不需要"一起发过去一个文件夹"**。

#### 场景 3：`media="all"` —— 327 MB 的输出，**但 HTML 只有 1.8 MB**

本机实测 `media="all"`：

```
chat.html          1,831,684 B     ← 页面本体
files/ 等 18 个附件 325,071,131 B   ← 其中两个安装包 174 MB + 150 MB
image_exported 12 / voice_exported 2 / file_exported 18 / file_dup 2 / inline_fallback 0
```

**第一眼像 bug**（"说好的自包含呢？"），其实是**设计**：

- **图片内嵌**（12 张，走 `data:` URI）——因为图片是"看记录"的一部分，必须随文件走；
- **文件不内嵌**——一个 174 MB 的安装包 base64 进去就是 232 MB 的字符串，
  浏览器打开会当场卡死。所以**附件一律落盘到旁边**，这是唯一正确的做法。
- `inline_fallback 0` 是关键：**没有任何一张图因为超限被挤出去**——
  说明"内嵌有上限"这条规则**在这份数据上没触发**，页面仍然是完整自包含的。

⚠️ **所以看体积要先看 `inline_fallback` 计数，而不是看总字节数**。
本机 326 MB 里 **99.4%** 是附件，跟"这份 html 能不能单独发给别人"是两回事。

#### 场景 4：`file_dup 2` —— 同一份文件被发过两次

本机实测 `media="all"` 里 **18 个附件出去、2 个被去重**。
去重不是省事，是**防错**：同一个安装包在会话里发过两遍，
如果不去重，`files/` 里会出现两份同名文件，第二份覆盖第一份——
**你少了一份文件却完全不知道**。

#### 场景 5：记录多到一个文件读不动

加 `split="month"` 按月拆子目录。配合 `since`/`until` 精确锁定某一段
（比如"只要 9 月那批"，而不是"从 2023 年导到今天"）。

#### 场景 6：语音变文字，让记录**可搜**

`transcribe_voice=true` → 语音在**本机**转成文字写进导出（SILK → Paraformer）。
音频不出机器。**没装模型也不影响导出**——逐条跳过并计数，文字与图片照常出。

#### 场景 7：**导出来做分析**

```
你：把我和「文件传输助手」的记录导出来，我想看看里面都聊了些什么
AI：export_chat(talker="文件传输助手", out_dir="D:\\导出", format="json")
    → 一份 JSON（带 `stats` 报表）+ 旁边一份独立的 `stats.json`
```

**本机实测**（384 条记录）：

| 文件 | 体积 | 里面有什么 |
|---|---|---|
| `chat.json` | **177,747 B** | `stats` 字段 + 全量消息（机读，喂模型/喂脚本） |
| `stats.json` | **2,282 B** | 报表本身，**任何格式都会落这一份** |

报表里是这些（**都是计数**）：条数 384 / 我 384 / 对方 0；类型 文本 330、文件 20、链接 15、
图片 12、引用 5、语音 2；2026-08-21 ~ 2026-10-14，跨 54 天、其中 29 天有消息；
按月 8 月 11 / 9 月 15 / 10 月 358；最忙的一天 119 条；另有按小时、按星期各一组。

**为什么要先给报表**：几千条记录全塞进模型的上下文，既贵又没用。报表先告诉你"这段对话
长什么样、集中在哪几天"，要细节再去读正文——**这是把"能导出"变成"能分析"的关键一步。**

#### 场景 8：**只要你要的那部分**

```
你：把提到「发票」的记录都导出来，我要对账
AI：export_chat(talker="张三", out_dir="D:\\导出", keyword="发票", format="json")
    → D:\导出\张三\q-发票\chat.json（只含命中的那几条）
```

不知道在哪个会话里提的？**省掉 `talker`** 就是全库搜：

**本机实测**：关键词「图片」→ 扫 **72 个会话**，**42 个**里有命中，按命中条数从多到少
导出前 2 个（其余 40 个如实报 `sessions_skipped`），根目录另出一份 `index.md` 清单。耗时 3.2 秒。

`limit` 默认封顶 500 条/会话（保留**最新**的那些），被切过就置 `truncated: true`——
**"就这么多"和"被上限切了"在结果里长得一模一样，不报就是让人把答案当事实。**

### 文件面

#### 场景 9：过期预警——趁还来得及

这是文件面**最不可替代**的场景：过期是单向的，报警只在这一侧有效。

```
你：我那些群里哪些文件已经过期了？
AI：（list_files(only_missing=true)）9 个文件已经下不动了……
```

**本机真实结果（2026-10-14）**：157 条文件消息里，**9 条 `missing`、3 条 `size_mismatch`、
145 条可归档**。那 9 条长这样：3 份 PDF、2 份**同名 zip**（同一文件被发了两次，两条都没了）、
2 个 `.exe` 安装包的两次转发、1 份 docx、1 份 2000 元方案的 PDF。
——**你没有任何别的办法知道这 9 条的存在。**

⚠️ 一旦落进这 9 条，任何工具都救不回来（服务器端也没了）。这就是为什么"预警"本身有价值：
**它把"永久损失"变成"赶紧下载"。**

#### 场景 10：批量归档，先看计划再落地

```
你：能下的都归档到 D:\wechat-backup
AI：（archive_files(out_dir="D:\\wechat-backup", talker="文件传输助手", dry_run=true)）
     → total 20 / 将拷贝 18 / 去重 2 / 过期 0 —— **此刻一个文件都还没落盘**
你：可以
AI：（dry_run=false）→ 已落盘 D:\wechat-backup\文件传输助手\files\，18 个文件
```

`dry_run=true` 是**默认值**：不显式说"真的拷"，它只算不改。归档几百个文件要跑几十秒，
你会看到 `notifications/progress` 持续上报「归档中 40/200（已拷贝 37）」——
**不用盯着转圈猜是不是卡死**。

#### 场景 11：回答「微信怎么这么占地方」，而且是**能据以行动**的答案

```
你：微信怎么这么占地方？
AI：（disk_usage()）
```

**本机真实结果（2026-10-14）**：

| 位置 | 大小 | 说明 |
|---|---|---|
| `msg/` | **1.29 GB** | 消息相关的一切都在这里 |
| ├ `msg/file/` | **896 MB** / 149 个文件 | 收发的文件（文件面的地盘） |
| ├ `msg/video/` | 269 MB / 77 个 | 视频（只报小计） |
| └ `msg/attach/` | 157 MB / 1073 个 | 加密 `.dat`（图片等，只报小计） |
| `db_storage/` | **67 MB** | **聊天记录本体只有这么大** |
| `cache/` | 66 MB | |
| `business/` | 43 MB | |

注意这张表本身就是一个反直觉结论：**记录只有 67 MB，占地方的九成是媒体与文件**。
所以"清理聊天记录"根本不解决问题。

`msg/file` 那 896 MB 再往下拆，**这才是能不能清干净的关键**：

| 分项 | 本机 | 含义 |
|---|---|---|
| `file_own_bytes` | **455 MB** | 只被**一个**会话引用的文件——**删了确实能省这些** |
| `shared_bytes` | **281 MB** | 被**多个**会话引用的转发文件——磁盘只占一份，**删了不一定省** |
| `file_unattributed` | **160 MB** | 磁盘上有、但**没有任何消息引用**它（本机 26% 的文件属于这类） |

⚠️ **这三个数不能随便相加**。按会话求和会得到 1039 MB > 磁盘实际 896 MB——
同一份被转发的文件在多个会话里各被数了一遍。这也是**别的工具不会告诉你的事**。

再往上，`by_ext` 还能直接指出元凶：本机 `msg/file` 里 **`.exe` 一项就占 581 MB**
（两个自己发的安装包），`by_month` 则显示 9 月一个月就落了 468 MB。

**本工具只报告、只读，不删任何东西**——清理是你的决定，它只负责让你**有依据**。

#### 场景 12：把「文件传输助手」当云盘用

本机实测：文件传输助手里有 **20 条文件消息、16 个独占文件、174 MB**，
其中 150 MB 是和其他会话共用的两个安装包。归档一次就知道自己往里塞了多少东西。

#### 场景 13：换机前的"抢救式"备份

`list_files()` 是**全库**的——它会告诉你哪些会话还有没导出的文件，按会话名分组。
配合 `only_missing`，搬家前的 5 分钟就能知道"有多少救不回来了"。

## 三、一套目录结构（记录与文件共用）

同一个会话搜三次，结果不会互相覆盖；归档与导出也**不会各建一棵树**：

```
D:\导出\
  index.md                       ← 一次导了多个会话时的清单
  文件传输助手\
    chat.json                    ← 正文（md / html / json）
    stats.json                   ← 报表（任何格式都有）
    assets\                      ← 图片、语音 wav
    files\                       ← 文件：media=files/all 收的附件 + archive_files 的落点
    q-发票\chat.json             ← 按关键词导的落点
    q-图片\chat.json
    2026-09\chat.json            ← split="month" 时按月拆
```

**记录面与文件面共用 `files/` 这一层**，所以"先导记录、再补归档"不会出现两份副本：
归档按大小判重，已经在 `files/` 里的直接跳过（`exists`）。
规整到这种程度的意义：Agent 不必"猜东西在哪"，拼路径就行；人也一眼看得出哪份是什么。
（这个结构只在一处定义——`exportcore.session_subdir`——归档那边调它，不另立一套。）

## 四、功能详解（5 个工具）

### 记录面

#### `list_sessions(query?)`

**做什么**：列会话，拿**确切**名字。

**为什么它不是可有可无的**：`talker` 名字对不上会给 `target_not_found`——
**这不是"这个会话没记录"**，是"我没法确定你指的是哪个"，
返回里带 `candidates`（名字相近的会话）。**先 `list_sessions` 拿准名字，比事后猜快得多。**

#### `export_chat(talker?, out_dir, format?, keyword?, limit?, since?, until?, media?, transcribe_voice?, split?, inline_max_mb?, max_sessions?)`

**参数逐条**：

| 参数 | 取值 | 效果 / 代价 |
|---|---|---|
| `format` | `md` / `html` / `json` | `md` 最小（本机 53 KB）；`html` 可分享、媒体内嵌；`json` 机读、带统计报表 |
| `keyword` | 任意字符串 | **只导出命中的消息**（正文 + 附件名，大小写不敏感）；给了它 `talker` 可省 = **全库搜** |
| `limit` | 默认 500 | 每个会话最多导多少条命中，保留**最新**的；切过就置 `truncated: true` |
| `max_sessions` | 默认 20 | 全库搜时最多导几个会话（按命中条数取前 N），其余计入 `sessions_skipped` |
| `media` | `none` / `images` / `files` / `all` | 见上：`images` 内嵌、`files` 落盘到 `files/`、`all` 两者 + 语音 wav |
| `transcribe_voice` | bool | 本机转写；**没模型逐条跳过并计数，不中断导出** |
| `since` / `until` | Unix 秒 | 只导出某一段，别整段重导 |
| `split` | `none` / `month` | 按月拆目录 |
| `inline_max_mb` | 默认 20 | 超过则退回落盘到 `assets/`，**页首写明"这份不再自包含"**，返回里 `inline_fallback` 计数 |

**统计报表（`stats`）里有什么**：条数 / 我 vs 对方 / 首末时间与跨度 / 有消息的天数 /
按月 / 按小时 / 按星期 / 消息类型分布 / 发言人排行 / 最忙的几天 / 媒体账。

**只有计数，没有一句判断**——不打意向分、不判情绪、不做画像。
工具只告诉你"数得出来的东西"，结论由你（或你的 AI）下。

**它刻意保留的三种"账目"**——这是最费心的部分，因为**它们代表用户要做的事完全不同**：

| 计数 | 含义 | 用户该做什么 |
|---|---|---|
| `image_no_key` | 图在磁盘上，但**缺解密密钥** | **在微信里点开任意一张图**，密钥就有了 |
| `image_missing` | 原图和中图本地都没有 | **没救了**——永久缺失 |
| `file_missing` | 文件过期/没下载 | 在微信里点开一次，或认了 |
| `file_mismatch` | 磁盘上有同名文件但**大小对不上**，可能是另一版 | 人工确认 |
| `file_dup` | 同一份被多条消息引用，**只收一次** | 无需动作 |
| `inline_fallback` | 有图因超限被挤出去 | 这份 html **不再自包含**，要连 `assets/` 一起发 |

**`image_no_key` 与 `image_missing` 分开报，是最有价值的一个设计**：
前者**你能修**（点开一张图），后者**修不了**。合成一个数字的话，
用户永远不知道该不该再试一次。

**枚举传错会被拒，不会静默降级**——否则"参数打错了"和"这批消息真没图"在返回里分不出来。

### 文件面

#### `list_files(talker?, since?, until?, types?, keyword?, only_missing?, limit?)`

**做什么**：把**文件消息**（`appmsg type=6`）列出来，并逐条到磁盘上定位。**只列清单、不落盘。**

**每条返回什么**：

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| `title` / `size` / `ext` | 微信消息里记的文件名与字节数 | 这是**服务器侧的事实**，不是磁盘猜的 |
| `name` / `sender` | 哪个会话、谁发的 | 群文件能标到人 |
| `ts` | 消息时间 | 可按时间范围筛 |
| `local_path` | 磁盘上的真实路径（定位不到为 `null`） | 拿去干别的也行 |
| `status` | `ok` / `size_mismatch` / `missing` | **这三个词是本工具的核心输出** |

**`status` 三种取值各自意味着什么**：

- `ok` —— 磁盘上有，**且字节数与消息里记的 `totallen` 完全一致**。
- `size_mismatch` —— 磁盘上**有同名文件，但大小对不上**。多半是**另一个版本**。
  本机实测 3 条。**这时别默认它就是要的那份**——所以它单独一个状态，不做静默兜底。
- `missing` —— 磁盘上没有。**未下载或已过期**，服务器端也没了。

**参数**：

| 参数 | 作用 | 典型用法 |
|---|---|---|
| `talker` | 限定会话（显示名或 wxid/群号） | `talker="文件传输助手"` |
| `since` / `until` | 时间范围（Unix 秒） | 只捞某个项目期的文件 |
| `types` | 按扩展名筛 | `types=["pdf","docx"]` |
| `keyword` | 文件名关键词 | 找"合同" |
| `only_missing` | **只看过期的** | 这就是"过期预警"本体 |
| `limit` | 默认 500 | 看 `total` 判断有没有被截断 |

**它带来的收益**：把"翻聊天记录找文件"从**分钟级的手工劳动**变成**一次可复现的查询**，
并且额外给出**你自己不可能知道的信息**（哪些已经下不动了）。

#### `archive_files(out_dir, talker?, since?, until?, types?, layout?, dry_run?)`

**做什么**：把定位得到的文件**拷贝**到你的目录。**只拷贝，绝不移动、绝不删除。**

**`layout` 三种摆法**：`by_session`（默认，落 `<会话名>\files\`——**与导出同一棵树**）/
`by_type`（按扩展名）/ `flat`（不分子目录）。

**返回的计数**（这是一份**对得上账**的清单）：

| 计数 | 含义 |
|---|---|
| `copied` | 这次真拷了几个 |
| `dedup` | **同一份磁盘文件被多条消息引用**，只拷一次（本机 20 条消息里有 2 条是这种） |
| `exists` | 目标上已经有一份**同一个文件**了（重跑幂等，不重拷） |
| `missing` | 过期/未下载，拷不了 |

**两条硬保证**：

1. **绝不覆盖**。目标已存在且**是另一份**（大小不同）→ 另存为带时间戳的名字。
   你昨天归档的那份，不会被今天的操作改掉。
2. **不编空文件**。定位不到就是 `missing`，**不会给你一个 0 字节的占位**——
   "文件在但内容是空的"比"文件不在"更难发现。

**它带来的收益**：归档是**幂等**的，可以放心重复跑（升级后、想起来就再跑一遍），
只会补差、不会重复、不会毁掉已有成果；而且和导出共用一个目录，
**"导记录"与"归档文件"不会各存一份**。

#### `disk_usage(session_limit?)`

**做什么**：算清磁盘**花在哪**，并把它拆成**能据以决定的三个数**。

**返回什么**：上面场景 11 那两张表就是它的原始输出（`trees` / `msg_trees` / `by_month` / `by_ext` /
`sessions` 排行 / `file_own_bytes` / `shared_bytes` / `file_unattributed`）。

**它刻意不做的事**：
- **不删任何东西**。它连一个 delete 语句都没有。
- **不把 `own` 和 `shared` 相加**当"能省的空间"——那会数重（本机 1039 MB vs 实际 896 MB）。
- **不假装能归属**：`msg/video`（269 MB）与 `msg/attach`（157 MB）**只报小计、不做会话归属**。
  因为视频靠消息配对本机只有约 1/6 能唯一定位、attach 是 md5 目录名 + 加密 `.dat`——
  **配不出来就不编**。
- `sessions[]` 默认只回前 20 名，**别拿这个截断后的榜单求和**（本机实测差 9.6 KB）；
  要验账用 `file_own_bytes` 这三个总数。

## 五、三条完整回路

**A. 导出来给人看（分享/存档）**

```
① list_sessions(query)          → 拿确切 talker（别猜名字）
② export_chat(format="md")      → 先出一份纯文字，确认会话对、范围对
③ export_chat(format="html", media="images", since, until)
                                → 单文件自包含，拖进微信就能发给人
④ 看返回的 image_no_key          → 如果 >0，去微信里点开一张图，回到 ③
⑤ 看 inline_fallback             → 如果 >0，说明要连 assets/ 一起发
```

第 ③→④ 步的循环是这套工具最日常的用法：
**它不是一次成功就完事，它会告诉你"还差什么、差的那件事在微信里点一下就能补"。**

**B. 导出来做分析**

```
① export_chat(format="json")   → 直接拿 stats 报表（不必先读正文）
② 看 stats：集中在哪几天、谁在说、说得多不多   → 决定要不要看细节、看哪一段
③ 要细节：export_chat(since, until, format="json") 只导那一段
   要指定内容：export_chat(keyword="发票", format="json")
   不知道在哪：省掉 talker → 全库搜，看 index.md 认领
④ 看返回的 truncated / sessions_skipped  → 被切过就如实说，别把"被截断"讲成"就这么多"
```

B 这条回路里的第 ② 步是重点：
**先给你一张报表，让你（或你的 AI）在花掉上下文预算之前就知道这段对话值不值得读。**

**C. 把文件搬出来（归档）**

```
① list_files(only_missing=true)   → 先看哪些已经来不及了（过期救不回来）
② list_files() / 按会话、类型、时间筛   → 确认要哪些
③ archive_files(dry_run=true)     ← 先给计划（将拷 N / 去重 M / 过期 K），此刻一个文件都没落盘
④ archive_files(dry_run=false)    ← 只拷贝、不覆盖、幂等，落在 <会话名>\files\
```

第 ③→④ 之间**必须让用户看一眼计划**：归档是不可逆的"往外搬"动作，
虽然只读微信、但落盘的是用户的目录，别替他决定。

## 七、同类工具，和该拿什么标准衡量它们

### 记录导出这一侧

| 工具 | 是什么 | 已知的坑 |
|---|---|---|
| **微信自带**「聊天记录备份与迁移」 | 出一个**加密备份** | **不能查看、不能挑选、不能编辑、不能导出**——只能整体恢复到另一台设备 |
| **WeChatMsg / 留痕 / MemoTrace**（开源） | 提取记录，导出 HTML/Word/CSV/TXT/PDF，还能出年度报告 | **官方版只支持微信 3.x**，4.x 得找第三方 fork；**官方仓库已停更删库**（腾讯 DMCA）；常见报错是 `wxid/key 为 none`、`key error`、中文路径；安卓端仅文本且**要 root** |
| **楼月**（商业） | 直读 PC 微信本地库，支持文字/图片/语音(wav)/视频/文件，批量导出 | **付费**（有用户反馈 199 元嫌贵）；有资料未明确其 4.x 支持情况 |
| **EchoTrace** | 本地导出与分析 | 已停更；**图片支持差**；不建议中文目录 |
| **WeFlow** | 实时查看/导出 + HTTP API | **只支持微信 4.0+** |
| **CipherTalk 密语 / ChatLab** | AI 摘要 / SQL+AI 分析 | 定位偏"分析"，导出形态不是重点 |
| **chatlog**（开源，Go） | 兼容 3.x/4.x，带 HTTP API 与 MCP，功能面最接近 | 取密钥有**版本上限**；macOS 需关 SIP；Docker 模式取不到密钥 |

**先说我们查到的结论**：

- **媒体普遍是"落盘"**：导出目录下另建一个 `_files/` 之类的文件夹，HTML 里**引用**它。
  代价就是**把 HTML 单独发给别人 = 一堆裂图**。
- **"自包含单文件"没有查到有人当卖点**（最接近的是 iOS 的 WechatExporter，
  部分版本称媒体内联嵌入）。**这是这个品类里少见的、我们独有的形态。**

**衡量"能不能发给人"的三个问题**：

1. **图在文件里，还是只是个链接？** 如果图片是外部引用（指向旁边一个 `files/` 目录），
   你把 HTML 单独发给别人就是**一堆裂图**。**要分享，就必须内嵌。**
2. **内嵌有上限吗？超了会告诉你吗？** 无上限的做法在大会话上会产出几百 MB 的页面，
   浏览器直接打不开；有上限但不告诉你的，会**静默**把你的图挤出去。
   本工具的做法是：超限退回落盘、**页首写明"这份不再自包含"、返回里给 `inline_fallback` 计数**。
3. **有没有分账？** "这批消息本来就没图"和"图导不出来"长得一模一样。
   不分账的工具，你永远不知道该不该再试一次。本工具的答案是分四笔：
   **`image_no_key`（你能修——去微信点开一张图）/ `image_missing`（没救了）/
   `file_mismatch`（可能是另一版）/ `file_dup`（同一份只收一次）**。

### 文件归档这一侧

**微信自带的办法**：

| 办法 | 实际能做到什么 |
|---|---|
| 设置 → 通用 → 存储空间 → 管理聊天记录 | 按**会话**列文件和图片，能长按保存。**但它只列得出现在还打得开的**——已过期的连条目都未必给你 |
| 设置 → 通用 → 聊天记录备份与迁移 | 一个**加密备份**，只能整体恢复到另一台设备 |
| 聊天里往上翻，看到文件气泡再点开 | 得先知道在哪个会话、大概什么时候——**这正是本工具替你做的事** |

**网上流传的"恢复过期文件"教程**，四类各自的天花板：

| 教程 | 真相 |
|---|---|
| **改手机日期**到接收后 7 天内 | 微信员工直接回应"**假得有点离谱**"：微信不是用你手机本地时间校验的，**从没点过接收的文件过期就是过期**，乱改时间还会让文件排序错乱 |
| 从"存储空间 / 聊天记录管理"里长按保存 | **只对"曾经打开过"的内容可能有效**——腾讯员工回应"过期图片可找回教程"时说的原话是"没一处是对的" |
| 去手机文件管理的 `Android/data/com.tencent.mm/...` 里翻 | 能翻到的是**已经落到本地的那部分**，翻不到的**本地根本没有** |
| 用数据恢复软件扫描 | 效果不保证；且**扫的是同一块磁盘**，本地没落过盘的内容它变不出来 |

腾讯客服的公开口径是：**聊天记录涉及隐私，服务器不保存用户聊天记录，数据被清除且未备份时无法恢复。**
——也就是说，**"过期"在服务器侧就是不可逆的。**

**一个空白位：没有人在做"文件级清单"**

> **没有查到任何一款工具**做「列出本机微信文件清单 + 标注哪些已过期/下不动 + 按会话批量归档」。

市面工具**全是"聊天记录导出"**——文件只是导出过程的附带产物，
不会有 `status`、不会有 `only_missing`、更不会替你算"删了到底能省多少"。
NAS / 私有云那一类（收件箱、时光机）本质是**"转存到别处"**，而且要**手动转发**，不是就地归档。

**微信自带的"存储空间管理"其实和本工具是互补的，不是竞争关系**：
它能删、能按大小排序、能只看某个会话——但它**没有文件级视图**，
也**不判哪个文件重要**、**不合并重复副本**、**连 `Video/_thumb` 缩略图目录都不显示**
（有资料提到 Mac 端这个目录半年能积 3–8 G）。

**它给不了的那一半，正好是本工具的全部。**

**所以本工具站在哪**：上面所有办法**都是事后**——过期已经在眼前了，才去想办法。
而本工具是唯一**事前**的那一环：

> **它不能救回过期的文件，但它能让你在过期之前知道有哪些。**

## 九、它做不到什么

- **过期/未下载的图片和文件导不出来、也归档不了**（微信服务器上已经没了）。
  记录面会分成 `image_no_key` / `image_missing` / `file_missing` / `file_mismatch` 四笔账，
  文件面给 `status=missing`——**如实告诉你哪些永久缺失**，不假装是完整的。
  文件面的价值在于**在变成这样之前提醒你**，而不是变完之后抢救。
- **语音转写要自备模型**。没装就逐条跳过并计数，**不影响导出**。
- **导出的是你本机这份数据**。手机上删了、本地没同步的部分不在里面。
- **附件从不内嵌**（不管 `inline_max_mb` 多大）——几百 MB 的 base64 会让浏览器打不开。
  这是刻意的，不是省事。
- **报表不替你下结论**。它给计数，不给意向分、不给情绪、不给画像——
  "这个客户值不值得跟"是**你**的判断，工具只把数摆出来。
- **全库搜一次最多导 20 个会话**（`max_sessions`）。命中更多时按条数取前 N，
  剩下的**如实报 `sessions_skipped`**——不是"只有这些"。
- **关键词只匹配正文与附件名**，不搜图片里的字（那要 OCR，不在这个产品的面上）。
- **图片与视频不在归档范围内**。`disk_usage` 会报 `msg/video`、`msg/attach` 的**体积小计**，
  但**不归属到会话、也不归档**：视频靠消息配对本机只有约 1/6 能唯一定位，
  attach 是 md5 目录名 + 加密 `.dat`。**配不出来就不编**——宁可只报体积，
  也不给你一个"看起来像"的错误文件。
- **不删任何东西**。占用分析只报告，清理永远是你的决定。
- **不会替你决定存哪**。`out_dir` 必须由你说或确认，它不自己挑目录。
- **导出与归档都只读**：不发送、不修改、不删除任何微信内容。
- ⚠️ 导出的记录与归档的文件都含**他人**的隐私。发给谁、放哪、要不要交给云端模型，
  请你自己评估——本工具做的是**让你手上有一份能自己掌控的副本**，怎么用它不由工具决定。
