# wechat-file-mcp · 微信文件归档

> 五件套之一。安装与参数细节见
> [`../../apps/windows/resources/wechat-file-mcp/README.md`](../../apps/windows/resources/wechat-file-mcp/README.md)。
> 文末的实测数据来自 2026-10-14 在本机真机上跑这套 exe 的原始输出。

## 一句话

**把微信里收发的文件趁早搬出来，并且告诉你哪些已经搬不动了。**

---

## 一、它解决什么问题

### 1. 微信里的文件会**自己消失**，而且不打招呼

微信的文件不是"存着"的，是**缓存**。服务器只保留一段时间，过期后本地没下过的就**永久没了**：
点开只会看到一句"该文件已过期或已被清理"。这不是 bug，是设计。

要命的是**你自己不知道哪个快过期了**。你当时在群里点开看过一眼，
以为"在微信里"，一周后要用才发现打不开——**你没有任何预警**。

### 2. 你要的文件散在几十个按月的目录里

微信 4.x 把文件按 `msg/file/<年-月>/` 分片存放，文件名还可能带 `20260812 ` 这样的日期前缀，
同名不同版本的两个文件（比如两份"报告.pdf"）**躺在不同月份里，靠文件名分不出谁是谁**。
想手工捞一份出来，得先知道它在哪个月。

### 3. 「微信怎么这么占地方」没人答得上来

微信自带的"存储空间管理"只给你一个**总数**和几个大类，它不会告诉你
**这是哪个会话发的、是不是同一份文件被转发了十次、删了到底能省多少**。
而这些恰恰是"该不该清"的唯一依据。

### 4. 这份数据已经在你机器上了，只是没人替你读

文件本体就躺在磁盘上、明文的、谁也没锁。缺的只是一个**能读懂消息 ↔ 磁盘对应关系**的读层。

**wechat-file-mcp 就是这一层。** 它做三件事：**列出来 → 告诉你哪些来不及了 → 搬到你要的地方**。

### 5. 这些不是假设的痛点

翻一圈公开的求助帖，抱怨的形状高度一致：

- 知乎上有一篇文章的标题就是**「救命！微信文件『已过期』差点让我当场去世」**；
- 工作群、客户合同、学生作业**「几天没点开就提示文件已过期或已被清理」**，清过缓存之后更抓狂；
- 手机微信几十上百 G，**"不敢随便清理"**——因为怕清掉的正是不该清的；
- 群文件同样会过期，**"群里重要文件找不到"**。

还有一条很说明问题：**"把手机日期改到接收后 7 天内就能恢复过期文件"**这个说法传得很广，
评论区一堆"学到了""亲测有效"——直到微信员工出来说**"假得有点离谱"**。

**谣言能被疯传，恰恰说明这件事上没有一个权威的、能自己查的入口。**
本工具想提供的就是那个入口：**别猜，直接列出哪些还没过期。**

## 二、典型场景

### 场景 1：过期预警——趁还来得及

这是本产品**最不可替代**的场景：过期是单向的，报警只在这一侧有效。

```
你：我那些群里哪些文件已经过期了？
AI：（list_files(only_missing=true)）9 个文件已经下不动了……
```

**本机真实结果（2026-10-14）**：157 条文件消息里，**9 条 `missing`、3 条 `size_mismatch`、145 条可归档**。
那 9 条长这样：3 份 PDF、2 份**同名 zip**（同一文件被发了两次，两条都没了）、
2 个 `.exe` 安装包的两次转发、1 份 docx、1 份 2000 元方案的 PDF。
——**你没有任何别的办法知道这 9 条的存在。**

⚠️ 一旦落进这 9 条，任何工具都救不回来（服务器端也没了）。这就是为什么"预警"本身有价值：
**它把"永久损失"变成"赶紧下载"。**

**时间窗只有 14 天**——聊天里的图片、视频、文件，微信官方的过期时限就是**两周**，不是"很久以后"。
另外微信设置里有开关「我 → 设置 → 通用 → 照片、视频、文件与通话 → 保留查看过的原图原视频」，
**但它只保得住你看过的**；本工具告诉你的恰恰是**你没点开、所以正在滑向过期**的那部分。

### 场景 2：批量归档，先看计划再落地

```
你：能下的都归档到 D:\wechat-backup
AI：（archive_files(out_dir="D:\\wechat-backup", talker="文件传输助手", dry_run=true)）
     → total 20 / 将拷贝 18 / 去重 2 / 过期 0 —— **此刻一个文件都还没落盘**
你：可以
AI：（dry_run=false）→ 已落盘 D:\wechat-backup\文件传输助手\，18 个文件
```

`dry_run=true` 是**默认值**：不显式说"真的拷"，它只算不改。归档几百个文件要跑几十秒，
你会看到 `notifications/progress` 持续上报「归档中 40/200（已拷贝 37）」——
**不用盯着转圈猜是不是卡死**。

### 场景 3：回答「微信怎么这么占地方」，而且是**能据以行动**的答案

```
你：微信怎么这么占地方？
AI：（disk_usage()）
```

**本机真实结果（2026-10-14）**：

| 位置 | 大小 | 说明 |
|---|---|---|
| `msg/` | **1.29 GB** | 消息相关的一切都在这里 |
| ├ `msg/file/` | **896 MB** / 149 个文件 | 收发的文件（本产品的地盘） |
| ├ `msg/video/` | 269 MB / 77 个 | 视频（只报小计） |
| └ `msg/attach/` | 157 MB / 1073 个 | 加密 `.dat`（图片等，只报小计） |
| `db_storage/` | **67 MB** | **聊天记录本体只有这么大** |
| `cache/` | 66 MB | |
| `business/` | 43 MB | |

注意这张表本身就是一个反直觉结论：**记录只有 67 MB，占地方的九成是媒体与文件**。
所以"清理聊天记录"根本不解决问题。

`msg/file` 那 896 MB 再往下拆，**这才是能不能清干净的关键**：

| 分项 | 本机 | 含义 |
|---|---|---|
| `file_own_bytes` | **455 MB** | 只被**一个**会话引用的文件——**删了确实能省这些** |
| `shared_bytes` | **281 MB** | 被**多个**会话引用的转发文件——磁盘只占一份，**删了不一定省** |
| `file_unattributed` | **160 MB** | 磁盘上有、但**没有任何消息引用**它（本机 26% 的文件属于这类） |

⚠️ **这三个数不能随便相加**。按会话求和会得到 1039 MB > 磁盘实际 896 MB——
同一份被转发的文件在多个会话里各被数了一遍。这也是**别的工具不会告诉你的事**。

再往上，`by_ext` 还能直接指出元凶：本机 `msg/file` 里 **`.exe` 一项就占 581 MB**
（两个自己发的安装包），`by_month` 则显示 9 月一个月就落了 468 MB。

**本工具只报告、只读，不删任何东西**——清理是你的决定，它只负责让你**有依据**。

### 场景 4：把「文件传输助手」当云盘用

本机实测：文件传输助手里有 **20 条文件消息、16 个独占文件、174 MB**，
其中 150 MB 是和其他会话共用的两个安装包。归档一次就知道自己往里塞了多少东西。

### 场景 5：换机前的"抢救式"备份

`list_files()` 是**全库**的——它会告诉你哪些会话还有没导出的文件，按会话名分组。
配合 `only_missing`，搬家前的 5 分钟就能知道"有多少救不回来了"。

## 三、功能详解（3 个工具）

### `list_files(talker?, since?, until?, types?, keyword?, only_missing?, limit?)`

**做什么**：把**文件消息**（`appmsg type=6`）列出来，并逐条到磁盘上定位。

**每条返回什么**：

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| `title` / `size` / `ext` | 微信消息里记的文件名与字节数 | 这是**服务器侧的事实**，不是磁盘猜的 |
| `name` / `sender` | 哪个会话、谁发的 | 群文件能标到人 |
| `ts` | 消息时间 | 可按时间范围筛 |
| `local_path` | 磁盘上的真实路径（定位不到为 `null`） | 拿去干别的也行 |
| `status` | `ok` / `size_mismatch` / `missing` | **这三个词是本工具的核心输出** |

**`status` 三种取值各自意味着什么**：

- `ok` —— 磁盘上有，**且字节数与消息里记的 `totallen` 完全一致**。
- `size_mismatch` —— 磁盘上**有同名文件，但大小对不上**。多半是**另一个版本**。
  本机实测 3 条。**这时别默认它就是要的那份**——所以它单独一个状态，不做静默兜底。
- `missing` —— 磁盘上没有。**未下载或已过期**，服务器端也没了。

**参数**：

| 参数 | 作用 | 典型用法 |
|---|---|---|
| `talker` | 限定会话（显示名或 wxid/群号） | `talker="文件传输助手"` |
| `since` / `until` | 时间范围（Unix 秒） | 只捞某个项目期的文件 |
| `types` | 按扩展名筛 | `types=["pdf","docx"]` |
| `keyword` | 文件名关键词 | 找"合同" |
| `only_missing` | **只看过期的** | 这就是"过期预警"本体 |
| `limit` | 默认 500 | 看 `total` 判断有没有被截断 |

**它带来的收益**：把"翻聊天记录找文件"从**分钟级的手工劳动**变成**一次可复现的查询**，
并且额外给出**你自己不可能知道的信息**（哪些已经下不动了）。

### `archive_files(out_dir, talker?, since?, until?, types?, layout?, dry_run?)`

**做什么**：把定位得到的文件**拷贝**到你的目录。**只拷贝，绝不移动、绝不删除。**

**`layout` 三种摆法**：`by_session`（默认，每会话一个子目录）/ `by_type`（按扩展名）/ `flat`。

**返回的计数**（这是一份**对得上账**的清单）：

| 计数 | 含义 |
|---|---|
| `copied` | 这次真拷了几个 |
| `dedup` | **同一份磁盘文件被多条消息引用**，只拷一次（本机 20 条消息里有 2 条是这种） |
| `exists` | 目标上已经有一份**同一个文件**了（重跑幂等，不重拷） |
| `missing` | 过期/未下载，拷不了 |

**两条硬保证**：

1. **绝不覆盖**。目标已存在且**是另一份**（大小不同）→ 另存为带时间戳的名字。
   你昨天归档的那份，不会被今天的操作改掉。
2. **不编空文件**。定位不到就是 `missing`，**不会给你一个 0 字节的占位**——
   "文件在但内容是空的"比"文件不在"更难发现。

**它带来的收益**：归档是**幂等**的，可以放心重复跑（升级后、想起来就再跑一遍），
只会补差、不会重复、不会毁掉已有成果。

### `disk_usage(session_limit?)`

**做什么**：算清磁盘**花在哪**，并把它拆成**能据以决定的三个数**。

**返回什么**：上面场景 3 那两张表就是它的原始输出（`trees` / `msg_trees` / `by_month` / `by_ext` /
`sessions` 排行 / `file_own_bytes` / `shared_bytes` / `file_unattributed`）。

**它刻意不做的事**：
- **不删任何东西**。它连一个 delete 语句都没有。
- **不把 `own` 和 `shared` 相加**当"能省的空间"——那会数重（本机 1039 MB vs 实际 896 MB）。
- **不假装能归属**：`msg/video`（269 MB）与 `msg/attach`（157 MB）**只报小计、不做会话归属**。
  因为视频靠消息配对本机只有约 1/6 能唯一定位、attach 是 md5 目录名 + 加密 `.dat`——
  **配不出来就不编**。
- `sessions[]` 默认只回前 20 名，**别拿这个截断后的榜单求和**（本机实测差 9.6 KB）；
  要验账用 `file_own_bytes` 这三个总数。

## 四、一轮完整回路

```
① wechat 里有人发了个文件
        │
② list_files()                    ← 消息侧：title + totallen + 会话 + 时间
        │
③ build_index() 扫 msg/file/<月>/ ← 磁盘侧：同名文件 + 真实字节数
        │
④ 同名消歧：totallen 对得上 → ok；对不上 → size_mismatch；没有 → missing
        │
⑤ archive_files(dry_run=true)     ← 先给计划
        │
⑥ archive_files(dry_run=false)    ← 只拷贝、不覆盖、幂等
```

第 ③→④ 步还认**带日期前缀的别名**（消息里叫"证书.pdf"、磁盘上叫"20260812 证书.pdf"），
这是手工翻目录最容易漏掉的一环。

## 六、别人怎么解决这件事，以及他们卡在哪

### 微信自带的办法

| 办法 | 实际能做到什么 |
|---|---|
| 设置 → 通用 → 存储空间 → 管理聊天记录 | 按**会话**列文件和图片，能长按保存。**但它只列得出现在还打得开的**——已过期的连条目都未必给你 |
| 设置 → 通用 → 聊天记录备份与迁移 | 出一个**加密备份**，只能整体恢复到另一台设备，**不能查看、不能挑选、不能导出** |
| 设置 → 帮助与反馈 → 故障修复 | 修的是索引，不是文件 |
| 聊天里往上翻，看到文件气泡再点开 | 得先知道在哪个会话、大概什么时候——**这正是本工具替你做的事** |

### 网上流传的"恢复过期文件"教程

腾讯客服的公开口径是：**聊天记录涉及隐私，服务器不保存用户聊天记录，数据被清除且未备份时无法恢复。**
——也就是说，**"过期"在服务器侧就是不可逆的**。

坊间教程大致四类，各自的天花板：

| 教程 | 真相 |
|---|---|
| **改手机日期**到接收后 7 天内 | 微信员工直接回应"**假得有点离谱**"：微信不是用你手机本地时间校验的，**从没点过接收的文件过期就是过期**，乱改时间还会让文件排序错乱 |
| 从"存储空间 / 聊天记录管理"里长按保存 | **只对"曾经打开过"的内容可能有效**——腾讯员工回应"过期图片可找回教程"时说的原话是"没一处是对的" |
| 去手机文件管理的 `Android/data/com.tencent.mm/...` 里翻 | 能翻到的是**已经落到本地的那部分**，翻不到的**本地根本没有** |
| 用数据恢复软件扫描 | 效果不保证；且**扫的是同一块磁盘**，本地没落过盘的内容它变不出来 |

**过期的时间线也值得记一下**：聊天里的图片、视频、文件，过期时间是 **14 天**——
不是"很久以后"，是**两周**。这就是"预警"这个功能唯一的窗口。

### 一个空白位：**没有人在做"文件级清单"**

这是这一轮横向查下来最明确的一个结论：

> **没有查到任何一款工具**做「列出本机微信文件清单 + 标注哪些已过期/下不动 + 按会话批量归档」。

市面工具**全是"聊天记录导出"**——文件只是导出过程的附带产物，
不会有 `status`、不会有 `only_missing`、更不会替你算"删了到底能省多少"。
NAS / 私有云那一类（收件箱、时光机）本质是**"转存到别处"**，而且要**手动转发**，不是就地归档。

**微信自带的"存储空间管理"其实和本工具是互补的，不是竞争关系**：
它能删、能按大小排序、能只看某个会话——但它**没有文件级视图**，
也**不判哪个文件重要**、**不合并重复副本**、**连 `Video/_thumb` 缩略图目录都不显示**
（有资料提到 Mac 端这个目录半年能积 3–8 G）。

**它给不了的那一半，正好是本工具的全部。**

### 所以本工具站在哪

上面所有办法**都是事后**——过期已经在眼前了，才去想办法。
而本工具是唯一**事前**的那一环：

> **它不能救回过期的文件，但它能让你在过期之前知道有哪些。**

| 你能做的最好的事 | 本工具多给的那一步 |
|---|---|
| 手动开「保留查看过的原图原视频」 | 那**只保住你看过的**——本工具告诉你有多少是**你没点开、所以快没了**的 |
| 定期去"存储空间管理"里翻 | 那是**按会话的树形浏览**，没有 `only_missing` 这个视角 |
| 重要文件随手另存 | 你得先知道哪些重要。本工具按扩展名/月份/会话给你元凶清单 |

| 手工做 | 用本品 |
|---|---|

## 八、它做不到什么

- **已过期的文件救不回来**。服务器端没了、本地也没下过，任何工具都无解。
  本工具的价值在于**在变成这样之前提醒你**，而不是变完之后抢救。
- **图片与视频不在归档范围内**。`disk_usage` 会报 `msg/video`、`msg/attach` 的**体积小计**，
  但**不归属到会话、也不归档**：视频靠消息配对本机只有约 1/6 能唯一定位，
  attach 是 md5 目录名 + 加密 `.dat`。**配不出来就不编**——宁可只报体积，
