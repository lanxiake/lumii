# wechat-mcp · 本机微信助手

> 五件套的**主产品**，其余四件是它的专项切片。安装与配置细节见
> [`../../apps/windows/resources/wechat-mcp/README.md`](../../apps/windows/resources/wechat-mcp/README.md)。
> 文中所有实测数字来自 2026-10-14 在本机真机上跑这套 exe 的原始输出。

## 一句话

**让你的 AI 用你自己的身份，读你本机的微信、并以你的身份回话**——不改微信、不注入、
不把数据传出去。

---

## 一、它解决什么问题

### 1. 微信对 AI 是一堵墙，而且是有意砌的

聊天记录在本机是**加密数据库**（`db_storage/`，靠进程内存里的密钥解），图片是加密
`.dat`、语音是 SILK 编码、文件散在按月的目录里、视频是另一套 hardlink 索引。
你自己翻得动——因为**是你用手指在翻**。AI 连门都摸不到：

- 它没有你的好友列表，不知道"文件传输助手"和"TOOLAN"谁是谁；
- 它不知道你刚才那句"好的"是在回哪一句；
- 它甚至不知道**你平时怎么说话**。

于是所有"让 AI 帮我处理微信"的想法都卡在同一句话上：

> **"AI 不知道我在微信里说了什么。"**

### 2. 打通它的两种做法，只有一种能用

- **注入 / hook 微信客户端**：把 DLL 塞进 `WeChat.exe` 挂钩子。
  技术上是可行的——**但我们不做**。微信 4.x 客户端带 **VMProtect 加固 + Detours 钩子**
  （社区扫描工具 `wcprobe` 自己就是这套机制）。跟这种客户端玩注入，等于
  ①和反调试器硬碰，②有你被它反制的一天，③把用户账号置于风险中。
  **零注入既是技术要求，也是伦理要求。**
- **只读本机数据 + 用系统正规接口操作窗口**：不碰微信一根汗毛。
  **wechat-mcp 走这条。**

### 3. 于是它由三块拼成

| 块 | 怎么做到的 | 边界 |
|---|---|---|
| **读** | 从微信进程内存里取 SQLCipher 密钥（只读内存，不注入），解本地库；图片/语音解码都在本机 | 微信**必须正在运行** |
| **写** | 窗口消息投递 + UI Automation 读数——即"替你在窗口里打字点按钮"，不移动你的光标、不动剪贴板 | 微信窗口存在即可，**不需要前台** |
| **蒸馏** | 从你自己的历史消息里算**实测数字**，生成画像卡 | 只算，不猜 |

三块合起来：**读得到上下文 → 算得出你的风格 → 发得出去且发得准**。

## 二、典型场景

### 场景 1：「这段对话聊到哪了？帮我回一句」

```
你：看看 TOOLAN 这个会话刚才聊到哪了
AI：（read_history(talker="TOOLAN", limit=10)）
你：帮我回一句，语气随意点
AI：（先 wechat_profile_get("self") 读你的画像 → 起草 → dry_run 给你看 → 你点头才发）
```

关键在于**"语气随意点"不能靠猜**。画像里的数字是实测的：

**本机真实结果（2026-10-14，近 30 天 3886 条我发出的消息）**：

| 指标 | 实测值 |
|---|---|
| 总体标点使用率 | **0.38** |
| 1–5 字短句带标点 | **0.07** ← 几乎不用 |
| 6–12 字 | **0.29** |
| 13–25 字 | **0.61** |
| 26 字以上 | **0.71** ← 长句基本都带 |
| 表情使用率 | 0.05 |

这组数字本身就是**反直觉结论**：凭几条样本目测，你只会得出"这人几乎不加标点"——
而真相是**短句不加、长句照加**。AI 按错误结论写出来的回复，一眼就是假的。

再看 293 条长消息的收尾方式：**标点 65% / 空格 32% / 什么都不加 9%**——
说明这个人的长句习惯是用**句号**收，不是用换行。

高频词（近 30 天）：**好的（21）/ 捂脸（15）/ 收到（13）**。
——"帮我写得像我"，这三条比任何风格描述都管用。

画像卡本身 **2605 字、11 个章节**，含《最高优先》《沟通风格（实测数字）》
《活跃时段》《主要来往对象（按我发出的条数）》《常聊话题》。它是**可编辑的文件**，
你改完 `wechat_profile_save` 存回去，下次用的就是你的版本。

### 场景 2：「哪些会话还没回？」

```
你：我有哪些没看的？
AI：（list_unread()）→ **132 个会话有未读**，按未读数排……
```

本机实测 **132** 个会话带未读。这个数字手工是**列不出来的**——
微信只给你一个红点总数，不会告诉你哪 132 个、各多少条。

配合 `poll_new(since_ts)` 做**增量**盯梢：它只解密新增的 WAL 帧、只扫有变化的会话表，
几秒一拍也没负担。把带场景描述的技能包放进客户端，Agent 自己认场景——
**MCP 只提供工具，不会自己回复**，回不回、怎么回是你接入侧的策略。

### 场景 3：「我上次说'谢谢'是在哪来着」

```
你：我最近跟谁说谢谢来着？
AI：（search_messages("谢谢")）→ 24 条命中，扫了 3000 条，**没截断**
```

**本机实测：24 条命中**。检索是**全库**的（跨所有会话），
每条带 `talker` / `local_id` / 时间 / 渲染后的一行文本。
命中里如果是图片/语音/视频，还会带上**本地路径**（见场景 4）。

### 场景 4：「找那段视频 / 那张图」

```
你：找一下我那几条视频
AI：（search_messages("视频")）48 条，其中 8 条本机有文件、能直接给你路径；
     其余 40 条本地没下载过——在微信里点开一次，之后再搜就有了
```

这是**唯一一件工具做不到、而你能做到的事**，所以文档里写明白了：
**视频没在微信里点开过就不会下载到磁盘**。本机 48 条视频消息只有 **8 条**能定位到文件。
**没有路径 ≠ 视频不存在**——消息在、时长在，就是本地没那份字节。
工具**不猜、不编**，也**不会拿别的视频顶上**。

图片同理，而且更微妙：**同一张图在磁盘上可能是高清也可能是缩略图，工具会明说拿到的是哪个**。
本机实测 `read_image` 返回 `{"bytes":5775,"variant":"thumb"}`——**一张 5.7 KB 的缩略图**。
`variant`（`hd`/`thumb`）加 `bytes` 就是唯一能发现的线索：
**"AI 说这图太糊看不清"到底是模型不行，还是它只拿到了 83×180 的缩略图**——
没有这两个字段，这个问题**永远查不出来**。

### 场景 5：听语音

```
你：那条语音说了什么
AI：（transcribe_voice(talker=..., local_id=...)）
    → 一条 13.2 秒的语音，**3.13 秒**转完，模型 paraformer-zh-small（sherpa-onnx，**本地**）
```

音频**不出机器**。这是硬约束：语音里是别人的声音，转写模型必须是本地的。

### 场景 6：让 AI 替你发

```
你：发给文件传输助手："测试"
AI：（send_text(talker="文件传输助手", content="测试", dry_run=true)）→ 校验通过，要真发吗？
你：发
AI：（dry_run=false）→ **9.5 秒**后 {ok:true}，read_history 读回确认
```

本机真实发送耗时 **9.5 秒**——所以调用方给到 **5 分钟超时**是必要的，
**超时 ≠ 失败**（消息很可能已经发出去了，这时应该 `read_history` 确认，**不要重发**）。

## 三、功能详解（19 个工具，pro 版）

### A. 环境与定位（4 个）——先确认"能不能读"

| 工具 | 做什么 | 为什么需要它 |
|---|---|---|
| `check_env()` | 微信是否运行、几个进程、窗口句柄/位置/大小、DPI | 本机实测：运行中、**5 个进程**、hwnd 132192、rect [60,40,1280,820]、dpi 96。**发送失败的第一现场** |
| `locate_db()` | 找出数据目录与来源 | 本机返回 `...\xwechat_files\<账号>\db_storage`，来源 `ini`（不是猜的路径） |
| `repair_env()` | 把掉到托盘/最小化的主窗口还原 | 实测把 `minimized:true, onscreen:false, rect:[-32000,-32000,160,28]` 还原成 `rect:[60,40,1280,820]`，之后 dry-run 发送立刻通过 |
| `list_sessions()` | 列所有会话 | 本机 **2.05 秒**。所有 `talker` 参数的正解来源 |

**这 4 个工具的价值**：把"没反应"变成**一句能读懂的原因**。
`env_not_ready` 不是你的参数问题，是你得先把微信打开——工具把这两件事分开了。

### B. 读（5 个）

| 工具 | 返回什么 | 实测/收益 |
|---|---|---|
| `read_history(talker, limit?, since?, until?)` | 一个会话的历史，**渲染成一行文本**（含 `[图片]`/`[视频 40 秒]`/`[语音 13 秒]`） | 每条带 `local_id`——**同一秒的多条也分得清**，这是"先搜到、再取它的图"的前提 |
| `search_messages(keyword, limit?)` | 跨会话全库检索 | 本机搜"谢谢" → **24 条 / 扫描 3000 条 / 未截断** |
| `list_unread()` | 有未读的会话 | 本机 **132** 个 |
| `poll_new(since_ts)` | **增量**新消息 | 只解密新增 WAL 帧、只扫变化过的会话表——所以几秒一拍也不心疼，盯梢回路靠它 |
| `read_image(talker, local_id)` | MCP **image 内容块**（内联位图）+ 元数据 | 跨机也能看；`variant` 明确是 `hd` 还是 `thumb`，`bytes` 是实际字节数——**"图模糊到底是模型的锅还是只拿到缩略图"，看这两个字段** |

### C. 媒体解码（1 个）

| 工具 | 做什么 | 实测 |
|---|---|---|
| `transcribe_voice(talker, local_id)` | SILK → Paraformer 转文字，**全本机** | 13.2 秒语音 → **3.13 秒**出结果，模型 `paraformer-zh-small（sherpa-onnx，本地）` |

模型没装会**逐条失败并计数**，不会中断整批——所以批量导出的场景里，转写是"尽力而为"，不拖垮主流程。

### D. 发（4 个）

| 工具 | 做什么 | 前台要求 |
|---|---|---|
| `send_text(talker, content, dry_run?)` | 发文本 | **不需要**，锁屏也能发 |
| `send_file(talker, path, dry_run?)` | 发图片/文件/视频/音频 | **不需要** |
| `send_batch(targets[], content, dry_run?)` | 群发给多个目标 | **不需要**，逐目标**独立校验**（一个失败不连坐） |
| `reply_to(talker, local_id, content)` | **带引用**的回复 | ⚠️ **唯一需要窗口可见且在前台的** |

**一条纪律覆盖 4 个工具：默认 `dry_run=true`。**
不显式说"真发"，它只校验、不动手。发出去是**不可撤回**的，以你本人身份发出——
所以默认值必须是**不发送**。

**发送的 5 道校验（fail-closed）**：

```
① 环境   微信在跑、窗口在
② 目标   内容锚点 + 头部双印证 + 群成员昵称第三重印证
③ 输入   字符确实落进了输入框
④ 发送   回车已按
⑤ 确认   读库看到这条消息
```

任一不过即中止，**绝不盲发**；②拿不准时**一个字都不输入**——
宁可报 `target_unconfirmed` 并自动排队补发，也不会发错人。

### E. 蒸馏与画像（5 个）

| 工具 | 做什么 | 实测 |
|---|---|---|
| `wechat_digest(scope, since?, limit?)` | 算风格数字 + 高频词 + 来往对象 | 近 30 天：self **3886** 条（其中**我发出 1119**），耗时 **0.42 秒** |
| `wechat_profile_get(scope?)` | 读画像卡（不带参数则列出有哪些） | self 卡 **2605 字**、`age_days 2.0`、`stale false` |
| `wechat_profile_save(scope, content)` | 存回（**用户可以手改**） | 改了不会被下次重算悄悄抹掉 |
| `wechat_distill_state()` | 蒸馏进度 | 长时间跑需要知道跑到哪了 |
| `wechat_distill_clear(scope?)` | 清掉重来 | 换了账号/想重算时用 |

**为什么画像必须是文件而不是提示词里的常量**：你的说话风格会变，而且**你自己最清楚哪里不对**。
做成文件，你就能直接改"我不用『呢』结尾"这种模型算不出来的事。

### F. 两档的差别

| 项 | **pro（19 个）** | **lite（12 个）** |
|---|---|---|
| 读收发文本/文件 | ✅ | ✅ |
| `image_path`/`voice_path`/`video_path` | ✅ | ❌ **主动剥离** |
| `read_image` / `transcribe_voice` / 画像 5 件套 | ✅ | ❌ |
| 语音转写 | ✅ | ❌ |

本机实测 lite：调 `read_image` 会得到明确回复
**「该工具属于高级版（pro），当前运行的是基础版（lite）」**——
不是静默失败，是**告诉你为什么没有**。
lite 的 `read_history` 里三个路径字段全是 `null`，搜"视频"命中的 3 条**一条都不带** `video_path`。

## 四、一轮完整回路

```
① list_sessions()          → 拿到确切的 talker（别猜名字）
② read_history(talker)     → 上下文，每条带 local_id
③ wechat_profile_get("self") → 你平时怎么说话（实测数字）
④ 起草
⑤ send_text(dry_run=true)  → 校验 + 给你看
⑥ send_text(dry_run=false) → 5 道校验 → 真发
⑦ read_history             → 读回确认（**唯一可信的"发没发出去"判据**）
```

第 ⑦ 步是这套东西和"调个 API 就完了"的工具最大的区别：
**它不假设自己成功了，它去库里确认。**

## 六、同类项目都停在哪一步

"让 AI 用你自己的聊天数据"这件事，社区里有人做，而且做得不错。
摆在一起看，能看清这五件套到底补的是哪一段。

| 项目 | 做到哪 | 停在哪 |
|---|---|---|
| **chatlog**（开源，Go；有多个 fork） | 直读本地库，兼容 **3.x / 4.x**；解图片、语音、`wxgf`；自动解密 + **新消息 Webhook**；TUI / CLI / Docker；**HTTP API**；**支持 MCP（Streamable HTTP / SSE）**；多账号 | 取密钥**有版本上限**（公开资料写的是 Windows < 4.0.3.36、macOS < 4.0.3.80）；macOS 取密钥要**临时关 SIP**；Docker 模式**取不到密钥**；要 CGO 编译。**能力面是"读 + 查询接口"** |
| **PyWxDump**（3.x 时代取密钥标配） | 内存扫密钥 + 解密 + HTML/CSV + 局域网 Web 查看 | **2025-10 收到微信律师函，已删库停更** |
| **wxauto / WePush 系**（桌面自动化） | 通过 UI 自动化操作微信窗口 | 论坛里直接反馈 **"不支持微信 4.0"**（表现是"无效窗口句柄"）；wxauto 已从 PyPI 下架且停更 |
| **WeChatFerry 系**（DLL 注入） | 读得最全、发得最自由 | 版本**锁死**（如 3.9.12.55）；2025-09 的封号风暴里"**几乎无一幸免**"（社区统计称封号率 >80%） |
| **腾讯官方 iLink / ClawBot**（2026 新开的口子） | 官方 Bot 通道，宣称"不逆向、不封号" | 硬限制：**只能被动回复**、连接 **24 小时过期**、每次扫码 **Bot ID 会变**、与 openid 生态不通 |
| **WeChat-MCP 类**（macOS Accessibility / pyautogui） | 读+回消息、截屏 | 多数停更；README 自列封号、数据泄露、系统不稳定等风险 |

**四条能看出来的规律**：

1. **读取侧已经有人做到了，而且做得比我们广**（HTTP API、Webhook、多账号、Docker 部署）。
   我们不去争这一块。
2. **所有人都在跟微信的版本赛跑，而且没有稳态**：`chatlog` 有取密钥的版本上限、
   `WeChatMsg` 官方版停在 3.x 且自述不再更新、`wxauto` 卡在 4.0 门口、
   PyWxDump 停在 3.x。**这个赛道上"支持最新版"是一张随时会过期的船票。**
3. **这个生态在萎缩，不是在扩张。** 腾讯曾**一次性 DMCA 投诉 30+ 个仓库**；
   PyWxDump 收到律师函删库；`wx_key` 删库时留了个讽刺的 README。
   死因几乎都是同一个：**注入 / 破解微信客户端**。
4. **"发送"这一半，公开资料里基本没人做。** 读取是"解一个数据库"；
   发送是"让一个真人账户真的把话发出去"——**必须驱动真实的客户端**，
   而这条路要面对的是 UI 的不可靠性、目标会话的歧义、以及"发错了撤不回来"的后果。
   **wechat-mcp 补的就是这一段。**

### 用户真正怕的是什么：不是模型，是**发错人**

社区里做个人微信自动回复的人，事后总结出奇地一致：
**"最难的不是大模型，是稳定读到真实消息，以及确认该发给谁。"**
具体的坑很实在——群聊误触发、**把自己发出的消息当成入站，于是自问自答循环**、
窗口一变就定位不到。

所以我们在发送这条路上加的每一道校验，都是**对着这些坑来的**：
内容锚点 + 头部双印证 + 群成员昵称第三重印证 → 确认目标；
`local_id` 区分自己与他人；拿不准时**一个字都不输入**。

另一条同样一致的经验：**"越自动越危险，越可控越安全"**——
默认关闭、白名单、发送前校验对象、失败留痕。
这也正是我们把 **`dry_run=true` 设成默认值**的原因：
**它不是保守，是社区用代价换来的共识。**

> ⚠️ 发送这条路上还有**协议层面的风险**（《微信软件许可及服务协议》8.2.1.6 明确禁止
> 第三方工具自动化访问/读取/控制微信；封号风险客观存在）。详见
> [`README.md` 的「风险与合规」](README.md#风险与合规必读不埋末尾)——**那一节不长，但请务必读**。

### 为什么我们的版本策略和别人相反

别人是"支持越多版本越好"，我们是 **版本未经核验就拒答**。这不是保守，是**这个动作的性质决定的**：

> 读错了版本 → 你可能拿到**错位的、串会话的**聊天记录，而**你没有任何办法察觉**。
> 发错了版本 → 一条以你本人身份发出、**不可撤回**的消息。

**一个会"看起来正常工作但结果全错"的工具，比一个会报错的工具危险得多。**
所以宁可拒答。

### MCP 这个位置本身的风险，我们怎么处理

安全研究（ACM TOSEM、MCP 官方文档、多家安全厂商 2025–2026 年的报告）反复指出同一个问题：
**MCP server 以用户权限在本机运行，而"工具的名称和描述本身会被模型当指令读"**——
于是可以串成"摄入 → 采集 → 外泄"的链，且协议层**不提供运行时隔离**。

落到这套东西上，三条对应的做法：

| 风险 | 我们的做法 |
|---|---|
| 工具描述被当成指令 | 工具描述里**只写"能做什么、失败了怎么办"**，不藏"该做什么"的策略。**回不回、怎么回，由你接入的客户端决定**——MCP 不替你拿主意 |
| 采集 + 外泄串联 | 前端（读）和后端（发）**在同一套工具里但需要显式动作**：发消息**默认 `dry_run=true`**，必须你明说才真发 |
| 越权读取 | 只读**你自己的账号**；不碰微信的任何数据与组件；**零注入** |

## 七、为什么值得

| 别人怎么做 | 本方案 |
|---|---|
| 注入 DLL hook 微信客户端 | **零注入**：只读内存取密钥 + 窗口消息投递。客户端带 VMProtect + Detours，**不去碰它** |
| 把消息上传到某台服务器解 | **全本地**：密钥、解密、语音转写、图像解码**都不出这台机器** |
| 发消息前把微信抢到前台、模拟鼠标 | 走窗口消息投递：**不移动光标、不动剪贴板、不搬窗口、锁屏也能发**（唯一可感的副作用：投递字符的一瞬微信自顶前台约 0.1–0.3 秒，工具自动还回去） |
| 发完就当成功 | 发完**读库确认**；发之前 5 道校验，拿不准时**一个字都不输入** |
| 猜用户语气 | **实测数字**：3886 条样本算出的分层标点率 |
| 版本对不上就硬读 | **fail-closed**：版本未经核验直接拒答，不猜着读 |

## 八、它做不到什么

- **发不了微信语音消息**。微信语音是按住录音，**无法自动化**——只能把音频**当文件**发。
- **`reply_to` 需要微信窗口可见且在前台**（其余发送不需要）。
- **发出去就撤不回来**。以你本人身份发出，跟你自己手打的一样。
- **微信必须正在运行**。密钥只存在于运行中的进程内存里，退出了就读不了。
  **而且刚启动、还没打开过任何会话时可能取不到**——点开一个会话等几秒就好。
  （这不是玄学，是错误提示里写明的一条，不用你猜。）
- **版本对不上不猜着读**。本机微信 **4.1.15.13** 落在**已真机验证**的范围内，
  密钥扫描/解密/读取/发送今天全部实测通过。
  版本不在验证范围内时，**每一条工具结果都会挂一句"这版没验过，读到的内容可能是错的"**——
  不是只在 `check_env` 里说一次，因为 **Agent 不会每次先调它，用户更不会**，
  而这条信息**只在出错前有用**。
- **多数视频和图片本地没有**：没在微信里点开过的就不在磁盘上（实测 **48 条视频消息只有 8 条**能定位）。
  补的办法很简单——**在微信里点开一次**，之后再搜就有了。
- **`read_image` 可能给你的是缩略图**（本机实测 5.7 KB 那张就是这个），
  但**它一定会告诉你** `variant` 是什么，不会让你拿缩略图当原图。
- **一次发一条**。失败会在 `detail` 里说明卡在哪一道校验。
- ⚠️ 读出来的都是**别人的**聊天内容。只读、本地处理、不外传——这是这个工具存在的前提，
  不是它的一个功能。
