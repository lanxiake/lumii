# wechat-recall-mcp · 撤回防护

> 详细安装、守护管理与判定规则见
> [`../../apps/windows/resources/wechat-recall-mcp/README.md`](../../apps/windows/resources/wechat-recall-mcp/README.md)。
> 文中数字是 2026-10-14 在本机真机上跑这套 exe 的**原始输出**。

## 一句话

**对方撤回的那句话，替你留住——不是拦截，是事前留档。**

---

## 一、它解决什么问题

### 1. 微信撤回是**真的删**

这不是"打个标记隐藏起来"。实测 **114 条撤回通知**：**原消息的行被删掉了，或者被原地改写了**，
而且**撤回通知里根本不带被撤回消息的 id**。

这意味着任何"事后去库里翻那条被撤回的消息"的做法**在数据层面就是死路**——
不是"代码难写"，是**东西已经不在了**。

**这也是为什么这一类工具大多不靠谱**：它们号称能查撤回，实际上只能查到一个
孤零零的"对方撤回了一条消息"——**而你要的恰恰是那条消息本身**。

### 2. 唯一的出路：**在撤回发生之前就存下来**

wechat-recall-mcp 换了个思路：**事前留档**。

一个常驻守护持续把消息写进自己的库（**只写一次、永不覆盖**）。
撤回/删除发生后，拿归档与当前库按 `(talker, local_id)` 对差——
**原文、引用、图片和文件的元数据全都在**。

### 3. 所以"守护有没有在跑"是这个工具**唯一**的命门

守护在跑 → 之后的撤回都留得住。
守护没跑 → **那段时间的撤回永久查不到**，任何补救手段都没有。

这个工具的设计因此围绕一件事：**让守护别死，并且如果它真死了，如实告诉你死了多久。**

## 二、典型场景

### 场景 1：群里有人撤回，看他到底说了什么

```
你：XX群里最近有人撤回消息吗？
AI：（list_recalls(talker="XX群")）→ 时间 / 发送者 / 原文摘要
你：第二条到底是什么？
AI：（read_recall(talker="XX群", local_id=…)）→ 完整原文 + 附件元数据
```

注意 `read_recall` 是**按 `local_id` 取单条**，不是按时间模糊匹配——
**同一秒发多条也能分清**，不会给你拿错那一条。

### 场景 2：确认它没偷懒

```
你：守护在跑吗？有没有漏记的时段？
AI：（daemon_status() + archive_gap()）
```

**本机实测输出**：

| 字段 | 值 |
|---|---|
| 已归档 | **4713** 条 |
| 覆盖会话 | **71** 个 |
| 归档库体积 | **1,945,600 B（约 1.9 MB）** |
| 归档间隔 | **5 秒** |
| 缺口数 | **0** |
| `alive` / `running` / `autostart` | `false` / `false` / `false` |

**这个状态值得当例子讲**：`autostart: false` 说明**没装开机自启**——
也就是说，**下次重启后守护不会自己起来，那之后的撤回就抓不到了**。
`daemon_status` 把这件事**明说出来**，而不是让你以为"装了工具就有防护"。

### 场景 3：验证它真的在工作（不只是"没崩"）

"没报错"不等于"在干活"。**本机实测做了一次真对账**：
按工具的判据把归档库与实时库逐条比——

| 结果 | 条数 |
|---|---|
| **一致**（原文原封不动） | **4713** |
| **内容变了**（= 发生了撤回/改写） | **0** |
| **现库已无此行**（= 发生了删除） | **0** |

**4713 条一条不差**——说明守护确实在持续、正确地留档，
而且**这段观察期内确实没有任何人撤回**（两个 0 是真的 0，不是"查不出来"）。

**这就是这个工具的判据和"猜"的区别**：它能证明自己覆盖到了 4713 条，
而不是"大概在跑吧"。

### 场景 4：「我自己误删的消息还能找回来吗」

能——**只要守护当时在跑**。

守护存的是**原文留档**，删除和撤回走**同一套判定**：
删行记为 `deleted`，原地改写记为 `recalled`，内容变体对不上记为 `changed`。
所以"我自己手滑删了"和"对方撤回了"是同一件事的两个触发源。

### 场景 5：长期跑的成本心里有数

`daemon_status().db_bytes` 让你看到归档库涨得多快：
**实测 4713 条 ≈ 1.9 MB**，折算约 **每条 400 字节**。
按这个速率，10 万条约 42 MB——**体积不是问题，所以默认不修剪是对的**。

## 三、功能详解（4 个只读工具）

| 工具 | 做什么 | 返回什么 |
|---|---|---|
| `daemon_status()` | 守护在不在跑 | 归档条数 / 会话数 / 体积 / 最早·最新时间 / **缺口数** / 是否已自启 |
| `list_recalls(talker?, since?, until?, limit?)` | 被撤回/删除的消息 | 每条带**类型**（`deleted`/`recalled`/`changed`）/ 发送者 / 时间 / 原文摘要 |
| `read_recall(talker, local_id)` | 取**完整原文** | 全文 + 引用 + 附件元数据 |
| `archive_gap()` | 归档漏记的时段 | 缺口清单——**如实报告，不假装全覆盖** |

### 判定机制：为什么它不会误报

按 `(talker, local_id)` 比较**内容变体集合**：

- **撞号的情况**（不同消息用了同一个 `local_id`）→ **两侧一致 → 不误报**（有专门单测兜）；
- **原地改写**（`recalled`）→ 同一 `local_id` 的内容变了 → 记一条；
- **删行**（`deleted`）→ 归档里有、现库里没有 → 记一条。

**这套判定的价值在于"两个方向都成立"**：
只判"库里没了"会漏掉"被改写了"（微信撤回的一种实现），
只判"内容变了"会漏掉"整行被删"。**实测 114 条撤回通知里两种都有。**

### 守护的四条硬保证

1. **自愈**：崩溃后自己重启（退避 5s→300s 封顶）并记日志。
   它挂了 = 那段时间的撤回**永久查不到**，所以"不让它死"是硬要求，不是 nice-to-have。
2. **不双开**：再起一个会当场认出"已经有一个在跑"并自己退出——
   **两个一起写库会互相打架**，所以宁可拒绝启动。
3. **优雅停止**：`--stop` 发信号，守护**在收尾里记完停机时间才退**，不是杀进程。
   否则库里会出现一个无法解释的缺口。
4. **不假装全覆盖**：每拍都看"上一拍距今多久"，超时落一条 `gap`。
   **休眠不会让守护退出**（`time.sleep` 只是被挂起），所以开机时查一次是不够的——
   这正是"每 24 小时回头做一次全量对账"的原因：接住"落库晚但时间戳更老"的行。

## 四、怎么装怎么用

**这一件必须多装一步**：双击装完客户端注册之后，**还要把守护开起来**，否则什么都查不到。

```powershell
wechat-recall-mcp.exe --install-autostart   # 开机自启（一次即可）
wechat-recall-mcp.exe --status              # 随时看状态
```

第 1 条**不是可选项**。本机实测 `autostart: false` —— 装了不自启，
**下次重启后守护不会自己起来**，而"守护没跑的那段时间"是**永久损失**。

---

## 五、一轮完整回路

```
① --install-autostart            → 守护开机自启（越早越好）
② daemon_status()                → 确认 alive / 归档条数 / 缺口数
③ 守护持续留档（5 秒一拍，只写一次、永不覆盖）
④ 有人撤回
⑤ list_recalls(talker)           → 判定出来，带类型
⑥ read_recall(talker, local_id)  → 完整原文
```

第 ② 步要**看 `autostart` 和 `gaps` 两个字段**，不是只看 `alive`——
`alive: true` 但 `autostart: false` 意味着"现在好着，重启就断"。

## 七、官方规则，以及为什么"查撤回工具"大多不成立

### 微信自己怎么说

微信官方账号「微信派」给过明确口径：

| 消息类型 | 撤回时限 |
|---|---|
| 文字、语音、表情、图片、视频、链接、小程序卡片 | **2 分钟** |
| Word / Excel / PPT / PDF / MP3 / 压缩包等文件 | **3 小时** |

**为什么限时**？官方的解释里有一句很关键：

> 若撤回不限时，发送者就能随意篡改聊天记录（如借钱记录、工作安排、商务承诺等），
> **保障关键信息的法律效力**。

**这句话就是整个产品定位的说明书**：撤回的设计目的**不是**"让对方看不到"，
而是**给发送者一个有限的反悔窗口**。所以——

**微信明确不支持无痕撤回**（撤回后对方一定看到灰色提示），
原因是通信工具首要保障送达准确；而且系统级推送（如 iOS）会先把消息推到对方通知栏，
**微信也无权清除那一层记录**。

（2026-08 起有个小变化：你可以长按删除**自己界面里**的"你撤回了一条消息"，
但**对方界面的提示依然存在**——这更能说明"撤回 ≠ 抹除"。）

### 所以市面上"能查撤回"的工具是怎么回事

公开资料里对这类工具的说法很一致：**没有任何第三方工具获得过"查看他人撤回消息"的官方依据**，
**官方明确不支持无痕撤回**，声称能看的一律缺乏依据。

**这里的逻辑闭环是死的**：

> 你要看的那条消息，**在撤回那一刻就已经从库里被删掉或改写了**（实测 114 条撤回通知，
> 两种机制都存在）。**事后去库里翻**，翻的是一个**已经不含那条消息**的库。
> 无论工具写得多好，**它没有的东西它变不出来**。

**wechat-recall-mcp 不是那类工具。它不破解、不拦截、不挂钩子、也不声称能"看穿"什么。**
它做的是任何一个人手工也能做的事：

> **在撤回发生之前，自己抄一份。**

这是唯一在物理上成立的路径，也是它和"号称能查撤回"的分界线。
**判据很清楚**：能不能证明自己覆盖到了多少条？
本工具的答案是 `daemon_status()` 里的 **4713 条**，和一次**逐条比对后 4713 条一致**的对账。

### 「防撤回插件」是另一件事，而且代价很大

社区里更常见的是"防撤回**插件**"——它改的是**微信自己的行为**（把撤回动作拦下来）。
这跟本工具**完全是两回事**，而且有公开的代价记录：

| 做法 | 公开反馈 |
|---|---|
| 防撤回补丁（改客户端） | **"上午安装防撤回补丁，下午被强制下线，重新登录还要签『不使用插件』承诺书"** |
| 装"微商版微信"（含防撤回，约 38 元/月） | **不到 24 小时**收到官方警告；卖家以"老号基本不会封"为由拒绝退款 |

**所以这里要做一个明确的措辞切割**：

> **本工具不是"防撤回"。它不拦截、不改微信的行为、不挂钩子——它只是自己抄了一份。**
> 微信那边该撤回还是撤回，对方看到的提示也照旧。

这个切割不是文字游戏，它决定了两件事：
**① 风险落在哪**（改客户端 vs 只读旁路），**② 功能上会发生什么**（撤销不了对方的动作 vs 你手上多一份记录）。
把"撤回留档"讲成"防撤回"，等于替用户做了一个他没同意的风险选择。

### 判定机制，有第三方实测印证

我们自己的实测（114 条撤回通知）判定出**两种机制**：**删行**和**原地改写**。
社区里另一个独立项目（`wechatauto-replica`）做过同样的实测，结论一致：
**撤回是把原行原地改写，`local_id` 和 `create_time` 都保留着**。

两条独立测量得到同一个结论，这是我们对"两种机制都要判"有信心的原因——
**只判"库里没了"会漏掉一半**，而漏掉的那一半**恰好是能留住的**。

### 和"备份聊天记录"的区别

| 做法 | 撤回之后还能看到原文吗 |
|---|---|
| 微信自带的「聊天记录备份与迁移」 | ❌ 备份是**加密快照**，且**只能整体恢复回去**——恢复的是"当前库"，撤回已经生效 |
| 定期手工导出（wechat-export-mcp） | 取决于**你导出的那一份在撤回之前**——它没有守护，会漏掉两次导出之间的撤回 |
| **常驻守护事前留档** | ✅ 5 秒一拍，**只写一次、永不覆盖**，所以"撤回前的原文"一定留得住 |

**这三条是本工具存在的全部理由。**

## 八、为什么值得

| 别人怎么做 | 本方案 |
|---|---|
| 号称能查撤回，实际只能查到"对方撤回了一条消息" | **事前留档**——原文、引用、附件元数据都在 |
| 只处理"删行"一种机制 | **两种都判**（删行 `deleted` + 原地改写 `recalled`），因为实测两种都存在 |

| 假装全覆盖 | `archive_gap` **如实报缺口**；休眠、关机漏的补不回来就说补不回来 |
| 静默修剪旧数据控体积 | **默认永不删**。要控体积得自己加 `--retain-days N`，**代价明说** |

## 九、它做不到什么

- **守护启动之前的撤回，看不到**。这是**唯一"过了就没了"的地方**——
  所以第一件事是装自启，**越早越好**。本机实测 `autostart: false`，
  也就是说现在这个状态**将来是抓不到的**。
- **关机 / 休眠期间漏的补不回来**。只能如实报成 `gap`，**不能变出来**。
- **不能阻止撤回**，只能事后查看。
- **不备份被撤回的文件本体**——那是 wechat-export-mcp **文件面**（`archive_files`）的事。
- **归档库只增不减**：默认**永不删**。要控体积得自己给守护加 `--retain-days N`，
  代价是**那段之后发生的撤回就查不到了**——**这个取舍交给你，工具不替你修剪**
  （`daemon_status().db_bytes` 能看出它涨多快；实测 4713 条才 1.9 MB，速率上不急）。
- **它是"记录"不是"证据"**：归档库是你本机的一份 SQLite 文件，**你可以改它**。
  需要法律效力的场合，请自行做哈希固化或公证——工具不假装能替代那一步。
- **读不了别人的账号**，也不上网——**全部本地处理**。
- ⚠️ 归档的是**别人撤回的东西**。撤回本身就是对方的意愿表达，
  **怎么用这份归档由你决定，工具不替你判断正当性。**
