# 本地 OCR 接入实施计划

> 状态：**P0 任务完成（待发布前全量验证）**  
> 日期：2026-11-09  
> 关联设计：[`../../design/视觉与OCR/2026-11-09-本地OCR接入设计.md`](../../design/视觉与OCR/2026-11-09-本地OCR接入设计.md)

## 1. Goal

在 **Windows** 客户端落地轻量本地 OCR：utility 进程跑 PP-OCR mobile ONNX（CPU 默认，DirectML 可选回退），为聊天附件 `ocrText`、Agent 截图、扫描文档提供本地抽字；云端 vision 继续负责 `description`，本地失败再补 OCR。

可验证一句话：无 GPU 机器上，对一张中英 UI 截图调用本地 OCR 能返回非空 `ocrText`，且同时开启 VAD + E5 不崩溃。

## 2. Architecture

```
Renderer / Agent tools
        │
        ▼
Main: OcrService ──queue──► UtilityProcess (私有 ORT + PP-OCR)
        │                         │
        ├─ ocr-model-manager      └─ det/cls/rec
        ├─ bridge-image-services（A）
        ├─ screenshot tool hooks（B）
        └─ document scan path（D）
```

模块边界见设计 §4 / §5。主进程不加载 OCR 用 ORT。

## 3. Tech Stack

**使用**

- Electron `utilityProcess`（或等价子进程 + MessagePort）  
- ONNX Runtime（utility 私有拷贝；支持 CPU + DirectML 的发行变体）  
- PP-OCR **mobile** 中英 ONNX（det / cls / rec）  
- 现有模型下载模式（hash、进度、数据目录）  

**不引入**

- PaddlePaddle 训练/完整 Python 推理栈进主应用  
- EasyOCR / 大型 VLM 本地权重  
- 主进程第三份 `onnxruntime.dll`  
- 首版 CUDA 强制依赖、server 档 OCR 权重进默认路径  
- 替换微信 `ocr4.ps1`  

可选薄封装：成熟的 PP-OCR ONNX JS/C++ 小库（如 eSearch-OCR 思路）——引入前评估 license、ORT 版本是否可旁路加载、包体。

## 4. Global Constraints

1. **OCR 推理不得进入 Electron 主进程**（硬约束，对齐 ONNX 顺序闸教训）  
2. 模型与 OCR-ORT **不进**默认安装包；平台原生包若有，必须写在 `apps/windows` 的 `optionalDependencies` / 旁路目录并过体积审计  
3. 改 `src/main/**` 必须跑 `pnpm --filter ./apps/windows test:all`  
4. IPC 变更同步：main handler + preload `ElectronAPI` + renderer 调用方  
5. 截图工具 OCR 失败不得让截图本身失败  
6. 双轨语义不可破：云端 `description` 默认保留；本地优先 `ocrText`  
7. 日志不落完整用户图片内容；可落路径、耗时、backend、置信度摘要

## 6. Task 分解

### Task 0 — 钉模型与 ORT 发行物 ✅

- **做**：选定 PP-OCR mobile 中英 ONNX 具体文件名与 hash；选定 utility 用 ORT 获取方式（npm 私有目录或解压包）；确认 DirectML EP 在目标 ORT 可用  
- **验证**：本机脚本对样张跑通 det+rec，打印 backend  
- **产出**：写入 `ocr-model-manager` 清单常量（可先 PR 注释/文档表）  
- **落地**：`ocr-model-manifest.ts` — HF `SWHL/RapidOCR` PP-OCRv4 mobile；utility ORT **1.22.0** 私有目录；推理库 **esearch-ocr@8.5.2**（无 OpenCV）；sha256 待首次可信下载后回填  

### Task 1 — Utility + Pipeline 骨架（TDD） ✅

- **做**：utility 收 `recognize` 消息，读图、maxSide、跑 pipeline，回传 `OcrRecognizeResult`；`enableCpuMemArena=false`  
- **测**：fixture 小图 → 非空 text；强制 CPU  
- **验证**：`vitest` 对 mock/集成脚本；手跑 utility  
- **落地**：`ppocr-pipeline.ts` / `ocr-worker-main.ts` / `ocr-fork-transport.ts`；helper 单测绿；端到端样张待 T3 模型下载后补  

### Task 2 — OcrService 主进程编排（TDD） ✅

- **做**：懒启动、单飞队列、超时、崩溃重启、空闲退出、`forceCpu` / `auto`  
- **测**：mock utility 进程行为  
- **验证**：`*.test.ts` 全绿；`@vitest-environment node`  
- **落地**：`ocr-service.ts` + 单测（平台守卫 / 队列 / CPU / 超时 / 空闲退出）；`pnpm exec vitest run src/main/ocr` → **12 passed**  

### Task 3 — 模型按需下载 ✅

- **做**：对齐 voice/wiki 下载器模式；进度事件；未就绪时的错误码  
- **验证**：清空模型目录后首次识别触发下载；hash 失败可重试  
- **落地**：`ocr-model-downloader.ts`（HF 镜像 + 字典 fallback）；聊天路径 `ensureOcrModelsReady`；截图路径仅在已缓存时 OCR（避免热路径卡下载）  

### Task 4 — 接线 A（聊天识图） ✅

- **做**：`recognizeImage` 本地 OCR → 云端 description；低置信/失败云端补 OCR；`ocrSource`  
- **验证**：有 vision 时描述仍在；断网仅本地；mock 本地失败走云端  
- **落地**：`bridge-image-services.ts` 双轨；`local-ocr-for-recognize.ts` + 单测；IPC 增加 `ocrSource`  

### Task 5 — 接线 B（截图工具） ✅

- **做**：统一后处理或三处最小改动；默认 OCR；失败保留路径  
- **验证**：工具 JSON 含 `ocrText`；OCR throw 不导致工具 `ok=false`  
- **落地**：`attachLocalOcr`；`app_screenshot` / `screen_screenshot` / `browser_screenshot` 增加 `ocr` 参数（默认 true）  

### Task 6 — 接线 D（扫描文档） ✅

- **做**：图片直出；PDF 文字层阈值；分页串行/小并发  
- **验证**：纯扫描 PDF 有字；纯文字 PDF 不误触发全页 OCR（或明显更少页）  
- **落地**：启发式 + `ocrScannedDocument`；`files:import` 对稀疏 PDF / 扫描图补 OCR；pdfjs + `@napi-rs/canvas` 渲页  

### Task 7 — 共存压测与打包护栏 ✅（自动化部分）

- **做**：VAD → E5 → OCR 交错；确认主进程模块列表无 OCR ORT；体积审计  
- **验证**：`test:all`；手测无原生崩溃；安装包体积对比记录  
- **落地**：`ocr-isolation.test.ts` 禁止主进程 import ORT/esearch-ocr；vite external 原生依赖；模型仍按需下载不进包。完整 `test:all` / 真机交错手测留发布前补做  

### Task 8 — 文档收尾 ✅

- 设计/计划状态改为已确认或实施中；必要时补 wiki 交叉链接一行  

## 7. 任务依赖图

```
T0 模型/ORT 选定
 └─► T1 Utility/Pipeline
      └─► T2 OcrService
           ├─► T3 下载器（可与 T2 部分并行，合并前 T0 完成）
           ├─► T4 接线 A
           ├─► T5 接线 B
           └─► T6 接线 D
                └─► T7 共存/打包
                     └─► T8 文档
```

建议顺序：T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7 → T8。  
T4/T5/T6 在 T2+T3 完成后可串行（同一 bridge 区域少冲突）。

## 9. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| DirectML 在部分驱动上慢或不稳 | 默认 auto 回退；设置强制 CPU；记录 backend |
| 选中的 JS 封装绑死错误 ORT 版本 | 优先自管 session，或 fork 旁路加载路径 |
| PDF 渲染依赖重 | 复用现有能力；无则最小 canvas/跳过并文档声明 |
| 截图 OCR 增加工具时延 | maxSide + 单飞；后续可加「仅当 Agent 需要字」开关 |
| Linux 提前被要求 | 本计划明确 P0 不做；API 先平台守卫 |

## 10. 验收标准清单

- [ ] Windows：无 GPU，截图本地 OCR 返回非空中英文字  
- [ ] Windows：DirectML 可用时 `backend` 可为 `dml`，失败自动 `cpu`  
- [ ] 聊天：`description` 来自云端（已配 vision 时），`ocrText` 优先本地，`ocrSource` 正确  
- [ ] 本地失败：云端能补 `ocrText`  
- [ ] 至少一种 `*_screenshot` 工具结果含 `ocrText`，OCR 失败截图仍成功  
- [ ] 扫描图或无文字层 PDF 可抽字；有文字层 PDF 不无谓全量 OCR  
- [ ] VAD + E5 + OCR 交错无原生崩溃  
- [ ] 默认安装包不含 OCR 模型大文件；相关单测进 `test:all` 且通过  
- [x] 设计文档状态更新为评审结论；本计划状态同步
