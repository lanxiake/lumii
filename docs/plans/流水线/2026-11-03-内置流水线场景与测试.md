## 2. 交付了什么

### 2.1 引擎：运行时变量（`{{input.x}}`）

**问题**：`pipeline_run` 原来只收 `{id, mode, resumeRunId}`，spec 里没有任何地方放"这次评测哪个仓库"。于是内置一条 spec = 内置一个模板，用户必须手工改文件。实测代价：`web-clone` 7 次运行里有一次是 `Page.navigate: Cannot navigate to invalid URL`（`__TARGET_URL__` 没换）。

**做法**（最小形态，不引入声明块）：

- `{{input.repoUrl}}` 在 `spec.ts` 里被识别为**变量**而不是步骤引用（向后引用校验里跳过 `input`）；
- 变量名从引用里**自动推导**（`collectInputNames()`），作者写一次引用就算声明；
- 值从 `{workspace}/pipelines/<id>/inputs.json` 读，`pipeline_run` 的 `inputs` 参数可覆盖；
- **没传变量不是静默替换成空串**，而是在用到它的那一步失败并说清原因——否则会拿去 clone 一个空地址，失败点被推后十几步。

改动文件：`types.ts`（`PipelineInput`/`inputTemplate`/`RunOptions.inputs`）、`spec.ts`（`collectInputNames` + 引用校验豁免）、`runner.ts`（`resolveParams` 支持 input）、`store.ts`（`readInputsFile`/`missingInputs`）、`runtime.ts`、`tools.ts`（`pipeline_run.inputs`、`pipeline_inspect.missingInputs`）。

### 2.2 引擎：播种改为基线哈希（原来"已存在就跳过"）

跳过会让**修好的 spec 永远到不了老用户**。实测已经发生过两次：占位符被用户手工替换后描述变成自相矛盾的话；引入 `{{input}}` 后老工作区永远停在旧形态。

改与 `bundled-skills-seeder` 同一套判据：

- 没有基线 → 不动（分不清"用户改过"与"只是旧"）
- 基线 == 上次种下的内容 → 用新版覆盖
- 基线 != 上次种下的 → 用户改过 → 保留

`runs/` 与 `inputs.json` 不算进"改没改过"，升级时也不覆盖用户填的 `inputs.json`。

### 2.3 测试：把假白名单换成真注册

原来的 `KNOWN_TOOLS` 是**手写白名单**——工具名写错或根本没注册，只要白名单里有就过。这是假门禁。

现在 `bundled-specs.test.ts` 真的建一个 `ToolRegistry`：内置工具（`ALL_BUILT_IN_TOOL_CONFIGS`）+ app/browser/screen-record/reverse 的真实注册函数。然后跑五道：

| 守卫 | 抓什么 | 实测有效性 |
|---|---|---|
| 工具名真实存在 | 拼错、未注册 | 注入 `app_goto_typo` → 红 ✅ |
| 必填参数齐全 | 用工具自己的 TypeBox `required` 对账 | 注入 `list_dir` 缺 `path` → 红 ✅ |
| 空跑全程 | 引用链断没断、变量漏没漏 | — |
| 不许 `cmd \| tail` 判成败 | 管道让 `$?` 变成 tail 的 | 注入 → 红 ✅ |
| 不许 `[ ] && echo` 作循环体 | 最后一项不成立时 for 返回 1 | 注入 → 红 ✅ |

后两条是**这轮真机踩出来的**（见 §3），不是凭想象加的。

## 4. 真机抓到的缺陷

| # | 缺陷 | 为什么静态验不出 |
|---|---|---|
| R1 | `app_goto` 的白名单不认 `plugin:*`，`plugin:pipeline` 返回 `{"ok":false,"error":"usage"}`，整条录制前 3 步全绿却在第 4 步失败 | 侧栏点得到，说明不是"不支持"；只有真跑才暴露校验没跟上 |
| R2 | `for f in ...; do [ -f "$f" ] && echo ...; done` 最后一项不存在时整个 for 返回 1，后面的 `&&` 链全断 | shell 语义，单测跑不到 |
| R3 | `git clone ... \| tail -3` 的退出码是 `tail` 的，clone 失败会被报成成功 | 同上；`deps`/`build`/`test` 三步都有这个坑，而"测试通过率"正是核心产出 |
| R4 | `find -size +10k` 在 **Git Bash 下按 1024 字节块向上取整**算，9120B 的文件被判成"小于 10k" | 跨平台语义差异 |
| R5 | **流水线步骤的超时被 bash 自动续期静默突破**：spec 写 `timeoutMs: 540000`，实际跑 1095866ms | 现象像「杀不掉子进程」，实际是根本没超时——续期问了嵌套 LLM 并把 deadline 往后推，返回与 journal 全无痕迹 |

R1–R4 都已修并加了守卫（R2/R3 进了 harness，R4 进了 `check-assets.test.ts`）。
**R5 已修**：`pipelineStepToolContext()` 给流水线步骤的工具上下文摘掉 `callLLM`，续期分支直接返回 `extendMs: 0`，原 deadline 的 killTimer 照常生效。`open-source-eval` 的 test 步另外用 `timeout 480` 兜一层，把「跑不完」变成可断言的结论。

## 6. 续修（同日后续）

上一轮留下四条，逐条处理后的结果：

| # | 项 | 结论 |
|---|---|---|
| R5 | bash 超时"杀不掉子进程" | **原判断是错的**。查日志发现是 bash 在截止前 60s 问了嵌套 LLM「要不要续期」，答 `renew:true, extendMs:300000` 把 deadline 往后推——根本没超时。现象看起来像"挂住"，实际是**spec 声明的时限被静默突破**。已修：流水线步骤的工具上下文摘掉 `callLLM`（`pipelineStepToolContext`），续期分支直接返回 `extendMs: 0` |
| L1 | 生图 `fetch` 不走代理 | 已修：`resolveLocalProxyDispatcher()` 给任意请求要一个自证过的本机代理出口；生图客户端直连失败时降级重试。真机验证提交+轮询均 200，产出 102K JPG |
| 旧三条的失败点 | `directory ... could not conflict`（web-clone/reverse-then-clone）、`无法解析发起流水线的 Agent 实例`（旧 journal） | **成因已定位**：前者是 scaffold 目录上次跑残留（scaffold 步已用 `rm -rf <slug>-scaffold` + `mkdir -p` 规避，但产物目录本身不清理）；后者是 agent 步经**恢复的旧 run** 触发时拿不到父实例。当前从对话发起的 run 不受影响（本轮 all 真机跑都没再出现） |
| content-to-assets 真机 | 生图恢复后暴露两个新问题 | ① illustrations 步 15 轮预算不够（每张图要提交+轮询 2-4 轮）→ 提到 40；② **research agent 步 `ok:true` 却没写文件**（只跑了 5 轮，输出一句"我改为抓取…"就结束）→ 加 `research-exists` 判据步 + 提示词改为"每条立刻追加" |

### 这一轮最值得记住的一条

**agent 步的 `ok` 只代表"这一轮跑完了"，不代表"活干完了"。**

现场：research 步 `ok:true, ms:426457, turnsUsed:5`，输出一句"我改为抓取 Stack Overflow 开发者调查…"，而 `research.md` 根本没落盘。下游 draft 步拿不到底稿、拒绝脑补（**行为正确**，它明确说"不能靠脑补糊过去"），最后由 `body-exists` 判据步拦住。

⇒ 凡是有产物的 agent 步，**后面必须跟一个判据步**。这与 `report-exists` / `body-exists` 同一条理由，只是上一轮只在工具步后面加了，没推广到 agent 步。

### 未完成

`content-to-assets` 的端到端真机验收**没跑完**：最后一次尝试时外部模型端点故障（`Stream ended without finish_reason`，`provider test` 30s 超时），不是流水线问题。恢复后需要重跑一次确认 research-exists → illustrations(maxTurns 40) → cover → verify-assets 这条链。

### R6：同一条 run 里第二个 agent 步解析不到父实例（2026-11-02 真机）

`web-clone` run `20261102-101043-jh31xq` 的 journal：

```
7  brief   agent  ok    232927ms
8  scaffold bash  ok    104101ms
9  export  file_write ok
10 build   agent  FAIL  811ms  「无法解析发起流水线的 Agent 实例」
```

同一个 run、同一次 `pipeline_run` 调用。根因：`currentToolExecutorInstanceId` 是**全局单值**，
子 Agent 的每个工具调用结束都会经 `toolLifecycle.afterActualToolExecute` 写回自己的栈顶；
子 Agent 跑完栈空了，写回 `undefined` —— 而流水线的父工具调用还在进行中。
所以第一次 agent 步能跑，之后永远解析不到。

修法：`pipeline_run` 是递归深度不变的单个长调用，父实例在整条 run 内是常量。
首次解析到就缓存（`pipelineParentInstanceId`），run 结束在 `finally` 里清掉，
避免下一条流水线沿用旧会话的归属。

> 这也是**为什么"旧三条失败率高"不能只看错误文案**：`web-clone` 2/7 里有一次是
> placeholder 没换、一次是 scaffold 目录冲突、一次是这条父实例丢失，三种完全不同的成因。

## 7. content-to-assets 端到端（2026-11-03 18:47，run `20261103-184647-225ziv`）

八步里前八步全过，只有最后的规格判据按**真实情况**判失败：

```
0 init            bash    830ms
1 gather          bash  22225ms
2 research        agent 16636ms
3 research-exists bash    902ms
4 draft           agent 22838ms
5 body-exists     bash    673ms
6 illustrations   agent 121849ms   ← 3 张图全部生成并搬对目录
7 cover           agent  54598ms
8 verify-assets   bash    FAIL  IMAGES=4 TOTAL=4, COVER=cover.jpg 1024x1024
```

### 判定：这是真结论，不是缺陷

`image_generate` **不支持指定宽高**（传 `width`/`height` 会 400，服务端 `imageSize` 字段歧义），
只能出服务商默认比例。3:4 是小红书的真实展示比例，所以判据**不放宽**——尺寸不对的封面
发出去就是会被平台裁掉标题。判错里给了可操作提示：发布前用任意图片工具裁一次。

### 这一轮真机修掉的四处

| 现象 | 根因 | 修法 |
|---|---|---|
| research 步 426s/554s 都没写出底稿 | 步骤被设计成**开放式外网调研**，agent 一直在换站点重试 | 拆成 `gather`（固定 4 个 RSS 源 + 代理回退，22s 拿全）+ `research`（只读底稿提炼，17s） |
| 3/3 成功但 `IMAGES=0` | `image_generate` 只收 filename，落点是 `outputs/<当天日期>/` | 提示词要求生成后立刻 `cp` 进目标目录 |
| 封面尺寸报 `unknown` | 脚本只认 PNG，而生图默认出 JPG | 补 JPEG 的 SOF 段解析 |
| 底稿 2 条被判死 | 判据卡 ≥3 条，但底稿有多少相关内容取决于当天 RSS | 只卡 ≥1 条；提示词已要求"有几条写几条" |

### 产出质量

`research.md` 每条要点都带信源、URL 与日期，并**主动报告信源本身的问题**：
阮一峰源返回 Cloudflare 拦截页、HN 源为空、IT之家源中途截断、美团那条只有标题不足以支撑
——这些如实写进 UNRESOLVED，没有拿别的条目凑数。`note.md` 正文两条事实都能在
`research.md` 找到依据。

## 8. 改用自然语言验收（2026-11-03 晚）

前面的真机验证全是「调用 pipeline_run，参数 id=xxx」这种指令式说法——那是测工具，
不是测**用户能不能自然用起来**。改按真实用户的口吻重测，立刻暴露出一个纯产品问题。

### 8.1 `settings-tour` 配不上"走一遍设置几个主要页面"

输入：「帮我录一段操作教程，把设置里几个主要页面走一遍，配上字幕导出成视频」

Agent 的行为**完全正确**：inspector → rehearsal → 然后**主动放弃流水线**改为手工录制，理由写在回复里：

> `settings-tour` 只跑 5 步，路径写死……设置页有 14 个分区……
> 当前流水线产物只有 5.9 秒、每页停约 1 秒，内容基本看不清，不构成教程。
> 我重录一版：每页停留 3 秒、覆盖 6 个主要分区，再配字幕和旁白。

它说得对。原来 5 步里只有 2 个设置分区（modelConfig / channels），`holdMs` 1200
在烧字幕的成片里几乎看不清——**内置位跑 0 次不是没人需要教程，是这条做得不像教程**。

改：8 步覆盖 6 个分区（通用 / 模型配置 / 渠道 / 语音 / 用量），每页 2.8–3s，
旁白逐页交代"这页能干什么"。改完再问同一个需求：

```
status ok  mode record
artifact { durationMs: 24173, mp4Path: …194901.mp4, burned: true, cueCount: 8 }
8 步全过，cueCount 8 == 旁白步数 8
分类切换确认到位：general → modelConfig → voice → usage
```

### 8.2 一条新的静态守卫

`app_goto` 的 `view` / `category` 是**取值域**问题，harness 只查必填参数、看不出来，
只有真机跑到那一步才炸（`plugin:pipeline` 就是这么失败的）。新增守卫：
**从实现文件 `goto.ts` 里读白名单**（不在测试里再抄一份，抄一份必然漂移），
逐条比对 spec 的 `view` / `category`。注入一个不存在的 category 验证过会红。

### 8.3 旧三条的真机结果

| 流水线 | 结果 |
|---|---|

## 9. 图卡方案修正 + 一个没能解决的问题

### 9.1 小红书图不该用 image_generate（已修）

真机对照发现旧技能产出的 6 张图**全是 1080×1440（3:4）**，而我的流水线走 `image_generate`
只能出 1:1。根因是旧技能用 **HTML 卡片 + 浏览器截图**（`@page size: 1080px 1440px`），
不是 AI 生图。

`content-to-assets` 改成同一路线：

- 新增 `render-cards.cjs`：把 note.md 渲染成 1080×1440 的 HTML 卡片，
  支持 `?only=card-N` 单卡模式；
- `illustrations` / `cover` 两步（生图）替换为 `render-cards`(bash) + `shoot-cards`(agent)；
- 判据的期望尺寸从 `768x1024` 改成 `1080x1440`。

**为什么单卡模式是必需的**：`browser_screenshot` 只收 `fullPage`，**不支持裁剪**。
所以用「`browser_set_device(1080,1440)` 视口 + `?only=card-N` 只渲染一张」达到
一卡一屏的效果，比事后裁剪稳，也不用引入图片库。

### 9.2 没能解决：模型仍然选择技能而不是流水线

按用户要求改用自然语言（「帮我做一篇小红书笔记……做完我直接发」）测了五次，**五次都没走
`content-to-assets`**。试过的办法：

| 尝试 | 结果 |
|---|---|
| 提示词加「流水线优先于技能」 | 模型在思考里复述了这句话，然后仍选技能 |
| 技能正文顶部加「止于成品时优先用流水线」 | 模型读到了（回复里引用了原文），仍自己手工做 |
| 移走已有成品，逼它必须产出 | 仍手工做（用 bash + browser 自己拼） |

它给出的理由都成立：发现已有成品 → 不重复造轮子；手工做更灵活。

**结论：这不是加一句提示词能解决的**，是流水线与技能的**边界没划清**——两者描述的
是同一件事，模型每次都要临场判断「这个算不算命中」。真正要改的是产品形态
（比如技能被流水线吸收、或流水线作为技能的唯一推荐入口），超出了本轮范围。
**如实记在这里，不假装解决了。**
