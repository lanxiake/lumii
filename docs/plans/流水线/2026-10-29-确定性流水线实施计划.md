## 1. Goal

一条**可枚举步骤**的自动化，由代码执行一份 JSON spec：运行态 LLM 往返为 0，每步落 journal，失败即停并报 `{failedAt, expected, observed}`，录制的字幕与操作时间**同源**。

可验证判据：同一 spec 连跑 3 次，步数与每步 `observed` 一致；`pipeline_run` 一次工具调用跑完全程（不撞 `maxTurns`）。

---

## 2. Architecture

```
{workspace}/pipelines/<id>/spec.json      ← 数据（人/Agent 写，随 git + 云同步）
{workspace}/pipelines/runs/<runId>/       ← journal（VCS 忽略，本机）

pipeline 插件（apps/windows/src/plugins/builtin/pipeline/）
  ├─ spec.ts     加载 + 三道校验（工具名存在 / 引用向后 / 无环）
  ├─ runner.ts   主循环：run → mark → hold → assert → journal
  ├─ journal.ts  append / 读回 / resume 跳过集 / specHash
  ├─ store.ts    目录扫描、run 目录管理
  ├─ tools.ts    pipeline_run / pipeline_list / pipeline_inspect
  ├─ ipc.ts      给 UI 的 IPC 表
  └─ renderer.tsx  app.nav + app.view + registerTimelineCard

依赖注入边界：
  runner 只认 { callTool, screenRecord, readViewState, clock } 四个接口，
  由 index.ts 从 S.agentRuntime / S.screenRecord 现取后填入 → 单测零 Electron。
```

**模块边界（硬）**：`runner.ts` 不 import 任何 `apps/windows/src/main/**`，只用本目录内的类型与注入接口。这条保证它能在 `@vitest-environment node` 下裸跑。

## 3. Tech Stack

**用**：TypeScript、Node `fs`、`node:crypto`（specHash）、Electron 主进程、Vitest、现有 `ToolRegistry` / `ScreenRecordService` / `PluginHost`。

**明确不引入**：

| 不引入 | 理由 |
|---|---|
| 任何工作流引擎（Temporal / LangGraph / Inngest） | 本机单进程，拿不到进程内的 `ToolExecutionContext`；持久化只到 journal 这一层 |
| 新 DSL / 编译步骤 | 用 JSON，键名照抄已投产的 `TutorialNavSpec` |
| YAML 解析库 | 仓库无 yaml 依赖；JSON 足够，且 Agent 写 JSON 更不易错 |
| 新 sqlite 表 | 引擎是可选插件，不给核心 `SCHEMA_VERSION`（现 54）加表 |
| 新的浏览器/界面自动化依赖 | 复用 `app-ui-control` 与 `lumii-ui` |

## 4. Global Constraints

1. **不改公共 API**：`ScreenRecordService`、`NarrateService`、`AppUiController`、`ToolRunner` 的签名一律不动。
2. **不绕过权限闸门**：执行器不得直接 `toolRegistry.get(n).execute()`（那只拿到未包 hooks 的裸工具，见设计 §1.2(f)）。统一走注入的 `callTool`，由宿主侧实现审批（设计 §7.1）。
3. **执行器不拥有时钟**：`atMs` 一律向 `screenRecord.mark()` 要，执行器自己不算时间。
4. **加载期拒绝优于运行期失败**：工具名不存在、前向引用、循环引用，在 `spec.ts` 就拒，不允许跑到第 7 步才炸。
5. **IPC 三处同步**：新增任何通道必须同时改 main handler / preload `ElectronAPI` / renderer 调用方（`docs/wiki/05-implementation/03-IPC跨层开发指南.md` 总纲第 5 条），缺一处视为未完成。
6. **守卫不可红**：`pnpm check:wiring` 新增项为 0；`pnpm check:large-files` 不新增超限文件。
7. **TDD**：§6 标 `[TDD]` 的 Task 必须先写失败测试；`runner.ts` / `spec.ts` / `journal.ts` 的用例清单见各 Task，**全部为绿**才算完成。
8. **类型检查独立**：Vitest 不做类型检查，每个 Task 结束必须跑 `tsc --noEmit`。

**验证命令（统一）**

```bash
# 单步快跑（TDD 循环内）
cd apps/windows && npx vitest run src/plugins/builtin/pipeline
cd apps/windows && npx tsc --noEmit

# 每个 Task 收尾必须跑（AGENTS.md 第 6 条：动过 src/main/** 就要全量）
pnpm --filter ./apps/windows test:all
pnpm typecheck
pnpm check:wiring
```

> 注意：`pnpm --filter ./apps/windows test` 只覆盖 `src/test/`，**全绿是假象**——本功能的测试全部在 `src/plugins/` 下，必须用 `test:all`。

### Task 1 — `types.ts` + `spec.ts` 校验 `[TDD]`

**Files**
- New `apps/windows/src/plugins/builtin/pipeline/types.ts`
- New `.../pipeline/spec.ts`
- New `.../pipeline/spec.test.ts`

**先写失败测试，覆盖 8 条**

| 用例 | 期望 |
|---|---|
| 未知工具名 | 拒，错误含 `unknown tool: <n>` 与该 step id |
| 前向引用 `{{later.path}}` | 拒 |
| 循环引用 A→B→A | 拒 |
| `steps` 为空 | 拒 |
| `id` 缺失 / 重复 | 拒 |
| 缺 `id` 的 `postCleanup` | 拒 |
| 合法 spec | 返回 `{spec, specHash}`，hash 对同内容稳定、改一字节即变 |
| 同一 spec 两次加载 | `specHash` 相等（证明归一化不含时间戳） |

**关键实现点**

- 校验签名是 `validateSpec(raw: unknown, knownTools: ReadonlySet<string>): { ok: true; spec; specHash } | { ok: false; errors: string[] }` —— **一次报全部错误**，不要只报第一条（用户改 spec 时最烦的是挤牙膏）。
- `specHash` = `sha256` of 归一化 JSON（键排序 + 去空白），不含任何运行时字段。
- 引用解析器支持 `{{stepId.a.b[0].c}}`，只需解析出 `stepId` 与"是否向后"；路径本身运行期再解析。

**验证**

```bash

**Files**
- New `.../pipeline/journal.ts` / `journal.test.ts`

**先写失败测试，覆盖 6 条**

| 用例 | 期望 |
|---|---|
| append 3 行后读回 | 顺序一致、字段完整 |
| 文件末行被截断（半行 JSON） | 读回跳过并计数 `corrupt: 1`，不抛 |
| resume 跳过集 | 只含 `ok === true` 的 step id |
| `specHash` 与 meta 不符 | `{ ok:false, reason:'spec_changed' }` |
| 并发 append（同进程串行队列） | 不串行化写入 |
| 空目录 | 返回空 journal，不抛 |

**关键实现点**

- 写入用 `fs.appendFileSync`（同步、原子追加足够），**不用流**：run 目录生命周期短，流要处理 close/error，收益为零。
- 每行写完立刻 `fsync`？**不做**——崩溃丢失最后一行已被"半行容忍"覆盖，而每步 fsync 在 Windows 上要 5~10ms，直接吃掉 §9.3 的 20ms 预算。

### Task 3 — `runner.ts` 主循环 `[TDD]`（本计划最重的 Task）

**Files**
- New `.../pipeline/runner.ts` / `runner.test.ts`

**注入接口（写死，单测只 mock 这四个）**

```ts
export interface RunnerDeps {
  callTool(name: string, params: Record<string, unknown>): Promise<{ ok: boolean; data?: unknown; error?: string }>
  screenRecord: { start(p): Promise<{ok:boolean; error?:string}>; stop(): Promise<{ok:boolean; data?:unknown}>
                  mark(p:{label:string}): Promise<{ok:boolean; data?:{atMs:number}}> } | null
  readViewState(): Promise<{ view: string | null; hub?: { open: boolean; tab?: string; category?: string } }>
  now(): number
}
```

**先写失败测试，覆盖 14 条**

| 用例 | 期望 |
|---|---|
| 3 步全成功 | journal 3 行全 `ok`，按序 |
| 第 2 步工具返回 `ok:false` | 停在第 2 步，第 3 步不执行 |
| 第 2 步断言失败 | 返回 `{failedAt:{i,id}, expected, observed}` |
| `holdMs` | `sleep` 被调用对应毫秒（注入 fake clock） |
| rehearsal：`needsPermission` 工具 | 不调用 `callTool`，journal 记 `skipped:'rehearsal'` |
| rehearsal：不 start 录制 | `screenRecord.start` 未被调用 |
| rehearsal：断言仍执行 | 断言失败 → 仍然 fail |
| `record.enabled` 而 `start` 失败 | 整条拒绝，step 一个都不跑 |
| `record.enabled` 成功路径 | 每个有 narration 的 step 调一次 `mark`，参数是 `step.narration` |
| 无 narration 的 step | 不调 `mark` |
| `postCleanup` 在失败时 | 仍执行，异常不抛出，只记日志 |
| `preconditions` 不满足 | 停在 precondition，**不 start 录制** |
| `{{prev.path}}` 取值 | 传给下一步的参数是解析后的值 |
| 引用路径解析失败 | 该步判失败，报 `bad_reference` |

**关键实现点**

- 步序：`preconditions → (record.start) → steps → (record.stop → narrate)`，`postCleanup` 在 `stop` **之前**（否则清理动作会录进成片——**这条容易写反**）。
- `mark` 必须在 `callTool` 返回**之后**、`hold` 之前。
- 断言失败也算 step 失败，写同一套 `{error, expected, observed}`。
- 任何异常 → catch → 变 step 失败（不让异常逃逸成工具级 `isError`，否则模型只看到一句"工具炸了"）。

**验证**

```bash
cd apps/windows && npx vitest run src/plugins/builtin/pipeline/runner.test.ts
```

## 9. 风险与缓解

| 风险 | 预兆 | 缓解 |
|---|---|---|
| `runner.ts` 依赖注入漏了某个 Electron 全局 | 单测起不来 / 需 `jsdom` | 注入接口只四个；`runner.ts` 禁止 import `main/**` |
| spec 里的工具名随插件启停变化 | 加载时才炸 | 加载期用 `toolRegistry` 快照校验；若引擎插件停用，`pipeline_run` 本来就不存在 |
| rehearsal 造"假返回"喂 `{{}}` 引用不准 | 第二步取到空值 | 假返回 = 工具 `parameters` schema 的字段全填 `null`；引用解析失败判该步失败而非静默 `undefined` |
| 长流水线撞 `maxTurns` | —— | 不适用：`pipeline_run` 是**一次**工具调用；`maxTurns` 计的是模型往返 |
| 录制中 `mark` 返回 `not_recording` | 前期调试常见 | 该步判失败并带 hint「先确认 record.enabled 与 start 成功」 |
| 前端动了核心页面 | 守卫 B4 红 | 只走槽位；`pnpm check:wiring` 每次跑 |
| 云同步镜像误删 | `runs/` 被同步 | `shouldSkipFile` 排除；测试用例覆盖"源有 dst 无 → 删；源无 runs → 不动" |
| 只有一条流水线能跑 | —— | Task 11 强制两条；这是 M3 的硬门 |

## 10. 验收标准

**引擎**

- [ ] 未知工具名 / 前向引用 / 循环引用 / 空 steps，**加载期**全部拒，且一次报全部错误
- [ ] 同 spec 连跑 3 次，步数与每步 `observed` 完全一致
- [ ] 失败返回 `{failedAt:{i,id}, expected, observed, journalPath}`
- [ ] `postCleanup` 在任何失败路径下都执行，且异常不外抛
- [ ] rehearsal 不调用 `needsPermission` 工具、不 start 录制、断言仍执行
- [ ] resume 在 `specHash` 变化时拒绝，理由可读

**录制**

- [ ] 有 narration 的 step 恰好一次 mark；无 narration 的零次
- [ ] 产物 `dubbed === true && burned === true`
- [ ] `cueCount === narrationCount`
- [ ] SRT 首条 `startMs` 与该步 journal 的 `markAtMs` 差值 < 50ms

**插件形态**

- [ ] 禁用后 `pipeline_*` 工具消失、侧栏条目消失、spec 文件与 journal 保留
- [ ] 启用即时生效，无需重启
- [ ] 运行中禁用 → 先 stop，journal 标 `aborted: 'extension_disabled'`
- [ ] 打包产物含 `resources/bundled-pipelines/`，且不在 `app.asar` 内（`npx asar list` 查不到它）

**数据**

- [ ] 新建工作区 `.gitignore` 含 `pipelines/**/runs/`
- [ ] 老工作区启动后自动追加该行
- [ ] `runs/` 不出现在工作区 VCS 的任何 commit 里
- [ ] 设备 A 建 spec → 同步 → 设备 B 可见；`runs/` 不同步

**前端**
