## 3. 真机与 code-review 抓到的关键缺陷

### 3.1 code-review 的 9 条（4 HIGH / 5 MEDIUM，全部属实）
见提交 `836580bb`。最重的四条：
1. 录屏 `start` 传 `sourceHint` 而契约要 `sourceId` → **record 一步都不会跑**
2. 种子 precondition 缺必填参数 → **那条 spec 永远跑不起来**
3. `cancel()` 只 abort 了 controller，signal 从没透传 → **取消后仍跑完全部**
4. 云同步 `shouldSkipFile` 用 `path.sep` 切而路径已归一化成 `/` → **runs/ 没被跳过**

### 3.2 真机新增发现
| # | 缺陷 | 为什么单测看不见 |
|---|---|---|
| R1 | `stop` 裸透传（`path` 在顶层，runner 读 `data.path`） | 录制真跑了、markAtMs 有值、5 步全绿，**只有 artifact 静默为空** |
| R2 | CSS 令牌名全写错（`--mt-text-primary` 等不存在） | CSS 变量不存在**不报错**，只是静默无样式 |
| R3 | 进度事件订阅到空气（`forwardIpcEvent` 只走 `agent-runtime:event`） | 两端各自「看起来对」，没人用真实事件验 |
| R4 | 种子断言猜错视图模型 + 依赖被 rehearsal 跳过的写操作 | 只有真跑才发现 |

> 共同点：**「能编译、能跑、测试绿」不等于「对」**。R1–R4 都在类型系统与单测的盲区里。

## 4. 与计划的偏差

| # | 计划 | 实际 | 原因 |
|---|---|---|---|
| D1 | Task 6 由 bridge 直接 import 插件实现 | 反转为 bridge **注入执行器**给插件 | wiring ⑪ 守卫禁止核心 import 插件实现 |
| D2 | preconditions 无 params | 加 `params` 透传 | `list_dir.path` 必填，零参写法跑不起来 |
| D3 | record 用 `sourceHint` | 先 `listSources` 挑源再传 `sourceId` | 契约要 sourceId，sourceHint 是人话 |
| D4 | `pipeline_run` 未要求 needsPermission | 标 `isReadOnly:false / needsPermission:true` | record 会执行有副作用的工具，必须过一次审批 |
| D5 | 计划的 chronicler 之类低风险目标 | 种子里不放需授权工具 | rehearsal 跳过 needsPermission 工具，依赖其产物的 spec 必然失败 |

## 5. 已知限制

| # | 限制 | 影响 |
|---|---|---|
| L1 | `{{}}` 引用只能向后 | 需要前向数据的流程只能拆成两条 spec |
| L2 | 不做条件分支 / 循环 / 并发 | 需要分支 = 路径不可枚举 = 不该做成流水线（设计 §7.4） |
| L3 | 种子「目录已有内容就整体跳过」 | 内置流水线后续更新到不了老用户（用户删掉该目录可重播） |
| L4 | `pipeline_draft`（从成功轨迹蒸馏）未实现 | 计划 Task 列表本身不含它；属 P1 后续 |
| L5 | rehearsal 跳过 needsPermission 工具 | 依赖它们产物的 spec 在 rehearsal 下必然失败——这是语义，不是 bug，但种子必须避开 |
