## 二、场景推演

> 数据口径统一说明：除非标注，均为**近 5 天**（2026-09-14 ~ 09-18）。
> 来源：`~/.lumii/logs/app/mtbot-2026-09-1[4-8].log`（事件层）与 `~/.lumii/data/agent-runtime.db`（hook 层）。

### 场景 1：一次 `file_edit` 失败，能穿过几个盲区

**设定**：弱模型在 minimal 档（生产主力，621 次）下改一个文件，`oldString` 缩进没对齐。

```
① 模型调 file_edit({filePath, oldString: "...", newString: "..."})
      │  schema 里参数名是对的（裁剪只删 description，不动 key）
      ▼
② 三级模糊匹配全失败 → 返回
      content: "Error: old_string not found in x.md (tried exact, line_trimmed, ...)"
      details: { success: false }              ← 无顶层 isError
      │
      ├─→ ③ ToolRunner: isError = Boolean(result.isError) = false     [tool-runner.ts:133]
      │      ├─ tool-usage-hook.afterExecute → recordToolUsage(..., false)   计数成功
      │      └─ ctx.isError === false → 不写 tool_audit_log
      │
      ├─→ ④ wrapper: if (result.isError) throw                         [tool-registry.ts:188]
      │      isError 是 false → 不抛 → pi-agent-core 认为成功
      │
      └─→ ⑤ 日志 tool:end isError=false

⑥ 模型读到的文本是「old_string not found」——**它以为参数名就叫 old_string**
      ▼
⑦ 下一次调用写 {old_string: "..."} → pi-agent-core validateToolArguments 抛错
      ▼
⑧ 校验在 tool.execute **之前** → wrapper 没被调用 → ToolRunner 没被调用
      → 所有 hook 全部看不到这次失败
      ▼
⑨ pi-agent-core catch → isError=true → 日志记一条 tool:end
      → 但 tool_usage_stats / tool_audit_log 里**什么都没有**
```

**这一步推演得到两个结论**：

**(a) 第 ⑥→⑦ 步是一个"错误文案自己制造新错误"的闭环。** 该工具的错误信息写得很用心（"tried exact, line_trimmed, whitespace_normalized"，是在教模型理解匹配策略），但把参数名写错了——**它教的是错的**。

**(b) 第 ③ 与 ⑨ 是两个独立的盲区，叠在同一次交互里**：
- ③ 是工具层不设 `isError` 造成的（`file_edit` 的锅）
- ⑨ 是校验层不在 hook 射程内造成的（架构的锅）

**实测对照**：

| 观测点 | 是否看得见 `file_edit` 的失败 |
| --- | --- |
| 模型（content 文本） | ✅ 看得见 |
| `tool_usage_stats.error_count` | ❌ 恒为 0 |
| `tool_audit_log` | ❌ 恒为 0 |
| 日志 `tool:end isError` | ❌ 恒为 false |
| 事件层 `tool_execution_end` | ❌ 同上（读的是同一个 isError） |

**近 5 天，`file_edit` 在四个统计口径里全部是 0 失败。** 而同一个工具的源码第 4 行写着：*「解决弱模型 old_string 缩进/空白对不齐的**高频失败**」*。

> **判定**：改，且是最高优先级。但改的是**错误文案**，不是 schema 描述——见 §一 第 4 条。

### 场景 2：照数据做决策，会得出反的结论

**设定**：季度工具面评审，拉最近 7 天的 `tool_usage_daily`：

```
file_edit     66 次    0 错误     ← 结论候选：很稳
file_write    77 次    0 错误     ← 很稳
bash          71 次    0 错误     ← 很稳
message       10 次    0 错误     ← 很稳
web_fetch     80 次   27 错误     ← 34% 失败率！结论候选：不稳定
list_dir      42 次    4 错误     ← 9.5%
glob          33 次    2 错误     ← 6%
resolve_sync_conflict 7 次 7 错误 ← 100% 失败！结论候选：该删
```

**照这张表，会得出两个完全错误的行动**：
1. 「`web_fetch` 有 1/3 失败，考虑替换或降级」
2. 「`file_edit`/`bash` 很稳，可以放心让弱模型用」

**真相在事件层**（同一时间窗，日志 `tool:end isError=true`）：

| 工具 | 数据库 `error_count` | 日志真实失败 | 差 |
| --- | --- | --- | --- |
| `web_fetch` | 27 | **64** | 2.4× |
| `bash` | 0 | **17** | ∞ |
| `file_edit` | 0 | 0 ⚠️ | 见下 |
| `task_complete` | 0 | **24** | ∞ |
| `file_read` | 0 | **8** | ∞ |
| `todo_write` | 0 | **2** | ∞ |
| `spawn_agent` | 0 | **2** | ∞ |
| `cron_create` | 0 | **1** | ∞ |

**这张表真正说明的是**：数据把所有工具按「**是否诚实地报告失败**」排了序，而不是按「是否可靠」。
- `web_fetch` 之所以难看，是因为它 `throw`（`web-fetch-tool.ts:257`）；
- `bash` / `file_edit` 之所以好看，是因为它们**什么都不做**。

**`file_edit` 那一行是个例外，值得单独说**：它在日志里也是 0。因为日志的 `isError` 和数据库读的是同一个 `result.isError`。**它是唯一一个连事件层都穿不透的**——场景 1 的第 ⑤ 步。

**`resolve_sync_conflict` 那 7 次失败要单独讲——它是一个已经修好的旧病，也是一堂现成的课。**

7 条记录的时间戳是**精确的每 10 分钟一次**（02:04:38 → 02:14:13 → 02:24:20 → … → 03:04:13），内容全是同一个超时：

```
{"status":"error","success":false,"error":"解决冲突超时（300000ms）。落决仍在后台继续，无需手动清理，稍后会自动重试。"}
```

那不是 7 次独立失败，是**一个循环**。而项目自己的设计文档已经把根因写清楚了：

> **L3 超时语义错误 —— 循环的直接原因。** 超时后 `resolveInner` 不会停：`enqueueWorkspace` 排的是 `resolveInner` 本身而非加过超时的外层，后台继续跑到底。但调用方（Agent）收到的是 `isError: true`。而调度器的冲突重试冷却 `CONFLICT_RETRY_COOLDOWN_MS = 2min` **小于** 5 分钟超时 —— 每一轮都必然重入：Agent 重新读文件、重新决策、重新发起落决，排到还在跑的那一轮后面。
> ——`docs/design/数据同步功能/2026-09-17-云同步异步化与分级传输设计.md` §2.3

修复（实施计划 T3.4）已把超时改成 `status: 'running'` + **`isError: false`**，理由是「超时不再被报成失败，Agent 不会因此重新决策、再排一轮落决」。**03:04 之后没有新的调用记录。**

**这个案例必须单独记，因为它给本文批次 1 提供了项目自己的先例**：`isError` 不是统计字段，是**行为契约**——语义写错会让 Agent 做出错误行为（这里是 7 次无效重排）。这不是本文的推论，是项目在云同步上已经付过代价的结论。

它同时给批次 1 立了一条硬规矩：**统一契约 ≠ 一律标失败**。例外清单见 §三 批次 1.1。

同批的 `cloud_sync_read_file`（105 次 0 错误）则是反面样本——同一份设计文档 §2.3 记着它「读 remote 侧在当轮 4 次全部失败」，而这 4 次一次都没进统计（它走 `details.success`）。

> **判定**：改，`isError` 契约统一是**所有后续治理的前置条件**。在这之前，任何"哪个工具该收敛/该优化"的决策都建立在**按诚实度排序**的数据上。

### 场景 3：守卫射程 68/94，且它没在跑

**设定**：开发者新增一个工具 `propose_dev_handoff`，忘了加进提示词分组。

**推演 A（假设守卫已在 CI）**：
```
加工具 → 提交 → CI 跑守卫 → ？
```
守卫的第 1 条是「每个已注册的 built-in 工具都归入正式分组」，用的是 `BUILT_IN_NAMES = ALL_BUILT_IN_TOOL_CONFIGS.map(...)`。
`propose_dev_handoff` 注册在 `apps/windows/.../bridge-tool-registrar-handoff.ts`，**不在 `ALL_BUILT_IN_TOOL_CONFIGS` 里**，也不在那 13 个硬编码的 `CLIENT_REGISTERED_NAMES` 里。
→ **守卫不红。合并。**

**推演 B（现状）**：守卫根本没跑（CI 只有 `large-files` + `typecheck`；`packages/agent-runtime` 的测试无任何调用方）。

**两条路通向同一个结果**，而这个结果**已经发生了**。生产日志实测：

```
Groups: File Tools (9), Shell (1), ..., Reference Guides (4),
        Other Tools (9), Desktop Control (18).
```

**94 个工具，其中 27 个（29%）在任何正式分组之外**：
- `Other Tools (9)`：`cloud_sync_read_file` / `resolve_sync_conflict` / `propose_dev_handoff` / `cloud_sync_git` / `cloud_sync_now` / `cloud_sync_push` / …
- `Desktop Control (18)`：`app_*` / `screen_record_*`

**而这些工具在真实使用**：

| 工具 | 近 7 天调用 |
| --- | --- |
| `cloud_sync_read_file` | 105 |
| `cloud_sync_git` | 48 |
| `propose_dev_handoff` | 7 |
| `resolve_sync_conflict` | 7（100% 失败） |

**更要命的是 minimal 档下的表现**：`buildTerseToolingLines` 只输出组名与数量——

```
Groups: ... Other Tools (9), Desktop Control (18).
```

**模型看到的就是「Other Tools (9)」这个数字，连名字都没有**（名字只在 tool schema 里）。这 9 个工具对模型来说是「有名字、无描述、无分组、不知何时用」的三无状态。

> **判定**：改，但要**两件事一起做**——接 CI（让它跑）+ 扩射程（让它有效）。只做前者，等于给一个 71% 覆盖率的守卫装上闹钟。

### 场景 4：147 次真实失败，数据库里只有 52 条

**设定**：想知道"模型最常在哪失败"。

事件层近 5 天 `tool:end isError=true` 共 **147** 次；同期 `tool_audit_log` 非 LLM 错误 **52** 条。

差 95 次，逐类拆开：

| 类别 | 次数 | 为什么丢 |
| --- | --- | --- |
| 工具名不存在：`read_file`(1) / `read`(3) / `file_manage`(2) / `global_search`(1) | **7** | 工具不存在 → 校验前就 throw → 永不进 hook |
| 参数校验失败（`Validation failed for tool`） | 9 | 同上 |
| `task_complete not found` | **24** | 见下 |
| `bash not found` | 17 | 子 agent 白名单没给 bash |
| 其余（`todo_write` / `cron_create` / `spawn_agent` 等） | ~38 | 需逐条归因 |

**`read_file` 那 1 次曾被当作"模型照做了失效引用"的实证——但 2026-09-18 的对照实验推翻了这个归因。**

```
日志原文：
  tool:end toolName=read_file isError=true
  resultPreview={"content":[{"type":"text","text":"Tool read_file not found"}],"details":{}}

          ▲ 这行 resultPreview 的结构（content + details:{}）
            正是 pi-agent-core catch 分支的产物

而 read_file 这个名字在本仓库里只出现在一个地方：
  packages/agent-runtime/src/tools/built-in/web-fetch-tool.ts:30
  "Do NOT use file:// URLs — use the read_file tool for local files instead."
```

当时的推理是：「这个名字在代码库里除了那行描述，别无出处」→ 所以是描述诱导的。

**对照实验（把描述改回 `read_file` → 重启 → 连跑 3 次 file:// 场景）的结果是 3/3 都调用了正确的 `file_read`。**

也就是说：**名字在代码库里唯一 ≠ 模型只能从那里学到它**。`read_file` 在训练语料里极常见，
模型自己就会先验地想到它——**那 1 次更可能是模型先验，不是描述诱导**。

这是本文的一处过度归因，特此更正。它同时给「修失效引用」的价值重新定了位：**值得修（零成本、零风险），但不能算作已获得的行为收益**。详见用例文档 TC-02 的对照实验小节。

**`task_complete not found` 24 次是另一类问题**，值得单独记：
`task_complete` 是**正常注册**的工具（`ALL_BUILT_IN_TOOL_CONFIGS` 里有）。它"not found"只可能是因为**调用它的那个 agent 的工具白名单里没有它**。而提示词在引导模型用 `task_complete`（`TOOL_SUMMARIES` 里写着 "Signal task completion"）。

→ **这是"提示词承诺了工具面没给的工具"**，24 次。和接缝一（描述与注册表不一致）是同一类病，只是方向相反：不是描述指向不存在的工具，而是**提示词指向了当前 agent 够不着的工具**。

> **判定**：改，但**不是补 bridge 审计**（那是给统计补丁），而是分两处：
> ① 修工具层的 `isError`（场景 2）→ 让 52 条这个数字先变准；
> ② 把「工具名不存在」这类失败**纳入守卫的检查范围**（场景 3 的扩射程）——它本质是同一类漂移，不该只靠事后 grep 日志发现。

### 场景 5：`duration_ms` 的修法，5 行 vs 一次架构迁移

**设定**：想知道"哪个工具最慢"。

```
tool_audit_log：
  llm:*       9873 条    duration_ms 全部有值   ← LLM 请求审计传了 [bridge-instance-factory.ts:281]
  真实工具    4158 条    duration_ms 全部为 null ← 两个写入点都没传
```

**方案原文的判断**：「hook 层拿不到可靠耗时」，因此提议把统计迁到事件层。

**推演后不成立**。`ToolHookResultContext` 与 `ToolHookErrorContext` 都带 `durationMs`：

```ts
// packages/agent-runtime/src/tools/tool-hooks.ts:38-39
export interface ToolHookResultContext extends ToolHookContext {
  result: AgentToolResult<unknown>;
  isError: boolean;
  durationMs: number;      // ← 一直在这里
}
```

而**同一个 hook 链上、同一个 context 里**，`bash-command-log-hook.ts:45-46` 就在用：

```ts
isError: ctx.isError,
durationMs: ctx.durationMs,
```

实测 `bash_command_log`：**1559 条，`duration_ms` 无一条为 null**。

**所以缺口是纯接口遗漏**：`ToolAuditRow`（`permission-gate-hook.ts:21-25`）和 `ToolFailureAudit`（`tool-usage-hook.ts:29-33`）两个类型都没有这个字段，而下游的 `AuditRepo.log()` 早就支持 `durationMs` 参数。

`bash` 的 `durationMs` 也没有 null，说明**它是唯一一个拿到了耗时的工具**——因为它的专用 hook 传了。

> **判定**：改，但按 5 行改，不做架构迁移。方案里的「迁到事件层」撤回。

### 场景 6：`tool_audit_log` 是一张什么样的表

**设定**：有人问"`bash` 被调用了多少次"。

```sql
SELECT COUNT(*) FROM tool_audit_log WHERE tool_name = 'bash'   -- 2100
```

**答错了。** 这张表里 `is_error = 0` 的行长这样：

```
tool_name     result_summary
bash          允许(仅本次)
file_write    允许(仅本次)
app_act       允许(仅本次)
```

它们来自 `permission-gate-hook.ts:109-116`——记录的是**权限决策**，不是工具执行。

于是这张表实际是三种东西叠在一起：

| 来源 | 条数 | `is_error` 的含义 | 带 duration |
| --- | --- | --- | --- |
| LLM 请求审计（`llm:*`） | 9873 | 请求失败 | ✅ |
| 权限决策（permission-gate） | ~4100 | **权限被拒** | ❌ |
| 工具执行失败（tool-usage-hook） | 54 | 工具失败 | ❌ |

**后果不只是"错误率不准"，而是表名撒了谎**：`tool_audit_log` 听起来像工具调用日志，用起来也像，但 `COUNT(*)` 得到的是**权限检查次数**。

**而它的排序还是反的**：一个失败的工具会产生 1 条权限记录 + 1 条失败记录（2 行），一个成功的工具只产生 1 条权限记录（1 行）。**越失败的工具，在这张表里"出现次数"越多。**

**这也顺带修正了方案里的一处误判**：方案说 `tool-usage-hook.ts:13` 的注释「只记失败、不记成功」与实现不符。实际上**注释正确**，那些"成功"行是另一个写入点写的。真正该做的是**让这张表名实相符**（拆表或加来源列），而不是订正注释。

> **判定**：改。但改法从「订正注释」变成「**给这张表加来源维度，或把 `llm:*` 与权限记录迁出**」。

### 场景 7：方案点名的 `file_write mode='range'`，靶子选偏了

**设定**：要找"最弱的一条改文件路径"。

**方案原文**：「零测试、零提示词引导、零使用证据，且是全仓**唯一一条不做内容校验就能改文件**的路径」。

**逐句核实**：

| 判断 | 核实结果 |
| --- | --- |
| 零测试 | ✅ `file-write-tool.test.ts` 仅 4 个 case（overwrite / 分段 / segments / append），无 range |
| 零系统提示词引导 | ✅ 提示词目录 grep `range`/`startLine` 零命中（但**工具自身 schema 有**：`file-write-tool.ts:131`） |
| 零使用证据 | ✅ 日志里 `startLine` 全部来自 `file_read` 的 details，`mode:"range"` **0 次** |
| 「无需先 file_read」 | ❌ **不属实**——`read-before-write-hook` 覆盖 range（`read-before-write-hook.ts:53-59` 只豁免 `append`），文件已存在时照样会被"未读过 → 拒绝"拦住 |
| 「全仓唯一不做内容校验的路径」 | ❌ **不属实**——`append` 与 `overwrite` 同样无内容锚点，其中 `append` **被显式豁免**，比 range 更松 |

**修正后的表述**：

> `file_write` 三个模式里，`append`（语义上不需要原内容）与 `overwrite`（整文件替换）不做内容校验是**自洽的**。
> **`range` 的问题不是"没有校验"，而是"用了一个看起来精确的锚点却不校验它"**——它借用了 `file_read` 返回的行号，却没有任何机制保证这些行号仍指向上次读到的那段内容。

**这个区别决定修法**：
- 若真是"唯一没校验的路径" → 该删掉分支，或从零造一套校验；
- 实际是"**锚点语义与保护机制不匹配**" → 让 `range` 复用**已经存在**的 `read-before-write` mtime/contentHash 比对即可，无需新造。

**顺带**：`append` 被 `read-before-write` 显式豁免，这个豁免本身合理（追加确实不需要知道原内容），但它**工具内部同样零校验**。若目标是"找出最弱的写路径"，`append` 比 range 更值得看一眼。

> **判定**：改，但**降级**——从方案 §七 阶段 3 的独立条目，降为**批次 2 的观察项**。它不是"多余能力"，是"能力少了一半"。

**宿主侧的同类缺口：已实施（2026-09-18）**

批次 1 的范围是 `packages/agent-runtime` 的内置工具。核查宿主侧（`apps/windows`）时发现同类问题的**结构性版本**：

```ts
// apps/windows/src/main/agent-runtime/bridge-utils.ts:30

  return { content: [{ type: 'text', text: JSON.stringify(data) }], details: undefined }
```

宿主工具有一个统一返回构造器，而它的类型**根本没有 `isError`**。
于是失败只能编码进 JSON 文本（`{ ok: false, error: 'capture_failed' }`），
模型得自己读 `ok: false` 才知道失败了——这正是契约要消灭的那种"模型自己猜"。

| 事实 | 数据 |
| --- | --- |
| `ok: false` 出现次数 | **95 处**，分布在 7 个文件 |
| 最多的文件 | `bridge-screen-record-tools` 27 / `bridge-tool-registrar-integration` 26 / `bridge-tool-registrar-client-cmd` 18 / `bridge-app-ui-tools` 15 / `bridge-wiki-tools` 6 / `bridge-tool-registrar-handoff` 2 / `bridge-browser-tools` 1 |
| **执行链路是通的** | 宿主工具经 `bridge-instance-factory:698` → `assembleAgent` → `assembleTools`（`packages/agent-runtime/src/host-kit/tool-assembly.ts:139` 的 `new ToolRunner` + `wrapMtBotToolsWithRunner`）装配——**与内置工具走同一个 ToolRunner**，所以顶层 `isError` 会被正常转成 throw。机制不缺，缺的是"没人标" |

**为什么不在本批次顺手做**：

1. **95 处需要逐个判语义**，不能按数量改——`ok: false` 有些是工具失败，有些只是业务字段
   （例如某个条目"未完成"的状态位）。批量改会把业务语义误标成工具故障，**比不做更糟**；
2. **归属未定**：是并进批次 1，还是作为独立批次（它有自己的验收标准）；
3. 其中一个文件（`bridge-tool-registrar-integration.ts`）**当时正被其他会话修改**，动它会冲突。

> **它值得单独记一笔的原因**：批次 1 的标题是「统一 `isError` 契约」，
> 而"统一"如果只统了一半（内置工具标了、宿主工具没标），
> 那么从模型视角看，**失败信号仍然是两套语义**——只不过换了个分界线。
> 这件事不做完，契约就还是局部约定。

##### 宿主侧的实施记录（2026-09-18 同日完成）

**规模比预估的翻了一倍**。原估计"95 处 `ok:false`"，实测**两套约定共 196 处**：

| 约定 | 处数 | 分布 |
| --- | --- | --- |
| `{ ok: false }` | **102** | app-ui(17) / screen-record(32) / client-cmd(19) / integration(26) / wiki(6) / browser(1) / guide(1) |
| `{ status: 'error' \| ... }` | **94** | maintenance / cron / handoff / sync / todo-write |

原估计只数了 `ok: false`，**漏掉了整套 `status:` 约定**——它藏在"形状不规范"的扫描里
（我最初的口径是"找 ok:false"，而这批调用根本没有 `ok` 字段）。

**实施方式：一处判定覆盖 196 处**，而不是逐个改失败分支：

```ts
// apps/windows/src/main/agent-runtime/bridge-utils.ts
const FAILURE_STATUSES = new Set(['error', 'not_found', 'partial'])
function payloadIsFailure(data: unknown): boolean {
  if (typeof data !== 'object' || data === null) return false
  const d = data as { ok?: unknown; status?: unknown }
  if (d.ok === false) return true
  return typeof d.status === 'string' && FAILURE_STATUSES.has(d.status)
}
```

**为什么集中判定**：196 处逐个加 `{ isError: true }` 会产生 196 处重复，且**新增工具时必然漏**；
集中判定只有一个判定点，守卫守它就够。代价是**必须逐个核实语义**——见下。

**逐处核实的结论（不是按字面猜的）**：

| 载荷 | 判定 | 核实依据 |
| --- | --- | --- |
| `ok: false` | 标 | 逐条看过，全是"工具没能完成它该做的事"（`disabled` / `usage` / `capture_failed` / `not initialized` …） |
| `status: 'error'` | 标 | 绝大多数；含 `HUB_NOT_READY`（消息确实没发出去） |
| `status: 'not_found'` | 标 | 删除时目标不存在——模型多半是 id 传错了，标出来它才知道 |
| `status: 'partial'` | 标 | 批量操作部分失败（载荷里同时带 `errors`） |
| `status: 'running'` | **不标** | `resolve_sync_conflict`："上一轮落决仍在后台执行，本次请求**未排队**。**不要重复调用本工具**"——标失败正好把 Agent 推向反面（契约 3a，T3.4 定案） |
| `status: 'started'` | **不标** | 同上："落决已在后台启动…**不要重复调用本工具**" |
| `status: 'proposed'` | **不标** | 开发转交在"宿主未启用自动执行"时的**正常终态**（提案已生成，等确认） |

> **后三类是本批次最容易犯的错**。统一语义时最省事的做法是"把所有非 ok 的都标失败"——
> 而那会让云同步的两条文案与它们的失败标记**互相打架**：文案说"别重复调用"，标记说"你失败了"。
> 守卫里这三条是逐条钉死的（`host-tool-failure-semantics.test.ts` 的 A2 组）。

**唯一形状不规范的一处**：`bridge-tool-registrar-guide.ts` 的
`{ error: ..., available_sections }`（既无 `ok` 也无 `status`）——集中判定认不出它，
已补 `ok: false` 规范化。这是扫描中唯一被漏判的失败返回。

**守卫**：`apps/windows/src/main/agent-runtime/host-tool-failure-semantics.test.ts`（13 用例）
- **A1**：五种失败载荷 → 标 `isError`
- **A2**：六种刻意不标的（含三个云同步/转交状态）→ **不标**
- **B**：扫描所有 `jsonToolResult({...})` 字面量，断言"含失败字样却无 `ok`/`status`"的载荷为零
- **变红验证**：从 `FAILURE_STATUSES` 移除 `'error'` → A1 红；把某处 `ok:false` 改成 `failed:true` → B 红

**CLI 验证**：`TC-CONTRACT-08`（真实客户端）——宿主工具的失败载荷在真实链路上确实变成 `is_error`，
而不只是单测里 `jsonToolResult` 返回了 isError。这条链路横跨两个包，单测覆盖不到。

### 4.2 每批次的提交门禁

沿用 12b:595-603 已定的六条，本轮无新增：

```bash
pnpm typecheck                                  # 本仓库无 ESLint，类型是唯一静态门禁
pnpm --filter @mtbot/agent-runtime test         # 批次 0.4 之后
pnpm check:large-files
cd apps/windows && pnpm test:all                # 动过 src/main/** 必须
pnpm dev:restart                                # 改主进程后，再跑真机冒烟
```

**提交卫生**：仓库有并行会话，**按文件显式 `git add`，不要 `git add -A`**（12b:602）。

> **批次 1 提交时的实际状态（2026-09-18）——一条关于"多会话下怎么把关"的经验**
>
> 五条门禁里，`typecheck` 与 `check:large-files` **都报错了**，但**无一与批次 1 相关**：
>
> | 门禁 | 结果 | 报错归属 |
> | --- | --- | --- |
> | `pnpm typecheck` | ❌ 2 条错 | 他人正在改的 `index.ts`（`Duplicate identifier 'drawerPointerId'`） |
> | `pnpm --filter @mtbot/agent-runtime test` | ❌ 1 文件 | 他人改到一半的 `palace-repo.ts` → `personal-memory-persistence.test.ts` 的 esbuild transform 失败 |
> | `pnpm check:large-files` | ❌ 18 项 | 全部是他人文件的长度增长（`schema.ts` +315、`conversation-repo.ts` +175 …） |
> | `cd apps/windows && pnpm test:all` | 见提交说明 | — |
>
> **逐项核实后的结论**：批次 1 的 15 个改动文件**无一出现在任何一份报错列表里**
> （`tsc` 只报 `index.ts` 两行；`check:large-files` 的 18 项经 grep 过滤后零命中）。
>
> **由此得到的做法**——多会话并行时，"跑全量门禁看退出码"这个动作本身就会被他人的中间状态污染：
>
> - **`退出码 == 0` 不是判据**（它会被别人的半成品拉红）；
> - **真正的判据是「报错列表里有没有我的文件」**——即按文件核实，而不是按命令核实；
> - 批次 1 自己的把关改用：`src/tools/` 目录全绿（205 passed，含新增 43 个守卫用例）
>   + tsc 对 14 个改动文件零报错 + CLI 套件 6/6。
>
> 这不是"放宽门禁"，而是**换一个不会被他人状态污染的等价判据**。
> 代价是失去了"跨文件影响"的检查——所以它只在确认改动**局部**时可用。
**提交信息**：中文 Conventional Commit，正文写清「起因（带数据/`file:line`）+ 改动 + 验证」，**不含署名尾注**（AGENTS.md:13、12b:606-612）。
