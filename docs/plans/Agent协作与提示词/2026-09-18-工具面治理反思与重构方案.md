## 一、结论先行

项目已经做过两轮高质量治理：

| 轮次 | 射程 | 成果 |
| --- | --- | --- |
| 2026-08-28 Tooling 重构 | **提示词层** | 修 7 处事实性漂移、TOOL_SUMMARIES 瘦身、`task_complete` 四处收敛为一处、加漂移守卫 |
| 12a 工具面收敛 | **工具清单层** | 33→31、加预算守卫、补 agent 维度统计、失败原因落库 |

而且两轮都**主动砍掉了过度设计**——P2「注册表驱动分组」经实勘判定过度设计并取消，`tool_search` 与 schema 按需加载被 YAGNI 明确排除。**这些判断本文都认同，不再翻案。**

所以问题不是「没治理」，而是：

> **治理的射程按「层」切，而病灶长在「接缝」上。**

三个接缝缺口，每个都是「两层各自都做对了，但没有人为中间那根线负责」：

| # | 接缝 | 现象 | 后果 |
| --- | --- | --- | --- |
| 1 | 守卫 ↔ 文本 | 守卫比对「注册表键集合」，不检查 schema **描述文本里**引用的工具名 | `read_file` / `skill_list` / `old_string` 三处失效引用活到今天 |
| 2 | 工具 ↔ registry ↔ provider | `isError` 有三套互不兼容的语义，没有一层对它负责 | 错误率数据系统性失真，`file_edit` 457 次 0 错误 |
| 3 | 机制 ↔ 执行者 | 三个工具面守卫测试**不在任何自动化路径上** | 再好的守卫也只防住「写它那天的漂移」 |

第 3 条最讽刺：`tool-budget.test.ts`、`tooling-section.test.ts`（漂移守卫）、`tool-definition-style.test.ts` 全在 `packages/agent-runtime` 下，而 CI 跑的是 `apps/windows` 的测试，后者的 vitest `include` 只匹配 `src/**`。

**还有一层值得单独点出**：`docs/AGENT设计实践教程/` 的 ch04 是从本项目的实践提炼的，但它 §6.2 那张「收敛案例」表，照抄的是 12a 里**已被本项目自己证伪**的版本（2026-09-16 复核：6 条里只有 2 条站得住）。也就是说——**教程的某些结论落后于项目的最新认识，而且落后在一个方法论问题上**（按名字判断正交性）。更正见 §七附。

## 二、先说做对了什么

反思容易滑向「只挑毛病」。以下设计**建议保留，不要在后述重构中被误伤**：

1. **read-before-write 防呆**（`host-kit/read-before-write-hook.ts`）。三条硬规则 + mtime 漂移检测 + contentHash 回退，且**故意不因 isPartialView 拒绝**以避开分页读取的高频误拦——这是一个考虑过 false positive 的防呆，不是拍脑袋的闸门。
2. **tooling-section 的 6 条漂移守卫**（`sections/__tests__/tooling-section.test.ts`）。无孤儿、无死键、无幽灵名、分组两两不重叠。覆盖面比多数项目都强。
3. **bash 演化的质量门**（`tools/bash-evolution/tool-quality-gate.ts`）。5 维规则中「样本回放 ≥80%」尤其好——它约束 LLM 不能瞎编命令结构，这是把「生成」锚回「真实数据」的关键一招。
4. **microcompact**（`compact/strategies/micro-compact.ts`）。旧工具结果替换为确定性微摘要、保留最近 8 个、正文 ≤200 字符不处理——执行面卫生里最有效的一层。
5. **tool-budget 的反向断言**（「预算不是摆设」）。防止预算被悄悄改大而无人察觉，这个设计比预算本身更值钱。
6. **minimal 档有 A/B 实测支撑**。实测结论（minimal 3/3 > detailed 2/3 > terse 1/3，且 detailed 档出现 60+ 次 `task_complete`+`bash` 失控循环）与直觉相反，说明这一档是**测出来的，不是猜出来的**。
7. **terse 折叠保留了最有价值的两条组注**（`buildTerseToolingLines` 里那句 "Prefer File Tools over `bash`…; call `cron_guide` before scheduling"）。折叠时知道该留什么，是设计成熟的表现。

## 三、接缝一：守卫的射程（结构 vs 文本）

### 现状

守卫检查的是**结构一致性**：

```
注册表键集合  ←→  PROMPT_TOOL_GROUPS 成员  ←→  TOOL_SUMMARIES 键
```

没检查的是**schema 描述文本里对工具名的引用**。于是三处失效引用至今模型可见：

| # | 位置 | 文本 | 问题 | 危害 |
| --- | --- | --- | --- | --- |
| 1 | `tools/built-in/web-fetch-tool.ts:30` | "use the **read_file** tool for local files instead" | 无此工具，实际叫 `file_read` | 模型照做 → 调用不存在的工具 |
| 2 | `tools/built-in/skill-tools.ts:165` | `hint: "Use **skill_list** to see available skills."` | `skill_list` 已并入 `skill_search` | 出现在 **tool_result** 里，模型最容易照做 |
| 3 | `tools/built-in/file-edit-tool.ts:196 / 221 / 236` | 描述与**错误文案**写 `old_string` | schema 参数名是 `oldString` | **错误信息主动诱导模型用错参数名重试** |

第 3 条最值得警惕：该工具的错误信息本身写得很可行动（"tried exact, line_trimmed, whitespace_normalized"），却因为参数名对不上，把一个自我修正机会变成了二次犯错源。这正是「错误信息是写给模型读的」这句话的反面教材。

### 为什么两轮治理都没抓到

- 2026-08-28 那轮修的是**提示词层**的键名漂移（`tts_generate` → `speech_generate`），依据是「真实渲染产物 vs 生成代码」的逐行实勘。**schema 文本不在那次的射程里。**
- 漂移守卫比对的是「键集合」，两个集合都在 `tooling-section` 与注册表之间，**schema 内部文本对它不可见**。

### 方案

**新增一条守卫：schema 文本的工具名引用检查。**

- 扫描所有 `*ToolConfig` 的 `description` 与参数 `description`，提取反引号包裹或 `[a-z][a-z0-9_]{3,}` 形态的标识符；
- 与注册表 + 已知宿主工具名（`app_*` / `browser_*` / `execute_skill` / guide 系）求差集；
- 差集非空即失败，并打印「哪个文件的哪段文本引用了谁」。

先修三处，再上守卫。成本约一个测试文件，收益是**这一整类 bug 永久绝迹**。

## 四、接缝二：错误契约（三套语义）

### 现状

`isError` 在整条链路上有三种互不兼容的表达，且**下游只认其中一种**：

| 来源 | 失败如何表达 | 谁消费 |
| --- | --- | --- |
| 部分工具（走 throw） | 异常 → registry 转 `isError: true` | ✅ hook 链、审计、遥测 |
| 文件工具（`file_write`/`file_edit`/`list_dir`/`file_copy`/`file_move`） | `details.success: false` | ❌ **无任何代码消费**（registry 只看顶层 `isError`） |
| MCP 工具（`mcp-proxy-tool.ts:69-83`） | `details.isError` | ❌ 同上 |
| `bash`（`bash-tool.ts:56-60`） | **什么都不做**（只拼 stdout/stderr + `details.exitCode`，不判非零） | ❌ |
| 参数校验失败 | `execute` **之前**抛出（pi-ai 的 Ajv 校验） | ⚠️ **错误被标记，但没进 hook 链**（见下） |

关于最后一行，实勘结论比「绕过全部 hook」更精确，也更说明问题所在：

`pi-agent-core/dist/agent-loop.js:225-226` 把 `validateToolArguments` 与 `tool.execute` 放在**同一个 try 块**里，catch 会正常置 `isError = true` 并发出 `tool_execution_end`。**所以错误信号本身没丢**——丢的是归因：ToolRunner 包在 `tool.execute` **内部**，校验失败时它根本没被调用，于是 logging / telemetry / persist / **usage-audit 全部看不到这次失败**。

这是「层」与「层」之间最典型的一处失配：**事件层看得见，hook 层看不见，而所有统计都建在 hook 层上**。（`tool-usage-hook` 是唯一统计入口，它挂在 ToolRunner 上。）

### 实测后果

最近 7 天 `tool_audit_log`（`tool_name NOT LIKE 'llm:%'`）：

```
bash        1242 次   0 错误
file_write   740 次   0 错误
file_edit    457 次   0 错误
web_fetch     29 次  29 错误   ← 唯一走 throw 路径的
```

**这些 0 是假的。** `file-edit-tool.ts:4` 的注释自己写着「解决弱模型 old_string 缩进/空白对不齐的**高频失败**」——「高频失败」与「0 错误率」不可能同时为真。

这直接击穿了 12a 自己立的方法论：*「仪器读数错了，后面全错」*。项目修过一次仪器（补时间维度、补 agent 维度），但更根本的 `isError` 语义问题还在。**当前拿 `tool_usage_stats` 做任何收敛决策，都是在假数据上做手术。**

另有两处口径污染：

- `tool_audit_log` 里 **9863 条是 `llm:openai:*`**（占全表 70%），「工具调用数」这个指标已失去意义；
- `tool-usage-hook.ts:13` 注释称「只记失败、不记成功」，但表里 13016 行只有 168 个 error——**注释与实现不符**，误导后来者。

**同一病症的第三个样本：`message` 工具。** 它对非活跃会话硬失败（`bridge-tool-registrar-integration.ts:173-177`），但返回的是普通 JSON content、**不设 `isError`**（`bridge-utils.ts:30-35`）——这批注定失败的调用在统计上被记成成功。

这也顺便解释了「一个标了 DEPRECATED 的工具为什么还有 64 次调用」：**是提示词在主动引导它**（`misc-sections.ts:303-336` 的 NO_REPLY 流程、`runtime-section.ts:44-45` 都点名 `message`），而它的失败又不可见。所以——**`message` 不是「半废弃遗留物」，它是承载了 `channel_send` 无法表达的语义的兼容层**（隐式回当前微信会话 + `markSentViaTool`）。要降低误用，该改的是提示词与默认渠道逻辑，不是它那句 description。这一点本文先前的判断有误，特此更正。

### 方案

**定义唯一的错误契约，并加守卫测试锁死。**

1. 立规：工具失败**必须**在顶层产出 `isError: true`；`details` 只承载结构化归因（`success` 保留给 UI，但不能是唯一的失败信号）。
2. 逐点修复：`bash` 判 `exitCode !== 0`；MCP 的 `isError` 提到顶层；五个文件工具补 `isError`。
3. **把 usage 统计从 ToolRunner hook 迁到事件层**（本轮唯一的架构性改动，但它同时解决三个问题）。
   现状：唯一的统计入口 `tool-usage-hook` 挂在 ToolRunner 上，于是「没进 ToolRunner 的调用」全部不可见——最典型的就是参数校验失败（§上文）。
   而 `tool_execution_start` / `tool_execution_end` 事件流本来就是**全量**的，且天然带 `toolName` 与 `isError`。
   收益：① 覆盖校验失败这类最常见的失败类型；② 顺带拿到 `duration_ms`（当前 `tool_audit_log` 里大面积为 null，因为 hook 层拿不到可靠耗时）；③ 统计口径与事件流对齐，不再依赖「工具内部是否包了 runner」。
   *若本轮不想动架构，最小替代方案是在 bridge 处理 `tool_execution_end` 时，对「未经过 hook 链的 toolCallId」补一条审计——但那是补丁，不是修法。*
4. 加守卫：对每个注册工具，断言其失败分支返回的 result 顶层带 `isError: true`。
5. 把 `llm:*` 移出 `tool_audit_log`（或加视图/过滤），并订正 hook 注释。

## 五、接缝三：机制的执行者

### 事实链

```
.github/workflows/ci.yml     → check-large-files + typecheck（无测试）
package.json "verify"        → typecheck + check-large-files + --filter lumii-windows test:all
apps/windows/vitest.config   → include: ["src/**/*.test.ts", ...]   ← 只含 apps/windows/src
packages/agent-runtime       → "test": "vitest run"，但 grep 全仓无任何调用方
```

**结论：`packages/agent-runtime` 的全部测试不在任何自动化路径上。**

而三个工具面守卫恰好都在那里：

- `agent/builtin/__tests__/tool-budget.test.ts`（预算守卫）
- `prompt/sections/__tests__/tooling-section.test.ts`（漂移守卫）
- `tools/__tests__/tool-definition-style.test.ts`（载荷裁剪契约）

### 判断

这不是「测试没写」，而是「**写了但没人跑**」。其后果比不写更隐蔽：它给人一种「我们有守卫」的安全感，而守卫实际只防住了「写它的那一天的漂移」。

`tool-budget.test.ts` 的注释其实已经预见了这个风险——*「没有它，今天的收敛半年后会被一条条『顺便加个工具』加回去，而且没人会发现」*。可惜它自己也在「没人会发现」的集合里。

### 方案

1. 根 `verify` 增加 `pnpm -r test`（或至少 `--filter @mtbot/agent-runtime test`）。
2. CI 增加 test job。
3. **注意技术障碍**：CI 现有 job 用 `--ignore-scripts` 跳过原生模块编译（为 typecheck 省时间）。工具面守卫基本是纯逻辑，应优先让这批**不依赖 better-sqlite3 / electron** 的测试先跑起来；依赖原生模块的再单独评估。
4. 顺带：把「工具面守卫」在 CI 里做成独立 job，失败信息直接点名「工具面变了」。

## 六、未完成的分层（对「过度设计」的重新表述）

复查代码后，我认为这个项目的过度设计**不是「设计得太复杂」，而是「引入新机制时没有说清它替代了谁」**，于是新旧并存。

| # | 现象 | 证据 | 判断 |
| --- | --- | --- | --- |
| 1 | **两套结果落盘** | runtime `tools/tool-result-storage.ts`（50K，flag 门控）vs windows `agent-runtime/tool-result-storage.ts`（30K，无条件）。实际是**按阈值切分职责**：>50K 走 runtime 侧、30–50K 走 windows 侧，靠 hook 链先后顺序隐式分流 | 切分本身可行，但**豁免规则只写在一侧**：`EXEMPT_TOOL_NAMES = {file_read}` 仅在 windows 侧，于是 >50K 的 `file_read` 会被 runtime 侧落盘——正是 windows 侧注释里要避免的「落盘→再 Read 回来」循环 |
| 2 | **两条工具进化线** | `bash-evolution/`（已接线）vs `autonomous/tool-evolution.ts` + `tool-thompson-sampling.ts`（**498 行源码 + 520 行测试**，未导出、公共 API 不可达） | 靠测试养着「绿色假象」；README 自标「P2 代码已落地待接线」 |
| 3 | **两套遥测** | `tools/telemetry.ts`（内存 Map，`snapshot()` 无调用方，sink 只有一行 `log.info`）vs `tool_usage_stats`/`tool_audit_log`（真在跑） | 前者是骨架 |
| 4 | **已实现未接线** | `enforceToolResultBudget`（40 行，同轮 120K 聚合预算，**零调用零测试**）、`capability-registry`（**243 行源码 + 217 行测试**，`apps/` 零引用）、`refine-patterns.ts`（主链路显式传 `null`）、`tool_usage_feedback` 表（零写入方） | 见下 |
| 5 | **装了门禁的样子** | `verification-gate-hook` 对 `task_complete` 返回的**不是 error**（`isError` 未设），且「第二次调用必放行」（`verification-tracker.ts:46-50` 放行时重置计数）；「已验证」判据是宽泛词正则，`grep -r "test" .` 也算验证 | 它是 nudge，不是护栏。可以留，但**不应被计入行为约束层的成果** |
| 6 | **装了能力的样子** | `file_write` 的 `mode='range'`（按行号整段替换）：零测试、零提示词引导、零使用证据，且是全仓**唯一一条不做内容校验就能改文件**的路径（`file_edit` 要求复现原文，`range` 只要行号） | 行号来自上一次 `file_read`，文件一变就静默改错位置。补测试+明确提示语，或删 |

其中第 4 类最危险：**它们在阅读代码时会被当成已生效的防线**。`capability-registry` 尤其典型——`agent-instance.ts:574-581` 里那段按 turn origin 拒 `isHighRisk`/`shell`/`admin` 的逻辑读起来像一道安全闸门，但 Windows 端从未构造注入，发行版里从不生效。

值得说明的是，**这个判断不是本文的臆断**：项目自己的设计文档已明确否决接线，并称其为「假护栏」（`docs/design/客户端UI/2026-08-13-Agent操作客户端设计.md:639,951`；`docs/plans/渠道与CLI/2026-08-15-CLI统一控制面实施计划.md:19,49`）。**决策已经做了，只是代码没删。**

同理，`autonomous/tool-evolution` 的 README 已标「待接入」——但「待」了多久、谁负责、什么条件下接入，没有记录。**挂起的代码应当移出主树**（`pending/` 目录或删除），否则每次重构都要陪跑。

### 建议的判定标准（供后续沿用）

新增机制时，在提交信息里回答两句：

1. **它替代了谁？** 若答案是「替代了 X」，则同一次提交里删掉 X。
2. **若无替代对象，为什么需要两份？** 说不出来就不加。

对第 4 类，二选一：要么接线（并加测试证明它真的拦得住），要么删除。**不要让「已实现未接线」长期存在。**

### 七附 · 一个方法论教训：那张收敛表是怎么错的

12a §3.2 的收敛表列了 6 条合并，2026-09-16 实施后复核**只有 2 条站得住**。项目自己写的根因是：

> 「表是照着工具名与描述列的，**没读实现、也没查谁在依赖它们**。」

逐条被证伪的依据（每条都读了实现）：

| 计划合并 | 复核结论 | 依据 |
| --- | --- | --- |
| `list_dir` → `glob` | ❌ 不做 | `glob` 只回路径不分目录；两者描述本就互相指名对方；且都在热路径（近 7 天 90 / 102 次） |
| `memory_read` → `memory_manage` | ❌ 不做 | 读 MemPalace 抽屉 vs 管工作记忆，**两个子系统**；合并会让描述自相矛盾 |
| `app_fill_form` → `app_act` | ❌ 不做 | `app_act.type` 必须给 `ref`，`fill_form` 能按 label 定位——**不是重叠，是唯一路径** |
| `app_goto_and_screenshot` | ❌ 不做 | screen-tutorial-pipeline **正是靠它**把教程任务的工具调用从 40~60 次压到 8~15 次 |

这张表被原样写进了 `docs/AGENT设计实践教程/chapters/ch04-工具设计与工具面治理.md` §6.2。**也就是说，教程里那条被当成经验传授的「合并候选」，方向是反的**——而这个项目恰好证明了按名字判断正交性会错。

两点值得单独记下：

1. **正交性判据必须落到实现层。** ch04 说「能否用一句人话讲清什么时候用 A、什么时候用 B」——但 `app_fill_form` 与 `app_act` 用一句人话是分不清的（都是「操作界面元素」），只有读实现才知道 `type` 要 `ref`、`fill_form` 按 label 定位。**判据是实现的，不是措辞的。**

2. **工具粒度存在双向最优。** 合并减少选择干扰，组合工具减少往返——`app_goto_and_screenshot` 把 7 步压成 1 步、调用降 5 倍，说明「高频的多步组合」应当合并成工具，而「低频的独立动作」应保持独立。ch04 §6.2 只讲了前半个方向。

**这两个方向在本仓库都有实证，建议后续把 ch04 那张表就地更正**，否则教程会继续把一个已被证伪的方法论传给读者。

## 八、明确不做（与既有决策保持一致）

以下方案**曾被考虑并正确地否决**，本文不再提议，并附上理由以免后人翻案：

| 不做 | 理由 | 出处 |
| --- | --- | --- |
| `tool_search` / schema 按需加载 | 项目有反例数据：API-Bank 上 Retrieve+Call 38.52% < Call 59.40%；ToolRet 显示检索层会把「选错」换成「漏掉」。而「高频工具常驻 + 其余可搜」的基础设施尚不具备 | 12a §四 |
| 注册表驱动分组（`promptGroup` 元数据） | 经实勘判定过度设计；`PROMPT_TOOL_GROUPS` 是必要的「何时用」索引而非重复 | 2026-08-28 §5 修订 |
| 删掉 `TOOL_SUMMARIES` | 同上，映射表承担跨工具「何时用」，schema 里没有 | 2026-08-28 P2-T5 |
| 大规模砍工具数 | 留着能 `curl`/`node -e` 的 `bash` 时，白名单收敛的边际收益有限；收敛的性质是「整理语义重叠」而非「限制能力」 | 12a §3.3 |

**唯一想补充的一点**：§8 第一条的结论「不做按需加载」是对的，但它**不导出**「116 个全量暴露无需处理」。针对默认 `assistant` 的**场景化工具集**（复用已有的白名单机制，而非引入检索）是另一条路——它不引入「漏工具」这个新故障类，也不需要新基础设施。这属于阶段 3，且同样**必须先有评测**。
