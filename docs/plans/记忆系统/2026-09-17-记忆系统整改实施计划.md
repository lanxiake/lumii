> 日期：2026-09-17
> 设计来源：[`../../design/记忆系统/2026-09-17-记忆系统评审.md`](../../design/记忆系统/2026-09-17-记忆系统评审.md)
> 范围：评审的 **P0 / P1 / P2** 全部条目。**P2-3（记忆宫殿自建）不在本计划**，见 [`2026-09-17-自建记忆宫殿实施计划.md`](2026-09-17-自建记忆宫殿实施计划.md)。
> 原则：不引入任何新依赖；只加两个迁移（V47 / V48）；不改 `memory_search` 的入参 schema

## 1. Goal（一句话目标，可验证）

> **让已沉淀的记忆真正可达、写入有门、信号可信。**

三条可独立验证的目标：

| # | 目标 | 基线 | 验收 |
|---|---|---|---|
| G1 | Agent 能检索到**只存在于 `agent_memories`** 的记忆 | `memory_search` 从不查该表（0% 可达） | 构造一条仅在工作记忆中的事实，Agent 调 `memory_search` 能命中，返回带 `provider: "work-memory"` |
| G2 | 垃圾不再入库，写入有门 | 5+ 条含 JSON 残片、`importance` 全 0.95 | 构造残片/超长/超短/重复候选全部被拒并告警；「记住：X。只回复 Y」不再吞入 `Y` 之后的内容 |
| G3 | 曝光与效用分离，自激解除 | 注入即刷新 `last_used`，recencyBonus 恒满额 | 同一记忆连续注入 10 轮，`utility_count` 与 `recencyBonus` 均不随注入变化 |

## 4. Global Constraints（不可违反的硬约束）

1. **纪律闸门先于读路径**：P0-3 的写入 schema 门必须与 P0-1 同批或更早合入。先开检索再关门 = 把垃圾从"偶尔注入"升级为"随时可查"。
2. **V47 加列必须与消费点切换同批**：只加列不切消费点，`passesInjectionGates` 会把 155 条「其实用过」的记忆误判成「从未用过」而集体跳过。
3. **V47 必须回填**：`exposure_count = use_count`、`last_injected_at = last_used`。
4. **墓碑先有生产者，再加读过滤**：`deleted_at` 全仓无写入方（评审 §2.4.5），先改 `removeById` 为软删，再加 `AND deleted_at IS NULL`。反过来做没有任何可观测效果。
5. **`superseded_at` 必须晚于检测器修复**：P1-1 内部顺序不可颠倒（先 `project_key`，再检测器，最后字段）。
6. **效用代理先观察后进打分**：`utility_count` 在 P0 只记录，**不参与 `scoreMemory`**；等抽样验证代理有效性后再切（见 §6 P1-5）。
7. **日志不落用户原文**：只记 `memory_id` / `drawer_id` / 长度 / 计数 / 拒绝原因。
8. **每个 Task 单独一次 Commit**，Conventional Commit（`fix(memory):` / `feat(memory):`）。
9. **测试不写进用户 workspace**；测试后必须重跑 `pnpm typecheck`（vitest 不做类型检查）。

## 6. Task 分解

> TDD：算法与编排模块先写失败测试再实现（规范 §1.3）。

### P0-1 · 读路径接通（G1）

- **做什么**：`memory_search` 的 `execute` 改为**按通道分段返回**：
  1. `work-memory`：`getMemoryManager().searchMemories(agentId, userId, query, limit)` → `AgentMemoryRepo.search()`（FTS5 + `bm25()`，中文 bigram 已就绪）
  2. `palace`：现有 MemPalace 分支（未安装则跳过）
  3. `profile` / `scene`：现有文件匹配降级路径
  每条结果带 `provider`；`work-memory` 条目额外带 `id`（供 Agent 接 `memory_manage`）。
  **余量分配**：`limit` 先满足通道 1，剩余给 2、3 —— 不做跨通道分数融合（量纲不可比）。
- **改哪些文件**：`bridge-tool-registrar-integration.ts`（`:164-261`）；`getMemoryManager` 已在 `BridgeToolRegistrarDeps`（`bridge-tool-registrar-types.ts:46`），无需加依赖
- **验证**：`cd apps/windows && npx vitest run src/main/agent-runtime/`
- **完成标志**：MemPalace 未安装时，仅存在于 `agent_memories` 的记忆可被检索到；结果含 `provider`

> **有效性已预验证**：评审 §2.5.1 把日志中 5 条真实查询按 `AgentMemoryRepo.search()` 原样逻辑重放，**5/5 命中相关记忆**，含 09-14 那次失败查询。本 Task 只做接线，不新增检索逻辑。

### P0-2 · 墓碑链路补全（生产者 + 过滤）

- **做什么**（顺序不可颠倒）：
  1. `removeById`（`memory-repo.ts:639`）由 `DELETE` 改为 `UPDATE ... SET deleted_at = ?`，同步清理 FTS 索引行使之不可检索
  2. 全部读路径补 `AND deleted_at IS NULL`：`loadCandidates`（`:216`、`:232`）、`listByWindow`（`:324`）、`search`/`searchByLike`（`:581`、`:602`）、`listActive`（`:613`）、`listActiveAllAgents`（`:625`）、`countByTemperature`（`:727`）
- **范围界定**：只改 `removeById`（用户在记忆页删错的那条）。`removeByTag`（标签整批轮换）与 `clearAllForAgent`（用户主动清空）**保持硬删**，但需在注释里写明理由
- **改哪些文件**：`memory/memory-repo.ts`；UI 删除路径无需改动（`agent-commands.ts:135` 调的就是 `removeById`）
- **验证**：`pnpm --filter ./packages/agent-runtime test -- src/memory`
- **完成标志**：删除一条记忆后该行仍在库中带 `deleted_at`，且不出现在注入 / 搜索 / 列表 / 温度统计中

### P0-3 · 写入 schema 门（G2）

- **做什么**：
  1. 新增 `validateCandidate()`，在 `parseCandidatesJson` 之后、`saveCandidate` 之前调用。规则：JSON 残片（含 `"}]` / `"]` / 未闭合引号）拒绝；`content.length < 8` 拒绝；`> 600` 拒绝并告警；与同 agent+user 既有 content 完全相同拒绝；`importance` 缺失**不拒绝**，按类别给保守默认
  2. 修正 `RULE_PATTERNS[0]`（`memory-extractor.ts:32-41`）：`.{2,200}` → `[^。！？!?\n]{2,200}`（按句读边界截断）；`importance: 0.95` 固定值 → 按内容长度与结构化信号给分
  3. 提取提示词补 `importance` 分档锚点示例（照 Generative Agents 的 1–10 分带例子的写法）
  4. 拒绝时 `console.warn`（拒绝原因 + content 前 40 字），供统计「写入拒绝率」
- **改哪些文件**：`memory/memory-extractor.ts`、`memory/manager.ts`（调用点）
- **验证**：`pnpm --filter ./packages/agent-runtime test -- src/memory/__tests__/candidate-validation.test.ts`
- **完成标志**：构造残片/超长/超短/重复候选全部被拒；对真实「记住：X。只回复 Y」输入，入库内容不含 `Y` 之后的部分

### P0-4 · V47 曝光/效用分离（G3）

- **做什么**：
  1. **V47 迁移**：`ALTER TABLE agent_memories ADD COLUMN last_injected_at TEXT / exposure_count INTEGER NOT NULL DEFAULT 0 / utility_count INTEGER NOT NULL DEFAULT 0`；**回填** `exposure_count = use_count`、`last_injected_at = last_used`
  2. **断开自激**：`loadTopMemories` 注入时改刷 `last_injected_at` / `exposure_count`（`memory-repo.ts:186-197`）；`scoreMemory` 的 recencyBonus 输入由 `lastUsedAt` 改为 `createdAt`
  3. **连带切换 6 处消费点**（评审 §4.3 清单）：`passesInjectionGates` 的冷数据门控 → `exposure_count`；`archiveCold` / `prune` / `countByTemperature` / `computeTemperature` → `last_injected_at`；云同步 `mergeMemory` 的时间戳比较键（`sync-importer.ts:509`、`:526`）→ `last_injected_at`
  4. **接线效用反馈**：新增 `MemoryFeedbackRepo`；`MemoryIntegration.recordInjectionOutcome()` 用 `_injectedSnapshot` + 末条 assistant 文本算 bigram 重叠，写 `memory_usage_feedback` + 递增 `utility_count`。在 `agent-instance.ts:438` 的 `clearInjectedSnapshot()` 之前调用
     - 表约束：`session_id` / `memory_id` / `query_length` / `was_used_in_response` / `contribution_score` / `features` 均 NOT NULL。`session_id` 取实例的 `conversationId`（无则退化为 `instanceId`）
     - `contribution_score` 三档：重叠 ≥0.5 → 1；≥0.2 → 0.5；否则 0
     - `features` 按 `MemoryRankingFeatures` 的 12 个字段填（`semanticSimilarity` / `keywordMatch` / `queryLength` / `memoryAge` / `accessCount` / `lastAccessRecency` / `memoryLength` / `topicRelevance` / `userFeedbackScore` / `taskTypeMatch` / `avgUtilityScore` / `retrievalSuccessRate`），当前不可得的填 0/`false`
     - **不写 query 原文**，只写长度（与 `memory-evolution.ts:49` 的既有约定一致）
     - 只写「被注入且 overlap > 0」的条目；单轮批量事务
- **不做**：`utility_count` **不进入 `scoreMemory`**（约束 #6）
- **改哪些文件**：`storage/schema.ts`、`memory/memory-repo.ts`、`memory/scorer.ts`、`memory/temperature.ts`、`memory/manager.ts`、`context/memory-integration.ts`、`agent/agent-instance.ts`、新增 `memory/memory-feedback-repo.ts`
- **验证**：`pnpm --filter ./packages/agent-runtime test -- src/memory` + `src/storage/schema-v47-v48.test.ts`
- **完成标志**：迁移后旧行 `exposure_count = use_count`；连续注入 10 轮 `utility_count` 与 recencyBonus 均不变；`memory_usage_feedback` 行数 > 0

### P1-5 判定结论（2026-09-18 执行）

**结论：`contribution_score` 这个代理不可用，命中率远低于 70% 门槛。**

抽样：`--exclude-probes` 后随机抽 50 条（跨 09-17 09:37 → 09-18 08:29、37 个会话）。

| 指标 | 值 |
|---|---|
| 代理判「用上」的条数 | 5 |
| 人工核对**确实用上**的 | 3（#201、#214、#218） |
| 人工核对**误判**的 | **2**（#562、#719） |
| 命中率 | 3/5 = **60%**（分母是样本框，不是判定数） |
| 误判率 | **≥ 40%** |

**两条误判长什么样**（足以说明代理的失效模式）：

```
记忆: 本项目验证用的暗号是「青竹三号」          （16 字，实测的暗号条目）
回复: 文件内容就一行：PROBE-OK-20260918
     这是一个探测/验证用的标记文件，没有别的内容。
代理判: score=0.5, used=1   ← 两者毫无关系，只是都出现了「验证 / 内容 / 一行」这类高频 bigram
```

这正是「bigram 重叠」作为代理的**结构性缺陷**：它测的是**词面重合**，
而「这条记忆真的影响了回复」是**语义因果**。短记忆尤其危险——分母小，
蹭到两三个常用词就够格。

**另一个必须记下的样本量问题**：50 条抽样只对应 **37 条不同的回复**——同一轮的 N 条
注入记忆共用一条回复，彼此的"是否被用上"高度相关。**有效样本量是 37，不是 50**，
按计划「抽 50 条」的字面门槛算，样本其实**不够**。

但 8% 与 70% 的差距大到不依赖精确 n：即便有效样本翻倍到 74，也需要 52 条命中而实际
只有 3 条。**结论稳健。**

**关于 P2-2 的后续动作（删除 `MemoryEvolution`）**：计划 §239 写明不满足则删除。该删除
是破坏性且影响面不小（`memory-evolution.ts` / `memory-ranking-model.ts` /
`memory_ranking_weights` 表），**待确认后执行**，不在本次判定内。

1. `findReply` 取「反馈时刻之后的第一条回复」太天真——#288 那条的回复是「我恐怕得先纠正

### 注入侧的三项改动（2026-09-18）

这几项不在原计划范围内，是排查「模型读错记忆」时逐层挖出来的，记在这里免得与
`检索` 相关的结论下次被重新发现。

**① 注入选取的席位数：24h 免门控席位 5 → 2。** 原值 5 时，24 小时内的条目（学习沉淀、
日终顺延、日常收尾）会**免相关性门控**占掉 5 个席位。实测 25 条标注查询：

| 配置 | 期望命中 | 无误注入 |
|---|---|---|
| 席位 5（原值） | 17/25 | 22/25 |
| **席位 2（现值）** | **22/25** | 22/25 |
| 席位 0（全关） | 5/25 | 25/25 |

端到端复验：`tocc-sync` 那轮现在同时注入 `060cdafe`（陈旧快照）与 `851dc264`（结案结论），
此前只注入陈旧的那条、模型于是照过时结论作答。

**② 相关性门槛未动，是实测决定不动。** 同期测了把 `RELEVANCE_GATE_THRESHOLD` 从 .15
提高：.30 → 命中掉回 17，.45 → 崩到 12。与下面的诊断一致——提高阈值会误杀
「关键词不重合但确实相关」的查询（如「tomcat8580 上部署了什么应用」）。

**③ 相关性度量换算法：实测无改善。** 用户提出「相关性不一定可靠，问题和内容关键词
很难对应上」，把这个直觉变成了数字（231 条真实语料）：

- 相关项与无关项的 overlap **中位排名几乎相同（8 vs 9）**，top1 命中仅 12/24
- 三种度量并排跑：现状 12/24、idf 加权 14/24、判别词过滤 12/24——**都没有改善排序**
- 根因：语料是**单用户单项目**，最高频 token 是 `09(104) 2026(98) 用户(92) 数据(63) 排查(43)`。
  判别词在这里根本不判别——不是算法不够聪明，是语料本身同质

**④ 乘法打分：实测更差，未启用。** 曾假设「把 relevance 从加法项改成乘法因子」能让
强相关的老条目压过陈旧的高 importance 条目。实测相反：

| | 期望命中 |
|---|---|
| 加法（现状） | 17/25 |
| 乘法 | 16/25 |
| 加法 + 席位2 | **22/25** |
| 乘法 + 席位2 | 21/25 |

机制：加法是**固定加项**（base 小时相对增益极大），乘法是**比例缩放**，对相关性的奖励
**弱于**加法。`relevanceMode` 开关保留（可复验），默认仍是 `additive`。

### P2-2 为什么是「明确延期」而不是按原文删除

计划原文写的是「`memory_usage_feedback` 累积 ≥ 200 行则接线，否则**删除**代码与表」。
这条阈值是在 P0-4 之前写的——当时那张表**没有生产者**，0 行是必然，删除是对的。

现在情况变了：P0-4 已给它接上生产者，74 行并在增长。此时删除会同时毁掉两样东西：
P1-5 的判定依据、以及这套反馈唯一的消费路径。

**结论**：保留，但把决策条件显式写死，避免它变成"永久悬置"：

- **触发条件**：`memory_usage_feedback` ≥ 200 行 **且** P1-5 抽样判定代理命中率 ≥ 70%
- **满足** → 接线 `MemoryEvolution`（`autonomous/memory-evolution.ts`），把 `scoreMemory`
  的 `useCountBonus` 输入切到 `utility_count`
- **不满足**（样本够了但命中率 < 70%）→ 删除 `MemoryEvolution` / `memory-ranking-model`
  与 `memory_ranking_weights` 表；反馈表保留为纯观测（它已服务 P1-5 与健康检查）
- **检查方式**：`node scripts/memory-feedback-sample.mjs` 会直接打印当前行数与是否达门槛
