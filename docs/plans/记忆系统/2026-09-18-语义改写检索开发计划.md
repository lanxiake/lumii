## 0. 两处决定方案选型的现状（写计划前先核实的）

### 0.1 既有范例：wiki 侧已跑通「FTS + 向量 + RRF」全链路

计划**不重新发明**，直接复用这套已上线的结构：

| 组件 | 落点 | 状态 |
|---|---|---|
| 向量存储 | `wiki_source_embeddings(source_id, agent_id, user_id, model_id, dims, embedding, content_hash, updated_at)` | 生产在用 |
| 融合 | `mergeSourceHybridRanks({ftsIds, vectorIds, sourceById})` — RRF + `0.01 × use_count` 微调 | 生产在用 |
| RRF | `reciprocalRankFusion(lists, k=60)` | 生产在用 |
| 语料构造 | `buildVectorCorpus()` — `title + summary + 主题路径`，**硬上限 300 字** | 生产在用 |
| 余弦检索 | `WikiSourceVectorIndex.searchSimilar()` — 线性扫描 | 生产在用 |

**直接对照的三条既有决定**（都被复用，不重新论证）：
1. **不编码全文**——`VECTOR_CORPUS_MAX_CHARS = 300`。理由是"长文压成单向量会被平均，
   且吸入噪声反而污染全库余弦"。宫殿段平均 1714 字、最长 94479，**同一条纪律必须适用**。
2. **不设余弦阈值**——只做 RRF。§3.1 的实验数据（正确项与 top-1 差距常为 0.0000）
   是这条纪律的**新证据**。
3. **embedder 为 null 即整体禁用**，由调用方写降级原因，**禁止静默降级**。

### 0.2 开关现状：wiki 向量**默认是开的**

## 1. 目标与验收

**目标**：让「用户措辞与记忆措辞不重合、但语义相关」的查询能被检索到，**且不伤害精确查询**。

**验收（硬指标，见 T1）**：
- 语义类 Recall@5 **提升 ≥ 20 个百分点**
- 精确类 Recall@5 **下降 ≤ 2 个百分点**
- 两条同时满足才接线（T3）；否则停在 T2 出结论

## 2. T0 · 建对照评测集（**前置，未完成不得进 T1**）

### 2.1 为什么必须先做

§3 的实验是 **n=9**，够推翻旧结论（n=4），**不够证明新方案有效**。
当前分类的样本量：

| 类别 | 现有 | 目标 | 缺 |
|---|---|---|---|
| 语义改写 | 4 | ≥10 | 6 |
| 同义词错配 | 3 | ≥10 | 7 |
| 精确主题（对照） | 3 | ≥10 | 7 |

### 2.2 产物

`docs/test/memory-eval/semantic-eval-set.json`，字段：

```jsonc
{
  "id": "s07-pool",
  "category": "同义词错配",        // 语义改写 | 同义词错配 | 精确主题
  "query": "数据库连接池初始化失败怎么办",
  "expect": ["HikariCP"],          // 必须能**区分两条具体内容**
  "reject": ["..."],               // 可选，明确不该出现的
  "note": "用户说「连接池」，库内写 HikariCP/maxActive"
}
```

**判据纪律（踩过两次的坑，必须写进每个 note）**：
- expect 不能只测"某个词在不在"。`injection-eval-set.json` 第一版把 `i01` 的
  expect 写成 `["工单断流故障"]`，结果**陈旧条目靠"见同项目『…』条目"这句提及就命中**
  ——测的是子串，不是正误。
- 每个 expect **必须先脚本校验字面量在库中存在**。`eval-set.json` 曾有 5 条假失败，
  `q14` 的 gold `pnpm` 在库里 **0 次命中**——那是评测集的错，不是系统的错。

### 2.3 退出点

样本凑不齐（如同义词错配在真实语料里确实罕见）→ **记录并按现有 n 出结论**，
在结论里写明 n 与置信边界。**不得为了凑数编造查询**。

## 3. T1 · 离线跑分

### 3.1 产物

`scripts/semantic-eval.mjs`（三组并排、分类别报）：

- 分类别报 R@5：同义类 / 语义类 / 精确类，**整体数字会把「精确掉了、语义涨了」平均掉**
- 同时报**精确类降幅**（融合最常见的事故是把本来对的挤下去）

### 3.2 语料口径（与线上一致，不得自创）

| 项 | 取值 | 依据 |
|---|---|---|
| 向量语料 | `content.slice(0, 300)` | 同 `VECTOR_CORPUS_MAX_CHARS` |
| 前缀 | 查询 `query:` / 文档 `passage:` | E5 约定 |
| 归一化 | mean pooling + L2 | `wiki-transformers-embedder.ts` |
| 候选 | 线性余弦全表扫描 | 291 条实测 <10ms |

### 3.3 判据

| 结果 | 处置 |
|---|---|
| 语义类 +≥20pp **且** 精确类 −≤2pp | 进 T3 接线 |
| 语义类有提升但精确类降幅 >2pp | 转「仅召回扩展」，不参与排序 |
| 语义类提升 <20pp | **停**。记录结论并关闭立项 |
| 纯向量反而全面劣于 BM25 | 同上，且**这是对 n=4 旧结论的最终确认**（这次有评测集支撑） |

### 3.4 跑分结果（2026-09-18 执行）

跑分台 `scripts/semantic-eval.mjs`（三组并排、分类别报），对照集 `semantic-eval-set.json`
（同义 7 / 语义 3 / 精确 5）。**5 次复跑逐位一致**，数字确定。

| 类别 | bigram | vector | **RRF** |
|---|---|---|---|
| 同义词错配 | 4/7 | 5/7 | **5/7** |
| 语义改写 | 1/3 | 1/3 | **3/3** |
| **精确主题（对照）** | **5/5** | **5/5** | **5/5** |
| 合计 | 10/15 | 11/15 | **13/15** |

**判据核算**（§3.3 的门槛）：
- 语义类（同义+改写 10 条）：bigram 5/10 → RRF **8/10**，**+30pp** ✅（要求 ≥20pp）
- 精确类：5/5 → 5/5，**−0pp** ✅（要求 ≤2pp）
- **两条同时满足 → 进 T3**

### 3.5 逐条明细与三条失败的性质

| 查询 | bigram | vector | 说明 |
|---|---|---|---|
| `s01` 线程泄漏→`goroutine 泄漏` | #17 | **#2** | 纯错配，向量完胜 |
| `s05` 不在白名单→`is blocked because of many connection errors` | #8 | **#1** | 用户转述现象 vs 工具原文 |
| `s09` 打分偏低→`feedback≤0.35` | #4 | **#1** | 口语 vs 符号 |
| `s07` AI 腔调→`去 AI 味` | #16 | #6 | 两者都不在前 5，但向量更近 |
| `s08` 别硬答→`先承认没底` | #12 | #9 | 均未命中，**真失败** |
| `s10` 两边都改了→`三方裁定` | #4 | **#80** | 均未命中；**向量明显更差** |
| `s06` pnpm | MISS | MISS | **语料缺失**（库里 0 次），任何方案都不该算失败 |

**三条未命中的性质不同，接线后要分开看**：
- `s06` 不是检索问题——库里根本没有这条记忆。
- `s08`/`s10` 是真失败，但**向量并未劣于 bigram**（`s10` 是向量更差、`s08` 略好）。
  RRF 的价值在于「两边至少有一边能找到时能融合」，这两条是两边都找不到。

### 3.6 建集子时发现的旧评测缺陷（重要）

**`eval-set.json` 的 `q13-paraphrase` 从未测到它以为在测的东西。**

该查询是「用户不想看到满篇黑话和抽象词」，gold 标 `['专业术语','难以理解','AI味','生动']`。
实测这四个字面量在库里的分布：`专业术语` **0 条**、`难以理解` **0 条**、`抽象词` **0 条**、
`AI味` **1 条**——而那唯一一条是**二十四史课程网页模板**，正文只在文风要求里顺带写了
一句「禁黑话、去 AI 味」，整条讲的是 CSS 布局与讲义生产流程。

也就是说：这条「语义改写」查询测的是**「能不能撞到一句出现在无关条目里的措辞」**。
评审 §2.5.2 那个 n=4 的「向量未强于 BM25」结论，一定程度上就是被这类 gold 标出来的。

**同类的坑在本集子里踩了两次，都已修正**（详见各条 note）：
- `s04` 初版查询写成「那个工具服务起不来是什么原因」→ 向量 #118。
  查下来是**我的措辞不含关键线索**：真实用户的 946 条消息全是「任务+对象+问题」的
  精确结构，不会有这种含糊指代。**含糊指代测的是运气，不是检索。**
- `s07` 的 expect 改了两次：`AI味太浓`（周复盘里的用户原话，属顺带提及）→
  `去 AI 味`（《二十四史讲义写作规矩》，**主题就是它**）。区别不只在空格，
  而在「用户在哪抱怨过」vs「当时定下的规矩是什么」——检索该找的是后者。

## 4. T2 · 决策与记录

### 4.1 决策（2026-09-18）

**T1 达标 → 进 T3 接线。** 依据是 §3.4：语义类 +30pp（门槛 20pp）、精确类 −0pp（门槛 2pp）。

### 4.2 一条必须在 T3 里兑现的保留意见

**打到达标线的是 15 条查询的小集子，不是 100+ 条的稳健基准。**
`+30pp` 的分子只有 3 条（5/10 → 8/10）——**一条翻转就是 ±10pp**。三条改善分别是：
`s01`（#17→融合内）、`s05`（#8→融合内）、`s09`（#4→#1）。

所以 T3 的开关**必须默认关**（§5.4 已定），且上线后需要**用真实会话再验一轮**：
真实使用的查询分布与这 15 条未必同形，`+30pp` 在新样本上可能明显缩水。
这一点写在这里，避免接线后把它当成"已验证"。

- 评审 §2.5.2 的修正标注已指向本立项（2026-09-18）

## 5. T3 · 接线（仅在 T1 达标时执行）

### 5.1 分层落点（沿用宫殿计划的边界，零模型依赖）

```
apps/windows (宿主)
  └─ createTransformersE5Embedder()   ← 已有，直接复用
       ↓ 注入
packages/agent-runtime (runtime)
  └─ PalaceVectorIndex                ← 新增，仿 WikiSourceVectorIndex
       ├─ upsertDrawer(drawerId, content)
       └─ searchSimilar(query, limit)
  └─ PalaceRepo.searchDrawers()       ← 加 hybrid 分支，调 mergeHybridRanks
```

**`agent-runtime` 不引入 transformers**——嵌入器由宿主注入，与 `WikiSourceVectorIndex`
完全同构（它的 `embedder` 就是注入的 `WikiEmbedder | null`）。

### 5.2 表（V51）

```sql
-- 仿 wiki_source_embeddings，字段一一对应
CREATE TABLE IF NOT EXISTS palace_drawer_embeddings (
  drawer_id     TEXT PRIMARY KEY,
  agent_id      TEXT NOT NULL,
  user_id       TEXT NOT NULL,
  model_id      TEXT NOT NULL,
  dims          INTEGER NOT NULL,
  embedding     BLOB NOT NULL,
  content_hash  TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_palace_emb_scope
  ON palace_drawer_embeddings (agent_id, user_id, model_id);
```

**建新表而非复用 `palace_drawer_vectors`**：宫殿计划附录预留的那个名字从未建表
（Phase 2 未启动），不必为一个不存在的表做兼容。

### 5.3 接线点（三处，与 wiki 侧一致）

| 时机 | 动作 | 落点 |
|---|---|---|
| 归档写入 | `upsertDrawer` 成功后 `upsertEmbedding` | `palace-backend.ts` |
| 启动 | 索引健康检查（条数不一致则后台补） | 复用宫殿既有的启动自愈模式 |
| 检索 | `searchDrawers` 内做 RRF | `PalaceRepo` |

**索引开销实测**：993 条 × 32ms ≈ **32 秒**（一次性）。必须先做**后台**补齐，
不能阻塞启动——宫殿既有的"启动健康检查自动重建"就是这个模式。

### 5.4 开关

`LUMII_PALACE_VECTOR`，**默认关**（与宫殿计划 Phase 2 的既定约定一致；
也不同于 wiki 的默认开——wiki 已在付这笔成本，宫殿是新账）。

### 5.5 与「钉入」的关系（必须一起验）

2026-09-18 刚加的 `pinnedIds` 机制（注入指针保送进候选池）**走的也是候选排序**。
向量融合会改变排序，**可能把钉入项挤出去**。

- 单测：钉入项在 hybrid 模式下仍在结果里
- 端到端：跑 `probe-pointer-usage.mjs`，`钉入回传` 不得从当前的 2/3 掉下来

## 7. 不可违反的约束（复用既有，逐条对应）

1. **零模型依赖**：`agent-runtime` 不 import transformers（`WikiEmbedder` 注入模式）
2. **不编码全文**：300 字上限，长文精确匹配仍归 FTS
3. **不做**：chunk 分块向量、ANN 索引、独立向量库（993 条，暴力余弦足够）
4. **禁止静默降级**：embedder 为 null → 明确写 `degradeReason`，不悄悄退回纯 FTS
5. **换检索栈要有数据依据**：T1 就是这条纪律的产物，**T1 不达标就不接线**
6. **复用而非重写**：RRF / 余弦 / 语料构造 / 存储表结构，全部照 `wiki-source-vector.ts`
