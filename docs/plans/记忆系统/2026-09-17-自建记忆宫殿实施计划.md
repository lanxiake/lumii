# 自建记忆宫殿实施计划（去 Python 依赖）

> 日期：2026-09-17
> 设计来源：[`../../design/记忆系统/2026-09-17-记忆系统评审.md`](../../design/记忆系统/2026-09-17-记忆系统评审.md) §4.6
> 范围：用 SQLite + FTS5 自建记忆宫殿，替换 MemPalace（Python MCP）；**分两阶段，本计划主体是 Phase 1，不含向量**
> 原则：宿主侧纯替换（runtime 接口不变）、零新增依赖、不碰 `agent_memories` 表结构

---

## 1. Goal（一句话目标，可验证）

> **把记忆宫殿的存储与检索搬进 `agent-runtime.db`，使 `memory_search` 不再依赖 Python 运行时；`palace_drawer_id` 覆盖率从 4/171 提升到 >90%，检索端到端 P95 < 150ms。**

验收方式：卸载/移走 `~/.lumii/runtimes/python-embed` 后，`memory_search` 仍能命中已归档段原文，且 `memory_read` 可按 id 读回。

### 1.1 为什么分两阶段

评审 §2.5.2 的实测结论：本地 e5-small 向量在本语料上**并未强于 BM25**（4 组对照打平 2、各胜 1），且 top-1 余弦全落在 0.873–0.893、绝对值无区分度。因此：

| 阶段 | 内容 | 依据 | 本计划 |
|---|---|---|---|
| **Phase 1** | SQLite + FTS5（BM25）承载段原文，替换 MemPalace | 工程收益确定：去 Python、降延迟、可测可观测 | ✅ 本次实施 |
| **Phase 2** | 向量通道（RRF 融合），开关默认关 | 质量收益未证实，等 P2-1 评测集给数据 | ⏸ 仅留接口与表结构 |

**Phase 1 单独就有完整价值**（今天的替代方案是"Python 未安装 → grep 两个 Markdown 文件"），且代码量约为完整方案的 40%。

## 2. Architecture

### 2.1 模块边界

```
┌─ apps/windows (宿主) ──────────────────────────────┐
│  index.ts      searchMempalace / readMempalaceDrawer│   ← 换实现
│  bridge.ts     archiveMempalaceDrawer               │   ← 换实现
└────────────────────┬───────────────────────────────┘
                     │ 只调 PalaceRepo，不碰 MCP
┌────────────────────▼───────────────────────────────┐
│  packages/agent-runtime/src/memory/                 │
│    palace-repo.ts    PalaceRepo（CRUD + 检索）       │  ← 新增
│    palace-index.ts   FTS 维护（仿 memory-index.ts）  │  ← 新增
└────────────────────┬───────────────────────────────┘
                     │
              agent-runtime.db
        palace_drawers / palace_drawers_fts
```

**接口契约不变**——`SegmentMemoryPipelineDeps.archivePalace`（`segment-memory-pipeline.ts:60-63`）与 `ArchivePalaceMeta`（`:22-37`）保持原样，宿主只换实现，runtime 零改动。

### 2.2 数据流

**写入**（沿用现有链路，不改时序）：

```
段关闭 → SummarizationQueue → 回读原文 → LLM 总结 → 写 agent_memories
                                              ↓
                                    archiveToPalace(segId, convId)   ← 已有
                                              ↓
                            宿主 archivePalace(text, meta)          ← 换实现
                                              ↓
                          PalaceRepo.upsertDrawer()  →  返回 drawer_id
                                              ↓
                     回填 memory_segments.palace_drawer_id
                     + agent_memories.palace_drawer_id（按 source_segment_id）← 已有
```

**检索**：

```
memory_search(query, limit)
  ├─ 通道 1 work-memory : AgentMemoryRepo.search()      ← 评审 P0-1，另一份工作
  ├─ 通道 2 palace      : PalaceRepo.searchDrawers()    ← 本计划
  └─ 通道 3 profile/scene: user-memory.md + 场景文件
```

`searchDrawers` Phase 1 实现：`bigram 分词 → FTS5 MATCH（OR 短语，引号转义）→ ORDER BY bm25()`。与 `AgentMemoryRepo.search()`（`memory-repo.ts:569-591`）同构，含 LIKE 回落与 FTS 缺失保护。

### 2.3 数据模型（V49）

```sql
CREATE TABLE IF NOT EXISTS palace_drawers (
  drawer_id       TEXT PRIMARY KEY,       -- deterministicDrawerId(wing, room, content)
  agent_id        TEXT NOT NULL,
  user_id         TEXT NOT NULL,
  conversation_id TEXT,
  segment_id      TEXT REFERENCES memory_segments(id) ON DELETE SET NULL,
  wing            TEXT NOT NULL,
  room            TEXT NOT NULL,
  content         TEXT NOT NULL,          -- 段原文（最长实测 94473 字符）
  char_count      INTEGER NOT NULL,
  created_at      TEXT NOT NULL,
  deleted_at      TEXT
);
CREATE INDEX IF NOT EXISTS idx_palace_drawers_scope
  ON palace_drawers (agent_id, user_id, deleted_at);
CREATE INDEX IF NOT EXISTS idx_palace_drawers_segment
  ON palace_drawers (segment_id);

-- 派生索引：独立虚表 + 应用层维护（与 agent_memories_fts 同构，不用触发器）
CREATE VIRTUAL TABLE IF NOT EXISTS palace_drawers_fts USING fts5(content, content_bigram);
```

**为什么 FTS 用独立表而非 external-content 表**：与 `agent_memories_fts`（`memory-index.ts:1-14`）保持同构。中文需要应用层 bigram 预分词，SQL 触发器做不到，维护点本来就在应用代码里；独立表还避免了 rowid 对齐的隐式约束。

**Phase 2 预留**（本计划不创建，仅记录形态）：

```sql
CREATE TABLE palace_drawer_vectors (
  drawer_id TEXT PRIMARY KEY REFERENCES palace_drawers(drawer_id) ON DELETE CASCADE,
  model_id TEXT NOT NULL, dims INTEGER NOT NULL,
  embedding BLOB NOT NULL, content_hash TEXT NOT NULL, updated_at TEXT NOT NULL
);
```

| 项 | 决定 |

## 4. Global Constraints（不可违反的硬约束）

1. **不改 `agent_memories` 表结构**。本计划只新增 `palace_*` 表。
2. **`drawer_id` 生成规则不变**：`deterministicDrawerId(wing, room, content)`（`content-address.ts:32-34`），16 位 hex。
3. **FTS 维护走应用层**，与 `memory-index.ts` 同构；不用 SQL 触发器。
4. **日志不落用户原文**：只记 `drawer_id`、长度、条数。
5. **归档失败不影响记忆写入主流程**：沿用 `segment-memory-pipeline.ts:209-214` 的 catch 语义。
6. **未回填不记账**：只有真写进库才回填 `palace_drawer_id`（沿用 `:201-206` 语义：宁可没有 id，也不记一个查不到的）。
7. **向量通道默认关闭**（Phase 2 才开），且必须在 Phase 1 验收通过后单独评审。
8. **`palace_drawers.deleted_at` 必须有生产者**（评审 §4.4 的教训）：本计划在 `PalaceRepo.deleteById()` 里写它，不做空墓碑。

## 9. 风险与缓解

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| **R1** | 已有 4 条 `palace_drawer_id` 由 Python 侧 `make_drawer_id_from_content` 生成，与 TS 侧 `deterministicDrawerId` **算法可能不同** | 回填后旧 id 指向不存在的 drawer | 旧宫殿本就不可用（覆盖率 2%），**回填时整体重算并覆盖**；T4 的 dry-run 先比对 4 条旧 id 与新算法的差异并记录 |
| **R2** | 单段原文最长 94473 字符 | FTS 行过大影响查询 | SQLite 无单值硬限；FTS 只索引 `content` 与 `content_bigram` 两列，测 `searchDrawers` 在最大段上的 P95 |
| **R3** | 回填期间用户在用，可能并发写同一段 | 重复行 / id 漂移 | `drawer_id` 内容寻址天然幂等；`upsertDrawer` 用 `ON CONFLICT(drawer_id) DO UPDATE` |
| **R4** | 切回 MemPalace 时 id 不一致 | 回退后 `memory_read` 读不到 | 开关是一次性方向决策；回退只保证「新增段走 MemPalace」，不保证旧 id 可读——写进开关的注释 |
| **R5** | Phase 2 向量通道质量不达标 | 白做 | **已用实测前置排除**（评审 §2.5.2）；Phase 2 必须由 P2-1 评测集的数据启动 |
| **R6** | 段原文含敏感内容落进新表 | 隐私面扩大 | 与原 MemPalace 同源同内容，无新增暴露面；`palace_drawers` 纳入云同步排除清单（原文不跨设备） |

### 11.3 与计划的差异

**#16 切换点从 `index.ts` 挪到 `bridge.ts`。** 计划写「`index.ts` 的三个回调换实现」，
但 `LocalDatabase` 由 `AgentRuntimeBridge` 私有持有，`index.ts` 注入的是闭包、拿不到 DB 句柄。
改为在 bridge 构造期用 `withBuiltinPalace(config, localDb)` 包一层；同时把三个回调从
`searchMempalace` / `readMempalaceDrawer` / `archiveMempalaceDrawer` 改名为
`searchPalace` / `readPalaceDrawer` / `archivePalaceDrawer`——后端已经不是 MemPalace，
留旧名会让下一个读代码的人以为走的还是 Python。

**#17 `segment_id` 去掉了外键。** 计划写的是 `REFERENCES memory_segments(id) ON DELETE SET NULL`。
写测试时直接踩到：`FOREIGN KEY constraint failed`。生产上这条路径真实存在——归档跑在
**异步**总结队列里，用户完全可能在归档落地前删掉会话，有外键就会让那次归档失败、
**原文丢失**，而存档最不该发生的就是这个。原文是自足的内容寻址对象，`segment_id` 只是溯源信息。

**#18 `loadSegmentText` 只认扁平 `text`，助手说过的话全被漏掉。** 这不在计划范围内，
是回填 dry-run 看样例时发现的：助手消息落库是 `assistant_parts`（parts 为唯一真相），
而 `loadSegmentText` 判的是 `parsed.type === "text"`。真实库抽样：多轮段 5 条消息里 2 条被静默丢弃
（整体字符数只差 0.4%，因为占比最大的恰是「单条长文」段——**这个缺陷在总量指标上看不出来**）。
影响面不止宫殿：**段落总结的输入一直也是残的**。已提为共享函数 `extractMessageText`
（thinking / tool part 不参与），`loadSegmentText` 改走它，并补回归用例。

**#19（2026-09-18 追加）漏切了第四个写入点，旧宫殿一直在增长。** 计划写「宿主三个回调换实现」，
`withBuiltinPalace` 也照此覆盖了 `searchPalace` / `readPalaceDrawer` / `archivePalaceDrawer`。
但每轮助手回复还有一条**即时归档**路径：`index.ts` 的 `onConversationEnd`（`wing='conversations'`、
`room=会话 id`），它不在 config 回调表里，是直接写在 ipc handler 上的。结果：切换后旧 Python
宫殿**仍在被写入**（2026-09-18 实测当天 09:54 还有新行），而那批内容在自建检索里永远搜不到
——写进去、读不到，正是 P2-3 要消灭的那种故障。

两处修复：
1. `withBuiltinPalace` 接管 `onConversationEnd`（先转发宿主原回调，自主进化的轮次结算挂在上面），
   `index.ts` 那一侧只保留 `LUMII_PALACE_BACKEND=mempalace` 的分支。
2. 存量搬家：`scripts/palace-import-legacy.mjs` 把旧 sqlite 的 234 条文档按 `parent_drawer_id`
   拼回 **161 组**后导入（逐条搬会把一条回复拆成互不相干的几行——旧宫殿给超长内容切过 chunk）。
   实测导入后宫殿活跃行 73 → 234，启动健康检查自动重建索引 234/234。

> 这条值得单记：**"换后端"要按"所有写入点"清点，不是按"所有回调"清点。** 回调表是显式的，
> 漏掉一眼可见；而绕过回调表直接写在 handler 上的那一处，只有对着旧实现 grep 才发现得了。

**#20（2026-09-18 追加）助手消息的历史缺口：63 万字符从没进过宫殿。** 修好漏切点后按内容寻址
逐条核对，932 条助手消息里只有 **59 条**能对上宫殿里的行——也就是说每轮归档这条路径**历史上
一直在漏**（不是"切换后漏"，是从头就漏）。缺口 690 条 / 61 万字符，时间跨度 8-28 → 9-18。

补法：`scripts/palace-backfill-messages.mjs`（与 `palace-backfill.mjs` 同一套纪律——默认
dry-run、写前留痕、`ON CONFLICT DO NOTHING`、不写 FTS 索引交给启动健康检查）。

**取文口径必须与线上逐字一致，这里踩了两次**：

1. **thinking 残留**：更早期的消息把模型独白写在 text part 里（`独白…</think>\n\n正文`），
   现行持久化已用 `parseThinkTagsFromRaw` 把它拆成独立 part，但存量没这个拆分。照抄 parts
   会把"模型的内心话"归档——检索命中后读回的是一段独白。实测 932 条里 10 条带该标记。
2. **分隔符**：线上是 `parts.map(p => p.text).join('')`（`bridge-agent-instance-events.ts:112`
   的 `assistantTextFromParts`），**不 trim、无分隔符**。我先写成 `join('\n')` + 逐条 trim，
   60 条样本里 32 条算出**不同的 drawer_id**——同一轮内容会在库里出现两行。改成 `join('')`
   后 924/932 一致，仅剩的 8 条差异正是上面那批含 think 的旧格式（本就该被剥离）。

> 内容是**寻址的一部分**，所以"取文口径"不是实现细节而是接口。回填脚本里那段 `join('')`
> 看起来像个可以"顺手改整洁"的地方，改一下就静默产生重复行——已在脚本注释里写明不可动。

**FTS 单列而非计划里的两列（`content` + `content_bigram`）。** 原文在 unicode61 下是
一整个巨型 token（中文连续串不切分），索引里用不上，只把体积翻倍；要原文按 rowid 回主表取即可。
与 `agent_memories_fts` 保持同构，两处维护逻辑一致。

**多了一个体检项，且它的第一版判据是错的（真实数据纠正）。** 计划没要求体检项，但 P1-3 的教训是
「计数没有消费者等于没有计数」——宫殿的两种失败（覆盖率 2.3%、索引与主表不一致）全程不报错，
`memory_search` 只是返回空，看起来像「过去没聊过这事」。

第一版判据写的是「近 7 天有已总结但未归档的段 → issue」，单测全绿。**真实库上一跑就是假警报**：
它报「近 7 天 18 个段没归档」，逐个查下来 17 个是 **2–49 字符的碎段**，是换自建后端**之前**
（旧 Python 后端）留下的欠账，跟「现在坏没坏」无关。

**历史欠账推断不出当下是否故障。** 改成在**写入点计数**：`SegmentMemoryPipeline` 记
`attempted / archived / notStored / failed / lastError`（`getPalaceStats()`），体检只认两类硬信号——
索引条数不一致、本进程归档失败计数 > 0。覆盖率只作为**状态数字**报出，不参与判定。

> 这条差异值得单独记：判据本身也要用真实数据验，不然就是「用一个看起来很合理的推断，
> 造一个永远报警的假警报」。单测能证明判据按预期执行，证明不了判据**对不对**。

### 11.4 已知特性（不是缺陷，写下来免得下次重新发现）

- **OR 语义召回**：查询按 bigram 切成 OR 短语，所以「完全不存在的词」这类查询也会命中若干条
  （命中的是「完全」「存在」等常见 bigram）。这与工作记忆通道 `AgentMemoryRepo.search()`
  完全同构——一致性优先于局部最优。要收紧得两处一起改，且需要评测集给依据。
- **纯语义改写搜不到**：P2-1 评测集里唯一漏掉的查询就是语义改写（「装依赖走更快的包管理器」→ `pnpm`）。
  这是 BM25 的天生盲区，也是 Phase 2 唯一的启动理由——但 §2.5.2 的实测显示向量并未强于 BM25，
  故选 Phase 2 未启动。
- **宫殿 drawer 的 `created_at` 两种口径**：回填写入的是**段的创建时间**，线上归档写入的是
  **归档时刻**。前者对检索更有意义（时间序），后者是事实时间戳，暂不统一。
- **`memory_search` 的通道配额是「先到先得」**：三个通道共用 `limit`，每个通道只在
  `hits.length < limit` 时才跑（`bridge-tool-registrar-integration.ts:249`）。工作记忆条目多，
  常把默认 `limit=10` 占满，于是**宫殿通道整个被跳过**——`providers.palace` 报 0，看起来像
  「宫殿里没有」，实际是没查。2026-09-18 实测：同一句 query 一次 `palace:0`，换个词
  `palace:9`。要根治得给通道分配额（如各占 limit/3）或让 `limit` 只管单通道，
  但那会改变 `memory_search` 的返回形状，需单独立项。

### 11.5 覆盖率口径（为什么不是 > 90%）

验收写的 `> 90%` 分母是「`char_count >= 50` 的段」（101 个）。实测 73/101 = **72.3%**，未达。
差额全部来自 **28 个起点消息已不存在的段**：它们的会话被删、消息被清，原文在任何地方都不存在了，
无从归档。按「可归档段」算，覆盖率是 **73/73 = 100%**。

换句话说：**目标里的 90% 假定了每个段的原文都还在**，这个假定不成立。基准数也随之更新——
基线不是「4/171 = 2.3%」，而是「可归档段 4/73 = 5.5%」。
