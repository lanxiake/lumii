> **设计依据**：[../design/性能优化/2026-08-21-性能监控与调用耗时统计方案.md](../design/性能优化/2026-08-21-性能监控与调用耗时统计方案.md)
> **插件规范**：[../../standards/plugin-development-standards.md](../../standards/plugin-development-standards.md)

## 1. 为什么要改

性能监控的目标是**定位资源占用高的函数/接口/慢查询**，不是记录常规运行数据。
现版本把两类东西混在一份日志里，慢信号被淹没。

2026-10-21 一天 `~/.lumii/logs/perf/perf-2026-10-21.jsonl`（2.4MB / 5480 条）的构成：

| 事件 | 条数 | 占比 | 结论 |
|---|---:|---:|---|
| `renderer.memory`（每分钟） | 1344 | 24.5% | 常规记录，删 |
| `memory.snapshot`（每分钟） | 1329 | 24.3% | 常规记录，删 |
| `ipc.aggregate`（每 60s × 每通道） | 2280 | 41.6% | 常规记录，删 |
| `startup.phase` | 385 | 7.0% | 保留（每次启动 11 阶段） |
| **`ipc.slow`** | **142** | **2.6%** | **核心信号，保留并扩展** |

改完后同一台机器一天预计 150–500 条、百 KB 级，且每一条都是「值得看一眼」的事件。

## 2. 采集口径（改后）

只记**超过阈值**的事件。常规调用只在内存里累计计数，用于页面顶部的总量展示，**不落盘**。

| kind | 触发条件 | name 字段 | detail |
|---|---|---|---|
| `ipc.slow` | IPC 耗时 > 200ms | channel | — |
| `ipc.error` | IPC 抛错 | channel | `error` |
| `db.slow` | 单条 SQL > 50ms | **SQL 模板**（字面量归一为 `?`） | `db`、`op`(run/get/all/exec) |
| `main.loop.lag` | 事件循环阻塞 > 100ms | — | `lag`、`inflight`（当时在跑的打点函数名） |
| `renderer.longtask` | 长任务 > 50ms | 任务 attribution 或 `unknown` | `entryType` |
| `renderer.interaction` | 关键交互耗时 > 500ms | 交互名 | — |
| `memory.spike` | 主进程 RSS > 2GB，或 10 分钟内涨幅 > 300MB | `main` / `renderer` | `rss`、`heapUsed` |
| `startup.phase` | 每次启动 | 阶段名 | — |

**删除**：`ipc.aggregate`（60s 窗口）、`memory.snapshot`（每分钟）、`renderer.memory`（每分钟）。

### 2.1 关键交互清单（固定三个）

`send-message`（发送 → 首 token）、`switch-session`（点击 → 消息可见下一帧）、
`open-workspace-panel`（展开工作台 → 下一帧）。加别的会让口径变宽，故写死。
首屏渲染不在此列：它由 `startup.phase` 与 `renderer.longtask` 分别覆盖。

### 2.2 隐私

只记函数名 / channel / SQL 模板 / 耗时。**不记**参数、消息内容、模型输入输出、URL 查询串。
SQL 模板归一：把 `'...'`、`"..."`、数字字面量替换成 `?`，压缩空白。

## 3. 数据模型：统一成一种事件形状

所有慢事件共用一条结构，日志、页面、复制三处口径一致（旧 `ipc.slow` 的 `args: []` 从来是空的，删掉）。

```ts
// apps/windows/src/shared/performance.ts
export type PerfEventKind =
  | 'ipc.slow' | 'ipc.error' | 'db.slow' | 'main.loop.lag'
  | 'renderer.longtask' | 'renderer.interaction' | 'memory.spike'

export interface PerfEvent {
  timestamp: number
  kind: PerfEventKind
  /** 维度标识：channel / SQL 模板 / 交互名 / 任务名 */
  name: string
  duration: number
  /** 少量补充字段，只放短字符串与数字 */
  detail?: Record<string, string | number>
}
```

`startup.phase` 保持原样（它本来就是「一次性、有阶段名和耗时」的事件）。

**服务契约**（核心 ↔ 插件唯一通路，守卫 ⑪）：`PerfMonitorLike` 增加一个方法

```ts
recordEvent(event: PerfEvent): void
```

不新增 contract 文件——perf 的对外能力本来就只有一个 `PerfMonitorLike`，
再拆一份只会让核心多认识一个契约。

## 4. 采集点接线

### 4.1 主进程 IPC（已有，改形状）

`kernel/measured-handler.ts` 不动。`PerformanceMonitor.recordIpcCall` 内部改为产 `PerfSlowEvent`。

### 4.2 主进程事件循环延迟（兜底）

`perf/index.ts` 的 `apply` 里加 `perf_hooks.monitorEventLoopDelay({ resolution: 10 })`，
每秒读一次 histogram 的 max（resolution 是直方图步长，必须远小于阈值，填 1000 会把一切报成 ~1000ms），超 100ms 落一条 `main.loop.lag`，并带上当前「正在执行的打点函数」。
定时器走 `ctx.effect`，插件停用即停。

> 为什么不全量包 `ipcMain.handle`：全仓有 191 处直连 `ipcMain.handle`、`agent-runtime` 等
> 已走 `createMeasuredHandler` 的重点通道覆盖了主要耗时。全量包裹侵入面过大（旧设计文档 §1 已论证过），
> 兜底交给事件循环延迟——它能抓到所有没列白名单的同步阻塞，代价只是一个 histogram。

### 4.3 慢查询（`packages/agent-runtime`）

`storage/local-database.ts` 的 `prepare/run/get/all/exec` 是**唯一收敛点**，
node:sqlite 与 better-sqlite3 两套实现都从这里出去，包一层计时即可覆盖全部 SQL。

共享包不能依赖 `apps/windows` 的类型，所以走**可空的回调钩子**（依赖注入，零 perf 时零开销）：

```ts
// packages/agent-runtime/src/storage/slow-query.ts
export interface SlowQuerySample { db: string; op: string; sql: string; durationMs: number }
export function setSlowQueryListener(fn: ((s: SlowQuerySample) => void) | null, threshold = 50): void
export function normalizeSql(sql: string): string   // 字面量 → ?，去注释，压空白，截断
```

**钩子在核心侧接线**（`main/index.ts` 的 `wireSlowQueryProbe()`），不在 perf 扩展里。

> 这是实测踩到的坑：perf 是独立 esbuild bundle，`@mtbot/agent-runtime` 会被内联成
> **第二份模块实例**；扩展里注册的监听器写进扩展那份的变量，而真正执行 SQL 的
> `LocalDatabase` 在主进程 bundle 里读的是另一份 —— 一条都记不到，日志里什么都看不见。
> 修法拉了两处：钩子状态挂 `Symbol.for` 全局单例（同 `cloud-sync-contract` 的做法），
> 接线点搬到主进程 bundle 内。回调每次现取容器里的 perf 服务，扩展停用时自然静默。
>
> `shared/performance.ts` 的「正在执行」栈同理挂了 `Symbol.for`，否则探针永远读到空栈。

### 4.4 渲染层

`ui/renderer-perf-probe.ts`（原 `renderer-memory-probe.ts` 改造而来）：

- `PerformanceObserver({ type: 'longtask', buffered: true })` → `renderer.longtask`
- 内存：仍每 60s 采样，但**只在越过阈值或相对上次上报变化超阈值时上报**（`memory.spike`）
- 上报走 preload `performance.recordEvent(event)`

关键交互的计时**不在插件里**：打点在 `send-user-message.ts` / `switch-session.ts` /
`WorkspaceWorkbench` 这些核心位置，而渲染层核心不允许 import 插件实现（守卫 ⑭）。
核心侧新建 `renderer/utils/perf-marks.ts`，直接调 `window.electronAPI.performance.recordEvent`，
perf 停用时该通道不存在，调用静默失败，业务零感知。阈值统一 500ms。

| 交互 | 起点 | 终点 |
|---|---|---|
| `send-message` | `sendUserMessage` 发 `user:send` 之前 | 该会话收到第一条主回复正文增量（`agent:message:delta`，子 Agent 的不算） |
| `switch-session` | `switchSession` 入口 | 状态提交后两帧（缓存命中与冷加载两个分支各一处；被更晚的切换作废时 `abortInteraction`） |
| `open-workspace-panel` | `WorkspaceWorkbench` 的 `open` 变为 true | 两帧后 |

> 「两帧」：第一帧是本次更新的提交，第二帧才真正画出去。只等一帧会把渲染耗时漏掉。

## 5. 页面改造（`ui/PerformanceDiagnostics/`）

页面从「健康度 + 两个趋势图 + 明细」改成**分析用的三块**：

```
┌ 顶部：今日 N 条慢事件 · 最慢 X ms · 磁盘占用 ────────────────┐
├ Tab：明细 │ 排行 ───────────────────────────────────────────┤
│ 明细：时间 | 类型 | 名称 | 耗时(detail 可展开)                  │
│       点行展开 → 完整 JSON + 「复制这条」                        │
│ 排行：按 (kind,name) 聚合 → 次数 / p50 / p95 / max / 合计耗时   │
├ 时间线：按分钟统计慢事件条数（recharts 柱图，与明细同源）        │
└ 工具栏：[类型筛选▾][只显示 > __ms][复制筛选结果 JSONL][打开日志] ┘
```

- **复制**两种：当前筛选结果（jsonl，一行一条）与单条事件（格式化 JSON）。
  走 `navigator.clipboard.writeText`（仓库既有做法）。
- 数据来源：`performance:listEvents({ since })`，主进程把**今日**磁盘日志回放进内存后返回，
  重启前后的事件都能看到；内存里保留最近 N 条，越界回落到磁盘读取。
- 图表守卫：新页面仍在 `CHART_FILES` 名单内（路径不变），颜色只用 `var(--mt-chart-N)`。
- 移除 `recharts` 之外的东西不加依赖。

## 6. IPC 与 preload

| 通道 | 变更 |
|---|---|
| `performance:getSummary` | 新增：返回 `PerfSummary`（今日计数 + 最慢 + 启动阶段 + 内存峰值）；旧 `getReport` 删除 |
| `performance:getHistory` | **删除**，由 `performance:listEvents` 取代 |
| `performance:listEvents` | 新增：`{ since?: number }` → `PerfEvent[]` |
| `performance:recordEvent` | 新增：渲染层上报慢事件（含边界校验，坏值丢弃） |
| `performance:recordRendererMemory` | **删除**（并入 `recordEvent`） |
| `performance:capture` | 保留，改为记一次手动内存现场（不再算常规快照） |
| `performance:openLogFolder` | 保留 |

preload `ElectronAPI.performance` 同步改（AGENTS.md 第 5 条：IPC 三层必须同步）。

## 8. 风险与取舍

| 风险 | 处置 |
|---|---|
| 删掉聚合后趋势图没数据 | 时间线改用慢事件同源统计，不再另采一份数据 |
| 内存只看阈值会丢掉「缓慢爬升」 | 阈值触发 + 每 10 分钟一次涨幅判断；RSS 阈值 2GB 取自 9-15 崩溃复盘 |
| `monitorEventLoopDelay` 的 histogram 占用 | resolution=10ms、每秒只读一次 max；`ctx.effect` 保证停用即释放 |
| 已有用户目录里的旧格式日志 | 回放时按 kind 过滤，不认识的 kind 直接跳过（现有 `asHydratableEvent` 已是这个策略） |
| 页面读取今日全量日志 | 慢事件一天最多几百条，一次读入内存无压力 |

## 9. 不做的事

- 不全量包装 `ipcMain.handle`
- 不做 CPU profile / heap snapshot / 火焰图
- 不上传、不告警、不引入第三方观测依赖
- 不做跨天查询（要查历史直接打开日志目录）

## 10. 真机验证记录（2026-10-29）

环境：本机 dev 实例（`pnpm dev`），真实模型回合（`Qwen3.8-Flash-Next`，`lumii-ui send --wait`）。

### 10.1 采集结果

一次启动 + 一条真实消息（3s 回合）+ 一次设置页浏览，`~/.lumii/logs/perf/perf-2026-10-29.jsonl` 共 29KB：

| kind | 条数 | p50 | p90 | max |
|---|---:|---:|---:|---:|
| `startup.phase` | 22（2 次启动 × 11 阶段） | — | — | — |
| `db.slow` | 13 | 399ms | 1348ms | 6755ms（`PRAGMA quick_check`） |
| `ipc.slow` | 12 | 594ms | 788ms | 823ms |
| `main.loop.lag` | 66 | 276ms | 1003ms | 1884ms |
| `renderer.longtask` | 128 | 56ms | 108ms | 607ms |
| `renderer.interaction` | 4 | — | — | 1179ms（`switch-session`） |

对照改前（2026-10-21 一天 2.4MB / 5480 条，慢事件占 2.6%）：现在**一条日志都是慢事件**，
且 `ipc.aggregate` / `memory.snapshot` / `renderer.memory` 三类一条都没有。

### 10.2 验证到的坑

1. **`monitorEventLoopDelay` 的 `resolution` 是直方图步长，不是上报间隔。** 填 1000 时
   任何阻塞都报成 ~1000ms（实测 5 条全是 999–1011ms，量什么都一样）。改 10ms 后
   分布才有意义（101–1884ms）。
2. **`@mtbot/agent-runtime` 被 perf 扩展 bundle 内联成第二份实例。** 扩展里
   `setSlowQueryListener` 写的是扩展那份变量，主进程 `LocalDatabase` 读的是另一份 ——
   静默一条都记不到。修法：钩子状态挂 `Symbol.for` 全局单例 + 接线点搬进 `main/index.ts`。
   同一坑也适用于 `shared/performance.ts` 的「正在执行」栈。
3. `main.loop.lag` 的 `detail.inflight` 多数为空：dev 实例里阻塞主要发生在未打点的路径
   （数据库同步调用、JIT/GC），只有 `agent-runtime:command` 一条被归因到。生产构建下
   预期更好，但**不要把空 inflight 当成探针没工作**——耗时本身已经记下来了。

### 10.3 页面

`设置 › 隐私与数据 › 性能诊断` 实测可读：顶部「今日慢事件 118 / 最慢 6755ms / IPC 慢 12 共 N」
+ 明细表（时间/类型/名称/耗时）+ 排行 Tab + 按分钟时间线；「复制筛选结果」点了之后
剪贴板里是逐行 JSONL（可直接 `JSON.parse` 每行），单条展开后的「复制这条」输出格式化 JSON。

### 10.4 未覆盖

- 未在打包产物（`dist:win`）上复验；dev 与生产的差异主要在 bundle 产物与 JIT 预热。
- 未做人为注入 60ms 主线程阻塞的行为验证（计划 T5 的验收项），现有证据是真实回合下的观测值。
