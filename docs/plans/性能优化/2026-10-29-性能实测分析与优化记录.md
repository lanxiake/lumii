## 2. 采集口径的四个缺陷（已修）

### 2.1 长任务阈值 = 无阈值 → 94% 的日志是噪音

浏览器的 longtask **本身就只有 >50ms 才产生条目**，阈值填 50 等于全收。
实测 4330 条里 ≥200ms 的只有 19 条，真正值得看的被埋在 4311 条 50–100ms 的帧预算波动里。

**改为 100ms**（RAIL 的响应预算）。改后同样时长 6 条。

### 2.2 内存尖峰用 JS 堆判定 → 永远不会触发

原实现读 `performance.memory.usedJSHeapSize`，阈值 1.5GB。实测渲染进程工作集 **1.33GB**
时 JS 堆只有 ~130MB —— DOM、解码位图、合成器全在堆外，按堆判永远够不着。

**改为 `selfPrivate`（进程私有内存，preload 侧读）**，阈值 1.2GB。改后立刻抓到 1.32GB 的常驻。

顺带修了两处：
- **冷却**：常驻超阈值不是事件。改前每分钟报一条、数值在 1.32GB 上下打转；改为「只报跃迁」——
  自上条起再涨 300MB 以上，或已静默 10 分钟。
- **子进程**：`sampleChildProcesses` 逐进程判定（renderer/Tab/GPU），各自冷却。
  改前只盯主进程 RSS（488MB），**完全看不到渲染进程这 1.33GB**。

### 2.3 「卡在哪个函数」几乎无法归因 → 156 条里只有 1 条

打点栈只在「阻塞发生的那一刻仍在栈上」才有值。但探针每秒才看一次，`await` 之后同步跑完的
耗时早就出栈了 —— 实测 156 条 `main.loop.lag` 只有 **1 条**带得出 `inflight`。

**加了「阻塞嫌疑」时间窗回看**：慢 SQL 与慢 IPC 结束时各登记一条（≥50ms 才收，
否则每秒几十次 0ms 的 IPC 会把真凶挤出去），探针触发时回看本窗口内与之重叠的条目。

改后实测：

```
2819ms → suspects: "get PRAGMA quick_check:1996ms"
 616ms → suspects: "ipc agent-runtime:command:553ms; all SELECT m.conversation_id ...:365ms"
```

3/13 的归因率还不高，剩下的是没打点的路径（JIT、GC、DOM）——但**比 1/156 已经有用了**。

> 踩坑记录：第一次实现没加 50ms 下限，结果满屏 `ipc agent-runtime:command:0ms`，
> 真凶被自己的噪音挤出窗口。**下限不是优化，是正确性**。

### 2.4 慢查询没有行数 → 无法判断「是变慢了还是扫多了」

同一条 `SELECT ... content_json ...` 实测在 320–522ms 之间波动，光看耗时没法判断
是库长大了、还是这次恰好命中更多行。

**加了 `rows`**（`all()` 返回数组长度；`get`/`exec` 记 -1 以免与「确实 0 行」混淆）。
改后一眼看到那条查询每次都搬 **3034 行**。

## 3. 确定的性能问题

### 3.1 会话列表 `hasStreamingMessages` 是 N+1，每次 707ms 压在主线程 ✅ 已修

`conversation:list` 对每个会话调一次
`SELECT COUNT(*) FROM messages WHERE conversation_id = ? AND is_streaming = 1`。
`is_streaming` 没有任何索引 → **每次都是全表扫**。

只读副本实测（1246 个活跃会话 / 8827 条消息 / 356MB）：

| 做法 | 耗时 |
|---|---:|
| 逐会话查询（原实现） | **707 ms** |
| 一次 `GROUP BY conversation_id` | **39 ms** |

同批把 `getAgentParticipantId` 也改成批量（30ms → 几毫秒）。
两者合起来每次拉列表省约 700ms 主线程时间 —— 而 `refreshLocalSessions` 在 ChatPage 有
**五个触发点**，还有「合并而非丢弃」的补拉逻辑（最坏同时 2 次）。

**改动**：`ConversationRepo.listStreamingConversationIds()` / `listAgentParticipantIds()`，
`handleConversationList` 改用批量结果。

### 3.2 会话列表预览查了 20 条消息，其中大部分从不使用 ✅ 已修（限幅）

`loadLastMessagesForConversations(ids, 20)` 给每个会话取最近 20 条带 `content_json` 的行。
实测一次 **4194 行 / 53.7MB 正文**，主进程要逐行 `JSON.parse`（实测 205ms 纯解析）。

但 `resolveLastMessagePreview` 是从**最后一条往前**扫、找到 Agent 的最后一句文本就停 ——
绝大多数会话用不到第 5 条。

| limit | 查询 | 载荷 | 与 20 相比预览一致的会话 |
|---:|---:|---:|---:|
| 20 | 374 ms | 53.7 MB | 基准 |
| 10 | 238 ms | — | 1240 / 1243 |
| **5** | **211 ms** | 38.6 MB | **1237 / 1243** |
| 3 | 204 ms | 33.8 MB | 1234 / 1243 |

**改为 5**：省 ~44% 载荷、质量只差 6 个会话（那 6 个是连发多条工具调用的回合）。

> 试过用 SQL `substr(content_json,1,600)` 截断正文再解析（132ms，更快），但**质量崩了**：
> 600 字符会把 `parts` 数组截断成非法 JSON，895/1243 条预览变成别的消息，89 条直接没有。
> 这条路不通，别回头试。

### 3.3 `PRAGMA quick_check` 每次启动 2–6.5 秒 ✅ 已修（见 §7.1）

```
15:58:09  2002ms  get PRAGMA quick_check
15:14:00  6584ms  get PRAGMA quick_check
```

356MB 库实测 1.2–6.5s（随页缓存冷热波动），占单次启动 8187ms 的 **1/4 到 4/5**。
它已经排在「干净关闭 → 跳过」的保护后面，但：

- 干净关闭标记 `agent-runtime.db.clean-shutdown` **本机从来没出现过** ——
  dev 下反复 `taskkill` 属于非正常退出，标记不会写；生产下正常退出才会写。
- 标记是**一次性**的（读到就删），崩溃一次后下次必然重扫。

**建议的下一步**（任一）：
1. 把检查挪到窗口显示之后异步跑，失败再弹恢复对话框（牺牲「启动即知损坏」）；
2. 用 `PRAGMA quick_check` 的替代开关——`PRAGMA cell_size_check=ON` + 只校验最近 N 页，
   或直接接受「每次非正常退出付 2s」；
3. 生产环境先量：如果正常退出路径稳定写标记，这条只在崩溃后付一次，可以不修。

> 决策前需要生产数据。dev 环境的 taskkill 会把这条放大成每次都付。

## 7. 第二轮（同日）：修复 + 页面收敛

### 7.1 `PRAGMA quick_check` 移出启动路径 ✅ 已修

原逻辑只有「存在干净关闭标记」才跳过，而该标记只在 `close()` 里写 —— dev 下 taskkill、
生产下崩溃都拿不到，于是**每启动必付 1.2–6.5 秒**（窗口已显示后卡在 S7.4 阶段）。

改为两个条件任一成立即跳过：
1. 上次是正常关闭（标记仍在）；
2. **24 小时内已完整校验过**。

跳过时**不刷新时间戳**（否则每天重启一次就永远不再校验，等于把保护关掉），
只有真正跑过校验才起算 24 小时窗口。

**真机验证**（同一台机、同一个 356MB 库、连续两次 `pnpm dev`）：

| | `localdb.3-integrity-checked` |
|---|---|
| 修复前 | **1945 ms** |
| 修复后（24h 窗口内） | **16 ms** |

### 7.2 `send-message` 口径拆分 ✅ 已修

原来一条 `send-message` 量的是「点击 → 模型出第一个字」，实测出现过
**213881ms 与 94904ms**（那是模型排队，不是本地卡顿），把它排到「最慢一次」顶上，
整个页面最重要的一格数字因此失去意义。

拆成两个交互、两档阈值：

| 交互 | 含义 | 阈值 |
|---|---|---:|
| `send-message` | 点击 → IPC 返回 runId（本地耗时） | 500 ms |
| `first-token` | 发出 → 模型第一个字（大头是网络/排队） | **10000 ms** |

`send-message` 现在只覆盖真正的本地路径；`first-token` 只在「明显不对劲」时才记。

### 7.3 诊断页：分页 + 折叠 ✅ 已修

- 明细表默认 **10 条/页**，底部「上一页 / 第 N / M 页 · 共 X 条 / 下一页」；
  筛选条件变化自动回到第 1 页。
- 明细表新增「明细」列：`all · 3034 行`、`ipc agent-runtime:command:553ms; ...` 这类
  一行摘要直接可见，不用展开 JSON 就能判断「慢在哪」。
- **启动阶段默认收起**，标题行显示合计耗时，点开才展开逐阶段明细。
- 今日事件达到内存上限（5000）时显示为 `5000+`，避免误读成「今天真的只有 5000 条」。
