## 一、起因

用户报「宠物还不会自己走动和爬墙，我没看到这些动作」。

查下来**不是功能坏了，是素材缺组**：客户端 `PetOrchestrator.resolveAmbientGroup` 找不到动作组时
**静默回落到基础待机**——日志里每一次 `[setAmbientActivity] → 组 "(基础待机)"` 就是一次缺失，
表现为「一边平移一边播呼吸」，看起来像在滑行。

仓库里其实有**两套「九个动作」规范**（交互那套 `Idle/Talk/Jump/Wave/Nod/Shake/Picked/Land/PlayBall`、
行为那套 `Idle/Walk/Sit/Talk/Fall/Picked/Jump/Climb/Crawl`），团子当时只有前者的一部分。
两套都要装。

另外用户明确要求：**走 / 攀爬 / 爬行要侧身**（"走路的图片记得是左右侧身哦，不是正面的"），
其余保持正面。坐下按参考素材定，见 §六。

### 第二轮（2026-09-23）：装上了，但贴不住

动作组装好之后用户又报了两条，**两条都不是"少了动作"，是"几何不对"**：

1. **「在天花板上爬行时反了，应该底部朝上，头部朝下。」** —— CRAWL 那一行是**正的**
   （脚朝下画的），吊在天花板上就头朝上。见 §九。
2. **「在屏幕两侧边缘时会自动上升，就像坐电梯一样靠近墙壁，应该是爬墙。」** ——
   Climb 动作组**在播**（日志有 `climb → 组 "Climb"`），朝向也**是对的**；
   问题是宠物**离墙 20px、离天花板 45px 悬着**，看着不是"贴着墙爬"而是"被电梯带上去"。
   根因是 `perchGaps` 从没写过 → 静默用了 Shimeji 那套素材的实测值。见 §九。


## 二、方法：两段式

H3 的 `first_frame` 是**机位标定**，且循环闭合靠 FL2VA（同一张图同时接 `first_frame` 和 `last_frame`）。
于是「用正面立绘直接生成侧身循环」会在末帧被**强制拉回正面**，循环里出现"转过去→被拉回来"的鬼畜。

所以非正面姿势走两段：

```
正面立绘 ──pose(I2VA，尾帧自由)──▶ 姿势拼条 ──pose-pick──▶ 挑一帧
   └─▶ stage-frame --keep-scale ──▶ staged/<角色>-<姿势>.png
        └─▶ sheet(FL2VA，首帧=该姿势) ──▶ 8 格动作表 ──▶ install-pet ──▶ 客户端
```

⚠ 两条路的 `freeEnd` **别接反**：循环必须接 `last_frame`，姿势图必须**不接**。
接反任一条都**静默**毁掉整轮，而出图看着完全正常。

## 七、这一路的坑（都已修，细节在 SKILL.md）

只列**方法学之外**的、属于本次交付的：

- **画布宽度连错四版**：`421 × 宽高比` → 错（忽略"组内最高"才是分母）；只按包围盒算 → 偏小
  （客户端按**重心**对齐，两侧余量要分开算）；按最小 16 倍数取 → **装完爬行距左边只剩 1px**。
  最终 `560×448`，工具已按四条一并实现。
- **`stage-frame --keep-scale` 保的是"像素"不是"比例"**：对整幅帧等价，对**拼条裁出来的格**
  会再缩 0.667 倍——爬行的猫比走路那格**连头都小**。**这是看出来的不是算出来的**。
- **`fall` 不能用 `displacement`**（"may rise, drop, or crouch within the frame" 会让模型照做，
  角色升出格线、头顶信息丢失），也不能用 `static`（"does not leave the ground" 与"在空中"矛盾）
  → 新增第四类 `suspended`。⚠ 同一个句子在不同动作上对错不同（`static` 对 `sit` 是对的），
  **逐个看，别按类名套**。
- **归因写错过一次并已更正**：`accc3d02` 说"改措辞之后不再升出格线"，实测三次底边漂移
  149 / 131 / 104px，**没变小**，过关的是余量。更正见 `cf91c658`。
  ⚠ 那次的教训值得留着：头被裁到 0 之后**漂移量是下界**，"再试一次更狠的"不可证伪；
  要断言措辞有效得用**同一批抽样帧**做 A/B。

## 九、续修：天花板倒挂与攀附几何（2026-09-23）

用户第二条反馈（原文见 §一）。**两条都不是"少了动作"**——`Climb`/`Crawl` 都在播
（日志有 `climb → 组 "Climb"`），纯粹是几何与朝向。

### 9.1 怎么确认的（方法比结论值钱）

排查绕了一大圈，**弯路本身值得记**：一开始怀疑"是不是动画没播""是不是朝向反了"，
两者都被证据否掉，最后落到"离墙多少像素"上。用到的判据：

| 问题 | 判据 | 结果 |
| --- | --- | --- |
| 动作组播了吗 | 日志 `[setAmbientActivity] climb → 组 "Climb"` | 播了 |
| 朝向对吗 | 素材的**尾巴在哪一侧**（正面表尾在左下、侧身表尾在左） | 对：`flipForPerch` 与素材朝向一致 |
| 动画有没有在动 | 逐帧包围盒/重心 + 相邻帧差异 | 动了（**比 walk 还大**：5.4~10.5% vs 1.8~5.6%） |
| **那到底哪儿不对** | **把客户端会画成什么样合成出来**（`mock-perch.mjs`） | **离墙 20px、离天花板 45px** |

⚠ **"量数字"到不了的地方要靠"画出来"**：包围盒、宽高比、像素差异全都正常，
只有把帧按真实公式摆到模拟屏幕上才看得见"它悬着"。

### 9.2 两个根因

1. **`Crawl` 素材没倒挂。** H3 照 `POSES.creep`（"趴在地上"）画的是**正的**，
   而这一行**只在天花板上播**。Shimeji 那套的作者本来就把 CRAWL 行画成脚底向上，
   `import-shimeji.mjs` 因此**不翻**——我们的素材形态相反，谁都没翻。
2. **`perchGaps` 从没写过。** `install-pet.mjs`（H3 这套唯一的安装入口）只拼图集、
   不写攀附几何，`pet-core` 于是**静默**用 `PERCH_DEFAULTS` ——那是 **Shimeji 素材的实测值**
   （0.43 / 0.99）。团子实测应为 `{ wall: 0.2478, ceiling: 0.5625 }`：
   锚点离墙该 27px 却放了 47px，离天花板该 61px 却放了 108px。

### 9.3 改了什么

| 位置 | 改动 |
| --- | --- |
| `verify/pet-sprite/characters/install-pet.mjs`（技能内各一份） | `ACTIONS.crawl` 加 `invertY: true`（翻转在**切格之前**，等价于每格就地上下镜像） |
| 同上 | 装完从**装好的图集**量 `perchGaps` 并写进 `manifest.json`（`packageDir` 与 `installedDir` 两处都要写） |
| `verify/pet-sprite/lib/perch-gaps.mjs`（新增） | 量测 + 独立 CLI（`--write` 可直接改一个已装的包） |
| `scripts/start-dev.ps1` | 新增 `-RemoteDebug <port>`——`lumii-cdp.mjs` 要的调试端口原先没有口子 |
| `scripts/lumii-cdp.mjs` | `shot` 加合成器底色（默认 `#f2f2f7`，`CDP_SHOT_BG` 可换） |
| `pixel-ascii.mjs` | 加 `--crop` / `--auto` / `--bg` 与多文件（截屏要用；⚠ 顺手修了下标越界打出 `undefined` 的 bug） |
| 新增诊断工具 | `atlas-cell.mjs`（按条目名抠格）、`mock-perch.mjs`（合成客户端摆位）、`shot-probe.mjs`（从截屏里找宠物） |

⚠ **`perch-gaps.mjs` 只量「距离」，不猜「朝向」**：归一化把内容**底边对齐到锚点**，
所以素材翻与不翻，装完之后 `crawl.y1 ≈ anchor[1]` 与 `ceiling` **是同一个数**
（实测都是 0.5625）。朝向只能由生产侧声明——所以有了 `invertY`。

### 9.4 判据（实机）

```
[perch] 吸附到屏幕左墙 x=27      ← 旧 47（perchGaps.wall 生效）
[perch] 吸附到屏幕右墙 x=2533    ← 2560 − 27
[perch] 松手（爬到尽头）@(2560, 61)  ← 旧 108（perchGaps.ceiling 生效）
```

装完的图集逐格看得见：Crawl 行的脚在上（与源表 `f000000.png` 上半部逐格镜像）；
`mock-perch.mjs` 按真实公式合成后，爬墙的猫**左缘落在 x=0**、爬天花板的猫**顶边落在 y=0**。

⚠ **每进程只读一次**：`registry.json` 与模型清单都是启动时读的，改完必须冷启动，
点 UI 开关不算。

### 9.5 顺带发现、**本轮没修**的两条

1. **爬完天花板会在屏幕正边缘掉下来**：`stepCrawl` 的终点就是 `rect.x` / `rect.x+width`，
   落地后宠物有一半在屏幕外，而且它会站着/坐着在那儿赖到下一次走动
   （走动时 `stepWalk` 才把它夹回边界）。修法是在 `releasePerch` 前把 x 夹进 `walkBoundsOf`。
2. **从走到坐会瞬间翻面**（见 §六.1，仍未动）。

## 十、拖到边缘/顶部要吸附，抛掷加弹性（2026-09-23）

用户第三条反馈：

> 鼠标拖动宠物到屏幕边缘和顶部时，宠物需要吸附在对应的边缘上。注意是鼠标和宠物
> **同时**到屏幕边缘或者顶部。原来丢宠物的功能还是保留的，可以增加 50% 的弹性。

追问后定下两条：**①拖动时内容贴边即停、松手吸附**；**②撞墙反弹系数 ×1.5**。

### 10.1 原来为什么吸不上

拖动那条路**从来没有边界**——`setPosition` 直接跟指针走，实测能把宠物拖到 `y = -21589`。
"放到边上就吸"这条（`resume` 里那句 `tryAttachNow`）其实存在，但被三件事挡着：

| 挡路的 | 现象 |
| --- | --- |
| **`onMouseUp` 的"速度不足"分支直接 `startThrow(pos, {0,0})`** | 宠物被先摔到地面，等 `resume` 再判吸附时它已经在地上了——位置早就不贴边。**这条是主因，用户"拖到边没反应"就是它** |
| `tryAttachScreen` 只判左右，**顶边压根没有这条**（注释写着"宠物站在地面线上，够不着屏幕顶"） | 拖到顶部没有任何反应 |
| 判定用的是**锚点**到墙线的距离，而锚点在脚底中心、周围还有一圈素材留白 | 用户按"看到的身子贴到边了"松手时，锚点可能还差几十像素 |

### 10.2 做法

**拖动时按「内容」夹，松手时按「内容贴住哪条边」吸。**

| 位置 | 改动 |
| --- | --- |
| `pet-core` 的 `perch.ts` | 新增 `contentExtents` / `dragBoundsOf` / `flushEdges` 三个纯函数 |
| `SpritePetRenderer` | 新增 `getContentExtents()`：从**已解码的图集**上量当前动作组的不透明包围盒（按组缓存） |
| `PetCanvas` | 指针移动时 `clampDrag` 夹住位置；松手**先问 `canAttachHere()`** 再决定吸还是落；抛掷走 `THROW_RESTITUTION = 0.825` |
| `PetWanderDriver` | 新增 `canAttachHere()`（只判不做）；`resume` 里**吸附判定提到坠落之前**；`attachPerch` 支持直接吸天花板；`clampPosition` 的下界 16 → 0 |

⚠ **判据必须是「内容」不是「画布」**：整个 `canvas` 贴上去是带留白的，团子的内容
只占画布宽度的 79%（444/560）。用画布算，宠物会停在离屏幕边 **22px** 的地方，
看着像没拖到位——这也正是用户说"要同时到边缘"的来源。

⚠ **`canAttachHere` 的位置必须问渲染器，不能用自己的 `x/y`**：拖动期间画布是直接写
`renderer.setPosition()` 的，驱动被让位挂着，坐标还停在"被拎起来之前"。拿它判会得出
"在**原来**的地方能不能吸"——与用户手上那一拖无关。

⚠ **`flushEdges` 的容差用 `attachDistance`（24px），不能是 1px**：拖动是直接操作，
光标最低只能到屏幕顶（`y=0`），而宠物相对光标有个抓取偏移——**光标推不动的地方
宠物也到不了**。实测从墙上把猫往上拖到 `(200, 0)`，锚点只到 `y=44`，而内容上伸量是
40，差 4px 就判不成"贴住"，松手掉了下来。1px 的判据等于要求人手把宠物推到恰好贴边。

⚠ **`clampPosition` 的 16 会吃掉贴顶吸附**：矮姿势的内容上伸量可能不到 16px，
锚点被抬到 16 就不再"贴着上沿"，`flushEdges` 判定失败，拖到顶端反而不吸。

### 10.3 判据

**单测**：`packages/pet-core` 45 条（新增 5 条：内容口径、翻转互换、夹取区间、退化情形、
贴边判定）、`apps/windows` 的 `PetWanderDriver` 20 条（新增 3 条：贴顶松手吸到天花板、
**没贴边时照旧坠落**、`canAttachHere` 只判不做）。

**实机**（`verify/pet-sprite/characters/drag-pet.mjs` 合成拖拽，日志为准）：

```
[onMouseUp] 贴住了屏幕边，吸附而非落下 @(39, 1172)     ← 左墙
[perch] 吸附到屏幕左墙 x=27
[onMouseUp] 贴住了屏幕边，吸附而非落下 @(2525, 829)    ← 右墙
[perch] 吸附到屏幕右墙 x=2533
```

⚠ **合成拖拽踩到两个坑，都写在 `drag-pet.mjs` 头部**：速度必须落在"丢"（`startThrow`
的门槛 320px/s）与"抛"之间；而**真鼠标的移动会不断打断它**——指针 hover 到模型上时
主进程会把穿透关掉，于是别处来的 `buttons: 0` 也送进页面，`PetCanvas` 把它当
"左键已松开"直接 `abandonDrag`。测试侧挂了个捕获监听挡掉这些事件（**没动产品代码**：
真机只有一个指针设备，不会误触）。

⚠ **顶边吸附只有单测**：实机试到的那几次都被真鼠标打断或误判成了"抛出去"。
用户手动拖一下最直接。




## 十一、概览页不显示宠物形象（2026-09-23）

用户报：「概览页面右下角宠物弹窗，没有显示当前被选中的宠物形象」。

### 11.1 根因

那块卡片（`DashboardPage/components/VirtualHuman`）是**只读**的：拿注册表条目的
`thumbnailUrl` 画 `<img>`，**没有就画一个占位星标**。而内置注册表里

顺带一处：同一张卡片的副标题**写死** `Live2D · 共 N 个形象`，显示精灵图宠物时

### 11.2 做法

缩略图在**安装期**生成，运行期一个字都不用改：

## 十二、抓在宠物哪一侧都要能贴边（2026-09-23）

用户实测：「鼠标在宠物左边贴左边墙是可以的，但是鼠标在宠物中心的右边是贴不住的。
需要的是不管抓取宠物哪边的位置，靠近边缘都可以吸附」。

### 12.1 为什么抓在某一侧就贴不上

拖动是**直接操作**：`want = 光标 − 抓取偏移`，所以**抓得离锚点越远，光标能推的余量越小**。
而光标最低只能到 `0`——**光标推不动的地方，宠物也到不了**：

```
抓在宠物左半边（偏移 = −50），往左推：
  want.x = 光标x + 50，光标最小 0 ⇒ 锚点最小只能到 50
  而"贴边"要求锚点落到「内容左缘」（实测 ~15px）
  ⇒ 永远差 35px，松手时 `flushEdges` 判不成立，宠物掉下去
抓在右半边（偏移 = +50）反之：want.x = 光标x − 50，光标到 0 时 want.x = −50，
  被夹到内容左缘 ⇒ 贴得上
```

⚠ 这与 §10.2 里那条"`flushEdges` 容差用 24px"是**同一个病的两个症状**：
当时只在上沿方向上撞到（差 4px），横向这一侧没试到，所以只把容差放宽了。

### 12.2 做法

`clampDrag` 加一条：**光标顶到屏幕边 24px 以内时，直接把宠物夹到那一侧的内容边界上**，
不再受抓取偏移限制。

```js
const EDGE_PUSH_PX = 24
if (pointer.x <= EDGE_PUSH_PX) x = b.minX
else if (pointer.x >= vp.width - EDGE_PUSH_PX) x = b.maxX
```

判据用「离屏幕边 24px 以内」而不是「越界」：`attachDistance` 就是这个语义（走到墙线
24px 内就吸），拖动这边保持一致；而落在边上的位移本来就很小——`want` 已经被推得很近了。

### 12.3 判据

`drag-pet.mjs` 加了 `--grab dx,dy`（相对身体中心抓），两侧各验一次：

```
--grab -30,0 → 0 1400   [onMouseUp] 贴住了屏幕边，吸附而非落下 @(35, 1400) → 吸附到屏幕左墙 x=27
--grab  30,0 → 0 1400   [onMouseUp] 贴住了屏幕边，吸附而非落下 @(39, 1400) → 吸附到屏幕左墙 x=27
```

⚠ **量"宠物身上哪一点按得住"的办法**（本轮用的，值得留着）：判据是**日志**——
`PetCanvas` 只在 `hitTest || isPointerOverModel` 为真时才打 `[onMouseDown] 按住 100ms 进入抓取`。
⚠ 采样点前**必须重拍一帧重新定位**：第一版拿一个静态包围盒扫，宠物 7 秒里自己走了 300px，
量出一条毫无意义的窄带，差点把结论带偏。

## 十三、智能化设计要的新动作素材（2026-09-24）

《宠物作为化身的智能化设计》§8.6.2 标了三条「需新素材」，另有几处只描述了行为、
没描述素材。这一轮把它们补齐：**8 个新动作组 + 1 张姿势图**，团子（`demo_cartoon_cat`）
的动作组从 14 组涨到 22 组。

**⚠ 本轮只交付素材，不接触发**——每一条接在哪、要满足哪条验收（§8.2 原则三的"可打断"、
U8"打断处平滑不跳帧"）都写在《宠物智能化实施计划》第二期的前置说明里。

### 13.1 出了什么

| 组名 | 动作 | 来源 | 帧数 | 回放 | `kind` |
| --- | --- | --- | --- | --- | --- |
| `Yawn` | 打哈欠 | 设计 §8.6.2（原文「8 帧」） | 16 | @8fps = 2.00s | once |
| `Stretch` | 伸懒腰 | 设计 §8.6.2（原文「12 帧」）/ §8.6.3 | 16 | @8fps = 2.00s | once |
| `Scratch` | 挠头 | 设计 §8.6.2（原文「10 帧」） | 16 | @8fps = 2.00s | once |
| `Dodge` | 躲开 | 设计 §4.4 拒绝的表现列 | 16 | @14fps = 1.14s | once |
| `Purr` | 呼噜（被摸头） | 设计 §8.3.1 / 计划 T2.4 | 16 | @6fps = 2.67s | **loop** |
| `Cheer` | 雀跃 | 设计 §7.3 目标完成 | 16 | @10fps = 1.60s | once |
| `Droop` | 蔫 | 设计 §7.3 目标失败 | 16 | @8fps = 2.00s | once |
| `Look` | 张望 | 设计 §8.3.1「转头看鼠标」 | 16 | @8fps = 2.00s | once |

帧数从设计里写的 8/12/10 统一抬到 16，是用户 2026-09-24 的要求（「帧数可以都适当提高，
这样的动画效果更好」）。**但抬高帧数不只是把抽帧数改大**——见 13.2，那是本轮最值钱的一条。

`Purr` 多一张姿势图（`staged/tuanzi-purring.png`），理由见 13.4。

### 13.2 ⚠ 口径一：抽帧数必须与源片长成对改

`h3-motion.mjs` 的 `DEFAULT_FRAMES`（源片帧数）与 `DEFAULT_PICKS`（抽出几帧）
**是一对，不是一个**。回放时长 = 抽帧数 ÷ 回放帧率，所以：

```
56 帧取 8  → 8 帧 @8fps 播 1.00s，源 2.33s  ⇒ 快放 2.33×   ← 既有 13 组的手感
107 帧取 16 → 16 帧 @8fps 播 2.00s，源 4.46s  ⇒ 快放 2.23×   ← 这一轮，帧数翻倍、手感不变
107 帧取 8  → 8 帧 @8fps 播 1.00s，源 4.46s  ⇒ 快放 4.46×   ← **只改源片长的后果：像抽搐**
```

只把 `DEFAULT_FRAMES` 抬上去，是**把动画放快**而不是变细腻。两处必须一起动。

顺带修掉一个同类隐患：动作 prose 里的完成时刻原先是个常量 `MOTION_DEADLINE = '2.10'`
（配 2.33 秒的片子）。片长一改，"2.10 秒完成"就成了一句跟画面无关的话——模型会在前半段
就把动作做完、剩下两秒无事可做，而**提示词里没有任何地方提示这个矛盾**，只有抽出来的帧
看得出来（中段开始重复）。现在由 `buildPrompt` 从 `seconds × 0.9` 算。

107（4.46s）是**官方模板与 sprite_h3 用的那一档**，当初压到 56 是因为"抽 8 帧用不上
107 帧"——那是按 8 帧输出算的账，抽帧数一抬就不成立了。

### 13.3 ⚠ 口径二：图集列数必须随帧数生长（贴图单边上限）

图集是**一张**贴图。`maxCols` 原先在 `packages/pet-asset` 里写死默认 **8 列**，
于是图集高度 = `⌈帧数/8⌉ × 格高`，帧数一多就成一条细长的竖条：

```
104 帧（14 组 × 8）            → 4480 × 5824
232 帧（+8 组 × 16）           → 4480 × 12992   ← 越线
```

**12992 越过不少 GPU 的 8192 上限**，而超限的后果不是报错、是**整张图集建不出纹理**——
宠物直接不显示。所以：

| 位置 | 改动 |
| --- | --- |
| `pet-creator/run.ts` | `pack` 调用把 `params.maxCols` 透传下去（不传 = 老行为 8 列） |
| `install-pet.mjs` | 按**总帧数**算出列数，让宽和高都留在 `ATLAS_MAX_DIM = 8192` 以内且尽量方形 |

8192 取的是 DX10 时代的保底值（DX11+ 保证 16384）。塞不下时**打警告并说清代价**
（少几条动作、或缩画布，而缩画布 = 宠物变小、必须同改 `scale`），不静默截断。

### 13.4 ⚠ 口径三：循环姿势要单独出一张首帧

`Purr` 是 `kind: loop`，而 **FL2VA 把同一张图钉死在首尾两端**——首帧是什么，循环每一圈
就回到什么。拿那张睁眼的站立立绘当首帧，循环就成了"闭眼 → 睁眼 → 闭眼"：
那是**眨眼**，不是"被摸得舒服得一直眯着眼"。长按摸头是**持续状态**（U3 要求"有持续回应"），
整段都得闭着眼，所以首帧本身必须是闭眼的。

走的是既有的两段式（`POSES`）：I2VA 尾帧自由出一轮 → 挑帧 → `stage-frame --keep-scale`
摆正 → 再拿它跑循环。**这是 `POSES` 存在的第二类理由**（第一类是换视角：侧身/贴墙）。

### 13.5 三处机制上的小改（都是"别复制粘贴"）

1. **`FACING['front-head']`**：`Look` 要"转头看"，而 `_FACING_DOWN` 的结尾是
   `the character does not turn`——直接拿那句配"转头"的提示词是**自相矛盾**，模型在
   两句话之间摇摆（和 `turn` 当初被逼出来的理由一模一样）。新句只放开**头**，
   明确锁住**身体**：身体一转，`PetWanderDriver.applyFacing` 写死的"素材默认朝右"就破了。

2. **`ACTIONS.cheer.stage = { from: 'hop' }`**：`Cheer` 要跳，而"跳"需要 `hop` 那张把
   角色在画面里压低（`baseline 0.95`，头顶留 168px）的首帧，否则 `displacement` 那句
   "整个人可以在画面里升起"会让头顶出格线。两张图**姿势完全一样**，重出一份只会多一个
   会各自漂移的副本——用名字显式声明依赖（`stage.from`），比复制文件强。

3. **`f0000.json`（`writeSheetGrid`）**：拼条的**列数从图本身推不出来**（任何约数都几何
   自洽）。2026-09-24 起 8 列与 16 列的表在同一个角色下**并存**，而 `sheet-canvas.mjs`
   把 8 写成了默认值——对 16 列的表按 8 列切，每"格"横跨两个角色，**量不出"装不下"**
   （错的方向是偏乐观），装完才发现被裁。列数由产出拼条的那一步写进 `f0000.json`。

### 13.6 判据

**出图闸门**（`packages/pet-asset/src/sheetcheck.ts`，经控制口 `sheetCheck` 逐张跑）：
8 张**全部 `ok`**，`bleedRatio` 全为 **0**（S1 边界干净）。`stretch` 与 `cheer` 各多一条
**S2**（格内偏移 19% / 16% > 12%）——不影响可用性，`normalize` 会按包围盒重新定位。

**逐组的包围盒弧线**（`cell` 空间的宽×高，起手格 → 中段 → 收尾格）——判"动作是不是真的在做"：

| 组 | 弧线 | 读作 |
| --- | --- | --- |
| `Yawn` | 246×315 → 257×300 → 246×315 | 头一仰、胸一鼓；ASCII 上中段面部**中央多出一条纵向暗区**（张开的嘴），起手帧没有 |
| `Stretch` | 246×315 → **361×224** → 247×315 | 前爪前伸、身子拉长压低 ✓ |
| `Scratch` | 246×315 → **278×325** → 246×315 | 爪子举到头侧（变宽变高）✓ |
| `Dodge` | 246×315 → **243×250** → 246×315 | 缩下去闪避 ✓ |
| `Cheer` | 246×314 → 270×**338** → 246×314 | 逐格在 284↔338 之间来回＝跳的节奏；ASCII 上**两只前爪举在头两侧** ✓ |
| `Droop` | 246×315 → 260×**277** → 246×315 | 塌下去再挺回来 ✓ |
| `Look` | 246×315 → **277×321** → 246×315 | 头转开再转回来 ✓ |
| `Purr` | 241×292 → 291×299 → 241×292 | 宽度摆动＝尾巴在摇 ✓ |

**`Purr` 的闭眼**（这是它单独出姿势图的全部理由，必须验）：

- 姿势图拼条：格 0~3 **睁眼**、格 4 起**闭着**——正是"站着 → 放松眯眼"的弧线，
  挑中的格 7 落在闭眼段里。
- 成品表：整段闭着眼。⚠ 判据（同一行里近黑像素有没有 ≥身宽 8% 的**两个宽簇**）
  在这张上有 **2/16 假阳性**（格 5、格 12），肉眼复核那两格与相邻格**完全一致**
  ——判据是**筛子不是证明**，正负对照（站立立绘 vs 闭眼姿势）才是决定性的那一半。

**画布与倍率**（`sheet-canvas.mjs`，`--dir verify/pet-sprite/sources/pet-motion --canvas 560x448`）：

```
组 384x448 —— 17 个动作 / 200 格
  组内最高包围盒 366 → 倍率 1.151      ← 与加这 8 组之前**逐位相同**（仍是 picked）
  按重心对齐要 485px 宽                  ← 之前 345（涨的是 stretch 的前伸前爪）
组 512x448 —— 4 个动作（climb/crawl/fall/walk，未动）
==> 画布宽至少要 524px；560 仍装得下，余量充足
```

**⚠ 结论：`--canvas 560x448` 不用改**，`scale` 也不用改——宠物在屏幕上的观感大小
**一点没变**。这正是 §13.7 预警的第 3 条风险，实测**没有发生**（见下）。

### 13.7 本轮没做的 / 下一轮要留意的

1. **触发接线一条都没接**（见本节开头）。八条各自的落点在计划第二期 / 第三期。
2. **⚠ 读代码看到一个疑似洞，尚未实测**：`once` 组的 `next` 是**渲染器自己跳的**
   （`SpritePetRenderer.maybeCompleteOnce` 里 `if (p.anim.next) this.playMotion(p.anim.next)`），
   **不通知编排器**。于是从 Walk/Sit 被打断时播完回的是 `Idle` 组，而驱动那边的环境姿态
   没变、`setAmbientActivity` 又对同值早返回——按读到的代码推，宠物会**站着往前滑**到
   下一次活动切换为止。点击动作（`Wave`/`Nod`）现在大概就有这个洞。
   （`motionListener` 已经存在但**没有任何订阅者**，它本来就是为"once 播完了"这件事留的口子。）
3. ~~**往归一化组里加动作会改整组的倍率**~~ **实测没有发生**：新组里最高的 `cheer` 是
   **338**，组内最高仍是 `picked` 的 **366**，倍率与加之前逐位相同。
   **⚠ 但这条约束本身仍然成立**，下次加动作还要量一遍——它离出事只差 28px。
4. **⚠ `waitDone` 的超时口径错了一轮**（已修）：超时原本从**提交时刻**算，于是
   **排队时间被算进执行预算**——批量里排第 8 位的 `purr` 干等 44 分钟（全在排队）
   就被判「等待超时（45 分钟）」，**而它随后照常跑完了**。现在排队的只受
   `queueTimeoutMs`（4 小时）约束，`timeoutMs` 只在**真的开始跑之后**才计时。
   ⚠ 顺带记一个 ComfyUI 的行为：**图与 seed 完全相同的重复提交会全量缓存命中、秒回**，
   指向同一个产物文件（重提 `purr` 时撞上，一度看起来像"生成失败又秒成"）。
