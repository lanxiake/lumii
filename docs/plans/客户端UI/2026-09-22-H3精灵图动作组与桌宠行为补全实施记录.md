## 一、起因

用户报「宠物还不会自己走动和爬墙，我没看到这些动作」。

查下来**不是功能坏了，是素材缺组**：客户端 `PetOrchestrator.resolveAmbientGroup` 找不到动作组时
**静默回落到基础待机**——日志里每一次 `[setAmbientActivity] → 组 "(基础待机)"` 就是一次缺失，
表现为「一边平移一边播呼吸」，看起来像在滑行。

仓库里其实有**两套「九个动作」规范**（交互那套 `Idle/Talk/Jump/Wave/Nod/Shake/Picked/Land/PlayBall`、
行为那套 `Idle/Walk/Sit/Talk/Fall/Picked/Jump/Climb/Crawl`），团子当时只有前者的一部分。
两套都要装。

另外用户明确要求：**走 / 攀爬 / 爬行要侧身**（"走路的图片记得是左右侧身哦，不是正面的"），
其余保持正面。坐下按参考素材定，见 §六。

### 第二轮（2026-09-23）：装上了，但贴不住

动作组装好之后用户又报了两条，**两条都不是"少了动作"，是"几何不对"**：

1. **「在天花板上爬行时反了，应该底部朝上，头部朝下。」** —— CRAWL 那一行是**正的**
   （脚朝下画的），吊在天花板上就头朝上。见 §九。
2. **「在屏幕两侧边缘时会自动上升，就像坐电梯一样靠近墙壁，应该是爬墙。」** ——
   Climb 动作组**在播**（日志有 `climb → 组 "Climb"`），朝向也**是对的**；
   问题是宠物**离墙 20px、离天花板 45px 悬着**，看着不是"贴着墙爬"而是"被电梯带上去"。
   根因是 `perchGaps` 从没写过 → 静默用了 Shimeji 那套素材的实测值。见 §九。


## 二、方法：两段式

H3 的 `first_frame` 是**机位标定**，且循环闭合靠 FL2VA（同一张图同时接 `first_frame` 和 `last_frame`）。
于是「用正面立绘直接生成侧身循环」会在末帧被**强制拉回正面**，循环里出现"转过去→被拉回来"的鬼畜。

所以非正面姿势走两段：

```
正面立绘 ──pose(I2VA，尾帧自由)──▶ 姿势拼条 ──pose-pick──▶ 挑一帧
   └─▶ stage-frame --keep-scale ──▶ staged/<角色>-<姿势>.png
        └─▶ sheet(FL2VA，首帧=该姿势) ──▶ 8 格动作表 ──▶ install-pet ──▶ 客户端
```

⚠ 两条路的 `freeEnd` **别接反**：循环必须接 `last_frame`，姿势图必须**不接**。
接反任一条都**静默**毁掉整轮，而出图看着完全正常。

## 七、这一路的坑（都已修，细节在 SKILL.md）

只列**方法学之外**的、属于本次交付的：

- **画布宽度连错四版**：`421 × 宽高比` → 错（忽略"组内最高"才是分母）；只按包围盒算 → 偏小
  （客户端按**重心**对齐，两侧余量要分开算）；按最小 16 倍数取 → **装完爬行距左边只剩 1px**。
  最终 `560×448`，工具已按四条一并实现。
- **`stage-frame --keep-scale` 保的是"像素"不是"比例"**：对整幅帧等价，对**拼条裁出来的格**
  会再缩 0.667 倍——爬行的猫比走路那格**连头都小**。**这是看出来的不是算出来的**。
- **`fall` 不能用 `displacement`**（"may rise, drop, or crouch within the frame" 会让模型照做，
  角色升出格线、头顶信息丢失），也不能用 `static`（"does not leave the ground" 与"在空中"矛盾）
  → 新增第四类 `suspended`。⚠ 同一个句子在不同动作上对错不同（`static` 对 `sit` 是对的），
  **逐个看，别按类名套**。
- **归因写错过一次并已更正**：`accc3d02` 说"改措辞之后不再升出格线"，实测三次底边漂移
  149 / 131 / 104px，**没变小**，过关的是余量。更正见 `cf91c658`。
  ⚠ 那次的教训值得留着：头被裁到 0 之后**漂移量是下界**，"再试一次更狠的"不可证伪；
  要断言措辞有效得用**同一批抽样帧**做 A/B。

## 九、续修：天花板倒挂与攀附几何（2026-09-23）

用户第二条反馈（原文见 §一）。**两条都不是"少了动作"**——`Climb`/`Crawl` 都在播
（日志有 `climb → 组 "Climb"`），纯粹是几何与朝向。

### 9.1 怎么确认的（方法比结论值钱）

排查绕了一大圈，**弯路本身值得记**：一开始怀疑"是不是动画没播""是不是朝向反了"，
两者都被证据否掉，最后落到"离墙多少像素"上。用到的判据：

| 问题 | 判据 | 结果 |
| --- | --- | --- |
| 动作组播了吗 | 日志 `[setAmbientActivity] climb → 组 "Climb"` | 播了 |
| 朝向对吗 | 素材的**尾巴在哪一侧**（正面表尾在左下、侧身表尾在左） | 对：`flipForPerch` 与素材朝向一致 |
| 动画有没有在动 | 逐帧包围盒/重心 + 相邻帧差异 | 动了（**比 walk 还大**：5.4~10.5% vs 1.8~5.6%） |
| **那到底哪儿不对** | **把客户端会画成什么样合成出来**（`mock-perch.mjs`） | **离墙 20px、离天花板 45px** |

⚠ **"量数字"到不了的地方要靠"画出来"**：包围盒、宽高比、像素差异全都正常，
只有把帧按真实公式摆到模拟屏幕上才看得见"它悬着"。

### 9.2 两个根因

1. **`Crawl` 素材没倒挂。** H3 照 `POSES.creep`（"趴在地上"）画的是**正的**，
   而这一行**只在天花板上播**。Shimeji 那套的作者本来就把 CRAWL 行画成脚底向上，
   `import-shimeji.mjs` 因此**不翻**——我们的素材形态相反，谁都没翻。
2. **`perchGaps` 从没写过。** `install-pet.mjs`（H3 这套唯一的安装入口）只拼图集、
   不写攀附几何，`pet-core` 于是**静默**用 `PERCH_DEFAULTS` ——那是 **Shimeji 素材的实测值**
   （0.43 / 0.99）。团子实测应为 `{ wall: 0.2478, ceiling: 0.5625 }`：
   锚点离墙该 27px 却放了 47px，离天花板该 61px 却放了 108px。

### 9.3 改了什么

| 位置 | 改动 |
| --- | --- |
| `verify/pet-sprite/characters/install-pet.mjs`（技能内各一份） | `ACTIONS.crawl` 加 `invertY: true`（翻转在**切格之前**，等价于每格就地上下镜像） |
| 同上 | 装完从**装好的图集**量 `perchGaps` 并写进 `manifest.json`（`packageDir` 与 `installedDir` 两处都要写） |
| `verify/pet-sprite/lib/perch-gaps.mjs`（新增） | 量测 + 独立 CLI（`--write` 可直接改一个已装的包） |
| `scripts/start-dev.ps1` | 新增 `-RemoteDebug <port>`——`lumii-cdp.mjs` 要的调试端口原先没有口子 |
| `scripts/lumii-cdp.mjs` | `shot` 加合成器底色（默认 `#f2f2f7`，`CDP_SHOT_BG` 可换） |
| `pixel-ascii.mjs` | 加 `--crop` / `--auto` / `--bg` 与多文件（截屏要用；⚠ 顺手修了下标越界打出 `undefined` 的 bug） |
| 新增诊断工具 | `atlas-cell.mjs`（按条目名抠格）、`mock-perch.mjs`（合成客户端摆位）、`shot-probe.mjs`（从截屏里找宠物） |

⚠ **`perch-gaps.mjs` 只量「距离」，不猜「朝向」**：归一化把内容**底边对齐到锚点**，
所以素材翻与不翻，装完之后 `crawl.y1 ≈ anchor[1]` 与 `ceiling` **是同一个数**
（实测都是 0.5625）。朝向只能由生产侧声明——所以有了 `invertY`。

### 9.4 判据（实机）

```
[perch] 吸附到屏幕左墙 x=27      ← 旧 47（perchGaps.wall 生效）
[perch] 吸附到屏幕右墙 x=2533    ← 2560 − 27
[perch] 松手（爬到尽头）@(2560, 61)  ← 旧 108（perchGaps.ceiling 生效）
```

装完的图集逐格看得见：Crawl 行的脚在上（与源表 `f000000.png` 上半部逐格镜像）；
`mock-perch.mjs` 按真实公式合成后，爬墙的猫**左缘落在 x=0**、爬天花板的猫**顶边落在 y=0**。

⚠ **每进程只读一次**：`registry.json` 与模型清单都是启动时读的，改完必须冷启动，
点 UI 开关不算。

### 9.5 顺带发现、**本轮没修**的两条

1. **爬完天花板会在屏幕正边缘掉下来**：`stepCrawl` 的终点就是 `rect.x` / `rect.x+width`，
   落地后宠物有一半在屏幕外，而且它会站着/坐着在那儿赖到下一次走动
   （走动时 `stepWalk` 才把它夹回边界）。修法是在 `releasePerch` 前把 x 夹进 `walkBoundsOf`。
2. **从走到坐会瞬间翻面**（见 §六.1，仍未动）。

## 十、拖到边缘/顶部要吸附，抛掷加弹性（2026-09-23）

用户第三条反馈：

> 鼠标拖动宠物到屏幕边缘和顶部时，宠物需要吸附在对应的边缘上。注意是鼠标和宠物
> **同时**到屏幕边缘或者顶部。原来丢宠物的功能还是保留的，可以增加 50% 的弹性。

追问后定下两条：**①拖动时内容贴边即停、松手吸附**；**②撞墙反弹系数 ×1.5**。

### 10.1 原来为什么吸不上

拖动那条路**从来没有边界**——`setPosition` 直接跟指针走，实测能把宠物拖到 `y = -21589`。
"放到边上就吸"这条（`resume` 里那句 `tryAttachNow`）其实存在，但被三件事挡着：

| 挡路的 | 现象 |
| --- | --- |
| **`onMouseUp` 的"速度不足"分支直接 `startThrow(pos, {0,0})`** | 宠物被先摔到地面，等 `resume` 再判吸附时它已经在地上了——位置早就不贴边。**这条是主因，用户"拖到边没反应"就是它** |
| `tryAttachScreen` 只判左右，**顶边压根没有这条**（注释写着"宠物站在地面线上，够不着屏幕顶"） | 拖到顶部没有任何反应 |
| 判定用的是**锚点**到墙线的距离，而锚点在脚底中心、周围还有一圈素材留白 | 用户按"看到的身子贴到边了"松手时，锚点可能还差几十像素 |

### 10.2 做法

**拖动时按「内容」夹，松手时按「内容贴住哪条边」吸。**

| 位置 | 改动 |
| --- | --- |
| `pet-core` 的 `perch.ts` | 新增 `contentExtents` / `dragBoundsOf` / `flushEdges` 三个纯函数 |
| `SpritePetRenderer` | 新增 `getContentExtents()`：从**已解码的图集**上量当前动作组的不透明包围盒（按组缓存） |
| `PetCanvas` | 指针移动时 `clampDrag` 夹住位置；松手**先问 `canAttachHere()`** 再决定吸还是落；抛掷走 `THROW_RESTITUTION = 0.825` |
| `PetWanderDriver` | 新增 `canAttachHere()`（只判不做）；`resume` 里**吸附判定提到坠落之前**；`attachPerch` 支持直接吸天花板；`clampPosition` 的下界 16 → 0 |

⚠ **判据必须是「内容」不是「画布」**：整个 `canvas` 贴上去是带留白的，团子的内容
只占画布宽度的 79%（444/560）。用画布算，宠物会停在离屏幕边 **22px** 的地方，
看着像没拖到位——这也正是用户说"要同时到边缘"的来源。

⚠ **`canAttachHere` 的位置必须问渲染器，不能用自己的 `x/y`**：拖动期间画布是直接写
`renderer.setPosition()` 的，驱动被让位挂着，坐标还停在"被拎起来之前"。拿它判会得出
"在**原来**的地方能不能吸"——与用户手上那一拖无关。

⚠ **`flushEdges` 的容差用 `attachDistance`（24px），不能是 1px**：拖动是直接操作，
光标最低只能到屏幕顶（`y=0`），而宠物相对光标有个抓取偏移——**光标推不动的地方
宠物也到不了**。实测从墙上把猫往上拖到 `(200, 0)`，锚点只到 `y=44`，而内容上伸量是
40，差 4px 就判不成"贴住"，松手掉了下来。1px 的判据等于要求人手把宠物推到恰好贴边。

⚠ **`clampPosition` 的 16 会吃掉贴顶吸附**：矮姿势的内容上伸量可能不到 16px，
锚点被抬到 16 就不再"贴着上沿"，`flushEdges` 判定失败，拖到顶端反而不吸。

### 10.3 判据

**单测**：`packages/pet-core` 45 条（新增 5 条：内容口径、翻转互换、夹取区间、退化情形、
贴边判定）、`apps/windows` 的 `PetWanderDriver` 20 条（新增 3 条：贴顶松手吸到天花板、
**没贴边时照旧坠落**、`canAttachHere` 只判不做）。

**实机**（`verify/pet-sprite/characters/drag-pet.mjs` 合成拖拽，日志为准）：

```
[onMouseUp] 贴住了屏幕边，吸附而非落下 @(39, 1172)     ← 左墙
[perch] 吸附到屏幕左墙 x=27
[onMouseUp] 贴住了屏幕边，吸附而非落下 @(2525, 829)    ← 右墙
[perch] 吸附到屏幕右墙 x=2533
```

⚠ **合成拖拽踩到两个坑，都写在 `drag-pet.mjs` 头部**：速度必须落在"丢"（`startThrow`
的门槛 320px/s）与"抛"之间；而**真鼠标的移动会不断打断它**——指针 hover 到模型上时
主进程会把穿透关掉，于是别处来的 `buttons: 0` 也送进页面，`PetCanvas` 把它当
"左键已松开"直接 `abandonDrag`。测试侧挂了个捕获监听挡掉这些事件（**没动产品代码**：
真机只有一个指针设备，不会误触）。

⚠ **顶边吸附只有单测**：实机试到的那几次都被真鼠标打断或误判成了"抛出去"。
用户手动拖一下最直接。




## 十一、概览页不显示宠物形象（2026-09-23）

用户报：「概览页面右下角宠物弹窗，没有显示当前被选中的宠物形象」。

### 11.1 根因

那块卡片（`DashboardPage/components/VirtualHuman`）是**只读**的：拿注册表条目的
`thumbnailUrl` 画 `<img>`，**没有就画一个占位星标**。而内置注册表里

```
mao_pro       thumbnail = mao_pro/runtime/icon.png      ← Live2D 三只有
ug_official   thumbnail = ug_official/runtime/icon.png
xiaomai       thumbnail = xiaomai/runtime/icon.png
demo_*        （空）                                     ← sprite 三只一只都没有
```

——**精灵图模型从来没做过缩略图**，所以选团子时卡片永远是占位图标。

顺带一处：同一张卡片的副标题**写死** `Live2D · 共 N 个形象`，显示精灵图宠物时
那句话也是错的。

### 11.2 做法

缩略图在**安装期**生成，运行期一个字都不用改：

| 位置 | 改动 |
| --- | --- |
| `lib/pet-thumbnail.mjs`（新增） | 从装好的图集取 `Idle` 首帧、按**不透明像素外接矩形**裁紧、缩到 128×128 正方形（不足补透明） |
| `install-pet.mjs` | 装完生成 `thumbnail.png`、往 `pet.json` 写 `thumbnailUrl`，然后**再装一次** |
| `VirtualHuman/index.tsx` | 副标题按 `rendererType` 出「精灵图 / Live2D」 |

⚠ **非正方形会被卡片的 `border-radius: 50%` + `object-fit: cover` 裁掉两边**，
所以输出统一是方的。

⚠ **`thumbnailUrl` 必须带上模型目录名**（`demo_cartoon_cat/thumbnail.png`）：
解析侧（`pet-model-resolver` 的 `toUserUrl`）是按**用户宠物目录**拼绝对路径的，
写成裸文件名会去找 `~/.lumii/pet-models/thumbnail.png`。内置注册表那三条也是这个写法。

⚠ **改完 `packageDir` 要重装一遍**，别自己去改 `registry.json`：注册表条目是
`install` 从 `pet.json` 归一化出来的，手写等于加了第三个写者，下次重装就被冲掉。

### 11.3 判据

实机（`lumii-cdp` 查主窗口 DOM）：

```
img src = lumii-pet://model/demo_cartoon_cat/thumbnail.png  naturalSize = 128×128
```

截下卡片那一块，能看见猫脸（耳朵、眼睛、口鼻）与下方名字。
