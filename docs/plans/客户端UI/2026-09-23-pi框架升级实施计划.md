### 3. 记忆注入路径重写：从 setSystemPrompt 改成 SystemMessage（4-6 小时）

**现状**：
- `memory-integration.ts:112/128/133` 调 `agent.setSystemPrompt(updatedPrompt)`
- `bridge-prompt-dispatcher.ts:369` 每轮调 `instance.setSystemPrompt(freshPrompt)`
- 新版 `setSystemPrompt` 不存在，`systemPrompt` 是 readonly getter

**改法（两条路径）**：

#### 3a. memory-integration.ts（已不被调用，但测试仍在）

**方案**：保留接口，内部改成 push SystemMessage。

```ts
// 旧：agent.setSystemPrompt(updatedPrompt)
// 新：
const messages = [...agent.messages];
if (messages[0]?.role === 'system') {
  messages[0] = {
    ...messages[0],
    content: updatedPrompt,  // 全量语义
    timestamp: messages[0].timestamp,
  };
} else {
  messages.unshift({
    role: 'system',
    content: updatedPrompt,
    timestamp: Date.now(),
  });
}
agent.messages = messages;
```

**问题**：`updatedPrompt` 是全量重建（base + 记忆注入），不适合用 `sections`（那是增量替换）。

**决策**：直接替换 `messages[0].content`（全量语义不变）。

#### 3b. bridge-prompt-dispatcher.ts（真实调用路径）

**同样改法**：替换 `messages[0].content`。

**附加工作**：
- 确认 `agent.state.messages = [...]` 是否安全（文档说 accessor 会拷贝，但需实测）
- 若不安全，改成逐条 push（但会触发多次事件，需确认影响）

**验证**：
1. typecheck 通过
2. 起 `dev:restart`，发一条消息，查日志 `[llm-prompt:full:begin]` 确认提示词正确注入

**P1.2 记忆注入** — 修复后才通过，且查出**本次升级最严重的回归**。

`defaultConvertToLlm` 只保留 `user/assistant/toolResult`，把 `system` 滤掉了。旧版 pi 的
系统提示词走独立的 `Context.systemPrompt` 字段、工具走 `Context.tools`，滤掉 system 无副作用；
**新版把提示词和工具声明都挂进 transcript 的 SystemMessage**，滤掉它等于两样一起删。

现场：inputTokens 从全天均值 6 万+（升级前）掉到 **78 / 84 / 86**，模型回
「当前环境没有文件系统读取工具」。修 `message-repair.ts` 放行 system 后回到
**72991 / 76251**，`file_read` 正常调用。新增 5 条用例。
**这个 bug 是静默的**——不报错、对话照常，日志与 `contextUsage` 全程"正常"。

**P1.3 harness/durable** — 调研完成，结论「短期不集成」。确认 `harness/` 下钩子系统（`before_run`/`before_tool`/`after_tool`/`transform_context`）、`session/` 下持久化（jsonl + 内存态）、`SuspendedRun`/`ResumeResult`/`DeferredHandle` 恢复链、`LaneBusy` 并发控制均已就位。不集成的理由是要把 `AgentInstance` 整体换成 `AgentHarness` 并自实现 `StorageState`，现有记忆注入/压缩/工具注册都得迁；收益（崩溃恢复、断点续跑）留到 P2+ 在新功能上试点。

**P1.1 steering 语义** — 已实测，**确实退化了，已修复**。

退化有两层，不止「轮询时机」：
1. steering 轮询从「每个工具后」挪到「整批之后」（`0.87.1 agent-loop.js:186`）
2. **批内默认并发执行** —— 这一条更致命：并行路径会在执行前把所有工具都 prepare 完
   （`agent-loop.js:410-440`），`beforeToolCall` 一个都拦不住

修复（`agent-instance.ts`）：`toolExecution: "sequential"` + `beforeToolCall` 检查自数的
`pendingSteerCount`。**不能用 `agent.peekQueuedMessages()`**——它在 steering 为空时会回退到
followUp 队列，会把本仓的 token-budget nudge 误判成插话。

实测证据（一条 assistant 消息含 `[bash, bash, file_mkdir, bash]`）：插话落在 bash #1 执行期间
（20:02:02），bash #1 于 20:02:25 结束后，剩余工具全部返回 `isError=true "用户插话，跳过本批剩余工具"`，
插话后 bash 执行 0 次。新增 4 条用例，已验证改回 `parallel` 会红 2 条（不是空跑）。

**实测踩的坑**（三个都造出过假结果）：

1. 模型把两条命令合并成 `sleep 30 && echo ...` → 只有一个工具调用，构不成场景。
   必须从 DB 核对该 assistant 消息的 tool 块数 ≥2 才作数。
2. 判据别数 `agent:tool:start`：主进程事件 + renderer 回显会翻倍；窗口起点错位还会给出
   假阳性。**只数 `ToolRunner → bash`**。
3. 这个模型（Qwen3.8-Flash-Next @ kms.sczxsc.cn）对**合成指令**不发结构化调用——让它
   「跑两次 sleep」，它把命令写成 markdown 代码块就收工，thinking 里还写着「我应该使用工具」。
   措辞越"元"越不肯用。换成自然任务描述才发。交付前需知：**用这个模型做 E2E 会撞上这条**。

**驱动方式**（供复用）：本机没有 `chrome-remote-interface`，但有 `playwright-core`，
用 `chromium.connectOverCDP('http://127.0.0.1:9222')` 即可驱动。composer 是
`[contenteditable="true"]`（不是 textarea），发送要**先填值、等 React 同步、再单独按 Enter**，
同一 tick 里做完会丢。临时脚本跑完已删。

**顺带发现（未处理）**：App 的 `conversation:delete` 不清理 `memory_segments`——实测 364 行里
100 行是孤儿（会话已不存在），多数早于本次改动。属既有行为，删测试会话时核对过。
