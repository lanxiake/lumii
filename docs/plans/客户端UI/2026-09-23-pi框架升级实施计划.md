## P0 详细步骤

### 1. contentText 替代手写（1-2 小时）

**现状**：`packages/agent-runtime/src/compact/api-invariants.ts:38-58` 手写 `readMessageContent()`，用 `as` 断言绕联合类型。

**改法**：
1. 从 `@earendil-works/pi-ai/utils/text` import `contentText`
2. 删除 `readMessageContent()` 函数定义
3. 全局替换调用点：`readMessageContent(msg)` → `contentText(msg.content ?? '')`
4. 处理边界：`msg.content` 可能不存在（如 `bashExecution`），需先过滤或用 `convertToLlm`

**影响文件**：
- `packages/agent-runtime/src/compact/api-invariants.ts`（定义 + 5 处调用）
- `packages/agent-runtime/src/compact/strategies/*.ts`（约 20 处调用）

**验证**：`pnpm --filter @mtbot/agent-runtime typecheck`

---

### 2. AgentMessage 联合类型：用官方 convertToLlm（2-3 小时）

**现状**：26 个 `.content` 类型错误，因 `AgentMessage` 包含没有 `content` 的 `BashExecutionMessage`。

**改法**：
1. 从 `@earendil-works/pi-agent-core/harness/messages` import `convertToLlm`
2. 在需要访问 `.content` 的地方，先调 `convertToLlm(messages)` 收窄为 `Message[]`
3. 或用 `contentText` 直接处理（它内部会过滤）

**关键位置**：
- `packages/agent-runtime/src/compact/strategies/micro-compact.ts`（16 个错误）
- `packages/agent-runtime/src/agent/agent-instance.ts`（8 个错误）
- `apps/windows/src/main/agent-runtime/bridge-agent-instance-events.ts`（3 个错误）
- `apps/windows/src/main/agent-runtime/bridge-context-compactor.ts`（2 个错误）

**策略**：
- 压缩策略（micro-compact）：在入口处 `convertToLlm` 一次，后续逻辑只处理 `Message[]`
- 事件处理（bridge-agent-instance-events）：按需收窄（或用类型守卫 `if ('content' in msg)`）

**验证**：`cd apps/windows && pnpm typecheck`

### 3. 记忆注入路径重写：从 setSystemPrompt 改成 SystemMessage（4-6 小时）

**现状**：
- `memory-integration.ts:112/128/133` 调 `agent.setSystemPrompt(updatedPrompt)`
- `bridge-prompt-dispatcher.ts:369` 每轮调 `instance.setSystemPrompt(freshPrompt)`
- 新版 `setSystemPrompt` 不存在，`systemPrompt` 是 readonly getter

**改法（两条路径）**：

#### 3a. memory-integration.ts（已不被调用，但测试仍在）

**方案**：保留接口，内部改成 push SystemMessage。

```ts
// 旧：agent.setSystemPrompt(updatedPrompt)
// 新：
const messages = [...agent.messages];
if (messages[0]?.role === 'system') {
  messages[0] = {
    ...messages[0],
    content: updatedPrompt,  // 全量语义
    timestamp: messages[0].timestamp,
  };
} else {
  messages.unshift({
    role: 'system',
    content: updatedPrompt,
    timestamp: Date.now(),
  });
}
agent.messages = messages;
```

**问题**：`updatedPrompt` 是全量重建（base + 记忆注入），不适合用 `sections`（那是增量替换）。

**决策**：直接替换 `messages[0].content`（全量语义不变）。

#### 3b. bridge-prompt-dispatcher.ts（真实调用路径）

**同样改法**：替换 `messages[0].content`。

**附加工作**：
- 确认 `agent.state.messages = [...]` 是否安全（文档说 accessor 会拷贝，但需实测）
- 若不安全，改成逐条 push（但会触发多次事件，需确认影响）

**验证**：
1. typecheck 通过
2. 起 `dev:restart`，发一条消息，查日志 `[llm-prompt:full:begin]` 确认提示词正确注入

## P1 步骤（后续排期，本次不做）

### P1.1 steering 语义验证与补救

**目标**：确认新版「整批工具后注入」是否削弱即插话体验。

**步骤**：
1. 复现插话测试场景（两次 `sleep 30`，第一个工具后插话）

3. **若退化**（两个 sleep 都跑完了）：在 `beforeToolCall` 钩子里实现提前终止
   ```ts
   beforeToolCall: async (ctx, signal) => {
     if (agent.peekQueuedMessages().length > 0) {
       return { block: true, reason: '用户插话', terminate: true };
     }
   }
   ```

## 风险与应对

| 风险 | 应对 |
|---|---|
| `agent.state.messages = [...]` 破坏不变量 | 若实测有问题，改成 push 增量 SystemMessage（但要处理事件风暴） |
| 压缩策略测试大面积失败 | 按新版消息结构调整 mock（预留 2-3 小时） |

**为什么比预计快这么多**：

1. **步骤 2 整个不需要**：一轮数出的 26 个 `.content` 错误，根因是 `readMessageContent` 与 `setSystemPrompt` 两处；这两处一改，其余错误连带消失。`convertToLlm` 是正确的备选方案，但本次没有用到它的场景。
2. **`sections` 没用上**：`buildPromptWithMemory` 产出的是**全量重建**的提示词，直接替换 `messages[0].content` 语义就对得上。`sections` 的按名增量替换适用于「只改一段」的场景，本仓当前不是这个形态——调研它的价值在于**证明了官方有这条路**，而不是这次必须走它。
3. **一轮的机械替换已铺好路**：73 个文件的包名与 `/compat` 入口都已就位，二轮只需处理两处真正的架构差异。
