# 宠物自制系统 P2-b 实施计划（键鼠联动 · 注视）

设计见 [`../../design/客户端UI/2026-09-20-虚拟人精灵图渲染后端设计.md`](../../design/客户端UI/2026-09-20-虚拟人精灵图渲染后端设计.md) §8（P2：多宠物同屏、好感度/状态系统、键鼠联动）。

## 一、先定一件事：不引全局键盘钩子

设计 P2 提到「键鼠联动（Bongo Cat 类）」。真要做 Bongo Cat 那种**全局**键盘联动，得引 native
全局钩子（uiohook 类）。**本轮不引**，两条理由：

1. **信任**：一个聊天应用装全局键盘钩子，技术上能看到用户输入的密码。这不该是默认行为。
2. **体量与稳定性**：native 模块要按 Electron ABI 重编（仓库已有这套设施，但每加一个就多一处
   平台相关的失败面），与设计里「客户端尽量轻量、不容易出错、不能破坏系统稳定性」相冲。

`globalShortcut` 也不能用——它会**吞掉**快捷键，拿来做"打字跟着敲"等于抢用户的键。

**不引依赖仍能做「键鼠联动」**，因为 Electron 自带两个安全的全局信号：

| 信号 | API | 能表达什么 | 看不到什么 |
| --- | --- | --- | --- |
| 光标位置 | `screen.getCursorScreenPoint()` | 宠物**看向**鼠标、跟随移动 | — |
| 系统闲置 | `powerMonitor.getSystemIdleTime()` | 用户离开 → 宠物静下来；回来 → 醒来 | — |

两者都拿不到按键内容，也就不存在"聊天应用偷看输入"的问题。本计划先做**注视**，
闲置感知另立 P2-c。

## 三、关键设计决策

### 3.1 为什么不让渲染层自己读光标

宠物窗口是**全屏透明 + 主进程 `setIgnoreMouseEvents` 控制穿透**的。光标在角色以外的区域时，
窗口收不到 `mousemove`——恰好那是"宠物该看向你"的多数时刻。

所以只能由主进程轮询后推送。

### 3.2 轮询频率与开关条件

30Hz（33ms）。理由：低于这个值转动会明显卡顿；高于这个值是在为一件视觉上感觉不到的事
持续付 IPC 成本（本仓库对 IPC 耗时是敏感的，MEMORY 里记过一次全量哈希冻主线程的事故）。

**只在宠物模式且窗口可见时轮询**，其余时候停掉——不是"发出去让渲染层丢掉"。

### 3.3 注视是**叠加**在程序化原语之上的

呼吸/浮动是振荡（时间驱动），注视是**朝目标**（位置驱动），两者性质不同，不能混进同一套
参数。渲染层组合成：`rotation = sway(振荡) + gazeTilt(朝向)`，`position = base + bob(振荡) + gazeShift(朝向)`。

### 3.4 死区、满量程与上限

- **死区**：光标离宠物很近时不做任何偏移。否则鼠标在角色身上划过去，宠物会抽搐。
- **满量程**：光标到 **0.8 倍宠高**（约一个身位）时给满响应。
- **上限**：倾斜最多 ±6°、位移最多 ±4% 画布高。桌宠是陪衬，"死死盯着你"会让人不适。

死区与上限这两个数不是拍的：桌宠的默认尺寸约 110px 高，6° 在头部（半径约 40px）上产生约 4px 位移，
肉眼刚好能看出"它在看我"，再大就变成"它在瞪我"。

**满量程是上机后调过的（2.5 → 0.8）**。初版取 2.5 倍宠高，手感是「宠物完全没反应」。
拿实测数据一算就清楚了——像素猫 56px 画布 × `scale` 2 = 屏幕 112px，而归一化的除数是
`getModelScreenBounds`（`getBounds()` + 12px 边距）即 **136px**；光标离宠物中心 88px 就是归一化距离
0.65，落在 2.5 倍量程的前 18%：`t ≈ 0.08` → 倾斜 0.14°、眼睛挪不到一个像素，等于没有。

**满量程定得太远，等于把响应压没**：桌宠周围一两个身位内恰恰是光标最常待的地方。
改成 0.8 后同一位置 `t ≈ 0.81` → 倾斜 1.4°、眼睛挪约 5 个屏幕像素，从"看不出来"到"看得出来"。

### 3.5 开关默认开，但必须能关

追踪鼠标是**可能让人不适**的行为（有人就是不喜欢被盯）。给设置项，默认开。

## 五、验收

**单测**（pet-core）

- 死区内输出恒为零（含边界点）
- 归一化输入 → 倾斜/位移在声明上限内
- 输入非有限数 → 输出零（不产生 NaN 旋转，那会让角色消失）
- 映射单调：离得越远、倾斜越大（到上限为止）
- **常见距离（≈0.65 倍宠高）下响应可见**：满量程被调远的回归防线（2.5 时这里只有 0.14°）

**手测**（真实客户端）

> **用哪个宠物测：`demo_pixel_cat`**（内置 · 也是注册表的 `defaultModelId`，不切就是它）。
> 它的动作组与分层表情层最全，**下面 5 条全部成立**。
> 换成别的模型会出现「按说明试了但没反应」——比如 `real_dog` 没有分层表情层，眼睛不动；
> Live2D 三个后端本轮根本没接 `setGaze`。**动手前先对照 §七 的能力表。**

1. 鼠标在屏幕上游走，宠物朝光标方向倾斜——**光标进到一个身位内就该看得出来**（满量程调成 0.8 要保证的就是这条）
2. 鼠标贴到宠物身上 → 不抽搐（死区生效）
3. 鼠标放到很远 → 倾斜到上限为止，不继续加大
4. 关掉设置项 → 不再跟随
5. 退出宠物模式 → 主进程停止轮询（不再有 IPC 流量）

### 5.1 手测怎么量（2026-09-21 首轮实测）

肉眼很难分辨 6°，所以这轮手测是**量化**做的：主进程轮询的光标位置由脚本直接设
（PowerShell `Cursor.Position`），每换一个位置截宠物窗口，取**宠物的连通域重心**比较。

| 光标偏移（相对宠物锚点） | −300 | −150 | −88 | −18 | +18 | +88 | +150 | +300 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 重心位移（半尺寸像素，相对死区中点） | −3.10 | −3.15 | −1.94 | **−0.02** | **+0.03** | +2.82 | +3.14 | +3.24 |

读法：**死区内 ±0.03 ≈ 不动**；±88（一个身位）已有 2~3 像素、肉眼可见；±150 起饱和；
**方向正确**（光标偏右 → 宠物右移）。A/B 对照——同一套测量，只把 `enableGazeTracking`
关掉：Δ 从 **+6.33 ± 0.02 变成 −0.00 ± 0.01**，第 4 条据此判定通过。

**两个测量上的坑，复测时必须避开**：
- **宠物进宠物模式后会落到地面**（P2-a 的物理），位置要等它落定后再取；否则锚点会偏几百像素。
- **别用「窗口内所有亮点」算重心**：控制坞按钮和暗色 UI 文字会把位移稀释掉一个数量级，
  还会把锚点带到宠物下方。**取最大连通域**才是宠物本体。

上面这两条已经固化进 [`verify/pet-sprite/check-gaze-response.mjs`](../../../verify/pet-sprite/check-gaze-response.mjs)：
`node verify/pet-sprite/check-gaze-response.mjs`（会接管鼠标，别同时操作）——它进宠物模式、
等落定、交错采样八个位置、按五条判据打分并把曲线写进
`docs/test/pet-sprite/evidence/check-gaze-response-result.json`。**判据量的是倾斜角
（行重心对 y 的加权回归斜率）而不是重心位移**：实测宠物会在测量期间自己挪位置
（一次跑动里右移 800px、下移 350px），依赖绝对坐标的量会整个作废；倾斜角只跟姿态有关。
代价是它带一个形状偏置（宠物自身不对称，静止时读数 ≈ −1.9°），所以判据只用位置之间的
**差**，不声称绝对角度。实测曲线：−300/−150 饱和在 −4.95/−4.94，−88 为 −3.52，
±18 完全相同（−1.87），+150/+300 饱和在 +1.30/+1.32 → 摆幅 6.28。

> 绝对读数**会随轮次漂移**（动画相位、宠物站立位置、采样数都会影响，复测见过摆幅 6.28~6.71、
> −88 处 −3.52~−4.05）。判据全部按**差值**设阈值，所以漂移不影响判定；
> 引用具体数字时请带上是哪一次跑出来的，别当成常数。

### 5.2 这轮手测抓到的三个真缺陷（已修）

| 缺陷 | 症状 | 根因 |
| --- | --- | --- |
| 模型加载 effect 卡死 | 切到精灵图**永久空白**（「按说明试了没反应」的另一种形态） | effect 依赖 `rendererReady` 状态 + `rendererRef` 引用两个来源，二者会不一致（读过 `rendererReady=true` 而 ref 仍为 null 的那一帧），提前 return 后两个依赖都不再变化 → **永不重试**。改成把渲染器实例放进 state 当依赖 |
| 注视倾斜**方向相反**且幅度更大 | 宠物朝光标的反方向歪 | `transform.rotation`/`tiltDeg` 是**度**，PIXI 的 `rotation` 是**弧度**，漏了换算（±6° 当成 ±6 弧度 ≡ ∓16°）。此前所有模型都没声明 sway/nod，`transform.rotation` 恒为 0，所以从没暴露 |
| 跨后端切换必弹降级提示 | 「切换 Live2d 报错模型加载失败」 | 上面那条修复的**副作用**：state 比 ref 慢一拍，切后端那一帧读到的还是**刚被销毁**的旧实例，`loadModel` 打在它身上 → 报「渲染器未初始化」。补两道守卫：实例必须是 `rendererRef.current`、后端必须与 config 一致 |
| `switchMode` 在已处于宠物模式时静默 no-op | 想换模型却什么都没发生（`durationMs: 0`，零日志） | `if (from === mode) return` 把「换模型」也一并挡掉了；现在放行并记一行日志 |

**一个已知未修的问题**（不属本次改动，但会撞上）：两个渲染器的 `destroy()` 都只做
`app.destroy(false, {...})`，**不释放 WebGL context**——PIXI 不管这件事，要等 canvas 被 GC 才回收。
反复切后端会累积 context，撞上浏览器每页上限后它会回收**最老的那个**，日志里表现为
`[init] WebGL context lost — 渲染将暂停`，且出现在**新渲染器刚建好**的那一毫秒，极易误判成新渲染器坏了。
（试过用 `WEBGL_lose_context` 主动丢，**反而更糟**：React 18 dev 的 StrictMode 会 setup→cleanup→setup
复用**同一个 canvas 元素**，主动丢 context 等于把下一个渲染器毒死——已回滚。要修得让每个渲染器世代
拥有自己的 canvas 元素，而不是共用 `key={rendererType}` 那个。）

## 七、测哪个模型：能力对照表

**这一节是实测反馈补的**：模型之间的动作组与表情集差别很大，不标注就会出现「按说明试了但没反应」——
因为那个模型根本没有这一组。

**切换位置**：设置页 → 宠物区块 → 「虚拟人模型」（切换后立即生效，宠物模式中会热重载）。
下表数据取自 `apps/windows/resources/pet-models/registry.json` 与各模型的 `manifest.json`（2026-09-20 核对）。

| 模型 | 来源 | 动作组 | 表情 | 能不能测注视 |
| --- | --- | --- | --- | --- |
| **`demo_pixel_cat`** | 内置 · sprite · **默认模型** | **9 组**：Idle / Talk / Jump / Wave / Nod / Shake / **Picked** / **Land** / PlayBall | 12 款眼神 | ✅ **全功能，测什么都用它** |
| **`demo_hires_girl`** | 内置 · sprite | 同上 | 12 款眼神 | ✅ 同上（只是画风不同） |
| `real_dog` | 用户工作区 · sprite（P1-c 生成线产出） | 2 组：Idle / Talk | 无分层槽 | ⚠️ 只能测待机与整体倾斜，**眼睛不会动** |
| `mao_pro` | 内置 · Live2D | 丰富（`actionMotions` 覆盖 8 组：`$unnamed` / Dance / Sleep / Fly / Jump / RPS / Taunt / Clap） | 12 | ⚠️ Live2D 后端，注视走它自己的视线机制（本轮未接 `setGaze`） |
| `ug_official` | 内置 · Live2D | **0 组**（`actionMotions` 是空对象） | 9 | ⚠️ 只有表情，没有动作 |
| `xiaomai` | 内置 · Live2D | 6 组：start / tap_head / tap_body / shake / random / new_msg | 1 | ❌ **Cubism 2 格式，当前渲染不了**（见 P0-b 的已知问题） |

**判断一个新模型能不能测注视，看一条就够：它有没有「分层表情层」**（`manifest.slots` 里带
`parts.eyes` 的槽）。眼睛是靠平移承载表情的那个 sprite 实现的（`applyEyeGaze`），没有分层槽的模型
（如 `real_dog`：整个 `manifest` 里连 `slots` 键都没有）只能整体倾斜，眼睛不会动。
这不是缺陷，是那类模型确实没有可动的眼睛层。
