> 创建：2026-10-26 · 状态：**fork 已完成并真机验收**（2026-10-26）；/btw 待实施（Phase 0 先验可行性）

## 一、会话分支（fork）

### 1.1 用户语义

在一个会话中途，把**到某条消息为止**的历史复制成新会话，两边各自继续演进。
父会话不动。

已确认的两个决策：

1. **纯复制，不带新问题** —— 复制完停在原地，等用户自己输入。
2. **不复制 `session_config`** —— 模型、会话级禁用集、压缩参数都回落全局默认。
   分支是「从这块历史重新开一局」，不是「父会话的克隆」。

### 1.2 现有代码（已取证）

```
packages/agent-runtime/src/storage/conversation-repo.ts:1016   forkConversation()
apps/windows/src/main/ipc/agent-runtime/conversation-commands.ts:937   handleConversationFork()
apps/windows/src/shared/agent-runtime-commands.ts:1239         ConversationForkCommand
apps/windows/src/renderer/hooks/business/useAgentRuntime/useAgentRuntime.ts:475  forkConversation()
```

现成能力（**不用改**）：

- 复制时保留 `agent_id` / `content_json` / `compacted_at`，timestamp 不变；
- 排除 `is_streaming = 1` 的残行；
- 事务包裹，`last_msg_at` 显式设为复制时刻（所以新会话会排到侧栏顶部）。

### 1.3 四个必须修的问题

**坑 1 · `newUserContent` 是必填，且会强插一条 user 消息**

```ts
// conversation-repo.ts:1019
readonly newUserContent: string
...
// 1080：无条件追加
insertMsg.run(generateId(), newConv.id, null, "user",
  JSON.stringify({ type: "text", text: newUserContent }), now, 0, null);
```

→ 改成 `readonly newUserContent?: string`，`if (newUserContent)` 才插。
命令层 `newContent` 同步改可选。现有唯一调用方就是 `handleConversationFork`，无外部依赖。

**坑 2 · 复制边界用 `timestamp <=`，同毫秒的多条消息会一起被拿走**

```ts
// conversation-repo.ts:1036
`WHERE conversation_id = ? AND is_streaming = 0 AND timestamp <= ? ORDER BY timestamp ASC`
```

`insertMsg` 在同一个事务里跑，一批消息可能落在同一毫秒。

**修订**：实施前必须验证 `messages` 表的主键是 `id` 还是 `rowid`：
- 若主键是 `id`（显式 `TEXT PRIMARY KEY`），改为 `ORDER BY timestamp ASC, id ASC`，然后用二分找锚点；
- 若主键是隐式 `rowid`（`INTEGER PRIMARY KEY`），改为 `ORDER BY timestamp ASC, rowid ASC`。

单元测试必须覆盖同毫秒多条消息场景，断言只复制到锚点。
若锚点消息本身 `is_streaming = 1`，直接抛错——分支一个半截回合没有意义。

**坑 3 · 分支会话永远叫「新对话」，多次分支会重名**

`maybeGenerateConversationTitle` 的触发条件是 `userCount === 1`（首轮）或 `% 4 === 0`（刷新）
（`conversation-commands.ts:580`）。分支会话创建时就带 N 条用户消息：
- 首次发消息时 `userCount` 从 N+1 开始 → 永远不是 1；
- 只有恰好叠到 4 的倍数才刷新。

→ `handleConversationFork` 里显式写标题：
```ts
const title = `${父标题 || "会话"} · 分支@${Date.now().toString().slice(-6)}`
```
时间戳后六位作为后缀，避免对同一会话多次分支时重名。

**坑 4 · 现在没有广播，侧栏看不见新会话**

`handleConversationFork` 全程不调 `forwardIpcEvent`（对比 `handleConversationCreate:140`）。
侧栏只在收到 `conversation:created` 时重拉（`event-handler.ts:1613`）。

**修订**：广播必须在 `forkConversation()` 完成、所有消息插入之后再发，避免侧栏读到空会话（尽管 `last_msg_at` 有写，但极端情况下事务未提交前的读会看到 0 条消息）。

另外，空分支（不追加 newUserContent）的 `last_msg_at` 改用 `Date.now()`（分支创建时刻），而不是锚点消息的 `timestamp`，确保新会话排在父会话之后。

### 1.4 改动清单

| # | 文件 | 改动 |
|---|---|---|
| F1 | `conversation-repo.ts` | `newUserContent` 可选；复制边界改 `(timestamp, rowid)` 定位；锚点 streaming 则抛错 |

## 二、旁问（/btw）

### 2.1 语义（照 Claude Code，但按 Lumii 的形态裁剪）

主回合在跑的时候，用户想问一个**不影响主线**的问题（"刚才那个参数为啥这么填"）。
主回合**不中断**，旁问**无工具**、**只答一轮**、**不进 transcript 上下文**。

与本仓 `steer`（插话）的区别必须写清楚：

| | steer（已有） | /btw（本次） |
|---|---|---|
| 效果 | **改主回合的方向** | **不碰主回合** |
| 落库 | 落库为插话气泡 | **不落库** |
| 进后续上下文 | 进 | **不进** |

### 2.2 现有可复用手部件（全部已存在）

| 能力 | 位置 |
|---|---|
| 斜杠命令注册 + 分发 | `renderer/pages/ChatPage/commands/slash-commands.ts`、`slash-command-executor.ts` |
| 非持久化系统消息（显示答案用） | `ChatPage.tsx:1015 addSystemMessage` |
| **单轮 stream 直调（不落全文日志、支持 abort、带超时）** | `plugins/builtin/selection/selection-llm.ts`（`SelectionLlmService`） |
| stream+model 解析（四级降级、按会话模型） | `bridge.ts:752 resolveSelectionChatStream()` → `compactor.resolveCallStream()` |
| 运行中取内存历史 / system prompt | `bridge.resolveMainInstanceForSession()` → `instance.getAgentMessages()` / `getSystemPrompt()` |
| 空闲时取历史 | `conversationRepo.loadMessagesAsPiFormat(sessionKey, { limit })` |

**不**用 `bridge.callLLM()`：它会把完整 prompt 与输出写进日志文件
（`bridge-context-compactor.ts:124` 注释明说）。旁问内容是用户正文，等同划词的隐私口径。

### 2.3 最大的落地难点：历史怎么变成一份合法请求

这是本功能唯一有真实风险的地方，**必须按保守版实现**。

三个约束：

1. **`AgentMessage[]` 含 `toolResult` 角色**。压缩器的做法是
   `flatMap` 只留 `user / assistant / toolResult` 并原样透传
   （`bridge-context-compactor.ts:555`）。但那只在摘要场景跑过，
   旁问要喂给**同一个 provider**，一旦历史里有 `assistant.toolCall` 而对应
   `toolResult` 已被 `compacted_at` 排除，OpenAI/Anthropic 两条线都会报「tool_use 无配对」。

2. **运行中取的是内存态**，可能含正在流式的半截 assistant 消息 → 必须剔除。

3. **system prompt 只有运行中才有**。空闲时 `resolveMainInstanceForSession` 返回 undefined，
   不能为了旁问去建实例（会触发完整的工具装配，代价过大）。

→ **保守版规则（本次就按这个做，不做优化）**：

```
取最近 N 条（N=20）is_streaming=0 且 compacted_at IS NULL 的消息
只保留每条消息的纯文本正文：
  - user：content 里 text 部分
  - assistant：content_json 解析后拼 parts 里的 text 段
丢掉：tool 调用、tool 结果、thinking、附件引用行
末尾追加：
  <system-reminder>旁问提示词</system-reminder>
  + 用户问题
```

代价：**prompt cache 必不命中**（结构被改写）。这是本次明确接受的取舍——
先把它做出来，缓存优化等有人抱怨慢再说。

**system prompt 的处理**：运行中能拿到就带上；拿不到（空闲）就不带，
并在提示词里说明"你只看到对话正文，看不到文件系统"。**不建临时实例**。

### 2.4 提示词（照抄 Claude Code 的有效约束，去掉面板相关）

```
<system-reminder>这是一次旁问。请直接在一条回复里回答。
- 你是一个独立的轻量实例，主对话**没有**被中断，它仍在后台继续
- 你没有工具：不能读文件、不能跑命令、不能搜索、不能执行任何动作
- **不要**把工具调用写进正文（写了也不会执行）
- 只有一轮，没有追问
- 只能说对话里已有的信息；不知道就说不知道，不要承诺去查
只回答问题本身。</system-reminder>
```

后置清洗（Claude Code 那两条实测补丁）：

- 答里出现 `tool_use` / `<invoke>` 形态 → 整条替换成
  `（旁问不能执行工具，这条回答里的工具调用未被执行。）`
- 输出为空 → `（旁问没有返回内容，换个问法再试。）`

### 2.5 入口：**不能**只在输入框里打 `/btw`

这是关键发现，照抄 Claude Code 的交互会直接失败。**流式期间打字可以，但回车被截走**：

```ts
// ChatInput/index.tsx:433-445  handleKeyDown
if (e.key === 'Enter' && !e.shiftKey) {
  e.preventDefault()
  if (disabled) return
  if (isStreaming) {                       // ← 流式期间，Enter 一律当插话
    if (sessionKey) onSteer?.(sessionKey, text)   // 打 "/btw 为啥…" 会被原样 steer 进主回合
    return
  }
  ...
}
```

配套事实（都已核对）：

- `disabled = isSending || !isConnected`（`ChatPage.tsx:630,1982`）。`isSending` **只在
  `handleSend` 自身执行期间**为真，而 `user:send` 的 IPC **立即返回 runId**
  （`user-commands.ts:272`，注释原文「不 await，让它在后台运行」）→ 流式期间
  `disabled` 是 `false`，**输入框能打字**。所以卡点不是"打不出字"，是"回车被截"。
- 发送按钮在 `isStreaming` 时是 **abort**（`ChatInput:1153`），也不是发送。
- 斜杠补全面板的 Enter 分支（`ChatInput:405-419`）同样被上面的 `isStreaming` 分支挡住吗？
  **不会** —— 补全面板分支在 394 行，先于 Enter 判断，且它直接 `onSendWithValue`。
  也就是说：**用补全面板选中 `/btw` 能发出去，但手打 `/btw xxx` 回车会变成 steer。**
  这个不一致本身是个坑，不要依赖它。

→ **两个入口都要做**：

**入口 1（主路径）· 流式中的「旁问」按钮**
`ChatInput` 已有的 `isStreaming && onSteer` 插话区旁边加一个「旁问」，
展开一个小输入框（复用 `steer-input-area` 的样式与状态管理方式），
提交后**完全不经过 `handleSend`**，直接调旁问命令。

**入口 2（顺手）· 空闲时 `/btw` 斜杠命令**
在 `slash-command-executor.ts` 的 switch 里加 `case '/btw'`，
命令表加一条 `{ name: '/btw', aliases: ['/b'], category: 'session', usage: '/btw <问题>' }`。
空闲时这条路和入口 1 走同一个 IPC 命令。

**入口 1 顺带修一个既有不一致（可选，建议做）**：
`ChatInput:433` 的 `if (isStreaming)` 分支里，先判 `text.startsWith('/')` 就走斜杠路径
（`onSendWithValue`），不要把斜杠输入 steer 进主回合。这样手打 `/btw` 在流式期间也能用。
**只放行 `/btw` 及其别名**，其余斜杠命令在流式期间保持现状（`/clear` `/compact` `/new`
在运行中执行的行为一个都没验证过）。

**不**改 `ChatInput` 的斜杠补全面板的优先级 —— 它现在的行为是对的（先于 Enter 判断）。

## 附录 · Claude Code `/btw` 的实现要点（本机反编译取证）

供对照，不必照搬：

- **入口**：`/btw` 是 `local-jsx` 全屏面板，`immediate: true`；侧栏有快捷键重新打开
- **上下文来源**：主线程每轮存一份 `cacheSafeParams`（systemPrompt + userContext +
  systemContext + 完整 messages + stickyBetas），旁问整套复用 → 命中 prompt cache
- **执行**：`runForkedAgent({ maxTurns: 1, skipCacheWrite: true, skipTranscript: true,
  canUseTool: 永远 deny })` —— 三件套确保零副作用
- **兜底**：答里含 tool_use 会被替换成合成消息并标 `synthetic`；`synthetic` 不进旁问历史
- **历史**：会话级 20 条，后续旁问会把之前的问答对重新拼进上下文
- **超时**：远程 control-request 侧 660s / 600s；本地无显式超时
- **模型回落**：归为 `local` 作用域，回落只影响这一次答复，不改会话模型

Lumii 不照搬的三点：面板（用不着）、cacheSafeParams 复用（我们的历史结构被改写，
缓存本来就不命中）、历史重拼（会让旁问越滚越贵）。
