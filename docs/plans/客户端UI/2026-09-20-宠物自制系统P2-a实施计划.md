# 宠物自制系统 P2-a 实施计划（场景 A：抓取—拖拽—投掷—落地）

设计见 [`../../design/客户端UI/2026-09-20-虚拟人精灵图渲染后端设计.md`](../../design/客户端UI/2026-09-20-虚拟人精灵图渲染后端设计.md) §5.2 / §8。
这是设计明确划进 P0-b 范围、但当时只交了 pet-lab 验证版的一项。

## 一、为什么先做它

设计 §5.2 原文：

> **拖拽（P0 验证场景 A 的额外语义）**：现有拖拽仅 `setPosition`。场景 A 需要扩展：拖拽时进入 `Picked` 状态播「被拎起」动作，释放时按速度积分做抛物线 + 落地判定，落地播 `Land` 一次型动作后回 `Idle`。接口层需要新增「位置/速度变化」的回调或状态查询，**这是本期唯一需要触碰接口的部分**。

P0-b 只验证了「拖拽后命中区仍正确」（pet-lab 网格探测 100% 一致），**客户端里仍只有 `setPosition`**——
没有 Picked/Land 动作衔接，没有抛物线，没有落地判定。这一项没做完就进 P2，等于把设计里
唯一标注「必须触碰接口」的部分跳过去。

## 二、目标与边界

| # | 内容 |
| --- | --- |
| W1 | 抛掷物理 + 速度估计（纯函数，进 pet-core，可脱离 DOM 单测） |
| W2 | `PetCanvas` 拖拽升级：采样估速 → 释放后抛物线 → 落地 |
| W3 | 编排器接入：`Picked` / `Land` 动作衔接（模型声明了才播） |
| W4 | 示范模型补 `Picked` / `Land` 姿态，让这条交互**看得见** |

**不做什么**

- ✗ 多宠物同屏、好感度、键鼠联动 → P2 其余部分
- ✗ 抛掷时与其他宠物的碰撞 → 单宠物，无此需求
- ✗ 把「被拎起」塞进 `petStateMachine`：那是**对话**生命周期（idle/listening/thinking/speaking），
  物理状态与它正交。硬塞会让两个维度互相干扰

## 三、关键设计决策

### 3.1 物理放 pet-core，不放在画布里

抛物线与落地判定是纯数学，扔进 pet-core 就能脱开浏览器单测——与 P0-b 把帧归一化放进去同一个理由。

**但物理的「驱动」留在客户端**：谁在什么时候开始积分、落地后通知谁，是编排的事。
pet-core 只回答「经过 dt 之后物体在哪、有没有落地」。

### 3.2 地面高度 = 拖拽开始时的 y，不是屏幕底部

桌宠站在桌面上，那个「桌面」就是它原本待着的位置。用屏幕底部当地面，会让宠物被扔出去后
落到一个它从没待过的地方——用户视角里就是「掉到屏幕外面去了」。

用拖拽起点作地面，语义是「把它扔出去，它会落回原来的高度」。

### 3.3 速度估计用时间窗，不用最后一个采样点

鼠标事件的间隔不均（快甩时十几毫秒一个，慢拖时上百毫秒）。只看最后两点，一次抖动就能
把速度估到天上或归零。

做法：取最近 N 毫秒内的采样点，用**首尾位移除以时间差**。窗口太短噪声大、太长会把
「先慢后快」抹平，取 80–120ms。

### 3.4 动作衔接：模型声明了才播

`Picked` / `Land` 是**约定组名**（与 `Idle` / `Talk` 同级）。模型的清单里没有这两组时静默跳过——
不报错、也不退化成随便播点什么。理由与 P1-c 里「不凭空造动作组」一致：
播一个语义不对的动作比不播更糟。

## 五、验收

**单测**（pet-core，纯函数）

- 抛物线：给定初速度与 dt，位置符合解析解；落地那一帧 `landed=true` 且速度归零
- 边界：撞左右边界反弹且速度反向；落地后不再继续积分
- 速度估计：均匀采样、抖动采样、采样不足、时间差为 0 都返回有限值
- 不变量：任何输入下输出都是有限数（NaN/Infinity 不得漏出去）

**手测**（真实客户端）

1. 按住宠物拖动 → 松手 → 它沿抛物线飞出、落地停住
2. 慢拖后松手 → 几乎原地落下（速度低于阈值不抛）
3. 快速甩出 → 飞得远；撞到左右边缘会反弹
4. 模型声明了 `Picked` / `Land` 时，抓起与落地各有对应动作；没声明时静默跳过
