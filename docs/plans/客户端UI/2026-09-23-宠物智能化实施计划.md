## 一、总览

| 期 | 目标 | 工作量 | 用户能看到的 |
|---|---|---|---|
| 一 | 宠物有自己的性格 | 2.5 天 | 每只宠物的脾气不一样，且不会因为训它而影响助手 |
| 二 | 性格看得出来 | 3 天 | 静止时的呼吸/眨眼/活动频率就有区别；控制坞显示气质标签；能长按摸头 |
| 三 | 宠物自己的目标管道 | 2.5 天 | （基础设施，无用户可见） |
| 四 | 宠物开始感知你 | 3.5 天 | 你卡壳时它靠近；工作久了它提醒；它知道你在做什么 |
| 五 | 宠物替你去看一眼 | 4 天 | 派它去看测试，它跑完回来报具体结果 |

**总计约 15.5 天。**

**排序逻辑见设计 §六**：闭环优先，不按层优先。**第三期是基础设施且无用户可见验收，但必须排在第四期之前**——感知有了却不能行动，只能憋出一句空话。

## 二、环境与前置

### 2.1 必须知道的坑（否则会白跑）

| 坑 | 说明 |
|---|---|
| **改主进程必须重启** | 改 `apps/windows/src/main/**` 或 migration 后要 `pnpm dev:restart`，运行中实例用的是旧代码旧 schema |
| **单实例锁** | 重启时若被拦，先 `stop-dev.ps1 -KillAllElectron` 清干净 |
| **renderer 测试用 npx** | `rtk vitest` 会丢 jsdom，renderer 测试必须 `npx vitest` |
| **别用 `git add -A`** | 并行会话常见；先看 diff → 按名 add → 不带 pathspec 提交 |
| **测试前清库** | 置 `rejected` 清掉残留 pending/executing 目标，否则同描述目标被去重拦截 |

### 2.2 本次新增的常量与键位

```ts
// 新增（放各自模块，不集中建配置文件）
```

## 五、第三期：宠物自己的目标管道（约 2.5 天）

**目标**：让宠物能**发起并执行**目标，且与任务 Agent 完全隔离。
**本期无用户可见验收**——但它是第四、五期的地基。

- [ ] **T3.1 宠物目标存储**
  - 首选：复用 `autonomous_goals` + `planned_by='pet'`
  - **先做判断**：读 `autonomous-repo.ts` 的配额统计与派发查询，确认能否按 `agent_id` 干净过滤
  - **若改动面过大 → 降级为单独轻量表**（结构同 `autonomous_goals` 的三个关键列），走一次 migration
  - 产出：写死这个选择，不留两套

- [ ] **T3.2 配额与预算按 agent_id 拆开**
  - `MAX_GOALS_PER_DAY` 统计加 agent_id 过滤
  - 新增 `MAX_PET_GOALS_PER_DAY` + 宠物 token 日上限（**硬闸门，不是软提示**）

- [ ] **T3.3 宠物侧派发循环**
  - **不复用任务 Agent 的 tick 语义**（设计 §4.1.2 末段：复用只在"读库判断"层，行动必须走自己的 pipeline）
  - 参照：`bridge.ts` 的 `executeGoal` 路径（`createRestrictedInstanceById` + `getGoalToolAllowlist`）
  - **⚠️ 陷阱**：任务侧 `hasActiveUserTurn` 会误判后台会话（历史坑：`cron:%` 与 `evolution:main`），宠物侧的实现**不要照抄这个函数的实现，只照抄思路**

- [ ] **T3.4 单飞锁**
  - 判断"宠物会话有没有活跃实例"，有则排队或拒绝
  - **不加调度器，就一个判断**

- [ ] **T3.5 结果落库 + 气泡播报**
  - 落宠物自己的会话（**不进 `evolution:main`**）
  - 播报走 `pet-notice-adapter`
  - **★ 断言：播报不经过 `dispatchNotifications`**
  - 自测：单测/集成断言通知路径

**第三期出口验收**
- ✅ 手动派一个目标给宠物 → 它跑完并在气泡报出结果
- ✅ 执行受工具白名单约束（跑不了 `bash` / `spawn`）
- ✅ 宠物目标不占任务 Agent 的每日配额
- ✅ 用户只收到宠物气泡，**没有重复的系统通知**
- ✅ 结果未出现在 `evolution:main`

## 六、第四期：宠物开始感知你（约 3.5 天）

**目标**：让"你"成为宠物的输入（原设计的输入全是"宠物自己怎么了"）。

- [ ] **T4.1 `petSensing`：只读判断**
  - 复用 `collectTickSignals`（`tick-signals.ts`），**同一份信号两个出口**
  - 只读，零网络零 token
  - **⚠️ 只复用读库判断，不复用它的派发语义**

- [ ] **T4.2 预判规则 ①：打断 ≥3 次 → 靠近陪着**
  - 信号：abort / resend / edit 计数（反馈信号，注意其**瞬态**性质——回合结束会清零，见记忆中的坑）

- [ ] **T4.3 预判规则 ②：连续工作 2h → 提醒休息**
  - **★ 空闲 > 5 分钟即断开计数**（否则中午吃饭一小时会误报）
  - 话里要带得出你在做什么（接 T4.5）

- [ ] **T4.4 预判规则 ③：会话评分低 → 写宠物自己的 mood**
  - 信号：`autonomous_satisfaction_scores.overall_score < 0.6`
  - **真实共情**：写的是宠物自己的 mood，不是"表现难过"
  - 产出：一句"我难过"都不说，但举止变缓、说话概率降低

- [ ] **T4.5 读沉淀让预判带具体内容**
  - 源：Wiki / 工作记忆（**只读**）
  - 例："前端又写了两小时了" 而不是 "该休息了"

- [ ] **T4.6 克制四纪律**
  - 错了收回 / 同类每日 1 次 / 只走气泡 / 感知与行动分离
  - 去重：记录最近说过的文案（24h Set）

- [ ] **T4.7 冷启动空状态**
  - 无历史数据 → **退回性格驱动的自发行为，不硬说**
  - 数据稀疏 → 阈值放宽（2h → 3h）

**第四期出口验收**
- ✅ 打断 3 次以上 → 靠近陪着，不追问
- ✅ 连续工作 2 小时 → 提醒，且带得出你在做什么
- ✅ **中途吃饭一小时回来接着干 → 不误报**
- ✅ 会话评分低 → 宠物真的蔫，但一句"我难过"都没说
- ✅ 猜错不追问；同类当天不重复
- ✅ **全新用户不硬说**
- ✅ 读沉淀是只读的

## 七、第五期：宠物替你去看一眼（约 4 天）

**目标**：从"被看着"到"会做事"。

- [ ] **T5.1 意图来源（只做两种）**
  - ① 用户明确要求（「让它去做」按钮）
  - ② 感知触发提议（"要不要我去看看？"）
  - **★ 不做宠物自主排期**（设计 §4.2.1，要新写 LLM 规划器，收益不到 10%）

- [ ] **T5.2 工作目录继承**
  - 派活时继承当前主会话 `projectPath`（`runtime-config.ts:22` 的 `workingDirectory`）
  - **不继承会静默读错项目或读到空**

- [ ] **T5.3 能力边界诚实化**
  - 读 `capability_dimensions` 的 Elo 边界；超出就直说"这个我不太拿手"
  - **能力边界本身就是萌点**，不要硬做

- [ ] **T5.4 真实失败与重试**
  - **★ 禁止用随机报错营造笨拙感**
  - 失败来自真实的边界/工具错误；重试是真的重试一次工具调用

- [ ] **T5.5 成功/失败的举止反馈**
  - 走 `applyMoodImpact`（注意 `task_failed` 是 valence ↓ **arousal ↑**）
  - **⚠️ 语义冲突**：分键后宠物与任务共用 `MOOD_IMPACT` 表，`task_failed` / `goal_completed` 会被两条线共用，**需确认语义是否要区分**（可能需要宠物专用事件名）

- [ ] **T5.6 控制坞双流分区**
  - 文件：`apps/windows/src/renderer/pet/components/PetControlDock.tsx`
  - 宠物流（气泡式，蓝色调）/ 对话流（现有）
  - **不做成两个 Tab**——宠物的话在另一个 Tab 里悄悄产生就失去意义

- [ ] **T5.7 「让它去做」按钮 + 进行态**
  - 输入框旁按钮；点后 < 200ms 有响应（头顶符号切"工作中" + 短气泡"我去看看"）

- [ ] **T5.8 结果条目 + 未读标记**
  - **★ 气泡是瞬时的**：用户去倒水就错过回执
  - 结果同时进气泡 + 控制坞持久条目，**带未读高亮直到用户看过**
  - 可展开完整结果 + 一键「转给主助手」（**用户主动触发**，是宠物与任务 Agent 的唯一通道）
  - 感知类的话（"该歇会儿了"）**不进**这个流

- [ ] **T5.9 设置项：是否允许宠物主动做事**

**第五期出口验收**
- ✅ 派它去看测试 → 跑受限实例 → 报回具体结果
- ✅ **回执一定能收到**（报结果时人不在 → 回来有未读条目）
- ✅ 超出能力就直说，不硬做
- ✅ 失败是真失败，能观察到真的重试一次
- ✅ **不会跑飞**：连点三次有单飞锁；超每日上限被拒
- ✅ **目录正确**：读的是当前项目的文件
- ✅ **U4/U5/U6** 同屏分区 / 即时反馈 / 不进用户会话历史

**两处实现口径（与计划的差异，都是刻意选的）**

1. **mood 迁移做在读路径上，不是独立迁移脚本**。`readMood(db, 'assistant')` 发现新键缺失、老键存在时，**先写新键再删旧键**——中途失败下次读会重试，不会丢老用户的当前情绪。代价是 `readMood` 从纯读变成「可能写一次」，且只发生一次。
2. **`migrated` 的判据是「`messages` 表有没有历史消息」**。设计只说"存量用户要标记"，没给判据。选 `messages` 是因为它最老最全：有历史消息说明宠物人格上线前用户就在用它了。探不到按新装算——"把升级日说成出生日"比"把出生日说成记录开始日"伤害小。

**验收证据（2026-09-23 真机实测，非单元测试）**

**踩到的坑**

| 坑 | 说明 |
|---|---|
| **`messages.conversation_id` 有外键** | 测试里造"存量装"必须先插一行 `conversations`，否则 `FOREIGN KEY constraint failed` |
| **既有 E2E 断言写死了 0.5** | `autonomous-e2e.test.ts` 场景 5 断言 `openness === 0.5` 与 `> 0.5`；抽签后必挂。改成**相对断言**（`> initialState.openness`），不再依赖绝对值 |
| **`toAsyncClient` 原本是模块私有** | `autonomous-wiring.ts` 里那个 sync→async 适配器要复用，改成 `export`（宠物人格读库走同一条路，别抄一份） |
