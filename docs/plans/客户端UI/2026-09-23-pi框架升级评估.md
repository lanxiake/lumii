## 一、为什么升级

`@mariozechner/pi-agent-core` **最后发布 0.73.1（2026-05-07，已停更）**；主线迁到 `@earendil-works/*`（0.87.1，2026-09-22 仍在更新）。新版提供旧线拿不到的能力：`finishTurn`（循环结束条件钩子）、`peekQueuedMessages()`、`prepareRequest`，以及 `harness`/`durable` 持久化架构（工具结果按 source order 持久化、崩溃后不重跑已完成工具）。

## 二、改动面

| 项 | 内容 |
| --- | --- |
| 依赖声明 | `packages/agent-runtime/package.json` 两处（pi-agent-core / pi-ai） |
| 锁定配置 | `pnpm-workspace.yaml` 的 `overrides`（原精确锁 `0.50.7`） |

## 三、类型检查结果（35 个错误）

`apps/windows` 的 typecheck 覆盖 packages 源码，**总计 35 个**：

| 文件 | 数量 | 性质 |
| --- | --- | --- |
| `packages/agent-runtime/src/compact/strategies/micro-compact.ts` | 16 | `AgentMessage.content` 不存在 |
| `packages/agent-runtime/src/agent/agent-instance.ts` | 8 | 同上 + 隐式 any |
| `src/main/agent-runtime/bridge-agent-instance-events.ts` | 3 | 消息类型收窄 |
| `src/main/agent-runtime/bridge-context-compactor.ts` | 2 | 同上 |
| `packages/agent-runtime/src/llm/direct-stream.ts` | 2 | `streamSimple` 不再从主入口导出 |
| `src/main/selection/selection-llm.ts` / `router/llm-caller.ts` / `compact-persist.test.ts` | 各 1 | 同上 |

**根因两条**：

1. **`AgentMessage` 变成联合类型**：`export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages]`（`dist/types.d.ts:318`）。旧版可直接 `.content`，新版需先收窄——**26 个错误里的绝大多数**。另有新类型 `BashExecutionMessage` 需要处理。
2. **通用 `streamSimple` 移到 compat 入口**：主入口不再导出，官方迁移路径见下。

## 四、官方留的迁移通道（重要）

**`@earendil-works/pi-ai/compat`** 是官方兼容入口，原文：

> Temporary compatibility entrypoint preserving the old global pi-ai API surface: api-dispatch `stream()`/`complete()` with env API key injection, the api-registry, generated catalog reads (`getModel`/`getModels`/`getProviders`), per-API lazy stream wrappers, and image generation.
> **Existing apps switch imports from `"@earendil-works/pi-ai"` to `"@earendil-works/pi-ai/compat"` unchanged**

即：**把 import 换成 `/compat` 即可零改动恢复旧 API 面**。⚠️ 但它是**临时**的（注释写明随 coding-agent 的 ModelManager 迁移删除），所以只适合作为过渡，长期应收敛到 `createModels()` + provider 工厂。

## 五、三处本地补丁：新版全部原生解决

原补丁 `@mariozechner__pi-ai@0.50.7.patch` 修了三处，逐条核对新版（`dist/api/openai-completions.js`）：

| 补丁 | 新版状态 |
| --- | --- |
| ① 未识别 `finish_reason` 只报 "unknown error" | **已原生支持**且更完善：`output.rawStopReason = choice.finish_reason` + `finishReasonResult.errorMessage`（:373-378） |
| ② 抛错时吞掉真实原因 | **已原生支持**：`throw new Error(output.errorMessage \|\| "Provider returned an error stop reason")`（:482） |
| ③ SSE 大帧被 TCP 分片截断（自建 fetch 重缓冲） | **问题从根上消失**：新版 `import OpenAI from "openai"`（:1）——**改用官方 SDK**，SSE 解析与分片由 SDK 负责，自建重缓冲不再需要 |

**结论：补丁可以退役**——不是被别处掩盖，是上游把问题解决了。这是升级最大的收益之一。

## 六、结论与建议（一轮结论，已被 §七 修订）

| 维度 | 评估 |

| 补丁 | 全部可退役 |

**建议**：先按 **compat 入口**完成升级（改 import + 修 35 个错误 + 全量测试），跑通后再单独排期把 `compat` 依赖收敛到新 API——**过渡与长期收益分开做**，避免一次性吃掉过大的改动。

**剩余待验证**（本次未做，需在真正迁移时补）：

## 七、二轮反思：架构变更与官方替代

> 用户指出："尽量使用框架本身的功能和组件去实现，避免带来意外和潜在的问题"。
> 这一节是响应该反馈的深入调研，**推翻了一轮评估中"改动量小"的结论**。

### 7.1 一轮方案的三个问题

| 我的改法 | 问题 | 官方机制 |
|---|---|---|
| 手写 `readMessageContent()` 用 `as` 断言绕联合类型 | 绕过新版**有意**的类型安全；不处理 `thinking` / `toolCall` 等块型 | **`contentText(content, separator?)`**（`pi-ai/utils/text`），过滤 `type: "text"` 块并 join |
| `agent.state.messages = [...]` 直接赋值 | 可能破坏框架不变量（虽然文档说 accessor 会拷贝数组） | 待定（见 §7.3） |
| 四处调用点各包 `normalizeContext` | 一轮认为是"症状治疗"，应收到 streamFn 边界一处 | **实为正确做法**（见 §7.2） |

**最重要的推翻**：`setSystemPrompt` 消失不是遗漏，是**架构改了**。

### 7.2 提示词架构变更：从可变字段到 transcript 派生

**旧版（0.50.x）**：
```ts
agent.setSystemPrompt(prompt)  // 直接覆盖一个可变字段
```

**新版（0.87.1）**：
```ts
get systemPrompt() {
  return getCurrentSystemPrompt(messages)  // 从 messages 派生的 readonly getter
}
```

文档原文（`agent.d.ts:327-331`）：

> Current system prompt, replayed from the transcript's system messages.
> 
> **Read-only: to change the prompt, append a system message with `content` or `sections`.**
> In `initialState`, this seeds the leading system message.

即：提示词不再是独立字段，而是从 `SystemMessage[]` 重放出来的**计算属性**。变更提示词的唯一路径是 **push 一条 SystemMessage 进 `state.messages`**。

#### 7.2.1 sections：官方的可变提示词机制

`SystemMessage.sections?: Record<string, string | null>` 是新版提供的**按名替换机制**（文档 `types.d.ts:336-341`）：

> Named, ordered prompt sections rendered verbatim after `content`. The leading message
> declares them; **later messages replace sections by name**, and `null` removes one.

配套三个官方函数：

1. **`getCurrentSystemMessage(messages)`** — "Replay every system message into one... **sections are patched by name**"
2. **`getCurrentSystemPrompt(messages)`** — 读当前生效的提示词
3. **`collapseSystemMessages(context)`** / **`resolveTranscript(context, supportsMidConvoSystemMessages)`** — 按模型是否支持会话中 system 消息，自动收敛或保留

这正是 `memory-integration.ts` 每轮动态注入工作记忆所需的机制——**用同名 section 覆盖，不累积**。

我一轮里说"append system message 会无限累积、所以要自建 `convertToLlm`"是**错的**。`sections` 就是官方按名替换，不会累积。

### 7.3 `normalizeContext` 不是症状治疗

一轮批评"四处分散调用"是误判。查签名：

- **`StreamFn`**（agent-core 契约）：`(model, context: TranscriptContext, options) => ...`
- **`streamSimple`**（compat 入口）：`(model, context: Context, options) => ...`

`normalizeContext` 的职责是把宽松 `Context`（含 `systemPrompt?` / `tools?` 顶层字段）转为严格 `TranscriptContext`（只有 `messages`，提示词与工具在 system message 里）。

我们四处调用点的身份：

| 文件 | 身份 | 是否需要转 |
|---|---|---|
| `selection-llm.ts` / `llm-caller.ts` | 手搓 `Context` 直接调 `streamFn` | **必须转**（契约要求 `TranscriptContext`） |
| `bridge-context-compactor.ts` | 同上 | **必须转** |
| `bridge-image-services.ts` | 同上 | **必须转** |
| `direct-stream.ts` | `StreamFn` 的**实现方**，收到的已是 `TranscriptContext` | **不需转**（透传给 compat `streamSimple` 超集兼容） |

所以四处分散是**对的**——调用者有义务遵守契约。收敛到 streamFn 边界反而破坏类型安全。

### 7.4 `AgentMessage` 联合类型与 `convertToLlm`

新版 `AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages]`。

`harness/messages.ts` 从**主入口无条件 re-export**（`index.d.ts:10`），其 module augmentation 对所有 import 者生效：

```ts
declare module "../types.ts" {
  interface CustomAgentMessages {
    bashExecution: BashExecutionMessage;   // 没有 content 字段
    custom: CustomMessage;
    branchSummary: BranchSummaryMessage;
    compactionSummary: CompactionSummaryMessage;
  }
}
```

这导致 26 个 `.content` 报错。**而同一个文件就导出了官方转换器**：

```ts
export declare function convertToLlm(messages: AgentMessage[]): Message[];
```

这正是我该用的——收窄联合类型 + 过滤非 LLM 消息。我手写 `readMessageContent()` 用 `as` 断言，等于在官方转换器旁边重造了不安全版本。

### 7.5 修正后的改动清单

| 项 | 一轮方案（已推翻） | 修正后的正确做法 |
|---|---|---|
| 消息文本提取 | 手写 `readMessageContent()`，用 `as` 绕类型 | **用官方 `contentText(content)`**（`pi-ai/utils/text`） |
| 记忆注入 | 自建 `convertToLlm`，担心累积 | **用 `SystemMessage.sections`**（按名替换，官方机制） |
| 提示词变更 | `setSystemPrompt` 消失待查 | **push SystemMessage 进 `state.messages`**（架构变更，唯一正确路径） |
| `normalizeContext` 位置 | "症状治疗"应收敛 | **分散四处是对的**（契约义务） |
| `AgentMessage` 收窄 | 手写读取 + 断言 | **用 `convertToLlm(messages)`**（官方转换器，harness 导出） |

### 7.6 修订后的风险与工作量

| 维度 | 一轮评估 | 二轮修订 |
|---|---|---|
| API 破坏性 | 中等 | **高** —— 提示词从可变字段改成 transcript 派生，是架构变更 |
| 改动量 | 小（35 个类型错误 + 机械替换） | **中等** —— 需重写 `memory-integration.ts` 的注入路径；`api-invariants.ts` / 压缩策略里 26 处消息读取改用官方转换器 |
| 补丁 | 全部可退役 | 不变 |
| 收益 | `finishTurn` / `peekQueuedMessages` / durable | 不变 |

**必须实测的风险**（新增）：

1. **steering 语义退化**：新版从「每个工具后」改为「整批工具后」（`agent-loop.js:186`），**会削弱刚交付的即插话体验**（用户今天验证的"第二个 sleep 被跳过"可能不再成立）。但新版提供 `beforeToolCall` 钩子，可在其中调 `agent.peekQueuedMessages()` 判断有无插话，返回 `{ block: true, terminate: true }` 提前终止批次——**可能需要自己实现这一层**。

2. **`agent.state.messages = [...]` 是否安全**：文档说 accessor 会拷贝数组（`agent.d.ts:78-79`），但直接赋值可能破坏框架其他不变量（事件、顺序校验）。需实测或查源码确认。

3. **记忆注入从 `setSystemPrompt` 改成 push SystemMessage**：现有路径是 `bridge-prompt-dispatcher.ts:369` 每轮调 `instance.setSystemPrompt(freshPrompt)`（全量重建），新版须改成替换 `messages[0]` 或 push 增量 section。两种语义不同（全量 vs 增量），需确认 `bridge-prompt-composer.ts` 产出的 `freshPrompt` 是否适合拆成 base + sections。

### 7.7 修订后的建议

**不再建议"先 compat 快速过渡"**——架构变更无法靠 compat 入口掩盖，必须正面处理。

**分两步走**：

1. **P0：类型与 API 适配**（约 3-5 天）
   - 用 `contentText` 替代 `readMessageContent`
   - 用 `convertToLlm` 处理 `AgentMessage` 联合类型
   - 重写 `memory-integration.ts` 注入路径（从 `setSystemPrompt` 改成 push SystemMessage + sections）
   - 确认 `agent.state.messages = [...]` 是否安全（或改用增量 push）
   - 跑 typecheck 到 0 + `apps/windows test:all` 全量

2. **P1：运行时行为验证**（约 2-3 天）
   - 实测 steering 语义（是否需要 `beforeToolCall` 补救）
   - 验证记忆注入在新架构下的实际效果（提示词是否正确重放）
   - 验证 `harness` / `durable` 的实际可用性

**总工作量预估**：5-8 天（vs 一轮的"1-2 天"）。
