## 二、诉求 2：HTML 划词不可用的四个真因

**全部由探针实测得出**，探针留在 [`verify/selection/probe-webview-preload.cjs`](../../../verify/selection/probe-webview-preload.cjs)
（`cd apps/windows && npx electron ../../verify/selection/probe-webview-preload.cjs`）。

修复前的链路**四处**都断，任何一处单独存在都足以让划词完全没反应：

### 2.1 preload 的 URL 必须是 `file:` —— dev 下拼出来的是 `http:`

`FilePreviewModal` 原先用 `new URL('../preload/webview-selection.js', location.href)` 拼路径。
dev 下渲染层在 `http://127.0.0.1:5174`，`..` **越不过站点根**，拼出来是
`http://127.0.0.1:5174/preload/webview-selection.js` ——

- vite 对该路径返回 **`200 text/html`**（SPA 兜底，实测），拿到的"脚本"是一份 HTML；
- 更重要的是 Electron 的硬约束：`<webview preload>` 的**协议必须是 `file:`**
  （webview-tag 文档原文：它由 Node 的 `require` 加载）。
- 探针 B 用例：http preload **完全不加载**，且**不发 `preload-error`** —— 静默失败，
  所以这条错从来没在日志里露过面。

**修法**：路径改由**宿主 preload** 算好暴露（`electronAPI.webviewSelectionPreload`）。
preload 自己就在 `out/preload/` 里，`pathToFileURL(join(__dirname, 'webview-selection.js'))`
在 dev 与打包（asar 内同样成立）下都是正确且绝对的形式。

### 2.2 `ipc-message` **不冒泡**，挂在 document 冒泡阶段一条都收不到

Electron 派发 webview 事件用的是 `new Event(eventName)`（`web-view-impl.ts::dispatchEvent`），
`bubbles` 默认为 **false**。

探针 A 用例（file preload + file src），三种监听的结果：

| 监听位置 | 收到 |
| --- | --- |
| webview 元素自身 | ✅ |
| document（冒泡） | ❌ |
| document（**捕获**） | ✅ |

**修法**：`document.addEventListener('ipc-message', handler, true)` —— 加捕获。
**这条与 dev/prod 无关，打包版同样坏**，是四因里最隐蔽的一条。

### 2.3 归属判定拿 `frameId` 比 `getWebContentsId()`，**恒不相等**

原实现用 `el.getWebContentsId() === event.frameId[1]` 找发信的 webview。
Electron 源码（`lib/browser/guest-view-manager.ts`）里这个字段是：

```js
guest.on('-ipc-message-host', (event, channel, args) => {
  sendToEmbedder(..., 'ipc-message', { frameId: [event.processId, event.frameId], channel, args })
})
```

即 **`[进程 id, 进程内帧 id]`**，与 webContents id **不是同一套编号**。
探针实测：`getWebContentsId()=2` 而 `frameId=[6,4]` —— 比下来恒为假，
**消息被静默丢光**。

**修法**：认 **`e.target`**。事件就派发在 `<webview>` 元素上，target 即发信的那个
（探针 D 用例实测 `target.tagName === 'WEBVIEW'`、`target === 该 webview`）。
比原方案更准，也不需要再遍历页面上的 webview 元素。

### 2.4 iframe 那条路：`sandbox=""` 会**禁用一切脚本**，注入的取词脚本根本不执行

静态预览（CSS / SVG）走 `<iframe srcDoc sandbox="">`。HTML 规范里 `sandbox` 不带
`allow-scripts` 时**页面不能运行脚本** —— 所以注入的 `IFRAME_SELECTION_SCRIPT` 形同废纸。
（原注释写的"内联脚本仍可执行"是错的：注入 `<style>` 能生效不代表脚本能跑。）

探针实测：

| sandbox | 脚本执行 / postMessage 到宿主 |
| --- | --- |
| `""` | ❌ 收不到 |
| `allow-scripts` | ✅ 收到，且 `event.origin === "null"`（不透明源） |

**修法**：`sandbox="allow-scripts"`，**仍不给 `allow-same-origin`**（文档留在不透明源里，
碰不到宿主 DOM / IPC）；同时补一条 `script-src 'nonce-…'` 的 CSP，
把脚本授权收到**只认我们自己注入的那段** —— 预览内容自带的 `<script>`（SVG 可以有）
照旧被挡。这比改之前"完全不跑脚本"也只松了"我们那一段"。

## 三、诉求 1：Composer 富文本化

### 3.1 落点

| 文件 | 性质 | 说明 |
| --- | --- | --- |
| `ChatInput/composer-content.ts` | 新增 | **纯逻辑**：文本 ↔ 片段 ↔ DOM 的翻译，chip 的建法 |
| `ChatInput/RichComposer.tsx` | 新增 | contenteditable 组件 + 命令式 handle |
| `ChatInput/RichComposer.module.css` | 新增 | chip 样式（盒模型仍用 `.chat-textarea`，见下） |
| `ChatInput/index.tsx` | 改 | textarea → RichComposer；插入/粘贴/IME/斜杠补全接过去 |
| `ChatInput/ChatInput.module.css` | 改 | `.chat-textarea` 保留为「盒模型度量」，占位符改自绘 |

### 3.2 三条不可动摇的约束

1. **文本仍是唯一的对外契约。** 组件只吐 `onChange(text)`，与 textarea 时代一字不差 ——
   草稿持久化、发送、渠道出站、Agent 认路径全都不需要知道实现换了。
2. **不受控。** React 只在「外部值与当前 DOM 的序列化结果不等」时才重写 DOM。
   每次渲染都重写的话光标会当场跳回开头 —— 这是 contenteditable + React 最经典的坑。
   IME 组合期间一律不写（会把正在组合的串抹掉）。
3. **chip 是命令式建的**（React 不接管这棵子树），所以删除走**事件委托**
   （根节点上听 `data-chip-remove`），重建 DOM 不会漏挂监听。

### 3.3 chip 的文本形态（不可改）

| chip | 文本 |
| --- | --- |
| 引用 | markdown 引用块 `> …` + `> —— 来自《标题》/助手回复/我的提问`（沿用 `buildQuoteMarkdown`） |
| 文件/目录 | `@相对路径` + 尾随空格 |

前者是消息列表渲染与渠道出站的既有口径，后者是 Agent 侧认路径的依据。
chip 上只放**摘要**（截断 + 出处），全文进 `title` 悬停看 —— 被引的正文不该在输入框里铺开。

### 3.4 文本 → chip 是**保守**的

挂载/切会话时要从文本把 chip 还原回来，规则卡得很死，宁可认不出也不误认：

- 引用块：只在**行首**且连续 `>` 行**能被 `buildQuoteMarkdown` 精确反解**时才认；
  正文中间的 `>` 是普通字符。
- 文件引用：`@` 后面的整段相对路径必须**在册**（在 `fileReferences` 里），
  且取**最长匹配**（`workspace/src` 与 `workspace/src/a.ts` 同时在册时不互相抢），
  路径后必须是空白或结束。

### 3.5 替换 textarea 后要自己管的事

| 事 | 做法 |
| --- | --- |
| 高度自适应 | div 本来就随内容长，`field-sizing: content` 不再需要 |
| 占位符 | `[data-empty='true']::before { content: attr(data-placeholder) }`，**绝对定位**（留在行内的话光标会落到占位文本末尾） |
| 换行 | 只留一种表示：自己插 `<br>`。交给浏览器的话 Shift+Enter 会产出 `<div>` / `<br>` 两种结构 |
| 粘贴 | 一律只取 `text/plain`（带格式的 HTML 会引入序列化不认识的结构）；有文件时让位给上传 |
| 禁用 | contenteditable 没有 `disabled`，用 `contentEditable={false}` 表达 |
| 末尾的 `<br>` | 序列化时忽略 —— 那是浏览器给光标落脚的，不是内容（发送前本来就会 `trim`） |

### 3.6 与上方 chip 行的双向同步

- 点**内联** chip 的 × ：先摘 DOM、再通知外部把引用从会话状态里摘掉。
- 点**上方** chip 的 × ：外部清单变了 → 收敛 effect 把内联 chip 一并摘掉（
  chip 就是那段 `@路径`，摘掉即等于从正文里去掉路径）。

两者不成回环：内联删除是"先摘 DOM 再通知"，外部更新回来时 chip 早已不在 DOM 里。

## 七、第二轮反馈（同日，用户实测后）

用户实测确认「HTML 能正常弹气泡与划词了」，随后提了三件事。

### 7.1 气泡的关闭按钮点不动（真 bug）

**真因是指针捕获**：气泡头部为了拖动调了 `setPointerCapture`，而**指针捕获会把后续的 `click`
派发到捕获元素（头部）而不是按钮本身**，于是按钮的 `onClick` 永远不触发。

- 修法：`handleDragStart` 里按到 `button` 上就整个让开（不捕获）。
- **为什么单测没兜住**：jsdom 不实现指针捕获的重定向，既有的「点关闭调 closeBubble」用例
  在真机坏掉时照样绿。所以补的用例直接**钉住机制本身**（按在按钮上不许捕获），
  并验证过它在去掉守卫后会红。
- 真机判据：用**真实鼠标事件**点关闭（`element.click()` 复现不出来），见 `verify-bubble-controls.cjs`。

### 7.2 复制要有「已复制」标记

气泡底栏的复制按钮点完只写剪贴板，界面上毫无反应。现在按钮切到成功态
（图标换对勾、文案换「已复制」、底色转 `--color-success-10`）并在 1.6s 后自己收掉。
「已复制」是**组件内瞬时态**，不进 store；换气泡（新 `requestId`）时清掉，免得串台。

### 7.3 L2 输出重新排版（手绘笔记）

原来气泡里是 `<p white-space: pre-wrap>` 的纯文本，模型一返回 Markdown 就是一屏 `**` 与 `##`；
长结果更是一堵字墙。两头都改了：

**提示词侧**（`main/selection/selection-prompts.ts`）——能长的两挡明确要结构，并且**都留退路**
（短文本别硬套标题，免得一个词的译文长出小标题）：

| 动作 | 要求 |
| --- | --- |
| 解释 | 开头一句结论 → 分点展开（**关键术语加粗**）→ 内容多时小标题分组；短文本不加标题 |
| 总结 | Markdown 无序列表，每条一行一个要点，关键信息加粗 |
| 翻译 | 保持原文的分段/分点结构，不自己加排版 |
| 润色 | 保留原文段落结构，解释性内容一律不要 |

**渲染侧**（新增 `selection/SelectionResultMarkdown.tsx` + `.module.css`）——**手绘笔记**语汇：

- `**重点**` → **荧光笔**：暖色半透明底 + **不规则圆角**，`box-decoration-break: clone` 让跨行时
  每行各自一道笔痕，而不是整段一个色块；
- `*补充*` → 波浪线（与荧光笔分工：一个是"这是重点"，一个是"这是补充"）；
- 标题 → 一道两头不匀、略微倾斜的手画下划笔痕；
- 引用块 → 手画方框的便签；分隔线 → 断续笔痕；列表圆点 → 手画小方块；
- **手绘感靠形状不靠字体**：中文字体动辄几 MB，为一个气泡换手写体不划算，所以手绘感来自
  不规则圆角 + 极小倾斜（0.25–0.6deg，再多就像没对齐了）。
- **颜色一律跟着主题色走**（2026-09-23 第二轮反馈后改）：全部由 `rgba(var(--mt-accent-rgb), α)`
  调出，不写死色相。三主题实测：dark `rgba(59,130,246,.3)` · light `rgba(42,118,246,.3)` ·
  eye-care `rgba(184,134,59,.3)` —— 即各主题的品牌色。
  第一版用的是 `--mt-warning`（固定琥珀），在蓝色主题下像"警告"而不是笔记，只有暖色的
  护眼主题碰巧好看。
  层次不靠换色相，靠**同一色相的浓淡 + 形状**：荧光笔最实（.30），笔痕类（下划线/波浪/
  分隔线）中等（.32–.62），便签底最淡（.09）。代码块与表格的分隔线保留中性的 `--mt-fg-*`
  —— 它们是"结构"不是"笔记"，上主题色会跟荧光笔抢视线。
- 与 `ChatMessage` 那套 Markdown 管线**故意分开**：那边挂了 KaTeX/代码高亮/图片灯箱，
  为一个 480px 的气泡全量加载不划算，且那套的标题尺度（20px+）在这里太大。
