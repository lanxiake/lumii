# 划词与引用 P1 实施计划（single 通道 + 就地气泡）

设计见 [`../../design/客户端UI/2026-09-22-划词与引用设计.md`](../../design/客户端UI/2026-09-22-划词与引用设计.md) §5.4 / §5.6 / §八.1。

P0 已交付（见 [`2026-09-22-划词与引用P0实施计划.md`](2026-09-22-划词与引用P0实施计划.md) §九）。P1 是「价值最大的一期」。

## 一、目标与边界

**目标**：划词后不止能「复制/引用」，还能就地拿到 LLM 结果——**翻译 / 解释 / 总结 / 润色**四挡，结果进**就地气泡**。

| # | 内容 |
| --- | --- |
| T1 | `single` 通道：main 侧薄调用器 + `selection:run` / `selection:abort` 两条 IPC |
| T2 | 气泡状态（独立于浮条生命周期）+ `SelectionBubble` 组件 |
| T3 | L2 动作进注册表（翻译/解释上浮条，总结/润色进菜单） |

**不做什么**

- ✗ 流式 —— §八.1 已实测收口：卡的是**端点排队**不是生成（同一短 prompt 首字 615ms↔5739ms），首字节之前无字可显示，**流式治不了排队**
- ✗ 提示词可编辑（设计 §十一 开放问题 2）
- ✗ 引用结构化 / chip / metadata 双写 → P2
- ✗ Agent 动作（追问 / 用技能）→ P3
- ✗ `<webview>` / `<iframe>` 预览里的划词（guest 注入，属独立议题）

## 二、关键决策

### 2.1 通道形态：一次 invoke 拿结果 + 一个 abort

不做流式的直接后果（见上）。请求形状：

```
selection:run    (renderer → main)  { requestId, action, text } → { ok, text?, error? }
selection:abort  (renderer → main)  requestId → boolean
```

失败**不 reject 而是走 `{ ok: false, error }`**：错误信息要原样给用户看，包一层 IPC 异常只会得到 `Error invoking remote method ...`。

### 2.2 提示词放主进程

契约只传 `action`，渲染层不持有提示词。理由：改提示词、按模型调提示词，都不该要求渲染层跟着改。代价是提示词硬编码不可编辑——与「提示词风格」实验功能的关系是设计 §十一 的开放问题，P1 明确不做。

翻译要**先判方向再输出**：目标语言跟着源文本走（中文为主译英，否则译中）。写死任一侧都会在另一侧翻车。

### 2.3 复用底层设施，不复用 `callLLM`

`compactor.callLLM` 是活的单轮累加通道，但**它会把完整 prompt 与输出写进日志文件**（`bridge-context-compactor.ts` 的 `[callLLM] ... prompt=${JSON.stringify(prompt)}`）。划词走它等于把用户选中的正文落盘。

于是：

- 新增 `compactor.resolveCallStream()` —— 与 `callLLM` **共用同一套四级降级**，但只解析不调用；
- 新增 `bridge.resolveSelectionChatStream()` —— 对上暴露 `{ streamFn, model }`；
- `SelectionLlmService` 自己发起调用，日志只记 `action / textLen / 耗时 / outputLen`，**正文与结果一概不落盘**。

这与设计 §八.1 的倾向一致：复用底层设施（凭据解析、direct stream）**有数据支持**；复用 `RouterLlmCallerImpl` 这个业务类不支持（语义绑在 skill 路由上，且在本构建里是死代码）。

### 2.4 气泡生命周期与浮条解耦 —— 这一期最容易写错的地方

**`api.close()` 会卸载整个 surface，而 `view` 里的东西跟着一起没。** 任何一次 mousedown 都会关浮条（`useSelectionWatcher` 的既定行为），所以「点别处 → 结果消失」——而用户此时正是要看结果。

因此气泡有自己的模块级 store（`bubble-store.ts`）与自己的根节点（`bubbleRef`）。浮条该关就关，气泡自己做主：只有显式关闭、Esc、滚动/缩放、程序化跳转才收。

连带三件事：

1. `SelectionLayer` 的 `shouldIgnoreEvent` 要**同时**判定浮条与气泡两棵根节点（原来只有一个 ref）；
2. `runSingleAction` 里按 `requestId` 丢弃迟到的响应——否则「换了选区/关了气泡之后，旧结果突然覆盖上来」；
3. 关闭时若还在 pending，**踢出一次 abort**（设计 §5.4 的硬要求）。

### 5.2 实施中的两处修正

1. **`requestId` 必须由渲染层生成。** 第一版把 `crypto.randomUUID()` 写在 `runSelectionAction` 内部——那样调用方拿不到 id，**「关闭即 abort」根本无从实现**。改成调用方传入，服务返回前不再自造 id。
2. **浮条/气泡的忽略判定要两棵根节点。** P0 的 `shouldIgnoreEvent` 只看 `surfaceRef`；气泡独立成枝后，点气泡里的「复制」会先触发划词层的任意-mousedown 收起——但气泡不在 surface 树里，`isIgnored` 判定为假，于是**气泡把自己关掉了**。加 `bubbleRef` 一并判。
3. **气泡的 Esc 与滚动监听去重。** 第一版两个都挂在气泡组件里；实则滚动/缩放由 `useSelectionWatcher` 的既有行为覆盖（它收的是整个 surface）。只保留 Esc。

### 5.3 实施记录（续：真机复现出的两个真 bug）

**bug 1：右键菜单里点 L2 动作「什么也没发生」（用户实测报告）。**

真因：菜单点击收尾时调 `api.close()`，而 `api.close` 被接成了 `closeView + closeBubble` —— **刚创建的气泡当场被关掉，发出去的请求 5-7ms 就被 abort**。主进程日志坐实：`[run] 开始 action=translate` 紧跟 `[run] 已取消 ... duration=7ms`。

**为什么浮条路径没暴露**：浮条路径不看 `view` 的存活，气泡建完就渲染；菜单路径的 `api.close()` 走的是同一份 `close`，于是「关入口」连坐「关结果」。

修法：把两个语义拆开 ——

- 动作的 `api.close()` **只收入口**（`closeView`）；
- 程序化跳转（`navigate/session-switch/session-create`）用 `closeAll`（浮条 + 气泡都收）——
  这几个事件的监听因此从 `useSelectionWatcher` 的 `closeOnEvents` 上移到本层。

**bug 2：`SelectionLayer` 在真机上直接崩掉（`Cannot access 'closeAll' before initialization`）。**

我把「监听 `closeAll` 的 `useEffect`」写在了 `closeAll` 定义**之前**，命中了 `const` 的暂时性死区。**`tsc` 查不出来**（它只当普通变量引用），单测也没覆盖到，表现是整页「界面加载失败」。修法是调整定义顺序。

**防复发**：新增 `SelectionLayer.test.tsx`（4 例）真渲染整层来守这两类问题 ——
真 store / 真组件 / 真事件链，只在 `window.electronAPI` 这层拦 IPC。
写它时踩到的坑记在这里备用：**在 document 的原生监听里 setState，测试里必须用 `act` 包住事件派发**，
否则 React 不会把这次更新提交上来，断言会看到「handler 跑了但菜单没渲染」的假象。

### 5.4 同期新增：气泡朗读

气泡底栏加了「朗读 / 停止」按钮（复制按钮旁）。实现没有复制第三份 TTS 播放逻辑：
把 `MessageActions` 里那段 chunk 排队播放抽成 `hooks/business/useTtsPreview.ts`，
消息朗读与气泡朗读共用一份 —— 连两条既有结论（`stop-preview` 是全局停、卸载只能停自己那次；
消息/气泡朗读不能用设置页的 100 字上限）一并收进 hook 的注释里。

### 5.5 同期新增（第二轮反馈）

| 需求 | 做法 |
| --- | --- |
| **气泡可拖动** | 按住气泡头部拖。用 **pointer capture** 而不是往 document 挂 mousemove —— 指针移出窗口再松开时捕获仍能收到 pointerup，不会留下粘在指针上的浮层。位移存在 `dragOffset`，开新气泡时归零 |
| **朗读防重复点击** | `useTtsPreview` 增加 `busy`（`voice:tts:preview` 未返回期间为真）。没有它的话：合成还在准备、`isSpeaking` 已是 true，用户再点一下就走了「停止」分支，把刚起的朗读掐掉。入口在 busy 时置灰并显示「准备中」 |
| **HTML 预览里划词** | 见下 |

**HTML 预览划词的架构**：预览是独立文档（HTML→`<webview>`，CSS/SVG→`<iframe srcDoc>`），宿主既收不到它的鼠标事件，`getSelection()` 也只看得到宿主自己的选区。做法是**只把「取词」送进 guest，展示仍留在宿主**：

```
guest 侧（preload / 注入脚本）        宿主侧
  监听 mouseup / contextmenu   ──►   toSelectionSnapshot()  → SelectionLayer
  读出 text + rect + point           （坐标平移 + 形状校验）
  webview: ipcRenderer.sendToHost      → showView({ snapshot, surface, point })
  iframe:  parent.postMessage
```

- guest 的 rect 是**它自己视口**里的坐标，宿主必须加上 webview/iframe 元素的位置 ——
  否则预览不在左上角时浮条整体漂移（这是本模块的主要测试对象）。
- 两条载体（webview preload / iframe 注入）**报文形状一致**，宿主一个解析函数通吃；
  改一处必须改另一处，注释里已标。
- 出处标为 `markdown-preview`（文件预览类的既有取值）；`plain` 会丢掉出处。
- iframe 那条仍是 `sandbox=""`：只多了一段内联取词脚本，导航与同源限制不变
  （本组件本来就靠向 srcDoc 注入 `<style>` 实现缩放）。

## 六、遗留

- 气泡内是**纯文本**渲染（`pre-wrap`）。模型若返回 Markdown 会看到原始标记——提示词里已要求「只输出译文本身」，但不强求渲染层做 Markdown。
- 浮条四项（引用/翻译/解释/复制）已达设计 §4.1 的上限。总结、润色只走右键菜单；若日后再加动作，需要先决定菜单排序是否要显式化（当前靠声明顺序）。
- 报错文案直接透传主进程的 message，未做用户化包装。
- 提示词硬编码不可编辑（设计 §十一 开放问题 2）。
- 气泡的**复制**动作没有「已复制」反馈，与浮条的复制动作一致（同一处 `writeClipboardText`）。
