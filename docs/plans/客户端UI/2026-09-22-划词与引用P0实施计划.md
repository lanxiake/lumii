## 二、关键设计决策

### 2.1 `Range` 只活在 `mouseup` 那一瞬

`useWindowedRows.ts` 会卸载离屏行的整棵子树。任何在 `mouseup` 之后仍持有活 `Range` 的写法，都会在「选完滚一下」时静默失效——`getBoundingClientRect()` 返回全零、`toString()` 返回空，而且**不报错**。

因此：`mouseup` 时同步构造 `SelectionSnapshot`（设计 §5.1 的形态），此后浮条、菜单、气泡**只读快照**。`Range` 引用在快照完成后立即丢弃。

连带结论：**快照里必须存 `rect` 的数值**，不能存 `Range` 或 DOM 节点。

### 2.2 出处靠 DOM 标记，不靠 React 树

快照发生在全局 `SelectionLayer` 里，**拿不到 ChatPage 的 React 上下文**，所以出处只能从 DOM 上读：正文容器根节点挂一组 `data-lumii-*` 属性，快照时从 `getRangeAt(0).startContainer` 往上 `closest()`。

属性全集与取值约束见设计 §5.1「出处（`source`）靠 DOM 标记解析」——**以那里为准，本文不重复**。这里只记实现侧的两点：

- 落点：`ChatMessage/index.tsx` 根节点；Wiki / 技能文档 / 记忆页各自的内容容器。**只加属性，不动渲染逻辑**——这是本轮对 Markdown 管线唯一的侵入。
- Wiki / 技能文档 / 记忆页的标记**可以后置**：未命中标记时 `source.kind = 'plain'`，引用只写文本不写出处，功能不残。

### 2.3 边界翻转抽成公共函数，`Tooltip` 本轮不动

设计 §3.2 已记录：全仓只有夹紧、没有翻转（`Tooltip.tsx:68`、`ContextMenu/index.tsx:42`）。浮条在视口底部必须翻到选区上方。

新增 `renderer/utils/floating-position.ts`：

```ts
export function placeFloating(
  anchor: SnapshotRect,
  size: FloatingSize,
  preferred: 'top' | 'bottom',
  viewport: FloatingViewport,   // 必传。不读 window：测试才不必依赖 jsdom 的窗口尺寸
): FloatingPosition              // { top, left, placement }
```

规则：先按 `preferred` 试，越界则翻到对侧；两侧都放不下时取空间更大的一侧，接受溢出，最后由夹紧兜底。`GAP = 8`、`VIEWPORT_PAD = 8` 与 `Tooltip` 保持一致。

> **落点定为 `renderer/selection/` 而非本节原先写的 `renderer/utils/`**（2026-09-22，实施时改）：它和快照共用 `SnapshotRect`，且只服务划词，放进子系统目录比散在通用 utils 里更内聚。

两处与 `Tooltip` 的差异是有意为之：

- **返回 `placement` 而不是 `flipped` 布尔**。调用方要拿它决定箭头朝向与 CSS 类，`placement !== preferred` 本身就是翻转判据，多返回一个布尔是冗余状态。
- **夹紧时上下界倒挂（浮层比视口还大）返回下界而非上界**。`Tooltip` 的 `Math.min(Math.max(...))` 在倒挂时会取到上界，等于把浮层整个推出视口；这里钉在起始边，至少保证左/上边缘可见。

**本轮不改 `Tooltip` 和 `ContextMenu` 去用这个函数**——它们是既有组件，改动会牵出无谓的回归面。等浮条跑通、函数被证明可用后，另起一轮收敛（记在 §八）。

### 2.4 引用走「注册式桥」，不把 Composer 草稿抽成全局状态

`SelectionLayer` 挂在 `App.tsx`（全局），但引用要写进 ChatPage 的 Composer 草稿。跨页面的选择有三条路：

| 方案 | 判断 |
| --- | --- |
| 把草稿状态抽成全局 store（`useSyncExternalStore`） | ✗ 改动面过大，要动 ChatPage 的草稿生命周期与切会话持久化 |
| React Context 提供引用目标 | △ 可行，但要求 `SelectionLayer` 必须在 `ChatPage` 的 Provider 子树内——而它是全局挂载的，反而要倒过来改挂载点 |
| **模块级注册桥** | ✓ 引用是「投递一个动作」，不是「同步一份状态」；用注册桥语义最准，改动面最小 |

新增 `renderer/selection/quote-bridge.ts`：

```ts
export function registerQuoteSink(sink: (ref: QuoteInput) => boolean): () => void
export function insertQuote(input: QuoteInput): boolean   // 无 sink 时返回 false
```

`ChatInput` 挂载时注册、卸载时注销。**未注册时引用动作置为 disabled**，`Tooltip` 说明「打开对话页后可用」——不做「自动跳转到对话页」，那是新的导航逻辑，不属于 P0。

### 2.5 主进程退让的粒度：只让「非可编辑 + 有选区」

`main-window.ts:239` 那段是**全局**的（覆盖文件预览、聊天记录、输入框）。退让判断必须收窄：

```
params.isEditable === true                     → 原生菜单（输入框需要剪切/粘贴，保持现状）
!isEditable && selectionText.trim() 非空        → 不 popup，交给渲染层
其余                                            → 原生菜单（保持现状）
```

放宽到「有选区就让」会连输入框一起让掉，剪切/粘贴直接消失。

### 2.6 渲染层 `preventDefault()` 与主进程 popup 的关系 —— **已实测修正**

~~Electron 的 `context-menu` 事件与 DOM `contextmenu` 是两条独立链路，**渲染层 `preventDefault()` 不能阻止主进程 popup**。所以 §2.5 的主进程改动不是优化、是必需项。~~

**实测（2026-09-22，Electron 36，本机）结论相反：能阻止。** 在主进程 `context-menu` 里加临时诊断后，渲染层接管的右键（聊天区 / 概览 / Markdown 预览三处）**主进程全程零事件**；而输入框不让位、不 preventDefault，每次都收到事件（`editable=true`）。三处右键均只出现一个自绘菜单。

**但这不推翻 §2.5**：主进程仍要主动让位。理由是「preventDefault 能挡住」只是本机实测、不是 Electron 的文档承诺，而主动让位在两种语义下都正确。**被修正的是「必需项」这个措辞 —— 它是防线，不是唯一防线。**

顺序上仍建议先落 S5 的主进程侧再验渲染层：否则渲染层一接管就会与原生菜单叠成两层，真机判据（「只有一个菜单」）无从判断。

### 9.2 实施中发现并修掉的真 bug：z-index

**症状**：文件预览里选中文字不出现浮条、右键不出现菜单 —— 表现为「功能完全没反应」。

**根因**：浮条用 `--z-popover`（1500），复用的 `ContextMenu` 是硬编码 1000，而文件预览弹窗是 `calc(var(--z-settings-hub, 12000) + 40)` = **12040**。菜单**渲染了**，只是画在弹窗背后。

**修法**：`tokens.css` 新增 `--z-selection: calc(var(--z-settings-hub, 12000) + 50)`（12050）—— 高于所有弹窗（最高 +41），低于 Toast（+60，让通知仍能露头）；`ContextMenu` 加可选 `zIndex` prop 由划词菜单传入。

**教训**：**划词必须在文件预览这类高层浮层里真机验一遍**。单测、以及在普通页面上跑浮条，都发现不了它 —— 层级问题只在「选区落在哪个浮层之上」时才暴露。

**定位过程的一个教训**：第一版诊断只挂在主进程，而它**只能证伪**（渲染层接管后主进程就收不到事件了，于是「修好了」和「事件压根没到」在日志里长得一模一样），白跑一轮。补上渲染层的对侧探针后才一次定位。**探针要能双向判定，别只有一半。**

### 9.3 已实测结清的未知项

设计 §八 的第 4、5 条已收口，结论写在设计文档里，此处只记要点：

- **渲染层 `preventDefault()` 确实能阻止主进程 popup**（原判断是错的，见 §2.6 的修正）。
