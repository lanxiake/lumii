## 一、目标与边界

**目标**：把「选中 → 浮条 / 右键菜单 → 动到东西」这条链路真正跑通，并交付两个 L1 动作（**引用**、复制）。

| # | 内容 |
| --- | --- |
| S1 | 选区快照（**纯函数**，可脱离浏览器单测） |
| S2 | 选区监听 + 浮条壳 + 边界翻转（全仓首次） |
| S3 | 动作注册表（浮条与右键菜单的**唯一定义处**） |
| S4 | 引用投递桥 + 引用最小形态（插 Markdown blockquote 进 Composer） |
| S5 | 右键菜单集成 + 主进程原生菜单退让 |
| S6 | 选区保住、关闭时机、生命周期收口 |
| S7 | §八.1 的通道选型实测（**只出结论，不出产品代码**） |

**不做什么**

- ✗ L2 直连 LLM 动作与就地气泡 → P1（依赖 S7 的结论）
- ✗ 引用的结构化形态（chip / metadata / 重发 / 渠道出站）→ P2
- ✗ L3 Agent 动作（追问 / 用技能 / 存为记忆 / 朗读）→ P3
- ✗ 替换原文（设计 §六已裁定不做）
- ✗ 系统级划词（独立阶段）
- ✗ 不改 `Tooltip`（见 §2.3）
- ✗ 不动 `ChatMessage` 的 Markdown 渲染管线（只加一个 `data-*` 标记，见 §2.2）

## 二、关键设计决策

### 2.1 `Range` 只活在 `mouseup` 那一瞬

`useWindowedRows.ts` 会卸载离屏行的整棵子树。任何在 `mouseup` 之后仍持有活 `Range` 的写法，都会在「选完滚一下」时静默失效——`getBoundingClientRect()` 返回全零、`toString()` 返回空，而且**不报错**。

因此：`mouseup` 时同步构造 `SelectionSnapshot`（设计 §5.1 的形态），此后浮条、菜单、气泡**只读快照**。`Range` 引用在快照完成后立即丢弃。

连带结论：**快照里必须存 `rect` 的数值**，不能存 `Range` 或 DOM 节点。

### 2.2 出处（`source`）靠 DOM 标记，不靠 React 树

快照要知道「这段文字来自哪条消息」，用于引用标注与（P3 的）会话路由。但快照发生在全局 `SelectionLayer` 里，拿不到 ChatPage 的 React 上下文。

做法：在几个正文容器根节点上挂 `data-*` 标记，快照时用 `anchorNode.parentElement.closest('[data-lumii-source]')` 往上找：

```html
<div data-lumii-source="chat-message"
     data-conversation-id="..."
     data-message-id="..."
     data-message-role="assistant">
```

落点：`ChatMessage/index.tsx` 的根节点；Wiki / 技能文档 / 记忆页各自的内容容器。**只加属性，不动渲染逻辑**——这是本轮对 Markdown 管线唯一的侵入。

未命中标记时 `source.kind = 'plain'`，引用只写文本、不写出处。

### 2.3 边界翻转抽成公共函数，`Tooltip` 本轮不动

设计 §3.2 已记录：全仓只有夹紧、没有翻转（`Tooltip.tsx:68`、`ContextMenu/index.tsx:42`）。浮条在视口底部必须翻到选区上方。

新增 `renderer/utils/floating-position.ts`：

```ts
export function placeFloating(
  anchor: DOMRectReadOnly,
  size: { width: number; height: number },
  preferred: 'top' | 'bottom',
): { top: number; left: number; flipped: boolean }
```

规则：先按 `preferred` 算，越界则翻到对侧；两侧都放不下时取空间更大的一侧再夹紧。`GAP = 8`、`VIEWPORT_PAD = 8` 与 `Tooltip` 保持一致。

**本轮不改 `Tooltip` 和 `ContextMenu` 去用这个函数**——它们是既有组件，改动会牵出无谓的回归面。等浮条跑通、函数被证明可用后，另起一轮收敛（记在 §八）。

### 2.4 引用走「注册式桥」，不把 Composer 草稿抽成全局状态

`SelectionLayer` 挂在 `App.tsx`（全局），但引用要写进 ChatPage 的 Composer 草稿。跨页面的选择有三条路：

| 方案 | 判断 |
| --- | --- |
| 把草稿状态抽成全局 store（`useSyncExternalStore`） | ✗ 改动面过大，要动 ChatPage 的草稿生命周期与切会话持久化 |
| React Context 提供引用目标 | △ 可行，但要求 `SelectionLayer` 必须在 `ChatPage` 的 Provider 子树内——而它是全局挂载的，反而要倒过来改挂载点 |
| **模块级注册桥** | ✓ 引用是「投递一个动作」，不是「同步一份状态」；用注册桥语义最准，改动面最小 |

新增 `renderer/selection/quote-bridge.ts`：

```ts
export function registerQuoteSink(sink: (ref: QuoteInput) => boolean): () => void
export function insertQuote(input: QuoteInput): boolean   // 无 sink 时返回 false
```

`ChatInput` 挂载时注册、卸载时注销。**未注册时引用动作置为 disabled**，`Tooltip` 说明「打开对话页后可用」——不做「自动跳转到对话页」，那是新的导航逻辑，不属于 P0。

### 2.5 主进程退让的粒度：只让「非可编辑 + 有选区」

`main-window.ts:239` 那段是**全局**的（覆盖文件预览、聊天记录、输入框）。退让判断必须收窄：

```
params.isEditable === true                     → 原生菜单（输入框需要剪切/粘贴，保持现状）
!isEditable && selectionText.trim() 非空        → 不 popup，交给渲染层
其余                                            → 原生菜单（保持现状）
```

放宽到「有选区就让」会连输入框一起让掉，剪切/粘贴直接消失。

### 2.6 渲染层 `preventDefault()` 挡不住主进程

Electron 的 `context-menu` 事件与 DOM `contextmenu` 是两条独立链路，**渲染层 `preventDefault()` 不能阻止主进程 popup**。所以 §2.5 的主进程改动不是优化、是必需项，顺序上必须先落 S5 的主进程侧再验渲染层。

## 五、测试计划

**写测试的三个坑（仓库既有结论，别重新踩）**

1. **vitest 不做类型检查** —— 新增测试后**必须重跑 `tsc`**，否则类型错误会一路绿到 CI。
2. 默认 `environment: 'jsdom'`。选区相关测试**优先用纯函数 + 假对象**（`snapshot.ts`、`floating-position.ts` 都设计成纯函数就是为了这个），不要依赖 jsdom 的 `Selection` 实现。
3. 本仓库**无 ESLint**，类型与测试是唯一门禁。

**命令**

```bash
# 就近单测
cd apps/windows && npx vitest run src/renderer/selection

# 全量（动过 src/main/** 必跑，本计划第 5 步之后）
cd apps/windows && pnpm test:all

# 类型检查（全 workspace）
pnpm typecheck
```

**测点分配**

| 层 | 测试 |
| --- | --- |
| 纯函数 | `snapshot.test.ts`、`floating-position.test.ts`、`registry.test.ts`（surface 过滤与 barOrder 排序） |
| 组件 | `SelectionToolbar.test.tsx`（渲染项、disabled 态）、`SelectionLayer.test.tsx`（触发条件：可编辑区不弹、collapsed 不弹） |
| 主进程 | `main-window` 的退让判断：建议把判断抽成纯函数（如 `shouldDeferToRenderer(params)`）再单测，避免靠 mock Electron |
