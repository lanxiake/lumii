## 〇、一句话结论

参考项目是**一份完整的 Shimeji 行为设计蓝图，不是工程质量标杆**。

lumii 在**物理、命中检测、逻辑分层、素材生成线、口型与表情**五个维度上已经领先它；真正值得吸收的是三件事：

| # | 吸收项 | 为什么是它 |
| --- | --- | --- |
| 1 | **自主运动行为系统**（走/爬墙/天花板） | lumii 宠物站立时**位置恒定在画布中心**，不会移动——这是当前最大的能力空白 |
| 2 | **用宠物镜像真实负载** | 参考项目写下了映射公式却**从未接线**（死代码）；而 lumii 的 IPC 管道**已经通了**，只差订阅与映射 |
| 3 | **阈值 + 迟滞 + 边沿检测的环境事件层** | 参考项目最成熟的一块实现，任何"环境驱动行为"都必须有这层，否则阈值附近疯狂刷屏 |

另外还有三个**"零件在位、线没接"**的既有缺口，应先于新功能修掉（§三·P0）。

## 一、参考项目的实测评估

先说清楚它是什么，避免把它的实现当成可照搬的标尺。

**它是一个单次 AI 生成的项目，不是长期演进的成熟工程：**

- `git log` 共 **9 个提交**，提交信息带 ` ``` ` 前缀（生成工具痕迹）
- README 声称"使用 Lottie 动画"，但 `lottie-compose` 依赖**在代码里零引用**，资源目录**没有任何 `.json` 动画文件**——全部是 PNG
- 测试只有 2 个文件（`PetTest.kt` / `MemoryTest.kt`），只覆盖 domain model
- 实际动画是**标准 Shimeji 精灵图集**（不是 Lottie），这一点 README 没写对

**但它确实把 Shimeji 行为系统跑通了**——实测 `albedo.png` 为 1024×1152 的 8 列 × 9 行、128px 网格图集，帧数分布为：

```
row1: 1 帧  STAND   row4: 4 帧  GREET   row7: 1 帧  DRAG
row2: 4 帧  WALK    row5: 1 帧  JUMP    row8: 8 帧  CRAWL
row3: 1 帧  SIT     row6: 3 帧  FALL    row9: 8 帧  CLIMB
```

与代码里的 `PetState` 枚举逐行吻合（`PetState.kt:20-60`），且每个动作自带 `spriteLine` / `frameMax` / `frameRate` / `loop` / `canInterrupt` 元数据。**这是一套完整的、可复用的动作表设计**，51 张素材同构。

**结论：抄它的行为设计，不抄它的工程实现。**

## 三、优化方案（按 ROI 排序）

### P0 — 先补"零件在位、线没接"的三个缺口

这三条都是**已有能力没生效**，不是新功能，成本低但用户可感知。

| # | 缺口 | 根因 | 方向 |
| --- | --- | --- | --- |
| P0-1 | **点击身体不播任何动作**（随包三只精灵模型） | `manifest.json` 未声明 `hitAreas` → `hitTestPolygons` 返回 null → 落到 `hit ?? 'body'` → 而注册表里 `tapMotions` 的 key 是 Live2D 风格的 `HitAreaBody` → 兜底候选 `['body','Tap','tap','TapBody','$unnamed']` 在只有 Idle/Talk/Wave 的模型里**全部不存在** → 静默 return | 生成线补 `hitAreas` 声明；或让 `tapMotions` 支持"无 key 时取第一个可用动作组" |
| P0-2 | **两套口型每帧白跑**（随包三只精灵模型） | 模型无 `mouthLevels`、无 `slots.mouth` → `mouthBinding` 恒 null → `setMouthOpen` 直接 return | 生成线补口型层（差分取层已具备能力，此前未达标）；或对无口型层模型**关掉 LipSync 驱动**，省掉每帧空转 |
| P0-3 | **打盹/睡着的脸演不出来** | `DROWSY_EMOTIONS` 的 5 个候选名（`sleepy`/`困`/…）对现役三只模型**全部落空** | 补素材；或改为按**索引**表达（现役模型有 `eye_shut` 等条目可用） |

（另：位置不持久化——关闭宠物模式再进入，宠物回到画布中心。参考项目同样有此缺陷，属两边通病，可并入 P1。）

### P1 — 让宠物成为 Agent 的活体仪表（**最高价值**）

这是参考项目**想做而没做成**的事，也正是 lumii 独有的机会。

**依据**：参考项目 `SystemStatusMonitor` 里定义了四个映射 getter——
`petHunger = 100 - batteryLevel`、`petEnergy = 100 - cpuUsage`、`petSatiety = 100 - memoryUsage`、`petMood = f(网络信号)`
——**全项目零引用**。它写下了"把环境指标连续映射成宠物内在状态"的公式，却没有接线。宠物的 hunger/mood/energy 永远是数据库初值，导致 `ChatEngine` 里"饿了会主动说话"的规则**永不触发**。

**lumii 的管道已经通了**：主进程 `bridge-renderer-ipc.ts:57-71` 的 `mirrorToPetWindow()` 已经**全量镜像** `agent-runtime:event` 到宠物窗口（含 `agent:tool:start` / `agent:tool:end` / `agent:tool:progress` / 流式 delta）。渲染侧的 `pet-event-adapter.ts` **只订阅了 `voice:event`**，`agent:text` 类型已定义但适配器里没有对应 case——注释写着"及未来 `agent-runtime:event`"，即承诺未兑现。

**这一步零主进程改动。**

| # | 内容 |
| --- | --- |
| P1-1 | `pet-event-adapter` 增加 `agent-runtime:event` 订阅，扩展 `PetBusEvent`（工具开始/结束/进度、轮次开始/结束） |
| P1-2 | `pet-core` 新增内在状态模块（纯函数 + 单测）：**精力**随任务量累积消耗、**专注**随任务进行、**心情**由工具成功率驱动 |
| P1-3 | 状态 → 行为映射：长任务运行→专注姿态；工具失败→沮丧；连续成功→雀跃；空闲→打盹（复用已有 `idle-stage`） |
| P1-4 | **短句气泡**：浮在宠物头上的即时反馈，走**模板池 + 分档**（参考项目 43 条台词按严重度分三档的做法），零延迟零成本；长对话仍走 LLM |

> **设计取舍**：不抄参考项目的**虚拟养成**（喂食/玩耍/饥饿度）。对 Agent 桌宠，"宠物饿了"是假需求；"Agent 刚跑了 12 分钟、调了 40 次工具"是**真信息**。内在状态的输入应该是真实负载，不是虚拟计时器。

### P2 — 自主运动（Shimeji 行为集）

lumii 当前**没有空间移动**：宠物只在原地播动作。参考项目的九态行为系统是这块的完整参考。

| # | 内容 | 说明 |
| --- | --- | --- |
| P2-1 | **动作表驱动**：模型清单声明有哪些动作组及元数据（`group` / `kind` / `fps` / `next` 已具备），运动调度器按 `availableStates` 自动降级 | 参考项目的"能力门控"设计：缺 `CLIMB` 时走到边界只转身、缺 `JUMP` 时直接瞬移落地——**降级路径必须显式写**，否则会静默卡死 |
| P2-2 | **`edge` 一等字段** | 参考项目用"宠物贴在哪条边"这一个字段，同时驱动了物理边界系、气泡锚点、精灵翻转、窗口偏移、拖拽落点五处逻辑 |
| P2-3 | **拖拽落点决定状态** | 松手位置 → 贴左/右墙→爬墙、贴顶→天花板爬行、悬空→自由落体。参考项目 `endDrag` 的 5 分支优先级 when，用户无需学任何额外 UI |
| P2-4 | **运动调度器进 `pet-core`**（纯函数，与 `throw-physics.ts` 同规格：`dt` 外部注入、不读时钟、NaN 兜底） | 参考项目的物理循环里**另读墙钟并丢弃 `dt` 形参**——这是无法做暂停/倍速/掉帧补偿的根因，必须反着做 |
| P2-5 | **素材分两步**：先"位移 + 摇摆/倾斜原语"模拟走动（零生图成本，先验证观感）；满意后再生成 Walk / Climb / Crawl 动作组（每批一次生图） | 参考项目 GREET 行实测只有 4 帧有内容（枚举写 8 帧），说明**动作表要按实际素材校准**，不能照抄 |

> **注意**：参考项目的"暂停时仍推进动画"值得保留——冻结位移不冻结呼吸，是宠物"活着"的常识。

### P3 — 待决策项

| 项 | 成本 | 说明 |
| --- | --- | --- |
| **多宠物同屏** | 高 | lumii 的窗口架构对此**天然友好**（单张全屏画布，不像参考项目要开多个 OS 窗口），但编排器/画布/命中/穿透/控制坞**全是单例**，改造面大。参考项目自身在此也做得不好：上限 `3` 硬编码在三处、除角落排列外零碰撞检测（宠物互相穿过） |
| **场景 / 道具层** | 中 | `slots.scene` 已在 schema 内且有测试，示范模型未使用 |
| **位置持久化** | 低 | 选定唯一坐标系（建议归一化），窗口销毁时回写 |

## 四、明确不吸收的

| # | 不吸收 | 理由 |
| --- | --- | --- |
| 1 | **每宠物一个 OS 窗口 + 每帧 `setBounds`** | 参考项目最大的性能陷阱（3 只 = 每秒 180 次窗口重排）。lumii 的单画布架构**已经规避**，不要倒退 |
| 2 | **多套 `while + delay` 互相 cancel** | 参考项目的 `selfTalkJob` / `talkJob` / `physicsUpdateJob` 三套时间轴无统一仲裁，导致真实竞态（自发牢骚的 `delay(3000)` 会清掉刚被系统事件写入的气泡；`talkJob` 全局共享使多宠物互相取消发言） |
| 3 | **用 `StateFlow` 承载事件** | 参考项目 `MutableStateFlow<StatusEvent?>` 靠"每事件后立即置 null"侥幸可用；StateFlow 会去重相等值，消费端一慢就**静默丢事件**。要用有缓冲的队列 |
| 4 | **双坐标系各自换算** | 参考项目的物理坐标与窗口坐标有两份近似但不同的换算，衍生出 `petSize/10`、`petSize/8` 这类"看着效果调出来"的魔数 |
| 5 | **关键词模板对话**（`ChatEngine`） | 8 类关键词硬编码匹配，且规则本身有缺陷（`AFFECTION` 含关键词"好"且排在 `QUESTION` 之前，任何含"好"字的问题都会被判成撒娇）。对已有真实 LLM 的 lumii 是**纯负债** |
| 6 | **空转的可打断配置** | 参考项目 `PetState.canInterrupt` 定义了、守卫也写了，但九个状态**无一覆写**，恒为 true，守卫永不触发。要么用起来要么删掉——不要留这种误导性配置 |
| 7 | **屏占整块的命中区** | 参考项目 628×628 整窗吃触摸，宠物周围大片透明区会拦住对下层应用的点击。lumii 已有多边形命中 + hover 穿透，**这是它的强项**，不要在加入新交互时退化 |
| 8 | **虚拟养成数值**（喂食/玩耍/饥饿/亲密度） | 见 P1 的设计取舍：对 Agent 桌宠是假需求 |
| 9 | **硬编码台词的"对话"** | 短反馈用模板池（P1-4）是对的，但**长对话必须走 LLM**——lumii 的宠物是 Agent 化身，退回模板是能力降级 |

## 五、验收方式

沿用本仓库既有做法（见设计 §9）：

- **纯函数进 `pet-core`**：运动调度、内在状态、阈值迟滞层全部零依赖、可脱 DOM 单测；不变量里必须包含"任何输入下输出都是有限数"
- **素材类改动走 `pet-asset` 闸门**：`sheetcheck` 出图闸门 + `validate` / `install` 两段式，坏数据隔离不得回归
- **UI 类改动走 `lumii-ui` CLI 实测**（截图 + click 验证），不靠"看着像对的"
- **量化手测**：像 P2-b 注视（±88px 位移 2~3px、±150px 饱和）与 P2-c 闲置（3s 打盹 / 8s 睡着）那样给出**数值判据**，而非主观描述
- 动过 `src/main/**` 必须跑 `apps/windows` 全量 `test:all`（默认 `test` 不覆盖 `src/main/`）

## 附：参考项目可用的常量与参数（一次性归档）

留档备查，实施时按 lumii 的观感重调，不要照抄。

**行为调度**（`PetPhysicsEngine.kt:24-32`）
`MOVE_VELOCITY 60px/s` · `GRAVITY 500px/s²` · `RANDOM_STATE_INTERVAL 5000ms` · `RANDOM_STATE_CHANCE 0.3`（**失败后计时器减半到 2500ms**，避免坏运气导致长时间发呆）· `FLIP_INTERVAL 8000ms` · `FLIP_CHANCE 0.2` · `BOUNDARY_MARGIN 30px`（地面留边距；爬墙切 `[0, W-pet]` 真边缘）· `CRAWL_DROP_CHECK_INTERVAL 2000ms` · `CRAWL_DROP_CHANCE 0.15`

**地面状态权重**（`:533`）：`STAND 0.3 / WALK 0.4 / SIT 0.2 / GREET 0.1`，按 `availableStates` **先过滤再取权重**，浮点累加不中时兜底取第一个

**环境阈值**（`SystemStatusMonitor.kt:399-409`）：CPU `80/50` · 内存 `85/70` · 温度 `40/35`（触发值/解除值，中间是迟滞死区）

**交互手势**（`FloatingPetService.kt:92-99`）：`DRAG_THRESHOLD 10px` · `DOUBLE_CLICK_INTERVAL 500ms` · `LONG_PRESS_THRESHOLD 500ms`（长按 500ms 才解锁拖动，防止"想点一下却把宠物拖飞"）
> ⚠️ 双击消歧让**每次单击必然延迟 500ms**。桌面端点击预期更即时，**不建议照搬**。

**多宠物间距**（`:724`）：`petSize × 0.8`——故意留 20% 重叠量显得"挤在一起"，但**没有任何碰撞检测**
