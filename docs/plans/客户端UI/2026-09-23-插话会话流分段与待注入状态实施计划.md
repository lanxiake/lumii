# 插话会话流优化实施计划（分段 + 待注入状态）

> 状态：**已实施并实测通过**（2026-09-23）。见文末「实施记录」。
> 背景：`2026-09-23-运行中插话与会话绑定实施计划.md`；pi 升级相关见 `2026-09-23-pi框架升级评估.md` §8.2.2

## 一、要解决的问题

用户实测后提出两点：

### 问题 1：插话前后的执行记录挤在同一个「执行过程」折叠块里

**根因在数据层，不是折叠组件**：

- 主进程**一个 run 只建一条 assistant 占位行**（`bridge-agent-instance-events.ts:537`），之后所有
  parts 都追加到同一条（`:584/616/687/699/714/722`）。
- 而 **pi 内部每次 provider 请求各产出一条 assistant 消息**——插话后必然是新一次请求。
- 同时还有一层历史包袱：修「看不到回复」时用的是**把整条 assistant 消息挪到插话之后**
  （`event-handler.ts:1503`），而那条消息里有一半是插话**之前**的工作。

现状读起来是：

```
[用户] 跑两个 sleep
[插话] 停！立刻结束          ← 排在了它之前就发生的工作前面
[助手] ▸ 执行过程（插话前后全塞这里）
       已停止，第二条不会执行
```

目标：

```
[用户] 跑两个 sleep
[助手] ▸ 执行过程（思考要跑两个 sleep / 发起 bash）
[插话] 停！立刻结束
[助手] ▸ 执行过程（bash 结果回来了 / 收到插话 / task_complete）
       已停止，第二条不会执行
```

### 问题 2：插话发出后，用户不知道模型看到没有

长工具运行期间（实测 bash 跑了 30s，`spawn_agent` 可达数分钟），插话气泡已经出现，但模型要到
下一轮 provider 请求才看到它。这段窗口里 UI 无任何提示。

## 二、为什么分段点是 `prepareRequest`

**不能按「插话入队」切分**：入队时可能还有工具在跑。实测现场（20:13:28 插话、bash#1 于
20:13:24 启动、20:13:54 返回）——那时切分会把「启动于插话前、返回于插话后」的工具拆成两半，
`tool:start` 进段 1、`tool:end` 找不到 part 而新建一个 → 重复工具卡。

**正确的切分点是「插话被注入、下一轮 provider 请求即将开始」** —— 也就是模型真正看到插话的那一刻。
pi 的 loop 顺序是：

```
inner iteration N (N≥2):
  emit turn_start
  inject preparedMessages + pendingMessages   ← 插话在这里进入 context
  prepareRequest                              ← 我们已经有这个钩子（pendingSteerCount 归零点）
  stream assistant response                   ← 新段的 parts 从这里开始
```

所以已有的 `prepareRequest` 钩子**恰好**落在边界上，不用改内核适配器、不用新增 pi 事件映射。

（补充事实：`agent-instance.ts:470` 直接订阅 **pi 原生事件**，`mapAgentEvent` 吃的是
`agent_start`/`message_update` 这类原生类型 —— 所以拿边界信号不必经过 kernel adapter。）

## 三、实现

### 3.1 事件：新增 `steer:delivered`

`packages/agent-runtime/src/types/events.ts` 的 `AgentRuntimeEvent` 加一个变体：

```ts
/** 插话已注入对话（工具批已收尾、下一轮 provider 请求即将开始）。消费方据此在对话流里分段。 */
| { type: 'steer:delivered'; instanceId: string; /**
 * 本次被注入的插话消息 id（宿主在落库插话行时登记）。
 * 渲染层据此把对应气泡的「待注入」状态转成普通插话。
 */ messageIds?: readonly string[] }
```

### 3.2 AgentInstance：在 `prepareRequest` 发信号

`agent-instance.ts` 的 `prepareRequest`（已有，用于 `pendingSteerCount` 归零）改为：

```ts
prepareRequest: (context, signal) => {
  if (this.pendingSteerCount > 0) {
    this.emit({ type: 'steer:delivered', instanceId: this.id });
  }
  this.pendingSteerCount = 0;
  return callerPrepareRequest?.(context, signal);
},
```

`messageIds` 由宿主（bridge）补：见 3.4 —— AgentInstance 不知道插话的落库 id，让 bridge 在转发时挂上。

### 3.3 主进程：封口当前段、开新占位

`bridge-agent-instance-events.ts` 处理 `steer:delivered`：

1. **收尾当前段**：若 `state.streamingAssistantMsgId` 有效且 `pendingParts` 有内容
   （`type === 'tool'` 或文本非空），调 `finalizeStreamingAssistantMessage`（`is_streaming=0`）。
   无内容则删掉空占位（复用 `agent:start` 里那套判断）。
2. **开新占位**：`conversationRepo.saveMessage({role:'assistant', contentJson:{type:'assistant_parts',parts:[]}, isStreaming:true})`，
   写回 `state.streamingAssistantMsgId`。
3. **让 converter 用新 id、且从 0 起算文本偏移**：
   `ctx.currentMessageId = newId`；`ctx.accumulatedLength = 0`；`ctx.completedTurnsLength = 0`；
   `ctx.thinkTagState = 'idle'`；`ctx.thinkTagBuf = ''`。
   ⚠️ 注意 `event-converter.ts:129` 的续轮分支：`currentMessageId` 已有值时会把
   `completedTurnsLength` 设成 `accumulatedLength + 2`（那是「同一气泡内拼接第二轮文本」的偏移）。
   新段必须绕开它，否则新气泡的 `textPositionAtStart` 全部偏 2。
   → 做法：给 `convertOldEventToIpcEvents` 加一个显式的 `newSegment?: boolean` 参数，或把偏移重置
   放在设置 `currentMessageId` **之后**并额外打一个「本段已重置」标记。二选一，实施时按最小改动定。
4. **通知渲染层**：转发一条 `agent:message:start` 等价事件（带新 `messageId`、`runId`、`sessionKey`）。

### 3.4 待注入状态

- `user-commands.ts` 的 `handleUserSteer` 已 `persistSteerMessage` 拿到插话行 id → 登记到
  「该 instance 尚未注入的插话行 id」列表（放 `bridge-instance-state.ts` 的实例状态里）。
- 转发 `steer:delivered` 时把该列表挂到 `messageIds` 并清空。
- **渲染层**：新建插话气泡时按登记的 id 置 `steerPending: true`；收到 `steer:delivered` 后按
  `messageIds` 翻转成普通插话。角标文案：待注入 →「插话 · 等待注入」，已注入 →「插话」。
  为不依赖事件到达顺序，插话气泡创建时默认 `steerPending: true`，只在收到对应 `steer:delivered`
  或该轮 `agent:end` 时清除。

### 3.5 渲染层：拆掉「整条消息前挪」的 hack

`event-handler.ts:1503` 的 `isSteer` 分支（把插话 splice 到流式 assistant 之前）**删掉**，改为正常追加。
分段后 DB 的时间序天然是 `[段1][插话][段2]`，排序自然正确。

同时：收到同一 run 下**不同 messageId** 的 `agent:message:start` 时，把上一条主 Agent 流式消息
置 `isStreaming: false`（封口），避免两个气泡同时显活。

## 四、风险与既有分支

| 风险 | 处理 |
|---|---|
| 自愈重试 / abort / NO_REPLY 删占位等既有分支假设「一个 run 一个占位」 | 逐条过一遍：`agent:start` 的上一轮清理（`:459-494`）、`agent:end` 收尾（`:915-975`）、NO_REPLY 删行（`:905-914`） |
| 插话后**没有**新 parts（例如插话后模型直接结束） | 段 2 的占位会空着 → `agent:end` 的「纯 NO_REPLY 轮」判断需要能识别「最后一段为空」并删掉它，而不是把上一段一起删 |
| 同一 run 连发多条插话 | 每次 `steer:delivered` 都封一次；多段是允许的，不必合并 |
| 并发子 Agent 的占位 | 只封自己 instance 的 `streamingAssistantMsgId`，不碰其他实例 |
| 渲染层重复 `message:start` | 现有逻辑按 messageId 查找/复用；新增的「换 id 即封旧气泡」需与子 Agent 分支区分（`isSubAgentStreamEvent`） |

## 五、验证

1. **单测**（`bridge-agent-instance-events.test.ts` 已有 `forwardIpcEvent` 注入口，可注入 repo 桩）：
   - `steer:delivered` → 旧段被 finalize（`is_streaming=0`）、新占位被创建、`ctx.currentMessageId` 换新
   - 空段不落库（无 parts 时不产生多余行）
   - 连发两条插话 → 三次封口、无重复行
2. **渲染层**：`steerPending` 默认 true → 收 `steer:delivered` 翻转；换 messageId 时旧气泡 `isStreaming=false`
3. **E2E**（判据必须落到 DB，别只看 UI）：
   - 跑「两个 sleep + 中途插话」，然后查 `messages` 表：**应为两条 assistant 行**，插话行夹在中间（按 timestamp）
   - 重载会话，UI 的分段与库一致（分段信息在数据里，不靠渲染层记忆）
4. **回归**：`pnpm typecheck` + `apps/windows test:all` 全量

## 六、不做的事

- **不**把「每次 provider 请求」都切段（那会让每个工具往返都冒一个气泡，几十条刷屏）。
  只在**用户插话**这个叙事断点上切。
- **不**恢复等待队列（`a5221f27` 已决定统一为即插话）。

### 实测结果（决定性判据在 DB）

会话 `a6926d53…`（已清理）的最终形状——**每条插话都夹在它之前的工作与之后的工作之间**：

```
13:05:50 user      跑两个 30 秒等待…
13:06:46 assistant 8b709cff parts(18)
13:06:48 user      同时开两个后台等待…
13:06:50 assistant 6a86d46c parts(11)   ← 段1
13:07:27 user      [插话] 并行验证…
13:07:38 assistant ab2f870c parts(11)   ← 段2
13:07:53 user      [插话] 停！
13:08:29 assistant c2913b79 parts(2)    ← 段3（插话后的回应）
```

对数：`steer:delivered 已分段：旧段 6a86d46c → 新段 ab2f870c`、`旧段 ab2f870c → 新段 c2913b79`。

### 实施中查出并修掉的两个新增问题

1. **delta 批处理的 key 不含 messageId**（`pendingDeltaTargetKey` 对主文本只按 `sessionKey`）。
   合并批次时只保留"最后一个 messageId"，于是跨段时上一段的残留 delta 被粘到**新气泡**上
   （实测「插话前的输出」出现在第二个气泡里）。已把 messageId 并入 key。

2. **封口会把时间戳推到当下**，于是「插话前的执行记录」排到了插话**之后**
   （实测旧段 12:52:58 vs 插话 12:52:56）。
   仅"保留原值"不够——流式持久化每次写入都在推它，原值早已不是段起点。
   最终：实例状态记 `streamingSegmentStartedAt`，封口时用 `timestampOverride` 写回**段起点**。

### 未做

- **重载后的一致性**只做了推理（分段落在数据里，重载按 timestamp 排序必然正确），
  未单独重载会话肉眼核对。
- 同一 run 连发多条插话（多段）在实测里自然出现过（本会话就是 3 段），未单独写用例。
- **§3.4 的 `messageIds` 没做**：实现时发现不必精确到 id——`steeringMode: 'all'` 下同一次投递
  会把排队中的插话**一起**注入，所以「收到 `steer:delivered` → 该会话没有还挂着待注入的」
  成立，渲染层整会话翻转即可。少一处 id 登记，也少一类对不上的风险。
