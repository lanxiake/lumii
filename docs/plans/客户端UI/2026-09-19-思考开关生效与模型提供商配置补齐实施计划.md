# 思考开关生效与模型提供商配置补齐实施计划

> 关联设计：[`../../design/客户端UI/2026-08-17-DeepSeek提供商与ResponsesAPI支持.md`](../../design/客户端UI/2026-08-17-DeepSeek提供商与ResponsesAPI支持.md)

**Goal:** 让对话页「思考开关 + 思考等级」真正影响发给 LLM 的请求；在设置→模型配置里补齐模型级思考能力与提供商预设。

**Architecture:** 宿主持有「模型能力」配置（provider.json 的 `modelReasoning` / `thinkingFormat`），经 `resolveModelProfile` 注入 `createDirectStreamFn`，由它合成 pi-ai 需要的 `model.reasoning` / `model.compat` / onPayload 注入；agent-runtime 不硬编码厂商常量。

**Tech Stack:** TypeScript, Electron(主进程/渲染进程), pi-ai 0.50.7, React, Vitest

## 背景

对话页思考开关的链路（UI → localStorage → IPC → `BridgeSessionThinkingPrefs` → `wrapStreamFn` 写 `options.reasoning`）本身完整无 TODO，但**参数从未进入请求体**。用户实测感受为「没生效」，实测抓包证实。

## 一、根因（已实测验证）

| # | 根因 | 证据 |
| --- | --- | --- |
| 1 | 会话模型是最小模型（只有 `{id, api}`），`direct-stream.ts:88` 把 `reasoning` 兜底为 `m.reasoning ?? isZaiLike` → 非 z.ai 端点恒 false | `model-router.ts:57-65`、`direct-stream.ts:88` |
| 2 | pi-ai 所有 provider 都以 `model.reasoning` 为发送门槛，false 时静默丢弃 | `openai-responses.js:152`、`openai-completions.js:399-407`、`anthropic.js:413` |
| 3 | Max 档映射的 `xhigh` 只对 3 个硬编码 OpenAI 模型有效，其余 clamp 成 high | `pi-ai/dist/models.js:31-38`、`simple-options.js:12-14` |
| 4 | pi-ai 不支持 Qwen 的 `enable_thinking`（只认 `thinkingFormat: "openai" \| "zai"`） | `pi-ai/dist/types.d.ts:196` |
| 5 | `normalizeApi` 不认 `google-genai`（Gemini 直连今天必然抛 "No API provider registered"） | `direct-stream.ts:156-162` vs `pi-ai/dist/providers/register-builtins.js:37-41` |
| 6 | `bridge.ts:706` 构造 direct stream 时未传 `apiFormat`，与其它调用点不一致 | `bridge.ts:706` vs `bridge.ts:2885` / `bridge-instance-factory.ts:249` |

**实测抓包**（本地假端点，模型对象与 Lumii 实际构造一致；档位/开关任意组合请求体完全相同）：

| 场景 | 开思考(high) | 换 max | 关思考 |
| --- | --- | --- | --- |
| 现状（responses，`model.reasoning=false`） | 无字段 | 无字段 | 无字段 |
| 若补 `model.reasoning=true`（responses） | `reasoning:{effort:"high",summary:"auto"}` | 同 high（xhigh 被夹） | 无字段 |
| 若补 `model.reasoning=true`（completions） | `reasoning_effort:"high"` | 同 high | 无字段 |

**连带风险（方案必须一并处理）**

- `openai-completions.js:478` `useDeveloperRole = model.reasoning && compat.supportsDeveloperRole`：合成 reasoning 会把 system 提示词改成 `developer` 角色，自建中转可能 400；responses 路径（`openai-responses-shared.js:46-53`）**无 compat 逃生口**，只能改写 payload。
- `simple-options.js:26-29` 的预算挤压 + `google.js` 路径不看 `model.maxTokens`：直接放大 thinkingBudgets 无效。
- 用户实际端点：`https://kms.sczxsc.cn:35019` + `Qwen3.8-Flash-Next`（apiFormat=completions），认哪种思考参数未知，必须先实测。

## 二、Global Constraints

- 思考参数格式在自建中转上必须 **opt-in**：未知模型默认不支持思考，避免发送未知字段导致 400。
- 关闭思考要**显式**（Qwen/z.ai 系服务端默认开思考），不能只靠「不发字段」。
- 不把「Max ≡ High」写进 systemPrompt（会打破 4 个快照测试），只做 UI 提示。
- 三处 `LocalProviderConfigView` / `ProviderType` 镜像（main / preload / renderer）必须同批改完。

## 三、片 1：思考能力贯通

### Task 0: 实测中转认哪种思考参数（决定默认值）✅

对 `https://kms.sczxsc.cn:35019` + `Qwen3.8-Flash-Next` 实测（思考走 `delta.reasoning`，pi-ai 能解析）：

| 请求体 | 结果 |
| --- | --- |
| 不发思考参数 | 思考 4362 字符 → **服务端默认开思考** |
| `enable_thinking:false` | 3611 字符 → **被忽略** |
| **`chat_template_kwargs:{enable_thinking:false}`** | **思考 0 字符 → 真正的关闭开关** |
| `thinking:{type:'disabled'}` | 无效 |
| `reasoning_effort` 档位 | 只认 `low`/`medium`/`xhigh`，**发 `high` 直接 HTTP 400** |

结论：该中转属于 vLLM/SGLang 系，注入形态定为 `chat_template_kwargs`，且注入时必须
`delete reasoning_effort`（pi-ai 默认发的 `high` 会被端点拒绝）。

## 六、风险与不做

- **不破快照**：Max≡High 提示只进 UI 的 title，不进 systemPrompt。
- **渠道会话 / 心跳 / cron 跟随对话页开关**（2026-09-20 追加）：`BridgeSessionThinkingPrefs`
  增加全局默认（对话页开关），未显式设置过偏好的会话回落到它；主进程把全局默认落盘到
  `config/session-thinking.json`，重启后开机心跳等新实例仍继承。新增 IPC
  `session:thinkingPrefs:setGlobal`，由 ChatPage（开关/档位变更与会话同步）与宠物窗推送。
- **已知限制**：OpenAI 兼容端点无法表达「显式关闭 + 指定档位」（pi-ai 只认档位语义），
  故 qwen 格式下 High/Max 都按端点默认档位（该中转是 xhigh）执行；要高精度分档需按端点的
  档位表逐个映射（本次未做，避免给不认 `reasoning_effort` 的端点发未知参数导致 400）。
