## 二、关键设计决策

### 2.1 用户目录位置

`app.getPath('userData')/pet-models/`（Windows 为 `%APPDATA%/Lumii/pet-models`）。

不进 `resources/`（打包后只读）、不进工作区（用户工作区可被 Agent 改写，宠物目录必须在 Agent 写权限之外——设计 §5.1 安全边界的直接推论）。

### 2.2 用户模型资源走自定义协议，不用 file://

内置模型沿用现有解析（dev 走 `/pet-models/` Vite 中间件，打包走 `file://`），**一行不改**，避免回归风险。

用户模型则必须解决一个现有机制覆盖不到的问题：**dev 模式下宠物窗口从 `http://127.0.0.1:5174` 加载，HTTP 页面无法读取 `file://` 子资源**，而 Vite 中间件只映射到 `apps/windows/resources/`，够不到 userData。

三条候选：

| 方案 | 否决理由 |
| --- | --- |
| 扩展 Vite 中间件加 `/pet-user-models/` 前缀 | 需在 vite config 里复算 `app.getPath('userData')`，而它依赖 `app.getName()`——dev 与打包取值不同，是会在改名/换端口时静默失效的隐式耦合；且要维护 dev/打包两条分支 |
| 读文件转 base64 data URL | 图集动辄数百 KB～MB，每次加载都要过一次 IPC |
| **自定义协议 `lumii-pet://`** | ✅ 选中 |

`lumii-pet://model/<相对路径>` → 解析到用户宠物目录下的同名相对路径。

选它的三个理由：

1. **无 dev/打包分支**——同一套 URL 在两种模式下都成立，消除一类只在打包后暴露的故障。
2. **路径语义干净**——注册 `standard: true` 后 `new URL('atlas.png', 'lumii-pet://model/mycat/manifest.json')` 得到 `lumii-pet://model/mycat/atlas.png`，清单里的**相对引用**直接可用。而 `lumii-local://media/?path=` 那种查询串形式做不到相对解析，会逼着渲染层自己拼绝对路径。
3. **收敛读取面**——协议处理器只认用户宠物目录这一个根，路径穿越在协议层被挡死，比在每个调用点各自校验更可靠。

复用 `local-media-protocol.ts` 已验证的写法（`registerSchemesAsPrivileged` + `protocol.handle` + `net.fetch(file://)`）。

**只对 `source: 'user'` 的模型生效**，内置模型仍走原路径。

### 2.3 合并规则

```
内置 registry.json ──┐
                     ├─→ mergePetRegistries() ─→ 合并列表（带 source 标记）
用户 registry.json ──┘
```

- 同 `id` 用户版本覆盖内置；被覆盖的内置项在合并列表里**打上 `shadowedBuiltin: true`**（供后续「恢复内置版本」用）
- 顺序：内置顺序在前（被覆盖的**原位置**替换），用户新增的追加在后——保证用户加宠物不会让既有列表跳位
- `defaultModelId` 三级回退：用户声明且存在 → 内置声明且存在 → 列表首项
- **单条坏数据只跳过该条**，记诊断，不拖垮整张表（稳定性要求：一份手写错的注册表不能让宠物模式整体失效）

不在合并层做 URL 解析——各来源的 base 目录不同，解析必须在客户端层按 `source` 分别处理。合并层保持纯函数、零依赖、可单测。

### 2.4 两段式安装

设计 §5.1 的安全边界是「Agent 只能写 `outputs/`，由固定 `install` 子命令校验后搬运」。落成两个子命令：

```
pet-asset validate <目录>            # 只读：报全部问题，不写任何东西
pet-asset install  <目录> [--id x]   # 先跑 validate，通过才搬；不通过一个字节都不写
```

**「校验不通过 → 装不上，但绝不影响渲染稳定性」靠三步保证**：

1. `validate` 与运行时共用 `pet-core` 的**同一份** `validateSpriteManifest`（安全边界单一落点）
2. 搬运先写 `<id>.installing/` 临时目录，**全部写完**再 `rename` 成正式目录——扫描永远看不到半成品
3. 安装前若目标已存在，**备份为 `<id>.bak/`**，失败则回滚

`validate` 的检查项：

| 检查 | 依据 |
| --- | --- |
| 清单 schema + 未知字段拒绝 + `params` 仅数值 | `validateSpriteManifest` |
| 图集文件、图集索引文件真实存在 | 同上（`assets` 选项） |
| 帧/部件/口型引用都能在图集里找到 | 同上（`atlasFrames` 选项） |
| **图集是否会「未抠底」** | 全不透明且无 alpha ⇒ 拒绝安装并提示先跑 `cutout` |

最后一条是设计 §7 风险表「抠底需背景色远离角色色 → 在安装校验阶段做前置检查」的落点。

> **实现修正（记于实施时）**：原设计写「校验背景色与描边色的距离」。实测下来这条**无法在 `validate` 阶段完成**——到了安装这一步图上已经没有背景了（要么已抠底，要么是待抠的原始图）。真正能拿到「描边距底色有多远」这个数的时机是 **`cutout` 过程本身**，P-1 的 `tuneSolid()` 已经会通过「占比突增」检出穿透。所以拆成两半：`cutout` 负责判「抠得动吗」（检不出穿透才放行），`validate` 负责判「抠过了吗」（无 alpha 就不给装）。两段接起来，效果等同原设计意图，且每一段都在信息真正存在的地方做判断。

## 四、验收

**单测**

- `pet-registry.test.ts`：同 id 覆盖、顺序稳定、脏数据隔离、`defaultModelId` 三级回退、非对象输入不抛
- `atlas-index.test.ts`：两种图集格式、坏 JSON、帧名为空
- `pet-package.test.ts`：缺文件拒绝、帧引用不存在拒绝、已抠底放行、未抠底拒绝、安装计划路径不越界
- `pet-model-resolver.test.ts`：两段式扫描与合并（mock 两个目录）

**命令**

```bash
pnpm --filter @mtbot/pet-core test
cd apps/windows && npx tsc --noEmit && pnpm test:all
```

**手测**（需真实客户端）

1. 手工造一个用户宠物放进 `%APPDATA%/Lumii/pet-models/<id>/` + 写 `registry.json` → 设置页能列出来
2. 用内置 id 写一份 → 列表里只剩一条，来源标记为「用户」
3. 放一份非法清单 → 列表里**没有它**，其余模型不受影响，宠物模式正常进
4. `pet-asset install` 一个未抠底的包 → 拒绝，用户目录无新增
5. 安装过程中目录被占用 → 回滚，用户目录回到安装前状态
