## 二、关键设计决策

### 2.1 工具链在运行时怎么跑：走控制口，不走 CLI

P0-a 把 `pet-asset` 定位为「构建期与 Agent 侧使用，不进运行时」。P1 要兑现「Agent 侧」，
于是必须回答：**打包后的应用里，技能脚本怎么调用工具链？**

技能的可执行入口是技能目录下的 `run.ts`（`apps/windows/src/main/index.ts:591`
的 `EXECUTABLE_ENTRIES`），宿主经 `TypeScriptRunner` 用子进程执行它。所以三条候选：

| 方案 | 否决理由 |
| --- | --- |
| 把 `dist/cli.mjs` 作为 extraResources 打进安装包，技能起子进程调它 | `sharp` 是原生模块，且 `asarUnpack` 只把它解到 `app.asar.unpacked/`——从包外的脚本 `require('sharp')` 要跨 asar 解析，dev 能跑、打包后大概率 `MODULE_NOT_FOUND`。**是一类只在打包后才暴露的故障**，P0-a 已经在这上面栽过一次（主进程外部化 pet-core） |
| 把工具链逻辑复制进技能脚本 | 与 P0-a 的验证算法重复实现，两边会漂移；且技能目录是 Agent 可写区，把安全边界（校验后搬运）放进可写区等于没有边界 |
| **控制口加固定端点，主进程用已打包的 sharp + pet-core 执行** | ✅ 选中 |

控制口的三个性质正好对上设计 §5.1 的安全边界：

1. **端点固定**——Agent 只能选调哪个端点、传什么参数，不能注入代码
2. **执行在主进程**——`apps/windows` 已经把 `pet-core` 打进 bundle、`sharp` 在其依赖里，
   dev 与打包同一条路径，不存在打包后才暴露的解析问题
3. **有既有先例**——控制口已有 `/ipc/pet/listModels` 这类 B 层路由，认证与错误约定现成

**做法**：`apps/windows` 增加 `@mtbot/pet-asset` 依赖，把它的**程序化 API**
（`runValidate` / `runInstall` / `runCutout`，以及 P1-a 新增的
`runSlice` / `runAlign` / `runPack`）挂到控制口的 `/pet/asset/*` 上。
`pet-asset` 的 CLI 入口（`src/cli.ts`）保持不动，构建期照旧用。

**连带约束**：`@mtbot/pet-asset` 进了主进程依赖树，就得和 pet-core 一样进
`electron.vite.config.ts` 的 `exclude` 白名单（同一条 `.js`→`.ts` 理由）。

### 2.2 `slice` / `align` / `pack` 的职责边界

三者都是**纯几何运算**，不碰 AI、不做判断——判断留给技能。

| 子命令 | 输入 | 输出 | 关键点 |
| --- | --- | --- | --- |
| `slice` | 一张大图 + 网格行列数（或显式切分线） | 每格一张图 | 等分切分，不做内容识别。**直出图集的格子是模型自己排的**，行列数由调用方指定 |
| `align` | 一组图 + 锚点规则 | 对齐后的图 + 每张的偏移量 | 「按共同地线对齐」——像素角色靠每格各自的 alpha 包围盒底边对齐，实测 P-1 A3 误差 0px |
| `pack` | 一组图 | `atlas.png` + `atlas.json` | 输出格式与 P0-b 消费的一致（TexturePacker Hash），供渲染器直接读 |

**为什么 `align` 必要**：设计 §7 明确「AI 生成序列帧的角色一致性」是素材生产问题，
直出图集的一致性由单次生成保证，但**取景与尺度不统一**（§3.2 实测结论），
逐格抠底后必须按共同地线对齐，否则角色会逐帧上下跳。

### 2.3 `layers.scene` 的表达方式

清单里 `slots.scene` 是 `kind: "layered"` 的一个普通槽位——**渲染器不需要为它加任何代码**，
P0-b 的 `buildLayers` 已经按 `manifest.slots` 通用地建层。所以 P1-e 的工作量在：

- 生成侧：示范模型补一个 `scene` 槽与若干道具部件
- 语义侧：什么时候显示/隐藏道具（这是**编排**的事，不归渲染器）
- 文档侧：把「怎么加场景层」写进清单格式说明

**关键判断：不为 scene 加专门代码。** 如果发现需要加，说明槽位抽象漏了东西，
那要改的是抽象而不是打补丁。

## 四、验收

**单测**（pet-asset，纯函数）

- `slice`：等分切分的边界（不能整除时余数怎么分）、单格、行列数为 1
- `align`：地线对齐后各图底边一致、空图（全透明格）不参与、偏移量可复现
- `pack`：生成的 `atlas.json` 能被 `parseAtlasIndex` 读回、条目名与输入一致、矩形不越界

**守卫**：生成的图集必须能通过 `validateSpriteManifest` 的交叉校验——工具链产出的东西
必须过得了自己的校验。

**端到端**：`pet-creator` 技能从一句「做一只 X 宠物」走到可用的宠物（需真实生图，产生费用）

**手测**：控制坞不再显示「暂无动作」；场景层道具能显示

## 五、实施顺序

1. P1-a 三个子命令 + 单测（零依赖，可独立验证）

### 6.1 P1-a 已完成（2026-09-20）

| 文件 | 内容 |
| --- | --- |
| `packages/pet-asset/src/slice.ts` | `planGrid`：网格切分，除不尽时余数给最后一格（不丢边缘像素） |
| `packages/pet-asset/src/align.ts` | `computeAlignPlacements`：按 alpha 包围盒地线对齐，基准不取整 |
| `packages/pet-asset/src/pack.ts` | `planAtlasLayout` + `buildAtlasIndex`：统一格子排布，输出 TexturePacker Hash |
| `packages/pet-asset/src/toolchain.ts` | 三者的 I/O 层；`pack` 带**往返自检**（用运行时解析器读回自产出的 json） |

CLI 接上 `slice` / `align` / `pack` 三个子命令；`pet-asset` 测试 67 → **98**。

冒烟（拿 `demo_variant_a` 的 384×336 图集跑真实闭环）：
`slice --cols 8 --rows 6` → 48 格 48×56；`align` → 公共画布 48×56、48/48 参与基准；
`pack --align` → 392×336 图集、往返自检通过。

**单测抓到两个真 bug**（都不是笔误，是公式/语义错了）：

1. **落位公式把对齐抵消掉了**。原本写 `p.y = bbox.minY + dy`（`dy = baseY − bbox.maxY`），
   代入后恰好还原成原位置——四个帧会**原样叠放**，对齐完全没生效。
   正确形式是直接解「包围盒该落在画布上的哪」：`p.y = baseY − bbox.maxY`。
   这个 bug 单看代码很像对的，是「对齐后所有底边应相等」这条断言把它逼出来的。
2. **基准取整导致画布平白宽 1 像素**。基准中心原本先 `round` 再求差，
   一组中心同为 `x.5` 的帧会各自位移 1px。改成基准保留原始均值、只在求差时取整。
   冒烟时表现为公共画布 49 宽（格子只有 48），修完是 48。

另有一条是**我的测试期望写错**：`horizontal: 'none'` 下断言帧落位等于内容原坐标，
但落位是 0（不位移）、内容自然还在原处。改成断言「内容有没有被挪动」。

### 6.3 P1-d 已完成（2026-09-20）

**根因：「暂无动作」不是素材不够，是解析路径写死成了 Live2D。**

`resolveModelMotionActions` 的自动解析那条分支只读 `model3.json` 的
`FileReferences.Motions`。sprite 清单里没有这个字段，于是**恒定解析出空动作列表**——
控制坞只能显示「暂无动作」。作者即使在清单里写了 `Wave`/`Nod` 也照样看不到。

修法：按 `rendererType` 分来源。Live2D 走原路径，sprite 读清单的 `animations`
并按声明顺序聚合组（组顺序即标签顺序，编号稳定）。待机/说话组的排除规则两者共用。

**素材侧同步补齐**（此前示范模型只有 Idle/Talk/Jump 三个组、4 个表情）：

| 项 | 之前 | 现在 |
| --- | --- | --- |
| 表情（眼睛层） | 4 款 | **12 款**（对齐设计 §4.2 的目标表情数） |
| 动作组 | Idle / Talk / Jump | 再加 **Wave / Nod / Shake**（单次型，播完按 `next` 回 Idle） |
| 身体姿态参数 | 只有 `lift` | 加 `pawLift`（抬爪挥手）与 `lean`（左右摇） |
| 单模型帧数 | 11 | 25 |

**对比表口径也一并修正**：生成器的外推表里表情数原本写死 4，而 `EYES` 扩到 12 之后
「演示帧数」与真实产出对不上。改成从 `EYES.length` 等常量算，并去掉「外推到 12 表情」那列
——**演示集现在本身就是 12 表情规模**，不再需要外推：

| 方案 | 帧数 | 公式 |
| --- | --- | --- |
| A 整体帧 | **144** | 身体帧 × 表情 × 口型 |
| B 分层差分 | 19 | 身体 + 表情 + 口型 |
| C 混合 | 19 | 身体帧 + 表情 + 口型 |

144 贴着 150 的阈值（设计 §8 场景 B 的淘汰线）——而这是**只有 3 个身体帧**的情况，
动作一多就越界。这条把「A 不可用于量产」从估算变成了实测。

**测试**：`pet-model-resolver.test.ts` 16 → 24，新增 8 例覆盖 sprite 解析、
待机/说话组排除、同组多 index、标签编号稳定性、精选优先、Live2D 不回归、
文件缺失与 `animations` 非数组的容错。

（该文件的既有注释写着「文件 IO 留给手测」，因为 fs mock 解析不稳；这次把
`getAppPath()` 改成可变的 `vi.hoisted` 状态并指向真实临时目录，就能测真实读盘路径了——
不需要 mock fs 本身。）

### 6.4 P1-e 已完成（2026-09-20）

**结论先写：渲染器一行都没改。** 计划 §2.3 判断 `slots.scene` 就是个普通的 layered 槽，
P0-b 的 `buildLayers` 已按 `manifest.slots` 通用建层——实测确实如此。
这条判断如果错了，会以「scene 需要特判」的形式暴露出来；没暴露，说明槽位抽象站得住。

改动全在生成侧与文档侧：

| 项 | 内容 |
| --- | --- |
| 道具几何 | `propShapes()`：ball / star / heart，外加 `prop_none`（空形状表 → 全透明图） |
| 槽位 | `demoSlots` 加 `scene: { kind:'layered', parts:{ prop: PROPS } }`，声明顺序在 `face` 之后 → 道具画在最上层 |
| 动画 | `PlayBall`（once → Idle）：同一段动作里球 → 星 → 收起，演示 scene 槽能被帧驱动 |
| 示范模型帧数 | 25 → 29（4 个道具） |

**「不显示道具」用全透明的空帧表达**，没加任何特判：对齐时全透明帧被排除出基准计算
（P1-a 已有的行为），打包时照常占一个格子。

**踩到并修掉的一个错**：给注册表批量加 `[motion:玩球]` 标签时，循环覆盖了**所有**模型，
包括三个 Live2D 模型——它们的清单里根本没有 `PlayBall` 组，加了会变成点了没反应的空标签。
改成只对 sprite 示范模型加，并核对了其余模型的动作标签数回到原值
（mao_pro 48 / xiaomai 20 / ug_official 0）。

文档侧：设计 §5.2 关键语义补第 7 条，写清 scene 槽的用法、图层次序的含义、
以及「空帧表达不显示」。

测试：素材守卫 18 → 24（+6 覆盖 scene 槽声明、道具与图集交叉校验、
帧驱动的道具切换、未声明帧的沿用语义）。
