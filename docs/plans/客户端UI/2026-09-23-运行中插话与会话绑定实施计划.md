# 运行中插话与会话绑定 实施计划

> 状态：**P0 + P1 已实施**（2026-09-23），单测与类型检查通过，待实机验收
> 触发：用户反馈「排队的消息切会话后跟着切换」+「长程任务插话要等很久」
> 后续：pi 依赖升级（切分支 → `@earendil-works/pi-agent-core` 0.87.1）见 §六

## 一、问题（现状核实）

三条「运行中投递」通路，两条存在会话绑定缺陷：

| 通路 | 存储 | 生效时机 | 落库/可见 |
| --- | --- | --- | --- |
| 等待队列 | `ChatInput` 局部 `useState<string[]>`（`ChatInput/index.tsx:205`） | 回合正常结束（`lastTurnEndAt` 边沿，`:461-467`）→ 走普通 `user:send` | 落库（普通用户消息） |
| 中途插话 steer | `steerValue` 局部 state（`:201`） | 每个工具执行完、下一轮 LLM 前（`agent-loop.js:262-272`），**跳过同批剩余工具** | **不落库、UI 不可见** |
| 打断 abort | — | 立即 | — |

**三个确定性缺陷**：

1. **队列跟着人走**：`queuedMessages` 绑在 ChatInput 组件（`<ChatInput>` 无 `key`、切会话不重挂载，`ChatPage.tsx:1823`），而输入草稿早已 per-session（`useSessionDrafts`）。切会话后队列不隔离；更糟的是切过去的会话 `lastTurnEndAt` 一变就触发 flush，**把 A 会话排队的消息发到 B 会话**。
2. **插话草稿同样串台**：`steerValue`/`steerSent`/`steerExpanded` 均为局部 state。
3. **主进程插话投错实例**：`handleUserSteer` 用 `getInstances().find(i => i.state === 'running')`（`user-commands.ts:275-276`），**忽略命令携带的 runId**；多会话并发时会插到别的会话。`handleUserAbort` 已有正确写法（`runIdToInstance` → `sessionToInstance`，`:317-321`）。

另有一处时序缺陷：`flushQueuedMessages` 用 `await Promise.resolve(onAbort?.())`（`ChatInput/index.tsx:449`），注释声称「先等打断完成」，实际未等待 —— `onAbort` 内部 await 未 settle 就继续发送。

## 二、已确认的产品决策

| 决策点 | 结论 |
| --- | --- |
| 切走会话后队列是否仍自动发送 | **后台照常自动发送**（不依赖前台会话） |
| 插话是否落库 | **落库 + 对话内显示带标记气泡** |
| 「问一句让 Agent 汇报」入口 | **不预置短语按钮**，在输入框 tips 中提示用法 |
| 本次范围 | P0 + P1（不做内核改造） |

## 三、方案

### P0-1 队列与插话草稿 per-session 化

- 队列数据从 `ChatInput` 局部 state 提升到 `agent-runtime-store` 的 `PerSessionState`：
  ```ts
  interface QueuedMessage { id: string; text: string; createdAt: number; modelId?: string }
  // PerSessionState 新增
  readonly queuedMessages: readonly QueuedMessage[]
  readonly steer: { draft: string; sent: boolean }
  ```
- **`modelId` 必带**：`handleUserSend` 里 `bridge.setSessionPreferredModel(sessionKey, command.modelId)`（`user-commands.ts:101`）在 `modelId` 为 `undefined` 时**会删除会话模型偏好**（`bridge-session-model-catalog.ts:261-264`）。队列自动发送不带 `modelId` 会把用户选的模型清掉，故入队时快照当时的 `selectedModelId`。
- 自动发送逻辑移入 `event-handler.ts` 的 `agent:turn:end` 分支（模块级、所有会话的事件都经过此处，与组件挂载无关）→ 满足「后台照常发送」。

### P0-2 steer 精确定位

- 渲染层 `steer(sessionKey, text)` 显式传会话（不再隐式读 `currentSessionKey`）。
- `UserSteerCommand` 增加 `sessionKey` 字段。
- `handleUserSteer` 改为 `runIdToInstance` → `sessionToInstance` 定位；定位失败记日志并**如实报错**，不再「猜一个 running 实例」。

### P1 插话落库与可见

- `handleUserSteer` 落库（`conversationRepo.saveMessage`，`contentJson` 加 `isSteer: true`）+ `forwardIpcEvent('conversation:message:new')` 广播（复用 `handleUserSend` 的成熟路径）。
- 渲染层 `RuntimeMessage` 增 `isSteer`，气泡加「插话」徽标。
- **恢复语义**：steer 消息随后会由 pi-agent 注入内存历史（`agent-loop.js:76-83`）；落库后 `restoreHistoryForInstance` 全量替换时内容一致，不产生重复。落库反而修复了现存的不一致（内存有、DB 没有 → `isInstanceMemoryRicherThanDb` 判据漂移）。

### P0-3 顺带修复

- `flushQueuedMessages` 的假等待：改为真正 `await onAbort()`。

## 四、验证

- 单测：store 队列操作（按会话隔离）、`handleUserSteer` 定位（新增用例，含多实例并发场景）、event-handler 自动发送分支。
- `pnpm --filter ./apps/windows test:all`（动了 `src/main/**` 必跑全量）。
- 实机：两个会话各跑一个回合，A 排队后切到 B，验证队列不串、B 不受影响；A 回合结束后台自动发送。

## 五、风险

- `agent:turn:end` 里发 `user:send` 需注意主进程会话锁（`SessionManager.promptLocks` + dispatcher 对 running 实例 `Promise.race([waitForIdle(), 2500ms])`）—— 回合刚结束时锁通常已释放。
- 落库的 steer 消息会进入后续会话恢复的内存历史（预期行为：插话本就该留在历史里）。

**改动要点**

- `agent-runtime-store.ts`：新增 `QueuedMessage`/`SteerState` 与会话级字段 `queuedMessages`/`steer`，以及 `makeQueuedMessage`/`enqueueQueuedMessage`/`removeQueuedMessageById`/`takeQueuedMessages`/`setSteerDraft`/`markSteerSent`/`resetSteer`。
- `event-handler.ts`：`agent:turn:end`（主 Agent 分支）末尾调 `flushQueuedMessages(sessionKey)` —— 后台会话的队列由此按自己的回合节拍发出。
- `ChatInput/index.tsx`：队列与插话草稿改读 store（按会话）；移除组件内的 `turnEndAt` 边沿自动发送（职责移到事件层）；`flushQueuedMessages` 的手动路径改走 `takeQueuedMessages` 原子取出；`await onAbort()` 修掉假等待。
- `user-commands.ts`：`handleUserSteer` 按 `runIdToInstance` → `sessionToInstance` 定位，定位不到只记日志不改投；新增 `persistSteerMessage` 落库 + 广播。
