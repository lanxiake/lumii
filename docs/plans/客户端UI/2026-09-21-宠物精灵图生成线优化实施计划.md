参考三处外部资料（2026-09-21 通读）：

| 来源 | 借什么 | 不借什么 |
| --- | --- | --- |
| [`302Sprite`](https://github.com/liangdabiao/302Sprite)（本机 `C:\myself\projects\my\open-source\302Sprite`） | 网格直出的**工艺**：一段连续动作的 N 个瞬间、首尾闭合、两段式提示词、「不许出现数字」、border 洪泛抠底 + 2px 腐蚀去残边、GIF/联系表审阅产物、批量并发与逐项 try/catch | 它的「等距 3/4 视角动作 RPG 精灵」是**反的**——桌宠要正视角固定机位；它只按 N 等分切图，**没有归一化/对齐/图层**；它的抠底容差是拍的（默认 45），没有本仓库实测出的「容差必须小于描边距底色」那条硬约束 |
| `~/.lumii/workspace/skills/精灵图动画/game-engine` | 只借一条格式契约 | 其余全是**消费**精灵图的 API，与生成工艺无关 |
| `~/.lumii/workspace/skills/精灵图动画/sprites-and-images` | 同上 | 同上 |

**那条格式契约**（Phaser 4）：`this.load.spritesheet(key, path, frameWidth, frameHeight)` —— **引擎侧只能表达等尺寸、等原点的格子，无法给单帧单独的原点或裁剪**。所以「共同画布 + 共同锚点、绝不逐帧紧裁」不是风格选择而是**约束**，它反过来决定了生成侧的网格必须是内容无关的等分格。Lumii 的 `manifest.canvas` + `manifest.anchor` 与 `planAtlasLayout` 的统一格子已经在遵守这条，本片不再动它，只是把它写成生成契约的一部分。

## 一、先修：生图模型选不了（阻塞项）

**症状**（用户报告）：客户端不支持配置多个生图模型，也不支持修改生图模型。

**根因是两处叠加，合起来表现为「点了没反应」**：

| # | 位置 | 问题 |
| --- | --- | --- |
| 1 | `apps/windows/src/main/provider-config.ts:347-356` | `allowedModelIds` 非空时原样保留，而 `modelId` 一旦不在其中就**被静默改回 `allowedModelIds[0]`**。盘上现状是 `modelId: "gpt-image-2"` + `allowedModelIds: ["gpt-image-2"]` |
| 2 | `.../SettingsPage/components/ModelConfigSection/index.tsx:461-481` | **image 槽只渲染一个单选 `Select`**；`allowedModelIds` 的编辑器（482-573 行）**只有 chat/vision 走得到** |

于是：选 `nano-banana-2` → `patchSlot` 只改 `modelId`，视图里 `allowedModelIds` 仍是 `["gpt-image-2"]` → 保存时被改回 → 界面弹回原值。「不支持改」与「不支持多选」是同一个洞的两个面。

**修法（两层都要）**

1. `normalizeSlotView`：用户显式给的 `modelId` **并入** allowlist，而不是被 allowlist 打回。
   现有不变量「`modelId` 必须落在 allowlist 内」用并集维持，用户意图不再无声消失。
   渲染层的勾选框自己已经维持了这个不变量（`nextIds.includes(cfg.modelId) ? … : nextIds[0]`），
   所以并集只在「界面没维持住」时生效——恰好就是 image 槽。
2. image 槽改用与 chat/vision 相同的模型编辑器（多选 + 逗号输入 + 「默认使用」）。
3. `model-pricing.ts` 补 `gpt-image-2.5` $0.06/次（已有的 `gpt-image-2` $0.04、`nano-banana-2` $0.12、
   `nano-banana-2-lite` $0.05 与用户给的一致）。

**为什么必须最先做**：`bridge-tool-registrar-integration.ts:804` 已经把 per-call `modelId` 原样透传
（注释写着「避免把自定义模型强行改写成 gpt-image-2」），`bridge-image-services.ts:203` 也认
`params.modelId ?? imageSlot.modelId`。**只要配置写得进去，Agent 就能在同一次运行里逐个模型试，不必来回改设置。**
不修这条，第五节的 A/B 根本开不了。

**边界**：`allowedModelIds` **不是**生图调用时的闸门（全仓库只在 `bridge.ts:2315` 的 chat 模型目录里被读），
所以修完不必再补一层校验。

## 二、生成契约：一批 = 一个动作组

**症状**：`real_dog` 的 `Idle = [body_00..03]` 就是「站立 / 呼吸 / **抬爪** / **低头**」四格，@fps 4
循环播出来是待机里抬爪低头。根子在实际用的提示词（`verify/pet-sprite/prompt-p1-e2e-gen.txt`）
把**四个不同动作**当成了四格。

> Idle 与 Talk 共用同一批帧**不是**缺陷——`demo_pixel_cat` 也这么干（差别只在 fps 与 `bob`）。
> 真正的缺陷是这四帧**不同源**。`demo_pixel_cat` 的每个动作有自己的帧：`wave_00/01`、`nod_00/01`、`shake_00/01`。

**契约改成：一批 = 一个动作组；格 = 这段动作的关键帧；读序即时间序；首尾闭合。**

### 2.1 把提示词抽进代码

新增 `packages/pet-asset/src/sheet-prompt.ts` 的 `buildSheetPrompt()`，SKILL.md **引用**它而不是复述散文
（可测、可版本化、改一处全生效）。302Sprite 的 `buildSpritePrompt()` / `buildRewriteSystemPrompt()`
就是函数——这是它能维护住的那一半原因。

技术段固定模板，补齐 302Sprite 有、Lumii 没有的三块：

| 段 | 内容 | 为什么 |
| --- | --- | --- |
| FORBIDDEN | 文字、**数字**、字母、标点、标签、水印、签名、UI、网格线、边框 | 「不许数字」尤其关键：提示词里一出现 `2×2`，模型很容易把数字画进格子。Lumii 现在只写了「不要文字、不要边框、不要阴影、不要地面」 |
| CAMERA | 正视角、正面朝向、全身可见、机位固定不俯不仰不旋转 | **不许**抄 302Sprite 的 isometric three-quarter view——那是 RPG 精灵的需求 |
| MOTION | 读序即时间序、每格是上一格的下一时刻、末格无缝接回首格、相邻差异小且均匀、整张图只表现「一个」动作 | 302Sprite 的 `ANIMATION FLOW` 段，Lumii 一个字都没有 |

创作段由 Agent 自己写（Lumii 的 Agent 就是 LLM，不必像 302Sprite 那样再调一次外部 LLM），
受两条约束：**不得用阿拉伯数字**、**不得提网格/像素/帧/格子/图片生成**。

### 2.2 底色不再写死 `#D9218F`

SKILL.md 有「底色必须与角色所有颜色保持距离」这条硬约束（实测描边距底色 191–201、安全余量 10），
**但提示词把洋红写死了**。奶油狗没事，粉紫色角色就是灾难。

改成：Agent 从角色配色推一个远离所有角色色的底色，出图后用 `estimateBackground` 回验
「底色 → 前景调色板最小距离 ≥ 安全余量」，不够就换色重出（判据 S8，见 §四）。

### 2.3 批次表重写

SKILL.md 第 3 步的批次表从「身体 / 表情 / 口型」三批改成「**一个动作一批**」。
动作组从 2 涨到 `demo_pixel_cat` 那个量级（Idle / Talk / Wave / Nod / Shake / Jump…）。
Idle 那批单独写清是「呼吸起伏、重心几乎不动」——它本来就该是几乎静止的微动。

## 三、表情层（方案 C）：差分取层

### 3.1 做法

**症状**：`real_dog` 连 `slots` 键都没有——端到端只跑了身体那一批。而 SKILL.md 给表情批的设计是
「**头部特写**，2×2 四格分别是睁眼/闭眼/笑眼/难过眼」。特写的取景、尺度与身体图集**完全不同源**，
贴回身体画布只能靠人估位置——这正是 P0-b 选型时说的「图层对齐风险的暴露面」。

**以身体批的基准帧为参考图，生成「除眼睛外完全一致」的同机位全身图集，然后帧间差分取层。**

- 差异区域就是眼睛——**不需要知道眼睛在哪、不需要估位置，自对齐**。
- 这里用上了本仓库实测过的那条结论：**参考图会压过文字提示**。它在链式生成里是缺陷
  （要求改姿势却被压住，与参考帧 IoU 93.1%），在这里恰好是**我们要的**——我们就是要它压住机位和取景。

**表情批不能套动作批的模板**：动作批要「每格是上一格的下一时刻」，表情批要的是
「每格除了那一个部位之外**逐像素一致**」——两者语义相反。所以 `buildSheetPrompt` 分了
`kind: 'motion' | 'expression'`，后者用 FACES 段并明写「这不是动作的先后顺序，身体姿势不要跟着变」。

### 3.2 实测（2026-09-21，狸花猫 · 2×2 眼神差分 · 带基准帧当参考图）

**参考图是有效的**：四格的全身包围盒在全分辨率下是 **378×516 / 377×517 / 378×516 / 377×516**，
彼此差不到 1 像素；S4 调色板重合 100%；S6 相邻差中位数只有 **5.4**（动作批是 26）
——正是「只有眼睛在变」。

**但差分一开始全军覆没，而失败信息是误导的。** 第一次跑四条判据全是「差异铺开 71~76% 画布」，
看着像「机位完全没对齐」。查下去发现两件事：

1. **平移补偿搜出来的最优偏移是 (0,0)** —— 根本不是错位。
2. 把变化像素做连通域分解：**959 个像素分成 275 个连通域，其中只有 2 个是有意义的**
   （288px 与 277px、各 21×20、位于 x=37 与 x=76 同一高度——就是两只眼睛，紧致度 0.69），
   其余 273 个都 ≤18px，合计 352px 全是噪点。

**根因**：两次**独立**的生成不可能逐像素一致——抗锯齿不可复现，描边周围必然散落几百个孤立的小差异点。
**这不是 bug，是扩散模型的性质**，只能靠后处理滤掉。

两条修复，各配一条回归防线：

| 修复 | 依据 | 回归防线 |
| --- | --- | --- |
| **连通域过滤**：丢掉面积小于画布 0.08% 的连通域 | 上面那组 275→2 的实测 | 单测「零星噪点被丢掉，成块的差异保留」 |
| **紧致度按连通域各算各的**，不拿「总像素 ÷ 整体包围盒」 | 两只眼睛天然分得开，中间的空隙把整体密度拉到 0.1 以下，一张干净的脸被判成「散落一圈」（实测两个 0.67 的连通域，整体算只有 0.47） | 单测「两只分开的眼睛仍判 usable」 |
| （附带）**平移补偿不降采样** | 降采样时采样网格一固定，候选平移一像素就把特征与采样行的相对位置整个换掉，实测选出了错误的 (-1,1) | 单测「整体错开几个像素时能搜回来，补偿后差异归零」 |

修完的结果（同四张图）：

| 帧 | 变化像素 | 连通域 | 紧致度 | 判定 |
| --- | --- | --- | --- | --- |
| `eye_open` 睁眼 | 19 px | 1/298 | 0.54 | ✓（基准帧本来就是睁眼，所以几乎无差异） |
| `eye_shut` 闭眼 | 565 px | 2/275 | 0.67 | ✓ |
| `eye_happy` 笑眼 | 591 px | 3/338 | 0.65 | ✓ |
| `eye_sad` 难过 | 105 px | 3/386 | 0.49 | ✓ |

**图层内容经 ASCII 复核**：`eye_shut` 抠出两个对称的闭合眼块；`eye_happy` 除眼睛外还多出嘴部一小块
（笑眼连带嘴型变了，被如实取到）。

**「没有任何差异」是合法结果**：表情批的第一格往往就是中性表情，与基准帧一致、抠出来全透明，
渲染时「什么都不画」正好等于「保持身体原本的脸」。流水线只在
「抠出来了但铺得太开」时才判失败。

### 3.3 端到端

两批动作 + 一批表情走完整流水线：**12 帧、`slots: ["face"]`、图集 1152×336**、Idle/Talk/Wave 三组。
客户端实测：`[buildLayers] 分层槽 1 个` → `[loadModel] 模型加载完成（12 张纹理）` →
`[setExpression] index=0 → eye_open`。

## 四、质量闸门：`sheetcheck` 进 pet-asset

**症状**：`cutout → slice → normalize → pack → validate → install` 里，`validate` 验的是**包**
（路径合法性、有没有真透明像素、清单交叉引用），**不验画**。而该验的那些
`verify/pet-sprite/check-sprite-sheet.mjs` 早就把 S1～S5 算出来了，只是**不在流水线里**——
出坏了要等用户装完才看见。

新增 `pet-asset sheetcheck` 子命令 + 控制口 op，在**出图之后、切图之前**跑：

| 判据 | 内容 | 来源 |
| --- | --- | --- |
| S1 角色不越格 | 每格角色包围盒完整落在格内 | 搬 `check-sprite-sheet.mjs` |
| S2 格内对中 | 包围盒中心与格中心的偏移 | 同上 |
| S4 跨格调色板重合 | 同一角色的核心判据 | 同上 |
| **S6 连续性**（新） | 相邻格差异小且均匀；首尾格差 ≈ 相邻差中位数 | §二要求了但没人验过 |
| **S7 对齐残差**（新） | 差分区域之外的残差占比 | §三的判据 |
| **S8 底色安全**（新） | 底色 → 前景调色板最小距离 ≥ 安全余量 | §2.2 的回验 |

S3（尺度离散度）**不列为判据**：实测 73.4% 离散度是**预期的**，尺度归一交给 `normalize`
（它用全体帧共同倍率，逐帧撑满会让「蹲下」的帧被放大到和「站直」一样高）。

有了它，「生图不可控」退化成「**每批出图立刻判，不合格只重出这一批**」，
返工被限制在 ~60s + 一次生图费。

## 五、A/B 实测（省钱版）

| 阶段 | 做什么 | 生图次数 | 花费 |
| --- | --- | --- | --- |
| 一 | **4 个模型**（`gpt-image-2` / `gpt-image-2.5` / `nano-banana-2` / `nano-banana-2-lite`）× 同一提示词 × 同一个动作（挥手）× 2×2 —— 量 S1/S2/S4/S6，并产出 GIF 供人眼复核 | 4 | ≈$0.27 |
| 二 | **胜出模型 × 三条跨批一致性路**：(a) 每批独立重述文字 (b) 每批带首批参考图 (c) 一次 4×4 大网格装 4 个动作 —— 复用 `check-reference-chain.mjs` 的 D1 调色板重合 / D2 体型 / D3 剪影 IoU | 2+2+1 | ≈$0.5 |

实测耗时基准（`~/.lumii/logs/app/mtbot-2026-09-20.log`）：`gpt-image-2` 单张 **54–90s**，
同刻可并发（19:11:09 三个任务同一秒提交）。

### 5.1 第一阶段实测结果（2026-09-21，一只狸花猫 · 挥手 · 2×2）

判据来自 `pet-asset sheetcheck`（§四）。四张图只改了 `modelId`，提示词逐字节相同。

| 模型 | 实际输出 | 单价 | S1 边界 | S4 一致性 | S6 连续性 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| `gpt-image-2` | **1254×1254** PNG | $0.04 | ✓ | 100% | ✓ 26.2 / 28.3 | ◐ 尺寸不听话 |
| `gpt-image-2.5` | **1254×1254**，另一批又变 **1024×1024** | $0.06 | ✓ | 100% | ✓ 12.8 / 26.3 | ✅ 综合最好 |
| `nano-banana-2` | 1024×1024 PNG | $0.12 | **✗** | 100% | ✓ 11.6 / 13.2 | ✗ **在格线上画了整条十字** |
| `nano-banana-2-lite` | 1024×1024 **JPEG** | $0.05 | ✓ | 100% | **✗ 29.9 / 10.9** | ◐ 有损底 + 首尾接不上 |

**五条结构性发现（比上面那张表更重要）**

1. **`gpt-image` 两个型号都不听 `width`/`height`**：要 1024 回 1254。而 **1254 不能被 4 整除**
   （1254 = 2×3×11×19）——4×4 网格会切出不等的格子。`gpt-image-2.5` 更麻烦：**它自己前后两次
   还不一样**（1254 与 1024）。所以切图前必须用**实际**尺寸算网格，别用请求的参数。这正是 S0 判据的由来。
2. **`nano-banana-2` 会在格线上画分隔线**：实测 x=510..513 与 y=510..513 各有 **1024 个非底色像素**
   ——一整条贯穿全图的十字。提示词的 FORBIDDEN 里明写了「网格线、边框、分隔线」，它没守。
   **这条把闸门的一条诊断缺陷逼了出来**：光数边界带里的非底色像素分不出「画了线」与「角色越界」，
   而处理方式完全不同。现在用「这条边是不是整条都被非底色占满」区分，两者报不同的原因。
3. **`nano-banana-2-lite` 回的是 JPEG**（有损）。抠底的前提是「底色是一整片平色」，
   有损压缩的振铃会让这个前提打折。同价位下这不是好选择。
4. **底色漂移依旧**：请求 `#00ffff`，四张的实测底色分别是 `#01fafd` / `#06f5fc` / `#04fcfd` / `#08f7fb`
   ——同色系但都不等值。再次确认「底色必须自动估计」，提示词里的 `#rrggbb` 只是个量级指示。
5. **S2（格内对中）四张全过**，偏移 0–3%，远好于阈值 12%。「同机位、角色位置不变」那段技术契约是有效的。

**⚠️ 一条必须说清的盲区**：S6 通过**只证明「帧之间有稳定变化且首尾闭合」**，
**证明不了「这段变化读起来是挥手」**。四张图都过了 S6，但把 `gpt-image-2.5` 那张降采样成
ASCII 看，四格是同一只猫在近乎相同的站姿上做微调——从字符画分辨不出动作语义。
要判「动作对不对」，要么人眼，要么**用视觉模型描述四格再核对动作名**
（Lumii 的 `vision` 槽现成可用）。这条列为下一步候选，不假装现在验过了。

## 六、三个形象（高清路线）

把内置示范的两个（`demo_pixel_cat` 像素猫、`demo_hires_girl` 高清少女）换成**三只角色**，
并把生成线跑一遍完整的（含表情层）。三只同时充当 §五 A/B 的测试对象。

**形象（用户 2026-09-21 指定）**：

| # | 形象 | 说明 |
| --- | --- | --- |
| 1 | **二次元少女** | 日式动画风 |
| 2 | **儿童向卡通猫咪** | 圆润、大眼、明快配色 |
| 3 | **3D 高达** | 三维渲染质感（成品仍是 2D 序列帧） |

**动作描述要求（用户 2026-09-21 补充）**：一组动作要有**清晰、连贯的经过描述**，
而不只是动作名；可以**尝试六格**（`cols: 3, rows: 2`）。
→ 已落进契约：`SheetBatchSpec.motion`（动作经过）进 MOTION 段，并要求「把这段经过按时间均分到 N 格」；
不给 `motion` 会出警告。格数由 `cols`/`rows` 任选，`buildSheetPlan` 不限定 2×2。

**走 2D 高清（144×168），不走像素风**，理由是 SKILL.md 自己写的那条结构性事实：
「无像素网格概念 → 像素风的整数网格对齐无法保证」。`demo_pixel_cat` 的 48×56 是**手绘的真像素网格**，
AI 出图降到 48×56 一定会糊。

### 6.1 实测（2026-09-21，`gpt-image-2.5`，九次出图）

每只三批：待机呼吸（2×2）+ 挥手（3×2，六格）+ 表情差分（2×2，带待机图集当参考图）。

| 角色 | id | 待机 | 挥手 | 表情 |

**机甲的表情档位不能照抄人脸**：它没有「闭眼/笑眼」，硬套的说法会让模型画出不存在的东西。
机甲的对应语义是眼部指示灯的明暗（`黄色常亮 / 灯光熄灭 / 明亮高光 / 转暗闪烁`），
**档位顺序与另两只对齐**（0 常规 / 1 熄灭 / 2 高兴 / 3 低落），这样注册表的 `emotionMap` 三只共用一份。

**三条实测出来的工程事实**（都不是提示词能解决的）：

| # | 现象 | 处理 |
| --- | --- | --- |
| 1 | **出图工具会重写文件名**：传 `pet-raw/girl-wave.png`，拿到的是 `outputs/20260921/pet-raw_girl-wave_png_20260921_<uuid8>.png`（非 `[\w一-鿿-]` 的字符全变 `_`，再拼日期与随机后缀）。**等在原路径上会一直等到超时** | 给扁平唯一名去等通配，落地后拷到稳定路径；参考图必须用**真实**的 workspace 相对路径 |

### 6.2 闸门被真图逼出的两个缺陷

这两条都是**合成夹具测不出来、真图一出就现形**的，也正是 §四那道闸门存在的意义。

**① S1 原来是「一个像素都不许有」，把好图判死了。**
`girl-idle` 那批四格各有 **9 个像素**落在边界带里，与青色底的最大通道差 **31–36**——肉眼完全看不出来，
是出图的柔和渐变与压缩残差。旧判据 `bleed === 0` 直接判 `unusable`，`run.ts` 会拒绝构建整批。

绝对像素数在「真噪声」与「真越界」之间没有分辨力（前者散落几粒，后者是「几十像素宽 × 3 行」的数百像素），
所以改判**比例**：`MAX_BLEED_RATIO = 0.005`，是实测噪声（0.12%）的四倍余量，又比真实越界低一个量级。
**画了分隔线仍按硬失败**——那条由 `drewLine`（要求某条最外沿覆盖率 ≥ 90%）单独判，不会被这条放过去。

**② 包围盒被一粒 alpha 21 的角像素从 188 撑到 408。**
同一批图，**四格的角上**各有一粒 alpha 21/23/25 的像素（背景渐变最远处）。它们不透明到足以被
`alphaBBox` 默认的 `thr = 16` 算进去，于是包围盒横跨整格。

后果不是「报错」而是「静默偏移」：包围盒是 `normalize` 逐帧落位的输入（按包围盒中心对齐），
一格的中心算成 423 而格中心是 313.5 —— 那一帧的角色会被平移 110 像素。
**同一个问题代码里早就有答案**：`computeNormalize` 的 `bboxThreshold` 默认就是 128，
理由写在它的注释里（「角色的『边界』应该是肉眼可见的地方，不是 alpha=17 的雾」）。
`sheetcheck` 与 `cutout` 命令没跟上，各用各的。现在把 `alphaBBox` 的默认值对齐到 128。

### 6.3 表情层：三只里成了一只

| 角色 | 表情层 | 真帧差分（`changed` / 包围盒 / 紧致度） |
| --- | --- | --- |
| 樱桃（少女） | ✅ | 四格全过 |
| 团子（猫） | ✗ | `eye_open` 47px/5%/0.42 ✓、`eye_shut` 763px/40%/0.50 ✓、`eye_happy` 1150px/**60%**/0.41 ✗、`eye_sad` 749px/**60%**/0.29 ✗ |
| 钢羽（机甲） | ✗ | `eye_happy` 958px/46%/0.31 ✓、`eye_sad` 824px/37%/0.35 ✓、`eye_open` 1258px/59%/**0.30** ✗、`eye_shut` 1075px/41%/**0.30** ✗ |

**卡住的是「残差噪点圈」，不是机位**：`rawChanged` 差不多是 `changed` 的两倍（如 2576 → 1258），
说明一半的差异像素是**被连通域过滤掉的零星噪点**——描边周围的抗锯齿残差；活下来的那些散布在角色
周围，把包围盒撑到 40–60%，而实际覆盖只有角色的 6–9%。密度正好压在 0.30 这条线上（0.29–0.31）。

**没有再次调这条线**。折过一次：曾经按「表情帧比基准帧大 3–4%」去加缩放补偿，后来发现那个「3–4%」
是 **±2px 扩张**的产物（124→128、156→160 正好 +4），真帧的包围盒是 123–124×156–158，与基准帧
只差一个像素。于是撤掉了那个改动——**判据不该按假设改，只该按实测改**。

现在手上有 6 个真实样本（少女 4 + 猫 4 + 机甲 4，其中 5 个过线、7 个不过），比当初定阈值时的
一个样本多得多。**重新标定需要先有 ground truth**：把过线与不过线的层都贴到身体上看一眼，
判断「包围盒 60% 但只覆盖 8%」的那一层到底会不会看出问题。这一步没做，所以阈值保持原样。

**顺带修的一个真缺陷**：`diffLayer` 原来是**原地覆盖**归一化后的帧。一次失败的差分会把
推导它的原始帧毁掉——「重出这一批」于是变成重出所有批次，调试时量到的也不再是
「表情帧与基准帧差多少」而是「图层与基准帧差多少」（实测被这个坑骗过两轮，
两次报出的 13640 / 13520 都是假的）。现在先写到 `diffed-N/`，判定通过才挪回去。
