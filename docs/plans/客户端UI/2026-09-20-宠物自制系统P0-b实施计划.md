## 二、关键设计决策

### 2.1 纯函数进 pet-core，PIXI 胶水留在客户端

设计 §6 原表把 `sprite-manifest.ts` 放在渲染层，P0-a 已把**清单类型与校验**移进 pet-core。
本轮延续这条线：把**运行时解析**（帧增量归一、口型档位映射、多边形命中）也放 pet-core——
它们是纯逻辑、零依赖，且在 pet-core 里能脱离 WebGL 单测。客户端只剩"把解析结果画出来"。

| 模块 | 落点 | 为什么 |
| --- | --- | --- |
| 帧增量归一 / 槽位状态机 / 口型档位 / hitArea 多边形 | `packages/pet-core/src/render/sprite-runtime.ts` | 纯逻辑，可单测；设计 §9.1 的「清单解析与归一」「口型档位映射」两条测点正落在这里 |
| PIXI 纹理、AnimatedSprite、ticker、缩放吸附 | `apps/windows/.../sprite/SpritePetRenderer.ts` | 依赖 DOM/WebGL，无法共享 |

### 2.2 帧增量语义在**加载期**解析，运行时只套用

清单里每帧只声明变化的槽位（设计 §5.2 关键语义 1）。若运行时每帧去 carry-forward，
就把可以一次算完的事摊到了 60fps 的热路径上。

做法：`loadModel` 时把每个动画解析成**全量帧快照**（`ResolvedFrame[]`），运行时直接套用。
解析规则：

- 动画内第 0 帧：未声明的槽位取**模型默认态**（各槽位的首个部件 / 首个 base 帧）
- 第 i 帧：未声明的槽位**沿用第 i−1 帧**
- 动画之间不互相继承——否则"当前正在播哪个动作"会隐式影响下一个动作的首帧，
  产生难复现的串味

### 2.3 程序化原语的作用面

`procedural-motion.ts` 的五个原语是纯函数 `f(t, params)`。SpritePetRenderer 每 tick 求值：

| 原语 | 作用 |
| --- | --- |
| `bob` | 根容器 y 偏移 |
| `breathe` | 根容器缩放（绕锚点） |
| `sway` | 根容器旋转 |
| `nod` | 根容器旋转（与 sway 叠加） |
| `blink` | 切换 face 槽 eyes 类部件的帧（不改 transform） |

`BlinkScheduler` 需要可重放的确定性——用 `procedural-motion.ts` 已有的哈希式间隔，不用 `Math.random()`。

### 2.4 缩放的整数吸附（像素风）

像素素材用线性采样会糊。两条一起做：

1. `BaseTexture.scaleMode = SCALE_MODES.NEAREST` + `roundPixels`（`pixelArt: true` 时）
2. **缩放取整**：`pixelArt` 模型的最终缩放吸附到 ≥1 的整数倍

第 2 条只对 `pixelArt` 生效；2D 高清模型保持连续缩放。整数倍是像素风的常规做法，
且"糊没糊"可以量化验证（邻近像素方差），不是主观判断。

### 2.5 PetCanvas 的分发方式

难点：`PetCanvas` 现有的注释写明「PIXI Application 绑定在 canvas 的 WebGL context 上，
绝不能随 modelId 变化而 destroy（会损坏 React 复用的 canvas）」。而**切换渲染后端类型**
必然要销毁重建——在同一个 canvas 元素上重建 WebGL context 正是那条注释警告的事。

做法：**让 canvas 元素本身随后端类型换新**。

```tsx
<canvas key={rendererType} ... />
```

React 见到 key 变化会创建新的 DOM 元素，旧元素整体丢弃，WebGL context 随之消亡，
不存在"在坏掉的 context 上重建"。而同类型（live2d→live2d）切换时 key 不变，现有行为一字不改。

代价：需要把模型配置的加载**提前到渲染器初始化之前**（当前是先建渲染器再取配置）。
配置加载是纯 IPC 读取，提前没有副作用。

### 2.6 三方案怎么造

三者在**同一份清单格式**里靠槽位声明区分（设计 §5.2 的"模式在槽位级选择"）。所以：

- 渲染器**只需要一个实现**，三方案是**三份清单 + 三套派生资源**
- 派生用脚本从同一套美术素材生成，保证美术内容一致、只变组织方式

这样对比才有意义：差异全部来自资源组织，不来自实现。

## 四、验收

**单测**（pet-core，脱离 PIXI）

- 帧增量归一：首帧取默认态、后续帧沿用、动画间不继承
- 口型档位：`setMouthOpen(0/0.25/0.5/1)` 的边界取档
- hitArea 多边形：内点命中、边界点、凹多边形、透明区不误命中、多区域重叠优先级
- 缩放吸附：`pixelArt` 取整、非像素模型连续

**场景 A｜抓取—拖拽—投掷—落地**（pet-lab，带物理积分）

- hitArea 跟帧命中：拖拽中切换动作后命中区域仍正确
- 动作中断语义：拖拽打断待机、落地播一次型动作后回待机
- 淘汰标准：某方案无法在拖拽中维持正确命中区域 → 该方案不可用于量产

**场景 B｜对话中表情 × 动作 × 口型同时叠加**

- 12 表情 × 4 口型 × 3 动作的组合能力与资源量
- 淘汰标准：无法在 < 150 帧/角色内表达 → 该方案不可用于量产

**端到端**：双示范模型在既有 `PetOrchestrator` 下跑通（口型、表情、动作、待机轮播、点击触发）

**产出**：三方案的帧数、图集体积、实现工时、观感评价 → 选型结论落盘

### 6.2 与设计文档不同的实现选择

| 设计 | 实现 | 理由 |
| --- | --- | --- |
| §4.3 用 PIXI `AnimatedSprite` | 自驱一个帧计数器 | `AnimatedSprite` 是「一个 sprite 一条帧序列」的模型。分层方案下一帧要同时决定**所有层**的部件，用它就得为每层各建一条序列并逐帧保持同步——等于把同一件事做两遍，还多出一堆「某层没跟上」的失败模式。pet-core 解析出的正是全量槽位快照，一个计数器套用整份快照天然对齐 |
| §5.2「sprite 以帧计数驱动」+ 降帧时同步 `animationSpeed` | 按 `deltaMS` 累加推进 | 设计要的是「降帧后动作速度不变」这个**结果**。按 tick 次数推进会与显示帧率耦合（`setFpsCap(15)` 时 8fps 的动画变慢动作），得靠同步 `animationSpeed` 去补；按真实时间累加则天然解耦，没有需要同步的东西 |
| §6 表把 `sprite-manifest.ts` 放渲染层 | 类型/校验/运行时解析全在 pet-core | P0-a 已开这个头（清单校验搬进 pet-core）。运行时解析同样是纯逻辑，放进去就能脱开 WebGL 单测——§9.1 的「清单解析与归一」「口型档位映射」两条测点正落在这里 |

### 6.3 三方案对比（演示数据）

同一套几何、同一份渲染器，**差异只来自资源组织**。像素图集 ×4 表情 ×4 口型 ×3 身体帧：

| 方案 | 演示帧数 | 图集字节 | 外推到 12 表情 | 公式 |
| --- | --- | --- | --- | --- |
| A 整体帧 | 48 | 13.6 KB | **144** | 表情 × 口型 × 身体帧 |
| B 分层差分 | 11 | 2.6 KB | 19 | 身体 + 表情 + 口型 |
| C 混合 | 11 | 2.6 KB | 19 | 身体帧 + 表情 + 口型 |

**结构性发现（比帧数更重要）：方案 A 表达不了运行时的口型切换。** 嘴被烘进整帧之后，
`setMouthOpen` 没有可切换的图层——要改口型只能换整张 base 帧，也就是要把「当前表情」
和「当前口型」耦合成一个帧索引。这不只是资源量问题，是**能力缺失**：
`PetLipSync` 每帧调一次 `setMouthOpen(0~1)`，方案 A 下每次调用都要重新算帧下标并可能
触发整帧切换，与「口型是高频小幅变化」的用法相冲。
这也是变体 A 的清单**不能声明 `mouthLevels`** 的原因（声明了会指向不存在的图集条目，
校验直接拦下——这条是生成脚本先写错、被 P0-a 的工具链当场抓出来的）。

### 6.4 素材生成

两个示范模型**共用一份几何描述**，只换光栅化后端（设计 §7 的意图）：

| 模型 | 画布 | 图集 | 半透明像素占比 | 颜色数 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `demo_pixel_cat` | 48×56 | 2.5 KB | 0.0% | 7 | 手写扫描转换，硬边、固定调色板 |
| `demo_hires_girl` | 144×168 | 16 KB | 0.7% | 128 | 同一几何转 SVG，有抗锯齿与渐变 |

五份包全部通过 P0-a 的 `pet-asset validate`——两条流水线互为交叉验证。

### 6.5 实施中撞到的问题

**问题一：切换模型时初始化 effect 重跑，踩中「在坏掉的 WebGL context 上重建」**

现象：切到 sprite 模型后立刻 `[SpritePetRenderer] [init] WebGL context lost`，画面空白。

`PetCanvas` 里那段注释早就写着「PIXI Application 绑定在 canvas 的 WebGL context 上，
绝不能随 modelId 变化而 destroy」——但改造分发时我把 `config` 放进了初始化 effect 的依赖，
于是**每次切模型都会先 destroy 再在同一个 canvas 上重建**，正是注释警告的那件事。
更隐蔽的是它平时不发作：只有当新模型与旧模型**后端类型相同**时才走这条路，
而此前只有 Live2D 一种后端，`rendererType` 恒定，没人踩过。

**修法两条一起**：

1. 初始化 effect 的依赖收敛到**只有 `rendererType`**；`rendererType` 在配置到位前是 `null`
   （不能默认成 `'live2d'`，否则首个模型是 live2d 时类型从头到尾没变、effect 不跑、
   渲染器永远建不起来）
2. 父组件传来的回调（`onDegrade` / `onModelLoaded`）放进 **ref**，不参与依赖。
   父组件每次渲染都可能给出新的函数身份，留着当依赖就还是每次重跑

**问题二：生成脚本的目录名与清单 id 不一致**

生成脚本把目录写成 `demo-pixel-cat`（连字符），而注册表 `modelUrl` 用的是清单 id
`demo_pixel_cat/manifest.json`（下划线）。客户端只在运行时报「读取失败 HTTP 404」，
界面上就是一片空白。

根因是**内置资源绕过了工具链校验**：`pet-asset install` 强制「目录名 = id」并做清单↔图集
交叉校验，而内置资源是脚本直接写进 `resources/pet-models/` 的，没有任何人校验。

**修法**：生成脚本的目录名改用 id；另加两个守卫测试，让这类问题在 CI 上就红：
- `apps/windows/src/main/pet/pet-registry-assets.test.ts`（21 例）：
  注册表引用的每个文件必须真实存在、资源目录名必须等于 id、rendererType 取值合法
- `apps/windows/src/renderer/pet/renderer/sprite/sprite-assets.test.ts`（17 例）：
  随包清单必须通过校验与图集交叉校验、能被运行时解析出 Idle/Talk、
  变体 A 不得声明 `mouthLevels`、A 与 C 的帧数比值符合组合爆炸预期

第二个守卫文件里还加了一条「测试前置」用例：路径写错时发现函数会返回空数组，
于是一堆用例「通过」但什么都没测——这条先兜住目录必须在且必须扫到东西。
