## 三、与设计文档的偏离与补充

**逐条都要看**——第 2 步接线时按本文，不按设计文档的原始措辞。

| # | 设计文档 | 实现 | 为什么 |
| --- | --- | --- | --- |
| 1 | `reduceNotices(prev, event, now)` | `reduceNotices(prev, event, ctx)`，`ctx = { now, windowFocused? }` | `turn:end` 的"用户发起后走开"、`file-changes` 的"主窗失焦"两条规则要看焦点，把 `now` 并入 `ctx` 比再加一个参数干净 |
| 2 | 只写了"超时后转为已销账"的判据，没给入口 | 新增 **`tickNotices(notices, now)`** | 纯函数没有定时器，超时与 TTL 必须有时间驱动入口（与 `tickAgentActivity` 同一模式）。宿主在渲染循环或定时器里喂 `now` |
| 3 | 幂等靠宿主维护 `announcedIds` 集合（容量 200 FIFO） | **列表本身**承担幂等：同 id 已在列表里（含已销账）就不再生第二条 | `reduceNotices` 拿不到那个集合；而条目在 `RESOLVED_KEEP_MS` 内都留着，重放窗口只有秒级，够用。宿主侧的 `announcedIds` 仍然要——它管的是**气泡**幂等（`pickNoticeForBubble` 的 budget），两者不是一回事 |
| 4 | 销账"按 `requestId`" | 销账同时**限定类型**（`permission` 的解除事件不销 `ask-user` 的账） | "回答了问题"不可能产生审批结果；按类型各销各的，比单纯按 id 匹配更不容易误伤 |
| 5 | 只说"销账 ≠ 删除"，没说留多久 | 新增 `RESOLVED_KEEP_MS = 5min` | 够控制坞把"已超时被拒"展示给用户，又不至于让历史条目吃满容量 |
| 6 | 未提控制坞的取数 | 新增 `pendingNotices(notices)` | 控制坞要"列出全部待办"，排序规则（action 在前、组内按时间）与气泡不同，收在 pet-core 里可单测 |
| 7 | `agent:tool:end` 的 `isError` → ambient | 同左，但**先于** `task_complete` 判定 | 失败的 `task_complete` 不是"做完了" |

### 3.1 三个需要留意的实现细节

- **`task_complete` 缺 `summary` 不算残缺通知**。摘要只影响文案与幂等键，不影响能不能处置
  （跳会话只需要 `sessionKey`），所以用兜底文案 `TASK_COMPLETE_FALLBACK_TEXT` + 轮次当键。
  **只有缺 `sessionKey` / 缺 `requestId` 才返回 `null`**——那两种是真的点了也没用。
- **`toolLabel()` 与 `ConfirmDialog` 的 `toolTitle()` 是同一张表的两个副本**。pet-core 不能反向
  依赖 app 层，只能复制。改一处要改两处；将来可考虑把那张表收敛到 pet-core。
- **`agent:error` 可重试时不给 `deepLink`**——它不进通道，也就没人会去点。

## 六、已知缺口

1. **`ask-user` 回答后没有销账事件。** 响应走的是命令方向（`user:ask-user:respond`），
   主进程**没有回广播**。所以用户回答了问题，宠物侧那条 `action` 销不掉账，只能等
   `RESOLVED_KEEP_MS` 或容量淘汰。`NoticeOutcome` 里预留了 `answered`，等主进程补事件时接上——
   这与 §7.1 修的"审批解除事件零产出"是同一类缺口，修法方向一致（在出口汇合点广播）。
2. **`agent:permission:cancelled`（非 `:prompt:` 变体）不存在**，销账表里没有它。
   真出现时补一行即可。

### 7.2 三个必须记下的实现决策

1. **通知优先、状态句补位，不是二选一。** 通知是**事件驱动**（错过有代价），
   `pickAgentAnnouncement` 的"还在忙…"是**时间驱动**（忙满 60s）——判据不重叠，
   完全交给通知会丢掉后者。两者共用同一份"同文案"节流表。
2. **气泡可点走 `pet-dock` 那套 hover 上报，不是 `pet-context-menu` 那套"挂着就报"。**
   `setIgnoreMouseEvents(false)` 是**整窗**开关：气泡一挂好几秒，那几秒里用户点桌面
   任何地方都会被吃掉。代价是点得特别快时可能落在窗口切回可点之前那一瞬（控制坞同样如此）。
3. **销账要主动撤气泡。** 只靠 TTL 的话，用户在主窗点了"允许"，宠物那句还挂 8 秒——
   看起来像没生效。实测 **250ms** 撤下。

### 7.4 实测抓到并修掉的一条文案缺陷

首跑的气泡是「**执行 Shell 命令：执行命令：node -e "conso…**」——工具中文名与
`description` 语义重叠，还把命令本身挤到截断之外。改成「**有 description 就用它**」，
脚本里加了回归哨兵（断言文案以 `执行命令` 开头）。

⚠️ **这条只有实机能发现**：三个字段各自都对，拼起来才冗余；而单测当时把
冗余的拼法当预期写了进去（"测试绿"在这里恰恰说明它没验到点子上）。

### 7.5 教训：脚本的"成功路径"也要清场

首跑时 `cleanup()` 只写在 `catch` 里，于是：**自动审批被留成关闭**（改了用户的设置）、
probe 会话留在列表里——而脚本打印的是"✓ 通过"。已修（正常路径末尾也调 `cleanup`），
并手工清掉了首跑留下的探针会话、把自动审批置回。

### 7.6 本步没做的两件

1. **主窗焦点广播**。`file-changes` 的"主窗失焦"与 `turn:end` 的"用户发起后走开"
   两条规则因此**不触发**。加它要动 shared / main / preload / renderer 四层，而
   `action` 档（核心价值）不依赖它、`report` 档少叫两次是**保守方向**。
   接口已留好（`PetOrchestrator.setMainWindowFocused`），S4 做系统通知时一并接。
2. **控制坞待办区只做到"接了"**：控制坞默认关着（产品取向），要展开得走右键菜单，

### 8.2 三个关键决策

1. **意图放 store 顶层，不放 props**。它是**跨会话的一次性 UI 意图**，不属于任何会话；
   而 props 要穿过 App → Router → ChatPage 三层。store 本来就是渲染层的共享状态，
   ChatPage 已经在读它。
2. **`focusNotice` 不并进 `focusSession`**。使用者不同：多会话清单只知道会话，
   通知是"有人把我叫过来办事"。分开也让"宠物只能走 `pet:*`"这条边界更清楚（设计 §5.2 的 ⚠️）。
3. **高亮是边沿触发（`false → true` 只跑一次动画），所以组件内部不自己熄**——
   但那个**意图**要清（命中 2.5s / 未命中 30s 兜底）。两者分开：一个是观感，一个是状态。
   未命中超时**安静放弃**：切会话是异步的，卡可能还没渲染出来，甚至已被用户在主窗处置——
   那不是错误，只是慢了一步（设计 §5.3）。

第 2 条是这次**特意加**的判据：`.click()` 是 DOM API，绕过 `setIgnoreMouseEvents`——
只验它的话，"可点"在真实鼠标下可能是假的（那条路要 mousemove 转发 → mouseenter → 上报 →
主进程开可点）。它拿的是主进程的**实际穿透状态**，不是 DOM 表象。

### 8.4 教训：React 的 `onMouseEnter` 是合成的

首跑这条判据是 `false`（`components: []`），看起来像功能坏了。原因是脚本派发的是原生
`mouseenter`——**React 的 `onMouseEnter` 在 root 上监听 `mouseout`/`mouseover` 自己配对**，
收不到原生 enter。改派 `mouseover`（`bubbles: true` + `relatedTarget: null`）后立刻为真。

⚠️ 判据为假时先怀疑**判据本身**：这次要是直接去"修"产品代码，会把一个对的实现改坏。

  （不是挪一百行能解决的）；而通知接线放在编排器里是符合现有架构的（编排器就是干这个的）。
  建议把「PetOrchestrator / PetModeShell / PetCanvas / SpritePetRenderer 的拆分」单开一片。

### 10.2 三个决策

1. **发通知的时机是"通知产生"，不是"气泡冒出来"**。免打扰时段气泡不冒（§6.3），
   但那条审批照样得叫你——它 5 分钟不响应就失败了。挂在气泡上会让"安静时段"变成"错过审批"。
2. **去重靠差集**（`alertedNoticeIdsRef`）：`noticeListener` 推的是全量列表、且每次变化
   （含 TTL 清理）都推。没有这道闸，一次审批能弹三遍（事件重放 / tick / 重绑各一次）。
3. **焦点广播用"先订阅、再补问、事件优先"**。补问是必须的（挂载时那次推送已经发过了，
   与 `onIdle` / `onPerch` 同一个坑）；顺序与 `onPerch` 那条**相反也没关系**——焦点是
   **幂等**的当前态，不像矩形那样"丢一次就永久失真"。唯一要处理的是竞态：补问的 Promise
   可能比订阅收到的事件晚 resolve，用一个 `gotEvent` 标志让事件优先，否则旧值会盖掉新值。

### 10.3 实测（`check-agent-notice.mjs`，10/10）

前 5 条是 S2 的，后 5 条是 S4 新增的：

```

   [DesktopNotify] title="Lumii · 需要你确认" body="执行命令：node -e "conso…" convId="65829c2b…"
✅ 通知带上了会话（点了会跳过去）
✅ 主窗焦点广播已启用（S4）
✅ 主窗焦点可补问（挂载补问那条路）   —— 返回 false
✅ （重跑 S2 的 5 条全绿 —— 改动没有回归）
```

判据取**主进程日志**而不是"屏幕上有没有弹窗"：通知是 OS 级的东西，截图判据既不稳
（系统可能折叠同等通知）又依赖人看；`[DesktopNotify]` 那行里 title / body / convId 三样都在，
足够判"发对了、且带对了会话"。

> 实测里 `getMainWindowFocus()` 返回 `false` —— 自动化跑的时候宠物窗覆盖全屏、主窗通常失焦。
> 这顺带说明了一件事：**"用户走开了"这条判据在测试环境里天然成立**，真要验它反而得先把主窗弄聚焦。

## 十二、用户实测反馈的两条修复（2026-09-23）

S1–S5 做完之后用户实测，报了两条。**两条都是真问题**，而且**第二条是 S6 那套 E2E 漏掉的**。

### 12.1 「审批、完成任务等弹窗都在主程序内部和系统通知，宠物头上没有，也无法点击跳转」

**根因：自动审批开着时，宠物侧的审批通知纯属误报。**

用户默认开着自动审批。于是每次 Agent 调受审工具：

```
14:38:13.638  agent:permission:request    ← 请求事件照发（发给了所有渲染层）
14:38:13.641  agent:permission:granted    ← 3 毫秒后就被自动放行
```

宠物侧收到 request 就产生一条 `action` 通知，但气泡要等下一个 16ms tick 才挑得出来——
**那时它已经被销账了**，所以宠物头上压根不会冒。**而 shell 那层的系统通知是"事件一到就发"**，
收不回来 → 用户看到「Lumii · 需要你确认」弹出来，**而那件事早被自动放行了**。

**修法**：`AgentPermissionRequestEvent` 加 `autoApproved?: boolean`（主进程在自动放行分支打上），
pet-core 的 `noticeFromEvent` 见到它就**不产生通知**。事件本身照发——审计与
"刚自动放行了什么"要靠它。

```
✅ 审批请求照发（审计要看）
✅ 不发系统通知
✅ 不冒气泡
✅ 主进程没弹桌面通知
```

### 12.2 「气泡、标识太小，不够醒目，并且不会跟着宠物移动」

两条都是**当初刻意做的取舍，实测证明取错了**：

| | 原设计 | 现在 |
| --- | --- | --- |
| 气泡字号 / 宽度 | 12px / 200px | **14px / 320px**（两百来像素放不下真实文案，是"信息被截没了"） |
| 位置 | 冒出来那一刻取一次 | **每帧跟随**（`getAnchor` + rAF，**直接写 DOM**，不走 state） |
| 头顶符号 | 22px / 字号 13 | **32px / 字号 19**，并修正为水平居中 |

当年不跟随的理由是"每帧 setState 会让整个 PetModeShell 重渲染"——**那个理由是对的，
结论是错的**：用 `style.left/top` 直接写 DOM 就没有这个代价。

### 12.3 ⚠️ 教训：E2E 必须覆盖**用户的真实设置**

`check-notice-e2e.mjs` 全程**关着**自动审批跑（因为要造出"挂住的审批"），
于是**从来没走过用户实际所在的那条路径**。S6 那一整轮"模拟真实使用"因此形同虚设——
它模拟的是一个**没有真实用户会处于**的状态。

修法已落到脚本里：`check-agent-notice.mjs` 补了一条"自动放行时应当静默"的判据。
**下次写端到端脚本前先问一句：用户的设置里，这一项默认是什么？**
