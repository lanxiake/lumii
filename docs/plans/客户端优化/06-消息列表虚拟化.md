## 一、根因（perf 日志实证）

渲染进程私存无界增长，涨的全是 Blink 原生内存，不是 JS 堆。同一渲染进程 pid 3092 存活 3 小时：

| 指标 | 16:54 首采 | 19:59 末采 | 增长 | 占 RSS 增长 |
|---|---|---|---|---|
| **RSS**（进程私存） | 394 MB | **1737 MB** | +1334 MB | 100% |
| **`blinkTotal`**（Blink 分配器预留总量） | 44 MB | **1020 MB** | +976 MB | **73%** |
| `blinkAllocated`（真正活跃分配） | 32 MB | 145 MB | +113 MB | — |
| `jsHeapUsed`（V8 堆） | 89 MB | 116 MB | +27 MB | 2% |
| DOM 节点（峰值 6619）/ 图片 1.7MB / canvas 5MB | — | — | 可忽略 | — |

三点结论：

1. **不是 V8 堆 OOM**。`jsHeapUsed` 峰值 146 MB，离 4GB 上限差两个数量级。`renderer-memory-probe.ts` 开头注释里"V8 堆撞 4GB 上限"是旧归因——当时日志只有 `rss` 一个读数，看不到 Blink 侧，缺口只能瞎猜。本次补上 `native` 口径后实测推翻。
2. **是 Blink 分配器碎片化**。`blinkTotal`（1 GB）远大于 `blinkAllocated`（145 MB），中间 **875 MB 是 Chromium PartitionAlloc 已经扩出去、但没在用的碎片**。典型成因：频繁增删大量 DOM 节点后各 bucket 扩张了就不归还系统。
3. **增长是阶梯式的，与"大内容加载"严格同步**，且每跳一次不再回落：

   | 时刻 | blinkTotal | 同一采样触发 |
   |---|---|---|
   | 16:54 | 44 MB | 冷启动 |
   | 17:05 | 319 MB | 第一波加载 |
   | 18:29 | 610 MB | `domNodes` 3053→5794，`fileEvents` 65→318，`contentChars` 375K→1335K |
   | 19:43 | **1120 MB（单跳 +431）** | `fileEvents` 332→1091，`contentChars` 1509K→3132K |

**DOM 来源**：`ChatContainer` 对消息列表**全量挂载**（`index.tsx:527` 的 `chatItems.map(...)`），全仓无 `react-window` / `react-virtuoso` / `@tanstack/react-virtual`。每条消息跑一遍完整 Markdown 管线（remark-math + rehype-katex + rehype-highlight），`markdown-limits.ts` 的注释自证量级：*"43 条消息 / 826KB 正文全量解析需 2.4s，产出 8.9 万个 DOM 元素（其中 4.3 万个是 highlight.js 的 `<span>`）"*。这些 span 每个都要在 PartitionAlloc 里分配，正是 `blinkTotal` 无界扩张的直接来源。"加载更早的消息"懒加载只控制**何时加载**，加载过的消息**永远保持挂载**。

**"现在没崩"是自愈兜底，不是没事**：perf 日志里今天有 4 个 renderer pid 接力（3092 → 35160 → 39760 → 37372），每次涨高后消失、新 pid 从 ~350MB 重新开始 = 至少 3 次崩溃重启。主窗口 `render-process-gone` 自愈（`main-window.ts:195`，5 分钟 3 次限流 + 递增延迟 reload）在兜底，用户看到的是"闪一下"而不是"崩死"。最新 pid 37372 的斜率比 3092 初期还陡（15 分钟 362→914MB）。

## 二、技术方案

两条腿走路，合在一个 `.message-row` 容器上实现（两处判定互斥，见下）：

### 前置：`.message-row` 行容器

每条消息/压缩卡片外包一层 `div.message-row`，同时承载 A、B 两条手段与 ResizeObserver 的测高目标。**它必须是 `display:flex; flex-direction:column`**：`.message` 依赖父级是 flex 上下文才有 `align-self`（user 靠 `flex-end` 右对齐）与"宽度收缩到内容"的语义，换成普通块级容器后 user 气泡会被撑满 `max-width`。flex 容器同时保证子元素外边距不与容器折叠（CompactionCard 的 8px 上下边距计入本层高度），实测高度才能原样用作占位高度。

顺带的两处配套改动（不改则静默退化）：

| 项 | 原状 | 改动 | 原因 |
|---|---|---|---|
| React key | `${item.id}-${index}` | `m:${id}` / `c:${id}`（前缀区分消息与压缩卡片） | 位置型 key 会让「前插历史」把所有行错位重挂，高度缓存随之作废 |
| 入场错峰 | `.message:nth-child(1..5)` | `.message-row[data-enter-index='0..4'] > *` | `.message` 在行内恒为第 1 个子元素，旧规则全部退化为 0ms；而 `.message-row:nth-child(N)` 也不行 —— `:nth-child` 按所有兄弟计数，列表里还有 history-loader 等节点，会把行序挤偏一位 |

### 方案 2 · `content-visibility`（跳过布局绘制，缓解）

在窗口带内、但**确实在视口外**、且**已被看见过**的行上加 `.message-row--skippable`：

```css
.message-row--skippable {
  content-visibility: auto;
  contain-intrinsic-block-size: auto var(--row-h, 240px);
}
```

`--row-h` 是 ResizeObserver 的实测值（内联 style 下发）。**这个值不是可选的**：跳过期间元素盒子取 `contain-intrinsic-size`，若用固定的兜底值，RO 会把这个假高度写回高度缓存，下一次占位就会用假高度替换真实高度 —— 正是我们要避免的滚动跳动。（CSS 里那个 240px 兜底不参与判定：类只在"已测高"的行上才加，它纯粹是防变量缺失导致属性整体失效。）

`seen` 这个前置条件同理不可省：跳过期间子树不跑动画，若让"挂载时就在屏外"的行（前插的历史页）跳过，它的入场动画会推迟到用户滚到它时才播。只对已经滚过去看过的行动手，既避开这个坑，也让"跳过"始终是纯优化。

### 方案 1 · 窗口渲染（卸载 DOM，治本）

自己实现一个**无第三方依赖**的轻量虚拟化，只对消息列表这一个场景特化，避免为它引入锁文件变更与联网安装（本地优先项目，且本机 `pnpm view` 联网探测已不可靠）：

- **高度缓存**：每个 `.message-row` 用 `ResizeObserver` 实测高度，存进 `Map<id, height>`。
- **两个 IntersectionObserver**（同一 `root` = 滚动容器，各司其职）：
  - 窗口带 observer（`rootMargin: ±2000px`）→ 维护 `bandHidden`，**判占位**；
  - 视口 observer（`rootMargin: 0`）→ 维护 `viewportHidden` 与 `seenKeys`，**判可否跳过**＋**判是否看过**。
- **占位替换**：`bandHidden && 已测高 && 非 pinned` 时，整行换成 `<div style={{height}}>`，
  真实子树卸载；高度取实测值，滚动位置不变。
- **未测过的行永远渲染真实内容**：新前插的历史、流式新增的消息都在此列，天然避免"估算高度 ≠ 实际高度"导致的滚动跳动。初始小列表全量渲染，滚过一遍后各行依次测得真实高度，再离开窗口带才换成占位。
- **决策全部收敛为"只信明确报告"**：两个 hidden 集合都从空开始、只被 `isIntersecting === false` 写入。尚未收到报告的行一律当作可见——否则行会在首帧、测高与观察回调之间的窗口里被误判离屏，造成闪烁。
- **pinned**：正在流式输出的那条永不占位。它高度每帧都在变，占位/回填会来回打架。

决策依据：不引 `@tanstack/react-virtual` 的理由是（a）本地优先、离线友好的仓库原则；（b）本项目滚动语义特殊（粘底自动跟随 + 前插历史锚点补偿 + 流式增长），特化实现比通用库更贴合；若特化实现后续证明不足，再评估换库（风险低，接口只封在 `useWindowedRows.ts` 一个文件）。

### 两条手段的分工

| | 方案 2（content-visibility） | 方案 1（窗口渲染） |
|---|---|---|
| 作用范围 | 窗口带内、视口外 | 窗口带外 |
| 对 DOM | **保留** | **卸载** |
| 回收内存 | ❌ | ✅ 治本 |
| 降渲染开销 | ✅ | ✅ |
| 前置条件 | 已测高 + 曾被看见 | 已测高 |

二者条件互斥（`bandHidden` 是与非），不会同时命中一行。

## 四、明确不做

- **不改消息内容渲染本身**：markdown 闸门（`markdown-limits.ts` 的 16KB/8KB/12KB 阈值）已存在，属"单条极端值"缓解，不是本片对象。
- **不动侧边栏会话列表 / Wiki 文件列表等其它长列表**：它们体量远小于消息列表，本片聚焦崩溃主因。
- **不改主进程 `render-process-gone` 自愈**：那是兜底，不是根因，保持现状。
- **不引入虚拟化三方库**（理由见 §二）。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 滚动跳动（占位高度 ≠ 实际高度） | 只有"已实测高度"的行才占位；未测行永远渲染真实内容。占位高度直接取 RO 实测值，**且不取整**（行高常是小数，逐行 0.5px 同号累积就是几十像素的误差） |
| `content-visibility` 的 `contain: paint` 裁掉子元素溢出 | 只加在"视口 observer 明确报告不可见"的行上，可见行永不加 —— 入场动画的 `translateY(20px)` 溢出因此不会被切 |
| 跳过期间的假高度污染高度缓存 | `contain-intrinsic-block-size` 用实测值（内联 `--row-h`）而非固定兜底值，RO 回报的高度与缓存一致 |
| 跳过期间不跑动画 → 入场动画被推迟到滚到时才播 | `seen` 门槛：只对已经进过视口的行动手 |
| 跳过期间行高被 size containment 冻结 | `pinnedKeys` 对 A、B **都**生效：占位与跳过都排除流式行（它的正文每帧都在长） |
| 全局重排（改字号 / Ctrl+滚轮 zoom / 窗口缩放 / 拖面板）后折叠行的高度是旧值 | `useLayoutEpoch`：字号或容器宽度一变就让整个高度缓存失效，折叠行退回"未测高"重渲染重测。两个信号都刻意避开自激量 —— 宽度取 border box（滚动条出现/消失不触发），字号只认 `--chat-font-size` 真的变了 |
| `unobserve` 不清空已排队条目 → 已 prune 的 key 被迟到条目写回（切回会话时首帧闪烁） | 观察回调统一经 `rowKeyOfEntry` 过滤，只认「当前仍在列表里」的 key |
| 流式期间每 token 全量重算（决策 memo、prune effect、pinned 集合） | `rowKeys` 走 `useStableMapById`（key 序列只在增删消息时变，流式 delta 复用同一数组）；pinned 先取签名再建 Set，引用在流式期间稳定 |
| `ResizeObserver` 回调触发渲染循环 | 只在高度真正变化时写 state |
| 粘底自动跟随 / 前插历史锚点补偿被破坏 | 两者基于 `scrollHeight` 差值，占位高度=实测高度，差值不变；且新前插的行当帧未测高、必为真实渲染，锚点补偿拿到的是真实高度 |
| 观察器尚未回调时误判离屏 → 闪烁 | 两个 hidden 集合都只被 `isIntersecting === false` 写入；未报告 = 可见 |
| 包一层行容器破坏消息对齐 / 错峰动画 | 行容器用 `flex-direction:column` 保住 `.message` 的 `align-self` 语义；错峰改由 `data-enter-index` 按行序下发（`:nth-child` 会被 history-loader 等兄弟挤偏） |
| 位置型 key 导致前插历史时全列重挂 | 行 key 改成 `m:${id}` / `c:${id}`；**行内 `<ChatMessage>` 上那个带 index 的 key 也一并去掉** —— 它同样会整树重挂并击穿 memo |
| 切换/压缩使集合随会话数无界增长 | prune 覆盖全部五个集合（含 `everCollapsed`） |
| 无 observer 环境（jsdom）行为变化 | 整块不启用，退化为全量渲染；既有测试不受影响 |
| 真实滚动观感 | 见 §六"待人工冒烟"清单 |

## 七、复核结论（2026-09-15，/code-review 10 角度）

### 已修（核实为真缺陷）

| 问题 | 性质 | 修法 |
|---|---|---|
| `everCollapsed` 未参与 prune | 与同段注释自相矛盾；只增不减，且切回旧会话时该批行的入场动画永久失效 | 补进 prune |
| 行内 `<ChatMessage key={\`${id}-${index}\`}>` 仍是位置型 key | 抵消了行 key 去位置化的收益：前插历史 / 压缩卡插入时整棵消息子树重挂，markdown+高亮全量重解析 | 删掉该 key（单元素上的 key 无意义），顺带去掉只服务于它的 `index` prop（它本身也在击穿 memo） |
| `selectSkippableKeys` 未排除 pinned | 流式行不占位、却可能被跳过；跳过期间 size containment 冻结行高，scrollHeight 停在旧值，滑回时跳变 | pinned 纳入 B 的前置条件 |
| 实测高度取整 | 占位高度与实测值不再严格相等，逐行 ≤0.5px 同号累积 | 不取整 |
| IO 迟到条目写回已 prune 的 key | `unobserve` 不清空已排队条目；幽灵记录会让行在切回会话的首帧被判离屏 | 观察回调统一按「当前仍在列表里」过滤 |
| 流式期间每 token 全量重算 | 决策 memo / prune effect / pinned 集合都随 `chatItems` 每 delta 换身份而重跑 | `rowKeys` 用 `useStableMapById`；pinned 先签名再建 Set |
| 全局重排后折叠行高度是旧值 | 应用内可达：TitleBar A−/A+ 改 `--chat-font-size`；窗口缩放、Ctrl+滚轮 zoom、拖面板同理 | 新增 `useLayoutEpoch`，字号或容器宽度变化即作废整个高度缓存 |
| 错峰规则被 `:nth-child` 的兄弟计数挤偏 | 有 `history-loader` 时行序整体后移一位，与注释声称的"按行序"不符 | 改由 `data-enter-index` 按行序下发 |
| hook 文件名 kebab-case | 违反 `docs/standards/code-style-guide.md` 的 Hook → `camelCase.ts` | 改名 `useWindowedRows.ts` |

### 核实后**不**改（记录结论）

| 结论 | 依据 |
|---|---|
| "空 assistant 消息会留下 0 高包裹层、多占一份 flex gap" —— 当前数据下不成立 | 实测运行时库：1085 条消息中 `role='assistant'` 且正文为空的 **0 条**（有 parts 的 331 条）。`ChatMessage` 的 null 守卫是防御性的，为它改行渲染结构不划算。仍登记为已知边界 |
| "`rowKeyOf` 去掉 index 后重复 id 会撞 key" —— 当前数据下不成立 | 实测重复 id **0 条**（`messages.id` 是主键，客户端乐观消息用的是 `incoming-*` 前缀，两者形状不同）。上游 `useStableMapById` 本就按 id 复用，重复 id 会先在它那里出问题 |
| 首帧仍是全量挂载 | 设计取舍：折叠的前提是"先测到高度"。要消掉它需要估算高度 + 滚动锚点补偿（真正的虚拟列表语义），是另一个量级的改动。**代价明确：冷启动/切回长会话的瞬时峰值与改动前一致**，窗口化只压稳定态 |
| 折叠会丢弃行内本地 UI 状态（展开态、编辑草稿、预览） | 虚拟化的固有代价。最坏情况是编辑草稿丢失；缓解办法是行在编辑时置 pinned，属后续可选项 |
