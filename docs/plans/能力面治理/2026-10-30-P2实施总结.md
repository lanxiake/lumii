## 3. 已解决的问题（每条附根因）

### 3.1 在 def 过滤之前裁 = 对窄白名单 Agent 直接删能力

**现象（推演出来的，未上线）**：若拿 `allTools`（~150，未按 `def.tools` 过滤）去裁，
再交给 `assembleAgent → filterToolsByDefinition`，chronicler 这种只认 10 个工具的 Agent
会被折掉它自己要的工具，然后白名单再把它扫掉——**工具无声消失**。

**根因**：`assembleAgent` 里工具经历了两次收窄：`def.tools` 白名单 + 我们的裁剪。
顺序反了，第二次收窄就作用在第一次的补集上。

**修法**：先 `filterToolsByDefinition`，再裁；`deferred` 存的就是「该 Agent 实际生效但被折叠」的那批。

**连带**：多数 Agent 白名单里**没有 `tool_search`**（chronicler 只有 10 项，见 `definitions.ts:227`）。
先过滤会让「折了工具又搜不回来」——折叠的唯一出口消失。故裁剪分支里**无条件补回 `tool_search`**
（只补它，不补 `task_complete`/`skill_search`：后者各自归 Agent 白名单管，强塞等于改能力面）。

### 3.2 `reason='search'` 行的口径偏差

见 §2-D2。search 行记的是「本轮被捞回、且此刻仍在装载集里」的工具名与 token 数，
**不是**装载前/后的差值，也对不上「turn 行 + search 行 == 轮末全量」这条会计恒等式。
它足以回答「模型有没有自己把折叠的工具捞回来」（Task 14 的 `tool_search` 命中率），
但对多轮交互后的 token 分账不可靠。已在 `bridge-prompt-dispatcher.ts` 的 `recordExposure` 注释里写明。

### 3.3 换提示词风格会丢掉 `tool_search` 捞回的工具

`originalToolDefs` 是**创建时**快照，不含之后装载的工具。逐轮风格切换若整份替换，
会把加载进来的工具悄悄丢掉——模型下一轮又"看不见"了，而它并没有做错任何事。
**修法**：重建时把 `state.loadedBySearch` 里的工具按名补回。

**连带坑**：补回要读 `targetInstance.getTools()`，而多数实例/测试替身没有它。
无条件调用会抛错并被外层 catch 吞掉，表现为「整个风格重建块静默失效」。
故**无装载时完全不碰 `getTools()`**——这是 `bridge-prompt-dispatcher.test.ts` 那两条
（`minimal 档裁剪` / `切回 detailed 还原`）暴露出来的。

### 3.4 `skill_search` 与 `tool_search` 的匹配语义必须同源

两者都是「从惰性目录里捞回能力」。各写一份 AND/OR 解析，改一处忘另一处就静默
退化成不同的检索行为（模型会以为「搜不到」是能力不存在）。抽出 `query-match.ts`，
`skill_search` 改走它（6 条旧测逐字回归绿）。

### 3.5 渠道维度只有 1 天，直接开裁剪会静默推平能力面

**这是本次最有价值的一条发现，也是「重启并测试」逼出来的。**

**现象**：按 (agent, channel) 的真实历史在本机极薄——`assistant|ipc` 只有 3 个工具的记录
（`bash`/`spawn_agent`/`task_complete`），`chronicler|cron` 3 个，`wechat-relay|ipc` 7 个。
用真数据模拟 `assistant|ipc`：

```
该渠道有历史: bash, spawn_agent, task_complete      ← 只有 3 个
=> 常驻 3 / 148   折叠 145
=> 折叠 token 8510，常驻只剩 479
```

**根因**：渠道维度是 **V56（2026-10-30）才加**的，此前全部落在 `unknown`
（340 行 / 33633 次，占 99.6%）。真实渠道数据总共才 178 次调用。回放实验那个 93.5%
来自 3174 条消息的**富分组**，而本机 live 每个渠道的历史是 **1 天**。

**修法（两道）**：
1. `tool-loadout.ts` 的冷启动判据保持「一条历史都没有 → 全量」；
2. 宿主侧加时间闸门 `MIN_CHANNEL_HISTORY_DAYS = 3`：渠道数据不足 3 天就跳过裁剪并**打日志**
   （原先是静默返回 null，真机上分不清「护栏生效」与「代码没跑到」）。

**为什么不是「按工具条数判」**：第一版护栏写的是「观测工具数 < limit 就 fail-open」，
但那是过保守的错误判据——一个稳定只用 12 个工具的渠道恰恰是最好的折叠对象
（保留 12、折 138），按条数拦会把它**永久**关在门外。真信号是「数据够不够老」，
已改回按天数判（`getScopeHistorySince`）。

## 3.6 提交后复核发现的三个问题（已修）

真机验证通过之后又通读了一遍实现，发现三处计划与我自己都没覆盖到的缺陷：

### (a) fail-open ② 是死代码 —— `tool_search` 未命中时从不调 `loadTools`

**现象**：宿主的 `missStreak` 计数**永远为 0**，`连续两次未命中 → 回落全量` 这条 C8 安全网从未触发。

**根因**：`tool_search` 的未命中分支**直接 return**，没调 `loadTools([])`；宿主的守卫写在
`loadTools(names)` 里（`if (names.length === 0) missStreak++`），于是拿不到「未命中」这个事件。
同时差额暴露行也不记未命中，命中率的分母**偏小**——等于把命中率测高了。

**修法**：未命中分支补 `context.loadTools?.([])`。**判据是「安全网必须在真机上真的会跳闸」**，
不是「代码写了就算」。已加单测钉住（`未命中也要调 loadTools([])`）。

### (b) fail-open 时仍塞 `tool_search` —— 19 token 的死重量

**现象**：`applyToolLoadout` 无条件补 `ensure`（`tool_search`），而 fail-open 时 deferred 为空。

**根因**：我第一版把「补 ensure」放在「判 deferred 空」之前，理由写的是「保持一致性」——
但那是空话：deferred 为空意味着 `tool_search` 的检索源为空，它一个工具也搜不到，
留着只是 19 token。而 fail-open 在当前数据条件下是**常态**（渠道数据不足 3 天）。

**修法**：deferred 为空时直接原样返回，不补 ensure。后来发现我先前那条单测的期望就是错的
（它断言补了 `tool_search`），一并改对——**测试断言写错会把 bug 固化成契约**。

### (c) 回合生命周期工具会被折掉 —— 补进 pinned

**现象（推演）**：`PINNED_TOOLS` 只有 `tool_search`/`task_complete`/`skill_search`。
`spawn_agent` 与 `ask_user_question` 要靠 LRU 争那 20 个名额。真机验证时它们进常驻集
**纯属巧合**——当时该渠道只有 3 个工具的历史，其余 17 个名额是「无历史按字母序」凑上的，
而两者字母都靠前。历史长起来后未必挤得进去。

**为什么要紧**：这不是「常用工具」（那种交给 LRU 就好），而是「缺了它这个 Agent
就没法完成回合，或者没法把结论交出去」。`task_complete` 在 pinned 里正因如此，
但另外两个被漏了——同一个理由只用了一半。

**修法**：`PINNED_TOOLS` 加 `spawn_agent` / `ask_user_question`，并把判据写在注释里。

> 三条的共同教训：**「能跑通」和「故障时会不会跳闸」是两件事**。真机验证证明了正常路径，
> 但 (a) 是故障路径的完全失效、(b) 是常态下的净损失、(c) 是边界条件下才暴露的隐患——
> 三条都不在你「验证通过」的那条路径上。
