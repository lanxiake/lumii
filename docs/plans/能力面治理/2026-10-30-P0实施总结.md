## 3. 已解决的问题（每条附根因）

### 3.1 暴露记录的 token 与日志差 2.4 倍

**现象**：真机第一轮写下的 `total_tokens = 22498`，同一时刻日志 `contextUsage` 的 `tools+mcp` 只有 `9191`。

**根因**（两层）：

1. `estimateToolTokens` 当时只有权重法（0.3/0.6 字符），而 `contextUsage` 明细走的是标定的 `charsPerToken`（本机 deepseek-v4-flash = 6.11）。同一个工具面在两条路上差 2.4 倍。
2. 更深一层：第一版把写入点放在 `setSystemPrompt` 之后。此时 `ctx.resolvedModelId` 还是 `undefined`（无显式会话偏好时，它要等 streamFn 跑完才被赋值），拿不到模型 → 拿不到标定值 → 必然退回权重法。

**修法**：`estimateToolTokens(tool, charsPerToken?)` 两条路都走；写入点挪到 `await instance.prompt()` 之后，用 `ctx.resolvedModelId` 取标定值。

**验证**：改完后 3 组配对的中位比值 = 0.979（偏差 2.1%，达标线 10%）。

> 这条值得记住：**「事后记」在这里是必要的，不是偷懒。** 我第一版为了"记的东西必须和送出去的一致"选了事前记，结果记到的是另一个口径。判定这一点的依据是日志里的实际数字，不是推理。

### 3.2 `tool-usage-store.ts` 被 git 当二进制，diff 看不见

**现象**：`git diff` 对该文件只输出 `Bin 19446 -> 22348 bytes`，改了什么完全看不出。

**根因**：该文件里 `KEY_SEP` 与三个复合键模板用的是**字面 NUL 字符**（`\x00`，从 V44 起就这样）。git 见到 NUL 就判定二进制。

**修法**：源码里写成转义 `'\u0000'`，字节里不再出现 NUL。文件从此可 diff。

**顺带修的**：原先是「切第一个空格」拆复合键。加了 channel 之后键变三段，那套写法会把 channel 一起吞进 agentId——**静默把 A 的数据算到 B 头上**。改成 NUL 分隔 + 只切固定刀数。

### 3.3 迁移索引的两处隐患

- `ALTER TABLE ... RENAME TO` 会把**索引一起带走**（探针实测：`idx_tud_day` 跟着旧表改名）。因此重建后必须重新 `CREATE INDEX`，且要放在 `DROP TABLE` 之后（放前面会因同名索引仍挂在旧表上而 `IF NOT EXISTS` 静默跳过）。
- V56 与 V44 同类：**重放不会报错，而是把已归因的 channel 压回 'unknown'**。已在 `local-database.ts` 的 `isMigrationAlreadyApplied` 补 `case 56`，并有单测固化「重放确实会毁数据」这个事实。

### 3.4 迁移不是原子的（review 抓到的真问题）

**现象**（代码走查，非线上）：`migrate()` 逐条 `db.exec(sql)`，**没有事务**。而 V56 是五条语句：
`RENAME → CREATE → INSERT SELECT → DROP`×2。

**后果**：进程若死在 `CREATE TABLE tool_usage_stats (… channel …)` 之后、`INSERT SELECT` 之前，
库变成半成品。下次启动时 `isMigrationAlreadyApplied('tool_usage_stats','channel')` **看到列存在**
⇒ 跳过迁移 ⇒ 340 行统计永久的留在 `tool_usage_stats_v55` 里，而活表是空的、
`schemaVersion` 仍是 55、**日志里一句错都没有**。

**这不是 V56 独有的**：V44 的重建表有同样的形状，只是当年没有中途崩溃的实例。

**修法**：把整个迁移循环 + 版本号写入包进已有的 `withTransaction(db, …)`（它带重入计数，
Repo 层也在用同一个 helper）。

**验证**：在真实库副本上模拟「CREATE 后 INSERT 失败」——`ROLLBACK` 之后
`tool_usage_stats` 仍是旧的 340 行，`_v55` 临时表不存在。

**守它的用例**：`storage/migrate-transactionality.test.ts`（检查 `migrate()` 的函数体结构 +
`withTransaction` 自身仍做 BEGIN/COMMIT/ROLLBACK）。结构断言而不是行为断言，是因为
注入"迁移中途失败"需要生产代码为测试开缝——那个口子比它防住的 bug 更危险。
