# 能力面治理实施计划（P0 / P1 / P2）

> 日期：2026-10-29
> 状态：**待评审**
> 设计：[`../../design/能力面治理/2026-10-29-能力面治理与流水线生命周期设计.md`](../../design/能力面治理/2026-10-29-能力面治理与流水线生命周期设计.md)
> 范围：可观察性 + 修断线（P0）→ 统一视图（P1）→ 按 (agent, channel) 的 LRU 与工具裁剪（P2）
>
> **分期是硬门禁**：P1 开工的前提是 P0 的 M2 过关；P2 开工的前提是 P1 的能力页能看到真实成本分布，且 P2 单独过一次评审。**P2 不允许与 P1 合并开发**——它是本计划唯一会改变模型可见面的改动。

---

## 1. Goal

一句话：**先让"这轮暴露了哪些工具"变成可查的事实，再用这份事实去裁掉 8K tokens/轮的固定开销。**

分三个可验证的目标：

| 期 | 一句话目标 | 判据 |
|---|---|---|
| **P0** | 让"展示 vs 使用"成为可查的差集 | 每条用户消息留一行暴露记录，`channel` 非空率 > 99%；技能提示词顺序 == `executionCount` 降序 |
| **P1** | 让人能回答"谁在吃我的上下文" | 页面上按 residentTokens 排序，前 10 名与日志 `tools:` 聚合值误差 < 10% |
| **P2** | 把常驻工具从 179 个压到 20 个 | 单 Agent A/B：Recall 与回放预测偏差 < 5pp；整轮 token 降幅可测且 > 6K |

**Not goals**（全套计划都不做）：

- 不做能力编排器 / DAG / 可视化步骤编辑器；
- 不做技能的自动排序（设计 §2.1b：51 个技能最高 10 次，撑不起决策）；
- 不做 MCP server 的独立治理（它们和工具走同一张表）；
- 不做渠道治理（渠道是投递终点，沿用 `channel_*`）。

## 2. Architecture

```
              ┌──────────────────────────────────────────────────────┐
 P0           │                                                      │
 用户消息 ───►│ BridgePromptDispatcher.prompt()                      │
              │   ├─ instance.getTools()          ← 本轮工具全集      │
              │   ├─ estimateTokenCount(每个 tool)                    │
              │   ├─ resolveChannelIdentity(...)                      │
              │   └─► recordToolExposure() ────┐                      │
              └────────────────────────────────┼──────────────────────┘
                                               ▼
                               tool_exposure_log（V56 新表）

 工具调用 ───► ToolUsageHook ──► recordToolUsage(agent, channel, tool, isError)
                                               ▼
                               tool_usage_stats / daily（重建，PK 加 channel）

              ┌──────────────────────────────────────────────────────┐
 P1           │ capability-inventory.ts  ──► sendCommand             │
              │   tools ← ToolRegistry + tool_usage_stats             │
              │   skills ← skill-store 索引                          │
              └────────────────────────────────┬─────────────────────┘
                                               ▼
                               ToolsPage 新 tab「上下文成本」

              ┌──────────────────────────────────────────────────────┐
 P2           │ bridge-instance-factory: allTools                     │
              │   └─► resolveToolLoadout(agent, channel)              │
              │         pinned ∪ LRU top-20  ──► instance.setTools()  │
              │                                        ▲              │
              │   tool_search(query) ──► loadTools ────┘              │
              └──────────────────────────────────────────────────────┘
```

两条统计通路互不依赖，各自 fail-open（统计失败绝不打断对话），这是 `tool-usage-store.ts` 头注释既有的约定。

模块边界：

| 层 | 职责 | 不做什么 |
|---|---|---|
| `storage/schema.ts` | 只出 DDL + 迁移 | 不写业务逻辑 |
| `tool-exposure-store.ts`（新） | 单行写入 / 查询 / 到期清理 | 不知道渠道怎么来的、不解析工具定义 |
| `tool-usage-store.ts`（改） | 加 `channel` 维度 | 不认识 `kind` |
| `tool-loadout.ts`（新，P2） | 纯函数：给定 (agent, channel) 与全量工具，返回本轮装载 | 不读 DB、不改 Registry |
| dispatcher / factory / hook | 接线 | 不自己拼 SQL |

## 3. Tech Stack

- **不引入任何新依赖**。SQLite 走现有 `node:sqlite` 适配器，token 估算走已导出的 `estimateTokenCount`，页面复用现有 `Select` / `Loading` / `Empty` 组件。
- 不引入 ORM、时序库、`uuid`、向量检索（P2 的 `tool_search` 用子串 + 关键词匹配即可，179 个工具不需要语义检索）。
- 测试沿用 vitest；schema 迁移照 `schema-v53.test.ts` 的写法。

### P0 · Task 1 — V56 迁移（0.5 人日）

**做什么**：一次迁移做完两件事，避免第二次改 PK。

**(a) 新表**

```sql
CREATE TABLE IF NOT EXISTS tool_exposure_log (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at   INTEGER NOT NULL,   -- epoch ms
  session_key  TEXT    NOT NULL,
  turn_id      TEXT,               -- 触发本轮的用户消息 id；取不到留 NULL
  agent_id     TEXT    NOT NULL,   -- 定义 id（C2）
  channel      TEXT    NOT NULL,   -- ipc|weixin|feishu|pcwechat|cron|evolution|unknown
  tool_count   INTEGER NOT NULL,
  total_tokens INTEGER NOT NULL,
  tools        TEXT    NOT NULL    -- JSON: [{"n":"bash","t":320}, ...]
);
CREATE INDEX IF NOT EXISTS idx_tel_created       ON tool_exposure_log (created_at DESC);
CREATE INDEX IF NOT EXISTS idx_tel_agent_channel ON tool_exposure_log (agent_id, channel, created_at DESC);
```

`tools` 存**逐工具 token**而非只有名字：P1 要回答"谁最贵"，多这一层几乎零成本，省一次迁移。

**(b) 用量表加 `channel`**

SQLite 不能 `ALTER` 主键，照 V44 的 `RENAME → CREATE → INSERT SELECT → DROP` 模式重建：

```
tool_usage_stats: PK (agent_id, tool_name)        → (agent_id, channel, tool_name)
tool_usage_daily: PK (day, agent_id, tool_name)   → (day, agent_id, channel, tool_name)
旧行 channel 一律回填 'unknown'（不猜 'ipc'，C4）
```

**为什么现在就加**：设计 §5.6.3 已证明"按 (agent, 渠道) 分组"是决定性的（`evolution` 97.4% vs 全局 32.0%），而 P2 的 LRU 就是一句 `ORDER BY last_used_at DESC LIMIT 20`。没有渠道列，P2 就得再改一次 PK。

**验证命令**：
```bash

pnpm typecheck
```

### P0 · Task 3 — 每轮写一行暴露记录（0.8 人日）

**这是整个计划的地基**：没有它，"裁剪到底伤不伤模型"永远无法证伪（设计 §5.6.6）。

写入点放在 `BridgePromptDispatcher.prompt()` 里、`setSystemPrompt` 之后（工具集已定稿）：

```ts
const tools = instance.getTools()
void recordToolExposure({
  sessionKey: this.deps.instanceToConversation.get(instanceId) ?? '',
  turnId: pendingUserMsgId ?? null,
  agentId: instance.definitionId,
  channel,
```

三条要点：

- `instance.getTools()` 就是送进请求的那份，不是另算的视图。

### P2 · Task 11 — `tool-loadout.ts`（0.5 人日）

**做什么**：纯函数。

```ts
resolveToolLoadout({
  all: AgentTool[]
  lastUsed: Map<string, number>   // 来自 tool_usage_stats 的 (agent, channel) 切片
  pinned: readonly string[]       // C8：'tool_search' | 'task_complete' | 'skill_search'
  limit: number                   // 默认 20
}): { loaded: AgentTool[]; deferred: AgentTool[] }
```

规则：

1. **无历史（`lastUsed` 为空）→ 返回全量**（冷启动 fail-open，C8）。设计 §5.6.3(b) 实测"首次使用某工具"只占 3.3%，但这个分支是零成本的安全网。
2. `pinned` 恒在，不占名额。
3. 其余按 `lastUsed` 降序取 `limit` 个，剩余进 `deferred`。

### P2 · Task 12 — `tool_search` 工具 + 加载回调（0.8 人日）

**做什么**：

1. `ToolExecutionContext` 加两个可选回调（与 `recordSkillExecution` 同风格）：
   ```ts
   searchTools?: (query: string) => readonly { name: string; description: string }[]
   loadTools?: (names: readonly string[]) => void
   ```
2. `tools/built-in/tool-search.ts`：模糊匹配**全量注册表**（含 deferred），返回命中的 `name + description`，并调 `loadTools()`。
3. 宿主侧 `loadTools`：从 `toolRegistry.getAll()` 取出对象，`instance.setTools([...instance.getTools(), ...found])`。

**结论已核实**：pi 原生支持单轮内更换工具集——`pi-agent-core/dist/agent-loop.js:212-243` 的 `declareToolChanges()` 会在每次请求前把 `context.tools` 的差集写成系统消息的 `toolsAdded` / `toolsRemoved`。**我们不需要自己发明协议**，只要改 `state.tools`。

**fail-open**：连续两次 `tool_search` 未命中 → `loadTools` 直接装载全量并记一条 warn（C8）。

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **重建两张用量表的 PK 丢历史** | 1325 行日数据损坏 | 照 V44 的 `RENAME → CREATE → INSERT SELECT → DROP`；测试断言"迁移前后行数相等、`count` 之和相等"；先在本机库副本上跑一遍 |
| **`channel` 大面积落 `'unknown'`** | §5.6.3 的分组结论无法复现，P2 失去依据 | 退出标准①量化为 < 1%；`resolveChannelIdentity` 已有前缀回退；首周每天看一次分布 |
| **暴露日志拖慢首字** | 每轮多一次写 | 异步 + 内部 catch；单行 ~600 字节，日均 400 轮 → 80KB/天。若首字可测地变差，改内存累加 + 批量 flush（照 `tool-usage-store` 的脏键模式） |
| **`estimateTokenCount(JSON.stringify(tool))` 与真实请求不一致** | P1 的"谁最贵"排序失真 | 用途是**相对比较**，不是绝对对账；Task 10 校准一次并记系数 |
| **`instance.definitionId` 取不到** | 暴露日志落 `unknown`，分组结论失效 | Task 3 单测覆盖；首轮人工核对 `agent_id` 分布，出现 unknown 即视为 bug |
| **P2 让模型"不会用"某个工具** | 任务失败，比省 tokens 严重得多 | C8 三条 fail-open；C9 单 Agent 灰度；`deferred` 的工具仍可 `tool_search` 一次取回；回滚 flag 常备 |
| **P2 的 `setTools` 中途生效导致行为漂移** | 模型反复重规划 | 已核实 pi 原生支持（`declareToolChanges`）；但**只增不减**——本轮加载后不卸载，避免模型"刚用过又没了" |
| **P0 做完没人用**（本仓库第三次） | 又一张死表 | C3 + Task 5：读侧脚本与写入同批交付 |
| 只加记录不加裁剪，用户看不到收益 | 被判定为"白干" | 收益在 P2（8K/轮）。P0 的产出是**让 P2 可证伪**；评审时要明确这条 |
