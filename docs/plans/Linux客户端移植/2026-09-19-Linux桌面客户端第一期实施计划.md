## 1. 目标与验收

**目标**：在 Ubuntu 24.04 上产出可安装、可启动、核心功能可用的桌面客户端。

**第一期验收（最小闭环）**——逐条对应设计 §9：

```
构建与分发
□ pnpm package:linux 一次性产出 .AppImage 与 .deb
□ AppImage 双击启动；deb 安装后菜单项与图标正常
□ 卸载 deb：应用文件清除、~/.lumii 保留

核心功能
□ 完成一轮对话（含至少一次工具调用）
□ 记忆：写入 → 检索命中；Wiki：搜索可用
□ 渠道：至少一个渠道完成扫码登录并收发一条消息
□ 定时任务：创建 → 到点触发 → 结果可见
□ 浏览器控制：启动 → 打开页面 → 取回内容
□ 语音：麦克风录制 → ASR 转写 → Edge TTS 回复（在线链路）

屏蔽与说明
□ 宠物模式入口置灰 + 说明文案；主进程不创建宠物窗口
□ 录屏、系统音频、Python 技能入口置灰并给出原因
□ .bat/.cmd 技能执行给出「请改用 .sh」的明确报错

桌面集成
□ 托盘在支持的 Shell 上出现；GNOME 无托盘时应用仍完全可用
□ 桌面通知可点击回到主窗口
□ 开机自启：开关 → 注销重登 → 生效（验证 APPIMAGE 路径）

Windows 零回归（三道门槛，见 §5）
□ 新增单测全绿（win32 分支行为不变）
□ test:all 失败集合与 M0 基线一致
□ Windows 上跑通一次 pnpm package:win
```

### 3.1 已探明的事实（2026-09-19）

| 项 | 实测 | 含义 |
|---|---|---|
| 系统 | Ubuntu 24.04.4 LTS，X11（X.Org 21.1.11，`DISPLAY=:1`） | 目标形态成立 |

| 镜像 | `registry.npmmirror.com` 200 / 0.15s；electron 镜像实测 **5 MB/s**；`nodejs.org` 7.2s | 走 npmmirror，不需要额外代理 |
| 磁盘 / 内存 | 1.7T 可用 / 15G 内存 | 充足 |

### 3.2 环境搭建步骤

**已执行（2026-09-19）**：

```bash
# ① Node 22 隔离安装（不遮蔽用户现有 v26）—— 已完成
mkdir -p ~/.local/share/lumii-tools
curl -sSL -o node22.tar.xz https://cdn.npmmirror.com/binaries/node/v22.23.2/node-v22.23.2-linux-x64.tar.xz
tar -xJf node22.tar.xz && mv node-v22.23.2-linux-x64 node22 && rm node22.tar.xz
# → ~/.local/share/lumii-tools/node22/bin/node = v22.23.2，npm 10.9.8

# ② corepack 启用（pnpm 由 packageManager 字段钉版）—— 已完成
mkdir -p ~/.local/bin
corepack enable --install-directory ~/.local/bin
# → ~/.local/bin/pnpm = 10.23.0（shim 在 /usr/local/bin 之前，实测未破坏现有 v26 环境）
```

**尚未执行**（需用户确认，涉及全局环境）：

```bash
corepack disable      # 移除 corepack 在 /usr/local/bin 放的 node/npm/npx shim（root 所有，需 sudo）
                      # 当前实测无功能影响，可暂缓
```

**每次构建会话必须注入**：

```bash
export PATH="$HOME/.local/share/lumii-tools/node22/bin:$PATH"
```

> **关键事实**：`pnpm` 自身可以跑在 v26 上（实测正常），但 `pnpm install` 触发的 `postinstall`（`@electron/rebuild`）会**继承 PATH**，所以安装与后续所有构建命令都必须在 Node 22 的 PATH 下执行，否则原生模块会按 v26 的 ABI 编译。
>
> **设计 D17 的落地**：构建固定 Node 22。建议写入 `apps/windows/.nvmrc` 或 `engines` 字段供他人复现；本机用隔离目录而非修改系统 Node（避免影响用户其他项目）。

### 3.5 Chromium sandbox 处置（新增硬要求）

**问题**：Ubuntu 24.04 默认 `kernel.apparmor_restrict_unprivileged_userns=1`，Electron 只能走 setuid sandbox；而镜像产出的 `chrome-sandbox` 权限是 `0755`（应为 `4755`），Chromium 因此 abort：

```
FATAL:sandbox/linux/suid/client/setuid_sandbox_host.cc:163
The SUID sandbox helper binary was found, but is not configured correctly.
```

**双轨处置**（已确认）：

| 轨道 | 做法 | 落地位置 |
|------|------|---------|
| **开发期** | `run-dev.cjs` 检测 `chrome-sandbox` 是否为 `root:root 4755`；**未满足则自动追加 electron-vite 的 `--noSandbox`**，并打印明确告知（不静默降级）。满足条件时走真实 sandbox | ✅ **已完成**（`apps/windows/scripts/run-dev.cjs`，实测 `pnpm dev` 可直接启动） |
| **发布产物** | deb 的 `postinst` 把 `chrome-sandbox` 设为 `root:root 4755`（Electron/VS Code 在 Linux 上的标准做法）；AppImage 走 `--no-sandbox` 或依赖用户命名空间配置 | ⏳ **并入 T2**（打包链路） |

> **为什么不在开发机直接 `sudo chown root:root && chmod 4755`**：每次重装依赖都要重做，且会让 pnpm 判定 store 被篡改。双轨方案下开发首日即可启动，发布产物无安全降级。

### T2 实测发现的坑（原计划未预料，均已解决）

| # | 问题 | 根因 | 处置 |

（子进程与孙进程的 stdout 都能正常收到，退出码正常）——这是本次改动最大的行为风险，

而不是「测试一字不改」**；若当时让实现去迁就旧测试，进程组收敛就白做了。

**冒烟查出的两个真实缺陷（已修）**：

1. **`VirtualHuman` 在屏蔽平台上仍调用 `pet:*` IPC**。组件的加载 `useEffect` 只判断
   `model` 是否存在就发起 `listPetModels` / `getCurrentPetModelId` / `getPetMode`，
   而 `registerPetModeIpc` 在 Linux 上**根本不注册**这些 handler，于是控制台刷：

   ```
   Error occurred in handler for 'pet:list-models': Error: No handler registered for 'pet:list-models'
   Error occurred in handler for 'pet:get-current-model-id': ...
   Error occurred in handler for 'pet:get-mode': ...
   ```

   `pet-service.ts` 有 catch 兜底所以不崩，但「入口层屏蔽」是**两层**的——UI 置灰只挡住了用户点击，
   没挡住组件自己的数据加载。
2. **`PetSettingsSection` 同样问题**（同样的三处调用）。此处 `getAgents()` 与宠物模式无关，
   保持始终加载。

**第一次修得不彻底（值得记下来）**：首版只在 `useEffect` 里加
`if (petModeBlocked) return`，看起来对，**实际一次都没生效**——`useFeatureAvailability`
的 `isAvailable` 在矩阵取回前一律返回 `true`（那是刻意的降级取向，见 hook 文件头），
而组件 effect 与 hook 的取数 effect **同批提交**，首次渲染时 `isAvailable` 必然走的是
「未就绪 → 可用」分支。第二次冒烟日志里三行 `No handler registered` 一字未少，就是这么来的。

正确做法是**把副作用挡在 `ready` 之后**：

```tsx
const { isAvailable, blockMessage, ready } = useFeatureAvailability()
useEffect(() => {
  if (!ready || petModeBlocked) return
  ...
}, [ready, petModeBlocked])
```

`ready` 的语义已写进 `UseFeatureAvailabilityReturn` 的注释，并有一条 hook 测试锁住
（「`ready` 在矩阵取回前为 false」）。

**为什么不用「未就绪即不可用」**：那会让入口先闪一下禁用态，且此时 `blockMessage`
必然为 `null`——用户看到「灰按钮 + 没有原因」，正是 D4 要避免的。**只约束副作用、
不约束 disabled** 才是对的。

**终态验证**（第三轮冒烟，`LUMII_CLIENT_DATA_DIR` 隔离）：

#### T6 实测记录

**矩阵是纯函数**，因此单测能穷举平台组合（21 个用例覆盖 Windows/Linux/Wayland/headless），
不必真的换系统——这是刻意的设计选择，不是巧合。

**两处判定依据值得说明**（实现时按设计决策逐一核对过）：
- `systemAudioCapture` **全平台屏蔽**：Windows 侧也没实现，不是平台差异问题。
- `pythonSkills` 的不可用原因是 **`missing-runtime` 而非 `platform-unsupported`**：
  装了 Python 3 就能用，文案直接给出 `sudo apt install python3 python3-venv python3-pip`。
  两者对用户的引导完全不同，所以 `BlockReason` 必须区分。

**`isWaylandSession` 的三种情况**（只判断 `WAYLAND_DISPLAY` 会出错）：以
`XDG_SESSION_TYPE` 为主、环境变量兜底。X11 会话里的 XWayland 客户端会继承
`WAYLAND_DISPLAY`，但它**不是** Wayland 会话（录屏走 X11 可行），误判会让功能被错误屏蔽。

**入口层 + 命令层双层屏蔽**（设计 §7 的约束）：`registerPetModeIpc` 在 Linux 上
**直接不注册**——若只把 UI 置灰而这里照常建 `PetWindowManager`，会留下半初始化状态
（窗口创建到一半、全局快捷键已占用、托盘监听残留），将来重写精灵图版时还要先清理。
命令层兜底仍在（`switchPetMode` 会报「PetWindowManager 未初始化」）。

**降级取向**：渲染层拿不到矩阵时按「**全部可用**」处理，而不是全部禁用——
main 侧 IPC 一有故障就把整个界面禁用掉，代价远大于「某个入口点了才发现不支持」
（后者还有命令层兜底）。已有测试固定这条。

**未在本机验证的**：真实 UI 上的置灰效果（需图形会话），列入 T7。三个挂载点
（`PetSettingsSection`、`VirtualHuman`、托盘菜单）均已接入。

#### 流程教训：一次「半边提交」

T3.2 新增了 `shell-env.ts` 并改了 `shell-runner.ts` 接入它，但 `git add` 时**漏掉了
`shell-runner.ts`**。当时全量测试全绿，于是继续做了 T3.3–T6 十几个提交都没察觉。

**为什么没被发现**：`pnpm test:all` 跑的是**工作区**，而工作区里那个文件是改好的；
版本库里的树是「半边」——`shell-env.ts` 已提交、接入代码没提交。旧版 `shell-runner.ts`
自洽（内联白名单还在），所以每个提交都能编译、CI 也不会红。**唯一破绽**：T3.2 的验收
结论（「Linux 上 .sh 技能能拿到 LANG/DISPLAY」）在版本库里根本不成立，只在本地成立。
已由 `82561811` 补齐，并在**干净检出**上复验通过（31 个测试）。

**据此调整的检查方式**（已写进团队记忆）：
1. 多文件改动的提交，`git add` 后先 `git status --short` 确认无残留；
2. 阶段性收尾时在 **`git worktree add --detach` 的干净检出**上验证，而不是工作区；
3. 判断「改动是否真进了版本库」用 `git ls-tree HEAD <path>` 或干净检出里 grep，
   **不要用 `&&` 链式命令**——短路会让人得出相反结论（本次就先误判成「HEAD 引用了
   不存在的模块」，又反过来推翻，来回折腾）。

#### 一条差点提交进去的破坏（2026-09-20）

提交前 `git status` 里冒出一个 **82 行删除** 的 `apps/windows/package.json` 差异：
`scripts`（35 条）与 `devDependencies`（41 条）整段消失。**这不是我编辑的**——
根因是 `npx asar extract-file <asar> package.json`：该命令**没有输出目录参数，
把文件解到当前工作目录**，于是在 `apps/windows/` 下执行时直接覆盖了源码。
asar 里那份是 electron-builder 生成的**最小包描述**（只有
`name/version/main/dependencies/...`），恰好没有 `scripts`。

**为什么危险**：它是合法 JSON，覆盖后不报任何错；`pnpm build` 只会说
「Missing script: build」。若这次没看 `git status` 就 `git add -A`，整个仓库的
构建/测试/打包脚本会一起消失。

**处置**：`git checkout` 还原（已复验 35 scripts / 41 devDeps 均在）；
后续查 asar 内容改用 `npx asar list`（只列不写），或在临时目录里 extract。

> 与「半边提交」是同一类问题的两面：**提交前看 `git status` 是唯一防线**。
> 那次是漏了改动的文件，这次是多了一个不该有的改动——都要在 add 之前扫一眼。

> **门槛 1 的判据在实施中修订过。** 原文写的是「用例不需要修改」，但 T3.1 与 T3.4
> 都**必须**改断言，且改得对：
>
> - **T3.1**：POSIX 侧信号从 `child.kill` 改为 `process.kill(-pid)`——变的是「信号发给谁」
>   （单进程 → 进程组），参数契约（`/pid <pid> /T /F`）与降级时序（2s）一字未动。
> - **T3.4**：平台换了，命令白名单自然从 Windows 命令表变成 POSIX 命令表。
>
> 若坚守「一字不改」，就会让实现去迁就旧测试，**进程组收敛与平台策略拆分都白做**。
> 正确的判据是：**逐条检查断言变化，确认变的是「平台/对象」而不是「契约/时序」**。
