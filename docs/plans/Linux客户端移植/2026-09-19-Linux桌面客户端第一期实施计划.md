## 1. 目标与验收

**目标**：在 Ubuntu 24.04 上产出可安装、可启动、核心功能可用的桌面客户端。

**第一期验收（最小闭环）**——逐条对应设计 §9：

```
构建与分发
□ pnpm package:linux 一次性产出 .AppImage 与 .deb
□ AppImage 双击启动；deb 安装后菜单项与图标正常
□ 卸载 deb：应用文件清除、~/.lumii 保留

核心功能
□ 完成一轮对话（含至少一次工具调用）
□ 记忆：写入 → 检索命中；Wiki：搜索可用
□ 渠道：至少一个渠道完成扫码登录并收发一条消息
□ 定时任务：创建 → 到点触发 → 结果可见
□ 浏览器控制：启动 → 打开页面 → 取回内容
□ 语音：麦克风录制 → ASR 转写 → Edge TTS 回复（在线链路）

屏蔽与说明
□ 宠物模式入口置灰 + 说明文案；主进程不创建宠物窗口
□ 录屏、系统音频、Python 技能入口置灰并给出原因
□ .bat/.cmd 技能执行给出「请改用 .sh」的明确报错

桌面集成
□ 托盘在支持的 Shell 上出现；GNOME 无托盘时应用仍完全可用
□ 桌面通知可点击回到主窗口
□ 开机自启：开关 → 注销重登 → 生效（验证 APPIMAGE 路径）

Windows 零回归（三道门槛，见 §5）
□ 新增单测全绿（win32 分支行为不变）
□ test:all 失败集合与 M0 基线一致
□ Windows 上跑通一次 pnpm package:win
```

### 3.1 已探明的事实（2026-09-19）

| 项 | 实测 | 含义 |

| 系统 | Ubuntu 24.04.4 LTS，X11（X.Org 21.1.11，`DISPLAY=:1`） | 目标形态成立 |

| 镜像 | `registry.npmmirror.com` 200 / 0.15s；electron 镜像实测 **5 MB/s**；`nodejs.org` 7.2s | 走 npmmirror，不需要额外代理 |

### 3.2 环境搭建步骤

**已执行（2026-09-19）**：

```bash
# ① Node 22 隔离安装（不遮蔽用户现有 v26）—— 已完成
mkdir -p ~/.local/share/lumii-tools
curl -sSL -o node22.tar.xz https://cdn.npmmirror.com/binaries/node/v22.23.2/node-v22.23.2-linux-x64.tar.xz
tar -xJf node22.tar.xz && mv node-v22.23.2-linux-x64 node22 && rm node22.tar.xz
# → ~/.local/share/lumii-tools/node22/bin/node = v22.23.2，npm 10.9.8

# ② corepack 启用（pnpm 由 packageManager 字段钉版）—— 已完成
mkdir -p ~/.local/bin
corepack enable --install-directory ~/.local/bin
# → ~/.local/bin/pnpm = 10.23.0（shim 在 /usr/local/bin 之前，实测未破坏现有 v26 环境）
```

**尚未执行**（需用户确认，涉及全局环境）：

```bash
corepack disable      # 移除 corepack 在 /usr/local/bin 放的 node/npm/npx shim（root 所有，需 sudo）
                      # 当前实测无功能影响，可暂缓
```

**每次构建会话必须注入**：

```bash
export PATH="$HOME/.local/share/lumii-tools/node22/bin:$PATH"
```

> **关键事实**：`pnpm` 自身可以跑在 v26 上（实测正常），但 `pnpm install` 触发的 `postinstall`（`@electron/rebuild`）会**继承 PATH**，所以安装与后续所有构建命令都必须在 Node 22 的 PATH 下执行，否则原生模块会按 v26 的 ABI 编译。
>
> **设计 D17 的落地**：构建固定 Node 22。建议写入 `apps/windows/.nvmrc` 或 `engines` 字段供他人复现；本机用隔离目录而非修改系统 Node（避免影响用户其他项目）。

### 3.5 Chromium sandbox 处置（新增硬要求）

**问题**：Ubuntu 24.04 默认 `kernel.apparmor_restrict_unprivileged_userns=1`，Electron 只能走 setuid sandbox；而镜像产出的 `chrome-sandbox` 权限是 `0755`（应为 `4755`），Chromium 因此 abort：

```
FATAL:sandbox/linux/suid/client/setuid_sandbox_host.cc:163
The SUID sandbox helper binary was found, but is not configured correctly.
```

**双轨处置**（已确认）：

| 轨道 | 做法 | 落地位置 |
|------|------|---------|
| **开发期** | `run-dev.cjs` 检测 `chrome-sandbox` 是否为 `root:root 4755`；**未满足则自动追加 electron-vite 的 `--noSandbox`**，并打印明确告知（不静默降级）。满足条件时走真实 sandbox | ✅ **已完成**（`apps/windows/scripts/run-dev.cjs`，实测 `pnpm dev` 可直接启动） |
| **发布产物** | deb 的 `postinst` 把 `chrome-sandbox` 设为 `root:root 4755`（Electron/VS Code 在 Linux 上的标准做法）；AppImage 走 `--no-sandbox` 或依赖用户命名空间配置 | ⏳ **并入 T2**（打包链路） |

> **为什么不在开发机直接 `sudo chown root:root && chmod 4755`**：每次重装依赖都要重做，且会让 pnpm 判定 store 被篡改。双轨方案下开发首日即可启动，发布产物无安全降级。

> **缺陷 3 的启示（重要）**：它**只在 Linux 上暴露，但根源是跨平台的**——`gitEnvFor` 的注释写着「Git for Windows 安装器会把 core.autocrlf 写在这里」，说明这段代码一直是按 Windows 的 git 行为写的（内置 MinGit 对非 UTF-8 locale 回退英文，所以英文匹配表一直有效）。Linux 用系统 git，尊重 locale，假设就崩了。
>
> 这类缺陷是移植的典型收益：**把「只在某个平台刚好成立」的隐式假设逼出来**。修复用「钉死 git 输出语言」而非「往匹配表加中文串」，是因为后者必须为每种 locale 无限追加，而前者一次解决所有语言。

### T2 实测发现的坑（原计划未预料，均已解决）

| # | 问题 | 根因 | 处置 |
|---|------|------|------|
| **1** | `onnxruntime-node` 与 sharp 的 libvips **完全不进包** | `apps/windows` 有自己的 `node_modules`（打包根），平台包按 **optionalDependencies** 解析。`onnxruntime-node` 是 `@xenova/transformers` 的 optional **传递**依赖，只链到仓库根 → 打包根里根本没有。`files` 白名单匹配不到不存在的文件 | 把 `onnxruntime-node` / `onnxruntime-common` / `@img/sharp-*` 显式声明为 `apps/windows` 的 `optionalDependencies`。**这是 pnpm hoisting 的固有陷阱，换任何包都可能复发** |
| **2** | Linux 产物里的 sharp 是 **Windows 版** | `dependencies` 里写死 `@img/sharp-win32-x64` → 无论在哪构建都装它 | 移入 `optionalDependencies` 并补 linux 包。**顺带发现：sharp 0.34 在 Windows 自包含（单一包含 libvips DLL），Linux 需要两个包**（`@img/sharp-linux-x64` + `@img/sharp-libvips-linux-x64`） |
| **3** | onnxruntime **三平台 94MB 全进包** | `asarUnpack` 是**独立白名单**，`files` 的排除规则管不到它；`**/*.node` 匹配所有平台的 `onnxruntime_binding.node`，asar 解包时会连带同目录的 `.dll`/`.so` | 用平台专属 `asarUnpack`（语义是**追加**，配合 `**/*.node` 使用）；`files` 里排除非本平台目录。残留：各平台那个 ~460KB 的 `.node` 仍会被解包，可接受 |
| **4** | deb 构建失败：`Please specify project homepage` | deb 需要 `homepage` / `maintainer` 元数据，而 `package.json` 没有 | 补 `homepage` / `repository`；`author` 补 email（deb 的 `Maintainer` 字段要求） |
| **5** | AppImage 在本机**无法直接运行**：`dlopen(): error loading libfuse.so.2` | Ubuntu 24.04 默认不装 `libfuse2`（设计 §12 已记录该环境风险，本次实测确认） | 文档需提示：装 `libfuse2t64`，或用 `--appimage-extract-and-run`。**deb 不受影响** |
| **6** | 失败时看不到真实原因 | `package-app.js` 的 `catch` 只打印 `e.message`（= `Command failed: <cmd>`），而 electron-builder 的真正错误在 `stderr` | 改为回显 stderr/stdout 末 40 行；产物列表也改为按 `--target` 过滤（此前 `--target deb` 会把旧 AppImage 一起列出） |

**未决**：`silk-wasm` 的 wasm 是否随包分发（存量缺陷 2）尚未实测——需在 T7 触发一次 SILK 解码（QQ/微信语音消息）确认。

**回滚**：纯新增/改名，回滚 = 还原 `electron-builder.json` 与脚本名。**注意脚本改名会同时影响 Windows**，回滚须两侧同步。**Windows 侧回归待验**（§5 门槛 3）。
