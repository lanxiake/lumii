> ### 勘误（2026-09-20 晚）：上面两条验收标准本身不成立
>
> 清单是 9-19 按设计文档写的，实施到 T7 时发现其中两条**按现设计根本无法达成**。
> 记在这里而不是悄悄改掉，是因为「验收时才发现标准写错了」本身是要留档的教训。
>
> **①「AppImage 双击启动」**
>
> 本机**双击必失败**，且不是环境没配好：Ubuntu 24.04 的源里已**移除 `libfuse2`**
> （`apt-cache policy libfuse2` 候选为空），而 type-2 AppImage 需要 `libfuse.so.2` 才能挂载。
> 更根本的是**格式层面的冲突**：AppImage 靠用户态打包 + FUSE 挂载，**无法携带 setuid 位**，
> 于是 `chrome-sandbox` 永远是 0755；叠加 Ubuntu 24.04 的
> `kernel.apparmor_restrict_unprivileged_userns=1`（非特权 userns 也不可用），
> GPU 子进程两条沙箱路都走不通，退出阶段必然 `FATAL: GPU process isn't usable`。
>
> **故 deb 是 Ubuntu 24.04 上唯一开箱可用的渠道**，AppImage 降级为「需自行解决 libfuse2，
> 或用 `--appimage-extract-and-run`」。这条验收标准应改写为**按渠道分别定标准**，
> 而不是要求两者都双击可用。
>
> 已完成的部分：用 `APPIMAGE_EXTRACT_AND_RUN=1` 走解包执行路径验过启动链路
> （与双击在文件布局上等价，只是挂载点路径不同），见下方「① AppImage 端到端启动」。
>
> **②「系统音频、Python 技能入口置灰并给出原因」**
>
> 这两个 `FeatureId`**在 renderer / main 里零挂载点**（实测 grep：只有
> `shared/feature-availability.ts` 的判定表提到它们，没有任何组件读）：
>
> | 功能 | 设计 §7.2 要求 | 实际 | 处置 |
> |------|--------------|------|------|
> | `systemAudioCapture` | 「全平台屏蔽 + 开关置灰」 | **没有独立入口**——回环音频是录屏的子能力，而录屏 D14 修订后 X11 下本就可用 | 判定保留（该能力 Windows 侧也没实现），但**没有可置灰的开关**，验收项无从执行 |
> | `pythonSkills` | 「技能页入口置灰」 | 判定已就位，UI 未接 | 按设计 §9/§10 属**第二期**（「第二期 · 运行时对等：系统 Python + venv」） |
>
> 即：**矩阵判定本身是对的，缺的是挂载点，而缺挂载点是有理由的**（一个没有入口、
> 一个明确排到二期）。验收清单当时把「判定就位」当成了「入口置灰」。
> 一期只保留 `petMode` / `screenRecord` / `localTts` / `voiceCloning` 四处的**实际置灰**。

### 3.2 环境搭建步骤

**已执行（2026-09-19）**：

```bash
# ① Node 22 隔离安装（不遮蔽用户现有 v26）—— 已完成
mkdir -p ~/.local/share/lumii-tools
curl -sSL -o node22.tar.xz https://cdn.npmmirror.com/binaries/node/v22.23.2/node-v22.23.2-linux-x64.tar.xz
tar -xJf node22.tar.xz && mv node-v22.23.2-linux-x64 node22 && rm node22.tar.xz
# → ~/.local/share/lumii-tools/node22/bin/node = v22.23.2，npm 10.9.8

# ② corepack 启用（pnpm 由 packageManager 字段钉版）—— 已完成
mkdir -p ~/.local/bin
corepack enable --install-directory ~/.local/bin
# → ~/.local/bin/pnpm = 10.23.0（shim 在 /usr/local/bin 之前，实测未破坏现有 v26 环境）
```

**尚未执行**（需用户确认，涉及全局环境）：

```bash
corepack disable      # 移除 corepack 在 /usr/local/bin 放的 node/npm/npx shim（root 所有，需 sudo）
                      # 当前实测无功能影响，可暂缓
```

**每次构建会话必须注入**：

```bash
export PATH="$HOME/.local/share/lumii-tools/node22/bin:$PATH"
```

> **关键事实**：`pnpm` 自身可以跑在 v26 上（实测正常），但 `pnpm install` 触发的 `postinstall`（`@electron/rebuild`）会**继承 PATH**，所以安装与后续所有构建命令都必须在 Node 22 的 PATH 下执行，否则原生模块会按 v26 的 ABI 编译。
>
> **设计 D17 的落地**：构建固定 Node 22。建议写入 `apps/windows/.nvmrc` 或 `engines` 字段供他人复现；本机用隔离目录而非修改系统 Node（避免影响用户其他项目）。

### 3.5 Chromium sandbox 处置（新增硬要求）

**问题**：Ubuntu 24.04 默认 `kernel.apparmor_restrict_unprivileged_userns=1`，Electron 只能走 setuid sandbox；而镜像产出的 `chrome-sandbox` 权限是 `0755`（应为 `4755`），Chromium 因此 abort：

```
FATAL:sandbox/linux/suid/client/setuid_sandbox_host.cc:163
The SUID sandbox helper binary was found, but is not configured correctly.
```

**双轨处置**（已确认）：

| 轨道 | 做法 | 落地位置 |
|------|------|---------|
| **开发期** | `run-dev.cjs` 检测 `chrome-sandbox` 是否为 `root:root 4755`；**未满足则自动追加 electron-vite 的 `--noSandbox`**，并打印明确告知（不静默降级）。满足条件时走真实 sandbox | ✅ **已完成**（`apps/windows/scripts/run-dev.cjs`，实测 `pnpm dev` 可直接启动） |
| **发布产物** | deb 的 `postinst` 把 `chrome-sandbox` 设为 `root:root 4755`（Electron/VS Code 在 Linux 上的标准做法）；AppImage 走 `--no-sandbox` 或依赖用户命名空间配置 | ⏳ **并入 T2**（打包链路） |

> **为什么不在开发机直接 `sudo chown root:root && chmod 4755`**：每次重装依赖都要重做，且会让 pnpm 判定 store 被篡改。双轨方案下开发首日即可启动，发布产物无安全降级。

（子进程与孙进程的 stdout 都能正常收到，退出码正常）——这是本次改动最大的行为风险，

**给后来者的一条经验**：T3.0 的单测在 T3.1 之后**必须改三处断言**——POSIX 侧信号从

而不是「测试一字不改」**；若当时让实现去迁就旧测试，进程组收敛就白做了。

当时只做了端到端验证、**没留下可复跑的证据**（结论在文档里、证据在当时的终端里，
和当初把脚本留在 `/tmp` 是同一个毛病）。现已补成断言
（`shell-runner.test.ts` 的「平台不匹配时的报错文案」），变异删掉该分支 → 3 条变红。

> **顺带发现一处死代码（已修，2026-09-20 晚）**：`describeUnsupported()` 的 `.ps1` 分支
> **原先永远走不到**——它只在 `resolveShell()` 返回 `null` 时被调用，而 `.ps1` 在**两个平台**
> 都返回了非空命令（win32 走 `powershell.exe`，POSIX 走 `pwsh`）。所以 Linux 上没装 pwsh 时，
> 用户看到的是 spawn 阶段的 ENOENT，而不是那句「需要先安装 pwsh（PowerShell Core）」。
>
> **修法**：把探测提前到解析期——`resolveShell()` 对非 win32 的 `.ps1` 先
> `findPwshExecutable()` 找一遍，找不到就返回 `null`，那句提示才走得到。
>
> `findPwshExecutable()` **不能只查 PATH**：Electron 从 GUI 启动时未必继承登录 shell 的
> 完整 PATH，「装了但没进 PATH」是最常见的情况——与 T3.5 处理 CLI 探测时是同一个结论，
> 所以先查 well-known 目录（`/usr/bin` / `/usr/local/bin` / `/snap/bin` / `~/.local/bin`）。
>
> **两侧都锁住了**（这点比修 bug 本身重要：探测写错会让**装了 pwsh 的用户**反被挡掉）：
> 变异成「无条件返回 pwsh」（即修复前的死路）→ 1 红；变异成「探测永远返回 null」→ 3 红。
> 真机复核（本机无 pwsh）：`resolveShell → null`，`error → 该技能提供的是 PowerShell 脚本（.ps1），
> 当前平台需要先安装 pwsh（PowerShell Core）才能执行。`

**冒烟查出的两个真实缺陷（已修）**：

1. **`VirtualHuman` 在屏蔽平台上仍调用 `pet:*` IPC**。组件的加载 `useEffect` 只判断
   `model` 是否存在就发起 `listPetModels` / `getCurrentPetModelId` / `getPetMode`，
   而 `registerPetModeIpc` 在 Linux 上**根本不注册**这些 handler，于是控制台刷：

   ```
   Error occurred in handler for 'pet:list-models': Error: No handler registered for 'pet:list-models'
   Error occurred in handler for 'pet:get-current-model-id': ...
   Error occurred in handler for 'pet:get-mode': ...
   ```

   `pet-service.ts` 有 catch 兜底所以不崩，但「入口层屏蔽」是**两层**的——UI 置灰只挡住了用户点击，
   没挡住组件自己的数据加载。
2. **`PetSettingsSection` 同样问题**（同样的三处调用）。此处 `getAgents()` 与宠物模式无关，
   保持始终加载。

**第一次修得不彻底（值得记下来）**：首版只在 `useEffect` 里加
`if (petModeBlocked) return`，看起来对，**实际一次都没生效**——`useFeatureAvailability`
的 `isAvailable` 在矩阵取回前一律返回 `true`（那是刻意的降级取向，见 hook 文件头），
而组件 effect 与 hook 的取数 effect **同批提交**，首次渲染时 `isAvailable` 必然走的是
「未就绪 → 可用」分支。第二次冒烟日志里三行 `No handler registered` 一字未少，就是这么来的。

正确做法是**把副作用挡在 `ready` 之后**：

```tsx
const { isAvailable, blockMessage, ready } = useFeatureAvailability()
useEffect(() => {
  if (!ready || petModeBlocked) return
  ...
}, [ready, petModeBlocked])
```

`ready` 的语义已写进 `UseFeatureAvailabilityReturn` 的注释，并有一条 hook 测试锁住
（「`ready` 在矩阵取回前为 false」）。

**为什么不用「未就绪即不可用」**：那会让入口先闪一下禁用态，且此时 `blockMessage`
必然为 `null`——用户看到「灰按钮 + 没有原因」，正是 D4 要避免的。**只约束副作用、
不约束 disabled** 才是对的。

> 单测侧另有三条锁**调用次数**的用例（屏蔽不发 / 可用照发 / 未就绪不发），删掉 `ready`

#### ⚠️ AppImage 的两个环境问题（2026-09-20 实测）

设计 §8 把 AppImage 当作「无 X11 库的精简系统」的兜底，实测发现**前提不成立**：

**问题 1：本机跑不了真实的 AppImage**（`dlopen(): error loading libfuse.so.2`）。
Ubuntu 24.04 默认只装 `fuse3`，type-2 AppImage 需要 `libfuse.so.2`；而本机
`apt-cache policy libfuse2` 显示**候选版本为空**——该包已从 24.04 的源里移除。
意味着**在全新 Ubuntu 24.04 上双击 AppImage 直接失败**，用户必须先自行找到
`libfuse2` 的安装途径（官方 22.04 包或改用 `--appimage-extract-and-run`）。

**问题 2：`--appimage-extract-and-run` 退出时报 GPU FATAL**。对照实验（同样
45s 超时 + SIGTERM，`LUMII_CLIENT_DATA_DIR` 隔离）：

| 布局 | 退出码 | React 挂载 | 托盘 | GPU FATAL | `error_code=1002` |
|------|--------|-----------|------|-----------|-------------------|
| AppImage（extract-and-run） | 124 | ✓ | ✓ | **1** | **9** |
| deb 解包布局 | 124 | ✓ | ✓ | 0 | 0 |

两者的**启动链路完全相同且都成功**；差异只在退出阶段：AppImage 那次
`zygote_communication_linux.cc: Failed to send GetTerminationStatus` →
`Network service crashed` → GPU 进程连试 9 次后
`FATAL: GPU process isn't usable. Goodbye.`。

**根因（已定位）**：`error_code=1002` 是 `sandbox::LINUX_NAMESPACE_SANDBOX` 失败。
对比两种布局里 `chrome-sandbox` 的权限：

```
deb 解包布局:      -rwsr-xr-x  (4755，setuid 在)
AppImage 解包:     -rwxr-xr-x  (0755，setuid 丢了)
```

**AppImage 从格式上就无法携带 setuid 位**——用户态打包 + FUSE 挂载都不允许，
解包到 `/tmp` 更不可能。而 Ubuntu 24.04 的
`kernel.apparmor_restrict_unprivileged_userns=1` 让非特权 userns 也不可用，
于是 GPU 进程既没有 setuid sandbox、也拿不到 namespace sandbox，
`--no-sandbox` 只影响 Chromium 的主沙箱策略、GPU 子进程仍会尝试自己那套。

> **这不是本次引入的问题，也不是代码能修的**——是 AppImage 与 Ubuntu 24.04
> 安全策略的固有冲突。**deb 能把 setuid 位正确装到 `/opt/Lumii/`**（`postinst`
> 还会再修一次），所以 **deb 是 Ubuntu 24.04 上唯一开箱可用的渠道**。

**问题 3：退出时 `app.exit(0)` 未能立即终止 MCP 子进程（已修）**。

> **勘误（2026-09-20 晚，本次冒烟复核）**：本条初稿把这个问题写成「GPU FATAL 的成因」，
> **归因错了**。逐行查原始日志后，时间线是：
>
> ```
> 2077  应用即将退出，等待清理完成...
> 2094  Network service crashed, restarting service
> 2103  资源清理完成
> 2104  清理完成，调用 app.exit(0) 强制退出所有进程
> 2106  zygote: Failed to send GetTerminationStatus      <- app.exit(0) 之后
> 2107  GPU process launch failed: error_code=1002       <- 之后
> ```
>
> **全部沙箱失败都发生在 `app.exit(0)` 之后**，是 Chromium 在拆自己的
> network/GPU 子进程时又尝试重启服务、而该布局的 `chrome-sandbox` 没有 setuid
> 才失败的。**与 MCP 子进程是否被停止无关**——MCP 那条修复改变不了它，
> 也**不需要**改变它：那 9 条 `error_code=1002` 是 AppImage 固有环境问题
> （问题 2）在退出阶段的回声，deb 布局下为 0。
>
> 下面记录的**子进程泄漏本身是真的、也确实被修掉了**，只是它和 GPU FATAL
> 是两件独立的事，不该记成因果。

日志时序显示 `清理完成，调用 app.exit(0)` 之后，`McpManager` 还在重连 MCP server、
`CloakBrowser` 还在下载——Electron 的退出被未终止的子进程拖住。

**排查结论**：`performCleanup` 共清理 12 项资源（录屏 / 桌宠 / 技能监控 /
浏览器服务 / 数据库 / ACP 进程 / 性能监控 / 更新器 / 托盘 / 日志 /
技能子进程 / AppUi 控制口），**唯独漏了 MCP Server**。

- `killAllTrackedChildren()` 只管技能类子进程（bash/python/node），
  MCP server 是 `McpStdioClient` 自己 spawn 的，不在跟踪列表（实到日志里该函数
  返回 0，未触发）。
- `bridge.destroyAll()` → `BridgeLifecycle.destroyAll()` 管的是 agent 实例、
  调度器、消息总线，**不碰 `mcpManager`**——MCP client 由 bridge 的私有字段
  `mcpManager` 独立持有。

**修复**（三处，Windows 同样受益）：

| 文件 | 改动 |
|------|------|
| `mcp-manager.ts` | 新增 `disconnectAll()`：遍历已有 client 调用 `disconnect()`（它已含「标记 `intentionalStops` 抑制重连 + 停 client + 从 Map 删除」），再清 `connecting` |
| `bridge.ts` | 新增 `stopMcpServers()` 薄封装（`mcpManager` 是私有字段，退出路径拿不到） |
| `index.ts` | `performCleanup` 里 `destroyAll()` 之后调用它 |

> **这是既有缺陷，不是移植引入的**（`mcp-manager.ts` 最后改动是 2026-09-02），
> 但在 Linux 上暴露得更明显——干净退出变成了带 FATAL 的退出。

> **测试**：新增 `mcp-manager.test.ts`（5 条，用桩 client 测编排）。
> 首版有两处问题被自己揪出来：① 一条「单个 Server 失败不影响其它」的用例
> **测不出东西**——`disconnect()` 内部已 `catch` 掉 `stop()` 的失败，外层
> `catch` 永不触发，变异测试（删掉外层 catch）全绿暴露了这点，遂删掉该用例
> 与冗余的外层 catch；② `mcpClients.clear()` 也是冗余的（`disconnect()` 内已
> `delete`），同样由变异测试暴露（删掉后全绿），一并删除。
> 最终保留的 `connecting.clear()` 有变异保护（删掉即红）。

### 问题 3 的补充：修复本身有竞态（2026-09-20 晚冒烟查出，已二次修复）

首版 `disconnectAll()` 只扫 `mcpClients`，**漏掉了「正在连接中」的 client**。
用桩 MCP Server 冒烟时稳定复现（桩启动 + 立即 SIGTERM）：

```
205  [connect] 连接 MCP Server: smoke-stub          <- 启动期发起
234  应用即将退出，等待清理完成...
246  [disconnectAll] 正在停止 0 个 MCP Server       <- 数不到（修复前）
394  [connect] MCP Server [smoke-stub] 已连接       <- 清理之后才落地
405  资源清理完成
406  清理完成，调用 app.exit(0)
```

**根因**：`connect()` 只在 `await client.start()` 返回后才把 client 写进
`mcpClients`，而 `disconnect()` 只从 `mcpClients` 取 client。卡在握手期的
client 谁都够不到，带着已 spawn 的子进程活过清理。更糟的是 `load()` 是
`void ...load()` 发出去的，清理后循环**还会接着连下一个**——实测日志里
`已连接` 之后紧跟着 `[connect] 连接 MCP Server: excel-mcp`。真实配置有
6 个启用的 Server，等于退出后仍会陆续 spawn 5 个子进程。

**二次修复**（`mcp-manager.ts`）：

| 改动 | 作用 |
|------|------|
| 新增 `inFlightClients` 映射，构造后**立即**登记、`finally` 里释放 | 握手期的 client 也能被 `disconnectAll()` 停掉 |
| `disconnectAll()` 额外扫 `inFlightClients` 并 `stop()` | 覆盖「已 spawn、未握手」这一档 |
| 新增 `shuttingDown` 标志，`disconnectAll()` 先置位 | 叫停 `load()` 循环与重连定时器 |
| `connect()` 起手 `if (this.shuttingDown) return` | 退出后不再 spawn 新进程 |
| `start()` 返回后再判一次 `shuttingDown` | 握手期跨过退出的 client 只停掉、不注册工具 |

新增 2 条测试（共 7 条），均经变异验证：删掉 `inFlightClients` 清扫 → 红；
删掉 `connect()` 的守卫 → 红（且实测会真的 spawn 出进程，用例挂 30s 超时）。

> **这条竞态是首版修复自带的**，不是既有缺陷——上一节的「既有缺陷」指泄漏本身。

#### 竞态冒烟实测对照（2026-09-20 03:00，桩 MCP Server）

方法：造一个只做两件事的桩 Server——启动写 `alive.marker`、收到 SIGTERM 写
`sigterm.marker`。`McpStdioClient.stop()` 走的就是 `process.kill()`（SIGTERM），
于是「退出路径有没有停掉子进程」变成一次**文件断言**，不用读日志猜。
桩在 `initialize` 上人为延迟 25s，把握手窗口拉开，再在桩刚起时立刻发 SIGTERM。

| 指标 | 修复前（02:54） | 修复后（03:00） |
|------|----------------|----------------|
| `[disconnectAll] 正在停止 …` | `0 个` | `0 个、**1 个连接中的**` |
| 清理后仍出现 `已连接` | **1 次** | **0 次** |
| 桩收到 SIGTERM | **否**（marker 缺失） | **是** |
| `GPU FATAL` / `error_code=1002` | 0 | 0 |

三个场景都跑过，覆盖两条分支：

| 场景 | 退出时机 | `disconnectAll` 结果 | 结果 |
|------|---------|---------------------|------|
| 竞态 | 桩刚起、握手未完成 | `0 个、1 个连接中的` | 通过 |
| **已连接** | 等日志出现「已连接，加载」后再退 | **`1 个、1 个连接中的`** | 通过 |
| 二者叠加 | 上面的场景里 excel-mcp 正在 `npx` 拉取 | 同上（见下） | 通过 |

第三行是决定性的一次——它**同时**覆盖了两条分支：

```
354  [disconnectAll] 正在停止 1 个 MCP Server、1 个连接中的（应用退出）
                                 ↑ 已连接的桩        ↑ 正在 npx 拉取的 excel-mcp
361  [connect] MCP Server [smoke-stub] 已断开
366  [load] 应用正在退出，跳过连接 MCP Server: mcp-trends-hub（其余 5 个同理）
```

即「已连接走 `disconnect()`」与「连接中走 `inFlightClients`」两条路径在同一次退出里
都被走到，且桩的 `sigterm.marker` 生成、`timeout.marker` 未生成（说明是**被停掉**的，
不是靠 stdin EOF 自行结束）。

> 两次冒烟**加载的是同一份 9 个 Server 的清单**。隔离目录里的
> `mcp-servers.json` 会被 `loadMcpServerConfigs()` 用内置预设回填
> （日志：`补充新增内置 MCP: comfyui-remote、excel-mcp、…`），所以连真实配置里
> 那 6 个启用的 `npx -y` 项也一并覆盖到了——这比只放桩更有代表性。

> **顺带确认了一件事**：修复后那次日志里，清理之后的 9 个 Server 全部打印
> `[load] 应用正在退出，跳过连接 MCP Server: xxx` 并被跳过。这正是
> `shuttingDown` 守卫的作用——首版修复在这里会继续 spawn 它们。

> **沙箱说明**：冒烟用 `--no-sandbox` 启动。Chromium 要求 `chrome-sandbox` 属主为
> root（uid 0）且 4755，未安装的目录里属主是当前用户，于是启动即 abort；真实渠道
> （deb）由 `postinst` 把 `/opt/Lumii/chrome-sandbox` 修成 `root:root 4755`，不受影响。
> 关掉它不影响本冒烟的可信度：被测对象是**主进程(Node)对 MCP 子进程的管理**，
> 与渲染进程沙箱无关。

> **效率教训**：`package-app.js` 的 `--target dir` 直接产出 `linux-unpacked`，
> 比 `both` 少掉 AppImage/deb 的压缩（约 160s → 约 60s）。冒烟迭代时用 `dir` 就够，
> 但**要用得对**：`package-app.js` 内部会重跑一遍 `electron-vite build`，
> 所以打完 `dir` 之后跑的冒烟是**最新代码**；反倒是「先 build 再手动指向
> 旧 `release/` 产物」会测到过期文件——本次就差点踩中（`app.asar` 比修复早 28 分钟）。

##### ② SILK：交叉验证两份独立副本

原判「需要一条 QQ/微信语音消息」——但 **silk-wasm 自带 encoder**，可合成一条。

故设计成**编码用 asar 外的工作区副本、解码用 asar 内的副本**，交叉验证：

```

✓ 编码（工作区副本）→ 1567 字节，500ms
✓ 魔数 #!SILK_V3 —— 正是 isSilkAudio() 的判据
✓ 解码（**asar 内副本**）→ 16000 字节 PCM，540ms
✓ 峰值 17097（确有波形）
✓ 主频估计 441.0Hz（原信号 440Hz）
```

> **一个容易忽略的前提**：asar 里的文件**普通 Node 读不到**（asar 是 Electron 打的 fs 补丁），

> 于是「能跑通」本身就证明了 **wasm 在 asar 内可加载并实例化**——这正是存量缺陷 2 的核心。
>
> `silk.wasm` 落在 `app.asar/node_modules/silk-wasm/lib/silk.wasm`（asar 内），
> 同时 `app.asar.unpacked/node_modules/silk-wasm/` 下也有副本；两种路径 Electron 都会正确解析。

##### ④附：真实任务触发通知的尝试与卡点（2026-09-20 晚）

**做法**：控制口白名单放行了 `cron:create`（注释写明「供自动化测试与控制面使用」），
于是建一个 60s 后触发的任务 → 任务完成时走 `showCronNotification` → 桌面通知。
通知到没到用 `dbus-monitor` 抓 `org.freedesktop.Notifications.Notify` 判定，
并用 `notify-send` 发对照通知确认**监听器本身有效**（对照组成功捕获）。

**顺带证实的（原先的怀疑被推翻）**：**cron 调度是正常的**。
一度以为「UI 走 `cron:create` 建的任务不会到点触发」，依据是日志里没有
`[scheduleJob]` 注册行——但**那条日志只对 `cron` 类型打印，`every` 类型不打**。
回查原始日志：任务确实按点触发并执行（`[runLocalCronJob] 开始执行 jobId=…`），
且该日志全程只有**一次**「启动中」（没重启过）。怀疑不成立。

**卡点**：agent 那轮报
`Error: 请先在设置中填写文本对话模型的 API Key`，
于是没有产出、也就没有通知。而 `~/.lumii/config/provider.json` 里
`chat.apiKeyEnc` **是有值的**。

用探针把「环境」与「这份密文」分开测（同一进程内自编自解作对照）：

```
后端: gnome_libsecret
① 自编自解:        ✓ 可用      ← safeStorage 在本环境完全正常
② 解 provider.json: ✗ 解不开    ← 这一份密文解不开
```

即：**不是环境没能力解密，是这份密文与当前密钥环不匹配**。
已排除的替代解释：不匹配应用名（`lumii-windows` / `Lumii` 两个名字各试一遍，均失败）。

> **一条方法学教训**：先前用**独立 Electron 探针**解不开就断言「密文不可解」，
> 并据此推断「密钥环被替换、可能是我 `pkill -9` 造成的」——**那套推理无效**，
> 因为我当时没做「自编自解」对照，无法区分「环境不行」与「密文不行」。
> 加上对照后才成为有效测量。文件创建时间也不能当「被替换」的证据：
> 该文件每次重写都换 inode（原子替换），创建时间等于最后一次写入时间。

**结论**：通知的**运行时**验证仍未完成，卡在用户环境的凭据解密上，
与本项目代码无关（同一份代码在 Windows 上通知是既有功能）。
一旦 `provider.json` 能被解密，`bash apps/windows/scripts/…` 同款流程即可复跑。

##### ④附二：卡点定位到根因，并修掉「读不出来被说成没填」（2026-09-20 晚）

上一节停在「这份密文解不开」。继续追下去，把它变成了**可复现的结论 + 一处修复**。

**证据链**（每一步都可重跑）：

1. **列出密钥环全部条目**（`gdbus` 读 `org.freedesktop.Secret`，本机没装 `secret-tool`）：

   ```
   /3  application = lumii-windows   |  Chromium Safe Storage
   /5  application = Lumii           |  Chromium Safe Storage
   /4  application = decrypt-probe   ← 我上一轮探针建的（已删除）
   ```

   **两个应用名各有一条**，所以「换个名字解」这条路本身就不成立——
   两把密钥都取了出来，穷举 **CBC / GCM × SHA1 / SHA256 × 128 / 256 位**，
   三份密文**全部解密失败**。

2. **比对密文格式**（这才是根因）：

   | | 前缀 | 长度 | 结构 |
   |---|---|---|---|
   | 当前 Electron `encryptString` 产出 | `v11` | 16 对齐 | ✅ |
   | `provider.json` 里的三份 | `v10` | 82 / 82 / 66 字节（去前缀 79 / 79 / 63） | ❌ **不是 16 的倍数** |

   AES-CBC 的密文必然是块大小的整数倍，**79 字节在结构上就不可能是当前实现写出来的**。
   三份同型，排除了「某一份损坏」。且文件 mtime 停在 `01:47` 从未变过——
   **用户那次「重新填写」并没有落盘到 `provider.json`**（渲染层保存是挑字段构造新对象，
   见下），所以他的实例能对话与这份文件无关。

3. **由此暴露一个真缺陷**：`decryptApiKey` 是 `catch { return '' }`，
   于是「密文读不出来」和「用户没填」在调用方看来完全一样，
   屏幕上永远是**「请先在设置中填写文本对话模型的 API Key」**。
   用户重填 → 重存 → 重启，凭据依旧读不出来，而没有任何线索指向真正的原因。

**修复（三处，Windows 同样受益）**：

| 改动 | 位置 | 作用 |
|------|------|------|
| `decryptApiKey` 返回 `{ value, failed }`，失败时 `log.warn` 出真实原因 | `provider-config.ts` | 失败不再被吞成「没填」 |
| 视图新增 `apiKeyDecryptFailed`；`missingApiKeyMessage()` 按它分两种文案 | `provider-config.ts` + 三层类型同步 + `bridge-instance-factory` / `provider-probe` / `bridge` ×2 调用点 | 用户看到的是「已保存的 API Key 无法解密…请重新填写」，而不是「你没填」 |
| 保存时**保住解不开的原密文** | `provider-config.ts` `preserveUnreadableKey()` | 见下 |

**第三条是读代码时顺带发现的破坏性路径，不是本次验收要求的**，但值得单独说：

> 解密失败时视图里 `apiKey` 是空串，而设置页保存是**挑字段构造新对象**
> （`ModelConfigSection/index.tsx:140` 的 `apiKey: chat.apiKey`，标记不会回传）。
> 于是「打开设置 → 顺手改个模型 → 保存」会把用户唯一的那份凭据**静默抹成 `''`**。
>
> 已实测复现（临时用例，跑完即删）：
> `读出来的 apiKey = ""  decryptFailed = true` → `保存后盘上的 apiKeyEnc = ""`。
>
> 修复判据刻意**不依赖视图上的标记**（渲染层会丢），而是回看**盘上那份能不能解开**：
> 能解开 → 用户是主动清空，照清；解不开 → 它对当前环境是惰性的，留着比抹掉好
> （万一密钥环能恢复、或这份配置要搬回原机器，那是唯一的恢复凭据）。

**验证**：新增 `provider-config.credentials.test.ts`（10 条，含保存守卫三条）与
`shell-runner.test.ts` 的平台文案用例，**四处变异全部被抓**：
失败标记吞回 `false` → 2 红；文案不再区分 → 1 红；保存守卫放行 → 1 红；去掉 `.bat` 专属文案 → 3 红。

**仍未解决**：这份 `provider.json` 里的密文**依然解不开**（那不是代码能修的——
它本就不是当前实现写的）。但**现在用户能从屏幕上看到这件事**，也知道该重填。
重填后新写入的是 `v11`，可正常解密。

> **结案（2026-09-20 23:05）**：用户重填后 chat / vision 已正常，对话实测跑通；
> 只剩 `image` 槽。过程与结果见 §9 A。

> **一条操作教训**：上一轮我用独立探针解不开就断言「密文不可解」，被认为推理无效——
> **但那个探针本身还有第二个缺陷**：它在 `whenReady()` 之后才 `setName`，
> 而且 `encryptString` 对**不存在的条目会新建密钥**，于是「自编自解 ✓」这个对照
> 根本不能证明「环境正常」，只证明了「我给自己造了一把新钥匙」。

##### 一次打包耗时观察（非缺陷）

同一份代码，`pnpm package:linux` 本轮耗时 **874.9s**，而先前同命令是 **153.8s**。

写脚本时踩到的三个坑（都记在脚本注释里，避免下次重踩）：

1. **`pgrep -f "…/lumii$"` 锚尾匹配不到**：真实 cmdline 是 `…/lumii --no-sandbox`，
   锚尾导致 `$PID` 为空，`kill` 静默什么都没杀，表现为「退出后未见注销」的假象。
   这与先前 `pkill -f "stub.js$"` 是同一个错误——**匹配进程命令行时不要锚尾**。
2. **`2>/dev/null` 吞掉了 Python 的 SyntaxError**：菜单解码器一直无输出却没报错。
   诊断类代码不该吞 stderr。
3. **f-string 表达式里不能写 `\"`**（即便 Python 3.12 的 PEP 701 允许嵌套引号）：
   `f"{a if b else \"-\"}"` 是语法错误。先算成变量再插值。
   另外 busctl 输出的中文是**八进制转义的 UTF-8 字节**，还原后需

asar 里那份是 electron-builder 生成的**最小包描述**（只有

后续查 asar 内容改用 `npx asar list`（只列不写），或在临时目录里 extract。

> 与「半边提交」是同一类问题的两面：**提交前看 `git status` 是唯一防线**。
> 那次是漏了改动的文件，这次是多了一个不该有的改动——都要在 add 之前扫一眼。

##### 浏览器控制：原判「环境阻塞」，当晚解掉并实测通过

**原先失败的样子**：

```
browser_navigate → {"ok":false,"error":"No supported browser found
                    (Chrome/Brave/Edge/Chromium on macOS, Linux, or Windows)."}
```

本机 `google-chrome` / `chromium` / `microsoft-edge` / `brave-browser` **全无**，只有 `firefox`
——而 Ubuntu 桌面**默认就只装 Firefox**。也就是说：**在一台全新 Ubuntu 24.04 上，浏览器控制开箱不可用**。

应用自带的兜底（CloakBrowser 自动下载）在当前网络下**四个源全部失败**（这次拿到了完整报错，
比早先「0.02–0.08 MB/s」的记录更硬）：

```
github.com（直连）: 连接超时      ghfast.top（镜像）:   连接超时
gh-proxy.com（镜像）: 连接超时    gh.ddlc.top（镜像）:  HTTP 429
→ [ensureCloakBrowser] 失败: 所有下载源均失败
```

**修法：给用户一条不依赖 GitHub、也不需要 root 的通道。** 排查中发现一处**我自己写错的文档**：
`AGENTS.md` 声称「可用 `executablePath` 手工指定 Chromium」，但客户端里
`buildWindowsBrowserConfig()` 是 `executablePath: undefined` **硬编码**——全仓库唯一的赋值点，
用户根本没有配置入口，那句话从来就不成立。补上两个环境变量：

| 变量 | 作用 |
|------|------|
| `LUMII_BROWSER_EXECUTABLE` | 直接指定浏览器可执行文件，**优先于** CloakBrowser 与全部自动探测（`chrome.executables.ts:668` 的既有分支，此前无人喂给它） |
| `LUMII_BROWSER_NO_SANDBOX` | 加 `--no-sandbox`，只认 `1`/`true` |

**第二个变量不是可选项**。手工解包的 Chromium 在 Ubuntu 23.10+ 上必然起不来：

```
FATAL:zygote_host_impl_linux.cc(129)] No usable sandbox!
```

——**和 AppImage 同一个根因**（`kernel.apparmor_restrict_unprivileged_userns=1`）。
包管理器装出来的浏览器自带 AppArmor profile 才不需要它，所以**优先路径仍是 `sudo snap install chromium`**；
`--no-sandbox` 关的是渲染进程沙箱，是真降级，因此实现上要求显式开启、不设默认。

**实测（2026-09-20 晚，`pnpm dev` + 真实数据根 + 控制口驱动，全程无人工点击）**：

| 步骤 | 证据 |
|------|------|
| 下载 | npmmirror 的 Chrome for Testing 153.0.8010.52，195.7 MB / 约 90s ≈ **2.2 MB/s**（GitHub 侧全灭） |
| 启动 | 日志 `[browser:chrome] MtBot browser started (custom) profile "mtbot" on 127.0.0.1:18791`——**`(custom)` 即走了 `executablePath`** |
| 进程实测 | `/proc/<pid>/cmdline`：`…/chrome-for-testing/chrome-linux64/chrome --remote-debugging-port=18791 --user-data-dir=~/.mtbot/browser/mtbot/user-data … --no-sandbox --disable-setuid-sandbox` |
| **打开本地页** | `browser_navigate http://127.0.0.1:18999/` → `success=true`（12.4s）；`browser_snapshot` 取回 DOM，含 `strong [ref=e4]: LUMIN-BROWSER-7742`；助手回复 `LUMIN-BROWSER-7742` |
| **打开真实站点** | `browser_navigate https://www.baidu.com/` → 助手回复标题 `百度一下，你就知道` |

> 判据用**本地页面 + 唯一标记**，是为了先把「链路通不通」与外网波动解耦；再用真实站点补一发，
> 确认不是只有 localhost 能跑。

**过程中我自己第三次栽在同一处**：`conversation:messages` 的返回是
`{items:[…]}`（不是 `messages`），且 `contentJson` 是**JSON 字符串**（不是对象）——
于是应用明明答了，我的判据读出「助手文本片段=0」。
差一点又写成「浏览器控制仍然不通」。**日志里 `message:end fullText="LUMIN-BROWSER-7742"` 再次把我拉回来。**

**剩下未做的**（产品决策，未擅自改）：deb 的 `Recommends` 补一个 Chromium 系浏览器
（现在只有 `libayatana-appindicator3-1` / `fonts-noto-cjk` / `libnotify4`）——
在 24.04 上它意味着默认拉一个约 200MB 的 snap。

##### 门槛 3 实测（2026-09-21）：命令跑通，但产物一度不可用

**原定风险（`package-windows.js` → `package-app.js` 改名打断 Windows 打包）未发生。**
`pnpm package:win` 261s 跑完，产出 `Lumii-Setup-0.1.4-x64.exe`（245.7 MB）+ `.blockmap` + `latest.yml`。

两个绕不开的前置与细节：

- **本机 `config/draw-config.json` 的 `drawApiKey` 是空的**（从 example 复制后没填），原样跑会卡在
  步骤 3.5 报「缺少 drawApiKey」——这段检查**改名前后逐字相同**，与本次移植无关；用脚本自带的
  `--skip-draw-check` 继续。（该错误分支没提示这个开关，另一处「文件缺失」分支才提；
  属可改可不改的小 UX 缺口。）
- **它抓到了另一件事**：产物的 `app.asar` 是坏的 —— 504 个 `package.json` 里 **439 个**
  （复跑一次是 453 个）装的是**别的文件的字节**，Electron 加载主脚本即失败，只弹一个标题为
  `Error` 的对话框：**没有窗口、不写日志、不建数据根**，看上去像「什么都没发生」。
  命令退出码是 0，安装包也照常生成。

| 轮次 | electron-builder | 形态 | asar 内 package.json 解析失败 |
|------|------------------|------|------------------------------|
| ① 正式打包 | 26.15.3 | nsis / 干净树 / 输出 `release` | **439 / 504** ❌ |
| ② 复跑同一命令 | 26.15.3 | 同上 | **453 / 504** ❌ |
| ③ 换版本 | **26.16.1** | 同上 | 0 / 504 ✅ |
| ④⑤ | 26.15.3 / 26.16.1 | `--dir`（asar 里混进别的目录） | 0 / 504 ✅ |

- 与 upstream [electron-builder#9661](https://github.com/electron-userland/electron-builder/issues/9661)
  （Windows + pnpm workspace 产出 mangled app.asar）同型；坏包走的是 `@electron/asar` 的
  `createPackageFromStreams` 流式写入口（#9419 引入），上游 2026-06~09 一直在修这块
  （#10185 / #10188 / #10200 / #10207）。
- **26.16.1 改的正是我们这个形态**：`app-builder-lib` 的 `appFileCopier.js` 新增
  `collectionMatchesAppDependencies` / `resolveFirstMatchingCollection`，注释原文——
  「*A package-manager `list` invocation can resolve to the wrong project root — most notably when
  electron-builder is run from a workspace sub-package whose dependencies are hoisted to the
  workspace root. In that case the collector returns a non-empty but unrelated tree.*」
  本项目恰好就是「从 `apps/windows`（workspace 子包）跑 + 依赖 hoist 到仓库根 + pnpm」；
  26.15.3 没有这道校验（收集到不对的树也照用），26.16.1 校验不过就回退手工遍历收集器。
  两次坏的条目数不同（439 vs 453）也说明「收集到哪棵树」本身带不确定性。
- **处置**：`electron-builder` 由 `^26.0.0` 改为精确 **`26.16.1`**（范围会随 `pnpm install` 漂移，
  正是「没人跑过 Windows 打包」才一直没暴露的那类问题）；新增
  `apps/windows/scripts/verify-win-package.mjs`（子命令 `asar` / `launch` / `all`，
  npm script `verify:win-package`），把「命令跑通」与「产物能用」拆成两条判据。
  实测：好产物 504/504 可解析 + 2s 起就绪；拿 ① 那份坏 asar 当反例，两条判据都拦下（退出码 1）。

**附带修掉的仓库内回归**：T2 引入的 `--target` 过滤按 target 名推扩展名（`nsis` → `.nsis`），
而 Windows 的 nsis/portable 产出的都是 `.exe`，于是**永远报「未发现 nsis 产物」**——安装包明明
躺在 `release/` 里。Linux 恰好名字与扩展名一致（appimage/deb），故**只在 Windows 暴露**。
已改为按平台声明 `targetExts` 映射 + 启动自检。

**同一轮里还做了包体治理**（起因是发现安装包比记忆中的 ~170 MB 大了 80 MB）：安装包
**253.9 → 162.3 MiB（−36%）**，排掉 8 类「运行时用不到」的东西（`.mtbot` 250 MB、渲染层专用包、
sourcemap、浏览器构建、占位 `onnxruntime-web`、浏览器专用 wasm……），顺手把「打包版 Wiki/记忆嵌入
一直静默退回 bigram」的既有 bug 也修了。**结论、electron-builder 三条反直觉配置真相与可复跑的
产物判据另行落档**：[`../../../design/工程基建/2026-09-21-打包体积治理.md`](../../../design/工程基建/2026-09-21-打包体积治理.md)。
