# 无头模式部署指南（systemd 用户服务）

> **面向**：把 Lumii 当常驻服务跑——没有桌面会话、无人值守，全部操作从终端用 `lumii-ui` 完成。
> **前置**：第二期无头形态（`--headless`）与终端引导体系（`status` / `setup` / `guide`）已实现，
> 设计与验收见《2026-09-22-无头模式用户引导设计.md》。
> **本文档的实测环境**：Ubuntu 24.04、GNOME/Wayland 会话、systemd 255；
> 源码树启动 + systemd 用户服务，以及 `package:linux:dir` 产物（`release/linux-unpacked`）
> 的完整链路，实测时间 2026-09-22 夜～2026-09-23 凌晨（证据见 §4）。

---

## 1. 装完之后有什么

deb 安装时，`postinst` 会调用包内的 `resources/headless/install-headless-assets.sh`，
写入两个文件：

| 产物 | 作用 |
|------|------|
| `/usr/bin/lumii-ui` | CLI 启动器。用**应用自带的 Electron**以 node 模式跑（`ELECTRON_RUN_AS_NODE=1`），因此**不要求系统装 node** |
| `/usr/lib/systemd/user/lumii-headless.service` | systemd **用户**服务模板，**默认不启用**，由用户自己 `enable` |

两个文件都由脚本在安装时生成，而不是直接放进包里——因为 `ExecStart` 必须指向真实的应用目录
（`/opt/Lumii`，目录名由 electron-builder 的 `sanitizedProductName` 决定），写死会变成
指向不存在文件的静默失效。脚本用 glob 探测应用目录，与 `postinst` 里修 `chrome-sandbox`
权限是同一套思路。

**AppImage / 手工解包的用户**没有 `postinst`，自己跑一次同一个脚本：

```bash
sudo squashfs-root/resources/headless/install-headless-assets.sh /path/to/squashfs-root
# 只看看生成什么、不动系统（三个参数分别是应用目录 / bin 目录 / systemd 单元目录）：
resources/headless/install-headless-assets.sh /path/to/squashfs-root /tmp/bin /tmp/units
```

## 2. 三步走

### 2.1 起服务并做首次配置

```bash
systemctl --user daemon-reload
systemctl --user start lumii-headless        # 先跑起来，再配
lumii-ui status                              # 服务是否起来、控制口在哪、缺什么
lumii-ui setup                               # 交互式向导：模型提供商 + 浏览器控制
lumii-ui status                              # 复核
```

`setup` 会依次问：提供商预设（OpenAI / Anthropic / DeepSeek / Gemini / 智谱 GLM /
阿里百炼 / Ollama / LM Studio / 其它 OpenAI 兼容）→ 模型 ID → API Key（不回显；
Ollama、LM Studio 这类本地服务不用 Key）→ 当场测连通性。只有选「其它 OpenAI 兼容服务」
时才问端点，其余用预设端点。
测不通会给排查方向（网络 / 端点是否写全 / Key 是否有效），并允许「先存下、回头再查」。

不想交互也可以：

```bash
cat key.txt | lumii-ui provider set --type openai --model gpt-4o-mini --api-key -
lumii-ui provider test
lumii-ui guide            # 按场景（对话/浏览器/技能/渠道）看怎么用
```

### 2.2 让它常驻（开机/登录自启）

```bash
systemctl --user enable --now lumii-headless
journalctl --user -u lumii-headless -f        # 跟随日志
```

无人值守（机器重启后**没人登录**也要起来）需要开启 lingering：

```bash
loginctl enable-linger $USER
```

> lingering 下用户服务在开机时就启动，此时**密钥环通常是锁着的**——见 §5 第一条。

### 2.3 日常操作

```bash
lumii-ui status                              # 一眼看服务/配置/推荐下一步
lumii-ui conversation create                 # 建会话
lumii-ui send --session <会话ID> --text "你好" --wait    # 发消息并等回复打印出来
lumii-ui context messages --session <会话ID> --limit 10 --text   # 看最近几轮说了什么
lumii-ui channel login weixin                # 渠道扫码登录（二维码见 §5 第四条）
systemctl --user stop lumii-headless         # 停
```

## 3. 服务模板全文

安装后位于 `/usr/lib/systemd/user/lumii-headless.service`（`ExecStart` 按真实应用目录生成）：

```ini
[Unit]
Description=Lumii 灵栖（无头模式：终端引导 + 渠道接入）
Documentation=file:/opt/Lumii/resources/app-ui-cli/lumii-ui.mjs
After=default.target
# 起崩循环兜底：5 分钟内超过 5 次就停下（否则 Restart=on-failure 会一直重试）
StartLimitIntervalSec=300
StartLimitBurst=5

[Service]
Type=simple
ExecStart=/opt/Lumii/lumii --headless
# 无头模式不创建窗口，也用不到图形会话；显式清空，避免从会话环境继承 DISPLAY 后
# 被能力矩阵误判成「有图形」（录屏/桌宠会显示为可用，点进去却静默失败）
Environment=DISPLAY=
Restart=on-failure
RestartSec=5

[Install]
WantedBy=default.target
```

几处不是随手写的：

- **`Environment=DISPLAY=`**：从用户会话继承来的 `DISPLAY` 会让能力矩阵以为有图形会话。
  `--headless` 已经让应用跳过窗口初始化，矩阵也会跟着把录屏/桌宠报成不可用
  （`isHeadlessSession()` 同时看启动参数与环境变量），但显式清空能避免用户会话环境
  带来的歧义——systemd 服务不该依赖「当前恰好登录着什么会话」。
- **`Type=simple`**：Electron 前台常驻，不加 `--headless` 之外的参数就不会 fork 出去。
- **`Restart=on-failure` + `StartLimitBurst`**：崩溃自愈，但不会无限重启刷日志。
- **不写 `After=graphical-session.target`**：无头模式本就不需要图形会话，
  这也正是它能在没人登录时提供服务的前提。

需要给服务加环境变量（例如浏览器控制）时用 drop-in，不要改模板（重装会覆盖）：

```bash
systemctl --user edit lumii-headless
# [Service]
# Environment=LUMII_BROWSER_EXECUTABLE=/usr/bin/google-chrome
# Environment=LUMII_BROWSER_NO_SANDBOX=1
```

## 5. 已知限制与排查

### 一、`status` 说「API Key 解密失败」

凭据用 Electron `safeStorage`（Linux 走 libsecret/密钥环）加密落盘。在桌面会话里填的 Key，
换到**密钥环没解锁**的环境（无人值守开机自启、换了用户、配置从别的机器搬来）就读不出来。

- 应用不会把它当成「没填过」：`lumii-ui status` 会直接说「解密失败」并给出重填命令，
  `lumii-ui provider show` 也会在 stderr 上补一句（stdout 仍是合法 JSON，脚本不受影响）。
- **处置**：在**将来要运行的那个环境里**重填一次（`lumii-ui setup` 或
  `provider set --api-key -`），覆盖掉读不出的旧密文即可，无需重启应用。
- 若那个环境里 safeStorage 也不可用（完全没有密钥环），重填会走代码里的 `plain:` 明文兜底
  ——功能可用，但请顺手收紧文件权限（`chmod 600 ~/.lumii/config/provider.json`）。
- 反过来，长期无人值守又想保住加密，就让密钥环随登录自动解锁（GNOME 的 login keyring + PAM），
  或让服务只在用户会话里运行。**聊天模型的 Key 目前没有环境变量注入通道**，
  只能走 `provider set`（`LUMII_BROWSER_EXECUTABLE` 那类是给浏览器控制的）。

### 二、开机自启但没人登录

默认 `enable` 只在**登录后**启动（`WantedBy=default.target` 是用户管理器级别）。
无人值守需要 `loginctl enable-linger $USER`；此时注意上一条的密钥环问题。

### 三、浏览器控制

无头环境里浏览器路径**不会自动探测到**（应用跑在服务环境里，看到的是服务的 PATH）。
用 §3 的 drop-in 设 `LUMII_BROWSER_EXECUTABLE` / `LUMII_BROWSER_NO_SANDBOX=1`，
改完 `systemctl --user restart lumii-headless`。`lumii-ui status` 会提示这两项缺不缺。

### 四、二维码去哪了

无头模式没有界面，扫码登录的二维码打印到**应用自己的 stdout**：

- 前台直接跑：就是你启动应用的那个终端。
- systemd 服务：stdout 进 journal。**必须用 `-o cat`**，默认格式每行会加
  `时间 主机 单元[pid]:` 前缀，二维码会被打散成不成形的一团：

  ```bash
  journalctl --user -u lumii-headless -o cat -f
  ```

`lumii-ui channel login` 的提示里也写了这条命令。扫码后用
`lumii-ui channel status <渠道>` 确认状态。

### 五、和桌面版同时跑

单实例锁按 **user-data-dir** 生效：同一用户下桌面版已经在跑，无头服务启动后会立刻退出
（日志里是「已有实例在运行，退出」）。要并存就给服务独立的两个目录：

```bash
systemctl --user edit lumii-headless
# [Service]
# Environment=LUMII_CLIENT_DATA_DIR=%h/.lumii-headless
# ExecStart=
# ExecStart=/opt/Lumii/lumii --headless --user-data-dir=%h/.lumii-headless-profile
```

（`ExecStart=` 空赋值表示清空原值，systemd 的追加语义如此。）

### 六、AppImage 的沙箱

deb 的 `postinst` 会把 `chrome-sandbox` 修成 `root:root 4755`，setuid 沙箱可用。
AppImage 没有这一步，在 Ubuntu 24.04（`kernel.apparmor_restrict_unprivileged_userns=1`）
上需要给服务加 `--no-sandbox`，或自行处理沙箱权限。

## 6. 卸载

```bash
systemctl --user disable --now lumii-headless
sudo apt remove lumii
```

`postrm` 会删掉 `/usr/bin/lumii-ui` 与 `/usr/lib/systemd/user/lumii-headless.service`
（这两个文件不在 dpkg 的文件清单里，是 `postinst` 生成的，必须显式删）。
用户自己的 `~/.lumii/` 数据保留；`systemctl --user disable` 需要**用户自己**执行——
`postrm` 以 root 运行，多用户机器上无法穷举是哪个用户启用过。
