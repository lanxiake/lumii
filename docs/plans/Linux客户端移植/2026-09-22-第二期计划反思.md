## 逐条反思

### 一、无头形态（D2 路线 A）

#### 原计划假设

- 启动路径：`xvfb-run` 包裹 Electron + `--headless` 跳过窗口创建
- 扫码登录：终端打印二维码（用已有依赖 `qrcode` 的 `type: 'terminal'`）
- 驻留：systemd user service
- **同步落实解耦约束**（事件出口接口 L1 雏形、dataRoot 注入 L3）

#### 一期实际情况

**与假设不符的发现**：

1. **录屏 D14 修订后在 X11 下可用**  
   原设计按「录屏全平台屏蔽」规划，现在只在 Wayland 屏蔽。无头形态若跑在 xvfb 上，
   **录屏能否工作、该不该屏蔽**？xvfb 提供的是虚拟 X11，录屏服务能否捕获它的内容？
   
   **需实测确认**：`xvfb-run` 下 `screen-record-service.ts` 的捕获源能否列出 xvfb 屏幕。
   若能，录屏在无头下也可用（适用于「无人值守但要录屏」的场景）；
   若不能，能力矩阵需增加 `headless` 维度，录屏按它屏蔽。

2. **浏览器控制已有环境变量覆盖通道**  
   原调查文档判定「Linux 上浏览器控制需探测」，现已补上 `LUMII_BROWSER_EXECUTABLE`。
   无头环境下，用户可能更倾向「指定一个已装好的 Chromium」而非让应用自己下载。
   **这条通道对无头依然有效**，只需在无头文档里提一句。

3. **能力矩阵已就位，扩展无头维度的成本已知**  
   `feature-availability.ts` 是纯函数，输入包含 `platform` / `isWaylandSession` / 运行时探测结果。
   **增加无头维度只需**：
   - 新增输入参数 `isHeadless: boolean`（从 `--headless` 启动参数或 `DISPLAY` 环境变量判定）
   - 在返回的 `FeatureAvailability` 里，桌宠/录屏/托盘按 `isHeadless` 追加屏蔽判定
   - `BlockReason` 已有 `'headless'`，文案表 `FEATURE_BLOCK_MESSAGES` 已就绪

   **结论**：矩阵扩展路径清晰，无需重新设计。

#### 调整建议

**保留原计划，补三条前置实测**：

| 实测项 | 判据 | 影响 |
|--------|------|------|
| xvfb 下录屏捕获源 | `xvfb-run` 启动后，`desktopCapturer.getSources()` 能否列出虚拟屏幕 | 决定 `screenRecord` 在无头下是否可用 |
| 无 DISPLAY 时 Electron 能否 `--headless` 启动 | `unset DISPLAY; xvfb-run --auto-servernum` 能否拉起应用且服务全初始化 | 若失败，systemd service 需显式设 `DISPLAY` |
| qrcode 的 `type: 'terminal'` 输出效果 | 真实终端里能否扫到 | 若失败（字符密度/对比度问题），改用 `qrcode-terminal` 或退回 base64 URL |

**D18 的解耦约束顺延决策需重新确认**：  
原文写「第二期开工时重新确认」——**现在是那个时点**。若第二期仍只做无头形态、不碰移动端/macOS，
**事件出口接口和 dataRoot 注入的真实需求是什么**？

- 事件出口接口（L1 雏形）：无头下渲染进程不存在，Agent 产出的通知/进度要往哪发？
  若只推到渠道（微信/QQ），不需要新接口；若要支持「监听应用事件流的外部脚本」，才需要。
- dataRoot 注入（L3）：无头下 `~/.lumii` 依旧可用，**什么场景需要从外部注入**？
  容器化部署时挂载卷？多实例？若没有这些场景，这条可以再往后推。

**建议**：先做无头形态的最小闭环（xvfb + systemd + 扫码打印 + 矩阵扩展），
解耦约束等「有真实外部客户端接入需求」时再做——否则是没有需求的设计抽象。

### 二、桌宠（精灵图重写）

#### 原计划假设

- 用精灵图重写渲染后端（`packages/pet-core` 的 `PetRendererProvider` 已预留可插拔后端）
- 穿透机制参考调查文档 §5.3 的 `PollingHitTestStrategy`（主进程光标轮询 + 区域命中）
- **前置条件**：精灵图资源就绪

#### 一期实际情况

**与假设相符的**：

1. **入口已屏蔽、主进程不初始化**  
   `registerPetModeIpc` 在 Linux 上根本不调用，桌宠窗口、托盘项、IPC handler 全都不存在。
   **重写时不必先清理半初始化状态**——这条路径在一期已闭环。

2. **能力矩阵对 `petMode` 的判定已就位**  
   四处 UI 挂载点（进入/退出按钮、虚拟人组件、工具栏 ✧ 按钮、托盘项）全部接矩阵。
   **重新开放时只需改矩阵里的一行判定**，所有入口会自动解除屏蔽。

3. **`screen.getCursorScreenPoint()` 在 X11 下的可用性已实测**  
   一期冒烟时用 `xdotool getmouselocation` 交叉验证过，坐标一致。
   **轮询策略的技术假设成立**。

**需要补充的**：

1. **精灵图的帧率与尺寸规格**  
   调查文档 §5.3 写「轮询间隔 50ms（20fps）」，但精灵图若本身是 30fps 或 60fps 的序列帧，
   轮询频率要匹配帧率才不会浪费。**资源准备阶段需明确**：
   - 帧率（决定轮询 `setInterval` 的间隔）
   - 单帧尺寸（决定 `BrowserWindow` 的 `width` / `height`）
   - 交互区域的标注方式（是每帧单独标、还是全局固定几个区域？）

2. **Live2D 素材的去留**  
   `packages/pet-core` 与 `src/renderer/pet/**` 在一期「一行不改」（设计 §1 D13），
   它们现在仍在仓库里。**精灵图重写后，Live2D 代码是删还是留**？
   - 留：占约 24MB（团子素材已入库，见 `10733daa`），但可作为「另一种渲染后端」的参考实现。
   - 删：减小仓库体积，但 `PetRendererProvider` 的可插拔设计会失去对照。

   **建议**：精灵图重写完成并验收通过后，把 Live2D 实现移到一个 archive 分支，
   主分支只保留精灵图后端。

3. **`PollingHitTestStrategy` 的 CPU 开销实测**  
   调查文档 §12 风险表写「光标静止提前返回；间隔可放宽至 80ms」。
   **二期开工前先实测**：在真实 X11 桌面上跑一个最小 demo（50ms 轮询 + `getCursorScreenPoint`），
   用 `top` 看 CPU 占用是否可接受。若 >5%，考虑「只在窗口 hover 时轮询」的优化。

#### 调整建议

**前置条件拆成两步**：

1. **精灵图规格确认**（输出一份「资源规格文档」）：帧率、尺寸、交互区域标注格式、是否循环播放
2. **穿透策略 demo 实测**（5 分钟轮询 + CPU profiling）：确认开销可接受

**二者齐备后再启动桌宠重写**。若精灵图资源短期内不就绪，这一方向可以推迟。

### 三、运行时对等

#### 原计划假设

- **系统 Python + venv**：不再内嵌 Python，改用系统 `python3` + 虚拟环境
- **sherpa-onnx Linux 原生包 + asar `.so` 实测**：本地 TTS / ASR 需要它
- **ffmpeg 三级解析 + 中文字体烧录**：已在一期 D14 修订中解掉大半（`@ffmpeg-installer/linux-x64` 随包、中文 SRT 正常渲染）
- **uv / 编码 CLI Linux 配方**：自动安装 uv、配置编码环境

#### 一期实际情况

**与假设不符的发现**：

1. **录屏在 X11 下已可用，ffmpeg 已随包**  
   一期 D14 修订后，录屏端到端跑通（`vp8 1728x1080` + opus 音轨），
   `@ffmpeg-installer/linux-x64` 确认随包分发，中文 SRT 通过 fontconfig 回退正常渲染。
   
   **「ffmpeg 三级解析 + 中文字体烧录」这条在一期已大部分解决**，
   二期只需补「用户手工指定 ffmpeg 路径」的逃生口（类似 `LUMII_BROWSER_EXECUTABLE`）。
   
   **调整**：从「需要改造」降级为「补一个环境变量覆盖」。

2. **语音在一期收窄为在线链路（D15）**  
   sherpa-onnx 本地 TTS / ASR 在一期被明确排除，原因是「`.so` 加载未验证 + 风险高」。
   
   **现在这个假设仍成立吗**？一期结束后，我们对 asar 打包、原生模块加载的理解更深了
   （`better-sqlite3` / `sharp` 都正常工作），**sherpa-onnx 的风险是否还那么高**？
   
   **需重新评估**：
   - asar 的 `asarUnpack` 对 `.so` / `.node` 文件有效（已实测：sharp 的 `libvips-cpp.so` 正常加载）
   - sherpa-onnx-linux-x64 的产物结构：是单个 `.node` 还是 `.node` + 多个 `.so`？
     若是后者，`LD_LIBRARY_PATH` 或 `rpath` 需要处理。
   - **若风险可控，sherpa-onnx 可以挪回二期**；若仍不确定，继续推迟到「有真实需求」时再做。

3. **系统 Python 的真实阻塞点在哪**  
   一期屏蔽了 Python 技能入口，但 `pythonSkills` 的矩阵判定已就位（`missing-runtime`）。
   **现在要补的是什么**？
   - 探测系统 `python3` 是否存在、版本是否 ≥3.8
   - 自动创建 venv（`python3 -m venv ~/.lumii/venv-py`）并写 shim
   - 依赖安装（技能的 `requirements.txt` 怎么装进 venv？）
   - **与内嵌 Python 的区别**：不再管 Python 本身的安装，但要确保 venv 干净隔离
   
   **这条在二期的优先级**：若用户明确要用 Python 技能，就做；若没有驱动，可以推后。

4. **uv / 编码 CLI 自动安装在一期已明确屏蔽（D15 编码 CLI）**  
   `codingCliAutoInstall` 矩阵判定是 Linux 屏蔽自动安装、只保留手动路径。
   
   **二期要做的是什么**？
   - 补 Linux 下 uv 的安装脚本（`curl ... | sh`，类似 Windows 的 `irm | iex`）
   - 补 `listLocalAcpToolsMetadata` 的 Linux `installCommand`（一期只改了提示词文案）
   - 自动探测 `~/.cargo/bin/uv` / `~/.local/bin/uv`（`cli-paths.ts` 已补候选）
   
   **结论**：这条改动清晰，若二期要做编码 CLI，直接按调查文档 P2 实施即可。

#### 调整建议

**按需求驱动，拆成三档**：

| 档位 | 内容 | 触发条件 |
|------|------|---------|
| **P1（用户明确要）** | 系统 Python + venv | 用户说「我要用 Python 技能」 |
| **P2（补全现有功能）** | uv / 编码 CLI Linux 配方 | 用户说「编码 CLI 在 Linux 上也要能自动装」 |
| **P3（技术探索）** | sherpa-onnx `.so` 加载实测 | 用户说「本地 TTS 在 Linux 上也要能用」 |

**ffmpeg 那条降级为「补环境变量覆盖」**（类似 `LUMII_BROWSER_EXECUTABLE`），5 分钟能做完。

## 第二期的真实优先级（2026-09-22 重排）

基于一期实际情况与外部前置条件的状态，**第二期应该先做什么**？

### 选项 A：补齐一期的外部前置条件

一期剩余的验收项（计划 §9 B 组）全是外部条件：

- **deb 真实安装 / 卸载**（需 root）
- **AppImage FUSE 双击**（24.04 已移除 libfuse2，结论是 deb 才是可用渠道）
- **注销重登验自启**（会杀图形会话）
- **通知点击回主窗口**（需人工点击）
- **渠道扫码登录、麦克风 ASR**（需硬件 / 人工）

**这些不是代码工作**，但**没验完就不能说「一期完成」**。

### 选项 B：先做无头形态

**理由**：
- 调查文档把它列为「形态 B」，是两种目标形态之一（与桌面并列）
- 一期已把「能启动 + 核心功能可用」在桌面形态验通，无头形态是**同一份代码的另一种启动配置**
- **技术风险小**：xvfb 是成熟方案，systemd user service 有标准模板，扫码打印是纯文本输出

**前置实测**（上面已列出，3 项）可以在 1 天内跑完。

### 选项 C：先做桌宠精灵图重写

**理由**：
- 这是一期**唯一屏蔽且有明确恢复路线**的核心功能
- 用户规划用精灵图重写，一期「不重写 Live2D 穿透」的决策就是为它留路

**阻塞点**：精灵图资源是否就绪？若短期内不就绪,这条推不动。

### 选项 D：按需补运行时对等

**理由**：
- 系统 Python / uv / sherpa-onnx 都是「用户要才做」的需求驱动型工作
- 没有明确需求前，做了也不知道对不对

**建议**：等用户说「我要用 X」时再做。

**一个实施教训**：无头模式最大的风险不是「起不起来」，而是**没有界面之后用户不知道下一步做什么**——
`lumii-ui send` 发完只回一个 `runId` 就等于把「怎么知道回复好了」丢给用户。补 `--wait` / `--text`
这类「终端里看得懂结果」的输出，和无头启动本身同等重要。

**第二个教训**：引导写好了，还要保证「用户能在真实安装里敲出这些命令」。第二期前期所有验证都跑在
源码树上（`node resources/app-ui-cli/lumii-ui.mjs`），直到收尾做 systemd 部署才发现打包产物里
既没有 CLI 入口、也没有常驻方式——**验收环境与交付环境不一致时，文档里的命令是假的**。
