# 无头模式用户引导体系设计（第二期补充）

> **问题**：无头模式下缺少 GUI 的交互引导，用户首次使用会很困惑  
> **目标**：参考 hermes-agent 的体验，提供完整的用户引导体系

---

## 1. 设计原则

### 1.1 用户痛点

在无头模式下，用户面临以下困难：

1. **不知道服务是否启动成功** — 没有窗口反馈
2. **不知道如何配置** — 缺少 GUI 设置界面
3. **不知道能做什么** — 没有菜单可以探索
4. **不知道哪里出了问题** — 缺少可视化的状态反馈

### 1.2 设计目标

1. **首次启动就有引导** — 显示快速开始指南
2. **状态透明可查** — 随时可以查看服务状态和配置建议
3. **场景化帮助** — 按使用场景（对话/浏览器/技能/渠道）分类
4. **交互式配置** — 提供配置向导，逐步引导用户完成关键配置

### 3.2 状态诊断命令（lumii-ui status）

**命令**：`lumii-ui status`

**功能**：

1. **服务运行状态**
   - 控制口是否就绪
   - Agent Runtime 是否初始化
   - 技能系统是否就绪

2. **关键配置项检查**
   - AI 模型提供商配置状态
   - 浏览器路径配置状态
   - 环境变量状态

3. **配置建议**
   - 缺失的配置项
   - 错误的配置项
   - 推荐的下一步操作

**输出示例**：

```
=== Lumii 服务状态 ===

✅ 服务运行中
   控制口: http://127.0.0.1:18795
   启动时间: 2026-09-22 22:38:37

✅ 核心服务
   ✅ Agent Runtime
   ✅ 技能系统 (22 个技能已加载)
   ✅ 目录管理器
   ✅ 配置管理器

⚠️  配置检查
   ❌ AI 模型提供商: 未配置
      → 运行: lumii-ui setup
      → 或手动运行: lumii-ui provider add
   
   ⚠️  浏览器控制: 未配置
      → 设置环境变量:
        export LUMII_BROWSER_EXECUTABLE=/usr/bin/google-chrome
        export LUMII_BROWSER_NO_SANDBOX=1
      → 重启应用

   ✅ 渠道服务: 就绪（未登录）

──────────────────────────────────────────
推荐下一步
──────────────────────────────────────────

1. 配置 AI 模型提供商（必需）
   lumii-ui setup

2. 创建第一个会话
   lumii-ui conversation create

3. 查看场景化使用指南
   lumii-ui guide
```

**实现方式**：

1. 添加控制口路由 `/status`
2. 主进程收集状态信息
3. 返回结构化 JSON
4. CLI 格式化输出

### 3.4 交互式配置向导（lumii-ui setup）

**命令**：`lumii-ui setup`

**功能**：逐步引导用户完成关键配置

**交互流程**：

```
=== Lumii 配置向导 ===

这个向导会帮助你完成 Lumii 的关键配置。

──────────────────────────────────────────
1/3 AI 模型提供商
──────────────────────────────────────────

Lumii 需要至少一个 AI 模型提供商才能工作。

支持的提供商：
  1. OpenAI (ChatGPT)
  2. Anthropic (Claude)
  3. 其他 OpenAI 兼容服务

请选择提供商 [1-3]: 2

请输入 Anthropic API Key: sk-ant-xxxxx

✅ 正在测试连接...
✅ 连接成功！已配置 Claude 3.5 Sonnet

──────────────────────────────────────────
2/3 浏览器控制（可选）
──────────────────────────────────────────

配置后，Agent 可以控制浏览器（打开网页、截图、点击等）。

是否配置浏览器控制？[y/N]: y

请输入 Chrome 系浏览器路径（留空跳过）: /usr/bin/google-chrome

✅ 已设置 LUMII_BROWSER_EXECUTABLE
⚠️  需要重启应用才能生效

是否启用 --no-sandbox 模式？
（在容器/无权限环境下需要启用）[y/N]: y

✅ 已设置 LUMII_BROWSER_NO_SANDBOX=1

──────────────────────────────────────────
3/3 完成
──────────────────────────────────────────

✅ 配置完成！

下一步：
  1. 重启应用以应用配置
  2. 创建第一个会话: lumii-ui conversation create
  3. 发送消息: lumii-ui send --session <会话ID> "你好"

💡 查看服务状态: lumii-ui status
💡 查看使用指南: lumii-ui guide
```

**实现方式**：

由于 `lumii-ui` CLI 是零依赖的，交互式向导需要用 Node.js 原生 API 实现：

```javascript
import { createInterface } from 'node:readline'

const rl = createInterface({
  input: process.stdin,
  output: process.stdout
})

function ask(question) {
  return new Promise(resolve => {
    rl.question(question, answer => resolve(answer))
  })
}

// 使用示例
const choice = await ask('请选择提供商 [1-3]: ')
```

## 6.4 实施记录（2026-09-22 收口）

设计稿之外，实施中补齐/修正的部分：

1. **`send --wait` 真正实现**：注册表里 usage 早就写了 `[--wait]`，但 `build()` 从没处理过它
   ——用户照着敲只会立刻拿到 `runId` 然后以为卡住了。现在 `--wait [<秒>]` 会轮询
   `conversation:messages` 直到本轮回复落库，打印正文；模型调用失败（`contentJson.llmError`）
   时给出非零退出码，脚本能感知。
2. **`context messages --text`**：assistant 消息的正文在新格式里存在
   `contentJson.assistant_parts.parts`，`content[].text` 只覆盖旧消息——只读后者会打印空字符串，
   看起来像「Agent 没回话」。默认仍输出原始 JSON（`docs/test/lumii-cli/lib/cli-harness.mjs`
   等测试工具依赖该契约），`--text` 才渲染可读转录。
3. **渠道命令**：无头模式没有渲染进程，扫码登录原先只能由界面触发。新增
   `/channel/login|status|logout` 路由 + `lumii-ui channel` 命令，二维码由主进程打印到
   **应用所在终端**（CLI 侧只回报状态，避免用户以为没生效）。
4. **`provider show|set|test`**：无头模式必须能在命令行完成模型配置。密钥只回 `hasApiKey`；
   换类型时清空 baseUrl 与模型候选（否则会留着上一个服务商的端点/模型，看着配好了其实不通）。
5. **`status` 的「已配置」判据**：`loadProviderConfig()` 永远返回对象（有默认值），
   必须按「启用 + 有模型 ID + 非本地类型需有 Key」判断，与 `provider-probe.ts` 保持一致。

## 7. 风险与依赖

### 7.1 技术风险

1. **零依赖限制** — `lumii-ui` CLI 不依赖 npm 包，交互式向导需要用 Node.js 原生 API
2. **控制口路由扩展** — 需要在主进程添加新的路由，确保不影响现有功能

### 7.2 用户体验风险

1. **文本过长** — 终端输出过长可能让用户困惑，需要精简关键信息
2. **场景覆盖不全** — 初期可能只覆盖常见场景，需要根据用户反馈持续补充
