## 一、目标

第 9 片处理"写法陈旧"，本片处理**"根本没用令牌"**——直接写 `#ef4444` 当错误红、`rgba(255,255,255,.5)` 当按钮上的白字。这些是第 7 片之后剩余的主要工作量。

按语义分两块：

- **B1 语义色**：有明确对应令牌（error / success / warning / info / accent）却写了字面量。
- **B2 中性色**：`#fff` / `rgba(255,255,255,α)` / `rgba(0,0,0,α)`——语义是"前景 / 背景 / 描边"，需要判断是"随主题变"还是"固有色"。

## 三、任务拆分

### 3.1 B1 语义色按"色值 → 令牌"批量映射

建一张映射表（**值必须精确相等**才批处理，近似色单独判断）：

| 字面量 | → 令牌 | 注意 |
|---|---|---|
| `#ef4444` | `--mt-error` | dark 下 `--mt-error` 就是 `#ef4444`，light 下不同 → 换主题后会变，这是**期望行为** |
| `#22c55e` | `--mt-success` | 同上 |
| `#f59e0b` | `--mt-warning` | 同上 |
| `#3b82f6` | `--mt-accent-500` | dark 值；light 下 `--mt-accent-500` 是 `#2a76f6` |
| `#60a5fa` | `--mt-accent-400` | dark 值 |
| `#dc2626` | `--mt-error-dark` | 需核对该令牌三主题下是否都有（08 片已确保） |
| `#f87171` | `--mt-error-light` | 同上 |
| `#16a34a` | `--mt-success-dark` | 同上 |
| `#34d399` | `--mt-success-light` | 同上 |

**近似色**（如 `rgba(245,158,11,0.1)` vs `--mt-warning` 的 `#f59e0b`）——`rgba(245,158,11,0.1)` 的 RGB 就是 `#f59e0b`，属于精确匹配，可批处理。**但形如 `rgba(234,179,8)`（`#eab308`）这类调色板色不在此列**，它们属于 [11 片](./11-图表调色板令牌化.md) 或 [13 片](./13-上下文分类色板.md) 的对象。

### 3.2 B2 中性色：先判断语义，再决定写法

**判断规则（关键）**：

| 场景 | 语义 | 正确写法 |
|---|---|---|
| 深色底上的叠加层（如卡片 hover、分隔线） | "在当前背景上加一点前景色的透明叠加" | `color-mix(in srgb, var(--mt-fg-1) 8%, transparent)` |
| 强调色 / 深色底上的**文字** | "强调色底上的前景" | `var(--mt-fg-on-accent)` |
| 独立于主题的固定层（宠物坞、预览黑底） | "这一层有自己的底色" | 保留字面量，或建局部作用域（见 [12 片](./12-canvas与宠物色层收敛.md)） |
| 阴影 | "投影" | `--mt-shadow-*` 系令牌 |
| 遮罩 | "模态背后的压暗层" | `--mt-bg-overlay` 或 `rgba(var(--mt-fg-rgb), α)` |

**为什么叠加层用 `color-mix` 而不是 `rgba(var(--mt-fg-1-rgb), α)`**：仓库当前只有 `--mt-fg-rgb`（主文字色三元组），没有 `--mt-fg-1-rgb` / `--mt-fg-3-rgb` 等分档三元组。若为每档补三元组，会一次性新增 4 个变量 × 3 主题块 = 12 行定义（08 片的守卫测试要求三块同步）。用 `color-mix(in srgb, var(--mt-fg-1) 8%, transparent)` 可以直接基于任意令牌的**实值**混合，零新增变量。

> 仓库已有 `color-mix()` 437 处使用，且 `UsageChart.tsx:293` 的 `cursor={{ fill: 'color-mix(in srgb, var(--mt-accent-500) 6%, transparent)' }}` 证明它在 SVG 属性里也能用。

### 3.3 `#fff` 的两种命运

第 7 片已把 38 处 `color: white` 改成 `var(--mt-fg-on-accent)`。本片处理剩下的 70 处：

- `color: #fff` 且位于有色底上 → `var(--mt-fg-on-accent)`
- `background: #fff`（浅色卡片）→ `var(--mt-bg-elevated)`
- `border: 1px solid #fff` → 判断是"强调色底上的描边"（`--mt-fg-on-accent`）还是"独立层描边"（保留）

**已知的一处例外**：`components/ui/Switch/Switch.module.css` 的 `#fff` 第 7 片刻意保留并写了注释（中性控件滑块，开关底是固定的灰/绿，白滑块不随主题变）。

## 四、验证

1. `pnpm typecheck` + `pnpm test:all`（基线 298 文件 / 2716 passed / 0 failed）。
2. **三主题截图对比**：本片的改动**会**产生视觉差异（这是预期——原本不随主题变的颜色现在会变），所以不能再用"零差异"当判据。判据改为：
   - `probe-theme-colors.mjs` 的整图数值**变化幅度可解释**（如 light 主题暖度不因改 `#ef4444` → `--mt-error` 而偏移超过 ±2）。
   - **逐项抽查**：随机取 10 处改动，在 light / eye-care / dark 三个主题下截图，确认该元素颜色符合预期且对比度达标。
3. **护眼主题专项**：护眼是新增主题，此前大量硬编码在其下显示的是"深色主题的值"。本片改完后，`rgba(255,255,255,α)` 类叠加层会开始跟随暖色调——**这部分变化最大，需要重点截图核对**。

## 七、执行记录（2026-09-20）

### 7.1 范围收窄：只做**有精确映射**的

计划把 B1 估为"约 900 处"，实测（09 清完 fallback 后）只剩 **268 处语义色 + 157 处中性色**——
计划那个数含了 09 已处理的部分。经与用户确认，本片只做两类：

- **B1 有精确令牌映射的**（dark 下值完全相等）
- **B2 语义明确的**（前景白 → `--mt-fg-on-accent`）

剩下约 190 处调色板色（`#0ea5e9` / `#8b5cf6` / `#fbbf24` 等）**没有对应语义令牌**，
归入 11–14 片。

### 7.4 顺带修的两处真缺陷

`::selection` 规则只写了 `[data-theme='light']` 与 `[data-theme='dark']` 两套，**eye-care 无分支**。
`global.css` 的全局规则有 eye-care 分支，但 `ChatInput` / `ChatMessage` 的局部规则**选择器更具体**，
会覆盖全局 → 护眼主题下文本选中是"蓝底白字"，在暖色页面上很突兀。已补 eye-care 分支。
