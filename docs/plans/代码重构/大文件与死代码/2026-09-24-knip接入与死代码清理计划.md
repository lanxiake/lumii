### 4.2 K1 —— 依赖声明（**最高优先，防打包崩溃**）

58 条 unlisted 按风险分四组。**这一阶段真正的风险不在 package.json 本身，而在它会翻转 `electron-vite` 的外部化决策。**

取证（2026-09-24，`out/main/index.js` 今天 18:35 构建、配置 09-23 未变）：

```
@anthropic-ai   2 次   ← external 模块会以字符串出现（探针自校验通过）
isolated-vm     8 次
better-sqlite3  8 次
earendil        0 次   ← pi-ai / pi-agent-core / typebox 现在是【被内联打包】的
```

而 `electron.vite.config.ts:230` 的注释写「pi-ai / pi-agent-core 已通过 externalizeDepsPlugin（默认规则）外部化」——**这句是错的**：它们没在 `apps/windows/package.json` 里，插件不会外部化它们。同一文件 177 行的设计意图是反的：「只外部化 electron，其他依赖内联打包，避免 pnpm 传递依赖无法被 electron-builder 正确打包」。

| 组 | 内容 | 改法 | 为何安全 |
| --- | --- | --- | --- |
| K1-1 | `packages/browser-control` 的 `ws`（4 处） | 补进该包 dependencies | 不影响 apps/windows 的外部化集合 |
| K1-2 | 根 `scripts/` 用的 `@xenova/transformers`/`sharp`/`sherpa-onnx-node`/`isomorphic-git` | 补进**根** devDependencies | 根不参与 electron-builder |
| K1-3 | `apps/windows` 的 `pi-agent-core`/`pi-ai`/`typebox`（27 处） | **声明 + 同步加进 `externalizeDepsPlugin.exclude`** | 保持内联（行为不变），去掉对 `.npmrc` hoist 的隐性依赖 |
| K1-4 | `tar`（skill-exporter）/ `isolated-vm`（skill-sandbox） | **先取证**：是否真装、是否 optional | `isolated-vm` 已在 `external` 正则里但不在 `onlyBuiltDependencies`，疑似未构建 |

**退出条件**：`knip --include unlisted` 归零或每条都有书面豁免理由；`pnpm typecheck` + `test:all` 全绿；`git diff pnpm-lock.yaml` 只有预期改动。

#### K1 执行结果（2026-09-24）

`unlisted` **58 → 1**（只剩下面的决策项），`pnpm typecheck` 全绿，`pnpm verify` 见进度日志。

| 组 | 做了什么 | 证据 |
| --- | --- | --- |
| K1-1 | `packages/browser-control` 补 `ws: ^8.16.0`（与 apps/windows 同范围，不引入新版本） | 锁文件只给该 importer 加了 3 行 |
| K1-2 | 根 `package.json` 补 devDependencies：`@xenova/transformers`、`isomorphic-git`、`sherpa-onnx-node`、`sharp`（版本对齐 apps/windows） | 锁文件 `.` importer 从 `{}` 变为 4 条 |
| K1-3 | `apps/windows` 声明 `pi-agent-core` / `pi-ai` / `typebox` / `tar`，**同时**加进 `externalizeDepsPlugin.exclude` | 重建后 `out/main/index.js` **字节数完全相同**（6,184,081）；探针 `earendil` 仍为 0 |

**验证方法（可复现）**：改完重跑 `electron-vite build`，再用同一套探针比对新旧 bundle。`external` 的模块会以字符串形式出现（同文件 `@anthropic-ai` 有 2 处，`isolated-vm` 8 处），被内联的不会（`earendil` 0 处）。字节数相同即证明外部化决策未变。

**顺手修正了一处错误注释**：`electron.vite.config.ts` 原写「pi-ai / pi-agent-core 已通过 externalizeDepsPlugin（默认规则）外部化」——与实测相反（它们一直是被内联的，只因没声明）。已改写为准确描述，并说明为什么必须靠 `exclude` 的显式排除来维持内联。

> 🔶 **K1-4 决策项：`isolated-vm` 未安装，技能沙箱的"完整隔离"路径从未生效**
>
> - `apps/windows/src/main/skill-sandbox.ts:105` 用 `require('isolated-vm')` 尝试加载完整沙箱，失败则落到 **"降级模式（Function 构造器，安全性较低）"**，只打一条 **WARN**（按[error 日志盲区]的口径，WARN 不进 error 文件，等于隐形）。
> - 实测：`isolated-vm` **既没在任何 package.json 声明，也没装进 node_modules**（`node_modules/.pnpm/isolated-vm*` 无匹配）→ 该分支**必然**走降级。
> - 代码自己在 WARN 里写「生产环境建议安装 isolated-vm 以获得完整隔离保护」——但依赖没声明，这个"建议"**根本无法被执行**。
> - 要注意：`isolated-vm` 是原生模块，装它要同时处理 `onlyBuiltDependencies`（当前没有它）、Electron ABI 重建（postinstall 只重建 better-sqlite3/sharp）与 electron-builder 打包。
>
> **三个选项**：(a) 声明 + 配原生构建 + 验证打包（工作量大，且要过隔离实例冒烟）；(b) 保持现状，但把「沙箱降级」升成 ERROR 级日志并在文档里写明这是已知状态；(c) 删掉完整隔离分支，只留降级实现并明确它不安全。**这是安全语义决策，需要定夺。**

### 4.9 K5 —— 清 1380 条 unused exports/types（✅ 已完成）

**与计划的偏离**：原计划是「批量 `knip --fix`」，实测后**改为自研 AST fixer**。
下面每一条都有实测支撑。

#### 一、为什么不用 `knip --fix`

先搭最小可复现工程穷举了各种导出形态，确认它的**语义是对的**（只去 `export` 关键字，从不删声明）：

| 输入 | 输出 | 判定 |
| --- | --- | --- |
| `export const x = 1` | `const x = 1` | ✓ |
| `export type T = ...` | `type T = ...` | ✓ |
| `export { a, b }` | 整行删除 | ✓ |
| `export default function Named(){}` | `function Named(){}` | ✓ |
| `export default Comp` | 行内容删空 | 合法但留空行 |
| `export default () => null` | **整行消失，表达式丢失** | ✗ |
| `export default { a: 1 }` | **整行消失** | ✗ |

真实数据里 120 条 default **全是 `export default <组件名>`**，落在「合法但留空行」那格 —— 危险形态不存在。
**但它写回文本的方式不能要**（本仓无 prettier/eslint，没有 formatter 可清理）：

| 症状 | 实测规模（试点 57 个文件） |
| --- | --- |
| 多行 `export { ... }` 删项后留 `\r\n \r\n` 残渣 | 11 个文件有残留空格行 |
| 整句删完留孤立的 `;` 行 | 4 个文件有残渣空行 |
| 单行列表删项后留 `{ SCHEMA_VERSION,  }`（双空格 + 尾随逗号） | 见 §4.9 抽查 |
| 追加 `export {};` 时用 LF，毁掉相邻行的 CRLF | — |

**改法**：`knip` 负责判定（报告里的 `name`/`line`），**TS 编译器 API 负责定位与改写** ——
删列表项时连逗号与缩进一起删、删整句时连整行一起删、文件失去全部 import/export 时补 `export {};`。

#### 二、dry-run 抓出的两个真 bug（都靠自检拦下）

1. **连续列表项的删除范围重叠** → 16 个文件语法错误（`'}' expected`）。
   相邻两项各自「删自己到下一项之间」，范围交叠。改为把连续命中项**合并成区间**。
2. **`async` 在 TS AST 里也是 modifier** —— 按「删第一个到最后一个 modifier」会把
   `export async function` 变成 `function`（**丢 async**），实测 12 处编译错误。
   改为只删 `export`/`default` 两个，逐个删、从后往前应用。

另有一条**行号陷阱**：TS 把孤立的 `\r` 也当换行，而 `apps/windows/src/main/app-ui-control/annotate.ts`
的行尾是 `\r\r\n`（100 处，**HEAD 里就是这个，不是本轮造成的**），于是 TS 数出的行号是真实行号的
双倍（实测某常量 TS 说第 29 行、knip 与文件都是第 15 行）。fixer 的行号一律按 `\n` 计数，与 knip 对齐。

#### 三、三类盲区 —— 删了会编译失败（实测崩 9 处）

knip 的 unused 判定有三类系统性盲区，**必须排除，不能照删**：

| # | 形态 | 实例 | 为什么看不见 |
| --- | --- | --- | --- |
| 1 | 内联动态类型导入 | `Partial<import('./voice-events.js').VoiceAsrConfig>` | knip 不追踪 `import('...').Type` |
| 2 | 动态 import 后展开 | `const m = await import('./x'); { ...m }` → `s.DAILY_RETENTION_DAYS` | 静态追不到展开后的成员 |
| 3 | re-export 链 | barrel 同时 `export { X }` 与 `export { X as default }` 时，knip 只报**源头**、不报 barrel 那行 | 消费者正是从 barrel 取 named（`SettingsPage.tsx` 实测），只删源头会让 barrel 悬空 |

处置：
- 第 1、2 类 → 给符号加 `/** @lintignore <理由> */`，配合 `knip.jsonc` 的 `"tags": ["-lintignore"]`。
  选标签而非「按文件忽略 issue 类型」是因为后者会连带漏掉同文件将来新增的问题，且理由写在代码旁更好追溯。
- 第 3 类 → **在 K5 fix 后自愈**：把同 barrel 的 `export default` 那条删掉，「一个源符号被两个导出名转发」
  的情形就不存在了，knip 又能正确追踪。所以只留了 6 个标签，另 2 个加完立刻被 knip 报成
  `Unused tag`（多余的），已移除 —— 这条 hint 反而是「假阳已消失」的证据。

**全仓 `import('...').Type` 形态共 53 处**，是这套盲区的来源（`k5-find-falsepos.mjs` 扫描得出 7 条与 claims 相交）。

#### 四、清完之后暴露的 4 个死文件（已删）

### 4.10 K5-2 —— `exports`/`types` 升 `error`（✅ 已完成）

**目标**：补上 K4 探针 B 的缺口（§4.5）—— 已有文件里新写的没人用的导出，此前三道门禁全漏。

**方案**：`ignoreExportsUsedInFile: true` + 把两类从 `warn` 升为 `error`。

**为什么必须是这两步一起**：knip 的这两类混装两种含义（§2.3）——

- **A 类真死**：全仓无人 import，**且**文件内也没用
- **B 类仅文件内使用**：`export` 关键字多余，但符号活着 —— **占存量的 45.9%（634 条）**

要拦 A 类就得能把 B 类摘出去，否则写一个只被本文件用的 `export interface Props` 就红 ——
门禁因假红失去意义。这正是 K4 当时只敢设 `warn` 的原因。

`ignoreExportsUsedInFile` 就是 knip 的分离开关。**实测**（最小工程造 7 个符号，A 类 4 / B 类 3）：

| 配置 | 报出 |
| --- | --- |
| 默认 | 7 条（A 类 4 + B 类 3） |
| `ignoreExportsUsedInFile: true` | **4 条，只剩 A 类** |

它还支持按符号种类细调（`class` / `enum` / `function` / `interface` / `member` / `type` / `variable`），
本仓先用 `true` 全摘。

**升完的实测探针**（在 `apps/windows/paths.ts` 临时造 6 个符号，跑完即还原）：

| 造的东西 | 类别 | 结果 |
| --- | --- | --- |
| 无人用的 `export function` | A 类 | **被报，`check:knip` exit 1** ✓ |
| 无人用的 `export const` | A 类 | **被报** ✓ |
| 无人用的 `export interface` | A 类 | **被报** ✓ |
| 文件内调用的 `export function` | B 类 | 未报（有意放行） |
| 被文件内使用的 `export interface` | B 类 | 未报（有意放行） |

**副产物**：开 `ignoreExportsUsedInFile` 后，K5 里加的 4 个 `@lintignore`
（`asset-checkup.ts` 两个、`voice-events.ts` 两个）被 knip 报成 `Unused tag` ——
那些类型**在文件内也被使用**，knip 现在不报它们了，标签成了多余，**已移除**。
剩下 2 个仍必要（`DAILY_RETENTION_DAYS`、`VoiceTtsPreviewOverride`）。

**代价**（已写进配置注释）：新写的「仅文件内使用」的导出不再有任何门禁拦，会慢慢积累
—— K5 清掉的那 634 条 B 类就是这么攒出来的。要看得把这一项临时设回 `false` 再跑 `check:knip:report`。

**假阳出口不变**：三类盲区（§4.9）仍在，遇到时加 `/** @lintignore <理由> */` 放行，**不要抬预算**。

**预算未动**：error 类仍是 **9**（files 1 + unlisted 1 + dependencies 3 + devDependencies 4），
`exports`/`types` 存量为 0，所以升 error 后 `pnpm check:knip` 直接 **exit 0**。
（K4-2 把 dependencies / devDependencies 清零后，预算已调为 **2**，见 §4.11。）

### 4.14 新发现的盲区：私有且零引用的声明（`noUnusedLocals` 没开）

`apps/windows` 加 `--noUnusedLocals` 跑 `tsc --noEmit`（只探针，**没有改 tsconfig**）。

```
315 条 error = 144 未用 import + 121 私有死声明（+ 36 待人工确认 + 8 成员 + 4 局部 + 2 类属性）
```

这 31 条只是这个类的一小部分 —— 同类的实例还有 `DEFAULT_BROWSER_CONTROL_PORT`、

`useQuery.ts` 的 `clearQueryCache`/`invalidateQuery`、`services/agent-service.ts` 的 `getAgent` 等。

**为什么三道门禁都不报**：

| 门禁 | 为什么看不见 |
| --- | --- |
| `check:wiring` | 只扫跨进程名字配对（六类断线），不扫"声明了没人用" |
| `check:knip` | 只报 **export** 出去没人 import 的；私有声明不在它的模型里 |
| `pnpm typecheck` | `noUnusedLocals` **没开**（全仓 tsconfig 都没有），而 `noUnusedParameters`/`noUnusedLocals` 是唯一直查这一类的开关 |

**代价是它一直在长**：K5-1 摘掉 1372 个 `export` 时，凡是"摘完就没人用"的都会掉进这个类
（本次 31 条里有 31 条就属于这种情况）；而这类已经不导出、不被引用，**没有任何判据会再提醒**。

**要不要开这个开关**：先测再定。315 条里 144 条是未用 import（机械可删）、121 条是私有死声明
（多数可删、少数是待接线）。**`packages/` 还没探**。开 `noUnusedLocals` 等于把这道门禁一次性
立起来，代价是必须先清完这批存量 —— 是否做、按什么预算做，**属独立决策，本批未动**（探针脚本与
分类脚本都在会话临时目录）。

> 与 `check:wiring` 的关系：那是 K2 以来"没接线"的主力判据，但它和 knip 都**不覆盖这一类**。

#### 一、两版改写器：为什么必须文本拼接

第一版用 `ts.createPrinter` 重印整个文件，两个后果：① **全文重排**（2 空格缩进→4 空格、补分号、
删空行、多行 import 折叠成单行）；② **行尾 LF→CRLF**。127 文件被无意义改写，diff 达 3.7 万插入 /
4.4 万删除。更糟的是它**静默跳过了一半输入**（多行 import 里 specifier 的行号 ≠ import 起始行号，
按行取 issue 取不到），而当时的"验证"跑的是**不带** `--noUnusedLocals` 的 tsc —— 那个命令不管删没删
都是绿的。**这是本轮最值得记的教训：dry-run 报的"232 条清除"只是把输入条数求和，从没验证过实际删除。**

第二版改为**文本拼接**（K5-1 的做法）：AST 只算"要删的字节范围"，在原文本上 splice，其余字节不动。
删除量立刻降到 4915 字节（纯删、零重排）。

#### 二、两次踩坑（都已升级为工具里的硬门禁）

1. **逐条算范围会重叠**：删「最后一个元素」吃它**前面**的逗号，删「倒数第二个」又吃它**后面**的逗号
   —— 同一个逗号被两条范围覆盖，逆序 splice 后坐标漂移，把 `}` 一并吃掉（实测 5 个文件语法坏掉，
   `TS1005: '}' expected`）。修法：**按 import 声明成组算范围**，连续被删段合并为一个范围，天然不重叠。
2. **重叠检测自己写错了**：`ranges[i][1]` 在存 `{range, issue}` 对象的数组上取下标，恒为 undefined，
   比较永远为 false —— 检测形同虚设，所以第一版没能自保。

新增两道硬门禁（写进工具，此后每批都跑）：

- **解析门禁**：改完的文本必须能被 `ts.createSourceFile` 重新解析，`parseDiagnostics` 非空则整文件拒绝写入；
- **对账**：`输入条数 = 覆盖 + 超范围 + 未匹配 + 失败`，不平就报（本次 234 = 162 + 72 + 0 + 0）。
