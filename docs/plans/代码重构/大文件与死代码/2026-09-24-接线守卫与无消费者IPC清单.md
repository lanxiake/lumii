## 一、为什么正则探针在这个仓库必然撒谎

实测踩过三种形态，正则全部误报：

| 形态 | 例子 | 正则为何错 |
| --- | --- | --- |
| 模板字符串拼 channel | `ipcRenderer.invoke(\`${prefix}:startLogin\`)`（`channel-api.ts` 的工厂） | 报出 16 个「孤儿 handler」全是假的 |
| 常量表 | `ipcMain.handle(PET_IPC.switchMode, ...)`、`FILE_PREVIEW_IPC.open`（在 `shared/*.ts`，还带 `as const`） | channel 名根本不是字面量 |
| 监听封装 | `createPetEventListener(...)`、`subscribeMainEvent(...)`、channel 名放数组里遍历注册 | **形态是开放的，追不完** |

另有两条判据坑，会让入口可达性分析把 main 一半判成死代码（实测 549 → 41）：

- TS/ESM 的 `.js` 说明符指向 `.ts` 源文件（`'./voice/model-manager.js'`）
- `await import()` 动态加载

以及一条容易搞错的：类型位置的 `import('./x')` 是 `ImportTypeNode`，**不算运行时依赖**。

「没人 import」也 ≠ 死代码：barrel（`index.ts`）会 re-export 让模块看着像活的，必须从真入口做可达性遍历才分得出来。

## 二、守卫的六类判定

| # | 判定 | 危害 |
| --- | --- | --- |
| ① | main 注册了 handler，preload 从不引用 | renderer 永远调不到 |
| ② | preload 引用了，main 没实现 | **调用必然 reject**（活 bug） |
| ③ | main 推送事件，但无人监听 | 事件石沉大海 |
| ④ | 工具导出但没进 `ALL_BUILT_IN_TOOL_CONFIGS` | 模型看不到这个工具 |
| ⑤ | 从真入口走不到的文件 | 死文件 |
| ⑥ | preload 暴露了，但 renderer 从不调用 | 链路通却没消费者 |

入口取四个：`main/index.ts`、`preload/index.ts`、`preload/webview-selection.ts`、`renderer/main.tsx`。

**棘轮机制**：存量断线记进 `scripts/wiring-baseline.json`，守卫只拦新增。`--strict` 供 CI（已接入 `pnpm verify` 与 `.github/workflows/ci.yml` 的 typecheck job），`--update` 在清理后收紧基线。

### ⑥ 的判据（刻意保守）

两级豁免：

1. AST 找 `electronAPI.<ns>.<method>` 链——覆盖 `window.` 前缀、`?.` 可选链、`as`/`!`/括号包裹
2. **方法名只要在 renderer 里以任何 `.name` 形式出现过就豁免**

第 2 条是因为 renderer 大量使用**转存**：

```ts
// renderer/hooks/business/useAgentRuntime/ 下 5 处
const api = window.electronAPI?.agentRuntime
api.isEnabled()
```

转存之后，属主既不在 AST 里也不在正则里，只能按名字兜底。代价是 `list` / `read` / `status` / `getState` 这类通用名会被全豁免（漏报），换的是不误报——**把活的判成死的，会让人直接去删活代码**。

> 因此 ⑥ 的数字是**下界**。§4 的 38 个里，B 组的 3 个（`updater.getState`、`updater.getConfig`、`news.latest`）就是 ⑥ 漏报、靠命名空间级交叉验证补出来的：`updater` 和 `news` 在 renderer 里**连转存入口都是 0 次**。

**消费者不只在 renderer 里**（2026-09-24 补）。E2E 与验证脚本会通过 CDP 在 renderer 上下文执行代码，调用藏在**字符串字面量**中——`verify/pet-sprite/check-pet-passthrough.mjs` 就是靠 `evaluate('window.electronAPI.pet.getMouseIgnoreState()')` 取证的。所以 ⑥ 也扫 `verify/` 与 `docs/test/` 下的脚本，**但只认字符串字面量内部**。

为什么强调「只认字面量」：`e2e-harness.mjs` 的注释里提过 `app.quit()`，若按纯文本匹配就会把那个真的无消费者的方法误豁免。实测双向验证过——字符串命中会豁免（30 → 29），注释命中不会。

### ⑥ 顺带补上的 ③ 盲区

③ 只查「main 推的事件 preload 有没有注册监听」，查不到「preload 注册了但 renderer 从不订阅」。实例：`updater:state-change` —— `updater-service.ts:208` 在推，`preload/index.ts` 也 `createEventListener` 了，但没人调 `updater.onStateChange`，事件实际无人接收。

### A 组 · renderer 本就不该有的能力（4 个）— ✅ 已执行

## 五、删除方案与影响

两种删法，影响不同：

| 方案 | 做法 | 后果 |
| --- | --- | --- |
| 只删 preload 侧 | 删 `electronAPI` 上的入口 | main handler 立刻变成孤儿 handler，**守卫 ① 会报出来** |
| 两处都删 | preload + main handler | 完整清理，但等于删掉这些能力本身 |

**建议分组处理**：

- **A 组（4 个）**：✅ **已执行**（见 §3 第四批）。这是能力收窄，与 B 层「不暴露文件操作」的既有取向一致
- **B 组（10 个）**：先别动。这更像「产品决定」而不是「代码卫生」——要删的话应当同步删 `updater-service.ts`
- **C 组（12 个）**：按产品意图逐个看，无统一答案
- **D 组（12 个）**：`pet` 那 4 个已处理（§3 第五批，其中 `getMouseIgnoreState` 判定为保留）；剩余 8 个逐个看
