# 云同步 "Could not find 864b3aea…" 修复记录

> 日期：2026-11-03
> 状态：**对象库已修复并验证**；gc 收尾中

---

## 1. 症状

云同步状态长期停在 `error`：

```
当前状态：错误 · Could not find 864b3aea3c0014c2c760611b22ae2fbdbfd901ce.
```

日志里这个错误从 **2026-10-30 22:15** 第一次出现，之后 11-02、11-03 反复出现，
累计 571 条。每轮的模式完全相同：

1. Agent 处理冲突，`resolve` 返回 `started`；
2. 落决 commit 生成成功（`fe33171c`、`a4b0aa0` 等）；
3. 紧接着 status 报 `Could not find 864b3aea…`；
4. state 仍为 `conflict`，`remote.headOid=null`、`pushed=false`；
5. 工作区没有落盘（源码消失，只剩 test-shots）。

历史日志里已经有多轮体检得出同一个结论并明确写了「禁止再 resolve，须用户重建仓库」——
**但没人做，于是每轮又试一次，循环了四天。**

## 2. 根因（fsck 定位）

```
broken link from  commit 912ba1cca52b4fc2b59ea9a8a24ab7c57024ad0e
              to  commit 864b3aea3c0014c2c760611b22ae2fbdbfd901ce
missing commit 864b3aea3c0014c2c760611b22ae2fbdbfd901ce
missing blob   a3e460aeed3a03e5d1f1b8cd5bd3fff355ffcaf8
```

- `912ba1cc`（2026-10-30 的本地提交）的**父提交 `864b3aea` 在对象库里不存在**；
- `912ba1cc` **不在远端链上**——它是一条本地生成、从未推送成功的提交；
- 因此本地 `main` 的祖先链从那里断开，任何需要走完整历史的操作
  （`status` 的 ahead/behind、`fetch` 的 commit-graph 写入、冲突落决）全部失败。

关键判断：**远端 `origin/main` 是健康的**（能完整 `log`，`fsck` 无坏对象）。

## 3. 修复

前置：**停掉应用**（`scripts/stop-dev.ps1`）。云同步在活跃地跑冲突处理循环，
边修边写永远修不完——实测修复前 HEAD 在一小时内自己前进了三次。

备份：`.git` 整目录复制到 `~/.lumii/sync.chloroplast-backup-<时间戳>`（6.4G），
另单独备份了当时暂存的 `memory/agent-memories.jsonl`。

```bash
cd ~/.lumii/sync
git fetch origin                    # 先把 origin/main 更新到最新
git reset --soft 8876626dc           # 本地 main → 健康的 origin/main（保留工作区文件）
git read-tree HEAD                   # 重建 index（原 index 还引用着缺失的 blob）
git reflog expire --expire=now --all # 让游离的 912ba1cc 失去 reflog 引用
git prune --expire=now               # 清掉它
```

- 用 `--soft` 而不是 `--hard`：**工作区文件一个都不动**，只移动分支指针与 index。
- 必须先 `reflog expire` 再 `prune`：只做 prune 时 `912ba1cc` 还被 reflog 保住，
  坏链一直在（第一次 prune 后 fsck 仍报同样的错）。
- `git read-tree HEAD` 是必需的：reset 之后 `status` 仍报缺 blob，因为 index 里
  还引用着那个不存在的 `a3e460ae`。重建 index 后才恢复。
