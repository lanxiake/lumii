### 关键发现（截至 P1.5）

- **chatlog 对微信 3.9.8.15 完全可用**：密钥提取 + 解密 + HTTP 读取全链路打通，回答设计 §9 的 Q1 = **是**。
- 解密后可读 **49,614 条消息**，跨度 **2024-07-31 ~ 2026-10-05**，覆盖 1:1、群聊、公众号。
- 两个实操坑：① 官方 release 已撤下，必须自建（需 C 编译器，cgo 依赖 go-lame/go-silk）；② `decrypt`/`server` 必须显式 `--version 3`，否则报 `unsupported platform: windows v0`。
- ⚠️ 安全提示：chatlog 自身日志会以明文打印 DataKey（`server config` 行），证据留存时需过滤。

### ⚠️ 重大负面发现：chatlog 不读 WAL（影响「实时」）

**结论**：chatlog 只能读到**已 checkpoint 进主库**的消息；仍留在 `-wal` 里的最新消息**不可见**。故 **chatlog 不能作为实时来源**。

**证据链**：
1. 源 `Msg\Multi\MSG4.db-wal` = **3.21MB**，mtime 22:03:51（用户刚发的消息写在这里）；主库 `MSG4.db` mtime 停在 11:16。
2. chatlog 复制出的 work-dir `MSG4.db-wal` = **0 字节**（它新建了自己的空 WAL，未导入源 WAL）。
3. 解密产物最新消息 = **2026-10-05 17:10**，当天（10-06）消息为 0。
4. **决定性实验**：把源 `MSG4.db` + `MSG4.db-wal` + `MSG4.db-shm` 一起复制到独立目录再解密 → 结果**完全相同**（3932 行 / 最新 10-05 17:10）。即 chatlog 明确不合并 WAL 帧。
5. 佐证：社区同类工具（wechatauto-replica）**专门实现了 WAL 增量合并**（按 salt 过滤帧），说明这是已知难点。

**影响**：
- 「历史读取」（P1.5）仍然可用 —— checkpoint 之前的数据完整。
- 「实时」（P1.6）**不成立**：webhook 机制虽已正确注册，但触发时机取决于 WeChat 何时 checkpoint，实测**滞后 > 1 天**。
- 该发现直接改变选型：读层需要**补充 WAL 感知能力**，或实时改用其他机制（Hook / UI 监听 / iLink）。

**闭环验证（2026-10-06 22:27）**：用户退出并重开微信后——
- 源 `MSG4.db-wal` **3.21MB → 0.03MB**（checkpoint 触发）；
- chatlog 自动重解密，行数 **3932 → 3937（+5）**，最新时间 **10-05 17:10 → 10-06 22:03**；
- 此前不可见的「发送消息测试」**立即出现**（+5 恰为今天 WAL 中的 4 条公众号 + 1 条 filehelper）；
- 用户重启后**又发的消息仍不可见**（再次滞留新 WAL）。

→ **结论凿实**：chatlog 只在 WeChat checkpoint 后可见数据；而 WeChat 实测 >1 天不 checkpoint（仅重启时触发）。**chatlog 不能作为实时来源，只能做历史读取。**

### ✅ 解决方案：自研 WAL 感知直读（已验证可行）

**思路**：chatlog 之所以读不到 WAL，是因为它用**页级解密**自己实现读库；而**真正的 SQLCipher/SQLite 在打开 `db + -wal` 时会自动重放 WAL**。所以只要有一个能解密的 reader，打开副本即可拿到实时消息。

**落地**：本机 `sqlcipher3-binary` 无 Windows wheel、`better-sqlite3-multiple-ciphers` 预编译件在本机崩溃，故**直接按 chatlog 的算法用 Python 自研**（`E:\lumii-wechat-poc\tools\wxread.py`）：

- **参数**（对齐 `chatlog/internal/wechat/decrypt/windows/v3.go`）：`page_size=4096`、`reserve=48`、`HMAC-SHA1`；
  `encKey = PBKDF2-HMAC-SHA1(passphrase, salt, 64000, 32)`、`macKey = PBKDF2-HMAC-SHA1(encKey, salt^0x3a, 2, 32)`；salt = 前 16 字节（本机为 16 个 0x00）。
- **验证**：page1/page2 的 HMAC 校验通过；解密后页首为 `0x1000`(4096)，`integrity_check=ok`。
- **WAL 重放**：帧 = 24B 头 + 4096B 页；解密后用 `pageno` 覆盖对应页，按末次提交页数截断。实测**应用 7 帧 0 失败**。
- **结果**：读出 **「发送消息测试1」@ 22:28:28** —— 正是 chatlog 看不到、仍在 WAL 里的那条。
- **性能**：全量解密 60MB **1.15s**；仅 WAL 增量重放 **2ms**。

→ **读层方案收敛**：`副本(+WAL) → 自研直读 → 明文 SQLite → 查询`。轮询间隔数秒即可，实时可做。

## 6.5 版本变更：微信被强制升级到 4.1.15（2026-10-06 晚）

**起因**：3.9.8.15 被提示「版本过低」，用户升级到 **4.1.15.13**。架构全换，读层需重新验证。

### 环境变化

| 项 | 3.9 | 4.1.15 |
|---|---|---|
| 主程序 | `WeChat.exe` | `E:\testsoft\Weixin\Weixin.exe`（多进程） |
| 数据目录 | `Documents\WeChat Files\<wxid>\Msg\` | `C:\Users\Administrator\xwechat_files\<wxid>_<4hex>\db_storage\` |
| 消息库 | `Multi\MSG0-4.db` | `message\message_0.db`（表 `Msg_<hash>`） |
| 加密 | SQLCipher3：page 4096/reserve 48/HMAC-SHA1/PBKDF2-SHA1×64000 | SQLCipher4：page 4096/reserve 80/HMAC-SHA512/**key 直接可用** |
| 消息内容 | 明文/XML | 可能 **zstd 压缩**（`WCDB_CT_message_content`） |
| 密钥提取 | 内存扫描 raw key ✅ | **chatlog 失败**（`no valid key found`） |

### 结果（全部通过）

1. **chatlog 取密钥失败** —— 与预期一致：4.1+ 内存不再有可直接用的 raw key。
2. **自研只读 Config.Cipher 扫描成功**（`tools/wxkey4.py`，改写自 `sunhanaix/pc_wechat_exp`）：
   `PROCESS_VM_READ|QUERY`、**不注入、无需管理员**、3.6s、**19/19 个库密钥全部取到**。
3. **SQLCipher4 直读成功**（`tools/wxread4.py`）：`page 4096 / reserve 80 / HMAC-SHA512`，
   取到的 key 直接作 AES key，`macKey = PBKDF2-SHA512(key, salt^0x3a, 2, 32)`。
4. **读到真实消息**：「发送消息测试11」「你好呀」「我是toolan」+ 公众号链接（含 23:04 最新）。

### 新增注意点

- **4.x 的 WAL**：`message_0.db-wal` 重放后 `dbsize(11) < 主库页数(16)` → 判定为陈旧，直接重放会破坏库。
  已改为**「尝试重放 → 校验 integrity → 不合法则回退主库单独版本」**。实测主库本身已含最新消息
  （疑似 4.x checkpoint 更及时），故主库优先即可工作。
- **zstd**：4.x 的 `message_content` 可能 zstd 压缩，读原文需解压（本机 `zstandard` 可用）。
- 当前测试账号数据量小（10.7MB），用户可随时制造测试消息。

| wxauto4 连接 | ❌ `未找到已登录的客户端主窗口`；其内部 `find_all_windows_from_root()` 返回 **0** |
| 原因判断 | wxauto4 v41.1.7 目标 ≤4.1.x（注释：*4.x 只对可见部分注册 UIA 控件*）；**4.1.15 连基础节点都不暴露**，或版本已超其支持范围 |

### 可行路径（按风险递增）

| 方案 | 机制 | 风险 | 备注 |
|---|---|---|---|
| **草稿模式** | Agent 出建议，**用户手动发** | 无 | 产品上已成立，推荐默认 |
| iLink 官方 | 以 **bot 身份**发 | 无 | Lumii 已实现；只能回 bot 会话 |
| OCR + 坐标 / SendInput | 不注入 | 中 | 脆弱：依赖窗口可见、置顶、布局 |
| **Qt 无障碍门** | 向 `Weixin.dll` 写"读屏标志位"物化 UIA 树（wechatauto-replica 做法） | **高** | 需**写进程内存（注入性质）+ 管理员** |
| Hook / 注入 | WeChatFerry / wxhelper | 最高 | 封号风险 |

**结论（已修正）**：UIA 系方案在 4.1.15 上**全部不可用**，但**发送能力已用「OCR + SendInput」打通**（见 6.6.2）。
对照：读取层（只读免注入）与发送层（OCR 驱动）**均零注入**，但发送层更慢、更依赖界面状态。

### 6.6.1 补充尝试：QT_ACCESSIBILITY 无效

| 尝试 | 结果 |
|---|---|
| 打开系统"读屏器"标志（`SPI_SETSCREENREADER`）并广播 | ❌ 无变化（已还原） |
| 以 `QT_ACCESSIBILITY=1` 重启微信 | ❌ 主窗口 UIA 后代仍为 **2**（`Weixin` / `MMUIRenderSubWindowHW`） |

→ **WeChat 4.1.15 的 Qt 构建未启用/render 层不暴露无障碍**，`QT_ACCESSIBILITY` 这条路关闭。
（其余路径见上表：键盘/鼠标盲操作、OCR 驱动、Qt 无障碍门写内存、草稿模式、iLink。）

**环境备注**：本会话内 `Read` 工具无法查看图片（PNG/JPEG 均返回 Unsupported），
故 OCR 驱动方案只能靠程序化 OCR 文本输出验证，开发闭环更慢。

### 6.6.2 ✅ 成功路径：OCR + SendInput（零注入）

| 环节 | 实现 | 验证 |
|---|---|---|
| "眼睛" | Windows 自带 OCR（`Windows.Media.Ocr`，zh-Hans-CN），输出**带坐标**的文本行 | `tools/ocr3.ps1` |
| "手" | `SendInput`（Unicode 直键）+ 鼠标点击；不注入、不改内存 | `tools/send_test3.py` |
| 选会话 | OCR 读会话列表 → 点目标条目 | 标题 **文件传输助手 → TOOLAN**，右面板内容同步切换 ✅ |
| 发消息 | 点输入框 → Ctrl+A/Del 清空 → 键入 → Enter | **读库校验**：`Agent发送测试001906` @ 2026-10-07 00:19:16 ✅ |

**代价/约束**：
- 必须**窗口可见且前台**（被遮挡/锁屏即失效）；坐标依赖布局与 DPI；
- OCR 会误读（如「发送」→「发麸」），匹配需容错；
- 每步秒级，比 UIA 慢；不适合高频批量。

→ **发送层方案收敛**：`OCR 定位 + SendInput 操作`。**零注入**，风险面与读取层同档。

### 6.6.3 闭环演示与一次真实失误（重要教训）

**目标**：轮询监听「文件传输助手」新消息 → 自动回复。

| 环节 | 结果 |
|---|---|
| 监听 | ✅ 消息 `闭环测试`（00:31:35），00:31:47 读到，**延迟 ~12s** |
| 回复 | ⚠️ 发出去了，但**发给了错误的会话** |

**根因**：脚本"切回目标会话"一步失败（OCR 把会话名识别成 `文仁传助李`，匹配未命中），
随后**未做校验就直接在当前会话（TOOLAN）发送**。

**硬性教训（必须落进实现）**：
> **发送前必须校验当前会话标题；与目标不符则中止，绝不盲发。**

OCR 发送路线的核心风险不在于"发不出"，而在于**"发错对象且无护栏"**——
这正是「草稿模式 + 人工确认」在 4.x 上仍然值得作为默认的原因之一。

### 6.6.4 发给上一层加固后的复核（结论：**零注入自动发送在 4.x 上不够可靠**）

按"A：键盘 + 目标校验"重做后（`tools/wxsend.py`，**fail-closed + dry-run 默认 + 标题/内容双校验**），
复核又暴露两类问题：

| 问题 | 现象 | 根因 |
|---|---|---|
| ❌ **校验假阳性** | 匹配到**右侧「文件传输助手-功能」帮助面板的标题栏**（`- 文件传输助手 _ ×`），误判为目标会话 | 标题取自"会话列表右侧最上方文本"，多面板布局下会取错元素 |
| ❌ **输入框点击落偏** | 文字未进输入框 → 回车无效 → **消息根本没发出**（全库无痕） | 输入框坐标由「发送」按钮反推，多面板/窗口尺寸变化下会偏 |
| ⚠️ 窗口尺寸漂移 | 实测 896 → **1340** px | 用户/微信自适应会改尺寸，坐标类方案天然吃这个亏 |

**综合判断（0 → 负）**：
- 能稳住的只有「**目标校验 + fail-closed**」这一道；但**校验自身也会被复杂布局骗过**。
- 真正稳的路径只剩 **Qt 无障碍门（写 `Weixin.dll` 读屏标志位）**——**注入类**，需管理员，风险高。
- 社区同类工具（`weixin-auto-send`、`wechatauto-replica`）也都在 OCR 与 UIA 间反复兜底，**没有零注入的稳定解**。

→ **结论：4.x 上「自动发送」不应作为默认能力**。产品默认走**草稿模式**（Agent 读 + 出建议，用户点发送）；
自动发送作为**显式开启的实验特性**，且必须先解决"输入落地校验"（typing 后 OCR 确认输入框已含该文本，否则中止）。

### 6.6.5 ✅ 加固发送器落地：确定性布局 + 数据库锚点校验（2026-10-07）

**结论：上面 §6.6.4 的「不够可靠」被三项修正翻盘** —— 零注入自动发送在本机可控环境下**已能稳定、安全地工作**（`tools/wxsend2.py`）。

**三条决定性修正**

1. **"聊天区抓不到"是误判**：此前截图看不到聊天区，疑为 GPU/MPO 叠加层不可截。实测：**只是当时没有打开任何会话**（空白态）。一旦点开一个会话，抓图**稳定可见**——连续 12/12 次都能读到「聊天头 + 消息 + 发送按钮」。故 OCR 路线并未被硬件合成"判死"。
2. **固定窗口几何**：发送前 `MoveWindow` 到 **1280×820@(60,40)**，布局确定——会话列表 x<300、聊天头部在聊天区左上、`发送` 按钮 ≈(1212,773)、输入框文字落点 ≈(330,680)。结束（含异常）**还原原位置尺寸**。
3. **头部误判根因**：会话/聊天分界阈值过松（`0.30·宽`），把**聊天头部那一行本身**误算成会话项 → `session_right` 变成 416 → 既排除了真头部、又排除了刚键入的输入文字（导致"输入未落地"假阴性）。改为 `0.24·宽` 后根治。

**安全校验（fail-closed，四道）**

- **主证据 = 数据库锚点**：把聊天区**可见文本**与**目标会话最近消息**（直接读 SQLCipher 库）比对。← 这是拦住上次"发错会话"的关键信号：**发错时聊天区是别家消息，锚点命中不了**。
- **头部仅作兜底**且必须"很强"（ratio>0.85），仅在目标**无可用消息**时使用；**中等匹配不再单独放行**（历史上正是被右侧帮助面板标题骗过）。头部定位同时收紧为「紧贴会话列表右侧、y<75、x∈[session_right, session_right+430]」。
- **输入落地校验**：键入后 OCR 输入区，匹配不到即清空并中止（对应 §6.6.4 的"点偏→没发出"）。
- 任一道不通过 → **中止，绝不盲发**。

**验证记录**

| 用例 | 结果 |
|---|---|
| 真实发送到 文件传输助手 | ✅ 库确认 `加固发送真实测试ZQ77`@01:11:50、`加固V2测试K9`@01:16:58、`发送校验测试S1`@11:20:51 **落点正确** |
| 当前开着 TOOLAN，要求发 文件传输助手 | ✅ 校验不通过 → **自动切会话** → 锚点命中 → 发对 |
| 目标不存在（fail-closed） | ✅ 中止；全库扫描标记 **命中 0 次** |
| 抓图稳定性 | ✅ 连续 12/12 次聊天区可见 |
| **闭环 demo（自动监听→回复）** | ✅ 监听检测到新消息 → 生成回复 → 四道校验 → 发出 → **落库确认**（端到端 ~32s，含读层 ~11s 延迟） |

**闭环 demo 暴露并修复的一个真 bug**：`send_text` 点「发送」按钮后**没有事后校验**——首次闭环里报告"OK"但**消息根本没发出**（全库无痕，与 §6.6.4 同类）。
现已加**发送成功校验**：发完核验「输入框已清空」（微信发送成功会清空输入框），未清空则改点按钮、再不行判失败并中止。修复后 Enter / 按钮两种方式均**落库确认成功**。

**仍未解决的边界**：OCR 对中文小字仍会误读（如「发送消息测试11」被读成「发麸…」）；坐标依赖固定窗口尺寸与 DPI；会话列表偶发 OCR 漏项（已加一次重试，仍非 100%）。故产品上仍建议**草稿模式为默认**、自动发送为**显式开启的实验特性**，且必须先过上述四道校验。

**⚠️ 操作教训**：**对微信主窗口按 Esc 会直接关闭/隐藏窗口**（本次误按导致主窗口消失、需重启恢复）——实现里禁止对主窗口按 Esc。

**新增工具**：`wxsend2.py`（加固发送器，本文件同步维护在 PoC 目录）、`ocr4.ps1`（四角坐标 OCR）、`shot.ps1`（窗口截图）、`enum3.ps1`/`children.ps1`（窗口枚举）、`dbq.py`（通用库查询）、`check_marker.py`（误发泄漏扫描）。

## 6.9 P5 · 组合联调（K1 只读 + 草稿）——最小接线

**接线方式（关键结论）**：Lumii 已内置 **MCP server 支持**（stdio JSON-RPC，配置 `~/.lumii/config/mcp-servers.json`，见

**接入 Lumii 的配置**（**未写入用户配置**，待确认后加）：


**草稿模式**：Agent 用 `wechat_history` 读上下文 → 生成回复建议 → 经现有渠道/通知呈现，**用户点发送**（不自动发）。

## 6.11 接入客户端：读取 + 发送（2026-10-07）

**落点**：`apps/windows/resources/wechat-mcp/`（`server.py` 为 MCP 入口；`wechat_core.py` 读取；`wechat_sender.py` 发送；`wxkey4.py`/`wxread4.py`/`shot.ps1`/`ocr4.ps1` 为底层）。

**工具**（5 个）：`wechat_sessions` / `wechat_history` / `wechat_poll` / **`wechat_status`** / **`wechat_send(talker, text, dry_run=true)`**。
`wechat_send` **默认 dry-run（只校验不发送）**，需显式 `dry_run=false` 才真发；发送前四道校验，任一不过即中止。

### 6.11.1 操作前置校验（2026-10-07，用户要求「验证完成再进行操作」）

**原则**：任何 UI 操作前先确认环境；**布局/状态只要有一项不符就中止，绝不带错往下做**。

1. `wechat_status()` / `check_env()`：微信**是否运行**（进程列表）、**主窗口是否可见**、**是否最小化**、**是否前台**、
   **窗口尺寸·比例**、DPI。`ok=false` 时给出 `hint`（通常＝让用户把微信窗口调出来，Agent 别自己去点）。
2. `Win.__enter__`：切前台（`SetForegroundWindow` + `AttachThreadInput` 兜底，**确认成功**）→ `MoveWindow` 固定尺寸 →
   **逐项复验**：未最小化、rect≈(60,40,1280,820)、确在前台。任一不符即 `RuntimeError`，`send_text` 转成失败返回、**不触碰窗口**。
3. 之后才是三道动作校验：目标会话（DB 锚点）→ 输入落地 → 发送生效。

→ **「固定常规动作脚本 + Agent 只传动态指令」**：Agent 只需给 `talker` + `text`（可先 `wechat_status` 看环境）；
会话定位、点击、输入、校验、发送全由脚本完成，Agent 不接触坐标。

### 6.11.5 附件发送：图片 / 文件 / 视频 / 音频（2026-10-07）

新增 `wechat_send_file(talker, path, dry_run=true)`（MCP 第 **6** 个工具）：
- **统一走剪贴板粘贴**：图片（png/jpg/jpeg/gif/bmp/webp/tiff）→ 剪贴板放**图像**（CF_DIB）；
  其余（pdf/docx/xlsx/txt/mp4/mov/mp3/wav/zip…）→ 剪贴板放**文件**（CF_HDROP）。
  **不点工具栏图标、不操作文件对话框** —— 比预想稳得多。
- **语音**：微信语音是「按住录音」，**无法自动化**；只能把音频文件当附件发（已写进工具说明与引导词）。

**两个坑（已修）**：
1. **剪贴板时序**：PowerShell 冷启动要 1~2s，过早 Ctrl+V 会粘到旧内容/空 → 改为
   「清空剪贴板 → 放数据 → 轮询 `IsClipboardFormatAvailable` 就绪 → 再粘贴」。
2. **图片延迟渲染**：图片数据由持有进程提供，PowerShell 一退剪贴板就空 → 保持该进程存活到粘贴完成（finally 里 terminate）。

**前置校验的连带修复**：Agent 跑在 Lumii 里 ⇒ Lumii 常是前台窗口 ⇒ 后台进程 `SetForegroundWindow` 被 Windows 前台锁拦。
`bring_to_front` 逐级升级：直接设 → `AttachThreadInput` 借线程 → **模拟一次 Alt 键取得「最近输入」**后强设；
仍失败则照旧**拒绝操作**（不降级为盲操作）。

### 踩到的坑与修复

1. **MCP 30s 硬超时**：发送流程 ~23s（首次含密钥扫描更久）会超默认 30s → 客户端报 `MCP request timeout`。
   修：条目加 **`"timeoutMs": 180000`**。（`McpStdioClient` 支持 `requestTimeoutMs`，见 `mcp-client.ts:36`。）
2. **发送按钮误判**：聊天气泡里的「…发送…」文本会被当成「发送」按钮 → 输入框定位被带偏 ~300px。
   修：限定按钮 `x1 > 0.85·宽`。
3. **窗口尺寸**：试过放大到 1500×950 想提升 OCR，但**该尺寸下 OCR 读不到「发送」按钮** → 定位失败。
   已回退 **1280×820**（该尺寸发送按钮/输入框定位经多轮验证）。
4. **改代码需重载 MCP server**：Python 进程已加载旧模块，改文件后必须「保存并重连」（或重启客户端）才生效。
5. **未命名群定位**：群 `50313322756@chatroom` 在 contact.db 里没有名字，UI 显示的是成员拼接名（本机 OCR 读作「TOOLAN、韩玉」），
   `resolve_talker` 解析不到 → 需人工提供该显示名才能定位。**建议后续**：从群成员表还原显示名，或让工具接受可选 `session_name`。
6. **聊天区偶发抓成空白**：截图取到空白时点一下聊天区逼重绘并重试（`read_ui_stable`）。
7. **锚点匹配对 OCR 噪声的容忍**：改用 **LCS（最长公共子序列）≥0.7** 兜底，群里的文件标题（读成「B3孬统一一重写版上tm」）也能匹配上。
