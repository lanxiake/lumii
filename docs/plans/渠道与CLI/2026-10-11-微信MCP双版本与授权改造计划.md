## 0. 目标

把当前**单一版本**的 wechat-mcp（v0.6.2，18 工具）改造成**基础版 / 高级版**两条独立分发线，
并补上**商用分发所需的离线授权、有效期与打包加固**，同时把「微信版本适配」从"只在 4.1.15.x 验过"
提升到「4.x 家族内自动择优 + 未知版本明确报错」。

**非目标（明确不做）**：

- **不支持微信 3.x**（SQLCipher3 参数、WeChatWin.dll 取密钥、`WeChat Files` 布局三套都不同，等于重写读取层）。
- **不做"自动回复"本体**：MCP 是工具服务器，自己不回复；代聊只交付一份 **demo 文档**，回路与角色定义由用户在客户端侧自行实现。
- **不做图片转文字**：高级版对图片只做「解密落盘 + 给路径」，画面理解交给用户自己的多模态模型。
- **不做在线激活服务端**（本轮只做离线；在线心跳见 §9 可选收紧项）。

| 位置 | 绑定 | 一换版本就 |
|---|---|---|
| `wxkey4.py:269-272` | Config.Cipher 结构体偏移 `0x10/0x18/0x28/0x88` | 取不到密钥 → **全线读不了** |

## 2. 决策记录（2026-10-11 已拍板）

| 决策点 | 定论 |
|---|---|
| 交付形态 | **两个独立 exe**：`wechat-mcp-lite.exe` / `wechat-mcp-pro.exe` |

| 打包加固 | **要防反编译破壳**（方案待 P2 实测选定） |
| 灵栖内置 | **免授权**（详见 §4.4） |

### 2.1 两版工具集切分

```
lite（12） = list_sessions / read_history / poll_new / search_messages / list_unread
           / check_env / locate_db / repair_env / send_text / send_file / send_batch / reply_to

pro        = lite + read_image + transcribe_voice(新，P3)
           + wechat_digest / wechat_distill_state / wechat_distill_clear

```

## 4. P1 —— 离线授权（一机一码）

### 4.1 机器指纹

三个子指纹分别哈希后**各自独立存放**在授权里，校验时 **2/3 命中**即通过——
这样换网卡、加硬盘、单硬件漂移都不会误伤，而换整机必挂。

```
board = sha256(Win32_ComputerSystemProduct.UUID)
disk  = sha256(系统盘物理序列号)
cpu   = sha256(ProcessorId)
```

> 不用 MAC：虚拟网卡/VPN 常变，误伤率最高。

### 4.2 授权文件

```jsonc
// %USERPROFILE%\.lumii\wechat-mcp\license.json
{
  "v": 1,
  "scope": "retail",              // retail | bundled
  "edition": "pro",
  "fp": { "board": "…", "disk": "…", "cpu": "…" },
  "exp": 1790000000,              // Unix 秒；签发时定，默认 365 天
  "iat": 1759000000,
  "sig": "<base64 RSA-2048 PKCS1v15/SHA256 over 除 sig 外的规范化 JSON>"
}
```

- **签名算法**：RSA-2048 + PKCS1v15 + SHA256，**复用已是依赖的 pycryptodome**（不引新依赖）。
- **公钥内嵌 exe**（PEM 常量）；**私钥离线保管**，签发脚本 `tools/sign-license.py` 不入包。
- **存放位置绝不与 exe 同目录**：灵栖按下文内容哈希同步 exe 目录、用户也会整目录拷走，
  license 必须落在用户级 `~/.lumii/` 下。

### 4.3 有效期与防回拨

- `exp` 控制有效期；到期**降级为 lite**（不是拒绝启动），stderr 给明确提示——用户损失最小。
- **防时钟回拨**：`~/.lumii/wechat-mcp/.state.json` 记见过的最大时间 `max_seen`；
  当前时间早于 `max_seen - 容差(1天)` 即判定回拨，按过期处理。

### 4.4 灵栖内置免授权

exe 运行时判定「由灵栖部署」→ 跳过授权校验，直接按 pro 全功能：

- 位置：exe 同目录（即 `<数据根>/mcp/wechat-mcp/`）；
- 标记：`bundled-mcp-exe.ts` 的 `syncMcpExecutable` **每次同步都补写** `.lumii-bundled`。
  补写时机必须在「内容相同就提前返回」**之前**——否则用户手删过标记就永远补不回来，
  表现为灵栖用户突然被要求授权（`bundled-mcp-exe.test.ts` 锁住了这条）。

> ⚠️ **这是"礼貌性豁免"，不是安全边界**。marker 可伪造，成本约等于 patch 一次校验。
> 本轮接受该弱点；收紧手段见 §9。真正的防盗边界只对**独立分发版**成立。

### 4.5 实施补充（2026-10-11 落地时确定的细节）

- **只对 exe 生效**：`effective_edition()` 在 `sys.frozen` 为假时直接放行——
  源码运行是开发/测试场景，否则 `test_edition.py` / `test_licensing.py` 全跑不起来。
- **降级而不是拒绝启动**：没授权时 `EDITION` 从 `pro` 变 `lite`，工具集与引导词一起退，客户端完全无感。
- **`--edition` 报的是构建档位**，不是运行期生效档位；后者看 `--license-status` 的 `effective_edition`。
  这条很关键：构建冒烟若比运行期档位，就会变成「构建机上有没有授权」决定构建是否通过。
- **阈值折算**：某项指纹取不到时按**实际可比项数**折算门槛（可比 2 项时需全中），
  且空串不参与比较——否则「取不到」会变成「永远命中」，把 3 项门槛悄悄降成 2 项。

## 5. P2 —— 打包加固（防反编译破壳）· 已实测选型（2026-10-11）

PyInstaller onefile 的实际强度**是零**，已用攻击验证过：`pyinstxtractor` 一键解出全部 `.pyc`，
其中 `licensing.pyc` 直接 `dis` 就能读出**完整控制流、内嵌公钥、`.lumii-bundled` 标记名、
所有 reason 字符串**——连反编译器都不用。

### 实测数据（同一份 `server.py`，Windows x64）

| 指标 | PyInstaller（现状） | Nuitka 4.3 `--onefile` | PyInstaller + PyArmor 9.2.7 |
|---|---|---|---|
| **一键解包** | ❌ 全部 `.pyc` 解出，授权逻辑可读 | ✅ 报「不是 PyInstaller 归档」，**无 .pyc 可解** | ❌ 仍是标准 PyInstaller 归档（攻击从"反编译"变成"替换模块"，一样通） |
| 热构建耗时 | **17 s** | 102 s（首次 11 min，含 MinGW 下载） | 待定（叠加步骤） |
| 产物体积 | 11.0 MB | **8.86 MB** | — |
| 冷启动 `--version` | 2.2–2.5 s | 1.0–3.1 s（抖动大） | — |
| 功能面 | 完好 | 完好（pycryptodome/zstandard/读库/发送门全 OK） | — |
| 授权门是否生效 | 正常 | **修复前失效**（见下） | — |
| 商用许可 | 免费 | 免费（Apache-2.0） | ⚠️ **trial 限 non-profits**，且不能 big-script / mix-str |

**PyArmor 直接出局**：trial 版明确 `non-profits`，而本 exe 是要**卖**的 → 必须买商用许可；
且它叠在 PyInstaller 上，档案仍可解包。

### 选型结论：**Nuitka**

唯一真正挡住「解包 → 改授权判断 → 重打包」这条最短路径的方案，且体积更小、冷启动不差。
代价是热构建 17s → 102s（开发期有 `--if-stale`，可接受）与首次要下 MinGW 工具链（~100MB，自动）。

### Nuitka 的移植点（**已修，且有测试兜底**）

1. **打包判定**：Nuitka **不设 `sys.frozen`**（实测 onefile：`sys.frozen=None`，注入的是 `__compiled__`）。
   只认 `frozen` 的话，**整条授权校验被静默跳过**——`--license-status` 报 `missing`，
   `effective_edition` 却给 `pro`，pro 全功能免费送且不报任何错。这是本轮最危险的一处。
2. **`_exe_dir()`**：Nuitka onefile 下 `sys.executable` 指向**临时解包目录里的 python.exe**，
   真 exe 目录在 `NUITKA_ONEFILE_DIRECTORY`（退路 `sys.argv[0]`）。不改则 `.lumii-bundled`
   永远找不到 → 灵栖用户被要求授权。
3. **随包数据文件**：`wechat_sender` 的 `getattr(sys, "_MEIPASS", HERE)` 在 Nuitka 下 `_MEIPASS` 为空、
   回落到 `HERE`，而实测数据文件恰好就解在 `__file__` 同级目录——**无需改动**（已用探针确认）。

### 顺带修掉的一个真 bug（与打包器无关）

`--license-status` / `--machine-id` 等诊断开关在 `main()` **之前**打印，而 UTF-8 只在线程主循环里
reconfigure 过 → CLI 输出走 Windows ANSI 代码页（本机 cp936），带中文的输出是 **GBK 字节**，
任何按 UTF-8 读的下游（jq / Node / 别的客户端）都会解析失败。两个打包产物都一样。
已修：新增 `force_utf8_stdio()` 并在 `__main__` 开头调用。

### 还没闭合的两项（发版前必须补）

- ⚠️ **杀软误报没测出来**：本机 Windows Defender 实时防护是关的（实际生效的是**腾讯电脑管家**，
  且它没有可用 CLI），`MpCmdRun` 直接 `hr=0x80004005` 失败。**这条只能换一台 Defender 开着的
  干净机器量**（⚠️ 不要把含私有代码的产物上传 VirusTotal，那是公开的）。
  经验上 onefile 自解压档案比编译产物更容易触发启发式，但这只是猜想，**没有数据**。
- **残留进程守卫未验证**：`server.py:_exit_with_parent` 同样只认 `sys.frozen`，
  按探针数据推断 **Nuitka 下该守护线程不会启动**。实测环境里有别的 wechat-mcp 进程、
  无法干净隔离，没得出结论。若切 Nuitka，这条要单独验（留着进程会占住 exe 文件换不掉）。

### 加固后叠加（未做）

授权校验**多点埋点**（`main` 启动 / `tools/list` / `tools/call` 三处交叉校验，
任一处被 patch 掉仍不生效）+ 关键常量自洽校验。

## 6. P3 —— 高级版语音转写 · 已完成（2026-10-11）

**实现**：新增 `wechat_asr.py`（`pilk` 解 SILK → `sherpa-onnx` 离线 Paraformer，与 App 侧**同一个模型**）；
`wechat_core` 新增 `voice_message(talker, local_id)` 给单条语音对位，顺带把 `image_message` 里
重复的按 id 取消息逻辑抽成 `_message_by_id`。新工具 `transcribe_voice` 归入 `PRO_ONLY_TOOLS`。

**喂法实测（这是本轮唯一有坑的地方）**

| 喂法 | 结果 |
|---|---|
| A pilk→16k，声明 16k | `使用生成绘本技能再生成一个绘本先和我讨论一下故事` ✅ |
| **B pilk→24k，声明 24k（采用）** | `该系统的默认设定你觉得你可以有自己的名字吗` ✅ 略优 |
| C pilk→24k，**声明 16k** | `而系统的目能思地你觉得你可以用自己的名字吗` ❌ 时间轴错位，明显变差 |

「线程数变了结果就变」是**假象**：干净对照下 2 线程与 4 线程输出**完全相同**；
此前看到的差异来自 `asr_spike.py` 把喂入率硬编码成 16000，把「解 24k 却声明 16k」这条错误喂法
当成了「24k 正常结果」。踩过就记这儿，别再被带偏。

**实测质量**（本机 12 条真语音，逐条连贯可读）：`你使用录屏功能将你上面制作这个绘本的过程录制下来作为一个教学课程`、
`刚才发了什么消息`、`hello 你还在吗`。**源码运行与 exe 运行对同一条给出完全相同的文字**。

**体积与依赖**

- `sherpa-onnx` / `pilk` / `numpy` **只有 pro 带**（构建脚本按档位分依赖表）：
  pro **39.5 MB**，lite **12.3 MB**（lite 里 `transcribe_voice` 不在工具表、直接调也返回门控错误）。
- **模型（78MB）不进 exe**：默认复用灵栖已下好的那份；独立用户 `--download-asr-model`
  （hf-mirror 优先、GitHub 兜底），或用 `LUMII_WECHAT_ASR_MODEL` 指路。`check_env` 的 `asr` 栏给状态。

**未闭合**：**字准率没有 ground truth**。微信自带的「转文字」不落库，没法自动逐条对比，
上面只能凭"读起来是不是人话"判断。要真量准率得手工建标（听音频写下来再对）——留到测试阶段。

## 7. P4 —— 微信 4.x 多版本加固 · 已完成（2026-10-11）

| 步 | 项 | 落地做法 | 验证状态 |
|---|---|---|---|
| **P4-1** | **版本探测** | `core.wechat_version()`：`find_wechat_pids` → `QueryFullProcessImageNameW` 取 exe 路径 → `GetFileVersionInfoW` 读文件版本。写进 `check_env` 与 `locate_db`，带 `verified` 标志与提示 | ✅ **真机通过**：`4.1.15.13`，命中所验集合 |
| **P4-2** | **密钥偏移去硬编码** | 快路径（实测布局 `node+0x28`→`obj+0x88`→`{ptr,len}`）保留；新增**无偏移兜底**：把节点窗口里所有 qword 当候选指针、候选对象里所有 qword 对当 `{ptr,len}`，**唯一判据是 `verify_enc_key`** | ✅ 真机无回归（快路径命中，12 个库全部验签通过）；⚠️ 兜底路径**未在第二个版本上验证** |
| **P4-3** | **窗口类名去版本号** | `Qt51514QWindowIcon` → `Qt*QWindowIcon`（`51514` 是 Qt 版本号 5.15.14，换 Qt 就变）。进程归属另由 `GetWindowThreadProcessId` 兜底，放宽不会认错窗口 | ✅ 真机 `find_main_hwnd` 正常命中 |
| **P4-4** | **UIA 路径尾段兜底** | `uia_read.ps1` 新增 `OneBySuffix`：精确点分路径失配时，按**尾段**（`current_chat_name_label`）认 | ⚠️ **本机无法验证**（见下） |

**P4-2 的设计要点**：这条路之所以可以"瞎试"而不怕给出错值，是因为**接受判据是密码学验签**——
错候选必然验不过，代价只是几次内存读。这也是唯一一个不需要"哪个版本用哪个偏移"映射表的做法。

**关于 P4-4 的验证**：本机 `uia_read.ps1` 返回的树只有两个包装 Pane
（`Weixin` / `MMUIRenderSubWindowHW`），连内层渲染窗也一样——而这不是我改坏的：
代码里早有记载「微信 4.x 可能整条生命周期都不向 UIA 暴露控件树」（`_uia_tree_blank`），
`check_env` 自己的 `uia_tree` 字段就是 `unknown`。**新旧代码在本机行为完全一致**（都取不到），
所以兜底路径在这里是空跑。要验证它，需要在**控件树确实暴露**的机器/版本上跑一次。
（`OneBySuffix` 里踩过一个坑：`AId` 在 AutomationId 为 null 时返回 `$null`，
直接 `.EndsWith()` 会抛「不能对 Null 值表达式调用方法」把整次读取废掉——已强转字符串。）

> ⚠️ **没有多版本真机就无法验证**。这一步的现实目标是「**不静默失败**」——
> 在没验证过的版本上给出可诊断的报错（P4-1 已做到），而不是装作能读却读出垃圾。

## 9. 风险与诚实边界

1. **没有绝对防破壳**。加固只能把成本推到不划算；真要硬需商用壳（VMProtect/Themida，付费）。
2. **加壳会推高杀软误报**——本进程已在用 `ReadProcessMemory` 扫微信内存，再加混淆/自校验，
   误报概率显著上升。这是桌面软件实打实的代价，P2 必须把误报和强度**一起量**。
3. **灵栖内置的 marker 豁免可伪造**（§4.4）。若要收紧，可选加「父进程必须是灵栖主程序」校验
   （代价：会打断灵栖自身的调试流程）。
4. **4.x 适配无真机不可验证**（§7），只能保证不静默失败。
5. **双 exe 改动外溢**：electron-builder 打包布局、`mcp-presets.ts`、`mcp-presets.test.ts` 对账、
   `test_mcp_client.py` 的工具数断言、以及 README/PUBLISHING 全部文案都要跟着改。
6. 若日后要**在线激活/心跳**（可吊销、可限设备数、可防整机转卖），
   需补一个极简校验端点；本轮不做，但 `license.json` 的 `scope`/`v` 字段已为其留位。

## 11. 客户端实测（2026-10-11）

两层真实客户端，**不用自己拼 JSON-RPC**：

**① 官方 MCP Python SDK 当客户端**（`uv run --with mcp`，临时脚本）
- `pro` **26/26**、`lite` **23/23**：握手/协议协商/instructions 分档/工具数 19 vs 12/annotations/
  只读工具/`read_image` 的 image 内容块/门控拒绝(-32602)/未知工具(-32602)。
- 结论：**`serverInfo.edition` 这类非标准字段会被规范客户端丢掉**（SDK 的 `server_info` 是 pydantic 模型）。
  客户端判档位只能靠**工具数 / instructions**，文档别写成"客户端可读 edition"。

**② 真实客户端（灵栖）**：`WM` 套件（`lumii-ui` + 真实 LLM）→ **17/20 通过**，
失败的只有 **WM-09/10/11**（都强依赖 UIA 控件树，见 §7）。

**过程中抓到的两类"假失败"，都不是产品逻辑**

1. **代聊抢同一个会话**：`filehelper` 的代聊档位是 `auto`，盯梢回路会在我发探针后自动回一句
   「…收到」，并和测试抢同一个微信窗口。症状极具误导性——工具返回 `send_not_confirmed`
   （不是 `busy`、不是报错）。直接连发三条探针的实测：**1 条失败（且确实没落库）、2 条成功**，
   日志里能看到代聊回路在同一窗口操作。
2. **窗口尺寸漂移**：`1041×843`（预设是 `1280×820`）时附件/工具栏锚点会失配，
   `repair_env` 纠正后 `WM-10` 的失败原因才暴露出真正的那条（见下）。

**确认的产品缺口**：附件路径（`_attach_via_dialog`）**强依赖 UIA 的「发送文件」按钮且没有兜底**，
UIA 树为空时**必然失败**（fail-closed，不会误发）。本机 `check_env.uia_tree` 常态是 `unknown`
（内外两层句柄都只有两个包装 Pane），因此 WM-09/10/11 在这台机器上无法通过。
**这是既有产品限制，不是本轮引入的**；文本路径有 OCR 兜底所以照常。

> 想做兜底的话得注意：那个按钮在界面上是**图标**，不一定能被 OCR 按文字找到；
> 得先在一台 **UIA 树确实暴露**的机器上把「按钮长什么样、能不能 OCR 到」验证掉，
> 别在 fail-closed 的发送链上盲加一条可能点错东西的路径。
