## 0. 实证摘要（体检结论，三段日志即可复核）

**A. 一次「你好」触发 9 次记忆提取（53 秒，7 次 0 产出）**

```
10:30:38  退出 → flushAllOpen('app_quit') 关闭 9 个会话残留段并入队
          → "开始总结段 4f9867d9" 刚发出，进程退出，LLM 调用被掐断 → 9 段滞留 closed
10:30:52  应用重启 → 无任何恢复动作（恢复是懒加载的）
10:51:36  用户发「你好」→ observeUserTurn → 首次创建 pipeline → start()
          → "重启恢复：发现 9 个待总结 closed 段" → 串行总结到 10:52:29
```

- 9 次调用 ≈ 68k 输入 tokens（每次固定前缀 ~7.5k：记忆架构说明 + 已有个人记忆全文 + 工作记忆 25 条）；**7 次返回 []，2 次各出 1 条且互相重复**，去重后净写入 1 条。
- 「你好」本身只开了个 2 字符新段（关闭时按 `<15 字符`规则跳过），**是扳机不是提取对象**。
- 这是日常模式：每次退出积压、下次首条消息集中爆发（09-14 的段同样如此，`closed_at=09-15T02:30:38` → `summarised_at=09-15T02:51:38+`）。

**B. planner 待办写进了「幽灵命名空间」（污染 + 功能空转）**

- 378 行、时间跨度 2026-09-06 ~ 09-15（每 10 分钟 tick 写 4 条），全部落在 `user_id='local'`。
- **但记忆系统读写一律用 `local-user`**（`bridge-instance-factory.ts:603`、`segment-memory-service.ts`）——这批行既不会被注入也不会被检索，等于功能空转 + 表体积白涨。
- 实现同时绕过了 `MemoryManager`：裸 `INSERT` 不做内容去重、不更新 `agent_memories_fts` 索引（设计文档 `2026-09-06-autonomous-proactive-planning-design.md:117` 原意是走 `MemoryManager.addMemory`）。

**C. 简要模式确实生效，但只覆盖 37 段中的 16 段（整份 −12.9%）**

- 用户设置确认是 terse（localStorage `promptStyle.style="terse"`；日志 `style=terse`）。
- 实测提示词 25,920 字符，最大几块全在豁免区：mcp 20.1%、workspace 11.4%、agentCollaboration 10.5%、identity 10.3%、个人记忆 6.7%、memory 6.7%、Client Diagnostics 4.4%。
- terse 形态**无快照/体积基线测试**，回退不会被任何信号捕获。

## 2. P0 详情

### P0-1 启动时恢复遗留 closed 段

**问题**：恢复只发生在「pipeline 首次被创建」时，而创建只由用户发消息（`observeUserTurn`）或 flush 触发 → 积压段全部堆到用户下一条消息时爆发（实测 53 秒 9 连发）。

**改动**：

1. `apps/windows/src/main/agent-runtime/segment-memory-service.ts` 新增公开方法：

   ```ts
   /** 启动恢复：为所有存在待总结 closed 段的 agent 创建 pipeline（内部 start() 续跑） */
   recoverPending(): void {
     if (!this.enabled) return
     const pending = this.deps.segmentRepo.findClosed(RECOVER_LIMIT)
     const agentIds = new Set(pending.map((s) => s.agentId))
     for (const id of agentIds) this.getPipeline(id)
   }
   ```

2. `apps/windows/src/main/agent-runtime/bridge.ts` 在 `finalizeInitialize()`（:1758-1783）内、紧随 `maybeConsolidateExistingPersonalMemory()`（:1760）之后调用 `this._segmentMemoryService?.recoverPending()`——与既有的「启动时检查个人记忆整理」同型，失败只记日志。

**验收**：重启后不再需要「先发一条消息」才恢复；日志出现 `[SegmentMemory] 重启恢复：发现 N 个待总结 closed 段` 于启动阶段而非首条消息之后；首条消息的 observe 不再伴随批量总结日志。

### P0-2 修复 SummarizationQueue 的 agent 作用域

**问题**：`SummarizationQueue.start()` 用 `repo.findClosed(limit)` **全局扫描**（`summarization-queue.ts:50`），未按 agentId/userId 过滤；而 `SegmentMemoryPipeline.flushAll()` 有过滤（`segment-memory-pipeline.ts:142-147`）——两者不一致。后果：一个 agent 的 pipeline 会总结别的 agent 的段；同一段可被多条 pipeline 各自入队（靠 `status !== 'closed'` 侥幸去重，并发时仍可能重复调 LLM）。

**改动**：

1. `packages/agent-runtime/src/storage/segment-repo.ts` 新增 `findClosedByScope(agentId, userId, limit)`（SQL 加 `AND agent_id = ? AND user_id = ?`）。
2. `SummarizationQueue` 依赖注入改为 `listPending: () => readonly MemorySegment[]`（由 pipeline 用自身作用域实现），`start()` 改用它——队列不再自己决定扫描范围，与既有 DI 风格一致（`loadSegmentText`/`summarize` 已是注入）。
3. `SegmentMemoryPipeline` 构造时传入作用域闭包（`agentId`/`userId` 已在 deps 中）。

**验收**：单测覆盖「A pipeline 的 start() 不会捞出 B agent 的 closed 段」；真实日志中恢复条数等于本作用域段数。

### P0-3 planner 待办停止污染工作记忆 + 存量清理

**问题**：`planner-landing.ts:232-246` 用裸 `INSERT INTO agent_memories (... category='reference' ...)` 写 planner todos——**写死 `user_id='local'`（幽灵命名空间，记忆系统读的是 `local-user`）**，且绕过了去重与 FTS 索引维护（`MemoryManager.addMemory` 注释明确「相同内容幂等（repo 去重）」，设计文档 `2026-09-06-autonomous-proactive-planning-design.md:117` 原意也是走 `MemoryManager.addMemory` / 复用 agent_memories）。结果：每 10 分钟 4 条、16 天 378 行。

**改动（已按拍板执行）**：

1. **待办保留在记忆中**（用户拍板："使用的时候也方便"），但改为轮换语义：`planner-landing.ts` 每批先 `removeByTag(agentId, userId, 'planner-todo')` 清上一批，再经 `AgentMemoryRepo.saveCandidate` 写入（幂等 + FTS 索引同步），作用域修正为 `local-user`（`PlannerLandingOptions.userId`，默认 `local-user`）。总量恒定 ≈ 每批 todos 条数。
2. **存量清理（已执行）**：378 行全部清除（用户拍板"当前都是作为测试"）。删除前导出备份 `~/.lumii/data/backups/planner-todos-local-2026-09-15.json`；主表 + FTS 索引同事务删除，删后一致性校验 110 vs 110 ✓。维护脚本入库：`scripts/cleanup-planner-todo-memories.mjs`（默认 dry-run，`--apply` 执行）。
   - 注意：应用仍运行旧代码时会继续按 10 分钟 tick 写入该命名空间，**重启加载新代码后**再跑一次该脚本即可清零。

**验收**：连续跑 ≥3 个 tick 后 `agent_memories` 中 `planner-todo` 标签行数稳定 ≤ 本批 todos 数；`user_id='local'` 恒为 0。

## 3. P1 详情

### P1-1 mcp 段 terse 化（20.1%，最大单块）

**现状**：`prompt-sections.ts:101` 注册表 `mcp terse:false`；`misc-sections.ts:382` `buildMcpSection` 无 style 参数，terse 下仍全量列出 5 个 server、约 40 个工具的完整中文描述（日志实测 5,214 字符）。

**改动**：

1. `misc-sections.ts` 的 `buildMcpSection` 增加 `style` 参数：terse 渲染 = `### <server 名>（N 个工具，<一句话用途>）` × server 数 + 引导句 `prompt_guide(section: "mcp")`；detailed 保持现状。
2. `section-guides.ts` 的 `PROMPT_GUIDE_SECTIONS` 增 `mcp` 条目（工具完整清单按 server 分组），供按需展开。
3. 注册表 `prompt-sections.ts:101` 改 `terse: true, expandVia: "prompt-guide"`。
4. 守卫测试：terse 段字面量断言 + guide 可发现；detailed 快照不变。

**预估**：5,214 → ~600 字符（−88%），整份 −18%。

### P1-2 workspace 段 terse 化（11.4%）

**现状**：`prompt-sections.ts:119` `workspace terse:false`；`runtime-section.ts:158` 全量渲染（目录结构 + Output Organization + 命名规则，2,951 字符）。

**改动**：terse 渲染 = 工作目录一行 + 「产物写 `outputs/<task>/`、临时文件写 `temp/<task>/`、不写工作区根」硬规则 + `prompt_guide(section: "workspace")`；detailed 不变。guide 收录现有全文。注册表改 `terse: true, expandVia: "prompt-guide"`。

**预估**：2,951 → ~700 字符（−76%），整份 −9%。

### P1-3 恢复批次合并总结（省 token 大头）

**问题**：恢复 N 个段 = N 次调用，每次重复携带 ~7.5k 固定前缀（实测 9 次 ≈ 68k 输入）。

**改动**：

1. `memory-extractor.ts` 新增 `buildBatchSegmentSummaryPrompt(segments: {id, text}[], existingContext)`：分节列出各段，要求输出 `[{segmentId, candidates:[...]}]`；沿用现有四类定义、去重规则与「不保存清单」。
2. `SummarizationQueue` 在 `drain()` 中按批取待处理段（如 ≤5 段/批，只在「恢复批次」启用；实时单段关闭仍走单段路径）→ 一次 LLM → 按 `segmentId` 分派 `onCandidates` → 逐段 `markSummarised`。
3. **回退策略**：批解析失败 → 降级为逐段重试（复用现有 retry 计数）；段数超阈值自动分批。

**风险**：Qwen 对多段结构化 JSON 的遵守度需实测（当前单段场景已有复读任务的倾向，日志中出现 1767 输出 tokens 的先例）。先在真实历史段上跑一版对照再合并。

**预估**：9 段批次 68k → ~12k 输入 tokens（−82%）。

## 4. P2 详情

- **P2-1 退出时等待队列**：`bridge.ts:750-756` 的 `before-quit` 目前只同步 `flushAllOpen`（`SegmentMemoryService.shutdown()` 全仓库无调用点）。改为 `event.preventDefault()` → `flushAllOpen` → `await shutdown()`（内部 `settle()`，加 3~5s 超时）→ `app.quit()`；超时则记日志放行（P0-1 兜底）。注意验证不会拖慢正常退出、不与既有 quit 流程冲突。
- **P2-2 terse 基线测试**：`system-prompt-snapshot.test.ts` 目前只快照 detailed（快照中 `prompt_guide` 出现 0 次）。补 terse 快照或整份体积断言（如「标准配置 terse ≤ X 字符」），防止后续段改动悄悄回退。
- **P2-3 Client Diagnostics 纳入风格轴**：该段由 `bridge-prompt-composer.ts:272-318` 构造、`:462` 注入，不读 promptStyle。terse 下压成「日志目录 + 一句自检指引」，detailed 保持现状。个人记忆段（6.7%）建议保持全量——价值密度高，不随风格裁。
- **P2-4 段总结价值门槛**：`SegmentTracker` 的 `minSummaryChars` 默认 15（`segment-tracker.ts:139`），实测 16/18/29/38 字符的段照跑且全 0 产出。提到 ~50 并在 pipeline 层增加「纯寒暄/无 assistant 回复」预筛。注意：长度与价值弱相关（226~287 字符段亦 0 产出），此项只作止损，不指望省大头。
- **P2-5 提取模型降本（评估）**：`callLLM(prompt, undefined, 'memory_extract')` 目前与主对话同模型（日志 model=Qwen3.8-Flash-Next）。评估 purpose→模型路由是否可配置，将段总结/记忆提取路由到更小模型；需先验证 JSON 输出合格率。
