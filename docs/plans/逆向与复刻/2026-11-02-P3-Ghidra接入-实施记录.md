## 范围

设计 §8.4 说 P3「需要额外工具链（jadx/apktool/Ghidra/IDA）与 Windows 专属 bootstrap，
**不做工具自动安装**」。本期只做其中价值最高、本机已具备的一块：

**把 Ghidra headless 接进 `reverse` 技能**，让桌面二进制分析从「只能停在 strings 与导入表」
变成「有函数数、能力分类、可疑字符串、业务入口伪代码」。

APK（jadx/apktool）与 EXE **复刻**（不是分析）仍未做——本机没有 jadx/apktool，
而复刻需要另一套设计。**没有把它当成「P3 完成」**。

## 为什么做成插件

第一版把驱动脚本放进技能目录（`bundled-skills/逆向与复刻/reverse/scripts/ghidra/`）。
**那是错的**：技能目录是**播种到工作区的数据**，用户能改、能删、能拷走——
关掉任何开关都没用，Agent 照样能 `node` 那个脚本。

改成插件后，「可选择接入」才成立：

| 关掉插件 | 打开插件 |
|---|---|
| `reverse_probe` 从工具表消失（真机验过：`tools list` 里 0 条） | 工具出现，`SKILL.md` 指向它 |
| 插件不加载，不探测 Ghidra | 启动日志打印找到的 Ghidra 路径 |
| 技能按 `desktop.md` §7 降级（Triage + strings + 导入表） | 技能走 §6（函数数 / 能力分类 / 反编译） |

脚本资产搬到 `assets/reverse/scripts/ghidra/`（与 `assets/wechat` 同族，`extraResources` 整体打包），
跟着插件的启停走。

## 实测暴露并修掉的 4 处

### 1. 能力标签的松散匹配把无关导入归错类

第一版用 `connect$` 匹配 network，真机上 **`SCardDisconnect`（智能卡）被归进了 network**。
标签一错，整段结论都跟着错。改为**锚定全名或明确前缀**。

### 2. 字符串段混进导入符号名

Ghidra 把外部符号也挂成 defined data，不过滤的话 `GetLastError` /
`RtlQueryFeatureConfiguration` 会混进「字符串线索」里。按 `IMPORTS_ALL` 集合排除。

### 3. 反编译名额被 CRT 样板函数占满

按引用数排序，`notepad.exe` 前两名是 `__security_check_cookie`(76) / `__GSHandlerCheck`(70)。
加 `isCompilerHelper()` 排除。

### 4. **Electron 里 spawn `process.execPath` 会起第二个应用**（最严重）

`spawn(process.execPath, [script])` 在 Electron 主进程里拿到的是 **`electron.exe`**，
于是：
1. 起了一个新的 Lumii 实例；
2. 单实例锁把它挡住，它既不退出也不跑脚本；
3. 子进程挂在 `child.on('close')` 永远不来 —— **工具不返回，会话锁 600s 后仍在等**（真机实测）。

修法：仓库早有正解 `resolveNodeExec()`（`runtime-env.ts`，Electron execPath +
`ELECTRON_RUN_AS_NODE=1` 就是一个纯 Node）。插件不许 import 主进程（wiring ⑪），
所以经 `createPipelineExecutor()` 注入 `resolveNode`。

# 追加：APK 后端（同日）

## 形态

`reverse_probe` 现在**按扩展名自动选后端**：

| 目标 | 后端 | 外部依赖 | 耗时 |
|---|---|---|---|
| `.apk` | 内置解析（`apk-probe.ts`） | **无** | 秒级 |
| PE / ELF / Mach-O | Ghidra headless | Ghidra | 3–5 分钟 |

内置实现让 APK 线**开箱可用**：不需要 jadx / apktool / aapt，装上客户端就能分析。
这一点很重要——`mobile.md` 原先写着「依赖外部工具，缺席就如实说」，而本机
连一个安卓工具都没有，等于这条线从来没真正跑起来过。

## 能拿到什么

包名/版本/SDK、权限（含敏感项计数）、组件与**导出组件**（攻击面）、
dex 字符串池里的 URL 与类名、原生库与 ABI、加固迹象、跨端框架判定、签名文件。

## 实现要点（三处静默错误，都是先踩后修的）

1. **dex 头偏移**：`string_ids_size` 在 `0x38`、`string_ids_off` 在 `0x3c`。
   按「56/60」读会拿到 `data_size`/`data_off`，结果字符串列表全空且**不报错**。
2. **AXML 属性值哨兵**：`rawValue === 0xffffffff` 是「无值」，不能当成索引 0——
   否则每个没有字符串值的属性都会变成池里第一条（`exported` 会读出上一个属性的值）。
3. **类描述符被当成普通标识符**：`Lcom/x/Y;` 符合标识符正则，先判标识符则
   `CLASS_DESC_COUNT` 恒为 0。判定顺序要在 `summarizeDex` 里固定住。

## 测试

16 条单测**造真字节**（手写 zip / AXML / dex 头），不 mock：这三个 bug 的共同点是
「输出看着合理但其实是错的」，只有真字节能测出来。另有 2 条工具层用例证明
`.apk` 走内置后端、不 spawn 外部进程、不依赖 Ghidra。

## 真机证据

对真实 APK（`nova_ai_...apk`，407 MB / 42257 条目）真机调用：

```
PACKAGE=com.larus.nova    VERSION_NAME=15.3.0    MIN_SDK=21  TARGET_SDK=35
PERMISSIONS=239           PERMISSIONS_SENSITIVE=13
EXPORTED_COMPONENTS=69    DEX_COUNT=40           DEX_READ=3/40（超过上限 3）
URL_COUNT=80              CLASS_DESC_COUNT=160
PACKER_SUSPECT=none       FRAMEWORK=unknown
SIGNATURE_FILES=META-INF/BYTESIGN.SF,META-INF/BYTESIGN.RSA
```

Agent 自己也说清了统计范围（「80 个 URL 只来自 3/40 个 dex」）与
「`FRAMEWORK=unknown` 表示没认出，不代表没有」——文档里那两条口径起作用了。

**关掉插件后** `tools list` 里 `reverse_probe` 为 0 条（APK 后端也跟着没了）。

**耗时**：3 个 dex 的字符串池解析约 2 秒；Ghidra 那条仍是 3–5 分钟。

# 追加：IPA 后端 + 分包容器（同日）

## 新增能力

| 目标 | 后端 | 说明 |
|---|---|---|
| `.apk` | 内置 | 同上一节 |
| `.xapk` / `.apks` | 内置（复用 APK 解析） | 外层 zip 里装若干 apk；**按「manifest 里有 `package`」挑主包**，其余只列清单 |
| `.ipa` | 内置（新增） | zip + 二进制 plist + Mach-O 加密标记，全部纯 Node |
| `.aab` | **明确拒绝** | manifest 是 protobuf；返回 bundletool 的转法，不落到 Ghidra 上瞎分析 |

## IPA 能拿到什么

`BUNDLE_ID` / `VERSION` / `BUILD` / `MIN_IOS`、`NS*UsageDescription`（**有这条就说明真申请了该能力**）、
`MACHO` / `ENCRYPTED`（`LC_ENCRYPTION_INFO` 的 `cryptid`）、`FRAMEWORK` / `FRAMEWORKS_COUNT`、
`PROVISION_TEAM` / `PROVISION_EXPIRY`。

**拿不到**：Mach-O 反汇编（需 macOS 工具链）、代码签名核验（需 `codesign`）。
后者输出里恒为 `SIGN_CODE=UNRESOLVED`，并在文案里说明原因——不猜。

## 实测修掉的 4 处

1. **字典标记只认了 `0xD0`/`0xD1`**：bplist 的字典是 `0xD0 | count`，Info.plist 永远十几个键，
   于是 `0xD5` 之类全被判成「不是字典」——**这条路径在真机上必挂**。改判高 4 位。
2. **字符串长度规则混了两种**：`info < 15` 时 `info` 本身就是长度；只有 `== 15` 才另跟一个 int。
   原来总是读一个 int，短字符串全长错位。
3. **`utf16be` 不是 Node 的合法编码**：按字节 `swap16()` 后用 `utf16le` 解。
4. **plist 解析出 0 个字段时静默输出 `UNRESOLVED`**：真机上八个 `UNRESOLVED` 看着像「包信息不全」，
   实际是解析失败。改为显式报错并说明「这不是包的问题」。

## 分包容器的主包判定

第一版取「第一个带 `AndroidManifest.xml` 的内层 apk」，真机上会选中 `config.arm64_v8a.apk`
（配置分包有极小的 manifest，但没有 package），结果 `PACKAGE=UNRESOLVED`。
改为**要求 manifest 里有 `package` 属性**。

## 测试

新增 15 条（`ipa-probe.test.ts` 12 条 + 容器/AAB 3 条），同样**造真字节**：
手写 bplist（含 `topObject` 字段与 0x0F 长度扩展）、手写 `LC_ENCRYPTION_INFO_64` 的 Mach-O。
工具层补 1 条证明 `.ipa` 走内置、不 spawn 外部进程。

合计 `reverse` 插件 **39 条**全绿。

## 真机证据

| 目标 | 结果 |
|---|---|
| `.apk`（407 MB 真包） | 秒级：`PACKAGE=com.larus.nova` / 239 权限 / 69 导出组件 / 80 URL |
| `.ipa`（自造桩） | `BUNDLE_ID=com.demo.ios` / `VERSION=3.1.4` / `MIN_IOS=14.0` / `NSCameraUsageDescription: 扫描二维码` / `ENCRYPTED=no` / `FRAMEWORK=Flutter` |
| `.aab` | 明确拒绝并给出 bundletool 转法；Agent 正确地没有伪造结果 |

一个值得记的现象：真机复验时 Agent 发现「同一个文件两次结果不同」，主动指出
**不宜拿单次结果下结论**。实际原因是中间重写过样本（旧样本的 plist 生成器有 bug），
但它的谨慎是对的——这类工具的输出必须配文件哈希才谈得上可复算。

| agent 步 | 实际轮次 | spec 上限 | 余量 |

**下一次要调时，journal 里已经有数据了。**

## A3 「只跑不录」mode —— **不做（YAGNI）**

原先的担心是「调用方只能二选一：彩排 / 录制」。但实际查下来：

1. `record.enabled:false` 时，`mode:'record'` **已经是**「照常执行、不录、原因写进 note」，
   返回 `ok:true`，不是一个假的失败；
2. 6 条内置流水线里 **4 条** 是 `record.enabled:false`——「跑但不录」不是边缘诉求，
   但它已经被现有语义覆盖了。

缺的只是一个「显式表达意图」的 mode 名。加它的成本（新 mode 枚举贯穿 runner / service /
tools / UI + 校验 + 测试）远大于收益——调用方传 `record` 拿到一句 note 并不影响任何事。
**按 YAGNI 不做**，P1 总结里的判断（「等出现高频诉求再加」）继续有效。

## A4 设置页 UI —— **不做（需求不成立）**

原先写的是「现在只能改 `~/.lumii/extensions.json`」。**这是错的**——设置 > 插件 页签
早就有完整的扩展卡片：`逆向工具…`（`com.lumii.reverse`）在列、显示「运行中」、带「禁用」按钮。
P2/P3 的文档沿用了这条错误前提。

那「看到 Ghidra 装在哪」这个真需求呢？两条理由不支持专门做 UI：

1. `reverse_probe` 缺工具时**会直接告诉模型**缺什么、怎么装（三条出路），用户从 Agent
   的回复里就能拿到答案；
2. 插件卡片要显示运行时探测结果，得给 `control.ts` 开一个「插件贡献状态」的通用口子——
   而 `control` **刻意不认识具体插件 id**（架构约束）。为一个信息项破这条约束不划算。

结论：不做。若将来同时有三个以上插件需要展示运行时状态，再统一加那个口子。

# 追加：D 类技术债（同日）

## D1 实例归属「两条通路共写一个栈」 —— **评估后维持现状**

现状：`toolLifecycle`（真实执行前后）与实例事件（`tool:start`/`tool:end`）**都写同一个
`toolExecutorStack`**，靠 `lastIndexOf` 只摘自己那条，重复计数不影响栈顶。

「更干净的做法」（让事件层完全不碰这个 ref）评估结果：**不改**。

理由：`tool:start`/`tool:end` 那个 ref 有一个生命周期通路不覆盖的消费方——
`background-tool-config.ts` 的 `run()` 在没有显式 `instanceId` 时读它来决定后台任务的归属。
删掉事件层写入，后台任务在「工具已开始、`toolLifecycle` 尚未进栈」的窗口里会拿到空归属，
`instanceToRootSessionKey` 查不到 → 后台任务挂到无主会话上。

两条通路共写一个栈、用 `lastIndexOf` 去重，代价是**栈里可能有重复项**（不影响栈顶判定），
收益是两条通路的语义都能自洽。**这是有意的取舍，不是遗留缺陷。**

## D2 `lumii-local://` 在 webview 里导航不工作 —— **根因未定位，但缓解已完成**

### 现象（可复现）

| 方案 | webview 内 `fetch` | webview **导航** |
|---|---|---|
| `lumii-local://`（ACL 内路径） | **200 + 全文** | **timeout**（无 `dom-ready`、无 `did-fail-load`、`getURL()` 空） |
| `lumii-local://`（ACL 外路径） | 403 | `dom-ready` |
| `lumii-remote://`（同 `stream:true`） | — | `dom-ready` |
| `lumii-plugin://`（无 `stream`） | — | `dom-ready` |
| `file://` | — | `dom-ready` |
| `https://` | — | `dom-ready` |

只有「ACL 通过、真正返回文件内容」的 `lumii-local` 导航会挂。事件序列是
`did-start-loading → did-attach → did-stop-loading`，**没有 `did-navigate`**——导航被静默取消。

### 排除过的方向（都有实验证据）

1. ~~webview 用独立 session~~ —— `partition` 为 null（继承主窗口），且 webview 内 `fetch` 200
2. ~~ACL 拒绝~~ —— ACL 内 200、ACL 外 403；**403 反而能导航**
3. ~~CSP `frame-src`~~ —— 已显式放行，且主进程还主动删 CSP 头
4. ~~scheme 特权缺失~~ —— `new URL()` 有 origin/host，standard 特权在
5. ~~`stream: true`~~ —— `lumii-remote` 同样有 stream 却正常
6. ~~流式 body~~ —— 改成 Buffer 返回**无效**（已回退，不留未验证的复杂度）
7. ~~子资源拖住主文档~~ —— 极简单行 HTML 同样 timeout
8. ~~src 设置方式~~ —— 直接设 / 先 about:blank 再改 / 先 append 空元素再设，三种都失败
9. ~~注册顺序/替换语义~~ —— 数组第一个 `lumii-local` 失败，第四个 `lumii-plugin` 正常；
   但第二个 `lumii-remote` 也正常

最小 Electron 脚本（`protocol.handle` + 同 privileges + 同响应形态）**怎么都复现不出来**，
说明触发条件依赖真实应用里的某个组合状态。继续逐项排除的成本已远超收益。

### 已做：把绕过方案的风险收紧

当前用 `file://` 加载复刻产物——**这等于让外部内容重建出的页面跑在「能读整个磁盘」的源里**。
`ComparePreviewModal` 原先没有设 `webpreferences`，继承主窗口的 `sandbox:false`。

现在显式收紧（真机验证：webview 内 `typeof require/process` 均为 `false`）：

```
webpreferences="sandbox=yes,nodeIntegration=no,contextIsolation=yes,webSecurity=yes,allowRunningInsecureContent=no"
```

**D2 的终态**：功能可用（`file://`）、风险已缓解（沙箱）；根因留作已知问题，
若将来 webview 必须用协议带来的 ACL 收紧，需要回到这里继续查。

## B1 dex 字节码反编译 —— **降级为「结构层」，不再是完全没做**

本机没有 jadx，也不该为了它自动安装。但「只有类名」到「能读代码」之间还有一层
不需要任何外部工具：**`class_data_item` 里的方法表**。

新增（`apk-probe.ts`）：

| 输出 | 含义 |
|---|---|
| `CLASS_METHOD_TABLE=1034` | 解析出方法表的类数 |
| `METHOD_NAMES_TOTAL=4044` | 方法名总数 |
| `--- CLASS_METHODS_SAMPLE ---` | 类 → 它自己声明的方法名 |
| `OBFUSCATED_METHOD_HINT` | 名字形如 `Mxxxxxxx` 的方法数（**混淆迹象**，不是结论） |

真机效果（`nova_ai` 包，读 3 个 dex）：

```
Lai/v1/ClientMessengerContext$b;: decode, encode, encodedSize
La/a;: a
LJ/N;: M$Y37M6J, M$lotPPc, M14GZgiH, ...
```

第二行说明这个包**部分类没混淆、部分混淆了**——这是能写进报告的结论。

**仍然不做伪代码**：字节码反编译要完整指令解码 + 控制流重建，半对的比不给更误导。
要读方法体仍然需要 jadx。

### 实测修掉 2 处（都是「读错但看着像对的」）

1. **`method_idx_diff` 是相对前一个方法的差值**，不是绝对索引。
   当绝对值用会读出杂乱名字——真机上 199 个方法的类只解析出 1 个名字，其余全空串。
   两段（direct / virtual）各自从 0 累加。
2. **`method_ids` 每项 8 字节**（class_idx 2 + proto_idx 2 + name_idx 4），
   写成 `idx * 4` 会读进相邻项。修前 `La/a;` 读出空串、`beta` 读不出；
   修后 `decode/encode/encodedSize` 这种真名才出来。

**第 2 条是单测抓到的，不是真机**：混淆包里方法名本来就都是随机串，
肉眼分辨不出「读错了」还是「本来就长这样」。这也是为什么这组测试坚持手写 dex 字节。

## B3 ELF 真机验证 —— **本机无样本，未做**

在本机（Git for Windows 的 `usr/bin`、Cursor 的扩展）找过 ELF，没有。
Ghidra 自己按魔数识别格式，代码层面不需要改；等有 Linux 目标时跑一次
`reverse_probe({ target: "/path/to/elf" })` 即可验证。

# 追加：C1-a asar 后端（同日）

设计：[`2026-11-02-P3-EXE与APP复刻设计.md`](../../design/逆向与复刻/2026-11-02-P3-EXE与APP复刻设计.md)

## 做了什么

`reverse_probe` 增加第四个内置后端：**asar**。判据不是扩展名而是文件系统——
`resolveBackend()` 先按扩展名判；判成 `ghidra` 时再看目标同目录有没有 `resources/app.asar`，
有就走 asar。

这解决的是一个真实浪费：Electron 应用的 `.exe` 只是个 Chromium 外壳，喂给 Ghidra
要花 3–5 分钟反编译一堆外壳代码，**真正的业务代码全在 asar 里的 JS**。现在 100ms 出结果。

对应设计 §8 的 **C1-a**。C1-b（技能文档）同批完成；C1-c（L2 复刻配方）按设计**暂不做**——
等 asar 后端在更多应用上验证过后再写，免得写出一条只有作者样本能跑的流水线。

## 输出

`APP_NAME` / `APP_VERSION` / `APP_MAIN` / `APP_DESCRIPTION`、`ENTRIES` / `UNPACKED` / `UNPACKED_DIR`、
`APP_FILE_COUNT` + `APP_FILES`（非 `node_modules`，按体积降序）、
`APP_SOURCEMAPS` / `DEP_SOURCEMAPS`、`BYTES_VERIFIED=n/n`。

## 三个坑（前两个是格式坑，第三个只在 Electron 里出现）

1. **`dataStart` 是 `8 + u32@4`，不是 `8 + u32@12`。** `u32@4` 是 payload 长度、
   `u32@12` 是 JSON 长度。实测两个样本里两者恰好相等（payload = 8 对齐后），
   所以写错了照样能跑——单测用一个 `pad` 变体把两者拉开守着。
2. **`unpacked:true` 的条目不在 asar 内。** 按 offset 读会读到隔壁条目的字节，
   不报错、只是数据是错的。这类条目不计入 `BYTES_VERIFIED` 的分母
   （LiteShell：6988 + 29 = 7017）。
3. **在 Electron 里读 asar 必须用 `original-fs`。** 这一条**只有真机能暴露**：

   | 调用 | 纯 Node / tsx | Electron 里 |
   |---|---|---|
   | `existsSync(asar)` | true | true |
   | `statSync(asar).size` | 45124570 | **0** |
   | `openSync(asar`,'r') | OK | **ENOENT, not found in <asar>** |
   | `readFileSync(asar)` | OK | **ENOENT** |

   Electron 把 `.asar` 当虚拟目录塞进 fs 层。`statSync` 返回 0 尤其误导——错误看起来像
   「文件是空的」。修法：`createRequire(import.meta.url)('original-fs')`，
   纯 Node 没有该模块就退回 `node:fs`。

   真机第一次调用就撞上了：`asar 解析失败：ENOENT, not found in ...app.asar`
   （耗时 0ms，日志里一眼能看出没进到解析逻辑）。

## 实测修掉的一处口径错误

原先把**所有** `.map` 数进 `SOURCEMAPS`，两个样本分别报 `3234` / `18903`，
看起来「这些应用带着 sourcemap，能读源码」。实际上业务代码的 sourcemap 是 **0**——
那三万个全是 `node_modules` 里依赖自带的。

拆成 `APP_SOURCEMAPS` / `DEP_SOURCEMAPS` 后结论才对：**业务代码是压缩产物，只能读结构**。
这是那种「数字是真的、结论是反的」的错误，只有拿真样本跑才会发现。

## 真机证据

| 目标 | 结果 |
|---|---|
| LiteShell 0.2.5（45 MB / 7017 条目） | `ENTRIES=7017 / UNPACKED=29 / BYTES_VERIFIED=6988/6988 / APP_FILE_COUNT=11 / APP_SOURCEMAPS=0`，**102 ms** |
| WeFlow 5.0.0（678 MB / 80967 条目） | `ENTRIES=80967 / UNPACKED=127 / BYTES_VERIFIED=80840/80840 / APP_FILE_COUNT=569 / APP_SOURCEMAPS=0`，**986 ms** |
| 三种入参 | `.exe` / 安装目录 / `.asar` 都路由到 asar；`notepad.exe` 仍走 Ghidra |

真机走的是完整工具路径（`user:send` → Agent → `reverse_probe`），不是直接调函数。

一个额外收获：模型在读完输出后自己指出
「`BYTES_VERIFIED=80840/80840` 但 `ENTRIES=80967`，相差 127，**正好等于 `UNPACKED=127`**，
属正常差额不是校验失败」——文档里那条口径真的被用上了。

## 追加：解包（同日，补齐 L1 的后一半）

第一版只做了「识别 + 校验」，文件还在 asar 里。设计 §2 说 L1 是「认出壳 **并解出内层资产**」，
所以补上 `extractTo`：

```
reverse_probe({ target: "…/LiteShell.exe", extractTo: "projects/_reverse/liteshell/unpacked" })
```

| 输出 | 含义 |
|---|---|
| `FILES_WRITTEN` / `FROM_UNPACKED` | 写了多少文件、其中多少来自 `app.asar.unpacked/` |
| `SKIPPED_NODE_MODULES` | 默认跳过依赖（WeFlow 有 80398 个），要依赖传 `includeDeps:true` |
| `EXTRACT_VERIFIED=n/n` | **落盘的字节**再核一遍 SHA256 |
| `SKIPPED_UNSAFE_PATH` | 路径越出输出目录的条目数 |

### 两处必须单独讲

1. **`BYTES_VERIFIED` 与 `EXTRACT_VERIFIED` 不是一回事。** 前者按头部偏移读 asar、核的是
   「头里写的 hash」；后者核的是**落盘字节**。asar 头来自待分析文件——凭什么是可信的？
   所以解包时再核一遍，两者都过才算数。
2. **路径逃逸是安全边界。** 头部由待分析文件提供，`../../x.js` 这样的条目能把内容写到
   输出目录外。按解析后的绝对路径判前缀，越界跳过并计数。**这条有单测守着**
   （`/../../escaped.js` 用例断言它没写到任何祖先目录去）。

### 实测

| 目标 | 结果 | 耗时 |
|---|---|---|
| LiteShell 0.2.5 | `FILES_WRITTEN=11` / `EXTRACT_VERIFIED=11/11` / `SKIPPED_NODE_MODULES=7006` | 49 ms |
| WeFlow 5.0.0 | `FILES_WRITTEN=569` / `SKIPPED_NODE_MODULES=80398` | 424 ms |

抽查：解出的 `out/renderer/assets/index-JMRNKZQK.css` 的 SHA256 与 asar 头里写的
`integrity.hash` 逐字节一致（`9cbe6ca1…`），说明「读偏移 → 写盘」这条链没有错位。

真机走完整工具路径（`user:send` → Agent → `reverse_probe`），产物落在工作区
`projects/_reverse/liteshell/unpacked/`，`out/{main,preload,renderer}` 齐全，耗时 169 ms。

## B4 `.aab` 解析 —— **从「明确拒绝」变为「内置解析」**

原先拒绝的理由是「manifest 是 protobuf」。这条只说对了一半，而且推导出了错误的取舍：

- `base/manifest/AndroidManifest.xml` 确实是 protobuf（`Resources.proto` 的 `XmlNode`）；
- 但 `base/dex/classes*.dex` 与 APK 里的 **完全相同**，现有 `summarizeDex` 直接可用；
- 那个 protobuf 就是**标准 wire format** 加一层固定消息结构，不是编码奇观。

写一个 80 行的通用解码器 + 一个树遍历就能拿到 package / versionName / 版本 / SDK / 权限 / 组件，
成本远低于「让用户先去装 bundletool」。

### 新增 `aab-probe.ts`

| 段 | 来源 |
|---|---|
| `PACKAGE` / `VERSION_NAME` / `VERSION_CODE` / `MIN_SDK` / `TARGET_SDK` | protobuf manifest 的字符串属性 |
| `PERMISSIONS` / `PERMISSIONS_SENSITIVE` / `EXPORTED_COMPONENTS` | 同上（与 APK 同一套判据） |
| `MODULES` | zip 顶层目录（`base` 一定有，`feature*` 另列） |
| `DEX_COUNT` / `DEX_READ` / `URL_COUNT` / `CLASS_METHOD_TABLE` | **复用 APK 的 dex 解析** |
| `ABIS` / `NATIVE_LIBS` / `FRAMEWORK` / `PACKER_SUSPECT` | zip 条目名 |

### 三处值得记的实现细节

1. **varint 必须按 64 位读**。用 `(x << 7)` 拼 32 位整数在超过 4 字节时静默截断——
   短字段不会踩到，`resource_id` 这类会，而截断不报错。用 BigInt 累加到最后再转。
2. **`XmlElement.child` 的类型是 `XmlNode`，不是 `XmlElement`**。少包一层会让树遍历在
   第二层就解不开（单测里我用错了，解析器当场报 `wire type 3`——正好说明「显式报错」
   比「静默跳过」值钱）。
3. **未知 wire type（3/4，已废弃的 group）直接抛错**。静默跳过会让后续字段全部错位，
   而错位后的输出**看起来仍然像个结果**——这是本仓库反复出现的那类 bug。

### 边界（不改）

- `compiled_item`（编译后的资源引用）不解析：那要接 `resources.pb` 的资源表。
  所以 `label` / `icon` 读不到是**正常的**，不是解析失败。
- 不产出 APK、不做签名、不合并分包。安装后的形态（哪个设备拿哪个 split）仍然用 bundletool。

### 与 APK 后端的关系

`.aab` 现在有自己的后端（`pickBackend` 返回 `'aab'`），不再落进 APK 的拒绝分支。
APK 侧那条分支保留并改了文案：万一有人直接拿 `.aab` 调 APK 解析器，
错误会**指向 aab-probe** 而不是只说「请装 bundletool」。

### 测试

新增 14 条（`aab-probe.test.ts`），同样**造真字节**：手写 protobuf 编码器把一棵
`XmlNode` 树写出来，再让解析器读回来。用 `Buffer.from('...')` 假数据测不出任何东西。
覆盖：varint 64 位、长度越界、未知 wire type、嵌套子元素、缺失 value 的属性、
dexLimit、模块排序、manifest 解出 0 元素的报错路径。
