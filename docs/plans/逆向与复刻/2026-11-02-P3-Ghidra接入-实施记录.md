## 实测暴露并修掉的 3 处

### 1. 能力标签的松散匹配把无关导入归错类

第一版用 `connect$` 匹配 network，真机上 **`SCardDisconnect`（智能卡）被归进了 network**。
标签一错，整段结论都跟着错。改为**锚定全名或明确前缀**（`^(socket|connect|send|recv|bind|listen|accept|closesocket)$`）。

修后 `certutil.exe` 的 network=3 全是真正的 WinInet（`InternetOpenUrlW` 等）。

### 2. 字符串段混进导入符号名

Ghidra 把外部符号也挂成 defined data，不过滤的话
`GetLastError` / `RtlQueryFeatureConfiguration` 会混进「字符串线索」里——
看着像发现了什么，其实一个字节的字符串都没读到。现在按 `IMPORTS_ALL` 集合排除。

### 3. 反编译名额被 CRT 样板函数占满

按引用数排序，`notepad.exe` 的前两名是 `__security_check_cookie`(76) 与 `__GSHandlerCheck`(70)。
`--decompile 3` 会返回三个样板函数，用户会以为「这程序没什么逻辑」。
加 `isCompilerHelper()` 排除 `__*` / CRT / GS 系列。

## 真机证据

**自检**（`node scripts/ghidra/reverse-probe.selfcheck.mjs`）：
不设 `LUMII_GHIDRA_DIR` → 8 条降级/源码断言全过；
设了 → 额外 5 条真机断言全过（含「反编译目标不是 CRT 样板」）。

**技能内真跑**（`/reverse C:/Windows/System32/certutil.exe`）：

```
FUNCTIONS=3278     IMPORTS=831
CAPABILITY.crypto=118      CAPABILITY.registry=11
CAPABILITY.network=3       CAPABILITY.file=3
CAPABILITY.debugger=1      CAPABILITY.inject=1
```

Agent 的产出（`projects/_reverse/certutil/analysis/`）质量要点：

- 用探针定位到 `FUN_1400c0c44`（refs=2727），反编译后判出它是**格式化输出核心**：
  `GetStdHandle(STD_OUTPUT_HANDLE)` → 宽字符格式化 → `GetFileType` 分三路
  （控制台走 `WriteConsoleW`，重定向走 `WriteFile`）
- **主动纠正了探针的标签误读**：`inject=1` 只来自 `VirtualAlloc`，反查
  `CreateRemoteThread` / `WriteProcessMemory` 命中数为 0 ⇒ 不下「注入了」的结论
- `wmain` 没挖出来 → 如实写进 `UNRESOLVED`，并说明下一步该怎么找（跟调用链 / 按字符串交叉引用）
- 附带的真发现：`.rsrc` 只有 4.1 KB，中文帮助在 `certutil.exe.mui` —— 只看 `strings` 会低估功能面

**耗时**：`notepad.exe`（534 KB）3m29s；`certutil.exe`（1.9 MB）约 4 分钟。

## 真机暴露的用法问题（已修）

Agent 第一轮用 `nohup … & sleep 90` 起分析，觉得没进展又跑了一遍——**白烧 4 分钟**，
两次输出逐字节相同。修法两层：

1. 脚本启动时把预估耗时打到 stderr，并明说「重复跑不会更快」；
2. `desktop.md` 写明**同步等它返回**，不要 nohup + 轮询。
