## P0 — 可行性验证（先决条件）

**目标**：把三个"不验则设计可能整体不成立"的假设钉死。**任一失败就停下来重新讨论设计，不要往下走。**

### P0-1 双击 Ctrl 键盘钩子 spike

| 步骤 | 内容 |
| --- | --- |
| 1 | 选依赖：优先 `uiohook-napi`（查是否有 win32-x64 prebuild，避免本地编译） |
| 2 | 写一个**独立最小脚本**（不进插件、不进主进程），只做：监听全局按键 → 检测双击 Ctrl → `console.log` |
| 3 | 在 dev 环境跑通，确认能捕获任意前台窗口下的 Ctrl 双击 |
| 4 | 主动测边界：`Ctrl+C` 后再按 Ctrl **不应**触发（`dirty` 标志）；连按三次 Ctrl 的行为 |
| 5 | 测杀软：观察 Windows Defender / 本机安全软件是否拦截或报毒 |
| 6 | 测 ABI：`pnpm install` 后 Electron 主进程能否正常 `require` 该原生模块 |

**验收**：给出结论「钩子可用 / 不可用 / 有条件可用」，附实测证据。

**决策分支**：

- ✅ 可用 → P3 走钩子为主路径
- ❌ 不可用 → P3 只做 `globalShortcut` 组合键，双击 Ctrl 记为已知限制并写进文档（**功能降级，但项目继续**）

### P0-2 ~~FTS5 在 Electron 运行时可用性~~ ✅ 已完成（2026-11-14）

探针：`verify/listary-p0/fts5-spike.cjs` → `fts5-spike.out`；诊断：`probe-bs3.cjs` → `probe-bs3.out`。

**结论：通过，且推翻了原设计的驱动选型。**

- Electron 36.9.5 内建的 `node:sqlite` 是 SQLite **3.50.4**，编译项含 `ENABLE_FTS5`
- `better-sqlite3` **未为 Electron 重建**（ABI 127 vs 135，`require` 即抛错）→ **不再使用它**
- 决定性旁证：生产库的 3 张 FTS5 表（1606 / 1109 / 1748 行）都是 Electron 的 `node:sqlite` 建的
- 预分词中文检索全命中；不预分词的对照组确认零命中
- 查询转义防住 FTS5 语法注入
- **净收益：零新增原生依赖**，省掉 ABI 重建与 asar unpacked 路径处理

**两个行为边界已记入设计 §3.1**：单字 CJK 查询落空；OR 语义带出弱命中条目（故 P2 必须接最小命中过滤）。

### P0-3 ~~独立索引库可开与 pragma~~ ✅ 已完成（2026-11-14）

WAL 生效、`lz_*` 表创建、主表与 FTS 行数一致、**与主库并行无锁冲突**、重开后数据完整可检索。
体积外推作废（6 条样例不足以外推，其中约 48 KB 是建库固定开销）→ 已列 R8，**P1 必须用万级条目重测**。

### P0-1 ~~双击 Ctrl 键盘钩子 spike~~ ✅ 已完成（2026-11-14）

探针：`verify/listary-p0/hook-spike.cjs` → `hook-spike.out`。**20 项全通过。**

**结论：可用。** `uiohook-napi@1.5.5` 是 **N-API 模块**，自带 `win32-x64` prebuild，
在 Electron 36.9.5 主进程内 `require` + `start()` 成功，**无需本地编译、无需 ABI 重建**。
端到端用 `keybd_event` 注入真实低级键盘事件，5 个场景全部符合预期。

**算法必须按实测结果写**（第一版被 `Ctrl+C` 打脸，见设计 §3.3）：

- 判定依据是「**一次 Ctrl 按住期间没夹别的键**」，**不是**「两次 Ctrl 之间没夹别的键」
- `Ctrl+C` 的 C 夹在 Ctrl 的按下与松开之间，用后者会把 `Ctrl+C` 的收尾误判成干净点击，
  导致紧接着按 `Ctrl`（如 `Ctrl+V`）误弹启动器
- 触发后必须重置状态，否则三连击会变成两次触发

**残留风险（不因本机通过而消除）**：杀软拦截、企业策略、**UAC 提权窗口与安全桌面**下能否收到事件——
本机均未复现，换环境必须复验。故 **`globalShortcut` 组合键兜底**照原计划同期实现。

### 依赖引入（P0 结论确定后再动 lockfile）

本次 spike **未改项目依赖**（从临时目录按绝对路径 require）。进 P3 实现时再正式加：

```bash
pnpm --filter ./apps/windows add uiohook-napi@1.5.5
```

⚠️ 它含原生 `.node`，需确认 electron-builder 正确 unpack（与现有 `@img/sharp-*`、
`sherpa-onnx-*` 等平台包同类处理，见 `AGENTS.md` 的平台包声明注意）。

### 实现时用哪个驱动 ⟶ **`node:sqlite` 的 `DatabaseSync`**

```ts

```

不再考虑 `better-sqlite3`。`applySqliteConnectionPragmas` 仍复用（它只依赖 `exec` 方法，与驱动无关）。

**P0 交付**：结论见设计文档 §11。**剩下 P0-1 待验。**

## P2 — 检索质量 ✅ 已完成（2026-11-15）

**交付见** [`2026-11-15-P2检索质量-实施总结.md`](2026-11-15-P2检索质量-实施总结.md)。

**两处被实测推翻的公式结构错误**（都不是"参数没调好"）：

1. **min-max 归一化让个性化信号永远翻不了盘** —— 它无条件把候选拉满 `[0,1]`，
   把 `-10` 与 `-9.9` 拉成 `1.0` 与 `0.0`，造出假鸿沟。后果：用过 50 次的仍排不过
   相关性略高但没用过的。改为**饱和变换** `|bm25|/(|bm25|+2)`。
2. **频次封顶过早** —— `min(cap, w*log(1+count))` 在 `count=2` 就触顶，之后 10/100/1000 次无差别。
   改为按参考次数（20）归一。

**评测结果**：字面组 10 条查询**测不出差异**（0.940 → 0.940，bm25 本来就排对了）——
探针会显式提示这一点，不粉饰。**判别组 4 条全部符合预期**（前 3 条加权改变了首位且改对了，
第 4 条"相关性差距大时不该翻盘"加权正确地没改）。使用历史实测把第 3 条顶到第 1 条。

**新增不变量断言**：连续检索 20 次后 `lz_usage` 行数 0 → 0（防"搜过即用过"的自激，
对照 `memory/scorer.ts` 记录的那次事故）。

### 原计划任务（已完成）

- [x] `rank.ts`：bm25 饱和变换 + 前缀/包含 + 频次 + recency + 根优先级 + 深度惩罚
- [x] 权重写死为常量并注明依据（**未建配置系统**）

| P7 内容搜索 | 2–3 天 | 中（体积/耗时） |
| P8 对话框跳转 | 2–3 天 | **高**（脆弱） |
| P9 设置与打磨 | 1–2 天 | 低 |

**合计约 15–21 天**。P0 结束后应重新评估 P8 是否值得做。
