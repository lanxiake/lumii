## 两个被实测推翻的实现（重要）

调参过程中发现两处**公式结构错误**，都不是"参数没调好"：

### 1. min-max 归一化让个性化信号永远翻不了盘

首版 `normalizeBm25` 用候选集内 min-max。问题：它**无条件把候选拉满到 `[0,1]`**，
于是两个真实相关性接近的候选（bm25 `-10` 与 `-9.9`）会被拉成 `1.0` 与 `0.0` ——
造出一个比真实差距大得多的**假鸿沟**。

后果实测：用过 50 次的条目**仍排不过**相关性略高但从未用过的。"越用越准"成为摆设。

改为**饱和变换** `|bm25| / (|bm25| + k)`（`k = BM25_SATURATION_K = 2`）：
保留相对差异（`-10` 与 `-5` → `0.833` 与 `0.714`，差 0.12 而非 1.0）。
该函数在 `|bm25|` 上单调递增，故不改变纯相关性排序的方向，只是不再拉伸量程。

### 2. 频次封顶太早，只对头两次生效

首版 `Math.min(cap, weight * log(1 + count))` 配 `weight = cap = 0.25`，
在 `count = 2` 就触顶 —— 之后 10 / 100 / 1000 次**全无差别**。

改为按参考次数归一：`cap × min(1, log(1+count) / log(1+USAGE_REFERENCE_COUNT))`，
`USAGE_REFERENCE_COUNT = 20`（`count=1` 拿 23%、`5` 拿 62%、`20` 拿满）。

## 评测结果

### 字面组（10 条真实查询）—— 测不出差异，如实记录

在 `E:\my-project`（36 745 条）上跑：

| 指标 | 纯 bm25 | 加权排序 |
| --- | --- | --- |
| 平均 P@5 | 0.940 | 0.940 |
| 首位命中率 | 1.000 | 1.000 |

**完全一致。** 探针会显式提示这一点：这组查询的关键词字面就在文件名里，
bm25 本来就排得对，**加权没有发挥空间**。这不能证明加权没用，只能证明这组评测集测不出来。

（`「启动器」` P@5 只有 0.40 —— 因为判据词 `启动器`/`listary` 在路径里本就少见，属评测集问题。）

### 判别组（4 条刻意构造的用例）—— 证明加权有效

基线一律是**正确的 bm25 升序**（bm25 为负，越小越相关）：

| 用例 | 纯 bm25 首位 | 加权首位 | 期望 | 结果 |
| --- | --- | --- | --- | --- |
| 前缀命中 vs 仅包含 | #1 | **#2** | #2 | ✅ 改变了，且改对 |
| 开始菜单程序 vs 深埋同名文件 | #1 | **#2** | #2 | ✅ 改变了，且改对 |
| 常用项 vs 相关性略高但没用过 | #1 | **#2** | #2 | ✅ 改变了，且改对 |
| 相关性差距很大时使用历史不该翻盘 | #1 | #1 | #1 | ✅ **没改**（正是期望） |

前三条证明加权在 bm25 排错的地方纠正了它；第四条证明有上限、不会"越用越偏"。

### 使用历史闭环（真实目录）

查询 `zip`，对第 3 条模拟打开 30 次：**位次 3 → 1**（↑2 位）。

### 权重敏感性

bm25 权重从 1.0 压到 0.3，结论都不变（使用历史始终能翻盘）——
说明饱和变换后个性化信号**有足够余量**。若换回 min-max，这一列会全部显示"高相关未用过"。

### 不变量：检索不写使用历史（防自激）

`memory/scorer.ts` 记录过一次自激事故：recency 用「每次注入都被刷新」的字段，
于是被注入的条目恒得满分、更易再被注入（9 条吃掉 54% 席位）。

启动器里的等价风险是：**检索过程被记成使用** → "搜过"变成"用过" → 越搜越偏。

探针加断言：连续检索 20 次后 `lz_usage` 行数 **0 → 0** ✅。使用历史只由显式的
`recordUsage` 写入（P3 的"打开"动作会调它）。

## 权重表与依据

`DEFAULT_WEIGHTS`（各项之和 ≈ 1.78，任一单项绝对值即"它最多贡献多少分"）：

| 权重 | 值 | 依据 |
| --- | --- | --- |
| `bm25` | 0.9 | 相关性最大，但饱和变换已让差距温和，故可占主导 |
| `namePrefix` | 0.35 | 判别组第 1 条实测：前缀命中该赢过仅包含 |
| `usage` | 封顶 0.25 | 判别组第 3/4 条实测：能翻盘，但有上限 |
| `root` | 0.18 | 判别组第 2 条实测：开始菜单该赢过深埋文件 |
| `nameContains` | 0.15 | 只是"包含"，区分度低于前缀 |
| `recency` | 0.12 | 比频次更弱：一次"上周用过"不如"用过十次" |
| `depthPenalty` | 0.03 | 只做同分时的微妙区分（>3 层才罚） |

同分时的稳定次序：**Start Menu → 短路径 → path 字典序**（最后一条保证输出可复现）。

## 遗留

- **字面组评测集判别力不足**：10 条查询 bm25 本来就对。要真正量化加权收益，需要
  **带标注的真实日志**（用户输入 → 最终打开了什么）。当前用判别性用例替代，
  能证明"该改的改了、不该改的没改"，但给不出端到端的命中率提升数字。
- **`namePrefix` 只比对了"开头/包含"两级**：没做模糊前缀（如输 `sj` 命中 `设计`），那是 P6 拼音的范畴。
- **`size`/`mtime` 仍不参与打分**：P1 为省 `stat` 未采集。若将来要"最近修改优先"，需补采集。
