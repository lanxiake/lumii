## 一、现状实测（本机 2026-09-16）

### 1.1 四个资产

| 资产 | 现状 | 判断 |
|---|---|---|
| 系统提示词 | 两家都有专属 prompt，片 11 已深化 | ✅ 是「自己的」 |
| 工具面 | 情报 13 / 维护 **31** / 记事 11（`definitions.ts` 实点） | ⚠️ 维护已进官方警告区间 |
| 会话 | `cron:<jobId>`（历次执行累积）+ `evolution:<id>`（自主，空转） | ⚠️ 有壳，见 1.2-① |
| 记忆 | **情报 5 条、维护 0 条**，且情报那 5 条混着 1 条垃圾 | ❌ 基本没用起来 |

### 1.2 四条已核准的机制事实（都不在提示词层面）

**① cron 执行是「无历史的」。**
`createInstanceById` → `prompt` → `destroy`，每次都是全新实例；把历史注入实例的 `restoreHistoryForInstance` **只在上下文压缩时被调用**（`bridge-context-compactor.ts:408`）。
→ `cron:<jobId>` 会话里累积的「第二轮/第三轮」记录，**Agent 执行时看不到**。

**② 自主开关对它们没开。**
`app.json` 的 `autonomousAgents` 是 `null`，但库里躺着它们名下的待执行目标（`autonomous_goals` 里 info-curator 5、system-keeper 2、chronicler 3 条 pending）——**有目标、没开关，永远不会执行**。

**③ 提示词进化的池子只有主助手一份。**
`prompt_variants` 全库 1 个 baseline（`expression-style`）、3 个变体、373 次试验。这两位**永远不会因为效果不好而自己变好**。

**④ 记忆的两条写入通道都不通，而且会产垃圾。**

| | 病因 | 依据 |
|---|---|---|
| 维护 | **纯「没写」**：提示词没让它写；自动提取只从**用户消息**抽（`memory-integration.ts:137` 读 `pickLatestUserText`），且节流是 `turnCount % extractEvery`，短会话永远不触发 | 库内 0 条 |
| 情报 | **「写了没用上」**：5 条靠提示词命令写入，但没有**确定的读取路径**，下轮靠 `memory_search` 在全局 228 条里碰运气 | 库内 5 条 + 该机制产出过 `的「少推」有哪些。"}]` 这类截断垃圾 |

> 情报那 5 条里有一条是标准领域经验：「web_search 结果被日历/AI工具导航类页面严重污染，几乎不可用；可靠路径是直接抓列表页——36氪快讯」。**这就是通用 Agent 攒不出来的东西**，说明这条路本身成立。

### 1.3 结论

> 这两位现在**有身份，没有积累**：会话是给用户看的、目标是挂着的、进化轮不到、记忆靠提示词偶然写几条。
> 且由于 ①，**唯一能跨执行传递的就是我们显式存下来并显式注入的东西**。

## 二、调研要点

### 2.1 记忆架构

**分层**：CoALA（arXiv:2309.02427）的四分法引用最多——working / episodic / semantic / procedural；且它把「反思」建模为 **learning action（写长期记忆的操作）**，不是记忆的一层。

**该用什么形态**：Letta 给了唯一的尺寸判据——*"For smaller amounts of data, it is best to simply place everything into the context window with memory blocks"*（<50k 字符 / <20 块）。台账天然属于这一档，**不需要上向量库**。

**结构化 vs 自然语言**：
- 支持方（arXiv:2604.27906 Schema-Grounded Memory）：生产要的记忆操作是**精确事实 / 当前状态 / 更新删除 / 聚合 / 关系 / 否定查询 / 显式未知**，这要求记忆「**更像 system of record，而不是更像搜索**」；做法是「把解释工作从读路径搬到写路径」。
- **反对方（更该记住）**：Mem0 自家消融——图记忆在 single-hop **65.71 vs 67.13**、multi-hop **47.19 vs 51.15**，**都比纯自然语言差**，只在 temporal/open-domain 回本。IBM/VLDB 2026：重结构「会把 token 预算花在下游检索栈根本不用的抽象上」。
- → **按查询类型分治**，不要用一种记忆包打天下。

**反思的危险**（arXiv:2605.29463，ICML 2026 Workshop）：agent 会**存储对任务的自信但错误的解释**并持续依据它行动。实测 16 个卡死环境，**121 条反思 0 条命中正确目标**；换成「程序化提取轨迹级失败信号」后正确率 **0% → 86%**，RRR **0.64 → 0.10**。

**巩固会破坏信息**：recursive summarization **35.3%** vs full-context **98.0%**（DMR）。→ **台账不能替代原始日志**，它只是派生视图。

**检索失败才是主因**：Generative Agents 论文自述最主要的错误来源是「检索不到该检索的记忆」，并把 "improper memory retrieval" 列为架构崩溃点。→ **写得进 ≠ 用得上**。

**可直接借用的机制**：

| 需求 | 机制 | 出处 |
|---|---|---|
| 台账形态 | **JSON 而非 Markdown**；每项含 `passes` 类**状态字段**；agent 只准改状态字段 | Anthropic harness |
| 计数语义 | insight 列表 + **ADD / UPVOTE / DOWNVOTE / EDIT** | ExpeL arXiv:2308.10144 |
| 状态更新 | **非破坏性**：不删旧行，只写失效时间戳 | Zep bi-temporal arXiv:2501.13956 |
| 结论形态 | 自然语言 + **指向证据的编号指针** | Generative Agents arXiv:2304.03442 |
| 命名空间 | `/agent/{agent_id}/...`，深度 ≤3；跨 agent 共享用**显式只读 slice** | CrewAI |
| 监控 | **RRR**：同一条（错误的）记忆被反复倚重的次数 | Honest Lying |

### 2.2 专家 Agent 与提示词进化

**人设基本无效**（多篇交叉）：
- Zheng et al. EMNLP 2024：162 个人设 × 2410 题 × 9 模型 —— *"none of the personas lead to statistically better model performance"*
- PRISM：MMLU 上 expert persona **68.0% vs baseline 71.6%**，**人设越长越差**（66.3%）
- 无关的人设细节可致性能下降**接近 30 个百分点**

**多 Agent 的收益在算力对齐后经常消失**：
- MAST（arXiv:2503.13657）：7 个框架 **失败率 41%–86.7%**；最高频失败是 step repetition 15.7%、reasoning-action mismatch 13.2%，而 **"disobey role specification" 仅 1.5%** → 「把每个专家的提示词写得更好」往往不是瓶颈
- Anthropic 2026 产品博客：*"teams invest months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equivalent results"*；按职能拆 agent 是反模式，实测「**子 agent 花在协调上的 token 多于干活**」
- Cognition 的自我修正：*"multi-agent systems work best today when **writes stay single-threaded** and the additional agents **contribute intelligence rather than actions**"*

**工具面收敛（本次 ROI 最高的一招）**：

| 来源 | 数字 |
|---|---|
| Anthropic 官方文档 | *"degrades once you exceed **30–50** available tools"* |
| Anthropic 产品博客 | *"when an agent has **15-20+ tools**…"* |
| RAG-MCP (arXiv:2505.03275) | 工具选择准确率 **13.62% → 43.13%**，prompt token **降 >50%** |
| Anthropic Tool Search | MCP 评测 **49% → 74%**（Opus 4）；tool 定义 token **降 85%** |
| ToolRet / API-Bank | **收敛有代价**：必须配 fallback（高频工具不延迟加载） |

关键补充：错误主因是**语义相近的工具互相干扰**，不是数量本身（MetaTool：Top-5 相似工具命中率近 50%）。

**提示词进化的门槛**：
- MAGE（单作者预印本，arXiv:2607.11944）：N=30 时 **GEPA 优化后 62.4% → 34.0%（−28.4pp）**，手工固定脚手架 70.0%；原文 *"scaffold choice dominates optimizer choice in low-data regimes"*
- DSPy 官方：**≥200 条**才建议跑 MIPROv2；官方还推荐反常的 **20% 训练 / 80% 验证**
- ProTeGi：**约 3 步后开始过拟合**；OPRO 自承训练比测试高 **5%–20%**
- **Self-Refine / Reflexion 不是提示词优化器**（前者无更新步骤，后者反思任务结束即丢弃）——这两家常被误引

**便宜的替代**：失败案例 → 错误分类学 → **3–5 条 few-shot**（ETGPO 只用 1/3 预算）；以及 Anthropic 内部的做法——让 agent 拿坏工具反复试，然后**重写工具描述**，任务完成时间 **−40%**。

### 2.3 领域 Agent 成熟实现

**事件级去重 = 三层数据模型**（GDELT 与 Event Registry 独立收敛到同一结构）：

| 层 | 解决什么 | GDELT | Event Registry |
|---|---|---|---|
| 0 | 同一篇稿被转载 | — | `isDuplicate` |
| 1 | 不同稿写同一件事 | `GlobalEventID` | `eventUri` |
| 2 | 多天多事件构成一条线 | — | `storyUri` |

关键：**去重的产出是「一个事件带 N 个来源」，而不是删掉 N 篇**。这顺带解决「情报不知道自己推过什么」。
线上验证参数（$100/月、180+ 源公开实践）：相似度阈值 **0.7**、文章与事件时间差 **≤18h**、事件存活 **≤36h**、事件向量只对最近 **3 篇**滑动平均；两遍聚类（先匹配已有事件吸收 70–80%，剩余建边取连通分量）。**已知失效**：带强烈本地语境的地区新闻会漏并——作者选择**宁可漏并也不降阈值换误并**。
跨语言注意：MinHash+LSH **只适用同语言**（中英日法同一事件 3-gram Jaccard = 0）。

**来源质量：别自建**。Ground News 的做法是**聚合外部评分取平均**（bias 取 AllSides + Ad Fontes + MBFC），自己只编了 2,276 家媒体的归属。两条硬约束：评分是**按出版物整体**的（只能降权，不能当"这篇可信"的判据）；**LLM 打的分与人类专家只有 ρ=0.50**，且指派党派角色会稳定使评级偏斜。

**「少推 X」的完整形态 = 四件套**：①规则对象化 + ②落库前**预览命中集** + ③**显式冲突优先级** + ④规则日志。
NewsBlur 作者原话：用户一直在**盲选**——过去只能先训练、再看整个 feed 的分数变化，这是规则训歪的唯一来源。只做①是当前最常见的半成品。

**维护动作：二十年了，业界从不自动改**。MediaWiki 特殊页面族（孤儿页/死链页/过期页）**从设计上就没打算自动改**。清理照 BCA 三级：**先只加标记不改内容 → 攒够再合并 → 可恢复窗口 + 清除前预告**。两条交互细节：**跳过不丢**（Guru 的 Skip 留在队列）；**冷却期 7 天**（否则会被整体静音，比不提醒更糟）。
合并本身抄 Obsidian Note Composer：**改写所有指向被合并条目的引用**（只删不转会留断链）+ **快照恢复兜底**。

**建议→确认→执行的四条不变式**（Terraform plan / CFN change set / ArgoCD diffing / Dependabot 收敛而来）：
① 预览**零副作用**；② 确认后执行**被审过的那一份**（不是重新生成一遍）；③ 结果写回**同一条**台账记录；④ **可回滚**或至少可追溯。

**台账粒度**：n8n 到**节点级**输入输出（逐节点可看、失败可重跑）；Home Assistant 的 Logbook 是**按时间铺开的事件流**而非任务表——后者更贴合「你今天都为我做了什么」这个真实提问。

## 三、调研与现有方案的对照

### 3.1 被证实的（方向对了）

| 我们的判断 | 调研证据 |
|---|---|
| 机械项该交给代码，不该让模型反思出结论 | Honest Lying：121 条反思 0 条命中；程序化提取后 0% → 86% |
| 提示词进化现在不能开 | MAGE：62.4% → 34.0%；DSPy 官方 ≥200 条 |
| 「人设」不是能力来源 | Zheng EMNLP 2024；PRISM 68.0 vs 71.6 |
| 台账应是「可被代码判定的状态」 | Schema-Grounded Memory 的 system-of-record 论证 |

片 11 补的全是**领域约束、输出格式契约、检查清单、专属工具**——正是「更划算的那两件事」。

### 3.2 被推翻 / 需修正的

| 原方案 | 修正 |
|---|---|
| 「台账把领域状态结构化」（范围过宽） | **收窄到检索式记忆做不到的查询**（计数/聚合/时序）；其余仍用自然语言，不搞全量结构化 |
| 台账是主要记忆载体 | **台账是派生视图**，原始 episode 必须无损保留（35.3% vs 98.0%） |
| 先设计存储形态 | **读取路径先于存储**（O4：写得进 ≠ 用得上） |
| （未提） | **工具面收敛比改提示词更划算**，且维护的 31 个已超标 |
| 「给每个 Agent 独立做提示词进化」 | **门槛 ≥200 条机械可判定记录**；在此之前只做失败案例 → few-shot |
| 想加更多能力/协作 | **先别加 Agent**（MAST 41–86.7% 失败率；协调 token 可能多于干活 token） |

## 四、方案（拟，待拍板）

### P0 · 确定性收益

| # | 做什么 | 为什么是它 | 体量 |
|---|---|---|---|
| 1 | **工具面收敛**：维护 31 → 目标 <20（`memory_*` 三件套合并、`wiki_*` 收敛、`app_*` 7 个收成 2–3 个）；高频工具不延迟加载 + 其余可搜 | 调研里 ROI 最高、最确定；"错误主因是语义相近工具互相干扰" | 中 |

| # | 做什么 | 关键约束（来自调研） |
|---|---|---|

## 七、可直接借用的机制清单（备查）

| 需求 | 机制 | 出处 |
|---|---|---|
