## 一、证据基础

### 1.1 工具使用的全量统计

`tool_usage_stats`：**124 个工具、8312 次调用、0 个零调用工具**（每个注册过的工具都至少被用过一次）。

分布极陡（前 6 项占 69%）：

| 排名 | 工具 | 调用 | 失败 | 失败率 |
|---|---|---|---|---|
| 1 | `bash` | 1726 | 2 | 0% |
| 2 | `file_read` | 941 | 16 | 2% |
| 3 | `file_write` | 938 | 3 | 0% |
| 4 | **`web_fetch`** | 555 | **123** | **22%** |
| 5 | `file_edit` | 533 | 2 | 0% |
| 6 | **`web_search`** | 418 | **181** | **43%** |
| 7 | `grep` | 375 | 6 | 2% |
| 8 | `glob` | 307 | 5 | 2% |
| 9 | `list_dir` | 291 | 12 | 4% |
| 10 | `memory_search` | 208 | 0 | 0% |

失败的**只有三个工具**超过 20%（count≥10）：`web_search` 43%、`image_generate` 31%、`web_fetch` 22%。

低调用尾巴（我们自己的内置工具，1–9 次）：`memory_read` 1、`session_create` 1、`asset_checkup` 1、`cron_guide` 2、`scene_memory` 2、`news_preference` 2、`info_status` 2、`session_resume` 2、`app_scroll_to_bottom` 2、`maintenance_report_write/read` 3、`skill_list` 4、`session_list` 4、`weixin_send_guide` 4、`wiki_read` 7、`file_mkdir` 8、`skill_search` 8、`dashboard_feed_read` 9、`app_scroll_to_text` 9。

### 1.2 三个数据缺口（这决定了 P0 的顺序）

**① `tool_usage_stats` 没有 agent 维度。**
表结构是 `tool_name PRIMARY KEY, count, error_count, last_used_at`——**全局按工具名计数**。所以「维护到底用没用过 `wiki_read`」这个问题，**现有数据答不了**。

**② `tool_audit_log` 的 `agent_id` 存的其实是实例 id。**
实测取值是 `agent-1789048421480-wst9ns` 这种形状（实例 id），不是 `system-keeper` 这类定义 id，且**没有回连路径**（实例不落库）。另外它只覆盖 14 个条目，且大头是 LLM 调用（`llm:openai:Qwen3.8-Flash-Next` 6526 次），**不是完整的工具审计**。`web_search` 在它里面 **0 行**。

**③ 失败原因不可见。**
`error_count` 只有次数，没有错误文本。所以 `web_search` 那 43% 到底是被限流、无结果、还是解析失败——**查不到**。

### 1.3 从数据里读出的四条结论

1. **`web_search` 43% 失败率是本机工具面最大的单点问题**（181 次失败），且它正是情报的主力工具。这与情报自己攒下的那条领域经验互相印证——它写的是「web_search 结果被日历/AI工具导航类页面严重污染，几乎不可用；可靠路径是直接抓列表页」。**两条独立证据指向同一个工具。**
2. **高频工具全是通用的**（bash / file_* / grep / glob / list_dir），专属工具的调用量普遍在个位数到几十。这符合预期（专属工具才刚做），但它也意味着：**收敛专属工具对整体效率的影响有限**。
3. **低调用 ≠ 可删**。`cron_guide` 2 次、`scene_memory` 2 次这类是「低频但关键路径」——它们不常被调是因为对应的场景不常发生，不是因为没用。**判据应该是「语义是否与别的工具重叠」，不是调用次数。**
4. **`app_*` 家族确实在用**（`app_goto_and_screenshot` 82、`app_act` 42、`app_screenshot` 36、`app_goto` 10），不是死工具。⚠️ 我一度因为 `docs/temp/工具使用情况.md` 里没有它们而误判——那份 md 是**过滤视图**（47 项 vs 库里 124 项），别拿它当全量。

## 二、P0-0 · 先把测量补上（前置，否则 P0-1 无据可依）

**为什么排第一**：调研的结论是「仪器读数错了，后面全错」。现在要做的是**逐 Agent 的工具收敛决策**，而现有数据答不了「谁在用」。在没有这个数据之前做合并，等于凭感觉砍。

若采纳 §3.4 的家族合并，再减 7 → **20**。

### 3.3 绕不开的问题：`bash` 让白名单收敛失去意义

`bash` 在维护的白名单里，且实测是**全库第一高频工具（1726 次）**。它没有沙箱、没有目录限制、120s 超时——**能跑任意命令**。

于是：把一个 33 个工具的白名单收敛到 27，而其中留着一个能 `curl`、能 `node -e`、能读写任意文件、能跑 `lumii-ui` 的 `bash`——**边际收益非常有限**。

三条路，需要你选：

| 路 | 做法 | 代价 |
|---|---|---|
| **A 保留 bash**（现状） | 认了——白名单主要防误用，不防能力 | 收敛变成"整理桌面"，收益小 |
| **B 把 bash 换成专用命令工具** | 新增 `lumii_settings`（读写设置）、`run_guide_sync`（跑 sync:guides）等，删掉 bash | **这是造新工具**，且会漏掉现在 bash 能做的边角事；维护的手册要重写 |
| **C 保留 bash 但收窄** | 给 bash 加命令白名单（只放行 `lumii-ui` 与 `pnpm sync:guides`） | 要动 `local-bash.ts` 的公共路径，影响所有 Agent；且命令白名单天然易漏 |

**我的倾向是 C**——它既保住维护的实际需要，又让「33 → 20」这个数字有意义。但它是唯一一条**会碰到所有 Agent 共用代码**的路，风险要你知情。

### 3.3-decision · 拍板：**选 A，保留 bash**

> 2026-09-16 拍板。理由与后果都记在这里，避免以后重新论证。

**后果要如实写下来**：

1. **工具收敛的性质变了**——从「收窄能力」变成「整理语义重叠」。留着一个能 `curl` / `node -e` / 读写任意文件的 `bash`，白名单里砍掉的其它工具**并不能真正阻止它做那些事**。所以 §3.2 那一档的价值是「减少模型的选项、收紧语义边界」，不是「限制能力」。
2. **因此它的优先级应低于有实测数据支撑的项**：`web_search` 43% 失败率（§四）与测量补全（§二）。收敛**不急于求成**。
3. **「维护 33 → 20」这个目标不再有意义**——它是为「进入 15–20 的安全区」而设的；既然 bash 留着，白名单的绝对数量就不再是那个能决定模型表现的变量。**建议只做 §3.2 的无争议档（33 → 27），家族合并档（§3.4）暂不做。**

**如果以后要重新考虑**：真正的问题不是工具数，而是 `bash` 的权限边界。触发条件建议写成——**当维护的动作开始真实改动用户资产（P1-5 落地）时**，再回来评估要不要给 bash 加命令白名单（那时它改的东西有了明确的清单，白名单才写得准）。

### 3.4 家族合并（可选档，收益更大但**有反例证据**）

模式不是新引入的：`memory_manage`（7 个 action）与 `news_preference`（3 个 action）**已经是这个形态**，推广而已。

| 现状 | 合并为 | 形态 |
|---|---|---|
| `wiki_overview` / `wiki_search` / `wiki_read` | `wiki` | `{ action: 'overview'\|'search'\|'read' }` |
| `skill_list` / `skill_search` / `skill_invoke` | `skill` | `{ action: 'list'\|'search'\|'invoke' }` |
| `app_*` 7 个 | `app_ui` + `app_screenshot` | `{ action: 'goto'\|'act'\|'fill'\|'scroll_to' }` |
| `maintenance_report_write` / `_read` | `maintenance_report` | `{ action: 'write'\|'read' }` |

→ 合计 **20**（27 − wiki 2 − skill 1 − memory 1 − app 2 − report 1）。

**但必须先说清反例**：工具收敛会掉点——[ToolRet](https://arxiv.org/abs/2503.01763) 的 Recall@10 < 52%；[API-Bank](https://arxiv.org/abs/2304.08244) 上 GPT-3.5 从 Call **59.40% → Retrieve+Call 38.52%**。而业界的安全做法是「**高频工具不延迟加载 + 其余可搜**」（Anthropic），**这个基础设施我们还没有**。

→ **建议：先做 §3.2（无争议的那一档，33 → 27），家族合并留到 P0-0 的数据出来之后再定。**

### 3.5 影响面与风险

| 家族合并 | 全部 | 见 §3.4 反例 | 暂不做 |

## 四、P0-1b · `web_search` 的 43% 失败率（我建议并入 P0）

**数据**：418 次调用 / **181 次失败（43%）**，是三个高失败工具里调用量最大的一个。而它正是情报的主力工具。

**已有旁证**：情报自己攒下的领域经验原话是「web_search 结果被日历/AI工具导航类页面严重污染，几乎不可用；可靠路径是直接抓列表页——36氪快讯」。**统计与一线经验独立指向同一处。**

**为什么它比工具收敛更值得先做**：收敛是把 33 个省成 27 个（省的是注意力），而 43% 的失败率意味着**情报每两次搜索就有一次是白跑的**——直接吃时间和 token。

**要做的事**：
1. 靠 §2.3 拿到失败原因分布（限流 / 无结果 / 解析失败 / 网络）
2. 按原因分别处置：
   - 限流 → 加退避 + 并发上限
   - 无结果 → **重写工具的 description 与参数**（Anthropic 内部做法：让 agent 拿坏工具反复试然后重写描述，任务完成时间 −40%）
   - 解析失败 → 修解析
3. 把情报那条「可靠路径是直接抓列表页」的领域经验，**固化成工具描述或手册条目**——它已经用两轮时间自己摸出来了，不该只留在一条自由文本记忆里

**体量**：中小（取决于原因）。**依赖**：§2.3。

## 五、P0-2 · 读取路径：执行时注入「自述」

**问题**（已核准）：cron 执行是全新实例、跑完即销毁，`restoreHistoryForInstance` 只在压缩时调用 → **会话里累积的执行记录 Agent 看不到**。

**做成什么样**：在 `driveAgent` 拼 prompt 时，在任务指令前加一段**自述**（不是历史）：

```
=== 你上次的情况 ===
上次执行：2026-09-16 12:00（14 小时前）
上次结论：本轮推 13 条增量；卡片累计 200+ 条
你的台账：关注 3 项 / 少推 5 项 / 最近 3 轮的排除原因：…
```

| 项 | 内容 |
|---|---|
| 改哪 | `apps/windows/src/main/agent-runtime/cron-scheduler.ts`（`driveAgent` 拼 prompt 处） |
| 数据从哪来 | ① 该会话最近 1–2 次执行的产出（已有）；② 台账（P1 才建）；③ 上期维护报告（已有） |
| 首版范围 | **只做已有数据**：最近一次执行的摘要 + 上期报告的一句话结论。台账有了再接第三段 |
| 为什么不是 restore 全量历史 | 全量历史贵且噪声大（调研：recursive summarization 35.3% vs full-context 98.0%，但那是「替代」场景；这里是「补一句摘要」，是加法不是替代） |
| 体量 | 小（1 处拼装 + 1 个读最近执行的函数） |
| 验证 | 跑两次同一 cron 任务，第二次的 prompt 日志里能看到「你上次的情况」段，且内容来自第一次的产出 |

## 六、P0-3 · 「少推 X」四件套

**现状**：`news_preference` 只有「规则对象化」（第一件）。NewsBlur 的说法是用户在**盲选**——写了规则看不到会命中什么，这是规则训歪的唯一来源。

| # | 件 | 具体做什么 | 改哪 |
|---|---|---|---|
| 1 | 规则对象化 | ✅ 已有（关注/少推/来源偏好/推送时段） | — |
| 2 | **预览命中集** | 偏好卡上加「看命中」：拿这条规则去匹配**已有条目的历史**（含已推过的），列出命中、命中处高亮；写新规则时先「拿这一篇试试」 | 新 IPC `news-preference:preview` + 资产体检同样的面板位置（偏好放哪见下） |
| 3 | **显式冲突优先级** | 「少推 X」与「关注 X」同时命中时的裁决顺序，写成界面上的可见文字。建议链：`明确少推 > 明确关注 > 来源偏好 > 默认排序`；并给「少推」加一档更硬的强度 | `news-preferences.ts` 加 `priority` 概念 + 渲染层显示 |
| 4 | **规则日志** | 「这条规则最近命中过多少篇、最近 10 次命中的是什么」 | 新表或用 `tool_usage_stats` 同款计数表 |

**两条要如实告知用户的边界**（NewsBlur 自己就这么写）：
- 预览**只对确定值开放**（「标题党」这种自然语言规则无法预览命中）
- 训练/加规则时**不立刻移除**已推条目，让人看见自己做了什么

**体量**：中。**依赖**：无（可独立做）。

## 七、P1-4 · 事件级去重

**问题**：现在按 URL 去重，同一事件多家转载会重复推。

**做成什么样**（抄 GDELT 的 Events/Mentions 分裂）：

```
事件（新表 news_events）
  id            稳定 id
  canonical_title
  first_seen / last_seen
  source_count
  created_at

条目（dashboard_feed_items）
  + event_id     ← 新列，指向所属事件
```

渲染：**一件事一行**，来源折叠在下面（「36氪、澎湃、界面 等 4 家」），点开看各家标题。

**轻量版（建议先做）**：不做 embedding 聚类，用 **标题相似度 + 时间窗**：

| 参数 | 值 | 来源 |
|---|---|---|
| 相似度阈值 | 0.7（先用字符 n-gram，后续可换 embedding） | 线上验证值 |
| 文章与事件时间差 | **≤18h** | 同上（防「同话题不同月」） |
| 事件存活 | **≤36h** | 同上 |

**已知失效要接受**：带强烈本地语境的地区新闻会漏并；**宁可漏并也不降阈值换误并**（原作者的取舍）。

**跨语言注意**：MinHash+LSH 只适用同语言（中英日法同一事件 3-gram Jaccard = 0）——我们目前是中文为主，先不管。

**体量**：中。**依赖**：无，但和 P0-2 的自述、P1-5 的台账共享「事件」这个概念，**建议一起设计**。

## 八、P1-5 · 维护的「从发现到动作」

**地基已有**：`maintenance_reports.findings` 带 `key` / `severity` / `title` / `evidence` / `suggestion`，跨期 key 已在做差分。**缺的是「从发现到动作」。**

**四条不变式**（Terraform plan / CFN change set / ArgoCD 收敛而来）：

| # | 不变式 | 落到我们 |
|---|---|---|
| ① | 预览**零副作用** | 生成「变更预览」时不写任何东西 |
| ② | 确认后执行**被审过的那一份** | 把预览存成实体（新表 `maintenance_actions`），执行的是它，不是重新生成 |
| ③ | 结果写回**同一条**台账 | `maintenance_reports` 加 `executed_at` / `result`，或 actions 表回指 report |
| ④ | 可回滚或至少可追溯 | 记忆改动已有 `.bak`；Wiki 改动要有快照 |

**动作分级**（抄 BCA 三级 + Guru 的交互细节）：

| 级 | 动作 | 交互 |
|---|---|---|
| 1 | **只加标记**（标记重复页 / 标记过期记忆） | 可直接做，不改内容 |
| 2 | **合并 / 归档** | 出预览 → 确认 → 执行；**合并要改写所有引用**（只删不转会留断链） |
| 3 | **清除** | 前置预告期 + 可恢复窗口 |

**两条交互细节**（Guru / Stack Overflow 的实证）：
- **跳过不丢**：Skip 掉的问题留在队列里，以后还会出现——用户不必为「暂时不想决定」做假决策
- **冷却期 7 天**：同一问题 7 天内不重复提醒；否则用户会把整个提醒静音，**比不提醒更糟**
- 呈现上：**倒计时比「已过期」更能驱动动作**（Slab）

**体量**：中大。**依赖**：`maintenance_reports`（已有）。

## 九、P1-6 · 来源质量

**结论：别自建。** Ground News 的做法是**聚合外部评分取平均**，自己只编归属信息（2,276 家）。

| 要做 | 不要做 |
|---|---|
| 聚合外部评分（可先做一份**人工小名单**：常看的 20–30 个源，手工标三档） | ❌ 用 LLM 打可信度分（与人类专家 ρ=0.50，且指派角色会稳定偏斜） |
| 用评分做**降权**与**背景提示** | ❌ 把评分当「这篇可信」的判据（评分是**按出版物整体**的） |
| 记「这个源最近 10 条被推了几条、被滤了几条」 | ❌ 自建九维度评分流程 |

**体量**：小（一张小名单表 + 一个降权系数）。
