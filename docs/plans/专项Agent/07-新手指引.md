## 一、背景：功能很多，用户发现不了

用户原话概括：客户端功能很多，但呈现给用户的很少；用户看不懂那些功能，看懂了也不知道怎么用；藏在设置与后台的功能没人主动介绍。目标：由**「灵栖维护」Agent 主导**，帮用户发现功能、学会使用、并用到自己的工作/生活/学习里。

**现状盘点（2026-09-13 核实，2026-09-15 按评审更正）**

| 类别 | 事实 | 位置 |
|---|---|---|
| 功能面 | 设置 Hub 9 个 Tab；设置页 11 个分类；主路由仅 3 页，侧栏只留「概览」+ 会话列表 | `SettingsHub/types.ts:48`、`SettingsPage.tsx`、`Router.tsx` |
| 已有引导 | 首启仅选工作空间向导；输入框 24 条**静态随机**轮播 tips；输入框帮助面板；云同步三步卡先例 | `WorkspaceWizard.tsx`、`useRotatingTip.ts`、`CloudSyncSection/index.tsx:151` |
| 场景卡基数 | 空状态场景卡 **38 条 / 7 分类**（工作效率 7 / 编程开发 6 / 生活助手 6 / 内容创作 5 / 学习研究 5 / 智能体 5 / 职场发展 4）〔v1 误记 48 条，评审 C2 更正〕 | `EmptyState/index.tsx:25-191` |

**关键洞察（v2 改写）**：选维护官做向导，正确理由是它是**唯一同时持有 `app_*` 带路工具、`skill_invoke` 与用户记忆的 system agent**（`definitions.ts:221-229`）——v1 以「它管用户指南同步」为据不成立（那是 `sync:guides` 构建管线，评审 C1）。缺的核心仍然是一个**结构化的功能目录**：作为问答、主动推荐、未来功能地图的共同数据源。但目录定位要改（评审 P0-A）：它必须是**用户认知模型**（用户想做什么 → 用什么功能），不能只是设置界面的镜像——详见 §3.1。

## 二、产品决策（拍板）

1. **向导会话优先**：用户随时问「这个功能怎么用 / 有啥用」，维护官基于产品知识回答；主动推荐作为第二层随后接上。
2. **主动推荐 = 本地使用统计 + 会话轻提醒**：纯本地记录功能使用情况（不上传），发现没用过/用得浅的功能后，在向导会话里发轻提醒；**不发系统通知弹窗**。〔v2：投递时机由「定时投递」改为「用户启动/新开会话时判定投递」（评审 P0-C/F，**已拍板 ⑨**）；「不发系统通知」不变。〕
3. **演示 = 带路式**：维护官把界面导航到对应位置 + 带标注截图告诉用户点哪里，**动手由用户**（指引流程中不代操作）。〔v2 注：`annotateSnapshot` 需要已有截图的坐标，「先滚到目标元素再出标注图」当前做不到——能力边界=「goto 到视图 + 整屏标注」（评审 P2-12），若要元素级标注需改 `controller.ts`，另立项。〕
4. **新手期更主动**：推荐节奏按使用龄分阶段（见默认值表），前期密、后期疏。〔v2：使用龄以主进程新增 `onboarding.firstSeenAt` 为准；存量老用户一律视为稳定期兜底（评审 P1-3）。〕
5. **会话内推荐**：新开会话给 3 个「为你推荐」使用场景（内容由 `userJourney` 驱动）；进行中会话给 ≤3 条「下一步」功能建议。〔v2：三套建议体系（tips / 场景卡 / 下一步）定优先级与会话级上限，见 §3.6（评审 P0-D）。〕
6. **询问组件优化**（`ask_user_question`）：多选 Tab 呈现、单选完成后自动前进（多选除外）；AI 给出推荐答案并解释理由；整体降低用户心智负担。〔v2 收尾补充见片 6。〕

**默认值（v2 修订）**

| 项 | 值 |
|---|---|
| 开关 `onboarding.enabled` | 默认开（新装与老用户一致）；关闭 = 停收集 + 停推荐，向导问答入口始终可用 |
| 使用龄来源 | `onboarding.firstSeenAt`（`runtime_state`，首次运行写入）；存量用户回填用 `~/.lumii/data/agent-runtime.db` 文件创建时间兜底，**且一律按稳定期处理**（宁少推不误推；回填误差显式接受） |
| 轻提醒节奏（按使用龄） | 新手期（首启 <7 天）每天 ≤1 条；成长期（8–30 天）每 3 天 ≤1 条；稳定期（30 天+）每周 ≤1 条 |
| 投递时机 | **应用启动 / 新开会话时判定**，满足间隔才落消息（评审 P0-C）；cron 每日一次仅作判定心跳 |
| 静默时段 | **沿用 `autonomous.settings.quietHours`（默认 `[23,8)`）**作为 nudge 的唯一勿扰判据（**已拍板 ⑪**：暂不抽通用「勿扰」）。边界：**关闭自主进化后该设置无 UI 入口**（判定仍读同一配置，保持默认值）；既有分裂保留——companion 侧硬编码 22-8（`local-companion-handler.ts:66-68`），本期不动（§八·8） |
| 启用宽限 | 老用户启用后 48h 内不推；新手期不设额外宽限（首启当天可见第一条 = 置顶的向导会话本身，nudge 另算） |
| 候选规则 | priority 降序取第一个「**`activated` 事件数 = 0** 且未推过」的功能（评审 P0-B：点开过不算用过）；无候选则不发 |
| 新会话推荐 | 每次新开会话展示 3 个场景卡（`userJourney` 驱动，仅消费 `coverageGate='verified'` 条目） |
| 会话中下一步 | 每轮至多 3 条；每会话至多出现 2 次；用户连续忽略 N 次（默认 5）后全局静默不再出现（评审 P0-D） |

### 3.1 功能目录（新资产；v2 重设计，评审 P0-A）

目录是**用户认知模型**（用户想做什么 → 用什么功能），不是设置界面的镜像。拆成**两张表**，`docs/guide/feature-catalog.json` 随 `sync:guides` 管线分发：

```json
{
  "version": 2,
  "userJourney": [
    {
      "id": "away-from-desk",
      "job": "离开电脑也能用助手",
      "featureIds": ["channels.weixin", "channels.feishu"],
      "scenarioPrompts": ["接入微信渠道，不在电脑前也能使唤助手"],
      "scenes": ["工作", "生活"],
      "coverageGate": "verified"
    }
  ],
  "features": [
    {
      "id": "channels.weixin",
      "name": "微信渠道",
      "summary": "把微信接入 Lumii，在微信里直接使唤助手",
      "jobStatement": "当你经常不在电脑前，却想随时给助手派活、查看进度时",
      "coverageGate": "verified",
      "location": { "view": "settings", "category": "channels" },
      "entryPoints": ["设置 → 渠道（channels）"],
      "steps": ["打开「设置 → 渠道」", "选择微信并扫码登录", "在微信里给助手发一条消息验证"],
      "scenes": ["工作效率", "生活助手"],
      "detectKey": "settings.channels",
      "priority": 5,
      "related": ["cron", "info-pipeline"]
    }
  ]
}
```

| 字段（v2 变化） | 说明 |
|---|---|
| `userJourney`（新增表） | 按「用户想做什么」组织；**推荐与场景卡的宿主**（`scenarioPrompts`/`scenes` 挂这里）；条目数不受设置界面约束 |
| `features`（保留表） | 面向问答与带路的入口事实；继续与设置界面对齐并保留完整性单测 |
| `jobStatement`（新增，必填） | 用户会在**什么处境**下需要它（when/why）。拍板承诺的「对你的工作/生活有什么用」只能以此为原料，写不出具体处境的条目标 `draft` 且不进推荐 |
| `coverageGate`（新增，必填） | `'verified' | 'draft'`；**推荐、场景卡、下一步建议只消费 `verified`**（评审 P0-2） |
| `scenes`（v2 改） | 直接采用现有场景卡 **7 分类**：工作效率 / 编程开发 / 生活助手 / 内容创作 / 学习研究 / 智能体 / 职场发展（评审 P1-4，零成本对齐 `EmptyState/index.tsx:25-191`） |
| `guideAnchor`（v2 **移除**） | 评审 C4/C4b/P1-2：示例锚点不存在，且应用内渲染侧无 slug/滚动能力——半成品锚点比没有更糟。**本期不收录**；锚点基建（heading id + 中文 slug 对齐 + `scrollIntoView` + `sync:guides` 存在性校验）归片 7，建成后随内容扩充一并恢复 |
| `location`（写入纪律，评审 C3/P1-1） | `category` **仅在 `view:'settings'` 时被消费**，其它 view 禁写 category（会被静默忽略）；枚举以 `goto.ts:4-31` 运行时集合为准。开工时顺手补齐 `bridge-app-ui-tools.ts:300/305/440/445` 模型可见清单缺失的 `wiki`/`autonomous`/`experimental`，否则「带路去资料库」等于没暴露 |

- **首批收缩到 10-12 条 `verified`**（评审 P0-A/P0-2）：选最高价值发现目标（渠道接入、定时任务、资料库、语音通话、录屏教程、宠物模式、技能、云同步、ACP 编码、消息推送、自主进化、新手指引自身），跑通全链路再扩张。**广度换来的不是覆盖，是稀释。**

### 3.4 主动推荐（轻提醒；v2 改为「时机投递」，评审 P0-C/P0-F/P0-G）

**为什么不用「cron 定时投递」**（v1 形态废弃的理由，留档）：`every` 24h 的实测语义是「新建时 `next_run_at=now`（新装即弹）、每次跑完 +24h 漂移、错过只补跑一次、撞静默时段白等一整天」（`cron-scheduler.ts:489-534`）——「先随机开火、再事后否决」的结构，对低频高时机敏感的 nudge 是错误匹配；且用户不看的会话里，消息等于没发生。

- **投递时机 = 用户行为触发**：应用启动 / 新开会话时运行判定，满足间隔才落消息（天然避开静默时段——用户在用时才判定）。
- **cron `onboarding-nudge` 保留但降级为「每日一次判定心跳」**：用 `cron` 类型（已支持 `Asia/Shanghai`，`cron-scheduler.ts:536-553`）**或** `active_hour_start/end` 窗口（`:158-172`），**不再**用 `every` + 外层静默补丁。
- **首启触点（全案缺失的一环，评审 P0-4 建议 1）**：首次启动自动创建并**置顶** `onboarding:guide`（`conversation:pin-toggle` 已有；置顶豁免清空历史 `ChatPage.tsx:1319`）。首启是唯一的黄金触点，成本极低；归片 2。
- **判定（纯函数 v2）**：开关开 ∧ 距上次 nudge ≥ 分阶段间隔（间隔基准 `firstSeenAt`）∧ 老用户启用 ≥48h ∧ 候选 = priority 降序第一个「`activated` 事件数 = 0 且未推过」。无候选则不发（候选集被误标已用掏空的问题已在 §3.3 回填修正）。静默判定**沿用 `autonomous.settings.quietHours`（默认 `[23,8)`）**（**已拍板 ⑪**：暂不抽通用「勿扰」；本片只加一个取该配置的判定函数，不新增第四套实现）。边界与既有分裂见 §二默认值表 / §八·8。
- **消息形态**：模板组文案（**生成零 token**；用户回复「带我看看」进入完整 Agent 回合，按正常会话计费——v1「零 LLM 消耗」的标题级表述按评审 P2-5/C8 修正）。
- **落库（评审 P0-8）**：**每次先 ensure 再 save + try/catch**（会话可被用户删除，FK `foreign_keys=ON` 下对已删会话 `saveMessage` 直接抛错）；落消息经桥上现成 public 的 `forwardIpcEvent`（`bridge.ts:2489-2491`），**不**把 `pushSavedMessage` 提为 public（评审 P2-9）。同时把会话**置顶或重排**提升可察觉度；无未读角标（本期不做，§七）。
- **开关语义（评审 P0-G，选 A）**：登记 `managedBy: 'onboarding'`——任务页开关**置灰**（`OverviewTab.tsx:80-84` 对受管任务 `disabled`），**唯一控制入口 = 设置页「新手指引」开关**；v1「任务页可暂停」表述删除。连带改动：① `managedBy` 枚举牵动四处（`cron-job-meta.ts:19`、`shared/agent-runtime-commands.ts:1884`、`useCron/types.ts:18`、`OverviewTab.tsx:22` 的 Record，缺一处编译不过）；② `classifyCronJobSource`（`cron-job-meta.ts:22-27`）加精确 id，否则落入「我的任务」分组且删除按钮可见；③ **重建语义显式实现**：采用 `evolution-tick.ts` 的 upsert 范式（seeded-if-missing），「删除后随重启重建」才是真的——v1 引用的「与其它系统任务一致」不准确（`seed-*` 系哨兵播种删了不重建）。

6. **cron 治理联动**：四处登记 + 分组分类 + upsert 重建显式实现（§3.4）；「删除会重建」从口号变成验收项。

## 十、已拍板问题（2026-09-15 第三轮裁决）
