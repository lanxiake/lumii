## B1 · ✅ 已完成（原定 `web_search`，实施中重定靶为 `web_fetch`）

### B1.R 实施结果（2026-09-16）

**原计划假设**：`web_search` 43% 失败率是本机工具面最大的单点问题（数据来自
`tool_usage_stats` 的 418 调用 / 181 失败）。

**实测推翻了它**（12b §四 的确认点，写这份计划时就预置在「失败主因与预期不符时先停下来对齐」）：

| 证据 | 结果 |
|---|---|
| 机制 | `85667e90`（2026-09-02 12:23）之前 `web_search` 没有内置 provider，未配 `LANGSEARCH_API_KEY`/`SEARXNG_BASE_URL` 时**每次调用必抛** `No search provider configured` |
| 统计交叉验证 | `count` 418 → 472（**+54 次调用**）而 `error_count` **纹丝不动停在 181** |
| 日志实测（09-10~09-16） | `web_search` **165 次调用 / 0 次失败**，全走内置 Bing，每次 4~10 条结果，无一次 `provider=unknown` |

→ **181 次是 09-02 之前那个时期攒下的存量，当前失败率为 0%。**
→ 根因是「统计表没有时间维度，把历史存量当成当前状态读了」——B2.1 加 agent 维度时，
一并考虑给统计加时间窗，否则同一个坑还会再踩。

**真正在失败的是 `web_fetch`**（近 7 天全工具 4100 次调用 / 164 次失败 = 4.0%）：

| 工具 | 调用 | 失败 | 失败率 |
|---|---|---|---|
| **`web_fetch`** | 313 | **110** | **35.1%**（占全部失败的 67%） |
| `task_complete` | 52 | 8 | 15.4% |
| 其余全部 | — | — | < 7% |
| `web_search` | 165 | 0 | 0% |

归因（87 条可解析）：**76% 连接层失败**（`zh.wikisource.org` 18、`arxiv.org` 16、
`github.com` 4、`en.wikipedia.org` 3、`huggingface.co` 3）、13% 404、8% 429（`api.semanticscholar.org` 7）、3% 403。

**用户拍板**：改靶 `web_fetch` + 收尾 B1.4；代理/网络出口部分**另行决定**（未做）。

### B1.1 ✅ 让失败可归因（提交 `42728ba2`）

`tool-usage-hook` 在 `onError` / `afterExecute(isError)` 两个失败出口各写一条
`tool_audit_log`（`is_error=1` + 错误文本压单行后截断 300 字）。放在 hook 而非各工具内部——
它是所有工具的统一出口，一处接线全工具受益（原计划的 B2.3 一并覆盖，故 B2 只剩两件事）。

压单行不只是省空间：归因要按错误文本 `GROUP BY`，多行会让同一种失败分裂成多组。
只记失败不记成功——成功没有归因价值，全量落库只会把审计表淹掉。

> 原计划的验收「跑一轮资讯任务后 `tool_audit_log` 里出现 `web_search` 的失败行」
> **已不成立**（它不失败了），改用真机 `web_fetch` 失败验证，见下。

### B1.2 ✅ 归因（原计划的「跑一轮看分布」被日志复盘取代）

不必等新代码跑数据：`~/.lumii/logs/app/mtbot-*.log` 里的渲染层 `tool:end` 事件
（含 `isError` 与 `resultPreview`）已覆盖近 7 天全部 4100 次调用，直接出分布表。
这比原计划的「等一轮 cron」更快也更全。**但注意**：主进程的 `[ToolRunner] ←` 只在
`afterExecute` 记，抛错路径整条不可见——这正是 B1.1 要补的洞。

### B1.3 ✅ 按分布修（重定靶到 `web_fetch`，提交 `bb9c3f7e`）

诊断信息是在**两处**被扔掉的，只修一处都不够：

1. `local-web.ts` 的 `classifyFetchError` 只读 `err.message`，而 undici 的 message 永远是
   笼统的 `fetch failed`，真正的原因（`UND_ERR_CONNECT_TIMEOUT` / `ECONNRESET` /
   `ENOTFOUND`）挂在 `err.cause.code` 或 `AggregateError.errors[]` 上。
   实测本机 133 次抓取失败日志全是「请求失败: fetch failed」，等于没记。
2. `web-fetch-tool` 抛 `HTTP ${status}: Failed to fetch ${url}`，把宿主已分类好的原因
   （放在 body 里）整个丢了；`status=0` 时模型只看到一个 0。

修法：递归挖 `cause`/`errors[]` 的 code + 码表译人话；`status=0` 带出原因并明说
「该站点不可达，换来源或用 web_search 找镜像」；404/403/429/5xx 各给一句可执行的下一步。
**只有 `status=0` 取 body**——其它状态码下 body 是站点错误页 HTML，塞进去纯属噪声。

**真实网络验证**（vitest node 环境，非 mock）：
- `zh.wikisource.org` →「无法访问 …：连接超时（10 秒内没建立起连接）（UND_ERR_CONNECT_TIMEOUT）。
  该站点在当前网络下不可达——换一个来源，或用 web_search 找它的镜像与转载。」
- 失效的 gov.cn 链接 →「HTTP 404: … 页面不存在（链接已失效，或 URL 有误）。
  先用 web_search 确认真实链接，不要凭记忆拼 URL。」

**真机验证**：重启客户端 → 新建会话 → 让 assistant 抓 `zh.wikisource.org` →
`tool_audit_log` 出现 `id=12318 / tool_name=web_fetch / is_error=1`，
摘要即上面那句；会话消息里模型的 tool result 也是同一句。

### B4.1 现状

cron 执行是全新实例、跑完即销毁（`restoreHistoryForInstance` 只在压缩时调），**会话里累积的记录 Agent 看不到**。

### B4.2 做成什么样

在 `driveAgent` 拼 prompt 时，任务指令**之前**加一段：

```
=== 你上次的情况 ===
上次执行：2026-09-16 12:00（14 小时前）
上次产出：本轮推 13 条增量；卡片累计 200+ 条
上次发现：5 条记录带 JSON 序列化残迹（未处理）
```

| 项 | 内容 |
|---|---|
| 改哪 | `apps/windows/src/main/agent-runtime/cron-scheduler.ts` 的 `driveAgent`（拼 prompt 处，约 `:923-980`） |
| 数据 1：上次执行 | 该会话（`cron:<jobId>`）最近一次 assistant 产出 —— 已有查询路径 |
| 数据 2：上次发现 | `readLatestMaintenanceReport()`（片 11 已有），只在维护类任务时拼 |
| 首版不做 | 台账（还没建）；事件层（B7） |
| 拼装函数 | 新增 `buildSelfBriefing(jobId, agentId): Promise<string>`，纯拼装、可单测 |
| 体量 | 小 |
| 验收 | 连跑两次同一 cron 任务，第二次的 prompt 日志（`[llm-prompt:full:begin]`）里能看到「你上次的情况」段，且内容来自第一次的真实产出 |

### B4.3 为什么不是「恢复历史」

- 全量历史贵且噪声大；调研的证据是「朴素摘要式巩固会破坏信息」（35.3% vs 98.0%），但那是**替代**场景——这里是**加法**（补一句摘要，不动原文）
- 且 cron 会话的历史会无界增长，恢复它很快会撞上压缩

## B6 · 维护的「从发现到动作」

### B6.1 地基（已有）

`maintenance_reports.findings` 带 `key` / `severity` / `title` / `evidence` / `suggestion`，跨期 key 差分已在做。**缺的是「从发现到动作」。**

### B6.2 四条不变式（逐条落到实现）

| # | 不变式 | 实现 |
|---|---|---|
| ① | 预览**零副作用** | 生成变更预览时不写任何东西；预览只是一段结构化描述 |
| ② | 执行的是**被审过的那一份** | 新表 `maintenance_actions(id, report_id, finding_key, kind, payload, preview, status, created_at, executed_at, result)`；确认后执行 `payload`，**不重新生成** |
| ③ | 结果写回**同一条** | `maintenance_actions.result` + 回指 `report_id`；概览页卡片上该条 finding 显示「已处理 / 已跳过」 |
| ④ | 可回滚或至少可追溯 | 记忆改动已有 `.bak`；Wiki 改动要有快照（B6.4） |

### B6.3 动作分级

| 级 | 动作 | 交互 |
|---|---|---|
| L1 | **只加标记**（标记重复记忆 / 标记过期页） | 可直接做，不改内容 |
| L2 | **合并 / 归档** | 出预览 → 确认 → 执行；**合并要改写所有引用**（只删不转会留断链） |
| L3 | **清除** | 前置预告期 + 可恢复窗口 |

### B6.4 交互细节（都有实证来源）

| 细节 | 来源 | 实现 |
|---|---|---|
| **跳过不丢** | Guru | `status='skipped'` 的记录留在队列，下次仍出现 |
| **冷却期 7 天** | Guru | 同一 `finding_key` 7 天内不重复提醒；否则用户会整体静音，**比不提醒更糟** |
| **倒计时比「已过期」更驱动** | Slab | 卡片上显示「还有 3 天到期」而不是「已过期」 |
| 合并要改写引用 | Obsidian Note Composer | 合并两条记忆时，指向被合并条目的引用一并改 |

### B6.5 分批

| 子批 | 内容 |
|---|---|
| B6-1 | `maintenance_actions` 表 + 从 finding 生成预览（只读，不执行） |
| B6-2 | 概览页卡片：finding 上挂「处理 / 跳过」，展示预览 |
| B6-3 | 执行 L1（只加标记）+ 结果写回 + 冷却期 |
| B6-4 | 执行 L2（合并 / 归档，含引用改写与快照）+ 可回滚 |

## B7 · 事件级去重（轻量版）+ 来源质量

### B7.1 事件级去重

**结构**（抄 GDELT 的 Events/Mentions 分裂）：

```sql
-- V45
CREATE TABLE news_events (
  id              TEXT PRIMARY KEY,   -- 稳定 id
  feed_id         TEXT NOT NULL,
  canonical_title TEXT NOT NULL,
  first_seen      TEXT NOT NULL,
  last_seen       TEXT NOT NULL,
  source_count    INTEGER NOT NULL DEFAULT 1,
  created_at      TEXT NOT NULL
);
ALTER TABLE dashboard_feed_items ADD COLUMN event_id TEXT;
```

| 项 | 内容 |
|---|---|
| 聚类（轻量版） | 标题 n-gram 相似度 + 时间窗，**不上 embedding** |
| 参数 | 相似度阈值 **0.7**；文章与事件时间差 **≤18h**；事件存活 **≤36h** |
| 参数来源 | 线上验证值（$100/月、180+ 源的公开实践） |
| 落点 | `dashboard_feed_write` 写入时先做事件匹配，再落 `event_id` |
| 渲染 | **一件事一行**，来源折叠（「36氪、澎湃、界面 等 4 家」），点开看各家标题 |
| 已知失效 | 带强烈本地语境的地区新闻会漏并；**宁可漏并也不降阈值换误并**（原作者的取舍，照抄） |

### B7.2 来源质量（不自建）

| 做 | 不做 |
|---|---|
| 一份**人工小名单**（常看的 20–30 个源，手工标三档） | ❌ 用 LLM 打分（与人类专家 ρ=0.50，且指派角色会稳定偏斜） |
| 用评分做**降权**与**背景提示** | ❌ 把评分当「这篇可信」的判据（评分是**按出版物整体**的） |
| 记「这个源最近 10 条被推了几条、被滤了几条」 | ❌ 自建九维度评分流程（NewsGuard 那种） |

### B7 验收

- [ ] 构造同一事件的 3 条不同来源稿件 → 落成 1 个 event + 3 条 item → 卡片渲染成一行
- [ ] 地区新闻的漏并率抽样看一次（接受漏并，但不接受误并）
- [ ] 来源名单生效：被降权的源在同等条件下排后
