## B1 · ✅ 已完成（原定 `web_search`，实施中重定靶为 `web_fetch`）

### B1.R 实施结果（2026-09-16）

**原计划假设**：`web_search` 43% 失败率是本机工具面最大的单点问题（数据来自
`tool_usage_stats` 的 418 调用 / 181 失败）。

**实测推翻了它**（12b §四 的确认点，写这份计划时就预置在「失败主因与预期不符时先停下来对齐」）：

| 证据 | 结果 |
|---|---|
| 机制 | `85667e90`（2026-09-02 12:23）之前 `web_search` 没有内置 provider，未配 `LANGSEARCH_API_KEY`/`SEARXNG_BASE_URL` 时**每次调用必抛** `No search provider configured` |
| 统计交叉验证 | `count` 418 → 472（**+54 次调用**）而 `error_count` **纹丝不动停在 181** |
| 日志实测（09-10~09-16） | `web_search` **165 次调用 / 0 次失败**，全走内置 Bing，每次 4~10 条结果，无一次 `provider=unknown` |

→ **181 次是 09-02 之前那个时期攒下的存量，当前失败率为 0%。**
→ 根因是「统计表没有时间维度，把历史存量当成当前状态读了」——B2.1 加 agent 维度时，
一并考虑给统计加时间窗，否则同一个坑还会再踩。

**真正在失败的是 `web_fetch`**（近 7 天全工具 4100 次调用 / 164 次失败 = 4.0%）：

| 工具 | 调用 | 失败 | 失败率 |
|---|---|---|---|
| **`web_fetch`** | 313 | **110** | **35.1%**（占全部失败的 67%） |
| `task_complete` | 52 | 8 | 15.4% |
| 其余全部 | — | — | < 7% |
| `web_search` | 165 | 0 | 0% |

归因（87 条可解析）：**76% 连接层失败**（`zh.wikisource.org` 18、`arxiv.org` 16、
`github.com` 4、`en.wikipedia.org` 3、`huggingface.co` 3）、13% 404、8% 429（`api.semanticscholar.org` 7）、3% 403。

**用户拍板**：改靶 `web_fetch` + 收尾 B1.4；代理/网络出口部分**另行决定**（未做）。

### B1.1 ✅ 让失败可归因（提交 `42728ba2`）

`tool-usage-hook` 在 `onError` / `afterExecute(isError)` 两个失败出口各写一条
`tool_audit_log`（`is_error=1` + 错误文本压单行后截断 300 字）。放在 hook 而非各工具内部——
它是所有工具的统一出口，一处接线全工具受益（原计划的 B2.3 一并覆盖，故 B2 只剩两件事）。

压单行不只是省空间：归因要按错误文本 `GROUP BY`，多行会让同一种失败分裂成多组。
只记失败不记成功——成功没有归因价值，全量落库只会把审计表淹掉。

> 原计划的验收「跑一轮资讯任务后 `tool_audit_log` 里出现 `web_search` 的失败行」
> **已不成立**（它不失败了），改用真机 `web_fetch` 失败验证，见下。

### B1.2 ✅ 归因（原计划的「跑一轮看分布」被日志复盘取代）

### B1.3 ✅ 按分布修（重定靶到 `web_fetch`，提交 `bb9c3f7e`）

诊断信息是在**两处**被扔掉的，只修一处都不够：

1. `local-web.ts` 的 `classifyFetchError` 只读 `err.message`，而 undici 的 message 永远是
   笼统的 `fetch failed`，真正的原因（`UND_ERR_CONNECT_TIMEOUT` / `ECONNRESET` /
   `ENOTFOUND`）挂在 `err.cause.code` 或 `AggregateError.errors[]` 上。
   实测本机 133 次抓取失败日志全是「请求失败: fetch failed」，等于没记。
2. `web-fetch-tool` 抛 `HTTP ${status}: Failed to fetch ${url}`，把宿主已分类好的原因
   （放在 body 里）整个丢了；`status=0` 时模型只看到一个 0。

修法：递归挖 `cause`/`errors[]` 的 code + 码表译人话；`status=0` 带出原因并明说
「该站点不可达，换来源或用 web_search 找镜像」；404/403/429/5xx 各给一句可执行的下一步。
**只有 `status=0` 取 body**——其它状态码下 body 是站点错误页 HTML，塞进去纯属噪声。

**真实网络验证**（vitest node 环境，非 mock）：
- `zh.wikisource.org` →「无法访问 …：连接超时（10 秒内没建立起连接）（UND_ERR_CONNECT_TIMEOUT）。
  该站点在当前网络下不可达——换一个来源，或用 web_search 找它的镜像与转载。」
- 失效的 gov.cn 链接 →「HTTP 404: … 页面不存在（链接已失效，或 URL 有误）。
  先用 web_search 确认真实链接，不要凭记忆拼 URL。」

**真机验证**：重启客户端 → 新建会话 → 让 assistant 抓 `zh.wikisource.org` →
`tool_audit_log` 出现 `id=12318 / tool_name=web_fetch / is_error=1`，
摘要即上面那句；会话消息里模型的 tool result 也是同一句。

### B2.1 ✅ `tool_usage_stats` 加 agent 维度（V44）

原计划写的 SQL 一字未改地用上了。两处与计划的偏离，都是**简化**：

### B2.5 ✅ 结论：时间窗**不该加在统计表上**

B1 的靶子之所以搞错，根因确实是这张表没有时间维度。但**正确的解法不是给它加一维**：

- 时间窗与失败原因用 `tool_audit_log` 回答更合适——它从 B1.1 起由 hook 在所有工具的
  失败出口写入，每行自带 `timestamp` 与原因，本来就是事件级的。
- 往统计表塞 `(agent_id, tool_name, day)` 会同时带来两个新问题：
  ① 行数按天膨胀（8 Agent × 124 工具 × 180 天 ≈ 18 万行）；
  ② `flushToDb` 现在是**整表 UPSERT**，每 2 秒重写几万行会卡——必须先改写成脏键集合。
- 分工定案：**累计次数与「最近用过吗」在这张表；时间窗与失败原因在 audit 表。**

> 尚未做的：UI 上还没有「最近 7 天」这个筛选。数据侧已经具备（audit 表有 timestamp），
> 但既然 B1 的教训是「看数不看窗会误判」，这个筛选值得在 B3 收敛前补上——
> 否则 B3 又会拿累计数字做逐 Agent 决策。

| # | 计划处置 | 复核后的事实 | 判定 |
|---|---|---|---|
| 1 | `list_dir` 并入 `glob` | **不是语义重叠**：`glob` 只回路径、不区分目录；`list_dir` 有 `[DIR]/[FILE]` 前缀 + 工作区/项目目录解析 + 越界与截断处理。两者描述**互相指名对方**（glob 上写着「单层目录列表请用 list_dir」）。近 7 天 `list_dir` 90 次、`glob` 102 次，都在热路径 | ❌ 不做 |

### B4.2 ✅ 做成了什么样

在 `driveAgent` 拼 prompt 时，任务指令**之前**加一段：

```
=== 你上次的情况（供接续参考，不是本轮任务）===

上次产出：顺延的三件事里，sjzh-service 那次故障还没归档。确认下此刻手上的这件，正是现在最该推进的。

```

| 项 | 计划 | 实际 |
|---|---|---|
| 改哪 | `cron-scheduler.ts` 的 `driveAgent` | 同 |
| 数据 1：上次执行/产出 | 「已有查询路径」 | **不完全是**：已有的 `readLatestAssistantText(…, since)` 回答的是「本轮产生了什么」，自述要的是「上一次留下了什么」。新增 `readPreviousAssistantTurn(convId)` 返回正文+落库时刻 |
| 数据 2：上次发现 | `readLatestMaintenanceReport()`，只在维护类任务时拼 | 同，判定用 `agentId === 'system-keeper'` |
| 拼装函数 | `buildSelfBriefing(jobId, agentId): Promise<string>` | `buildSelfBriefing(input): string`——**同步纯函数**，IO 留在 scheduler 侧。这样单测不用摆 mock |
| 体量 | 小 | 小（4 文件 / 374 行，含测试） |

**几处刻意加的（计划里没写，但不加会出问题）**：

- **首次执行什么都不注入**，不给一个空的「你上次…」块——空块会让模型以为上轮出了问题。
- **抬头点明「不是本轮任务」**：上次产出常带结论与数字，不点明的话模型很容易把上一轮的事再答一遍，或以为任务已经做完。
- **绝对 + 相对时间都给**（`09-16 18:02（32 分钟前）`）：绝对回答「什么时候」，相对回答「隔了多久」，后者更能让模型判断「算不算同一批」。
- **产出压单行、截断 300 字**：它是「上次说到哪」的提示，不是要复述整篇。
- **`NO_REPLY` 哨兵不算产出**（那是「本轮无话可说」），但「上次跑过」本身有信息量，所以时间行照给。

### B4.3 为什么不是「恢复历史」

- 全量历史贵且噪声大；调研的证据是「朴素摘要式巩固会破坏信息」（35.3% vs 98.0%），但那是**替代**场景——这里是**加法**（补一句摘要，不动原文）
- 且 cron 会话的历史会无界增长，恢复它很快会撞上压缩

计划把它们分成「新 IPC + 新表 + 情报运行时落一条」。实际做成**一个匹配器 + 一个只读命令**：

| 项 | 计划 | 实际 | 为什么 |
|---|---|---|---|
| 匹配器 | 「与运行时一致」 | 新写 `news-preference-match.ts`：标题 + 摘要 + 来源，大小写不敏感 | 运行时没有代码级匹配；只能新写。三字段都匹是因为「36氪」既可能是来源也可能是话题 |

### B7.1 ❌ 事件级去重：**不做**（实测证明不需要）

原方案是 GDELT 式的三层模型 + `news_events` 表 + n-gram 两遍聚类 + 0.7/18h/36h 参数 + 来源折叠渲染。

|---|---|

| 0.6 | 0 |
| 0.5 | 1 |
| 0.4 | 2 |
| 0.3 | 7 |

最近三期 44 条肉眼核对：**一条重复都没有**，且模型自己标了 4 处「（进展）」
（GPT-6 刷榜、哪吒汽车破产重整、宁德时代跌超 5%、引力一号遥三）——
它已经在区分「同事件的新进展」和「同事件的同一篇稿子」，正是提示词第 2 步要求的。

> **测量里的循环性要说清楚**：feed 里是模型**已经筛过**的，没有重复恰恰说明它在做去重。
> 所以这组数证明的是「**结果已经是对的**」，不是「模型从不出错」。

**结论仍然成立，而且理由更硬**：n-gram 聚类能抓的只有「措辞几乎相同的重复」——
数据里确实不存在；而真正会漏的是「换个说法讲同一件事」，那需要语义判断，**聚类抓不到**。
它既没必要，也不够用。新增一张表 + 一套两遍聚类算法 + 参数，换来的折叠次数是 0。

**保留现状**：提示词第 2 步的指令 + 模型的「（进展）」标注就是机制。零改动。

### B7.2 ✅ 来源质量：只做 `source` 归一化

原方案是「人工小名单（20–30 家标三档）+ 降权」。动工前核到一个**前置问题**：
`source` 是模型自由发挥的文本，同一家媒体会散成多个 key——实测 215 条里
`36氪/新智元`、`36氪 / 新智元`、`36氪·新智元` **是三个不同的 key**，
48 家媒体写成 97 个取值。在这个前提下做名单，匹配不上。

所以先归一化（`normalizeSource`，写在写入口 `normalizeItem`）：
- **只统一分隔符**（`/ ／ | ｜ ·` → `·`，去掉两侧空格）
- **不重排顺序**：`机器之心 / 36氪` 与 `36氪 / 机器之心` 谁是媒体谁是转载源，
  代码判不了，重排等于把一个猜测写成事实
- **不合并媒体名**：`InfoQ` 与 `InfoQ 中文` 是两家站点，不是写法差异
- 要按媒体聚合时 `split('·')` 即可——那是派生视图，不需要动存储

`dashboard_feed_write` 的 `source` 参数描述同步写明格式要求（代码兜底 + 契约说明）。

| 项 | 数据 |
|---|---|
| 历史效果 | 97 → **91** 个 key；45/215 行写法被规整（`36氪·新智元` 从 11 涨到 21） |
| 为什么只降 6 | `36氪/定焦One` 与 `36氪/新智元` 本就是不同的对，**不该并**。合并的只有「同一对写了两三种」的那些 |
| 真正的价值 | **以后不再产生三种写法**。历史 215 行未回改——那是数据改写，没做，需要的话是一次独立操作 |

**人工名单与降权暂不做**：没有需求证据（没人提过要治理来源），原动机来自 Ground News 的做法。
归一化是它的前置，先把这个做好；真要治理时再补名单。
