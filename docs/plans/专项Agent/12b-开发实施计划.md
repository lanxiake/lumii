## B1 · `web_search` 失败归因与修复

### B1.0 目标与已知

| 项 | 值 |
|---|---|
| 事实 | `web_search` 418 次调用 / **181 次失败（43%）**；`web_fetch` 555 / 123（22%） |
| 旁证 | 情报自己攒下的领域经验：「web_search 结果被日历/AI工具导航类页面严重污染，几乎不可用；可靠路径是直接抓列表页——36氪快讯」 |
| 现状缺口 | `error_count` 只有次数，**没有错误文本** → 归因无处下手 |
| 相关文件 | `packages/agent-runtime/src/tools/built-in/web-search-tool.ts`（配置）、`web-shared.ts`、平台侧实现（待定位）、`apps/windows/src/main/tool-usage-store.ts` |

### B1.1 第一步：让失败可归因（最小测量）

| 项 | 内容 |
|---|---|
| 做什么 | `web_search` 的失败出口写一条审计：`tool_audit_log(is_error=1, result_summary=<错误文本前 300 字>)` |
| 改哪 | ① `apps/windows/src/main/agent-runtime/hooks/tool-usage-hook.ts`——`onError(ctx)` 分支已有，补一条审计写入；② 若 `web_search` 的失败不走 `onError`（而是在 `execute` 内部返回 `{status:'error'}`），则在工具实现里补 |
| 为什么放 hook | hook 是**所有工具的统一出口**，一处接线全工具受益（这也是 B2.3 要的东西），不是给 web_search 开小灶 |
| 体量 | 小 |
| 验收 | 跑一轮资讯任务后，`tool_audit_log` 里出现 `web_search` 且 `is_error=1` 的行，`result_summary` 能看出是限流 / 无结果 / 解析失败 |

### B1.2 第二步：归因（跑一轮，看分布）

```sql
SELECT substr(result_summary, 1, 60) AS reason, COUNT(*) n
FROM tool_audit_log
WHERE tool_name = 'web_search' AND is_error = 1 AND timestamp > <开跑时刻>
GROUP BY reason ORDER BY n DESC;
```

**这一步没有代码产出**，产出是一张分布表，贴在提交信息里。

### B1.3 第三步：按分布修（分支）

| 归因 | 修法 | 改哪 |
|---|---|---|
| **限流 / 超时** | 加退避与并发上限；失败重试一次 | 工具实现 |
| **无结果 / 结果质量差**（最可能） | **重写工具的 description 与参数**——把「可靠路径是直接抓列表页」固化成描述里的一句；必要时补一个 `site:` 参数 | `web-search-tool.ts` 的 `description` / `parameters` |
| **解析失败** | 修解析 | `web-shared.ts` 或平台实现 |
| **网络/代理** | 检查出口配置 | 本机环境，非代码 |

> 依据：Anthropic 内部的做法是「让 agent 拿坏工具反复试，然后**重写工具描述**」，后续任务完成时间 **−40%**。

### B1.4 第四步：把情报摸出来的经验固化

情报用两轮时间自己摸出「列表页比搜索可靠」，现在只躺在一条自由文本记忆里。**固化成两处**：

1. `web_search` 的 description 里加一句「结果质量参差时，优先直接抓取目标站点的列表页」；
2. 情报的**手册/提示词**里记一条（它没有手册，就写在 `INFO_CURATOR_PROMPT` 的第 3 步「采集」下）。

### B1 验收

- [ ] `web_search` 的失败率在下一轮实测中**下降**（对照 43% 基线；目标先定 <25%）
- [ ] 失败日志（若仍失败）能看出原因，不再是黑盒
- [ ] 情报的一轮真实抓取里，条目来源分布比之前更集中（说明它改用列表页了）
- [ ] 提交信息里带**归因分布表**

### B1 风险

| 风险 | 缓解 |
|---|---|
| 失败原因在工具实现内部被吞掉，hook 拿不到 | B1.1 的两个接线点都试；实在拿不到就在 `execute` 的 catch 里直接写审计 |
| 改 description 影响其它 Agent 的搜索行为 | 描述改的是**策略建议**不是参数契约，且搜索对谁都是同一件事；改后跑一次 assistant 的普通搜索确认无回归 |

### B2.1 `tool_usage_stats` 加 agent 维度（迁移 V44）

**为什么**：「维护到底用没用过 `wiki_read`」现在答不了；逐 Agent 的工具决策全靠猜。

```sql
-- V44：主键从 tool_name 改为 (agent_id, tool_name)
ALTER TABLE tool_usage_stats RENAME TO tool_usage_stats_v43;
CREATE TABLE tool_usage_stats (
  agent_id     TEXT NOT NULL,
  tool_name    TEXT NOT NULL,
  count        INTEGER NOT NULL DEFAULT 0,
  error_count  INTEGER NOT NULL DEFAULT 0,
  last_used_at INTEGER,
  PRIMARY KEY (agent_id, tool_name)
);
-- 历史全局计数无法归因，不假装能：统一记为 'unknown'
INSERT INTO tool_usage_stats (agent_id, tool_name, count, error_count, last_used_at)
SELECT 'unknown', tool_name, count, error_count, last_used_at FROM tool_usage_stats_v43;
DROP TABLE tool_usage_stats_v43;
```

## B4 · 执行时注入「自述」

### B4.1 现状

cron 执行是全新实例、跑完即销毁（`restoreHistoryForInstance` 只在压缩时调），**会话里累积的记录 Agent 看不到**。

### B4.2 做成什么样

在 `driveAgent` 拼 prompt 时，任务指令**之前**加一段：

```
=== 你上次的情况 ===
上次执行：2026-09-16 12:00（14 小时前）
上次产出：本轮推 13 条增量；卡片累计 200+ 条
上次发现：5 条记录带 JSON 序列化残迹（未处理）
```

| 项 | 内容 |
|---|---|
| 改哪 | `apps/windows/src/main/agent-runtime/cron-scheduler.ts` 的 `driveAgent`（拼 prompt 处，约 `:923-980`） |
| 数据 1：上次执行 | 该会话（`cron:<jobId>`）最近一次 assistant 产出 —— 已有查询路径 |
| 数据 2：上次发现 | `readLatestMaintenanceReport()`（片 11 已有），只在维护类任务时拼 |
| 首版不做 | 台账（还没建）；事件层（B7） |
| 拼装函数 | 新增 `buildSelfBriefing(jobId, agentId): Promise<string>`，纯拼装、可单测 |
| 体量 | 小 |
| 验收 | 连跑两次同一 cron 任务，第二次的 prompt 日志（`[llm-prompt:full:begin]`）里能看到「你上次的情况」段，且内容来自第一次的真实产出 |

### B4.3 为什么不是「恢复历史」

- 全量历史贵且噪声大；调研的证据是「朴素摘要式巩固会破坏信息」（35.3% vs 98.0%），但那是**替代**场景——这里是**加法**（补一句摘要，不动原文）
- 且 cron 会话的历史会无界增长，恢复它很快会撞上压缩

## B6 · 维护的「从发现到动作」

### B6.1 地基（已有）

`maintenance_reports.findings` 带 `key` / `severity` / `title` / `evidence` / `suggestion`，跨期 key 差分已在做。**缺的是「从发现到动作」。**

### B6.2 四条不变式（逐条落到实现）

| # | 不变式 | 实现 |
|---|---|---|
| ① | 预览**零副作用** | 生成变更预览时不写任何东西；预览只是一段结构化描述 |
| ② | 执行的是**被审过的那一份** | 新表 `maintenance_actions(id, report_id, finding_key, kind, payload, preview, status, created_at, executed_at, result)`；确认后执行 `payload`，**不重新生成** |
| ③ | 结果写回**同一条** | `maintenance_actions.result` + 回指 `report_id`；概览页卡片上该条 finding 显示「已处理 / 已跳过」 |
| ④ | 可回滚或至少可追溯 | 记忆改动已有 `.bak`；Wiki 改动要有快照（B6.4） |

### B6.3 动作分级

| 级 | 动作 | 交互 |
|---|---|---|
| L1 | **只加标记**（标记重复记忆 / 标记过期页） | 可直接做，不改内容 |
| L2 | **合并 / 归档** | 出预览 → 确认 → 执行；**合并要改写所有引用**（只删不转会留断链） |
| L3 | **清除** | 前置预告期 + 可恢复窗口 |

### B6.4 交互细节（都有实证来源）

| 细节 | 来源 | 实现 |
|---|---|---|
| **跳过不丢** | Guru | `status='skipped'` 的记录留在队列，下次仍出现 |
| **冷却期 7 天** | Guru | 同一 `finding_key` 7 天内不重复提醒；否则用户会整体静音，**比不提醒更糟** |
| **倒计时比「已过期」更驱动** | Slab | 卡片上显示「还有 3 天到期」而不是「已过期」 |
| 合并要改写引用 | Obsidian Note Composer | 合并两条记忆时，指向被合并条目的引用一并改 |

### B6.5 分批

| 子批 | 内容 |
|---|---|
| B6-1 | `maintenance_actions` 表 + 从 finding 生成预览（只读，不执行） |
| B6-2 | 概览页卡片：finding 上挂「处理 / 跳过」，展示预览 |
| B6-3 | 执行 L1（只加标记）+ 结果写回 + 冷却期 |
| B6-4 | 执行 L2（合并 / 归档，含引用改写与快照）+ 可回滚 |

### B6 验收

## B7 · 事件级去重（轻量版）+ 来源质量

### B7.1 事件级去重

**结构**（抄 GDELT 的 Events/Mentions 分裂）：

```sql
-- V45
CREATE TABLE news_events (
  id              TEXT PRIMARY KEY,   -- 稳定 id
  feed_id         TEXT NOT NULL,
  canonical_title TEXT NOT NULL,
  first_seen      TEXT NOT NULL,
  last_seen       TEXT NOT NULL,
  source_count    INTEGER NOT NULL DEFAULT 1,
  created_at      TEXT NOT NULL
);
ALTER TABLE dashboard_feed_items ADD COLUMN event_id TEXT;
```

| 项 | 内容 |
|---|---|
| 聚类（轻量版） | 标题 n-gram 相似度 + 时间窗，**不上 embedding** |
| 参数 | 相似度阈值 **0.7**；文章与事件时间差 **≤18h**；事件存活 **≤36h** |
| 参数来源 | 线上验证值（$100/月、180+ 源的公开实践） |
| 落点 | `dashboard_feed_write` 写入时先做事件匹配，再落 `event_id` |
| 渲染 | **一件事一行**，来源折叠（「36氪、澎湃、界面 等 4 家」），点开看各家标题 |
| 已知失效 | 带强烈本地语境的地区新闻会漏并；**宁可漏并也不降阈值换误并**（原作者的取舍，照抄） |

### B7.2 来源质量（不自建）

| 做 | 不做 |
|---|---|
| 一份**人工小名单**（常看的 20–30 个源，手工标三档） | ❌ 用 LLM 打分（与人类专家 ρ=0.50，且指派角色会稳定偏斜） |
| 用评分做**降权**与**背景提示** | ❌ 把评分当「这篇可信」的判据（评分是**按出版物整体**的） |
| 记「这个源最近 10 条被推了几条、被滤了几条」 | ❌ 自建九维度评分流程（NewsGuard 那种） |

### B7 验收

- [ ] 构造同一事件的 3 条不同来源稿件 → 落成 1 个 event + 3 条 item → 卡片渲染成一行
- [ ] 地区新闻的漏并率抽样看一次（接受漏并，但不接受误并）
- [ ] 来源名单生效：被降权的源在同等条件下排后
