## 二、现状事实（2026-09-15 工作区核实，全部带行号）

### 2.1 硬实证：`sessionKey` 前缀**不代表**此刻服务它的渠道

同一会话键 `qbot:964A476991442C6FA18DC32EF18AFEFC`，同一天：

| 时间 | 日志 | 谁在说话 |
|---|---|---|
| 09:42 | `[WeixinChannelAdapter] [handleMessage] sessionKey=qbot:964A…` | 微信 |
| 10:00 / 10:02 | `[QbotChannelAdapter] [handleMessage] sessionKey=qbot:964A…` | QQ |

用户可以续聊任何会话，于是「会话键的来处」与「这轮是谁在说话」分离。**用前缀推断渠道的代码，此刻必然推断错。**

### 2.2 一次渠道消息的会话键，来自四层优先级

```
buildSession(msg) → getActiveSessionKey(channelUserId)
   ① 内存 Map  activeSession                      进程内，重启即丢
   ② ChannelSessionStore.getActive                runtime_state（落库）
   ③ [仅微信] WeixinSessionBindingManager          runtime_state（落库，/link 专用）
   ④ 兜底 `{channelType}:{channelUserId}`
```

- 四层只在 **weixin** 成立（`weixin-channel-adapter.ts:495-511`）；qbot/feishu/wecom 是三层（`qbot:174-181`、`feishu:211-218`、`wecom:199-209`）；
- 四层里有**两套持久化**都在回答同一个问题（「这个用户该路由到哪个会话」）：`weixin:binding:{uid}`（`weixin-session-binding.ts:18`）与 `channel:active:weixin:{uid}`（`channel-session-store.ts:30`）。`/link` 同时写两者（`link.ts:38,41`），接续只写后者（`cross-channel-continuity.ts:336`）——**「接续不写 binding」只靠注释约束**，无类型或测试保证。

### 2.3 四个适配器：同一功能，四份拷贝

| 项 | weixin | qbot | feishu | wecom |
|---|---|---|---|---|
| `getActiveSessionKey` 层数 | **4**（含 /link） | 3 | 3 | 3 |
| `setActiveSessionKey` 日志 | 有 | 无 | 无 | 无 |
| `resetToChannelSession` 解绑 /link | **有**（`:526-536`） | 无 | 无 | 无 |
| `/new` 实现 | 共享 `new.ts`（**硬编码 `weixin:` 前缀**，`:9`） | 本地副本 | 本地副本 | 本地副本 |
| ACP / `/project` `/claude` 等 | 有 | **无** | 有 | **无** |
| `ChannelSessionStore` 实例 | 各自 `new` 一份（**非单例**） | 同 | 同 | 同 |

`qbot:174-197` / `feishu:211-234` / `wecom:202-225` 是三段近乎逐字的重复。`wecom:199-202` 还留着**重复的 JSDoc 块**（复制粘贴物证）。

### 2.4 接续状态机：把「询问」与「扣住消息」焊在一起

`cross-channel-continuity.ts` 一个类同时管：候选判定、询问推送、改写路由、持久化绑定、**扣住当前消息**、60 秒超时（默认接续）、答复后**重放**、以及「问过没问过」。

关键机制：
- 扣住的消息只能靠 `replay: () => void this.handleMessage(msg)` 重放（四渠道同款，`weixin:307` 等），**重放不走 `userQueues`**；
- 所有作废路径都要想清楚 `replayHeld` 传什么（`abandon` `:295`、`tryConsumeReply` `:262`、`clear` `:273`、`abandonWithReplay` `:283`）；
- 「只问一次」用 `asked: Set<sessionKey>`（`:188`），键是**路由**而非**用户**，所以 `resolve()` 里手工补两处 `asked.add`（`:338`、`:356`）防重放时再问。

### 2.5 一条入站文本有 6 个潜在消费者

顺序即代码顺序（`channel-interaction-hub.ts:193-227` 的插队路径 + 各 adapter 的 `handleMessage`）：

| # | 消费者 | 接受词 | 何时 |
|---|---|---|---|
| 1 | 斜杠命令（先作废挂起项） | `/…` | 最先——否则命令会被当成「答复」吞掉 |
| 2 | `ChannelInteractionHub`（审批 / 提问） | `1` `2` `3`… | 非斜杠且该会话有挂起项 |
| 3 | `CrossChannelContinuity`（接续） | `1`/`y`/`是`/`接续`；`0`/`n`/`否`… | 非斜杠且该会话有挂起项 |
| 4 | `/stop` `/abort` | 命令词 | 插队路径末尾 |
| 5 | `tryConsumeHandoffConfirm`（转交，**已架空**） | `1`/`确认`/`ok`… | `handleMessage` 内、普通消息之前 |
| 6 | 普通消息 | — | — |

「1」既是审批词也是接续词；挂起项同时存在时归属由顺序决定，**用户无法表达自己在回答哪一个**。

### 2.6 命令面（渠道侧）

`slash-commands/` 12 个文件：`new` `resume` `back` `link` `/unlink` `clear` `compact` `stop` `project` `backend` `switch-backend`（`/claude` `/codex`… `/lumii`）`help`。注册矩阵：weixin 15 项、feishu 同集；**qbot / wecom 没有 ACP 相关命令**（无 `/project` `/backend` `/claude` `/codex` `/opencode` `/cursor` `/lumii`）。

`/back` 的实现是 `adapter.resetToChannelSession`——**四渠道语义不同**，`back.ts:16-32` 对此无区分。

## 四、目标模型：三层分离

一句话：**身份归身份、路由归路由、交互归交互**，各有单一真相源。

### 4.1 身份层：渠道归属写进数据

```
conversations 增 channel_type（+ channel_user_id），创建时写入，存量按前缀 + /link 回填
channel/channel-identity.ts：唯一一份 CHANNEL_PREFIXES / NON_USER_PREFIXES / labelOf()
```

- 五个消费点（A1 的五套实现）改读数据；前缀函数降级为迁移期兼容；
- 顺带满足 07 计划会话守卫清单里的 c 项（`onboarding:` 前缀必须纳入「非用户会话前缀」，否则向导会话会混进接续候选与 `/resume` 列表——该项随 07 文档正在并行修订，此处按内容引用）。

### 4.2 路由层：一个 `ChannelRoute`

```ts
interface ChannelRoute {
  own: string          // 本渠道本人的会话（显式，不再靠「约定 + 兜底」）
  active: string       // 当前生效（可能借自别处）
  borrowedFrom?: 'link' | 'continuity'
}
```

- 读写集中一处（`ChannelSessionStore` 已有雏形，改成**单例**），adapter 只提供「own 怎么算」；
- `/new` `/resume` `/back` `/link` `/unlink` 全部改成对该结构的操作，**一张表说清每种切换对 `borrowedFrom` 的副作用**（消 B4/B5）；
- 运行期写入前校验目标会话存在（消 B6）；
- 明确 `dev-context`/backend 是否随路由迁移（B7）——**建议：随 active 走**，即把 dev-context 的键从 `sessionKey` 改为「路由解析后的会话」。

### 4.3 交互层：接续不再扣消息

**方案 A（推荐）**：提示式
- 检测到候选 → 发提示 + **当前消息照常处理**（留在本渠道会话里回答）；
- 用户回 `1` / `/resume <n>` → **后续消息**走目标会话；
- **无超时、默认保持现状**（安全默认值）；`asked` 改为按 `(渠道, 用户)` 记录，且可被 `/clear`、`/new` 重置。

**方案 B（备选）**：维持询问式，但把扣留/重放补全
- 保留扣消息 + 重放；补齐 C2/C3 的路径与测试，重放走 `userQueues`，`clear` 语义与调用点对齐。

| | A | B |
|---|---|---|
| 当前消息 | 本会话回答 | 带到目标会话回答 |
| 复杂度 | 删掉 pending/replay/timer 三件事 | 保留并补全 |
| 风险 | 用户可能觉得「答非所问」 | 重入 `handleMessage` 的老问题继续存在 |
| 默认值 | 不变（安全） | 1 分钟默认接续（会「自己动」） |

### 4.4 入口层：一个分发器 + 消歧

`ChannelInboundRouter`：挂起交互 → 挂起接续 → 斜杠命令 → 普通消息，**规则集中、有测试**（补 D2）；挂起项**互斥**（进入挂起态时拒绝叠加），文案不再共用裸数字（消 D1）。

### S4 · 接续瘦身（方案 A）（2026-09-15 代码完成）

**决策**（拍板 1）：提示式——当前消息照常处理、无超时、默认什么都不变。

**删掉的三件事**（C1-C3、C5 随之消失）

| 删掉 | 原问题 |
|---|---|
| **扣住消息 + 重放**（`PendingAsk.replay` / `abandon` / `replaySafely` / `abandonWithReplay`） | 重放 = 让 adapter 重跑一遍 `handleMessage`，不走 `userQueues`，与紧随的 `/clear` 竞态；每条作废路径都要判断 `replayHeld` |
| **60 秒定时器 + 默认接续** | 用户没看见提示也会被换会话；`timer.unref()` 还得单独照顾 |
| **`asked: Set<sessionKey>`** | 键是「路由」不是「用户」，只增不减；接续后路由变成借来的键，还要手工补两处标记 |

**换成**

- `maybeNotice({adapter, session})`：发提示，**不拦截消息**（返回值只表示「发了没有」）；
  四个 adapter 的调用点从「`const asked = maybeAsk(...); if (asked) return`」变成一行调用。
- 有效提示 `offers: Map<用户键, {candidate, expiresAt}>` —— **惰性过期**（读到才判），没有 timer；
  有效期 10 分钟（与转交确认的窗口一致）。
- `noticedRoute: Map<用户键, 会话键>`：记「该用户已就**哪条路由**提示过」。用户换会话
  （`/new`、`/resume`、`/back`）后路由变了，自然可以再提示一次；`/clear` 走 `resetNotice()` 显式重新武装。
- `tryConsumeReply(adapter, session, text)`：`1` → `setActive(..., 'continuity')` 并**回读确认**
  （目标会话可能已被删，store 会拒绝写入——此时如实回「那条会话已不可用」）；`0` → 什么都不变；
  识别不了 → 不消费，当普通消息放行。没有提示时一概不消费（不会顺手吃掉无关的「1」）。
- 提示文案去掉「1 分钟内不回复默认接续」，改为如实说明两条路各会发生什么。

**连带更新**：设置页「跨渠道会话接续」详情里的行为说明（S1 写的旧文案已不符）；
`channel-interaction-hub` 的 `continuity` 端口从 4 个方法收成 2 个（`tryConsumeReply` / `clear`）。

**验证**

- `cross-channel-continuity.test.ts` 状态机部分重写为 **15 例**：提示不扣消息 / 同一路由此一次 /
  换会话可再提示 / 无候选不提示 / 查询抛错不阻断 / 回复 1 切路由并回执 / 目标失效如实告知 /
  回复 0 什么都不变 / 无法识别放行 / 无提示不消费 / **过期失效**（含边界内仍可兑现）/ 兑现一次即作废 /
  `clear` 与 `resetNotice` 的区别；
- 定向 181 例绿（channel 172 + 设置页 9）；4 包 typecheck 干净。

### S5 · 入口统一与「1」消歧（2026-09-15 代码完成）

**先纠正一处**：四个渠道 adapter 早已**共用一个**插队函数 `tryHandleChannelOutOfBand`
（不是四份拷贝），所以本片不是「造一个 Router 类」，而是把**裁决规则显式化、可测、消歧**。

**D1 · 「1」不再多义**

- 接续提示改用词：「回复**接续**继续那条对话（本条消息仍在这里回答），回复**不接续**忽略」。
  渠道里另一套「回 1/2/3」是审批与提问的位阶选项（`formatPermissionPrompt` 三选一、
  `formatAskPrompt` 带序号选项），天然用数字——两套都问「1」时，用户根本没法表达在答哪一个。
  现在词面就分得开；`parseContinuityReply` 仍容忍 `1`/`0`/`是`/`否` 等旧写法，老用户不会撞墙。
- **互斥**：该会话正等审批/提问答复时**不发接续提示**（且不记为「看过」，等那套流程结束再评估）——
  否则用户下一条消息必然被审批协议吃掉，这条提示纯属噪音。
- 反方向（先有接续提示、后来了审批）由裁决顺序保证：审批优先消费，接续提示照常等到过期。

**D2 · 裁决点补测（此前零覆盖）**

`channel-interaction-hub.test.ts` 新增 **8 例**：无挂起项放行 / 斜杠命令不被吞且作废挂起项 /
审批有效答复回填决定 / 看不懂的答复重新提示而非当新需求 / 接续答复按其结果消费 /
`/stop` 打断并清挂起项 / 无运行任务时的如实文案 / 空文本不裁决。

**D3 · 窗口魔数收成一份**

新模块 `channel/recent-conversations.ts`：`RECENT_SCAN_LIMIT = 200` +
`sortByUpdatedAtDesc(rows)`。四处消费方（路由兜底查 own `200` / 接续候选 `50` /
`/resume` `100` / `session_list` `200`）全部改用它，口径统一为
**「取宽窗口 + 自己按时间倒序」**，需要更窄窗口（如接续的 3 天活跃窗）各自过滤。
（`/resume` 与 `session_list` 的排序还带分组 / 关键词语义，只共用常量与时间序助手。）

**验证**
