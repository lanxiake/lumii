## 一、背景：为什么「各自为战」（2026-09-13 侦察结论）

四路代码核实（行号清单见附录 A），四个根因：

1. **共享层名不副实（最伤）**
   - **Wiki 按 Agent 隔离**：所有查询带 `agent_id`，工具层按实例 definitionId 解析 → 「灵栖维护」调用 wiki 工具看到的是 `system-keeper` 空库，用户的资料库（`assistant`）它根本看不见 → 策展职责无从履行。
   - **工作记忆注入硬编码 `assistant`**：专家自己积累的 `agent_memories`（按 definitionId 写入）永远注不进模型——写-only，「越用越准」在专家身上是断的。
2. **协作通路断线**：`send_message` 无实例→报错、空闲→入队不唤醒；子 Agent 被禁用；互喂三条全零（开发→日报、情报→资料库、维护→全员）。
3. **产出可见性断在最后一公里**：async 子 Agent 完成渲染层空实现；cron 失败零通知；转交完成汇报不弹通知；无未读/聚合。委托在父会话只有折叠工具行（富子 Agent 卡片是死代码）。
4. **身份隐形 + 装备不齐**：会话行无 Agent 徽标；chronicler / info-curator 无手册技能；`prompt_guide` 不在四位专家工具白名单（terse 段引用不可执行）。

- **摄入来源标记**：摄入统一记为库 owner（`agent_id` 列保留但不区分专家）——UI 今天本就无来源展示，如需「谁录入」再另立字段；
- 其他硬编码 `'assistant'` 的调用点（IPC 兜底 / 两个 purge 工具）本轮不动，避免扩大 diff；
- 多用户/多库未来形态不设计（独立版单用户）。

## 四、G2-G4 概要（开工前细化）

### G2 · 通知补点（四个点，全部复用桌面通知链：`desktop-notify.ts` + 点击导航）

| 点 | 现状 | 改动 |
|---|---|---|
| async 子 Agent 完成 | `agent:subagent:completed` 渲染层空实现 | 视口不在父会话时弹通知（点击跳父会话） |
| cron 失败 | 零通知 | `dispatchNotifications` 失败分支补发（标题含任务名） |
| 转交完成/失败 | 只写回原会话 | `dev-handoff-executor` 汇报后补桌面通知 |
| 自主反思/日记 | 不通知 | 高价值产出走 `sendOutreach` 既有预算（或仅落会话+轻提示，开工时定） |

噪声纪律：用户正在该会话（presence.userAtClient）时不弹。

### G3 · 委托可见

现状：`spawn_agent` 在父会话是折叠工具行「调用子 Agent N 次」；富 SubagentCard 组件存在但数据源死。
方向（开工时二选一或组合）：① 激活 SubagentCard 数据链（子实例 sessionKey/工具/摘要已有落库素材）；② 降级方案——spawn 行升级为专用卡片（专家名 + 状态 + 关键步骤 + 结果摘要），折叠区外可见。

### G4 · 协作通路最小修复

- `send_message` 空闲分支补唤醒（复用 `deliverSubagentCompletion` 的 idle 三分支模式，约 3 行，设计 §7.5 原案）；
- 传话落库：发送/接收写入父会话消息流并带 `sourceAgent` 标记（复用既有 `contentJson.sourceAgent` 通道）；
- 不做：持久信箱、子 Agent 放开 send_message、互喂全量（阶段 2 逐 Agent 深挖时按场景引入）。

### G4 语义重设计（2026-09-13 拍板：任务级追加）

**问题（实测证据）**：G4 把机制修好了，但通路没有任何真实入口——① 提示词只写「不要用 send_message 委派」，
模型从不自发使用；② 自然话术「顺便帮我嘱咐它一句」两轮都被折叠进委托 prompt（0 次调用）；
③ 拆两轮「它还在跑，帮我带句话」时实例已销毁，主助手用实例 id / 显示名 / 定义 id 三次重试均 not found；
④ 子 Agent 被 `CHILD_AGENT_DISALLOWED_TOOLS` 禁掉 send_message。结论：机制装了，线没接。

**改动（任务级追加语义）**
- 提示词（`agent-collaboration-section.ts`）：有 `send_message` 时新增「Messaging a Running Task」段（terse 档一行）——
  `to` = `spawn_agent` 返回的实例 id 或专家名；用于**对正在跑的任务补要求 / 纠偏 / 转达用户追问**，
  不要为同一件事再 spawn 一个；任务已结束则改为重新委托。
- 工具描述与 `to` 参数说明（`send-message-tool.ts`）同步改为「追加到正在运行的任务」，并明确不是委派通道。
- 未命中错误的出路（`orchestrator.sendMessage`）：报错文案说明「实例在任务完成后即回收，继续这项工作请用
  `spawn_agent` 重新委托，而不是反复重试 send_message」——把失败路径变成可执行的指引。

**同步修复：NO_REPLY 哨兵噪声（重复投递类问题的可见面）**
- 子 Agent 以 `NO_REPLY` 收尾时，摘要原样进入完成投递与桌面通知 → 通知正文变成「NO_REPLY」；
  现在 `guardSubagentSummary` 把它归一化为「（子 Agent 本轮无文本产出）」。
- 整轮回复就是 `NO_REPLY` 时不再落库（`bridge-agent-instance-events` 的 `agent:end` 分支删除占位行）；
  带工具轨迹的轮次保留工具 part，只剔除哨兵文本。渲染层通知正文对哨兵值同样走兜底文案。

**未做（记入阶段 2）**：子 Agent 长产出以流式消息挂进父会话（实测连续 6.5 分钟 `is_streaming=1`），
