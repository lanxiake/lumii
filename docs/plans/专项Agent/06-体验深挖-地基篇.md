## 一、背景：为什么「各自为战」（2026-09-13 侦察结论）

四路代码核实（行号清单见附录 A），四个根因：

1. **共享层名不副实（最伤）**
   - **Wiki 按 Agent 隔离**：所有查询带 `agent_id`，工具层按实例 definitionId 解析 → 「灵栖维护」调用 wiki 工具看到的是 `system-keeper` 空库，用户的资料库（`assistant`）它根本看不见 → 策展职责无从履行。
   - **工作记忆注入硬编码 `assistant`**：专家自己积累的 `agent_memories`（按 definitionId 写入）永远注不进模型——写-only，「越用越准」在专家身上是断的。
2. **协作通路断线**：`send_message` 无实例→报错、空闲→入队不唤醒；子 Agent 被禁用；互喂三条全零（开发→日报、情报→资料库、维护→全员）。
3. **产出可见性断在最后一公里**：async 子 Agent 完成渲染层空实现；cron 失败零通知；转交完成汇报不弹通知；无未读/聚合。委托在父会话只有折叠工具行（富子 Agent 卡片是死代码）。
4. **身份隐形 + 装备不齐**：会话行无 Agent 徽标；chronicler / info-curator 无手册技能；`prompt_guide` 不在四位专家工具白名单（terse 段引用不可执行）。

### 改动点

1. **`bridge-prompt-composer.ts`**：`fillWorkMemoryPlaceholder` 回调签名增 `instanceId` 参数（调用处 `:479` 传入）。
2. **`bridge.ts:275-286`**：按 `agentRegistry.get(instanceId)?.definitionId ?? 'assistant'` 解析归属 → 专家开始注入自己的 agent_memories（相关性门控与 assistant 完全同规则）。
3. **新增 `wiki-library.ts`**（主进程小模块）：`SHARED_WIKI_LIBRARY_AGENT_ID = 'assistant'` 常量 + 拍板缘由注释（用户级共享库）。
4. **`bridge-wiki-tools.ts`**：`resolveAgentId` 删除，三工具统一用共享库常量；随之移除不再使用的 deps（`toolCallInstanceMap` / `getCurrentToolExecutorInstanceId` / `getDefinitionIdByInstanceId`）及接线。
5. **`bridge-instance-factory.ts:560-562`**：`resolveWikiAgentId` 改返回共享库常量——所有 Agent 的 `uploads/`·`outputs/` 摄入落同一个库（写入归属标记沿用库 owner；详见「已知边界」）。

### 已知边界（本片不做）

- **摄入来源标记**：摄入统一记为库 owner（`agent_id` 列保留但不区分专家）——UI 今天本就无来源展示，如需「谁录入」再另立字段；
- 其他硬编码 `'assistant'` 的调用点（IPC 兜底 / 两个 purge 工具）本轮不动，避免扩大 diff；
- 多用户/多库未来形态不设计（独立版单用户）。

## 四、G2-G4 概要（开工前细化）

### G2 · 通知补点（四个点，全部复用桌面通知链：`desktop-notify.ts` + 点击导航）

| 点 | 现状 | 改动 |
|---|---|---|
| async 子 Agent 完成 | `agent:subagent:completed` 渲染层空实现 | 视口不在父会话时弹通知（点击跳父会话） |
| cron 失败 | 零通知 | `dispatchNotifications` 失败分支补发（标题含任务名） |
| 转交完成/失败 | 只写回原会话 | `dev-handoff-executor` 汇报后补桌面通知 |
| 自主反思/日记 | 不通知 | 高价值产出走 `sendOutreach` 既有预算（或仅落会话+轻提示，开工时定） |

噪声纪律：用户正在该会话（presence.userAtClient）时不弹。

### G3 · 委托可见

现状：`spawn_agent` 在父会话是折叠工具行「调用子 Agent N 次」；富 SubagentCard 组件存在但数据源死。
方向（开工时二选一或组合）：① 激活 SubagentCard 数据链（子实例 sessionKey/工具/摘要已有落库素材）；② 降级方案——spawn 行升级为专用卡片（专家名 + 状态 + 关键步骤 + 结果摘要），折叠区外可见。

### G4 · 协作通路最小修复

- `send_message` 空闲分支补唤醒（复用 `deliverSubagentCompletion` 的 idle 三分支模式，约 3 行，设计 §7.5 原案）；
- 传话落库：发送/接收写入父会话消息流并带 `sourceAgent` 标记（复用既有 `contentJson.sourceAgent` 通道）；
- 不做：持久信箱、子 Agent 放开 send_message、互喂全量（阶段 2 逐 Agent 深挖时按场景引入）。

## 五、明确不做（地基篇）

### G2 · 通知补点（2026-09-13 代码完成，真实场景验收待跑）

**代码（四个点）**
- **async 子 Agent 完成**：`agent:subagent:completed` 事件增 `sessionKey`（父实例所在会话，`bridge-lifecycle.ts` emit 时从 `instanceToConversation` 取）——此前事件无会话标识、渲染层路由会落回当前会话；渲染层 `event-handler.ts` 的空实现改为：用户不在父会话、或窗口不在前台时弹桌面通知（标题「Lumii · <名字> 已完成/执行失败/已超时」，正文摘要截 120 字），点击直达父会话；`cancelled`（父主动中止）不弹。
- **点击直达链路**：`notify:desktop` IPC / preload `notifyDesktop` / `app-service.notifyDesktop` 增可选 `convId`，落到 `desktop-notify` 既有的 `conversation:navigate`（此前渲染层通知无法带跳转目标）。
- **cron 失败**：`cron-scheduler.ts` 失败分支补系统通知（标题「灵栖 · <任务名>」、正文含失败原因、点击跳 `cron:<id>` 任务会话）。成功路径仍按 `notify_targets` 派发；失败一律外推——命中失败的任务此前零通知、只在定时任务页可见，等于静默消失。通知自身异常只记日志，不影响失败记账。
- **转交完成/失败**：`handoff-commands.ts` 写回原会话后，用户不在原会话（`getLastActiveConversationId()`）时补桌面通知，点击跳回原会话；在原会话时报告消息已实时可见，不打扰。
- **自主反思/日记（§四「开工时定」的决策）**：**不弹桌面通知**——两者只在静默时段（`quietHours`）产生，弹窗会违反用户自己设置的静默语义；改为把已落库的产出行（提问 + 正文）推送渲染层（`conversation:message:new`），会话开着时实时可见，不再"写完只能靠重开查看"。

**验证**
