## 一、背景：两层失败，不是一层

### 1.1 事实

用户在桌面客户端提交「根据当前 lumii 项目代码的实际情况…深入反思 07 方案，并搜索业界成熟方案」。项目 `lumii` 已注册（`codingDevProjects` 含 `realPath: C:\myself\projects\my\open-source\lumii`）且为活动项目（`codingDevActiveProject = "lumii"`）。

**第一层：主助手没转交。**

- `tool_audit_log` 全表 `LIKE '%handoff%'` = **0 行**——`propose_dev_handoff` 自实现以来从未被调用；
- 但工具确实在主助手工具面：`assistant` 定义 `tools: ["*"]`（`packages/agent-runtime/src/agent/builtin/definitions.ts:96`）+ `registerHandoffTools` 无条件注册（`apps/windows/src/main/agent-runtime/bridge-tool-registrar.ts:78`）；
- 主助手实际走了 `spawn_agent(builtin:explore)` + 自建脚本读文件。

原因：转交的适用域被写死为「改代码」（`bridge-tool-registrar-handoff.ts:37-40` 的 `bug fixes / features / refactors`；`prompts.ts:217` 的 "For **development** in a registered/bound project"），而「分析/评审/调研」不在其中；同时 `builtin:explore` 的适用描述（"answer questions about the codebase"）精确命中此类请求。

**第二层（更严重）：即使转交，也进不了项目。**

`runDevHandoff` → `handleUserSend(agentId: 'code-dev')` → `resolveDevContext`（`apps/windows/src/main/coding-dev-env.ts:188-207`）：

```
devCtx      = getDevContext(...)        → 新建会话，dev-context.json 无记录 → undefined
binding     = resolveAgentDevBinding(...) → app.json 无 codingDevAgentBindings → undefined
backendId   = undefined ?? undefined ?? fallbackBackendId  → 'lumii'（user-global 选择）
projectPath = undefined ?? undefined                        → 项目丢失
```

`backendId === 'lumii'`（= `DEFAULT_CODING_DEV_BACKEND_ID`）→ **不走 ACP 分支**（`ipc/agent-runtime/user-commands.ts:212`）→ 落 `bridge.prompt`（pi 内核），`cwd` 取 `getCwd()`（`main/index.ts:536-539`）= `workspaceDirectory ?? ~/.lumii/workspace`。

即：**灵栖开发会在 `~/.lumii/workspace` 里干活，看不到 lumii 仓库**——与主助手撞的是同一堵墙。

### 1.2 根因一句话

**「项目」只接进了 ACP 执行链，没有接进「委托/转交」决策链，也没有接进工具沙箱。**

- `codingDevProjects` / `codingDevActiveProject` 只喂 `MTBOT_*_ACP_CWD` 环境变量（`coding-dev-env.ts:57-62`），**不参与 `resolveDevContext`**；
- 唯一的项目通道是 `codingDevAgentBindings`，未配置即全链路失效；
- 主助手无任何工具可读 `app.json` 的项目清单 → 不知道有哪些项目存在。

### 1.3 三个后果

| # | 后果 | 严重度 |
|---|---|---|
| 1 | 主助手读不到已注册项目 → 只能写脚本绕路（内联转义失败、编码乱码、复制到工作区） | 体验 |
| 2 | 转交后 cwd 落在全局 workspace → 开发任务在错误目录执行 | **功能失效** |
| 3 | 桌面端无绑定是**静默降级**（渠道端明确拒绝，`weixin-channel-adapter.ts:677-683`）→ 用户以为转交成功 | **静默假成功** |

## 三、P1 · 工具沙箱纳入已注册项目

### 3.1 现状事实

| 事实 | 位置 |
|---|---|
| 路径解析只接受单根 `cwd` | `packages/agent-runtime/src/tools/resolve-file-path.ts:14,25-27` |
| **底层已支持多根**（`allowedDirectories.some(...)`） | `packages/agent-runtime/src/security/tool-sandbox.ts:22-30,37-46` |
| toolContext 构造（4 处 `resolveAgentFilePath` + 1 处 `getCwd`） | `apps/windows/src/main/agent-runtime/bridge.ts:850-871`（见 `:853,855,859,866` 与 `:871`） |
| 其余调用点 | `file-read-tool.ts:262`、`file-write-tool.ts:138`、`file-edit-tool.ts:204`、`file-fs-ops.ts:18`、`bridge-image-services.ts:147`、`file-memory-handler.ts:117` |
| cwd 来源 | `apps/windows/src/main/index.ts:536-539` |
| 项目清单 | `AppConfig.codingDevProjects`（`main/config/types.ts`），含 `name` / `realPath` |
| bash 无路径沙箱 | `local-bash.ts`（cwd 可注入，命令本身可 `cd` 任意处） |

**关键判断**：`normalizePath` 本身已是多根实现，**P1 只是把第二根传下去**。同时注意 bash 早已能访问任意路径——现行 file_* 边界是「防误读」而非强安全边界；让工具绕道 bash 反而更不可控。

### 3.2 改动点

1. **`resolveAgentFilePath` 增可选多根**（`packages/agent-runtime/src/tools/resolve-file-path.ts`）：

   ```ts
   export function resolveAgentFilePath(
     filePath: string,
     cwd: string,
     extraRoots?: readonly string[],
   ): string {
     const trimmed = filePath.trim()
     if (!trimmed) throw new Error("filePath 不能为空")

     const base = path.resolve(cwd)
     const resolved = path.isAbsolute(trimmed) ? path.resolve(trimmed) : path.resolve(base, trimmed)
     const roots = [base, ...(extraRoots ?? []).map((r) => path.resolve(r))]
     const normalized = normalizePath(resolved, roots)
     if (!normalized) throw new Error(`路径不在工作空间内: ${filePath}`)
     return normalized
   }
   ```
   向后兼容：不传 `extraRoots` 时行为与今天完全一致。

2. **`ToolExecutionContext` 增可选 `getAllowedRoots?: () => readonly string[]`**（`packages/agent-runtime/src/types/tool.ts`，紧邻 `getCwd`）。未注入 = 单根，宿主零影响。

3. **宿主接线**（`apps/windows`）：
   - `bridge.ts` `initializeToolContextAndRegistry()`：抽私有方法 `private resolveAgentPath(p: string): string`，内部 `resolveAgentFilePath(p, this.config.getCwd(), this.config.getAllowedRoots?.() ?? [])`；用其替换 `:853,855,859,866` 四处调用。
   - bridge config 增 `getAllowedRoots?: () => readonly string[]`（`agent-runtime/bridge-types.ts:15` 的 `AgentRuntimeBridgeConfig`，与 `getCwd` 同级）。
   - `main/index.ts` bridge 构造处注入：
     ```ts
     getAllowedRoots: () =>
       (configManager?.getAppConfig().codingDevProjects ?? []).map((p) => p.realPath),
     ```

4. **调用点清单（全部按同一模式处理）**：

   | 层 | 调用点 | 覆盖工具 |
   |---|---|---|
   | packages | `file-read-tool.ts:262` | `file_read` |
   | packages | `file-write-tool.ts:138` | `file_write` |
   | packages | `file-edit-tool.ts:204` | `file_edit` |
   | packages | `file-fs-ops.ts:17-19`（`resolveFsPath` 单点） | `list_dir` / `file_mkdir` / `file_move` / `file_copy` |
   | apps | `bridge.ts:853,855,859,866` | toolContext 的 `readFile` / `writeFile` / `glob` / `grep` |
   | apps | `bridge-image-services.ts:147` | 生图参考图路径 |
   | apps | `file-memory-handler.ts:117` | 记忆文件读写 |

   packages 侧模式：`resolveAgentFilePath(p, context.getCwd(), context.getAllowedRoots?.())`。

5. **放开范围（2026-09-14 拍板：读写均放开）**：
   - 上述**全部调用点**（读 + 写 + 列目录 + 移动复制）一律纳入已注册项目根；
   - 理由：bash 本就无路径沙箱（`local-bash.ts` 的 cwd 仅作默认值，命令可 `cd` 任意处），若只放开读，「读得到改不了」只会逼模型改走 bash——**反而绕开审计日志与 diff 卡片呈现**。不对称的边界不产生安全收益，只产生绕行。
   - 红线不变：**边界只随用户显式注册扩大**，未注册目录仍拒绝（§3.4）。

6. **工具描述同步（7 处，不做则模型仍以为自己碰不了项目文件）**：

   | 文件 | 行 | 现文案（节选） |
   |---|---|---|
   | `file-read-tool.ts` | 256 | "Only works within the workspace." |
   | `file-write-tool.ts` | 132 | "Only works within the workspace. Prefer this over `bash` echo/redirection." |
   | `file-edit-tool.ts` | 198 | "Only works within the workspace. Prefer this over `bash` sed/awk." |
   | `file-mkdir-tool.ts` | 29 | "Only works within the workspace." |
   | `list-dir-tool.ts` | 28 | "… Only works within the workspace." |
   | `file-copy-tool.ts` | 32-34 | "Copy files and directories within the workspace. … must be within the workspace." |
   | `file-move-tool.ts` | 35 | "… must be within the workspace." |

   统一改为：`Works within the workspace and any project directories registered in Settings → Development.`（保持英文，与其余描述语气一致）。

### 3.3 验收

- [ ] `resolve-file-path.test.ts` 新增：多根命中 / 多根外拒绝 / 不传 `extraRoots` 行为不变
- [ ] 单测：`allowedRoots` 为空数组时与现行行为逐字一致
- [ ] 手工：注册项目 A → 主助手 `file_read` 项目内文件成功；未注册目录仍报「路径不在工作空间内」
- [ ] 手工：**回归**——撤销项目注册后，同一路径重新被拒（边界随配置即时变化）
- [ ] 7 处工具描述已同步（`grep -rn "within the workspace" packages/agent-runtime/src/tools/` 无残留）
- [ ] 两包 typecheck 干净；`packages/agent-runtime` 全量绿

### 3.4 已知边界

- 项目根来自 `app.json`，**不含 junction 链接的展开**——`codingDevProjects` 已有 junction 挂载设计，`realPath` 即解析后路径，按现状取用；
- 未注册项目**不放开**（这是本片的安全红线：边界只随用户显式注册扩大）；
- 路径边界放宽后，`bash` 与 `file_*` 的能力更趋一致，但**审计口径不同**（bash 记 `bash_command_log`）——不追求二者等价。

## 四、P2 · 转交提案携带项目上下文

### 4.1 现状事实

| 事实 | 位置 |
|---|---|
| `PendingHandoff` 无项目字段 | `apps/windows/src/main/agent-runtime/handoff-store.ts:13-24` |
| 工具 schema 只有 `task` / `summary` / `session_mode` | `bridge-tool-registrar-handoff.ts:15-29` |
| 执行器只建会话 + 发消息，**不写 dev-context** | `ipc/agent-runtime/dev-handoff-executor.ts:135-154` |
| dev-context 写入 API（已存在） | `coding-dev-dev-context.ts:109-138`（`setDevContext(accountId, peerId, patch)`） |
| 解析优先级 | `coding-dev-env.ts:188-207`（会话显式 > Agent 绑定 > 全局默认） |

**关键洞察**：`dev-context.json` 是现成的会话级通道，`/project` 命令就在用它（`channel/slash-commands/project.ts`）。转交只需**在提案时解析一次、在执行时写入**，即可让 `resolveDevContext` 自然命中 `source: 'session'`。

### 4.2 改动点

1. **`PendingHandoff` 增字段**（`handoff-store.ts`）：
   ```ts
   readonly projectName?: string          // 命中项目名（写入 dev-context）
   readonly backendId?: CodingDevBackendId // 提案时解析出的后端，供 P3 校验
   ```

2. **`propose_dev_handoff` 增可选参数 `project?: string`**（`bridge-tool-registrar-handoff.ts`），描述口径：

   > 目标项目名（可选）。省略时用全局活动项目。项目需已在本机注册（设置 → 开发 → 项目管理）。

   同时**扩展工具适用域**（本片一并做，这是第一层失败的修复）：

   > Use for project-level work in a registered/bound project — bug fixes, features, refactors, **and project-scoped analysis/review/research** (e.g. "根据这个项目的代码评审这份方案"). Only casual snippets outside any named project → handle yourself.

3. **提案时解析开发上下文**：`propose_dev_handoff` 的 `execute` 内复用 `resolveDevContext`（`coding-dev-env.ts:188`）+ `getCodingDevConfig()`，得到 `{ backendId, projectName, projectPath, source }`，`projectName` 取「参数指定 > 全局活动项目」；结果存入提案并回传给模型（让主助手能在回复里说明「将在项目 X 用 Y 执行」）。

4. **执行时写入会话级上下文**（`dev-handoff-executor.ts` `runDevHandoff`，在 `handleUserSend` 之前）：
   ```ts
   if (handoff.projectName) {
     setDevContext(LOCAL_USER_ID, devSessionKey, {
       projectName: handoff.projectName,
       ...(handoff.backendId ? { backendId: handoff.backendId } : {}),
     })
   }
   ```
   （`accountId` 用 `LOCAL_USER_ID`，与桌面会话键结构 `local-user:<conversationId>` 一致。）

5. **会话创建与上下文写入的顺序**：先 `handleConversationCreate` 拿到 `devSessionKey`，再 `setDevContext`，最后 `handleUserSend`——保证首个回合就命中。

### 4.3 验收

- [ ] 单测：`proposeHandoff` 携带 `projectName` / `backendId` 并可被 `consumeHandoff` 取回
- [ ] 单测：`runDevHandoff` 在发起前写入了 dev-context（`getDevContext` 能读回）
- [ ] 端到端（真实对话）：注册项目 A → 主助手识别项目级请求 → 提案 → confirm → 日志出现 `ACP 路径: backendId=… cwd=<项目路径>`（不是「(全局)」）
- [ ] 回归：未指定项目的提案，行为与今天一致（回落到绑定/全局）
- [ ] 渠道：`/project` 已写入的会话级上下文不被转交覆盖（转交写的是**新开发会话**的键，天然隔离）

### 4.4 已知边界

- 提案仍是**内存级**（重启失效，`handoff-store.ts:6-8` 既定设计），本片不改；
- `projectName` 存的是名字而非路径（沿用 dev-context 既定语义），项目被移除后自然失效；
- 不自动创建 `codingDevAgentBindings`——绑定是「Agent 级固化配置」，仍由用户在设置面板维护。

## 五、P3 · 无绑定不静默降级

### 5.1 现状事实

| 事实 | 位置 |
|---|---|
| 桌面：`backendId === 'lumii'` → 直接落 `bridge.prompt`，无任何提示 | `ipc/agent-runtime/user-commands.ts:212,246` |
| 渠道：无绑定**明确拒绝**并给出配置指引 | `channel/adapters/weixin-channel-adapter.ts:677-683`、`qbot-channel-adapter.ts:383-389` |
| 完成判定会把 ACP 错误消息当成功上报 | `dev-handoff-executor.ts:186-198` |

**判断**：渠道端行为是对的，桌面端应对齐——**失败要看得见**。参考设计 §4.1 记录的 codex「拒绝写文件却假报成功」，静默假成功比失败更坏。

### 5.2 改动点

1. **转交路径发起前校验**（`dev-handoff-executor.ts` `runDevHandoff`，紧跟 P2 的上下文解析之后）：
   ```ts
   if (resolved.backendId === DEFAULT_CODING_DEV_BACKEND_ID) {
     report({ ok: false, devSessionKey: '', text: '<可操作提示>' })
     return   // 不建会话、不发消息
   }
   ```
   提示文案（对齐渠道）：
   > ⚠️ 灵栖开发还没有绑定编码工具，无法在项目中执行。请在「设置 → 开发 → 项目管理」为「灵栖开发」配置开发绑定（选择编码 CLI 与项目目录）后重试。

2. **完成判定修正**（`dev-handoff-executor.ts:186-198`）：区分「正常助手回复」与「ACP 错误落库」。最小做法——ACP 侧错误消息落库时带标记（如 content 前缀 `❌` 或 parts 内 error 标志），监听判定命中标记即 `ok: false` 并透传原因。若改动面偏大，本项可拆为 P3b 单独立项。

3. **不影响手动路径**：用户**手动**新建「灵栖开发」会话（会话选择器 `selectable: true`）并发消息，仍走 pi 内核兜底——那是显式选择，不是静默降级。因此校验只加在 `runDevHandoff` 内，**不放** `user-commands.ts` 通用分流。

### 5.3 验收

- [ ] 单测：无绑定时 `runDevHandoff` 不建会话、不调 `handleUserSend`，且 report 为 `ok: false` + 含指引文案
- [ ] 单测：有绑定时行为不变
- [ ] 单测（P3b）：错误落库的 ACP 消息不被判为完成
- [ ] 手工：清除绑定 → 发起转交 → 原会话收到明确失败提示（不再出现「转交完成」但项目无改动）
- [ ] 手工：渠道与桌面提示口径一致
- [ ] 回归：手动开「灵栖开发」会话发消息，pi 兜底行为不变

### 5.4 已知边界

- 不自动降级到「用 pi 内核在项目目录里跑」——那会引入第二套执行语义（工具面 / 权限 / 续接全不同），留待有真实需求时另议；
- 90 分钟超时上报（`dev-handoff-executor.ts:173-183`）本片不改。

## 六、明确不做（本计划）

| 项 | 理由 |
|---|---|
| 自动创建 / 修改 `codingDevAgentBindings` | 绑定含本机绝对路径与 CLI 选择，应由用户在设置面板显式配置；P2 已让「注册项目」这条路可用 |
| 主助手提示词注入「已注册项目清单」 | 有价值但非本计划必需（P1 让主助手能**读到**项目；「知道有哪几个项目」是另一件事），单独立项 |
| 转交产出自动回流主助手上下文（除现有汇报） | 现有 `reportToOriginSession` 已满足；完整回流属会话接续（设计 §8） |
| 提案持久化 | 既定设计为内存级（避免陈旧提案被误确认），维持 |
| bash 工具的路径沙箱 | 现状即无强边界；引入需独立安全设计 |
| `builtin:explore/plan/verify` 持有 `propose_dev_handoff` 的工具面泄漏 | 真实问题（三者的定义无 `tools` 白名单，且该工具不在任何 disallowed 列表内），但与本计划的用户价值无关，归入工具面清理清单 |

## 八、风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| P1 放宽路径边界被滥用（读到无关目录） | 中 | 边界**只随用户显式注册扩大**；未注册目录仍拒绝；补「撤销注册后重新被拒」用例 |
| P1 写权限放开导致误改项目文件 | 中 | 已拍板读写均放开（§3.2-5）。缓解：边界只随用户**显式注册**扩大；`file_edit` 有 diff 呈现；`permissionMode` 闸门不变（注册项目不绕过审批） |
| P2 写入 dev-context 污染用户既有会话选择 | 低 | 只写**新建/复用的开发会话**键，不动主助手会话；`/project` 语义不变 |
| P3 收紧后转交率下降（原本会「跑起来」的场景现在直接失败） | 低 | 这正是目的：把静默假成功换成明确指引；提示文案给出可操作路径 |
| 提案时解析的 backend 与 confirm 时不一致（用户中途改配置） | 低 | confirm 时以 `resolveDevContext` 实际结果为准（P3 校验读实时值，不读提案里的快照） |
