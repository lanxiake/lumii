### 1.1 实测证据（2026-09-14）

**名称（现象 1）** —— 全库 spawn 调用的 `agentType` 取值只有三种，`name` 全是模型自造：

| agentType | 结果 | name 示例 |
|---|---|---|
| `"worker"` | `Unknown agent type: worker` 失败 | `24shi-b9` |
| `"researcher"` | `Unknown agent type: researcher` 失败 | `规划研究员` |
| `"default"` | 成功 | `24shi-b11`、`24shi-b12-fix` |

`default` 是 `assistant` 的历史别名（`definitions.ts:376-379`，显示名「系统默认」），但卡片表里只有 `assistant`（且写的是「灵栖」，与定义已漂移）→ 查表落空 → 显示 `args.name`。

**两个执行过程（现象 3）** —— 微信会话里同一时间戳、两个不同子实例的消息：

```
01:24:11.991  assistant parts=178  sourceAgent={instanceId:"agent-1789346095555-cyffjt", label:"系统默认"}
01:24:11.991  assistant parts=175  sourceAgent={instanceId:"agent-1789346096237-u4afme", label:"系统默认"}
```

两者都被合并进前一条父消息的 `parts` 数组（`mergeAssistantParts` 纯拼接），父消息 `isStreaming` 被置 true。

**中断残留（现象 3b）** —— 同会话存在 `is_streaming=1` 的消息（269 KB / 99 parts），其内的 `spawn_agent` part 状态停在 `running`。

2. **防漂移单测**：断言 `BUILTIN_AGENT_DISPLAY_NAMES` 与 `BUILTIN_AGENT_DEFINITIONS` 的 `id → name` **完全一致**（多一个、少一个、名字不同都红）。这是本片的核心护栏——06 文档记的教训就是两份手工副本会漂。

3. **`spawn_agent` 结果回传真名**：`orchestrator.spawnAgent` 在 `resolveDefinition` 之后已持有 `agentDef`，把 `agentDefinitionId: agentDef.id` 与 `agentName: agentDef.name` 加进 sync / async 两种返回体；`bridge-tool-registrar.ts:244-261` 的封装同步透传。

4. **`SpawnAgentCard` 名称解析**：优先 `result.agentName`；回退链改为 `resolveBuiltinDisplayName(normalizeAgentTypeId(agentType)) ?? rawName ?? agentType ?? '子 Agent'`。

6. **`event-handler.ts:1400-1407` 加护栏**：只在现有 label 是「占位值」时才用快照名覆盖（占位判据 = 等于 `instanceId`，或以 `agent-` / `user-` 开头 / 等于某个已注册的 `definitionId` 字面量）。真实名优先，绝不反向覆盖。

## 四、P2 · 子 Agent 过程归属（本计划主体）

### 4.1 产品判断

用户给了两条路：**① 点击跳转到「对应会话」查看；② 在委托卡片下方内联渲染。**

**① 在当前架构下没有落点**：子 Agent 不产生独立会话——`childSessionKey = child-<ts>-<rand>` 只用于实例路由，`conversationId` 刻意继承父会话（`orchestrator.ts:437-454`，注释：「子 Agent 消息写入同一个 DB 对话，不产生新会话」），且该 sessionKey **不落库**（`event-converter.ts:23-26`）。要支持跳转就得给子 Agent 开独立会话，代价是会话列表膨胀 + 上下文割裂。

**因此本片做 ②**：让子 Agent 的过程在父会话里**有明确归属、可展开、不被误读**。

### 4.2 现状事实

| 事实 | 位置 |
|---|---|
| 子消息被合并进前一条父 assistant 消息并 `continue` 掉，不单独渲染 | `renderer/.../ChatContainer/index.tsx:457-494` |
| `mergeAssistantParts` 是纯拼接（不去重、不留边界） | `ChatContainer/mergeAssistantParts.ts:12-21` |
| 合并后父消息 `isStreaming` 被置 true | `ChatContainer/index.tsx:485` |
| `ThinkingBlock` 的 `isLive` 只看 `message.isStreaming` → 合并后**所有**思考块都变 live | `ChatMessage/index.tsx:656-665` |
| 过程/答案切分以**最后一个** thinking/tool 为界 → 子 parts 追加后，父的最终答案被吞进「执行过程」 | `ChatMessage/index.tsx:394-408` |
| 独立路径：`wrapSubAgent` 的 `<details open={isStreaming}>`，标题「<label> · 执行中（N 工具）」 | `ChatMessage/index.tsx:625-640` |
| 「执行过程」折叠与实时状态 | `components/ActivityFold/index.tsx:36-103`、`ChatMessage:420-431` |
| 卡片已解析 `instanceId` 但未使用 | `SpawnAgentCard/index.tsx:33-39` |
| 合并是**有意为之**（注释承认：带来源的子消息会并入父消息过程折叠区） | `bridge-tool-registrar.ts:316-324` |

**注意**：这份「合并」的初衷是修消息乱序（`mergeAssistantParts.ts` 文件头注释），但它把子 Agent 的身份与过程边界一并抹掉了——这是现象 3 与 4 的共同来源。

### 4.3 改动点

1. **停止合并进父气泡**（`ChatContainer/index.tsx:457-494`）
   - 子消息（`sourceAgent.instanceId` 存在）不再写入父项 `parts`，也不再 `continue` 掉。
   - 改为按 `sourceAgent.instanceId` **归组**，作为父项的可选字段 `subAgentRuns: SubAgentRun[]` 附加（`{ instanceId, label, isStreaming, parts, fileChanges, firstAt }`），时序在同组内保持。
   - 无父项可挂（父消息不在列表 / 已被压缩）时，退化为独立时间线单元——**内容永不丢**。
   - `mergeAssistantParts` 保留给该兜底路径；`mergeFileChanges` 语义不变。

2. **子 Agent 运行块组件化**（`ChatMessage/index.tsx:625-640` 升级）
   - 把现有 `wrapSubAgent` 的裸 `<details>` 升级为「子 Agent 运行块」：`专家名 · 状态 · 工具计数 · 用时`（数据来自 `sourceAgent.label` + P1 的名字解析 + `subAgentRuns` 状态），流式中默认展开、完成后折叠。
   - 内部渲染复用现有 `ActivityFold` + `ToolBatchGroup` + `ThinkingBlock`，**不再把子 parts 混进父的 parts 数组** → 父气泡的「执行过程」只属于父。
   - 视觉上与父气泡明确区分（嵌套边框 + 左侧色条，沿用现有 `sub-agent-wrap` 样式令牌）。

3. **卡片与子运行联动**（`SpawnAgentCard`）
   - `ChatMessage` 透传 `subAgentRuns`，卡片按 `result.instanceId` 命中后：
     - 命中 → 卡片下方渲染该子运行的「过程」区（复用第 2 点的运行块）；卡片状态胶囊改为**以子运行状态为准**（避免卡片说「执行中」而子块已结束）。
     - 未命中（同步执行中，`result` 尚未回来）→ 保持卡片现状（「正在等待这位专家执行…」），子运行块在其下方时间线中实时呈现。
   - 卡片头部增「查看过程」动作：命中时滚动定位并展开对应子运行块（同会话内锚点，不做跨会话跳转）。

4. **同步/异步两种模式的表现一致性**
   - async：卡片立即拿到 `instanceId` → 「已派发」，子运行块在下方**实时**流式。
   - sync：卡片 `running` 期间子运行块实时流式；`result` 回来后卡片转为「已完成」，子运行块折叠。

### 4.4 验收

- [ ] 单测：`ChatContainer` 归组——子消息不再进入父 `parts`；父 `parts` 长度与合并前一致
- [ ] 单测：无父项时子消息仍作为独立单元出现（内容不丢）
- [ ] 单测：子 Agent 运行块的标题/状态/折叠行为（流式展开、完成折叠）
- [ ] 单测：`SpawnAgentCard` 命中 `instanceId` 时渲染子过程；未命中时保持现状
- [ ] 组件测试（防回归）：父气泡「执行过程」摘要**不包含**子 Agent 的工具计数
- [ ] 人工（真实对话）：`spawn_agent async` 委托一位专家 → 会话里只有一条主线索；卡片下方有该专家的运行块且实时更新；父的「执行过程」不再被子内容污染；不再出现并排的两个「执行过程」
- [ ] 人工：`sync` 委托 → 等待期间子运行块实时流式，完成后折叠、卡片转「已完成」
- [ ] 红线：验证前后 `SELECT COUNT(*) FROM messages WHERE is_streaming=1` 必须为 0（见 §七）

### 4.5 已知边界

- **子运行块仍是同一会话的消息**，只是不再混进父气泡；用户仍不能「跳到一个只属于该子 Agent 的会话」——这是非目标（§六）。
- 上下文压缩（compaction）后父消息可能被摘要替换，此时子运行退化为独立单元。
- 多个子 Agent 并发时按 `instanceId` 分组互不干扰；同名专家（如两次委托「灵栖维护」）靠 `instanceId` 区分，卡片与子块一一对应。

## 五、P3 · 中断残留收尾

### 5.1 现状事实

| 事实 | 位置 |
|---|---|
| `finalizeAssistantParts` 只把 streaming thinking/text 置 done，注释明写「running tool 保持不变」 | `packages/agent-runtime/src/storage/assistant-parts.ts:197-208` |
| 卡片判运行中：`part.status === 'running' \|\| part.result === undefined` | `SpawnAgentCard/index.tsx:92` |
| 启动时扫 `is_streaming=1` 写中断标记，随后 `finalizeAllStreamingMessages`（**保留内容**） | `bridge.ts:816-843`、`packages/agent-runtime/src/storage/conversation-repo.ts:377-414` |
| 中断恢复只覆盖**会话主实例**（注入 continuation prompt），不恢复子任务 | `conversation-commands.ts:564-612` |
| `agent:abort` 渲染层不区分子/父，清的是**会话级**流式态 | `event-handler.ts:1232-1245` |

### 5.2 改动点

1. **委托卡片不再永久「执行中」**（P0，纯渲染）
   - `ChatMessage` 向 `SpawnAgentCard` 透传「本条消息是否流式中」。
   - 判据改为 `isRunning = part.status === 'running' && 本条消息仍在流式`；否则按 `result` 判定（有 `result` 走完成/失败，无 `result` 走「已中断」）。
   - 新增「已中断」态文案（区别于「失败」：主动中断不是错误）。

2. **工具 part 中断收尾**（P1，存储层；修的是同一根因的一般情形）
   - `applyAssistantPartEvent` / `finalizeAssistantParts` 增中断分支：把 `running` 的 tool part 收尾为 `interrupted`（`AssistantPart` 的 tool `status` 联合类型扩展 `"interrupted"`），并把未回填的 `result` 置为说明性占位。
   - 调用点：abort / `agent:error` 的收尾路径 + 启动的 `finalizeAllStreamingMessages`。
   - 渲染层同步：`ChatMessage:318-322` 的状态映射增 `interrupted`（不再是 `running` 的转圈）；`ToolCallCard` 一并处理。
   - **风险**：`AssistantPart` 是对外类型（`browser.ts` 导出），消费方需一并核对；旧数据不含该值，向后兼容。

3. **子中止不清父流式态**（P0）
   - `event-handler.ts:1232-1245` 的 `agent:abort` 分支补 `isSubAgentStreamEvent` 判断（与 `turn:start` / `turn:end` / `idle` 保持一致），子 Agent 的中止只收尾子运行块，不重置父会话的 `isStreaming` / `isThinking` / `activeRunId`。

### 5.3 验收

- [ ] 单测：中断（`user:abort`）后，落库的 tool part 不再停在 `running`
- [ ] 单测：`SpawnAgentCard` 对「无 result 且消息不在流式」渲染「已中断」而非「执行中」
- [ ] 单测：子 Agent 的 `agent:abort` 不影响父会话的 `isStreaming` / `isThinking`
- [ ] 人工：发起一个长委托 → 中途点停止 → 卡片显示「已中断」；重启应用后仍是「已中断」
- [ ] 人工：`agent:abort` 后父会话能正常继续发消息（流式态未被卡住）
- [ ] 红线：验证前后 `is_streaming=1` 计数为 0

## 六、明确不做（本计划）

| 项 | 理由 |
|---|---|
| **子 Agent 独立会话 / 跨会话跳转** | 共用父 `conversationId` 是刻意设计（`orchestrator.ts:439` 注释）；另开会话带来列表膨胀与上下文割裂，且 `childSessionKey` 未落库。P2 用「同会话内归属 + 定位」满足可见性需求 |

| `create_execution_plan` / `delegate_to_agent` 死代码清理 | 全仓无工具实现，仅提示词提及；归入既有死代码清理清单 |
| 事件通道按 session 过滤的重构 | 「单通道全量广播 + 渲染层事后路由」是结构性问题（缺 `rootSessionKey` 即兜底到当前会话）；另立项 |
| 用户自建 Agent 的 `agentType` 命名规范 | 涉及 Agent 创建/编辑 UI 与 id 生成规则，超出本计划 |

- **委托卡片不再永久「执行中」**：`SpawnAgentCard` 增 `messageStreaming` prop，判据改为
