## 一、诊断：这两个 Agent 是「通用 Agent + 一段提示词」

本轮开工前的形态对照（`packages/agent-runtime/src/agent/builtin/definitions.ts`）：

| Agent | 专属抓手 | 结论 |
|---|---|---|
| 灵栖开发 `code-dev` | ACP 运行面（外部 CLI 直达） | 真的更强 |
| 灵栖记事 `chronicler` | `work_report_read`（专属取数工具）+ 跨 Agent 读视图 | 真的更强 |
| 灵栖情报 `info-curator` | **只有提示词** | 与「主助手 + web_search」差别不大 |
| 灵栖维护 `system-keeper` | **只有提示词 + 一份手册** | 与「主助手读手册」差别不大 |

差距的实质：**专项能力没有沉淀成工具和数据，只沉淀成了文字**。文字每轮都要靠模型自觉执行，
工具与数据结构则由代码保证。这就是「要更加强、更加高效」的着力点。

三条可验证的佐证：

1. `agent_memories` 里 `system-keeper` / `info-curator` 的记录数是 **0**——它们的读视图是缺省的
   `own`，而它们平时不参与干活，自己名下必然是空的：维护做不了记忆体检，情报看不见用户画像。
2. 资讯卡是**一条无界流水**：本机实测 157 条、单日 +17；`dashboard_feed_meta.summary` 是单行、
   每次抓取覆盖——**上一期的综述被直接抹掉**，这是已经发生的静默数据损失。
3. 情报**没有任何工具能读回自己的产出**，无法知道自己推过什么，每轮都可能重推同一篇稿子。

## 二、本轮交付

### P0-1 归属与可见性（提交 `21c02bea`）

侧栏「默认」tab 按 Agent 分组，定时任务记录在归属非主 Agent 时进对应分组（chronicler 早已如此），
但情报/维护名下一条都没有：

| 问题 | 修法 |
|---|---|
| 概览页「立即抓取」写死 `assistant` + `cron:news-pipeline`，与定时路径不是同一个会话、不是同一个执行者，同一件事在侧栏分裂成两条且都落在「默认」 | 新增 `news-feed-job.ts` 作为资讯管线的定位唯一真相源（判定依据 = 任务指令里是否调用 `dashboard_feed_write`），两条路径统一到同一会话与同一执行者 |
| 用户自建的资讯任务漏网（旧迁移只认预置 id `news-pipeline`） | 迁移 `migrateNewsFeedJobsToInfoCurator`：按「指令里调用资讯卡工具」认领，只动 `agent_id` 仍为 `assistant` 的行 |
| 工作区文件整理仍挂在 `assistant` 名下 | 种子改挂 `system-keeper` + 迁移 `migrateWorkspaceTidyToSystemKeeper` |

**wiki 保洁类任务（`wiki-purge-broken-refs` / `wiki-purge-invalid-files`）有意不迁移**：
它们是 `agent_id = null` 的确定性 companion 通道（不建实例、不建会话、零 LLM 成本）。
把它们做成 LLM 任务是**降级**——花 token 去办一件不需要判断的事。用例 CK-04 守住这条边界。

### P0-2 维护体检报告落库（提交 `e7050764`）

**问题**：巡检产出只是会话里的一段 markdown。用户看不出上次体检是什么时候、发现了什么、
这次还在不在；同一个问题每期都要靠模型记得才不重复报。

**结构**（schema V42，`maintenance_reports`）：

| 字段 | 作用 |
|---|---|
| `summary` | 一句话结论，直接显示在概览页卡片正面 |
| `findings`(JSON) | `[{ key, severity, title, evidence, suggestion }]` |
| `checked`(JSON) | **查过且没问题的项**——只报「发现 3 项」而不说「另外 4 项查过没事」，用户分不清是没查还是真没事 |
| `scope` / `trigger` / `conversation_id` | 覆盖哪类资产、谁触发的、出自哪个会话（可跳回追问） |

**关键设计：`key` 是跨期稳定的问题标识**（如 `memory:duplicate`）。
差分的身份用 key 而不是 title——title 是给用户看的措辞、模型每期都会改写，
拿它做身份会让「上期有、这期没了」永远判不出来。有了它，「已解决」由两期数据**直接算出**，
不需要用户手工标记，也不会因为用户忘记标记而反复提醒同一件事。

**工具**：`maintenance_report_write` / `maintenance_report_read`（packages 定义 + apps/windows 落库）。
`agentId` 与 `conversationId` 由当前执行实例反查、`trigger` 按会话前缀判定，不采信模型自填。

**可读**：概览页新增「资产体检」卡——结论 / 发现（严重度 + 依据 + 建议）/ 已查无问题三段，
顶部显示与上一期的差分（新增 / 仍在 / 已解决）；点某条发现跳对话页并预填追问。

**真机验证（CK-08）**：让「灵栖维护」跑一次记忆体检，报告落库 `scope=memory`、发现 5 项。
报告质量经人工核对为真：读到偏好层实测 1668/2400 字符预算、扫了 211 条跨 Agent 工作记忆，
5 项发现各带条目 id 与依据（JSON 序列化残迹、指令式话术残留、近似重复、层级错放、取代链分散），
另列 6 项「已查无问题」。

### P0-3 资讯卡片期刊化（本次提交）

**问题**：卡片是一条无界流水——所有批次平铺在 `dashboard_feed_items` 里靠时间戳排序，
用户分不清「今天推了什么」；综述只有一行、每期覆盖。

**结构**（schema V43）：

```
dashboard_feed_batches   期：id / feed_id / summary / source / conversation_id / created_at
dashboard_feed_items     + batch_id
```

- **每次写入 = 一期**：本期综述记在期上，不再覆盖上一期；
- `batch_id` **只在首次入库时落定**（与 `timestamp` 同理）：同一篇文章再次被抓到时仍属最初那一期；
- 本批条目全是别期已有的（重复抓取）→ **删掉这个空期**，不留噪音；
- 回填：既有条目按自然日合成 `legacy:` 期。这是近似（`created_at` 是 UTC 串，与本地日可能错位几小时），
  历史只求能读，从建表起每一期才是精确边界。

**渲染**：默认只展开最新一期，更早的按期折叠（期头显示时间 / 来源 / 条数 / 综述）。
期的时间标签用「今天 14:00」而不是「3 小时前」——后者看不出「今天推了几期」。

**排序的坑（两处，都是实测撞出来的）**：`created_at` 只有毫秒精度，同一毫秒写入的两期会撞在一起。
- 维护报告列表：平局原本用 `id` 兜底，而 id 是**随机 UUID** → 等于随机排序。改用 `rowid`（插入序）。
- 期 id：分页游标是 `(created_at, id)`，随机 id 会让**翻页随机**。改为带进程内自增序号
  （补零后字典序 = 数值序）。

**真机验证**：真机跑一轮资讯任务 → 落成 `source=agent`、`conversation_id=cron:local-cron-…`、
19 条、153 字综述的一期；概览页期头渲染为 `▾今天 11:46 情报推送 19 条 最新`。

## 四、登记备查（不在本轮范围）

| 发现 | 依据 | 为什么不动 |
|---|---|---|
| **流式落库的 assistant 消息不带 `agent_id`** | 全库 403 条 `role='assistant'` 消息 `agent_id IS NULL`（走流式路径的）；cron 兜底 `saveMessage` 路径的 244 条带 `assistant` | 归属的正确载体是会话参与者（侧栏据此分组，已通）与期上的 `source`；消息级归属要动所有会话的流式保存路径，风险与收益不成比例。CK-07 因此改为断言期的出处而非消息的 agent_id |
| wiki 保洁任务仍是 companion 通道 | `local_cron_jobs.agent_id IS NULL`，`runLocalCronJob` 在 companion 分支直接 return | 见 P0-1 表下说明：它们是确定性动作，改成 LLM 任务是降级。CK-04 守边界 |
| 情报卡无「已读 / 收藏」 | 渲染层与 service 内无相关命中 | 属用户状态，期刊化之后再谈才有意义（先有「期」才有「这期读没读」） |
| 情报管线并发无互斥 | 定时与手动同时触发会叠加两次 Agent 运行 | 现状影响是重复抓取（有去重兜底），优先级低于本轮两项 |
