# 05 · 队长制：主助手接团队

> 创建：2026-09-13
> 前置：[专项 Agent 设计（一等公民）](../../design/专项AGENT/专项Agent设计.md)（v3.1 §2.5 团队蓝图 / §8 会话接续）
> 讨论拍板（2026-09-13）：目标画面 = **队长制**；起步线 = 主助手接团队。D1 分工（开发→转交，维护/情报/记事→委托）；D2 委托直接做、转交先确认；D3 一键转交（桌面按钮 / 渠道文本确认，确认后直接发起 CLI run 新开或续接历史会话）；D4 产出回流（委托天然回流，转交产出回原处：桌面→开发会话事件流，渠道→微信回执链）；D5 新开/续接由**主助手自动判断**。
> 原则：小步快跑——每片独立验证；完成一片结算一片。
> **2026-09-15 修订**：D2/D3 的「转交先确认」作废——转交改为**提案即执行**（详见 §七末条）。
> 状态：**F1 / F2 / F3 完成**；转交自动执行 + 渠道结果出站已代码完成，待人工验收。

---

## 一、背景：为什么做这条线

讨论诊断出 5 个「没串起来」的断点：① 主助手不认识团队（协作清单只注入用户自建 Agent）；② 灵栖开发有机制没入口（Agent 绑定无 UI）；③ 成员间传不了话（send_message 只 followUp，空闲不出队）；④ 知识储备不均；⑤ 产出互喂为零。

本计划解决 ①（并部分消解 ④ 的协作面）：让主助手认识四位成员、按分工委托 pi 型成员执行、开发类走转交。②在同一计划的后续片补入口。③⑤留待下一轮「协作通路」。

## 四、F2 / F3 概要（开工前细化）

### F2 · 桌面一键转交

- **转交工具**（主助手可调，名字实现时定）：入参 = 任务背景包 + 会话选择意图（新开/续接，主助手判断）+ 项目（缺省走绑定/全局）；主进程解析开发上下文（三级链）→ 新建或选中 code-dev 会话 → `startRun`（带 cwd / backend / 续接）。
- **确认按钮**：主助手回复上的「交给灵栖开发」动作；点击=确认发起（不是跳会话手发）。
- **入库清单**：`code-dev` 进入协作清单（与三位不同：标注「会话型，用转交流程」）。
- 待细化：`startRun` 复用形态（`user-commands.ts` 调用点封装）、按钮的消息协议与渲染、背景包格式（沿用 §8 五字段：originUserRequest / confirmedNeed / constraints / artifacts / doneDefinition）。

### F3 · 渠道一键转交

- 主助手发确认请求（「将交给灵栖开发在项目 X 执行：<一句话>，回复 1 确认」）→ pending 注册 → 用户回复「1」时在渠道消息入口拦截并触发。
- 执行复用渠道 ACP 直调路径（带 dev-context 项目 + peer 级 backend）+ 现有微信回执链（ACK / 🔧 工具名 / 完成原文）。
- 待细化：pending 注册表的位置与过期策略、微信消息处理链路的拦截点、与 `/project`·`/claude` 现有命令的优先级关系。

**验证**
- 单测：`agent-collaboration-section.test.ts` 5 例；agent-runtime 全量 **1863 例绿**；两包 typecheck 干净（apps/windows 仅存量 2 错，非本次引入）；

**实测校准（重要，供 F2/F3 参考）**
1. 注入生效三证据：主助手能原样列出三位专家 / 日志 `[createInstance] Loaded 3 custom agents` / thinking 明确引用职责范围（"记忆整理属于灵栖维护的职责"）；
2. **模型委托行为存在随机性**（Qwen3.8-Flash-Next）：同一句请求曾出现 ①thinking 已决定委托但未发出工具调用（thinking 截断后空转、`end_turn`）②自己调记忆工具干活 ③委托成功三类结果——强化提示词 + 真实文案后首次即命中；若后续再现①类空转，属模型/平台侧问题（空回合无重试）；
3. **测试性约束措辞会削弱委托动机**（「先给个方案、不要直接改」让模型倾向自己先看）——场景用例坚持真实口吻，数据安全靠测试侧护栏（快照 + 探针清理），不在任务文案里加保险；
4. 主助手委托时会把约束**自行传递**给专家（"绝对不许修改——硬性约束"），专家方案落 workspace `outputs/`（测试保留、报告注明）；
5. 环境注意：多会话并行时的应用重启会打断长回合；`waitTurnDone` 以 `is_streaming=0` 为准 + 重试兜底。

**待办**：全量 15 例重跑（选环境安静窗口）；F2 桌面一键转交。

### F2 · 桌面一键转交（2026-09-13 完成）

**代码**
- 主进程：`handoff-store.ts`（提案存储，一次性消费 + 上限淘汰）→ `bridge-tool-registrar-handoff.ts`（`propose_dev_handoff` 工具）→ `handoff-commands.ts`（`handoff:confirm`：recent/new 会话选择 → 复用 `handleUserSend` 发起，天然获得 devContext 解析与 ACP/pi 分流）+ 命令类型/分发/白名单接线；
- 提示词：code-dev 以转交型进入协作清单（描述注明 handoff 工具、勿 spawn）+ section handoff 规则（工具存在时条件渲染）+ personality 兼容措辞；**转交边界 = 绑定项目里的开发任务，小片段/随手改文件由主助手自己干（用户反馈：不能大炮打蚊子）**；
- 渲染层：`HandoffCard` 组件（ready→confirming→done/failed；「交给灵栖开发」→ 成功后「去会话查看」）+ ChatMessage 分流（handoff 独立渲染单元）+ **折叠区修复：handoff 永不进折叠** + `ChatMessageActions` 扩展（confirmHandoff/openSession，走 ref 保持稳定性契约）。

**验证**
- 单测：handoff-store 2 例 + HandoffCard 4 例 + ChatMessage.parts 4 例（含「卡片露在折叠区外」防回归）；两包 typecheck 干净；
- 端到端实测（真实场景「把沙箱项目的分页 bug 修掉」）：主助手识别 → 提案（背景包含问题定位 + 验证清单）→ confirm → 新开发会话 → **`ACP 路径: backendId=claude source=binding cwd=沙箱`** → claude 完成修复并附验证证据 ✔；**UI 真实点击**验证 ✔（卡片渲染 → 点击 → 卡片变「去会话查看」）；
- 套件：`AT-F2` 注册并 PASS（提案硬断言 + 已转交日志硬断言 + binding 直达硬断言 + 沙箱修复硬断言；UI 点击 soft 降级，链路不可用时走 CLI confirm）。

**实测校准**
1. **单实例锁坑复现**：该环境下 `pnpm dev:restart` 可能被未死透的旧进程顶掉（「app ready in 5s」是假象）——用进程启动时间验证，必要时 `stop-dev.ps1 -KillAllElectron` 清干净再起（本次曾因此误判「工具没注册」，实际是旧 bundle 在跑）；
2. **折叠区 bug**：propose 之后模型还会有一段 thinking，「最后一个 thinking 划过程区」的规则会把卡片折进 ActivityFold（收起时不渲染 children）→ 用户看不到按钮；修复 = handoff 单元强制拣出折叠外，并加防回归测试；
3. 主助手会先自行定位问题、把定位写进背景包，并对 API 语义（1-based 页码、越界返回 `[]`）主动对齐后再提案——提案质量高；
4. 「先给方案/只检查」类措辞同样削弱转交动机（与 F1 观察一致）。

**遗留**：全量 16 例重跑（环境安静窗口）；F3 渠道一键转交。

### F3 · 渠道一键转交（2026-09-13 代码完成，真实微信验收待跑）

> **2026-09-15 更新：本节描述的渠道确认链路已删除**（见 [10-渠道会话路由重构](./10-渠道会话路由重构.md) §八 S6）。
> 转交自 2026-09-15 起改为**提案即执行**：`propose_dev_handoff` 生成提案后立刻消费，
> 渠道侧的「回复 1 确认」永远等不到 pending 提案，属不可达代码。下方记录保留作实现沿革。

**代码**
- `handoff-store` 扩展：`findLatestHandoffFor(sessionKey, withinMs)`（渠道按会话定位提案）+ `isHandoffConfirmText`（保守确认词：1 / 确认 / ok / y / yes）；
- `propose_dev_handoff` 渠道文案：检测微信上下文（`weixinCtx`）→ 引导「回复 1 确认」（桌面仍是点卡片）；即使文案退化，拦截逻辑不依赖文案（按 pending 命中）；
- 微信 adapter：`handleMessage` 普通处理前拦截确认回复（`tryConsumeHandoffConfirm`）→ 消费提案 → 按开发上下文解析（**以 code-dev 名义**，命中与桌面 F2 同一套 Agent 绑定）→ 复用 `handleAcpPrompt` 直达 CLI（完整回执链：🔧 工具进度 / 完成原文 / 超时与失败提示）；未绑定项目/工具 → 明确提示引导到桌面配置，不在微信硬跑。

**验证**
- 单测：handoff-store 4 例（含按会话查找 / 时间窗 / 确认词边界）；apps/windows typecheck 干净；
- **QQ 渠道实测（2026-09-13 晚，用户执行）**：实测发现「转交在渠道原会话里直接执行」→ 驱动「执行与汇报分离」模型修正（见下）；修正后桌面端到端全通；**QQ 复核待用户完成**（发任务 → 回复 1 → 开发会话执行 → 异步汇报回 QQ）。

**设计要点**
- 拦截位置：斜杠命令与普通消息处理之前；确认即消费（成败都消费，防陈旧提案循环触发）；TTL 10 分钟；
- 会话选择（D5）：渠道沿用同 peer 的 CLI 续接（`acp-session` 键）自然获得上下文，不需要 new/recent 二选一；
- 产出回流：渠道转交的产出走渠道回执链回到微信（与 F2 桌面「产出回开发会话」对应）。

**模型修正（2026-09-13，用户反馈驱动）——执行空间与汇报通道分离**
- 问题：初版在「原会话」里直接执行开发任务（桌面在会话里跑、渠道在 peer 会话跑），原会话被工具过程刷屏且结果不成体系；用户明确：**执行必须在「灵栖开发」分组下的开发会话（新建或复用历史）完成，完成后把结果异步汇报回原会话**（桌面与渠道一致）。

### 转交自动执行 + 渠道结果出站（2026-09-15，代码完成，待人工验收）

**触发（用户反馈，两轮）**

1. 「客户端的转交改为自动审批，不需要用户手动点击」——卡片确认成了转交的必经关卡；
2. 「通过消息渠道比如 QQ，完成任务转交和汇报后，没有将对应的结果发送到对应的消息渠道，对于用户来说没有响应」。

**改动**

- **提案即执行**（`56d04f07`）：`propose_dev_handoff` 生成提案后**直接在主进程发起**（`runHandoffFromProposal` → `runDevHandoff`），不再等卡片点击；卡片从「待确认」变为状态展示（`已交给灵栖开发 · <标题>` + 去会话查看）。放主进程而非「渲染层自动点击」的原因：后者依赖卡片被渲染，用户切走会话就永远不会触发。发起后立即 `consumeHandoff`——否则渠道侧 10 分钟内的「回复 1」会再触发一次（重复执行）。
- **渠道结果出站**（本次）：`reportToOriginSession` 新增渠道出口——`bridge.pushChannelText` → `ChannelInteractionHub.pushText(sessionKey, text)` → `adapter.sendTextReply`，把完成/失败汇报发到该会话所在的渠道。此前只落库 + 转发渲染层 IPC，渠道用户看不到开发会话、也收不到桌面通知，等于**完全没有响应**。
  - 之所以要经 Hub：回复上下文（QQ 的 chatId、微信的一次性 contextToken）只有 Hub 的 `routes` 持有，且由每轮入站消息刷新（`trackSession`）。应用重启或该会话久未收消息时无路由 → 返回 false，只记日志。
  - **不做成二选一分支**：adapter 的 `sendTextReply` 失败时只记 error 日志、不抛错，把返回值当「已送达」会变成静默失败——两条出口并存，桌面行为与改动前一致。
- **提示词同步**（本次）：`agent-collaboration-section.ts` 的两档转交规则此前仍是「仅 fixes/features」+「用户需在卡片确认（渠道回复 1）」，与实际行为矛盾（detailed 正是默认档；P2 当时只改了工具描述）。改为「项目级工作（开发 / 项目内分析、评审、调研）+ **立即执行、无需确认**」。
- **CLI prompt 传递修复**（`9dcd82b5`，本链路的根因）：claude 是 npm `.cmd` shim → cmd 命令行放不下含换行符的长 prompt → 排在 prompt 之后的 `--output-format stream-json` 被一起吃掉 → Claude Code 退回纯文本输出 → JSONL 解析器逐行丢弃 → 开发会话只剩「（Claude Code 无输出）」，但任务实际已完成。改为 **prompt 走 stdin**（真实 CLI 实测多行完整送达 + stream-json 正常）；cursor 同为 `.cmd`，prompt 移到 argv 末位。
