## 二、当前演进（v3+ · 异步化与分级传输）

> **已实施**（2026-09-17）。**数据层不变**，改的是架构层：超时语义修正、传输按 1MB 阈值分级（大文件走独立后台队列，50MB/批）、Agent 工具秒回 + 按需推送。
>
> **实测结果（2026-09-17）**：阶段一 **18 秒**完成（此前动辄数分钟，812 个未变更文件靠 mtime 短路跳过）；阶段二分批推进且**不再重复传同一文件**；排除了一个只有真实文件系统才暴露的 mtime 精度死循环（见实施计划的「实测发现并修复」）。

**问题背景**：同步仓库已达 993 文件 / 工作区 500 MB / `.git` 966 MB；冲突落决的墙钟 300s 超时小于实际所需，超时后后台继续跑但 Agent 收到"失败"→ 每 10 分钟一轮的无限重试（2026-09-17 上午实录）。

**⚠️ 前置事故（2026-09-16 22:09）**：远端被**第二台设备**从 918 个文件删到 22 个（`9fbeaf4`）。原因是镜像删除安全阀的"二次确认"在自动化流程中失效——第一次挡下后置位 `massDeleteConfirmed`，1 分钟后的下一次同步即自动放行。**本地 993 个文件是唯一完整副本；在 Phase 0「数据抢救」完成前，所有设备必须保持云同步关闭**，因为当前任何一次落决成功都会让本地 863 个文件被删除。远端剩余 130 个文件中有 42 个是本地没有的，恢复时不可丢弃。详见[设计 §2.5](../../design/数据同步功能/2026-09-17-云同步异步化与分级传输设计.md)。

**重要教训（v2 反思结论，v3 亦沿用）**：Git Squash 在多设备场景是毁灭性的——squash 丢弃原 commit ID，两设备各自 squash 后互相 non-ff，再 force push 会令对方全量冲突。**同步层由此硬拦截 `--squash` 与 `--force`。**

## 六、同步范围（用户需求基线）

**同步**：Wiki 知识库 · 记忆数据（`agent_memories`）· 用户配置（`soul.md`、`user-memory.md`）· 自主进化数据（goals、diaries）· 用户自定义技能 · **workspace 产出（`files/`、`outputs/`，含视频/图片/文档，2026-09-17 确认全量同步）**

**不同步**：聊天记录与历史对话 · 工具结果缓存 · 临时文件

理由：对话历史体积大且隐私敏感，Agent 记忆已提取其中的关键信息。

## 八、设计决策速查

| 决策 | 理由 |
| --- | --- |
| 不同步对话历史 | 用户明确要求；体积可能 GB 级；隐私敏感；记忆已提取关键信息 |
| 用 JSONL 而非 SQL dump | 可读、易调试、Git 友好（可 diff）、支持增量追加 |
| 独立 CLI 工具 | 不依赖应用运行，便于测试与自动化 |
| 快照体积 | DB 数据 2.86 MB（v3 优化，自 615 MB）；**含 workspace 产出后 sync 工作区 500 MB**（2026-09-17 实测） |
| 分级传输阈值 1 MB | 68% 的文件只占 1.6% 体积——阶段一 71 MB 即可覆盖 83% 的文件 |
| 放弃 git 历史重写 | pack 504 MB ≈ 工作区 500 MB，历史大文件已被 delta 压缩至几乎不占空间，重写收益不抵 force push 代价 |
