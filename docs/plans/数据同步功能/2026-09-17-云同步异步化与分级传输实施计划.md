# 云同步异步化与分级传输实施计划

- 日期：2026-09-17
- 状态：已确认，待实施

- 前序：[`2026-09-09-云同步V3实施计划.md`](./2026-09-09-云同步V3实施计划.md)（本计划不改其数据层）

## 1. Goal

让云同步在 993 文件 / 500 MB / `.git` 966 MB 的规模下，**不再产生超时重试死循环**，且 Agent 能以异步方式主动管理同步（提交 / 推送 / 拉取 / 按需传输指定文件）。

**可验证判据**：设计文档 §8 的六条验证标准全部通过，`pnpm --filter ./apps/windows test:all` 全绿。

## 2. Architecture

```
┌─────────────────────────────────────────────────────────┐
│ Agent 侧（bridge-tool-registrar-sync.ts）                │
│   cloud_sync_git(只读诊断)  cloud_sync_push/now/scope    │
│         │                        │                       │
│         │ 只读，不排队            │ 秒回 {jobId, phase}   │
│         ▼                        ▼                       │
│   ┌──────────────────────────────────────┐              │
│   │  任务回填（复用 spawn_agent async）   │              │
│   └──────────────────────────────────────┘              │
└─────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────────┐
│ CloudSyncManager（sync-manager.ts）                      │
│   enqueueWorkspace 串行队列（per-workspace）              │
│   ┌─────────────┐  ┌──────────────┐  ┌───────────────┐  │
│   │ 阶段一 sync  │  │ 阶段二队列    │  │ 冲突落决       │  │
│   │ ≤1MB,完整流  │  │ >1MB,50MB/批 │  │ resolveInner  │  │
│   │ 程,完成即 idle│ │ 批次间让路    │  │               │  │
│   └─────────────┘  └──────────────┘  └───────────────┘  │
│         └──────── ProgressFence 双预算续期 ────────┘      │
│                  idle 120s + ceiling（按操作类型）        │
└─────────────────────────────────────────────────────────┘
                          │
          isomorphic-git（纯 JS，无 CLI 进程）
```

**模块边界**：
- 一切 git 写操作必须走 `enqueueWorkspace` 串行队列；只读诊断（`gitStatus`/`gitLog`/`gitRemote`）**刻意不排队**，避免排到在跑的任务后面（现有设计，保持）
- 分级只影响"传什么"，不影响 v3 的导出/合并数据流
- 续期机制只影响"等多久"，不改任务本身的可取消性（队列任务不可取消，续期语义是放宽等待方）

## 3. Tech Stack

**不引入任何新依赖**：
- 不引入 `simple-git` / `nodegit`（继续用 `isomorphic-git`）
- 不引入 git-lfs
- 不引入 `git-filter-repo`（该工具依赖 Python，本机无 Python）
- 滑动续期复用同仓 `packages/agent-runtime/src/compact/progress-fence.ts`（已实现并验证）
- 异步回填复用 `spawn_agent` 的既有完成队列机制

## 4. Global Constraints

1. **不改 v3 数据层**：`sync-exporter.ts` / `sync-importer.ts` 的 JSONL 格式、`deleted_at` 软删除、时间戳合并规则不动
2. **不破坏生成物冲突分流**：`wiki/` `memory/` `autonomous/` 前缀的冲突仍自动取远端、不进 Agent（`sync-manager.ts:535-551`）
3. **镜像删除安全阀语义不变**：跳过 ≠ 删除；源目录缺失 ≠ 删除信号
4. **同步范围不扩大**：不含对话历史、工具结果缓存、临时文件
5. **测试不写进用户 workspace**（历史教训）
6. **改过 `src/main/**` 必须跑 `apps/windows` 全量** `test:all`，默认 `test` 只覆盖 `src/test/`（全绿是假象）
7. **TDD**：算法模块（批次切分、阈值判定、排除集匹配）与核心编排模块（分级流程、队列）先写失败测试再实现；模块级覆盖率 ≥ 80%
8. **token 不回显**：日志脱敏沿用 `sync-manager.ts:1190` 的 `split(token).join('***')`
9. **Phase 0 完成前，所有设备保持云同步关闭** —— 当前任何一次落决成功都会删除本地 863 个文件（设计 §2.5）

### Phase 1：止血 —— 停掉正在发生的死循环

**T1.1 重入守卫** ✅ 已完成（2026-09-17 12:05）—— **实际驱动源是进化心跳，不是调度器**

排查推翻了原假设：`SyncScheduler` 的 tick 间隔是 15–30 分钟，与实测的"每 10 分钟一轮"不符。真正的驱动链是：

```
local_cron_jobs['autonomous-tick']（默认每 10 分钟）
  → handleEvolutionTick()（evolution-tick.ts）
  → driveConflictGoal() → bridge.executeSyncConflictGoal()
```

而该调用**位于 `isAutonomousEnabled()` 检查之前**（代码注释明确写"独立于自主进化开关与能量/预算门闩"）—— 即无条件每 10 分钟驱动一轮冲突处理。落决外层超时 5 分钟、队列任务不可取消 → **数学上必然重入**。

改动：

- `sync-manager.ts`：新增 `resolveInFlight` 标志与 `isResolveInFlight()`（含 30 分钟失效保护，防止守卫自身变成永久死锁）；`resolveConflict` 在飞行中直接拒绝新请求
- `bridge.ts`：`executeSyncConflictGoal()` 在创建/驱动 Agent 前先查 `isResolveInFlight()`，命中则返回 `skipped: resolve-in-flight`
- 验证：新增测试覆盖「飞行中拒绝重复请求 → 落决结束后复位」

**T1.2 `cloud_sync_read_file` 读 remote 失败** ✅ 已定位（**非 bug**）+ 消息改进

定位结论：那 4 个文件是 **modify/delete 冲突**（远端删除、本地修改），`readFileAt('remote', …)` 返回 null 是**正确行为**。问题在于原错误消息只说「无冲突或文件不存在」，Agent 无法区分"路径写错"与"该侧已删除"，每轮都要多绕数圈才敢下结论。

改动（`bridge-tool-registrar-sync.ts`）：按文件是否在当前冲突列表中分流错误消息；确认是冲突文件时明确告知「这是删除/修改型冲突：该侧删除了它，另一侧修改了它 —— 选该侧即接受删除，选另一侧即保留修改」。

**T1.3 查明卡住的提交** ✅ 已完成（2026-09-17 11:30，恢复操作中顺带解决）

该提交为落决残留；恢复合并（`fc3baa0`）后本地与远端 tip 已对齐。

**退出标准**：死循环根因消除 ✅（守卫就位；实际日志验证需重新启用同步后进行）；三方读取语义明确 ✅；tip 对齐 ✅。

### Phase 3：超时语义修正（原「滑动续期」，实施中收窄范围）

> **范围调整（2026-09-17）**：原计划的 ProgressFence 注入经评估后**推迟到 Phase 4**。理由：实测确认 `syncInner` 内部每个耗时步骤（fetch 300s / push 600s / gc 600s）**各自都有超时**，只要 idle 预算大于最长单步就不会误杀 —— 再包一层 fence 边际价值很低。真正需要续期的是 Phase 4 的阶段二队列（长时间连续传输、批次之间没有天然超时点），届时一并引入。

**T3.3 `isPushTimeout` 类型化** ✅ 已完成

- 新增 `TimeoutError`（通用墙钟超时）与 `PushTimeoutError extends TimeoutError`（push 专用）；`withTimeout` 接受 `string | Error`
- `isPushTimeout` 由 `err.message.includes('git push 超时')` 改为 `instanceof PushTimeoutError` —— 字符串匹配一旦措辞变动就静默失效，而这条分支决定「是否复核远端」，失效后果是**远端已接受推送却被当成普通失败处理**
- **测试当场暴露了这个问题**：原有测试正是用裸 `Error('git push 超时…')` 模拟的，类型化后立即失败 —— 恰好证明字符串匹配有多脆弱
- `PushTimeoutError` 已导出，供测试构造同类型错误

**T3.4 超时语义修正** ✅ 已完成

- `resolveConflict` 返回值新增 `stillRunning`：超时（`TimeoutError`）为 true，业务失败为 false
- Agent 工具据此返回 `status: 'running'` 且 **`isError: false`** —— 超时不再被报成失败，Agent 不会因此重新决策、再排一轮落决
- 提示语明确：「落决仍在后台执行（超时只中止了本次等待，任务没死）。**不要重复调用本工具**，等一会儿用 `cloud_sync_git` 核实后台结果即可」

**附带：push 超时预算修正**

- `PUSH_TIMEOUT_MS` 120s → **600s**；`RESOLVE_PUSH_TIMEOUT_MS` 240s → **600s**
- 依据：落决路径实测 240s 仍超时（落决 commit 含 `applyRemoteNonConflictingChanges` 带来的大量变更对象）；超时只中止**等待**，push 本身仍在跑，宁可给足时间也不要误判失败
- `RESOLVE_TIMEOUT_MS`（300s，Agent 工具等待上限）保持不变，并在注释中明确它与内部 push 超时**不必构成嵌套** —— 超时后由 T1.1 的 `isResolveInFlight` 守卫防止重入

**T3.1/T3.2 ProgressFence 注入** ⏳ **推迟到 Phase 4**（理由见上方范围调整）

**退出标准**：慢而正常的操作不被误杀 ✅；超时不再被报成失败 ✅。

### Phase 4：分级传输

**T4.1 配置项** ✅ 已完成（2026-09-17 12:20）

- `types.ts`：`CloudSyncConfig` 新增 `smallFileThresholdBytes`（分级阈值）与 `largeFileBatchBytes`（阶段二批次上限）
- `sync-config.ts`：默认值分别为 `SYNC_OUTPUTS_MAX_BYTES`（5 MB）与 50 MB
- **顺序约束（关键）**：默认值**暂等于旧的硬上限**。阶段二队列（T4.4）实现前把阈值调小，会让 1–5 MB 的文件从「同步」退化为「无人接手的不同步」—— 队列就绪后再改为 1 MB
- `saveConfigFromView` **显式沿用现值**：View 不含这两个字段，不特殊处理的话每次保存配置都会把它们覆写回 undefined（已加测试锁定）

**T4.3 阶段一阈值接线** ✅ 已完成（2026-09-17 12:20）

- `sync-exporter.ts`：`SyncExportOptions` 新增 `outputsMaxBytes`，`exportUserFiles` 用它替代硬编码的 `SYNC_OUTPUTS_MAX_BYTES`
- `sync-manager.ts`：`exportAndCommit` 与 `mergeUnrelatedHistory` 两处构造 exporter 时均传 `loadCloudSyncConfig().smallFileThresholdBytes`
- **本步行为零变化**：默认阈值 = 旧硬上限，所以这是一次纯接线 —— "阶段一读配置"的能力已就位，拨到 1 MB 的动作留给 T4.4 完成后
- 测试：新增 2 例（默认阈值正确；`saveConfigFromView` 保留阈值不被覆写）
- 验证：`typecheck` ✅；`test:all` 270 文件 / **2430 测试全绿**

**T4.2 修 `stageAllChanges` 误删缺陷（前置条件）** ✅ 已完成（2026-09-17 12:16）

分级传输的死穴：阶段一导出按 1MB 阈值跳过大文件 → 它们不在工作区、却存在于 HEAD（阶段二提交过）→ `statusMatrix` 判定 `HEAD 有 + 工作区无 = 删除` → **每跑一次阶段一就删掉阶段二刚提交的大文件**。

改动（三层串起）：

- `sync-copy.ts`：`CopySyncDirectoryResult` 新增 `skippedLargePaths`（跳过大文件的绝对路径，此前只有计数）
- `sync-exporter.ts`：`exportUserFiles` 收集这些路径并转为**仓库相对路径**（`workspace/outputs/xxx`），经 `SyncExportResult.skippedLargePaths` 暴露
- `sync-manager.ts`：新增纯函数 `computeStagePlan(status, isExcluded)` —— 排除集内的路径不参与 `hasChanges` 判定、不产生 `removals`；`stageAllChanges(p, excludeFromRemoval?)` 接受排除集；两个调用点（`exportAndCommit` / `mergeUnrelatedHistory`）均传入

测试：新增 4 例（HEAD 有+工作区无 → 判删除；排除集内的不判删除；排除集只豁免被排除项、其他删除照常；内容变化不计 remove）。

**T4.4 阶段二队列（新增模块）** ✅ 已完成（2026-09-17 12:30）

新文件 `sync-large-queue.ts`，四个设计约束：

1. **不落盘**：待传集合每次从「工作区 vs sync 目录」的 **size+mtime 差异**重建 —— 与 `copySyncDirectory` 的 `skipUnchanged` 完全同一套判据。重启不丢、重复调用不重传
2. **批次间让路**：每批都是**独立的 `enqueueWorkspace` 任务**，批次之间还插了 5 秒喘息 —— 高优先级同步可随时插入。批次开始前也检查一次 `state`，非 idle 则结束本轮（`yielded: true`）
3. **续期**：整轮 pump 用 `ProgressFence` 的 **ceiling（30 分钟）** 封顶 —— 批次之间没有天然超时点，靠它防无限跑。idle 预算设为极大（大文件传输天然"每批都有进展但整体很慢"，idle 在此无意义）。**Phase 3 推迟的 fence 在这里落地**
4. **不动 stage 判定**：批次用精确的 `git.add({filepath})`，绝不走 `stageAllChanges` 的 `add '.'` —— 否则会把阶段一尚未提交的变化卷进大文件提交，两个阶段的边界就没了

- 触发点：`sync()` 在阶段一完成且 idle 时调用 `kickLargeQueue()`（**不 await**，后台传）
- 目录用 getter 现取，用户切换工作空间无需重建实例
- 测试：12 例覆盖两个纯函数（`scanPendingLargeFiles` / `splitIntoBatches`）—— 它们是唯一有正确性风险的部分（**扫漏 = 大文件永远传不上去；扫多 = 重复上传数百 MB**），含 size 变化 / mtime 变化 / 跳过重目录 / 源目录缺失 / 单文件超批次独占一批 / 边界恰好等于上限

#### 实测发现并修复：阶段二 mtime 死循环（2026-09-17 13:15）

首次真实运行阶段二时，队列连跑 **131 批**、每批都是同一个 32.5MB 文件，`>1MB 已同步` 只从 160 涨到 161，本地 tip 始终追不上远端。

**根因：mtime 精度失真。**

```
源文件 mtime（NTFS 100ns）: 1789142563487.7825   ← 带亚毫秒小数
utimesSync 回写后读回:       1789142563488        ← 被舍入到整数 ms
严格相等比较 ===            → 永远 false          → 刚复制完的文件下轮又判"待传"
```

**为什么单元测试没抓到**：测试里的 mtime 是测试代码写入的**整数毫秒**，恰好掩盖了精度问题 —— 只有真实文件系统才暴露。

**修复**：新增 `SYNC_MTIME_TOLERANCE_MS = 2`，比对改为 `Math.abs(dst.mtimeMs - src.mtimeMs) <= 容差`，覆盖 `isSameStat`（sync-copy）与 `scanPendingLargeFiles`（large-queue）两处。2ms 足以覆盖 utimesSync 的舍入（也覆盖 FAT 的秒级精度差异），又远小于任何人手改文件的间隔 —— 不会漏检真实变更。

**回归测试**：两处各加一例（构造带亚毫秒小数的 mtime），均已验证「修复前必失败」；另用 mtime 探针独立确认源文件读回确实带小数。

**副作用**：远端历史留下 ~131 个 `sync: 大文件批次（1 个文件）` 的 commit —— 内容完全相同，git 不产生新对象，**体积无影响**，仅是历史噪音。

#### 修复验证结果（2026-09-17 13:28）✅

重启后运行修复版，两次 pump 的 commit 内容对比给出决定性证据：

| pump | 提交 | 内容 | 大小 |
| --- | --- | --- | --- |
| 第 1 次 | `80a0774` | 新-星星视频-V1.mp4 + 教学课程-…-微信档.mp4 | 43 MB（2 个文件） |
| 第 2 次 | `b5ecb3ea` | 教学课程-AI绘本制作全过程-高清.mp4 | 29 MB（1 个文件） |

**两次传的是不同文件** → 修复生效（旧行为是 133 批全传同一个文件）。

同时验证了**批次切分**：20+22 MB 合成一批（逼近但不超 50 MB 上限），下一个 29 MB 因累加会超限而单独成批。

**阶段一实测**：**9 秒**完成（此前动辄数分钟），其中导出耗时 219ms —— mtime 短路让 812 个未变更文件不再重拷。

#### 新发现：GitCode 推送限流 ⚠️

死循环期间连续推送 133 个 commit 后，阶段二的 push 开始返回 `Request timed out` —— **9 秒即超时，远早于我们设的 600s 预算**，说明来自 isomorphic-git 的 HTTP 层或服务端限流。

表现为：每轮 pump 推进一批后因 push 失败退出，**收敛速度受网络限制**。

- 已复制的文件不会被重传（mtime 已回写），未推送的 commit 在网络恢复后一次性推上
- **需要留意**：若超时持续，会出现「本地已传完但远端落后」的状态，而此时设置页仍显示「同步完成」
- 后续可考虑：push 失败的重试退避；UI 区分「已提交未推送」；或把 `Request timed out` 也纳入类型化错误（现在是通用 Error）

### Phase 5：Agent 工具异步化（收窄版）

> **范围调整（2026-09-17）**：原计划的「jobId + 回填」经调研后**大幅收窄** —— 回填机制既不适用也不必要。
>
> - **不适用**：`handleAsyncSubagentComplete` 要求父 Agent 实例活着（`agentRegistry.get(parentId)` + 等父 idle 再 drain），而云同步冲突的发起者是由 `executeSyncConflictGoal` 创建的**受限实例**，跑完 `waitForInstanceIdle` 后即被 `destroy()` —— 后台任务完成时没有活着的实例可回填
