## 0. 目标与非目标

两件事：

1. 设置页「实验功能」里的三个功能——**提示词风格 / 跨渠道会话接续 / 自主进化**——
   改成插件（主进程接线 + 渲染层 UI 都进插件）。
2. 插件的**启用/禁用要同时作用到前端和后端**：关掉一个插件，它的 IPC、定时器、页面入口、
   设置项一起消失；同时把插件代码从主代码里分离出去，**一个插件目录里同时放前后端代码**。

非目标：

- 不改 `packages/agent-runtime` 里的**纯算法**（`autonomous/*`、`prompt/*`、`tool-definition-style`）。
  那是库，被主进程与官方扩展共同使用；插件拿的是「装配 + IPC + UI」这一层。
- 不做真正的沙箱与权限（沿用决策记录 D1/D2）。
- 不追求把外部扩展（`~/.lumii/extensions/`）也做到前后端一体——它仍然是主进程单侧，
  这次只解决内置插件。

## 1. 现状

### 1.1 三个功能的代码面（2026-10-22 盘点）

| 功能 | 主进程 | 渲染层 | 开关 | 实际消费点 |
|---|---|---|---|---|
| 提示词风格 | `main/index.ts` 缓存 + `ipc/settings-ipc.ts`；`bridge-prompt-dispatcher.ts` 每轮读 | `ExperimentalSection` 三态切换 + `settings-service` | 渲染层 localStorage `promptStyle.style`（默认 `terse`） | **每轮对话**：dispatcher 读风格 → 重建提示词 + 按 minimal 裁工具定义 |
| 跨渠道会话接续 | `channel/cross-channel-continuity.ts`、`channel-feature-store.ts`、`ipc/channel-ipc.ts` | `ExperimentalSection` 开关 + `useChannelFeatures` | `userData/channel-features.json`（默认 false） | **每条渠道消息**：4 个 adapter 读开关 → `continuity()?.maybeNotice()`；Hub 拦截回复；`/clear` 重置 |
| 自主进化 | `agent-runtime/autonomous-wiring.ts`、`evolution-tick.ts`、`autonomous-cron-linkage.ts`、`planner-wiring.ts`、`ipc/autonomous-ipc.ts`（20 个通道）+ bridge 里十余处接线 | `AutonomousPage`（仪表板）+ 5 个展示组件 + `autonomous-service` + 设置页红点/角标 | SQLite `runtime_state['autonomous.enabled']`（默认关）+ `autonomous.settings` | **cron 心跳 + 每轮回合结束**：tick → 目标/反思/日记；bridge 装配协调器与规划器 |

三者的共同点：**核心在「每轮/每条消息」的路径上直接调用它们**。所以插件化不能只搬文件，
必须把调用点改成「插件提供 → 核心按需取，拿不到就走默认」的服务契约。

### 1.2 插件体系的现状与缺口

| 维度 | 现在 | 缺口 |
|---|---|---|
| 主进程内置插件 | `src/main/plugins/builtin/<name>/index.ts`，`apply(ctx)` 接线，12 个已可运行期启停 | 代码在 `src/main` 名下，渲染层要用就得反向 import `@main/...` |
| 渲染层客户端插件 | `~/.lumii/plugins/<dir>/client.js`，槽位注册 + 1 秒轮询 | **只有外部插件**；内置功能没有任何渲染层插件形态 |
| 启停联动 | 主进程 `activate/stop` 即时生效 | 渲染层完全不知道主进程插件被关了；设置页/页面入口不会消失 |
| 前后端同包 | 无 | 需要「一个目录里 index.ts + renderer.tsx」的新形态 |

## 2. 目标结构

### 2.1 插件根目录：`apps/windows/src/plugins/`

```
src/plugins/
  README.md            约定与生命周期（由 main/plugins/README.md 演进）
  registry.ts          唯一清单：BUILTIN_EXTENSIONS + hot + renderer
  host.ts control.ts active.ts    主进程宿主 / 控制面 / 运行期门
  renderer/runtime.tsx 渲染层运行时：按启停状态 setup/teardown 插件 UI
  builtin/<name>/
    index.ts           主进程：manifest + apply(ctx)
    renderer.tsx       渲染层：注册槽位（可选）
    *.ts / *.tsx       该插件独占的实现与测试
  external/ external-src/ install/    （同现在，原样迁入）
```

- 主进程通过相对路径 `../../plugins/...` 引用；渲染层通过 `@/plugins/...` 引用。
- **为什么不在 `src/main/plugins/` 里加 `renderer.tsx`**：渲染层文件躺在 `src/main/` 下是层次错位，
  且会让「核心不得 import 插件」的守卫失去意义。一次搬完，后面都省事。
- 目录搬迁沿用上次的工具与判据（`git mv` + 相对说明符重写 + tsc/测试/守卫逐批过）。

### 2.2 插件契约（新增渲染层半边）

```ts
// src/plugins/builtin/<name>/index.ts —— 主进程
export const xExtension = { manifest, definition }   // 现状不变

// src/plugins/builtin/<name>/renderer.tsx —— 渲染层（可选）
export const renderer: RendererPlugin = {
  id: 'com.lumii.x',
  /** 返回清理函数；禁用时调用 */
  setup(api: RendererPluginApi): () => void,
}
```

`RendererPluginApi` 是**受控的最小面**：`registerSlot`、`registerCard`、`usePluginData`。
不给 `window.electronAPI` 全量——插件能调的 IPC 由它自己的主进程半边提供，
这一条同时约束了「前后端一体」的边界。

`registry.ts` 里一个插件一行，主进程与渲染层共用这张表：

```ts
{ ...promptStyleExtension, hot: true, renderer: promptStyleRenderer }
```

### 2.3 前后端联动启停

```
设置页点开关
   └→ extension:set-enabled (IPC)
        ├→ main: host.activate/stop（IPC、定时器、订阅随作用域拆）
        ├→ 写 extensions.json
        └→ mainWindow.webContents.send('plugin:state-changed', {id, enabled})
             └→ renderer runtime（订阅一次）
                  ├→ enabled  → rendererPlugin.setup(api)
                  └→ disabled → 调用上次 setup 返回的清理函数
```

关键点：

- **推送而不是轮询**：客户端插件 1 秒轮询是因为它们来自磁盘、可能被外部改动；
  内置插件的状态变化只有设置页一个入口，推一次就够。
- **渲染层初始状态**：`renderer/runtime.tsx` 挂载时拉一次 `extensions.list()`，
  与推送走同一套 `applyState`，避免「启动时全开、点一下才关」。
- **UI 消失而不是灰掉**：禁用 = 清理函数执行 = 槽位条目注销。页面里留下空槽，不留死按钮。
- 需要重启才生效的开关（`restartRequired:true`）**不推**，UI 继续沿用原来的「待重启」提示。

### 2.4 核心如何调用插件（服务契约）

现在的写法是核心直接 `import` 插件实现。改成服务容器注入：

| 功能 | 服务键 | 插件 apply 时注册 | 核心拿不到时 |
|---|---|---|---|
| 提示词风格 | `S.promptStyle` | `{ get(): Promise<PromptStyle> }` | 默认 `terse`（与 `DEFAULT_PROMPT_STYLE` 一致） |
| 跨渠道接续 | `S.channelContinuity` | `{ for(channel): Continuity \| undefined }` | `undefined` ⇒ 不做接续 |
| 自主进化 | `S.autonomous` | `{ init(db, callLLM) / onTurnEnd(convId) / syncCron() }` | 不装配、不播种 cron |

服务键一律用 `LateRef`（插件晚于核心装配），见 `kernel/services.ts`。

## 3. 分批计划与验收门

每批同一道门：`tsc --noEmit` → 相关测试 → `node scripts/check-wiring.mjs` → 提交。
涉及运行期行为的批次再加一条**真机判据**（CDP/日志）。

| 批次 | 内容 | 验收 |
|---|---|---|
| **P0 基建** | 插件根迁到 `src/plugins/`；`renderer/runtime.tsx`；`plugin:state-changed` 推送；preload `extensions.onStateChanged`；守卫改扫描根 | 全量测试不变；开关一次，渲染层日志出现 setup/teardown |
| **P1 提示词风格** | 插件 `prompt-style`：主进程缓存 + IPC + `S.promptStyle`；渲染层设置项走槽位 | 禁用后设置项消失、`[llm-prompt] style=` 回落到 `terse`；恢复后回到所选档 |
| **P2 跨渠道接续** | 插件 `channel-continuity`：状态机 + 开关存储 + IPC + 4 个 adapter 的接线改服务契约；渲染层开关 | 禁用后 `channel-features.json` 开关项消失、渠道消息不再询问接续 |
| **P3 自主进化** | 插件 `autonomous`：wiring/tick/cron 联动/20 个 IPC + 渲染层仪表板页 | 禁用后仪表板入口消失、`autonomous-tick` 不播种、状态查询走「未启用」分支 |
| **P4 收口** | 守卫：渲染层插件必须在 registry 声明；文档；全量 + 冷启动 | 全量 4094 passed 之外无新增失败 |

回滚：每批一个提交，`git revert <sha>`。

## 4. 风险

| 风险 | 处置 |
|---|---|
| 自主进化面太大，一次性搬会长期红灯 | 拆成「装配层先搬、IPC 后搬」两刀；每刀后跑 `evolution-tick` / `autonomous-*` 测试 |
| 核心在每轮/每条消息路径上调用，服务为空时必须安全降级 | 每个服务契约先写「拿不到时」的默认行为与对应测试 |
| 渲染层 import 主进程代码会把 node 模块拖进 renderer bundle | 插件 `renderer.tsx` 只 import `src/renderer/**` 与 `src/shared/**`；守卫加一条检查 |
| 状态推送时序：渲染层早于主进程宿主就绪 | 初始状态走 `extensions.list()`（宿主未就绪时返回空 ⇒ 全部按关闭处理，随后推送纠正） |
| `src/plugins/` 搬迁后守卫扫不到插件里的 handler | `check-wiring` 的 `SCAN_DIRS` 与 ⑪ 的路径前缀同批改 |
| 与并行会话冲突 | 提交前按文件显式 `git add` |
