## 1. 已完成

### 1.1 卡片注册表（P4-a）

`components/A2UIRenderer/card-registry.ts`

- 插件类型先查注册表，未命中再走内建 switch；
- **内建 12 种的实现一行没动**——它们的 props 各不相同，硬套统一签名要写 12 个适配器，收益为零；
- 内建类型不可被插件覆盖（防劫持整个渲染面）；
- 重复注册抛错，而不是后者静默生效（「谁生效」不该取决于加载顺序）。

### 1.2 SlotHost（P4-b）

`components/slots/slot-registry.ts` + `SlotHost.tsx`

- `registerSlot(slot, {id, component, order, owner})` 返回注销函数；
- 同 slot 内 id 唯一；按 order + 注册顺序排序；
- `SlotHost` 只负责「渲染谁、按什么顺序」，**布局与上下文留在页面**。

### 1.3 第一个真实消费者：概览页

`pages/DashboardPage/dashboard-cards.tsx`

- 拆成**两个** slot：`dashboard.main`（整宽资讯）/ `dashboard.grid`（底部三栏）。
  两个而不是一个，因为「顶部整宽 + 底部三栏」是**页面布局**，不该由注册表决定；
- 内置 4 张卡片用同一个 `registerSlot` 注册（幂等），插件卡片走同一套 API。

**验证**：真机截图与改动前布局一致；7 个注册表用例全绿。

## 2. 实施时抓到的两个真问题

### 2.1 `useSyncExternalStore` 的快照必须缓存

`getSlotEntries` 原本每次返回新数组（spread + sort），React 判定快照变化 →
**Maximum update depth exceeded**，页面无限重渲染。

单测全绿，只有把页面真跑起来才暴露。修法：按 slot 缓存快照，任何增删时清空。

**教训**：渲染层改动必须用真浏览器验证——纯函数测试看不到「渲染循环」这类问题。

### 2.2 布局不属于 slot

最初想用一个 `dashboard.card` slot 把 4 张卡都塞进去，但顶部资讯是整宽、底部三栏是网格。
硬塞进一个 slot 等于把布局决策搬进注册表——插件将无法知道「我这张卡会被放进哪种容器」。

改成两个语义明确的 slot 后，页面继续掌握布局，slot 只表达「这里有位置可以放东西」。

## 6. 插件加载器（2026-10-20 完成）

### 6.1 形状

```
~/.lumii/plugins/<目录>/
  ├── client.js      必需
  └── plugin.json    可选 { id, name, version }
```

- 主进程用 `lumii-plugin://local/…` 协议提供 `list.json` 与文件（**不开 IPC、不改 preload**）；
- 渲染层拉清单 → 注入 `<script>` → 取 `globalThis.__LUMII_REGISTER_PLUGIN__(id, factory)`；
- 工厂收到宿主模块 `{ React, ReactDOM, jsx, registerCard, registerSlot }`——插件**不得自带第二份 React**；
- 清单按 `revision`（mtime+size）每秒轮询；变化即卸载旧的、加载新的，实测 **~0.3 秒**生效；
- 卸载会注销该插件注册过的所有卡片与槽位（工厂返回的 dispose + 注册时收集的注销函数）。

### 6.2 三个只有真机才暴露的问题

1. **`protocol.registerSchemesAsPrivileged` 是替换语义，不是累加**
   分三次调用（lumii-local / lumii-pet / lumii-plugin）时**只有最后一次生效**，
   渲染层报 `Fetch API cannot load ... URL scheme "lumii-plugin" is not supported`。
   修法：集中在 `main/protocol-schemes.ts` 一次注册三个 scheme。

2. **`corsEnabled: true` 必须显式给**
   从 http(s) 源 fetch 自定义 scheme，缺了它 Chromium 直接按「scheme 不支持」拒绝，
   报错文案完全看不出是 CORS 的问题。

3. **`console.info` 不进日志文件**
   主进程只捕获 `log/warn/error`。插件宿主最初用 `console.info` 打成功日志，
   结果「一条都没有」，误判成没加载。这是本仓库反复踩的同一个坑。

### 6.3 布局约束（重要）

概览页是**像素预算的一屏布局**：底部三栏固定 `1.7fr / 1fr / 216px` 且限高。
实测把第 4 张卡片注册进 `dashboard.grid` 会溢出（被限高裁掉），
注册进 `dashboard.main` 会挤压资讯区。

因此 `SlotHost` 加了 `max` 容量声明：超出不渲染并打一条**去重**警告
（`[slot] dashboard.grid 注册了 4 个条目，但页面只放得下 3 个`）。

**结论**：页面能不能被插件扩展，取决于它有没有为插件预留布局预算。
「slot 化」不等于「布局自动适配」——这一点必须在上线任何页面 slot 前想清楚。

### 6.4 布局预算的解决方式（同日完成）

上一节说「slot 化 ≠ 布局自适应」。落地时给插件**专属预算**，而不是去改既有布局：

| 位置 | 做法 | 验证 |
|---|---|---|
| 概览页 | 新增 `dashboard.plugins` 槽位 + `.plugin-band`：最多 168px、内部自滚、空时不渲染 | 截图：插件卡片出现在底部，上方资讯与三栏完全没被挤压 |
| 设置中心 | 新增「扩展」页签承载 `settings.section`，不碰现有 20+ 分区 | 截图：插件分区显示在「扩展」页签内 |

「扩展」页签与已有的「插件」页签是两类东西：后者是资产/组件（ffmpeg、微信 MCP），
前者是**代码扩展**。命名沿用决策 D4。
