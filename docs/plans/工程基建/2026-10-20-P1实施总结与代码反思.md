## 2. 代码反思（按严重程度）

### 2.1 高风险代码零测试

新增的四个文件**一个测试都没有**：

```
apps/windows/src/main/extension-loader.ts   223 行   ← 动态 import、热重载、轮询
apps/windows/src/main/plugin-host.ts         50 行
apps/windows/src/main/kernel/extension-store.ts 52 行  ← 容错读取
apps/windows/src/main/kernel/services.ts     33 行
```

而它们恰恰是「读用户目录、跑陌生代码、按 mtime 判断要不要重载」的地方。内核有 34 个单测，
外壳却是零——测试覆盖的分布和风险分布是反的。

**结论**：P2 开始前必须先补 `extension-loader` 与 `extension-store` 的单测（发现逻辑、
revision 跳过、坏 JSON 容错、卸载路径）。

### 2.2 外部扩展热重载失败不回滚

计划里写的是「失败回滚到旧版本」，实现是：

```ts
if (previous) await this.unload(previous.dir)   // 先卸旧的
mod = await import(...)                          // 新的坏了
// → 旧的已经没了，什么也没起来
```

用户的扩展在编辑到一半时保存，会出现「功能凭空消失」几秒后也不恢复。这与我写在计划里的
承诺不符，属于**实现落后于文档**。

**结论**：改成「先加载新的、成功后再卸旧的」，失败时旧版本继续服务并记一条 warn。

### 2.3 manifest 校验写了但从未使用

`validateManifest()` 在 `plugin-core` 里有实现、有单测、从 `index.ts` 导出，
但应用里**零调用**（`grep` 结果全是同名的无关私有函数）。后果：

- 内置扩展的 manifest 是手写的对象字面量，id 格式、`engines`、`kind` 与入口的一致性全不校验；
- 外部扩展只查了 `manifest.id` 是否存在、`definition.apply` 是不是函数；
- 版本号写错、id 与目录不符、两个扩展撞 id，都要到运行时才炸（撞 id 时抛的是「重复注册」，
  看不出是外部扩展撞了内置扩展）。

另外内置扩展的 `manifest.main` 写的是 `'./perf.js'`，而仓库里只有 `perf.ts` ——
**这些元数据在撒谎**。要么让它们真（指向构建产物），要么承认 P0/P1 阶段它们只是标签。

**结论**：manifest 要么接上校验，要么把它降级成「展示用描述」并改名，不要留半真半假的字段。

### 2.4 `effects` 指标会误导

`effects=2` 里的 2 个，对 cloud-sync 而言是 `ctx.provide` 注册的两个服务清理器，
**不是**两个业务 teardown。真正的泄漏点（定时器、监听器、子进程）没被区分出来。
排查「禁用后还有残留」时，这个数字会让人以为清理齐了。

**结论**：统计改成两类——`services` 与 `teardowns`，或者干脆只报 teardowns。

### 2.5 云同步扩展没有真正的 teardown

`extensions/cloud-sync.ts` 只创建 manager/scheduler 并 provide，**没有注册任何 effect**。
这意味着热卸载该扩展时，调度器与文件监听仍在跑。今天不出问题仅因为调度器的 stop
在 `performCleanup` 里独立执行。

**结论**：P2 里凡是「持有长期资源」的扩展，必须在 `apply` 里登记对应 teardown，
并让 `effects` 能反映出来。

### 2.6 类型逃逸与错误归属

```ts
this.host.register(definition as never)        // extension-loader.ts:195
throw new DuplicateServiceError("service", name) // context.ts:18
```

前者是外部模块类型不可信的必然结果，但 `as never` 会连**结构**都放过；后者把 pluginId
硬编码成 `"service"`，冲突日志变成 `[service] service "perf" 已被注册`，看不出是谁。

**结论**：前者改成先做结构校验再类型收窄；后者把发起方 pluginId 传进容器。

### 2.7 禁用只有读路径，没有写路径

`extension-store.ts` 只有 `readDisabledExtensionIds()`。要禁用只能手改
`~/.lumii/extensions.json`。P1-d 的标题写的是「启用/禁用」，实际交付的是「能读偏好」。

**结论**：不算缺陷，但**文档不能这么写**。要么补写路径（+ 设置页/CLI 开关），
要么把这一项如实标为「仅文件配置」。

### 2.8 `index.ts` 只瘦了编排，没有瘦文件

```
P0 开始时：1999 行
现在：     2072 行（+73）
```

`initialize()` 从 378 → 39 行是真的，但阶段函数仍住在同一个文件里，净结果是变大。
「`index.ts` ≤200 行」的目标没有推进，只是把线性脚本变成了函数。

**结论**：P2 里要把阶段函数搬到 `main/kernel/stages/*.ts`，否则这个数字只会继续涨。

### 2.9 跳过 P1-c 的代价

控制口 `server.ts` 仍是 25 个硬编码 `case`。云同步那 11 个 `cloudSync:*` IPC、
`/ipc/cloudsync/*` 路由、设置页分区都还锁在核心里 —— 云同步「能禁用」但「不能拆」。

## 3. 反思得出的四条规矩（写进 P2）

1. **新模块必须带测试**，尤其是读文件系统、动态执行、判重/去重这类逻辑。
   先写测试再写实现，或者至少同一次提交里带上。
2. **文档不写实现做不到的话**。「失败回滚」「启用/禁用」这类承诺要么实现，
   要么写成实际做到的样子。
3. **元数据要么真、要么不写**。悬空路径、从未被校验的字段，比没有字段更糟。
4. **指标要能指导行动**。`effects=2` 若不能回答「禁用后还有残留吗」，就是噪音。
