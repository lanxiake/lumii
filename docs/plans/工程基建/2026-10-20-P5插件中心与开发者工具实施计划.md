## 0. 结论先行

P5 的原始表述是「插件中心 UI + 脚手架 + 监测面板 + 插件文档」。落到本仓库，
**只有一件事真正缺**：现在没有任何地方能看见「进程里到底有哪些扩展、谁没起来、为什么」。

三个来源各自的情况：

| 来源 | 目录 | 能否看见 | 能否关掉 |
|---|---|---|---|
| 内置扩展（打进 bundle） | — | 只有启动日志 | 手改 `~/.lumii/extensions.json` + 重启 |
| 外部扩展（主进程，bundle 外） | `~/.lumii/extensions/` | 只有日志 | **不能** |
| 客户端插件（渲染层） | `~/.lumii/plugins/` | 只有 console | **不能** |

所以 P5 = **一张统一列表 + 一个开关 + 一个「新建」按钮 + 一份契约文档**。
脚手架不做成 CLI（本机 CLI 路径不可靠，见记忆 `lumii-cli-not-implemented`），
做成设置页里一个按钮——点一下就在 `~/.lumii/plugins/` 生成可直接生效的示例插件。

**明确不做**：npm / GitHub Release 分发、工具调用数面板、内存面板、8 个页面的迁移
（见 §7）。

## 1. 一个关键取舍：主进程扩展的开关「重启后生效」

P5 最初想做成全实时启停。**做不到，而且原因不是懒**：

- `main/index.ts` 在启动时把 `performanceMonitor` / `updaterService` / `cloudSyncManager` /
  `syncScheduler` 取成**模块级变量**，十余处调用点直接引用它们。运行时卸载扩展，
  变量仍指向旧实例——「禁用后仍在跑」比「需要重启」糟得多。
- `com.lumii.voice` 更硬：ONNX 顺序闸的状态机不可逆（`e5Running` 后 `sherpaFirst()` 拒绝），
  禁用语音 = 本进程不再可能启用，**必须重启**。这条约束在 `extensions/voice.ts` 的注释里已写明。

因此：

| 类别 | 开关生效时机 | 理由 |
|---|---|---|
| 主进程扩展（内置 + 外部） | **重启后** | 捕获的模块级引用 + ONNX 闸 |
| 客户端插件（渲染层） | **≤1 秒** | 渲染层没有这类单例捕获，宿主本来就每秒轮询 |

UI 上必须把这个差别写在明面上，不能让人点了开关以为立刻生效。

## 2. 数据模型

`~/.lumii/extensions.json` 扩成两个独立集合：

```json
{
  "version": 2,
  "disabled": ["com.lumii.voice"],
  "disabledClient": ["demo-card"]
}
```

- `disabled` —— 主进程扩展的 **manifest id**（内置与外部共用一张表）；
- `disabledClient` —— 客户端插件的 **id**。

两个集合而不是一个带前缀的集合：主进程与渲染层的 id 是**两个独立命名空间**
（同名插件可以各存在一个），前缀约定迟早被忘掉。

读取保持容错（文件缺失 / JSON 损坏 / 结构不对 → 空集合 + 一条 warning），
与 P1 的既定语义一致：坏掉的偏好文件不该让应用失去功能。

## 3. 接口契约

### 3.1 主进程 IPC（`ipc/extension-ipc.ts`，owner `plugin-host`）

| 通道 | 入参 | 返回 |
|---|---|---|
| `extension:list` | — | `ExtensionInfo[]` |
| `extension:set-enabled` | `(id, enabled)` | `{ ok, error?, restartRequired? }` |
| `extension:set-client-enabled` | `(id, enabled)` | `{ ok, error? }` |
| `extension:create-sample` | — | `{ ok, dir?, error? }` |

```ts
interface ExtensionInfo {
  id: string
  name: string
  version: string
  kind: 'builtin' | 'external'
  dir?: string            // 外部扩展才有
  enabled: boolean
  state: 'registered' | 'activating' | 'active' | 'failed' | 'stopped' | 'disabled' | 'unknown'
  activationMs?: number
  error?: string
}
```

客户端插件**不走 IPC**：它们的元数据来自渲染层自己的 `list.json`，加载状态只有渲染层知道。
主进程只负责回答「它是否被禁用」（写进 `list.json` 的 `enabled` 字段）。

### 3.2 外部扩展的禁用

`ExternalExtensionRuntime` 构造时接收 `disabledIds`，`reload()` 导入模块后先查这张表：

- 命中 → 若上一版还挂着就卸载，然后**只登记不激活**（`enabled: false`）；
- 未命中 → 照旧注册 + 激活。

登记而不是丢弃，是为了让「禁用后重启」的扩展**仍然出现在列表里**，否则用户关掉它之后
就再也找不到怎么打开——那等于给自己造了一个只能手改 JSON 的死角。

代价：被禁用的外部扩展的**模块顶层代码**仍会执行一次（`apply()` 不会）。如实记在文档里。

### 3.3 客户端插件的禁用

`lumii-plugin://local/list.json` 的每条描述符增加 `enabled: boolean`
（主进程读 `disabledClient` 得出）。渲染层：

- `enabled === false` → 已加载则卸载，不再加载；
- 每次轮询（1 秒）自动反映，因此开关**实时生效**。

## 4. 实施分片

### S1 偏好存储（`kernel/extension-store.ts`）

- `readExtensionPrefs(file?) → { disabled, disabledClient, warning? }`
- `setMainExtensionEnabled(id, enabled, file?)`
- `setClientExtensionEnabled(id, enabled, file?)`

写盘用临时文件 + `rename`（Windows 上 `renameSync` 覆盖已有文件是原子的），
避免写一半崩掉把整个偏好文件变成坏 JSON。

**验收**：单测覆盖「空文件 / 坏 JSON / 结构不对 / 往返写入 / 只改一个集合不动另一个」。

### S2 外部扩展可禁用 + 可列举（`extension-loader.ts`）

- 构造参数加 `disabledIds`；
- 条目增加 `name` / `version` / `enabled` / `error`；
- `inspect()`：返回所有**已知**外部扩展（含被禁用的与导入失败的）。

**验收**：现有 `extension-loader.test.ts` 全绿；新增用例覆盖「禁用后 inspect 仍能看到、且 host 里没有它」。

### S3 控制面（`extension-control.ts`）

`createExtensionControl({ host, external, builtins?, storeFile? })`：

- `list()` —— 合并内置 + 外部；
- `setEnabled(id, enabled)` —— 写偏好，返回 `restartRequired: true`。

`builtins` 做成可注入依赖（默认 `BUILTIN_EXTENSIONS`），否则单测会连带把
voice / onnx 整条依赖链 import 进来。

### S4 示例插件生成（`plugin-template.ts`）

`createSamplePlugin(root?)` 在 `~/.lumii/plugins/<name>/` 写三件套：

```
plugin.json    { id, name, version }
client.js      可直接生效的示例：卡片 + 导航 + 整页 + 设置分区
README.md      契约速查（怎么改、有哪些槽位、哪些坑）
```

目录名自动避让（`my-plugin` → `my-plugin-2` → …），**不覆盖已存在的目录**。

### S5 IPC + preload

- `ipc/extension-ipc.ts` + `scripts/ipc-owners.json` 登记；
- preload 增加 `extensions` API（type + impl 两处，与既有 `plugins` 同形）。

### S6 渲染层

- `client-plugin-host.ts`：
  - 记录 `lastDescriptors` / `lastErrors`，导出 `getClientPluginStates()` + `subscribeClientPlugins()`；
  - 处理 `enabled === false`；
  - **HMR 自接受**：`import.meta.hot.dispose(stopClientPlugins)` + `accept(init)`——
    否则编辑这个文件本身会把所有插件弄成「重复注册」；
- `components/ExtensionsPanel/`：两段列表（主进程 / 客户端）+ 开关 + 「新建示例插件」+ 提示文案；
- `SettingsHubModal` 的「扩展」页签改为 `<ExtensionsPanel />` + `<SlotHost name="settings.section" />`；
- `Router` 给插件整页传 `onViewChange`；
- `Sidebar` 的 `app.nav` 上下文补 `classNames`，让插件导航条能用原生样式。

## 5. 插件开发契约（随 P5 落地的文档）

### 5.1 渲染层插件

```
~/.lumii/plugins/<目录>/
  ├── client.js      必需
  └── plugin.json    可选 { id, name, version }；缺省 id = 目录名
```

```js
// 一个插件 = 一个 id = 一次 REGISTER 调用。分成两次注册的话，后一次永远拿不到
// （宿主按 manifest id 取工厂）。
__LUMII_REGISTER_PLUGIN__('my-plugin', (api) => {
  api.React          // 宿主提供，禁止自带第二份 React（两份 React 会让 hooks 直接抛错）
  api.ReactDOM
  api.jsx            // react/jsx-runtime
  api.registerCard(type, renderer)      // 返回注销函数
  api.registerSlot(slot, entry)         // 返回注销函数
  return () => {}                       // 可选：卸载时清理
})
```

**读数据有两条现成通道**（2026-10-21 真机探针实测，不是推测）：

| 侧 | 通道 | 实测 |
|---|---|---|
| 渲染层插件 | `window.electronAPI.*`（与页面同一 JS 上下文，不做沙箱） | `performance.getReport` / `plugins.list` / `extensions.list` 均为 function，`extensions.list()` 返回 7 条 |
| 主进程扩展 | `ctx.get('agentRuntime')` → `LateRef<AgentRuntimeBridge>`；`ctx.get('perf'/'cloudSync'/'mainWindow'/…)` | 服务已在 `kernel/services.ts` 注册 |

所以**不需要**再为插件包一层 `S.mcp` 之类的窄接口：完整桥本来就暴露着（决策 D1/D2）。

可用槽位：

| 槽位 | 出现在 | 上下文 props |
|---|---|---|
| `dashboard.main` | 概览页顶部整宽区 | `{ onViewChange }` |
| `dashboard.grid` | 概览页底部三栏（**最多 3 个**，超出不渲染并告警） | `{ onViewChange }` |
| `dashboard.plugins` | 概览页插件专属区（168px，内部滚动） | `{ onViewChange }` |
| `app.nav` | 侧栏导航下方 | `{ activeView, onViewChange, collapsed, classNames }` |
| `app.view` | 整页视图，id 需与 `plugin:<id>` 对应 | `{ onViewChange }` |
| `settings.section` | 设置中心 › 扩展 页签 | — |
| `message.card` | 消息时间线（由 CardRegistry 承担，非 slot） | — |

三条硬规则（都是踩过的）：

1. `SlotEntry.id` 在**同一槽位内唯一**，重复注册抛错，不静默覆盖；
2. 卸载/热更新靠注册时返回的注销函数，**别在全局留自己的副本**；
3. 卡片内建类型不可被插件覆盖（防劫持整个渲染面）。

### 5.2 主进程扩展

```
~/.lumii/extensions/<目录>/main.js

export default {
  manifest: { id: 'com.example.foo', name: '…', version: '0.1.0',
              engines: { lumii: '>=0.1.0' }, kind: 'code' },
  definition: { id: 'com.example.foo', apply(ctx) { … } },
}
```

- 与主进程**同权限**，不做沙箱（决策 D1/D2）；
- 依赖窗口的装配挂在 `ctx.on('app:window-ready', …)`，不要假设激活时窗口已存在；
- 晚绑定的东西用 `LateRef`（`S.agentRuntime` / `S.mainWindow` / `S.tray`），
  **不要** `container.provide(key, () => obj)`——工厂返回值会被缓存，拿到的是首次的 `null`。

### 8.2 实施中发现的四个问题

1. **`.embedPane > *` 给每个直接子节点 `flex: 1`**
   把 `<ExtensionsPanel/>` 和 `<SlotHost/>` 直接放进去，两块各抢一半高度、
   `.embedPane` 又 `overflow: hidden` → 列表后 3 行被插件分区**盖住**。
   修法：包一层 `.extensionsPane`（`overflow-y: auto`），让它成为唯一子节点。

2. **加载失败的外部扩展每秒重试**
   `reload()` 解析失败时直接 `return`，条目的 `revision` 没更新 → `rescan` 每秒
   判定「文件变了」再导入一次。修法：失败也把这次 `revision` 记进条目
   （旧版本仍在服务时只改 `revision` 与 `error`）。这也是渲染层宿主
   `failedRevision` 的同一个教训。

3. **禁用后从 UI 里消失 = 死角**
   外部扩展若禁用时不登记，重启后列表里就没有它，用户只能去手改 JSON。
   修法：`reload()` 对被禁用的条目**登记但不激活**（`enabled: false`）。

4. **`client-plugin-host.ts` 没有 HMR 自接受**
   编辑这个文件会让旧 `setInterval` 继续跑、新模块 `loaded` 为空 →
   重新注册撞「已存在 id」，所有插件报废。修法：`import.meta.hot.dispose(stop)` +
   `accept((m) => m.initClientPlugins())`。
