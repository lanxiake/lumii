## 0. 为什么要「从架构上」解决

前面两轮把三个实验功能做成了插件，但都是**逐个手工搬**。再往下搬会一直撞同样四堵墙：

| # | 根因 | 现在的表现 |
|---|---|---|
| **R1** | 三套投放通道、两套渲染契约 | 内置插件用 `RendererPlugin.setup(api)`；客户端插件（`~/.lumii/plugins`）用 `__LUMII_REGISTER_PLUGIN__` + 另一套 `api`；外部扩展没有渲染层半边。清单已经统一（`LumiiPluginManifest` 带 `main` / `client` 字段），**契约没统一** |
| **R2** | 核心 ↔ 插件边界靠自觉 | 守卫 ⑪ 抓出 **32 条核心直连插件实现**（pet 11 / vcs 6 / dashboard-feed 4 / voice 3 / browser 2 / selection 1 / usage 1 / skill-evolution 1）。访问器逐个手写，规则散在注释里 |
| **R3** | 插件内注册写法各异 | `ctx.registerIpc` / `registrar.handle(...)` 注入 / `registerChannel(...)` 攒表 三种；渲染层 `registerSlot` / 实验项静态登记 两种 |
| **R4** | 官方外部扩展的实现还在核心 | perf / cloud-sync / screen-record 的「扩展」只是壳，实现在 `src/main/<name>/`，核心直连 —— 拆出去的是外壳不是代码 |

目标不是「再搬几个文件」，而是让**下一个插件（内置 / 官方 / 用户写的）照同一套规则落地**，
并且**违反规则时守卫会红**。

## 1. 统一模型：一个插件包

一个插件 = **一份清单 + 两个可选半边**，投放通道只决定文件从哪来：

```
<plugin>/
  manifest.json      LumiiPluginManifest（唯一格式；内置可写成 index.ts 里的对象）
  main.js / index.ts 主进程半边：apply(ctx) —— 注册 IPC、定时器、服务、订阅
  client.js / renderer.tsx  渲染层半边：setup(api) → dispose —— 注册槽位、页面、卡片
```

| 通道 | 主进程半边 | 渲染层半边 | 生效方式 |
|---|---|---|---|
| 内置（bundle 内） | `plugins/builtin/<id>/index.ts` | `plugins/builtin/<id>/renderer.tsx` | 同一进程，运行期启停 |
| 官方/用户扩展（`~/.lumii/extensions`） | `main.js`（动态 import） | `client.js`（协议 `lumii-plugin://`） | 主进程热重载；渲染层轮询 |
| 客户端插件（`~/.lumii/plugins`） | — | `client.js` | 渲染层 ≤1 秒 |

**统一的是契约，不是位置**：三种通道的主进程半边都拿到同一个 `PluginContext`，
渲染层半边都拿到同一个 `RendererPluginApi`。通道差异只体现在「谁负责把它加载进来」和
「启停是否即时」。

## 2. 三层契约

### 2.1 宿主契约（`packages/plugin-core`，已有）

`apply(ctx)`：`ctx.registerIpc` / `ctx.provide` / `ctx.effect` / `ctx.on` / `ctx.get`。
主进程三种通道共用。

### 2.2 服务契约（核心 ↔ 插件唯一的运行期通路）

```ts
// src/plugins/api/service.ts —— 统一入口（本轮新增）
export function defineServiceAccessor<T>(name: string): {
  setResolver(fn: (() => T | null) | null): void
  get(): T | null
}
```

- 插件在 `apply` 里 `ctx.provide(S.xxx, impl)`；服务随作用域来去。
- 核心用访问器 `getXxxService()?.…`，**拿不到就是功能关闭**。
- `index.ts` 只在宿主建好后注入一次：`accessor.setResolver(() => pluginHost?.container.get(S.xxx) ?? null)`。
- 服务接口定义在插件目录（`service.ts`），核心 **type-only** 引用 → 编译期擦除，守卫 ⑪ 不计。

### 2.3 渲染契约（统一 `RendererPluginApi`）

```ts
export interface RendererPluginApi {
  registerSlot: typeof registerSlot
  registerCard: typeof registerCard
}
export interface RendererPlugin {
  id: string
  setup(api: RendererPluginApi): () => void   // 返回清理函数
}
```

- 内置插件：`renderer.tsx` 导出 `RendererPlugin`，由 `plugins/renderer/registry.ts` 登记。
- 客户端插件：宿主在加载 `client.js` 时，用**同一形状**的 `api` 调用工厂
  （现有的 `api.React / api.Page / api.storage / api.format` 保留为扩展字段，不另立一套）。
- 外部扩展要支持渲染半边时，走与客户端插件相同的加载路径，不新增第四套。

### 2.4 插件内注册 IPC 的**唯一写法**

```ts
// 少：ctx.registerIpc('x:y', handler)
// 多：createIpcTable() 攒表，apply 里一次性挂
const table = createIpcTable()
table.register('autonomous:getStatus', async () => …)
…
apply(ctx) { table.install((ch, fn) => ctx.registerIpc?.(ch, fn)) }
```

原因：handler 多时逐个 `registerIpc` 会散落全文件；攒表后「哪些通道属于这个插件」
一眼可见，也便于守卫核对。

## 3. 边界规则（可执行）

| # | 规则 | 守卫 |
|---|---|---|
| B1 | 核心不得 import 插件实现（服务访问器除外） | ⑪ 棘轮，目标清零后改成「只许 `plugins/api`」 |
| B2 | 核心只能 type-only import 插件里的**契约类型** | ⑪ 已排除 type-only |
| B3 | 插件不得 import 兄弟插件的运行时实现（共享代码下沉到 `src/shared` 或核心） | 新增 ⑫ |
| B4 | 渲染层文件（`renderer.tsx` / `ui/**`）只能 import `src/renderer/**`、`src/shared/**`、`src/plugins/api/**` | 新增 ⑫ |
| B5 | 插件里的 IPC 必须经 `ctx.registerIpc` 挂载（停用能摘） | ⑫ 扫 `ipcMain.handle` |

## 5. 各插件的服务清单（P1 依据）

| 插件 | 核心直连的符号 | 服务键 | 拿不到时 |
|---|---|---|---|
| selection | 选区 LLM 调用 | `S.selection` | 不做选区问答 |
| usage | `recordUsage` | `S.usage` | 不记账（事件订阅本身随作用域拆） |
| dashboard-feed | store 读写 + 工具注册 | `S.dashboardFeed` | 资讯卡空态、工具不注册 |
| browser | 启动/停止/上下文 | `S.browser` | 浏览器工具不提供 |
| skill-evolution | 引擎（注入/观察） | `S.skillEvolution` | 不做提示注入（现已 `manifest.disabled`） |
| voice | `VoiceModelManager` / `VoiceCallService` / `voiceEventBus` | `S.voice`（已有） | 语音入口隐藏 |
| vcs | 快照 / 队列 / 回合快照 | `S.vcs` | 不做快照（云同步队列也走它） |
