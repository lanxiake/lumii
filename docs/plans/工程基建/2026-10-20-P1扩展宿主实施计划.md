## 0. 一句话目标

**让「关掉一个功能，应用照常运行」成为可验证的事实**，而不是架构图上的承诺。

判断标准只有一条：把 `perf` 扩展从配置里禁用，重启后性能监控不采集、应用一切正常；
重新启用后恢复，且**不需要改任何业务代码**。

## 1. 与 P0 现状的三处冲突（必须先解决）

### 1.1 宿主启动早于配置

P0 把 `startExtensions()` 放在 **S1b**（`S1-perf` 之后、`S6-config` 之前）。
但真实扩展几乎都要配置：云同步要工作区与仓库配置、更新检查要渠道、控制口要端口。

**实施时的结论（与初稿不同）**：**不**把激活整体挪到配置之后。原因是
`installAgentRuntimeCommandIpc(performanceMonitor)` 在窗口创建之前就要拿到 perf 实例，
晚于它会让 `agent-runtime:command` 的耗时统计**静默消失**——那是行为回退，不是优化。

采用的规则：

| 扩展类型 | 激活时机 | 拿配置的方式 |
|---|---|---|
| 不依赖配置（hello、perf） | S1b，与启动同批 | 不需要 |
| 依赖配置（云同步、控制口） | 仍在 S1b 激活，但**只能**通过 `S.config` getter 取配置 | getter 在配置就绪前返回 `undefined`，扩展自行等 `config:ready` |

好处：宿主只有一个激活点，不会有「一半扩展在跑、另一半还没起来」的中间态；
代价：依赖配置的扩展要写成「先挂监听、配置到了再干活」的形状——这本来就是
长驻服务的正确写法。

### 1.2 秒级热更新的真实边界

关键决策 D5 写的是「秒级热更新」，但**主进程代码被 electron-vite 打包成单文件**，
运行时没有可替换的模块边界。必须把承诺拆成两档写清楚：

| 场景 | 机制 | 真实延迟 |
|---|---|---|
| 内置扩展（编译进 bundle） | electron-vite 检测改动后重启主进程 | 数秒（整机冷启 ~9s，见 §7） |
| 外部扩展（`~/.lumii/extensions/<id>/main.js`） | 文件监听 + 带 `?v=` 的动态 import | 亚秒级 |
| 渲染层扩展 | — | **P4 才做** |

P1 只把第二档做出来（P1-f），第一档如实标注为「dev 重启」。
「毫秒级随意改」在打包应用里做不到，写成能做到就是骗人。

### 1.3 启用状态存哪

不能用 `AppConfig`：它要等 `S6-config` 才可用，而**是否启用**必须在激活前就知道，
且外部扩展的启用状态要在配置损坏时也能读。

**处理**：独立文件 `~/.lumii/extensions.json`，只存**偏离默认的禁用项**：

```json
{ "version": 1, "disabled": ["com.lumii.cloud-sync"] }
```

内置扩展默认全开；只有用户显式关掉的才进这个数组。
读取失败（文件损坏/无权限）一律按「全部启用」处理并记 warn——不能让一个坏文件让应用失去功能。

## 2. 契约

### 2.1 主进程事件表

`src/main/kernel/events.ts`：

```ts
export interface MainEvents {
  'app:activated': { at: number }
  'app:shutdown': { reason: 'quit' | 'restart' }
  'tool:post-execute': { toolName: string; durationMs: number; success: boolean }
  'conversation:completed': { conversationId: string }
}
```

只登记**已有真实发射点**的事件。没有发射方的事件不要写进表——那是假契约。

### 2.2 服务 key 表

`src/main/kernel/services.ts`（类型单一来源，避免 declaration merging 的漂移）：

```ts
export const S = {
  log:     createServiceKey<Logger>('log'),
  config:  createServiceKey<() => AppConfig>('config'),
  perf:    createServiceKey<PerformanceMonitor>('perf'),
  updater: createServiceKey<UpdaterService>('updater'),
  control: createServiceKey<ControlPlane>('control'),
}
```

约定：**能拿到服务，不等于能改它的状态**。服务只暴露扩展需要的那部分能力，
例如 `perf` 给的是 `recordStartupPhase` / `recordMetric`，不给内部队列。

### 2.3 扩展描述

内置扩展放 `src/main/extensions/<id>.ts`，统一形状：

```ts
export interface BuiltinExtension {
  manifest: LumiiPluginManifest          // 复用内核类型，构建期校验
  definition: PluginDefinition<MainEvents>
}
```

`manifest` 的价值是**同一份数据将来喂给 UI 和守卫**，而不是现在就读磁盘。

## 3. 分片与顺序

每片独立可验收、可回滚。顺序按「风险 × 依赖」排，不按重要程度排。

### P1-a：perf 扩展（最小闭环）✅ 已完成 2026-10-20

| 项 | 内容 |
|---|---|
| 迁移 | `initPerformanceMonitor()` 搬进 `extensions/perf.ts`；定时器改由 `ctx.effect` 持有 |
| 宿主 | S1b 激活；`performanceMonitor` 由宿主从 `S.perf` 取回，十余处调用点一行没改 |
| 启用开关 | `~/.lumii/extensions.json`（`{"version":1,"disabled":[...]}`），坏文件按全启用处理 |
| 验收（已实测） | 启用：`[plugin:com.lumii.perf] 性能监控已启动` + `性能监控 IPC handlers 已注册`；禁用：`扩展已按配置禁用: com.lumii.perf`，无 perf 日志，`启动完成` 照常 |
| 风险 | 低。perf 无外部依赖，调用点都是 `?.` 可选链 |

实测数据：`S1-perf 14ms + S1b 2ms` 合并成 `S1-extensions 10ms`。

**注意**：`performanceMonitor` 是模块级单例，被 `setupPerformanceIpcHandlers`、`initAgentRuntime` 等
十余处引用。迁移时必须保留单例读法（扩展提供、宿主暴露 getter），**不能改成扩展内部私有**。

### P1-b：updater 扩展 ✅ 已完成 2026-10-20

| 项 | 内容 |
|---|---|
| 迁移 | `initUpdaterService()` 搬进 `extensions/updater.ts`，配置项一项没改 |
| 窗口引用 | 扩展激活时窗口还没建；宿主在 `createWindow` 之后用 `S.updater` 取回实例再 `setMainWindow` |
| 验收（已实测） | 禁用：`扩展已按配置禁用: com.lumii.updater`，perf/hello 照常；启用：`[plugin:com.lumii.updater] 自动更新已启动` |
| 风险 | 低。`updaterService` 只在 `index.ts` 用到，且 renderer 从不调用 `updater.*` |

**副作用**：`updater` 的 IPC handler 由扩展注册，禁用后不注册。因为渲染层根本不调用
`updater:*`（接线守卫第 ⑥ 项早有登记），所以禁用不会产生「No handler registered」。

### P1-c：控制口路由贡献

| 项 | 内容 |
|---|---|
| 现状 | `app-ui-control/server.ts` 里 10+ 领域路由混装，命令白名单 `command-allowlist.ts` 硬编码 |
| 迁移 | 只搬**路由注册**，不搬安全策略（白名单、限流、坐标校验留在内核） |
| 验收 | 控制口 `/status` 返回的扩展列表与实际激活一致 |
| 风险 | 中。控制口是外部进程（lumii-ui CLI）的接口，改坏会静默失败——必须用 CLI 实跑验证 |

### P1-d：启用/禁用与外部扩展目录 ✅ 已完成 2026-10-20

| 项 | 内容 |
|---|---|
| 存储 | `~/.lumii/extensions.json`（见 §1.3），P1-a 已落地 |
| 外部扩展 | `~/.lumii/extensions/<目录>/main.js`，动态 `import(url + '?v=' + mtime-size)` |
| 契约 | `export default { manifest, definition }`；也容忍具名导出 |
| 热重载 | 轮询 → 变化则 unregister（dispose 旧作用域）→ 重新 import → register → activate |
| 验收（已实测） | 加载 ✅／改文件 **~1s** 生效且旧作用域先卸载 ✅／删目录自动卸载 ✅ |

**两处实施偏离，都有实测依据：**

1. **`fs.watch` 在本机收不到子文件改动**。最小复现：`fs.watch(扩展根目录)` 后
   `appendFileSync` 子文件，3 秒内零事件（persistent 开/关都一样）。改为 1 秒轮询 +
   按 mtime/size 比对；扩展数量是个位数，代价可忽略。已用 `ponytail:` 注释标了升级路径。
2. **内核补了两个方法**：`PluginHost.activate(id)` / `unregister(id)`。P0 只有 `start()`
   全量激活，而热重载需要按单个扩展启停。这不是契约缺陷，是动态加载的正当需求；
   补了 3 个单测（单独激活、失败返回错误不抛、同 id 重新注册）。

实测时间线（全程未重启应用）：

```
14:05:26.097  写入 v3
14:05:27.058  外部扩展 v2 已卸载   ← 旧作用域先销毁
14:05:27.065  外部扩展 v3 已激活
14:05:34.123  删除目录 → 外部扩展 v3 已卸载
```

### P1-e：监测 ✅ 已完成 2026-10-20

| 项 | 内容 |
|---|---|
| 启动日志 | 每扩展一行：`[ext] com.lumii.perf active 10ms effects=2`；失败走 error 日志 |
| 控制口 | `POST /status` 增加 `extensions` 字段（id/state/activationMs/effects/error） |
| CLI | `lumii-ui status` 渲染「扩展 (N)」段；老客户端没这字段时不打，而不是打「0 个」 |
| 不做 | 独立监测面板 UI（P5） |

`effects` 是「注册了几个可逆副作用」——禁用/热重载时最容易漏清理的地方，所以放在显眼位置。
实测：hello 1 / perf 2 / updater 1，与各自 `ctx.effect` 数量一致。

### P1-f：云同步全栈样例

**排在最后**：5483 行、跨服务/定时任务/IPC/设置页五个面，是 P1 里唯一的中风险项。
先让前五项把契约压稳，再动它。若前五项暴露出契约缺口，改契约的成本远低于改完云同步再改。

## 5. 验收标准（每片都要过）

| 检查 | 判据 |
|---|---|
| 禁用后功能消失 | 日志无对应初始化行，相关 IPC/定时器不注册 |
| 应用仍可用 | 主窗口可交互，Agent 能跑一轮对话 |
| 重新启用即恢复 | 无需改代码，只改 json |
| 启动不回退 | `S0..S8` 各阶段耗时与迁移前同量级（见 §7 基线） |
| 单测 | `pnpm --filter @mtbot/plugin-core test` 与 `apps/windows` 全绿 |
| 类型 | `pnpm -r typecheck` 干净 |

**反例必须验**：故意让一个扩展 `apply()` 抛错，预期「该扩展 failed、其余正常、应用启动完成」。
只验成功路径的迁移不算做完。

## 6. 回滚

每片一个提交，回滚粒度 = 一个扩展。

- P1-a/b/c 回滚：删扩展文件 + 把原 `initXxx()` 调用加回 `initialize()`
- P1-d 回滚：删除 `extension-loader.ts` 与 `extensions.json` 读取，内置扩展不受影响
- P1-f 回滚：云同步本来就是最后做的，回滚等于不做

## 7. 启动基线（2026-10-20 13:29 实测）

```
S0-app-shell 74ms  S1-perf 14ms  S1b-extensions 2ms  S2-S5-ui 1140ms
S6-config 69ms     S7-services 6817ms              S8-post-ready 361ms
```

P1-a 把 perf 从 S1 移到 S6.5 后，S1 会消失、S6.5 会新增约 15ms。
**S7 的 6.8s 不变**——那是技能种子与 Agent Runtime，属于 P2 的服务分解，不在本计划范围。

若某片让总启动增长 > 100ms，该片必须拆小或回滚。

## 8. 已知风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 单例被改成扩展私有 | `performanceMonitor` 等被十余处引用 | 扩展提供实例，宿主保留 getter，调用点不动 |
| 禁用路径没测 | 只测启用 → 禁用后炸在很晚的地方 | §5 的反例必须验 |
| 控制口改坏静默失败 | lumii-ui CLI 只报超时 | 每片后用 CLI 实跑一次 `status` |
| 外部扩展热重载内存泄漏 | ESM 无法真正卸载 | 接受并写进文档；标 `restart-required` 给 Native |
| 契约在 P1-f 才暴露缺口 | 云同步跨五个面 | 把 P1-f 放最后，契约先被前五项压稳 |

## 9. 与后续阶段的衔接

- P1 结束后，`extensions/` 目录就是 P2 服务分解的落点；
- P2 拆 `bridge.ts` 时，每个领域服务先成为 `S.xxx`，再考虑是否升级成扩展；
- 渲染层的 slot/card（P4）复用同一份 `LumiiPluginManifest`，不再定义第二套清单。
