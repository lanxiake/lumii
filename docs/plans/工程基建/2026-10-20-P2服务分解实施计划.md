## 2. 分解方案

### 2.1 先拆 getter（P2-1），再拆方法（P2-2）

22 个 getter 全部是 `get xxx() { return this.requireInitialized(this._xxx, 'xxx') }`，
它们不做业务，只做「初始化检查 + 透传」。把这一步做完，`bridge` 就失去服务定位器的角色，
剩下的才是真正的领域方法。

### 2.2 目标服务划分

| 服务 | 归属方法（示例） | 预估行数 |

| **SessionService** | `abort*` / `compact*` / `ensureConversationExists` / `listRecentConversations` / `getSessionContextUsage` / `restoreHistoryForInstance` / `hasStreamingMessages` | 500 |
| **ModelService** | `callLLM` / `setModelCatalogFromApi` / `setSessionPreferredModel*` / `clearInvalidSessionPreferredModels` / `calibrateSessionCharsPerToken` / `getSessionProviderInputTokens` | 350 |
| **McpService** | `callMcpTool` / `upsertMcpServer` / `removeMcpServer` / `reconnectMcpServer` / `stopMcpServers` / `readMcpConfigFile` / `writeMcpConfigFile` / `importMcpServers` / `getMcpStatus` | 500 |
| **ToolService** | `listTools` / `toggleTool` / `refreshAllInstanceTools` / `registerEvolvedTool` / `resolvePermission` / `waitForPermission` / `resolveAskUserQuestion` | 450 |
| **CronService** | `createLocalCronJobRecord` / `listLocalCronRuns` / `runCronJobManually` / `reloadLocalCronScheduler` / `triggerCronNotification` / `cancelBackgroundTask` | 350 |
| **ChannelService** | `enqueueWechatOutbox` / `notifyIncomingMessage` / `notifyNavigateToSession` / `pushChannelText` / `replayWechatWatchInbox` / `setWeixinMessageContext` | 300 |

以及向上述服务转发的门面方法（保留一版，便于调用方渐进迁移）。

### 2.3 服务的对外形态

每个服务同时提供两种取用方式：

1. **访问器**：`getSessionService()` —— 给 137 个现有调用方的机械替换路径
2. **扩展服务**：`S.session` —— 给扩展用（P1 已建立的 `kernel/services.ts`）

两者指向同一实例。不要为扩展另造一套。

## 3. 分片与顺序

### P2-0：前置修复（先做，约 2–3 天）

按反思文档 §4，把「实现落后于文档」和「高风险零测试」清掉：

| 项 | 验收 |
|---|---|
| `extension-loader` 单测 | 发现、revision 跳过、坏模块、卸载；用临时目录，不碰真实 `~/.lumii` |
| `extension-store` 单测 | 缺文件 / 坏 JSON / 结构不对 / 正常，四种都覆 |
| 热重载失败回滚 | 先加载后卸载：新版本失败时旧版本继续服务，日志有 warn |
| `effects` 拆成 `services` / `teardowns` | `/status` 与启动表同步改 |
| `DuplicateServiceError` 带上发起方 pluginId | 冲突日志能看出是谁 |
| `as never` 换成结构校验 | 外部模块先校验 `manifest.id` / `definition.apply` 再收窄 |

**为什么放最前**：后面每一片都要靠热重载与外部扩展做快速验证，而它们现在没有测试。

### P2-1：getter 拆解（进行中，方案已修正）

**原方案是错的，实测否掉了。** 2026-10-20 试跑一次：

1. ✅ `agent-runtime/accessors.ts` 已建：18 个仓储槽位 + `setAgentRuntimeRepos()` /
   `clearAgentRuntimeRepos()`，语义与桥上 getter 一致（未初始化即抛错）。
2. ✅ `bridge.initialize()` 末尾注册；关闭路径 `clearAgentRuntimeRepos()`；
   惰性创建的 `wikiLibraryMigrate` 单独补登。
3. ❌ **机械替换 61 处调用点 → 44 个测试失败**。原因：测试通过注入假 bridge
   （`{ conversationRepo: { saveMessage } }`）建立依赖注入缝，而模块级访问器绕过了注入物，
   被测代码直接抛「未初始化」。tsc 完全看不出这类断裂。
4. ❌ 同一改动还让 bridge 自己的早期路径挂掉：`initialize()` 里
   `finalizeAllStreamingMessages()` 跑在注册之前，getter 转发到访问器就抛
   `AgentRuntimeBridge not initialized (conversationRepo)`——真机 error 日志抓到。

**修正后的做法**：

- 访问器**只作为新增读取路径**存在，不替换调用点；桥上的 getter 保持直读私有字段
  （它被 bridge 自己的早期路径使用，那一刻访问器还没注册）。
- 真正要迁移某个模块时，**先改它的依赖获取方式**（构造参数注入、或经 `kernel/services`），
  再删掉它那一处 `bridge.xxxRepo`；顺序反了就会打断测试缝。
- 验收改为：某个模块「不再 import bridge 取仓储」，而不是全局 `grep` 计数归零。

#### 第二个样例：`ChannelAgentGateway`（2026-10-20）

用 `Pick<AgentRuntimeBridge, …>` 给渠道模块内部三处消费者收窄类型
（`channel-interaction-hub` / 两个上下文策略 / `session-manager`），共 14 个成员。
签名从桥上派生，改名即编译报错，不会漂移。

**四个渠道适配器不在范围内**，实测原因：它们把 `this.bridge` 原样转交给
`coding-dev-acp-run.ts` 的 `startRun({ bridge })`，那条链要的是整份门面。
只收窄适配器会当场编译失败——它们把 bridge 当**管道**用，不是消费者。
要收窄它们，必须先收窄 ACP 执行器，那是独立的一片。

结论：`bridge` 的耦合有两种——**消费者**（可以收窄）和**管道**（收窄会级联）。
`grep` 计数区分不了这两种，只能逐个读用法。

### P2-2：方法按域拆服务（约 3–4 周）

按 §2.2 的顺序，**从调用次数少的域开始**，每次迁移一个服务：

```
McpService → CronService → ChannelService → MaintenanceService
→ EvolutionService → ModelService → ToolService → SessionService
```

理由：`SessionService` 的 500 行里有会话主循环的交织，风险最高，放最后；
其余七个先做，用来把「服务形态 + 访问器 + 单测」的模板压稳。

每迁移一个服务：
- 新服务类持有它需要的 repo（从访问器取）
- bridge 上的对应方法改为一行转发，**不删**
- 新服务带自己的单测（至少覆盖「初始化前调用」「实例销毁后调用」两条边界）

### P2-3：阶段函数搬出 index.ts（约 1 周）

`prepareAppShell` / `initUiStages` / `initConfigAndWorkspace` / `initLocalServices` /
`startPostReadyServices` / `initChannelServices` 搬到 `main/kernel/stages/*.ts`。
它们依赖的模块级单例已经大半进了 `kernel/services.ts`，剩下的按同样方式补。

验收：`index.ts` ≤ 800 行；七个阶段各自独立文件；启动耗时不变。

### P2-4：门面收窄（约 1 周）

删除 bridge 上已被服务接管的转发方法，只留 Agent 核心入口。
此时 `bridge.ts` 应 ≤1200 行、方法 ≤40。

### P2-5：S7 启动治理 ✅ 已完成 2026-10-20（9.7s → 3.4s）

**猜的全错，测的全中。** 计划里写「可能是 `initSkillWatcher` 的全量扫描」，实测：

```
S7.1-seed-skills      30ms
S7.2-skill-runtime    70ms
S7.3-skill-watcher   149ms     ← 猜的这里，只占 1.5%
S7.4-agent-runtime  9416ms     ← 真正的大头
```

继续下钻到 `bridge.initialize()` 的七个子块，再下钻到「开库」那一段，找到三个真凶：

| 问题 | 证据 | 修法 |
|---|---|---|
| **开库备份每次都拷 306MB** | `backups/*.db.bak` 15:21、15:24 各一份，`fs.copyFileSync` 同步 | 24 小时内已有备份就跳过（每日定时备份仍在） |
| **自动 VACUUM 同步跑在启动路径** | `void maybeRunAutoVacuumSync(db, dbPath)` 名字里的 Sync 是真的：306MB 库 9.7s | 推迟 30 秒（`unref`）+ 7 天节流（旁路标记文件） |
| **`PRAGMA integrity_check` 全库扫描** | 开库路径 4.4s → 换 `quick_check` 后 3.0s | 启动用 `quick_check`；新增 `verifyDatabaseIntegrityFull` 留给维护路径 |

**验收结果**（2026-10-20 15:36，真机）：

```
S7-services        9669ms → 3447ms   （−64%）
bridge.initialize   8116ms → 3198ms
其余阶段不变（S0 58 / S2–S5 1079 / S6 55）
```

技能列表仍可正常查询（`S7.2-skill-runtime` 未改动，仅 70ms）。

**留给后续**：`open()` 里仍有约 3s（`migrate()` + `quick_check` + 空库判断）。
再往下要拆 `migrate()` 的每次启动成本，属于独立一片。

## 5. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 会话主循环被拆坏 | `SessionService` 与 Agent 事件流交织 | 放最后；先只拆 getter 与方法，不动事件路径 |
| 访问器引入初始化时序问题 | `requireInitialized` 原本在 bridge 上做检查 | 访问器保留同样的「未初始化即抛」语义，并有单测 |
| 机械替换偷改语义 | 批量替换可能漏掉可选链 | 每批后 tsc + 抽样人工核对；禁止用脚本改带 `?.` 的行 |
| 137 个调用方改不完 | 迁移期两套写法并存 | bridge 保留转发，允许长期并存；用 `grep` 计数追踪进度 |
| 启动优化掩盖问题 | 把同步改成后台可能丢日志/丢错误 | 改后台必须补「就绪事件 + 失败可见」，不能只测耗时 |
