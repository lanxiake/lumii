## 0. 结论先行

P3 的目标不是「把五个模块搬进 `extensions/`」，而是**让它们能被关掉、能在禁用时不拖累启动**。
按 P1/P2 的经验，先接线（生命周期），后搬家（目录），且**每个模块的可行性差别很大**：

| 模块 | 规模 | 能否懒激活 | 主要障碍 |
|---|---|---|---|
| 录屏 `screen-record/` | 3663 行 | ✅ 可以 | 依赖 ffmpeg 资产；窗口捕获要在主窗口就绪后 |
| 桌宠 `pet/` | 2726 行（+渲染层 13142） | ✅ 可以 | 渲染层未插件化（P4），P3 只能接主进程侧 |
| VCS `workspace-vcs/` + `project-git-*` | 2155 行 | ✅ 可以 | 历史上有「每消息全量哈希卡死主线程」的教训 |
| 编码后端 `coding-dev-*` | 10+ 文件 | ✅ 可以 | 外部 CLI 检测/安装，属于慢操作 |
| **语音 `voice/`** | **6712 行** | ❌ **不行** | **ONNX 顺序闸**，见 §1.1 |

**语音是唯一不可懒激活的**，原因不是设计取舍，是进程级原生约束。

## 1. 三个硬约束（都来自既有代码与实测）

### 1.1 语音必须在 E5 之前拿到 ONNX 运行时

`onnx-runtime-gate.ts` 记录的问题：进程里有两份 `onnxruntime.dll`（sherpa 1.27 / onnxruntime-node 1.14），
Windows 按**基名**解析，E5 先加载会让 VAD 绑到 1.14，加载 opset 27 的模型直接原生崩溃。

闸门状态机：

```
idle ──sherpaFirst()──> sherpaHolding ──sherpaDone()──> sherpaDone
  └──waitForSherpa()──> e5Running（不可逆；此后 sherpaFirst() 拒绝）
```

**推论（本计划最重要的一条）**：如果语音扩展被**禁用**，闸门停在 `idle`，E5 直接进入
`e5Running`；此时若用户**再启用**语音，`sherpaFirst()` 会被拒绝，VAD 起不来。

所以语音只能二选一：

- **A（推荐）**：语音在启动期激活（S1 之前），禁用时**同时**让闸门保持 `idle` 并跳过语音——
  语义是「本次进程不装 VAD」，跨进程重启后才可能启用；
- B：彻底懒激活，但必须给闸门加「语音不参与 → 允许 E5 先行 → 之后拒绝语音」的显式分支，
  并在 UI 上如实提示「启用语音需要重启」。

本计划选 **A**：实现最小，且与「自用客户端优先稳定」一致。禁用后重启即可恢复正常。

### 1.2 录屏依赖 ffmpeg，且必须在窗口就绪后

- `screen-record` 的录制/烧录/字幕都走 ffmpeg（资产插件 `ffmpeg`）；
- 窗口捕获需要主窗口存在，因此激活点不能早于 `createWindow`。

处理：扩展在 **S2–S5 之后**激活；`manifest` 里声明资产依赖，资产缺失时功能降级并在日志如实说明。

### 1.3 桌宠的渲染层不在 P3 范围

主进程 `pet/` 只有 2726 行（窗口、资产协议、模式切换 IPC），而渲染层 `pet/` 有 13142 行。
P3 只接主进程侧（窗口创建与 IPC 注册），渲染层跟随 P4 的 slot 化。

**这意味着 P3 完成时桌宠「能禁用」但「不能独立升级」**，要在文档里说清楚。

## 2. 每个模块的迁移形态

### 2.1 录屏（P3-a）✅ 已完成 2026-10-20

| 项 | 内容 |
|---|---|
| 现在 | `initScreenRecordService()` + `mountScreenRecordMediaServices()` 在 `initUiStages` 里 |
| 迁移 | 创建 `extensions/screen-record.ts`：装配 service、注册 IPC、挂 narrate/burn 服务 |
| 服务 | `S.screenRecord`（供 bridge / 托盘读） |
| teardown | `ctx.effect(() => service.flushBeforeQuit())`，把 `performCleanup` 里那段收进作用域 |
| 验收（已实测） | 启用：`[ext] com.lumii.screen-record active` → `录屏服务已装配`；禁用：`扩展已按配置禁用`、装配日志消失、应用照常启动 |

**实施时踩到的两个坑（都已修）：**

1. **`container.provide(key, fn)` 会把函数当工厂求值并缓存**，所以「getter 服务」拿到的是
   第一次的值。主窗口 getter 因此被缓存成 `null`，录屏扩展永远等不到窗口
   （表现为渲染层刷 `No handler registered for screen-record:status`）。
   改成显式 `LateRef<T> { get() }` 对象。`S.agentRuntime` 之前也有同样问题，一并修了。
2. **禁用后渲染层仍会查一次状态**，控制台刷 6 条 `No handler registered`——用户看到的是
   「坏了」而不是「关掉了」。补 `disabled-stub`，返回设计里本就有的
   `{ ok: false, error: 'disabled' }`。

### 2.2 VCS（P3-b）⏭️ 不做（2026-10-20 决策）

| 项 | 内容 |
|---|---|
| 现在 | `workspace-vcs/` + `project-git-status.ts` 由 IPC 层直接调用 |
| 迁移 | 创建扩展，提供 `S.vcs`；文件系统监听放进作用域 |
| 特别要求 | **必须带节流**：2026-10 曾因每消息全量哈希把主线程卡 20 秒。扩展激活时打印监听策略（节流间隔、忽略规则），禁用时清理 watcher |
| 验收 | 禁用后工作区不监听、`vcs:*` IPC 不注册；启用后 Git 状态正常且 CPU 无可观测尖峰 |
| **实际结论** | **不做。** 实测 `workspace-vcs/` 里没有 `fs.watch`、没有长生命周期对象，只有一组用户触发的 IPC handler（`log`/`statusDiff`/`ensureInit`/`commit`/`rollback`）。搬进扩展的收益是「0 个可管理资源」，代价是禁用后渲染层打开 VCS 面板会报 no-handler，还得再补一个桩。<br>计划里写的「节流 + watcher 清理」针对的是一个**不存在的 watcher**——那次 20 秒卡顿来自每回合快照（`workspace-turn-snapshot`），是 hook 不是 watcher，需要的是**事件/钩子贡献点**（P2 之后才有），不是扩展。 |

### 2.3 语音（P3-c）✅ 已完成 2026-10-20（唯一不可懒激活）

| 项 | 内容 |
|---|---|
| 现在 | `initAgentRuntime` 里内联：建 `VoiceModelManager` / `VoiceCallService`、注册 IPC、预热 VAD |
| 迁移 | `extensions/voice.ts`，**激活点必须在 bridge 初始化之前**（保持现有顺序） |
| 顺序保全 | 扩展内先 `sherpaFirst()`，预热完成后 `sherpaDone()`；禁用时**不调用** `sherpaFirst()`，闸门留 `idle` |
| 资产 | 模型（ASR/TTS/VAD）走资产插件，缺模型时语音入口显示「需下载」而不是报错 |
| 验收（已实测） | 启用：`语音通话服务已注册` → `VadEngine 初始化完成` → `AsrEngine 初始化完成` → 启动完成；闸门顺序正确，无原生崩溃 |
| 时序 | 装配等 `app:window-ready`：窗口在 S2–S5 建、bridge 在 S7 初始化，**装配点天然落在两者之间的唯一合法窗口** |
| 已知限制 | 禁用后本进程无法再启用语音（闸门已 idle→e5Running），恢复需重启；这是既有语义，已写进扩展注释 |
| 非回归核对 | 预热报 `Edge TTS 403`，今天 10:40 起就存在（共 42 次），与本次迁移无关 |

## 3. 分片顺序与验收

按「风险 × 增量」排序，不按模块大小：

```
P3-a 录屏      ← 最小、有明确产物（文件），验证扩展能持有长期资源
P3-b VCS       ← 有性能前科，验证扩展能带节流与 watcher 清理
P3-c 语音      ← 唯一有原生崩溃风险，放中间（前两片已把契约压稳）
P3-d 编码后端  ← 外部进程，验证资产依赖
P3-e 桌宠      ← 依赖窗口与渲染层，风险最高，放最后
```

每片的验收模板（与 P1 一致）：

1. 禁用 → 对应日志消失、IPC 不注册、应用照常启动；
2. 启用 → 功能可用（按模块的真实产物验证，不是看日志好看）；
3. 启动耗时不变差（当前基线：S1-extensions ≈10ms、S7-services ≈2.9s）；
4. `pnpm -r typecheck` 干净、相关测试通过。

**每片必须验「反例」**：让扩展 `apply()` 抛错，确认只该扩展 failed、其余正常、应用能启动。

## 5. 风险与回滚

| 风险 | 说明 | 对策 |
|---|---|---|
| **语音原生崩溃** | 闸门顺序错 → 进程级崩溃（Exit 4294930435） | 激活点固定在 bridge 之前；禁用时保持 idle；两种路径都实跑 |
| 录屏 ffmpeg 缺失 | 用户没装资产 | 扩展激活时检测，缺就降级并如实提示，不抛 |
| VCS 卡主线程 | 历史事故（每消息全量哈希 20s） | 扩展内节流 + 只监听工作区；验收看 CPU 尖峰 |
| 桌宠窗口遗留 | 禁用时窗口未销毁 | teardown 里显式 dispose 窗口与 IPC |
| 编码后端 CLI 缺失 | 外部依赖 | 检测失败 → 扩展 failed 但应用正常（宿主既有语义） |
| 扩展顺序耦合 | 语音必须先于 bridge | 在 `plugin-host.ts` 的清单里用注释标死顺序，并加启动期断言（若闸门已 e5Running 则拒绝激活语音并报错） |

**回滚**：每片独立提交，回滚=删对应扩展文件 + 把原 `initXxx()` 调用加回 `initialize()`。
