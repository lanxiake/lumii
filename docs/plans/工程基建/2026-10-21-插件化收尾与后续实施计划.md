## 0. 结论先行

**已经没有「必须做才能用」的项了。** 插件系统的能力闭环（卡片 / 整页 / 设置分区 /
启停 / 热更新 / 示例生成）都在，剩下的工作分两类，不要混在一起排期：

| 类别 | 含义 | 排期 |
|---|---|---|
| **清债（S1）** | 门禁是红的，每次跑全量都要人工分辨「这 4 条是不是我弄的」 | 现在做 |
| **增量（S2/S3）** | 服务层模板、用真实插件压出缺口 | 紧接着做 |
| **按需（S4/S5）** | cron/数据库/阶段拆解、分发 | **不排期**，等触发条件 |

一条重要判断写在这里，避免以后反复讨论：

> **剩余重构不阻塞任何功能。** `initializeCronScheduler`(487) / `initializeDatabaseAndRepos`(252) /
> `index.ts` 的阶段函数，只在**要改那块代码时**才值得先拆。为行数拆它们是用回归风险换一个好看的数字。

## 2. 口径统一（决策项）

设计索引写「P5 完成时 `bridge.ts` ≤300 行」，P2 计划写「P2-4 后 ≤1200 行、公有方法 ≤40」。
**取后者**，并把索引改掉：

- 300 行的前提是「bridge 不留任何转发方法」，意味着 137 个调用点一次性改完——
  这正是 P2-1 试过并回滚的路（44 个测试失败，测试注入的假 bridge 被绕过）。
- 转发方法是**调用方渐进迁移的保险**：服务搬走、桥上一行转发、调用点不动。
- 真正该压的是**公有方法数**（135 → 40），行数自然跟着降。

## 4. S2 服务层模板：`McpService`（1 天）

### 4.1 为什么是它

bridge 里的 9 个 MCP 方法**已经是一行转发**到 `McpManager`（`getMcpStatus` / `callMcpTool` /
`stopMcpServers` / `readMcpConfigFile` / `writeMcpConfigFile` / `upsertMcpServer` /
`importMcpServers` / `removeMcpServer` / `reconnectMcpServer`）。
也就是说**领域逻辑早就搬完了，缺的只是服务层那三件套**。

### 4.2 做法

```
main/agent-runtime/services/mcp-service.ts    # 新增：包住 McpManager，注册进 S.mcp
main/agent-runtime/services/registry.ts       # 可选：getMcpService() accessor
```

1. `McpService` 持有 `McpManager`，方法一行转发（**不重新实现**）；
2. 注册进内核服务容器：`S.mcp = createServiceKey<McpService>('mcp')`；
3. bridge 的方法改为 `return getMcpService().xxx(...)`，**签名不变**；
4. 单测两条边界：**未初始化时调用**、**管理器销毁后调用**。

### 4.3 验收

- `typecheck` 0；全量无新增失败；
- 插件侧可以用 `ctx.get(S.mcp)` 直接拿服务（这是「插件能调用内部服务」的第一个真实样例）；
- bridge 行数**预期不变**——这一片的产出是模板与插件能力，不是减行。

### 4.4 复用到其余 8 个域

顺序照 P2 计划：`Cron → Channel → Maintenance → Evolution → Model → Tool → Session`。
每个 0.5–1 天；`SessionService` 最后（与主循环交织）。
**不要一次做三个以上**——每片都要跑全量，堆着做等于放弃门禁。

## 5. S3 用真实插件压缺口（1–2 天，价值最高）

### 5.1 为什么现在做

P0–P5 的能力是**按设计**验证的（示例插件、demo 卡片），没有按**真实需求**验证过。
再拆 500 行 bridge 不会暴露「插件缺什么」，写一个真想用的插件会。

### 5.2 做法

1. 从下面挑一个（或用户另提）：
   - **资讯卡片增强**：概览页 `dashboard.main` 里给情报加「按话题过滤 + 收藏」；
   - **会话快捷操作**：`app.nav` 加一个入口，列出最近未读会话并直达；
   - **工作日报面板**：`app.view` 整页，读 `~/.lumii` 下的日报数据画一张表。
2. 只在 `~/.lumii/plugins/` 里写，**不改仓库代码**；
3. 遇到缺口记成清单，**先判断是不是该开放的能力**，再决定补不补。

### 5.3 预期会撞到的三类问题（提前写在这里）

| 类型 | 例子 | 处理 |
|---|---|---|
| 数据拿不到 | 插件只能拿 `React` / 注册 API，读不到应用数据 | 这是最大的缺口。候选解法：给插件开放只读的 IPC 白名单，或注入一个 `lumii` 数据客户端 |
| 样式不同源 | `classNames` 只覆盖侧栏导航 | 需要补「设计令牌暴露」（把 CSS 变量表交给插件） |
| 生命周期 | 插件页面切走时要不要卸载 | 目前 `app.view` 常驻挂载，插件自己处理 |

### 5.4 产出

`docs/standards/plugin-development-standards.md`——只写**踩过的坑**，
不抄 P5 §5 的契约表（那份已经在计划里，抄一遍会分叉）。

## 7. S5 分发（可选，2–3 天）

前提三件，缺一不做：

1. **版本兼容**：manifest 的 `engines.lumii` 必须在安装/加载时真校验并给可读错误；

3. **更新策略**：装了的插件谁负责升级、失败如何回滚。

不做：插件市场 UI、搜索、评分——本地路径分发已经够自用。

## 9. 纪律（每片都适用）

1. **先量后改**：拆之前先数行数/调用点/赋值，计划的字面顺序经常被实测推翻（P2-3 就是）。
2. **动过 `src/main/**` 必须跑全量**：`cd apps/windows && pnpm test:all`。
3. **抽函数模板**：显式 deps（结构类型收窄，不 import 大对象）+ 独立测试 + 守卫跟着代码走。
4. **组合根不外提**：依赖 >20 个或「每个都是 getter」时，留在类里。
5. **提交按文件显式 add**；提交信息写清「为什么」与「验证命令」。
