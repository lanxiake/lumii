# 聊天真实模拟测试用例（L3）

> 规范：[CLI-TEST-SPEC.md](../CLI-TEST-SPEC.md)
> 定位：**最接近用户真实操作的测试**——用 `lumii-ui` CLI 创建会话、发送消息（真实 LLM 回合）、观察落库/日志/回复，验证功能在真实对话中按预期工作。
> 执行器：`run-chat-core-suite.mjs`、`run-chat-memory-suite.mjs`、`run-chat-compression-suite.mjs`、`run-chat-wiki-suite.mjs`
> 前置：应用运行中（`pnpm dev`）、chat 模型已配置、应用日志可读（`~/.lumii/logs/app/mtbot-<日期>.log`，日志断言依赖；注意仓库根 `.lumii-dev.log` 是停滞的历史文件，不可用）。共享库 `lib/cli-harness.mjs`。

约定：
- 全部会话标题带 `[chat-suite]` 前缀（探针命名空间）。
- 硬断言 = 落库/文件/字段/日志可达确定性；软断言 = LLM 语义（宽松匹配 + 最多 1 次重试）。
- 「回合」= 一次 `send` 触发的完整回复（30–120 秒）。

---

## 一、核心对话体验（run-chat-core-suite.mjs）

#### CHAT-CORE-01 发送→回复→持久化
- **优先级**: P0 ｜ **预计回合**: 1
- **步骤**: 创建会话 → `sendAndWait` 发一条简单消息 → `context messages` 与 DB `messages` 表对比
- **预期**: 会话内出现 user + assistant 消息；DB 落库条数与 CLI 读取一致
- **断言**: 硬（消息角色序列、计数一致）

#### CHAT-CORE-02 多轮上下文记忆
- **优先级**: P0 ｜ **预计回合**: 3
- **步骤**: 第 1 轮告知「我的幸运数字是 47」→ 第 2 轮闲聊 → 第 3 轮问「我的幸运数字是多少」
- **预期**: 第 3 轮回复包含 47
- **断言**: 软（关键词「47」；失败允许换会话重试 1 次）

#### CHAT-CORE-03 编辑消息（edit 负反馈信号）
- **优先级**: P1 ｜ **预计回合**: 0（不发新回合）
- **步骤**: 发一条消息等回复 → 取 user 消息 ID → `send edit` 改正文
- **预期**: DB 该消息内容更新为编辑后文本；CLI 读取一致
- **断言**: 硬（内容变更落库）

#### CHAT-CORE-04 编辑并重发（resend 信号）
- **优先级**: P1 ｜ **预计回合**: 1
- **步骤**: `send resend` 修改上一条 user 消息并触发新回答
- **预期**: 产生新的 assistant 回复；会话消息数增长
- **断言**: 硬（新回复落库）
- **备注**: 运行时负反馈信号键名（`feedback:*`）以实际实现为准，证据中记录观察值

#### CHAT-CORE-05 中止回复（abort）
- **优先级**: P1 ｜ **预计回合**: 1（被中止）+ 1（验证回合）
- **步骤**: 发一条要求长输出的消息 → 2.5 秒后 `send abort` → **等待会话安静（生成可能继续完成并落库）** → 再发一条短消息
- **预期**: abort 命令被接受；会话保持可用（后续消息正常回复）
- **断言**: 硬（abort 命令 ok + 后续回合成功）；**不做「回复不完整」断言**（中止为尽力而为语义）
- **实测观察（2026-09-12）**: abort 后生成长文（2703 字）仍完整落库、未截断；生成期间发送的后续消息会排队等待，排队时长可超过 3 分钟——等待策略必须先等会话安静，且后续消息窗口放宽（240s）

#### CHAT-CORE-06 双会话隔离
- **优先级**: P0 ｜ **预计回合**: 2
- **步骤**: 创建两个会话 A/B → 各发一条带独特标记的消息（A 用「菠萝」，B 用「哈密瓜」）
- **预期**: A 会话上下文不含「哈密瓜」相关内容；B 会话不含「菠萝」（各自 user 消息互不出现）
- **断言**: 硬（消息列表交叉检查）

#### CHAT-CORE-07 参数错误处理
- **优先级**: P1 ｜ **预计回合**: 0
- **步骤**: `send` 缺 `--session`；`send --session <sk>` 缺文本
- **预期**: 退出码非 0，不产生消息
- **断言**: 硬（退出码 + 会话消息数不变）

#### CHAT-CORE-08 会话列表可见性
- **优先级**: P2 ｜ **预计回合**: 0
- **步骤**: `conversation list` 查找探针会话
- **预期**: 返回列表包含 `[chat-suite]` 前缀的会话
- **断言**: 硬（列表包含）

## 二、记忆链路（run-chat-memory-suite.mjs）——场景记忆重点

> 探针数据：`_registry.json` 注册探针项目 `chat-probe-project`（别名 `chat-probe-alias`），场景文件 `project-chat-probe-project.md` 含特有词「蓝色协议」。套件开始快照、结束恢复（`CHAT_NO_RESTORE=1` 跳过恢复）。

#### CHAT-MEM-01 对话透露偏好 → 记忆提取落盘
- **优先级**: P0 ｜ **预计回合**: 1–2
- **步骤**: 发「请记住：我写代码时习惯用 pnpm 而不是 npm」→ 轮询 `user-memory.md` mtime 变化（≤90s）
- **预期**: 记忆文件更新且包含「pnpm」相关内容
- **断言**: 硬（mtime 变化）+ 软（内容关键词）
- **备注**: 提取为 LLM 判定 + 异步管道，未触发时记 SKIP 并注明（非产品缺陷）

#### CHAT-MEM-02 memory_search 可检索已写入记忆
- **优先级**: P1 ｜ **预计回合**: 0
- **步骤**: `memory search pnpm`
- **预期**: 返回结果包含 MEM-01 写入的内容
- **断言**: 硬（命中条目）
- **依赖**: MEM-01 已 PASS（未 PASS 则 SKIP）

#### CHAT-MEM-03 场景记忆命中注入（正例）
- **优先级**: P0 ｜ **预计回合**: 1
- **步骤**: 记录日志游标 → 发含探针别名「chat-probe-alias」的消息 → 等回合完成
- **预期**: 日志出现 `[buildSceneMemorySections] 注入场景记忆 scene=project key=chat-probe-project`；回复可体现「蓝色协议」相关内容
- **断言**: 硬（日志标记）+ 软（回复提及探针内容）

#### CHAT-MEM-04 场景记忆不注入（负例）
- **优先级**: P0 ｜ **预计回合**: 1
- **步骤**: 记录日志游标 → 发与探针无关的普通消息 → 等回合完成
- **预期**: 该窗口日志**无** `chat-probe-project` 注入标记
- **断言**: 硬（日志无匹配）

#### CHAT-MEM-05 scene_memory 工具写入探针场景
- **优先级**: P0 ｜ **预计回合**: 1–2
- **步骤**: 发「记住：在 chat-probe-alias 项目里，提交前必须先跑 pnpm typecheck」
- **预期**: 探针场景文件出现该约定（agent 调 `scene_memory` 工具而非写全局）
- **断言**: 硬（场景文件内容）+ 软（回复确认）
- **备注**: 若 agent 未调用工具（直接回答不记录），记 FAIL(soft) 或 SKIP 并注明观察

#### CHAT-MEM-06 全局记忆无污染
- **优先级**: P0 ｜ **预计回合**: 0
- **步骤**: MEM-05 完成后读取全局 `user-memory.md`
- **预期**: 不含「typecheck/提交前」等场景约定内容
- **断言**: 硬（字符串不存在）
- **依赖**: MEM-05 有写入行为时才有意义（否则 SKIP）

#### CHAT-MEM-07 主动回忆（记忆召回）
- **优先级**: P2 ｜ **预计回合**: 1
- **步骤**: 发「你还记得我在这个项目上说过什么约定吗？」（同会话续 MEM-05）
- **预期**: 回复提及 typecheck 约定（场景记忆在上下文）
- **断言**: 软

#### CHAT-MEM-08 渠道记忆（环境受限）
- **优先级**: P2 ｜ **预计回合**: 0
- **预期**: SKIP——渠道记忆需要真实渠道（微信/飞书）消息触发，CLI 会话为 ipc 渠道不具备条件；渠道验证在渠道联调时人工执行
- **断言**: SKIP（注明原因）

#### CHAT-MEM-09 探针注册表一致性
- **优先级**: P0 ｜ **预计回合**: 0
- **步骤**: 套件开始时读取 `_registry.json`
- **预期**: 探针项目项存在（key/aliases 正确），命中解析可依赖
- **断言**: 硬

## 三、上下文压缩（run-chat-compression-suite.mjs）

#### CHAT-CMP-01 手动压缩基本流
- **优先级**: P0 ｜ **预计回合**: 2（先造消息）
- **步骤**: 发 2 轮消息 → `context compact --keep 2`
- **预期**: 命令返回压缩前后消息数；压缩后 CLI 可见摘要就位（摘要消息/标记）
- **断言**: 硬（前后计数 + 摘要存在）
- **备注**: 压缩具体形态（摘要消息角色/字段）以实现为准，证据记录

#### CHAT-CMP-02 压缩后仍记得早期事实
- **优先级**: P0 ｜ **预计回合**: 1–2
- **步骤**: 造 3 轮（第 1 轮埋「我的幸运数字是 47」）→ compact → 问「我的幸运数字是多少」
- **预期**: 回复包含 47（来自摘要而非原文）
- **断言**: 软（关键词「47」）

#### CHAT-CMP-03 context usage 字段一致性
- **优先级**: P1 ｜ **预计回合**: 0
- **步骤**: `context usage`
- **预期**: 返回 usedTokens/contextWindow/阈值字段；usedTokens > 0
- **断言**: 硬（字段齐备）

#### CHAT-CMP-04 压缩后会话可用
- **优先级**: P0 ｜ **预计回合**: 1
- **步骤**: compact 后立即发新消息
- **预期**: 正常回复；消息继续落库
- **断言**: 硬

#### CHAT-CMP-05 压缩后原文保留（可追溯）
- **优先级**: P1 ｜ **预计回合**: 0
- **步骤**: compact 后查询 DB `messages` 原历史
- **预期**: 压缩不删除原始消息记录（被压缩的旧消息仍在 DB）
- **断言**: 硬（计数不减少）

#### CHAT-CMP-06 压缩中止（abort）不破坏会话
- **优先级**: P2 ｜ **预计回合**: 0
- **步骤**: 对未处于压缩中的会话调用 `context abort`
- **预期**: 返回明确响应（成功或「无进行中压缩」语义），会话仍可用
- **断言**: 硬（响应结构 + 会话消息可读）

## 四、Wiki 摄入（run-chat-wiki-suite.mjs）

> 背景：记忆重构一期起「聊天摄入 Wiki」已切断——聊天消息不再自动产生收件箱条目。本套件验证「切断」后的真实行为与检索链路。

#### CHAT-WIKI-01 聊天提问触发 wiki 检索
- **优先级**: P0 ｜ **预计回合**: 1
- **前置**: Wiki 库中有资料（`wiki source list` 非空）
- **步骤**: 发「我知识库里有哪些资料？用 wiki 工具查一下」
- **预期**: agent 调用 wiki 工具（toolCalls 记录可见）；回复列出资料
- **断言**: 硬（assistant 消息 toolCalls 含 wiki 工具）+ 软（回复含资料名）
- **依赖**: 库空则 SKIP

#### CHAT-WIKI-02 聊天消息不自动摄入（负例）
- **优先级**: P0 ｜ **预计回合**: 1
- **步骤**: 记录 `wiki_inbox` 计数 → 发一段密集知识内容（「以下是一段资料……请记住」）→ 等回合 → 复查计数
- **预期**: inbox 计数不变（聊天不自动摄入，设计如此）
- **断言**: 硬（计数不变）

#### CHAT-WIKI-03 指定资料读取（wiki_read 链路）
- **优先级**: P1 ｜ **预计回合**: 1
- **前置**: `wiki source list` 取一个资料标题
- **步骤**: 发「帮我读一下知识库里的《<标题>》，概括一下」
- **预期**: agent 调用 wiki_read（toolCalls）；回复概括内容
- **断言**: 硬（工具调用）+ 软（概括语义）
- **依赖**: 库空则 SKIP

#### CHAT-WIKI-04 检索不到时的行为
- **优先级**: P2 ｜ **预计回合**: 1
- **步骤**: 发「我的知识库里有没有关于『不存在的量子面条理论』的资料？」
- **预期**: agent 检索后如实说明未找到（不编造）
- **断言**: 软（回复含「没有/未找到」语义，且不编造资料名）

#### CHAT-WIKI-05 CLI 播种 → 聊天检索闭环
- **优先级**: P2 ｜ **预计回合**: 1
- **步骤**: 用 `wiki folder import`（或 `command` 总线）导入一个临时标记文件（含特有词「青花瓷协议」）→ 等导入完成 → 聊天问「知识库里『青花瓷协议』是什么」
- **预期**: 检索命中新资料；回复提及
- **断言**: 硬（导入落库）+ 软（回复命中特有词）
- **备注**: 导入链路复杂（可能触发 agent 归档），失败降级 SKIP 并记录链路现状

## 执行与开关

| 环境变量 | 作用 |
|---|---|
| `CHAT_ONLY=<前缀>` | 只跑匹配 ID 的用例（如 `CHAT-MEM`） |
| `CHAT_SKIP_LLM=1` | 跳过需要 LLM 回合的用例（记 SKIP） |
| `CHAT_TURN_TIMEOUT_MS` | 单回合等待超时（默认 180000） |
| `CHAT_NO_RESTORE=1` | 探针写入（registry/scene/user-memory）结束后不恢复，供人工检查 |
| `CHAT_VERBOSE=1` | 打印每条用例的中间证据 |

## 已知限制

1. 渠道记忆（微信/飞书）无法经 CLI 验证——需真实渠道联调（CHAT-MEM-08 SKIP）。
2. 自动压缩触发需要接近上下文窗口极限（固定开销巨大），成本高——本轮以手动压缩验证链路，自动触发由 autonomous 套件与人工观察覆盖。
3. Wiki 摄入链路处于「切断自动摄入」设计下的验证（WIKI-02 为负例断言），导入闭环（WIKI-05）可能受后台归档任务异步性影响。
4. 全部断言依赖真实 LLM，非 100% 确定性——软断言采用宽松匹配 + 1 次重试策略。
5. **测试产物清理**：测试消息会经真实记忆链路提取（这是链路正确工作的证据）——CORE-02 的「幸运数字 47」、MEM-01 的「pnpm 偏好」可能写入全局 `user-memory.md`，套件结束自动按行清理探针句（`CHAT_NO_RESTORE=1` 保留供人工检查）。首次全量运行曾发现「幸运数字 47」已实际落盘，验证清理逻辑有效。
6. **abort 语义**：中止为尽力而为——实测 abort 后生成仍可能完整落库；生成期间发送的后续消息会排队（排队超 3 分钟的个案见 CORE-05 观察）。断言策略不依赖「中止生效」，只验证「命令被接受 + 会话最终可用」。
