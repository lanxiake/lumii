> 对应计划：[06-体验深挖-地基篇](../../../plans/专项Agent/06-体验深挖-地基篇.md)
> 驱动脚本：[run-agent-deepdive-e2e.mjs](./run-agent-deepdive-e2e.mjs)
> 规范：[CLI-TEST-SPEC.md](../CLI-TEST-SPEC.md)

## 一、目的

把「体验深挖 · 地基篇」（G1 共享层 / G2 通知 / G3 委托可见 / G4 协作通路）的**人工验收项**转成
CLI 驱动的真实使用旅程：经 `lumii-ui` 操作真实运行的客户端与真实 LLM，断言用户视角能看到的东西
（会话消息、界面元素、系统通知日志、落库数据），而不是只看单元测试。

原则（沿用既往套件约定）：
- 用例必须走**用户真实动作路径**（建会话 → 说人话 → 看结果），不播种 DB、不直调内部函数；
- 触碰用户数据的用例必须自带**范围约束 + 事后红线校验**（详见 §五 事故记录）；
- 概率性行为（模型是否委托/是否用某工具）允许重试，但失败要留证据，不用软断言掩盖。

## 三、执行

```bash
# 全量（父进程编排：非 UI 用例并发 3，UI 用例串行）
node docs/test/lumii-cli/agent-deepdive/run-agent-deepdive-e2e.mjs

# 只跑若干条（父子进程都认 G1-01 / DD-G1-01 两种写法）
DD_ONLY=G1-01,G1-02 node docs/test/lumii-cli/agent-deepdive/run-agent-deepdive-e2e.mjs

# 调并发度 / 超时 / 追加转交场景
DD_CONCURRENCY=5 DD_TURN_TIMEOUT_MS=300000 DD_WITH_HANDOFF=1 node docs/test/lumii-cli/agent-deepdive/run-agent-deepdive-e2e.mjs
```

产物：`agent-deepdive-evidence.jsonl`（逐条原始证据）+ `agent-deepdive-report.md`（概要/逐条/失败明细）。
子进程各自写 `agent-deepdive-<CASE>-evidence.jsonl`，父进程合并后删除。

**并行约束**：`group=ui` 的用例会操作用户界面（切会话/截图/点击），彼此以及与任何截图/点击操作
都不能并发；`group=parallel` 的用例只用 CLI 会话通道 + 只读 DB + 日志，互不干扰。

## 四、用例细节

### DD-G1-01 专家私有记忆 · 跨会话复述

- 修复前：工作记忆注入硬编码 `assistant`，专家写进 `agent_memories` 的内容永远注不回模型 →
  换个会话再问 = 失忆（这正是「越用越准」在专家身上断掉的原因）。
- 步骤：建 `system-keeper` 会话 → 说「请记住：我的发布口令是 LUMII-DD-913…」→
  轮询 `agent_memories` 探针行（写入侧）→ 另建一个全新 `system-keeper` 会话问口令（注入侧）。
- 清理：按 id 删除探针记忆；若误写 `user-memory.md` 则按行清理。
- 若记忆走的是用户级 `user-memory.md`（全员可见）而非专家私有记忆 → SKIP（无法验证 G1 注入修复）。

### DD-G1-02 共享资料库 · 维护官读到全库

- 修复前：wiki 工具按实例 `definitionId` 解析归属 → 维护官读的是自己那份 4 条空库。
- 步骤：建 `system-keeper` 会话 → 问「我的资料库里现在有多少条资料」→ 断言：
  1. 会话里出现过 `wiki_overview` / `wiki_search` / `wiki_read` 调用（归因到共享层，而不是绕过工具直接查库）；
  2. 回复里的数字落在共享库 ±20%（修复前只会出现 4 或「没有资料」）；
  3. 回复不含「资料库为空/没有资料」。
- 红线：归档计数与有效集逐条比对，必须零变化。
- 备注：不采用「主助手委托维护官」路径——实测「看资料库」类请求主助手会自理（自己调 wiki 工具），
  只有「整理」类诉求才委托；直接找维护官问现状同样是真实旅程，且判别力更强。

### DD-G2-01 定时任务失败 · 桌面通知外推

- 修复前：失败零通知（只在定时任务页可见），命中的任务等于静默消失。
- 步骤：`cron:create` 造一个 `agentId` 指向不存在定义的任务（模拟配置损坏）→ `cron run` →
  断言运行记录 `error` + 日志 `[AgentRuntime:CronNotify]`/`[DesktopNotify]` 含任务名与 `cron:<id>`。
- 清理：删除探针任务与它的运行记录（finally）。失败通知本身是验证证据，会真实弹到系统通知。

### DD-G3-01 委托在会话界面可见（卡片）

- 修复前：委托在父会话只是折叠工具行「调用子 Agent 1 次」，等于隐形（富卡片是死代码）。
- 步骤：现场发起一次委托 → `goto chat` + 侧栏点开会话（**轮询等待会话出现在侧栏**，新建会话的渲染层刷新有延迟）→
  截图 refs 断言存在「团队委托」按钮且名称含专家名 → 点击（最多 3 次重试，ref 会失效）→
  断言按钮名里的「详情」变为「收起」或出现任务/产出标签。
- 数据来源：卡片全部取自工具 part（args + jsonToolResult），所以历史回放、断线重连都能重现。

### DD-G4-01 传话 · 送达 + 落库可见

- 修复前：`send_message` 空闲实例入队不唤醒；消息不落库 → 用户完全看不到协作痕迹。
- 语义（2026-09-13 拍板后）：`send_message` = **对正在跑的任务追加要求/纠偏**（`to` = spawn 返回的实例 id 或专家名）；
  已结束的任务不可达，应重新委托。
- 步骤（两轮真实旅程）：第 1 轮派一个后台长任务（8 条、多源核对，保证第 2 轮时实例仍存活）→
  第 2 轮「它还在跑，帮我给它带句话：优先看中文来源」（未触发工具则改用显式点名话术）→
  断言 `send_message` 返回 ok + 会话里出现「【传话】…」。
- 时序要点：回合判定用「跳过带 sourceAgent 的子产出消息」的 `lastParentAssistant`；
  实例在任务完成后即回收（拍板不做持久信箱），此时 not found 属已知边界 → 记 INFO 并整体重试。
- 实测发现：同一轮里「派活 + 嘱咐」会被模型折叠进委托 prompt（0 次 send_message）；
  拆两轮、任务仍在跑时追加才能稳定触发。

### DD-G2-02 后台委托完成 · 桌面通知

- 修复前：`agent:subagent:completed` 渲染层是空实现，后台委托完成后用户毫无感知。
- 步骤：主助手 async 委托灵栖情报（必须 `mode=async`，sync 没有「完成通知」可言；模型有概率选 sync，
  用例用两次递增明确度的话术重试，仍不后台则 SKIP）→ 界面切到别的会话 →
  等日志 `[Subagent] complete child=<instanceId>` → 断言存在 `convId="<父会话>"` 的 `[DesktopNotify]` 行且带状态文案。
- 匹配纪律：完成行用 **子实例 id**（同名专家在并发用例里会撞车）；通知行用 **父会话 sessionKey**（日志窗口里混着别的用例的通知）。
- 日志游标必须在发消息**之前**取：切界面/截图可能耗时数分钟，子 Agent 会在那之前就跑完（首跑即因此漏判）。
- 设计依据：渲染层只在「不在父会话或窗口失焦」时弹通知，切走即满足条件。
- 实测补充：并行压测下子 Agent 可能被判 stale（180s 无进度）→ 通知状态为「已超时」，同样计入通过。

## 五、红线与事故记录

**2026-09-13 事故**：G1-02 首版用例用「帮我整理下我的资料库」话术，维护官按策展职责真的执行了整理——
分两批归档 84 条（有效条目 298 → 212），并写入若干整理报告类条目。经用户确认后全部
`wiki source archive --restore` 恢复（有效条目回到 298，库内总数 303 = 原有 299 + 4 条整理报告产物）。

由此确定的用例纪律：
1. 只读类用例的话术必须显式写「只看不动，不要改动/归档/删除」；
2. 用例体内前置快照 + 事后逐条校验（归档计数、有效集 id 集合），越界即 FAIL；
3. 会改数据的操作一律在 finally 里恢复，并把恢复口径写进报告。

## 六、副作用声明与覆盖限制

副作用：
- 探针会话（`[deepdive] *`）保留待人工清理（CLI 无删除能力）；
- 探针记忆行、探针定时任务（含运行记录）已清理；
- 套件期间后台 cron 临时禁用，结束恢复；
- G2-01 的失败通知为真实系统通知。

未覆盖（由单测或人工覆盖）：
- 转交通知（G2-3）默认不跑（需 code-dev 绑定 + claude CLI，`DD_WITH_HANDOFF=1` 启用）；
- 反思/日记「不弹窗、只推渲染层」（G2-4）：渲染层 DOM 无法经 CLI 断言，由 `agent-runtime-store.test.ts` 覆盖；
- `send_message` 空闲唤醒分支：真实旅程中专家完成后实例即销毁，难命中 idle 窗口，由 `orchestrator.test.ts` 覆盖；
- 「正在父会话且窗口聚焦 → 不弹通知」：CLI 难稳定复现前台聚焦，由单测覆盖。
