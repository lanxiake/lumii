# 渠道会话路由 手工验收用例（CR 套件）

> 对应实现：[10-渠道会话路由重构](../../../plans/专项Agent/10-渠道会话路由重构.md)（S1-S6，提交 `e8af97ea` → `cb2aa48d`）。
> 相关：[05-队长制](../../../plans/专项Agent/05-队长制-主助手接团队.md) §七（转交）、[09-项目上下文路由](../../../plans/专项Agent/09-项目上下文路由.md)（P2/P3）。
> **执行方式：手工**（本套件不接 CLI harness——要点分布在客户端界面、渠道消息与真实 CLI 三处，脚本化收益低于维护成本）。
> **设计原则：以真实使用场景为主轴**——每条都是一个「用户带着真实诉求走一遍」的旅程，不是接口冒烟。
> 可观测面：客户端界面 / 渠道消息 / 应用日志 `~/.lumii/logs/app/mtbot-<日期>.log` / 运行库 `~/.lumii/data/agent-runtime.db` / 开发上下文 `~/.lumii/config/coding-dev-backends/dev-context.json`。

## 零、执行前置（必做）

1. **重启应用**：本套件全部用例都要求重启后的新构建（主进程改动不会热更新）。
2. **确认迁移落地**（只读，任选终端）：

```bash
node -e "const {DatabaseSync}=require('node:sqlite');const os=require('os'),p=require('path');
const db=new DatabaseSync(p.join(os.homedir(),'.lumii/data/agent-runtime.db'),{readOnly:true});
console.log('schemaVersion=',db.prepare(\"SELECT value FROM runtime_state WHERE key='schemaVersion'\").get()?.value);
console.log(db.prepare('SELECT channel_type, COUNT(*) c FROM conversations GROUP BY channel_type').all());"
```

期望：`schemaVersion=41`，各渠道计数与升级前一致，**没有 NULL**。

3. **准备两个渠道**：至少一个即时通讯渠道（QQ 或微信）已连接，且客户端可正常收发。

**时间紧就只跑这 5 条**：CR-01、CR-03、CR-08、CR-10、CR-13。

## 一、用户旅程地图（为什么是这些用例）

| 真实旅程 | 用户期望 | 用例 |
|---|---|---|
| 🚀「升级后打开客户端，一切照旧」 | 悄悄迁移完，会话与分组不变 | CR-01、CR-02 |
| 💬「在 QQ 让它改个项目里的东西，干完了告诉我」 | 不用点确认；干完**在 QQ 收到结果** | CR-03、CR-04、CR-05 |
| 🗂️「微信/QQ/客户端各自的会话别混在一起」 | 分组与来源标注正确 | CR-06、CR-07 |
| ↩️「切错会话了，怎么回去」 | `/back` 在任何渠道都是「回到自己的会话」 | CR-08、CR-09 |
| 🔧「微信里设了项目，换到 QQ 接着说」 | 项目与编码工具**跟着会话走** | CR-10、CR-11、CR-12 |
| 🔔「我在客户端聊了一半，去微信接着说」 | 微信里提示我一句，我说「接续」就过去了；**不回也不会被擅自换会话** | CR-13 ~ CR-16 |
| 🧹「别再有莫名其妙的行为」 | 渠道里不该再出现「回复 1 确认」之类话术；命令面符合各渠道能力 | CR-17、CR-18 |

## 二、用例

### A. 迁移与开关

#### CR-01 升级后静默迁移，会话分组不变
- **故事**：用户升级到含 V41 迁移的版本，只关心「我的会话还在不在、分组对不对」
- **前置**：完成前置 1、2
- **步骤**：1) 重启应用 2) 看侧栏会话列表 3) 查看运行库 `conversations.channel_type`
- **预期**：会话数量与升级前一致；微信/QQ/飞书/企微各在自己的分组，客户端会话在「默认」；`channel_type` 全部有值
- **断言**：`schemaVersion=41`=硬；无 NULL=硬；分组显示正确=硬
- **失败先看**：日志 `[load] 载入 N 条活跃会话记录`；若某会话归错组，看它的 `channel_type` 落库值

#### CR-02 接续开关在「设置 → 实验功能」，且改完即生效
- **故事**：用户想开/关跨渠道接续提示，但不想为此重启应用
- **步骤**：1) 打开 设置 → 实验功能，找到「跨渠道会话接续」（应显示当前状态）2) 进详情切换开关 3) 返回列表确认状态已变 4) 去「设置 → 渠道设置」确认**那里不再有这个开关** 5) 立刻在渠道发一条消息（不必重启）
- **预期**：开关位置正确；切换后立即生效（开启时按 CR-13 表现，关闭时渠道消息一律留在本渠道会话）
- **断言**：位置=硬；渠道设置里已移除=硬；无需重启即生效=硬

### B. 渠道转交结果回流

#### CR-03 渠道发起转交 → 完成后渠道收到结果（本套件最重要的一条）
- **故事**：用户在 QQ 说「帮我改 lumii 项目里的 X」，然后放下手机去干别的
- **前置**：已注册项目 + 「灵栖开发」已绑定编码 CLI（设置 → 开发）
- **步骤**：1) 在 QQ 发一句项目级任务 2) 观察主助手回复 3) 打开「灵栖开发」开发会话看过程 4) 等任务跑完后回到 QQ
- **预期**：
  - 主助手**不要求确认**，直接说已交给灵栖开发；
  - 开发会话里能看到工具调用实时滚动、最后有完整回复文本；
  - **QQ 收到**「✅ 转交完成：「…」+ 结果摘要」
- **断言**：不要求确认=硬；渠道收到完成汇报=硬（本轮修复的核心）；开发会话过程可见=硬；回复文本非空=硬
- **失败先看**：日志 `[handoff] 结果已推送到渠道 sessionKey=…`；
  - 若为 `无该会话的回复上下文` → 应用在任务执行期间重启过（已知边界：回复上下文只在进程内）；
  - 若开发会话是「（Claude Code 无输出）」→ CLI 输出解析问题，收集该会话的消息与日志

#### CR-04 未绑定编码工具时，渠道也收到明确指引（不再假成功）
- **故事**：用户没配绑定就想转交，得知道自己缺什么
- **前置**：临时清掉「灵栖开发」的 Agent 绑定，且默认编码后端为「灵栖内置」（`/lumii`）
- **步骤**：1) 在渠道发一句项目级任务 2) 看渠道回复与原（主助手）会话
- **预期**：渠道收到 `⚠️ 灵栖开发还没有绑定编码工具…`（含两条出路：配绑定 / 本会话 `/claude` 切换）；**不会**说「转交完成」；不留空会话
- **断言**：明确拒绝=硬；不留空开发会话=硬
- **失败先看**：日志 `[runDevHandoff] 拒绝执行：未绑定编码工具`

#### CR-05 汇报发到「此刻你在的那个渠道」
- **故事**：用户同一会话先在微信聊、后用 QQ 接着聊，转交的汇报应该出现在**最后说话的地方**
- **步骤**：1) 微信里让主助手转交一个任务 2) 任务执行期间在 QQ 里对同一会话说句话 3) 等任务完成
- **预期**：汇报出现在**最后发言的渠道**（本例为 QQ）；数据库里该会话有一条 `✅ 转交完成…` 消息
- **断言**：汇报渠道=最后发言渠道=硬（这是「按 Hub 路由推送」而非「按会话键前缀猜」的直接验证）
- **失败先看**：日志 `[pushText] 已推送异步消息到渠道 sessionKey=…`

### C. 身份与分组

#### CR-06 渠道会话的归属与来源标注正确
- **步骤**：1) 桌面侧栏看各分组 2) 在渠道里发 `/resume` 看列表分组与来源标签
- **预期**：两侧一致；被 `/link` 绑定到微信的客户端会话在 `/resume` 里标「微信」
- **断言**：分组正确=硬

#### CR-07（可选）渠道偏好按会话归属加载
- **故事**：同一条会话被两个渠道续聊时，场景记忆/渠道偏好应跟着**会话归属**走
- **步骤**：给某渠道准备一份渠道场景文件，跨渠道续聊该会话，观察注入内容
- **断言**：软（观察项；无渠道场景文件时可跳过）

### D. 路由一致性

#### CR-08 `/back` 在四个渠道语义一致
- **步骤**：1) 在渠道 A 用 `/resume` 切到另一条会话 2) 确认后续消息确实进了那条会话 3) 发 `/back` 4) 再发一句话
- **预期**：`/back` 后消息回到**本渠道自己的会话**；四渠道表现一致（微信不再有额外副作用）
- **断言**：回到 own=硬；重启后仍生效=硬（见 CR-09）
- **失败先看**：运行库 `SELECT value FROM runtime_state WHERE key LIKE 'channel:active:%'` —— 看 `active` / `own` / `source` 三个字段

#### CR-09 路由持久化 + 指向已删会话时拒绝写入
- **步骤**：1) 渠道里 `/resume` 切到某会话 2) 重启应用 3) 再发一句话确认仍在那个会话 4) 在客户端删掉那条目标会话 5) 再发一句话
- **预期**：重启后路由保持；目标会话被删后**不会**被静默重建成空会话
- **断言**：重启保持=硬；不重建空会话=硬
- **失败先看**：日志 `[setActive] 目标会话不存在，路由不变`

### E. 项目与编码工具跟随会话

#### CR-10 微信设项目 → 换渠道继续，项目还在（本计划的核心卖点）
- **步骤**：1) 微信里 `/project <已注册项目名>`（回执应显示项目与目录）2) 用 `/resume` 在 QQ 或桌面切到**同一条**会话 3) 问「当前开发项目是什么」
- **预期**：仍是那个项目；`dev-context.json` 里的键是**裸会话 id**（不是 `账号:会话id`）
- **断言**：项目跟随=硬
- **失败先看**：`~/.lumii/config/coding-dev-backends/dev-context.json` 的键格式；日志里 ACP 的 `cwd=`

#### CR-11 微信切编码工具 → 换渠道继续，工具不变
- **步骤**：1) 微信里 `/claude` 2) 换渠道继续同一会话，发一句话 3) 看回复形态/日志
- **预期**：仍走 claude（不是回落到内置）；`/backend` 显示一致
- **断言**：工具跟随=硬

#### CR-12 老 dev-context 文件兼容（升级不丢选择）
- **前置**：升级前 `dev-context.json` 里已有 `local-user:<会话id>` 形式的记录
- **步骤**：1) 升级重启 2) 打开那条会话，看模式 chip / `/project`
- **预期**：原项目选择仍生效（旧键可读）；**再次写入后**该会话的键变成裸会话 id，旧键被清掉
- **断言**：旧选择不丢=硬；写入即迁移=软

### F. 接续提示（S4 + S5）

#### CR-13 提示出现，且本条消息照常被回答
- **前置**：设置 → 实验功能 → 打开「跨渠道会话接续」；客户端有一条近期进行中的对话
- **步骤**：1) 在渠道发一句**普通消息**（非斜杠命令）2) 观察渠道回复
- **预期**：收到「检测到你在【客户端】有进行中的对话：「…」/ 回复「接续」继续那条对话（本条消息仍在这里回答），回复「不接续」忽略。」——**并且这条消息本身被正常回答**（旧版会把它扣住等答复）
- **断言**：提示出现=硬；本条消息被回答=硬（S4 的核心）
- **失败先看**：日志 `[maybeNotice] 已提示接续 …`；若当前会话归属不属于本渠道（比如你在别的渠道借来的会话里），按设计**不提示**

#### CR-14 「接续」生效 / 「不接续」不变 / 不回不变
- **步骤**：1) 收到提示后回「接续」→ 再发一句话，确认进了那条目标会话 2) 另起一次，回「不接续」→ 确认仍在原会话 3) 另起一次，**什么都不回**，直接发下一句 → 确认仍在原会话
- **预期**：三种答复各自符合预期；`不接续`/不回**都不会**改变路由（旧版「1 分钟不回默认接续」已废除）
- **断言**：接续生效=硬；默认不变=硬

#### CR-15 提示过期与幂等
- **步骤**：1) 收到提示后等 10 分钟以上再回「接续」2) 另起一次，接续成功后连回两次「接续」
- **预期**：过期的「接续」不再生效（当普通消息处理）；接续只生效一次
- **断言**：过期失效=硬；只生效一次=硬

#### CR-16 与审批提示不打架
- **故事**：用户同时可能收到审批请求与接续提示，两者都问「回复什么」会让人不知道在答哪个
- **步骤**：1) 制造一个审批挂起（例如让 Agent 执行需审批的工具）2) 在该会话里发一句话，观察是否同时冒出接续提示 3) 回「1」
- **预期**：**审批挂起期间不出现接续提示**；回「1」被审批消费（不是被接续吃掉）；接续提示改用中文词「接续/不接续」，与审批的 1/2/3 在词面上就分得开
- **断言**：不并发打扰=硬；「1」归审批=硬

### G. 卫生回归

#### CR-17 渠道命令面符合各渠道能力
- **步骤**：分别在微信/飞书 与 QQ/企微 里发 `/project`、`/claude`、`/help`
- **预期**：微信/飞书能识别；**QQ/企微**回「未知命令 + 可用命令列表」（它们是未接 ACP 的渠道）；`/help` 各渠道都列出自己实际支持的命令
- **断言**：能力边界与文档一致=硬；未知命令有明确提示=硬

#### CR-18 渠道里不再出现「回复 1 确认」话术
- **步骤**：在渠道发起一次转交，通读主助手与卡片/回执文案
- **预期**：全程没有「回复 1 确认」「确认后才会开始执行」一类措辞；接续提示也只要求「接续/不接续」
- **断言**：文案无不一致=硬

## 三、回归底线（跑完必看）

- 渠道与客户端**原有功能不受影响**：微信/QQ 收发消息正常、`/new`、`/clear`、`/stop`、`/link`、`/resume` 行为与升级前一致；

- 定时任务（若有）到点仍能推送；
