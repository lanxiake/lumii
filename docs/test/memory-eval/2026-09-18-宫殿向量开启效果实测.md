## 2. 检索质量：生产口径 A/B 是**变差**

### 测法与评测集

- 脚本：`scripts/palace-prod-ab.mjs`（口径逐条对齐生产源码：FTS 候选池 30 +
  最小命中 2 + 向量余弦 top-30 + RRF k=60 + `content.slice(0,300)` 语料）
- 评测集：`docs/test/memory-eval/palace-eval-set-v6.json`
  （查询 = **真实用户提问**；gold = **同一会话中该提问之前归档的最近一条抽屉**。
  因果由 `palace_drawers.created_at` × `messages.timestamp` 的时间序保证；
  实测仅 5/31 的 gold 含查询原文，**不是循环**）

### 结果（n=31）

| | R@1 | R@5 | R@10 |
| --- | --- | --- | --- |
| 纯 FTS（开关关闭时的实际行为） | **19/31** | 22/31 | 22/31 |
| 开向量（FTS + 向量 RRF） | **7/31** | 13/31 | 19/31 |

**开启向量使 R@1 从 19/31 掉到 7/31。**

## 3. 为什么变差：两个叠加的机制

### 机制一：向量语料只有前 300 字，而长抽屉的关键信息在后面

`palace-vector.ts` 用 `content.slice(0, 300)` 做向量语料（为与 T1 跑分口径一致）。
而宫殿抽屉平均 1673 字，且**开头常是原始日志粘贴**。

对 v6 的 31 条 gold 统计查询词的位置：

| 位置 | 条数 |
| --- | --- |
| 只在 300 字内命中（向量看得见） | 6 |
| **只在 300 字外命中（向量看不见）** | **14** |
| 内外都有 | 3 |
| 完全没命中 | 8 |

**17/31（55%）的 gold 对向量通道是"不可见"的。**

实例（探针话题 `sjzh-service` 的 gold，48042 字）：

```
语料（前 300 字）= "root@...:~# docker logs -t --tail 500 95994806a535 | grep -iE -C20 ... 2026-09-12T04:00..."
查询词在全文中的首次出现位置：
  「故障」 无   「排查」 无   「服务」 无   「日志」 无   「进程」 无   「重启」 无
  「启动」 286（唯一一个，勉强在窗口内）
```

用户问的是"排查的完整过程"，而向量看到的是 300 字的原始日志头。

### 机制二：RRF **奖励「两边都还行」、惩罚「一边独占第一」**

`reciprocalRankFusion`（k=60）：`score(d) = 1/(60+ftsRank) + 1/(60+vecRank)`。

- FTS 的 #1 得 `1/61 = 0.0164`
- 一条 **FTS #30 + 向量 #1** 得 `1/90 + 1/61 = 0.0275` —— **比 FTS 第一名高 68%**

`scripts/diag-rrf-displacement.mjs` 在失败的 case 上看到的**是同一种形状**：

```
gold 4ec3a715: fts=#1  vec=缺席  → 融合后 #8
  挤在它前面的：
    fts=#3  vec=#1   ← 两边都高
    fts=#5  vec=#2   ← 两边都高
    fts=#10 vec=#8
    ...
```

gold 在向量那一路**缺席**（因为它不在 top-30 向量命中里，或语义上确实是那个 300 字窗口看不出来），
于是一条排名得 0——**FTS 的第一名就这样输给了"两边都中游/上游"的条目**。

这不是实现 bug，是 RRF 的固有性质。它只有在**两路都携带有效信息**时才是净收益；
当一路在目标上系统性失明（机制一），它就纯是拖累。

## 4. 语料窗口消融：放宽有帮助，但**不足以转正**

`scripts/exp-palace-corpus-window.mjs` 用同一套查询（n=31）重新编码全部抽屉，只换语料窗口：

| 配置 | R@1 | R@5 | R@10 | 编码耗时 |
| --- | --- | --- | --- | --- |
| 纯 FTS（基线） | **19/31** | 22/31 | 22/31 | — |
| w300（**当前生产**） | 7/31 | 15/31 | 19/31 | 63s |
| w1000 | **12/31** | 19/31 | **22/31** | 152s |
| w3000 | 9/31 | 18/31 | 22/31 | 149s |
| full4000 | 9/31 | 18/31 | 22/31 | 146s |

三点读法：

1. **当前窗口（300）是最差的一档**——比"不截断"低 5 个 R@1。截断确实在伤它。
2. **w1000 是窗口档里最好的**，且 R@10 已打平纯 FTS。但 **R@1/R@5 仍低于纯 FTS**
   （12 vs 19、19 vs 22）。
3. **继续放宽（3000/full）反而回落**：更长的语料被平均池化稀释，语义中心更模糊。

**结论不变**：放宽窗口能把损失减半，但**不能让无条件融合变成正收益**。
根子在机制二（RRF 的算术），窗口只是加剧项。

## 5. 融合策略对比：**条件启用是零损失的安全解**

`scripts/exp-palace-fusion-strategies.mjs` 在同一套查询（n=31）上比各策略：

| 策略 | R@1 | R@5 | R@10 |
| --- | --- | --- | --- |
| `fts`（对照） | **19/31** | **22/31** | **22/31** |
| `vec-only`（只用向量） | 6/31 | 8/31 | 9/31 |
| `rrf10`（k=10） | 8/31 | 18/31 | 20/31 |
| `rrf60`（**当前生产**） | 7/31 | 13/31 | 19/31 |
| `rrf200`（k=200） | 7/31 | 13/31 | 19/31 |
| `fts-then-vec`（FTS 空时才用向量） | **19/31** | **22/31** | **22/31** |
| `rrf-on-weak`（FTS 结果 <5 条才融合） | **19/31** | **22/31** | **22/31** |

三个结论：

1. **不是 k 的问题**：k 从 10 换到 200，R@1 只在 7~8 之间徘徊，全都远低于纯 FTS。
   调到最优参数也救不了无条件融合。
2. **向量单独比 FTS 差得多**（R@1 6/31 vs 19/31）——它在本语料上**不是**一个能独立
   承担召回的通道。
3. **条件启用策略与纯 FTS 完全打平**（19/22/22，逐档相同）。本集子里 FTS 没有
   "弱到触发回退"的查询，所以向量一次都没上场——**既没救到，也没伤到**。
   这正是期望的安全性质：**永远不比 FTS 差**。

## 6. 结论

1. **开关默认关（`DEFAULT_LUMII_PALACE_VECTOR = '0'`）在当前数据下是正确的。**
   本机实测支持这个决定，不是保守。
2. **绝不要以当前的「无条件融合」打开它**——会把 R@1 从 19/31 打到 7/31。
3. **要打开就先改成条件启用**（`fts-then-vec` 或 `rrf-on-weak`）：实测零损失，
   且保留了「FTS 找不到时才指望语义」的理论价值。
4. 这几条都是**可反驳**的：换评测集（尤其换成真正的措辞错配集）结论可能变化。

## 7. 下一步（按价值排序）

1. **把 `searchDrawersHybrid` 改成条件启用**——这是让该功能"可安全打开"的前提。
   建议用 `rrf-on-weak`（带阈值），而不是 `fts-then-vec`：后者只在 FTS **完全为空**
   时回退，而"FTS 只找到 1~2 条沾边的"同样是该让语义出场的场景。
   **阈值需要单独调**——本次数据里没有落在该区间的查询，调不出依据。
2. **语料窗口若要用，选 1000**（消融档里最好，R@10 打平纯 FTS），且必须**重建索引**。
   注意：换窗口 = 换口径，T1 的历史结论不再适用。
3. **建一个真正的「措辞错配集」**——v6 证明了这个需求（见 §8），但本机真实样本不够，
   需要人工构造 + 明确标注其局限性。
4. **评测集继续扩**：31 条里一条翻转 ≈ ±3.2pp，够看趋势、不够定精度。

## 8. 这个评测集的效度边界（**结论不能外推的部分**）

### 8.1 向量救援实验：0/9

`scripts/exp-palace-vector-rescue.mjs` 单独问「FTS 完全漏掉的查询里，向量救得回几个」：

| 语料窗口 | 救回 |
| --- | --- |
| w300 | **0/9** |
| w1000 | **0/9** |
| full4000 | **0/9** |

放宽窗口、甚至用全文，**一个都没救回来**。

### 8.2 但逐条看，这 9 条**大多不该被救**

FTS 漏掉的 9 条查询是：

```
截图看下电脑管家页面是否打开
按照当前HTML风格样式重写上述行动清单，然后发送给我
删除资料库里面关于技能的文件。
刚才发了什么消息 [语音转录: ...]
将ch01-Agent系统演化全景.md发送给我
AI 时代普通程序员行动清单.md  是这个文件中的内容
1.尽量使用在线样式，降低代码编写难度和代码量。 2.文字背后还是有…
使用开发AGENT删除【07-新手指引-评审.md】文档
现在你可以看到企业微信群了吗。我@你了
```

**它们全是「动作指令」，不是「回忆过去」。** 用户在下达操作、追问当前状态、
指定文件——这类查询的正确响应是**执行/回答**，而不是"把同会话之前的归档找回来"。

也就是说：**这 9 条的 gold 标注本身是错的**，向量"没救回"是正确行为，
把它记成失败是评测集的效度缺陷，不是向量通道的缺陷。

### 8.3 由此得出的边界

| 本报告能说的 | 本报告**不能**说的 |
| --- | --- |
| 在「同会话前序归档」这个标注下，无条件融合使 R@1 从 19/31 掉到 7/31 | 「向量检索对记忆宫殿没有价值」——**未测** |
| 语料 300 字窗口是该配置下最差的一档 | 「向量在真实语义改写场景无效」——**本集子里这类样本太少** |
| 融合的挤占机制（RRF 算术）确实存在且可复现 | 「改策略后一定有提升」——待测（见 §5） |

**v6 集子的根本局限**：它的 gold 是「同一会话里更早归档的那条」，
而真实检索里**大量查询根本不是回忆型的**（本次实测占 9/31 ≈ 29%）。
要测「语义改写能不能救」，需要的是**专门的措辞错配集**
（v1 那 8 条是这个方向，但样本太小、且措辞由人编写）。

### 8.4 已知的口径缺憾（不是本次引入）

- `palace_drawers` 无 title/summary 字段，向量只能用截断原文。若上游能提供
  `memory_segments` 的总结，换成摘要会明显更好——**但那需要重跑 T1**。
- 探测脚本产物（`NO_REPLY`、`PROBE-OK-*`）也进了索引，数量是个位数，暂不过滤。
