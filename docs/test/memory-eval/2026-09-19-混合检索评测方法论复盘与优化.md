## 1. 三个结构性缺陷（已用数据确认）

### 1.1 致命：判据是"全库任一文档含查询原句"，不是"命中 gold"

v6 的每条样本 `expect` **就是 query 本身**（31/31 完全相同），而跑分脚本的判定是：

```js
const isGold = (id) => byId.get(id)?.includes(q.expect[0])   // 全库扫子串
```

于是"命中"的定义变成了「返回的抽屉里**任何一条**包含这句话」，而不是「命中标注的
那条 `gold`」。实测满足该判据的抽屉条数分布（n=31）：

| 全库满足 `isGold` 的抽屉数 | 条数 | 后果 |
| --- | --- | --- |
| 0 条 | **8** | 判据永远为假 → 无论算法多好都是 0 分 |
| 1 条 | 9 | 看似唯一，但**其中 0 条是标注的 gold** |
| 多条 | **14** | 撞上任意一条即满分 |

**同一套 FTS、同一批查询，仅换判据**：

| 判据 | R@1 | R@10 | 完全漏 |
| --- | --- | --- | --- |
| 子串命中（v6 报告用的） | **19/31** | 22/31 | — |
| 命中标注的 `gold` 抽屉 | **3/31** | 20/31 | 4 |

逐条可见判据在**反向**打分。典型：

```
v6-a71aa23b-092014   子串=#1     真gold=MISS    ← 拿一条错抽屉记了满分
v6-8a17853d-133032   子串=#3     真gold=MISS
v6-c3971d7d-090405   子串=MISS   真gold=#2      ← 找对了却判错
v6-8c94fa77-020341   子串=MISS   真gold=#1      ← 找对且排第一，仍判错
```

复现：`node scripts/eval-criteria-contrast.mjs`

### 1.2 `expect` 只有 5/31 真的出现在 gold 里

生成器 `mine-palace-eval-v6.mjs` 的注释声称用 `content.slice(0, char_count)` 快照
校验过因果，但实际写进 `expect` 的是**用户提问原文**：

```js
expect: [text],      // text = 用户提问；而 gold 是提问【之前】归档的抽屉
```

gold 归档于提问之前，**当然不含这句提问**。实测 `expect` 出现在 gold 全文的只有
**5/31**，出现在归档快照的同样 5/31。那段快照校验只算了 `ctxOverlap`（bigram 覆盖
率）用于分层，**从未施加到 `expect` 上**。

### 1.3 8/31 存在时间泄漏

`goldArchivedAt >= askedAt` 的样本有 **8 条**——gold 是在提问同刻或之后归档的
（即 `ctxOverlap: 1`、`goldChars` 8000~15000 那批）。它们是"把这轮对话本身归档
了"，检索它等于检索当前上下文，不是回忆。

### 1.4 连带：81% 的查询不是检索任务

按动作/回忆特征词粗分（n=31）：

| 类型 | 条数 | 占比 |
| --- | --- | --- |
| 纯动作指令（"发给我"/"输出"/"删除"/"重写"） | **17** | 55% |
| 纯回忆型（"之前"/"刚才"/"记得"/"为什么"） | **6** | **19%** |
| 两者兼有 | 1 | 3% |
| 都不含 | 7 | 23% |

v6 报告 §8.2 已自行发现这点（记为"9 条 gold 标注是错的"），但**没有据此作废跑分**，
而是保留了 19/31 的结论。实际比例比它估的更糟：真正该测的只有 6 条。

### 1.5 缺陷的净效应

旧报告的核心论断「RRF 使 R@1 从 19/31 掉到 7/31」两侧都不可用：

- **19 不是真实基线**：子串判据下 14 条查询存在多个"正确答案"，bm25 撞上任一个的
  概率被系统性抬高
- **7 也不是真实的融合表现**：它同样在错判据下测的
- 换成唯一正确答案后纯 FTS 只有 **3/31**——**融合的效果必须重测**

### 1.6 一个被旧报告完全漏掉的信号

按真 gold，FTS 是 **R@1=3/31 但 R@10=20/31**。gold 大量落在 **#2~#17**：

```
真gold 位次分布：#1×3  #2×7  #3×2  #4×1  #5×3  #6×1  #9×2  #11×2  #15×3  #16×1  #17×1  MISS×4
```

**召回基本够了，排序是短板**——这正是 rerank 的典型适用形态。旧报告因判据错误
（子串判据下 R@1 就有 19，看着"头部已经很好"）完全没往这个方向看。

## 2. 为什么不能靠挖掘修补 v6

尝试过一条更硬的标注路径：`memory_segments.palace_drawer_id` 提供了
**段 → 抽屉 1:1 硬链路**，且段有 `start_message_id`/`end_message_id` 消息区间，
可以精确反推"哪些消息进了哪个抽屉"，判据落在 `drawer_id` 上而非子串。

结果：

- 有 `palace_drawer_id` 的段只有 **77/276**，其中抽屉未删且区间完整的 **71** 条
- 由此能构造的"段结束后的下一条用户提问" 候选 **38** 条
- 但这 38 条**仍以动作指令为主**（"将完成后的html发送到微信"、"继续输出后续课程内容"）

**结论**：本机真实数据里天然缺少回忆型查询。`memory_search` 的宫殿通道在生产中
被调用的场景本就少，用户更多是在下达操作。靠挖掘拿不到合格的评测集，必须改变
标注策略（见第 3 节）。

复现：`node scripts/probe-hard-linked-eval.mjs`

## 3. 外部方案调研（有实证支撑的部分）

### 3.1 融合：凸组合 > RRF，且「有界性」是关键

Bruch et al. *An Analysis of Fusion Functions for Hybrid Retrieval*
（[arXiv:2210.11934](https://arxiv.org/html/2210.11934v2)，TOIS 2023）直接回答了我们的问题：

- **凸组合显著优于 RRF**：MS MARCO 上 TM2C2 的 nDCG@1000 = 0.454 vs RRF 0.425
- **k=60 不是原理常数**，只是 Cormack et al.（[SIGIR 2009](https://dl.acm.org/doi/10.1145/1571941.1572114)）
  在 TREC 上调出来的值。我们实测 k=10~200 几乎无差别，与论文"RRF 参数跨域不迁移"一致
- **归一化方式本身不重要**（min-max 与 z-score 在均匀伸缩下秩等价），但**不归一化会严重退化**
- **推荐 α ∈ [0.6, 0.8]**（α 为稀疏路权重），且 <5% 训练数据即收敛——对小评测集是好消息
- **一路系统性失明时，boundedness 比什么都重要**：per-query min-max 会把失明那路的噪声
  **拉伸到满量程**，故论文推荐 TM2（theoretical min-max，用理论界而非 batch 内实际 min/max）

### 3.2 长文档：late chunking 做不了，退 chunk + max-pooling

- Late chunking（[arXiv:2409.04701](https://arxiv.org/abs/2409.04701)）在长文档上增益可观
  （NFCorpus nDCG@10 23.46→29.98），但要求**整篇过一遍 transformer** 再按 chunk 边界 mean-pool
- **e5-small 只有 512 token 窗口，做不了 late chunking** —— 硬约束，不是取舍
- 退路：朴素 chunk + max-pooling。论文里 "no chunking" 在部分数据集上反而略胜 late chunking，
  说明差距不大，而这条在本机可落地

### 3.3 评测方法论

- 判据泄漏是经典 bug。**gold 必须是文档 ID，不是文本匹配**；query 必须与 gold 文本解耦。
  DuReader-retrieval（[EMNLP 2022](https://aclanthology.org/2022.emnlp-main.357/)）甚至专门删除
  与 dev/test 语义相近的训练 query 来防泄漏
- **多 gold 是常态**：C-MTEB 的 T2Retrieval 平均每 query **5.21 条**相关文档
- 指标分工：**Recall@k** 诊断召回层（决定 rerank 天花板）、**MRR@10** 诊断头部、**nDCG@10** 综合
- 样本量：31 条远不够。Voorhees & Buckley（[SIGIR 2002](https://dl.acm.org/doi/10.1145/564376.564432)）
  表明 50 topic 下小差异错误率已可观。Sanderson et al.（[IR 2019](https://marksanderson.org/files/papers/IR2019.pdf)）
  论证**「多 query + 浅标注」优于「少 query + 深标注」**——故策略是扩 query 数、每条只标 1~3 个 gold

## 4. v7 评测集（已建成）

`docs/test/memory-eval/palace-eval-set-v7-seed.json`，**34 条人工标注**。

### 4.1 三条硬规则

1. **gold 是 `drawer_id`，判据不做任何子串匹配** —— 从根上消除 §1.1 的缺陷
2. **query 由标注者另行措辞**，刻意避开抽屉原文用词 —— 消除 §1.2 的泄漏
3. **全部是回忆型查询**，不含动作指令 —— 修正 §1.4 的 81% 无效样本

标注方式：读抽屉原文（前 700 字）后手写「用户会怎么回头问这件事」，并按 `intent`
分层：`lexical`（字面词能命中）/ `paraphrase`（换了说法）/ `semantic`（几乎无字面重叠）。

### 4.2 健康检查（跑算法之前先证明评测集没病）

`node scripts/validate-eval-set.mjs`：

| 检查项 | v6 | v7 |
| --- | --- | --- |
| gold 缺失/已删 | — | **0** ✅ |
| 判据泄漏（query 原样在 gold 里） | 5/31 | **0/34** ✅ |
| query↔gold bigram 重叠 | 8 条 =1.000 | 均值 **0.362**，最大 0.611 |
| 回忆型占比 | 19% | **100%** |

intent 分层的重叠梯度自洽，说明分层标注不是拍脑袋：

```

semantic    n=14  平均重叠 0.329
```

### 4.3 池化补判（已做）

只标"最明显那条 gold"会把**找到另一条同样正确的抽屉**误判为失败。本库同主题
抽屉大量重复——讲 `exit 3` 的 7 条、讲 `oldString not found` 的 8 条、
讲 `flush-hosts` 的 **57** 条。不补判就是系统性低估所有方案。

做法（对齐 BEIR / T2Ranking）：

1. `pool-candidates-for-judging.mjs` —— 四路（fts / vec / convex α=0.6 / rrf k=60）
   top-10 **并集**为待判池（不是单系统 top-K，否则池子自带方案偏见），共 978 条
2. 聚焦**最优方案 top-2 内的未判项**（62 条）——它们直接决定 R@1 / MRR
3. **人工逐条读原文判定**。关键词自动判已验证不可靠（`落盘` 命中 142 条）
4. `merge-judgments.mjs` 合并

结果：**追加 22 个 gold，多 gold 查询从 1 条 → 19 条**。

补判后所有方案的绝对值都上移，印证了低估的存在：

| | 补判前 | 补判后 |
| --- | --- | --- |
| `fts` nDCG@10 | 0.752 | **0.844** |
| convex α=0.6 nDCG@10 | 0.818 | **0.906** |

**但排序与相对优势完全不变**——结论是稳的。

#### 争议样本：发现一条 gold 标错了

`v7-040`（"我问机票比价那次，你说之前根本没聊过？"）召回的
`3666eae7dff565f4` 里**含机票比价的实际方案原文**（9/27 出发 + 10/1 返程
¥902/人），与 gold"我说之前根本没聊过"直接矛盾 → **历史上确实聊过，
gold 的前提站不住**。

标为 `disputed` 并从评测中**排除**，而不是硬塞任一边。故最终 n=53。

### 4.4 剩余局限（必须随结论一起报告）

- **53 条仍不够**：一条翻转 ≈ ±1.9pp。按 Sanderson 的结论应扩到 150+
- **单标注者**：我自己读抽屉、自己出题、自己补判，无第二人复核，存在标注者偏差
- **补判只做了 top-2**：top-3~10 区间还有约 158 个未判项。按 BEIR 经验这会
  **继续**低估——故当前所有指标应视为**保守下界**

## 5. 融合算法对比（正确判据 + 池化补判后）

`node scripts/palace-fusion-bench.mjs`，**n=53**（排除 1 条争议样本），
判据 = drawer_id，候选池 30。

| 策略 | nDCG@10 | MRR@10 | R@1 | Recall@30 |
| --- | --- | --- | --- | --- |
| **convex min-max α=0.6** | **0.906** | **0.917** | **45/53** | **1.000** |
| convex min-max α=0.7 | 0.901 | 0.910 | 44/53 | 1.000 |
| convex TM2 α=0.8 | 0.896 | 0.917 | 45/53 | 0.980 |
| convex TM2 α=0.6 | 0.894 | 0.906 | 44/53 | 1.000 |
| convex min-max α=0.8 | 0.884 | 0.893 | 43/53 | 1.000 |
| `fts`（基线） | 0.844 | 0.860 | 41/53 | 0.970 |
| rrf k=10 | 0.832 | 0.821 | 37/53 | 1.000 |
| **rrf k=60（当前生产）** | **0.794** | 0.772 | **34/53** | 1.000 |
| rrf k=200 | 0.794 | 0.772 | 34/53 | 1.000 |
| `vec`（基线） | 0.528 | 0.531 | 25/53 | 0.788 |

### 5.1 结论

1. **融合有效，但必须换掉 RRF**。凸组合 α=0.6 对纯 FTS：nDCG **+7.3%**
   （0.844→0.906）、R@1 **41→45**、Recall@30 **0.970→1.000**。
2. **RRF 比纯 FTS 更差**（0.794 vs 0.844，−5.9%）。旧报告这个方向性判断是对的，
   尽管它的数字不可用。k 从 10 换到 200 无实质差别 —— 与论文一致，
   **不是调参能救的**。
3. **向量单独很弱**（0.528）但**不可省**：它是 Recall@30 从 0.970 上到 1.000 的
   唯一来源，即 FTS 完全漏掉的那些查询只有它能捞回。
4. 分层看，增益主要在 `paraphrase`（0.874→0.938）；`semantic` 本来就不低
   （0.908→0.933）；`lexical` 两条恒为 1.000，融合不伤它。
5. **α 的最优区间 0.6~0.7**，与论文推荐的 [0.6, 0.8] 吻合。α=0.9（过度偏向稀疏）
   掉到 0.859，α=0.5（两路等权）掉到 0.878 —— 都不如 0.6。

### 5.2 一个与论文预期相反的发现：TM2 输给 min-max

论文推荐 TM2（理论界归一化），实测却是 min-max 更好（0.778 vs 0.733）。
定位到原因——**余弦的理论界 [-1, 1] 在本语料上只用到 3% 量程**：

```
候选池内余弦实际范围: 0.862 ~ 0.931
```

用 [-1,1] 归一化后，所有向量分被压成 ~0.93 的窄带，区分度几乎归零。
把界收紧到经验分位数后 TM2 追上来：

| bm25 界 | cos 界 | α=0.6 的 nDCG@10 |
| --- | --- | --- |
| [-20,-5] | [-1, 1]（数学界） | 0.690 |
| [-20,-5] | [0.7, 0.95] | 0.707 |
| [-20,-5] | **[0.8, 0.95]** | **0.756** |

**可复用的结论**：TM2 的前提是"分数分布跨查询可比**且铺满理论量程**"。
稠密检索在**同构语料**上不满足后半句——必须用经验分位数，数学上下界是错的抽象。

### 5.3 稳定性：三轮口径变化，排序始终不变

这是本次最重要的稳健性证据 —— 样本量翻倍、再加池化补判，**策略排序一次都没变**：

| 策略 | n=34 | n=54 | n=53（+补判） |
| --- | --- | --- | --- |
| convex-mm α=0.6 | **0.778** | **0.818** | **0.906** |
| convex-mm α=0.7 | 0.772 | 0.815 | 0.901 |
| `fts` 基线 | 0.696 | 0.752 | 0.844 |
| rrf-k60（生产） | 0.641 | 0.708 | 0.794 |
| `vec` 基线 | 0.515 | 0.490 | 0.528 |

绝对值随口径改善而整体上移（补判消除了低估），但**凸组合 > FTS > RRF > 纯向量**
这个次序、以及 α=0.6 最优，三轮完全一致。

## 6. 语料窗口 / 分块：对融合**无增益**

`node scripts/exp-palace-chunking.mjs`，n=34，chunk=350 字、上限 12 块。

| 配置 | 向量数 | 编码 | 纯向量 nDCG | 纯向量 Rec@30 | 凸组合 nDCG | 凸组合 Rec@30 |
| --- | --- | --- | --- | --- | --- | --- |
| `head300`（生产） | 1181 | 82s | 0.524 | 0.779 | **0.774** | **1.000** |
| `head1000` | 1181 | 234s | 0.531 | 0.647 | 0.748 | 0.941 |
| `chunk-max` | 3533 | 287s | **0.587** | **0.897** | 0.776 | 0.941 |
| `chunk-max-delog` | 3532 | 345s | 0.587 | 0.897 | 0.776 | 0.941 |

三条结论：

1. **分块确实改善了向量通道本身**：纯向量 nDCG 0.524→0.587（+12%）、
   Recall@30 0.779→0.897。截断确实在伤它，这点旧报告判断正确。
2. **但融合后几乎无差别**（0.774 → 0.776），且 **Recall@30 反而从 1.000 掉到 0.941**。
   代价是向量数 ×3、编码时间 ×3.5。**不值得做。**
3. 机制：凸组合已经让 FTS 兜住了召回，向量只需在 FTS 弱的地方补位——
   而补位所需的信号在前 300 字里**已经够了**。

### 6.1 「剥掉开头日志」是个伪需求（基于 v6 的错误认知）

v6 报告称「17/31 的 gold 关键词只在 300 字之外，长抽屉以原始日志粘贴开头」，
据此我以为剥日志会有明显收益。实测**不成立**：

- 第一版规则只剥到 **17/1182** —— 因为归档格式把粘贴内容包在 **`user: ` 前缀**
  后面，`^root@` 之类的行首规则一条都匹配不到（已修正正则）
- 修正后剥到 **31/1182**，但其中「前 300 字由非自然语言变为自然语言」的
  只有 **5 条（0.4%）**
- 全库口径：前 300 字中文占比 <15% 的文档共 **47/1182（4%）**

**4% 不是主要矛盾。** v6 的「55% 不可见」是**错判据下的统计**——它统计的是
"查询原句是否出现在 300 字内"，而查询原句本就 26/31 不在 gold 里（§1.2）。

## 7. 重排序：增益最大，但本机延迟不可接受

`node scripts/exp-palace-rerank.mjs`。模型 `Xenova/bge-reranker-base`
（XLM-R-base，278M，量化 ONNX 267MB，512 上下文）。

### 7.1 增益（n=53，已池化补判）

| 方案 | nDCG@10 | MRR@10 | R@1 |
| --- | --- | --- | --- |
| `fts` | 0.844 | 0.860 | 41/53 |
| `convex` α=0.6 | 0.906 | 0.917 | 45/53 |
| `fts+rerank` | 0.910 | 0.943 | **48/53** |
| **`convex+rerank`** | **0.915** | 0.935 | 47/53 |

- 对纯 FTS：nDCG **+8.4%**（0.844→0.915）、R@1 **41→47**
- 对凸组合：nDCG **+1.0%**、R@1 **45→47** —— rerank 在融合之上仍有净增益

### 7.1b 一个被补判推翻的中间结论（值得记）

补判**之前**（n=34 / n=54 两轮），结果都是 `fts+rerank` 略胜 `convex+rerank`：

| | n=34 | n=54 | n=53（补判后） |
| --- | --- | --- | --- |
| `fts+rerank` | 0.821 | 0.867 | 0.910 |
| `convex+rerank` | 0.817 | 0.864 | **0.915** |

当时我据此推断"rerank 足够强时会吸收掉前置融合的排序贡献"。**补判后反超**，
说明这个推断是**判据缺陷造成的假象**（单 gold 时，融合捞回的那些 gold 被当成
误判，压低了 convex 一侧）。

修正后的正确理解：**融合与 rerank 的贡献互补叠加**，不是替代关系 ——
两者捞回的是**不同**的失败案例：

- rerank 救的是「gold 在候选池里但排太后」（R@1 41→47/48）
- 融合救的是「gold 完全不在 FTS 结果里」（Recall@30 0.970→1.000）

rerank 只能重排候选池里已有的东西，对此无能为力。所以两者都该上。

### 7.2 延迟：本机不可行

i5-14400（16 核）+ transformers.js **WASM** 后端：

| 变量 | 实测 | 含义 |
| --- | --- | --- |
| 单对延迟 | **721ms**（848 对 / 612s） | 决定性瓶颈 |
| 文档 200 字 vs 1200 字 | 1094ms vs 985ms | **长度无关**，截短文档不省时间 |
| 批处理 N=1 vs N=16 | 920ms vs 789ms/对 | **几乎无规模效应** |
| `numThreads=14` | 1101ms（无变化） | WASM 后端在 Node 下不并行 |

瓶颈是**单次前向的固定开销**，不是计算量。rerank 8 条 ≈ **5.8s/查询**，
20 条 ≈ 14s，生产不可接受。

**唯一出路是换原生 `onnxruntime-node`** —— 但那会撞上已修的 DLL 版本冲突
（见 [顺序闸设计文档](../../design/工程基建/2026-09-18-原生ONNX运行时加载顺序闸.md)：
sherpa 1.27 与 onnxruntime-node 1.14 两份同名 DLL 按基名解析）。
即引入 reranker = 再开一个原生 runtime 战场，这是独立的工程决策，不在本次范围。

## 8. 给生产的实施建议

按「收益/代价」排序。

### 8.1 ✅ 已实施：融合从 RRF 换成凸组合 α=0.6

`2026-09-19` 已落地：

- 新增 `convexScoreFusion`（`packages/agent-runtime/src/wiki/wiki-vector.ts`）
- `searchDrawersHybrid` 改用它（`packages/agent-runtime/src/memory/palace-repo.ts`）
- `palace-repo.test.ts` 的 `searchDrawersHybrid` 用例**未改动**且仍通过 ——
  其断言写在纯 FTS（向量关闭）路径上，两种融合方式下行为相同

**依据**：nDCG 0.794→0.906（**+14%**）、R@1 34→45、Recall@30 持平 1.000。
**代价**：零——纯算术替换，无新依赖、无额外延迟。

两个实现细节值得记，它们都容易写错：

1. **BM25 侧要翻转**：`ftsRankedRows` 返回的 `rank` 是 `bm25()` 原始分，
   **越小越相关**（实测 −5~−38），与其他分数方向相反
2. **`span === 0` 要记 0.5**，不能记 1 或 0：全等分意味着这一路没有信息，
   给中间值既不打压也不抬举，与「缺席记 0」区分开

**注意**：这条路径只在 `LUMII_PALACE_VECTOR=1` 时生效（默认关）。
即改动已入库并验证，但**生产默认配置下不会执行**——等开启向量时自动生效。

**行为变化**：`PalaceSearchItem.score` 的量纲随模式而异了 ——
`mode: "fts"` 时仍是 `-bm25`（无上界），`mode: "hybrid"` 时是
凸组合归一化分（**[0, 1]**）。已在类型注释与 `MemorySearchHit` 处写明；
确认过没有代码据此做阈值判断（工具侧只是原样透传给模型）。

**验证**：
- 单测 9 条（含「BM25 翻转方向」「span=0」「两路都好者胜」）
- 宫殿集成测试 51 条通过，含生产路径端到端 `palace-hybrid.real.test.ts`
- 全量 `test:all` **2591 通过 / 0 失败**；两个包 `tsc` 干净
- 真实库端到端复核：R@1=45/53、R@5=53/53、**零漏召回**、分数落在 [0,1]，
  与 bench 数字完全一致

### 8.2 不要做：语料窗口 / 分块

分块把纯向量 nDCG 0.524→0.587，但**融合后无增益**（0.774→0.776），
且 Recall@30 反而 1.000→0.941。代价是向量数 ×3、编码时间 ×3.5、存储 ×3。
现有 300 字窗口在融合框架下够用。

### 8.3 待立项：reranker（增益最大，但须先解决原生 runtime）

- **收益**：nDCG 0.906→0.915、**R@1 45→47**、MRR 0.917→0.935
- **障碍**：WASM 后端 721ms/对，8 条候选 5.8s/查询 —— 生产不可接受
- **前置工作**：
  1. 解决三份 onnxruntime 的共存问题（sherpa 1.27 / onnxruntime-node 1.14 /
     reranker 所需的原生 runtime）。当前顺序闸只能保证**不崩**，不保证**能跑第三个**
  2. 实测原生后端的单对延迟，重新算预算；若 <50ms 才值得
  3. 候选数需调参：rerank 的边际收益是递减的，top-8 与 top-20 的差要量
- **模型**：`Xenova/bge-reranker-base`（278M）已够用；不必上
  bge-reranker-v2-m3（568M），后者 CPU 延迟只会更差
- **当前决定**（2026-09-19）：暂不处理，先观察凸组合在真实使用中的效果

### 9.4 ⏱ 评测集扩到 150+

素材充足：1182 条抽屉，只标了 54 条。

按 Sanderson et al.（IR 2019）「多 query + 浅标注优于少 query + 深标注」，
策略是**扩 query 数、每条只标 1~3 个 gold**，不是深挖现有那几条。

做法：`scripts/` 里的标注流程是「读抽屉 → 手写改写过措辞的回忆型查询 → gold

这些系统产出的抽屉，它们不是用户会回头问的东西。

换个人可能分层不同，而分层结果直接支撑「增益集中在 paraphrase」这类结论。

挖查询，那才是真实的措辞错配样本。本次探路（§2）发现本机这类样本极少。
