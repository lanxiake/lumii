# 上下文压缩引擎测试指南

> **测试范围：** Phase 1（Proactive Prune 三级压缩）+ Phase 2（Per-Model 阈值 + Idle Compaction + ProgressFence 双预算）+ Phase 3（Commit Fence 永不中断）

## 前置准备

### 1. 构建应用

```bash
cd E:\my-project\open-source\lumii
pnpm install
pnpm build
```

### 2. 启动应用（开发模式，查看日志）

```bash
pnpm dev
```

开发模式会在终端输出详细日志，包括压缩相关的关键事件。

### 3. 准备测试会话

打开应用后：
1. 创建一个新的对话会话
2. 选择一个支持的模型（如 claude-sonnet-4.6 或 gpt-4o）
3. 准备进行多轮对话测试

## Phase 1: Proactive Prune（三级压缩）测试

### 测试场景 1.1: 工具结果微压缩（Micro-Compact）

**目标：** 验证大文件读取后工具结果被自动压缩

**步骤：**
1. 在会话中发送：`读取 package.json 文件内容`
2. 等待 AI 调用 `Read` 工具返回完整文件内容
3. 观察终端日志

**预期行为：**
- 日志中出现 `[microcompactToolResults]` 相关输出
- 工具结果被压缩为摘要（保留前 N 行 + "...省略 M 行..." + 后 N 行）
- 压缩前后 token 数量对比（如：1200 → 350）

**日志示例：**
```
[compact/micro-compact] Read 工具结果微压缩：1200 tokens → 350 tokens（节省 70.8%）
```

### 测试场景 1.2: 去重压缩（Dedup）

**目标：** 验证连续相同工具调用被去重

**步骤：**
1. 连续发送 3 次相同的请求：`列出当前目录的文件`
2. AI 会多次调用 `Glob` 或 `Bash ls` 工具
3. 观察第 2、3 次工具结果是否被标记为重复

**预期行为：**
- 第 1 次：完整保留工具结果
- 第 2、3 次：日志显示 `[Dedup] 工具结果与前一次相同，已去重`
- 重复结果被替换为占位符 `"[与上次结果相同]"`

### 测试场景 1.3: 摘要压缩（Summary）

**目标：** 验证长对话触发 LLM 摘要生成

**步骤：**
1. 连续进行 8-12 轮对话（每轮包含用户消息 + AI 回复）
2. 话题可以多样化（代码、文件操作、技术问答等）
3. 观察 token 占用达到阈值后的压缩行为

**预期行为：**
- 当 token 占用达到模型上下文窗口的 75% 时自动触发压缩
- 日志显示 `[runSummaryStage] 开始生成 LLM 摘要`
- 旧消息被归档，生成摘要消息注入到历史前端
- 压缩后 token 占用显著下降（如：80000 → 25000）

**日志关键字：**
```
[compact/summary-compact] LLM 摘要生成成功，摘要长度=450
[transform-context] 压缩完成：80000 tokens → 25000 tokens（节省 68.8%）
```

## Phase 2: Per-Model 阈值 + Idle Compaction 测试

### 测试场景 2.1: Per-Model 阈值匹配

**目标：** 验证不同模型使用不同的压缩阈值

**步骤：**
1. 创建两个会话，分别选择不同模型：
   - 会话 A：`claude-sonnet-4.6`（200K 上下文）
   - 会话 B：`gpt-4o-mini`（128K 上下文）
2. 在两个会话中进行相同数量的对话（约 10 轮）
3. 观察触发压缩的时机差异

**预期行为：**
- `claude-sonnet-4.6`：阈值为 150K（200K × 0.75），更晚触发压缩
- `gpt-4o-mini`：阈值为 96K（128K × 0.75），更早触发压缩
- 日志显示 `[resolveModelThreshold] 匹配模型 claude-sonnet-4.6 → 阈值 150000`

**验证方法：**
查看应用界面右上角的"上下文用量"指示器，观察触发压缩时的 token 数量。

### 测试场景 2.2: Idle Compaction（60s 自动压缩）

**目标：** 验证会话空闲 5 分钟后自动触发压缩

**步骤：**
1. 创建一个新会话，进行 8-10 轮对话，让 token 占用达到 60-70%
2. **停止输入任何消息，等待 5 分钟**
3. 观察终端日志

**预期行为：**
- 5 分钟后（300 秒），日志出现：
  ```
  [scanIdleInstances] 实例 main 满足 idle 条件（idle=305s, used=70000, threshold=90000），开始压缩
  [tryIdleCompact] 实例 main idle 压缩完成
  ```
- 应用界面的"上下文用量"指示器自动下降
- 压缩过程中 UI 不会卡顿（后台异步执行）

**关键配置：**
- `idleCompactAfterSeconds: 300`（5 分钟）
- 扫描间隔：60 秒（每分钟检查一次所有会话）

### 测试场景 2.3: 碰撞检测（压缩中不重复触发）

**目标：** 验证压缩进行时不会重复触发新的压缩

**步骤：**
1. 创建一个新会话，快速发送 5 条消息触发压缩
2. 在压缩进行时（日志显示 `[compactContextAsync] 开始生成 LLM 摘要`）
3. 立即再发送一条新消息

**预期行为：**
- 第二次压缩请求被拒绝，日志显示：
  ```
  [tryIdleCompact] 实例 main 正在运行或压缩中，跳过
  ```
- 不会出现多个并发的摘要生成请求

## Phase 2: ProgressFence 双预算测试

### 测试场景 2.4: 慢模型流式续命（120s idle 预算）

**目标：** 验证慢速 LLM 流式输出时不会超时中断

**步骤：**
1. 选择一个较慢的模型（如 `claude-opus-4`）
2. 触发一次压缩（发送足够多的消息）
3. 观察摘要生成过程（通常需要 30-60 秒）

**预期行为：**
- 即使摘要生成耗时超过 60 秒，只要每 120 秒内有新 token 到达，压缩不会超时
- 日志显示每次收到 token 时的 `touchProgress` 调用：
  ```
  [ProgressFence] 收到流式 token，续命（距上次进度 2.3s）
  ```
- 最终摘要成功生成，不会因超时降级为占位符

### 测试场景 2.5: 600s 绝对封顶（ceiling 预算）

**目标：** 验证即使流式持续，10 分钟后也会超时

**测试方法（仅理论验证，实际很难触发）：**
- 正常模型下，摘要生成通常在 30-90 秒完成
- 600 秒封顶作为极端保护，避免死循环占用资源
- 如果真的超时，日志会显示：
  ```
  [compact/summary-compact] 摘要生成 ProgressFence 超时：距上次进度 125.2s，放弃
  ```

## Phase 3: Commit Fence 永不中断测试

### 测试场景 3.1: commit-in-flight 永不中断



**目标：** 验证 DB 写入期间即使超过 ceiling 也不会中断

**测试方法（需要代码注入延迟）：**
由于正常 DB 写入速度很快（< 1 秒），该场景需要开发环境下注入人工延迟才能测试。

**理论验证点：**
- `beginCommit()` 后 `fence.commitInFlight === true`
- `withProgressTimeout` 进入 overrun 分段等待循环（每 30s 一段）
- 日志显示 WARNING → ERROR 升级：
  ```
  [CommitFence] SessionDB 提交仍在进行中，已越界 35.2s（总等 635.2s，ceiling 600s）；**永不中断**，继续等下一段 30s
  ```

**实际建议：**
在生产环境中，如果看到上述日志，说明磁盘或数据库出现性能问题，需要排查硬件健康状态。

### 测试场景 3.2: finally revoke 防分叉

**目标：** 验证异常退出时不会留下半写状态

**测试方法：**
1. 在压缩过程中强制关闭应用（Ctrl+C 或任务管理器杀进程）
2. 重新启动应用
3. 检查之前的会话状态

**预期行为：**
- 会话历史完整，没有出现"半压缩"状态（部分消息丢失但摘要存在）
- `revokeCommitAdmission()` 在 `finally` 块中被调用，防止后台线程继续写入

## 综合测试场景

### 场景 A: 长时间连续对话（压力测试）

**目标：** 验证多次压缩循环的稳定性

**步骤：**
1. 创建一个新会话
2. 连续进行 30-50 轮对话，涵盖：
   - 文件读取（触发 Micro-Compact）
   - 代码编写（大段文本输出）
   - 技术问答（普通对话）
3. 观察多次压缩后的表现

**预期行为：**
- 第 1 次压缩：token 从 80K 降至 25K
- 第 2 次压缩：token 从 90K 降至 30K（包含前一次摘要）
- 第 3 次及以后：持续保持在阈值以下
- 整个过程中应用响应流畅，没有卡顿或崩溃

### 场景 B: 多会话并发（Idle Compaction 压力）

**目标：** 验证多个会话同时空闲时的批量压缩

**步骤：**
1. 创建 3-5 个不同的会话
2. 在每个会话中进行 8-10 轮对话，token 占用达到 60-70%
3. 同时停止所有会话的输入，等待 5 分钟

**预期行为：**
- 60 秒扫描间隔内，所有满足条件的会话被依次压缩
- 日志显示多个 `[scanIdleInstances]` 和 `[tryIdleCompact]` 事件
- 压缩过程串行执行，不会同时压缩多个会话导致 CPU 飙升

### 场景 C: 模型切换（Per-Model 阈值动态调整）

**目标：** 验证同一会话切换模型后阈值实时更新

**步骤：**
1. 创建一个会话，初始选择 `gpt-4o-mini`（128K 上下文）
2. 进行 5-8 轮对话，token 占用达到 50K
3. 在设置中切换模型为 `claude-sonnet-4.6`（200K 上下文）
4. 继续对话，观察压缩触发时机

**预期行为：**
- 切换前：阈值为 96K（128K × 0.75）
- 切换后：阈值自动更新为 150K（200K × 0.75）
- 日志显示 `[resolveModelThreshold] 匹配模型 claude-sonnet-4.6 → 阈值 150000`
- 压缩触发时机延后，允许更多对话轮次

## 常见问题排查

### Q1: 压缩没有触发？

**检查项：**
1. Token 占用是否达到阈值（右上角指示器）
2. 模型上下文窗口大小是否正确识别（日志中搜索 `resolveModelThreshold`）
3. 会话是否处于活跃状态（Idle Compaction 需要 5 分钟空闲）

### Q2: 摘要生成失败？

**可能原因：**
1. LLM API 调用失败（网络问题、API key 无效）
2. 模型上下文长度超限（PTL 错误）
3. 超时（120s idle 或 600s ceiling）

**查看日志：**
```
[compact/summary-compact] LLM 摘要生成失败：<错误信息>
```

### Q3: 应用响应变慢？

**排查步骤：**
1. 检查是否有多个会话同时压缩（日志搜索 `compactContextAsync`）
2. 查看 CPU 和内存占用
3. 确认磁盘 I/O 性能（SQLite 数据库位置）

### Q4: 日志中看到 "CommitFence overrun" 警告？

**含义：** DB 写入耗时超过 10 分钟（极端异常）

**处理：**
1. 检查磁盘健康状态（SMART 检测）
2. 确认数据库文件未被其他进程锁定
3. 考虑迁移数据库到更快的存储设备

## 总结

本测试指南覆盖了上下文压缩引擎的全部核心功能。重点测试场景：

1. **Phase 1**：工具结果压缩 + 去重 + 摘要生成
2. **Phase 2**：不同模型的阈值匹配 + 空闲自动压缩
3. **Phase 3**：DB 写入期间的永不中断保护

建议按顺序执行测试场景，每个场景完成后记录日志输出和观察结果。如遇到问题，参考"常见问题排查"章节。
