# 工具选择评测（tool-choice）

> 测的是**模型会不会按工具面的设计意图选工具**。
> 对照集：[`eval-set.json`](./eval-set.json) · 跑分器：[`run-tool-choice-eval.mjs`](./run-tool-choice-eval.mjs) · 校验：[`../../scripts/verify-tool-choice-eval.mjs`](../../scripts/verify-tool-choice-eval.mjs) · 历次结果：[`baseline.md`](./baseline.md)

## 它和别的套件分别管什么

| 套件 | 管什么 | 什么时候失败 |
| --- | --- | --- |
| `lumii-cli/tool-contract`（TC） | **工具本身**的契约：失败标没标 `isError`、大输出落没落盘 | 工具实现写错了 |
| `agent-runtime` 单测（含守卫） | **文本与注册表**的一致性：描述里引用的工具名存不存在、失败分支登没登记 | 代码与文档脱节 |
| **本套件** | **模型的选法**：有专用工具时会不会走 shell、语义邻近的工具会不会选错 | 工具面/描述/提示词**没教会模型** |

三者的失败原因完全不同——这也是为什么它们必须分开：一个工具实现得完全正确，
模型仍可能因为描述写得含糊而永远不用它。

## 对照集的设计原则

写在 `eval-set.json` 的 `_设计原则` 里，核心是四条：

1. **判据必须能追溯到原文**。每条用例的 `why` 都指向提示词或工具描述里的具体句子——
   工具面的规则是**给模型看的**，评测就是验它有没有照做，而不是评我们自己的偏好。
2. **reject 精确到命令内容**（`rejectCommandPatterns`）。`bash` 本身不是错的，
   错的是用它跑 `find`/`cat` 这类有专用工具的操作。
3. **只锁底线，不锁走法**。`expectTools` 是"至少出现一个"，`rejectTools` 是"一个都不该出现"——
   **不规定完整序列**：同一件事有多种合理路径。
4. **每条 note 记为什么它值得单独一条**——通常是"这里出过事"或"这两个工具语义贴得近"。

## 前置校验（必做）

```bash
node scripts/verify-tool-choice-eval.mjs
```

**为什么必须跑**：评测集里写错工具名时，`expectTools` 断言会**永远不命中**——
而"不命中"在汇总里看起来和"模型没选对"**一模一样**，于是整条评测静默失效，
还会把人引去"修模型"。这比没有评测更糟：它给出错误的行动方向。

校验脚本自己也有盲区，已修复三处（都记在脚本注释里）：
常量式 `name: XXX_TOOL_NAME` 扫不到、锚点先命中注释里的同名串、把已下线的 `wiki_capture` 当注册成员。
**"扫不到 ≠ 不存在"** —— 报错方向恰好是反的，所以每次修扫描器都要用实际数量对一遍。

## 运行

```bash
# 全部（15 用例，约 20~40 分钟——每个用例一个真实回合；提问挂起的用例要多等 ~5 分钟）
node docs/test/tool-choice/run-tool-choice-eval.mjs

# 只跑某个
TC_ONLY=t01 node docs/test/tool-choice/run-tool-choice-eval.mjs

# 覆盖默认回合预算（默认 600s；提问挂起要等超时被拒答，见「证据从会话消息取」与特性 2）
TC_TURN_TIMEOUT_MS=240000 node docs/test/tool-choice/run-tool-choice-eval.mjs

# 端点被压住时调大用例之间的冷却（默认 10s）
TC_COOLDOWN_MS=30000 node docs/test/tool-choice/run-tool-choice-eval.mjs
```

**为什么这么慢 / 为什么不进 CI**：它测的是模型的选择行为，绕不开模型。
对照 `memory-eval`——那边是离线读 DB 算分，可以随时跑；这边每个用例都要一个真实回合。
所以定位是**按需跑**：改工具面、改工具描述、改系统提示词之后跑一次。

**副作用**：不切全局设置（不像 TC 套件要切 `promptStyle`），但**会在真实用户数据上动手**——
t15 是真实用户请求，回合会建定时任务、还可能写记忆条目（2026-09-19 实测）。
跑分器在用例前后对 `local_cron_jobs` / `agent_memories` 做快照与清理（失败路径同样清理，
见 `finally`）；`TC_NO_RESTORE=1` 保留现场供检查。
用例各自独立会话——共用会话会让后跑的用例被前面的对话污染，而那种失败看起来像"模型选错了工具"。

## 三个必须知道的特性（都是实测撞出来的）

### 1. 结果有波动——模型是随机的

同一个用例跑两次可能给不同结果。实测：`t01` 第一次 `find . -name "*.md"`（FAIL），
第二次 `glob`（PASS）——**同一份代码、同一条提示词、同一个工具面**。

所以：

- **不要把单次 100% 当达标**，也不要把单次失败当回归；
- 判读要看**多次跑的趋势**，至少关注"两次以上都失败"的用例；
- 这条同样适用于"改完提示词跑一次看看有没有变好"——单次对比没有统计意义。

### 2. 有两类「不是模型的失败」，都可能整批出现

它们和「模型选错了工具」在汇总里长得**一模一样**，但处置方向完全相反——
所以要靠错误措辞区分，并从分母里剔除。

| 类别 | 触发条件 | 实测症状 |
| --- | --- | --- |
| `ENV-ERROR` | 应用不可达 | 全线 `connection_failed` |
| `MODEL-BUSY` | 模型端点被压住（并发过高） | 整批「回合等待超时（…ms）：未等到新的 assistant 消息」 |

`ENV-ERROR` 的实测来源：`palace-vector` 后台补齐 518 条向量时，控制口**只接受连接、不响应**。
**日志里它还在正常打进度，看起来完全不像故障**——这一点最坑：不看日志会以为评测脚本坏了。

`MODEL-BUSY` 的实测来源：**并发**。注意本套件「一个用例」远不止一次模型往返——
实测单回合最多发出 22 次工具调用（t09），每次都是一次往返。连着跑就是持续压同一个端点，
而并行会话的探针、应用自身也在压它。压过头就整批超时。

跑分器对此有四层处理：

| 层 | 做法 |
| --- | --- |
| 冷却 | 用例之间默认停 **10 秒**（`TC_COOLDOWN_MS`）——**降低评测自身并发的主要手段** |
| 重试 | `ENV-ERROR` 退避 8s、`MODEL-BUSY` 退避 **30s** 后各重试 3 次（端点卡住时立刻重试只会再压一次） |
| 区分 | 重试仍失败的按类别标出，**从分母里剔除**——它们不是模型的失败 |
| 熔断 | **连续 3 条被挡住即提前终止**，并说明剩余多少条没跑、该调哪个旋钮 |

> 第一次基线跑时没有这些层，t12~t15 的 `connection_failed` 被计成模型的失败，
> 把通过率从 ~73% 拉到 40%——**那种数字会把人引去查工具面，而问题在环境**。
> 同类事故在 2026-09-18 又以 `MODEL-BUSY` 重演一次（t04/t05 双双超时）。

⚠️ 熔断和冷却都不能替你判断「端点现在空不空」：跑之前最好确认没有别的会话在同时压模型。

### 3. 证据从会话消息取，**不要退回日志解析**

判据读取「该会话落库的 assistant 消息 parts」（`parts[type=tool].name/args`），
即「这个回合真实发生的工具调用序列」。退回日志解析会踩两个实测过的坑：

- **params 截断**：宿主把 `ToolRunner →` 行的参数预览**截断在 200 字符**
  （`packages/agent-runtime/src/tools/hooks/logging-hook.ts:23`）——长参数调用
  （`cron_create` 的 taskText、`ask_user_question`、`memory_manage`…）行尾**没有收尾 `}`**，
  按 `params={...}` 解析的正则会**整条静默丢掉**（实测一个回合 8 条丢 3 条，
  评测据此把 t15 记成「没建任务」——而任务真在 DB 里）；
- **桥接口径**：`tool:end` 类日志行走渲染进程 console 桥接，后台/无 UI 订阅的回合不落盘。

另外，**提问挂起的回合是合法回合**：评测环境无人应答 `ask_user_question`，
问句要等超时被拒答（实测 ~5 分 13 秒）模型才继续——所以默认回合预算 600s、
t15 单独放宽到 720s；预算小于它，这类回合会被误判成 MODEL-BUSY。

## 加用例

1. 在 `eval-set.json` 的 `cases` 里加一条，**必须写 `why`**（指向原文，不是偏好）；
2. 跑 `verify-tool-choice-eval.mjs` 确认工具名存在；
3. 跑单条（`TC_ONLY=<id>`）确认断言能红——**写不出会红的用例就是没用的用例**；
4. 如果新用例暴露了真实的选择错误，把**实际序列**记进 `note`（这是最有价值的记录）。
