## 一、缘起

2026-09-19 查过一次导出期间的 96 秒异常。当时确认其中有一处**主线程完全冻结**：
应用日志某行的**外层**落盘时间戳比**内层**生成时间戳晚 **54 秒**。
但那是启动 + 同步并发下的偶发事件，之后六次复现尝试都没再出现。

09-20 装上捕获器后，一天内抓到 **6 次现场**——两类都查清了，都是**机制级**的结论（见第四、六节）。

## 二、捕获器：判据的三代演进

`scripts/capture-main-freeze.mjs`。它的价值全在判据上，而判据错了两次。

### v1：用日志当判据 —— 挂了一整晚，**一次都没触发**

判据是「日志**最后一行**的**内层**时间戳」。三个缺陷各自都足以致命，且**全部静默**：

| # | 缺陷 | 实测 |
| --- | --- | --- |
| 1 | 日志路径在**启动时**算死（`mtbot-<启动日>.log`） | 跨日后读一个不再增长的旧文件 |
| 2 | 只取**最后一行** | 那行高频被 `[AgentRuntime:IPC] ... mcp:status` 这类由 `[Main]` 直打、**不经 file-logger 包装**的单时间戳行占据。实测 09-19 日志尾部 8192 字节 / 99 行里，含内层时间戳的行数是 **0** |
| 3 | 解析失败走 `continue` | **不打任何警告**。它连上了 inspector、打印了启动横幅，然后永远沉默 |

**「装上了」被当成了「在工作」。**

### v2 之前：一个被实验室推翻的假设

换判据时我先想到的是「CDP 往返延迟」——听起来天经地义：主线程卡住，命令自然回不来。
**实测把这个假设直接推翻了**（`scripts/probe-freeze-detect-via-cdp.mjs`，起一个自身忙等 5 秒的进程）：

| 探测 | 忙等期间的表现 |
| --- | --- |
| `Runtime.evaluate` | **1 ms 返回**（返回值还正确） |
| `Profiler.stop` | **4 ms 返回** |
| 忙等窗口内的采样 | **1586 个样本，栈顶正是那行忙等循环** |

V8 用 interrupt 把命令插进主线程，Node 的 inspector 跑在独立线程上，**命令不排主线程的队**。

两条可复用的结论：
- **判据不能是 CDP 往返延迟**；
- **采样线程在冻结期间照常工作** —— 只要能触发抓取，就能定位到行。

### v3：注入心跳

向主进程注入 `setInterval` 心跳，轮询 `Date.now() - __lumiiFreezeHb`。
**心跳停摆 = 不跑事件循环 = 冻结**，与日志格式、路径、是否有输出全部无关。

其精确语义是：**心跳落后 = libuv 的 timers 阶段被推迟了多久 = 主线程被某个回调阻塞了多久。**

三处现场用出来的修正：

1. **先落盘再取 profile**。v2 把元信息写在 `Profiler.stop` 之后，而 native 冻结时 stop 可能
   **永远不返回**（10:06：主线程卡 ≥16 秒，随后进程被重启），代码根本走不到写盘那步。
   现在 `.json` 在等 stop **之前**就写 —— **「有 `.json` 而无 `.cpuprofile`」本身就是证据**。
2. **断线自动重连**。dev 环境应用重启是常态，v2 一断就退，应用重启顺手就把它带走了。
3. **采样覆盖率判读**。窗口内样本数 × 0.2ms ÷ 窗口时长 < 15% 时，明确提示
   「主线程不在执行 JS，阻塞在 native 层」——这种形态下栈天然看不到。

> 一次**失败**的尝试也记一下：为排除「单个 timer 被推迟」，我加了第二个心跳（递归
> `setTimeout`），但**实测两个值几乎完全相等**（40/40、150/150、163/163）——它们由同一个
> timers 阶段驱动，**没有提供独立性**。保留只作冗余。

## 四、已查清并修复：会话列表预览

### 4.1 因果链（日志逐帧对上）

```
09:59:09.574  vite HMR 更新 App.tsx / AppProviders.tsx
09:59:10.443  refreshLocalSessions 开始      ← 第 1 次
09:59:11.176  refreshLocalSessions 开始      ← 第 2 次
09:59:11.875  refreshLocalSessions 开始      ← 第 3 次
09:59:12.908  conversation:list 条数=686     ← 第 1 次才返回
```

捕获器记的冻结起点是 **10.413**、检测于 **12.466** —— 与 10.443→12.908 的 **2.47 秒**几乎逐帧重合。

两个成因叠加：

- **单次 400~770 ms**：`handleConversationList` →
  `conversationRepo.loadLastMessagesForConversations` 是一条**同步** SQL
  （better-sqlite3，跑在主进程主线程上）；
- **无去重**：`ChatPage.tsx` 有**五个**触发点会调 `refreshLocalSessions`
  （挂载 / `isReady` 变 true / `activeView` / `sessionListRevision` / 会话缺失兜底），
  彼此之间没有任何合并。

### 4.2 SQL：窗口函数 → 相关子查询

原实现用 `ROW_NUMBER() OVER (PARTITION BY conversation_id ...)` + 外层 `rn <= ?`，
要求 SQLite 先对**全部候选行**算完行号再丢弃，且窗口里带着 `content_json`。

执行计划对比（真实库）：

```
旧  SEARCH messages USING INDEX idx_messages_conversation_ts
    USE TEMP B-TREE FOR LAST TERM OF ORDER BY   ← 建临时 B 树
    SCAN (subquery-3)                            ← 全扫描
    SCAN ranked                                  ← 全扫描
    USE TEMP B-TREE FOR ORDER BY                 ← 再建一棵

新  SEARCH m  USING INDEX idx_messages_conversation_ts
    CORRELATED LIST SUBQUERY 1                   ← 相邻行会话相同，结果可复用
    SEARCH m2 USING INDEX idx_messages_conversation_ts
    （无临时表）
```

四种写法实测（686 会话 / 1691 结果行 / 只读副本 / 取最优 3 次）：

| 写法 | 耗时 | 语义 |
| --- | --- | --- |
| 窗口函数（原实现） | 1080 ms | 基准 |
| 窗口不带 `content_json` + JOIN 回取 | 543 ms | 一致 |
| **相关子查询（本修复）** | **144 ms** | **一致** |
| SQL 里用 JSON1 抽取预览文本 | 209 ms | **不一致** |

**没选 JSON1 版的原因**：SQLite 的 `trim()` 只去空格、不去 `\n`/`\t`，而 `extractPreviewText`
用的是 JS 的 `.trim()`（去所有空白）——实测 686 条里 **468 条结果不一致**。
为省带宽改语义不值得。

### 4.3 前端：合并而非丢弃

`refreshLocalSessions` 增加 ref 上的并发状态：飞行中收到新调用**只记标记**，
结束后**补拉一次**。丢弃会让列表停在旧数据上（新建会话后立刻切视图就看不到）。
代价是 N 次并发 → 2 次串行，而不是 1 次。

### 4.4 真实应用上的实测

| | 单次 `conversation:list` | 三次触发 |
| --- | --- | --- |
| 修复前 | **768 ms** | 并发叠加 ≈ 2.3 s（超 2 s 阈值） |
| 修复后 | **326 ms** | 合并为 2 次串行 ≈ 0.65 s |

日志佐证（修复后）：`48.824` 第二次调用被合并、`48.850` 第一次完成、`48.851` 立即补拉。

代码：`packages/agent-runtime/src/storage/conversation-repo.ts`、
`apps/windows/src/renderer/pages/ChatPage/ChatPage.tsx`（提交 `ff60e6c6`）。

## 五、⚠️ 对上述修复方案的反思

**这一节是本文最重要的部分。** 上面那个修复**交付了、有效、但不够好**，理由逐条如下，
每条都有数据。

### 5.1 「快 7.5 倍」是被特定数据放大的，不是普遍结论

我在提交信息里写了「1080ms → 144ms（7.5 倍）」。**换一组数据就不成立**：
在合成库上（每会话均匀 4 条 × 15KB），686 会话下新写法是 **329 ms**、旧写法 601 ms，**只有 1.8 倍**。

差异来源：真实库 686 会话只返回 **1691 行**（平均 2.46 条/会话，消息分布长尾），
合成库返回 **2744 行**。我在提交信息里报的是**最有利的那组数据**。

**准确的说法应该是**：在真实数据分布下 7.5 倍；在均匀分布下约 2 倍。

### 5.2 新写法仍是 **O(会话数)** —— 只把常数变小，没有改变增长阶

| 会话数 | 新写法 | 旧写法 | 倍数 |
| --- | --- | --- | --- |
| 100 | 38 ms | 72 ms | 1.9× |
| 686（当前） | 329 ms | 601 ms | 1.8× |
| 1500 | 614 ms | 1357 ms | 2.2× |
| **3000** | **1337 ms** | 2914 ms | 2.2× |

**会话涨到 3000，单次就是 1.3 秒，三次触发又回到 4 秒 —— 冻结会回来。**
当前数据量救了这个方案，不是方案本身解决了问题。

### 5.3 没有回答上游问题：**为什么列表要拉全部 686 个会话？**

`listActiveConversations` 的注释写着「不能设全局 LIMIT：否则数量最多的『默认』会话会把
『渠道』『系统』会话挤出列表」——**所以全量是有意为之**。但这意味着：

- 686 个会话里大量是 cron / evolution / 渠道会话，用户**根本不会去点**；
- 每次刷新都把这 686 行的 `content_json` 从 SQLite 取出来、跨 native→JS 边界复制、
  解析 JSON 只为抽出**一个预览字符串**，然后把 686 个对象序列化过 IPC；
- 实测 100 会话的新写法是 **38 ms** —— **少查会话数比换写法有效得多**。

**真正的解法不在 SQL 里**：主进程**已经有** `conversation:created|updated` 推送
（现在只被用来递增 `sessionListRevision`，触发渲染层全量重拉）。**推增量**才是对症的。
这是一个**架构级改动**，不在本轮范围 —— 但应当记下来，因为 5.2 的增长阶问题只有它能解。

### 5.4 没有性能守卫

语义有测试（`conversation-repo-batch-preview.test.ts`，6 用例，含新增的「多会话各自取最近
limit 条」）。**但没有任何机制防止有人改回慢写法** —— 单元测试里只有几条消息，测不出
1080ms 与 144ms 的差别。CI 也不跑 `apps/windows` 的测试。

### 5.5 前端那处改动**没有单元测试**

`ChatPage.tsx` 的并发合并逻辑，验证方式是**读运行日志**（第二节 4.4 的时序），
不是测试。这属于「验证过」但不属于「有回归保护」。

### 5.6 捕获器 v3 的重连逻辑**没测就上线**，靠偶然场景才暴露

`findWsUrl()` 被写在 `closed = false` **之前**，而外层循环每轮结束会把它设回 `true` ——
重连第一次循环就抛「会话已关闭」，永远连不上。这个 bug 是**停应用时偶然看到日志**
才发现的，不是测出来的。修在 `e98df570`。

**教训**：这个脚本是排查工具，但它自己也需要被验证 —— 它已经因为"没验证"失败过两次
（v1 的判据、v3 的重连）。

## 六、已定位：native 层阻塞 = 同步写 stdout 被读端拖住

### 6.1 线索：606 秒的双时间戳落差

扫描 09-19 全天的双时间戳落差，最大的 12 条**全是同一种日志**：
`[cloud-sync/copy] [copySyncDirectory] 跳过大文件`，最高 **606 秒**。

**但不能停在「某个函数很慢」**：那段时间日志里**有 3833 条在正常写**——
主线程不可能卡 10 分钟又同时写日志。矛盾说明我对时间戳的理解有缺口。

### 6.2 两个时间戳之间隔着什么

读 `apps/windows/src/main/logger.ts:30` 与 `file-logger.ts:235`：

- **内层**时间戳由 `createLogger().formatMessage()` 生成 = **`logger.warn` 被调用的时刻**
- **外层**时间戳由 `FileLogger.writeLog()` 生成 = **落盘那一刻**

两者之间只隔一件事（`file-logger.ts:293`）：

```ts
console.warn = (...args) => {
  this.safeConsoleWrite(this.originalConsoleWarn, ...args)  // ← 写 stdout
  this.writeLog('WARN', ...args)                            // ← 外层时间戳在这里生成
}
```

而 `file-logger.ts` 自己的注释就写着：Windows 上这是 **`SyncWriteStream`（同步写）**
（那段注释本来是为了处理 EPIPE）。

### 6.3 实验室确证

`scripts/probe-stdout-block.mjs`：子进程持续写 stdout，父进程分三段处理。
**同一个子进程**，只改父进程读不读：

| 阶段 | 心跳落后 |
| --- | --- |
| A 正常读 | 140 ~ 199 ms |
| B **停读**（6s → 14s） | **8 秒内零心跳**（连心跳的 stderr 都出不来） |
| C 恢复读（14s） | **立刻恢复**，首条报 `落后 8059ms` —— 正好等于停读时长 |

**因果方向确认：冻结时长 = 读端不读的时长。**

注意阶段 A 也**不是 0ms**：同步写本身一直占着主线程（140~199ms 的持续落后）。

### 6.4 与实际日志对上

`copySyncDirectory` 批量 WARN 的落盘形态正是「阻塞后集中释放」：

```
[10:19:46.481] [WARN] [10:18:57.660] ... 跳过大文件   ← 内层比外层早 49 秒
[10:19:46.481] [WARN] [10:19:46.481] ... 跳过大文件   ← 同一毫秒一大批
[10:19:46.488] [WARN] [10:19:46.488] ... 跳过大文件
```

- 09-19 当天这类 WARN 共 **71893 条**；
- 09-19 的实例是 **dev**：`app.asar` **0 行**、`[vite]` 18 行、`Renderer:console` 16512 行。

### 6.5 完整机制

```
dev 实例经管道启动（run-dev.cjs 的 stdio:'inherit' → 接到终端/父进程的 stdout）
  → 应用写 stdout（Windows 上同步写）
  → copySyncDirectory 一次产生数万条 WARN
  → 管道缓冲区（约 64KB）瞬间填满
  → 读端跟不上 → 同步写阻塞
  → 主线程停摆：定时器、IPC、日志落盘全停
  → 阻塞时长完全由读端决定
  → 解除后积压日志在同一毫秒集中落盘
```

这一条解释了此前的**全部**观察，包括两个一直说不通的地方：

- **为什么 profile 里只有 `(idle)`**：阻塞在 native 写操作里，V8 采样线程拿不到 JS 栈；
- **为什么六次复现都失败**：复现需要「大量日志 + 慢读端」的特定组合，
  而不只是"数据量大"。数据量在那些尝试里一直是够的。

### 6.6 修复实施（2026-09-20，已完成）

**目标**：掐掉「日志风暴 → 管道缓冲填满 → 同步写阻塞主线程」这条链路。
注意目标**不是减少日志的信息量**，而是去掉「逐条」这个形态 ——
没有任何人需要 7 万条「跳过了哪个文件」。

#### 改动 1：聚合 `copySyncDirectory` 的逐文件 WARN

| | |
| --- | --- |
| **位置** | `apps/windows/src/main/cloud-sync/sync-copy.ts`（删逐条）+ `sync-exporter.ts`（汇总加示例） |
| **改前** | 每个被跳过的大文件一条 `logger.warn` —— 09-19 一天 **71893 条** |
| **改后** | **一条汇总**：`outputs 跳过大文件 N 个（阈值 X bytes）；示例: a, b, c …` |
| **信息没丢** | 数量与**完整路径**本来就在 `result.skippedLarge / skippedLargePaths` 里，下游 `stageAllChanges` 用它们构造 git 排除列表（**与日志无关**）；汇总里再给 3 个示例保可诊断性 |
| **为什么这是治本** | 触发条件就是「瞬间产生几万条 WARN」。这个形态没了，管道就填不满 |

#### 改动 2：dev 启动不再让 PowerShell 接管输出管道

| | |
| --- | --- |
| **位置** | `scripts/start-dev.ps1` |
| **改前** | `pnpm ... dev *>&1 \| ForEach-Object { Write-Host; Add-Content }` —— **每行一次 `Add-Content`**（打开→写→关闭文件），读端极慢 |
| **改后** | 内层脚本**落成文件**用 `-File` 执行；输出**自然流向子进程 stdout**，由外层 `Start-Process -RedirectStandardOutput / -RedirectStandardError` 做 **OS 级重定向到文件**（文件**没有读端**，结构上不可能被拖住） |
| **副作用** | 那个 dev 窗口不再实时刷日志。应用自身的日志一直在 `~/.lumii/logs/app/mtbot-*.log`，窗口里也写了提示 |

**改这个脚本时踩的坑（记下来免得再踩）**：

- 脚本第 3 行**原本就写着** `Encoding: ASCII-only comments to avoid PS 5.1 parse
  issues without BOM`。**我一开始没注意，加了中文注释和中文 `Write-Host`** ——
  于是 PS 5.1 按 ANSI 读该文件，中文变乱码，**末尾的单引号被吃掉**，报
  「字符串缺少终止符」。**改回纯 ASCII 即好**。
- `-Command` / `-EncodedCommand` 传多行脚本会在内层**再解析一遍**，引号与尖括号
  都容易出事。**落成文件 + `-File`** 最稳；写文件时用
  `[System.IO.File]::WriteAllText(..., UTF8Encoding $true)` **显式带 BOM**。

#### 效果与验证

| 项 | 结果 |
| --- | --- |
| 单次导出的 WARN 条数 | 数万 → **1 条**（09-19 那天是 71893） |
| dev stdout 的读端 | **无**（文件）→ 结构上不可能再出现「读端拖住写端」 |
| `sync-copy.test.ts` | **24/24 通过** |
| cloud-sync 全目录 | **11 文件 / 131 用例通过** |
| `apps/windows` typecheck | 干净 |
| 实际重启验证 | `pnpm dev:restart` 后 `.lumii-dev.log` 46KB、electron 6 个进程、应用日志正常增长 |

**没有改善的部分（不要误读）**：这两处只掐掉了**当前已知的触发条件**。
若将来别处出现日志风暴（任何逐条打印 + 慢读端），机制依然成立 ——
届时仍应优先**聚合日志**，其次才是「换个不会被拖住的输出目标」。

### 6.7 另一处 native 阻塞：启动时同步删除截图目录（已修）

**现场**：12:18:51 的捕获 —— `kind: native`（evaluate 超时）、窗口 60 秒、
采样覆盖率 **4%**，栈顶分布：

```
7125  unlink@native:-1      ← 占窗口内样本的 61%，约 1.4 秒
4449  (idle)@native:-1
  40  Tray@native:-1
```

**定位**：`unlink` 是文件系统删除调用。对照日志时间线，
`workspace temp 布局已确保` 出现在 **12:18:52.400**，正落在冻结窗口内 ——
其上一行就是 `apps/windows/src/main/index.ts:1387` 的
`clearScreenshotTempDir()`，而它是：

```ts
fs.rmSync(dir, { recursive: true, force: true })   // 同步递归删除，在主线程
fs.mkdirSync(dir, { recursive: true })
```

**量化**（每文件 100KB，与真实截图同量级）：

| 文件数 | 总大小 | `fs.rmSync` 耗时 |
| --- | --- | --- |
| 2000 | 195MB | 277 ms |
| 5000 | 488MB | 699 ms |
| 10000 | 977MB | **1565 ms** |

1.4 秒的观测值与一万个截图吻合。**而这是每次启动都跑的**。

**修法（rename + 后台删）**：目录整体改名（毫秒级）→ 立刻建新空目录 →
真正的删除走 `fs.promises.rm`，**耗时与文件数无关地移出主线程** →
顺带清掉上次遗留的 `.trash-*`。

不直接改成「异步删原目录」的原因：那样在新目录建好与旧文件删完之间有窗口，
用户若立刻截图会被误删；**先改名则不存在这个窗口**。

**验证**（`scripts/probe-screenshot-cleanup-cost.mjs`，10000 个文件）：

| 实现 | 主线程耗时 |
| --- | --- |
| 旧（`rmSync` 递归删） | **1674 ms** |
| 新（rename + 后台删） | **17 ms** |

新目录立刻为 0 项、残留 trash 0 个；`app-ui-control` 测试 10 文件 / 148 用例通过。

### 6.8 未定论：12:23:39 那次「离开 V8 视野」的 4.4 秒

**形态**（`scripts/probe-freeze-timeline.mjs` 输出的时间轴）：

```
-9500ms ~ -500ms   每 500ms 稳定 500 个样本（98% 是 idle）    ← V8 正常
      0ms          251 个样本（其中 247 是 idle）             ← 仍在 idle
 500ms ~ 4000ms    **一个样本都没有**                          ← 关键
   4500ms          55 个样本（emit@node:events / writeBuffer） ← 恢复，处理积压
```

**判读**：主线程是从「idle（事件循环等待）」**进入某个 native 调用**的 ——
中间那 3.5 秒**连 `(idle)` 都没有**，比「只有 idle」更彻底。
这与 §6.7 的 unlink 形态不同：那次还有 61% 的 native 样本可看，这次连采样都采不到。

**三项证据同时指向「主线程真的停了」**（不是某一个信号孤立）：

- 注入心跳停摆 **4361ms**
- 窗口内采样覆盖率 **0.6%**（136 / 10304）
- 日志在 `[12:23:35.4, 12:23:39.8]` 内**一行都没有**

**已排除的假设**（都有证据，不是猜测）：

| 假设 | 排除依据 |
| --- | --- |
| 渲染层卡死 | ❌ 12:23:39.753 那两条 `获取开机启动状态` 正是渲染层发的 IPC —— 它当时活着 |
| IPC 积压 / 大载荷反序列化 | ❌ 恢复后 0.2 秒处理的是 `app:getOpenAtLogin` 这种小消息 |
| `resolveProxy` | ❌ 主进程没有任何 proxy 代码（只有个无关的 `local-proxy.ts`），且窗口内仅 1 个样本，大概率是采样噪声 |
| 系统挂起（Windows Hang） | ❌ 事件日志近 6 小时无 1002 / Hang 记录；4.4 秒也低于其判定阈值 |
| `clearScreenshotTempDir` | ❌ 已修（§6.7），且这次不在启动路径上 |

> ⚠️ **顺带纠正一个判读错误**：`mcp:status` 曾出现 **3 分钟断档**
> （12:21:20 → 12:24:24），我一度当成「渲染层卡了三分钟」。**错了** ——
> `mcp:status` 是**渲染层某几个组件 / hook 发的**（`useMcpServers`、`mcp-service`、
> `useToolSearch`），**组件卸载就不再发**；恢复后的「密集补发」（间隔 11ms、3ms、
> 1ms、2ms）也只是重置后的正常节奏。**它不是心跳，不能像心跳那样当判据用。**

**结论：这次没有定论。** 困难在于该形态**不产生任何可观测的中间状态** ——
无 JS 栈、无日志、连 V8 的 idle 采样都没有。只能等它重现，用两次对比来收敛；
单次推测的证据强度不够。

## 附录：本文修正的四条此前写错的结论

**① 「profile 干净 = 没复现」**（09-19 的结论）

原文：「六次 CPU profile 全部干净，无 >200ms 的 JS 空隙」——据此判断没能复现。
**错了。干净恰恰是 native 阻塞的特征**：V8 采不到 JS 栈，于是留下一个"看不见东西"的
profile。09-20 抓到的两次（10:24:59 的 832 样本、10:25:20 的 119 样本）正是这个形态。
**当时那句「抓不到现场」，实际是「抓到了但没认出来」。**

**② 「瓶颈是 19.4MB 的载荷传输」**

做 SQL 优化前我判断大头是载荷跨 native→JS 边界。**错了**：相关子查询的载荷同样是
19.4MB，却快 7.5 倍 —— **瓶颈是窗口函数的排序**。（对照实验：窗口函数不取 `content_json`
仍需 213ms，与取出全部载荷的 434ms 同一量级。）

**③ 「心跳判据可能误报」——查下来不成立**

10:25:20 那次我一度怀疑误报：冻结窗口是 17.743→20.353，而应用自己的 `mcp:status`
**在 18.661 正常写了日志**。但这两件事不矛盾 —— `mcp:status` 是在阻塞**前或后**的
间隙执行的，而阻塞发生在中间某个回调里。**心跳落后的语义（timers 阶段被推迟多久）
是对的**，不需要推翻。

> 附带说明为什么"双心跳"没能提供独立性：`setInterval` 与递归 `setTimeout` 由**同一个
> timers 阶段**驱动，实测两者数值几乎完全相等。真正独立的信号应当是**不走 timer 的**
> 东西（I/O 回调、外部进程心跳），这留作后续。

**④ 「断档 = 冻结」也需要限定条件 —— 反过来也会错**

v1 的教训是「安静期本来就不打日志，把静默误判成冻结」（假阳性）。但这次扫描
09-20 全天发现**反方向的问题**：14 处 > 8 秒的心跳断档里，**大多数期间日志在正常写**
（最长那处 374 秒的断档里有 183 条其他日志）—— 那些是**渲染层没发这个心跳**，
主线程好得很。只有少数几处是「完全静默」。

**⇒ 判读断档必须问一句：断档期间有没有别的日志？** 有 = 主线程活着；没有 = 才可能是冻结。
本文第六节那条 606 秒线索之所以能成立，也正因为那段时间日志**在写** ——
矛盾（"卡了 10 分钟"却"还在写日志"）才是把注意力引向 `writeLog` 之间那段代码的起点。
