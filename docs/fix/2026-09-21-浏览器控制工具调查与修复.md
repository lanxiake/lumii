## 一、缘起

一次真实会话的错误日志里有两条看似无关的故障：

1. `browser_eval` 返回 `ReferenceError: player is not defined`
2. `bash` 报 `python.exe: can't open file '.../gen_sprites.py': [Errno 2] No such file or directory`

查下去发现是**两个独立的根因**：前者是工具返回体缺了关键字段（§2），后者是模型把工具调用
写进了推理文本、从未真正发出（§3）。两者都不是「浏览器不好用」，而是**模型看不见自己在哪**
与**调用没发出来还编了结果**。

---

## 二、`browser_eval` 的可见性缺陷（已修）

### 2.1 症状与两次误判

模型在页面上求值一个变量，得到 `player is not defined`，随后**连续两轮排查作用域问题**——
写了包装函数、检查了 IIFE、怀疑 `const` 不挂 `window`。全程 **0 次 `browser_navigate`**。

**同一个坑我也踩了**：我采信了模型的归因，把「Playwright 的 `page.evaluate` 看不见顶层
`const`」写进了代码注释。核查 Playwright 源码后是错的——`page.evaluate` 走**主世界 + 间接
eval**（`frames.js` 的 `world ?? "main"`；`utilityScriptSource.js` 用 `this.global.eval(expression)`），
作用域链终点是**全局环境记录**，顶层 `const`/`let` 对它**可见**。只有 `<script type="module">`
的模块作用域与函数/IIFE 内的局部变量不可见。（修正记录见附录 ①）

### 2.2 真因

**会话从头到尾没导航过**，标签一直停在浏览器启动时的 `about:blank`。空白页上不存在任何脚本，
于是任何变量名都报 `is not defined`——这与「目标页上的同名报错」是**完全不同的两件事**，
处置方式也完全不同（一个要先 `browser_navigate`，一个才该查作用域）。

**促成缺陷在产品侧**：`/act` 的 evaluate 分支本就回了 `url` / `targetId`
（`agent.act.ts:315-320`），但工具层的 `pick` 把它们**丢掉了**，只把 `result` 递给模型
——模型拿不到「我在哪个页面」这个**唯一凭据**。日志里那句报错因此成了孤证。

### 2.3 修复

`apps/windows/src/main/agent-runtime/bridge-browser-tools.ts`：

- 新增 `browserEvalPayload()`：透出 `url` / `targetId`，并在 **url 是空白页**
  （`about:blank` / `chrome://newtab` / `chrome://new-tab-page`，允许尾斜杠）时**附一条
  可执行的提示**——「当前标签停在空白页……先用 `browser_navigate` 打开目标 URL 再求值」。
- 提示文案直指**下一步动作**，不复述现象：模型缺的不是「页面是空白的」这个事实（它可以从
  `url` 推出来），而是「**这时候该先导航**」这个处置。

`packages/agent-runtime/src/prompt/sections/misc-sections.ts`：极简档（terse）的浏览器提示
补上 `browser_navigate` 前置条件——此前**只有详细档**写了完整工作流，用极简档的会话
（本机默认 `promptStyle.style = "minimal"`）根本不知道要先导航。

```diff
-You control a live browser: `browser_snapshot` lists interactive elements with refs …
+You control a live browser: `browser_navigate` first to open a URL — until then the tab is
+ a blank page with nothing in it. Then `browser_snapshot` lists interactive elements with refs …
```

**为什么不让提示去替模型判断**：工具返回的是**事实**（你在哪个页面），提示只在该事实
有唯一合理动作时给出（空白页 → 先导航）。目标页上的求值失败**不附任何提示**——
那才轮到模型自己查。

### 2.4 回归

`BROWSER-EVAL-01`（`url` 字段在、求值结果与 CDP 直读交叉一致）、
`BROWSER-EVAL-02`（导航到 `about:blank` 后求值，返回体必须带含 `browser_navigate` 的 `note`）。
两条都在套件里，全通过。

> **注意 EVAL-02 的构造**：必须做**成功**的求值（如 `1+1`）。抛错走的是 `wrapExecute` 的
> error 分支，**不带** `url`/`note`——用抛错去测这个提示是测不到的。

## 三、工具调用只写进推理文本（已加防御）

### 3.1 症状

模型先用 `bash` 去跑一个**并不存在的脚本**，再花两轮才找到真正原因。往回查发现：
它在前一轮把 `file_write` 调用写成了 **XML 文本**（`<invoke name="…"><parameter name="…">`）
放进**推理通道**，而没有作为结构化 `tool_calls` 发出——**调用从未执行**，而它顺手把
「`File written: …`」这个返回也一起编了出来，下一轮就以为自己写过了。

它自己在下一轮醒悟了：「**那条 `File written` 是我在文本里写的幻觉结果**」。

实测规模（Qwen3.8-Flash-Next @ `kms.sczxsc.cn`，OpenAI 兼容端点，思考开启）：
**一次会话里发生 35 次**，其中 3 次编的是 `file_write`。

### 3.2 判据

`packages/agent-runtime/src/reliability/text-tool-invocation.ts`。三个条件**同时**成立：

1. 至少有一个 thinking 块
2. thinking 里同时出现 `<invoke name=` **与** `<parameter name=`
3. 该消息**没有任何** `toolCall` 块

**为什么加第三条**：单看「文本里有 `<invoke`」会误伤——用户完全可能让模型写一段讲 XML
调用的文档。而「一条既不调工具、又在推理里写完整 `<invoke>` 块」的消息，几乎只可能是调用没发出来。

**为什么只看 thinking**：实测 XML 全部落在推理通道（三条消息的正文通道合计 **0 次**），
而推理内容对用户不可见，进一步压掉误判面。

**块顺序不构成判据**：第一版实现在遇到 `toolCall` 时提前 `return false`，导致「thinking 在前
还是 toolCall 在前」会改变结果。已改为扫完再判，并补了一条顺序无关的测试。

### 3.3 防御

接在 `turn_end`，与 `StuckGuard` **同层**——两者处理的是同一类问题：「回合正常结束了，
但过程有问题」。靠 `agent.followUp` 注入纠正提示，**每次运行最多 1 次**（实测模型一次就改；
屡教不改时再注入只会空转烧 token，那种情况该由 `maxTurns` / `StuckGuard` 兜底）。

注入的提示对着模型**自己悟出来**的那两点写：① 调用必须是结构化的；② **不要顺手编返回**
——编了就会把没发生的事当成已发生。

### 3.4 边界：这个检测器抓不到的变体

**2026-09-21 下午实测到另一种形态**（浏览器套件 ERR 步骤，会话 `b9eddfb8`）：
模型在 thinking 里写 "Just one call."，正文直接给出「工具原样返回内容如下：
`- Page snapshot (1 nodes) / RootWebArea`」——**该消息零 tool 块，日志零 `tool:start`**。
结果是编的。

**判别只能靠日志**（`grep "ToolRunner\] → <tool>"` 有没有那一行）。消息结构上无从下手：
模型没有声称要调用，只给了一份"结果"，长度与措辞与正常工具回合**完全一致**。

**没有据此扩检测器**：启发式（「无 toolCall + 含完成态措辞 + 含类工具输出」）误报面太大，
用户讨论工具时会命中。已覆盖的 XML 变体判据更硬——三个条件同时成立。

## 四、首次截图 79–231 秒（已查明，未修）

### 4.1 症状

套件首轮（浏览器刚被拉起）实测：

```
[ToolRunner] ← browser_screenshot durationMs=231641 isError=false
```

**231 秒**。功能正确（产出的图正常），但用户会以为卡死。

### 4.2 定位：排除三个假设

用**裸 CDP** 做对照实验（不经工具层），逐步排除：

| 假设 | 实验 | 结果 |
|---|---|---|
| CDP 通道慢 | 同一次连接里测 `Runtime.evaluate` | **19ms** —— 通道没问题 |
| `captureBeyondViewport` 硬编码惹的祸 | 置 `false` 对比 | **反而更慢**（120s 超时） |
| 页面太大（2751px > maxSide 2000）触发压缩循环 | 只截视口对比 | **一样慢**（视口图 15.3KB） |

### 4.3 真因

**连续截图**的实测序列给出了答案：

| 连续第 N 次 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 耗时 | **79648ms** | 79ms | 90ms | 76ms | 84ms |

**首次极慢，之后快 1000 倍。**

Chrome 以 `headless: false` 运行（`apps/windows/src/main/browser-service.ts:109`），
窗口在**后台**时合成器休眠；首次 `Page.captureScreenshot` 要**等首帧产出**，此后帧已在产就快了。
（`fromSurface: false` 不解决问题，实测更慢——它绕不开合成器。）

### 4.4 建议（未实施）

浏览器拉起后**异步预热一帧**，或在截图前先激活窗口。套件里的 `BROWSER-PERF-01` 会把两次
耗时如实记进证据——它是"用户第一次截图会等多久"的回归防线，**不设阈值断言**（窗口是否在
前台依环境而变）。

## 五、能力边界：没有标签管理

工具集**没有**列标签 / 切标签的命令，且目标选择**粘在** `lastTargetId`
（`browser-control/src/browser/server-context.ts:403-412` 的 `pickDefault()`：优先复用上次
操作过的标签，否则取第一个 `page`）。

**后果**：用户在 Chrome 里手动切到别的标签后，Agent 仍会操作**上一个**标签，而它无从得知。

**缓解**：`browser_snapshot` 返回首行的 `[page] <url> refs=N` 让模型能看见自己在哪一页
——这正是 §2 补 `url` 字段的连带价值。

**未做**：加 `browser_tabs`（列/切）属于能力扩展而非缺陷修复，需单独评估。

## 六、回归防线：浏览器控制套件

`docs/test/lumii-cli/browser/` —— 19 条用例，覆盖 10 个工具 + 稳定性 + 错误处理。

**架构上的一个硬约束**：浏览器工具**只能靠真实 LLM 回合驱动**（CLI 无浏览器命令、控制口
白名单未收录、`browser-control` 的 dispatcher 是进程内的），但**判据绝不能也走工具层**
——用 `browser_eval` 自读页面等于拿被测对象验证被测对象，工具链任何一环撒谎都测不出来
（§3.1 那次幻觉正是如此：当时没有任何独立通道能证伪它）。

所以判据走**裸 CDP**（`127.0.0.1:18791`，Node 24 自带 WebSocket）直连 Chrome 读页面真实状态，
要求**执行层**（DB `messages.parts` 的 `tool` 块）+ **效果层**（CDP 直读 `window.__probe`）
双证据，模型在正文里的自述一律不作为判据。

套件细节、基础设施的坑（探针服务器必须独立进程、端口自动探测、`closeAllConnections`）
见 [`browser-test-cases.md`](../test/lumii-cli/browser/browser-test-cases.md) 与
[`CLI-TEST-SPEC.md`](../test/lumii-cli/CLI-TEST-SPEC.md) 的陷阱清单 13/14。

## 附录：本文修正的两条此前写错的结论

### ① 我信了模型的错误归因，并把它写进了代码注释

模型说 `player is not defined` 是「顶层 `const` 不挂 `window`」，我当时**照抄进了注释**。
真相见 §2.1：`page.evaluate` 走主世界 + 间接 eval，顶层 `const` 对它**可见**；真因是没导航。

**教训**：模型的自我诊断**不可采信**，要自己验。它在下一次故障里又编了一条规律
（「凡是把 `file_write` 和其它调用混在一起发时就容易丢失」）——核对 52 次调用后，
出事的那几次它都是**单独发的**。

### ② 我冤枉了运行时

我曾断言「运行时回报了写入成功、实际没执行」（runtime-reported false success）。
第二个核查证明**不存在这样的代码路径**，运行的代码是清白的。真因是 §3.1 的模型幻觉。

**两次误判的共同毛病**：拿「看起来合理」当「已核实」。这在 §3.1 的现场尤其危险
——模型和我在同一个故障上各自编了一个自洽但错误的解释，而**唯一能分辨的通道是日志与 DB 的
原始记录**，不是任何一方的叙述。

### ③ 顺带：善后数据前必须逐条配对

事故后我写了清洗脚本，第一版判据是「推理里有 XML 签名 → 删掉该消息所有 tool part」。
**预演显示它会删掉 49 个 part，包括 35 个真实执行的记录**——真实执行与幻觉块在 parts 里
长得一模一样（都是 `status: done` + 同样的结果文本）。

逐条与执行日志配对后的结论是：**那三条消息没有一个伪造 part，无需清洗**。
配对方法：`grep "ToolRunner\] → "` 的序列 ↔ parts 里 `type === 'tool'` 的序列按序一一对应，
文件写再用 `FileMemoryHandler [file:created]` 交叉验证。
