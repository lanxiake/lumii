## 🎯 核心设计决策

### 1. 三级风险分级

```typescript
L0 - internal (内部)
  ├─ learning (学习目标)
  ├─ capability-improvement (能力提升)
  └─ memory-optimization (记忆优化)
  → 可自动批准，记审计，可回滚

L1 - user-visible (用户可见)
  └─ proactive-message (主动消息)
  → 需审批，超时拒绝（过期消息是骚扰）

L2 - side-effect (有副作用)
  ├─ skill-enhancement (技能增强)
  └─ 任何包含外部动作关键词的目标
  → 始终需人工审批，超时归档（绝不自动批准）
```

### 2. 超时策略

| 目标类型 | TTL | 超时动作 | 送达失败时 |
|---------|-----|---------|----------|
| learning | 4h | 批准 | 批准（L0） |
| capability-improvement | 4h | 批准 | 批准（L0） |
| memory-optimization | 4h | 批准 | 批准（L0） |
| proactive-message | 2h | 拒绝 | 归档 |
| skill-enhancement | 24h | 归档 | 归档 |

**关键原则**: 送达失败时不能当作"默示同意"，L0 外一律归档。

### 3. 审批文案设计

```
🎯 我想做一件事，需要你确认

[能力提升] 提升代码生成能力：从 52% 提升到 70%
原因：最近 7 次代码任务中有 3 次你不满意
优先级：⭐⭐⭐⭐

回复 1 = 同意  2 = 拒绝  3 = 以后同类都自动同意

（超时将按目标类型采取默认动作，不会打扰你）
```

**设计要点**:
- 复用渠道审批的 1/2/3 语义，保持一致
- 提前告知超时行为，用户不回复也知道会发生什么
- 简洁明了，适合在手机端快速操作

## 📈 性能考虑

### 数据库索引

已创建的索引：
- `idx_approvals_pending`: 支持快速查询待审批项
- `idx_approvals_goal`: 唯一索引，保证一个目标只有一条审批记录

### 刷新策略

- 仪表板每 30 秒自动刷新
- 超时扫描每 15 分钟执行一次
- 可根据实际需求调整频率

### 内存占用

- 审批队列使用数据库持久化，不占用内存
- 超时扫描器仅持有定时器，内存占用极小
