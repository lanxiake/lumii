## 3.0 主轴：模型给语义信号，代码掌握控制权

这是整门课唯一一条贯穿所有章节的规则：

> **模型提供语义信号；代码负责权限、规则、顺序和副作用。**

固定规则、授权、金额限制、安全联锁**放在代码里，不靠模型记忆**。

原语定义"问什么"，**架构模式定义"判断结果怎样进入程序"**。

| 模式 | 它做什么 | 声称收益 |
| --- | --- | --- |
| **推测式扇出** | 单次调用发送多个问题（含推测性问题），代码决定哪些相关 | 成本、速度 |
| **置信度门控路由** | 把置信度用作**第二个决策轴** | 可靠性、安全性 |
| **复合评分** | 把多个分析维度合并为单一评分 | 成本、可靠性、速度 |
| **意图路由** | 分类用户意图并路由到相应处理器 | 成本、速度 |

---

## 3.1 推测式扇出

**核心**：把系统**可能需要**的全部问题放进一次请求并行评估，
之后**由代码判断哪些相关、忽略不相关的答案**。

### 示例：支持工单分诊

一次请求问 5 个问题：

| 问题 | 类型 | 说明 |
| --- | --- | --- |
| `category` | `choice` | `bug_report` / `billing` / `feature_request` / `account` |
| `bug_severity` | `score` | 3 档：外观问题 / 功能降级有绕过 / 阻塞无绕过 |
| `has_reproducible_steps` | `noul` | 用户是否描述了具体复现步骤 |
| `refund_requested` | `noul` | 用户是否明确要求退款或抵扣 |
| `frustration` | `score` | 3 档：平静 / 不满但克制 / 非常愤怒 |

**其中两个是推测性问题**——`bug_severity` 和 `has_reproducible_steps` 只在缺陷报告时有意义，
`refund_requested` 只对账务类有意义。官方解释提前放入的理由：

> 增加的问题通常对响应时间**几乎没有影响**；
> 若工单是功能请求，缺陷严重程度的结果不相关，**代码直接忽略**。

对应的路由代码：

```python
category    = response.answers["category"]
bug_severity = response.answers["bug_severity"]
bug_repro   = response.answers["has_reproducible_steps"]
refund      = response.answers["refund_requested"]
frustration = response.answers["frustration"]

if category.choice == "bug_report":
    if bug_severity.score > 1.5 and bug_repro.noul > 0.6:
        escalate_to_engineering(ticket_id, severity="high")
    else:
        add_to_bug_backlog(ticket_id)

elif category.choice == "billing":
    if refund.noul > 0.7:
        route_to_billing_with_flag(ticket_id, refund_likely=True)
    else:
        route_to_billing(ticket_id)

elif category.choice == "feature_request":
    log_feature_request(ticket_id)

# 无条件末尾——与类别无关的情绪信号
if frustration.score > 1.5:
    flag_for_priority_response(ticket_id)
```

注意 `frustration` 那一段：它是**跨类别通用的一条策略**，写在分支之外。
这是扇出的一个典型价值——**一次调用同时喂了多条正交策略**。

### 成本依据

官方索引页与 `primitives` 页声称：**13 个问题合并到一次调用比 13 次单独调用便宜、快得多**。

> ⚠️ **文档内数字不一致**：`primitives` 页写「便宜 **11.5** 倍、快 **9.6** 倍」，
> 而 `cookbooks` 索引与 `parallel_questions` cookbook 本身都写「便宜 **12.2** 倍、快 **10.0** 倍」。
> 以 cookbook 实测页为准（见 [04-配方：检索与证据](04-配方-检索与证据.md)）。

## 3.2 置信度门控路由

**核心**：把置信度当作**第二个维度**——

> **答案告诉你「是什么」，置信度告诉你「是否行动」。**

### 示例：语音银行指令

一个问题定意图，代码按置信度分层：

```python
action = response.answers["intent"]

if action.confidence < 0.6:
    # 模型真正不确定——一律转人工，不猜
    route_to_support_agent(account_id)

elif action.choice == "check_balance":
    # 低风险：0.6 就够。最坏情况是再听一遍余额播报。
    show_balance(account_id)

elif action.choice == "approve_transfer":
    if action.confidence > 0.85:
        # 高风险 + 高置信：自动执行
        approve_transfer(account_id)
    else:
        # 高风险 + 中等置信：先确认
        ask_user_to_confirm("Just to confirm: you would like to approve this transfer, is that correct?")

else:
    route_to_support_agent(account_id)
```

**阈值依据**（官方原话）：0.6 的下限**会捕捉模型真正不确定的一切情况**；
在此之上每种操作各有阈值，**依据是分类错误时执行该操作的后果有多严重**。

| 操作 | 阈值 | 理由 |
| --- | --- | --- |
| 任何意图 | `< 0.6` → 转人工 | 真正不确定 |
| 查余额 | `≥ 0.6` 即可 | 最坏情况是重听一遍播报 |
| 批准转账 | `> 0.85` 自动，`0.6–0.85` 请用户确认 | 后果不可逆 |

### 关键反例：选最大概率不总是最优动作

这是整门课最重要的一个反例。给定预测分布 `p(y|x)` 与损失函数 `L(a,y)`，
决策论中的 **Bayes 动作**是最小化**后验期望损失**：

```
a* = argmin_a Σ_y p(y|x) · L(a,y)
```

**玩具例子**（损失单位任意，只用于演算）：

- 模型判断「有紧急问题」的概率 = **0.20**（非紧急 0.80，**是最大概率类别**）
- 自动关闭的损失：问题确实紧急时 = **100**，否则 = 0
- 转人工审核：无论如何 = **4**

```
自动关闭期望损失 = 0.20 × 100 + 0.80 × 0 = 20
转人工期望损失   = 4
```

> **结论：尽管「非紧急」是最大概率类别，最小期望损失策略仍然是转人工。**

只有当「动作就是预测类别且采用 0–1 损失」时，这套规则才退化成 argmax。
**实际设计要把拒绝 / 澄清 / 人工审核也当成可选动作**，
阈值用验证数据和真实业务成本定——**不是把 0.7 当通用常数**。

### risk–coverage 权衡

拒绝选项（selective prediction）允许系统只对一部分样本自动作答：

| 概念 | 定义 |
| --- | --- |
| **Coverage** | 自动接收的比例 |
| **Risk** | 这些已接收样本中的错误率 |

- **降阈值** → 覆盖率↑，风险↑
- **升阈值** → 反之

**阈值应按标注数据与业务损失选择，而不是把 0.7 当成通用常数。**

> 学术背景：`SelectiveNet (ICML 2019)` 把 reject option 与 risk–coverage trade-off 作为研究问题。
> 教程里的门控是**应用策略示例，不是 SelectiveNet，也不自动提供风险保证**。

## 3.3 复合评分

**核心**：**独立地对每个维度评分**，然后在代码里归一化 + 加权组合。

### 示例：简历筛选

一次请求问 4 个 Score 问题（各 5 档）：

| 维度 | 最低档 → 最高档 |
| --- | --- |
| `python_depth` | 没提 Python → 深度专长：架构、性能、库 |
| `team_leadership` | 没提管理 → 管过多个团队或工程组织 |
| `system_design` | 没提架构 → 跨多领域的大规模系统设计 |
| `generalist` | 只有一个领域 → 反复在陌生领域快速上手并交付 |

```python
py      = response.answers["python_depth"].score / 4      # 5 档 → 除以 4 归一化到 0–1
lead    = response.answers["team_leadership"].score / 4
arch    = response.answers["system_design"].score / 4
general = response.answers["generalist"].score / 4

# Senior IC
ic_score = (0.40 * py) + (0.10 * lead) + (0.40 * arch) + (0.10 * general)

# Engineering Manager
em_score = (0.15 * py) + (0.40 * lead) + (0.20 * arch) + (0.25 * general)
```

**归一化公式**（对 K 档量表）：

```
normalized = score / (len(criteria) - 1)
```

**这套做法的价值**：若排名最高的候选不符合预期，**调整权重**即可——
单个维度的评分细节不会丢失。

### ⚠️ 三个必须注意的地方

1. **权重是业务政策，不是模型事实**——官方称之为「业务取舍的表达」
2. **尺度不一致时加权没有清晰含义**——先归一化，或先确认各单位可比
3. **官方禁令：不要在一个问题里隐藏多个判断**——所以是拆成 4 个 Score 而不是 1 个总分

## 3.4 意图路由

**核心**：把 TypeSafe 作为**快速、廉价的分类器**部署在昂贵处理器**之前**。

### 示例：客服路由

一次请求问 2 个问题：

| 问题 | 类型 | criteria |
| --- | --- | --- |
| `intent` | `choice` | `order_status` / `product_question` / `return_exchange` / `complaint` |
| `complexity` | `score` | 简单查询或标准流程 / 需要判断或多步 / 异常情况或需要升级 |

```python
def route_ticket(ticket_id, response):
    intent = response.answers["intent"]
    complexity = response.answers["complexity"]

    # 第一道门：意图本身是否可靠
    if intent.confidence < 0.5:
        return route_to_human_agent(ticket_id)

    if intent.choice == "order_status":
        # 完全不需要 LLM 的确定性代码
        handle_order_status(ticket_id)

    elif intent.choice == "product_question":
        handle_with_llm(ticket_id, PRODUCT_SPECIALIST)

    elif intent.choice == "return_exchange":
        handle_with_llm(ticket_id, RETURNS_SPECIALIST)

    elif intent.choice == "complaint":
        # 第二道门：复杂度分数 + 它自己的置信度
        low_confidence = complexity.confidence < 0.5
        if complexity.score > 1 or low_confidence:
            route_to_human_agent(ticket_id)
        else:
            handle_with_llm(ticket_id, COMPLAINT_RESOLUTION)
```

**四条分支代表了四类不同成本的处理器**：

| 意图 | 处理器 | 成本 |
| --- | --- | --- |
| `order_status` | **确定性代码，无 LLM** | 最低 |
| `product_question` | 产品专家 LLM（**加载不同上下文**） | 高 |
| `return_exchange` | 退货专家 LLM | 高 |
| `complaint` | 投诉解决 LLM / 人工 | 最高 |

> 官方强调两点：
> （1）**TypeSafe 一次快速调用完成全部分类，昂贵资源只被真正需要的请求调用**。
> （2）**注意针对复杂度分数的额外置信度检查**——
> **结合系统情境和决策风险理解低置信度分数的含义始终十分重要**。

### ⚠️ 路由器本身会错

四个模式里官方唯一点明的失败方式是「**路由器本身会错**」。
所以意图路由**必须**配上：**未知类、fallback 和监控**。

（课程第 4 章的练习里也专门要求："把五类消息分派给处理器。**另加未知意图、低置信和处理器失败路径**，
避免把『未识别』硬塞进最接近的已知类。"）

## 3.5 设计检查清单（官方给的，直接可当评审项）

- [ ] **固定规则、授权、金额限制、安全联锁在代码里**，不靠模型记忆
- [ ] 遇到**无证据、低置信或超出选项范围**的结果，要有**拒绝或人工升级**路径
- [ ] 多维分数先定义**单位、尺度和权重来源**；**权重是业务政策，不是模型事实**
- [ ] 对自动动作**记录输入版本、判断结果、使用的规则和动作结果**，便于复盘

## 3.6 组合起来的样子

官方给的整体流程图（一份 state 走完四种模式）：

```
State
  → 扇出：提出候选问题
  → 类型化判断与分布
  → 门控策略判定
      ├─ 未知或风险高 → 拒绝 / 澄清 / 人工复核
      └─ 达到目标条件 → 代码组合维度与权重
                        → 意图路由
                        → 受控处理器
```

> **代码掌握控制流**：模型只在这条链路的判定节点上出现，**不掌握跳转**。

## 3.7 与"智能体"架构的对比

`concepts/how-to-build-with-system-one` 给了三种软件架构的定位：

| 架构 | 特征 | 风险 |
| --- | --- | --- |
| **传统代码** | 简单原语组合成可靠抽象 | 无法处理语义 |
| **智能体** | 自行选下一步 | **每循环都有脱轨风险** |
| **TypeSafe** | 代码掌控控制流，**模型做原子且受约束的判断** | — |

官方明确建议：**避免智能体式 while 循环（软件能表达同样行为时）**。
