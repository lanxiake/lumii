## 6.1 结构恢复（`06_结构恢复`）

**任务**：从丢失格式的纯文本重建 Markdown。

**核心承诺**：**模型从不生成文本**，只回答关于文档的狭窄问题；
**渲染由代码完成，因此输出每个字符都来自输入、每个判断都带概率。**

### 两遍请求

**第 1 遍 · 拼接**：对每对相邻行提一个 Noul——「这一行是否从句子中间接续上一行？」
所有问题对放进**单次请求**；被空行分隔的行对跳过。

**第 2 遍 · 分类**：对每个合并后的块提一个 Choice（六类）+ **伴随问题**：

| 块类型 | 伴随问题 |
| --- | --- |
| `heading` | 级别（title / section / subsection） |
| `list_item` | 步骤顺序（Noul） |
| `callout` | 种类（note / tip / warning） |

**伴随问题的策略**：**在同一次请求中提前问，即使大多数答案永不被读取**。
官方理由：

> 多加一个问题代价小（**state 占大部分 token，只发一次**），
> 而**多一次往返会增加整整一个请求的延迟**。

### 六类块的 criteria（原文，可直接借鉴）

| 类型 | 描述 |
| --- | --- |
| `heading` | **不是完整句子**的短标签或标题，命名文档或其后的章节 |
| `paragraph` | 连续散文：一个或多个完整句子 |
| `list_item` | 平行列表中的**一项**——读起来像是若干同级条目之一 |
| `quote` | 归属于某人或某来源的话 |
| `code` | 计算机代码、shell 命令、终端输出或配置片段，**需逐字阅读** |
| `callout` | **打断行文**以标记读者不能错过之事的警告/提示/重要说明 |

（`heading` 那句"不是完整句子"是关键——它是与 `paragraph` 的分界。）

### ⚠️ 最重要的教训：问题要问"最狭窄的事实"

官方做了 A/B 对照：

| 问法 | 结果 |
| --- | --- |
| ❌「这两行是否属于**同一段落**？」 | 无标记的短行列表在主题上连续，模型对每对都答"是"，**整个列表被拼成一个长块** → **12 块** |
| ✅「这一行是否**从句子中间接续**上一行？」 | 问的是**文本本身** → **17 块**（正确） |

对照数据（同一批行，两种问法）：

| 行 | "same paragraph" | "mid-sentence" |
| --- | --- | --- |
| L015 | 0.77 | **0.22** |
| L016 | 0.81 | **0.11** |
| L017 | 0.78 | **0.12** |
| L020 | 0.88 | **0.08** |
| L021 | 0.91 | **0.05** |

> **官方结论：当一个主观判断要喂给阈值时，问题应当指明决定它的那个最狭窄的事实。**

### ⚠️ 阈值必须分两档

```python
JOIN_AFTER_DANGLING, JOIN_AFTER_TERMINAL = 0.2, 0.5

def ends_terminal(text):
    return bool(re.search(r'[.!?:;…]["\')\]]*$', text))

bar = JOIN_AFTER_TERMINAL if i and ends_terminal(LINES[i-1]["text"]) else JOIN_AFTER_DANGLING
```

**为什么不能只用一个 0.5**：

- 真实的句中被拆行得分**低至 0.39**，单一 0.5 截断会**拆散健康段落**
- 而团队列表跟在冒号后只得 **0.22**，会**越过 0.2 截断**

**关键点**：`ends_terminal` 是**代码读得到的事实**（上一行是否以终结性标点结尾），
不需要模型判断。

逐行拼接概率实测：

```
真接续行：L002 0.77、L003 0.62、L004 0.39、L007 0.42、L008 0.59、L011 0.48、L012 0.40、L014 0.50
作者本意换行：L015 0.22、L016 0.11、L017 0.12
```

### 实测规模与成本

| 项 | 值 |
| --- | --- |
| 备忘录规模 | **28 个非空行** |
| 第 1 遍 | 16 个 pair 问题、**单次请求 0.32s** |
| 合并结果 | **28 行 → 17 块**（11 处换行被修复） |
| 第 2 遍 | **62 个问题**关于 17 个块、**单次请求 0.51s** |
| 合计 | **10,211 tokens、0.8s** |

> ⚠️ **页面内部成本不一致**：附录代码输出打印 `$0.0003`，
> 但正文两处都写 `$0.0015`。**照实记录，不判定哪个对。**

### 分类置信度分布

| 块 | 类型 | conf | 伴随 |
| --- | --- | --- | --- |
| B000 | heading | 0.99 | title |
| B002 | heading | **0.75** | section |
| B004 | code | 1.00 | |
| B006 | paragraph | **0.43** | |
| B007–B009 | list_item | 0.99 / 1.00 / 0.99 | step **0.15 / 0.16 / 0.12** |

**置信度最低的块**："The cutover touches three teams, so check whether you are on this list
before you plan anything for Monday:" → **confidence 0.43**
（paragraph 0.53 / list_item 0.24 / callout 0.19）

**STEP_THRESHOLD = 0.5 的用法**：`ordered = sum(step) / len(items) >= 0.5`

## 6.2 实体对齐（`09_实体对齐`）

**任务**：判断两份啤酒目录的 **450 个候选配对**哪些是同一款产品。

### 一道 Score + 三个伴随 Noul，同一次请求

```python
LEVELS = [
    "They describe two different products.",
    "They describe closely related products that may or may not be the same one: "
    "a variant, a special edition, or a name that could plausibly refer to either.",
    "They describe one and the same product.",
]
OUTCOME = {0: "leave unlinked", 1: "curator queue", 2: "assert sameAs"}

QUESTIONS = {
    "link_state":   Score(instructions="How do the two entity descriptions relate as products?", criteria=LEVELS),
    "same_name":    Noul(instructions="Do the two entities state the same beer name?"),
    "same_brewery": Noul(instructions="Are the two entities from the same brewery?"),
    "same_style":   Noul(instructions="Do the two entities describe the same beer style?"),
}
```

**注意为什么没有 `alcohol content` 的 Noul**：

> `alcohol content` **不做 Noul，因为比较两个数字是算术，想在代码里算就行**。

### 全套做法就一行

```python
def route(score_value: float) -> str:
    """The whole decision rule: the nearest level names the outcome."""
    return OUTCOME[min(int(score_value + 0.5), len(LEVELS) - 1)]
```

> **四舍五入到最近层级——无需任何针对自己数据拟合的阈值。**

切割点 **0.5 与 1.5** 不是调出来的，**源自层级措辞**。

### 为什么用 Score 而不是 Choice 或 Noul

官方给了完整理由（这段是选型的好教材）：

> 要把语义标签（评分标准）**直接附加到每个结果上，包括中间结果**；
> `Noul` 需要对其输出做**阈值处理**才能间接做到；
> 而 `Choice` 会**丢失三种结果之间的有序关系**。

### 为什么必须有中间层

> **不恰当地合并两个实体是代价更高的错误**——
> 每条事实、每个链接都会带到合并实体，撤销要弄清事实来源；
> **漏匹配只留下一个重复项**。

所以需要第三个选项：**"既不能安全合并也不能安全丢弃"**。

中间层措辞覆盖：**变体、特别版、可能合理指向任一产品的名称**。

### 实测

| 配对 | score | confidence | 路由 | name / brewery / style |
| --- | --- | --- | --- | --- |
| `c446` | **1.94** | 0.92 | assert sameAs | 0.97 / 0.99 / 0.81 |
| `c427` | **0.03** | 0.95 | leave unlinked | 0.02 / 0.09 / 0.08 |
| `c100` | **1.30** | **0.27** | curator queue | 0.95 / 0.94 / **0.35** |
| `c428` | **1.10** | 0.77 | curator queue | 0.63 / 0.98 / 0.74 |

**全量路由结果**：

| 结果 | 数量 | 占比 |
| --- | --- | --- |
| `assert sameAs` | 40 | **8.9%** |
| `curator queue` | 50 | **11.1%** |
| `leave unlinked` | 360 | **80.0%** |

**分数分布**：大多数落在 **0.25 附近**，**并不整齐落在整数上**。

**切割点拥挤度**（说明为什么中间层重要）：

- **9 对**位于上切割点 1.5 附近 **0.1 以内** → 决定**什么被合并进图谱**
- **47 对**与下切割点 0.5 靠得同样近 → 只决定**策展人是否看到该对**

**`c100` 是一个好例子**：name 0.95、brewery 0.94 都高，但 **style 只有 0.35**——
两个数据源对 style 措辞不同，所以进策展人队列。

## 6.3 日期抽取（`14_日期抽取`）—— 最值得抄的一篇

**核心**：模型**只读文本、绝不做日历计算**；**所有日历运算都在代码里**。

### 为什么日期可以被"枚举"

官方解释（这段很有洞察）：

> 日期的每个组成部分都是**一个小型封闭集合**：十二个月份、三十一个可能的日期、有界的年份范围。
> 这让**提取变成在枚举选项上做 `Choice`**，而不是自由格式的解析，
> 也让你**可以放一个明确的"未提及"选项**，
> 从而让**缺失的部分被报告出来而不是被猜测**。

### 7 个 Choice 问题

| 键 | criteria |
| --- | --- |
| `mode` | `absolute`（写明月份的日历日期）/ `relative`（相对今天）/ `none` |
| `month` | 12 个月 + `none` |
| `day` | `1`–`31` + `none` |
| `year` | **1900–2050 每年一项** + `out_of_range` + `none` |
| `day_anchor` | `today` / `tomorrow` / `day_after`（后天）/ `weekday` / `none` |
| `weekday` | 周一到周日 + `none` |
| `week_offset` | `current`（this Thursday）/ `next`（next Thursday）/ `none`（裸星期几） |

**两个逃生口的设计**（关键）：

```python
"out_of_range": "A year is stated for this date but is outside the listed range."
"none":         "No year is stated for this date."
```

统一缺席文案：

```python
absent = "The document does not state this, or it is not this kind of date."
```

> **提示**：如果嫌 year 选项列表太长（151 项），可以**先从文本抽出像年份的数字、只把那些喂给模型**。

### 代码里的日历约定

```python
TODAY = date(2026, 7, 30)     # 固定「今天」（星期四），让相对日期可复现
REVIEW_BELOW = 0.60
YEAR_WINDOW = list(range(1900, 2051))

def resolve_weekday(today, weekday, week_offset) -> date:
    w = WEEKDAYS.index(weekday)
    this_monday = today - timedelta(days=today.weekday())
    if week_offset == "next":    return this_monday + timedelta(days=7 + w)   # 下一日历周
    if week_offset == "current": return this_monday + timedelta(days=w)       # 本周
    return today + timedelta(days=(w - today.weekday()) % 7)                  # 裸：今天或之后最近
```

> **「next Thursday」可指两个不同日子，由代码约定决定哪一个——
> 不要交给模型算。**

年份补全规则：

```python
if year == "none":
    resolved = date(today.year, MONTHS[month], int(day))
    # 只有当该日期已过去一个多月才移到下一年
    if resolved < today - timedelta(days=31):
        resolved = date(today.year + 1, MONTHS[month], int(day))
```

异常处理：

| 情况 | 处理 |
| --- | --- |
| `year == "out_of_range"` | **不猜**，标 note `f"year outside {YEAR_WINDOW[0]}-{YEAR_WINDOW[-1]}"` |
| `mode == absolute` 但缺 month/day | `result(None, "absolute date incomplete")` |
| `date(...)` 抛 `ValueError`（如 2 月 30） | `result(None, f"impossible date: {month} {day}")` |

### 置信度传导：取最低

> 置信度 = **该日期形态实际用到的各部分置信度中的最低者**。

```python
needs_review = (resolved is None or confidence is None or confidence < REVIEW_BELOW)
```

**任何一个 part 弱都可能把整个日期送审核。**

### 实测（`TODAY = 2026-07-30`）

| 文档 | 角色 | 结果 | conf | 路由 |
| --- | --- | --- | --- | --- |
| CONTRACT | takes effect | 2025-01-01 | 0.97 | auto |
| CONTRACT | expires | 2027-12-31 | 0.91 | auto |
| FORM | deadline to return | 2026-08-14（**无年份，代码补 2026**） | 0.95 | auto |
| FORM | kickoff call | **None** | **0.46** | **review**（note: `absolute date incomplete`） |
| SURVEY | survey closes | 2026-07-30（"today"） | 0.94 | auto |
| REVIEW | design review | 2026-08-06（"next Thursday"） | 0.92 | auto |

**auto-accept 5 个，send to review 1 个。**

## 6.4 预解析值抽取（`15_预解析值`）

**核心**：**正则先把候选找出来（宁多勿漏），模型只在候选里挑一个**，
**代码对选中的值逐字复制再规范化**。

> **模型不可能凭空发明值或调换数字。**

### 三个正则

```python
EMAIL_RE = re.compile(r"[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}")
PHONE_RE = re.compile(r"\(?\+?\d[\d\s()\-.]{6,}\d")
MONEY_RE = re.compile(r"[$€£¥]\s?\d[\d,]*(?:\.\d{2})?")
```

`find(pattern, text)` 去重、**保持文档顺序**。

### 候选本身就是选项

```python
NONE = "none"

criteria = {c: None for c in candidates} | {NONE: "None of these is the requested value."}
```

**`choice` 是候选之一的原样副本。**

### 实测三个案例

**邮件**——4 个候选：

```
['dana.whit@acme-corp.com', 'billing@acme-corp.com', 'orders@acme-corp.com', 'dana.personal@gmail.com']
```

| 问什么 | 结果 | conf |
| --- | --- | --- |
| receipt → | `dana.personal@gmail.com` | 0.98 |
| sender（From 行）→ | `dana.whit@acme-corp.com` | 1.00 |

**电话**——3 个候选（都无国家代码）：

| 问什么 | 结果 | conf |
| --- | --- | --- |
| mobile → | `(415) 555-0177` | 1.00 |
| country → | `US`（选项列表 `["US","GB","DE","FR","CA","AU"]`） | 0.90 |

→ `phonenumbers.format_number(parsed, PhoneNumberFormat.E164)` → **`+14155550177`**

**金额**——发票 INV-2087，4 个候选 `['$1,200.00', '$115.50', '$1,315.50', '$50.00']`：

| 问什么 | 结果 | P(credit) | 归类 |
| --- | --- | --- | --- |
| total due → | `$1,315.50` | 0.01 | charge |
| credit → | `$50.00` | 0.99 | credit |

### ⚠️ 三条边界

1. **一个 Choice 最多 255 个选项**；候选超过时分两步：**先挑区块、再挑其中的片段**。
2. **找候选才是费功夫的部分**：邮箱/电话/金额都有正则，
   **但「名字」没有**——**名字候选必须来自已有名册、命名实体识别器或 LLM 提出**。
3. **`to_decimal` 假定美的分组**（`$1,315.50` = 逗号千位、句点小数）；
   **`€1.315,50` 正相反**。官方建议：
   **用一个 Noul 问文档用哪种约定、再在代码里分支**。

## 6.5 层级分类（`16_层级分类`）

**核心**：把文档在深层层级中分类到叶子，用 Choice 概率做**并行束搜索**，
按**几何平均边概率**保留 K 条路径，**并和贪心搜索对比**。

### 每个兄弟集合 = 一个 Choice

```python
def child_question(labels):
    keys = {f"c{i}": label for i, label in enumerate(labels)}
    return Choice(instructions="Which direct child category best matches this document?", criteria=keys)
```

> 把 label 映射到 `c0/c1/...` 是**可逆映射**——避免长标签名占 token。

### 两条打分公式（页面明确写出）

```
path_score = product(edge_probabilities) ** (1 / decisions)     # 几何平均，用于剪枝
separation = top_path_score / second_path_score                  # 仅作指标，不用于剪枝
```

- **`separation` 接近 1× = 含糊；大 = 区分清晰**
- **备选指标**：`min(top_prob / second_top_prob)`——优化「**每个节点都决定得很清晰**」的路径
- **超过 10 层的层级**：用 `exp(mean(log(probs)))` 替代，**避免浮点精度损失**

### 束搜索

```python
MODEL, BEAM_WIDTH, MAX_DEPTH, EPSILON = "jev-1.12", 3, 12, 1e-9

# 每层：区分 expandable / finished；对前沿并行提问；合并后按 score 取 top-K
beam = sorted(finished + expanded, key=score, reverse=True)[:BEAM_WIDTH]
```

```python
def extend_candidate(candidate, label, probabilities):
    is_decision = len(probabilities) > 1
    probability_product *= max(probabilities[label], EPSILON) if is_decision else 1.0
    decision_count += is_decision
    score = probability_product ** (1 / decision_count) if decision_count else 1.0
```

> **`is_decision` 的技巧**：单标签节点不是"决策"，**不计入分母**——
> 否则假决策会**稀释**路径分数。

### 实测：束搜索 4/4，贪心 2/4

| 分类体系 | 预期叶子 | 贪心 | 束搜索 K=3 |
| --- | --- | --- | --- |
| **CPC patents** | `A01K31/12 Perches for poultry or birds, e.g. roosts` | ❌ `E99Z99/00 Subject matter not otherwise provided for in this section` | ✅ |
| **Shopify products** | `Cat Window Beds & Perches` | ❌ `Pet Chairs` | ✅ |
| MeSH | `C06.405.469.432.500 Crohn Disease` | ✅ | ✅ |
| CookSafe files | `retrievers.py` | ✅ | ✅ |

> **贪心搜索早期错误不可挽回；束搜索让更深层证据修复早期含糊决定。**
>
> 束搜索**每层把 frontier 当并行问题跑，额外探索几乎不增加实际耗时**。

### 三条工程细节

1. **MeSH 是 DAG**——一个描述符可出现在多个父节点下，
   要把官方 tree-number 路径**展开**成树才能喂给树形束搜索。
2. **`_load_codebase` 读的是渲染时冻结的快照**（`codebase_files.txt`），**不是实时 walk**——
   否则**分类体系和所有数字会随读者 checkout 漂移**。
   而且**行序有意义**（兄弟选项按出现顺序提问，**属于问题本身而非展示**）。
3. 此篇用 `os.environ["TYPESAFE_API_KEY"]` **直接索引**（无 `.get`），
   并配了显式重试：`RetryPolicy(max_retries=5, backoff_initial=1.0, backoff_max=20.0)`。

## 6.6 自动研究特征发现（`17_自动研究特征发现`）

**核心**：**LLM 提案者自己提出 TypeSafe 问题**，把自由文本变成数值特征喂给 CatBoost，
再用**模型误差反馈**驱动下一轮提案。

### 四步循环

```
propose  ← LLM 读 [当前问题清单 + 60 条笔记 + 上轮记分板]，返回 ≤18 个 action（add/revise/drop）
answer   ← 每条笔记一次请求（携带该轮所有问题），得概率
fit      ← 编码成数值列 → CatBoost 5折×3重复 CV
feedback ← 记分板：CV RMSE 历史、变好/变差的笔记数、每特征重要性与列标准差
```

### 编码：Score 概率 → 数值列

```python
mean = probabilities @ levels
variance = probabilities @ (levels**2) - mean**2
# mode="mean"       → 1 列 (name, mean)
# mode="mean_spread"→ 2 列 (name, mean) 与 (f"{name}_sd", sqrt(clip(variance, 0, None)))
# 否则               → 每档一列 {name}_p{i}
```

`presence`（Noul）→ 1 列。

### 修订/删除必须"先试再留"

> **修改或删除会移走模型正在用的列，所以必须先试**
> （重拟合**无 API 调用，免费**），**只有 dev 误差下降才保留**。

```python
if cv_trial <= cv + tolerance:   # CHANGE_TOLERANCE = 0.0
    keep
else:
    return f"would cost {cv_trial - cv:+.3f}"
```

新增问题另有门槛：**列 std < `MIN_SPREAD`(0.05) 视为 flat，不保留**。

### 实测（2,000 条 WineMag 品鉴笔记）

所有对比**在 800 条留出行上各评一次**（模型与循环从未见过）。

| 方案 | RMSE | Spearman |
| --- | --- | --- |
| 预测训练行平均分 | 3.088 | -0.014 |
| 同一 CatBoost 把笔记当词频 | 2.466 | 0.605 |
| 直接让 TypeSafe 给分再重缩放平移（shift -1.71） | 2.145 | 0.761 |
| 一次提案 18 个问题、无循环 | 1.869 | 0.778 |
| **循环五轮后 38 个问题** | **1.772** | **0.799** |

**逐轮 dev CV RMSE**：

| 轮 | action | 特征数 | dev CV RMSE |
| --- | --- | --- | --- |
| 1 | 18 add / 0 revise / 0 drop | 18 | 1.903 |
| 2 | 5 add / 3 revise / 3 drop | 23 | 1.881 |
| 3 | 7 add / 2 revise / 1 drop | 30 | 1.861 |
| 4 | 5 add / 2 revise / 3 drop | 35 | **1.838** |
| 5 | 4 add / 2 revise / **8 drop** | 38 | **1.840** |

> **第 1 轮 → 第 5 轮的留出增益：-0.097 分，95% CI [-0.147, -0.050]。**
> 即**后四轮在留出行上价值约 0.10 分**。
>
> 注意第 5 轮：**提案者已从"加问题"转向"删问题"**，且给出了第一个**没有改善**的 dev 数字。

**最终 38 个问题 = 29 score + 9 noul** → **67 个数值列**。

**特征重要性 top 5**：

| 特征 | 重要性 |
| --- | --- |
| `note_overall_tone_positivity`（score） | **17.4%** |
| `savory_food_wine_seriousness`（score） | 8.7% |
| `positive_superlative_language`（score） | 8.4% |
| `single_vineyard_or_prestige_signal`（**noul**） | 7.2% |
| `descriptive_detail_density`（score） | 5.7% |

### ⚠️ 四条最重要的实操边界

1. **`Score` 最多 10 档，11 个会返回服务器错误**——`SCORE_LEVELS` 正好 10 档。
2. **请求数随行数增长、不随问题数增长**：
   > 每轮每行一个请求，**100,000 行 = 每轮 100,000 请求**；
   > 一次 revise 算新问题，**要对每一行重答**。
   > 工作线程池要**缓慢调大**，**8 个并流就足以在共享密钥上触发速率限制**。
3. **提案前不预过滤任何问题**：
   > 一个只适用 1/10 行的问题，在提案者读的 60 条笔记里看似无用，
   > **却可能是全集最有用的列**。
4. **直接问分路线需要偏移量**：
   仅把档位铺到 80–100 量表不够（问题里没写该刊物评分实际落点），
   所以用 dev 测出的**单一 offset** 平移（`shift = -1.71`）——
   **这是该捷径从分数里学到的唯一信息**。

### 官方列出的后续改进方向（10 条，节选）

- **在花钱回答候选前先用 Noul 元问题筛选**：能否从源文本回答、评判标准下是否含义单一、
  是否适用大多数行、是否随行变化——四项都够置信才发送
- 加简单基线（TF-IDF、字符数等）
- **混用不同家族的提案者**（Anthropic / OpenAI / Google Gemini / 开源模型）合并去重
- 让验证与部署方式匹配（时间序划分、分组划分、
  **保留不被特征发现和模型选择触碰的最终测试集**）
- **平台期停止**（CV RMSE 连续固定轮不改善，或达到问题数/请求数预算）

| **模型只做"在给定候选里挑"，绝不做生成或计算** | 6.0 |
