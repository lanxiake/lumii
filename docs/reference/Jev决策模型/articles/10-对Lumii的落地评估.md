# 10 · 对 Lumii 的落地评估

> ⚠️ **本篇的全部 Jev 数字都来自英文语料的官方课程**，
> 而 Lumii 的输入以中文为主，官方明说中日韩「**可以处理但效果不一**」。
> **任何性能结论都不能外推**——下面每条都标了"已测 / 未测"。

---

## 10.1 前置问题：数据合规

**在讨论任何技术方案之前，这条必须先定。**

Jev 默认是**云 API**：`state`（也就是你的证据材料）会发到 `api.typesafe.ai`。

对 Lumii 来说这意味着：

| 候选场景 | 要发出去的东西 |
| --- | --- |
| 微信代聊护栏 | **用户的微信聊天记录** |
| 记忆检索重排 | **私人记忆条目内容** |
| 消息意图路由 | **用户的对话内容** |
| 工具名册筛选 | **只有工具名与描述**（最轻） |

> 官方声明**不在客户请求/响应上训练**，企业可谈 **ZDR（零数据留存）**——
> 但这是**法务问题，不是技术问题**，且「声明不训练」与「数据不出本机」是两回事。

**三条路**：

| 路线 | 适用 |
| --- | --- |
| **A. 只发不含用户数据的内容**（工具名册、模式分类） | 最低摩擦，可立即评估 |
| **B. 谈 ZDR / 企业版** | 需采购流程 |
| **C. 走本地模型** | 素材里有现成路线：`27 Build your own Jev (100% local)`、`34 Unsloth 训练决策模型`、`laya-model`（Apache-2.0 开源权重） |

> **本项目的默认姿态是本地优先**，所以下面所有方案都按
> **"先做 A、C 才是长期解"** 的前提评估。

---

## 10.2 回到最初的问题：MCP 工具的渐进式加载

### 先纠正一个我原来的错误假设

我最初估的是「Lumii 的 MCP 工具只有十来个」。**实测不是。**

从运行时库 `tool_usage_stats` 枚举（**累计值，可能含已停用的工具**）：

```
总计 155 个工具名  =  内置/本地 87  +  MCP 68
```

**MCP 按服务端**：

| 服务端 | 工具数 | |
| --- | --- | --- |
| **mcp-trends-hub** | **29** | ← 单个服务端就 29 个 |
| **wechat-local** | **15** | |
| filesystem | 6 | |
| 12306-mcp | 4 | |
| comfyui-remote | 3 | |
| basic-memory / bing-cn-mcp-server / bing-search | 2 each | |
| FlightPriceCompare / civil-code-mcp / excel-mcp / fetch / flight-price-compare | 1 each | |

**最近会话的 `inputTokens` ≈ 81,000**（日志实测，总 prompt，非工具部分单独）。

### 这个规模意味着什么

**`mcp-trends-hub` 的 29 个工具几乎全是同构的**：

```
get-36kr-trending / get-toutiao-trending / get-weibo-trending / get-zhihu-trending /
get-bbc-news / get-bilibili-rank / get-douban-rank / get-douyin-trending /
get-gcores-new / get-ifanr-news / get-infoq-news / get-juejin-article-rank /
get-netease-news-trending / get-nytimes-news / get-smzdm-rank / get-sspai-rank /
get-tencent-news-trending / get-thepaper-trending / get-theverge-news /
get-weread-rank / get-9to5mac-news / ...
```

**这正好命中官方描述的那个失败场景**：

> 在这个宽度下，「**编辑** .pptx 文件的技能」读起来和「**撰写**它们的技能」**几乎一模一样**。
> 你要求一份路演 PPT，代理可能加载错误的那个。
> **而在根本没有技能适用的一轮里，它也可能照样加载一个，因为一列名字会诱使人去猜。**

**用户说"看看今天有什么热点"时，模型面对的是 22 个近乎同义的选项**——
这正是"一列名字诱使人去猜"。

> 附带发现：清单里同时存在 `get-36kr-trending` 与 `get_36kr_trending`
> （连字符 / 下划线两套命名），说明命名规范变过而旧名仍在统计里。

### 但**不能**直接照搬官方方案——一个关键差异

官方那套之所以有效，**很大一部分来自 Hermes 把描述截断到 60 字符**：

> Hermes 默认把它截到 60 个字符。例如在这个宽度下，
> 「编辑 .pptx 文件的技能」读起来和「撰写它们的技能」几乎一模一样。

**Lumii 的 MCP 工具带的是完整 JSON Schema + description，不是一行截断描述。**
所以官方 16.8% → 7.3% 那个增益，**不能期望在 Lumii 上复现**。

### 那还剩什么值得做

**核心可迁移的不是"两阶段"，是这三条**：

| # | 可迁移的设计 | 为什么 |
| --- | --- | --- |
| 1 | **注入"一行建议"而不是删工具** | 名册不变 ⇒ **前缀缓存不失效**；agent 保留完整索引与自己的判断 |
| 2 | **建议措辞显式允许被忽略** | 「语气再强硬也会在错误建议上赢得顺从，而**错误建议比没有建议更糟**」 |
| 3 | **无建议时也要发一句** | 「什么都不发的话，名册自身『宁可加载』的指令就无人制衡」 |

**但第 2、3 条有个前提 Lumii 目前不满足**：
Hermes 的名册提示词里写着"你 **MUST** 加载技能……**宁可多加载**"——
所以它需要一行反向的制衡。
**Lumii 的工具提示词没有这种强制性措辞**，这两条的价值要重新评估。

### ✅ 第一步（不是写代码，是测量）

**在决定做不做之前，先量三个数：**

| # | 测什么 | 怎么测 |
| --- | --- | --- |
| 1 | **工具 schema 占 prompt 多少 token** | 当前日志只有总量（~81k），**没有分段计数**——需要先加一个探针，在构建 `tools` 数组后打印其序列化长度 |
| 2 | **`mcp-trends-hub` 是否真被启用** | `tool_usage_stats` 是累计值；**当前启用集**要读会话配置 |
| 3 | **模型选错工具的实际频率** | 走日志的 `tool:end` 事件配对（⚠️ 别用 `tool_usage_stats`，那是累计值会骗人） |

> **如果第 1 项测出来只占几个百分点，这件事就不值得做。**
> 按官方那篇的规模推测：68 个 MCP 工具 + 87 个内置，
> 若 schema 平均 200–400 token，量级在 **2万–4万 token**——
> **但这是推测，必须实测。**
>
> （作为对照：Hermes 182 个技能**只放一行截断描述**，索引总共 **16,089 字符**。）

## 10.3 逐项评估

> 图例：**已测** = Lumii 侧有实测数据；**未测** = 只有官方英文语料数据。

### 值得做的（低风险、可立即评估）

#### ① 工具选择的"一行建议"（对应 `08 技能推荐`）

| 项 | 状态 |
| --- | --- |
| 前提 | **只需发工具名 + 描述**，不含用户数据 ✅ 符合合规格 |
| 收益 | **未测**。官方在 182 技能上 16.8%→7.3%，**Lumii 规模更小、描述不截断，增益应显著小于此** |
| 成本 | 每轮 **+1 次 API 调用** |
| 关键约束 | **名册文本每轮必须逐字一致**，否则前缀缓存失效 |
| 建议 | **先做 10.2 的三项测量**。收益不明就不做 |

#### ② 工具调用轨迹校验（对应 `02 构建` 的九问分解）

官方在 `how-to-build-with-system-one` 里给的分解很对口：

```
geocode_tool_is_relevant / geocode_location_matches / geocode_arguments_match_schema
geocode_result_matches_call / weather_tool_is_relevant / weather_arguments_match_schema
weather_uses_geocoded_coordinates / weather_date_matches / weather_unit_matches
```

**这正好是"工具调用没发出 / 发错了"这类问题的结构化判据**——
把「这次工具调用对吗」拆成九个可验证的窄问题，
比事后从日志里配对 `tool:start` ↔ `ToolRunner` 要**前置**得多。

| 项 | 状态 |
| --- | --- |
| 收益 | **未测** |
| 成本 | 每轮 +1 次调用（九问同一次请求） |
| 数据 | **要发工具参数与结果摘要**，可能含用户数据 ⚠️ |

#### ③ 段记忆 / 消息分类的"置信度回退"（对应 `18 基于置信度的分类`）

官方那篇的做法**极简且效果明确**：

```python
sure = answer["confidence"] >= CONFIDENT
label = answer["group"] if sure else division(answer["group"])   # 回退到宽标签
```

实测：被迫报细粒度 **39/60** → 允许答粗 **48/60 有用答案**
（没把握的那一半从 40% 提到 70%）。

| 项 | 为什么适合 Lumii |
| --- | --- |
| 收益 | **不是提高准确率，是"低置信时给一个更宽但可用的答案"**——比硬答或丢弃都好 |
| 成本 | **一次调用，零额外调用**（宽标签由窄标签直接推导） |
| 适用 | `SegmentMemoryService` 的段分类、渠道消息分类 |
| 注意 | **中日韩准确率不明** ⚠️ |

### 可以试但要先量

#### ④ 记忆检索的重排层（对应 `04 重排序`）

| 官方数据 | Lumii 已有数据 |
| --- | --- |
| CLERC 40 查询，BM25 top-1 **5% → 18%**、top-10 **38% → 62%** | 凸组合 α=0.6 → **0.906**；纯 FTS 0.844；RRF 0.794；**本地 reranker 5.8s/查询** |
| 1,200 次调用花 **$0.0645** | — |
| ⚠️ **未做显著性检验** | — |

**为什么不建议直接换**：

1. Lumii **已经有一套测过的方案**（0.906），公开的 80 样本 SciFact 数字换不掉它
2. **reranker 修不了召回层的问题**——官方自己强调的那条对 Lumii 同样成立
3. 数据要出本机 ⚠️
4. 中文场景准确率未测 ⚠️

**如果要试，正确做法**：拿 Lumii 自己的评测集，**分开报 `Recall@K` / `MRR` / `nDCG@K`**，
而不是只看一个综合分（参考 [04 章](04-配方-检索与证据.md) 4.0）。

#### ⑤ 微信代聊的出站护栏（对应 `12 LLM 防护栏`）

**这一条要打折看，理由在官方自己的文档里**：

> **State 是数据，jev-1.13 默认不会把它当作有敌意的内容对待。**
> ……**都可能改变答案。**

以及第 9 章：

> **提示注入检测不是安全边界**，真实保护来自**权限隔离、受限工具、确定性验证和可审计执行**。

**微信消息正是对抗性输入源**。所以：

| 项 | 判断 |
| --- | --- |
| 作为**辅助信号**（低置信/命中 → 转人工确认） | ✅ 可以做，且与 Lumii 已有的"通知→granted 只隔 3ms"教训同构 |
| 作为**安全边界** | ❌ **官方明确否定** |
| 数据合规 | 要有聊天内容出去 ⚠️⚠️ |

### 明确不该做的

| ❌ 别做 | 官方依据 |
| --- | --- |
| **用 Jev 做计数**（工具调用次数、token 数、消息条数） | 「**无法可靠地计数**……误差会随着被计数对象的规模增大而增大」 |
| **用 Jev 做日期比较**（消息排序、时间窗口判定） | 「**把日期当作文本读取，而不是有先后顺序的量**」 |
| **用 Jev 生成文本**（摘要、代聊内容） | 「**没有经过文本生成训练**……串联 Choice 强行让它生成，**效果不佳且非常慢**」 |
| **一个问题里塞多个判断** | 官方禁令 |
| **把整个上下文丢进 `state`** | context rot，官方禁令 |
| **把 Noul 的阈值搬到 Choice 上** | 官方实测 `P(退款)=0.72` + `P(非退款)=0.47` = **1.19** |

> ⚠️ **日期比较那条对 Lumii 尤其危险**——
> 本项目已经踩过**消息排序与时间戳的两个口径**的坑
> （ChatContainer 按 `timestamp` 排序，而 assistant 在渲染层是"回合开始"、落库是"完成时刻"）。
> **再引入一个"把日期当文本读"的判断层，只会把这个问题复杂化。**

## 10.4 如果要试，最小第一步

**不要先写集成。先写一个离线探针。**

```
1. 从 ~/.lumii/logs/app/mtbot-*.log 里捞 N 条真实的中文回合
2. 手工构造 3–5 个窄问题（例如「这条用户消息是否在要求发送微信消息？」）
3. 用 @typesafe-ai/sdk 跑一次，只看两件事：
     a. 中文场景下 confidence 的分布是否合理（还是普遍偏低？）
     b. 与你自己的判断比，错了哪些
4. 结论：如果中文 confidence 普遍糊成一团，整条路线到此为止
```

**理由**：官方那句「**其他语言（包括中日韩文字）可以处理但效果不一**」
是全部材料里**唯一直接适用于 Lumii 的风险**，
而它**只有实测才能回答**。

> 相关：官方还建议**从保守的阈值开始，用你自己的数据测试，并根据观察到的结果调整**。

## 10.5 一句话总结

| 问题 | 答案 |
| --- | --- |
| 该不该用 Jev？ | **先测中文置信度**。这是唯一的 go/no-go |
| 最初的 MCP 渐进式加载问题呢？ | 规模倒是够（68 个 MCP 工具、单服务端 29 个），但**先量 schema 占多少 token**——官方那套的增益大半来自"描述被截断到 60 字符"，Lumii 没这个问题 |
| 最值得抄的是什么？ | **不是某个 API**，是三条工程习惯：<br>**① 能确定性算的放代码**<br>**② 阈值集中在单处、且用自己数据定**<br>**③ 把"不确定"当一等公民而不是异常** |
| 最大的不适用风险 | **中文准确率未测** + **数据默认出本机**（本地路线在 `27 / 34 / laya-model`） |
