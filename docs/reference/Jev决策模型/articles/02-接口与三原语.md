## 2.1 端点与请求骨架

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <TYPESAFE_API_KEY>
Content-Type: application/json
```

请求体顶层三个字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `state` | `string \| object \| array` | **必填**。要评估的内容 |
| `model` | `string` | **必填**。用 `"jev-latest"` |
| `questions` | `map<string, Question>` | 问题的**键由你自选** |

一个容易被忽略但很重要的性质：

> `questions` 的键**不发给底层模型、不参与推理**——它只是响应里回传的标识符。

响应体：

| 字段 | 说明 |
| --- | --- |
| `model` | 实际作答的带版本 ID（如 `jev-1.13.0`）——**别名漂移时靠它记录** |
| `answers` | `map<string, Answer>`，键与请求一致 |
| `usage` | `{ input_tokens, output_tokens }` |

## 2.2 `state`：把你的证据整理好

`state` 是**你要求 System One 模型评估的内容**。三种形态：

| 格式 | 适用情形 | 示例 |
| --- | --- | --- |
| **字符串** | 一条消息、一篇文章或一个段落 | `"My card was charged twice."` |
| **对象** | 具名字段、相关记录或应用状态 | `{"message": "...", "order_id": "A-104"}` |
| **数组** | 一系列消息或记录 | `["Hi", "My customer number is TS1337.", "My card was charged twice."]` |

> **官方建议：大多数请求应使用对象**——这样状态的每个部分都有一个描述性名称，
> 各部分之间的关系也保持清晰。只有当用例简单、只需要一段文字时才用字符串。

官方给的心智模型：

> **把状态想象成你在请专家小组做判断之前呈给他们的材料。**

一个完整示例（包含对话、订单和政策三块，因为它们需要**互相比较**）：

```json
{
  "ticket": {
    "subject": "Duplicate charge",
    "messages": [
      {"from": "customer", "text": "I was charged twice for order A-104. Please refund the duplicate."},
      {"from": "support",  "text": "We are checking the charges."}
    ]
  },
  "order": {
    "id": "A-104",
    "charges": [
      {"amount_usd": 49, "status": "captured"},
      {"amount_usd": 49, "status": "captured"}
    ]
  },
  "refund_policy": "Duplicate charges are eligible for a refund."
}
```

### 内容与问题必须分开

> **状态包含内容和支撑性事实。问题定义模型应当就这些材料做出哪些判断。**

把退款请求和政策放进 state，然后**问**"客户是否请求了退款"、"政策是否支持退款"。
不要把判断写进 state。

### 三个设计维度（`concepts/how-to-build-with-system-one`）

设计 state 时要同时考虑：

1. **信息充分性**——够不够做这个决定
2. **无关信息干扰**——**state 越脏准确率越低**（context rot，见 [08](08-短板与评测校准.md)）
3. **信息边界**——只提供**合法且必要**的字段

**不要包含**：未来结果、标签、答案本身、权限不允许读取的数据。

## 2.3 三个原语

每个问题的结构：`id`（自选键）+ `type` + `instructions` + `criteria`。

官方对"一个问题"的定义很实用：

> 每个问题只要求**一个快速判断**——
> **懂行的人拿到正确上下文后一秒内能做的判断。**

### 2.3.1 `Noul`（是/否）

返回**「是」的概率**（0 = 否，1 = 是）。

```json
{
  "type": "noul",
  "instructions": "这条消息是否要求退款？",
  "criteria": {
    "true":  "客户明确要求退款或返还",
    "false": "客户没有提出退款要求"
  }
}
```

响应：

```json
{ "type": "noul", "noul": 0.95 }
```

**没有独立的 `confidence` 字段**——官方解释：分布只有是/否两个结果，**单个 `noul` 值已完整描述**。

官方记录的示例值（`jev-1.13.0`）：

| 场景 | noul |
| --- | --- |
| 谢谢，问题解决了 | 0.02 |
| 怎么重置密码 | 0.07 |
| 今天就要解决 | 0.26 |
| 你是机器人吗 | 0.40 |
| 找人谈发票 | 0.84 |
| 已问三次，要真人 | 0.99 |

#### ⚠️ Noul 不是程度量表

> `noul = 0.5` 表示模型给「是」「否」**相等概率**，
> **不代表中等技能水平**。

官方的对照实测（同一批候选人对"Python 是否很强"）：

| 候选人 | Noul | Score（0–3 量规） |
| --- | --- | --- |
| A | 0.03 | 0.0 |
| B | 0.14 | 1.0 |
| C | 0.81 | 2.05 |
| D | 0.92 | 2.89 |

中间的 noul 值**既可能是"中等经验"，也可能是"情况不明"**——两者不可区分。
要表达程度请用 `Score`。

**阈值转换**：`noul > 0.9` → 布尔。
阈值取决于出错代价（官方建议）：

| 情形 | 阈值取向 |
| --- | --- |
| 两种错误都好处理 | 用 0.5 |
| **错误行动**的代价高 | **调高** |
| **漏掉真正「是」**的代价高 | **调低** |
| — | 中间值交人工 |

### 2.3.2 `Choice`（从选项中选一个）

```json
{
  "type": "choice",
  "instructions": "这属于哪一类？",
  "criteria": {
    "safety":  "涉及安全、人身或财产风险",
    "refund":  "退款/退货诉求",
    "general": "普通咨询"
  }
}
```

响应：

```json
{
  "type": "choice",
  "choice": "safety",
  "probabilities": { "safety": 0.85, "refund": 0.10, "general": 0.05 },
  "confidence": 0.85
}
```

三个字段的含义：

- `choice` — 概率最高的选项
- `probabilities` — **完整的概率分布**，和为 1
- `confidence` — **分布形态压缩成的一个 0–1 数**（平坦 = 低，尖峰 = 高）

**选项名和描述都会发给模型**，所以描述要能区分选项。
criteria 的值可以是 `string | object | array | null`——**传 `null` 就是没有描述**。

#### ⚠️ 硬限制：Choice 最多 255 个选项

这个数字在多篇 cookbook 里直接成为设计约束：

- **逐行语义搜索**：一个 Choice 最多搜索 255 行文档；超了要分两遍（先选行窗口，再在窗口内排序）
- **预解析值提取**：候选超过 255 时分两步缩小范围

**每增一个选项只消耗少量 token**，所以别为了省 token 砍选项——该加 `other` / `none of the above` 就加。

官方给的实测响应样本（`jev-1.13.0`）：

```json
// 简单示例
{ "choice": "returns", "confidence": 1.0,
  "probabilities": { "shipping": 0.0, "returns": 1.0, "billing": 0.0 } }
// usage: input_tokens 328 / output_tokens 34
```

### 2.3.3 `Score`（有序等级）

```json
{
  "type": "score",
  "instructions": "这个 bug 有多严重？",
  "criteria": [
    "纯外观问题；不影响功能",
    "功能受损或有降级；有绕过办法",
    "阻塞性问题；没有绕过办法"
  ]
}
```

响应：

```json
{
  "type": "score",
  "score": 1.43,
  "legend": { "0": "纯外观问题…", "1": "功能受损…", "2": "阻塞性问题…" },
  "probabilities": { "0": 0.0, "1": 0.57, "2": 0.43 },
  "confidence": 0.35
}
```

关键性质：

- **级别编号 = criteria 数组下标，从 0 开始**
- **模型只看描述，看不到编号，也看不到相邻级别**——所以「比上一级更严重」这种写法无用
- `score` 是**级别编号的概率加权和**，**可以落在两级之间**（如 1.43）

解读表（三级 bug 严重程度）：

| 场景 | score | confidence |
| --- | --- | --- |
| 像素错位 | 0.0 | 1.0 |
| PDF 导出无反应 | 1.0 | 1.0 |
| 一直转圈 | 1.11 | 0.84 |
| Safari 崩溃 | 1.43 | 0.35 |
| 全员无法登录（500） | 2.0 | 1.0 |

#### ⚠️ 同一个 score 可以来自不同分布

`1.0` 可能是「全部概率在级别 1」，也可能是「一半在 0、一半在 2」。
所以**必须结合 `probabilities` 和 `confidence` 一起看**。

#### 低置信度的三个原因

1. 级别之间语义重叠
2. 一个问题同时在衡量多件事
3. state 里信息不足

#### 怎么写出好的级别

| 建议 | 说明 |
| --- | --- |
| **描述情境，而不是程度** | 见下方实测对比 |
| **别只用数字** | 数字-only criteria 效果很差 |
| 级别数按"能清晰区分"定 | 至少 2 级、**最多 10 级**；**三个就很好** |
| 每个 Score 只留**一个维度** | — |
| 罕见极端情况**单设一级** | 如情感量表加「辱骂或威胁」 |
| 无中间地带就改用 `Choice` 或拆成多个 `Noul` | — |

**数字 vs 描述的实测对比**（同一份报告）：

| criteria 写法 | score | confidence | probabilities |
| --- | --- | --- | --- |
| 只用数字 | 0.55 | 0.33 | `{0: 0.45, 1: 0.55, 2: 0.0}` |
| 描述 + **切题的** examples | 1.03 | **0.96** | — |
| 描述 + **无关的** examples | 1.43 | 0.35 | — |

（注意：并非"分数越高越准"——重点是**切题的 examples 把 confidence 从 0.35 拉到 0.96**。）

#### ⚠️ 别用 score 做数学

官方在 `model-jaggedness/jev-1.13` 明确警告：

> 请不要使用 score 输出（例如期望值和概率）来计算某个数值在**标准两个级别之间的精确大小**。
> 你可以用期望值判断是否**通过某个特定阈值**，但 jev-1.13 的 score 级别
> **在数值校准方面较弱**，无法通过插值还原精确数值。

## 2.4 结构化 `instructions` / `criteria`

这是全套能力里最容易被低估的一块。

**允许结构的位置（统称 `EntryType`）**：

| 位置 | 允许 | 结构 |
| --- | --- | --- |
| `instructions`（三种问题通用） | ✅ | `string \| object \| array` |
| Choice 的选项描述（criteria 的**值**） | ✅ | `string \| object \| array \| null` |
| Score 的级别描述（criteria 的**项**） | ✅ | `string \| object \| array` |
| Noul 的 `criteria.true` / `.false` | ✅ | `string \| object \| array` |

**什么时候用结构**（官方两条）：

1. **结构有助于清晰**——键自带标签
2. **问题需要支撑数据**——schema / 分类体系 / 数据库行**直接放 JSON**，
   不要序列化成字符串模板

**字段名不是 API 保留字**，可以自选；**模型连字段名带值一起看到**。
官方示例里出现的约定字段名：

| 用途 | 字段名 |
| --- | --- |
| 问题主体 | `question` |
| 关注点 | `focus` |
| 选项是什么 | `what` |
| **明确不是什么** | `not_for` |
| 例子 | `examples` |
| 要检视的东西 | `inspect` |
| 要对比的东西 | `compare` |
| 级别摘要 / 信号 | `summary` / `signals` |

一个完整的结构化示例（发票字段验证，同一个结构驱动四种问题）：

```json
{
  "field": { "name": "total", "type": "money", "description": "发票总额", "unit": "USD" },
  "extracted_value": "$1,315.50",
  "question": "这个取值是否是 `field` 所描述的字段的正确取值？"
}
```

### 引用 state 里的具体字段：反引号路径

在 `instructions` 里用**反引号 + 点号/下标路径**指向 state 的具体部分：

```
`ticket.message`
`ticket.messages[0].text`
`policy.sensitive_credentials`
`customer.open_orders`
```

顺带一提，`primitives` 页给了一个判断 `Noul` 值含义的辅助思路：
用反引号路径可以让问题"按名字指明 state 中的相关部分"，
这正好是 [08 章](08-短板与评测校准.md)里"减少间接引用"那条短板的替代做法。

## 2.5 组合特性：两条官方承诺

### ① 答案被约束在提供的选项内

> **绝不超出。**

这条是类型化接口相对"让 LLM 返 JSON"的核心优势——不再需要解析和兜底。

### ② 答案相互独立

> **一个答案不成另一个问题的隐藏上下文。**

所以可以放心地**一次提出多个问题**：

- 并行评估
- **增加问题几乎不改变响应时间**，只消耗额外的问题 token（**非常便宜**）
- **问可能不需要的问题几乎无成本** → 这就是 [推测式扇出](03-架构模式.md)

### 依赖问题怎么办

同一请求内的问题彼此独立；**真正有依赖关系时才发第二个请求**——
因为代码在拿到第一个答案前无法构建第二个请求。

官方点名的三个**值得付第二次往返**的例子：

| 配方 | 为什么值得 |
| --- | --- |
| 技能推荐 | 先对 182 个技能排序，再取前**三**的全文基于更好证据判断 |
| 结构恢复 | 先问每处换行是否拆句子，合并块**之后**再分类 |
| 层级分类 | 每个 Choice 答案决定**下一次请求**的选项 |

## 2.6 `confidence`：置信度

- `Choice` 和 `Score` 的答案**都带** `probabilities`（完整分布）和 `confidence`（0–1 的摘要）
- `Noul` **不带** `confidence`

官方对 `confidence` 的定位很克制：

> 一个可靠的默认值：我们提供 confidence 作为**适用于大多数用例的便捷度量**，
> 但你**绝不会被困在我们的定义里**。取决于你在评估什么，另一种度量可能更适合你——
> **这正是我们在响应中给出完整 `probabilities` 的原因。**

### 三路分流

官方推荐入门模式——把置信度划三个区间：

| 区间 | 行为 |
| --- | --- |
| **高置信度** | **自动执行**。判断清晰明确，无需人工参与 |
| **中等置信度** | **谨慎推进**。请用户确认、标记审核、或在行动前收集更多信息 |
| **低置信度** | **不要行动**。转人工、请求澄清、或回退到另一个系统 |

> 这些边界画在哪里**取决于风险高低**。

### 阈值随风险调整

```python
action = response.answers["action"]
confidence = action.confidence

if confidence < 0.5:
    # Model is genuinely unsure. Don't guess.
    route_to_human(user_message)

elif action.choice == "check_balance":
    # Low stakes. Showing the wrong screen is recoverable.
    show_balance(account_id)

elif action.choice == "approve_transfer":
    if confidence > 0.9:
        # High stakes, high confidence. Proceed with confirmation.
        confirm_then_execute(account_id)
    else:
        # High stakes, moderate confidence. Verify first.
        ask_user_to_confirm(account_id)
```

> **0.5 的置信度下限会拦下所有模型报告为真正不确定的情况。**
> 在此基础上，**未经确认就执行操作的阈值，对破坏性操作要高于只读操作。**
> **你的代码负责编码风险容忍度。**

> ⚠️ 正确的阈值取决于**你的领域**以及**模型在你的用例上的表现**。
> 从保守的阈值开始，**用你自己的数据测试**，并根据观察到的结果调整。

**`confidence` 的读法要小心**（来自"基于置信度的分类"一篇）：

> 读的是 **`confidence` 而不是获胜者自身的概率**：
> 获胜者 0.45 而第二名 0.44（分散）与获胜者 0.45 而其余稀薄散开，
> 是**两种情形**，`confidence` 把它们区分开。

## 2.7 `instructions` / `criteria` 的实战写法

官方在 `how-to-build-with-system-one` 里给了完整示范，含一个"垃圾检测"的**分解对比**：

| 写法 | 内容 |
| --- | --- |
| ❌ 一个宽问题 | `is_spam` |
| ✅ 六个窄问题 | `requests_credentials` / `offers_unexpected_reward` / `creates_time_pressure` / `sender_identity_mismatch` / `link_domain_mismatch` / `disguises_link_destination` |

**工具调用轨迹校验**同理，从 1 个宽问题拆成 9 个窄问题：

```
geocode_tool_is_relevant / geocode_location_matches / geocode_arguments_match_schema
geocode_result_matches_call / weather_tool_is_relevant / weather_arguments_match_schema
weather_uses_geocoded_coordinates / weather_date_matches / weather_unit_matches
```

> 这类"轨迹校验"的分解正对应本项目在排查工具调用问题时的需求。

**五条设计原则**（原文）：

1. **控制流、确定性规则、副作用留在代码里**
2. **宽泛判断拆为狭窄类型化问题**（明确 instructions 和 criteria）
3. **只给每个问题所需上下文**
4. **用概率与置信度决定行动 / 审核 / 升级**
5. **独立问题一起提出，代码组合答案**

核心代码形态：

```python
# 确定性短路——能用普通代码表达的，不要问模型
if ticket["status"] == "closed":
    return no_action(ticket)

# 组合独立信号，权重由代码掌控
spam_risk = (
      0.45 * answers["requests_credentials"].noul
    + 0.30 * answers["sender_identity_mismatch"].noul
    + 0.25 * answers["unexpected_reward"].noul
)

spam_is_uncertain = 0.4 < spam_risk < 0.6
if spam_is_uncertain or answers["topic"].confidence < 0.75:
    return route_to_human_review(ticket)
if spam_risk >= 0.6:
    return quarantine_as_spam(ticket)

if answers["topic"].choice == "billing":
    return route_to_billing(ticket, refund_requested=answers["refund_requested"].noul >= 0.7)
if answers["topic"].choice == "orders":
    return route_to_orders(ticket, mentions_open_order=answers["mentions_open_order"].noul >= 0.7)
```

注意这段里的三个模式：**确定性短路 → 归一化加权 → 阈值 + 不确定区间 → 按 choice 分流**。

官方对"质量分"的加权示范：

```python
quality = (  0.4 * answers["answers_request"].noul
           + 0.4 * answers["citations_are_supported"].noul
           + 0.2 * (1 - answers["contradicts_context"].noul) )
```

**注意 `1 - noul` 的用法**——把"反向指标"翻成正向，这是 `Noul` 在加权组合里的常见形态。

### Python

```bash
uv add typesafe-sdk    # 或 pip install typesafe-sdk
export TYPESAFE_API_KEY=...
```

要求 **Python ≥ 3.10**。

```python
from typesafe_sdk import AsyncTypeSafeClient, Choice, Noul, Score, TypeSafeClient

# 同步
with TypeSafeClient() as client:
    response = client.system_one(state=..., questions={...})

# 异步
async with AsyncTypeSafeClient() as client:
    response = await client.system_one(state=..., questions={...})
```

问题对象：

```python
Noul(instructions=...)                                   # criteria 可选
Choice(instructions=..., criteria={"calm": None, "frustrated": None, "angry": None})
Score(instructions=..., criteria=["can wait", "this week", "today"])
```

### ⚠️ 一个文档内的不一致（照实记录，不猜）

## 2.9 硬限制速查

集成前先过一遍这张表：

| 限制 | 值 | 出处 |
| --- | --- | --- |
| `Choice` 选项数 | **最多 255** | `api`、`primitives/choice`、多篇 cookbook |
| `Score` 级别数 | **最少 2、最多 10** | `api`、`primitives/score`、autoresearch |
| 上下文 | **64k token / 请求**（`state` + 所有问题之和） | `models` |
| | **32k token**（`state` + **单个最长的问题**） | `models` |
| 输入形态 | **仅文本**：字符串 / JSON 对象 / 文本数组 | `models` |
| 速率限制 | 250,000 token/秒；1,200 请求/分钟 | `models` |

> `Score` 的第 11 档会直接返回**服务器错误**——autoresearch 那篇的 `SCORE_LEVELS` 正好 10 档。

**错误码**（`api` 页）：

| 码 | 含义 | 处理 |
| --- | --- | --- |
| `401` | 缺 / 无效 key | — |
| `422` | 请求体校验失败（响应体详述出错字段） | — |
| `429` | 超速率限制 | 退避重试 |
| `529` | TypeSafe 过载 | 延迟重试 |

> 429 / 529 用**指数退避**；客户端 SDK 默认自动处理，并遵循 `retry-after` 头。
