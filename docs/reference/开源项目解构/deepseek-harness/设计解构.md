## 0. 一句话结论

DeepSeek Harness（下称 dsh）的插件化不是"提供一些扩展点"，而是**把整个产品拆成插件树**：

- 内核只有 **Context + Service + Effect + Event** 四件事；
- 所有注册都是**可逆副作用**，卸载即回滚；
- 所有依赖都是**声明式 coeffect**，提供者消失时消费者自动卸载、恢复时自动重载；
- 组合靠 **Profile → Bundle → Patch** 三层声明，不靠改代码；
- 前端同样是一棵插件树：**client module system + Slot 系统 + Conversation Node**，卡片/区块/整页都是 slot 贡献。

它值得学的不是某个 API，而是**四条不可妥协的契约**：注册可回滚、依赖可声明、扩展点分层、模型可见即落日志。

## 2. 插件内核：Cordis

Cordis 是 Koishi 作者 Shigma（Yifan Shi）做的 TypeScript 元框架，论文为 *A Programming Paradigm for Spatiotemporal Composability*（arXiv:2608.25512，Peking University / DeepSeek-AI）。dsh 把它 vendored 进 `vendor/`，并做了大量生命周期与 HMR 加固。

### 2.1 五个核心概念

来自 `docs/cordis-primer.md`：


| 概念               | 含义                                                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Plugin**       | 一个实现 Service 的对象；可以是带 `inject` / `apply(ctx)` 的函数，也可以是 `Service` 子类                                              |
| **Context**      | 服务的仓库；每个服务占据稳定的 `ctx.<key>`（如 `ctx.tools`、`ctx.llm`、`ctx.sessions`）                                              |
| **inject**       | 声明依赖的服务；依赖就绪前插件保持 PENDING，加载顺序由服务可用性决定，而不是手工 boot 顺序                                                             |
| **Typed Events** | 通过 TypeScript declaration merging 声明事件名；按语义选择五种分发模式                                                              |
| **Effect**       | 所有注册（prompt section、tool schema、adapter、provider、listener）都通过 `ctx.effect()` / `ctx.on()` 安装，返回 disposer，卸载时自动回滚 |




### 2.2 两种可组合性

论文把动态组合拆成两个正交维度：

- **时间可组合性（temporal）**：组件被移除时，它的副作用能**完整回滚**——即 revertible effects。
- **空间可组合性（spatial）**：组件能**声明并响应**组件间依赖——即 reactive coeffects。

Cordis 的实现要点（据论文与社区分析）：

- `effect()` 收集清理逆操作，卸载时按 **LIFO** 执行；
- `ctx.provide('db', impl)` 本身也是 effect；提供者卸载时服务消失，依赖它的消费者 epoch 变化，自动卸载；
- 提供者恢复/热替换时，只有**真正用到该服务的消费者**会被重新激活，其他插件的缓存与连接不受影响；
- `inject` 是持续跟踪的，不只是一次性启动检查。

这套机制的实践验证来自 Koishi 的 4000+ 社区插件；论文本身仍是 preprint，**没有性能基准与受控实验**，这是采用时必须知道的边界。

### 2.3 事件分发五模式

事件模式是**公开契约的一部分**，不是实现细节：


| 模式          | 是否 await | 顺序               | 返回值 | 典型用途           |
| ----------- | -------- | ---------------- | --- | -------------- |
| `emit`      | 否        | 注册顺序             | 无   | 通知、日志          |
| `waterfall` | 否        | 注册顺序，`next()` 环绕 | 有   | 权限闸门、请求改写、工具拦截 |
| `parallel`  | 是        | 并行               | 无   | 扇出副作用          |
| `serial`    | 是        | 注册顺序             | 有   | 有序决策、回合停止      |
| `bail`      | 否        | 注册顺序，首个 bail 停止  | 有   | 单值决策           |


`waterfall` **是 dsh 最重要的扩展形态**：监听器签名是 `(...args, next)`。调用 `next()` 表示委托，返回值会穿透；不调用 `next()` 直接返回表示**短路**。权限拒绝、消息改写、工具结果替换都靠它。

### 2.4 Fiber 生命周期与响应式依赖

一个插件实例对应一个 Fiber，状态机大致是：

```
PENDING → LOADING → ACTIVE → FAILED
                       ↓
                   UNLOADING → DISPOSED
```

- `fiber.dispose()` 会等待所有同步/异步 disposer 完成；
- 多个异步 disposer 可能并发执行；需要严格顺序时，应把相关清理放进**同一个** effect 里按顺序 await；
- `inject` 缺失时 Fiber 保持 PENDING，不会"半加载"；
- 服务替换会导致依赖者的 epoch 变化，触发**事务式**卸载/重载（HMR 会备份 ESM `loadCache` / CJS `require.cache`，失败则恢复，避免半重载状态）。

## 3. 组合层：Profile / Bundle / Patch

dsh 不在代码里写死"启动哪些插件"，而是用三层声明组合：

### 3.1 Profile

一个命名组合，存在 Harness home 里。它列出：

- 叠加的 bundles；
- 安装的 out-of-tree 插件；
- 用户自己的 `cordis.patch.yml`。

内置 profile 模板：`web`、`headless`、`sdk`、`sdk-minimal`、`acp`。

最小自定义 profile：

```json
{
  "name": "my-profile",
  "private": true,
  "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base"] } }
}
```



### 3.2 Bundle

Bundle 是"一组 Cordis 配置行 + 挂载这些行的代码"的分发格式。包在 `package.json` 里声明：

```json
{
  "name": "@fixture/bundle",
  "version": "0.0.1",
  "type": "module",
  "exports": { ".": "./index.js" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

`dsh-base` 是所有主要 profile 的第一层：模型适配、工具、持久化、沙箱与审批策略、设置、凭据、遥测。

### 3.3 Patch

Patch 是 YAML 覆盖层，按顺序应用：

```
profile 的 ordered bundles
  → profile 的 cordis.patch.yml
  → home patch
  → --patch 覆盖层
```

Patch 按 **entry id** 定位，可以**整体替换某行的 config**，也可以插入新行。平台差异用表达式：

```yaml
disabled: !!js process.platform === 'win32'
```

**可借鉴的治理点**：插件管理器的 enable/disable 不直接改运行中对象，而是把 `disabled` 写回 profile patch；写入时只记录"与 bundle 默认状态不同的偏离"，避免配置文件被写成全量快照。

## 4. 能力接缝：Definition / Provider / Consumer

dsh 反复强调：**一个接缝（seam）必须同时具备三个角色**：


| 角色                     | 职责                            |
| ---------------------- | ----------------------------- |
| **Service Definition** | 声明接口，不含实现                     |
| **Service Provider**   | 实现接口，注册到 `ctx.<key>`          |
| **Consumer**           | 通过 `ctx.<key>` 使用能力，通常是模型可见工具 |


只有一个角色不构成接缝。例如：

- `ctx.fs`：本地 FS provider / 远程沙箱 provider 可互换，Bash、PTY、LSP 都跟着走；
- `ctx.shell`：本地 shell 后端通过 `ctx.subprocess` 启动；
- `ctx.sandbox`：消费者在 spawn 前包装 argv；
- `ctx.llm`：模型适配器可替换；
- `ctx.subagent`：子 Agent provider 可以从"新开子 Agent"换成"委托给另一个产品"。

这条约束对 Lumii 很关键：**不要为了插件化而造一个只有实现、没有抽象接口的"管理器"**。每个要开放的能力，都先写清楚 Definition / Provider / Consumer 三方。

## 5. Agent 循环本身也是插件

dsh 没有"特权内核"：

- `core/agent` 提供 `ctx.agents`；
- `core/agent-loop` 是默认驱动，实现 `Agent` 接口，注册为 `ctx.agentLoop`；
- 想换循环，就挂另一个实现，而不是改核心代码。

一次 turn 的扩展点（`docs/architecture.md`）：

```text
turn/start
  claim input
  assemble prompt sections + tool schemas
  -> agent/pre-step              （waterfall：接受/改写/拒绝输入）
  -> agent/request               （waterfall：路由与请求准备）
  -> llm/stream                  （waterfall：模型流）
  -> agent/assistant-stream      （live：start / chunk* / end）
  -> tool/call*
     -> tools/pre-execute        （waterfall：权限、参数改写、短路）
     -> tools/execute            （waterfall：真正执行）
     -> tools/post-execute       （waterfall：结果改写）
     -> tool/result*             （durable session event）
  -> agent/turn-stopping        （serial：终止回合）
turn/end
```

**"Where new behavior goes" 表**（同文档）值得直接背下来：


| 想做的事          | 机制                                            |
| ------------- | --------------------------------------------- |
| 加模型 provider  | 在 `ctx.llm` 注册 adapter                        |
| 加模型可见能力       | 在 `ctx.tools` 注册工具，schema 自动进 prompt 装配       |
| 给某个会话不同能力集    | 组合 agent preset（服务行需要 `isolate` realm）        |
| 加 shell / 终端  | 注册 `ctx.shell` / `ctx.terminals` 后端           |
| 加人类命令         | 注册 `ctx.commands`，不经过模型回合                     |
| 管理后台任务        | 注册 `ctx.jobs`                                 |
| 拦截请求/工具/回合    | 用对应 `agent/*`、`tools/*` 事件                    |
| 注入模型上下文       | `agent.inject()`，落到下一次被接纳的请求                  |
| 加 UI          | 驱动 `ctx.agents`，从 `session/event` 渲染          |
| 加 Web Chat 节点 | `ConversationNodeDefinition` + keyed renderer |
| 加持久会话状态       | 扩展 `SessionEventMap`，从日志渲染与回放                 |


另外两条硬规则：

- **Model-visible means logged**：任何模型可见的新输入，必须能从会话日志重建；
- **Plugins, not loop changes**：优先挂扩展点；改循环本身必须更新架构映射表。

## 6. 前端插件化

dsh 的前端不是"一个大 React 应用 + 几个动态组件"，而是**浏览器端的插件树**。三层机制：

### 6.1 Client Module System：插件代码怎么到达浏览器

包在 `package.json` 声明客户端半边：

```json
{
  "dsh": {
    "client": {
      "platform": "web",
      "entry": "./client",
      "external": ["some-shared-module"]
    }
  }
}
```

宿主侧：

- 扫描已启用的 Loader entries，组合出 boot graph；
- 把 graph 注入 `window.__DSH_BOOT__`（字符串里的 `<` 会被转义，防止插件内容逃逸出 `<script>`）；
- 通过 `/plugins` 路由提供 bundle；
- 用 `mtimeMs` / `ctimeMs` / size 生成 revision，组合 URL `/plugins/??...&rev=...`；
- 通过 SSE 推送 graph 变化，页面据此 live enable/disable。

浏览器侧是 **lazy-CJS**：

- 执行插件 bundle 只注册一个 factory，模块体副作用（包括 CSS 注入）都在 factory 闭包内；
- 首次 `require` / 物化时才执行；
- `factory(require)` 递归物化依赖，结果 memoized 在 `loadCache`；
- 同步 require 成环会抛错（CJS 无法交付半成品 exports）；
- 共享模块走冻结的 platform seed 表，非基线依赖必须在 `dsh.client.external` 精确声明。

**为什么值得学**：它把"插件代码加载"抽象成一个统一的 module system，而不是每个插件一种加载方式。代价是模块图是扁平的、revision 基于文件元数据而非内容哈希，且 release 变更检测依赖 graph stream。

### 6.2 Slot 系统：UI 扩展点

`packages/client/ui-slots/README.md` 定义了四种 slot：


| 类型       | 语义                         |
| -------- | -------------------------- |
| `single` | 一个占用者                      |
| `list`   | 有序条目                       |
| `keyed`  | 按 key 分发                   |
| `chain`  | 条目按 priority 竞选，第一个非空返回者当选 |


配套概念：

- **Component Factory**：可复用组件装配，调用方选择局部 Component；
- **五种 framework props share**：runtime、child-render、factory-render、store、business（由 `inject` 推导）；
- **Store seats**：声明式状态座位，`defineStore` 的 `init` 推导 schema，`actions` 是完整写集；
- **声明纪律**：声明一个 slot 就是认领它；向未声明 slot 注册、重复声明子 slot、同一 handle 挂两个 scope、chain 没有 `select`，都会在加载期抛错，而不是运行时静默。

这条"**加载期失败**"很值得抄：插件装错时要立刻炸，不要等用户点到那个按钮才发现。

### 6.3 会话节点装配：卡片化渲染的真正底座

`docs/subsystems/conversation.md` 定义了一套可回放的节点装配模型：


| 概念               | 作用                                                                    |
| ---------------- | --------------------------------------------------------------------- |
| Event Definition | 匹配一类 durable / transient 事件，按稳定 `(kind, id)` 关联，折叠出确定性 State，可选物化一个节点 |
| Context          | 一个 `(kind, id)` 的有序 Matches 与当前 State                                 |
| Location         | 从边界事件推导 Session / Turn / Step 坐标                                      |
| View Definition  | 每个 target（chat / trajectory）自己的增量 builder 与最终快照                       |
| Group Definition | 从节点派生分组、摘要、增量缓存                                                       |
| View             | Chat / Trajectory 等 slot 条目，只读 target 快照                              |


业务方贡献一个节点只需要：

1. 定义事件（start / progress / end），带稳定业务 id；
2. 写 `ConversationNodeDefinition`（`match` / `start` / `update` / `publication` / `buildLocationData` / `buildViewNode`）；
3. 在 `conversation.chat.node` 注册 keyed renderer。

关键约束：

- 一个 `(kind, id)` 最多一个 start；
- 只有 update、start 还没加载时，保留 pending Context，不臆造 State；
- 增量事件必须能按 `seq` 确定性重放；
- 历史回放与实时流走同一套匹配/更新接口；
- 渲染性能与验证义务由节点定义方承担。

这套模型直接回答了"卡片如何既实时又能在重启后回放"——**卡片是日志的投影，不是内存里的临时对象**。

### 6.4 设置页与插件管理器

- `ui-settings-*` 系列把设置页拆成插件；
- `ui-plugin-manager` 提供安装/启用/禁用/重试/组合；
- `ui-plugin-market` 提供市场索引与 bundle 安装；
- `plugin_manager` 工具把同一套操作暴露给模型，但被 `danger-full-access` 或逐次审批门控。

**重要边界**：插件管理器明确写了"installed Host code executes in-process outside the workspace sandbox"——也就是说，**插件是受信任代码，不是沙箱代码**。这和 VS Code 的 extension host 是"failure boundary, not automatically a security boundary"是同一个结论。

## 7. 安装、启用与热更新



### 7.1 包管理

Plugin Manager 用 pnpm 做真实的包操作：

- `installBundle` / `remove` / `inspect` / `listBundles`；
- 安装前检查 `engines.dsh` 与 peer deps；不兼容直接拒绝，不下载；
- 支持版本豁免 `package-name@version → dsh runtime versions`，必须显式接受风险；
- 安装失败恢复 `package.json` 与 `pnpm-lock.yaml`；
- 安装日志与状态通过 `plugin-manager/install-log` / `install-state` 流式输出；
- 支持 registry fallback（默认 npmmirror），私有 registry 不会回落到公共源。



### 7.2 启用/禁用

- 只改 profile patch 里的 `disabled`；
- 如果改完与 bundle 层默认状态一致，就删除这条覆盖，不写入冗余配置；
- bundle 的启停改的是 `package.json` 的 `dsh.profile.bundles` 有序数组；
- 禁用保留依赖，重新启用会追加到末尾，可能改变配置优先级——这是一个被明确承认的语义。



### 7.3 HMR

- YAML 控制是否启用 `dsh-hmr`；
- 配置变更立即重组；未启用 HMR 时运行中的组合保持不变，返回 `restart-required`；
- 客户端 bundle 变化通过 revision 切换单资源 combo URL；
- 移除插件时先等待其异步 effects 完成，再逐出未使用模块与样式；
- 替换失败保留旧版本继续运行（客户端），Host 侧则可能进入 `failed` 并在下次操作重试。



### 7.4 失败语义

Plugin Manager 的失败表值得抄：


| 失败操作                  | 处理                                      |
| --------------------- | --------------------------------------- |
| 安装：pnpm 或 bundle 校验失败 | 恢复 manifest/lockfile；已下载文件可能残留；报告失败     |
| 启用：保存选择或加载失败          | 保留依赖与选择；允许修复/禁用/移除                      |
| 发布：包操作成功但运行时解析失败      | 保留磁盘变化与旧运行时表；报告 `application: 'failed'` |
| 移除：任一步失败              | 停在失败步骤；保留已完成变化；不重新启用                    |


核心原则：**不假装成功，不回滚已经不可逆的步骤，如实报告剩余状态**。

## 8. 运行时自修改

`packages/extensions/` 提供：

- `tool-cordis`：只读的运行时 API 发现（`cordis_inspect`）；
- `cordis-host-runner`：Host 半边的定义注册、沙箱化生命周期；
- `cordis-client-runner`：浏览器半边把一段源码求值成 live plugin；
- `ui-cordis`：面板与历史生命周期卡片。

这使 Agent 可以在运行时**定义、运行、停止插件**，但读取与写入被分离：inspect 是只读工具，define/run/stop 走受控 runner。对 Lumii 的启示是：**自修改能力要作为独立的高危插件**，不要混进普通工具集。

## 9. 设计思想提炼

1. **没有特权内核**：连 Agent 循环都是插件；扩展靠挂载，不靠打补丁。
2. **注册即副作用**：每个贡献返回 disposer；卸载顺序 LIFO；异步清理要显式串行。
3. **依赖是声明式 coeffect**：加载顺序由服务可用性决定，不由文件顺序决定。
4. **扩展点按域划分**：session（durable）/ agent（live）/ capability（policy & adapter）三类事件，先选域再选事件。
5. **接缝三角**：Definition / Provider / Consumer，缺一不成缝。
6. **组合与代码分离**：Profile / Bundle / Patch 三层，运行什么由配置决定。
7. **静态声明 + 运行时绑定**：manifest 负责可发现性，代码只绑定 handler（VS Code 同款思想）。
8. **加载期失败**：slot 冲突、缺依赖、版本不兼容在加载时炸，不等到运行时。
9. **模型可见即落日志**：可回放是 UI 与审计的共同底座。
10. **失败要如实**：部分成功就是部分成功；恢复快照、保留已完成步骤、给出下一步。

## 10. 不能照搬的地方


| 点                | 现实约束                                                                  |
| ---------------- | --------------------------------------------------------------------- |
| **论文成熟度**        | Cordis 论文是 preprint，验证集中在 Koishi/TypeScript，无基准；不要把它当"已被大规模异构系统验证"的结论 |
| **全量插件化的认知成本**   | 一个简单改动可能要跨越 manifest、patch、bundle、slot 多层；小团队会显著变慢                    |
| **进程内插件不是沙箱**    | dsh 自己写明 Host 插件在 workspace sandbox 之外执行；安全靠信任与审批，不靠隔离                |
| **pnpm 包管理很重**   | 安装/卸载涉及锁文件、构建脚本审批、registry fallback、平台差异；桌面端体验成本高                     |
| **扁平模块图**        | 客户端 bundle 是一个模块节点，细粒度 externalization 需要改接口                          |
| **元数据 revision** | mtime/ctime/size 无法区分"内容没变但元数据变了"与真正变更；也不能保证内容等价的模块不重载                |
| **类型声明合并**       | 跨包 `declare module` 可读性差，冲突只能在加载期发现                                   |
| **HMR 状态丢失**     | 客户端替换会重建组件；需要显式状态迁移或接受重置                                              |
| **平台/发布耦合**      | Electron 桌面壳与 Web 宿主共享运行时但包管理与激活分离，发布流程复杂                             |

## 12. 对 Lumii 的直接启示

1. **不要直接引入 Cordis 作为第二内核**。Lumii 已经建立在 `@earendil-works/pi-agent-core` 之上，Electron 又是双进程；再引入一套 loader/HMR 会把启动、构建、类型都变成三套。更稳的做法是**借它的契约，在** `packages/plugin-core` **里实现最小内核**。
2. **先做可逆 effect 与声明式依赖**，这两条是插件化能否热更新的分水岭；没有它们，插件中心只能"安装/卸载后重启"。
3. **前端已经有一半底座**：`A2UIRenderer` 是现成的卡片渲染器，缺的是"组件注册表可扩展 + 插件模块懒加载 + slot 位置"。不要从零造卡片系统。
4. **会话消息的** `parts` **已经是天然节点模型**；先加 `part -> renderer` 的注册表，再逐步引入稳定 `(kind, id)` 与回放约束。
5. **组合层可以简化**：Lumii 不需要 dsh 那么重的 pnpm profile，先用"内置 bundle + 用户 profile + 工作区覆盖"三层 JSON 足够。
6. **安全模型要提前说清楚**：同进程渲染插件 = 受信任代码；不可信内容只允许声明式 A2UI（无 JS）或 iframe/Worker 隔离。不要等出事再补。
