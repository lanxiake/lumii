# Memex 设计解构与 Lumii 参考建议

## 1. 结论

`vndee/memex` 是一个 Go 编写的、本地优先的时态知识图服务。它的关键价值在于将**原始交互**（episode）、经规则或 LLM 提取的**实体/关系**、检索索引和后台摄取任务分层，并把“提取失败”降级为仍可保存的 episode。Lumii 可以借鉴其可恢复摄取和可重建索引边界；不应直接采用其自动合并、强度衰减后物理删除，以及独立 MCP/HTTP 服务形态。

本文基于 `main` 提交 `a3bda8beac51ef590aaf15b4cf81502925889abd`。已验证内容来自源码和测试；“建议”是针对 Lumii 的设计推导。

## 2. 已验证：分层模型与摄取

```text
内容 -> episode（原文、来源、元数据）
              -> 规则提取，失败时 LLM 提取
              -> 实体解析 / embedding -> entities + relations
                                           |-> FTS5
                                           |-> 向量索引
提取或 embedding 失败 -> episode 保留 + ingestion_tasks，供后续重试
```

- `knowledge_bases` 将每个库的 embedding/LLM 配置隔离；`episodes` 保存未经改写的原文，实体、关系和社区另存。关系带 `episode_id` 作为来源，`valid_at`/`invalid_at` 表示事实有效期，`created_at` 记录写入时间。
- `Pipeline` 的注释和测试确认其顺序是 episode、抽取、实体解析、向量、存储；规则抽取优先，LLM 是回退。任务表对降级路径的阶段、状态、错误与次数持久化，未完成任务可重新入队。
- FTS5 外部内容表分别索引 entity、relation、episode，并通过 insert/update/delete trigger 维持同步。

**对 Lumii 的建议：** 将 `raw` 导入物、用户 Markdown/Wiki 页、AI 编译得到的结构化事实分为不同真相层。P0 先保证原文和页面的原子写入、可重建 FTS；任何抽取失败只能产生可见待处理项，不能让导入消失。

## 3. 已验证：检索与图谱

- `SearchFTS` 使用 BM25；`hybrid.go` 将关键词、向量和图候选经 RRF 融合。图实现可在指定有效时间下排除已失效边，并输出带 hop distance 的子图。
- 向量引擎按 KB 隔离。小规模使用 brute force，达到默认 10,000 条后异步构建并原子替换为 HNSW；HNSW 持久化格式有 magic/version/dimension 校验。测试覆盖 HNSW 召回、序列化和升级，而非 Lumii 目标硬件基准。
- 关系重复时，存储层将同一 `(source,target,type)` 合并，权重使用概率并集，保留较长摘要；实体 consolidation 按向量近似候选并重定向边。

**对 Lumii 的建议：**

- P0 仅采用 FTS5、路径/状态/来源过滤和 `[[wikilink]]` 反链；索引永远不是唯一真相源。
- P2 如确需机器可查询事实，采用 observation 的 `valid_from/valid_to` 与来源引用；图检索必须是可关闭的候选增强，不能覆盖正文搜索结果。
- P3 才评估本地 embedding 与 RRF。HNSW 阈值、维度、召回率要在 Lumii 中文/中英混合数据和 Windows 安装包中实测，不能移植上游默认值。

## 4. 已验证：生命周期与风险

- `decay_state` 根据访问日志维护 strength；测试验证一个半衰期后强度约为 0.5。`PruneKB` 会物理删除低强度且无连接的实体。
- consolidation 测试验证相似实体会合并、关系会重定向并去重。这是为了压缩 agent memory 的服务端策略，而非用户可编辑知识库的版本语义。

**不适合直接采用：** 自动合并会删除原实体，prune 会物理删除低访问内容；两者都可能损失用户资料、原始出处与可解释性。Lumii 应使用 `active/outdated/disputed/archived` 和人工确认的 supersede，归档优先于删除。独立 Go 二进制、MCP tools、HTTP 路由及每 KB 的 API key 配置也不符合 Electron main/preload/renderer 边界。

## 5. 可迁移决策

| 模式 | 阶段 | 决策 |
| --- | --- | --- |
| 原文先落库、失败任务可重试 | P0/P1 | 采用 |
| SQLite 迁移、FTS trigger、索引重建 | P0 | 采用，但显式提供 rebuild |
| 来源关联和有效时间事实 | P1/P2 | 条件采用 |
| RRF、向量、HNSW | P3 | 仅测量达标后采用 |
| 自动 consolidation / decay prune | 不采用 | 以人工审核和归档替代 |
| Go MCP/HTTP 服务 | 不采用 | 通过 Lumii IPC 暴露能力 |

## 6. 待验证问题

1. Lumii 现有 SQLite 构建的 FTS5、备份与恢复是否覆盖新索引表。
2. 导入任务在应用退出、模型不可用和数据库迁移中如何保持幂等。
3. 哪些 AI 提取结果可见为候选，哪些经用户确认才能成为可检索事实。
