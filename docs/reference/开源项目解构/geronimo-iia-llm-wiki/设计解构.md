# geronimo-iia/llm-wiki 设计解构与 Lumii 参考建议

## 1. 结论

`geronimo-iia/llm-wiki` 是一个本地 Rust 知识库引擎：Git 跟踪的 Markdown 与 JSON Schema 是真相，Tantivy BM25 索引和 petgraph 图是可丢弃、可重建的派生状态。相比通用“AI 记忆”项目，它更值得 Lumii 借鉴的是**schema 驱动类型系统、原子索引替换和索引陈旧检测**；其独立 Rust 二进制、MCP/ACP 服务端和 Git 依赖不适合直接嵌入 Electron。

## 2. 调研边界与证据

分析基于提交 `b4e224f34470d7034887703b2dda90b58ab3b50b`，双许可证及检出位置见[源码/README.md](源码/README.md)。本文的“已验证”来自源码、设计规范和测试；“对 Lumii 的建议”均为推导。

## 3. 架构与数据流

```text
Markdown + frontmatter + schemas/*.json + wiki.toml
  -> 类型注册/校验 -> 解析 page + section
  -> Tantivy 文本、关键字、存储字段索引
  -> search/list（BM25 + filter）与 graph（结构关系）
  -> state.toml 记录 schema hash、Git commit、构建统计
```

### 3.1 Schema 是类型和索引的唯一来源

**已验证：**`docs/invariants.md` 明确 schemas 文件的 `x-wiki-types` 决定可用页面类型，`wiki.toml` 只能覆盖显示配置，不能创造无 schema 的类型。`index-management.md` 描述从类型 schema 和 `x-index-aliases` 推导 Tantivy schema：文本字段走 BM25，关键字字段用于 type/status/tags 过滤，存储字段供结果返回；正文也进入文本索引。`slug` 是增量 delete+insert 的唯一键，项目没有稳定 UUID，避免把身份仅存入可重建索引。

**对 Lumii 的建议：**定义 TypeScript 的 `WikiPageKind` 和每类 metadata schema，并让 repository 校验、FTS 字段构造和 renderer 表单共享同一份定义。页面 ID 应由 Lumii 生成并写入真实存储；不要让 FTS rowid、文件名或向量行号成为唯一身份。

### 3.2 可恢复的索引生命周期

**已验证：**上游用 `state.toml` 记录 schema hash、最后 Git commit、页面数和每类型 hash。增量更新合并“工作树对 HEAD”和“上次索引 commit 对 HEAD”的差异，对每个变更 slug delete 后再按当前文件是否存在决定 insert；schema hash 不匹配、状态缺失或增量失败则走全量重建。全量重建先在 building 目录完成 Tantivy commit，再经三次 rename 原子替换，失败回滚旧索引。索引文档明确它不会提交或共享。

**对 Lumii 的建议：**P0 采用 `wiki_index_meta`：记录 schema/index 版本、源数据 revision、完整构建时间和健康状态。全量重建应建新 FTS 表/临时数据库后切换，不要先清空线上索引。不要采用 Git diff 作为应用内增量依据，改以写入事务中的 page revision 或 change log 驱动；导入、迁移、崩溃恢复都必须可请求全量重建。

### 3.3 图谱是结构视图，不替代搜索

**已验证：**上游禁止运行时 LLM、embedding 和网络依赖，检索维持 Tantivy BM25，图分析只基于结构关系。图缓存按稳定的索引内容 key 失效；跨进程 CLI 必须使用持久 commit key，而非进程内 generation。只有未过滤的完整图进入缓存，带 root/type/relation 过滤的请求重新构建，深度限制则在完整图上截取。跨 wiki 链接在图构建时解析，而非索引时解析，以保持单 wiki ingest 局部性。

**对 Lumii 的建议：**P0 把 wikilink/backlink 做成关系查询，FTS 保持主检索。P2 若引入图视图，缓存键必须包含链接/页面 revision；过滤子图的缓存需要独立 key，不能复用完整图。跨工作区关系在产品明确需求前不做，避免把单页保存变成跨库一致性问题。

### 3.4 并发和副作用边界

**已验证：**`docs/invariants.md` 将 graph cache refresh 的拥有者固定为 ops 层，以确保 CLI 与 MCP 调用一致；还规定 RwLock 不可重入的获取顺序。索引读者采用手动 reload，避免多 reader 文件监视竞争。这些不变量有对应 engine/index/graph 与集成测试覆盖。

**对 Lumii 的建议：**将“页面写入、FTS 更新、链接更新、索引状态修改”收敛在 `agent-runtime`/repository 的一个事务边界，Electron main handler 只做 IPC 编排。任何重建完成后的缓存失效应由同一服务负责，禁止 renderer 私自清缓存或直接查询数据库。

## 4. 可迁移性决策

| 模式 | Lumii 阶段 | 结论 |
| --- | --- | --- |
| schema 驱动元数据与索引字段 | P0 | 采用 |
| 派生索引状态与原子替换 | P0 | 采用，使用 SQLite 方案 |
| 变更驱动的增量更新 + 全量回退 | P0 | 采用，基于内部 revision 而非 Git |
| BM25/FTS 主检索 | P0 | 采用 |
| wikilink/backlink 结构图 | P0/P2 | P0 做关系，P2 才可视化 |
| graph cache 的稳定失效键 | P2 | 条件采用 |
| Tantivy/Rust 二进制、Git commit 状态 | 不纳入 | 不采用 |
| MCP/ACP 服务端、跨 wiki 图 | 不纳入 | 不采用 |

## 5. 分阶段落地建议

1. **P0：**页面类型 schema、SQLite 迁移、FTS5、`wiki_links`、索引元数据和 `rebuildWikiIndex()`；测试原子性、删除页、重建失败恢复及 schema 变更。
2. **P1：**依据产品实际引入字段级筛选和来源/状态审计，给查询结果返回命中依据。
3. **P2：**在链接规模和查询需求成立后加入图缓存与邻接扩展；先验证关系查询价值，再制作图 UI。

## 6. 约束与风险

- 上游的原子目录 rename 和 Tantivy 读者机制不能逐字迁到 SQLite；需要按 SQLite transaction/WAL 和现有 `LocalDatabase` 实现。
- Git commit 是其本地文件工作流的版本钟，不是桌面数据库的版本模型。
- BM25 对中文分词质量取决于 tokenizer；必须用 Lumii 真实中文和中英混合语料验证。
- 虽为宽松双许可证，本调研仅采用架构思想，保持 Lumii 独立 TypeScript 实现。
