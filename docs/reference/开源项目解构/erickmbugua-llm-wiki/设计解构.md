# erickmbugua/llm-wiki 设计解构与 Lumii 参考建议

## 1. 结论

`erickmbugua/llm-wiki` 是一个“文件 vault 为真相 + SQLite 搜索副本”的 Python 知识库原型。它把文件监听、摄取队列、LLM 提取、页面写入、增量 reconcile、FTS5/vector 检索和 backlink 重建串成闭环。最有参考价值的是**队列状态、索引可重建、向量失败时的 FTS 降级和最小影响域的 backlink 更新**；最大的风险是 LLM 可直接覆写页内容、stem 链接歧义及未声明许可证。

## 2. 调研边界与证据

分析基于提交 `bf4e075dd1c81342f9fd4cd6ae939e315eb3fb0b`，检出位置与许可证调查见[源码/README.md](源码/README.md)。“已验证”来自实际 Python 实现和测试；“对 Lumii 的建议”不是现有实现描述。

## 3. 架构与数据流

```text
raw/ 文件创建或移动
  -> watchdog -> SQLite ingest_queue(pending/processing/done/failed)
  -> 提取文本；大文件分块摘要；LLM 生成 source/page updates
  -> 写入 wiki Markdown、追加 log.md
  -> partial_reconcile: pages + FTS5 + links + 受影响 backlinks
  -> FTS5，或 embedding + sqlite-vec + RRF 混合查询
```

### 3.1 Vault 和 SQLite 双层模型

**已验证：**`core/db/connection.py` 建立 `pages`、外部内容 FTS5 `pages_fts`、`page_vectors`（768 维 vec0）、`ingest_queue`、`ingest_jobs` 与 `links` 表。pages 的写入触发器维护 FTS；`reconcile()` 按磁盘 mtime 扫描 Markdown，新增/更新/删除 pages 后重建 backlinks，`partial_reconcile()` 则只更新已知变更页和受影响链接邻域。集成测试验证“LLM 写页 -> DB reconcile -> backlinks -> log -> index”的完整摄取链。

**对 Lumii 的建议：**保留源页面与 SQLite 派生索引的分离，并让全量 reconcile/rebuild 成为一等能力。应用内写入要用一个 SQLite 事务同时更新页面记录、FTS 和 links；若未来支持外部 Markdown 同步，再单独设计变更检测，不能只靠浮点 mtime 判断内容变化。

### 3.2 受控摄取队列

**已验证：**`watcher.py` 只监听 `raw/` 的创建/移动事件，忽略数据库和临时下载后缀，并把 vault 相对路径写入队列。队列状态依次为 pending、processing、done 或 failed；单项失败会记录错误但不会中断其余任务，重入同一路径可将 failed 重置为 pending。相关单测覆盖重复入队、重试和错误持久化。

**对 Lumii 的建议：**P1 可复用明确 job 状态机和失败可重试语义，但把监听放在 Electron main/后台服务，向 renderer 通过 IPC 推送状态。入队项要附 source hash、创建者和取消/重试策略；避免只有路径而在文件被替换后摄取错误版本。

### 3.3 检索与向量降级

**已验证：**`search.py` 先以 FTS5 BM25 搜索 title/content，并清理用户输入中的 FTS 特殊字符；可选 vector KNN 由 sqlite-vec 提供。`hybrid_search()` 用 `1 / (60 + rank)` 的 RRF 合并两份候选；没有 query embedding 或向量查询异常时直接返回 FTS 结果。`query.py` 与 ingest 的 related-page 逻辑都捕获 embedding 失败并退回词法检索。

**对 Lumii 的建议：**P0 只交付 FTS5，并在 API 返回检索模式/降级原因。P3 才接入 embedding 和 RRF，且需要使用索引版本绑定的向量，防止内容更新失败后仍召回旧 embedding。上游使用的 FTS `porter ascii` 不适合直接用于中文。

### 3.4 链接与 AI 写入风险

**已验证：**写页时 `upsert_page()` 用正则抽取 `[[target]]`，将边写入 links；全量和增量 backlink 重建均从 links 表而非重复解析正文生成。若多个文件有同 stem，逻辑按字母序选第一个并写 warning，测试验证此行为稳定。另一方面，`write_pages()` 接受 LLM 的完整内容，并对 `create` 和 `update` 都直接覆盖文件；只做路径必须位于 wiki 根内的校验。`chunking.py` 对大文本做重叠字符窗并逐块调用 LLM 摘要。

**对 Lumii 的建议：**采用关系表与增量 backlink 思路，但链接 target 应存 page ID/规范化路径，不能依赖文件 stem 决胜。AI 输出只能写“候选修订”，展示 diff 并由用户确认后覆盖原页；路径校验之外还需校验类型、来源引用、尺寸限制和并发 revision。大文件分块必须保留 chunk 到来源偏移的可追溯映射，不能只拼接摘要。

## 4. 可迁移性决策

| 模式 | Lumii 阶段 | 结论 |
| --- | --- | --- |
| vault 真相 + SQLite 可重建索引 | P0 | 采用 |
| FTS5、输入净化、明确 FTS 降级 | P0 | 采用，验证中文 tokenizer |
| links 表 + 邻域增量 backlinks | P0 | 采用，改用 page ID |
| ingest job 状态机和可重试失败 | P1 | 采用 |
| RRF/embedding/sqlite-vec | P3 | 条件采用 |
| LLM 文件全量覆盖 | 不纳入 | 不采用，改候选/审批 |
| stem 歧义的字典序决策 | 不纳入 | 不采用 |
| Python watchdog/LiteLLM/MCP/HTTP 服务 | 不纳入 | 不采用 |

## 5. 分阶段落地建议

1. **P0：**定义 `wiki_pages`、`wiki_links`、FTS 和 index metadata，覆盖 CRUD、删除、重建、断链和中文查询测试。
2. **P1：**建立导入/编译 job 表，支持 pending/running/succeeded/failed/cancelled、源快照、进度和安全重试；候选修订必须带 base revision。
3. **P2：**为附件建立 chunk/source-offset 模型和可解释引用，再考虑由 AI 生成摘要或建议链接。
4. **P3：**用 Lumii 查询集评估 embedding、候选过取和 RRF；模型不可用时保持完整 FTS 功能。

## 6. 约束与风险

- 根目录没有许可证文件或声明，不能复制任何实现，直至取得许可。
- 以 mtime 为唯一同步依据会受文件系统精度、回滚和复制影响；内容 hash/revision 更可靠。
- FTS 触发器适合普通写入，但迁移、导入和恢复仍需要显式全量重建。
- LLM 输出直接替换完整 Markdown 容易丢失用户编辑；这是 Lumii 必须排除的行为。
