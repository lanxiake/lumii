# 第 5 章实践：单 Agent 基线 vs orchestrator + 2 worker

同一个任务、同一份语料，跑两种架构，把"协调开销"和"覆盖收益"变成可以打印出来的数字。

## 任务设定

语料（`corpus/` 下 10 篇**虚构但逼真**的报道，事件：青云地铁 12 号线开通首月"客流口径之争"）分三个阵营：

| 阵营 | 文件 | 核心口径 |
|---|---|---|
| 官方 | 01 交通局通报 / 02 地铁集团发布会 / 03 统计局简报 | 日均客运量 51.2 万（含换乘）；预测 65 万是"高峰日目标"；分担率抽样口径 9.2% |
| 媒体 | 04 晚报 / 05 省台 / 06 财经周刊 / 07 行业自媒体 | 进站量口径 38.4 万，"缺口超四成"；经营账本；同类城市爬坡规律 |
| 社区与学术 | 08 本地公众号 / 09 论文摘要 / 10 论坛摘编 | 票价/间隔不满；四阶段法数据过时、岗位西移 |

任务：**汇总三方口径差异**（数字、统计口径、分歧原因、独立数据）。内置 10 条 rubric（R1–R10）作为要点覆盖的打分标准。

## 两种架构

```
A. 单 Agent 基线                          B. orchestrator + 2 worker
loop:                                    1 orchestrator 规划（只看语料索引，不看正文）
  prompt = 任务 + 累计笔记 + 新一批语料     2 worker×2 只读：各领一个阵营的语料
  每轮新增笔记；笔记超预算→旧笔记被挤出        只回结构化要点，不回全文
final = 幸存的笔记                        3 orchestrator 合并：只读 worker 结论
```

A 的"笔记容量上限"模拟单 Agent 的上下文预算：早期材料的关键事实会被挤出上下文——这正是长任务里单 Agent 丢信息的机制。B 里 orchestrator 全程读不到语料正文，worker 之间不共享上下文（本任务是可并行的"读多写少"任务，这是多 Agent 为数不多真正划算的形态）。

## 输出解读（桩模式参考值）

| 指标 | 单 Agent | orchestrator+worker |
|---|---|---|
| LLM 调用步数 | 3 | 4 |
| 总 token（估算） | 4170 | 5931 |
| 协调开销占比（指令+状态） | 27.7% | 33.4% |
| rubric 覆盖 | 6/10（漏 R5 R7 R8 R9） | 9/10（漏 R7） |

## 你应该观察到什么

1. **多 Agent 更贵**：总 token 高约 40%，协调占比更高——worker 各自重复领任务说明、结论要回传给 orchestrator 再合并，这些都是"协调税"。
2. **多 Agent 覆盖更全**：单 Agent 的早期材料要点被笔记预算挤出（官方阵营的 R5/R9 最先阵亡）；worker 各自独立上下文，官方阵营的要点存活到了最后。
3. **orchestrator 没读过一篇原文**——检查 `run_multi`：规划与合并两个调用的 prompt 里只有索引和结论。这就是"worker 只回结论不回全文"的信息流形态。
4. **多 Agent 也不是全自动满分**：worker B 语料多、额度只有 7，财经账本 R7 同样被裁掉了。多 Agent 不消灭信息丢失，只是把丢失的位置从"主上下文"挪到了"worker 额度/接口设计"。
5. **协调税是可以量化的**：`协调开销 = 指令重发 + 状态与交接`。把它除以"多覆盖的要点数"，就是这张架构的单价。

## 桩模式的局限（重要，请先读完再引用任何数字）

- 桩模式的"模型"是**启发式句子抽取**（任务词 + rubric 关键词打分），不是语言模型。桩模式下的覆盖差异来自**架构的信息流**（上下文预算、笔记挤出、worker 额度、只回结论），**不能外推为真实模型上的能力差**。
- token 是估算值（1 汉字≈1 token，1 个英文词≈1.3 token），两侧同规则，**只用于相对比较**；真实模式优先采用 API 返回的 usage。
- worker 拆分边界（官方 vs 其余）在桩模式里是硬编码的，等价于"orchestrator 做了一个完美规划"；真实模式下规划本身可能出错，成本会更高（Anthropic 的工程博客对此有大量记载）。
- 演示中 worker 串行执行；真实系统应并发发起，那时"墙钟时间"和"总 token"会朝不同方向变化——这正是第 5 章正文说的：并行的主要收益是彻底性，不是速度。
- 语料与事件均为虚构，数字之间的差异是人为设计的。

## 值得做的练习

1. 把 `SINGLE_NOTES_CAP` 从 7 调到 15：单 Agent 覆盖会升到多少？token 怎么变？——这就是"加上下文预算"与"加 worker"两种手段的比价。
2. 把 worker 额度 `quota` 都改成 5：多 Agent 会漏掉什么？
3. 用 `--real` 跑一遍：比较两种架构的 usage 数字与真实模型的要点质量；注意 orchestrator 规划这一步真实输出是否稳定。
4. 给 worker 的返回格式里加一个"必须包含数字及口径"的硬约束，看 R 系列覆盖怎么变——接口设计就是多 Agent 的 API 设计。
