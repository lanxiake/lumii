## 1. 逆向结论（全部来自本机取证）

### 1.1 进程与模块分层

| 组件 | 体积 | 职责 | 证据 |
| --- | --- | --- | --- |
| `Listary.exe` | 2.1 MB | WPF 宿主：托盘、设置、启动器搜索框 | 目录内含 `HandyControl.dll`、`MahApps.Metro.IconPacks.*`、`Listary.Localization.*.dll` |
| `Listary.Service.exe` | 32 KB | Windows 服务形态（提权索引） | 同目录 `Listary.Service.dll.config` |
| `listary-core.exe` | 15.2 MB | **Rust 引擎**，gRPC 服务端 | VersionInfo：`ProductName=listary-core`，`FileVersion=0.2.1` |
| `listary_engine.dll` | 14.5 MB | 同引擎的 DLL 形态 | 引擎日志命名空间 `listary_engine::*` |
| `Hooks\ListaryHook{32,64}-6.1.10.1.dll` + `ListaryHookHost{32,64}.exe` | 214/271 KB | **全局键鼠钩子**（双击 Ctrl、文件对话框内拦截输入） | 无对应 .NET 实现，故为原生 DLL |

### 1.2 索引引擎（从 `listary-core.exe` 字符串取证）

关键字符串：

```

$MFT::$DATA
```

推出四条核心机制：

1. **全盘枚举走 NTFS `$MFT` 直读**，不走 `FindFirstFile`/`readdir`。这是它"秒出全盘结果"的根因——MFT 是一次顺序读元数据，而非按目录递归。
2. **存储是 RocksDB**。`Cache\<主机名>\Index\` 下有 `*.sst` / `CURRENT` / `IDENTITY` / `LOCK` / `LOG.old.*` / `000xxx.log`，且字符串里含大量 `rocksdb::` 符号（`BlockBasedTable`、`PartitionedIndexBuilder`、`cache_index_and_filter_blocks` 等）。本机该目录实测约 **504 MB**。
3. **对外是 gRPC**（`Grpc.Net.Client`、`Grpc.Core.Api`、`Google.Protobuf` 在安装目录；引擎侧 `hyper` + `tokio` + `prost`）。C# 前端 → gRPC → Rust 引擎。
4. **文件 id 与硬链接槽位**（`db::builder` 的 hard link slot 日志）——用 NTFS file id 去重硬链接。

### 1.4 其他取证

- 设置结构（`Preferences.json`）含 `Commands.Items`、`WebSearch.Items`、`Actions.Items`、`DiskSearch.{FolderPriority,FileNamePriority,SearchFilter}`、`Menus.Favorites` —— 即"自定义命令 / 网络搜索 / 快捷动作 / 文件夹与文件名优先级 / 收藏夹"。全部是**规则表**，无智能成分。
- 日志显示大量 `Get icon ... with non zero result but empty hIcon` —— 图标走 `SHGetFileInfo` 一类 Win32 调用，且存在失败重试。
- `Listary.Core.Utils.WindowUtils: ForceForegroundWindow failed` —— 唤起窗口时会抢前台焦点（并有失败兜底）。

### 1.5 明确不复刻的部分

| 机制 | 为什么不做 |
| --- | --- |
| NTFS `$MFT` / USN Journal 直读 | 需管理员权限 + 原生代码 + 卷设备访问（`DeviceIOControlLib.dll` 就是这个用途）。收益是"首扫几分钟→几十秒"，代价是本项目无法承受的原生依赖与权限要求。 |
| RocksDB 存储 | 引擎为它准备了 504 MB。SQLite FTS5 在本项目的扫描规模下完全够用，且仓库已有 5 张成熟 FTS5 表。 |
| gRPC 多进程拆分 | 我们与 Electron 主进程同进程，跨进程边界只会增加复杂度。 |
| UIAutomation 对话框注入全套 | 只在「对话框跳转」一项上有限复刻（见 §6.6）。 |
| 遥测 / 自动更新 / 多语言 | `RudderAnalytics.dll`、`AutoUpdater.NET.dll`、46 种 `Localization.resources.dll`。与本功能无关。 |

## 2. 目标与非目标

### 2.1 目标（用户已拍板四项全要）

1. **启动器核心**：搜索本机文件、应用、快捷方式；结果可打开、打开所在目录、复制路径、以管理员运行。
2. **双击 Ctrl 唤起**：与 Listary 一致的交互——任意界面下双击 Ctrl 弹出搜索框。
3. **对话框跳转集成**：「打开 / 另存为」对话框中直接跳转到指定目录。
4. **文件内容搜索**：除文件名外可检索文件正文。
5. **暴露为 Agent 工具**：让 AI 在对话中主动检索本机文件。

### 2.2 非目标

- 不做 MFT/USN 直读（见 §1.5）。
- 不做 Listary 的「收藏夹 / 自定义命令」管理器 UI（P1 只保留数据结构，UI 后置）。
- 不做多语言（本项目中文优先）。
- 不替代系统开始菜单（只索引 Start Menu `.lnk` 作为应用来源之一）。

## 3. 关键技术决策

### 3.1 中文全文检索：**复用 `tokenizeBigram` 预分词，不重新发明**

**这是本次设计中最容易踩坑的一点，已实测确认。**

`packages/agent-runtime/src/memory/memory-index.ts` 的注释与 `storage/schema.ts` V15/V16 迁移注释里记录了本项目早前的实测结论，本次复核一致：

| 分词器 | "设计" 能否命中 `项目设计文档.docx` | 结论 |
| --- | --- | --- |
| `unicode61`（默认） | ❌ 零命中 | 把连续中文整段当作**单个 token**，`项目设计文档` 是一个词 |
| `trigram` | ❌ 零命中 | 要求查询词 **≥3 字符**；`设计`（2 字）被判无效 |
| `trigram` + 3 字查询 | ✅ `设计文` 可命中 | 印证下限存在于**查询侧** |
| `porter unicode61` | ❌ 零命中 | 同 unicode61 |
| **`tokenizeBigram` 预分词 + `unicode61`** | ✅ **命中** | 写入前 JS 侧切成 bigram，落库为空格分隔 token |

`tokenizeBigram` 的契约（`packages/agent-runtime/src/memory/segmentation.ts`）：

- CJK 连续串 → **bigram**（"项目设计文档" → `项目 目设 设计 计文 文档`）；单字时取单字
- 拉丁/数字串 → **整词小写**
- 标点/空格/emoji 丢弃
- 返回 `Set<string>`

**决策**：新增 FTS5 表沿用**同一套预分词**（写侧 `bigramJoin`，读侧 `tokenizeBigram` + 每 token 单独加引号转义）。理由：仓库已有 5 张同构表（`agent_memories_fts`、`wiki_pages_fts`、`wiki_sources_fts` 等）在生产验证，`palace-repo.ts` 还有 848 条真实数据的调参记录（`MIN_QUERY_TOKEN_HITS = 2`）。自己另起一套是重复造轮子。

**必须注意**：`bigramJoin` 目前定义在 `memory-index.ts` 内（`packages/agent-runtime/src/memory/`）。复刻时**直接 import 复用**，不要拷贝一份。

**两个已实测的行为边界（P0-2 spike 确认，实现时别当缺陷去修）**：

1. **单字 CJK 查询必然落空**。`tokenizeBigram` 对长度 ≥2 的中文段只产出 bigram（`我的设计稿` → `我的 的设 设计 计稿`），索引里**不存在单字 token**，所以查「稿」零命中。实际使用中用户至少输入 2 字，影响有限。
2. **OR 语义会把只蹭到一个 bigram 的条目带进结果**。实测：查「设计文档」（tokens = `设计 计文 文档`）时，`我的设计稿.psd` 因命中 `设计` 而混入。**这正是 §6.3 要启用最小命中过滤的实证依据**——上过滤后收敛到 `项目设计文档.docx` 一条，与 spike 断言一致。

### 3.2 数据库落点：**独立 SQLite 文件，不并入主库**

索引是**可重建的派生物**，且规模可能到几百 MB（Listary 本机 504 MB）。若并入 `packages/agent-runtime` 的主库：

- 备份轮转（`storage/backup.ts`）会把索引体积复制一遍
- 索引损坏会波及用户真实数据
- `SCHEMA_VERSION` 迁移耦合

**决策**：独立文件 `<userData>/listary/index.db`，独立连接。**复用而非重写**：

- `applySqliteConnectionPragmas()`（`storage/local-database.ts`）——WAL、busy timeout 等 pragma 一次性套用
- `DatabaseAdapter` / `PreparedStatement` 接口类型
- `tokenizeBigram` / `bigramJoin` 分词

工人驱动选 **Electron 内建的 `node:sqlite`**。

> ✅ **已由 P0-2/P0-3 spike 实测确认（2026-11-14）**，原始判断在两点上是错的，此处已改正：
>
> | 问题 | 原设想的答案 | 实测结果 |
> | --- | --- | --- |
> | `node:sqlite` 有没有 FTS5 | ❌ 没有（Node 22 下 3.47.2，`no such module: fts5`） | ✅ **Electron 36.9.5 内建的 `node:sqlite` 是 SQLite 3.50.4，编译项含 `ENABLE_FTS5`** |
> | `better-sqlite3` 能不能用 | ✅ 已依赖、可用 | ❌ **没为 Electron 重建**（NODE_MODULE_VERSION 127 vs Electron 需 135，`require` 即抛错） |
>
> **决定性旁证**：生产库 `~/.lumii/data/agent-runtime.db` 里的 `agent_memories_fts`（1606 行）、
> `palace_drawers_fts`（1109 行）、`wiki_sources_fts`（1748 行）三张 FTS5 表**都有数据**；
> 而 plain Node 下读同一个库会报 `no such module: fts5` —— 说明**唯一能建出这些表的就是 Electron 里的
> `node:sqlite`**，本项目一直在走这条路径，且记录在 `local-database.ts` 里被误读成了「node:sqlite 不可用才回退」。
>
> **收益**：零新增原生依赖。`better-sqlite3` 那条 fallback 分支实际是死的，P0 不必再处理 ABI 重建与
> asar unpacked 路径问题。详见 §11 P0 实测记录。

### 3.3 唤起方式：**双击 Ctrl（低层键盘钩子），组合键作兜底**

**Electron 的 `globalShortcut` 做不到双击 Ctrl。** 它注册的是**组合键**（如 `Ctrl+Shift+Space`），无法感知"Ctrl 被按了两次"这种时序模式。

现状核实：仓库内 `globalShortcut` 的唯一使用点是 `plugins/builtin/pet/pet-mode-ipc.ts:520/532`，注册的是固定组合键；且 `apps/windows/package.json` 里**没有任何**键盘钩子依赖（`uiohook-napi` / `node-global-key-listener` / `iohook` 均无）。

因此双击 Ctrl 需要引入低层键盘钩子。这带来三类风险，必须在实施计划的 P0 阶段先做**可行性 spike**：

| 风险 | 说明 |
| --- | --- |
| 原生依赖编译 | 需要为 Electron ABI 重建（`pnpm install` 已有 rebuild 流程，但新原生模块未必有 prebuild） |
| 杀软误报 | 全局键盘钩子是键盘记录器的标准技术特征，实际有被拦截的先例 |
| 权限 | 某些环境（UAC 提权窗口、安全桌面）下钩子收不到事件 |

**决策**：

- 主路径：`uiohook-napi@1.5.5`（**N-API，自带 win32-x64 prebuild，无需本地编译、无需为 Electron 重建**）
- **兜底路径必须同期存在**：`globalShortcut` 注册一个可配置组合键（默认 `Ctrl+Shift+Space`）。钩子加载失败/被杀软拦截时自动降级，UI 里明确告知用户当前生效的是哪种
- 二者都收敛到同一个 `toggleLauncher()` 入口，交互层无感

**双击判定算法（易错点，已实测修正）**：

判定依据是「**一次 Ctrl 按住期间没夹别的键**」，**不是**「两次 Ctrl 之间没夹别的键」。二者差别在 `Ctrl+C` 上：

```
Ctrl+C 的序列：Ctrl↓  C↓  C↑  Ctrl↑
                └────────────┘  C 夹在 Ctrl 的按下与松开之间
```

若只看「两次松开之间」，`Ctrl+C` 收尾的那次 `Ctrl↑` 会被误当成一次干净点击，于是 100ms 内再按 `Ctrl`
（例如紧接着 `Ctrl+V`）就会弹出启动器——而 `Ctrl+C` → `Ctrl+V` 是最常见的操作序列之一，必然误弹。
P0-1 spike 第一版就是这么写的，**被实测打脸**，故改为：

```ts
let lastUpAt = 0
let ctrlHeld = false
let heldDirty = false   // 本次 Ctrl 按住期间是否夹了别的键

onKeyDown(code) {
  if (isCtrl(code)) { ctrlHeld = true; heldDirty = false }
  else if (ctrlHeld) heldDirty = true      // Ctrl 被当修饰键用了（Ctrl+C / Ctrl+V ...）
}
onKeyUp(code) {
  if (!isCtrl(code)) return
  const t = Date.now()
  if (heldDirty) {
    lastUpAt = 0                            // 修饰键用法：作废待配对的点击
  } else if (lastUpAt !== 0 && t - lastUpAt < DOUBLE_PRESS_MS) {
    toggleLauncher(); lastUpAt = 0          // 触发后重置，三连击不会变成两次触发
  } else {
    lastUpAt = t
  }
  ctrlHeld = false; heldDirty = false
}
```

代价：`Ctrl+C` 之后必须重新连按两次 `Ctrl` 才能唤起。这个代价可接受，误弹不可接受。

**另两个实测要点**：

- `uiohook-napi` 的事件**没有 `injected` 字段**（已实测），将来若要区分真实按键与注入事件需另想办法。
- 键码与库常量一致：`UiohookKey.Ctrl === 29`、`CtrlRight === 3613`。

### 3.4 文件枚举：**`fs.readdir` 递归 + 增量，不上原生**

全盘首扫用 Node `fs.readdirSync(withFileTypes)` 递归。按本机实测（E: 盘为主），预期**首扫数分钟**量级——远慢于 Listary 的 MFT 直读，但：

- 只在**首次**或**根目录变更**时全量扫
- 常规运行为**增删改的定向更新**（`fs.watch` 按已索引目录订阅，或定时重扫）
- 索引根默认**只含高价值目录**（桌面、下载、文档、项目目录、Start Menu），不做全盘默认

这是本项目对 Listary 最大的性能让步，必须在文档与 UI 中如实标注，不能假装等同。

## 5. 数据模型

```sql
-- 主表：条目（文件 / 目录 / 应用 / 快捷方式）
CREATE TABLE IF NOT EXISTS lz_items (
  id        INTEGER PRIMARY KEY,
  path      TEXT    NOT NULL UNIQUE,   -- 规范化绝对路径（小写盘符 + 反斜杠归一）
  name      TEXT    NOT NULL,          -- basename，搜索与展示用
  ext       TEXT,                      -- 小写扩展名（不含点）
  kind      TEXT    NOT NULL,          -- 'file' | 'dir' | 'app' | 'lnk'
  size      INTEGER,
  mtime     INTEGER,                   -- 毫秒
  root      TEXT    NOT NULL,          -- 所属索引根，用于增量与优先级
  is_start  INTEGER NOT NULL DEFAULT 0 -- 是否来自 Start Menu（应用来源）
);

CREATE INDEX IF NOT EXISTS idx_lz_items_root ON lz_items(root);
CREATE INDEX IF NOT EXISTS idx_lz_items_name ON lz_items(name);

-- FTS5：预分词列（非 external content，索引在 JS 侧维护）
-- 三分词列拆开是为了将来能按列加权（文件名命中 > 路径命中）
CREATE VIRTUAL TABLE IF NOT EXISTS lz_items_fts USING fts5(
  name_tokens,
  path_tokens,
  tokenize='unicode61 remove_diacritics 2'
);

-- 使用历史：对应 Listary 的 SearchHistory.json，但带计数（Listary 只有时间戳）
CREATE TABLE IF NOT EXISTS lz_usage (
  keyword   TEXT    NOT NULL,
  path      TEXT    NOT NULL,
  count     INTEGER NOT NULL DEFAULT 1,
  last_used INTEGER NOT NULL,
  PRIMARY KEY (keyword, path)
);

-- 索引根（用户可增删）
CREATE TABLE IF NOT EXISTS lz_roots (
  path     TEXT PRIMARY KEY,
  enabled  INTEGER NOT NULL DEFAULT 1,
  added_at INTEGER NOT NULL
);

-- 扫描状态（增量）
CREATE TABLE IF NOT EXISTS lz_scan_state (
  root      TEXT PRIMARY KEY,
  last_scan INTEGER,
  duration  INTEGER,     -- 上次耗时，UI 展示
  item_count INTEGER
);
```

**与 Listary 的差异**：Listary 用 RocksDB 存 MFT 派生结构；我们用关系表 + FTS5。字段语义对齐（path/name/ext/mtime/size 对应 MFT 的 `$FILE_NAME` 属性），便于将来若要换实现时保持查询层不变。

## 6. 分模块设计

### 6.1 文件枚举（`indexer/scanner.ts`）

```ts
interface ScanOptions {
  roots: string[]
  skipDirs: Set<string>   // node_modules / .git / $Recycle.Bin / AppData\Local\Temp ...
  maxDepth: number
  onBatch: (items: Item[]) => void   // 批量回调，避免一次性大数组
}
```

- **跳过规则**：`node_modules`、`.git`、`.svn`、`$Recycle.Bin`、`System Volume Information`、`AppData\Local\Temp`、`Windows\WinSxS`、`Windows\Installer`。这些目录条目数巨大且几乎无检索价值。Listary 也有同类过滤（`DiskSearch.SearchFilter`）。
- **批处理**：每 2000 条 flush 一次写库，避免大数组常驻内存。
- **单遍扫描**：一个 `readdir` 同时拿到 `Dirent`（类型）无需 `stat`；只在需要 size/mtime 时才 `statSync`。这是把首扫从"分钟"压到"分钟"以内的关键——`stat` 是逐文件系统调用，能省则省。

### 6.2 写入（`indexer/writer.ts`）

```ts
upsert(item: Item): void {
  // 先删后插：FTS5 不支持原地覆盖（沿用 memory-index.ts 的做法）
  const rowid = upsertMain(item)          // INSERT ... ON CONFLICT(path) DO UPDATE
  delete FtsRow(rowid)
  insert FtsRow(rowid, {
    name_tokens: bigramJoin(item.name),
    path_tokens: bigramJoin(item.path),
  })
}
```

- `rowid` 用主表自增 id，FTS5 用 `rowid` 列绑定（非 external content 表支持手动指定 rowid）
- 索引维护在**应用代码**，不用 SQL 触发器——分词发生在 JS 侧，触发器做不到（`memory-index.ts` 已踩过这个坑，注释明确记录）

### 6.3 检索（`indexer/query.ts` + `rank.ts`）

**查询流程**：

```
用户输入 "设计文档"
  ↓ tokenizeBigram
{设计, 计文, 文档}
  ↓ 每 token 加引号转义（防 FTS5 语法注入）
'name_tokens' MATCH '"设计" OR "计文" OR "文档"'
  ↓ 取候选（limit 200）
  ↓ 重排
score = w1 * bm25_norm
      + w2 * namePrefixBoost      // name 以 query 开头
      + w3 * usageBoost           // log(1 + count) 归一
      + w4 * recencyBoost         // 最近使用时间衰减
      + w5 * rootPriority         // Start Menu / 桌面 > 普通目录
      + w6 * pathDepthPenalty     // 越深越降权（Listary 的 FolderPriority）
  ↓ 截断 top N（默认 50，UI 可配）
```

- **查询转义必须做**：用户输入会含 `"` `*` `(` `)` 等 FTS5 语法字符。`palace-repo.ts:406` 已有成熟写法——每 token 单独加引号、内部 `"` 转 `""`。**照抄该实现，不要另写**。
- **最小命中过滤**：`segmentation.ts` 的 `requiredTokenHits` 已有实测调参（长文里蹭到任一 bigram 就进结果会污染 top-1）。文件名字段短，污染风险低于长文，**P1 先不启用**，用实测数据决定是否加。
- **权重初值**：先给一组可解释的初值，用真实查询调。**不要先建配置系统**——权重写死在 `rank.ts` 常量里，调稳后再考虑暴露。

**降级**：FTS MATCH 失败（如索引损坏）时回落 `LIKE '%kw%'`，与 `memory-repo.ts:764` / `palace-repo.ts:444` 的既有降级策略一致。

### 6.4 拼音匹配（`indexer/pinyin.ts`）— P4

Listary 的中文体验里拼音是刚需（实证：`youdao` → 有道云笔记）。两种实现：

| 方案 | 成本 | 效果 |
| --- | --- | --- |
| 新增 `pinyin-pro` 依赖 | 1 个依赖（~300 KB） | 全拼 + 首字母 + 多音字，成熟 |
| 自写首字母映射表 | 一张 2 万字符的映射数据 | 只能做首字母，多音字处理粗糙 |

**决策**：用 `pinyin-pro`。理由——拼音映射表不是"几行代码能做的事"，自写一张全量 CJK 映射表既大又易错；而 `pinyin-pro` 是这类需求的既有成熟解。**但排到 P4**，因为文件名精确匹配（bigram）已覆盖大部分场景，拼音是增益不是地基。

实现：索引时把 `pinyin(name, {pattern:'first', toneType:'none'})` 的结果也写进 `name_tokens` 列尾（或单开 `pinyin_tokens` 列）。查询侧若输入是纯拉丁串，额外拼一个拼音查询分支做 OR。

### 6.5 悬浮窗（`launcher-window.ts`）

复用 `plugins/builtin/pet/pet-window-manager.ts` 与 `builtin/file-preview/preview-window-manager.ts` 的既有模式：

```ts
new BrowserWindow({
  width: 720, height: 480,
  frame: false, transparent: true,
  resizable: false, skipTaskbar: true,
  alwaysOnTop: true, show: false,
  webPreferences: { preload, contextIsolation: true },
})
```

- **唤起时**：`show()` + `center()`（多显示器下取光标所在屏的 `workArea` 居中，与 Listary 的 `LauncherPositionX/Y` 语义一致但更合理）+ `focus()`
- **失焦即隐藏**：`blur` 事件 → `hide()`，符合启动器交互惯例
- **Esc 关闭**、`↑↓` 选择、`Enter` 打开、`Tab`/`→` 展开快捷菜单
- ⚠️ **不要**用 `pet-window-manager` 的 `setIgnoreMouseEvents` ——宠物窗是点击穿透的，启动器窗必须接收鼠标

### 6.6 对话框跳转（`dialog-jump.ts`）— P6

Listary 靠 FlaUI（.NET UIAutomation）实现。我们的**零原生依赖**等价物是 **PowerShell + .NET `UIAutomationClient`**：

```powershell
Add-Type -AssemblyName UIAutomationClient
$root = [System.Windows.Automation.AutomationElement]::RootElement
$fg   = [System.Windows.Automation.AutomationElement]::FocusedElement
# 1. 向上找顶层窗口，判定标题是否为 打开/另存为/Open/Save As
# 2. 在其中找 ControlType=Edit 的文件名框（或 Address bar）
# 3. 聚焦后 SendKeys 目标路径
```

**已知风险（必须实机验证，不可纸上假设）**：

- 常见文件对话框的编辑框**不接受 `SetValue`**，只能聚焦后 `SendKeys`——所以流程是"聚焦 + 打字 + 回车"，而非直接赋值
- 中文路径在 `SendKeys` 下有编码问题，需走剪贴板粘贴（`Ctrl+V`）而非直打
- PowerShell 启动开销约 200–500 ms，每次跳转都要付
- 企业策略可能禁用 UIAutomation

**降级路径（必须有）**：失败时把目标路径复制到剪贴板并提示"已复制路径，请按 Ctrl+V 粘贴"。这比静默失败好。

**排到 P6**：依赖 OLE 对话框内部结构，是四项里最脆弱、最可能随 Windows 更新失效的一项。

| --- | --- | --- | --- |
| `file_search` | `{ query, kind?, limit?, root? }` | ✅ | 检索本机文件、返回路径与元数据 |

| --- | --- | --- | --- |

| R6 | `fs.watch` 在大目录树上句柄耗尽 / 不可靠 | 中 | 限深度订阅；不可靠时回落定时增量重扫 |
| R7 | 悬浮窗抢焦点失败（Listary 日志里有此报错） | 低 | 参照 `ForceForegroundWindow` 的重试/兜底思路 |

**过程中修掉的三处问题**（都记在 §3.3，实现时别再踩）：

1. **算法真错**：`dirty` 只覆盖"两次 Ctrl 之间"，漏掉了 `Ctrl+C` 这种「键夹在 Ctrl 按下与松开之间」的情形 → 改为"一次按住期间无别的键才算有效点击"。
2. **测量被环境噪声污染**：全局钩子收全系统输入，本机其他键盘活动会混入无关按键（实测单场景混入 22 个），导致假失败 → 改为按场景白名单过滤后重放。
3. **重放时钟用错**：同步重放用 `Date.now()` 会让所有事件落在同一毫秒、间隔全变 0 → 改为取事件自带 `time`。

**未覆盖**：

- **杀软拦截**未观察到（本机无拦截），但**换了机器/企业环境仍需复验**——这是钩子类技术的固有风险，不能凭本机一次通过就下结论。
- **UAC 提权窗口、安全桌面**下能否收到事件，未测。
- 键码实测与库常量一致（`Ctrl=29` / `CtrlRight=3613`）；事件**不含 `injected` 字段**。

### 对设计的三处修正

1. **`better-sqlite3` 换成 Electron 内建 `node:sqlite`**（§3.2 已改）。原判断错在两点：误以为 Electron 的
   `node:sqlite` 不带 FTS5；且 `better-sqlite3` 实际未为 Electron 重建（ABI 127 vs 135，`require` 即抛错）。
   **净收益：零新增原生依赖**，省掉 ABI 重建与 asar unpacked 路径处理。
2. **`better-sqlite3` fallback 是死代码** —— `local-database.ts` 里"node:sqlite 不可用才回退"的假设与
   Electron 侧实测相反。**这是既有代码的一处认知偏差**，本期不改动它（超出范围），仅记录。
3. **体积外推作废**，新增 R8 风险项，P1 必须用万级条目重测。

### 未覆盖（留给打包复验与真机验收）

- **杀软 / 企业策略**下钩子是否被拦、**UAC 提权窗口与安全桌面**能否收到事件：本机未复现，换环境必须复验。
