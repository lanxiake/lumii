## 一、这份设计解决什么

当前宠物已经能**看得出 Agent 在干活**（R5/R6 姿态调制 + 气泡通知）、能**自己溜达**（R9 走/坐/站/爬墙），但它仍然是**被动**的：

- 没有**情绪**与**记忆** — 每次重启都忘记你是谁、之前说过什么
- 没有**好感度** — 你点它一百次和点一次，它的反应一样
- **自发行为库太窄** — 只有 4 种（STAND/WALK/SIT/CRAWL），没有"追鼠标、蹭窗口边、打哈欠"
- **不会主动说话** — 除了 Companion 的固定模板（日限额 3 条），从不主动搭话
- **与工作联动浅** — 只有"忙得够久"和"出错了"两条气泡，不记得"这个工具失败三次了"

本设计让它变成**有记忆、有情绪、会主动关心你**的陪伴：

- **B. 情绪与记忆** — 宠物记住你们的对话、有好感度（会涨会跌）、情绪影响表情与行为
- **A. 丰富的自发行为** — 行为库扩充到 15+ 种，决策读情绪（心情好多动、心情差趴着）
- **D. 与工作深度联动** — 记住工具失败次数、连续工作时长，主动提醒
- **C. 主动说话** — 心情驱动（不是随机），有理由才说，先用模板池、LLM 后接

### 1.1 设计原则（继承既有约束）

本设计**不推翻** `2026-09-21-宠物系统需求分析.md` §1.3 Non-Goals 里的三条禁令：

| 禁令 | 本设计的处理 |
|---|---|
| **不表演情绪** | 情绪只影响**举止**（行为频率、姿态调制），不说"我好开心呀~" |
| **不做虚拟养成数值** | 好感度**不显示数字**，用模糊指示（"很喜欢你" / "有点陌生"） |
| **不做关键词模板对话** | 主动说话先用**场景模板池**（按情绪/好感度/上下文选），LLM 生成放第三期 |

**"事后可理解"仍然是基线**（`2026-09-21-精灵宠物自主行为设计.md` §3.1）：宠物说话 / 做动作不是因为掷到了骰子，是因为**你四十分钟没理它且它心情不好**。

### 1.2 与"喂食/饥饿/亲密度"的本质差别

参考项目 `AI-desktop-pets` 的作者**自己实现过情绪/饥饿/能量/亲密度/等级，然后主动删掉了**（提交 `c443605`，需求分析 §3.1）。那套是"虚拟养成游戏"，本设计是"Agent 的有记忆化身"：

| 维度 | 虚拟养成 | 本设计 |
|---|---|---|
| **驱动来源** | 虚拟生理需求（饿了要喂） | 真实 Agent 活动 + 用户交互 |
| **状态持久化** | 数值恒为初值（作者删了） | 对话内容 + 好感度 + 情绪历史 |
| **陪伴目标** | 让用户"养宠物" | 让用户感觉 Agent "记得我" |

**核心判断**：lumii 已有真实 Agent 与对话系统，宠物的价值在**把 Agent 的状态拟人化**，而不是再造一套独立的养成数值。

## 二、四个维度的依赖关系

用户要求"A/B/C/D 都要"（丰富行为 / 情绪记忆 / 主动说话 / 工作联动）。这四条有**严格的依赖顺序**，做反了会返工：

```
B. 情绪 + 好感度 + 记忆（状态层，所有其他维度的数据源）
    ↓
A. 自发行为库（读 B 的状态选行为：心情好多动、好感高主动靠近）
    ↓
D. 工作联动（读 B 的情绪 + 记住失败次数 → 有料可提醒）
    ↓
C. 主动说话（站在 B + D 之上才有料可说，否则是尬聊）
```

**为什么必须 B 打底**：现有自主行为（`ambient.ts`）的权重表是固定的 `{stand: 0.45, walk: 0.35, sit: 0.2}`。如果先做 A（加行为库），那些行为选哪个的依据还是随机数；B 有了之后，同样的行为库就变成"心情差 → 趴着不动"——**同一份动作资产，表现力差一个量级**。

#### 3.1.1 ⚠️ 实测修订：Mood 三维拿不到，宠物窗只有四档

**2026-09-23 核代码发现**：`readMood()` 的签名是 `readMood(db: DatabaseAdapter, now)`，**mood 存在主进程的 SQLite 里**，渲染层拿不到。

而 `apps/windows/src/main/agent-runtime/bridge.ts:2708-2712` 已经在做这件事：

```ts
const mood = decayMood(readMood(this.localDb.db, now), now)
const emotion = moodToPetEmotion(next)   // 三维 → 四档
// 发 autonomous:mood:emotion
```

`moodToPetEmotion`（`mood.ts:101`）把三维**降维成四档**：`joy` / `sadness` / `surprise` / `neutral`。宠物窗（`PetModeShell.tsx:830`）订阅的就是这个降维后的事件。

**后果**：§4.2 设计的 `adjustWeightsByMood(base, mood, affection)` 需要 `energy` / `valence` / `arousal` **三个连续量**，而宠物窗现在只有**一个四值枚举**。"心情差多趴着"能写，但"心情**有多**差 → 趴多久"写不了，权重表退化成二值判断。

**解决方案（已选：加 IPC 推三维）**：主进程在发 `autonomous:mood:emotion` 的同时，把三维数值一并推给宠物窗。

```ts
// apps/windows/src/main/agent-runtime/bridge.ts ── 扩展既有事件载荷（不新增事件名）
// 现在：{ type: 'autonomous:mood:emotion', emotion: 'joy' }
// 改后：{ type: 'autonomous:mood:emotion', emotion: 'joy',
//         mood: { energy: 0.3, valence: 0.7, arousal: 0.5 } }
```

**为什么扩展而不是新增事件**：两者同源同频（都来自那一次 `readMood`），分成两个事件会让"表情"与"权重"可能读到不同时刻的 mood。载荷里带上三维，消费者各取所需。

**兼容性**：`mood` 字段可选，旧消费者（只读 `emotion`）不受影响。

#### 3.1.2 ⚠️ 实测修订：`emotionMap` 全是空的，表情链路接上也无效

**2026-09-23 实测**：仓库里七个模型的 `emotionMap` **全部是空对象 `{}`**。

```
$ grep -rho '"emotionMap"[^}]*}' --include=registry.json --include=pet.json .
"emotionMap": {}
"emotionMap": {}
...（7 个全是空）
```

`resolveExpressionIndex(emotion, emotionMap, defaultExpression = 0)` 在空表上**永远返回 0**。所以：

> **`STATE_EXPRESSION` 不是"写好了没接线"，是"接线也没效果"。**

这解释了创作平台设计 §2.3 把它标为"零消费者"却一直没人接——接了没有可见变化，自然没人有动力。

**根因**：这正是需求分析 §五 **决策 D3「⚠️ 前提已失效，待重决」**。示范模型**没有可用的表情层**（出图 19 次全未过残差阈值），三条出路（改判据 / 改出图策略 / 承认没表情层）**一条都没选**。

**本设计的处理（第一期不碰表情）**：

| 层 | 第一期 | 理由 |
|---|---|---|
| **L1 姿态调制** | ✅ 做 | 不依赖 `emotionMap`（`agent-activity-modulation.ts` 直接改 transform），已有且有效 |
| **L2 表情切换** | ❌ 不做 | 依赖 `emotionMap`，空表下无效果。**等 D3 重决** |
| **L3 动作组** | ✅ 做 | 走 `motionGroups`，不依赖 `emotionMap`（T1 规则表的 `{type:'motion'}` 动作） |
| **L4 气泡** | ✅ 做 | 纯文本，与表情无关 |

**所以 §4.1 行为库扩充、§5 主动说话、§6 工作联动全部不受影响**——它们走 L1/L3/L4，不碰 L2。

**表情的替代路径**（若 D3 短期不决）：并行会话已落地一半的 **SVG 贴片**（状态可见化设计修正块第 7 条）不依赖图集帧，可以直接在任意模型上叠表情。这条作为 L2 的**备选实现**登记，不在本期范围。

**结论修订**：「情绪 → 表情」这条链路**第一期不通**，改成「情绪 → **姿态调制 + 动作组选择 + 行为权重**」。这三条都不依赖表情层，效果照样能被感知——只是表达从"换脸"变成"改变举止"。

### 3.2 好感度模型

#### 3.2.1 数据结构

```ts
interface PetAffection {
  /** 好感度值 [0, 100]，初始 50（中立） */
  value: number
  /** 上次更新时间戳（用于衰减计算） */
  lastUpdate: number
  /** 今日交互次数（用于防刷） */
  todayInteractions: number
  /** 今日日期（用于重置计数） */
  today: string  // YYYY-MM-DD
}
```

**不显示数字**（用户决策 2-B）：UI 上只显示模糊指示，但内部是精确数值以便计算。

#### 3.2.2 加减规则表

| 事件 | 变化 | 条件 / 备注 |
|---|---|---|
| **点击宠物** | +2 | 单日上限 +20（防刷：点 100 次也只算 10 次） |
| **拖拽宠物** | +1 | 单日上限 +10 |
| **发起对话** | +5 | 每次对话（不限轮数） |
| **对话超过 5 轮** | +3 | 额外奖励（说明用户真的在聊，不是试探） |
| **语音通话** | +8 | 比文字对话权重高（语音更亲密） |
| **24 小时未交互** | -10 | 每日结算一次（宠物会"想你"） |
| **72 小时未交互** | -30 | 额外惩罚（"被冷落"） |
| **连续 7 天每天交互** | +15 | 陪伴奖励 |

**衰减曲线**：自然衰减（非惩罚）按 `value * 0.98` 每 24 小时，半衰期约 35 天。高好感度不会"一劳永逸"，需要持续陪伴维持。

#### 3.2.3 好感度的影响

好感度**不直接改变宠物能力**（不解锁新动作 / 不提升"智商"），只影响**行为倾向**：

| 好感度区间 | 模糊指示（UI） | 行为影响 |
|---|---|---|
| 0–20 | "还不太熟" | 待机多、少走动、姿态调制偏低落、主动说话概率 ×0.3 |
| 21–40 | "有点陌生" | 待机多、主动说话概率 ×0.6 |
| 41–60 | "挺喜欢你的" | 正常（当前默认行为） |
| 61–80 | "很喜欢你" | 走动多、装饰性待机动作频率 ×1.5、主动说话概率 ×1.5 |
| 81–100 | "超级喜欢你" | 走动多、主动靠近鼠标、主动说话概率 ×2、长时间未交互主动提醒间隔减半（4h → 2h） |

**"主动靠近鼠标"**（好感 80+ 新行为）：`locomotion.ts` 加一条目标导航逻辑，检测鼠标位置 → 如果距离 > 200px 且宠物在 `walk` 活动 → 朝鼠标方向走（不是瞬移，是把下一次折返的目标点设为鼠标附近）。

### 3.3 记忆系统

#### 3.3.1 记什么（用户决策 1-C：内容记忆）

宠物记住**对话内容**（不只是行为统计）。三类记忆：

| 类型 | 内容 | 示例 | 用途 |
|---|---|---|---|
| **对话事实** | 用户说过的关键信息 | "我在学 Rust" / "我最近在重构前端" | 主动说话时引用（"你的 Rust 学得怎么样了"） |
| **偏好记录** | 用户的习惯与喜好 | "喜欢用 TypeScript" / "讨厌写测试" | 调整表达措辞 |
| **互动历史** | 重要的对话时刻 | "2026-09-20 我们聊了两小时关于宠物设计" | 长期陪伴感（"还记得我们上周聊的那个设计吗"） |

**隐私边界**（用户决策：不告知，默默记录）：
- 记忆**只在本地**（`~/.lumii/data/` 或 MemPalace 存储）
- 不上传、不同步到云端
- 用户可以在设置里"清空宠物记忆"（一键删除，不可恢复）

#### 3.3.2 记忆归属与 drawer

宠物的记忆**不归属于任何现有 Agent**（不是 `assistant`、不是 `code-dev`），需要新增一个定义 id：

```ts
const PET_AGENT_ID = 'pet-companion'  // 独立身份，与 assistant 平级
```

**为什么不能混在 `assistant` 里**：
- `assistant` 的记忆是"帮你完成任务"的上下文（代码、文件、工具调用）
- 宠物的记忆是"认识你"的上下文（你说过什么、你喜欢什么）
- 混在一起会污染 `assistant` 的检索（搜代码问题时翻出"你喜欢猫"）

**drawer 结构**（复用 MemPalace 的 palace 机制）：

```
~/.lumii/memory/pet-companion/
├── conversations/          # 对话事实（按日期分 drawer）
│   ├── 2026-09-23.json
│   └── 2026-09-24.json
├── preferences/            # 偏好（长期保留）
│   └── coding-habits.json
└── milestones/             # 重要时刻（手动或自动标记）
    └── highlights.json
```

#### 3.3.3 记忆的写入时机

| 时机 | 触发条件 | 写什么 |
|---|---|---|
| **对话结束** | `agent:turn:end` 且回复轮数 ≥ 3 | 提取关键信息（主题、关键词、情绪） |
| **明确陈述** | 用户说"我喜欢..." / "我在做..." / "我讨厌..." | 立即写入 preferences |
| **长对话** | 单次对话超过 10 轮 | 标记为 milestone（重要时刻） |

**提取逻辑**（两条路，按成本递增）：

**路线 A（第一期）**：规则提取（零 token）
- 正则匹配关键句式：`/我(?:正在|在|想要|喜欢|讨厌)(.+)/`
- 提取实体：技术栈（Rust/TypeScript/...）、项目名、时间
- 记录原文 + 时间戳 + 会话 ID

**路线 B（第二/三期）**：LLM 提取（有 token 成本）
- 对话结束后调用一次 LLM："从这段对话中提取 3 个关键事实"
- prompt 模板：`这是用户与 AI 助手的对话。请提取用户透露的关键信息（正在做什么、学什么、喜欢什么），每条不超过 15 字。`
- 写入时带上 LLM 提取的摘要

**第一期用 A，第二期升级 B**（避免一开始就烧 token）。

#### 3.3.4 记忆的检索与引用

**检索时机**：
- 宠物准备主动说话时（§五.3）
- 用户发起对话时（注入到 Agent 上下文，见 §3.3.5）

**检索策略**（复用 MemPalace 的检索能力）：
```ts
const memories = await memoryManager.search({
  agentId: 'pet-companion',
  query: '用户最近在学什么',  // 或当前对话主题
  limit: 3,
  drawerFilter: ['conversations', 'preferences']
})
```

**引用示例**（主动说话模板，见 §五.3.2）：
- 检索到"用户在学 Rust" → 气泡："你的 Rust 学得怎么样了？"
- 检索到"用户讨厌写测试" + 当前 Agent 在跑测试 → 气泡："又要写测试了，加油~"

#### 3.3.5 记忆注入到对话上下文

**现有机制**：`PetModeShell.tsx:1011-1058` 的 `handleSendText` 已经激活虚拟人上下文（persona 注入）。

**扩展**：在发送消息前，检索宠物记忆 → 注入到 Agent prompt：

```ts
const memories = await memoryManager.search({
  agentId: 'pet-companion',
  query: text,  // 用户刚发的消息
  limit: 5
})

const contextPrefix = memories.length > 0
  ? `[宠物记忆] 你记得用户：\n${memories.map(m => `- ${m.content}`).join('\n')}\n\n`
  : ''

await agentRuntime.sendMessage(contextPrefix + text, { sessionKey, agentId })
```

**克制**：只在**用户主动发起对话**时注入，不在 Agent 自己的工具调用/思考里塞记忆（那会污染推理）。

```ts
  base: AmbientConfig,
  mood: { energy: number; valence: number; arousal: number },
  affection: number

  const energyFactor = 0.5 + mood.energy * 0.5  // [0.5, 1.0]
  const valenceFactor = 0.7 + mood.valence * 0.3  // [0.4, 1.0]
  const affectionFactor = 0.5 + (affection / 100) * 0.5  // [0.5, 1.0]
  
  return {
    activities: {
      stand: {
        ...base.activities.stand,
        weight: base.activities.stand.weight * (2 - energyFactor)  // 没精神多站着
      },
      walk: {
        ...base.activities.walk,
```

```ts
export function matchRules(
  trigger: InteractionTrigger,
  rules: PetInteractionRule[],
  context: InteractionContext
): InteractionAction[] {
  return rules
    .filter(rule => matchTrigger(rule.on, trigger))
    .filter(rule => !rule.when || matchCondition(rule.when, context))
    .flatMap(rule => rule.do)
}

function matchCondition(cond: InteractionCondition, ctx: InteractionContext): boolean {
  if (cond.activity && ctx.activity !== cond.activity) return false
  if (cond.affection !== undefined) {
    if (typeof cond.affection === 'number') {
      if (ctx.affection !== cond.affection) return false
    } else {
      if (cond.affection.$gt !== undefined && ctx.affection <= cond.affection.$gt) return false
      if (cond.affection.$lt !== undefined && ctx.affection >= cond.affection.$lt) return false
    }
  }
  // ... 其余条件
  return true
}
```

```ts
  type: 'long-absence' | 'mood-drop' | 'work-too-long' | 'tool-failure' | 'good-mood-share'
  reason: string  // 用于去重与日志
  priority: number  // 0–10，高优先级可打破频率限制
}

function checkOutreachTriggers(ctx: {
  affection: number
  mood: Mood
  lastInteractionMs: number
  continuousWorkMs: number
  recentToolFailures: number
}): OutreachTrigger | null {
  const idleHours = (Date.now() - ctx.lastInteractionMs) / 3600000
  
  // 长时间未交互 + 好感高
  if (idleHours >= 4 && ctx.affection > 60) {
    return { type: 'long-absence', reason: '好久不见', priority: 5 }
  }
  
  // 心情骤降（valence 下降 > 0.3 in 1h）
  if (ctx.mood.valenceDelta < -0.3) {
    return { type: 'mood-drop', reason: '你好像不太开心', priority: 7 }
  }
  
  // 连续工作 > 2 小时

  if (ctx.recentToolFailures >= 3) {
    return { type: 'tool-failure', reason: '这个工具好像卡住了', priority: 9 }
  }
  
  // 好心情 + 高好感度（分享喜悦）
  if (ctx.mood.valence > 0.5 && ctx.affection > 80 && idleHours >= 1) {
    return { type: 'good-mood-share', reason: '今天心情不错', priority: 3 }
  }
  
  return null
}
```

```ts
export interface ContextFatigueState {
  level: 'fresh' | 'tired' | 'exhausted'  // 三档
  usagePercent: number  // 当前上下文占用百分比
}

export function reduceContextFatigue(
  state: ContextFatigueState,
  event: { type: string; usage?: { used: number; limit: number } }
): ContextFatigueState {
  if (event.type !== 'agent:context:usage' || !event.usage) return state
  
  const percent = (event.usage.used / event.usage.limit) * 100
  
  let level: ContextFatigueState['level'] = 'fresh'
  if (percent >= 80) level = 'exhausted'
  else if (percent >= 60) level = 'tired'
  
  return { level, usagePercent: percent }
}
```

**调制映射**（接入 `PetOrchestrator` 的 L1 层）：

⚠️ **不是表情映射**——`emotionMap` 是空表，表情切不了（§3.1.2）。疲惫只走 **L1 姿态调制**，
叠在既有的 `agent-activity-modulation.ts` 之上（那个模块直接改 transform，不依赖表情层）。

| 疲惫档位 | 调制 |
|---|---|
| `fresh` | 无调制 |
| `tired` | 呼吸 ×0.9、浮动 ×0.85 |
| `exhausted` | 呼吸 ×0.8、浮动 ×0.7、倾角 -3°（蔫了） |

**与 activity 调制的叠加顺序**：先算 activity 调制（`thinking`/`working` 那套），再乘疲惫
系数。两者相乘，不互相覆盖——所以"忙得久 **且** 上下文快满了"会比单看任一项更蔫。

**接入**：`PetModeShell.tsx` 订阅 `agent:context:usage` → 推进状态机 → 通知编排器。

### 6.3 工具失败计数器（1 小时实现）

**状态**（持久化到 `pet-mode-store`）：

```ts
interface ToolFailureTracker {
  recentFailures: Array<{
    toolName: string
    timestamp: number
    sessionKey: string
  }>
}
```

**记账逻辑**（`pet-notice-adapter.ts` 扩展）：

```ts
// 订阅 agent:tool:end
if (event.type === 'agent:tool:end' && event.isError) {
  toolFailures.push({
    toolName: event.toolName,
    timestamp: Date.now(),
    sessionKey: event.sessionKey
  })
  
  // 清理 1 小时前的记录
  const oneHourAgo = Date.now() - 3600000
  toolFailures = toolFailures.filter(f => f.timestamp > oneHourAgo)
  
  // 同一工具失败 ≥ 3 次 → 触发主动说话
  const failCount = toolFailures.filter(f => f.toolName === event.toolName).length
  if (failCount >= 3) {
    petBus.emit({
      type: 'outreach:trigger',
      trigger: { type: 'tool-failure', reason: `${event.toolName} 失败 ${failCount} 次`, priority: 9 }
    })
  }
}
```

**气泡文案**（§5.3.1 的模板池已有）："这个工具好像卡住了" / "又失败了…" / "要不要换个方法试试"。

### 6.4 连续工作时长提醒（2 小时实现）

**状态**（内存态，不持久化）：

```ts
interface WorkSessionTracker {
  startTime: number | null  // agent:turn:start 时记录
  continuousMs: number  // 累积时长
  lastBreakTime: number  // 上次中断时间
}
```

**记账逻辑**：

```ts
// agent:turn:start
if (!workSession.startTime) {
  workSession.startTime = Date.now()
}

// agent:idle（空闲 > 5 分钟算中断）
const idleMs = Date.now() - workSession.lastActivityTime
if (idleMs > 300000) {
  workSession.continuousMs = 0
  workSession.startTime = null
}

// 每 30 分钟检查一次
setInterval(() => {
  if (workSession.startTime) {
    workSession.continuousMs = Date.now() - workSession.startTime
    
    if (workSession.continuousMs > 7200000) {  // 2 小时
      petBus.emit({
        type: 'outreach:trigger',
        trigger: { type: 'work-too-long', reason: '连续工作 2 小时', priority: 8 }
      })
    }
  }
}, 1800000)  // 30 分钟检查一次
```

**气泡文案**："休息一下吧" / "要不要喝杯水" / "眼睛累了吧"。
