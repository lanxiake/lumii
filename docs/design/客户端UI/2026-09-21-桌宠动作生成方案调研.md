## 一、问题：三个症状，一个根因

| 症状 | 表面原因 | 调研后的实际根因 |
| --- | --- | --- |
| 帧不够连续、没有动作关键帧 | prompt 写得不够细 | **路线错**：让模型独立画多张姿态，每帧都会"失忆" |
| 生成的图片大小不一样 | 模型没听话 | 同上 + 缺帧间 scale/baseline 跳变的 QA 门 |
| 动画和表情确实没有 | 素材没做 | **不是**。实测（见 §一·补）后修正：眨眼、表情、呼吸的代码链路全部是通的，断的是**清单缺 `hitAreas`** 与**两只角色没有面部层** |

第一条是三个独立项目各自撞墙后得出的同一个结论，**不是参数问题**：

- `zhongpei/mypet`：「图生视频的帧共享时序 latent，腿部交替是真运动且身份天然稳定——
  **这是独立生成多张关键帧拼接（永远对不齐）做不到的**」
- `pixel-sprite-animator` 作者：最早也用 AI 生成多张 walk pose，结果角色**每帧"失忆"**，
  帽子、身份、pose 都漂，**最后改成绑定骨骼**
- `mypet` 据此给出的行动建议：「**不要再花大量时间修 multi-image generation consistency**，
  视频模型已经天然解决了大部分 temporal consistency」

**推断**：这条结论解释了此前「挥手为什么没被参考图压住」的追问——
参考图能压住**身份**，压不住**帧与帧之间的运动连续性**，后者不是同一个问题。

### 补：关于「动画和表情确实没有」——实测修正

本节最初把这条归因成「待机只有 4 帧、放不下眨眼」。**查代码与日志后推翻了这个归因**：

| 我原以为 | 实际（实测） |
| --- | --- |
| 待机没有眨眼，因为 4 帧不够 | **眨眼根本不用帧**。`procedural-motion.ts` 有 `BlinkScheduler`（带抖动的确定性间隔 + 120ms 闭眼时长），渲染器按 `anim.params.blink` 建调度器，闭眼时把表情层临时换成 `eye_shut`（`SpritePetRenderer.ts:452`）。清单里 `blink: 3200` 已声明，链路是通的 |
| 表情没有，因为没出表情图 | 图纸出了、`emotionMap` 也配了（樱桃 21 键 → 索引 0..3，正好对上 4 个眼睛部件）。日志里有 `[setExpression] index=0 → eye_open`——**链路通，只是永远停在 0** |
| 动画没播 | 日志里有 `[playMotion] group="Idle" index=0 帧数=4` + `bob: 9`（屏幕像素）+ `breathe: 1.01`。待机是**在动的** |

真正的断点是两个，都很具体：

1. **清单缺 `hitAreas`**（三只全缺）。渲染器的 `hitTestPolygons` 在 `hitAreas` 为空时恒返回
   null，而注册表的 `tapMotions` 按 `HitAreaHead` / `HitAreaBody` 索引——**两边对不上，
   点击一路静默走到 return**。表现是：**`Wave` 是唯一的非待机动作，而它一直播不出来**。
   查遍当天的日志，一次 `[playMotion] group="Wave"` 都没有。
2. **`cartoon_cat` / `mecha_gundam` 没有面部层**（清单里连 `slots` 都没有）。
   嘴和眼都烘在整帧里，所以这两只**永远不会眨眼、也不会有表情**——`emotionMap` 里
   只有 `neutral: 0` 一个键，是如实反映了这一点，不是配置缺失。

> 结论：**「加帧」不是这两条的解法。** 第 1 条是补一个字段，第 2 条要重新出图。

## 二、结论速览

1. **「视频模型当演员」是公认答案**，但 Lumii 当前无此能力（§六）。
2. **确定性程序化微动画（我们已有的 `procedural-motion.ts`）只够 T1 微动作**
   （呼吸/眨眼/摆尾）。mypet 对 PocketMen 的裁定原话是「**只留 T1**」。
   原因是 `Motion(dx/dy/sx/sy/angle/flip)` 只有 4 个自由度，**造不出一只抬起来的手**。
3. **动作数量应靠"派生"而不是靠"生图"扩**：镜像 / 速度变体 / 情绪贴片，
   20 组生成 → 100 个动作。我们目前**一样都没做**。
4. **有一批零新依赖、不依赖出图质量的活可以先干**（§七 第一批），
   直接命中「动画和表情确实没有」。

## 四、五条路线对比与裁定

| 路线 | 代表 | 能做什么 | 代价 | 裁定 |
| --- | --- | --- | --- | --- |
| **A. 视频当演员** | WAN 2.2 i2v / MiniMax H3 / Wan2.2-Animate | 走/跑/挥手等真实肢体运动，时序天然连贯 | 本地 24G 显存 + ~80G 权重（`comfyui-2d-character-pipeline` 实测 RTX 3090 峰值 22.5G）；或云端 API | **公认最优，Lumii 暂无此能力**。本期不做 |
| **B. 确定性微动画** | PocketMen `Motion`、我们已有 `procedural-motion.ts` | 呼吸/眨眼/摆尾；数学上绝对平滑、零出图 | 4 个自由度（位移/缩放/旋转/翻转） | **只用于 T1**。定位是「让待机活起来」，不是补挥手 |
| **C. 网格形变** | Inochi2D / Live2D | 真点头、转头、身体扭转 | 绑定工具链 + D 运行时/C FFI | 重。mypet 的明确裁定：「自己做骨架+ControlNet → **不做，复杂化了**」 |
| **D. 动作族派生** | mypet / PocketMen / DeskPet | 20 组生成 → 100 个动作 | **零出图** | **性价比最高，我们完全没做** |
| **E. 后处理插帧** | RIFE | 补帧间连续性 | 额外依赖 | 治标，且掩盖不了姿态本身画错 |

## 五、六个可直接借鉴的技术

### 5.1 逐格关键帧标注（最该先试）

`sprite-animator` 的做法和我们的**正好相反**。

- **我们**：把动作过程写成 prompt 里的一段散文，并且明确
  `FORBIDDEN: 图中任何位置都不得出现文字、数字、字母、标点、编号、标签…`
- **它**：把每格是什么姿态**画进模板图**，连图一起送进去（`template.py:7-54`：
  灰底 `(200,200,200)`、网格线 `(100,100,100)` 宽 3、每格正中央写标签文字）

```python
labels = [
    "1:stand",  "2:arm↑¼",  "3:arm↑½",  "4:arm↑¾",
    "5:arm up", "6:wave R", "7:wave L", "8:wave R",
    "9:wave L", "10:wave R","11:arm↓¾","12:arm↓½",
    "13:arm↓¼", "14:stand", "15:smile", "16:stand",
]
```

模型看到的是**空间锚定**的「第 5 格是 arm up、第 6 格是 wave R」，
而不是一段要自己切分的文字。

**它的 idle 标签更值得看**——16 格 = 呼吸 8 格 + 眨眼 8 格，两条微动作交织：

```text
Row1: stand, breathe↑, breathe↑↑, breathe↑
Row2: stand, blink¼,   blink½,    blink¾
Row3: eyes shut, blink¾, blink½, blink¼
Row4: stand, breathe↓, breathe↓↓, breathe↓
```

**注意它和我们的架构差别**：它把呼吸与眨眼都烘进帧里，所以需要 16 格；
我们的眨眼是**图层切换**（`eye_shut` + 调度器），不占帧；呼吸是**程序化缩放**，也不占帧。
它的 16 格对我们没有直接的参照意义——我们要不要加帧，只取决于**动作本身够不够顺**。

> ⚠️ 与现有 prompt 冲突：我们禁文字是为了怕模型把标签画进成品。
> 这是个**需要实测的取舍**，不预设结论（§七 第二批）。
> 另有一个变体：`hatch-pet` 的做法是附「canonical 母版 + 布局导引图」到**每一行**，
> 但不写文字。两条可对比。

### 5.2 Idle Pin（首末帧都锚回待机）

`sprite_h3` 的招：让**第一帧 = 最后一帧 = canonical idle**，把模型在时间上夹住。
三个好处（`mypet` 原文）：

```text
身份不容易越走越远
动作自然回到 neutral
不同动画可以直接连续切换
```

MiniMax H3 官方工作流原生支持 `first_frame` / `last_frame`，**不是 hack**。
`sprite-animator` 的 wave 也是这个形状：`14:stand, 15:smile, 16:stand`。

我们现在的 prompt 里写了「最末一格要能无缝接回最初一格」，
但**没有强制它必须是待机姿态**。

### 5.3 动作族派生（零出图扩动作数）

mypet 的路线：**真正 AI 生成的动作族控制在 ~20 组，其余靠派生**。三种派生：

| 派生方式 | 做法 | 我们的现状 |
| --- | --- | --- |
| **左右镜像** | `walk_left ← walk_right`；DeskPet 更省——**只画朝右，运行时自动镜像** | **已完成**（渲染层 `setFlip`，见 §七·补五 的修订说明） |
| **速度变体** | 调帧时长 | **刚做完**（`durationMs`），一个动作可出「慢悠悠/活泼」两版 |
| **情绪变体** | 见 5.4 | 未做 |

### 5.4 情绪贴片：程序化叠加，不单独生图

mypet 明确：情绪修饰（blush / 泪滴 / 怒符 / 汗滴）**用小贴片程序化叠加，不单独生图**。

对我们的意义：现在是 `drive-gen.mjs --expression` **单独出一批表情图集、还要带参考图**。
而**贴片与动作正交**——任何动作都能配任何表情，N 个动作 × M 个表情不必 N×M 张图。

**推断**：我们的 manifest 已有图层系统（`kind:'layered'` + `parts`），贴片天然就是一个 layer。

### 5.5 PocketMen 的 QA 指标

`validate_atlas` 里这几项直接对应我们踩过的坑：

| 指标 | 治什么 |
| --- | --- |
| 帧间 **baseline 跳变** | 脚底基线在帧之间跳 |
| **scale 跳变** | 「生成的图片大小似乎也不一样」 |
| 空帧、alpha 残留 | 抠底失败 |
| 调色板漂移、与 canonical 的直方图相似度 | 廉价的身份检查 |
| **与 canonical 的姿态差异度** | 检测「所有动作塌回站姿」 |

最后一项配 story-ai 的教训（被 mypet 引用）：
「编译顺序把**动作主体锚点放最前**、构图原型显式变化、禁止项明确
（**禁止默认站姿/禁止对称站立体态**）」。

### 5.6 累积运动弧长抽帧（有视频之后才用得上）

**不要按固定间隔抽帧**，按累计视觉变化量均匀取样：

```text
frame:  0  1  2  3  4  5  6  7
motion: 0 .1 .2 .3  3  5  8  1
```

一个 90 帧的 H3 clip 最终只留 8~12 帧精灵图。`ai-game-spritesheets` 实测也是选 8–12 帧。

**认知**：视频不是最终素材，是「**高质量运动采样器**」。桌宠按 8fps 播 6~12 个关键帧就够看。

### 补：已完成项与实测到的硬约束

**#1 补 `hitAreas`** —— 落在 `packages/pet-asset/src/hit-areas.ts`（纯几何）+ 工具链 op
`hitAreas`，由 `pet-creator/run.ts` 与 `compose-review.mjs` 在打包时调用。
三只示范宠物的清单已补上（**图集一个字节没动**，只有 `manifest.json` 变化）。

**加帧的像素预算（实测，别凭感觉定格数）**：

| 项 | 实测值 |
| --- | --- |
| `image_generate` 的宽高上限 | **只支持 1024 或 1536**（`image-generate-tool.ts:61`），我们一直用 1024 |
| 实际拿到的图 | **1254×1254**（请求 1024，provider 返回 1254） |
| 待机（4×1）的格 | 313×1254，角色占 270×1020（宽 86%、高 81%） |
| 角色长宽比 | **3.7**（日式动画全身站姿），而画布 384×448 的长宽比是 1.17 |
| ⇒ 后果 | 归一化后**角色只占画布 28% 的宽度**——画布有 72% 的宽度是空的 |

由此推出的格数上限：**横条最多 8 格**（8×1 时每格 157 宽，角色约 140×520，归一化到
448 是 0.86× 降采样，安全）；**16 格必须走 8×2**（每格 157×627 恰好容纳 3.7 长宽比的角色）。
16×1 会让每格只剩 78 宽，角色降到 250 高再放大到 448 —— **1.8 倍放大，就是马赛克**。

> **顺带记一条**：1254 不能被 4 整除（1254/4 = 313.5），`slice` 会取整。
> 四列以上时格线有半像素错位，`sheetCheck` 会因此报 `divisible: false`。

### 补二：Idle Pin（#2 已完成）

**落地方式与 §5.2 的原文不同——按名引用，不是让模型重画。**

先量了前提（樱桃的待机帧 vs 挥手帧，降采样到 24×24 再比，滤掉 1px 边缘位移）：

| 帧 | 粗差 | 轮廓包围盒 | 重心 x |
| --- | --- | --- | --- |
| 待机四帧 | 0 / 16.3 / 2.1 / 11.8 | 106–111 × 404–421 | 191.0–191.4 |
| 挥手四帧 | 27.0 / 41.5 / 23.7 / 24.4 | **128–169** × 413–421 | **196.4–210.9** |

待机的重心稳在 x≈191、包围盒 106–111 宽；挥手的包围盒 128→169、重心右移 5–20px。
**挥手首帧不是待机姿态**，两头都会跳。

而「让模型把待机站姿也画进第一格」解决不了：生成模型重画同一个姿势**必然有漂移**，
端点只是"看起来差不多"，接上去仍会顿。真正无缝的唯一办法是端点**就是同一张图**。

所以做法是：**图集里本来就有待机帧，让一次性动作的首末两格引用它**。

| 位置 | 内容 |
| --- | --- |
| `packages/pet-core/src/model/idle-pin.ts` | `pinIdleFrames`（前后各插一格待机首帧，深拷贝）+ `checkIdlePin`（自检）。16 条单测 |
| `pet-asset-ipc.ts` | 新 op `idlePin`（纯计算、不碰盘，同 `sheetPlan` 的定位） |
| `pet-creator/run.ts` | 批次带 `idlePin: true` 时调用。**推不出来只报警告**——推荐级字段不该否决整次构建 |
| `sheet-prompt.ts` | 新增 `loopMode: 'cycle' \| 'idle_pin'`，两种模式对首末格的要求**正好相反**，不能共用一句话 |

产出（`demo_anime_girl`）：

```text
Idle  loop  4 帧: body_00(420) → body_01(200) → body_02(420) → body_03(200)
Wave  once  6 帧: body_00(300) → wave_00 → wave_01 → wave_02 → wave_03 → body_00(240)
                  ^^^^^^^^^^ 与 Idle 首帧是**同一个图集条目**          ^^^^^^^^^^
```

代价是零：图集一个字节没变（新增的两格引用已有条目），生成的四格**全部**用在动作经过上。

首末格的时长沿用被锚定动作自己的首末格（300 / 240），**不搬待机帧的 420**——
那是待机循环的节奏，放进一次性动作里没有意义。

#### 五处「按实测改了说法」

**① 帧数不能只按「这一行有几格有内容」数。**
`shimeji_nekojapan.png` 第 0 行有 **9 格**，但 9 格包围盒全等（45×36）、两两姿态差异 **0.0**
——那是**把同一帧复制填满了整行**。按内容数会得出「待机 9 帧」，而声明值是 1。
现在以声明值为准、内容只做交叉校验：少了报缺帧，多了当填充丢掉。

**② `poseMin` 不能用来判塌缩——被 Idle Pin 自己破坏了。**
最初想用「两两差异的最小值」当判据（两帧一样就是塌缩）。但 **Idle Pin 会故意造出一对
完全相同的帧**（一次性动作的首末格都引用待机首帧），于是每个钉过的动作 `poseMin` 恒等于 0，
判据全线误报。**能判别的是 `poseMax`**：「最不像的两帧有多像」才是塌缩该问的问题。

**③ 基线抖不是区分度指标，是回归哨兵。**
实测所有包的地线抖动都在 **0–1px**——因为 `normalize` 与裁剪已经在管地线了。
它量的是**流水线**，不是**素材**。留着当回归哨兵（哪天不是 0 就说明对齐链路坏了），
但拿它判素材好坏是错的方向。同理，`heightSpread` 量的是「这段动作本身跳多高」，也不是质量。

**④ 负对照在对称角色上是空转的。**
`check-mirror.mjs` 的负对照是「换用未镜像的多边形」——覆盖率应当塌掉。
5 只 Shimeji 猫里 4 只塌了（91%→43%、81%→39% 等），但 **`demo_anime_girl`（83.66%→83.57%）
与 `demo_mecha_gundam`（95.84%→95.82%）纹丝不动**——因为这两个角色的剪影**本身就近似左右对称**，
翻不翻都一样。**负对照不塌不是「通过」，是「这个模型上这条检查证明不了任何事」。**

**⑤ 命中区的「过盖」从没量过，量出来不小。**
§七 #1 的判据里写着「多边形不盖住角色旁边的透明区」，当时只做了目视。
新增的量法：**多边形盖住的像素里有多少是透明区**（那些空白会吃掉鼠标、让窗口无法穿透）。
实测 `demo_mecha_gundam` **34.5%**、`demo_anime_girl` 28.9%、`demo_shimeji_nekojapan` 26.5%。

> （`setFlip`，落在 `root.scale.x` 取负上）。
>
> 之前那次搜索得出的"没有翻转能力"是**事实描述**而非限制——漏掉的是**锚点校正与缩放符号无关**：
> sprite 的世界坐标是 `root.position + root.scale × (pivot.position + local)`，要让 `local = anchorX`
> 落在 root 原点上，条件是 `scale.x × (pivot.x + anchorX) = 0`，**与 `scale.x` 的符号无关**。
> 所以翻转不必动 `pivot`，一行就够，「图集翻倍」这个代价根本不必要。
>
> 教训不是"当初搜错了"，而是**"某处没有某个能力"不能直接推出"必须换条路"**——
> 还要问一句"缺的是能力，还是只是没人写"。
>
> `check-mirror.mjs` 仍然留着：它验的几何关系（镜像后命中多边形要跟着翻）没变，
> 那套判据现在由 `hit-polygon.test.ts` 的 `flipX` 用例继续守着。

**#5 + #7** —— `qa-animation.mjs --calibrate` 在 19 条多帧动作上定出阈值：

```text
姿态最大 poseMax   min=0.52  p50=8.15  p90=24.95  max=46.20   ← 判据用这条
```

阈值取 **2.0**：真人画的走路循环落在 2.5–7.6 全部通过；而
**`demo_mecha_gundam` 的 Idle/Talk 只有 0.7、`demo_cartoon_cat` 的 Idle 只有 2.4（勉强过线）**
——AI 直出的待机**实质上是静止帧**。这是第一次用数字说出「那只宠物待机时不怎么动」。

**#3 情绪贴片** —— 落点比预想的干净：**装进「表情槽」就不用改渲染器**。
槽位绑定只认名字在白名单 `['eyes','eye','expression','face']` 里的类别，
把贴片槽的类别命名成 `face`，现有的 `emotionMap → setExpression` 那条路**直接就通**。
贴片全部是 SVG 画的几何图形（腮红/星星/汗滴/怒气/爱心），**零生成**；
位置从 `HitAreaHead` 的包围盒按比例推，换宠物不用改一行。
实测 5 个贴片 100% 落在头框内、`face_none` 改动 0 像素（恒等元正确）。

**仍未验的一步**：贴片在真机上到底切没切到那一档，要看客户端日志里有没有
`[SpritePetRenderer] [setExpression] index=N → face_xxx`。离线脚本验不了这条。

**#6 加帧** —— 素材侧的问题被绕开了：Shimeji 的 GREET 本来就是 **8 帧**，
Idle Pin 之后是 10 帧（`stand → greet×8 → stand`），比之前 AI 直出的 4 格挥手强一个量级。
**「多少帧才够」第一次有了参照物**：真人画的走路循环用 4 帧，打招呼用 8 帧。

### 补六：出图预览页——把三层摆到一页上（2026-09-21）

`make-viewer.mjs`（补三）只读**打包产物**，于是"AI 出的那张网格图到底长什么样"始终
没有落点：格子画歪了、串格了、背景没抠净，到了图集里都已经成了事实。

新增 `verify/pet-sprite/review/index.html`（**手写**）+ `characters/make-preview.mjs`
（出数据与素材）。左栏是**原始出图**（网格 + 格子高亮 + 悬停报帧名），右栏是**合成播放**
（变换与 `SpritePetRenderer.applyProcedural` 逐行对应：锚点、缩放、旋转、程序化原语、眨眼），
底栏是**关键帧条**（逐帧缩略图 + 时长 + Δ脚底）。播放速度 0.1×~4×，
空格播放/暂停、←/→ 逐帧、点原图格子跳到对应帧。八只模型（AI 三只 + Shimeji 五只）都在里面。

**数据与页面分家是有意的**：`make-viewer.mjs` 把整页塞进模板字符串，注释里一个反引号
就把字符串截断，`node` 只抛语法错、产物不更新，而校验脚本照样把**上一次的旧页面**
验通过。手写的页面在编辑器里就能看见语法错。

`check-preview.mjs` 走 **`file://`**（用户就是双击打开的，不加
`--allow-file-access-from-files`——加了验的是另一回事），验二十余项。
像素级断言绕开 canvas 跨源污染，走「元素截图 → sharp 读像素」。
页面自己不 `getImageData`，所有量化信息都是生成脚本用 sharp 预算好的。

#### 三条新判据

| 判据 | 量什么 | 怎么算 |
| --- | --- | --- |
| **Δ脚底** | 内容底边相对锚点线的偏差 | 逐帧包围盒的 `y1 − anchor[1]`。**同组各帧互相比**才有意义，单看一帧的绝对值没有 |
| **孤儿格** | 画了东西却没被任何动作引用 | 内容占比 > 2%，且没有任何帧名指向它 |
| **重复帧** | 不同名却逐像素相同的帧 | 排除同名引用（Idle Pin 是有意为之）后逐字节比对 |

内容占比按图源分两路：有 alpha 的（Shimeji 表）看 alpha；没有的（AI 直出是纯色背景、
RGB 三通道）拿**背景色距离**判——色号是 `plans.json` 里声明过的，阈值取 90，
远低于它对角色颜色算出的 `minDistance`（实测 234）。

#### 实测：真人素材也有大量重复帧

第一次跑就抓到三条，**都不是我们这边的问题**：

1. **`demo_shimeji_nekojapan` 的 Walk 第 0 格与第 2 格逐字节相同**。回原表验过：
   **在原表里就已经相同**，不是切图切错。五只猫**全部**如此（同一位画师、同源素材）。
   4 帧其实只有 3 个姿势。
2. **Climb 与 Crawl 各 8 格，各自只有 3 个不同画面**（`{0,1,7} {2,6} {3,4,5}`），
   五只一致。两行的重复模式相同，但整行像素不同。
3. **`demo_cartoon_cat` / `demo_mecha_gundam` 的表情批 4 格画满了，0 格被引用**——
   图出了、格切了，manifest 里却一个 face 槽都没有。

放在一起看，反倒给"AI 出的 4 帧待机"平了反：那 4 帧**没有重复**，
`poseMax` 低是因为动作幅度小（见 §5.5），不是帧重复。

**"多少帧才够"要改成"多少个不同画面"来问**——补五里"打招呼 8 帧"那条参照物，
在攀爬那两行上得打对折。

#### 未落地

`import-shimeji.mjs` **不报**重复帧，这条判据现在只在预览页上看得到，导入时是静默的。
要不要把它变成导入报告的一部分，待定。
