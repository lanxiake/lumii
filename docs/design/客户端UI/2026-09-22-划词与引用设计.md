## 一、背景与定位

豆包 PC 端的「划词」实际是两层能力，成本差一个数量级：

| | 应用内划词 | 系统级划词 |
|---|---|---|
| 场景 | 在自家界面里选中文字 | 在**任意应用**（Word、网页、微信）里选中文字 |
| 取词 | DOM 选区 | 全局鼠标钩子 + 模拟 Ctrl+C，或 UIA |
| 浮出 | 选区附近小工具条 | 全屏透明置顶悬浮窗 |
| 典型动作 | 复制 / 翻译 / 解释 / 总结 / 朗读 | 「问豆包」把文本带进去 |

**本期只做应用内。** 依据：Lumii 里值得划词的文本密度极高（聊天回答、Wiki、技能文档、记忆、文件预览），这些全是 DOM，零延迟、零隐私风险；而系统级划词要新增 native 全局输入钩子（仓库当前**没有任何**输入钩子依赖，`uiohook` / `robotjs` / `ffi` 全无命中），还要处理剪贴板保存恢复与密码框黑名单——**它是独立特性，不是应用内版的增量**，后置为独立阶段。

**与豆包的差异在动作集。** 豆包只有「通用 LLM 快捷动作」；Lumii 有 Agent 运行时、技能、记忆、TTS，因此动作分三层（§四），其中**「引用」是一等公民且置于浮条首位**——这是 AI 应用里划词的正解，而不是翻译。

## 四、动作集设计

三层，按「要不要进模型 / 进哪个模型」划分：

| 层 | 动作 | 执行 | 落点 |
|---|---|---|---|
| **L1 本地瞬时** | **引用到输入框**、复制、朗读、存为记忆 | 不进模型 | 即时生效 |
| **L2 直连 LLM 单轮** | 翻译、解释、总结、润色 | 单轮、流式、**不进对话历史** | 就地气泡 |
| **L3 Agent 运行时** | 追问、用技能处理 | 走 `user:send` 完整循环 | 当前会话新消息 |

### 4.1 两个入口的动作分配

- **浮条（4 项）**：`引用` · `翻译` · `解释` · `复制`
  - 「引用」必须第一，且必须在浮条上（最高频）。
  - 只放 4 项是为了不遮挡正文；溢出全部进右键菜单。
- **右键菜单（全量）**：
  ```
  引用到输入框
  复制
  朗读
  ──────────
  翻译 · 解释 · 总结 · 润色
  ──────────
  追问（Agent） · 用技能处理（Agent）
  ──────────
  存为记忆
  ```

两条入口共用同一份动作定义（§5.3），避免两处各写一遍导致行为漂移。

## 五、设计

### 5.1 取词层：快照，不持有活 Range

```
mousedown  ─┐
            ├─ 记录起点，判定是否拖拽
mouseup    ─┘
             └─ 选区非空 且 不在可编辑区内 → 快照 { text, rect, source } → 弹浮条
```

**核心约束：`mouseup` 时立刻快照，之后浮条只依赖快照，不持有活 `Range`。**

理由：`useWindowedRows.ts` 会把离屏行的整棵子树卸载，一旦用户滚动，原有 `Range` 的 `anchorNode` 会脱离文档，`getBoundingClientRect()` 返回全零、`toString()` 返回空。凡是「选完再滚一下」的操作都会命中。

快照形态：

```ts
interface SelectionSnapshot {
  text: string
  /** 来自 range.getBoundingClientRect()，坐标已含滚动偏移；气泡锚点用 */
  rect: { top: number; left: number; width: number; height: number }
  /**
   * 选区**末行**的矩形，浮条锚点用。
   * 多行选区的联合框上沿在第一行、横向铺满整行，浮条贴上去会离指针很远。
   * 取末行时会跳过零面积矩形（选区末尾常带一个换行符产生的零宽矩形，
   * 认了它浮条会飘到下一行行首）。
   */
  anchorRect: { top: number; left: number; width: number; height: number }
  source: {
    kind: 'chat-message' | 'markdown-preview' | 'wiki' | 'skill-doc' | 'memory' | 'plain'
    conversationId?: string
    messageId?: string
    role?: 'user' | 'assistant'
    title?: string
  }
  createdAt: number
}
```

`source` 用于两件事：引用时标注出处；L3 动作路由到正确的会话。

#### 出处（`source`）靠 DOM 标记解析

快照发生在全局的 `SelectionLayer` 里（挂在 `App.tsx`），**拿不到 ChatPage 的 React 上下文**，所以出处只能从 DOM 上读：正文容器根节点挂一组属性，快照时从 `startContainer` 往上 `closest('[data-lumii-source]')`。

```html
<div data-lumii-source="chat-message"
     data-lumii-conversation-id="..."
     data-lumii-message-id="..."
     data-lumii-role="assistant"
     data-lumii-title="...">
```

- `data-lumii-source` 的取值限定在 `SelectionSourceKind` 枚举内，**不认识的值一律降级为 `plain`**（宁可丢出处，不要把野值带进引用）。
- `data-lumii-role` 只认 `user` / `assistant`，别的值当没写。
- 落点：`ChatMessage/index.tsx` 根节点，以及 Wiki / 技能文档 / 记忆页各自的内容容器。**只加属性，不动渲染逻辑**——这是本轮对 Markdown 管线的唯一侵入。
- 未命中标记时 `source.kind = 'plain'`，引用只写文本、不写出处。

### 5.2 触发层

**浮条触发条件**（全部满足才弹）：

1. `mouseup` 且 `!selection.isCollapsed`
2. **选区不在可编辑区内** —— `input` / `textarea` / `[contenteditable]` 一律不弹
3. 当前没有别的浮条/菜单开着

> ⚠️ **「拖拽」不作触发条件（2026-09-22 修订）。** 本节原写作「不是拖拽（`mousedown` → `mouseup` 位移 < 阈值，使双击选词也能触发）才弹」，**该规则是错的**：拖拽选中是最主流的选中方式，照此实现会让最常见操作失效；而且它给的理由本身不成立——双击选词的位移天然接近 0，不需要靠排除拖拽来保住。
>
> 现行规则：**只要 `mouseup` 时选区非空就弹，不论怎么选出来的。** 位移阈值（`DRAG_THRESHOLD_PX = 4`）改作另一个用途——**拖拽过程中提前收起浮条**（见下方防御 4）。

**必须做的四个防御**：

- **保住选区**：浮条自身的 `mousedown` 调 `preventDefault()`。否则点浮条时浏览器会先清空选区，`getSelection().toString()` 变空，动作拿不到文本。
- **主进程退让**：`main-window.ts:239` 那段要改判断——
  ```
  isEditable                     → 原生菜单（保持现状，输入框需要剪切/粘贴）
  非 editable 且有 selectionText  → 不 popup，交给渲染层自绘
  其余                            → 原生菜单（保持现状）
  ```
  不改的话会和自绘菜单叠在一起。
- **滚轮/滚动处理**：滚动时**关闭**浮条（重定位会让浮条在虚拟化列表里乱跳，关闭更符合直觉）。Esc 也关闭。
- **拖拽起手即收起**：指针位移超过 `DRAG_THRESHOLD_PX` 时立刻收起浮条，免得它横在用户正在扩展的选区上。阈值保证普通点击（含双击选词）不会误收。

**浮条的定位**：借用 `Tooltip.computeCoords()` 的算法，但**要补翻转**——选区在视口底部时气泡/浮条要翻到选区上方。这是全仓第一次实现翻转，抽成公共函数以便 `Tooltip` 后续复用。

### 5.3 动作注册表

```ts
interface SelectionAction {
  id: string
  label: string
  icon?: React.ReactNode
  /** 在哪些入口出现 */
  surface: 'bar' | 'menu' | 'both'
  /** bar 上的排序，越小越靠前 */
  barOrder?: number
  /** 执行档位，决定走哪条通道 */
  tier: 'local' | 'single' | 'agent'
  isEnabled?(ctx: SelectionSnapshot): boolean
  run(ctx: SelectionSnapshot, api: SelectionActionApi): void | Promise<void>
}
```

`SelectionActionApi` 提供 `closeBar()` / `closeMenu()` / `showBubble()` / `appendQuote()` / `copy()`。

浮条与右键菜单都从同一份注册表渲染，`surface` 过滤。

### 5.4 就地气泡

**只服务 L2（翻译/解释/总结/润色）。**

- 定位锚点：`SelectionSnapshot.rect`，默认在上方，空间不足翻转到下方。
- 内容：流式文本 + 底部工具条（复制 / 引用结果 / 关闭）。
- 状态：`idle → streaming → done | error`，`error` 要显示可读原因而不是空白。
- **取消**：换选区、关闭、切换会话时 abort 当前请求。**必须实现**，否则并发请求会和「模型端点被多会话共用」的既有问题叠在一起。

### 5.5 引用体系

分两步走，**P0 不动数据模型**。

#### P0 最小形态（纯文本）

引用 = 往 Composer 草稿插入一段 Markdown blockquote 前缀：

```markdown
> {选中文本}
> —— 来自《{会话标题}》
```

- 插入位置：草稿**顶部**（若已有内容则插到最前，不与用户正在写的内容粘连）。
- 插入后光标落到引用块之后，并聚焦输入框。
- 实现落点：`useComposerDraft` 的 `setDraft` **必须配 `flushDraft`**——只调 `setDraft` 只改本地 state，切会话会被 `useLayoutEffect` 用父状态覆盖掉。

零数据模型改动，当天可用。

#### P2 完整形态（结构化引用）

```ts
interface QuoteRef {
  id: string
  text: string
  source: {
    conversationId: string
    messageId?: string
    role?: 'user' | 'assistant'
    title?: string
  }
  createdAt: number
}
```

- **状态**：`quotes: QuoteRef[]` 与会话草稿同生命周期（同样按 `sessionKey` 存取）。
- **UI**：Composer 上方一排引用 chip，可单独删除。
- **发送时必须同时写两处**：
  - `content` 里渲染成可见的 blockquote —— **Agent 只读 content，不写它 Agent 就看不见**；
  - `metadata.quotes` 结构化存 —— **只写 content 则来源丢失**，编辑/重发/回放/渠道出站（飞书、企微、微信）时无法还原。
  
  这两条是一条硬约束，缺任一条都会在后续环节出问题。

### 5.6 执行通道

| 档位 | 通道 |
|---|---|
| `local` | 渲染层直接做（剪贴板、草稿写入）；朗读走既有 `voice:tts:*` |
| `single` | **新增**一条单轮、流式、可取消的 LLM 通道 |
| `agent` | `user:send`（`shared/agent-runtime-commands.ts:36`） |

**`single` 是本期唯一的新 IPC**，候选形态：

```
selection:run    (renderer → main)  { requestId, action, text, locale? }
selection:chunk  (main → renderer)  { requestId, delta }
selection:done   (main → renderer)  { requestId }
selection:error  (main → renderer)  { requestId, message }
selection:abort  (renderer → main)  { requestId }
```

按 `AGENTS.md` §5，**必须三处同步**：main handler → preload `ElectronAPI` 类型与方法 → renderer 调用点。

## 六、边界与明确不做

| 不做 | 理由 |
|---|---|
| **替换原文** | 消息正文是 React 受控渲染的 Markdown（`ChatMessage/index.tsx`，react-markdown + 一整套自定义组件）。DOM 层面替换会被下一次重渲染覆盖；要真做就得改消息存储与编辑链路，成本远超收益。**降级为「复制结果 + 引用原文进输入框」。** |
| 系统级划词 | 需 native 全局输入钩子，独立特性，后置（§一） |
| 在输入框内弹浮条 | 与原生右键菜单职责重叠，且输入框内的复制/粘贴走系统菜单更可靠 |
| 跨行选择时把每行当独立引用 | 一个选区 = 一个引用，不拆分 |
| 划词触发 Agent 的自动执行 | 全部 L3 动作都要用户再确认一次（写进草稿或显式发送），不静默起任务 |

## 七、风险与防御

| # | 风险 | 防御 |
|---|---|---|
| R1 | 虚拟化卸载行导致 `Range` 失效 | §5.1 快照制；**验收必须包含「选完滚动」用例** |
| R2 | 点浮条导致选区丢失 | 浮条 `mousedown` → `preventDefault()` |
| R3 | 与主进程原生右键菜单叠加 | `main-window.ts:239` 按 `isEditable` 退让 |
| R4 | 重蹈 TTS 全局停的坑 | `MessageActions/index.tsx:55-60` 已记录：`voice:tts:stop-preview` **不带 messageId 是全局停**，窗口化让「滚动导致卸载」成为日常路径。选区朗读的停止逻辑必须只停自己发起的那一次 |
| R5 | 气泡贴着视口边缘溢出 | 补翻转（全仓首次）；`VIEWPORT_PAD=8` 与 `Tooltip` 保持一致 |
| R6 | 并发请求打爆模型端点 | 每个 `single` 请求可 abort；同一时刻只允许一个浮条请求在飞 |
| R7 | 硬编码颜色 | 只用 `--mt-*` 令牌。仓库有「主题色系收尾切片」计划与守卫测试，新代码不新增硬编码色 |
| R8 | 引用在渠道出站时格式崩坏 | §5.5 的 content + metadata 双写，且**渠道侧渲染要单独验收** |

## 八、待实测验证的未知项

**不靠推理定，按实测收口。**

1. **`single` 通道走复用还是新开？**
   - 候选 A：参数化复用 `router/llm-caller.ts:31` 的 `RouterLlmCallerImpl`。
   - 候选 B：新开一条独立的 selection LLM 服务，与 router 解耦。
   - **判据**：A 现在**非流式**（累加后返回）、`temperature: 0.1`、`maxTokens: 800`、`purpose` 硬编码 `'skill_route'`。要查清改这些是否会影响语义路由本身，以及 **`purpose: 'skill_route'` 是否被用量统计/日志/计费依赖**——若被依赖，换 purpose 会污染既有统计。
   - 验证方式：两条路各写一个最小探针，实测流式首字延迟、abort 生效性、purpose 改动对统计的影响，再定。
2. **`content-visibility` 对取词的影响。** 虚拟化行带 `content-visibility`，需实测离屏/近屏行的选区行为是否与普通 DOM 一致，以及快照在跨行选择时是否完整。
3. **右键菜单退让后的回归面。** `main-window.ts` 那段是**全局**的（覆盖文件预览、聊天记录、输入框）。退让后要逐区域验收：文件预览、Wiki、技能文档右键是否仍能复制。
4. **浮条与原生文本选择菜单的时序。** Electron 的 `context-menu` 事件与 DOM `contextmenu` 是两条独立链路，渲染层 `preventDefault()` **不能**阻止主进程 popup。需实测确认「渲染层收到 contextmenu」与「主进程决定不退让」的时序，确保不会出现「右键弹两次」。

**取词与浮条**

## 十、分期

1. **「存为记忆」的写入路径**：记忆有四条写入路径且要在唯一落盘点 reconcile（见既有约定）。划词存记忆走哪条、要不要走 LLM 抽取，需在 P3 前明确，否则会被定时整理抹平。
