# Agent 通知与审批闭环设计（宠物系统·第二篇）

> 接 [`2026-09-21-Agent状态可见化设计.md`](2026-09-21-Agent状态可见化设计.md)。
> 那一篇解决的是「**看得出**」——让 Agent 的忙碌/等待有一个持续的底色表达（L1 姿态调制 / L2 表情 / L3 动作组 / L4 气泡）。
> 本篇解决的是「**叫得动**」——在 Agent 停下来的那几个时刻，把用户**真的叫回来**并**给出一条能走完的路**。
>
> 需求依据：`2026-09-21-宠物系统需求分析.md` §四 R6（需要决策时宠物来叫人）/ R7（即时气泡短句），
> 以及用户 2026-09-22 的原话：「有任务完成了，需要提示用户任务完成了；需要用户审批，可以提示用户去审批」。

---

## 〇、一句话

**「看得出」不等于「叫得动」。**
现在宠物能表现出"我在等你"，但用户**不在看**的时候它什么也做不了；而即使看到了，也**没有任何一条路**能从宠物走到那张审批卡上。

---

## 一、四个断点（全部有实现依据）

| # | 断点 | 现状 | 依据 |
| --- | --- | --- | --- |
| **D1** | **任务完成没人说** | `task_complete` 的判定**只存在于主窗渲染层**，写进该会话的 `lastTaskCompletion`；随后仅在**主窗失焦**时发一条桌面通知——而那条通知**不带 `convId`**，点它不会跳到那个会话 | `renderer/hooks/business/useAgentRuntime/event-handler.ts:1145-1162`、`renderer/pages/ChatPage/ChatPage.tsx:862-874`（对比 `event-handler.ts:1577` 的子 Agent 通知**传了** `sessionKey`） |
| **D2** | **审批叫不动** | `agent:permission:request` 确实**镜像进了宠物窗口**（`bridge-renderer-ipc.ts:57-71` 全量镜像），但被压成 `waiting` **一档**：`toolName` / `description` / `riskLevel` / `timeoutMs` / **`requestId`** 全丢。宠物既看不到审批内容，也**没有回传通道** | `packages/pet-core/src/state/agent-activity.ts:265-272`；`PET_IPC` 里没有任何审批通道（`shared/pet-mode.ts:58-155`） |
| **D3** | **别人的会话不出声** | 跨会话的等待只影响**头顶符号**与控制坞 chip，**不冒气泡**——因为气泡只由主体会话的 `agentActivity` 驱动 | `PetModeShell.tsx:168-171`（`foreignAttention`）、`PetOrchestrator.ts:395-403`（`maybeAnnounce` 只吃主体） |
| **D4** | **通知没有统一预算** | 气泡有 10 分钟节流；桌面通知只有"关掉上一条"。**跨通道（气泡/系统通知/托盘/粒子）没有统一预算**，也没有幂等——同一条审批被重放就会再叫一次 | `agent-activity-announce.ts:41`、`desktop-notify.ts:44-53` |

**D2 是最要紧的一条**：审批有一个 **5 分钟超时，超时即 deny**（`bridge-instance-factory.ts:421-435`、
`permission-controller.ts:35-49`）。也就是说用户在 5 分钟内没看见，这次工具调用就**失败**了——
而 Agent 会拿着一个"被拒绝"的结果继续往下跑。这不是体验问题，是**任务正确性问题**。

## 二、核心判断：需要的是**第二个维度**，不是第五个档位

现有 `agentActivity`（`idle` / `thinking` / `working` / `waiting` / `blocked`）回答的是
**「Agent 现在在忙什么」**。它是**连续的底色**——用户可以不看它，错过也没有代价。

而「任务完成了」「等你审批」是另一类东西：

|  | `agentActivity` | `PetNotice`（本篇新增） |
| --- | --- | --- |
| 回答的问题 | 它在忙吗 | **要不要我现在看一眼** |
| 时间性 | **当前态**，下一秒就被 `tool:start` 覆盖 | **有生命周期**：产生 → 处置 / 过期 |
| 数量 | 每会话恒为 1 | 一会话可多条，全局要排队 |
| 错过的代价 | 无 | **有**（`action` 档超时即失败） |

把它们塞进 `agentActivity` 会同时坏掉两边：

- **语义对不上**。`task_complete` 塞进 `waiting` 的话，用户看到气泡"需要你确认一下"而其实是干完了。
- **时序对不上**。`agentActivity` 是**当前态**，而"有一条审批在等你"必须**一直挂着**，
  直到用户处置或超时——它不能被下一个 `tool:start` 顶掉（实际上审批期间根本没有后续事件，
  所以 activity 会在 `waiting` 上停住，看似能用；但只要用户**不处置**、Agent 超时继续跑，
  activity 立刻变成 `working`，那条"待办"就凭空消失了，而它其实已经被 deny 了）。

> **所以：`PetNotice` 与 `agentActivity` 正交**，各自独立订阅事件、独立驱动表达。
> 这与 P2-a 立下的"维度正交"原则一致（`petStateMachine` / `Mood` / `idleStage` / `agentActivity` 已四维）。

## 三、三档紧迫度：`action` 档的判据只有一条

| 档 | 语义 | **判据（可测）** | 通道 | 会自动消失吗 |
| --- | --- | --- | --- | --- |
| `ambient` | 知道就好 | 不改变用户的任何决策 | **默认不进任何通道** | — |
| `report` | 干完了，来看一眼 | Agent **已停下**，产出是一个**结果** | 气泡 + 控制坞一行 | 是（30s 后自清） |
| `action` | 卡住了，非你不可 | **不做，它就永远不动** | 气泡 + 头顶符号 + 控制坞条目 + **系统通知** | **否**（等处置或超时） |

`action` 的判据刻意收成一句话：**Agent 是否已经停下等你**。
这是 C1「不表演」的延伸——只有真卡住才配强打扰；`report` 是"顺便告诉你一声"，
所以它**永远不用系统通知**（那会变成 D4 的骚扰）。

**`agent:turn:end` 不入表。** 实测当日 205 个 turn（`2026-09-21` 的设计文档修正块 §1 的统计）——
每一个 turn 结束都通知一次，就是一天 205 次骚扰。turn 结束只在**同时满足**下列之一时才升级为 `report`：
带 `task_complete` 工具、或该 turn 时长 ≥ 90s、或该 turn 是用户主动发起且**主窗失焦**。

## 四、事件 → 通知（完整映射表）

> **本表是数据，不是逻辑。** 落地时先作为内置默认表（形状见 §八），
> 后续由模型清单 / 创作平台的 `interactions[]` 覆盖（见 `2026-09-21-宠物创作平台预留设计.md` §3.2
> 的 `on.type: 'agent'` 与 `do[].type: 'bubble'`）。

| 事件 | 档 | 幂等键 | 文案（默认） | 处置入口 | 备注 |
| --- | --- | --- | --- | --- | --- |
| `agent:tool:end`，`toolName === 'task_complete'` 且 `!isError` | `report` | `task:${sessionKey}:${summaryHash}` | 取工具入参的 `summary`（**已有解析代码**，见 D1） | 跳到该会话 | **必须带 `sessionKey`**——现在那条系统通知没带，点了不跳转 |
| `agent:turn:end`，时长 ≥ 90s | `report` | `turn:${sessionKey}:${turnIndex}` | 「这一轮跑完了」 | 跳到该会话 | 无 `task_complete` 时的补位 |
| `agent:permission:request` / `agent:permission:prompt` | **`action`** | `perm:${requestId}` | 按 `toolName` 取中文名 + `description` | **去审批**（§5.2 深链） | **`requestId` 必须原样带上**，否则无法回执 |
| `agent:ask-user:request` | **`action`** | `ask:${requestId}` | 「有个问题要你答」 | 去回答 | 取消事件 `agent:ask-user:cancelled` 清掉它 |
| `agent:subagent:completed`，`status === 'failed' \|\| 'stale'` | `report` | `sub:${sessionKey}:${name}` | 「{name} 没跑成」 | 跳到该会话 | `succeeded` **不通知**（主窗已在做，宠物再加一条是重复） |
| `agent:error` | `isRetryable ? ambient : report` | `err:${sessionKey}:${errorCode}` | 「出错了」 | 跳到该会话 | 可重试的错误会自动恢复，不该叫人 |
| `agent:abort`，`reason === 'user_cancel'` | `ambient` | — | — | — | **用户自己按的停止**，回头再告诉他一次是噪音。`timeout` / `error` 升为 `report` |
| `agent:tool:end`，`isError` | `ambient` | — | — | — | 单个工具失败 Agent 通常会自己重试；只有它导致 turn 结束才由上面的规则接住 |
| `agent:context:compacted` | `ambient` | — | — | — | 已有"疲惫"表达（R8），不另开通知 |
| `agent:message:delta` / `thinking:delta` / `tool:start` / `tool:progress` | — | — | — | — | 过程事件，走 `agentActivity`（上一篇的设计），**不进本表** |
| `agent:turn:file-changes` | `report`（**仅当主窗失焦且无 user 消息**） | `files:${sessionKey}:${turnIndex}` | 「改了 N 个文件」 | 跳到该会话 | 与 `task_complete` 同 turn 出现时**让位**（完成通知优先） |
| 自主进化目标审批（另一套体系） | `action` | `goal:${goalId}` | 已有文案「🎯 我想做一件事，需要你确认」 | 去审批 | 走 `outreach-budget` 的预算，**不与本表共用计数器** |

**清账规则**（每条 `action` 都必须有出口，否则会永远挂在控制坞上）：

| 事件 | 动作 |
| --- | --- |
| `agent:permission:granted` / `denied` / `timeout` / `cancelled`（含 `:prompt:` 变体） | 按 `requestId` 销账 |
| `agent:ask-user:cancelled` | 按 `requestId` 销账 |
| 用户在**主窗**里处置了那张卡（不经过宠物） | 同上——**销账只认事件，不认处置来自哪个窗口** |
| 会话被删除 / 应用重启 | 整表清空（宠物窗口是内存态，不持久化） |

## 五、通道：「宠物只负责叫人，不负责人审批」

### 5.1 通道分层

| 通道 | `report` | `action` | 备注 |
| --- | --- | --- | --- |
| 气泡（L4） | ✓ 一次 | ✓ 一次，**可点** | 文案来自 §四，长度由 `announceDurationMs` 按字数定 |
| 头顶符号 | 不新增 | ✓ `?`（已有 `pickStatusGlyph` 的 `waiting` 分支） | 复用现有实现 |
| 控制坞条目 | ✓ 一行，30s 自清 | ✓ **常驻**，带「去审批」按钮 | 复用多会话清单的 chip 版式与 `onFocusSession` 通路 |
| 粒子特效 | ✓ 完成时放一次（已有 click 烟花可复用） | ✗ | 庆祝归庆祝，催办不用喜庆特效 |
| **系统通知**（Electron `Notification`） | ✗ | ✓ | 已实现：`main/desktop-notify.ts:64-128`，含 **点击跳转**（`:87-99`，`convId` 存在时 restore+focus 主窗并派发 `conversation:navigate`） |
| 声音 | ✗ | ✓（沿用系统通知的提示音） | 全仓**没有独立提示音**（实测确认）；`Notification` 的 `silent` 默认 false 即可，不新增音频资源 |

**为什么 `report` 不给系统通知**：`report` 的语义是"顺便告诉你一声"。
给它最强的通道，等于把"任务完成"变成需要处理的待办——那是 D4 骚扰的定义。

### 5.2 `action` 档的处置入口：**去审批**，而不是"就地批准"

宠物气泡上**只放一个按钮：「去审批」**，点了做三件事：

1. 主窗 `restore()` + `show()` + `focus()`
2. 切到该 `sessionKey` 的会话（复用现有 `app-ui:goto`，`App.tsx:140-171`）
3. **把那张审批卡滚进视野并高亮**

**不在宠物上就地批准**，理由是三条硬约束：

- **信息密度**：审批卡要展示命令原文、风险等级、倒计时（`ConfirmationDialog.tsx:62-151`）。
  气泡宽度只有两百来像素、还是透明置顶无边框窗口，装不下——**看不到内容就点"允许"，是在训练用户盲批**。
- **误触代价不对称**：误触"拒绝"要重跑一次；误触"**允许**"可能批准一条 `riskLevel: high` 的命令。代价不可逆，按钮就不该出现在"顺手就能点到"的地方（宠物窗口覆盖整个工作区）。
- **已经有了正确的落点**：`ConfirmationDialog` + `findAnyPendingPermission()` 已支持**跨会话**取卡
  （`agent-runtime-store.ts:415-430`），并在卡上标明"来自后台会话"（`ChatBottomOverlay.tsx:48`）。
  宠物要做的是**把人送到那张卡前面**，不是再造一张卡。

> ⚠️ 一个必须记下的既有事实：`user:permission:respond` **在 agent 的 app-ui 白名单里**
> （`main/app-ui-control/command-allowlist.ts:7`），即 Agent 可以批准自己的权限弹窗。
> 本篇**不动**这条（它有自己的场景与风险面），但新增的宠物通道**绝不能**走 app-ui —— 那条路是给 Agent 的，
> 不是给宠物的。宠物侧走 `pet:*` 命名空间（见 §八）。

### 5.3 深链需要扩展现有的 `app-ui:goto`

现在 `app-ui:goto` 只支持 `{ view, sessionKey }`（`main/pet/pet-mode-ipc.ts:264-271`）。
要聚焦到具体那张卡，得再加一个意图：

```ts
// 扩展（不是替换）：既有调用方不受影响
win.webContents.send('app-ui:goto', {
  view: 'chat',
  sessionKey,
  focusPermissionRequestId: requestId,   // 新增可选字段
})
```

渲染层收到后：切会话 → 等该会话的 `pendingPermission.requestId` 与之一致 → 给卡片加一个
**一次性高亮**（滚进视野 + 2s 描边）。若 `requestId` 已不在（用户刚在主窗处置了），
**安静降级为"只切会话"**——不能报错，那只是慢了一步。

## 六、打扰预算：跨通道统一，且必须在**幂等**之后

### 6.1 幂等优先于预算

**同一个 `id` 只叫一次**，与预算无关。理由：事件是**可能重放**的——
`bridge-renderer-ipc.ts:138-154` 有 IPC 队列，宠物窗口 `Page.reload`（实测验证脚本里天天做）
会重新挂载订阅，主窗重连也会补发。没有幂等的话，一次审批能叫三遍。

实现上就是 §三 表里的**幂等键**：`notice.id` 一经出现过就进 `announcedIds` 集合（容量 200，FIFO 淘汰）。

### 6.2 预算表

| 档 | 预算 | 依据 |
| --- | --- | --- |
| `action` | **不受预算限制**（真卡住就该叫），但受 **§6.1 幂等** 与"同时最多 1 条占气泡"限制 | 超时即失败的代价远大于被打扰一次 |
| `report` | 每会话 ≤ 1 条 / 分钟；全局 ≤ 3 条 / 分钟；气泡沿用 `ANNOUNCE_THROTTLE_MS = 10min` 的同文案不重复 | `agent-activity-announce.ts:41` |
| `ambient` | 不进任何通道 | — |

### 6.3 免打扰时段

复用主动联系的免打扰窗口（22:00–08:00，`local-companion-handler.ts:209-217`），但**语义要分开**：

- `action` 档**照叫**，只是降级：**不冒气泡**（怕吵醒旁边的人），保留**头顶符号 + 控制坞 + 系统通知**。
  真卡住的事不能等到早上——它有 5 分钟超时。
- `report` 档在免打扰时段**直接吞掉**（静默记进控制坞，用户主动看时才看到）。

> ⚠️ 与 `local-companion-handler` 的"主动联系"是**两件事**：那边是"没人理我，我想说句话"（有日限额 3 次、
> 4 小时最小间隔），这边是"有事必须让你知道"。**不共用计数器**，但两者都在同一个"总打扰预算"下——
> 建议后续把 `outreach-budget.ts` 提升为全局预算器，本篇**只提出要求，不实现**（避免在没量过之前就动它）。

## 七、并发会话：排序、抢占与"谁代表宠物"

用户已定过基调（2026-09-21 问答）：**主体演当前会话，紧急的跨会话抢占**。落到通知上：

| 情形 | 规则 |
| --- | --- |
| 同一会话多条 `action` | 按 `createdAt` 排队，气泡同时只显示**最新一条**；控制坞列出全部 |
| 主体会话 `action` vs 外部会话 `action` | **按到达时间**，不按主体优先——"卡住了"这件事与是哪个会话无关。但气泡上要标出**来源会话**（复用 glyph 的 `source: 'other'` 角标语义） |
| `action` vs `report` 抢占 | `action` 抢占气泡；被顶掉的 `report` **不再重播**（已被系统通知/控制坞接住） |
| 多个 `action` 同时存在 | 头顶符号用 `?`（已有），控制坞显示「N 件事等你」并展开列表 |

**推翻 D3**：外部会话的 `action` **必须冒气泡**。现行为（`foreignAttention` 只进符号与 chip）
用在 `agentActivity` 上是对的（别人的会话在忙，与我无关），但用在 `action` 上是错的——
**别人的会话卡住了，也占着同一个 Agent 进程与同一份配额**。

### 7.1 实测回填（2026-09-22）

「主体演当前会话、别的会话等你出手时抢头顶符号并标来源」这条链路**已实测通过**：
`verify/pet-sprite/check-foreign-attention.mjs`（关自动审批 → 别的会话跑 bash 触发真 permission
→ 读宠物窗 DOM 断言 `?` 符号带角标 → 人工响应后销账），6/6 通过。

首跑顺带发现并修掉一个真缺口：**审批的解除事件（`granted`/`denied`/`timeout`）全仓零产出**——
`session-activity` 与 pet-core 的 `waiting-resolved` 都按这族事件设计，但没有任何地方发送。
后果是 waiting 只能等 `turn:end` 兜底：**自动放行开着时（用户默认），后台会话每次调受审工具
都会让头顶亮一会儿「另一个会话在等你确认」**（实测持续约 4s，纯误报；等待期用户看不到
任何待办，因为审批早被自动放行）。修复：`bridge-instance-factory` 的 `requestPermission`
在**全部出口**（自动放行 / 渠道回复 / 审批卡 / 原生对话框 / 超时 / 停止时的批量拒绝）
统一广播 `forwardPermissionResolved`。对照实验（脚本 `--keep-aa`）显示修复后同样的操作
**符号不再出现**；人工等待场景下符号出现、响应后 **500ms 内销账**。

对本文档的意义：§四 的销账、§十「审批可到达 / 销账」两条判据，现在**有真实事件可依赖**了，
不需要按"等回合结束"来设计预算与幂等。

## 八、架构落点

严格按既有分层：`pet-core` 纯 TS 零依赖；Electron 专属逻辑在 `apps/windows`。

### 8.1 新增（pet-core，纯函数，可脱浏览器单测）

| 文件 | 职责 |

## 九、与既有维度的仲裁

| 冲突对象 | 规则 | 理由 |
| --- | --- | --- |
| **对话进行中**（用户在跟宠物说话） | `report` **推迟到对话结束**；`action` **立刻插队** | 用户在场时"完成任务"可以等等，但"卡住了"不能等 5 分钟超时 |
| **`agentActivity` 的 L1 姿态调制** | 不冲突（正交分量） | 通知改的是**气泡/符号/系统通知**，不动呼吸/浮动 |
| **拖拽 / 投掷宠物** | 气泡**不弹**（用户正在玩它，别在这时弹待办）；`action` 的系统通知照发 | 物理交互优先于自动表达（沿用 P2-a） |
| **闲置感知（打盹/睡着）** | `action` 档**唤醒**宠物（从 `asleep` 强制回 `awake`）；`report` 不唤醒 | 睡着的宠物冒气泡是自相矛盾的 |
| **免打扰时段** | §6.3 | |
| **多个宠物（本期不做）** | 通知归属默认宠物 | 多宠物同屏是后续设计（`2026-09-21-多宠物同屏设计.md`） |

## 十、验收判据

### 10.1 单测（pet-core，纯函数）

- §四 映射表**逐行**：每个事件 → 期望的 `level` / `id` / `text` 非空
- **销账只认事件**：注入 `permission:granted` 后该条消失；**不**因为 activity 变化而消失
- **幂等**：同一条 `agent:permission:request` 连发 3 次 → 只有 1 条通知
- **超时**：`timeoutMs` 到点后该条 `action` 转为已销账（不是删除——控制坞要能显示"已超时被拒"）
- **不通知**：`turn:end`（无 `task_complete`、时长 < 90s）→ 0 条
- **不变量**：缺字段（无 `requestId` / 无 `sessionKey`）时**返回 null 而不是造一条残缺通知**

### 10.2 端到端（脚本化，沿用 `verify/pet-sprite/` 的 CDP 做法）

| 判据 | 期望 |
| --- | --- |
| 任务完成 | 跑一个以 `task_complete` 收尾的真实回合（`send-turn.mjs` 已有驱动真实回合的能力）→ 宠物冒气泡 + **主窗失焦时**发系统通知 |
| 通知可跳转 | 点击那条系统通知 → 主窗前台 + **切到该会话**（现在不切，这就是 D1 的判据） |
| 审批叫人 | 造一条 `riskLevel: high` 的权限请求 → 气泡出现 + 控制坞出现「去审批」+ 系统通知发出 |
| **审批可到达** | 点气泡上的「去审批」→ 主窗前台 + 切到该会话 + **那张卡被高亮**（判据：`ConfirmationDialog` 的 DOM 上有高亮类，且 `requestId` 一致） |
| 销账 | 在主窗点「允许」→ 宠物的气泡与控制坞条目**在 1s 内消失** |
| 幂等 | 重载宠物窗口（`Page.reload`）→ 同一张待审批**不再冒第二次气泡** |
| 不打扰 | 连跑 10 个普通回合（无 `task_complete`）→ 宠物**零气泡** |
| 开关 | 关掉 `enableAgentNotice` → 系统通知与气泡均不再出现 |

### 10.3 必须**盲测**的一条（沿用上一篇修正块 §8 的教训）

`action` 档的表达强度是否**过**了：录两段（有审批 / 无审批），不标注，问观察者"哪一段让你想起了还有事没做"。
如果观察者对**普通忙碌**也说"想起了有事没做"，说明 `working` 的表达太强，得压。

## 十一、实施顺序

1. **pet-core `notice.ts` + 单测** —— 映射表、销账、幂等、预算。可完全脱离 Electron 完成，**先把判据跑绿**
2. **宠物窗户的订阅与渲染**：`PetModeShell` 事件分支 + 编排器持有 + 气泡可点 + 控制坞待办区（此时系统通知**不打**，先验宠物侧）
3. **深链**：`PET_IPC.focusNotice` + `app-ui:goto` 扩展 + 审批卡高亮（**这一步才让"叫人"真正走得通**）
4. **系统通知**：`action` 档接 `showDesktopTaskNotification`，并**修掉 D1 的 `convId` 缺失**
5. **预算与免打扰** + 设置开关
6. **数值校准**：跑 §10.2 全表 + §10.3 盲测

> 第 3 步之前，宠物的"叫"是**假的**（看得见、点不动）——所以要按顺序来，别先做 4（系统通知）
> 而把 3 拖着：那样只会在原有的桌面通知之外，再多一条**同样点了不跳转**的通知。
