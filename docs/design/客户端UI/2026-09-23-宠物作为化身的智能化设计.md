# 宠物智能化设计：一个会感知、有性格、能上场的独立 Agent

需求依据：用户 2026-09-23 反馈「当前宠物还不够智能化、拟人化，交互互动还比较少」，并提出「每个宠物都应该有自己的性格和脾气，初始化时随机」
设计日期：2026-09-23
文档状态：**本文档已合并原《宠物智能化与陪伴感设计》（2026-09-23）的全部内容，原文档已删除**

> **📌 本文档的定位**
>
> 原设计走的是「把 Agent 的状态显示得更好」——情绪影响权重、权重选动作、动作表现在屏幕上。那是一条**素材驱动**的路，成本高、天花板低。
>
> 本设计走的是「**让宠物成为一个有自己生活的独立 Agent**」。
>
> 两条路线不冲突：原设计的行为库、触发器、模板池等资产全部保留，只是换掉驱动源。逐条对照见 §十。

## 一、目标：三个理想特质

用户描述的"想象中的智能宠物"，参考数码宝贝 / 瓦力 / MOS / 机器人管家：

| # | 特质 | 具体表现 |
|---|---|---|
| **①** | **主动感知与预判** | 察觉你情绪低落会主动靠近；预判需求（工作太久提醒休息）；观察并学习你的习惯 |
| **②** | **真实的性格与情感** | 独立个性（胆小/好奇/慵懒/活泼）；被忽略会失落、被陪伴会快乐；被不合理对待会闹脾气 |
| **③** | **有限但真诚** | 不是万能助手，有明确能力边界；偶尔笨拙但努力；失败沮丧、成功雀跃 |

**"感知外部信号"（天气 / 智能家居 / 打印机）属于 ① 的延伸**，单独在 §四.5 讨论。

## 二、现状差距：原设计缺了什么

原设计的四个维度（B 情绪记忆 / A 行为库 / D 工作联动 / C 主动说话）做得扎实，但对上面三个特质：

| 特质 | 原设计 | 缺口 |
|---|---|---|
| ① 主动感知 | ❌ **完全没有** | 原设计的输入全是"宠物自己怎么了"（mood / affection / activity），**没有一条是"你"怎么了**。它的"主动说话"由宠物自己的状态触发（我心情好 / 我很久没说话了），不是由你的状态触发 |
| ② 性格与情感 | ⚠️ 部分 | 有好感度数值（那是养成游戏路线），**没有性格**；情绪不驱动决策，只影响权重 |
| ③ 有限但真诚 | ❌ **完全没考虑** | 原设计里宠物不干活，无所谓能力边界；也没有失败/成功的情绪闭环 |

**① 的缺口是最根本的**：这是"反应机"和"伙伴"的分水岭。瓦力会注意到 Eve 不动了，管家会注意到主人今天话少——**感知用户是陪伴的前提**。

## 三、支柱 A：性格——随机的出生 + 不可逆的演化

### 3.1 现状：能力全在，只是没随机

`packages/agent-runtime/src/autonomous/personality-tracker.ts` 已实现完整的 Big Five 追踪：

| 已有 | 说明 |
|---|---|
| 五维状态表 `personality_state` | 主键 `agent_id` |
| EMA 演化 | `PERSONALITY_EVENT_DELTAS`：`user-feedback-negative` → neuroticism +0.03 / conscientiousness +0.02 … |
| 边界校验 + 变更审计 | `validatePersonalityState` / `describePersonalityChange` |
| 消费点已通 | `autonomous-wiring.ts:78` 的 `readOpenness(db, agentId)` 已在读这张表 |

**唯一缺口**：初始值写死 `0.5`（`personality-tracker.ts:127-135`）。每只宠物出生时是同一个"中性人"。

### 3.2 出生抽签：截断正态

把初始化分支里五个 `0.5` 换成一次随机抽取：

```ts
/** 出生抽签：截断正态，σ=0.15，clip [0.15, 0.85] */
export function rollInnateTraits(rng: () => number = Math.random): PersonalityTraits {
  const draw = () => {
    const u = Math.max(rng(), Number.EPSILON)   // Box-Muller
    const v = rng()
    const gauss = Math.sqrt(-2 * Math.log(u)) * Math.cos(2 * Math.PI * v)
    return Math.min(0.85, Math.max(0.15, 0.5 + gauss * 0.15))
  }
  return {
    openness: draw(), conscientiousness: draw(), extraversion: draw(),
    agreeableness: draw(), neuroticism: draw(),
  }
}
```

**为什么是截断正态而不是均匀分布**：均匀抽样在五维空间里会大量产出极端个体（又极度神经质又极度内向）。σ=0.15 让大多数宠物"正常但有偏向"，少数偏得明显——这是真实的个体差异分布。

**为什么是"抽一次并落库"而不是按 id 哈希重算**：哈希只保证机器之间一致，用户主观上看到的仍是每只一个固定值，等于没抽。**第一次进游戏时真掷一次骰子，写进 `personality_state`，此后永不再掷。**

**落库时机**：`getCurrentState` 首次调用（惰性初始化，现有逻辑不动）。

### 3.3 出生快照：不可逆性需要对照组

要展示"它变了"，需要知道它出生时是什么样。

`runtime_state` 加键 `personality:birth:{agentId}`，写入 `{ at, traits }`（属性表已有，**零 schema 迁移**）。用于详情页的"成长"展示（出生 → 现在），以及演化越界被拒时回查原始值。

**⚠️ 存量用户的 `at` 不能当安装时间用**（2026-09-23 场景走查补）：老用户升级时首次抽签，`at` 是**升级时间**，但经历页会把它当"出生日期"显示——用户装了半年，却看到"出生：2026-09-23"。

**做法**：存量用户写入时带 `migrated: true`，经历页显示"**性格记录始于 X 日**"而不是"出生"。新用户才是真出生。**一个布尔字段的差别，但用户能看出真假。**

### 3.4 性格必须影响决策，不只影响措辞

继承自主进化设计 §11 的铁律：**内在状态必须影响决策，不只影响措辞**。情绪只改语气是廉价角色扮演，用户会发现"说累但活儿照干"。

五维各自的落点——**全部落在已有的旋钮上**：

| 维度 | 影响什么 | 挂接点 | 现状 |
|---|---|---|---|
| **openness** | 探索率：试新行为、去屏幕陌生角落 | `computeExplorationRate(mood, openness)`（`mood.ts:96`） | 函数已存在，**生产零消费者** |
| **extraversion** | 主动说话概率、走动权重、靠近你的倾向 | 自主行为权重表 | `ambient.ts` 权重固定 |
| **neuroticism** | 情绪波动幅度：失败时 valence 掉多少、半衰期多长 | `applyMoodImpact` 冲击系数、`decayMood` 半衰期 | 均为常量 |
| **conscientiousness** | 目标坚持度、提醒频率 | 目标执行 / outreach 间隔 | 常量 |
| **agreeableness** | 拒绝概率（§四.4） | 新增 | — |

**两个时间尺度叠加**：性格是月级的（`emaAlpha = 0.05`），情绪是小时级的（半衰期 4h）。宠物既有"稳定的脾气"，又有"当下的心情"——这正是真实动物的两个时间尺度。

### 3.5 演化是缓慢且不可逆的

`emaAlpha = 0.05`，量级在月。一只被长期训斥的宠物会真的变得更容易受打击，这不是一次性表演，是它会带着走的东西。

**这条是"共同历史不可逆"的实现**：好感度是**能衰减的连续量**（那是养成数值），真正的陪伴感来自不可撤销的事件。

### 3.6 用户看到的是气质标签，不是数值

取偏离 0.5 最远的两维合成一句话：

```
openness 高 + extraversion 低        →  "好奇，但有点怕生"
conscientiousness 高 + neuroticism 低 →  "靠谱，不太会慌"
```

与"好感度不显示数字"同一个道理，也避开自主进化 §11 的禁令「不要把 mood 数值直接展示给用户」。

### 3.7 ⚠️ 身份：宠物是独立 Agent（用户已拍板）

**2026-09-23 决策**：宠物作为**单独的 Agent** 存在，**不影响用户的任务行为**；状态与通知走**另一条通道**。

| 事项 | 定论 |
|---|---|
| `personality_state` 的行 | 宠物独占 `pet:<configId>`（实现口径：每个宠物一个独立个体），**不碰** `assistant` 那一行 |
| 通知通道 | 宠物走气泡 / `pet-notice-adapter`，不进任务 Agent 的通知流 |
| 状态隔离 | 宠物的 mood、牵挂、日记不参与任务 Agent 的决策 |

**为什么这条是对的**：共用一行意味着"你因为抢它玩具而在心情差时戳了它"会**真实改变你干活时助手的行为**——不可控的耦合。宠物互动是高频、随意、情绪化的；任务执行需要稳定的行为基线。两者共用一套状态，只会让用户觉得助手"今天怎么怪怪的"而找不到原因。

**独立不等于孤立**：宠物干出来的**成果**可以进共享的产出层（工作记忆 / Wiki），那是"产出共享"，不是"状态共享"。留作后续可选。

## 四、支柱 B：三个能力

### 4.1 主动感知与预判

#### 4.1.1 先说明：外部感知系统曾被否决，不要加回来

`docs/design/自主进化Agent/10-心跳与外部交互设计.md` §9.2 记录了对「四通道感知」的否决：

> **四通道感知（文件/进程/剪贴板/网络监听）→ 全部删除**
> 问题：直接违反隐私边界，而且没有一条能产出可用信号。"用户改了个文件"到"Agent 该做什么"之间隔着巨大的推断鸿沟，中间那些推断全是幻觉温床。
> 结论：Agent 需要外部信息时自己调工具。感知阶段只读自己的数据库。

**本设计不加监听层。** §4.1 的全部信号都来自本地库。

#### 4.1.2 信号来源：只读任务 Agent 已经产出的结果

守住隐私红线的前提下，能读的东西比想象中多——任务 Agent 已经把大量用户状态落库了：

| 信号 | 从哪读 | 说明 |
|---|---|---|
| **你这次干得顺不顺** | `autonomous_satisfaction_scores.overall_score` | 会话级真实评分 |
| **你打断了几次** | 反馈信号（abort / resend / edit 计数） | 最真实的挫败指标 |
| **你坐了多久** | 会话消息时间戳的连续性 | 连续 > 2h 无中断 = 该起来走走 |
| **你在琢磨什么** | Wiki、工作记忆、`assistant` drawer 的记忆 | 任务 Agent 已沉淀的产出 |
| **你最近什么作息** | 上述信号的时间分布 | 习惯统计 |

**"感知"被重新定义**：宠物不偷看你的屏幕，它读**任务 Agent 已经写下并且被允许读的东西**。这既守住隐私红线，又比任何屏幕嗅探都准——那些是真实发生过的、有明确语义的信号，不是"用户改了个文件"这种要靠猜的。

**巧的是这套信号已经有人算了**：`collectTickSignals`（`tick-signals.ts`）就是干这个的。宠物的感知层**复用同一个函数**：

```
collectTickSignals(db)
  ├─→ decideAction（自主进化：决定要不要干活）    ← 已有
  └─→ petSensing（宠物：决定要不要安慰你）        ← 本设计新增
```

同一份信号，两个出口，两条通道——符合 §3.7 的独立 Agent 决策。**但注意**：这个复用只在"读库判断"这一层成立，宠物一旦要**行动**，必须走它自己的目标 pipeline（§4.2），不能借用任务 Agent 的心跳。

#### 4.1.3 三条预判规则

| 感知到 | 宠物做什么 | 输入信号 |
|---|---|---|
| **你被打断/改了 3 次以上** | 靠近、安静陪着；冒一句"要不要歇会儿" | abort/resend 计数 |
| **你连续坐了 2 小时** | 提醒休息 | 消息时间戳连续性，**空闲 > 5 分钟即断开计数** |
| **这次会话评分低** | 情绪也跟着低落（**真实共情，不是表演**） | `overall_score < 0.6` → 喂给 `recordMoodEvent` |

**"空闲 > 5 分钟即断开"这条不能省**（2026-09-23 场景走查补）：没有它，用户 11:00–12:00 干活、吃饭一小时、13:00 回来再干一小时，时间戳跨度是 2 小时，会在**刚吃完饭时弹"该休息了"**——纯粹误报。这个口径任务侧的 `WorkSessionTracker` 老设计里本来就有，合并时丢了，这里补回。

**第三条是关键**：宠物的低落**不是**"检测到你心情差所以我要表现得难过"，而是把"你干得不顺"作为**它自己的**情绪事件写进它自己的 mood。它于是真的有点蔫——mood 变了，举止、权重、说话概率全都跟着变。

这正是"不表演情绪"（自主进化 §11 禁令）的落实：**没有一句"我难过"，但整个人的状态都不同了。**

#### 4.1.4 学习习惯：读沉淀，不嗅探

"观察用户行为模式，自主学习用户习惯"这条，在**信号层**已经完成了——任务 Agent 的 Wiki、工作记忆、场景记忆里就有"用户在做什么、习惯怎么做"。

宠物要做的是**读这些沉淀**并在**它的通道**里用：

- 知道"你在重构前端" → 连续工作 2h 时说的是"前端又写了两小时了"，而不是通用的"该休息了"
- 知道"你一般 23 点后不干活" → 22:40 你说"再改一会儿"，它可以有反应

**权限边界**：宠物对这些沉淀**只读**，且不写入任务 Agent 的状态。它读到的东西进它自己的记忆，不回流。

#### 4.1.5 预判的克制

预判最容易变成打扰。四条纪律：

1. **预判错了要能收回**——猜你在卡壳但其实是正常思考，不要追问，等下次信号
2. **同一天同类预判不超过 1 次**——"该休息了"说两遍就是唠叨
3. **只在宠物模式下出现**——不做系统级通知（走气泡）
4. **感知只读，行动另走 pipeline**（§4.1.2 末段的约束）

#### 4.1.6 新用户的空状态：不能装作在工作

**2026-09-23 场景走查补**：全新用户没有 `satisfaction_scores`、没有打断记录、没有历史会话——三条预判规则**全部静默失效**。宠物表现得跟没有感知一样，用户会觉得"说好的智能呢"。

**这不是 bug，是必然的冷启动**。要处理的是**表现**，不是逻辑：

| 状态 | 表现 |
|---|---|
| **冷启动**（无历史数据） | 不装：不说"你最近怎么样"，改成探索型的话（"这个屏幕好大"、"你在做什么呀"）。**感知层没料时，退回性格驱动的自发行为** |
| **攒够数据**（有 ≥1 次完整会话评分） | 开始出预判 |
| **数据稀疏**（只有零星记录） | 阈值放宽（"连续 2 小时"改成"连续 3 小时"），宁可少说 |

**核心原则**：**感知没料时不要硬说**——冷启动期硬憋出一句"你今天心情不太好哦"，比不说话糟糕得多（与 §4.1.5 第 2 条同源）。

### 4.2 能上场：宠物能替你去看一眼

这是本设计**成本最低、感知最强**的一条。

拆解后发现几乎全是接线：

| 需要的东西 | 现状 |
|---|---|
| 受限执行实例 | `createRestrictedInstanceById` + `getGoalToolAllowlist` 已有（`executeGoal`） |
| 工具白名单硬防线 | 已实现（T1 无条件 / T2 预算内写 / T3 高危关闭） |
| 结果落库 | 宠物自己的会话，**不进 `evolution:main`**——它不属于自主进化那条线 |
| 结果播报 | 气泡 + `pet-notice-adapter`，**不走任务 Agent 的通知流** |

**缺的只是**：让宠物能**发起**这类目标，并在完成时通过自己的通道说出来。

对照原设计 §5「主动说话」——那条路是"检索记忆 → 选模板 → 说一句关心"。本设计给它的是一条**有内容的**话：不是"你的测试好像挂了"，而是"我去看了一下，`pet-core` 那个测试挂在第 42 行"。

#### 4.2.1 ⚠️ 意图从哪来：只做两种来源

2026-09-23 场景走查发现的**最大逻辑缺口**：上面的执行链路写得很细，但**"宠物的目标从哪产生"从没定义**——链路只有出口没有入口。

三条可能的路语义完全不同、基础设施也不同：

| 路径 | 谁生成 | 需要 |
|---|---|---|
| **① 用户明确要求**（点「让它去做」） | 用户 | 只需一个入口 |
| **② 感知触发后提议**（"要不要我去看看"） | `petSensing` | 需要触发规则 |
| ③ 宠物自己排期 | pet 心跳 + **LLM 规划器** | 新增一个低频 LLM 开销 |

**第一期只做 ①②，不做 ③。**

**Why**：③ 需要新写一个规划器（任务侧 `planner.ts` 是按 agent_id 跑的，加宠物线等于多一路 LLM 调用），而它覆盖的是"用户压根没提过"的场景——①② 已经覆盖绝大多数真实需求。**等 ①② 跑顺、并且观察到用户确实期待它自己找事做，再议 ③。**

#### 4.2.2 ⚠️ 结果必须可回溯，气泡不是唯一通道

**气泡是瞬时的。** 用户点完「让它去做」去倒杯水，30 秒后宠物报结果——**气泡对着空气说**，用户回来什么都没有，以为没执行。

这是最糟的失败形态：**用户交代了事，却没收到回执。**

**两类话必须分开对待**：

| 类型 | 例子 | 通道 | 丢了怎么办 |
|---|---|---|---|
| **感知类**（说了没听见就算了） | "该歇会儿了"、"外面下大雨" | 气泡（瞬时） | 丢掉，不补 |
| **结果回执类**（用户交代过的） | "测试挂在 42 行"、"这个我不拿手" | 气泡 + **控制坞持久条目** | **必须能回来看到** |

**实现口径**：执行结果**同时**进气泡和控制坞的"宠物流"（§8.4），且控制坞条目**带未读标记**直到用户看过。气泡负责"当下被看见"，控制坞负责"回来能看见"。

#### 4.2.3 ⚠️ 闸门与并发：宠物侧目前一个都没有

`MAX_GOALS_PER_DAY`、`tokenAllowed`、`hasActiveUserTurn` 全是**任务侧**的机制。按 §3.7 拆开 agent_id 之后，宠物侧**什么都没有**：

| 风险 | 后果 |
|---|---|
| 用户连点三次「让它去做」 | 三个实例同时跑，抢 LLM |
| 宠物一天无上限烧 token | 成本不可控 |

**务实做法——两个判断，不加调度器**：

1. **单飞锁**：宠物侧做一个"有没有实例在跑"的判断，照抄 `hasActiveUserTurn` 的思路（查宠物会话有没有活跃实例）。有则**排队或拒绝**，不做并发。
2. **每日硬闸门**：`MAX_PET_GOALS_PER_DAY` 常量 + token 上限，超了直接拒（**不是软提示**——任务侧的 `tokenAllowed` 就是硬闸门，宠物侧照抄）。

#### 4.2.4 ⚠️ 工作目录：派活时必须继承当前项目

核过代码：`workingDirectory` 是运行时配置项（`runtime-config.ts:22`），`file_read` / `glob` / `grep` 都在它下面解析。但设计里从没写**宠物会话的工作目录是什么**。

后果：派它去看 A 项目的测试、它却按 B 项目的根去读 → **静默读错文件或读到空**。

**务实做法**：派活时**继承当前主会话的 projectPath**（覆盖场景最多、零新概念）。跨项目等真有人提再说。

#### 4.2.5 ⚠️ 通道纪律（最容易做错的地方）

宠物看到的东西是**它的见闻**，不是系统的通知。任务 Agent 的完成通知该由任务 Agent 自己发，不能因为宠物去看了一眼就重复发一条——那会让用户收到两条同一件事的消息。

实现时**断言宠物播报不经过 `dispatchNotifications`**（任务的系统通知 / 渠道推送路径）。

#### 4.2.6 ⚠️ 与独立性的冲突，必须处理

想省一个调度器、复用 `autonomous_goals` 表 + 心跳派发，但会与 §3.7 冲突——宠物目标会占用任务 Agent 的每日配额（`MAX_GOALS_PER_DAY`）并落进同一个 `agent_id` 命名空间。

| 要拆的 | 做法 |
|---|---|
| 每日配额 | 配额统计按 agent_id 过滤 |
| 心跳派发 | `collectTickSignals` 派发时按 agent_id 分流，宠物目标不能被任务侧心跳抢先执行 |
| 预算 | 宠物的 token / 主动消息预算独立计数 |

**若改动面过大，降级方案是给宠物单独一张轻量表**（结构同 `autonomous_goals` 的三个关键列），接受一次 migration 换干净隔离。

### 4.3 不可逆的共同历史

已有资产，无需新建：

| 资产 | 位置 | 状态 |
|---|---|---|
| 日记 | `autonomous_diaries` 表（V32） | 已落库，含 `recentDiaries` 连续性注入 |
| 牵挂 | `autonomous_goals` 的 `type='follow-up'` | 已设计，含三条纪律（不追问超 2 次） |
| 出生快照 | §3.3 新增 | 本次新增 |

**清空记忆不应该重置人格**——这条要写进设置页的文案（"清空记忆不影响它的性格"）。

### 4.4 会拒绝（严格边界）

**只允许在"互动请求"上拒绝，绝不允许在"任务请求"上拒绝。**

管家的定律冲突、瓦力不肯松手之所以动人，是因为那是个**有内心的人**在权衡；而一个该干活时不干活的助手是 bug。

| 场景 | 可否拒绝 | 表现 |
|---|---|---|
| 你戳它、拖它、让它表演 | ✅ | 低 agreeableness + 低 valence → 躲开、扭过脸、不动 |
| 你让它查个文件、跑个测试 | ❌ | 一律执行 |

触发：`agreeableness < 0.35 && mood.valence < -0.2` → 拒绝概率 ≈ 0.3。

这是"每只宠物不一样"最直观的体现——一只温顺的宠物和一只脾气差的宠物，在同一个动作上反应完全不同。

### 4.5 感知外部信号：天气 / 智能家居 / 打印机

必须分清两件本质不同的事：

| | 流向 | 本质 | 风险 |
|---|---|---|---|
| **取信息**（天气、设备状态） | 外部 → 宠物 | 出门看一眼 | 低（只进本地，不产生外部后果） |
| **控设备**（开灯、打印、调空调） | 宠物 → 外部 | 对物理世界动手 | **高且不可逆** |

#### 4.5.1 天气 / 环境信息 → 已经在做

`web_search` + `web_fetch` 在 **T1 无条件白名单**里（`goal-executor.ts:31-32`），查天气是标准用法。**不需要新建"天气感知通道"**——那会退化成 §4.1.1 已否决的被动监听层。

**但必须区分"感知"与"取数"**：

| | 成本 | 频率 | 用在哪 |
|---|---|---|---|
| `petSensing` 读本地库（§4.1.2） | 零 token、零网络 | 每次 tick | 判断你累不累、卡没卡 |
| 天气这类外部信息 | 一次工具调用 + 一次 LLM | **不能每 10 分钟跑** | 有明确意图时才取 |

既有设计已明确否掉高频拉取（`10-心跳与外部交互设计.md:140`：「心跳每 10 分钟拉一次天气是纯浪费」）。

**正确形态**：

```
宠物有意图（"我想知道今天天气"）
  → 走它自己的目标 pipeline（§4.2，不是任务 Agent 的心跳）
  → 一次 web_search
  → 结果写进宠物自己的本地存储
  → 之后 petSensing 从本地读，驱动行为判断
```

**最干净的用法是喂给它自己的 mood**，而不是每条都播报：下大雨 → 宠物自己有点蔫 → 你回来时它说"外面下好大雨"。外部信号改变的是**它的状态**，然后通过状态改变举止。

#### 4.5.2 智能家居 / 打印机 → 目前不存在，且不能简单开

**现状**：`GOAL_EXECUTION_TOOLS` 里没有任何设备类工具；更关键的是 **`mcp__*` 被明确列在 T3「绝不放行」**（`goal-executor.ts:25-26`）。智能家居集成绝大多数走 MCP——**按现有规则，一条都进不来**。

这不是遗漏，是既有设计的选择。要不要改，取决于一条判断：

> **宠物会自信地做错事。**
> 发错一条消息的成本是 0；打错一份文件要费纸、要人走过去拿；开错一扇门、启动错一个设备，成本不在一个量级。这就是 T3 存在的理由。

**建议的分级（若确要做）**——沿用既有 T1/T2/T3，**不新建层级**：

| 级别 | 例子 | 授权方式 |
|---|---|---|
| **T1 只读状态** | "打印机是不是还在跑"、"客厅灯开着吗" | 无条件可读。**读状态永远安全**，只进本地 |
| **T2 可逆动作** | 关灯、调温度 | 需用户**逐类显式授权**（不是一次总开关） |
| **T3 不可逆硬件动作** | **打印**、开门锁、燃气/暖气、任何通电启动 | **永久禁止** |

**⚠️ 一条硬规则：宠物绝不自主触发硬件动作。** 哪怕用户授权了 T2，也只在**用户当下明确要求**时执行（"帮我把灯关了"），不允许由宠物目标 / 心跳 / 预判自行发起。理由是错的代价不对称——**它可以在心里想，不能在物理世界动手**。

#### 4.5.3 最值得先做的：读了状态之后主动去看

> 3D 打印机停了 40 分钟没动 → 宠物察觉（**读状态，T1**）→ 它去查打印日志（**§4.2 受限实例**）→ "我去看了下，它卡在第 42 层，可能在等换料"

这是 §4.2「上场」用在物理设备上，**不需要给宠物任何控制权**，却是感知外部信号里感知最强的一种——它把"我知道你的设备出问题了"变成了"我查明白了"。

**建议第一期只做这个**，控制类等有真实需求再议。

### 5.2 ⚠️ mood 三维 IPC 缺口仍然存在（原设计 §3.1.1 有效）

`apps/windows/src/shared/agent-runtime-events.ts:582-585` 当前载荷：

```ts
  readonly emotion: 'joy' | 'sadness' | 'surprise' | 'neutral'
}
```

`bridge.ts:2713` 只推 `emotion`，三维数值不出主进程。**载荷加 `mood: { energy, valence, arousal }` 是硬前置**——§3.4 的 neuroticism 联动、§4.1.3 的共情都要读三维。

### 5.3 🔴 mood 是全局单键，必须按 agent_id 分开（本设计新发现的硬缺口）

**2026-09-23 核代码**：`mood.ts:36` 的存储键是写死的常量：

```ts
const MOOD_STATE_KEY = 'autonomous.mood';   // runtime_state 全局单键
export function readMood(db: DatabaseAdapter, now = Date.now()): Mood
export function writeMood(db: DatabaseAdapter, mood: Mood): void
```

`readMood` / `writeMood` **都不带 agent_id**。

**后果**：既然宠物是独立 Agent（§3.7），**宠物的情绪和任务 Agent 的情绪现在会互相覆盖**——你训完宠物，助手的心情也变了。

**修法**：

```ts
export function readMood(db: DatabaseAdapter, agentId: string, now = Date.now()): Mood
export function writeMood(db: DatabaseAdapter, agentId: string, mood: Mood): void
// 键：`autonomous.mood:{agentId}`
```

**迁移**：现有全局键 `'autonomous.mood'` 是任务 Agent 的（`bridge.ts:2705` 的 `recordMoodEvent` 是它的消费者）。迁移时先读出来写到 `'autonomous.mood:assistant'`，再删旧键。**老用户的当前情绪不能丢。**

**改动面**：`mood.ts` 两个函数签名 + 所有调用点（`bridge.ts` / `tick-signals.ts` / 测试）。约 2h，但**必须在第一期做**，否则后面所有情绪相关的东西都会串。

### 5.4 `pet-mode-store` 现状确认

`apps/windows/src/main/pet/pet-mode-store.ts` 目前只存 `currentModelId` + `vhSettings`，**没有** `configId` / `affection` / `position`。原设计 §3.4 的扩展计划仍然有效，与本设计不冲突（性格走 `personality_state`，不进这个文件）。

## 六、分期实施

### 排序逻辑：按"闭环优先"而不是"层优先"

原设计的分期是 **B → A → D → C**（状态层 → 行为库 → 工作联动 → 主动说话），自上而下打地基。

**本设计改成闭环优先**：每一期结束时，用户都能看到一个**完整的新行为**，而不是"这一期只加了数据结构"。

理由：旧顺序里，做完整个 B 层（情绪+好感度+记忆+持久化）之前，用户**什么都看不到**；这不是"小步快跑"。而依赖链并不要求这样——`pet-core` 的行为层可以直接读 `personality_state`，不必等宠物自己的状态层建好。

关于感知与行动的**耦合**：感知越强，"不能行动"的短板越刺眼——你察觉到用户卡住了，如果什么都做不了，那就只能憋出一句空话。所以感知规则与"能上场"配套：**每加一条感知规则，同时加上它能触发的那一件事**。

## 七、③「有限但真诚」的实现

理想宠物的第三条**不需要造任何新系统**，但需要把已有的东西**诚实地用起来**。

### 7.1 能力边界要真实，不要装作有

宠物被派活时（§4.2），它的成功率**必须来自真实的 `capability_dimensions`**——那张表已经记录了每个维度（document_analysis / code_generation / …）的 Elo 边界值。

| 做法 | 结果 |
|---|---|
| ❌ 让宠物假装什么都会 | 一次失败就露馅，且用户会真的损失时间 |
| ✅ **超出边界就直说** | "这个我不太拿手，要不要让主助手来？" |

**"能力边界"本身就是萌点**：一个会说"这个我不会"的宠物，比一个假装万能然后搞砸的，可爱得多，也可信得多。

### 7.2 笨拙：真的笨拙，不是随机报错

**禁止用"随机做错"来营造笨拙感**——那是欺骗用户。

真实的笨拙来自能力边界的**边缘地带**，而且系统里已经有真实数据支撑：

- 在 `boundary` 边缘的任务 → 可能真的做不完（不是演的）
- 对某个工具不熟 → 用得不顺（`capability_dimensions` 里那个维度的真实分数低）
- 它**努力**的表现是：失败后换方法、再试一次——然后结果如实说

**努力也是真的**：不是"再试一次"的动画，是真的重试了一次工具调用。

### 7.3 成功与失败的情绪：走真实的 mood 通道

| 事件 | mood 影响 | 已有映射 |
|---|---|---|
| 目标完成 | valence ↑、arousal ↑ | `applyMoodImpact` 的事件表 |
| 目标失败 | **valence ↓ 但 arousal ↑** | 已有设计（`11-参数配置与生命感设计.md` §六） |
| 被你打断 | valence ↓ | 反馈信号 |

**注意失败时的双向影响**：失败不只让它低落，还让它**在意**。这是既有设计里"牵挂"的来源，也是"失败会沮丧但会再试"的机制基础——纯降 valence 会得到一个抑郁的宠物，它就不会再试了。

`applyMoodImpact`（事件 → 情绪）、`moodToPetEmotion`（情绪 → 表情键）、mood 驱动的行为权重**三条都已在跑**。接上就是真的雀跃和真的沮丧，**不需要写任何"表演"代码**。

### 8.2 三条设计原则

#### 原则一：可感知的差异，不依赖新增美术素材

`demo_cartoon_cat` 和 `demo_mecha_gundam` 只有 1 个表情、2 个动作组。如果设计的表现力全靠"多出 15 组动作帧"，那么这两个模型**永远得不到新能力**——用户换了模型，宠物就"变笨了"。

**所以表现力必须主要落在三类不依赖美术的资源上**：

| 资源 | 能力 | 谁在提供 |
|---|---|---|
| **程序化参数** | `bob`（浮动）/ `breathe`（呼吸）/ `sway`（摇摆）/ `nod`（点头）/ `blink`（眨眼） | `procedural-motion.ts` 已实现，参数化 |
| **时间** | 频率、持续时长、间隔、过渡速度 | `ambient.ts` 的 weights + durations |
| **空间** | 移动范围、速度、朝向、停留位置 | `locomotion.ts` + `perch.ts` |

**这正好也是性格的落点**（§3.4）：openness 改的是频率和范围，neuroticism 改的是幅度和恢复，extraversion 改的是时长和倾向——**全是数值，不是素材**。

美术资源（新增动作组）是**加成**，不是**前提**。

#### 原则二：动画表达内在状态，不做装饰性动画库

禁止"为了丰富而丰富"的动画（比如定时随机播一个跳舞）。每一个动作都应当能回答"**它现在为什么这样动**"。

**正例**：`valence` 低 → `breathe` 幅度 ×0.8 + `bob` ×0.7 → 看起来蔫。
**反例**：30 秒随机播一次"卖萌"。

这条继承自主进化 §11 的"事后可理解"，也继承 `ambient.ts` 已经写下的取舍（注释里明确拒绝参考项目"5 秒一次、三成概率随机打招呼"的做法）。

#### 原则三：动画必须可打断

宠物在用户的**余光**里。任何超过 2 秒、不可打断的动作序列，都会从"可爱"变成"烦人"。

- 一次性动作（打哈欠、伸懒腰）必须能被点击 / 拖拽 / Agent 事件打断
- 打断不是"取消"，是**插队**——新动作接上，旧动作平滑收尾（不跳帧）
- 优先级：用户直接交互 > Agent 事件 > 自主行为 > 环境随机

#### 10.3.1 非语言交互：身体就是界面

宠物的"回应"不应该总是文字。三种不说话的反馈：

| 你做了什么 | 它怎么回应 | 依赖 |
|---|---|---|
| 点击头部 | 歪头（`tapMotions.HitAreaHead`，已有） | 无 |
| 连续快速点击 | 根据 agreeableness 分流：高 → 转圈卖萌；低 → 躲开（§4.4 拒绝） | 第二期 |
| 拖拽后松手 | 投掷物理（`throw-physics.ts` 已有） | 无 |
| 长按（新增） | 摸头手感：闭眼 + 呼吸放缓 + 持续 3 秒后气泡"呼~" | 第二期 |
| 鼠标靠近 | 高好感 / 高 extraversion → 转头看鼠标 | 第三期（追鼠标） |

**长按摸头是本设计推荐新增的第一个交互**——成本极低（复用现成的 `calm` 表情 + `breathe` 参数），但它是**唯一一个"持续的、有回应的接触"**，单次点击给不了这种手感。

#### 10.3.2 语言交互：宠物有自己的一句话，不是一个聊天窗口

**现状问题**：控制坞现在就是个缩小版聊天界面（6 条消息历史 + 输入框），它承载的是**虚拟人对话**。加了本设计之后，宠物还会**主动说话**（§4.1.3 预判、§4.2 播报执行结果），这些如果都挤进同一个消息流，会变成一团乱麻。

**设计**：控制坞的消息区**分两条流**，用视觉分区而不是两个 Tab（Tab 会藏起来）：

```
┌─ 控制坞 ────────────────────────────┐
│  ［气质标签：好奇，但有点怕生］        │  ← 第二期新增
├─────────────────────────────────────┤
│  🐾 宠物 · 刚刚                      │  ← 宠物自己的流（气泡式，蓝色调）
│     "我去看了下，那个测试挂在 42 行"   │
│                                     │
│  💬 对话                            │  ← 虚拟人对话流（现有）
│     你：帮我看看测试                  │
│     猫猫：好，我这就去～              │
├─────────────────────────────────────┤
│  [输入框]                    [让它去做] │  ← 第五期新增按钮
└─────────────────────────────────────┘
```

**为什么不做成两个 Tab**：宠物主动说话的价值在于"**它自己冒出来**"。如果用户在"对话" Tab 里，宠物的话在"宠物" Tab 里悄悄产生，那就完全失去了意义。**分区但同屏**，才能让它在余光里被看到。

**⚠️ 结果条目必须带未读标记**（§4.2.2 的落点）：气泡是瞬时的，用户去倒杯水就错过了。宠物流的**结果回执类**条目要保持未读高亮，直到用户真的看过——这是"用户交代了事必须收到回执"的唯一保障。感知类的话（"该歇会儿了"）不进这个流，说了没听见就算了。

**两类话的归属**：

| 类型 | 进哪 | 未读标记 |
|---|---|---|
| 感知类（"该歇会儿了"、"外面下大雨"） | 只走气泡 | ❌ 不需要 |
| 结果回执类（"测试挂在 42 行"、"这个我不拿手"） | 气泡 **+** 宠物流 | ✅ 必须 |

**去重与克制**（继承原设计的既有约束）：

| 规则 | 值 | 来源 |
|---|---|---|
| 同轮最多一次主动说话 | 1 | 气泡已有规则 |
| 同一句最短重复间隔 | 10 分钟 | 气泡已有规则 |
| 气泡停留时长 | `4s + (字数-4)×0.5s`，夹在 [4s, 10s] | `announceDurationMs` 已实现，**直接复用，不另起一套** |
| 日限额 | 5 条 | 可配置 |
| 最小间隔 | 2h（好感高）/ 4h（好感中低） | 可配置 |
| 免打扰 | 22:00–08:00 | 可配置 |

#### 10.3.3 派活交互：怎么让它去做事

**入口**：控制坞输入框旁的"让它去做"按钮（第五期）。

**交互流程**（关键：**用户能看到它去做了，而不是干等**）：

```
1. 用户输入："看看测试挂了没"        → 点「让它去做」
2. 宠物窗立刻响应（< 200ms）：
   - 头顶符号切到"工作中"（复用 Agent 状态可见化）
   - 气泡："我去看看"（短，立即出现）
3. 执行中：控制坞"宠物"区显示进行中条目（带转圈）
4. 完成：
   - 气泡播出结论（带具体内容）
   - 控制坞条目落地，可点击展开完整结果
   - 失败也如实报，不假装成功（§7）
```

**⚠️ 一条硬约束：宠物的执行结果不进用户的会话历史。**
它落在**宠物自己的会话**（§4.2），在控制坞的"宠物"区展示。理由是**污染**——用户的主会话是他和助手的对话，被宠物"我去看了下有 42 行报错"插进去，会让真正的对话记录变得不可读。

**"宠物"区的条目可点击展开**查看完整结果，也可一键"转给主助手"（把它看到的东西交给真正的任务 Agent 处理）——这是宠物与任务 Agent 之间**唯一**的通道，且是**用户主动触发**的。

| 牵挂 | `autonomous_goals` 的 `type='follow-up'` |
| 做过的事 | 宠物自己的会话记录 |

**这个 Tab 是整个设计的"证据页"**——用户能在这里看到"它真的变了"，而不是只有一个模糊的感觉。

### 8.5 状态可见性：让内在状态"读得出来"

**用户不该看到数字**（§3.6），但必须能**看出区别**。三条通道：

| 通道 | 表现 | 依赖 | 覆盖模型 |
|---|---|---|---|
| **举止** | 走动频率、停留时长、移动范围、速度 | `ambient` / `locomotion` 参数 | ✅ 全部模型 |
| **程序化动作** | 呼吸幅度、浮动幅度、眨眼频率、点头 | `procedural-motion` 参数 | ✅ 全部模型 |
| **表情** | 12 种表情切换 | `emotionMap` | ⚠️ 仅部分模型 |

**表情层的诚实降级**（对应 §8.1.1 的模型差异）：

| 模型等级 | 表现策略 |
|---|---|
| 有表情层（mao_pro / xiaomai / ug_official / anime_girl） | 举止 + 程序化 + **表情** |
| 无表情层（cartoon_cat / gundam / shimeji） | 举止 + 程序化（**加倍幅度补偿**） |

**⚠️ 且必须让用户知道差异**：设置页模型列表给每个模型标一个能力等级（"表情丰富 / 基础"），并注明"基础模型的情绪主要通过动作幅度表达"。**否则用户会以为宠物坏了**——"我心情这么差它怎么一点反应都没有"，实际是这个模型只有一张脸。

### 8.6 基本动画规范

#### 10.6.1 性格 → 参数映射表

这是"性格看得见"最直接的落点。**全部是数值调整，不需要新素材**：

| 参数 | 高位性格 | 低位性格 | 出处 |
|---|---|---|---|
| `blink` 频率 | 高 energy → 慢而稳 | 高 neuroticism → 快而乱（`BLINK_JITTER` 调大） | `procedural-motion.ts` |
| `breathe` 幅度 | 高 energy → 大 | 低 energy → 小（蔫） | 同上 |
| `bob` 幅度 | 高 extraversion → 大 | 低 → 小 | 同上 |
| `sway` 幅度 | 高 openness → 大 | 低 → 小 | 同上 |
| `nod` 频率 | 高 agreeableness → 多 | 低 → 少 | 同上 |
| 活动间隔 | 高 openness/extraversion → 短 | 低 → 长 | `ambient.durations` |
| 移动范围 | 高 openness → 远 | 低 → 近 | `locomotion` |
| 活动切换速度 | 高 energy → 快 | 低 → 慢 | 过渡时长 |

**这才是"每只宠物不一样"最日常的体现**——不用等到它说话或拒绝，用户看着它发呆的样子就能感觉出来。

#### 10.6.2 一次性动作（呼应 §4.1 的素材计划）

| 行为 | 提示 | 触发 | 依赖 |
|---|---|---|---|
| **打哈欠** | drowsy 阶段 | `idleStage === 'drowsy'` | 需新素材（8 帧）或程序化近似 |
| **伸懒腰** | 从 asleep 醒来 | idle 阶段跃迁 | 需新素材（12 帧） |
| **挠头** | Agent blocked / 心情差 | 事件驱动 | 需新素材（10 帧） |
| **追鼠标** | 好感高 | 鼠标移动 | **零素材**（`locomotion` 加 chase 模式） |
| **长按呼噜** | 被摸头 | 长按 3 秒 | **零素材**（复用 `calm` + `breathe`） |
| **装睡** | 不想被打扰 | 低 agreeableness + 长闲置 | **零素材**（复用 `fake_sleep`，mao_pro 已有） |

**优先做零素材的四条**（追鼠标、长按呼噜、装睡、以及用 `procedural` 近似的打哈欠）——它们在**所有模型**上都可用，不依赖出图管线。

#### 10.6.3 过渡与打断

| 场景 | 要求 |
|---|---|
| 站立 ↔ 行走 | 速度渐进（加速 / 减速），不瞬间切换 |
| 醒来 | 先 `stretch` 再进入 stand，不直接弹起 |
| 入睡 | `drowsy` → 眨眼变慢 → `breathe` 变小 → asleep |
| 被拖拽 | 立即切 `fall` / `picked`，不播完当前动作 |
| 事件打断 | 新动作插队，旧动作**平滑收尾**（不跳帧） |

#### 10.6.4 性能约束

| 项 | 约束 | 理由 |
|---|---|---|
| 帧率 | 跟随显示器，不做额外节流 | 桌宠常驻 |
| 程序化计算 | 纯函数、无 GC 压力 | `procedural-motion` 已是纯函数 |
| 空闲时 | 无活动 → 降到最低重绘 | 宠物大部分时间是静止的 |
| 素材加载 | Live2D 模型按需加载，切模型不重载窗口 | 已有实现 |

### 8.7 无障碍

| 项 | 要求 |
|---|---|
| **减少动效** | 尊重系统 `prefers-reduced-motion`：关闭装饰性动作，保留状态表达（举止变化） |
| **键盘可达** | 控制坞所有功能可用键盘操作（Tab / Enter / Esc） |
| **不劫持焦点** | 宠物窗是覆盖层，**永不抢主窗焦点**（已有实现，需保持） |
| **气泡可关闭** | 主动说话必须能一键静音（控制坞已有静音开关） |
| **色不单独承载信息** | 状态不只靠颜色表达（头顶符号已有形状区分） |

### 8.8 验收

| # | 判据 | 分期 |
|---|---|---|
| U1 | 用户能看出两只性格不同的宠物在**静止时**就有区别（呼吸、眨眼、活动频率） | 第二期 |
| U2 | 控制坞显示气质标签，不显示数字 | 第二期 |

## 九、Non-Goals

| 不做 | 理由 |
|---|---|
| 好感度数值 / 等级 / 饥饿 | 那是养成游戏，与"有完整内在生活"的定位冲突（原设计 §1.2 的判断仍成立） |
| 宠物状态影响任务 Agent 的行为 | 用户已拍板：宠物是独立 Agent（§3.7） |
| 宠物通知混进任务通知流 | 同上 |
| 文件 / 进程 / 剪贴板 / 窗口监听 | 已否决（§4.1.1） |
| 宠物自主触发硬件动作 | 错的代价不对称（§4.5.2） |
| 用随机报错营造笨拙感 | 欺骗用户（§7.2） |
| 任务请求上拒绝 | 该干活时不干活是 bug，不是性格（§4.4） |
| 表演情绪（"我好开心呀~"） | 继承自主进化 §11 禁令 |
| 宠物主动调用高危工具 | 沿用 T3 关闭（bash / spawn / channel / browser / mcp） |
| 性格手动编辑 | 性格只能出生决定 + 经历演化，可编辑就变成了捏脸 |

## 十、与原设计的关系

本设计**不推翻**原设计的资产，只改变它们的**驱动源**：

| 原设计资产 | 本设计的处理 |
|---|---|
| 行为库扩充（§4.1，4 → 15+ 种） | 保留，但权重由**性格**驱动（§3.4），不只由情绪 |
| 权重表动态化（§4.2） | 保留，输入从 `(mood, affection)` 扩为 `(mood, affection, traits)` |
| 触发器系统 T1/T2（§4.3） | 保留，`InteractionCondition` 增加 `traits.*` 条件 |
| 主动说话（§5） | 保留模板池，但**有内容的播报**（§4.2）优先于关怀文案；触发条件补上**感知用户**（§4.1），不只由宠物自己的状态触发 |
| 工作联动（§6） | 保留，与 §4.2「上场」合流——从"报告状态"升级为"我去看过" |
| 记忆系统（§3.3） | 保留；**修正 §3.3.2 归属**——隔离靠 drawer，但宠物是独立 Agent（§3.7） |
| 好感度（§3.2） | **降级为可选**：本设计用"性格不可逆演化"提供陪伴感。若要保留，只保留模糊指示，不参与决策 |
| `emotionMap` 排除结论（§3.1.2） | **已过期**，见 §5.1 |
| mood IPC（§3.1.1） | **仍然有效**，见 §5.2；另有更根本的 §5.3（mood 分键） |

**实现顺序建议**：原设计的 1.5（T1/T2 触发器）与本设计第二期可并行；其余按各自节奏推进。
