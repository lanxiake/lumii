## 三、背景与代码事实核查

### 3.1 问题陈述

当前宠物（虚拟人）仅支持 Live2D 渲染，内容扩张被三重约束卡死：

1. **资产授权**：`apps/windows/resources/pet-models/LICENSE` 明确记载，现存三个模型（mao_pro / ug_official / xiaomai）**仅限开发测试**，产品化发布前必须替换为自有或商用授权模型。即当前架构下**零可发布资产**。
2. **制作成本**：Live2D 需要 Cubism 建模、参数绑定、动作关键帧，个人开发者难以规模化产出。而 AI 生成工具（图像/视频生成）产出的是**序列帧**，无法直接转成 Live2D 模型、参数或动作。
3. **能力天花板**：场景、道具、粒子、装饰物、多角色同屏等游戏化交互，在 Live2D 模型体系内缺乏表达手段（模型是单一角色的参数化网格，无场景层概念）。

精灵图路线可同时缓解三者：像素/2D 素材来源广泛（含 CC0 素材库）、渲染层可自由叠加场景与道具层。

### 3.2 创作者系统需求（2026-09-20 追加）

用户进一步提出目标：**借助客户端 Agent 能力，让用户动态更新、自制宠物角色 / 交互 / 场景**，形成一个可扩展的创作系统。

代码事实核查（能力侧）：

| 能力 | 位置 | 结论 |
| --- | --- | --- |
| 文生图 + 图生图 | `packages/agent-runtime/src/tools/built-in/image-generate-tool.ts:69` `referenceImagePaths` | 已有。注释明确支持「风格迁移、局部修改、**角色保持**、多图融合」 |
| 文件读写 / 移动 | `file-write-tool` / `file-edit-tool` / `file-move-tool` | 已有 |
| Shell 执行 | `bash-tool.ts`（Git Bash） | 已有，允许「写临时 Node 脚本处理非平凡文件操作」 |
| 图像处理库 | `apps/windows/package.json:82` `sharp@0.34.5` | 已有，切图/缩放/对齐/拼图集均可覆盖，**无需新增依赖** |
| 技能系统 | `apps/windows/bundled-skills/`（`SKILL.md` + `scripts/`，支持 `[executable]` 入口） | 已有。可承载「编排与判断」，不承载像素操作 |
| 可执行技能入口 | `packages/agent-runtime/src/tools/built-in/execute-skill-tool.ts` | 已有，宿主经 `skillRuntime.executeSkill` 执行 |

**架构级障碍（必须先解）**：宠物模型资源当前**只从应用安装目录解析**（`apps/windows/src/main/pet/pet-model-resolver.ts:83` → `process.resourcesPath/pet-models`），打包后为只读，用户无任何可写位置。即**用户当前无法添加自己的宠物**——这是创作者系统的前提条件，即使不引入 Agent 也必须先解决。

**能力边界（关键结论）**：主流生图模型**结构性无法直接产出精灵图序列**：

| 限制 | 后果 |
| --- | --- |
| 输出无透明通道 | 精灵图必须有 alpha，需后处理抠底 |
| 尺寸仅支持 1024 / 1536（`image-generate-tool.ts:60-68`） | 做不出 32×32 像素帧 |
| 无像素网格概念 | 像素风要求的整数网格对齐无法保证 |
| 帧间无一致性保证 | 「同一动作第 1/2/3 帧」体型五官逐帧漂移，拼合后动作不成立 |

因此**「AI 直出序列帧」不作为主路径**。正确分工为：**AI 生成静态部件**（身体 / 表情差分 / 口型档位 / 场景 / 道具 / 缩略图），**动画由运行时程序化合成**（呼吸、摇摆、眨眼、浮动、点头等原语）。透明度限制通过「纯色底 + 后处理抠底」绕过。

图生图参考链（以上一帧为参考生成下一帧）是序列帧唯一可能成立的路径。**已实测（验证点 D）**：

| 对比 | 剪影 IoU |
| --- | --- |
| 相邻一跳 | **91–93%** |
| 相隔三跳 | **73%** |

**每跳忠实，但漂移累积且不自纠正**；且**参考图会压过文字提示** —— 实测要求「回到站立」时，模型仍保持参考帧的坐姿比例（与参考帧 IoU 93.1%）。

→ **链式图生图不可作量产手段**（除非改为始终参考同一张锚点图）。

**已实测的更优路线 —— 直出图集**：让模型**一次生成多姿态图集**（如 2×2 四格）。实测四格角色一致（调色板重合 93.3%）、互不越界（边界带非角色像素 0）、抠底可用；仅取景与尺度不统一，而这正是精灵流水线本就要处理的步骤（逐格抠底 + 按共同地线对齐，已在验证点 A3 验证误差 0px）。

→ **素材生产推荐走直出图集**：一致性由单次生成天然保证，成本为链式的 1/N。

### 3.3 渲染后端现状核查

**结论：渲染后端抽象已预留，`PetOrchestrator` 与 Prompt 链路对本重构零改动。**

| 事实 | 位置 | 影响 |
| --- | --- | --- |
| 语义渲染接口已 DOM 无关 | `packages/pet-core/src/render/pet-renderer.ts:28` `PetCoreRenderer` | sprite 后端只需实现 `setExpression`/`playMotion`/`playRandomMotion`/`getMotionCount`/`setMouthOpen`/`resize` 六个方法 |
| 宿主端扩展接口已定义 | `apps/windows/src/renderer/pet/renderer/types.ts:32` `PetRendererProvider` | 补 `hitTest`/`isPointerOverModel`/`setPosition`/`getModelScreenBounds`/`setFpsCap` 等 DOM 能力 |
| 精灵帧后端已在规划内 | `apps/windows/src/renderer/pet/renderer/types.ts:7` 注释「MVP 仅实现 Live2dPetRenderer，精灵帧后端留远期」 | 本次即兑现该规划 |
| 渲染类型已含 sprite | `apps/windows/src/renderer/pet/config/pet-model-types.ts:9` `PetRendererType = 'live2d' \| 'sprite'` | 类型无需新增，仅需落地实现 |
| **后端选择处硬编码** | `apps/windows/src/renderer/pet/components/PetCanvas.tsx:117` `new Live2dPetRenderer()` | **唯一的接入点**，需按 `rendererType` 分发 |
| 动作播放回调已通用 | `apps/windows/src/renderer/pet/orchestrator/PetOrchestrator.ts:128` `setMotionPlayedListener` | 控制坞动作名展示对后端无感知 |
| Prompt 注入只读注册表 | `apps/windows/src/main/pet/virtual-human-context.ts:104` | `emotionMap`/`motionActions` 语义平移即可，无需改提示词模板 |
| 注册表解析在主进程 | `apps/windows/src/main/pet/pet-model-resolver.ts` | 需新增清单文件路径解析，registry 结构不变 |
| 依赖现状 | `apps/windows/package.json`：`pixi.js@6.5.10` + `pixi-live2d-display@0.4.0` + `sharp@0.34.5` | sprite 后端复用 pixi.js，图像处理复用 sharp，**不新增依赖** |

**Live2D 现状的额外事实**：

- Cubism Core（`apps/windows/resources/live2d/live2dcubismcore.min.js`）是 Live2D 专有许可文件，随应用分发，开源项目需持续承担合规说明义务。
- 模型体积：mao_pro 9.2MB / ug_official 3.3MB / xiaomai 3.0MB，合计约 15.5MB。
- 现有实现存在一处时序级复杂度：口型覆写必须挂在 `internalModel` 的 `beforeModelUpdate` 事件上，否则被待机动作覆盖（`apps/windows/src/renderer/pet/renderer/live2d/Live2dPetRenderer.ts:101` 附近注释）。精灵图后端不存在该问题。

## 四、方案对比与选型

### 4.1 渲染后端去留（方案 A/B/C）

| 方案 | 说明 | 优势 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **A 保留但不默认启用** | 保留 `Live2dPetRenderer` 与 Cubism Core，默认模型切 sprite，仅在用户导入 Live2D 模型时激活 | 现有三个模型不失效；保留未来接商用 Live2D 模型的能力；渲染器已稳定且有测试，属低频维护 | 继续维护 650 行；Cubism Core 专有许可仍随包分发 | **采纳** |
| B 彻底移除 | 删除渲染器、`pixi-live2d-display`、Cubism Core | 卸载专有许可负担与约 5MB 依赖 | 三个现有模型全部下线；未来接商用模型需重做 | 否决（不可逆且收益有限） |
| C 保留且仍为默认 | sprite 仅作扩展线，Live2D 维持默认 | 无迁移动作 | 默认线仍是「仅限开发测试」资产，问题未解 | 否决（不解决核心矛盾） |

**合规缓解（随 A 一并执行）**：默认模型切为 sprite 后，Live2D 样本模型与新仓库一同从默认安装包中移除，改为「可选下载 / 用户自行导入」，发布检查清单相应更新。

### 4.2 资源组织（方案 A/B/C）——本期实测选型

这是本设计**唯一待实测决定**的选型。三种模式在槽位级共存于同一份清单格式，可平行验证。

| 方案 | 资源组织 | 场景 B 资源量估算 | 实现成本 | 预期问题 |
| --- | --- | --- | --- | --- |
| A 整体帧 | 每个「表情×口型」组合一套完整帧 | 12 表情 × 4 口型 × 动作数 ≈ **300–600 帧** | 最低 | AI 跨帧一致性差；动作扩充时组合爆炸 |
| B 分层差分 | 身体/眼睛/嘴三层分离，运行时叠加 | 表情 12 + 嘴 4 + 眼睛 12 ≈ **40 张** | 最高（需图层对齐工具链） | 像素风图层对不齐会抖动，需偶数坐标对齐约束 |
| C 混合 | 身体动作用整体帧，面部用分层覆盖 | ≈ **60–100 帧** | 中 | 面部覆盖层需遮罩，否则头发/角穿模 |

**实测结论（2026-09-20，见 [验证报告](../../test/pet-sprite/验证报告.md) 与 [P0-b 实施计划](../../plans/客户端UI/2026-09-20-宠物自制系统P0-b实施计划.md) §6）**：**选方案 C（混合）**。

**P0-b 的三方案实测**（同一套几何、同一份渲染器，差异只来自资源组织；脚本 `verify/pet-sprite/check-p0b-scenarios.mjs` 用 Playwright 驱动 pet-lab 产出）：

| 方案 | 演示帧数 | 图集 | 外推 12 表情 | 运行时口型切换 | 命中区一致性 |
| --- | --- | --- | --- | --- | --- |
| A 整体帧 | 48 | 7.0 KB | **144** | ✗ **结构上不可能** | 100% |
| B 分层差分 | 3 + 表情/口型 | 1.2 KB | 19 | ✓ | 100% |
| C 混合 | 3 + 表情/口型 | 1.2 KB | 19 | ✓ | 100% |

**淘汰方案 A，依据不是帧数而是能力缺失**：口型烘进整帧后没有可切换的图层，
`setMouthOpen(0~1)` 每帧调一次就得重算帧下标、可能触发整帧切换——与「口型是高频小幅变化」
的用法相冲。帧数外推 144 也贴着 150 的阈值，动作一变多就越界。**资源量只是次要理由，主要理由是它表达不了这个交互。**

**B 与 C 在本次实测中资源量相同**（都是 19 帧），差异在**图层对齐风险的暴露面**：
B 把身体也拆成层，作者得对齐身体各层；C 的身体是整体帧，只有面部覆盖层需要对齐。
§7 风险表里「分层方案的图层对齐在真实素材上失效」这条一旦发生，C 只损失面部、
B 整个角色报废。既然两者资源量持平，选退化面更小的那个。

**与 P-1 结论一致**：P-1 测得分层覆盖层在缩放 1×/2× 下与 base 的相对位置差仅 **0.25px**，
7 张图（body 1 + eyes 2 + mouth 4）即实现「眨眼 × 嘴型 4 档」组合。P0-b 补上的是
**方案 A 的淘汰依据**与三方案的端到端可跑性。

**这次实测的边界要说清楚**：占位素材的 body 与 face 是**同一份坐标**画出来的，
对齐误差恒为 0，因此上面的「命中区一致性 100%」并不能证明真实素材的对齐质量——
它证明的是坐标变换、分组筛选、拖拽跟随这条链路没算错。
真实素材的对齐数据仍是 P-1 那次 0.25px 的实测。

验证点 D（图生图序列帧一致性）已于 2026-09-20 执行，结论是**链式漂移不可用、改走直出图集**，
详见验证报告。方案 C 的价值恰在于**不依赖帧序列**，进一步降低了该方向的风险敞口。

### 4.3 渲染实现选型

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| **PIXI `AnimatedSprite`（复用现有 app）** | 复用已初始化的 PIXI Application / ticker / destroy / resize / fpsCap 链路 | **采纳**：零新依赖，降帧、缩放、销毁逻辑可直接复用 |
| 原生 Canvas2D | 另起一套渲染循环 | 否决：与现有 WebGL 穿透/缩放链路割裂，重复造轮子 |
| 新增引擎（Phaser 等） | 引入游戏引擎 | 否决：为纯帧动画引入整引擎，包体与维护成本不成比例 |

## 五、核心设计

### 5.1 架构

```
PetOrchestrator / PetLipSync / PetEmotionMapper     ← 零改动
        │  语义接口 PetCoreRenderer
        ▼
PetRendererProvider                                  ← 接口不变，新增实现
        │
   ┌────┴────┐
   ▼         ▼
Live2dPetRenderer    SpritePetRenderer               ← 新增
（保留，可选用）      （默认）
                          │
                    PIXI.Application（复用）
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
            base 槽     face 槽     scene 槽
          （整体帧）  （眼/嘴分层） （预留）
```

后端选择点在 `PetCanvas`：按 `config.rendererType` 构造对应渲染器，其余逻辑（hitTest 穿透、拖拽、滚轮缩放、降级提示）完全共用。

**资源供给与分层（2026-09-20 追加）**

```
┌─ 框架层 packages/pet-core：资产工具链（固定、可单测、零依赖）
│    cutout 抠底 → slice 切图 → align 锚点对齐 → pack 打包图集 → validate 校验
│    ↑ 唯一正确答案的操作写死在这里，不由 Agent 每次现场发挥
│
├─ 生成层 skill：pet-creator（SKILL.md + 轻脚本）
│    只做编排与判断（拆部件策略、何时该问用户、失败如何回退），不做像素操作
│    经 image_generate（文生图/图生图）产出静态部件 → 调用工具链处理
│
├─ 客户端层 apps/windows：轻量
│    用户宠物目录解析 → 两段式扫描与合并 → 两阶段安装（校验后写入） → 渲染
│    ✗ 不承载生成逻辑   ✗ 不允许 Agent 直接写入
│
└─ 安全边界：Agent 只能写 workspace/outputs/
     由固定 install 子命令校验（尺寸/图集存在性/帧边界/清单 schema）后搬运
     校验不通过 → 装不上，但绝不影响渲染稳定性
```

**资源查找：两段式（内置只读 + 用户可写）**

| 来源 | 位置 | 优先级 | 说明 |
| --- | --- | --- | --- |
| 内置 | `resources/pet-models/`（打包后只读） | 低 | 随包发布，含默认模型 |
| 用户 | `~/.lumii/pet-models/`（客户端数据根） | **高** | 可写，支持导入与 Agent 生成；同 id 覆盖内置 |

用户目录取**客户端数据根**（`~/.lumii`，见 `main/client-data-root.ts`），不用 `app.getPath('userData')`。
后者在 dev 下按 package.json 的 `name` 是 `%APPDATA%/lumii-windows`、打包按 productName 才是
`%APPDATA%/Lumii`——`app.setName()` 在 `whenReady()` 之后调用，改不动启动早期已算好的路径。
而工具链 CLI 不依赖 Electron，无从得知当前模式，两边必然对不上。数据根在两种模式下都是
`~/.lumii`，且 `LUMII_CLIENT_DATA_DIR` 可覆盖，便于隔离测试（该问题在 P0-a 实施时实测撞到）。

注册表合并：扫描两个目录的模型清单后合并，同 `id` 以用户目录为准（保证内置模型可被用户版本覆盖，也便于用户迭代内置角色）。

### 5.2 资源清单格式 v1

**设计要点：模式在槽位级选择，而非模型级互斥**。序列帧模型的清单退化为「无 `slots` 的整体帧」，分层模型在同一份 schema 内声明分层槽——三种方案共用一份格式，P0 实测时可直接横向对比。

```jsonc
{
  "id": "demo_pixel_cat",
  "rendererType": "sprite",
  "pixelArt": true,                    // true → nearest 采样 + 缩放整数倍吸附
  "canvas": { "w": 128, "h": 128 },
  "anchor": [0.5, 0.92],               // 脚底中心，便于"站在桌面上"
  "atlas": "atlas.webp",
  "atlasJson": "atlas.json",           // TexturePacker / Aseprite 通用格式

  "slots": {                            // 省略整个字段 → 退化为整体帧方案
    "base":  { "kind": "whole-frame" }, // 身体动作（整体帧）
    "face":  { "kind": "layered", "at": [64, 40],
               "parts": { "eyes": [], "mouth": [] } },
    "scene": { "kind": "layered", "at": [0, 0], "parts": { "prop": ["prop_none", "prop_ball"] } }
  },

  "animations": [
    { "group": "Idle",   "index": 0, "kind": "loop", "fps": 8,
      "frames": [ { "base": "idle_00" }, { "base": "idle_01" } ] },

    // 程序化动画：无 frames，由运行时原语合成（生成线主用）
    { "group": "Idle", "index": 1, "kind": "loop", "source": "procedural",
      "params": { "bob": 3, "breathe": 1.02, "sway": 1.5, "blink": 3200 } },

    // 混合：身体帧序列 + 程序化叠加
    { "group": "Talk", "index": 0, "kind": "loop", "fps": 8, "frames": [ { "base": "talk_00" } ],
      "params": { "bob": 1 } },

    { "group": "PickUp", "index": 0, "kind": "once", "fps": 12, "next": "Idle",
      "frames": [ { "base": "pickup_00" }, { "base": "pickup_01" } ] }
  ],

  "mouthLevels": ["m0", "m1", "m2", "m3"],   // 每模型自定档数
  "hitAreas": [                               // 按帧/按组的可交互多边形
    { "id": "HitAreaHead", "frames": ["Idle"], "points": [[40,10],[88,10],[88,44],[40,44]] }
  ]
}
```

**关键语义**：

1. **增量帧**：帧条目只声明**本帧变化的槽位**，未声明的沿用上一帧。分层模式下 `{ "face": { "eyes": "happy" } }` 即一次表情切换，无需复制整套帧数据。
2. **循环与一次性**：`kind: "loop" | "once"`，`once` 需给 `next` 指定回到哪个组——补齐 Live2D 库原生「动作播完自动续播待机」的语义，使 `PetOrchestrator` 的既有调度逻辑直接生效。
3. **口型档位**：`mouthLevels` 由模型自定（像素风常见 2–3 档），不写死 0–1 到帧的映射；`setMouthOpen(0~1)` 按档位数等分映射。
4. **`hitAreas`**：多边形按帧/动作组声明。Live2D 走部件网格命中，sprite 无此能力，若不声明则退化为**包围盒**——像素角色包围盒内有大片透明区，会导致鼠标在该区域被吃掉、穿透体验劣化。这是 sprite 路线的已知退化点。
5. **`pixelArt`**：决定纹理采样过滤与缩放策略。像素素材若用线性采样会糊，故需 `nearest` + 滚动缩放吸附整数倍。
6. **动画双来源（2026-09-20 追加）**：`source: "procedural"` 的动画不含 `frames`，由运行时**原语**合成；含 `frames` 的为帧序列。两者可混用——同一动画可有 `frames` 与 `params` 并存（帧序列 + 程序化叠加）。

7. **场景/道具层（P1-e 起可用）**：`slots.scene` 是**一个普通的 layered 槽**，没有专属 API——
   帧本来就能声明任意槽位，`{ scene: { prop: "prop_ball" } }` 就是"举起小球"。
   **渲染器为此没有加过一行代码**：`buildLayers` 按 `manifest.slots` 通用建层，
   `applyState` 通用套用槽位快照。若哪天发现 scene 需要特判，说明槽位抽象漏了东西——
   那要改的是抽象，不是给 scene 打补丁。

   图层次序即 `slots` 的声明顺序，所以把 `scene` 写在 `face` 之后，道具就画在最上层
   （像被角色举着）；写在 `base` 之前则会被角色挡住（像放在身后）。

   「不显示道具」用一个**全透明的空帧**表达（如 `prop_none`），不需要为它加特判：
   对齐时全透明帧被排除出基准计算，打包时照常占一个格子。

**程序化原语（白名单，固定实现）**

| 原语 | 参数 | 效果 | 参数类型约束 |
| --- | --- | --- | --- |
| `bob` | 振幅（像素） | 垂直浮动 | number |
| `breathe` | 缩放倍率（如 1.02） | 呼吸缩放 | number |
| `sway` | 角度（度） | 左右摇摆 | number |
| `blink` | 平均间隔（ms） | 定时切换眼部帧 | number |
| `nod` | 角度（度） | 点头 | number |

**安全约束（硬性）**：`params` 的值**仅允许数值**，不解析任何表达式或函数字符串。清单是**数据，不是代码**——若允许可执行内容，等于为宠物系统开放任意代码执行入口。

该约束已落地为 `packages/pet-core/src/model/sprite-manifest.ts` 的 `validateSpriteManifest`（零依赖纯函数，客户端运行时与工具链共用）。校验规则：

| 规则 | 说明 |
| --- | --- |
| 未知字段一律拒绝 | 顶层与各子对象均有字段白名单，防止夹带 |
| `params` 仅接受有限数值 | 复用 `validateProceduralParams`，拒绝字符串/函数/对象/NaN/Infinity |
| 交叉引用校验 | 提供 `atlasFrames` / `assets` 时校验帧、部件、图集文件是否真实存在 |
| `kind: once` 必须声明 `next` | 且 `next` 指向的组必须存在 |
| **一次报出全部错误** | 不发现第一个就返回，便于作者一次改完 |

**注册表字段平移**：`emotionMap` / `tapMotions` / `idleMotionGroup` / `talkMotionGroup` / `idleMotionFallbackGroup` / `idleMotionRandomGroups` / `personaAddon` / `toolPrompts` 语义完全不变，`PetOrchestrator` 与 `virtual-human-context.ts` 无需改动。

### 5.3 关键流程

**口型驱动**：`PetLipSync` 每帧调 `setMouthOpen(0~1)` → sprite 后端按 `mouthLevels.length` 等分取档 → 切换 `face` 槽的 `mouth` 部件帧。全程无参数插值，不存在 Live2D 的「动作覆盖嘴参数」时序问题。

**动作播放**：`playMotion(group, index)` → 查找 `animations` → `AnimatedSprite` 按 `fps` 推进 → `kind: "once"` 播完触发 `onComplete` → 发 `motionPlayed` 回调（控制坞展示）→ 跳转 `next` 组。

**帧率与降帧**：sprite 以**帧计数**驱动而非时间驱动。`setFpsCap` 降帧时同步降低 sprite 的 `animationSpeed`，避免失焦降帧变成慢动作。

**拖拽（P0 验证场景 A 的额外语义）**：现有拖拽仅 `setPosition`。场景 A 需要扩展：拖拽时进入 `Picked` 状态播「被拎起」动作，释放时按速度积分做抛物线 + 落地判定，落地播 `Land` 一次型动作后回 `Idle`。接口层需要新增「位置/速度变化」的回调或状态查询，**这是本期唯一需要触碰接口的部分**。

## 七、风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 三种资源方案实测差距不明显 | 选型悬空，后续量产方向不明 | 场景 B 专门为「组合数量」设计，若差距不显著则**选择实现成本最低的整体帧方案**（成本优先） |
| 分层方案的图层对齐在真实素材上失效 | 像素风抖动、锚点漂移 | P0 阶段引入**偶数坐标对齐**硬约束；若仍无法稳定，回退混合方案 |
| hitArea 退化导致穿透体验劣化 | 鼠标在角色周围被吃掉，违背桌宠「不打扰」原则 | 逐帧声明多边形；未声明的模型暂用包围盒并在设置页提示局限 |
| AI 生成序列帧的角色一致性 | 帧间形象漂移，动作不可用 | 属素材生产问题非渲染问题；本期用占位素材验证渲染链路，量产链路单独立项 |
| Live2D 保留带来的合规负担 | 开源项目分发专有 Core 需说明义务 | 默认模型切 sprite，Cubism Core 改为可选下载；发布检查清单同步更新 |
| 双示范模型使 P0 周期拉长 | 验证成本上升 | 两个模型**共用动作集与清单结构**，仅美术风格不同；实质是同一份清单跑两条采样路径 |
| **抠底需背景色远离角色色** | 连通性抠底穿透描边，整个部件报废 | 实测：flood fill 容差超过描边色距底色的距离时（如 tSolid=200 > 墨线 189），误差从 0.00028 暴涨 300 倍。**生成提示词必须指定与角色所有颜色（尤其描边）保持足够距离的背景色**，并在安装校验阶段做前置检查 |
| **AI 生图无法直出精灵图** | 生成线主路径不成立 | 已确认属结构性限制（§3.2）。改为「AI 出静态部件 + 代码做动画」，验证点 A/B/C 独立把关 |
| **图生图序列帧误差累积** | 生成的帧序列不可用 | **已实测确认存在**：3 跳后 IoU 降至 73%，且参考图压过文字提示。**缓解：改用直出图集**（已验证可用，见 §3.2） |
| **创作者系统安全面** | 恶意 / 错误清单影响稳定性 | 三层防护：清单仅接受数值参数（禁表达式）、Agent 只能写 `outputs/`、`install` 前强制 `validate`；校验不通过则装不上 |
| 两段式扫描引入模型来源歧义 | 用户不知当前用的是哪个 | 合并规则明确（同 id 用户优先），控制坞显示模型来源标记 |
| 用户目录与内置模型的版本冲突 | 内置模型升级被用户旧版覆盖 | 用户目录优先是**有意设计**（允许用户迭代内置角色）；提供「恢复内置版本」操作 |

### 9.2 手测点

- 双示范模型切换、拖拽移动、滚轮缩放（像素模型需整数倍吸附且不糊）
- 桌面穿透：鼠标移过角色旁的透明区应**穿透到下层窗口**（这是 hitArea 质量的关键验收项）
- 对话全流程：口型张合、表情切换、`[motion:tag]` 触发、待机随机轮播
- **用户自制流程**：手工放入用户宠物目录 → 被扫描到 → 可在设置中选中；同 id 时用户版本覆盖内置版本
- **两阶段安装**：故意放入一份非法清单 → `validate` 拒绝 → 渲染不受影响（宠物不崩、不白屏）
- 失焦降帧下动作速度不变（验证帧计数驱动而非时间驱动）
- WebGL 不可用时的降级提示（复用现有 `onDegrade` 链路）

### 9.3 性能目标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 渲染帧率 | 稳定 60fps（受 `setFpsCap` 上限约束） | 复用 `pet_render_fps` 可观测指标 |
| 内存占用 | 单模型 < 100MB | 对比 Live2D 现状需实测基线 |
| 模型加载耗时 | < 500ms | 图集本地加载，无网络往返 |
| 资源体积 | 单模型 < 2MB | 对比 Live2D 现状 3.0–9.2MB |
