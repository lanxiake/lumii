# 多宠物同屏设计（R11）

需求依据：[`2026-09-21-宠物系统需求分析.md`](2026-09-21-宠物系统需求分析.md) §四 R11（此前一直挂"待定"）。
相关：[`2026-09-21-宠物创作平台预留设计.md`](2026-09-21-宠物创作平台预留设计.md)（R13 会让"用户拥有很多宠物"成为常态）。

---

## 一、先定语义：多宠物在 lumii 意味着什么

这是本项**最根本的问题**，比技术成本更先决。三种可能的语义，产品含义完全不同：

| 语义 | 描述 | 价值 | 与"安静的助手"的关系 |
| --- | --- | --- | --- |
| **S1 多角色装饰** | 用户同时养几只不同的宠物（参考项目那种） | 陪伴感、喜好表达 | **有张力**：桌面上更多视觉元素 = 更吵 |
| **S2 多会话化身** | 每个对话会话一只宠物，反映该会话 Agent 的状态 | 多任务可见 | 一致，但每只都该是"安静的" |
| **S3 多 Agent 任务** | 主 Agent 一只，子 Agent / 后台任务各一只 | 并行任务可见 | 一致，但子 Agent 生命周期短 |

**判断**：

- **S2 / S3 有真实功能价值，但当前需求不明**——`agent:activity:snapshot` 确实带 `agents[]`（含 `isSubAgent`），技术上"一只宠物对一个 Agent 实例"是可行的。但**用户从没提出要监控多个 Agent**，为一个假设的需求做高成本改造不划算。
- **S1 是最可能的意图**（参考项目就是这么用的，且它是参考项目"真正能用"的闭环的一部分：*选 1~3 只*）。但它是纯装饰，与 D1「安静的助手」直接有张力。
- **R13 会改变 S1 的合理性**：当用户能自己造宠物时，"造了很多只想同时摆出来"是自然需求。**R11 的价值会随 R13 上升。**

> **本设计不替用户选语义**。下面给的是**技术方案与成本**，语义确认后再定实施范围。
> 但有一条可以先说：**S1 与 D1 的张力可以按 [`宠物创作平台预留设计`](2026-09-21-宠物创作平台预留设计.md) §1.3 的同一原则化解**——约束我们的默认值（默认单只），不约束用户的上限（用户想养多只是他的选择）。

## 二、技术现状：单例边界（实测）

改造面比想象的大——**不是"复制一份"，而是全链路从单数变复数**：

| 层 | 单例对象 | 位置 |
| --- | --- | --- |
| 渲染 | `canvasRef` / `orchestratorRef` / `orchestratorRendererRef` / `emotionMapperRef` / `modelConfigRef` / `sessionKeyRef` | `PetModeShell.tsx:69-75` |
| 渲染 | 单份 `avatarStatus` / `messages` / `degrade` 状态 | `PetModeShell.tsx:93-105` |
| 渲染 | `PetCanvas` 单组件、`orchestratorRef.current.setModelConfig()` 模型切换是**替换**而非叠加 | `PetModeShell.tsx:233-241` |
| 主进程 | `petWindow` 单窗口、`currentModelId` 单值 | `pet-window-manager.ts:59, 65` |
| 主进程 | 会话绑定 `activeSessionKey` 单值 | `pet-mode-ipc.ts` |
| 存储 | `pet-mode-store.json` 的 `currentModelId` 单值 | `pet-mode-store.ts:32` |

**一处天生的优势**：宠物窗口是**覆盖工作区的单张透明画布**（`pet-window-manager.ts:171-182`），所以多宠物**不需要开多个 OS 窗口**。参考项目恰恰栽在这里——每宠物一个 `WindowManager` 窗口、60FPS 每帧 `updateViewLayout`（3 只 = 每秒 180 次窗口重排）。**lumii 天然避开了它最大的性能陷阱。**

## 三、关键技术约束：不能"多开 renderer 实例"

`SpritePetRenderer.init()` 里每个实例自建 `PIXI.Application({ view: options.canvas, ... })`（`SpritePetRenderer.ts:173-186`）——**一个实例 = 一个 canvas 元素 + 一个 WebGL context + 一套 ticker**。

多开意味着：

| 风险 | 说明 |
| --- | --- |
| **WebGL context 耗尽** | 浏览器上限通常 8–16 个。2~3 只尚可，但这是**会随数量撞墙**的设计（代码里已有 `webglcontextlost` 处理，见 `:187-191`，说明这条路径并非理论风险） |
| **N 套 ticker** | 每个 Application 独立 rAF，帧推进/原语求值各跑一遍，无法统一降帧（`setFpsCap` 失焦降帧在多个 app 上要各调一次） |
| **N 个 DOM canvas** | 全屏透明窗口里叠 N 个全屏 canvas，每帧合成 N 层 |

**结论：多宠物必须共享一个 `PIXI.Application`，每只宠物是一个独立 `Container`（各自持有自己的图层树）。**

这意味着渲染层要做一次结构性改造：把"Application 的创建与所有权"从 `SpritePetRenderer` 里**提出来**，交给一个舞台层；renderer 改为挂载到给定 stage。

> **Live2D 后端同理**：`Live2dPetRenderer` 也自建 app，两套后端需要同一个舞台抽象，否则多宠物在两种后端下行为不一致（这正是 §2.4 已记录的"两套后端能力不对等"的又一次体现）。

## 四、参考项目的实践：**没有好实践可抄**

参考项目做了多宠物，但质量不足以作为参考：

| 项 | 它的做法 | 问题 |
| --- | --- | --- |
| 上限 | `maxPets = 3` 硬编码在 **Service / ViewModel / UI 三处**（其中一处还是字面量字符串 `"/3"`） | 必然漂移 |
| 碰撞 | **零碰撞检测**，除"聚到角落"外宠物互相穿过 | 视觉上糊成一团 |
| 角落排列 | `spacing = petSize × 0.8`，**故意留 20% 重叠** | 取巧，不是解 |
| 环境感知归属 | `handleSystemEvent` 只作用于 `firstOrNull()`——谁感知环境取决于 map 迭代顺序 | 隐式行为 |
| 发言仲裁 | `talkJob` 全局单例，**任意一只说话会取消另一只正在说的话** | 非有意设计 |

**唯一可借鉴的是它的"角落排列"交互**（把所有宠物收拢到左右下角坐下）——这是个好用的"让开"手势，成本低，适合"安静的助手"定位。

## 五、技术方案

### 方案 A：共享舞台 + 多宠物槽（推荐，若要做）

```
PetModeShell
  └─ 一个 <canvas>（全屏）
      └─ PetStage：持有唯一的 PIXI.Application
           ├─ PetSlot[0]：renderer + orchestrator + modelConfig + emotionMapper
           ├─ PetSlot[1]：…
           └─ PetSlot[N]：…
```

| 改造点 | 内容 |
| --- | --- |
| 渲染层 | 新增 `PetStage`（Application 的**唯一**所有者）；`SpritePetRenderer` / `Live2dPetRenderer` 支持挂载到外部 stage |
| 编排器 | 每只一个 `PetOrchestrator` 实例（状态天然独立）；`PetModeShell` 的 6 个 ref → `Map<petId, Slot>` |
| 交互路由 | `PetCanvas` 的 window 监听器改为**先判命中哪只**（按 z 序取最上层），再路由到该 slot；拖拽期间**锁定**该 slot |
| 穿透聚合 | hover 判定改为"任意一只被悬停"，主进程逻辑基本不变（它已经按 `componentId` 聚合） |
| 主进程 | `currentModelId` → `modelIds[]`；窗口仍是单个（**零改动**） |
| 存储 | `pet-mode-store` 增加列表字段；保留单值字段做向后兼容 |
| 控制坞 | 增加"当前交互对象"的选择（默认：最近说话的那只） |
| 设置 | 模型选择从单选变多选（上限建议 3，**上限值只在一处定义**） |

**关键设计约束**：

1. **窗口层零改动**——这是 lumii 相对参考项目的结构性优势，务必保住，别退化成多窗口
2. **上限只定义一次**（放 `pet-core` 或 shared 常量），三处硬编码是参考项目的现成教训
3. **交互仲裁必须显式**：发言/动作的互斥规则要写清楚（参考项目的"任一只能取消另一只发言"是 bug 不是设计）
4. **宠物间斥力**：至少要有"不重叠"的最小间距——参考项目零碰撞检测的后果是糊成一团

### 方案 B：不做

保持单只，把精力放在 R5/R6（状态可见化）与 R1-R4（修断点）。

## 六、成本与风险

| 项 | 评估 |
| --- | --- |
| **工作量** | 高。不是"加功能"，是**把宠物模式的接线层从单数改写成复数**——渲染舞台重构 + 编排器多实例 + 交互路由 + 存储/设置改造 |
| **最大技术风险** | 渲染层重构成共享 stage 时，**两套后端都要改**，且 Live2D 的 `autoLoopsIdle`、动作优先级等差异（§2.4）会在多实例下放大 |
| **最大产品风险** | 语义未定——若最终只是 S1（装饰），高成本换来的可能是与"安静的助手"相冲突的视觉噪音 |
| **回归风险** | 单实例是当前唯一被充分验证过的路径（P0-b / P2-a / P2-b / P2-c 全部在单只上验证）；改成多实例后，**这些验证全部需要重跑** |

## 七、决策（2026-09-21）

> **本期不做。** 方案固化在本文，触发条件满足时重启。

理由：

1. **语义未决**是根本问题——技术成本再清楚，也不该为一个没定的产品目标付出"重写接线层"的代价
2. **有更优先的事**：R5/R6（让 Agent 状态可见）是 D1「安静的助手」的全部意义所在，且成本低得多
3. **参考项目在此没有好实践可抄**，等于要独立趟一遍，风险与收益不成比例
4. **R11 的价值会随 R13 上升**——当用户能自己造宠物后，"想同时摆出几只"才成为真问题。**那时再做，需求也更明确**

**触发条件**（满足其一即可重启本项）：

- 用户明确提出"想同时养几只宠物"（S1）
- 出现"同时监控多个 Agent / 会话"的真实需求（S2 / S3）
- R13 创作平台落地后，用户造出的宠物数量显著多于 1

**若重启，建议的落地顺序**：

1. 先做**渲染舞台重构**（单只状态下完成，验证零回归）——这是最大的一块，且能在单只场景下充分验证
2. 再做**多实例编排**（第二只作为"只读展示"跑起来，无交互）
3. 最后做**交互路由与仲裁**（命中、拖拽、发言互斥）

> 这个顺序的关键是**第一步可以独立于多宠物需求提前做**——它是一次纯粹的架构改进（消除 N 个 WebGL context 的隐患），做完即收益，不做也不阻塞。

---

## 八、验收（若实施）

- **性能**：3 只同屏 60FPS；WebGL context 数恒为 **1**；失焦降帧对全部宠物同时生效
- **交互**：点击/拖拽/滚轮各自命中正确的宠物；拖拽期间不误触其他宠物
- **穿透**：任一只身上的 hover 都能恢复窗口可点；宠物之间的透明区仍穿透
- **仲裁**：一只说话时另一只的行为有明确、可预测的规则（且规则写进设计，不是隐式 map 顺序）
- **回归**：P0-b / P2-a / P2-b / P2-c 的既有量化判据在单只场景下全部复跑通过
- **上限**：数量上限在**唯一一处**定义，UI 与服务端读取同一常量
