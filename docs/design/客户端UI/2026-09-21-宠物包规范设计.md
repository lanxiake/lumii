# 宠物包规范设计（修断点 + 素材重跑）

需求依据：[`2026-09-21-宠物系统需求分析.md`](2026-09-21-宠物系统需求分析.md) §四 R1-R4、§五 决策 D3。
相关：[`2026-09-21-宠物创作平台预留设计.md`](2026-09-21-宠物创作平台预留设计.md)（未来用户自制同一套规范的产出方）。

---

## 一、问题：四个断点是同一个根因

| 断点 | 缺失的东西 | 缺失后的实际行为 |
| --- | --- | --- |
| B1 情绪演不出 | `slots.face` + 语义 `emotionMap` | 查不到映射 → 打 warn → **宠物一张脸** |
| B4 点击无动作 | `hitAreas` 声明 | `hitTestPolygons` 在 `hitAreas` 为空时**恒返回 null** → `tapMotions` 的 key 永远匹配不上 → **静默 return**（不是"退化到包围盒"：`isPointerOverModel` 里那次 `getBounds()` 只用于鼠标穿透判定，与点击触发无关） |
| B5 说话嘴不动 | `mouthLevels` | `mouthBinding` 恒 null → `setMouthOpen` 直接 return → **两套 LipSync 每帧白跑** |
| B6 打盹看不见 | 素材命名与代码候选名脱节 | 候选名命中 **0/5** → 脸上不演、只停动作 |

**共同点：缺失是静默的。** 作者（无论是 AI 技能还是用户）不知道自己做少了什么，用户只感觉到"开了没用"。

所以本规范要解决的不是"多几个字段"，而是**把静默失败变成可检出的契约**。

## 二、合格线：一个宠物包至少要声明什么

### 2.1 分级

| 级别 | 含义 | 缺失后果 |
| --- | --- | --- |
| **必需** | 缺失即功能残废 | `validate` 拒绝安装 |
| **推荐** | 缺失可降级，但能力打折 | `validate` 通过 + **作者可见警告** |
| **可选** | 锦上添花 | 无提示 |

> **关于"必需"的取舍**：不把表情层列为硬必需——像素角色可能天然只有整体帧，强行拒绝会挡住合法的简单模型。**但必须让降级可见**（§四）。

### 2.2 清单

| # | 字段 | 级别 | 为什么 |
| --- | --- | --- | --- |
| 1 | `id` / `rendererType` / `canvas` / `anchor` / `atlas` / `atlasJson` | **必需** | 已有校验覆盖 |
| 2 | `animations` 至少含一个 `kind: "loop"` 的待机组 | **必需** | 没有待机就没有"活着"的基线 |
| 3 | `slots`（至少 `face` 表情层） | **推荐** | 缺了 Agent 情绪透不出来（B1） |
| 4 | `emotionMap` 含**语义键**（§三.2） | **推荐** | 同上 |
| 5 | `mouthLevels`（≥2 档） | **推荐** | 缺了说话嘴不动（B5） |
| 6 | `hitAreas`（至少一个覆盖身体的区域） | **推荐** | 缺了点击无回应（B4） |
| 7 | `animations` 含 `Idle` 与 `Talk` 组名 | **推荐** | 编排器默认按这两个名字找组 |
| 8 | `params`（呼吸/眨眼等原语） | **可选** | 缺了是静止的，但不是坏的 |
| 9 | `slots.fx`（**特效层**：星星/爱心/汗滴/闪光等图集部件） | **可选** | 有则角色自带视觉反馈，且**零运行时机制成本**（与表情层同一套 `slots` 机制，见 [`宠物创作平台预留设计`](2026-09-21-宠物创作平台预留设计.md) §3.3） |

## 三、命名约定（B4 / B6 的真正根因）

两个断点都不是"缺字段"，而是**两套命名体系对不上**。

### 3.1 命中区 id ↔ `tapMotions` key

**现状**：`PetCanvas.tsx:464` 在命中区缺失时传字面量 `'body'`；而注册表里写的是 Live2D 风格的 `HitAreaBody`。两者永不相等。

```
sprite 侧：hitTest() → null → 传 'body'
注册表侧：tapMotions: { "HitAreaBody": { "Wave": 0 } }
                                        ↑ 永远查不到
兜底链：['body', 'Tap', 'tap', 'TapBody', '$unnamed']  ← 三只模型的动作组是 Idle/Talk/Wave，全部为 0
```

> ⚠️ **本节建议已被实现覆盖，且方向要反过来**（2026-09-21 二次核查）：
> 实际实现用的是 `HitAreaHead` / `HitAreaBody`（`packages/pet-asset/src/hit-areas.ts:250-251`，从帧的 alpha 轮廓自动生成），注册表 key 也是它。
> **「统一命名 `body`」这条不要执行——那会把刚修好的链路重新打断。**
> 约定应当是：`hitAreas[].id` 即 `tapMotions` 的 key，**sprite 身体区用 `HitAreaBody`**（与自动生成器保持一致）。

> ⚠️ **本条已作废（2026-09-21 二次核查）**：问题不在兜底链不够宽，**是 `hitAreas` 缺失**。
> 并行会话已补上 `hitAreas`（8 个 sprite 包全有），链路第一分支就命中 `tapMotions[HitAreaBody]`，**兜底链根本不会被走到**。
> 「追加任意 `once` 组」不必做，且语义上有反例：`Land`（`gen-demo-pets.mjs:450`，语义是"刚刚落地"）会被选中——站在地上的宠物被点一下却演"落地"。这与 `PetOrchestrator` 既有的「语义不对的动作比不播更糟」原则冲突。

### 3.2 表情语义键 ↔ 代码候选名

**现状**：素材命名是 `eye_happy` / `exp_01`，代码候选名是 `sleepy` / `困` / `drowsy`，实测命中 **0/5**。

**约定**：`emotionMap` 必须包含以下**语义键**（值指向具体部件索引）：

| 键 | 用途 | 触发方 |
| --- | --- | --- |
| `neutral` | 基线 | 默认 |
| `joy` | 正向 | Mood（valence>0.3 && energy>0.6）、闲置醒来 |
| `sadness` | 负向 | Mood（valence<-0.3） |
| `surprise` | 唤起 | Mood（arousal>0.6） |
| `sleepy` | 打盹 | 闲置感知（P2-c） |

> **`sleepy` 是新加的语义键**——它是 B6 的直接修复。此前代码候选名里没有它，五只模型全部落空。

**为什么必须是语义键而不是素材名**：`emotionMap` 是**代码与素材之间唯一的翻译层**（registry.json 里每个模型自己定义）。让代码去猜素材叫什么，就是把翻译责任推给了最不该承担的一方。

### 3.3 动作组名（既有约定，此处固化）

| 组名 | 约定 | 声明方 |
| --- | --- | --- |
| `Idle` | 循环待机 | `idleMotionGroup` |
| `Talk` | 循环说话 | `talkMotionGroup` |
| `Picked` | 被抓起的单次动作 | 约定组，模型声明了才播 |
| `Land` | 落地的单次动作 | 同上 |

Picked / Land 的"**声明了才播、没声明就静默跳过**"是 P2-a 定下的正确做法（"播一个语义不对的动作比不播更糟"），**保持不变**。它与本规范不冲突：本规范要求的是**降级要可见**，不是要求必须演。

## 四、降级必须可见

这是本规范与现状最大的分歧点：**现状是静默的，规范要求每一步降级都留下痕迹**。

| 缺失 | 现在的行为 | 规范要求 |
| --- | --- | --- |
| 无表情层 | 运行时不报，Prompt 只注入 neutral | `validate` 警告 + 设置页该模型标注"无表情层" |
| 无 `mouthLevels` | `setMouthOpen` 直接 return，LipSync 白跑 | `validate` 警告 + **关掉该模型的 LipSync 驱动**（省掉每帧空转） |
| 无 `hitAreas` | 点击静默 return | 走 §三.1 的兜底链；仍无可用组时冒提示气泡"这只宠物还没有点击动作" |
| 语义键缺失 | 打 warn | 设置页可见 |

**"关掉空转"这条是额外收益**：现在两套 LipSync 对无口型层模型每帧求值后丢弃，属纯浪费。

## 五、三只示范模型的补齐路径（**前提已修正**）

> ⚠️ 本节原写"用已有能力重跑生成即可"，**基于一个错误推断**，已作废。
> 实测证明：差分取层能力（`fccc1cd2`，11:01:41）**早于**模型入仓（11:33）；能力落地后**已重跑过**——表情批累计出图 **19 次（猫 10 / 机甲 9）一次都没过阈值**；用 HEAD 版 difflayer 复跑归档帧**确定性复现失败**（机甲 `eye_open` density 0.299 < 0.3；猫 `eye_sad` bbox 51% > 50%）。
> 根因是**残差噪点圈**（`rawChanged` ≈ `changed` 的两倍，连通域散布在角色周围把包围盒撑到 40–60%）。详见需求分析 §2.2 B1 二次核查。

**因此要区分两类断点——它们的解法完全不同：**

| 断点 | 依赖差分取层？ | 可行路径 |
| --- | --- | --- |
| **B1 表情层** | ✅ 是（差分取层正是为它做的） | 三条路：**改判据**（放宽 `MAX_DIFF_AREA_RATIO` / `MIN_DIFF_DENSITY`，风险是把噪点当表情）／**改出图策略**（让表情差异更大、噪点更少）／**承认这两只没有表情层**。前两条都需要重新验证，不能想当然 |
| **B5 口型层** | ⚠️ **需确认**——口型批同属 `kind: expression`，走的是同一条差分链路，**很可能同样卡住** | 先确认；若同样失败，考虑**整帧替换**式口型（不走差分），但那是另一套方案 |
| **B4 命中区** | ❌ 不依赖 | ✅ **已解决**（并行会话已补 `hitAreas`，8 个 sprite 包全有；`hit-areas.ts` 从 alpha 轮廓自动生成）。**只差真机点击验证** |
| **B6 打盹命名** | ❌ 不依赖 | 改名对齐即可，纯数据改动 |

**这条区分很重要**：B4/B6 现在就能修，不必等 B1/B5 的素材问题解决。**不要把它们绑在一起**。

原表按"重跑后"列出的目标作废；新的目标应是**分断点独立推进**，各按上表路径走。

**动作组保持不变**（Idle / Talk / Wave）——按决策 D1「安静的助手」，不需要更多动作；点击动作靠 §三.1 的兜底链直接复用 `Wave`。

**出图批次设计**（每批一次生图）：

```
1. 表情批  kind: "expression", part: "眼睛", variants: ["睁眼","闭眼","笑眼","难过","困倦"]
   → 5 款差分，覆盖 neutral / joy / sadness / sleepy / surprise
2. 口型批  kind: "expression", part: "嘴",  variants: ["闭嘴","半开","全开"]
   → 3 档，满足 mouthLevels ≥2
```

> 表情批的 `variants` 读序即差分顺序，与 `emotionMap` 的索引一一对应——**这一步不能靠人记，应由脚本写入**（§六）。

## 六、对 `pet-creator` SKILL.md 的修改点

技能是规范的主要产出方，必须同步。当前 SKILL.md 已支持表情批（`kind: "expression"` + `part` + `variants`），缺的是：

| # | 补充 | 解决 |
| --- | --- | --- |
| 1 | 出图计划**默认包含一批表情批与一批口型批**（除非用户明确只要像素整体帧） | B1 / B5 |
| 2 | 脚本在写清单时**自动生成 `emotionMap` 语义键**，而不是让模型手写 | B6 |
| 3 | 脚本默认写入 `hitAreas`（按抠底后的 alpha 包围盒生成多边形，或先给矩形） | B4 | **已实现**，见 §八 |
| 4 | 收尾自检：对照 §二.2 清单逐项检查，缺失项**报告给用户**而不是静默通过 | 全部 |
| 5 | （可选）出图计划可包含**特效批**——与表情批同构（同机位、透明底、逐格变化），产出 `fx` 槽位，供"点击→播特效动作组"使用 | 表现力 |

**第 3 条有现成基础**：`pet-asset` 的 `slice` / `align` 已经在算 alpha 包围盒（`align.ts` 用底边做地线），生成一个保守的命中矩形是顺手的。

## 附录：顺带发现的实现瑕疵（与本规范相关，建议一并修）

代码走查中发现的三处，都不是设计问题而是实现疏漏，且都落在本规范涉及的链路上：

| # | 位置 | 现象 | 影响 |
| --- | --- | --- | --- |
| 1 | `PetCanvas.tsx:438` | `hitTest` 的结果存进 `dragRef.current.hit`，但**从未被读取**（死字段） | 无功能影响，属清理项 |
| 2 | `PetCanvas.tsx:550` | `tapMotions[hitArea]` 只取 `Object.entries(...)[0]`——**作者配多条会被静默丢弃** | 与 B4 同源："静默"是本规范要消除的东西 |
| 3 | `PetFakeLipSync.ts:449-456` vs `packages/pet-core/src/lipsync/mouth-waveform.ts:22-29` | 同一套波形算法**两份实现**，Windows 端未引用 pet-core 那份（注释还声称"抽出的纯波形算法"，实际没接） | 两份常量会各自漂移；pet-core 那份是纯函数、本可单测 |

第 3 条与本规范同源：**实现声称与实现事实不一致**。要么接上 pet-core 那份，要么删掉它——不要留着一份"看起来是正本、实际没人用"的代码。

## 八、B4 修复记录（补 `hitAreas`）

2026-09-21 完成。§六 第 3 条落地为：

| 位置 | 内容 |
| --- | --- |
| `packages/pet-asset/src/hit-areas.ts` | 纯几何：从一张帧的 alpha 轮廓推 `HitAreaHead` / `HitAreaBody`（12 条单测） |
| `packages/pet-asset/src/toolchain.ts` | `runDeriveHitAreas` —— 读盘 + 调纯函数，只读不写盘 |
| `apps/windows/src/main/pet/pet-asset-ipc.ts` | 新 op `hitAreas` |
| `pet-creator/run.ts` | 打包时用 **Idle 首帧**推，写进清单 |
| `compose-review.mjs` | 同上（跳过闸门的检查版那条路） |
| `patch-hit-areas.mjs` | 给**已装好的**包补字段的修复脚本（只动清单、不动图集） |

三处与 §六 原文的偏离，都是实测逼出来的：

1. **不用包围盒，用逐行贴着轮廓扫的多边形。** 包围盒会把角色旁边的透明区圈进去，
   而 `isPointerOverModel` 先看 `hitTest` ——鼠标在那片空白里会被宠物窗口吃掉、
   穿不到下层窗口。逐行扫描贴住轮廓，两个问题一起解掉。
2. **基准帧取 Idle 首帧，不是随便一帧。** 其它动作会把轮廓撑开（举手）或收窄（下蹲），
   据此推的命中区会随动画呼吸而抖动，点同一个位置时灵时不灵。
3. **`patch-hit-areas.mjs` 是必要的，不是偷懒。** 三只示范宠物里 `cartoon_cat` /
   `mecha_gundam` 的**原始图是旧网格**（待机 2×2、挥手 3×2），与当前 `plans.json`
   （4×1 / 2×2）不符——照计划重切会把帧切坏。它们要重新出图才能对齐计划。

### 8.1 覆盖率（实测）

「覆盖率」= 命中区盖住的**角色不透明像素**占比。三只示范宠物：

| 角色 | 覆盖率 | 未覆盖的是什么 |
| --- | --- | --- |
| `demo_anime_girl` | **98.39%** | 轮廓边缘 1–2px 的细条；最差一行只剩轮廓最尖那一行的 5 个像素 |
| `demo_cartoon_cat` | **98.57%** | 同上 |
| `demo_mecha_gundam` | **98.04%** | 同上 |

采样行数选 32（默认）而非更少，判据不是「覆盖率多那半个百分点」，而是
**「某一整行里有大片点不到」这件事消失了**——8/12/20 行时都存在某一行漏掉 17–26%。

还有一个反直觉的坑记在这里：**轮廓包围盒的最上/最下一行是轮廓收成尖的地方**
（樱桃脚底 y=441 整行只有 5 个不透明像素，而 y=432 有 44 个）。
只按那一行取样，多边形会从上一采样点直接连到这个近退化的尖点，**中间 9 行被直线切掉**
——实测 y=439 有 70% 的角色像素点不到。修法是首尾各取半格窗口的并集，
代价是最底部几行略微多覆盖一点空白；命中区本就该偏保守。

**尚未解决**（B4 之外）：三只的原始图**都过不了 `sheetCheck` 闸门**
（最差越界：挥手 0.56% / 猫 28.6% / 机甲 21.9%，上限 0.50%），
`resources/` 里的是跳过闸门的检查版。详见
[`2026-09-21-桌宠动作生成方案调研.md`](2026-09-21-桌宠动作生成方案调研.md) §七·补。
