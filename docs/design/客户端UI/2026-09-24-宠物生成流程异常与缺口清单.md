# 宠物生成流程 · 异常与缺口清单（2026-09-24 月兔小仙实跑）

这一轮的定位：**用一只新宠物（月兔小仙）把「路线 A：AI 直出图集」整条链路跑一遍，
目的不是产出这只宠物，而是把流程本身调到能稳定复用。**

下面每条都带「现象 / 根因 / 影响 / 状态」。状态分：**已修** / **待定** / **观察**。

## 零、最重的一条：流程不该要求用户说技术术语

用户原话（2026-09-24）：

> 你使用客户端对话时应该使用人类的自然语言，模仿非专业的真实来输出提示完成任务，
> 太专业了，普通人也完不成这个任务

**这条推翻了我前面「把参数给清楚就行」的整个思路。**

我下发给客户端 Agent 的任务书里写满了 `diffBase`、`emotionMap` 索引、`idlePin`、
`slot: "base"`、`group`/`kind`/`next`……那是我为了**调试**需要精确控制才写的。
它是**我的需求，不是用户的需求**。一个普通人想做只宠物，会说「给她加个挥手的动作」，
不会写 `"group": "Wave", "kind": "once", "next": "Idle"`。

**而且这轮恰好证明了「说清楚也不管用」**：我把完整的 build 参数逐字照抄给了 Agent，
它仍然没照用——自己重新组织了参数，结果 `group` 丢了，
wave/nod 两个批次的帧被拼进了同一个 Idle 循环（16 帧），
而 `tapMotions` 指向的 `Wave`/`Nod` 在清单里根本不存在。
**参数给得再细，也不能替代 skill 自己把事情做对。**

→ 合格线应该是：skill **接得住一句人话，自己补全参数**。
现在正好反过来——用户得先学会这套术语才能用。

## 一、已修（改在正本上，不只是绕过）

### 1. `plan` 把批次规格丢在转发层 —— `apps/windows/bundled-skills/设计与可视化/pet-creator/run.ts:276`

- **现象**：`action:"plan"` 渲染出的提示词里**没有「动作经过」**；同时 warning 报
  「这个批次没给 motion（动作经过）」——而调用方明明给了。
- **根因**：`runPlan` 往控制口转批次时只挑了 `action/cols/rows` 三个字段，
  `motion`、`kind`、`part`、`variants`、`loopMode` 全被丢在这一层。
  而 `buildSheetPlan` 是支持它们的（`SheetBatchSpec`），warning 也由它发出。
- **影响**：**两条 SKILL.md 反复强调的硬要求根本到不了渲染器**——
  ① 动作批退化成「四个看着像挥手的姿势」（`real_dog` 那类事故的成因）；
  ② 表情批按 motion 模板渲染，而模板说「每格是上一格的下一时刻」，
  对表情批是**反的**。走路线 A 的每一个人（包括客户端 Agent 自己）都中招。
- **状态**：**已修**，改成整体透传（`undefined` 经 JSON 序列化会被丢掉，不传时行为不变）。

### 2. 创作段的「禁止阿拉伯数字」把 hex 颜色码也算进去 —— `packages/pet-asset/src/sheet-prompt.ts:269`

- **现象**：任何按规范写的角色描述，都会稳定收到 5 条
  「创作段里出现了阿拉伯数字——改成中文数字或去掉」。
- **根因**：`ARABIC_DIGIT = /[0-9]/` 直接测整段文本，而规范（宠物开发规范 §八 硬规则③）
  要求创作段写「**颜色名 + hex**」——hex 必然含阿拉伯数字。
- **影响**：警告**没法照办**（hex 改不成中文数字），而且永远误报；
  真写了「第1格」时那条真警告反而被淹没。
  `sheet-prompt.test.ts:125` 早有「除 BACKGROUND 的色值外不出现阿拉伯数字」的用例，
  说明**色值例外本来就是设计意图**，只是这条字符检查没跟上。
- **状态**：**已修**（先剔 `#RGB/#RRGGBB/#RRGGBBAA` 再判数字），补了 3 个测试；
  `#1` 这类短编号不会被误放行。
  ⚠ 它在 App 主进程里跑，**要重启 App 才生效**。

### 4. 两份 `alphaBBox` 的默认阈值分歧（128 vs 16）—— 验收会被误导

- **先澄清：工具链是对的。** `packages/pet-asset/src/cutout.ts:253` 的
  `alphaBBox(buf, w, h, thr = 128)` 自带阈值；对鲤鲤那张立绘实测给出 bbox **516×1158**，
  与独立复算（thr=200 → 516×1157）一致。
- **有分歧的是 `verify/pet-sprite/lib/cutout.mjs:178`**：同名函数默认 `thr = 16`。
  同一文件里 `alphaCentroidX` 的注释写着「**必须与 `packages/pet-asset/src/cutout.ts`
  完全一致**」——说明这一族函数的设计意图就是镜像工具链，`alphaBBox` 的阈值属于漏改。
- **现象**：鲤鲤立绘实心内容 516×1158，verify 版报 **1254×1203（整幅）**，
  掩膜填充率从真实的 58.7% 掉到 23.4%。原因是 alpha 17–31 的散点
  （约占 0.1%，一千多个）落到画面四角，把**极值统计**的包围盒撑满。
- **影响**：**照它判断会得出「这张图抠底废了」的错误结论**，
  而重出一张图要一分钟和一次真金白银。本轮我自己就被它误导过一次。
- **状态**：待定。建议把默认值对齐到 128，或至少在注释里写明这处分歧、
  要求验收脚本显式传参。

### 5. 调试脚本 `app.exit()` 不 flush stdout —— 这轮坑得最深的一条

- **现象**：生图脚本退出码 1，日志停在「进度 2%」，**没有任何错误行**；
  我据此判定「带参考图的两批全失败」。
- **真相**：其中**眼睛差分其实成功了**（文件 18:36:51 落盘，出图闸门 `verdict=ok`，
  四格包围盒 341×582/582/583/582 高度一致，是合格的表情批）。
  失败的是同一批里的口型差分。日志被缓冲区吞了，于是我**误判了自己的产物**，
  差点让 agent 重出一张已经合格的图。
- **根因**：Electron 主进程 `console.log` 重定向到文件时是**块缓冲**，
  而 `app.exit()` 立即终止进程、不 flush。
- **影响**：**这是"调试工具本身骗人"的典型**——退出码和日志都指向错误结论。
- **状态**：已在调试脚本里修（console 全量镜像一份同步追加到文件）。
  **值得写进规范**：任何用 electron 跑的探针脚本，日志必须走同步落盘，不能只靠 stdout。

### 11. 判据要落到「形态」，不是「跨度」—— 挥手没做出来，三个数字判据全放行

- **现象**：月兔小仙的挥手表**根本没做出挥手**（vision 原话「手臂没有发生变化」），
  但手头的数字判据**一条都没拦住**：
  - 相邻格形态变化 2.4%（> 0，看着像"在动"）
  - 首尾差 0.2%（循环闭合良好）
  - 上半身宽 min/max 跨度 17.8%（**比待机的 12.3% 还大**）
- **根因（两层掩盖）**：
  1. `min/max/span` 是**极值统计**，一个孤立点就能拉满 —— 挥手表里只有格 4 是 179，
     其余 15 格都在 153 上下，跨度照样 17.8%。
  2. **整体包围盒**（211~253）确实在变，但变的是**裙摆和飘带** ——
     这个角色有两条长飘带，飘带自己会摆，于是"手臂没动"被彻底盖住。
- **有效判据**：把上半身宽度打成**逐格序列**看形状——
  - 待机：`153 150 142 138 143 149 155 155 148 139 139 145 150 155 155 155`（平滑呼吸波）
  - 挥手的实测：`153 155 158 154 179 158 155 153 158 157 157 152 153 154 153 153`（**平线加一根针**）
  - 挥手**本该**是"连续几格变宽、再连续变窄"的峰形。
- **教训**：**能用形态判的，别退化成阈值判。** 阈值告警还要人来再判断一次，
  而形态差异直接可判。同一个问题上 `vision` 一句话就点破了（「手臂没有发生变化」），
  纯数字来回绕了两轮。
- **状态**：已固化进验收工具 `.tmp-petgen/inspect-sheets.mjs`（**打序列，不设阈值**，
  并在注释里写明「别用跨度判」——因为我自己先踩了一次）。

### 13. 判「动作做没做出来」必须有**基线对照** —— 否则"大/小"只是感觉

- **经过**：我先判"挥手没做出来"，依据是"相邻格变化只有 2.4%"——
  可那个 `2.4%` 到底算大算小？我**没有依据**，是拍脑袋的。
- 跟团子（`verify/pet-sprite/sources/pet-motion/`，已入库的成套素材）对照后才看清：

  | 判据 | 团子 | 月兔小仙 | 真实结论 |
  | --- | --- | --- | --- |
  | nod 头顶跨度 | **28px**（8 格里低头占 2 格） | 12px | 月兔的**确实没做出来** |
  | wave 上半身宽跨度 | 9px（4.5%） | 26px（全在单格） | 团子也含蓄 →「幅度小」不是问题，**形态**才是 |
  | idle 头顶跨度 | 8px | **18px** | 月兔的**呼吸幅度偏大**，会盖住小幅动作 |

- **两条教训**：
  1. **没有基线，"大/小"就只是感觉。** 而基线往往就在手边——

  2. **我的第一条判断说重了一半**：挥手"含蓄"是这条管线的常态（团子 4.5%），
     我说成"没做出来"是错的；只有 nod 是真失败。**报缺陷前先找基线。**
- **状态**：已用于本轮判断，并回给 Agent 修正了先前的说法。

### 6f. 「侧身」的判据是按四足写的 —— 二足人形会被判反

- **出处**：SKILL.md §五 与 §六 都写着按包围盒宽高比判侧身，并给了基准值：
  > 逐帧量包围盒宽高比（**正面基准 0.78、侧身 >1**）
  > 侧身四足是**宽>高**（实测走路 1.19、下落 1.33、低伏爬行 1.75）

- **问题**：那是**四足动物**的规律——四足侧身是"身体横过来"，自然宽>高。
  **二足人形正相反**：正面看肩宽、侧面看身体厚度，**转过去应该变窄**。
- **实测**：月兔小仙的侧身姿势图，宽高比从 `0.77` 一路降到 `0.47~0.53`（窄了约 35%），
  而 vision 逐条确认**她确实转过去了**（第 1 格正面、末格侧身、头朝画面左侧、16 格同一角色）。
  也就是说：**照 SKILL.md 那条判据去验，会把做对的判成失败。**
- **连带影响**：§五 的画布公式 `画布宽 ≥ canvas.h × 0.94 × 所有动作里最大的宽高比`
  也会算偏——二足角色"最大的宽高比"出现在**正面**动作上，不是侧身动作上。
- **这是 6c 的又一个具体落点，而且比措辞问题更危险**：6c 是"prose 会给人形画出猫爪"，
  这条是**判据方向反了**——错的判据会把对的成果毙掉，而且看起来很有依据。
- **状态**：待定。修法不是改某个数字，而是让判据**按体型分支**（四足 / 二足），
  并说明各自的理由——光改阈值会埋下下一个坑。

### 17. 「跨度」只能回答"有没有变过"，回答不了"怎么变的" —— 我在它上面栽了三次

| # | 我用跨度判什么 | 当时的结论 | 实际 |
| --- | --- | --- | --- |
| 1 | wave 的 min/max 跨度 17.8%（> idle 的 12.3%） | "挥手比待机活跃" | 那是**孤立尖峰**，15/16 格是平线 |

| 3 | climb 的上半身宽跨度 59px | "有变化" | 那是手臂屈伸 —— 侥幸说对了，但推理过程是错的 |

**回答不了"怎么变的"** —— 而后者才是判动作的关键。

**有效替代：打成序列看形状。**

```
wave 重出前  153 155 158 154 179 158 155 153 158 157 157 152 …   ← 平线加一根针
wave 重出后  153 154 155 187 209 194 177 186 206 187 197 159 …   ← 连续波动（抬手→摆→放下）

nod  重出前  153 150 138 131 138 148 158 157 147 135 131 142 …   ← 做成了呼吸
nod  重出后  153 154 153 138 112 92 88 88 96 120 145 153 …       ← 低头再抬起

climb 重出前 头顶 92 87 51 56 54 32 …（原地）                     ← 几乎静止
climb 重出后 头顶 92 87 51 56 54 32 54 33 27 36 10 … 92          ← 升了 82px 再闭合
```

**同一条曲线、两个版本一对比，形状差异直接可判**，不需要任何阈值。

### 21. 底色有**三个真相来源**，而唯一权威的那份没人读 —— climb 整张表白跑

- **现象**：climb 表（16 格拼条）**完全没有抠底**。alpha 直方图 100% 落在 224-255，
  四角是 `rgba(2,246,248)`（青底）。而同一轮的 walk 表四角是 `rgba(2,243,0, 0)`，干净。
- **根因**：抠底色（ComfyUI `ColorToMask` 的 `key`）来自
  `resolveStage()` 的 `bg: A.background || prof.background` —— `ACTIONS` 没有 `background`
  字段，于是取角色档案里**写死的** `#00FF00`（绿）。
  而 climb 的首帧 `staged/moonrabbit-ascend.png` 是**青底** `#00FFFF`
  （Agent 跑 `stage-frame.mjs` 时按用法示例传了 `--bg 00ffff`）。
  **拿绿色去抠青底，色距 ≈248 ≫ threshold 30，一个像素都匹配不到 → alpha 全 255。**
- **三个真相来源**：

  | 来源 | 值 | 谁在读 |
  | --- | --- | --- |
  | `stage-frame.mjs --bg`（命令行） | 青 | 决定 staged 图**实际**铺什么 |
  | `CHARACTERS[x].background`（角色档案） | 绿 | `resolveStage` 拿它当抠底色**和**提示词 |
  | `h3-motion.mjs` 的 `BACKGROUND` 默认 | `#00FFFF` | 只在没给角色档案时兜底 |

  **而 `staged/*.json` 里明明记着这张图真实铺的底色**（`"background": "#00ffff"`），
  `resolveStage` 也**读进了这个 meta** —— 却只取 `figureHeightRatio` / `baselineRatio`，
  把 `background` 放着不用，宁可去角色档案里拿一个写死的常量。
- **⚠ 我自己在这条上又栽了一次（第五次「没验证就断言」）**：
  先看到元数据里 `background: "#00ffff"` 与 `estimatedBackground: "rgb(2,241,1)"` 打架，
  就断定"图是绿底、元数据写错了"，方向**正好相反**。
  两个字段**都对，只是含义不同**：`background` 是**产物铺的**色，
  `estimatedBackground` 是**源图**（H3 出的那张）被估出来的底色 —— 而源图确实是绿底，
  它被 `stage-frame` 抠掉、换成了青底。**字段名没说明这一点，我又照名字下了结论。**
  真正定案的是去看 staged 图四角的实际像素。
- **状态**：根因已定位（2026-09-24），已连同下一条交给客户端 Agent 修。
- **顺带记一条判据**：**判「抠底有没有生效」看四角的 alpha** —— 一眼就能分，
  比任何统计都快。

### 23. vision 会把「抠底残留」**善意地解释成特效** —— 两次都这样

- 第一次（第 20 条）：把角色周围的绿点说成「**绿色的光点（或魔法粒子）**」。
- 第二次（本轮 walk 表）：原话是「周围有一些**微小的绿色光点/粒子**作为特效」。
- **它的结构性判断很可靠**（「手臂没有发生变化」「脚下没有云」一次就点破），
  但**归因会往合理的方向编** —— 它不知道我们的底色是绿幕，
  于是把绿幕渣读成了魔法粒子。
- **配合判据**：vision 说「有粒子」时，**去量它的颜色**。
  贴底色的（`residue-probe` 的 `bgShare` 高）就是渣，离底色远的才是画上去的。
  **vision 负责「有什么」，数字负责「是什么」。**

  有没有水印/多角色，都是这么验的。规范 §七 的「取证四件套」里没有这条，值得补。

### 20. 基准图的抠图遗留会被 H3 **逐帧复制** —— 校验要加在生成之前

- **用户的判断**（原话）：
  > 有绿色是因为基准图抠图遗留的。需要加强基准图的校验
- **验证**：对两张 `staged/` 基准图做连通域分析 ——

  | 基准图 | 连通域 | 内容 |
  | --- | --- | --- |
  | 正面 | **1 个** | 只有主体（363×470） |
  | floaty | **6 个** | 主体（324×477）+ 5 个碎块（面积 56~225px，3 个在脚下、1 个在中部、1 个在右侧贴边） |

- **因果链**：基准图是 H3 的 `first_frame`，**模型会把它当成"角色的样子"照抄**。
  基准图上那 5 个碎块，于是出现在**每一帧**里 → 整张表带绿色残留
  （floaty 表 2.40%，是 side 那组的 2.9 倍，与基准图的脏污程度成比例）。
- **信号早就有了，只是没人判**：`stage-frame` 的产物元数据里就写着
  `sourceBBox.components`（floaty **13**、正面 **1**），它**只记录、不判断**。
- **该加的校验**（位置很关键：**在花 6 分钟生成之前**）：

  | 判据 | 动作 |
  | --- | --- |
  | `components > 1` | 警告并要求确认，别静默放行 |
  | 碎块总面积占比 > 0.3% | 判失败 |
  | 碎块离主体超出某半径 | 判失败（贴着角色的花瓣可接受，飘在远处的多半是残留） |

- **顺带定下一条设计原则**：花瓣、云、光点这类元素，要么**贴着角色连成一块**，
  要么**走特效层**（`slots.fx`）—— **不该以"孤立小块"的形式画在主帧里**。
  在主帧里它们的运动完全由视频模型决定、作者控制不了；放到特效层则位置和时机都可控。

### 24. 「静默不执行」的连环坑：cmd 传不了中文路径 → 建 junction 绕开 → 撞死 `isMain`

- **发现者**：客户端 Agent。它原话是「命令行传不过去中文，……用 Node 建一个 ASCII 目录
  junction」→「cmd 现在吃不下中文路径，绕开它——建 `C:\lm` junction」→
  「junction 让 `isMain` 判断失效（模块 realpath ≠ argv 路径），**静默没跑**」。
- **我实测复核**（不再照它的话直接采信）：

  | 调用方式 | `process.argv[1]` | `import.meta.url` | `isMain` |
  | --- | --- | --- | --- |
  | 直接跑（中文路径） | `…\中文目录测试\entry.mjs` | 同一个（URL 编码） | **true** |
  | 走 junction（ASCII 路径） | `C:\jprobe\entry.mjs` | **`…\中文目录测试\entry.mjs`** | **false** |

  **机制**：Node 的 ESM 加载器会把模块 URL 做 **realpath**，而 `process.argv[1]`
  保留**你敲进去的那个路径**。于是 `import.meta.url === pathToFileURL(process.argv[1]).href`
  这个到处都在用的写法，**在 junction / symlink 下恒为 false** —— main 块整个不执行，
  **退出码 0、没有输出、没有报错**。
- **中文路径那半段也一次量清**（同一份文件的三种 shell）：

  | shell | 传中文路径给 node |
  | --- | --- |
  | bash | OK |
  | **cmd.exe** | **FAIL —— 静默「找不到文件」** |
  | PowerShell | OK |

  所以 Agent 的绕法是**药不对症**：那条路上真正的问题在 cmd.exe，**换个 shell 就完事**；
  而它选的 junction 恰好踩中一个更深的、同样静默的坑。（本机已有记忆
  「中文路径别绕 Node 脚本，那是 cmd.exe 的顾虑」—— 与本次实测一致。）
- **铺得多宽**：仓库正本里 **5 个**文件用这个惯用法、**0 个**用正确写法 ——
  `bundled-skills/…/pet-sprite-h3/characters/` 下 3 个（`h3-motion` / `stage-frame` /
  `motion-frames`）、`verify/pet-sprite/characters/` 下 2 个（`build` / `drive-gen`）。
  加上 `~/.lumii/workspace/` 里的部署副本，实际受影响的是**整条宠物管线**。
- **⚠ 它正好堵死我们清单里的一条设想**：6d 提的「把技能副本做成指向仓库的符号链接」
  当回流机制 —— **symlink 与 junction 在这个判据下等价**，照那条做，这三个脚本会集体
  静默罢工，而且表现是「什么都没发生」，不是报错。
- **修法**（一行）：两边**都比 realpath**，或者干脆别用这个惯用法 ——
  让入口永远是一个显式的 `cli.mjs` 包装文件，业务模块只导出函数。
  后者更稳：**凡是「靠比较路径字符串来判断自己该怎么活」的代码，都会在软链接下说谎。**
- **Agent 的处理**：诊断对了，但**只绕开、没修**（它改成直接 import 函数来驱动，
  `IS_MAIN` 那行原封不动留在文件里）。本轮能过，**下一轮换个入口还会再撞一次**。
- **状态**：待定。这条**不是宠物管线独有的**，是仓库级的写法问题。

### 25. 同一份元数据里两个字段、同一个性质、**两个口径** —— 又是 #4 那个形状

- **现象**：重摆后的悬浮机位图 `debris.dropped: [113,103,83,60,25,18]`（清掉 6 块）、
  `debris.remaining: []`（没有留下大的）—— 也就是**渣已清空**。
  可同一个 JSON 里 `sourceBBox.components` 写着 **3**。
  拿图独立量（`.tmp-petgen/staged-probe.mjs`）：主体之外**一块都没有**。
- **根因**：两个字段的**面积门槛不同**，而且谁都没写出来。
  - `sourceBBox.components` 来自 `largestFigureBox` —— 逐像素 `alpha > 128` 数连通域，
    **没有面积下限**，连 1 像素的孤立点都算一块。
  - `debris` 那套来自 `figureComponents` —— 有 `area >= 16px²` 的门槛，
    低于它的连"要不要清"都不问。
- **交叉验证**（这条算术在旧值上完全对得上）：
  `largestFigureBox` 记 `components`（总数）与 `merged`（并入主体包围盒的块数），
  于是**留在主体之外**的块数 = `components - 1 - merged`。

  | 版本 | components | merged | 推算残余 | 实测 |
  | --- | --- | --- | --- | --- |
  | 修之前 | 13 | 7 | **5** | 探针量到 **5 块** ✓ |
  | 修之后 | 3 | 1 | **1** | 肉眼看不出（< 2px²，见下） |

  门槛放到 `--min 2 --tol 25` 能看见：**8 个 2~13px² 的淡绿点**，
  颜色 `#2bf219 #14f215 #16ea13 …` —— 离底色只有 25~40，**本质还是底色**，
  是抠底边缘的抗锯齿残留，不是"画上去的东西"。**肉眼与 tol 40 都看不见它们。**
- **为什么这条危险**：它是一个**静默的误报源**。今天没人读 `components` 所以没事；
  但按 #21/#22 的教训，下一步要做的正是「让下游读它自己记的值、并且判断」——
  一旦有人写下 `if (meta.sourceBBox.components > 1) 拒绝`，
  **它会把每一张干净的机位图都判成脏的**（因为底色边缘永远留着几个 1~13px² 的点）。
  这和 #4「两份 `alphaBBox` 默认阈值 128 vs 16」是**同一个形状**：
  同名/同类的东西两处实现、两个口径，而**照错误的那个读会得出反向结论**。
- **⚠ 我自己在这条上又差点栽（第 6 次判据出错）**：`staged-probe.mjs` 第一版
  我直接借用了「判表」的判据（四角 alpha 不透明 = 抠底失败），
  于是两张**完全正常**的机位图双双报「✗ 底色没抠掉」。
  **机位图本来就该整张不透明** —— `stage-frame` 的设计就是抠完再刷一层精确纯色底，
  好让后面每一帧的阈值有统一分母。「四角 alpha」是**表**的判据，不是**机位图**的判据。
  连通域那半段也因此废掉（整张一块不透明，碎块数恒为 0）。
  → **判据是带上下文的**：脱离"这是哪个阶段的产物"去复用判据，会得到看起来很有依据的错答案。
- **修法**：给 `largestFigureBox` 的计数加上与 `debris` 相同的 `>= 16px²` 门槛
  （或者干脆别在元数据里放这个容易误读的数字，只留 `debris` 那份有口径的）。
  **两个口径必须在同一个文件里写明，否则下一个人一定读错那个。**
- **状态**：已独立复核，待定。

### 26. ⚠ 校验加在了**错的阶段** —— 干净的机位图照样出脏表，而且这更正了我 #22 的归因

- **先记好消息**：修**生效了**。新的爬云表四角 `rgba(2,244,0,0)` —— **alpha 全 0**，
  直方图 67% 落在透明档。修之前那张四角是 `rgba(2,246,248,255)`、100% 落在 224-255
  （整张顶着青底）。**底色这条彻底通了。**
- **但碎块还在，而且 16 格里 14 格都有** —— 而这张表的机位图是我**单独验证过零碎块**的
  （`staged-probe` 量 ascend：连通域 1 块；`stage-frame` 也报 0）。
  **也就是说：「机位图干净 → 表就干净」不成立。**
- **碎块是从哪来的，判据在「哪些格干净」**：
  干净的恰好是**格 0、1、14、15**（循环的首尾，≈ 首帧本身），
  中间 12 格才有。**这个分布说明它是在动画过程中长出来的**，不是从首帧复制来的。
  机制：角色往上飞，**它腾出来的那片区域由视频模型重新画** —— 画出来的绿和 key
  的色距超出抠底阈值（`threshold: 30`），于是 alpha 保住了 255，变成一块浮着的绿。
  角色身上**半透明的飘带**压在绿底上也会合成出这种"中间绿"，同一个下场。
- **调阈值不是解法**（实测扫了四档）：

  | 容差 | 格4 主体 | 格4 碎块 |
  | --- | --- | --- |
  | 60 | 64465px | 3 块（6.75%） |
  | 100 | 66657px | 3 块（4.04%） |
  | 130 | 65271px | **6 块**（3.78%） |
  | 160 | 62695px | 4 块（3.34%） |

  也被判成"贴底色"割断了，反而**多出**碎块。**这是绿幕遇上半透明元素的经典死结。**
- **⚠ 这更正了我 #22 的归因**。我在 #22 写的是「走路的绿点是悬浮机位上那 5 块渣被逐帧复制」，
  依据是两者**颜色同族**（`#b0bb85/#b8bd8d` vs `#81bd62/#7bbe61`）。
  现在看，**"被冲淡的绿"是任何一张绿幕表都会有的颜色**，不能当复制的证据 ——
  我这又是"照着一个像证据的东西下了结论"（第 7 次）。#22 里「悬浮机位确实有 6 块真渣」
  是**独立成立**的（三基线对照：ascend/side 都是 0），但**它是否被逐帧复制，我没验过**。
- **判定性实验正在跑**：Agent 正拿**已清干净的**悬浮机位图重出走路表。
  如果新走路表**还有**绿点 → #22 的归因基本推翻，碎块主要来自视频模型；
  如果**没了** → 两个来源都成立。**等它落地，这是唯一能分开两者的对照。**
- **✅ 定案（同日 22:5x，Agent 自己跑的对照，我复核了日志）**：
  它用同一把尺子（「距绿 < 80 的不透明像素占比」）量了两张表 ——

  | 表 | 源机位图 | 底色残留 全表 | 最差格 |

  | `moonrabbit-climb-sheet`（新） | **0 碎块**（验证过） | **10.04%** | 16.92% |

  但「**源干净仍然出 10% 残留**」这一条自身就足以否掉「源干净 → 表干净」。）
- **顺带解开的疑团**：走路表这次跑了很久不是因为渲染变慢，是**在队列里等了 584 秒**
  （日志原话「（排队 584s 后轮到它跑）」）—— climb 那份先提交、先执行。

  `placement.top: 8` —— 角色已经**顶天立地**，头上只剩 8px。

- **✅ 补测（23:08 重出的踏云机位拼条，逐格量顶边）** —— 这条被量实了，而且**在源头就有**：

  **再放一道在抠底产物上**：保留最大连通域，远处的**小块丢掉**、

### 27. ✅ A/B 定案：**#22 的机制是真的，但它不是主因**；那些"草屑"是**视频模型自己撒的**

- **实验设计**：拿**已清干净**的悬浮机位图重出走路表，与旧表（源有 6 块渣）逐格对照。
  **格 0 就是首帧 ≈ 机位图本身**，所以格 0 的碎块数应当直接反映源上的渣：

  | | 格 0 | 格 1~14 | 格 15 |
  | --- | --- | --- | --- |
  | 旧表（源 **5~6 块渣**） | **5 块** | 3~6 块 | 5 块 |
  | 新表（源 **0 块**，验证过） | **0 块** | 3~7 块 | **0 块** |

  **格 0 / 格 15 直接对上源上的渣数（5 → 0）。** 所以：
  1. **#22 的机制成立** —— 机位图上的渣**确实会被搬进表里**（至少在首帧）。
  2. **但它不是主因** —— 换一张零渣的机位图，中间 **12 格照样 3~7 块**。
  → **清机位图是「必要但不充分」。** 我先前把「用户看到的草屑」整个归给它，是**说重了**。
- **那中间那些到底是什么 —— 形状把它们认出来了**（给 `residue-probe` 加了外接盒与填充率）：

  ```
  格1  106px/17×9/fill0.69/#97ba83   93px/11×10/fill0.85/#98ba8b   90px/12×11/fill0.68/#96c082
  ```

    （拉长的 `fill` 会远小于 0.5）。**「半透明飘带被割断」这个猜想也否掉了。**

- **结论**：这些是**视频模型自己凭空加的圆粒子**，在绿幕前被染成草绿。
  它大概是在给"仙女"补光点特效 —— **而作者完全控制不了它们的位置和时机**。
- **⚠ 这正好撞上流程自己早就写下的一条原则**（本文档 #20 末尾）：
  > 花瓣、云、光点这类元素，要么**贴着角色连成一块**，要么**走特效层**（`slots.fx`）——
  > **不该以"孤立小块"的形式画在主帧里**。在主帧里它们的运动完全由视频模型决定、
  > 作者控制不了；放到特效层则位置和时机都可控。

  **模型没被告知这条，于是它自己往主帧里撒了一把。**
- **修法方向**（不是调阈值 —— 调阈值已被 #26 的容差扫描否掉）：

### 30. 边缘一直挂着一圈绿 —— **抠底管透明，不管颜色**；两种修法实测，**简单的那版是错的**

- **怎么发现的**：用户问「把底图换成透明或别的颜色，再抠图或者消除不行吗，一直用 GPU 重出既费资源又费时间」。
  查下来：透明底做不了（视频模型输出 RGB，没有 alpha 通道），换底色也不解决粒子
  （粒子是半透明的，压什么底就合成什么色）—— **但"别老重出"这个方向是对的**，
  于是去量了一个一直没人量过的东西：**抠完之后，边缘的颜色对不对**。
- **实测（走路表，`.tmp-petgen/spill-probe.mjs`）**：判据 `e = g - max(r,b)`，
  「边缘带」= 距透明区 ≤ 4px 的不透明像素：

  | | 像素数 | 其中 e>0 | 其中 e>30 | 平均超出 |
  | --- | --- | --- | --- | --- |
  | **边缘带** | 75,596 | **45,580 (60.29%)** | 36,008 (47.63%) | **88.3** |
  | 内部 | 604,852 | 4,706 (0.78%) | 2,743 (0.45%) | — |

  **轮廓上六成的像素带着绿，平均超出 88 —— 那是一圈实打实的绿边。**
  而内部只有 0.78% ⇒ **这个角色身上没有绿色元素**，所以只修边缘**几乎不会误伤**。
- **抠底为什么管不了**：`ColorToMask + threshold` 只决定**透明不透明**，
  它不碰 RGB。边缘压在绿底上的像素 alpha 拿到了，**颜色已经被绿幕钓走了** ——
  这是"颜色问题"，得在颜色层面修，而且**纯本地、确定性、零 GPU**。
- **⚠ 两种修法实测，我先想的那版是错的**：

  | 修法 | 边缘 e>0 修后 | 边缘平均色 | 与角色本色 `rgb(222,200,218)` 的距离 |
  | --- | --- | --- | --- |
  | 修前 | 45,580 | `rgb(113,164,121)` | 150 |
  | **A. 把绿压到 max(r,b)** | **0** | `rgb(113,110,121)` | **171 ✗ 反而更远** |
  | **B. 边缘换成"干净内部色"** | **93** | `rgb(169,155,178)` | **80 ✓ 近了一半** |

  **A 把绿边换成了灰边** —— 绿是没了，可那条边变成中性灰，离角色自己的色更远。
  B 的做法：找出「干净内部像素」（不透明且 e≤0），多源 BFS 往外扩散颜色，
  边缘像素换成扩散来的颜色，**alpha 一个不动**（形状/描边/柔和度全不变）。
- **B 自带一道闸门，而且实测有效**：扩散源距离 > `maxdist`（用 6px）就不动。
  实测**只跳过 93 个像素** —— 正好是飘在远处、模型自己撒的那些碎块。
  **它们不该被染成角色的颜色**（染了只会更显眼），归连通块过滤管，
  两道各管各的、不互相抢。
- **教训（与用户一贯的做法一致）**：**「简单的那版是错的那版」**。
  我本来的判断是"压绿就够了，一行代码" —— 差点直接收口给这个方案。
  是**把两个候选都实现出来量**才看出 A 在"离本色多远"这个判据上是**反向**的。
  如果只实现 A，交付的会是一个把绿边换成灰边的"修复"。
- **状态**：已实测（2026-09-24），脚本 `spill-probe.mjs` 可作为常备工具；
  方案已交客户端 Agent 并入 `lib/` 的后处理那一层。








### 31. 客户端重启打断 Agent 的回合 —— **交出去的活不会丢，但认领凭证只在远端**

**现象**：`dev:restart`（或崩溃重启）会打断 Agent 正在跑的回合，会话上留 `wasInterrupted: true`。
2026-09-24/25 这一夜发生了**两次**（00:15 用户手动重启、01:25 又一次）。

**打断后什么丢了**：Agent 自己说得很准 ——「被打断的批处理里它的状态未知」。
回合内的 tool 输出不保证留在它上下文里，所以它**不敢靠记忆**，只能重新验磁盘。
这是对的反应；靠回忆继续干才是灾难。

**什么没丢**：**已经提交到 ComfyUI 的任务一个都没少**。它们在远端那台 4060Ti 的队列里排队，
本地进程死不死跟它们无关 —— 这一点和 `pull` 那条恢复路径是同一个道理
（杀掉的是收帧的进程，不是渲染）。

**实测的认领办法**（这次就是靠它数出 13 个任务的）：查 `/queue`，从每个任务的 prompt 图里挖

```
SaveImage.inputs.filename_prefix  →  petmotion/moonrabbit-land-sheet   ← 动作名在这
LoadImage.inputs.image            →  moonrabbit-hop.png                ← 首帧用的哪张
```

`filename_prefix` 里带着动作名，`image` 带着首帧名 ⇒ **promptId → 动作 的对应关系可以完全重建**，
不需要 Agent 的上下文。13 个任务当场就对上了号（11 张表 + falling/purring 两张机位）。

**缺口**：`h3-motion.mjs` 提交后只把 `prompt_id` 打到 **stdout**
（「prompt_id 记住：xxx（重拉用 pull）」），**不落盘**。
于是「记住」这件事完全依赖 Agent 的上下文 —— 而上下文恰恰是重启会吃掉的东西。
更糟的组合是：队列也跑完了、`/history` 过了保留期，凭证就真没了，只能重渲染（十分钟 × N）。

**改法**（待做）：提交成功后 append 一行到 `outputs/pet-motion/jobs.json`
（`{promptId, char, action, firstFrame, submittedAt, state}`），`pull` 成功后再回写 state。
落盘之后，「打断 → 认领」这条链就不再依赖任何人的记忆。

**顺带一条**：重启还会**换掉控制口 token**（`~/.lumii/runtime/app-ui.json` 的 token 变了、端口不一定变）。
所以「读端口」不够，**token 也要现读**，别缓存。

### 34. 「等全齐再交付」是个脆门槛 —— 用户要求改成**增量装包**
