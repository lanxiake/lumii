## 一、结论先行

**并排不是卡片的布局属性，是外壳的能力。** 时间线保持单列不动；所有"左右"发生在
外壳的层（右侧工作台）和单张卡的内部（候选网格），不发生在卡片之间。

| 决策 | 结论 | 一句话理由 |
|---|---|---|
| 时间线里的卡片能否左右并排 | **不做** | 单列是窗口化 + memo 的既有契约，横排会让行高随宽度跳变 |
| 右侧工作台是否复用 | **复用** | `WorkspaceWorkbench` 已有可拖拽宽度、记忆宽度、对话区让位 |
| 稿件放哪 | **右栏新 Tab** | 760px 够写；中栏换模式要动 `ChatContainer` 的挂载与滚动，风险大一个量级 |
| 中栏能否切换成文档 | **暂不做** | 先让右栏 `doc` Tab 跑一轮，有真实使用数据再说 |
| 聊天是否挪进右栏 | **不挪** | 现有卡片按 640–820px 设计，塞进 372px 会把它们全压坏 |
| 是否新建"创作 App" | **不建** | 工具链、产物台账、变更记录全在 ChatPage 里，另起一个等于复制一遍 |
| **谁决定用哪种模式** | **Agent（`app_panel` 工具）** | 意图信息全在对话里，UI 只看得见文件名；见 §3.1 |
| 首个场景 | **小红书 → 公众号** | 用户明确排序；两者共享同一套"正文 + 右栏"形态 |

## 三、需求分层：四类动作 → 四种布局原语

用户在创作时真正在做的只有四件事，每种对应一种布局：

| 动作 | 用户在想什么 | 布局原语 | 典型场景 |
|---|---|---|---|
| **写** | 我要在这儿连续写，别打扰我 | 右栏文档（可编辑，760px） | 公众号正文、小红书笔记 |
| **选** | 这几个哪个好 | 卡内 / 栏内多候选网格 | 标题候选、ComfyUI 出图 |
| **比** | 改前改后差在哪 | 左右两栏同源对照（同一 Tab 内） | 回合 diff、前后两版稿 |
| **查** | 我在看的东西在哪儿 | 右栏清单 ↔ 中栏定位（双向） | 素材、设定、分镜 |

四类之外的一切（时间线、后台任务卡、审批卡）**保持现状**，不进这套体系。

### 3.1 谁来选模式：Agent，不是 UI

判定"该用哪种呈现"的信息全在对话里——用户说的是"通读一遍"还是"改第三段"，
是"给我几个标题"还是"这版和上版比"。UI 只看得见文件扩展名，看不见意图。

| 原则 | 说明 |
|---|---|
| **UI 不猜** | 不做"检测到 `.md` 就开文档 Tab"这类启发式 —— 那是把意图判断降级成文件名判断 |
| **Agent 选，UI 忠实执行** | Agent 通过 `app_panel` 工具声明「用哪个模式、打开什么」；渲染层只做匹配与降级 |
| **不可用要明说** | 请求了不存在的模式 → 返回 `{ok:false, error:'unknown_mode', available:[...]}`。静默回落会让模型以为成功了 |
| **模式列表只有一份** | `src/shared/app-panel-modes.ts`：工具 schema 从它生成，渲染层按它校验 |

**模式选择写进工具描述，不写进系统提示词。** 提示词是全局的、每轮都占 token；
工具描述只在模型考虑"要不要用这个工具"时才相关，而且改起来不影响其他工具的行为。
一个反例：`a2ui_guide` 的组件表是手写在工具返回里的，已经和真实组件轻微不一致——
所以这里把提示文案与模式清单放在同一个模块，`APP_PANEL_MODE_HINTS` 的键必须等于 `APP_PANEL_MODES`
（由单测强制），加模式忘了写说明会直接测试失败。

已有的同款先例（不是新机制，是把既有原则延伸到面板层）：

- `app_goto` —— Agent 决定去哪一页；
- `a2ui_guide` 的 `selection_guide` —— Agent 决定用 Chart 还是 DataTable；
- 本设计 —— Agent 决定面板用哪个模式。

**这意味着**：`a2ui`（消息内）与 `app_panel`（面板层）是两条并行的呈现通道，Agent 按场景二选一：

| 用户在说的 | 该走 | 说明 |
|---|---|---|
| "给我看看数据/图" | `a2ui` 的 Chart / DataTable | 结果在对话里就够，不该开面板 |
| "把这篇打开我改改" | `app_panel { mode:'doc' }` | 需要持续编辑，必须离开消息流 |
| "这几个比一下" | `a2ui` 多组件并列（现在）/ `app_panel { mode:'compare' }`（后置） | 两个候选以内放消息里；多了才值得占面板 |

模式清单（当前只有一个；后续按 §五 场景逐个加）：

| mode | 何时该用（写给模型，也写给未来加模式的人） | 用户的典型说法 |
|---|---|---|
| `doc` | 需要通读 / 逐段修改的 markdown 稿件 | 看这篇、改这段、通读一遍 |
| *（后续）* `candidates` | 多个候选里挑一个 | 给我几个标题、生成 4 张 |
| *（后续）* `board` | 多行结构化内容 | 分镜、清单、矩阵 |
| *（后续）* `compare` | 两份内容对照 | 这版和上版比、A 和 B 比 |

**不加的模式**：任何"自动判断"的模式（如 `auto`）。让模型显式选择，出错才可归因。

**Agent 选错怎么办**（这一条必须在设计里说清，否则"Agent 控制"就变成了甩锅）：

| 情况 | 处置 |
|---|---|
| 该开面板却只贴了正文 | 用户一句话即可纠正（"打开我改"），不需要重开会话 |
| 该只贴正文却开了面板 | 面板是**非模态**的：对话仍可读、可发消息、Tab 可关。最坏情况是"多了一块板"，不是"被打断" |
| 反复选错 | 这属于提示词调优，不是机制问题；调 `description` 里的正反例，不动代码 |

**这就是"Agent 控制"能成立的前提**：控制错了的代价必须小。如果面板是模态的，
一次误判就挡住用户全部操作，那就不该交给模型判断。**非模态是本设计选择"Agent 控制"的必要条件，
不是附带好处。**

## 四、布局原语

### P0 · 现有（不改）

- 中栏：对话时间线，单列纵向卡片。
- 右栏：`WorkspaceWorkbench`，`files / changes / vcs` 三个 Tab。

### P1 · `app_panel` 工具 + 右栏 `doc` 模式（最小新增能力）

**Agent 通过工具声明意图，UI 忠实执行**（见 §3.1）。不做"UI 猜"的自动开关。

```ts
// src/shared/app-panel-modes.ts —— 模式清单的唯一真相源
export const APP_PANEL_MODES = ['doc'] as const
export type AppPanelMode = typeof APP_PANEL_MODES[number]

export interface AppPanelRequest {
  mode: AppPanelMode
  /** 打开什么：工作区相对路径或绝对路径 */
  path?: string
}
```

**工具**（`src/main/agent-runtime/bridge-app-panel-tools.ts`，照 `bridge-app-ui-tools.ts` 的写法）：

```ts
name: 'app_panel'
parameters: {
  mode: 'doc',              // 从 APP_PANEL_MODES 生成，不硬编码
  path: '正文.md',          // 工作区相对路径
}
description: `在右侧面板打开内容供用户阅读/编辑。
模式（当前只有 doc）：
- doc：可翻可改的 markdown 稿件。用户说"打开这篇/改这段/通读一遍"时用。
不要用它显示数据图表——那是 a2ui。不要用它打开二进制文件——那是 A2UI FilePreview。`
```

返回 `{ok, mode, path}`；失败码：`unknown_mode`（附 `available`）、`file_not_found`、`disabled`、`app_not_running`。
**不静默回落**——回落会让模型以为面板开了。

**通路**：工具 → 主进程发 `app-ui:panel` → `App.tsx` 写进 runtime store → `ChatPage` 消费
（与 `focusPermissionRequestId` 完全同一套手法：跨会话的一次性意图放 store 顶层、用完即清）。
**不走** `ChatMessageActionsContext`——那条链是"消息行 → 页面"，而这是"主进程 → 页面"。

**渲染侧**：
- `WorkbenchTab` 加 `'doc'`；
- Tab 内容 = `<FilePreviewModal variant="embedded" filePath={docPath} />`（已有嵌入 + 编辑 + 保存）；
- `docPath` 为空时 Tab 不出现（同 `vcsEnabled` 的做法），避免"点进去空白"。

> 何时扩成多模式：第二个模式（`candidates` / `board` / `compare`）真的要用时，
> 往 `APP_PANEL_MODES` 加一项 + 在 `WorkspaceWorkbenchArea` 加一个分支。
> **不要**现在就把四模式的渲染都写出来——三个没有调用方。

### P2 · 卡内网格（多候选）

```css
.candidates {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(200px, 1fr));
  gap: 8px;
}
```

窄了自动退化成单列，不需要媒体查询。用于：标题候选、ComfyUI 出图。

### P3 · 右栏板式（表格 / 图墙）

右栏可以是「板」：分镜表（行 = 镜头）、图墙（网格 = 产出）。**都是只读展示 + 单击定位**，
不是编辑器。分镜表就是 `DataTable`；图墙就是 P2 的网格换个数据源。

**放在右栏而不是中栏**：760–1100px 足够放一张 5 列表格，而中栏换模式要动 `ChatContainer` 的
挂载/滚动路径，风险差一个量级（见 §8.7）。

### P4 · 中栏模式（对话 / 文档）— 暂不做

```
┌──────────┬──────────────────────────┬───────────────┐
│ 左导航    │ 中栏（对话 ⇄ 文档）        │ 右栏          │
│ 264      │                          │ 对话 / 预览   │
└──────────┴──────────────────────────┴───────────────┘
```

只有等 P1–P3 都用过一轮、且用户明确说"我想只看着稿子写"时才做。
**不新增 `ViewType`**：这是 ChatPage 内部的模式，不是新页面。

## 六、降级阶梯

宽度不够时的退路，从宽到窄：

| 可用宽度 | 布局 | 说明 |
|---|---|---|
| ≥ 1400 | 三区：左导航 264 + 对话 + 右栏 760–1100 | 完整形态 |
| 1100–1400 | 两区：对话 + 右栏 480 | 左导航自动折叠成图标条（现有 `ChatSidebar` 已支持） |
| 760–1100 | 两区：对话 + 右栏 420 | 右栏 Tab 收成下拉 |
| < 760 | 单区 + 右栏全屏覆盖 | `Esc` 返回对话（沿用 `FilePreviewModal` 全屏行为） |

**降级的判定不新增代码**：`WorkspaceWorkbench.getMaxWidth()` 已经按「对话区宽度 − 280」钳制，
把它的返回值直接当断点用即可。

## 七、明确不做

| 项 | 理由 |
|---|---|
| 时间线里的卡片左右并排 | 见 §8.1 一脉：行高、窗口化、阅读顺序三重冲突，收益不抵风险 |
| 把聊天挪进 372px 右栏 | 现有卡片按 640–820px 设计（`AgentDashboard` / `BackgroundTaskCard` 都是 `max-width:640`），塞进 372 会全部压坏 |
| 独立"创作 App" / 新 `ViewType` | 工具链、产物台账、变更记录都在 ChatPage；另起一个等于复制一遍，且要重做鉴权、MCP、会话 |
| 时间轴 / NLE 剪辑器 | 没有剪辑引擎，也没有这个需求方；导出给人用剪映 |
| ComfyUI 节点图编辑 | 参数表单足够；节点图是 ComfyUI 自己的活 |
| 富文本所见即所得（WYSIWYG） | `@uiw/react-md-editor` 已在用，markdown 源码 + 预览双栏够用；换 ProseMirror 是另一个季度的事 |
| 文档版本库（命名版本 / 分支） | 先做「回合快照 + 建议块」，命名版本等有人真的要求 |
| 跨设备 / 云端稿件同步 | 已有云同步管文件；在工作台上再造一层是重复 |

## 八、反思：demo 的主张，哪些收回、哪些坚持

六个 demo 是 2026-10-20 画的静态稿。对照真实代码后，**三处收回、两处坚持**，
另外还推翻了我自己上一版草稿里的两处设计（8.6、8.7）。

### 8.1 收回：demo 01 的「聊天挪到右侧 372px」

demo 把三栏定成 `左 264 / 中 文档 / 右 372（对话）`。但现有对话内的卡片是按宽屏设计的：

- `AgentDashboard` `max-width: 640px`
- `BackgroundTaskCard` `max-width: 640px`
- `CompactionCard` `max-width: 640px` / `480px`
- 时间线本身按 820px 的对话柱排版

把聊天塞进 372px，这些卡要么横向溢出，要么全部挤出滚动条，委托卡里的「详情」按钮和子 Agent 轨迹直接不可用。
**改法：中栏保持对话，文档进右栏（760–1100px）。**

### 8.2 收回：demo 的「左栏 = 项目文件树」

demo 的左栏是 Binder / 文件树，但 ChatPage 的左栏现在是**会话列表**（`ChatSidebar`）。
两个"左栏"抢同一个位置，是最容易做出"第二个 App"的地方。

**改法：不复用左栏。** 文件树继续待在右栏的 `files` Tab 里（现在就是），
中栏文档要打开的稿子从右栏点进去。等证明"写作时确实需要常驻目录"，再讨论左栏切换 —— 而不是一开始就占位。

### 8.3 收回：demo 06 的「块级 transclusion / 反链」

块引用看起来很美，但它的前提是**稳定的段落 id**。现有 markdown 文件没有任何锚点，
AI 改一次稿，段落 id 就全变。仓里 `selection/snapshot.ts` 已经踩过同款问题
（持有活 Range，滚一下就静默失效），最后是靠"快照 + 数值矩形"绕过去的。

**改法：第一版只做「轻量稳定引用」**：链接 + 文本快照 + 回退（找不到就显示原文快照并标注"已失效"）。
块级引用要等有真正的段落锚点存储再说，不在这一期。

### 8.4 坚持：inline 建议块（demo 01 的 `.suggestion`）

六个 demo 里**价值最高、代价最低**的一处。AI 改稿时给出「删掉这句、换成那句」的行内建议，
用户逐条接受/拒绝。它把"整篇重写 → 全量 diff → 肉眼找"压缩成"一眼看、一点接受"。

前提是**建议要带段落定位**，否则接受之后对不齐。低成本做法：建议块携带改前原文片段，
接受时在文档里找**最后一次出现**的该片段并替换；找不到就降级为"手动复制"。
这就是"轻量稳定引用"的同款思路 —— 不追求永不失效，只保证失效时可见、可回退。

> 本期不做：它要改 `FilePreviewModal` 的编辑面（现在只有整篇 md-editor），
> 而那一块没有测试覆盖。等 `doc` Tab 跑一轮、用户确实要"逐句改"再动。

### 8.5 坚持：右栏 Tab 化（demo 03/04 的 `rail-tabs`）

「标题 / 预览 / 检查 / 对话」四页签挤在一个右栏里，比开四个窗口好得多，
而且正好是 `WorkspaceWorkbench` 已有的能力（现在只有三个 Tab）。
加 Tab 的成本远低于加一层面板系统 —— `WorkbenchTab` 是联合类型，加一个成员只需改 9 处（见实施计划 T2）。

### 8.6 推翻自己：不做 `openPanel(kind, payload)` 泛化接口

本设计初稿写的是「给 `TimelineCardContext` 加 `openPanel(ref)`，`kind` 支持五种」。
这是典型的为未来设计：当前只有**一个**真实模式（`doc`）。
一个 `kind` 五分支的联合类型，实际只用其中一支，代价是每个调用方都要理解一套并不存在的协议。

**改法：模式清单只写 `['doc']`，但把清单本身抽成 `src/shared/app-panel-modes.ts`。**
第二个模式出现时往数组加一项 —— 那时才知道它到底需要哪些字段。
抽清单不是提前设计，是因为工具 schema、渲染层校验、错误码三处都要读它，
散在三处必然会漂移（`a2ui_guide` 的组件表就是手写的，已经有轻微不一致）。

### 8.7 推翻自己：板式（分镜表 / 图墙）不放中栏，放右栏

初稿把分镜表和图墙放中栏，理由是"表格要宽"。但中栏是 `ChatContainer`，换模式意味着：

- 消息列表整体卸载重挂 → 滚动位置丢失、`useWindowedRows` 高度缓存作废；
- 重型卡片（640–820px）在 `chat-main` 里让位，布局路径要多一条分支；
- 而这些表格实际只有 5–6 列，760–1100px 的右栏完全放得下。

**改法：板式是右栏的一种 Tab。** 中栏换模式（P4）降级为"暂不做"，
等右栏真的不够宽再谈。

## 九、风险与缓解

| 风险 | 缓解 |
|---|---|
| 右栏变宽导致对话柱变窄、卡片换行 | `useLayoutEpoch` 已监听容器宽度并防抖重测；宽度钳制保证 ≥280px |
| **Agent 频繁开面板打断阅读** | 工具描述里写明"仅在需要用户通读/编辑时用"；面板只在真被请求时开，没有自动开 |
| **Agent 请求不存在的模式** | 返回 `{ok:false, error:'unknown_mode', available:[...]}`，不静默回落 |
| `app_panel` 与 `app_goto` 争用窗口焦点 | 两者都是"声明意图、渲染层执行"，互不抢占；面板开在当页，不切 view |
| 建议块接受后对不齐 | 改前片段 + 最后出现位置；找不到降级为手动复制，且界面上明示 |
| 新 Tab 与插件体系冲突 | `WorkbenchTab` 与 `APP_PANEL_MODES` 都是内置联合类型，不开放给插件 |
| `doc` Tab 里编辑与 Agent 写同文件冲突 | 保存前比对 mtime；不一致时提示"Agent 刚改过，是否覆盖"，不静默覆盖 |
