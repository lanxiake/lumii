# 精灵宠物自主行为设计（R9 基础版）

需求依据：[`宠物系统需求分析`](2026-09-21-宠物系统需求分析.md) §五之二（D1/D2 的边界放宽）
素材来源：[`桌宠动作生成方案调研`](2026-09-21-桌宠动作生成方案调研.md) §七·补五（Shimeji 精灵表导入）
实施日期：2026-09-21

---

## 一、这份设计解决什么

精灵宠物此前是**被动**的：Agent 说话它才动、用户点它才回应，其余时间站在原地做呼吸。
**空间维度完全没用上**——位置恒定，只有拖拽时才移动（需求分析 §3.2 把这条列为"参考项目最值得借鉴的手法"）。

本设计让它自己活动起来：

- 在地面线上**走动**，撞墙折返、朝向跟着翻
- 在站立 / 坐下 / 走动之间**按节奏轮换**
- 被抛出去时用**下落姿势**，被拎起时用**被抓姿势**

**明确不做**（留给后续）：贴边语义（吸附到屏幕边缘而非窗口）、位置持久化（R10）。
爬墙与天花板爬行**在同一天补上了**，见 §七——它原本列在这里，
是因为当时以为"需要窗口枚举"，实现时发现只需主窗口一个矩形。

## 二、分层

```
pet-core（纯逻辑，可脱开浏览器单测）
├── behavior/ambient.ts      决策：下一个活动是什么、持续多久（权重表 + 时长表）
├── behavior/locomotion.ts   运动：匀速前进、撞边界折返、画布边界 → 可达区间
└── behavior/perch.ts        攀附：吸附判定、沿墙上爬、沿天花板爬行、何时松手

apps/windows/src/renderer/pet/
├── behavior/PetWanderDriver.ts   驱动：rAF 循环、位置权威、让位互斥、攀附接线
├── renderer/sprite/SpritePetRenderer.ts
│     新增能力：setFlip（水平翻转）、getLayout（锚点与缩放）、resetToGround（地面线）
└── components/PetCanvas.tsx      接线：拖拽/抛掷时让位，活动变化上报
    orchestrator/PetOrchestrator.ts  仲裁：环境动作组 vs 对话/交互优先级

apps/windows/src/main/pet/
└── pet-perch-tracker.ts     主窗口矩形推送（窗口事件驱动，拖动时跟手）
```

**决策与运动分离**的理由：决策要能被整表替换。后续接 Agent 真实状态驱动时（R5/R6），
换的是 `AmbientConfig` 这张数据，不是这段逻辑。

## 三、四处关键决策

### 3.1 不用骰子

参考项目是 `[STAND 0.3, WALK 0.4, SIT 0.2, GREET 0.1]` + **每 5 秒掷一次 30%**，
需求分析 §3.3 把这套判为"表演"（无缘由地突然坐下、打招呼，事后不可理解）。

本实现只借手法不借节奏：

| | 参考项目 | 本实现 |
| --- | --- | --- |
| 决策节拍 | 5 秒一次 | 平均 20~35 秒一次（各活动有独立的时长区间） |
| 动作池 | STAND/WALK/SIT/**GREET** | STAND/WALK/SIT —— **去掉 GREET**，打招呼留给真实事件 |
| 首次行为 | 启动即掷签 | **一定是站着**，先安静待 15~45 秒 |

`ambient.test.ts` 里有一条**回归哨兵**：默认时长区间的中位数不得低于 15 秒——
把默认值改回"5 秒一次"就会红灯。

### 3.2 位置权威是排他的

同一时刻只能有一个东西写宠物位置：鼠标（拖拽中）、抛物线积分（抛出后）、驱动（落地静止）。
用 `suspend()`/`resume()` 互斥，不是"各自算各自的"——两个写者会互相覆盖，
表现为宠物一边走一边被拽回去。

### 3.3 让位按 reason 记账，**不是计数器**

**这条是实测撞出来的**。最初用计数器，`mousedown` 记 `suspend('drag')`，
而点击分支改记 `suspend('tap')` 并只解除自己——两个名字对不上，
`drag` 那一次永远无人解除，**每点一下泄漏一个**：

```
[PetWander] [suspend] 让位（drag），suspendCount=1
[PetWander] [resume] 仍有 12 个让位方未解除（tap）      ← 点了十几次之后
```

宠物永久卡在"让位"状态，**走路完全停摆，但日志里没有任何报错**。

改成 `Set<string>` 语义后：同一个 reason 重复让位只算一次、重复解除是无害的，
调用方不必再小心翼翼配对。代价是**同一件事必须用同一个 reason**——
所以 `PetCanvas` 里把指针交互统一成 `AMBIENT_HOLD_POINTER`，各分支只决定"什么时候还"。

`PetWanderDriver.test.ts` 钉住了这套语义。

### 3.4 翻转落在 `root.scale.x`，不是 `pivot`

调研文档 §七·补五 当日的结论是"渲染层没有翻转能力，所以镜像只能落打包期、图集翻倍"。
实现时发现漏了一点：**锚点校正与缩放符号无关**。

sprite 的世界坐标是 `root.position + root.scale × (pivot.position + local)`，
要让 `local = anchorX` 落在 root 原点上，条件是 `scale.x × (pivot.x + anchorX) = 0`，
**与 `scale.x` 的符号无关**。所以翻转不必动 `pivot`，在 `root.scale.x` 上取负即可，
「图集翻倍」这个代价根本不必要。

**命中判定必须同步翻**：`ModelTransform` 加了 `flipX`，由 `toManifestPoint` 在反算时取反。
漏掉这一步的症状是「点左肩中右肩」。`hit-polygon.test.ts` 用非对称的 L 形多边形守这条，
并配了负对照——**拿矩形或左右对称的剪影去测，镜像前后结果一样，测试会永远通过而什么都没验**。

## 四、实测

用 `scripts/lumii-cdp.mjs` 驱动（宠物窗口默认全窗穿透，PowerShell 的鼠标模拟会被拦掉，
CDP 的 `Input` 域绕过那一层）。

**活动轮换**（真实运行，无人工干预）：

```
[PetWander] [tick] stand → walk，持续 7693ms
[PetWander] [tick] walk → walk，持续 3804ms
[PetWander] [tick] walk → stand，持续 24603ms
```

**抓取 → 抛出 → 落地**：

```
[PetWander] [suspend] 让位开始（pointer）

[PetCanvas] [onMouseUp] 抛出 v=(913, -1756) px/s
[playMotion] group="Fall" 3帧                          ← 下落姿势
[PetWander] [resume] 恢复（pointer）位置 (2455, 1352)   ← 落地，干净恢复
[playMotion] group="Idle"                              ← 回待机
```

## 五、实测暴露的两个既有 bug

两条都不是本次改动引入的，是"跑起来才看得见"的那类。

### 5.1 拖拽永远被判定为点击

`onMouseUp` 判断"是否拖动过"的基准是 `宠物当前位置 + 拖拽偏移`。
但拖拽过程中宠物**一直跟着光标走**，这个值恒等于光标的当前位置，差值永远是 0——
于是每一次拖拽都进了点击分支，**「抛出」这条路径根本走不到**。

实测证据：拖了 477px、以 4400px/s 甩出去，日志里连一行 `[onMouseUp]` 都没有。

修复：基准改用 `samples[0]`（mousedown 那一刻的光标位置）。

### 5.2 应用静默退出（未定位）

宠物模式运行一段时间后，Electron 主进程以 exit code 1 退出，
**dev 日志与应用错误日志里都没有对应记录**（最后几行是正常的服务心跳）。

本轮复现 2 次，与需求分析阶段记录的"应用两次死掉且无崩溃记录"是同一现象。
伴生的可观测错误是 PIXI 的
`Invalid value of '0' passed to checkMaxIfStatementsInShader`——
那是 **WebGL context 耗尽**（每个 `SpritePetRenderer` 自建一个 `PIXI.Application`，
即一个 WebGL context，多宠物设计 §七 已经点过名），但它出现的时间戳与退出对不上，
**不能断定是因果**。

未定位，保持记录。

## 六、与既有维度的关系

自主行为是**正交维度**，不进 `petStateMachine`（那条状态机回答"宠物在跟用户对话吗"）：

| 维度 | 内容 | 变化频率 | 与自主行为的关系 |
| --- | --- | --- | --- |
| `petStateMachine` | 对话生命周期 | 秒级 | 对话进行中，自主行为让位（`ambientEnabled` 里判 `phase === 'idle'`） |
| `Mood` | 内在情绪 | 小时级 | 无交互 |
| `idleStage` | 用户是否在场 | 分钟级 | 无交互（打盹由待机调度管，不走空间） |
| **`ambientActivity`** | **宠物自己溜达到哪一步** | **数十秒级** | 本设计 |

**表情层完全不受自主行为影响**：它只动位置与姿态（走/坐/站），不碰 `setExpression`。
D1 里"不得无缘由表达情绪"这条**没有放宽**。

## 七、攀附在程序主窗口上

宠物能**爬到 Lumii 主窗口的边缘上**，沿墙爬到顶、再沿窗口上沿横爬，爬到另一角掉下来。
这条借鉴参考项目最标志性的行为（需求分析 §3.2），也是"宠物知道屏幕上有别的东西"的第一次体现。

### 7.1 素材本来就画好了这两种姿势

实测逐帧包围盒：

| 行 | 尺寸 | 形状 | 用途 |
| --- | --- | --- | --- |
| CLIMB | 36 × 62 | 竖长 | 爬墙 |
| CRAWL | 63 × 40 | 横扁 | 爬天花板 |

**不需要任何旋转**——素材作者就是按这两处用法画的。这一条推翻了我自己前一天在调研文档里
"爬墙大概要把横版姿势转 90°"的猜测；**去看一眼真实像素比推演快得多**。

### 7.2 两段路径，爬到尽头就掉

```
地面行走 ──吸附──▶ wall（沿墙向上）──到顶──▶ ceiling（沿上沿横爬）──到角──▶ 掉落 ──▶ 回到地面
```

**到顶不折返，爬到另一角就掉**。折返的话宠物会永远赖在窗口上；
"爬到头掉下来"才是有始有终的收尾。掉落只改状态不做自由落体——
自由落体是用户的投掷才有的待遇，自己爬下来的用常规活动接管即可。

吸附要同时满足三条（`tryAttach`）：

1. 宠物**在窗口底边之下**——否则它是在窗口内部走，没有"边上"可爬
2. 水平距离在 `attachDistance`（24px）内
3. 窗口高度 ≥ `max(120, 模型屏幕高度 / 2)`——太扁的窗口爬上去立刻到顶，没有意义

第 3 条用**模型高度**而不是固定像素：换一只体型大的宠物，同一个窗口对它可能是"扁的"。

### 7.3 缝隙按模型高度给，不是固定像素

锚点语义在攀爬时**不变**（仍是"脚底中心"），但 CLIMB 行的内容底边距全表地线有 19px 空隙
（19/128 ≈ 0.148）——那是素材自己留的。所以爬墙时宠物与墙面之间会自然出现
`19 × scale` 的缝，`gapRatio = 0.15` 就是补它的量级。

用**比例**而不是像素：这个缝的本质是"素材留白占体型的比例"，换算成固定像素后换个模型就不对了。

### 7.4 主进程推矩形：窗口事件，不是轮询

主窗口在宠物窗口坐标下的矩形由主进程推送。这里**没用**光标追踪那套 33ms 轮询，
理由有两条：

- 光标必须轮询是因为**光标不在窗口里时窗口收不到 mousemove**；窗口位置没有这个问题，
  Electron 直接给 `move`/`resize` 事件
- 更关键的是**跟手**：用户拖主窗口时宠物要跟着一起走，250ms 的轮询会让它一跳一跳地追

坐标换算留在主进程做（屏幕坐标减去宠物窗口原点）——否则"宠物窗口在哪"这个知识
要同时存在于主进程和渲染层两处。

窗口静止时**零流量**（内容没变就不发），所以还额外需要一次挂载补问，见 §8.3。

### 7.5 与让位机制的关系

攀爬期间 `activity` 计时**冻结**：回到地面时从 `stand` 重新起算，
而不是把墙上耗掉的时间算进"这一轮待机还剩多久"。

拖拽/抛掷期间不判吸附——位置权威那时归鼠标或抛物线，此时吸附会跟它们抢。
但**原地落下的那一刻要补判一次**：`resume` 里调 `tryAttachNow`，
用户把宠物拎到窗口边上本来就带着"放这儿"的意图，只在走路途中判的话那个动作完全没反应
（实测时用户这么试了好几轮，宠物纹丝不动）。

**抛出不算**：飞出去的宠物要落回地面，不该在半空被窗口吸走；它落地时 `resume` 才判。

## 八、攀附的实测与四个缺口

完整链路（真实运行）：

```
[PetCanvas] [onMouseUp] 速度不足（51 px/s），原地落下
[PetWander] [resume] 恢复（pointer）位置 (585, 1352)
[PetWander] [perch] 吸附到左墙 x=538
[PetOrchestrator] [setAmbientActivity] climb → 组 "Climb"
[playMotion] group="Climb" 8帧
        ⋮  （沿墙爬升 1144px ÷ 45px/s ≈ 25 秒）
[PetWander] [perch] 爬到顶，转为沿窗口上边缘爬行
[PetOrchestrator] [setAmbientActivity] crawl → 组 "Crawl"
[playMotion] group="Crawl" 8帧
        ⋮  （沿上沿爬行 1442px ≈ 32 秒）
[PetWander] [perch] 松手（爬到尽头）@(1980, 208)
```

### 8.1 松手后悬在半空（已修）

上一条日志里的 `@(1980, 208)` 就是问题：**208 比窗口上沿还高 42px**。
按最初的写法"松手只改状态、不做自由落体"，宠物会**悬在窗口右上角的空中**，
之后还会在那条看不见的地面线上走来走去——它原本站在 `y = 1352`。

原因是把"掉落"当成了状态变更而不是物理过程。修法是复用已有的 `stepThrow`：
自己掉下来和用户扔出去**是同一套物理，差别只在初速度**
（自己掉：`v = 0`；被扔：用户的释放速度）。吸附时记住脚下的 `groundY`，落回那里。

### 8.2 拖走正在爬的宠物会弹回墙上（已修）

让位期间 `tick` 不跑，于是**没人发现位置已经离墙很远了**；恢复自主活动的第一帧
`stepPerch` 会把宠物**瞬移回墙上**。修法是在 `resume` 里加一次 `revalidatePerch`：
用 `shouldLetGo` 核对，判定脱离就转入下落而不是回站立（此刻它悬在半空，
站着会像被钉在空中）。

半空中被抓住又放下时同理——`resume` 认出 `falling` 还在，接着往下掉。

### 8.3 进宠物模式时的第一次推送**必然**丢（已修）

进入宠物模式的顺序是「窗口 show 出来 → 主进程立刻推一次矩形」，
而**那一刻渲染层还没加载完**，`webContents.send` 直接丢掉。此后主进程只在
**矩形变化**时才推（窗口静止时零流量），于是只要用户不动主窗口，宠物就永远不知道
有东西可爬——**这不是偶发竞态，是必现的**。

修法对齐了 `idle-watcher` 已有的先例：加一个 `PET_IPC.getPerchRect`，
渲染层挂载时**先订阅、再补问一次**（顺序不能反，否则两步之间主窗口动的那次推送会丢）。

**这条是被实测逼出来的**：订阅日志打出来之后迟迟没有任何矩形到达，
当时还以为是"用户没动主窗口所以不推"的正常行为——直到发现**新开一次宠物模式也一样**，
才确认是加载时序问题。

> 排查时踩的坑：`Monitor` 有超时，被杀之后**已经抓到的行还在，后面的行不会再来**。
> 当时把"监视器停了"读成了"日志不再产生"，据此推断出一个并不存在的第三个缺口
> （"鼠标悬停在宠物上时吸附不触发"）。翻回原始日志才发现第一次拖拽就完整走通了。
> **工具的静默和系统的静默长得一模一样**——判据要落在能自己说明"我还活着"的地方。

### 8.4 模型 ID 没补问，攀爬一路播成待机（已修）

同一个根因的第三处：主进程只在**切换时**推 `model:changed`，页面加载之后不再推。
于是 `currentModelId` 一直是空串，`PetCanvas` 取配置时回退到**默认模型**——
用户明明选了 nekojapan，实际加载的是内置的 `real_dog`（4 张纹理 vs 40 张）。

**显露出来的却是完全不相干的现象**：攀爬的动作组解析不出来，
`[setAmbientActivity] climb → 组 "(基础待机)"`——因为默认模型没有 Climb/Crawl/Fall。
宠物于是贴在墙上**用站姿往上飘**。

这条是**从动作组反查出来的**：先怀疑 manifest 缺组，查了两份（内置 + 用户目录）都有 9 组；
再怀疑模型热切换没重建运行时；翻日志才看见**加载的根本不是那只模型**。

所以 §8.3 那句"挂载时补问一次"不是补一个漏洞，而是**补一族**——
目前已经三处（`getIdleStage` / `getPerchRect` / `getCurrentModelId`），
共同前提都是「主进程只在**变化**时推，而渲染层会在任意时刻重新加载」。
**再往这条链路上加东西时，先问一句：它是不是也需要一次挂载补问。**

补问之后还留了个小尾巴：`currentModelId` 到位之前 `PetCanvas` 已经拿着空串取过一次配置，
于是先加载出一只默认宠物再整个换掉，看起来是"闪一下变了只宠物"。
在配置 effect 开头加一句 `if (!modelId) return` 即可——依赖变了它自然会再跑。
