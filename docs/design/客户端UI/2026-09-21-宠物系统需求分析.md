对照对象：`C:\myself\projects\my\open-source\AI-desktop-pets`（外部 Shimeji 路线桌宠，以下简称**参考项目**）。
本文只做**需求侧**的核查与建模，不含技术方案。技术方向见 [`../../plans/客户端UI/2026-09-21-宠物系统对照AI-desktop-pets优化方案.md`](../../plans/客户端UI/2026-09-21-宠物系统对照AI-desktop-pets优化方案.md)。

## 一、问题定义

### 1.1 一句话

**用户希望 lumii 的桌宠具备参考项目那样的表现力，但参考项目与 lumii 是两个物种——照抄功能会做错方向。**

参考项目是**独立养成游戏**（宠物自己饿、自己玩、自己随机走动）；lumii 的桌宠是**Agent 的可见化身**。两者的"功能"看似重叠，实则服务不同目的。

### 1.2 定位：两个来源（都不是我发明的）

| 来源 | 原文 |
| --- | --- |
| 用户指南 §4.3 | "桌宠功能，提供**可视化的 AI 助手形象**" |
| 生命感设计 §7.4 | "Mood 三维直接映射表情……**这是生命感最直接的载体**——用户不看仪表盘，但会看到桌宠。Agent 昨晚连续失败，今早桌宠看着不太精神，这一眼胜过一百条日志" |

**推论**：lumii 桌宠的第一职责是**把 Agent 的内部状态如实透出来**，不是自娱自乐。

### 1.3 Non-Goals（明确不做，防止范围蔓延）

| 不做 | 依据 |
| --- | --- |
| **表演情绪**（无缘由的可爱动作、"我好开心呀~"） | 生命感设计 §11 明令："最快毁掉生命感的就是表演情绪……比中性表达更糟" |
| **情绪只影响措辞不影响决策** | 同 §11："廉价的皮肤。用户会发现它'说累但活儿照干'" |
| **把 mood 数值展示给用户** | 同 §11："'energy: 0.34' 是仪表参数不是生命" |
| **虚拟养成数值**（喂食 / 饥饿 / 亲密度） | 同上：宠物不该"饿"，它没有生理需求；真实负载才是它的状态来源 |
| **关键词模板对话** | 参考项目 `ChatEngine` 的 8 类关键词匹配；lumii 已有真实 LLM，退回模板是能力降级 |
| **系统负载监控**（CPU / 内存 / 电量驱动宠物说话） | 参考项目是手机场景。lumii 有远比 CPU 更精确的信号——`agent:tool:*` 直接说明 Agent 在做什么 |

## 二、现状事实核查（全部实测，2026-09-21）

### 2.1 已经打通的链路（**这些不要重做**）

| 链路 | 证据 |

**结论：宠物侧的"Agent 状态 → 视觉表达"骨架已经建好了。问题不在缺骨架，在断点。**

### 2.2 实测断点

| # | 断点 | 实测证据 | 用户感受 |
| --- | --- | --- | --- |
| **B1** | **自制宠物演不出 Agent 情绪** | 三只精灵模型 `emotionMap` 条目数 **21 / 3 / 3**；`demo_cartoon_cat` 与 `demo_mecha_gundam` **连 `slots` 都没声明**（结构上无表情层），只有 `neutral`。且 Prompt 只注入这 3 个标签 → LLM 被约束成只能用 neutral | 用户自己造的宠物**永远一张脸**；Mood 设计的"生命感最直接载体"落空 |

> **B1 的性质（2026-09-21 核查）**：**能力已经具备，素材没跟上**。提交 `fccc1cd2`（本日 11:01）刚落地"表情层差分取层——生成出来的宠物第一次有了可分层的脸"；但 `pet-models/README.md:31-32` 明确记录团子与钢羽"表情层：无（差分取层未达标）"——它们是该能力具备**之前**生成的旧素材，未重做。
> 所以 B1 不是"要造能力"，而是"**要用已有能力把示范模型重新生成一遍**"，成本远低于初判。
| **B2** | **Agent 干活过程完全不可见** | 宠物只订阅 6 个事件（`turn:start/delta/end/idle` + mood）。`agent:tool:start/progress/end`、`thinking:delta`、`context:usage/compacted`、`subagent:completed`、`activity:snapshot` **全部未订阅** | Agent 跑 12 分钟调 40 次工具，宠物在**随机待机或静止**——最该有表现力的时段最空 |
| **B3** | **需要用户决策时不提醒** | `agent:permission:request`（含 `riskLevel` / `timeoutMs`）未订阅 | Agent 停在等批准，**用户不知道**，超时后才在别处看到 |
| **B4** | **点击身体不播动作** | 三只均未声明 `hitAreas` → 命中落到 `'body'`；注册表 `tapMotions` 的 key 是 `HitAreaBody`（Live2D 风格）→ 兜底候选 `['body','Tap','tap','TapBody','$unnamed']` 在只有 Idle/Talk/Wave 的模型里**全部不存在** → 静默 return | 点击宠物只有烟花，没有回应 |
| **B5** | **说话时嘴不动** | 三只均未声明 `mouthLevels` → `mouthBinding` 恒 null → `setMouthOpen` 直接 return；两套 LipSync **每帧白跑** | 有字幕有声音，但嘴不动 |
| **B6** | **打盹演不出来** | 打盹候选名（`sleepy`/`困`/`打瞌睡`/`drowsy`/`tired`）在三只模型上**命中 0/5**；睡着/醒来对团子与钢羽同样 **0/4、0/6** | 只有 `demo_anime_girl` 能演出睡着与醒来，另两只三个阶段的迁移**一次都看不见** |

**B1 的影响是双向的**（这是它比"少一个表情"严重得多的原因）：

```
素材缺表情层 → emotionMap 只有 neutral
   ├─→ Mood 事件查不到映射（运行时断）
   └─→ Prompt 只注入 neutral，LLM 被禁只能用 neutral（生成时断）
```

### 2.3 用户可配置项现状（9 项）

`shared/virtual-human.ts:23-42`：对话 Agent、跟随模型 Agent、表情标签 Prompt、动作标签 Prompt、文字回复朗读、待机随机动作、点击互动、强制鼠标穿透、注视跟随、闲置感知。

**缺口**：以上开关都在，但 B4/B6 说明"开了也看不出来"——**开关的有效性依赖素材，而素材没跟上**。

## 三、参考项目对照

### 3.1 它**真正能用**的功能（不是文档承诺的）

用户说"大部分功能我都比较满意"，核查后可以精确定位满意的是什么——**一条闭环**：

> 看它动（自己走 / 爬墙 / 天花板爬行）→ 点它说话（随机语录气泡）→ 拖它 / 投掷 / 固定 / 聚到角落 → 开关（互动 / 攀爬 / 大小）→ 选 1~3 只

**而以下功能是死的**（做需求对照时应当作不存在）：

| 看似有的功能 | 实际情况 |
| --- | --- |
| 喂食 / 玩耍 / 聊天 / 设置 / 隐藏（长按菜单 + 电量 CPU chips） | **整套 UI 与处理逻辑都写好了，但不可达**——长按已被"解锁拖动"占用，`onPetLongClick` 参数在 Compose 侧声明后**从未被调用** |
| 情绪 / 饥饿 / 能量 / 亲密度 / 等级 | **被作者主动删除**（提交 `c443605` 精简 `PetStateManager`）。数值恒为初值，`updatePetStatus` / `addExperience` 全是无调用者的孤儿方法 |
| 宠物创建 / 自定义精灵 | 创建页已被删除，设置页入口留着但**空实现**（`onNavigateToCustomPet` 默认空函数） |
| 开机自启动开关 | 写入的 key 与 `BootReceiver` 读的 key **不一致**，开关与实际行为无关 |
| "静止"按钮 | 打开操作栏本身就 `setPaused(true)`，关闭时又 `setPaused(false)`——**暂停无法保持** |
| 记忆相册"重要时刻" Tab | 永恒为空，`recordMilestone()` 无任何调用者 |
| README / 设计文档承诺 | Lottie 动画、情绪随时间变化、向下滑动最小化、长按显示快捷菜单——**均与代码不符** |

**这条事实比功能清单更重要**：参考项目的作者**也做过情绪与养成系统，然后主动砍掉了**。这说明"虚拟养成"这条路连它的实现者都不认为值得保留——与我们在 §1.3 的 Non-Goals 判断一致。

### 3.2 可借鉴的**手法**（与"功能"区分开）

| 手法 | 为什么值得借鉴 |
| --- | --- |
| **空间行为**（走 / 爬墙 / 天花板爬行） | lumii 宠物**位置恒定在画布中心**，只在拖拽时移动。空间维度完全没用上 |
| **位置感知的 UI** | 气泡按宠物贴附的边缘切换弹出方向（贴左墙→气泡在右）；用一个 `edge` 字段驱动五处逻辑 |
| **即时气泡短句** | lumii 有卡拉OK字幕与控制坞聊天面板，但**没有浮在宠物头上的即时反馈** |
| **阈值 + 迟滞带 + 边沿检测** | 参考项目最成熟的一块（CPU 80/50、内存 85/70、温度 40/35）。任何"状态驱动行为"都必须有这层，否则阈值附近疯狂刷屏 |
| **拖拽落点决定状态** | 松手位置 → 贴左墙就爬墙、贴顶就倒挂。用户无需学任何额外 UI |
| **暂停时仍推进动画** | 冻结位移但不冻结呼吸——"静止"不等于"死机" |

### 3.3 必须警惕的**原则冲突**

参考项目的自主行为是**随机权重抽动作**（`[STAND 0.3, WALK 0.4, SIT 0.2, GREET 0.1]` + 5 秒骰子）+ **固定台词池随机选**。

按 lumii 生命感设计 §六的标准，这**恰是"表演"**：

> "它的反应**不完全可预测**，但事后能理解" —— 参考项目的随机**事后不可理解**（就是随机）
> "最快毁掉生命感的是表演情绪" —— 无缘由地突然打招呼、坐下，正是表演

**所以：借它的手法，不借它的驱动方式。** lumii 的自主行为应由**真实状态**驱动（Mood / Agent 活动 / 闲置阶段），而不是骰子。

## 四、需求候选与优先级

评估维度沿用需求分析方法论的矩阵法。「应交付」= 是否属于用户核心价值闭环。

| # | 需求项 | 应交付 | 复杂度 | 成本 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| R1 | **让自制宠物能演出情绪**（补表情层 / 补 emotionMap 映射 / 补 Prompt 可用的表情名） | ✅ 核心 | 中 | 中 | 🔴 **P0** |
| R2 | **点击有回应**（hitAreas 声明 或 tapMotions 匹配修正） | ✅ 核心 | 低 | 低 | 🔴 **P0** |
| R3 | **口型层接上**（否则说话嘴不动，且 LipSync 白跑） | ✅ 核心 | 中 | 中 | 🔴 **P0** |
| R4 | **打盹/睡着/醒来能看见**（对齐候选名与素材命名） | ✅ 核心 | 低 | 低 | 🔴 **P0** |
| R5 | **Agent 干活过程可见**（订阅 tool/thinking/context/subagent → 专注/忙碌姿态） | ✅ 核心 | 中 | 低 | 🔴 **P0** |
| R6 | **需要决策时宠物来叫人**（`permission:request` + `ask-user:request` → 走到面前 / 冒气泡 / 焦急） | ✅ 核心 | 中 | 低 | 🟡 **P1** |
| R7 | **即时气泡短句**（浮在宠物头上，模板池 + 分档，零延迟） | ✅ | 中 | 低 | 🟡 **P1** |
| R8 | **上下文压力 → 疲惫表达**（`context:usage` 逼近阈值） | 部分 | 低 | 低 | 🟡 **P1** |
| R9 | **空间行为**（自主走动 / 贴边 / 拖拽落点语义） | 部分 | 高 | 高（需生成动作组） | 🟢 **P2** |
| R10 | **位置持久化** | 部分 | 低 | 低 | 🟢 **P2** |
| R11 | **多宠物同屏** | ⚠️ 待定 | 高 | 高 | 🟢 **P2**（**本期不做**，见 D4） |
| R12 | 虚拟养成数值 | ❌ | — | — | 不做（§1.3） |
| **R13** | **用户创作平台**：用户在客户端上自己设计**角色 / 动作 / 交互 / 特效**并**实时运行** | ✅ | 高 | 高 | 🔵 **预留**（当前不实现，架构须可接） |

**判断依据**：

- **R1-R4 是"零件在位、线没接"**——已有设计意图、已有代码路径、已有开关，**断在素材与命名对齐上**。用户已经能感知到"开了没用"，属体验破损而非新功能。
- **R5-R6 是 lumii 独有的价值**（参考项目不可能有）：它的宠物只能感知机器负载，lumii 的宠物能感知**Agent 的意图与困境**。尤其 R6——桌宠能"走到你面前"，这是普通通知做不到的事。
- **R9 是参考项目最亮的部分**，但成本最高（每个动作一批生图），且与"不表演"原则有张力（无缘由走动 = 表演）。**建议先做驱动来源（R5）再做动作本身**：如果宠物会因 Agent 状态而动作，空间行为的价值才立得住。

### 关于 R13（用户创作平台）

它的性质与前面都不同：**不改变宠物"是什么"，而是改变"谁来定义"**。

| | 现在的模式 | R13 之后 |
| --- | --- | --- |
| 角色 | 开发者出示范 + AI 技能生成 | 用户在客户端里设计 |
| 动作 | manifest 声明（已是数据） | 用户在客户端里编排 |
| 交互 | **代码硬编码** | 用户定义触发与响应 |
| 特效 | **代码硬编码** | 用户定义 |
| 生效方式 | 装载后固定 | **实时运行**（改完即见） |

本轮**只做架构预留，不实施**（见 [`2026-09-21-宠物创作平台预留设计.md`](2026-09-21-宠物创作平台预留设计.md)）。但它有两条**现在就生效**的约束，会反过来影响 R1-R10 的做法：

1. **不把行为写死在代码里**——凡是要进"事件 → 表现"这条链的，都应当走数据路径。否则未来接编辑器等于重写。
2. **规范要能容纳"造得不完整"**——用户造的包一定比示范模型更残缺，所以降级必须可见、必须不崩（见 [`2026-09-21-宠物包规范设计.md`](2026-09-21-宠物包规范设计.md) §四）。

**一处必须提前想清楚的张力**：R13 要"用户能定义交互"，而 §1.3 明令"不表演"。两者不冲突——**平台提供能力，规范引导默认**：内置模板与默认行为继续遵守"不表演"，用户若明确要一只乱蹦的宠物，那是他的选择。**约束的是我们自己的默认值，不是用户的上限。**

## 五、已决策（2026-09-21）

| # | 问题 | 决定 | 影响 |
| --- | --- | --- | --- |
| D1 | **性格取向** | **安静的助手**——有状态才动，没状态就静静呼吸/眨眼；行为由 Agent 真实状态驱动，不做无缘由动作 | 生命感来自"它的反应对得上刚发生的事"。R9 空间行为不服务于这个目标，故降级；补素材时表情以**准确**为先，不追求数量 |

**由 D1/D2 推出的执行顺序**：

```
第一优先：让状态可见（R5/R6/R8）——这是「安静的助手」的全部意义所在
第二优先：修断点（R1-R4）——开关开了要看得见
推迟：R9 空间行为、R11 多宠物
```

### 由 D4 带出的一项可独立推进项

R11 不做，但它的**第一步可以单独做**：**渲染舞台重构**（把 `PIXI.Application` 的所有权从 `SpritePetRenderer` 提出来交给舞台层）。

它不依赖多宠物需求——现在是"每个 renderer 实例自建一个 Application"，即一个 WebGL context；这在单只场景下也是隐患（失焦降帧要各调一遍、两套后端各自为政）。**单只状态下就能做完并验证零回归，做完即收益。**详见 [`多宠物同屏设计`](2026-09-21-多宠物同屏设计.md) §七。

## 五之二、决策变更：D1/D2 的边界放宽（2026-09-21 晚）

**触发**：用户提出「参考 AI-desktop-pets 先实现一份基础版精灵宠物」，并在被告知这与 D1 冲突后，明确选择了「**空闲时自己游走**」。

**为什么可以变**：D2 当初的两条理由，有一条已经不成立。

| D2 的原理由 | 现在的状态 |
| --- | --- |
| 成本最高（**每个动作一批生图**） | **同日已消除**。现成 Shimeji 精灵表自带 STAND/WALK/SIT/JUMP/FALL/DRAG/CRAWL/CLIMB 九行动作，导入成本为零（[`桌宠动作生成方案调研`](2026-09-21-桌宠动作生成方案调研.md) §七·补五） |
| 无缘由走动 = 表演（§3.3） | **仍然成立**，故只放宽边界、不放弃原则——见下表的做法 |

**变更后的边界**（D1 的哪部分保留、哪部分放开）：

| | 变更前 | 变更后 |
| --- | --- | --- |
| 空闲时会不会自己动 | 不会（只有呼吸/眨眼） | **会**，但节奏与参考项目差一个量级 |
| 驱动方式 | — | **不用骰子**。一张集中的权重/时长表，平均 20~35 秒一次活动；参考项目是 **5 秒一次、30% 概率**（§3.3 判为表演的那套） |
| 动作池 | — | **去掉 GREET**。无缘由打招呼是"表演"最典型的形态，它留给真实事件（用户回来、Agent 需要决策） |
| 空间维度 | 位置恒定在画布中心 | 地面线行走 + 撞墙折返 + 朝向翻转。**不做爬墙 / 天花板倒挂**（那是 D2 说的"高复杂度"部分，本次不碰） |

**D1 未变的部分（仍然禁止）**：宠物不得**无缘由地表达情绪**。自主行为只动**位置与姿态**（走 / 坐 / 站），完全不碰表情层；表情继续只由 Agent 真实状态与用户交互驱动。

**对优先级表的影响**：R9 从 🟢 P2 变成**基础版已实施**（地面行为）。未做：贴边语义、攀爬、位置持久化（R10）。
