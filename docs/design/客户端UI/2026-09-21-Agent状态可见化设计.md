# Agent 状态可见化设计（宠物系统）

> ## ⚠️ 二次核查修正（2026-09-21，**动手前必读**）
>
> 本文有七处经实测推翻或修正。**结合既有实现时以本节为准**：
>
> 1. **§2.1 的时序图方向画反了。** 实测（`~/.lumii/logs/app/mtbot-2026-09-21.log`，当日 205 个 turn 全量统计）：真实顺序是**每个 LLM 轮里正文 delta 先产出、工具随后才跑**，且一个 turn 内 text 与 tool **反复交错**（95% 的 turn 同时含两者；115/205 有 ≥2 个文本轮，最多的一个 turn 有 14 个）。原图画成 `tool:start → tool:end → message:delta`，恰好相反。
>
> 2. **§四的"让位"规则会抖。** 既然 95% 的 turn 内两者在 2–12ms 的边界上交替，而本文的平滑常数是 600ms——**量级不匹配**。应改为**按"段"切而非按"每个工具"切**（工具阶段总长 p50=6s / p90=102s，而单个工具 87% < 200ms），并给 activity 加迟滞。
>
> 3. **"不需要仲裁"不成立。** 既有实现里说话链**跨越整个工具阶段**：`turn:start` 就 `startTextReply`，伪口型在最后一次 delta 之后还会动约 2s（`ACTIVE_HOLD_MS=500` + `ENERGY_DECAY_PER_SEC=0.85`），而工具在 3–12ms 后就开始了。**"嘴在动 + 工具在跑"的叠加现在就在发生**，只是没人观测过。
>
> 4. **命名冲突——`activity` 已被占用。** 占用者：`AmbientActivity`、`PetPose`、`PetWanderDriver.getActivity()`、`PetOrchestrator.ambientActivity`、`agent:activity:snapshot`。**本文所有 `activity` 应改为 `agentActivity`**：模块 `state/agent-activity.ts`、类型 `AgentActivityState`、接口 `setAgentActivity()`、开关 `enableAgentActivityAwareness`、渲染器调制接口叫 `setStateModulation`。值域里 `thinking`/`idle` 与 `PetState`、`phase` 同字面量，**日志与 status 字段必须叫 `agentActivity`**，别在 `phase` 旁边再放一个叫 `activity` 的键。
>
> 5. **接入点修正。** `AmbientConfig` **不是**合适的接入点——它是"空闲时随机溜达"的权重池，把 `working`/`waiting` 塞进 `weights` 等于把表演请回来；而且它**目前没有调用者**（`PetWanderDriver` 的 `config?` 参数没人传）。正确落点是**编排器的门控 + §三的调制层**，与 ambient 只在"谁有权播动作组"这一层交汇（已有汇合点：`PetOrchestrator` 的 `enterIdle`）。
>
> 6. **前置阻塞：真机验证被一个 bug 挡住**——宠物模式进入 3.5–10 秒后自己退回桌面（判据脚本已写未跑完）。**本文 §七的所有真机判据都排在它后面。** 另有渲染尺寸口径待核（`applyAdaptiveScale` 自称 109px，截图量出 262px，差 2.4 倍），**调倍率表前必须先确认这条**，否则量的是错的量。
>
> 7. **§5.4「情绪贴片」不是本文的重复，而是 L2 的现成答案。** 并行会话已落地"SVG 贴片塞进 `slots.face`"（5 只 Shimeji 包，走既有 `emotionMap → setExpression` 路径，**渲染器零改动**）。它是**内容层**（表情词汇零成本获得）；本文 L1 是**强度/动态层**（呼吸/浮动/倾斜的运行时倍率）。两者正交，同一 activity 可以既切贴片又改呼吸。**而贴片绑在 `slots` 上——团子/钢羽这种没有分层脸的模型用不了，L1 恰好补这个洞。**
>
> 8. **§7.2 的判据全是实现指标，需补效果判据。** "呼吸幅度差异 ≥10%"证明不了"用户能感觉到它在忙"。对 L1 这种整个价值都押在微妙感知上的设计，必须加**盲测**：录两段（idle / working）不标注，问观察者"哪段更忙"。

> ## ✅ 实现回填（2026-09-21 晚，实施顺序 1–3 步已落地）
>
> 动手时又推翻了设计里的三处判断，**以本节为准**：
>
> 1. **L1 不参与「让位」（推翻 §四第一行）。** 原文写"`message:delta` 到达即让位：activity 停止影响表达"。照此实现会让 L1 在**整个 turn 内**失效——实测 95% 的 turn 同时含文本与工具，而说话链从 `turn:start` 一直延续到 `turn:end` 之后约 2s，"让位"等于覆盖全程，activity 永远等不到表达机会。
>    正确的划分是 **口型与呼吸作用于不同分量**（嘴部帧 vs root 的呼吸/浮动/倾斜），叠在一起视觉上完全协调——"一边说话一边有点忙"。让位只该作用于 **L3 动作组与 L4 气泡**（它们与对话链路抢同一个资源）。拖拽/投掷期间仍完全不表达。
>
> 2. **平滑用插值，不用 EMA（改 §3.1 与 §7.1）。** EMA 的输出取决于"喂了多少帧、每帧间隔多少"，同一组 `(state, now)` 在不同帧率下算出不同的值——那就不是纯函数，也没法写"给定 `now` 断言输出"的测试。改成 `previousActivity → activity` 的 smoothstep 时间插值：完全由 `(activity, previousActivity, activityChangedAt, now)` 决定，可重放、可断言，起止导数为 0。**连带**：§7.1 的"EMA 600ms 内到 90%"作废，改为"走满 600ms 恰好到位"。
>
> 3. **§7.2 的「单帧变化 < 1%」在 600ms 参数下数学上不可能。** smoothstep 中点斜率为 1.5，60fps 下单帧变化恒为 `1.5 × 16.67 / 600 = 4.2%` 的**总幅度**——与幅度差无关，是参数决定的。要么把平滑时间拉到 750ms 以上，要么该判据按**相对量**重写（现取"中点单帧 ≤ 总幅度 5%、两端 ≤ 1%"）。留给数值校准阶段定。
>
> 4. **呼吸倍率必须乘在偏离量上。** `evaluateProcedural` 的 `scale` 是 `1 + (max-1)·wave`，一个**以 1 为中心**的振幅。写成 `scale × 1.3` 会把"呼吸加重 30%"变成"宠物整体放大 30%"：不报错、不 NaN、只是肉眼可见地胀一圈。这条已抽成 `applyActivityModulation()` 并被单测钉住（含一条专门卡住错误写法的上界断言），**不要绕过它手写那三个乘法**。
>
> 5. **文件与符号名**（对齐修正块第 4 条）：`state/agent-activity.ts`、`render/agent-activity-modulation.ts`；`AgentActivityState`、`reduceAgentActivity` / `tickAgentActivity` / `mapAgentEvent`；渲染器 `setAgentActivityModulation`、编排器 `pushAgentActivity` / `setEnableAgentActivity`。
>
> 6. **`WORK_SEGMENT_GAP_MS = 200` 的依据与一个反例。** 200ms 来自"段内间隔 2–12ms"。但真机跑"读文件 → 再读另一个"的轮次时，观测到**两次工具之间隔了 750ms**（模型在思考）——迟滞窗口小于它，于是状态正确地切回 thinking 又切回来。语义没错（那 750ms 确实在思考），但 600ms 的平滑在 750ms 的间隔里永远走不到稳态，观感是"幅度来回起伏"。**这是校准项**：要么把窗口拉大到 ~1000ms 把整个工具段并成一段，要么接受这种起伏（它确实反映了真实节奏）。
>
> 7. **关闭必须真的归零。** `setEnableAgentActivity(false)` 只停推进是不够的：状态机不再被 tick，也就没有下一次 setter 去覆盖，宠物会永远停在最后那一档的呼吸上。必须**立刻**把恒等调制送出去。
>
> **真机验证**（`verify/pet-sprite/check-agent-activity.mjs`）：三条判据全过——`idle → thinking`（订阅通）、`thinking → working`（工具段识别）、`setAgentActivityModulation` 已送达渲染器。
> **未验证**：视觉上"是否感觉得到"（§7.2 修正块第 8 条要求的盲测），以及 §7.3 的端到端闭环。

## 一、这份设计解决什么

### 1.1 问题

Agent 真正干活的时段，宠物**没有任何表达**。

实测量化：宠物窗口只订阅 6 个事件（`turn:start` / `message:delta` / `message:end` / `turn:end` / `agent:idle` / `autonomous:mood:emotion`）。而 `agent:tool:start|progress|end`、`thinking:delta`、`context:usage|compacted`、`subagent:completed`、`activity:snapshot`、`permission:request` **全部未订阅**。

后果：Agent 调 40 次工具跑 12 分钟，宠物在这 12 分钟里**只在播随机待机或静止**——最该有表现力的时段最空。

### 1.2 约束（来自决策与既有设计）

| # | 约束 | 来源 |
| --- | --- | --- |
| C1 | **不表演**：每个可见行为都必须能追溯到一条真实事件 | 生命感设计 §11 禁令 |
| C2 | **安静的助手**：有状态才动，没状态就静静呼吸 | 决策 D1 |
| C3 | **素材受限**：三只示范模型只有 `Idle` / `Talk` / `Wave` 三个动作组；团子与钢羽连表情层都没有 | 实测 |
| C4 | **不打扰**：桌宠的可视面积在用户工作区之上，表达强度必须与信息价值匹配 | §1.3 Non-Goals |
| C5 | **不与既有维度打架**：对话链路、Mood、闲置感知、注视、拖拽投掷都已在线 | P2-a 的既有原则 |

### 1.3 设计主线

> **不是"给宠物加动作"，而是"把 Agent 的真实活动翻译成宠物能表达的最小信号"。**

素材受限（C3）不是障碍——它反而把设计逼向正确的方向：**表达的主力是"姿态"而不是"动作"**。

## 二、核心模型：activity（正交维度）

### 2.1 为什么是新维度

lumii 已有三个宠物维度，且**互相正交**（这是 P2-a 明确立下的原则："物理状态与对话生命周期正交，硬塞会让两个维度互相干扰"）：

| 维度 | 内容 | 变化频率 |
| --- | --- | --- |
| `petStateMachine` | 对话生命周期（listening / thinking / speaking…） | 秒级 |
| **Mood** | 内在情绪（energy / valence / arousal） | 小时级 |
| **idleStage** | 用户是否在场（打盹 / 睡着） | 分钟级 |
| **activity（本文）** | **Agent 正在做什么** | 秒级 |

`activity` 与 `petStateMachine` 最容易混淆，边界必须划清：

- `petStateMachine` 回答「**宠物在跟用户对话吗**」
- `activity` 回答「**Agent 在干活吗**」

一轮对话里两者**交替出现**，而不是并行：

```
turn:start ──→ thinking ──→ tool:start ──→ [工具执行中] ──→ tool:end ──→ message:delta ──→ turn:end
   │              │              │                              │              │
   │         activity=          activity=                    activity=      activity=
   │         thinking           working                      working        (让位给对话)
   └─ 对话链路（口型/字幕）在这段是**沉默**的，直到 message:delta 才接管
```

**关键结论**：`activity` 与对话链路**天然错开**，不需要复杂的优先级仲裁——`message:delta` 一到，`activity` 自动退场。

### 2.2 状态定义

```ts
type PetActivity =
  | 'idle'        // 无活动
  | 'thinking'    // 模型思考中（thinking:delta 已开始、还没有工具或正文）
  | 'working'     // 有工具在执行
  | 'waiting'     // 等用户决策（permission / ask-user）—— 唯一允许强打扰的状态
  | 'blocked'     // 出错 / 被中止
```

五个状态，刻意不做更多。「Agent 在读文件」与「Agent 在跑命令」对用户是同一件事：**它在忙**——细分只会让表达失真（C1）。

### 2.3 转移规则（纯函数）

```
任何状态 --agent:turn:start--> thinking
thinking --tool:start--> working
working  --tool:end(还有后续)--> working
working  --tool:end(最后一个)--> thinking
任何状态 --permission:request|ask-user:request--> waiting
waiting  --(用户已响应 / 超时)--> 回到进入前的状态
任何状态 --agent:error|agent:abort--> blocked
blocked  --(3s)--> idle
任何状态 --message:delta--> 让位（activity 不影响表达，见 §四）
任何状态 --turn:end|agent:idle--> idle
```

**计数**：`working` 需要记住本轮的累计工具数与起始时间——它们是表达强度的输入（§四）。

## 三、表达分层

素材受限（C3）下，表达按"素材依赖从低到高"分四层。**上层缺失时自动降级到下层，绝不静默失败**（这是 P2-a「模型声明了才播，没有就静默跳过」的教训——那次是**不该演就不演**，这次是**演不了要有替代**）。

| 层 | 手段 | 素材依赖 | 感知强度 | 用途 |
| --- | --- | --- | --- | --- |
| L1 | **姿态叠加**（呼吸/浮动/倾斜的调制） | **零**（程序化原语） | 弱、常驻 | 状态底色：一直在，但说不出具体是哪一帧在变 |
| L2 | **表情** | 需表情层 | 中 | 有表情层时表达思考/疲惫/警觉 |
| L3 | **动作组** | 需对应动作组 | 强、瞬时 | 关键节点（如 `waiting` 时播一次 `Wave`） |
| L4 | **气泡短句** | **零** | 最强 | 只有 `waiting` 默认使用 |

**L1 是主力**——这是本设计最关键的一个判断。理由：

1. 它零素材成本，对所有模型（含用户自制）都能生效
2. 它**天然符合"不表演"**：姿态变化是连续的、可归因的，没有"突然做了个动作"的突兀感
3. 它可逆、可叠加、可平滑过渡

### 3.1 L1 的具体映射

不修改原语的**周期**（改周期会让 `sin` 相位跳变，视觉上"一顿"，且违反 `SpritePetRenderer` 里"不要手写一遍"的既有约束），而是在 `evaluateProcedural()` 的输出之上**叠加一层由 activity 驱动的调制量**，并用 EMA 平滑：

| activity | 呼吸幅度 | 浮动幅度 | 倾斜 | 直白解释 |
| --- | --- | --- | --- | --- |
| `idle` | ×1.00 | ×1.00 | 0° | 基线 |
| `thinking` | ×1.15 | ×0.85 | 微倾 2° | 屏息凝神：气吸得深一点，动得少一点 |
| `working` | ×1.30 | ×1.20 | 0°，带小幅摆动 | 忙起来了：呼吸重、动作幅度大 |
| `waiting` | ×1.35 | ×1.45 | 前倾 4° | 探身：它在等你 |
| `blocked` | ×0.85 | ×0.70 | 后仰 -2° | 蔫了一下 |

数值全部**待实测校准**（见 §七），此处只确立方向与相对关系。调制量的平滑时间常数取 **600ms**——足够快以对上事件，足够慢以避免抽搐。

> **为什么这套能工作**：人对"活物"的感知对**呼吸节奏**高度敏感（这是生命感设计 §六"状态连续变化"的直接应用）。呼吸变重、幅度变大，用户未必能说出原因，但**能感觉到它在忙**——这正是 §六 "用户不需要被告知它的心情，用户从它的行为里感觉到"。

### 3.2 L4 的克制原则（防骚扰）

C4 是硬约束。参考项目每 10~20 秒随机冒一句台词——那是**骚扰**，且违反 C1。

本设计的气泡规则：

| activity | 气泡 |
| --- | --- |
| `thinking` / `working` | **默认不冒**。仅在"连续工作超过 60s"或"工具数超过 15 个"时冒**一次**（"还在忙…"），且同一轮内只冒一次 |
| `waiting` | **必冒**，且这是唯一默认开启的强打扰："需要你确认一下" |
| `blocked` | 冒一次（"出错了"） |
| `idle` | 不冒 |

**所有气泡受同一个节流器**：同一条消息在 10 分钟内不重复。这与参考项目"随机从池里挑一条"的做法相反——**宁可不说，不要废话**。

## 四、冲突与仲裁

| 冲突对象 | 规则 | 理由 |
| --- | --- | --- |
| **对话链路**（口型/字幕/动作） | `message:delta` 到达即让位：activity 停止影响表达，直到 `turn:end` | §2.1——两者天然错开，不需要优先级判断，只需让位 |
| **闲置感知**（打盹/睡着） | **Agent 活动期间抑制打盹** | 用户离开 30 分钟但 Agent 仍在跑长任务时，"我困了"是假的，"我在干活"是真的（C1）。用户回来时看到的是工作姿态而非睡姿，这更诚实 |
| **Mood** | Mood 是**底色**（慢），activity 是**前景**（快）。两者都要改表情时 activity 优先；activity 回 `idle` 后淡回 Mood 的表情 | 时间尺度差三个数量级，叠加不会打架 |
| **注视** | 注视驱动 `gazeOffset`（眼睛与倾斜），activity 驱动叠加层——**两者都叠加在 root 上但作用于不同分量** | `setGaze` 已占 `tiltDeg` 与位移，activity 的倾斜要另开分量或与之相加（实施时确认，避免 P2-b 实测过的"朝反方向歪"类问题） |
| **拖拽/投掷** | 拖拽期间 activity **完全不表达**（`setPicked` 已暂停待机调度） | 用户手动交互优先于一切自动表达 |
| **用户关闭开关** | 新增 `enableActivityAwareness` 开关，默认开 | 所有自主行为都必须能关（P2-c 的既有约定） |

| `apps/windows/src/renderer/pet/renderer/types.ts` | `PetRendererProvider` 增加可选 `setActivityModulation?`（Live2D 后端可不实现，与 `setGaze` 同规格的守卫写法） |
| `apps/windows/src/shared/virtual-human.ts` | 新增 `enableActivityAwareness` 设置项 |

### 5.3 接口草案

```ts
// pet-core：纯函数，无副作用
export function reduceActivity(
  prev: PetActivityState,
  event: ActivityEvent,
  now: number,
): PetActivityState

export interface ActivityModulation {
  readonly breatheScale: number   // 乘在 transform.scale 上
  readonly bobScale: number       // 乘在 transform.offsetY 上
  readonly tiltDeg: number        // 加在 transform.rotation 上
}
export function activityModulation(
  state: PetActivityState,
  now: number,
): ActivityModulation
```

**不变量**（单测必测，与 `throw-physics.ts` 同规格）：任何输入下输出都是有限数；未知事件不改变状态；`activityModulation` 的输出恒在预设边界内。

## 六、素材策略（支撑 L2 / L3，但 L1 不依赖它）

本设计的 L1 **不依赖任何新素材**——这是它能对所有模型（含用户自制）生效的原因。

L2/L3 的素材补齐属于需求 R1（B1/B5/B6），由决策 D3「用已有能力重跑生成」解决，**不在本文范围内**，但有一条设计约束必须现在定下：

> **表情命名要与代码侧的候选名对齐。**
> B6 的根因是素材命名体系（`eye_happy` / `exp_01`）与代码候选名（`sleepy` / `困` / `drowsy`）脱节，实测在三只模型上**命中 0/5**。
> 重跑生成时，`pet-creator` 技能的产出规范应保证每个表情层**同时写入 `emotionMap` 的语义键**，而不是让代码去猜素材叫什么。

## 七、测试与验收

### 7.1 单测（pet-core，纯函数）

- 转移表：19 条转移全覆盖，含非法事件保持原状态
- `working` 计数：连续 `tool:end` 不误判为结束
- 让位：`message:delta` 后 activity 不再影响调制输出
- 平滑：EMA 在 600ms 内到达目标值的 90% 以内，且**不超调**
- 不变量：NaN / Infinity / 负时间 / 时钟回退 均不产生非法输出

### 7.2 量化手测（沿用 P2-b / P2-c 的做法）

| 判据 | 期望 |
| --- | --- |
| 基线冻结 | `idle` 下连续采样 10s，调制量恒为 `{1, 1, 0}`，宠物姿态与本设计上线前**逐像素一致**（零回归） |
| 状态可分辨 | `thinking` / `working` / `waiting` 三态下的呼吸幅度两两差异 ≥ 10% |
| 平滑无跳变 | 状态切换瞬间，`scale` 单帧变化 < 1%（不出现"一顿"） |
| 让位正确 | `message:delta` 到达后 1 帧内调制回落到基线 |
| 气泡节流 | 一轮 40 次工具调用，气泡出现次数 ≤ 2 |
| 不打扰 | `waiting` 之外，10 分钟内气泡 ≤ 1 次 |
| 开关有效 | 关掉 `enableActivityAwareness` 后 Δ 全为 0 |

### 7.3 闭环验证（需求方法论 §1.5）

> 用户发出一个长任务 → Agent 开始调工具 → **宠物呼吸变重、幅度变大**（用户瞥一眼就知道它在忙）→ Agent 需要授权 → **宠物探身并冒一句"需要你确认一下"**（用户被叫回来）→ 用户确认 → Agent 继续 → 回复开始 → **宠物转回说话姿态**（口型接管）

每一环都有可观测判据，无"看起来像对的"环节。
