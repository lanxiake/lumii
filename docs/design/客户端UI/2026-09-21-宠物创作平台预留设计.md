# 宠物创作平台预留设计

需求依据：[`2026-09-21-宠物系统需求分析.md`](2026-09-21-宠物系统需求分析.md) §四 R13。
相关：[`2026-09-21-宠物包规范设计.md`](2026-09-21-宠物包规范设计.md)（规范是编辑器的产出约束）。

**本轮不实现编辑器 UI**。本文交付的是**架构预留**：把运行时改成"经得起接编辑器"的形状。

---

## 一、需求与边界

### 1.1 R13 要什么

用户在客户端上自己设计 **角色 / 动作 / 交互 / 特效**，并**实时运行**（改完即见）。

### 1.2 什么叫"预留到位"

判据只有一条：

> **未来接编辑器时，是"加一层"还是"重写一遍"。**

- ✅ 预留到位 = 运行时已经在读数据，编辑器只是**改数据的 UI**
- ❌ 预留不到位 = 运行时到处是硬编码，编辑器要先把它们挖出来

**所以本文的核心交付不是格式草案，而是「硬编码点清单 + 每一点的抽取方案 + 现在做/以后做的分界」。**

### 1.3 分界标准

| 判据 | 结论 |
| --- | --- |
| 现在不做，未来也只是"加个表"、不需要动运行时结构 | **可以不做**，只需在本文登记 |
| 现在不做，未来要重构运行时才能接 | **建议现在做**（成本低、收益大） |

## 二、现状盘点：哪些已经数据驱动

### 2.1 已经是数据（作者改清单就能改）

| 维度 | 承载字段 | 位置 |
| --- | --- | --- |
| **形象**（分层） | `slots` / `parts` | `manifest.json` |
| **动作** | `animations[]`（`group` / `kind` / `fps` / `frames` / `next`） | `manifest.json` |
| **程序化原语** | `animations[].params`（`bob` / `breathe` / `sway` / `nod` / `blink`） | `manifest.json` |
| **表情映射** | `emotionMap`（语义名 → 索引） | `registry.json` / `pet.json` |
| **待机调度** | `idleMotionGroup` / `idleMotionRandomGroups` / `idleMotionFallbackGroup` | 同上 |
| **语义动作** | `actionMotions`（`[motion:tag]` → 组/序号） | 同上 |
| **点击动作** | `tapMotions`（命中区 → 组） | 同上 |
| **命中几何** | `hitAreas[]`（多边形） | `manifest.json` |
| **口型档位** | `mouthLevels[]` | `manifest.json` |
| **人设** | `personaAddon` / `toolPrompts` | `registry.json` |

**这一半已经很好了**——清单格式（`sprite-manifest.ts`）本身就是按"数据不是代码"设计的，且有完整校验。

### 2.2 仍然是硬编码（要接编辑器就得先数据化）

**A. 交互入口**（`PetCanvas.tsx`，7 个监听器全部写死）

| 监听 | 硬编码的行为 | 目标值来源 |
| --- | --- | --- |
| `mousedown` | 命中 → 拖拽开始 → `setPicked` | 组名 `'Picked'` 硬编码 |
| `mouseup`（点击） | `triggerTapMotion(hit ?? 'body')` + 烟花 | ⚠️ 部分（查 `tapMotions`，但兜底链与 `'body'` 字面量写死） |
| `mouseup`（拖拽） | 速度 ≥320 → 抛掷；否则原地落下 → `notifyLanded` | ❌ 组名 `'Land'`、阈值 `320` 硬编码 |
| `wheel` | `adjustScaleByDelta` | ❌ 灵敏度与倍率夹取写死 |
| `mousemove` | hover → `reportModelHover` | ❌ 驱动窗口穿透，属系统行为 |
| `mouseleave` | 清 hover | 同上 |
| `resize` / `blur` / `focus` | 重算布局 / 降帧 | 系统行为，不需要数据化 |

**B. 时间驱动**（`PetOrchestrator.ts`）

| 行为 | 硬编码值 |
| --- | --- |
| 待机随机轮播间隔 | `IDLE_MOTION_MIN_MS = 8000` / `MAX = 15000` |
| 打盹时轮播拉长 | `IDLE_MOTION_DROWSY_FACTOR = 3` |
| 对话结束冷却 | `POST_DIALOGUE_IDLE_DELAY_MS = 10_000` |
| 装饰性待机组的判定规则 | "与库基础 idle 组不同 + 组内 >1 个动作" |

**C. 特效**（`click-fireworks.ts`）

`PARTICLE_COUNT = 28`、`GRAVITY = 900`、`LIFE_DECAY = 0.9`、7 色调色板、粒子尺寸范围——**全部写死，唯一入口 `spawnClickFireworks(x, y)`**。

⚠️ 但**这只是"代码特效"那一半**。另一半——**图集特效**（角色周围的星星/爱心/汗滴/闪光）——**现有 `slots` 机制已经完整支持**，不需要预留（见 §3.3）。后文把两者分开处理。

**D. 状态驱动**（本次新增的 activity 设计）

`Agent 状态可见化设计` 里的调制倍率表、气泡节流阈值同样是硬编码——**它们也应当进同一张规则表**（见 §三.3）。

### 2.3 现成的、但没接线的资产（**最重要的一条**）

`pet-core` 里已经有三张"事件 → 表现"的表，**Windows 端一个都没用**：

| 模块 | 内容 | 状态 |
| --- | --- | --- |
| `packages/pet-core/src/state/petStateMachine.ts` | 融合 9 态状态机 + 完整转移表 | **零消费者**（仅导出与测试引用） |
| `packages/pet-core/src/expression/state-expression-policy.ts` | `STATE_EXPRESSION`：9 态 → `{ emotion, motionGroup }` | **零消费者** |
| `packages/pet-core/src/mapping/agentSignalMapper.ts` | `AgentSignal → PetEvent` + 网络错误码白名单 | **零消费者** |

> `STATE_EXPRESSION` 用的正是**语义标签**（`neutral` / `calm` / `joy` / `sadness`），且已有 `resolveExpressionIndex(emotion, emotionMap, default)` 做"语义 → 索引"的解析——**与 [`宠物包规范设计`](2026-09-21-宠物包规范设计.md) §三.2 要求的语义键体系完全一致**。这套体系不是要新建，是已存在却没接上。

**这对本设计的意义**：表 B 里那 33 条硬编码映射，**不必从零设计格式**——`STATE_EXPRESSION` 已经是"状态 → 表情语义 + 动作组"的雏形，把它扩展成 §三 的 `interactions[]` 是**顺着既有形状长**，而不是另起一套。

Windows 端实际用的是 `PetOrchestrator` 里一组**布尔标志 + 硬编码 switch**（`speaking` / `textReplyActive` / `dialogueActive` / `idling` / `interactionActive` / `idleStage` / `inPostDialogueCooldown`）。**这两套东西最终要合一。**

### 2.4 两套后端的能力不对等（创作平台必须面对）

这是**格式设计之前必须先承认的现实**——同一个清单在两套后端上能力不同：

| 能力 | Live2D | sprite |
| --- | --- | --- |
| 待机自动循环 | ✅ 库自己循环（`autoLoopsIdle` 省略即 true） | ❌ **必须编排器主动启动**（`SpritePetRenderer.ts:112` 显式 `false`），否则永远停在第一帧 |
| `setGaze` 注视 | ❌ 未实现（`PetCanvas.tsx:319` 是可调用守卫，静默 no-op） | ✅ 已实现，含眼睛额外增益 |
| 动作播完跳转 `next` | ❌ 靠库的 MotionManager 续播 | ✅ 清单 `next` 字段驱动 |
| "表情"语义 | expression 索引（库管理） | 图层部件列表（索引会被夹进 `parts.length`） |
| 动作播完回调 | Promise resolve | 帧计数 |
| 命中区 | 库的 `getHitAreaDefs()` | 清单 `hitAreas[]` 多边形 |

**设计含义**：

1. **规则必须声明能力前置条件**——一条 `motion` 规则在 Live2D 上可能被库的优先级拦截（返回 `false`），在 sprite 上是"后播覆盖先播"。设计规则语义时**不能假设后端行为一致**。
2. **`interactions[]` 里应当允许 `when: { rendererType: 'sprite' }` 这类条件**（或等价的"能力声明"），让作者能为不同后端写不同规则，而不是被迫取交集。
3. **§七 验收必须两端各跑一遍**——只测 sprite 会漏掉 Live2D 的优先级差异（这是 P0-b 已经踩过一次的坑：`autoLoopsIdle` 的差异导致 sprite 后端"永远停在第一帧"）。

## 三、数据格式设计（v2，全部可选）

### 3.1 设计原则

| 原则 | 理由 |
| --- | --- |
| **全部可选，缺省 = v1 行为** | 现役 7 个模型零改动；不破坏既有校验 |
| **只接受数据，不接受表达式** | 沿用 `sprite-manifest.ts` 已立的安全边界："清单是数据不是代码"。放宽到字符串表达式 = 开放任意代码执行面 |
| **触发器是枚举，不是自由文本** | 枚举可校验、可穷举、可在编辑器里下拉选择 |
| **一次报出全部错误** | 既有校验的约定，编辑器体验依赖它 |

### 3.2 `interactions[]`——事件到表现的映射

```jsonc
"interactions": [
  {
    "id": "tap-body",                                   // 可选，供编辑器引用
    "on": { "type": "tap", "hitArea": "body" },
    "do": [
      { "type": "motion", "group": "Wave" },
      { "type": "effect", "name": "sparkle", "at": "pointer" }
    ]
  },
  {
    "on": { "type": "agent", "event": "tool:end", "isError": true },
    "when": { "activity": "working" },
    "do": [{ "type": "expression", "name": "sadness" }]
  }
]
```

**触发器（`on.type`）全集**——覆盖现有硬编码点，并为未来留位：

| 类型 | 参数 | 对应现有硬编码 |
| --- | --- | --- |
| `tap` | `hitArea?` / `button?` | `mouseup` 点击分支 |
| `drag:start` | — | `setPicked` |
| `drag:end` | `minSpeed?` / `edge?` | 抛掷阈值 320、`notifyLanded` |
| `hover:enter` / `hover:leave` | `hitArea?` | `mousemove` hover |
| `wheel` | `direction?` | `adjustScaleByDelta` |
| `timer` | `everyMs` / `jitterMs?` / `chance?` | 待机随机轮播 |
| `state` | `dimension` + `value` | 闲置/对话/activity 迁移 |
| `agent` | `event` / `toolName?` / `isError?` | R5/R6 新增的订阅 |
| `mouth` | `atLevel?` | 口型档位联动 |

**动作（`do[].type`）全集**：

| 类型 | 参数 | 说明 |
| --- | --- | --- |
| `motion` | `group` / `index?` | 播动作组——**图集特效也走这条**（特效就是一个动作组） |
| `expression` | `name?` / `index?` | 切表情 |
| `effect` | `name` / `at` | **仅代码特效**（位置由事件决定的粒子类），见 §3.3 |
| `bubble` | `text` / `pool[]` / `ms?` | 冒气泡 |
| `modulation` | 姿态调制覆盖 | 本次 activity 设计的产物 |
| `scale` | `delta` | 缩放 |

**条件（`when`）**——刻意保持贫弱，防图灵完备：只支持**键值匹配**与 `$lt` / `$gt` 两个比较符，键限定为 `activity` / `mood.energy` / `mood.valence` / `mood.arousal` / `idleStage` / `dialogue`。

### 3.3 特效：两条路，**主力是图集，不是代码**

> **这条修正了一个初版设计的偏差**：特效不一定是额外写的代码粒子，更多时候它就是**角色图集里的一组图片**——星星、爱心、汗滴、闪光、怒气符号。这更符合精灵图路线的传统，也更适合用户创作（画/生成图片比调参数直观）。

#### 路线一：图集特效（**现有机制已支持，零改动**）

特效 = 一个普通的 `layered` 槽位。实测确认 `buildLayers`（`SpritePetRenderer.ts:329-340`）对**任意** slot 名一视同仁：遍历 `slots`、为每个 `parts` 类别建 sprite、位置取 `def.at`；`applyState` 同样遍历所有 layered slot 按帧切换纹理。**唯一的特殊化是 `bindMouthAndExpression` 去"认"哪个槽是嘴/眼**（为了口型与表情轴能驱动它们），其余槽位一律由**动画帧**驱动。

```jsonc
"slots": {
  "face": { "kind": "layered", "at": [0, 0], "parts": { "eyes": ["eye_open", "eye_happy"] } },
  "fx":   { "kind": "layered", "at": [0, -12], "parts": { "aura": ["fx_star_00", "fx_star_01", "fx_star_02"] } }
},
"animations": [
  { "group": "Sparkle", "kind": "once", "fps": 8, "next": "Idle",
    "frames": [
      { "fx": { "aura": "fx_star_00" } },
      { "fx": { "aura": "fx_star_01" } },
      { "fx": { "aura": "fx_star_02" } },
      { "fx": {} }                                   // 增量语义：不写 = 沿用，写空 = 隐藏
    ] }
]
```

**三个直接结论**：

1. **特效零预留成本**——它用的是和表情层完全相同的机制。`interactions[]` 里也**不需要新增 `effect` 动作类型**，播特效就是播一个动作组：`do: [{ type: "motion", group: "Sparkle" }]`。
2. **创作平台的"特效"主要落在素材生成上**，不是运行时机制——`pet-creator` 要能出一批特效图（与表情批同构：同机位、透明底、逐格变化）。
3. **`at` 让特效位置相对角色固定**（头顶、脚边、周身），这正是图集特效的适用范围。

#### 路线二：代码特效（补充，用于"位置动态"的场景）

`click-fireworks.ts` 那类与角色无关、**位置由事件决定**的效果（点在哪儿就在哪儿炸），图集做不到——它的位置是动态的。这类保留为代码特效，可选参数化：

```jsonc
"effects": {
  "sparkle": { "kind": "particles", "count": 28, "gravity": 900, "lifeDecay": 0.9,
               "palette": ["#ff6b6b", "#ffd93d"], "speed": { "min": 80, "max": 220 } }
}
```

**两条路的边界**：

| | 图集特效 | 代码特效 |
| --- | --- | --- |
| 位置 | 相对角色固定（`at`） | 动态（事件坐标） |
| 素材成本 | 需出图 | 零 |
| 用户可创作 | ✅ 画/生成即可 | ⚠️ 要调参数 |
| 本轮状态 | **已支持** | 现有硬编码，可选参数化 |

> **注意**：`click-fireworks.ts:20-28` 有一段明确的"**刻意不接主题令牌**"注释（理由：宠物窗无 `ThemeProvider`、每帧 `getComputedStyle` 是性能反模式）。用户自定义调色板与这条**不冲突**——反而正是它想要的能力，别顺手把调色板改成读令牌。

## 四、运行时改造

### 4.1 现在做（成本低、未来省事）

| # | 改造 | 落点 | 为什么现在做 |
| --- | --- | --- | --- |
| T1 | **内置默认规则表**：把 §2.2 的硬编码映射写成一份 `DEFAULT_INTERACTIONS`（代码内的常量，不是文件） | `pet-core/src/interaction/default-rules.ts` | 这一步不做，未来要到处挖硬编码 |
| T2 | **交互入口改为"发触发器事件"**：`PetCanvas` 不再直接调 `setPicked` / `triggerTapMotion`，而是 `emit({type:'tap', hitArea})` | `PetCanvas.tsx` | 同上；且它让"用户自定义交互"变成"换一张表" |
| T3 | **规则执行器**（简化版）：接收触发器事件 → 匹配规则 → 执行 `do[]` | `pet-core`（纯函数匹配）+ `PetOrchestrator`（执行） | 匹配逻辑纯函数化才能单测 |
| T4 | **代码特效参数化**：`spawnClickFireworks(x, y)` → `spawnEffect(name, x, y, spec)`。**图集特效无需此项**（已支持） | `click-fireworks.ts` | 改动极小 |
| T5 | **清单新增字段的校验**（`interactions` / `effects` 白名单 + 类型校验） | `sprite-manifest.ts` | 校验是安全边界，必须与新字段同时落地 |

**T1/T2 是本设计最重要的两条**：它们把"交互"从代码变成数据。做完之后，未来接编辑器 = **让用户能改这张表**。

### 4.2 以后做（本文只登记）

| # | 项 | 为什么可以等 |
| --- | --- | --- |
| L1 | 编辑器 UI | R13 明确"当前可不实现" |
| L2 | 热重载（§五） | 需要 T1/T2 先落地才有意义 |
| L3 | 资源导入 / 图片上传 | 独立议题 |
| L4 | 特效编辑器（可视化调参） | 依赖 L1 |
| L5 | 规则的可视化编排（时间轴 / 节点图） | 同上 |

### 4.3 明确不做（安全边界）

| 不做 | 理由 |
| --- | --- |
| 规则里的表达式 / 脚本 / 函数字符串 | 既有安全边界："清单是数据不是代码"。**这条不能为了编辑器好做而松动** |
| 引用外部 URL 的素材 | 宠物包是本地目录，引入网络来源会带来一整套信任问题 |
| 规则间的相互调用 / 循环 | 保持"触发器 → 动作"的单向、有限、可静态分析 |

## 五、热重载（以后做，此处定分层）

编辑器的核心体验是"改完即见"，但**不是所有改动都能廉价热重载**。分三层：

| 层 | 改动内容 | 重载方式 | 状态 | 成本 |
| --- | --- | --- | --- | --- |
| **L1 规则** | `interactions` / `effects` / `emotionMap` / `tapMotions` | **内存替换规则表** | 全保持 | 极低 |
| **L2 素材** | `atlas.png` / `atlas.json` | 重建 `PIXI.Texture` | 保持（需重绑部件） | 中 |
| **L3 结构** | `slots` / `animations` / `canvas` / `anchor` | 重新解析清单 + 重建图层 | **丢失**（需重新施加当前状态） | 高 |

**结论：L1 是编辑器 90% 的操作路径，必须做到零成本热重载**——这正好是 T1/T2 做完后自然得到的能力（规则表是纯数据，换一份即可）。L2/L3 可以先"重载即重建"，状态丢失可接受（编辑形象本来就该从头看）。

**一个必须现在就注意的技术点**：`SpritePetRenderer` 的纹理与图集 JSON 走 `fetchJson`（`file://` 下用 XHR）。热重载时会命中缓存——**实现 L2/L3 时必须带 cache-busting**（查询参数或 Electron 协议层处理），否则"改了没反应"。

## 六、编辑器契约（不实现，只定边界）

未来编辑器需要的能力，现在就明确边界，避免届时运行时被改坏：

```ts
/** 编辑器会话（未来实现，此处只定形） */
interface PetEditorSession {
  /** 打开一个宠物包目录 */
  open(packageDir: string): Promise<void>
  /** 独立的预览渲染实例——不得干扰桌面上的宠物实例 */
  createPreview(canvas: HTMLCanvasElement): Promise<PetRendererProvider>
  /** 手动触发一条触发器（模拟点击/拖拽/agent 事件），用于"实时运行" */
  emit(trigger: InteractionTrigger): void
  /** 热更新规则（L1），立即生效 */
  applyRules(rules: PetInteractionRules): void
  /** 校验当前编辑内容，返回全部错误 */
  validate(): ManifestValidation
  /** 写回磁盘（走 pet-asset 的两段式安装） */
  save(): Promise<void>
}
```

三条边界约束：

1. **预览实例与运行时实例必须隔离**（多实例天然可行——`SpritePetRenderer` 每实例自建 `PIXI.Application`，见 `SpritePetRenderer.ts:173`）
2. **编辑器不得直接改运行时状态**，只能通过 `emit()` 走同一条规则路径——**否则"编辑时看到的"与"桌面上跑的"会不一致**
3. **保存必须走 `pet-asset` 的两段式安装**（`validate` → 临时目录 → `rename`），不能直接写目标目录

## 七、分期与验收

| 期 | 内容 | 验收 |
| --- | --- | --- |
| **本期（预留）** | T1-T5 | 现役 7 个模型**行为零变化**（默认表逐条等价于现有硬编码）；`interactions` / `effects` 校验有单测；改一份清单能改变点击行为（证明路径通了） |
| 未来一期 | L1 + L2 | 改规则立即生效，桌面宠物状态不丢 |
| 未来二期 | 编辑器 UI + 资源导入 | 用户可完成"造一只宠物并装上"的全流程 |

**本期最关键的一条验收**：把 `DEFAULT_INTERACTIONS` 里某条规则改掉（例如把点击 `Wave` 换成别的组），**桌面上点击行为应随之改变**——这证明运行时真的在走数据路径，而不是"表在那摆着、代码还是走老路"。
