# 性能监控与调用耗时统计方案（精简闭环版）

> **For agentic workers:** Implement this plan task-by-task. Each task must complete its focused tests before moving to the next task.

**Goal:** 在不大范围改动现有业务代码的前提下，为 Lumii 增加可落盘、可查询、可展示、可导出的性能观测能力，覆盖启动耗时、重点调用耗时和内存趋势。

**Architecture:** 主进程新增一个轻量 `PerformanceMonitor`，负责有限埋点、内存聚合、JSONL 落盘和健康状态维护。渲染进程通过新增的 `performance` preload API 获取已经聚合的报告，并在现有“设置 > 隐私与数据”中展示，不直接读取日志文件。

**Tech Stack:** Electron 36、Node.js、TypeScript、`performance.now()`、Node `fs.createWriteStream()`、Vitest、React 18。

**Scope:** 本文既是设计方案，也是第一阶段实施计划。第一阶段必须完成“采集 -> 落盘 -> 查询 -> 设置页展示 -> 复制/打开日志”的闭环。

## Global Constraints

- 不修改业务初始化顺序和业务返回值。
- 不包装全部 `ipcMain.handle`；只观测明确列出的重点入口。
- 不记录 API Key、Token、Cookie、Prompt、模型响应、用户消息、文件内容、命令参数和 URL 查询参数。
- 性能日志写入失败、采样失败或队列丢弃不得影响应用启动、IPC 返回和应用退出。
- 不引入 OpenTelemetry、Prometheus 或其他第三方观测依赖。
- 不新增独立后台服务，不上传远程，不要求用户使用命令行才能查看结果。
- 性能日志与现有业务日志分开存储。

---

## 1. 复盘结论

原方案的方向正确，但第一版过重，主要问题如下：

1. 计划包装约 151 个 `ipcMain.handle`，侵入面过大，容易改变 handler 注册、异常透传和返回值行为。
2. 每次 IPC 都写独立事件，高频调用会增加 JSON 序列化、磁盘写入和日志清理成本。
3. 同时加入所有子进程指标、汇总脚本、10 次基线和大量配置项，第一阶段难以快速交付和验证。
4. 只定义了日志文件和未来脚本，没有设置页、查询 API、手动采集和健康状态，存在“能输出但不能使用”的问题。
5. 没有规定启动运行标识，多个启动实例写入同一天文件后不易关联。
6. 没有明确 preload 类型、渲染组件、IPC 返回结构和组件测试，开发者不能直接按文档闭环实现。

本版本的处理原则是：减少接入点、减少事件数量、将报告查询放入主进程、将结果接入现有设置页，并优先完成可使用的最小闭环。

## 4. 闭环架构

```text
启动阶段 / 重点 IPC / 内存采样
                |
                v
       PerformanceMonitor
       | 运行聚合与健康状态
       | 异步 JSONL 落盘
       | 脱敏和容量限制
                |
                +--> ~/.lumii/logs/performance/performance-YYYY-MM-DD.jsonl
                |
                +--> performance:getReport
                +--> performance:capture
                +--> performance:openLogFolder
                              |
                              v
              preload performance namespace
                              |
                              v
           设置 > 隐私与数据 > 性能诊断
           查看 / 刷新 / 手动采集 / 复制 / 打开目录
```

### 4.1 新增文件

```text
apps/windows/src/main/performance/
  performance-types.ts       # 事件、报告、健康状态和 IPC 参数类型
  performance-monitor.ts     # 埋点、聚合、写入、采样、报告查询
  performance-ipc.ts         # 仅注册 performance:* 三个 IPC handler
  performance-monitor.test.ts

apps/windows/src/renderer/pages/SettingsPage/components/
  PerformanceDiagnostics/
    PerformanceDiagnostics.tsx
    PerformanceDiagnostics.module.css
    PerformanceDiagnostics.test.tsx
    index.ts
```

不修改 `FileLogger`。性能日志路径为：

```text
普通安装/开发：%USERPROFILE%\\.lumii\\logs\\performance\\performance-YYYY-MM-DD.jsonl
便携版：      %PORTABLE_EXECUTABLE_DIR%\\logs\\performance\\performance-YYYY-MM-DD.jsonl
```

路径必须通过 `resolveClientStateDir()` 和现有 `PORTABLE_EXECUTABLE_DIR` 规则派生，不能在性能模块中复制一套数据根目录逻辑。

### 4.2 生命周期

1. 模块加载时只创建 monitor 对象，不创建目录、不打开文件流、不启动定时器。
2. `app.whenReady()` 后调用 `performanceMonitor.initialize()`，此时创建性能目录和当天文件。
3. `initialize()` 开始时生成本次启动唯一 `runId`，所有事件携带 `runId`、`appVersion`、`pid` 和 `process="main"`。
4. 启动阶段和重点服务初始化写入少量即时事件。
5. 重点 IPC 正常调用只进入内存聚合；失败和超过慢调用阈值的调用即时写入一条事件。
6. 每 60 秒写出一次 IPC 聚合和内存快照；用户点击“立即采集”时立即写出并返回最新报告。
7. 退出时停止定时器，写入最终内存快照，异步 flush，最多等待 1 秒。

## 5. 采集内容

### 5.1 启动阶段

只记录现有初始化边界：

- `app-ready`
- `create-window`
- `renderer-ready-to-show`
- `directory-config`
- `skill-runtime`
- `skill-watcher`
- `agent-runtime`
- `browser-service`
- `channel-services`
- `startup-complete`

`renderer-ready-to-show` 表示窗口可见，`startup-complete` 表示后台初始化链路完成，二者不能合并。

每个阶段记录一次 `startup.phase`：

```json
{"ts":"2026-08-21T10:00:04.021Z","event":"startup.phase","runId":"run-abc","appVersion":"0.1.1","process":"main","pid":1234,"durationMs":1250.6,"ok":true,"meta":{"phase":"agent-runtime"}}
```

阶段失败时记录 `ok=false` 和稳定的 `errorType`，仍按原有流程抛出或处理异常。

### 5.2 重点 IPC

第一阶段只接入下列高价值入口：

| 类别 | channel | 观测原因 |
| --- | --- | --- |
| Agent Runtime | `agent-runtime:command` | 对话、技能、工具和大部分 Agent 操作的集中入口 |
| 语音 | `voice:command` | 可能触发 ASR/TTS/sidecar，耗时和内存都较高 |
| 录屏 | `screen-record:start`、`screen-record:stop`、`screen-record:narrate` | 涉及桌面采集、文件写入、TTS 和 FFmpeg |
| Provider | `provider:listModels`、`provider:testConnection` | 网络请求和模型探测耗时明显 |

不在第一阶段观测普通窗口、简单配置读取和列表查询 IPC。后续只有在报告证明某类调用有必要时，才增加接入点。

IPC 计时使用 `performance.now()`，不复制参数和返回值：

```ts
measureIpc<T>(
  channel: string,
  handler: (...args: unknown[]) => Promise<T> | T,
): (...args: unknown[]) => Promise<T>
```

事件策略：

- 成功且未超过阈值：只更新内存聚合。
- 成功且超过 `200 ms`：立即写 `ipc.slow`。
- 失败：立即写 `ipc.error`，只记录错误类型，不记录参数和错误正文。
- 每 60 秒按 channel 写 `ipc.aggregate`，包含 `count`、`errorCount`、`slowCount`、`sumMs`、`maxMs` 和有界 p95 样本。

示例：

```json
{"ts":"2026-08-21T10:01:00.000Z","event":"ipc.aggregate","runId":"run-abc","process":"main","pid":1234,"meta":{"channel":"agent-runtime:command","count":18,"errorCount":1,"slowCount":4,"sumMs":6420.5,"maxMs":1250.2,"p95Ms":910.4,"windowMs":60000}}
```

### 5.3 内存

默认每 60 秒采集一次，启动完成后延迟首次采集，手动点击时立即采集。

主进程字段来自 `process.memoryUsage()`：

- `rssBytes`
- `heapUsedBytes`
- `heapTotalBytes`
- `externalBytes`
- `arrayBuffersBytes`

Electron 子进程字段来自 `app.getAppMetrics()`，每个 Renderer/GPU/Utility 进程各写一条 `memory.snapshot`。读取失败时写入 `ok=false`，不影响业务。

```json
{"ts":"2026-08-21T10:01:00.000Z","event":"memory.snapshot","runId":"run-abc","process":"main","pid":1234,"meta":{"scope":"main","rssBytes":312000000,"heapUsedBytes":76000000,"reason":"interval"}}
```

报告只展示最近 7 天的聚合结果，不把全部原始日志加载到渲染进程。

## 6. 日志和报告设计

### 6.1 文件写入

- 使用异步 `createWriteStream`，不使用 `console.log`，避免与 `FileLogger` 互相触发。
- 单条 JSONL 事件限制 16 KB。
- 内存队列上限 200 条，优先保留启动、错误、慢调用和内存事件。
- 队列溢出只记录累计 `droppedEvents`，不能无限补写丢弃日志。
- 默认保留 14 个日期文件，并增加单文件 20 MB 上限；超过上限时停止普通聚合写入，但继续保留错误和健康状态。
- 写入流错误保存到 monitor 健康状态，并通过业务 logger 写一条低频告警，禁止错误日志再次写入性能流。
- 关闭性能监控时不创建性能目录；环境变量 `LUMII_PERF_LOG=0` 仅用于开发和故障排查，不增加应用设置项。

### 6.2 Monitor 健康状态

报告必须包含：

```ts
interface PerformanceHealth {
  enabled: boolean
  writable: boolean
  logPath: string | null
  lastEventAt: string | null
  lastMemorySampleAt: string | null
  droppedEvents: number
  lastWriteError: string | null
}
```

这样用户能区分“没有性能问题”和“监控没有正常写入”。

### 6.3 查询报告

```ts
interface PerformanceReport {
  generatedAt: string
  runId: string | null
  health: PerformanceHealth
  startup: {
    current?: StartupSummary
    recent: StartupSummary[]
  }
  ipc: IpcSummary[]
  memory: MemorySummary
}
```

报告由主进程生成：

- 当前运行数据来自 monitor 内存聚合。
- 应用重启后从最近 7 天性能 JSONL 中读取 `startup.phase`、`ipc.aggregate` 和 `memory.snapshot`。
- 读取范围限制为最近 7 个文件和每文件最多 20 MB。
- 文件损坏或某行 JSON 非法时跳过该行，并在健康状态中记录 `readErrorCount`，不能让设置页整体失败。
- p95 使用固定的有界样本计算，并在报告中标记 `approximate=true`，避免误认为精确统计。

## 7. 应用内使用闭环

### 7.1 主进程 API

新增独立 IPC 注册文件 `apps/windows/src/main/performance/performance-ipc.ts`，只提供三个 handler：

```ts
performance:getReport(): Promise<PerformanceReport>
performance:capture(): Promise<PerformanceReport>
performance:openLogFolder(): Promise<{ success: boolean; path?: string; error?: string }>
```

约束：

- `performance:getReport` 不触发昂贵采样，只返回当前聚合报告。
- `performance:capture` 触发一次主进程和 Electron 子进程快照后返回报告。
- `performance:openLogFolder` 只打开 monitor 自己计算出的固定目录，禁止接受任意路径参数。
- 报告接口返回结构化数据，不让 Renderer 解析 JSONL。

### 7.2 Preload API

在 `apps/windows/src/preload/index.ts` 的 `ElectronAPI` 和实现中新增：

```ts
performance: {
  getReport: () => Promise<PerformanceReport>
  capture: () => Promise<PerformanceReport>
  openLogFolder: () => Promise<{ success: boolean; path?: string; error?: string }>
}
```

类型从 `performance-types.ts` 引用，不能在 preload 和 renderer 各复制一份匿名类型。

### 7.3 设置页

在现有 `SettingsPage.tsx` 的“隐私与数据”区域加入 `PerformanceDiagnostics`，不新增分类、不引入图表库。

组件必须提供：

- 监控状态：启用/禁用、可写/不可写、日志路径、丢弃事件数。
- 最近一次启动：窗口可见耗时、后台完成耗时、各阶段耗时。
- 重点 IPC：调用次数、失败次数、慢调用次数、p95、最大耗时。
- 内存：主进程当前 RSS、启动到当前增量、最近样本时间；子进程按类型汇总。
- “刷新报告”按钮：调用 `getReport`。
- “立即采集”按钮：调用 `capture`，显示采集时间和结果。
- “复制脱敏报告”按钮：将结构化报告格式化后写入剪贴板。
- “打开日志目录”按钮：调用 `openLogFolder`，失败通过现有 Toast 展示。
- 加载、空数据、监控关闭、日志不可写、解析失败和 IPC 失败状态。

组件不展示原始消息、参数、文件路径、错误正文和 Token。报告为空时必须显示明确的“暂无性能数据”，不能显示空白区域。

## 10. 验收标准

### 功能闭环

- [ ] 性能事件能够独立落盘到性能日志目录。
- [ ] 设置页能够读取并展示性能报告，不要求用户手工解析 JSONL。
- [ ] 支持手动采集、复制脱敏报告和打开性能日志目录。
- [ ] 重启后能够读取最近 7 天的历史聚合结果。
- [ ] 能看到监控自身的启用状态、可写状态、最近采样时间和丢弃事件数量。

### 数据正确性

- [ ] 窗口可见耗时与后台初始化完成耗时分开记录。
- [ ] 重点 IPC 能看到调用次数、失败次数、慢调用次数、p95 和最大耗时。
- [ ] 内存报告包含主进程 RSS 和 Electron 子进程汇总。
- [ ] 每次启动有独立 `runId`，不同启动不会在报告中错误合并。

### 低侵入和安全

- [ ] 未包装全量 IPC，没有修改 `ipcMain.handle` 全局行为。
- [ ] 业务 handler 的参数、返回值和异常行为保持不变。
- [ ] 性能写入失败不阻塞启动、IPC 和退出。
- [ ] 日志和报告不包含 Token、Key、Cookie、Prompt、模型响应、消息正文、文件内容、命令参数和 URL 查询参数。
- [ ] 性能监控关闭时不创建性能目录。

### 性能开销

- [ ] 性能监控启用后，冷启动总耗时增量目标不超过 2%。
- [ ] 性能监控启用后，空闲 RSS 增量目标不超过 10 MB。
- [ ] 普通重点 IPC 不逐条写盘，只进行内存聚合。
- [ ] 定时采样不触发 GC、heap dump 或文件扫描。

## 11. 后续扩展边界

只有第一阶段报告证明存在明确缺口时，才考虑以下扩展：

- 增加其他 IPC channel 的显式包装。
- 增加独立 JSONL 汇总脚本，用于 CI 对比。
- 增加更细的 Renderer React 渲染耗时。
- 增加远程上报或在线仪表板。
- 增加 CPU profile、trace 或 heap dump。

这些能力不属于第一阶段，不能提前引入额外依赖和侵入性。
