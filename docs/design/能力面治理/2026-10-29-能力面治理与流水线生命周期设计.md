## 0. 结论摘要

| 项 | 结论 |
|------|------|
| 两个问题其实是同一个 | 「流水线怎么被创建/进化」和「能力越积越多怎么管」，本质是**能力面（capability surface）没有统一模型**：没有统一描述符、没有统一度量、没有分层暴露 |
| 最关键的发现 | 仓库里**已经设计过两轮能力治理，两轮都断线**：`usageCount` 从未被填充、`autoActivationScope` 算出来了但唯一消费者被 flag 关着、`skill_usage_records` 表 0 行（进化插件停用）。再给流水线加第三套而不修前两套，是把同一个错误做第三遍 |
| Q1 路线 | 流水线的生命周期与技能**共用同一套动词**（search / invoke-or-run / draft），差异只在状态机与验收：流水线有 `expect`，所以它的"进化"是**可评测**的，而技能不是 |
| Q2 路线 | 三种能力的上下文成本差 100 倍（实测：skills 86 tokens vs tools 10–20K）。按**是否常驻上下文**分三层，把"几乎不用但很贵"的沉到检索层 |
| 排序与打分 | **初稿的六项加权公式被自己的回放实测推翻**。3174 条真实消息做时间切分：纯 LRU **93.5%** @ N=20，六项公式 **90.6%**（全局口径 92.5% vs 86.1%）。频率项、共现项、会话项**全部是负增益或冗余**，半衰期从 0.25 天到 180 天结果完全一样。重写为三行规则：**按 (agent, channel) 分组 + 最近使用降序 + 常驻 20 个**（§5.6） |
| 数据量级 | 工具侧够做 LRU（33 626 次调用）；**技能侧撑不起任何排序**（51 个技能最高只用过 10 次，差三个数量级，§2.1b）。所以技能列表保持现状，补 `usageCount` 只为"说真话" |
| 可观察性 | **四个数据空白**（§5.7）：① 从未记录"每轮暴露了哪些工具"；② 用量表没有 channel 维度；③ 只有总 token 分摊不到单工具；④ 技能只有次数没有成败。**P0 必须补第 ① 条**，否则裁剪是否伤模型永远无法证伪 |
| 最大风险 | ① 做成"能力中心"大页面，字段越加越多最后没人维护；② 回放的 93.5% 是**上界**——裁剪后模型行为会变（§5.6.6）。缓解：描述符只四个字段；折叠工具必须一次检索可取回，连续两次未命中自动回落全量 |
| 交付形态 | **回放脚本已落地** `verify/capability-ranking/replay.mjs`（零风险）→ 补 `tool_exposure_log`（P0）→ 修断线 → 统一度量 → 按 (agent,channel) 的 LRU + 裁剪（P2，需 A/B） |

## 1. 背景：两个问题其实是一个

用户提了两个问题：

1. **流水线和 skill 一样是可创建/修改/复用的技能资产，它如何被 Agent 规范地创建、使用、更新（进化）、管理？**
2. **随着使用增加，积累了越来越多的流水线、技能、MCP、渠道，如何恰当管理、串联、暴露给 Agent？**

看起来是"资产生命周期"和"能力膨胀"两件事。实际上它们是同一件事的两端：

- 第 1 个问题问的是**新能力怎么进入系统**；
- 第 2 个问题问的是**进入系统的能力怎么被看见、被选中、被淘汰**。

两者共用同一套基础设施：一个能力的**描述、成本、用量、健康度**。缺了这套，新能力进不来（不知道往哪放），旧能力出不去（不知道谁在用）。

而本仓库当前状态是：**这套基础设施被设计过两次，两次都没接上线**。

## 2. 代码事实核查

以下每条都已在本仓库核实（含本机运行时库实测）。

### 2.1 度量：三条断线

**(a) `usageCount` 从未被填充 —— 提示词按用量排序是空转**

`skills-section.ts:33` 明确写着"按 usageCount 降序排序，未提供时视为 0"：

```ts
const sorted = [...skills].sort((a, b) => (b.usageCount ?? 0) - (a.usageCount ?? 0))
```

但唯一的生产者 `apps/windows/src/main/index.ts:429-501` 的 `getSkills()` 返回的 `results` 数组**根本没有 `usageCount` 字段**（类型声明里也没有）。索引里明明有 `executionCount`（`skill-store.ts:126`，且 `recordExecution()` 在 `skill-tools.ts:218` 被真实调用），却没有映射进 `SkillInfo`。

**后果**：`sorted` 里所有值都是 `0`，`sort` 是稳定排序 → **实际顺序 = 目录扫描顺序**。提示词对模型宣称"ordered by usage"，而模型拿到的是字母序。这是一句代码里的谎话。

**(b) `autoActivationScope` 算出来了，没人读**

`skill-store.ts:527-590` 的 `updateAutoScopeBatch()` 实现得很完整：0.95 衰减、阈值 4.0/0.5、10 轮观察保护期、自动在 `always/contextual/on_demand` 之间迁移，还写日志。它由 `skill-hit-rate-hook.ts` 每轮 flush 驱动（`bridge-instance-factory.ts:504` 已接线），结果经 `getAutoScopeMap()` → `getSkills()` → `SkillInfo.activationScope` 一路传到了提示词装配门口。

**然后被一个 flag 关住了**：

```ts
// feature-flags.ts:62
ENABLE_SKILL_ACTIVATION: false,
```

唯一的消费者是 `bridge-prompt-dispatcher.ts:351` 的 `resolveSkillActivations()`，在 flag 之内。**默认关闭 = 整套自动分层在生产里从未生效。**

**(c) `skill_usage_records` 表 0 行**

`autonomous/skill-evolution.ts` 写这张表，但驱动它的插件 `plugins/builtin/skill-evolution/index.ts:81` 是 `disabled: true`。本机实测：

```
skill_usage_records  0 行
tool_usage_daily     1325 行
tool_audit_log       46165 行
```

工具侧在认真记账，技能侧一个字都没记。

> **这三条合起来的结论**：仓库不是"不知道怎么做能力治理"，而是**做了两次、都没通电**。所以本设计的第一条原则是：**先修线，再加新东西**。

### 2.1b 技能侧的数据量级：撑不起任何排序

§2.1(a) 说 `usageCount` 没被填。但**即使填上，量级也不够**。本机 `~/.lumii/workspace/skills/index.json` 实测：

```
51 个技能，只有 15 个有执行记录
执行次数 top15：10, 5, 4, 3, 3, 3, 2, 2, 2, 1, 1, 1, 1, 1, 1
weightedScore > 0 的只有 7 个
```

**最高 10 次、多数 1 次。** 在这个量级上按使用次数排序，排的是噪声——
1 次与 2 次的差别是随机事件，不是偏好。

对照工具侧：179 个工具、33 626 次调用、单工具最高 7056 次。**差三个数量级。**

**结论：技能侧现在不具备做数据驱动排序的条件。**
技能列表保持现状（按目录顺序 + `skill_search` 按需检索）是正确的；
补 `usageCount` 仍要做（让提示词说真话），但**不要指望它带来排序收益**。

同理，`capability_tests` 有 14 万行看起来很多，实测**全部由 `pet-task-store` 在
2026-09-20~24 期间写入**（单日最高 3.9 万行），是宠物任务执行的记录，与能力面无关。
**行数多 ≠ 信息量大**——这是本仓库第三次在这类"看起来有数据"的地方差点判断错。

### 2.2 暴露：三类能力的上下文成本差 100 倍

本机日志实测（`~/.lumii/logs/app/mtbot-2026-10-29.log`，`contextUsage` 事件）：

```
breakdown=systemPrompt:1060, tools:9688,  mcp:1050,  conversation:14220
breakdown=systemPrompt:1202, skills:86,   mcp:973,   conversation:15551
breakdown=systemPrompt:3162, tools:20535, mcp:2240,  conversation:…
```

| 能力类别 | 每轮上下文成本 | 暴露策略 | 机制 |
|---|---|---|---|
| 工具（内建） | **9–20K tokens** | 全量 schema 常驻 | 每轮 `getEnabledTools()` 全集进请求 |
| MCP 工具 | 1–2K（本机 4 个 server）；代码注释记录过单 server 占 **150K/200K** 的情况 | 全量 schema 常驻 | 与工具同一张 `ToolRegistry` |
| 技能 | **86 tokens**（44 个内置 + 19 个本机安装） | 只列名字 + 120 字描述，正文按需 `skill_invoke` | `skills-section.ts` 的工具化模式 |

**技能之所以只花 86 tokens，是因为它被"工具化"过**——这是本仓库已有的一次成功改造（`skill-tools.ts:1-10` 注释：~1500 → ~40 tokens）。**工具从没被这样改造**，所以它成了最大的固定开销。

这个不对称是 Q2 的全部答案所在。

## 3. 能力模型：四种东西，两个轴

### 3.1 分类

| 类型 | 是什么 | 例子 | 谁执行 |
|---|---|---|---|
| **工具** tool | 一个动作，有 schema | `file_read` / `bash` / `mcp__wechat-local__read_history` | 代码 |
| **技能** skill | 一段方法（散文），可带单入口脚本 | `screen-tutorial-pipeline` | 模型读 → 自己组织工具调用 |
| **流水线** pipeline | 一份声明式步骤表 | `wechat-reply-demo` | 代码逐条执行 |
| **渠道** channel | 一个出口（收/发端点） | `weixin` / `wecom` / `feishu` | 插件 + Hub |

前三种是"能做什么"，第四种是"往哪送"。**渠道不该和能力资产混在一个列表里**——它不是可调用的动作，是投递终点。本设计只治理前三种，渠道沿用现有 `channel_list` / `channel_send`。

### 3.2 两个正交轴

**轴一：是否常驻上下文**（决定成本）

- **常驻（T0）**：完整 schema/正文每轮都在
- **索引（T1）**：只有名字 + 一句话，可检索
- **按需（T2）**：不在提示词里，只有显式检索才出现

**轴二：谁决定用不用**（决定可靠性）

- **模型自决**：技能、内建工具 —— 模型判断"这事该用什么"
- **代码强制**：流水线 —— 步骤表写死了，模型不能改路

交叉后：

```
                  模型自决          代码强制
T0 常驻       内建工具(现状)         —
T1 索引       技能(现状)         流水线(设计目标)
T2 按需       MCP(应改造)            —
```

**这张表就是 Q2 的答案**：按成本分层，按可靠性分工。技能已经在 T1 且工作良好；流水线应当**直接生在 T1**（不重蹈工具的老路）；MCP 是唯一还没被治理的（当前实际是 T0，最贵且最不可控）。

### 3.3 统一描述符（只四个字段）

不建大模型，只统一四个字段，其余留在各领域模型里：

```ts
export interface CapabilityDescriptor {
  kind: 'tool' | 'skill' | 'pipeline'
  id: string
  /** 一句话：什么时候该用它。检索与提示词都用这一条 */
  whenToUse: string
  /** 每轮常驻的上下文成本（tokens）。技能为索引成本，工具为完整 schema 成本 */
  residentTokens: number
}
```

另附**一份共享的度量表**（见 §4.2），不塞进描述符。

为什么只四个：多了之后每类能力都要填自己填不了的字段，最后退化成 `Record<string, unknown>`。「能力中心」类设计的通病是字段越加越多、没人填、最后没人信。

## 4. Q1：流水线的生命周期

### 4.1 状态机

```
draft ──rehearsal 全绿──> rehearsed ──首次 record 成功──> active
  ↑                          │                              │
  │                          │             连续 N 次失败     │
  └────── 修改 spec ─────────┴─────────────> degraded <──────┘
                                                │
                                         人工确认下线
                                                ↓
                                           deprecated
```

**状态由数据判定，不由人填**：

| 转移 | 判据 | 谁判 |
|---|---|---|
| draft → rehearsed | 最近一次 rehearsal 全绿 | 代码 |
| rehearsed → active | 有一次 record 成功且产物通过 `inspect` | 代码 |
| active → degraded | 最近 5 次运行失败 ≥ 3 | 代码（读 journal） |
| degraded → draft | 用户在页面上确认要改 | 人 |
| 任意 → deprecated | 用户显式操作 | 人 |

状态落在 `{workspace}/pipelines/<id>/meta.json`，**不进 spec**（spec 是给执行器吃的，状态是给人和调度器看的）。

### 4.2 创建：三条路，按可靠性排序

**(1) 从成功轨迹蒸馏（最佳）**

Agent 刚把一件事做对了 → 那条轨迹就是 spec 的雏形。

```
Agent 做完任务
  → pipeline_draft({ fromSessionKey, fromMessageId, toMessageId })
  → 读出这段区间的工具调用序列，生成 spec 草稿（LLM 一次，把探索步骤剔掉、补 narration）
  → 写进 {workspace}/pipelines/<新 id>/spec.json（状态 draft）
  → 立刻跑 rehearsal
  → 绿了才提示用户"要不要固化这条？"
```

**为什么这是最佳**：spec 的内容全部来自**已被证明能跑通**的真实调用，参数、选择器都是实测值，不是模型编的。这正是 `skill-creator` 里 "Capture Intent: The current conversation might already contain a workflow the user wants to capture" 的流水线版本。

**新增成本**：一个工具 `pipeline_draft`，读会话历史 + 一次 LLM。无新表。

**(2) 手写 spec（次佳）**

模板 + `file_write` + `pipeline_validate` + rehearsal。适合"我知道要做什么但没跑过"。

**(3) 从技能导入（最差）**

技能里若已有一份 `TutorialNavSpec` 或等价步骤表，机械转写（设计附录 A 已给映射表）。一次性动作，不做自动转换器。

### 4.3 使用：与技能同一套动词

这是"规范"的核心——**模型不该学两套发现方式**：

| 意图 | 技能 | 流水线 |
|---|---|---|
| 有什么 | `skill_search(query?)` | `pipeline_search(query?)` |
| 看正文 / 看步骤 | `skill_invoke(name)` | `pipeline_inspect(id)` |
| 执行 | `execute_skill(id, params)` | `pipeline_run(id, {mode})` |
| 固化 | `skill-creator` 技能 | `pipeline_draft` + rehearsal |

四个动词一一对应。**不发明第五个概念**。

> 反向不成立：技能不能"执行"流水线（技能是散文，执行由模型决定）；流水线也不能"调用"技能（技能不是函数）。**两者只在 `pipeline_draft` 这个入口上汇合**——从一段执行轨迹生成 spec。

### 4.4 进化：journal 是评测集

这是流水线相对技能的**结构性优势**，也是本设计最值得记录的一条：

| | 技能 | 流水线 |
|---|---|---|
| 有没有"正确答案" | 没有。只能看人满不满意 | **有**。每步 `expect` 是机器可判的 |
| 失败能不能定位 | 不能。只知道"这轮不行" | **能**。`failedAt: {i, id, expected, observed}` |
| 能不能自动改 | 不能。只能靠 LLM 重写散文，改好改坏都靠抽样 | **能**。改哪一步是确定的 |

所以流水线的进化是 **evaluator-optimizer，但评委是代码不是 LLM**：

```
一次失败 run
  → 读 journal：第 5 步 expected={hub.category:"modelConfig"} observed={hub.category:"general"}
  → 生成补丁：只改第 5 步的 spec（选择器/参数/断言之一）
  → 立即 rehearsal（这就是评测）
  → 全绿 → 写回 spec，状态回 rehearsed → 等用户确认
  → 仍红 → 丢弃补丁，报告"这步需要人看"
```

**三条硬约束**：

1. **只改失败的那一步**。整份重写 = 放弃已积累的正确性。
2. **必须过 rehearsal 才写回**。没过的补丁连草稿都不留。
3. **不自动改断言**。UI 真的变了的时候，正确做法是让人决定"是 spec 错了还是产品坏了"——自动放宽断言会把回归测成通过。

> 这条也解释了为什么技能进化在本仓库一直没成：`skill-evolution.ts` 的判据是 `successRate` / `avgSatisfaction` / `avgExecutionTime`——**三个都是弱信号**，且 `skill_usage_records` 根本是空的。流水线的判据是 `expect` 的布尔结果，**强信号**。

### 4.5 管理：Agent 侧与用户侧分开

**Agent 侧**只有四个动词（§4.3），不提供"删除""改名""设状态"——那些是人的决定。

**用户侧**一个页面（原型已出）：
- 列表：名称 / 步数 / 状态 / 上次结果 / 成功率
- 详情：步骤表 / 断言 / 历史 run / 产物
- 动作：跑 / 彩排 / 续跑 / 打开 spec / 停用

**不做**：拖拽编排器、可视化时间轴、参数表单生成器。spec 是给人改的文本，有 GUI 就要维护两套模型。

## 5. Q2：能力面治理

### 5.1 分层暴露

目标不是"把所有能力塞进提示词"，而是**让模型知道有什么、按需取细节**。

| 层 | 进提示词的内容 | 谁在这里 | 判定依据 |
|---|---|---|---|
| **T0 常驻** | 完整工具 schema | 高频工具（bash / file_read / file_write / grep / memory_* / task_complete） | 近 30 天调用次数 |
| **T1 索引** | 名字 + 一句话 + 何时用 | 全部技能、全部流水线、中频工具 | 默认 |
| **T2 检索** | 一行都不到，仅 `*_search` 可达 | 低频工具、未启用的 MCP server | 近 90 天 0 次 或 用户显式降级 |

**本机实测支撑这三分**（`tool_usage_stats` 聚合）：

```
179 个工具被用过，其中 114 个在近 30 天用过
top10: bash:7056, file_read:4106, file_write:2699, memory_manage:2153, grep:1762,
       task_complete:1629, web_fetch:1421, file_edit:1379, memory_search:1006, glob:949
尾部:  大量只有 1 次的 MCP 工具（mcp__comfyui-remote__queue:1 …）
MCP:   79 个工具用过，合计 1460 次 —— 占全部 179 个工具的 44%，但只贡献 4.7% 的调用量
```

**44% 的能力数量贡献 4.7% 的调用量**，而它们全量常驻上下文。这是分层的直接理由。

### 5.2 统一度量（先修线）

把三类能力的用量写进**一张表**，键是 `(agent_id, kind, id)`：

```sql
-- 只描述形状，不写死迁移
capability_usage (
  agent_id TEXT, kind TEXT, id TEXT,
  count INTEGER, error_count INTEGER,
  last_used_at INTEGER, day TEXT,
  PRIMARY KEY (agent_id, kind, id, day)
)
```

**为什么不新建**：`tool_usage_stats` / `tool_usage_daily` 已经在生产里跑（1325 行日数据），形状与需求一致。**P0 的做法是给它们加 `kind` 列**（默认 `'tool'`），而不是并排再建第三张表。技能与流水线的记录用同一个写入器。

同时**填上那个空字段**：`getSkills()` 把 `executionCount` 映射进 `SkillInfo.usageCount`。这是一行改动，让提示词里"按用量排序"从谎话变成事实。

### 5.3 分层暴露的实施顺序（按风险排）

**先做零风险的，后动提示词。**

| 步 | 做什么 | 风险 | 收益 |
|---|---|---|---|
| 1 | 填 `usageCount` | 无（只是排序变了） | 提示词说真话；高频技能浮到前面 |
| 2 | 打开 `ENABLE_SKILL_ACTIVATION`（先灰度一个 Agent） | 低 | 自动分层生效；`on_demand` 技能不再占位 |
| 3 | 统一度量表加 `kind` 列 | 低（加列） | 三类能力同口径 |
| 4 | 能力页：一张表看全部（工具/技能/流水线），带 token 成本与近 30 天用量 | 无 | 用户能回答"谁在吃我的上下文" |
| 5 | 工具沉底：给 MCP 工具加 `tool_search` → 命中后再把 schema 加进下一轮请求 | **高**（动提示词装配 + 每轮工具集可变） | 这是唯一能真正压掉 9–20K 固定成本的办法 |

第 5 步单独说明，因为它最容易做成灾难：

- **只对 MCP 工具做**，内建工具不动（MCP 是外部加的，数量和体积都不可控；内建是可控的）
- **命中即加载**：`tool_search("微信 读历史")` 返回 `mcp__wechat-local__read_history`，下一轮请求带上它的 schema，此后**本轮内常驻**
- **降级路径**：`tool_search` 不可用时（老宿主 / 测试）回落到全量常驻
- **不做**：让模型"记住"工具名而 schema 不在请求里——它没法调用一个 schema 不存在于请求中的工具

> 这一步是"能力膨胀"的真正解法，也是唯一需要动 `assembleTools` 的一步。放到 P2 单独评审。

### 5.4 串联：谁能调谁

"串联"这个问题，答案是一张**调用关系图**，不是一个新的编排层：

```
Agent（模型）
  ├─ 直接调 → 工具（原子）
  ├─ 读 → 技能（散文）→ 模型据此调工具
  └─ 调 → pipeline_run → 执行器 → 工具（原子）
                              └─ 渠道（作为工具，如 send_text）
```

**规则**：

1. **只有工具是原子的**。任何组合最终都落到一次工具调用。
2. **流水线组合工具**，不组合技能，不嵌套流水线（v1）。要复用就抽成一条 spec 再复制步骤——嵌套会让 journal 变平，指标失去意义。
3. **技能可以"点名"流水线**（散文里写"这个任务用 pipeline:X"），但不构成硬依赖——技能运行时并不会去检查 X 是否存在。
4. **渠道是工具，不是能力**。`channel_send` / `send_text` 已经在工具表里，不需要单独的编排机制。
5. **Agent 之间用 `spawn_agent`**，与能力面正交。

**负面清单**（明确不做）：
- 不做能力间的 DAG 编排器（那是流水线的事，且流水线只做线性）
- 不做"技能调技能"（`sub-skills/` 目录是文档组织方式，不是调用关系）
- 不做跨 Agent 的能力继承（白名单已经是显式的）

### 5.5 组织层面的代价：一处改动要改几处

这是"从根本上解决"必须面对的账。新增一个能力类型，当前要改：

| 位置 | 改什么 |
|---|---|
| `ToolRegistry` 或 `skill-store` 或 `pipeline store` | 存储 |
| `*_search` / `*_invoke` 工具 | 发现 |
| `prompt/sections/*.ts` | 提示词呈现 |
| `context-usage-breakdown.ts` | 成本统计 |
| `useToolSearch` / 各自页面 | UI |
| 本设计的 `capability_usage` | 度量 |

**本设计只能压缩到"1 个描述符 + 1 张度量表"**，不能压成 0。任何声称"零改动接入新能力类型"的架构，最后都会在某个地方长出一个 `switch (kind)`。

所以诚实的目标是：**让这个 `switch` 只有一处，且被守卫测试盯着**。

### 5.6 排序与打分：什么进常驻、什么折叠

> **本节经过一次自我推翻。** 初稿给了一个六项加权公式（频率 + 近期 + 会话 + 共现 + 相关性 − 成本），
> 并用"top20 覆盖 89.5% 调用量"支撑它。**那个数字是事后统计，不是预测能力。**
> 用 3174 条真实历史消息做时间切分回放后，**最简单的 LRU 打败了那个公式**，
> 其中三项（频率、共现、会话）是负增益。下面是实测结果与据此重写的设计。

#### 5.6.1 回放实验：怎么测的

数据：本机 `messages` 表里 3174 条含工具调用的 assistant 消息（2026-08-28 → 10-29），
按 timestamp 升序，每次只允许用**该时刻之前**的信息排序（严格时间切分，无泄漏）。

指标：`Recall` = 该条消息实际调用的工具中，落在"常驻前 N"里的比例（部分命中按比例计）。

单条消息实际用到的不同工具数：中位 3、p90 7、max 20；**21.4% 的消息只用 1 个工具**。
这条决定了 Recall 不可能到 100%——工具数本身就在浮动。

#### 5.6.2 实测结果：简单胜过复杂

两种作用域都跑了（脚本：`node verify/capability-ranking/replay.mjs [--global|--by-agent]`）：

**按 (agent, channel) 分组**（推荐口径）：

| 策略 | N=10 | N=20 | N=30 |
|---|---|---|---|
| 全量常驻（现状） | 100% | 100% | 100% |
| **纯近期（LRU，无衰减）** | **86.5%** | **93.5%** | **95.7%** |
| 纯累计次数 | 77.9% | 89.0% | 93.9% |
| 30 天次数（对数） | 78.3% | 89.2% | 93.9% |
| 频率 + 近期 | 79.0% | 90.0% | 94.6% |
| **初稿的六项公式** | 79.8% | **90.6%** | 94.9% |

**全局作用域**（对照）：

| 策略 | N=10 | N=20 | N=30 |
|---|---|---|---|
| **纯近期（LRU）** | **83.1%** | **92.5%** | **95.2%** |
| 初稿的六项公式 | 69.0% | 86.1% | 91.6% |

**四条结论**：

1. **LRU 在两种口径下都赢。** 分组口径 93.5% vs 90.6%（+2.9pp）；全局口径 92.5% vs 86.1%（+6.4pp）。
   每个加进去的"聪明"项都在拖后腿。
2. **频率项是负增益。** 原因：高频工具（`bash` 7056 次）在 30 天窗口里恒为最高分，
   把真正"这轮要用"的工具挤掉了。累计次数更糟。
3. **会话粘性项与共现项是冗余/有害的。** 纯近期 + 会话项与纯近期**逐位相同**（"本会话用过"
   在时间上必然就是"最近用过"）；共现项 93.5% → 91.4% → 91.0%（权重越重越差），
   因为它把"历史上常配对但这次不需要"的工具顶上来。
4. **半衰期无信息量。** 0.25 / 1 / 3 / 7 / 14 / 30 / 60 / 180 天，**全部 93.5%**（全局口径全部 92.5%）。
   说明"谁最近被用过"这个**序**才是全部信息。这直接否掉了初稿里"半衰期 7 天"——
   **没有信息量的参数，不配拥有默认值**。

#### 5.6.3 但 LRU 有两个真问题，必须补

**(a) 按 agent 分组是决定性的，不是可选项**

同一份数据，按会话来源分组各自排序，对比"用全局热度排"：

| 分组 | 事件数 | 组内 LRU N=20 | 用全局热度 N=20 |
|---|---|---|---|
| cron | 1431 | **96.8%** | 73.7% |
| evolution | 210 | **97.4%** | **32.0%** |
| pcwechat | 459 | **94.7%** | 57.0% |
| local | 878 | 89.0% | 68.8% |
| feishu | 126 | 85.2% | 78.9% |
| weixin | 70 | **78.6%** | 68.7% |

`evolution` 那行是最刺眼的：**全局热度让它的 Recall 掉到 32%**——自进化 Agent 用的工具
（`file_read` / `grep` / `memory_*`）和"高频工具"（`bash` / `task_complete`）几乎不重叠，
拿全局榜去排它就是灾难。

工具集本身也不一样：只在 cron 出现的有 `dashboard_feed_write` / `mcp__mcp-trends-hub__*` /
`file_manage`；只在人类会话出现的有 `browser_*` / `image_generate` / `app_act` / `speech_generate`。

**结论：排序的作用域必须是「Agent 定义 × 渠道」，不是全局。**
这也解释了为什么 `tool_usage_stats` 在 V44 加 `agent_id` 维度是对的——那个方向是对的，
只是没人用它排序。

**(b) 冷启动几乎不是问题，但"偶发工具"是**

"某 agent 首次使用某工具"只占 **3.3%** 的调用——初稿里的"探索配额"为此服务，
实际收益很小，可以从 P0 降级为可选。

真正的长尾在别处：179 个工具里，**57 个只被用过 1–3 次**（其中 38 个是 MCP）。
这些不值得占常驻位，但也不能消失——它们是 `tool_search` 存在的理由。

#### 5.6.4 重写后的设计：三行规则

```
1. 作用域：按 (agentDefinitionId, channel) 分组，各自维护一份 LRU
2. 排序：  最近使用时间降序。不衰减、不加权、不看次数
3. 名额：  常驻 N=20；其余全部折叠进 *_search，一次检索即可恢复
```

**为什么 N=20**（分组口径的 N 曲线，`--curve` 可复跑）：
N=10 → 86.5%，N=15 → 91.5%，**N=20 → 93.5%**，N=25 → 94.8%，N=30 → 95.7%。

从 20 到 30 多花 10 个名额（+50% 成本）只买到 +2.2pp；从 10 到 20 同样 10 个名额买到 +7.0pp。
**边际收益在 20 附近明显变平**。这是**策略选择**，不是数据结论——数据只给曲线。

**为什么不需要黑名单**：一个工具如果 30 天没被用过，它自然沉出前 20。
不需要"降权""惩罚""健康度"——LRU 已经把这件事做完了。

#### 5.6.5 成本：常驻 20 个能省多少

本机日志实测（256K 窗口会话）：

```
tools: 9476 → 14483 → 14604 → 13393 → 13769 → 20535   （中位约 13.5K）
mcp:   1027 →  1570 →  1583 →  1451 →  1492 →  2240   （中位约 1.5K）
```

工具定义占固定开销的 85%+。常驻 20 个 ≈ 当前的 40%，**每轮省约 8K tokens**。
按 p50 上下文 17.5%（约 45K）算，等于**再省 18% 的上下文**——这是实打实的收益，
也是这件事唯一值得做的理由（Recall 从 100% 掉到 93.5% 是代价）。

> **成本项的最终位置**：初稿把 token 成本放进打分公式（`− w_cost · costNorm`）。
> 实测表明**不该进公式**——因为排序只需决定"谁在前 20"，而成本是**名额问题不是排序问题**。
> 正确做法：先按 LRU 排，再按名额截断；要控成本就调 N，别去污染排序。

#### 5.6.6 一个必须诚实标注的局限

回放用的是**当前全量常驻下产生的真实调用**。一旦开始裁剪，模型看到的面变了，
它可能改用别的方式（比如从 `file_read` 换成 `bash cat`）。所以：

- **93.5% 是上界**，真实上线后会更低。
- 这也是为什么 §5.3 把"工具沉底"列为**高风险、需单独评审**的一步。
- 缓解：折叠的工具必须**一次检索就能拿回**（`tool_search` 命中即注入下一轮），
  并且**连续两次没命中**就自动回落到全量（fail-open）。

#### 5.6.7 落地顺序

| 步 | 内容 | 风险 | 产出 |
|---|---|---|---|
| 0 | **回放脚本固化为 `verify/` 工具**（本节的数字来自一次性脚本，必须可复跑） | 无 | 任何排序策略的评测基线 |
| 1 | 按 `(agent, channel)` 记录 LRU（新表或现有表加列） | 无 | 数据基础 |
| 2 | 能力页显示"当前 LRU 前 20 / 总计 N"，人能看懂 | 无 | 可观测 |
| 3 | 先只对**一个低风险 Agent**（如 `chronicler`）启用裁剪 | 中 | A/B 对照 |
| 4 | 全量启用 + `tool_search` 兜底 | 高 | 省 8K/轮 |

### 5.7 可观察性：这次实测暴露的四个空白

§5.6 的回放是我写了三个一次性脚本、反复试错才跑通的。过程中**四次卡在"数据没有"**，
每一次都要绕路或放弃。这些缺口不是"统计不够漂亮"，而是**直接导致优化做不了**。

| # | 想回答的问题 | 现状 | 后果 |
|---|---|---|---|
| 1 | **这个工具被展示了多少次、用了多少次** | 只有"被调用"（`tool_audit_log` / `tool_usage_stats`），**没有任何"本轮暴露了哪些工具"的记录** | 无法区分"没用"和"没机会用"。裁剪后若 Recall 掉，也查不出是排错了还是模型换了做法（§5.6.6 那条局限正是它导致的） |
| 2 | **这次调用发生在哪个渠道** | 用量表只有 `agent_id`；渠道信息只在 `messages.conversation_id` 的前缀里（`cron:` / `feishu:` / `pcwechat:`） | §5.6.3 那个"按 agent×渠道分组"的决定性结论，是靠**人肉解析 conversation_id 前缀**才得到的。生产代码读不到这个维度 |
| 3 | **工具定义本身占多少 token** | 只有**聚合值**（`tools:9476` → `14483` → `20535`），日志里没有"哪个工具占多少" | 无法定位"谁该被裁"。初稿的成本项因此只能拍一个 `residentTokens` 常量，而实测表明它根本不该进公式（§5.6.5） |
| 4 | **技能/流水线的执行效果** | 技能有 `executionCount`（51 个技能只有 15 个有记录、最高 10 次），但**没有成功/失败**；`skill_usage_records` 0 行 | 技能排序只能用次数。而 10 次 vs 1 次的差异没有统计意义——技能侧目前**不具备做数据驱动决策的量级** |

**这四条合起来的判断**：工具侧的数据**够做 LRU**（够用），但**不够做任何更复杂的优化**；
技能侧的数据**连 LRU 都撑不起来**。所以：

> **裁掉复杂算法不是因为懒，是因为数据不支持。** 任何需要"权重""衰减""共现"的方案，
> 都需要上面四个缺口先被补上，否则就是在给噪声配参数。

#### 5.7.1 要补的记录（按性价比排序）

| 优先级 | 记录什么 | 落点 | 为什么是它 |
|---|---|---|---|
| **P0** | **每轮暴露的工具集**（`turn_id`, `agent`, `channel`, `tool_names[]`, `resident_tokens`） | 新表 `tool_exposure_log`，或 `tool_audit_log` 加 `event='exposed'` | 没有它，"裁剪是否伤害了模型"永远无法证伪。这是 §5.6.6 那条局限的**唯一解** |
| **P0** | 上面这张表**带 channel 列** | 同上 | §5.6.3 已经证明渠道分组是决定性的，而它现在只活在 conversation_id 的字符串前缀里 |
| **P1** | 按工具记 token 成本 | 每次装配时写进同一张表 | 回答"谁最贵"，且能验证 `cost` 项到底该不该存在 |
| **P1** | 技能的**结果**（不只是次数） | 复用 `tool_audit_log` 的 `is_error`，或给 `skill-store` 加 `lastOutcome` | 技能侧要能回答"这条技能还靠谱吗" |
| **P2** | 展开率：被检索工具 vs 从未被检索 | 派生自 P0 | 判断 `tool_search` 的兜底是否真的被用到 |

**存储量的诚实估算**：每轮一行、约 200 字节（20 个工具名 + 元数据）。日均 400 轮 → ~80KB/天，
一年 ~30MB。**比现在 `tool_audit_log` 的 46K 行还小**，不构成负担。
保留期照抄 `tool_usage_daily` 的 90 天即可。

#### 5.7.2 一条硬规矩（来自本仓库三次翻车）

**统计必须回答一个具体的决策，否则不记。**

本仓库已经有三张"记了没人读"的表/字段：`skill_usage_records`（0 行）、
`queryExecutionLogs`（无消费者）、`capability_tests`（14 万行，但写它的是
`pet-task-store` 的宠物测试，与能力面无关）。它们不是失败在"没记"，是失败在**记完没人用**。

所以 §5.7.1 每一行都标了"为什么是它"——**没有决策消费者的字段，不进 P0**。

## 8. 风险与缓解

| 风险 | 缓解 |
|---|---|
| **把能力治理做成一个大页面**，字段越加越多，最后没人维护 | 描述符只四个字段（§3.3）；页面是**只读清单 + 一个开关**，不做编辑器 |
| 打开 `ENABLE_SKILL_ACTIVATION` 后技能被错误降级，模型突然"不会用"某技能 | 先灰度单个 Agent；`on_demand` 的技能仍可通过 `skill_search` 找到（降级 ≠ 删除）；观察一周再全量 |
| `pipeline_draft` 蒸馏出"看起来对但没验证"的 spec | draft 状态**不能直接 record**，必须过 rehearsal；生成的 spec 强制带 `source: {sessionKey, range}` 便于回溯 |
| 自动补丁改坏 spec | 只改失败那一步；必须过 rehearsal；**不改断言**；写回前留 `spec.prev.json` |
| MCP 沉底后模型"不知道有这个工具" | `tool_search` 的描述里点名"外部工具（MCP）都在这里"；`capability:inventory` 页可查；降级回落全量 |
| 统一度量表变成又一个无人读的表 | **P1 的页面必须消费它**；若 P1 不做，P0 不加表（先不建死表，这是 §2.1 的教训） |
| 渠道被误当能力 | §3.1 已划界：渠道是投递终点，沿用 `channel_*`，不进能力面 |

## 9. 测试与验收

### 单测

- `getSkills()` 返回 `usageCount` 且等于索引的 `executionCount`
- `capability_usage` 加 `kind` 后，旧行默认为 `'tool'`，查询不丢历史
- `updateAutoScopeBatch` 在 `ENABLE_SKILL_ACTIVATION=true` 时产生 `on_demand`；在 false 时行为不变（**证明灰度开关真的有效**）
- `pipeline_draft` 对一段含 12 次工具调用的轨迹，能剔除纯读取的探索步骤（断言输出步数 ≤ 输入工具调用数，且每步工具名在原始轨迹中出现过）

### 真机

0. **回放脚本可复跑**：`node verify/capability-ranking-replay.mjs` 输出与 §5.6.2 表一致（±0.5%）
1. 连跑 5 轮对话 → 对比日志里技能顺序与 `executionCount` 排序一致
2. 灰度 Agent 上开 flag → 观察日志出现 `激活范围自动调整` → 该技能仍在 `skill_search` 可查
3. 能力页排序与 `contextUsage` 日志的 tools/mcp/skills 三分误差 < 10%
4. 造一条成功轨迹 → `pipeline_draft` → rehearsal 绿 → active → 改坏一步 → 失败 → 自动补丁 → rehearsal 绿（完整闭环）
5. **`tool_exposure_log` 能回答"这个工具当轮有没有被展示"**：抽查一轮，`tool_names[]` 与实际发给模型的工具数一致，且能被 `tool_audit_log` 里的同一 turn 调用反查

### 可观察性（§5.7 的验收）

- `tool_exposure_log` 的 `channel` 列非空率 > 99%（不能像 `definition_id` 那样只有 73%）
- 用这张表重算 §5.6.3 的分组表，结果与人肉解析 `conversation_id` 前缀**一致**（误差 < 1%）
- 每张新表/新字段都必须有一个**读它的地方**（页面、脚本或告警），
  否则不进 P0——照抄 §5.7.2 的硬规矩

- `pnpm typecheck` 0 错误
- `pnpm --filter ./apps/windows test:all` 全绿
- `pnpm check:wiring` 新增 0
- 能力页三个主题下无硬编码色值

## 附录 A：为什么不给流水线单独建一套治理

考虑过三个方案：

| 方案 | 否决理由 |
|---|---|
| **A. 流水线独立治理**（自己的索引、自己的页、自己的统计） | 直接变成第三套断线。仓库已有两套，加起来是 0 效果 |
| **B. 把流水线塞进 skill**（一个 SKILL.md + spec.json） | 混淆了"散文"与"可执行"，`skill_invoke` 返回什么？模型读散文还是执行？语义会打架 |
| **C. 共享动词 + 独立存储 + 统一度量**（选定） | 四个动词一一对应（§4.3），存储各自合理（散文 vs 声明式），度量同一张表 |

C 的关键是承认一件事：**"可复用的能力资产"这个说法是对的，但"可复用"不等于"同构"**。技能是给人看的，流水线是给机器跑的。它们共享的是**发现与度量**，不共享**执行语义**。

## 附录 B：Open Questions（评审需定）

1. **`ENABLE_SKILL_ACTIVATION` 能否直接默认开？** 现状默认 false 的理由已经查不到记录（`feature-flags.ts` 只写"v12 扩展默认关闭，保持现网行为不变"）。若没有具体事故，建议灰度后置 true。
2. **`pipeline_draft` 是否需要用户在页面上确认才落盘？** 倾向：先落到 `runs/.drafts/` 不直接进 `pipelines/`，用户确认后才转正。
3. **能力页放在哪**：独立页面（`app.view`，像流水线页）还是并入现有「工具」页的一个 tab？倾向前者——它是跨三类的，塞进任何一类的页都会偏。
4. **P2 是否值得现在做**：本机 MCP 只占 1–2K（因为只有 4 个 server），但代码注释记录过单 server 150K 的情况。取决于是否要支持重度 MCP 用户。建议：等有真实用户反馈再做，但要先把度量铺好，否则将来无法判断。
