工具、技能、流水线三类能力资产的**生命周期、度量、分层暴露**。

## 一句话

先修断线，再加新东西 —— 仓库已经设计过两轮能力治理，两轮都没通电。

## 五件事（按优先级）

1. **回放评测已落地**：`verify/capability-ranking/replay.mjs`（零风险、零生产改动）。
2. **补可观察性**：每轮暴露了哪些工具**现在完全没记**（§5.7）——不补这个，任何裁剪都无法证伪。
3. **修三条断线**：`usageCount` 没填、`autoActivationScope` 被 flag 关着、`skill_usage_records` 0 行。
4. **统一度量**：三类能力共用一张 usage 表（`kind` 列区分 + **channel 列**），能力页消费它。
5. **分层暴露**：T0/T1/T2 分三层；层内**纯 LRU**（不是加权公式，见下）。

## 与流水线设计的关系

- 流水线的**创建/使用/更新/管理**四动词与技能一一对应（search / invoke-or-inspect / draft）。
- 流水线的**进化**靠 journal（每步 `expect` 是机器可判的），这是它相对技能的结构性优势。
- 渠道**不在**能力面内：它是投递终点，沿用 `channel_*`。

## 实测数字（本机）

| 能力 | 每轮上下文成本 | 数量与用量 |
|---|---|---|
| 内建工具 | 9–20K tokens | 高频前 10 个占绝大部分调用 |
| MCP 工具 | 1–2K（本机）；代码注释记录过单 server 150K | 79 个用过，占 44% 的能力数、4.7% 的调用量 |
| 技能 | **86 tokens** | 63 个（44 内置 + 19 安装） |

技能能做到 86 tokens，是因为它被"工具化"改造过；工具从没被这样改造，所以成了最大的固定开销。

## 排序：回放实测推翻了初稿

初稿给了一个六项加权公式（频率 + 近期 + 会话 + 共现 + 相关性 − 成本），并引"top20 覆盖 89.5%"支撑。
**那个 89.5% 是事后统计，不是预测能力。** 用 3174 条真实消息做时间切分回放：

| 策略 | N=20（按 agent×渠道分组） |
|---|---|
| 纯近期（LRU） | **93.5%** |
| 初稿六项公式 | 90.6% |

频率项、共现项、会话项**全部负增益或冗余**；半衰期从 0.25 天到 180 天**结果完全一样**。
最终设计砍成三行规则：**按 (agent, channel) 分组 + 最近使用降序 + 常驻 20 个**。

复跑：`node verify/capability-ranking/replay.mjs [--global|--by-agent|--curve]`

## 调用集中度（事后统计，仅作规模参考）

```
179 个工具，33626 次调用：top5=53.0% top10=72.0% top20=89.5% top30=93.7%
每日活跃工具数：中位 27，p90 50；每会话用到不同工具：中位 4，p90 8
```

**这组数只能说明"长尾确实很长"，不能说明"排前 20 就够"**——后者要回放才知道（见上）。
