## 0. 结论摘要

### 0.1 定位

Wiki 是 **散乱资料的自动收集与整理层**，不是手写笔记本。用户在 Lumii 里持续产生上传文档、任务产物、网页搜索结果、多媒体文件，这些数据散落在 `uploads/`、`outputs/` 与对话历史中，人难以查找阅读、Agent 难以利用、也没有定期清理归档的入口。Wiki 负责把它们自动收进来、由 AI 分类归档、并让人与 Agent 都能检索。

**AI 在其中是整理者，不是作者。** 它的主要工作是给资料分类、生成摘要页、编入固定目录骨架，而不是重写或合成既有知识。

### 0.2 分期总览

| 阶段 | 主题 | 交付价值 |
|---|---|---|
| **P0** | 自动摄入 + AI 分类归档 + 检索 | 资料不再散乱：进得来、整得齐、查得到（人与 Agent 双端） |
| **P1** | 人工知识组织闭环 + 归档清理 + 导出 | 用户可校正与深化 AI 的整理结果，可定期清理，数据可带走 |
| **P2** | 知识合成 + 图谱 + 智能检索 | 从「资料整理」升级为「知识积累」 |

### 0.3 与 08-24 设计的关键差异

| 议题 | 08-24 设计 | 本设计 | 原因 |
|---|---|---|---|
| MVP 核心 | 手动登记资料 + 三栏编辑器 | 自动摄入 + AI 分类归档 | 手动登记是散乱的成因而非解药；堆积的文件不会被逐个手动登记 |
| AI 编译 | 扩展 1 | P0 | 它是核心价值而非增值项 |
| 编译形态 | Karpathy 四步含 Cascade 涟漪更新 | 仅分类 + 摘要 | AI 定位为整理者，无需重写既有页；LLM 调用量从 10-15 次降到 1-2 次 |
| 目录结构 | 完全自由 `path` | 固定 6 顶层分类 + AI 落点规则 | 自由路径会让 AI 每次发明新结构，换一种散乱 |
| 写权限 | AI 绝不直接写，全部走候选 | P0 直接写，revision 即保护 | 整理类操作出错代价低，全程确认会让全自动失去意义 |
| 多媒体 | 未涉及 | 双角色（资料源 + 页面附件） | 用户实际产生大量图片/音视频 |
| 中文检索 | `unicode61` 分词器 | 复用既有 `tokenizeBigram` 预分词 | `unicode61` 对中文按单字切分，精度不足；`trigram` 依赖 SQLite 版本，而主/回退双路径版本均不可假定 |
| Agent 接口 | 仅 renderer IPC | 专设 Agent 工具族 | Agent 侧检索是明确痛点，薄封装不够用 |
| 手动编辑器 | P0 三栏完整形态 | P0 简化，完整形态入 P1 | 让位给自动化管线 |

### 0.4 设计原则

1. **自动优先**：主数据流（上传/产物/搜索）零操作入库并归档；需要用户记得去点的功能等于不存在。
2. **失败不静默**：LLM 失败、分类失败、导出失败都要留痕并可重试，资料绝不因失败而消失。
3. **修订即保护**：不建权限模型，任何写入都留 revision，错了回滚。
4. **派生可重建**：FTS 索引、链接索引、向量表均为派生数据，删了可重建，零数据损失。
5. **AI 自由度小于用户自由度**：AI 受固定落点规则约束，用户可在任意路径自由组织。

### 1.2 关键技术项核实结论

三项影响可行性的技术项已核实，结论如下：

| # | 核实项 | 结论 | 对设计的影响 |
|---|---|---|---|
| 1 | 中文全文检索方案 | 项目**无任何 FTS5 先例**（全库无 FTS5 表）；`node:sqlite` 为主、`better-sqlite3` 为回退，`trigram` 在两条路径的可用性不可假定；但 `memory/segmentation.ts` 已有经单测验证的中文 bigram 分词器 | **放弃 trigram，改为 bigram 预分词方案**（见 §3.6） |
| 2 | 多模态视觉能力 | 存在 `recognizeImage`（`main/agent-runtime/bridge-image-services.ts`），由独立的 `vision` 槽位配置驱动（含 `enabled` 与 `modelId`） | 图片描述可实现；降级条件明确为 vision 槽未启用或未配置模型 |
| 3 | Agent 工具注册机制 | 存在完整注册层：`createMtBotTool` 定义 + `ToolRegistry` 注册；宿主侧已有 `bridge-browser-tools.ts`、`bridge-app-ui-tools.ts` 等按域分文件注册的既成范式 | Agent 工具族可在 P0 交付，无需补基础设施 |

补充核实：当前 `SCHEMA_VERSION = 14`，Wiki 迁移从 **V15** 起。既有 `memorySearchToolConfig` / `memoryReadToolConfig` 是 Agent 侧检索工具的直接范式参照。

## 2. 数据分层与目录骨架

### 2.1 四层数据职责

```text
收件箱（inbox）    自动摄入的待整理条目 —— 有生命周期，整理后退场
资料层（sources）  资料原文与提取文本 —— 不可变的事实层，知识可从中重建
知识层（pages）    分类归档后的知识页 —— AI 与用户共同演进
修订层（revisions）每次写入的不可变快照 —— 支持追溯与回滚
派生索引           全文索引、链接索引、向量表 —— 可删可重建
```

收件箱是本设计相对 08-24 新增的一层，也是「自动」得以成立的关键：它把「资料已进入系统」与「资料已被整理」解耦，使摄入可以同步完成而整理异步进行，任一环失败都不丢数据。

### 2.2 固定目录骨架

顶层分类固定，不允许 AI 新增顶层目录；AI 只能在既定顶层下创建子路径。

| 顶层分类 | 内容 | AI 写入权限 | 启用阶段 |
|---|---|---|---|
| `sources/` | 每份文档资料一个摘要页（与资料条目 1:1） | 默认落点，自动写 | P0 |
| `media/` | 多媒体资料索引页（图片描述、音视频元数据与来源上下文） | 按媒体类型自动分流写入 | P0 |
| `inbox/` | AI 无法判定归属的兜底页；对话提取的落点 | 自动写，UI 显示计数待用户处理 | P0 |
| `concepts/` | 概念、方法、原理等可复用抽象知识 | 需跨资料复现门槛才可建 | P1 |
| `entities/` | 人、项目、工具、组织等具名实体 | 需跨资料复现门槛才可建 | P1 |
| `syntheses/` | 跨资料综述与洞察 | **AI 不自动创建**，仅用户显式触发 | P2 |

**落点规则的设计意图**：`sources/` 与 `media/` 是「一份资料一个页」，不触碰既有知识，出错代价最低，因此允许全自动。`concepts/` 与 `entities/` 需要判断「是否已存在同一概念」，有合并语义，因此设门槛（同一概念在多份资料中复现方可建页），避免 AI 给每份资料都发明一批概念页。`syntheses/` 需要真正的知识合成，风险最高，只在用户明确要求时执行。

用户不受此规则约束，可在任意路径（含顶层之外）自由建页与移动页面。

## 3. P0：自动摄入 + AI 分类归档 + 检索

### 3.1 目标与非目标

**目标**：用户正常使用 Lumii，不做任何额外操作，上传的文件、任务产出的文档、搜索的网页自动进入 Wiki 并被 AI 分类归档；用户与 Agent 都能检索到这些内容。

**P0 非目标**：`[[wikilink]]` 与反链、修订历史 UI 与回滚、Markdown 批量导出、页面附件嵌入渲染、归档清理 UI、概念与实体页、综述、图谱、向量检索、音视频转录、多人协作与云同步。

### 3.2 数据模型

#### 收件箱 `wiki_inbox`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | |
| `agent_id` / `user_id` | TEXT | 归属隔离，与既有表一致 |
| `item_type` | TEXT | `upload` / `output` / `search` / `chat` |
| `source_path` | TEXT 可空 | 磁盘路径（upload、output） |
| `source_url` | TEXT 可空 | 网页来源（search） |
| `title` | TEXT | 摄入时的初始标题（文件名或网页标题） |
| `content_preview` | TEXT 可空 | 内容前若干字符，供列表展示与批量分类输入 |
| `media_type` | TEXT | `document` / `image` / `audio` / `video` |
| `status` | TEXT | `pending` / `organized` / `discarded` |
| `attempt_count` | INTEGER | 分类重试次数，用于退避与死信判定 |
| `last_error` | TEXT 可空 | 末次失败原因，UI 可见 |
| `organized_source_id` | TEXT 可空 | 整理后指向生成的资料条目 |
| `created_at` / `organized_at` | TEXT | |

索引：按 `(agent_id, user_id, status, created_at DESC)` 建索引，服务待整理列表与队列取件。

#### 资料层 `wiki_sources`

延续 08-24 定义（`id`、归属、`title`、`source_path`、`content_md`、`content_hash`、`mime_type`、`created_at`），新增：

| 新增字段 | 说明 |
|---|---|
| `media_type` | `document` / `image` / `audio` / `video` |
| `extracted_text` | 图片的 LLM 描述、文档的正文提取结果；**入全文索引**，是多媒体可被检索的唯一途径 |
| `media_meta` | JSON：时长、分辨率、页数、文件大小等 |
| `preview_path` | 缩略图或封面路径，可空 |
| `origin_context` | 来源上下文文本：由哪次任务/对话产生、当时的任务目标 |
| `archived_at` | 归档标记，可空；检索默认排除（P1 提供 UI，P0 仅落字段） |

**`origin_context` 的设计价值**：音视频不做转录，其正文不可检索。但用户的真实检索意图通常是「那次竞品调研下载的视频」而非视频中的某句话，来源上下文比转录更贴近检索意图，且零成本。

#### 知识层 `wiki_pages`

延续 08-24 定义（`id`、归属、`path`、`title`、`content_md`、`version`、`created_at`、`updated_at`，`(agent_id, user_id, path)` 唯一），新增：

| 新增字段 | 说明 |
|---|---|
| `category` | 冗余存储顶层分类，供 Agent 概览与按类筛选，避免每次解析 `path` |
| `last_used` / `use_count` | 检索命中与读取时更新，服务 P1 清理提示与 P2 排序衰减 |

不设 `authority` 权限字段：AI 与用户共写同一批页面，修订历史即保护机制。

#### 修订层 `wiki_page_revisions`

延续 08-24 定义（`page_id`、`version`、`content_md`、`title`、`path`、`editor`、`created_at`，`(page_id, version)` 唯一）。`editor` 取 `user` / `ai`，AI 写入时记录其依据的资料条目标识。P0 只写不读（UI 在 P1 交付），但**必须从 P0 起写入**，否则 P1 无历史可回滚。

#### 归档运行日志 `wiki_organize_runs`

| 字段 | 说明 |
|---|---|
| `id` / `agent_id` / `user_id` | |
| `inbox_ids` | 本批处理的收件箱条目标识（JSON 数组，批量分类为多条一批） |
| `status` | `running` / `succeeded` / `partial` / `failed` |
| `result_summary` | 分类结果概要：各条目落到哪个分类、生成了哪些页 |
| `error` | 失败原因，可空 |
| `created_at` / `finished_at` | |

全自动写入必须可审计。用户事后发现分类不对时，需要能查到「这页是哪一批、依据什么内容生成的」。

#### 派生索引 `wiki_pages_fts`

FTS5 虚拟表，索引**预分词后**的标题列与正文列（见 §3.6 的 bigram 方案）。因索引内容是分词产物而非原文，不采用外部内容表模式，改为独立表由写入路径与重建函数显式维护 —— 这样分词逻辑变更时只需重建索引，无需迁移主表。

项目此前无 FTS5 使用先例，因此 FTS5 表的创建、写入与查询须在 P0 以单测覆盖两条 SQLite 路径的行为一致性。

资料层的 `extracted_text` 通过其对应的 `media/`、`sources/` 页正文纳入索引，不单独建资料 FTS 表 —— 一个检索入口即可覆盖，避免双索引一致性负担。

#### 索引元信息 `wiki_index_meta`

键值表，记录索引健康状态、末次重建时间、分词器实际生效类型（供 UI 显示与问题诊断）。

### 3.3 自动摄入管线

四路摄入源，钩子挂在既有流程的完成点上，**只插收件箱记录，不做任何 LLM 调用**，保证摄入同步完成且不拖慢主流程。

| 摄入源 | 触发点 | 摄入策略 |
|---|---|---|
| 上传文件 | 文件落盘 `uploads/` 且元数据注册完成后 | 全自动 |
| 任务产物 | 任务产出文件写入 `outputs/` 后 | 全自动 |
| 网页搜索 | 搜索结果获取后 | 全自动，记录 URL 与页面摘要 |
| 对话提取 | **仅显式沉淀信号**触发 | 降级处理，见下 |

**对话提取的降级设计**：另外三路都有明确的用户意图作为信号（用户确实上传了、任务确实产出了、用户确实搜了），对话提取没有。若全自动判断「哪段对话值得沉淀」，会把随口提问、试探性想法、已废弃的方案讨论都写成知识页 —— 结果是把「文件散乱」变成「Wiki 塞满垃圾页」，与本功能的目标相反。因此：

- 仅在出现显式信号时摄入：用户明确表达要记录（如「记下来」「存到 wiki」），或 Agent 主动调用沉淀工具。
- 落点固定为 `inbox/`，不进 `sources/`，UI 单独分栏，由用户决定去留。

**摄入去重**：以 `source_path` 加内容哈希判定。同一路径同一内容重复摄入时跳过；同一路径内容已变化时作为新条目摄入（旧资料条目保留，符合「资料不可变」）。

### 3.4 AI 分类归档管线

异步后台队列，与任务执行解耦。

```text
收件箱取件（批量，同类型聚合）
  → 内容提取（文档抽正文 / 图片走视觉描述 / 音视频只取元数据与来源上下文）
  → 批量分类（单次 LLM 请求处理一批，返回结构化分类结果）
  → 落库：写资料条目 → 生成摘要页写入对应分类 → 写修订记录 → 收件箱标记 organized
  → 写运行日志
```

**关键设计点**

1. **批量合并调用**：用户一次拖入数十个文件时，不可退化为逐条 LLM 调用。分类任务足够简单（判定分类 + 生成标题与摘要），可将一批条目的标题与内容前若干字符合并为单次请求，让模型返回结构化数组。批大小需可配置，按内容长度动态收缩以适应上下文限制。
2. **失败留在 pending**：LLM 调用失败（网络、额度、模型未配置）时条目保持 `pending`，累加 `attempt_count` 并记录 `last_error`，按退避策略重试。**绝不标记失败后消失** —— 用户看到的应是「待整理 3 项」，而不是资料凭空不见。超过重试上限的条目转入需人工处理的展示态，仍不删除。
3. **部分成功可接受**：一批中个别条目分类失败时，成功者正常落库，失败者留 `pending`，运行日志记 `partial`。
4. **顺序与并发**：单队列串行处理，避免多批并发争抢 LLM 配额与写库冲突。队列在应用启动时恢复未完成条目。
5. **分类不准的补救**：P0 不做确认流程，但页面可被用户改路径与正文（§3.7），运行日志可追溯依据。这是「全自动 + 事后可改」的完整闭环。

### 3.5 多媒体处理

多媒体在 Wiki 中承担 **双角色**：既可作为资料源被提取与归档，也可作为附件被页面引用。P0 交付资料源角色，附件嵌入角色在 P1 交付（依赖编辑器与渲染能力）。

| 媒体类型 | P0 提取方式 | 生成页面内容 |
|---|---|---|
| 文档 | 正文抽取 | `sources/` 摘要页 |
| 图片 | 复用既有 `recognizeImage` 生成描述文本 | `media/` 索引页：描述 + 元数据 + 来源上下文 |
| 音频 / 视频 | **不转录**，仅元数据 | `media/` 索引页：文件信息 + 来源上下文 |

图片描述直接复用宿主既有的 `recognizeImage` 能力（`bridge-image-services.ts`），不新建视觉调用链路。该能力由独立的 `vision` 槽位配置驱动，因此降级条件明确：**vision 槽未启用或未配置模型时**，图片降级为与音视频相同的处理方式，页面与界面标注「未生成描述」，并允许在能力配置好后重新提取。

音视频不转录是明确的成本取舍（避免引入本地语音模型或外部转录服务）。代价是其内容不可检索，缓解手段为 `origin_context`。**此限制须在 UI 上向用户明示**，否则用户会误以为搜过了就是库里没有。

### 3.6 检索设计

#### 中文分词：bigram 预分词方案

三种候选方案的比较：

| 方案 | 问题 |
|---|---|
| `unicode61`（08-24 设计） | 中文按单字切分，检索「架构设计」实际匹配四个独立单字，任何同时含这些字的页面都会命中，精度低且 BM25 打分失去区分度 |
| `trigram` | 中文质量好，但依赖 SQLite ≥ 3.34。项目主路径是 Electron 内建的 `node:sqlite`，回退路径是 `better-sqlite3`，**两条路径的版本均随宿主变化**，不可假定可用；且项目无 FTS5 先例，无既有经验兜底 |
| **bigram 预分词（采用）** | 复用项目已有的 `tokenizeBigram`，与分词器特性解耦 |

**采用方案**：写入页面时用 `memory/segmentation.ts` 的 `tokenizeBigram` 对标题与正文预分词，将 bigram 以空格连接后存入专用的检索列，FTS5 表对该列使用默认分词器（按空格切分即可正确工作）。查询时对用户输入施加同一分词函数，得到 bigram 序列后再构造 FTS5 查询。

选择理由：

1. **不依赖 SQLite 版本特性** —— 规避了主/回退双路径版本不确定这一最大风险。
2. **复用已验证代码** —— `tokenizeBigram` 已有单测覆盖（CJK 连续串转 bigram、拉丁词整词小写、标点与 emoji 忽略）。
3. **与记忆召回口径一致** —— 记忆系统的相关性匹配用的是同一分词函数，两处检索行为可预期地一致。
4. **精度优于单字** —— 「架构设计」分词为「架构 / 构设 / 设计」，要求 bigram 共现，精度显著高于单字匹配。

代价：需维护一个派生的分词列（属既有派生索引骨架，重建逻辑一并覆盖），且检索列不适合直接展示（片段展示从原始正文取）。

分词方案与实际生效配置写入索引元信息表，供 UI 显示与问题诊断。

#### 查询处理

- 用户输入须做 FTS5 特殊字符转义（引号、星号等），避免语法错误直接抛给用户。
- 结果返回路径、标题、分类、匹配片段与更新时间；按 BM25 排序。
- 归档资料对应的页面默认排除在结果外（P0 落字段，P1 给 UI 开关）。
- 命中即更新 `last_used` 与 `use_count`。

### 3.7 P0 界面形态

在 `MemoriesPage` 新增 Wiki Tab，两栏布局（左侧导航 + 右侧内容），P0 不做第三栏。

- **左栏**：搜索框；固定分类树（`sources/` `media/` `inbox/`，含页数）；「待整理」入口显示 `pending` 计数与失败计数。
- **右栏 - 页面视图**：标题、路径、正文渲染；可切换到编辑态修改标题、路径、正文并保存（每次保存写新修订）；显示来源资料链接与所属运行日志入口。
- **右栏 - 待整理视图**：收件箱列表，展示类型、标题、预览、状态与失败原因；支持手动重试与丢弃；支持手动指定分类后立即归档。
- **右栏 - 运行日志视图**：归档批次列表与结果概要，用于追溯某页的生成依据。
- 空状态：说明 Wiki 会自动收集资料，不生成示例数据。
- 窄窗口：左栏可折叠。
- 主题：编辑器接入 `useDataThemeColorMode`；按钮复用既有组件；新增样式限定在 `MemoriesPage` 作用域。

P0 的编辑能力刻意保持最小（改标题、路径、正文），目的是让用户能纠正 AI 的分类错误，而非提供完整写作体验 —— 后者是 P1 的内容。

### 3.9 Agent 工具族

Agent 的检索需求与人不同：人可以搜出列表再逐个点开，Agent 每次工具调用都是一轮 LLM 往返，成本高。因此工具不能只是命令的薄封装。

| 工具 | 职责 | 设计意图 |
|---|---|---|
| `wiki_overview` | 返回各分类的页面数与近期页面标题 | **让 Agent 先建立地图**。没有它，Agent 只能盲目猜关键词搜索，搜不到就报告「没有资料」，而库里其实有 |
| `wiki_search` | 检索并返回匹配段落**全文**（非短 snippet） | 一次调用拿到足够上下文，避免「搜列表 → 逐个读页」的多轮往返 |
| `wiki_read` | 读取指定路径的完整页面 | 需要全文时的精确读取 |
| `wiki_capture` | 将指定内容沉淀到 `inbox/` | 对话提取的显式信号入口（§3.3） |

P0 的 Agent 工具限于读取与沉淀，不提供改写既有页的工具 —— 自动归档已覆盖写入需求，额外的改写能力在 P0 收益不明确且风险更高。

**实现范式**：工具以 `createMtBotTool` 定义、经 `ToolRegistry` 注册，遵循宿主侧按域分文件的既成做法（参照 `bridge-browser-tools.ts`、`bridge-app-ui-tools.ts`），新增独立的 Wiki 工具注册文件。既有 `memorySearchToolConfig` 与 `memoryReadToolConfig` 是最近的形态参照，Wiki 工具在命名、参数风格与返回结构上与其保持一致。

工具属性设定：全部为只读（`isReadOnly`）、无需权限确认，`wiki_capture` 因产生写入应标记为非只读。

### 3.10 关键类设计

运行时通用逻辑置于 `packages/agent-runtime/src/wiki/`，仅依赖 SQLite 与 TypeScript；Electron 侧只做 IPC 分派与文件对话框。不引入 service/factory 分层，与 `AgentMemoryRepo` 一致直接持有数据库适配器。

| 单元 | 职责 | 关键方法（签名略） |
|---|---|---|
| `WikiRepo` | 收件箱、资料、页面、修订、运行日志的读写与检索 | 收件箱取件与状态流转、页面保存（同事务写修订）、检索、按分类统计 |
| `WikiIngestHook` | 四路摄入的统一入口 | 由上传/产物/搜索/沉淀调用，负责去重判定与收件箱插入 |
| `WikiOrganizer` | AI 分类归档管线编排 | 取件 → 提取 → 批量分类 → 落库 → 写日志；含批大小收缩与退避重试 |
| `WikiContentExtractor` | 按媒体类型提取文本 | 文档正文抽取、图片视觉描述、音视频元数据 |
| `WikiClassifier` | 分类决策与提示词构造 | 输入一批条目摘要，输出结构化分类结果；含落点规则约束 |
| `WikiIndex` | 派生索引重建与检索列生成 | 清空后从页面表全量重建；调用 `tokenizeBigram` 生成检索列内容 |
| `WikiQueryBuilder` | 查询分词与 FTS5 查询构造 | 对用户输入施加同一分词函数，转义特殊字符后构造查询 |
| `WikiOrganizeQueue` | 串行异步队列 | 入队、启动时恢复未完成条目、并发闸门 |

分类结果的结构化输出须做严格校验：分类必须落在允许的顶层集合内，路径不得含空段、`..`、绝对路径或分隔符逃逸；校验失败的条目落 `inbox/` 而非拒绝入库。

### 3.11 P0 验收标准

- 上传文件、任务产出、网页搜索后，无需任何用户操作，条目出现在收件箱并在后台完成归档。
- 一次拖入数十个文件时，LLM 调用次数远小于文件数（批量合并生效）。
- 断网或模型未配置时，条目停留 `pending` 并显示原因，恢复后重试成功，全程无资料丢失。
- 图片生成描述文本且可被搜索命中；音视频可凭来源上下文被搜索命中。
- 中文与中英混合检索质量达标（须以实际样本验证，含「架构设计」类多字词的精度对比）。
- 引号、星号等特殊字符输入不报错。
- 归档产生的页面记录了修订与运行日志，可追溯生成依据。
- 用户修改页面标题、路径、正文后重启保持不变；同归属同路径不重复；跨归属隔离。
- 重建索引后检索结果与重建前一致。
- Agent 可通过工具获得分类概览、检索到内容、读取指定页面。

## 4. P1：知识组织闭环 + 归档清理 + 导出

P0 解决「进得来、整得齐、查得到」，P1 解决「改得动、理得清、带得走」。

### 4.1 页面链接与反链

采用 `[[页面标题]]` 与 `[[目录/页面标题]]` 两种子集，不支持别名、标题锚点、块引用与嵌入。解析规则：

1. 带路径的按规范化路径精确匹配。
2. 不带路径的先匹配当前目录下同标题，再匹配全库唯一标题。
3. 多重匹配不写边，非阻塞提示候选，引导用户改为带路径写法。
4. 未匹配不写边但保留原文，允许「先链接后建页」。
5. 修改标题或路径**不自动改写其他页正文**，受影响链接在下次重建时显示为未解析。

链接索引表记录源页与目标页的有向关系，仅作反链与后续图谱的缓存；**解析失败永不破坏正文内容**。

AI 归档时可写入链接（如资料摘要页链接到其来源的 `media/` 页），但不承担全库链接维护责任。

### 4.2 修订历史与回滚

P0 已写入修订数据，P1 交付其界面与能力：

- 修订列表展示版本号、时间、编辑者（用户或 AI）。
- 版本预览与与当前版本的差异对比（复用已装 `diff` 依赖）。
- 回滚语义：读取目标版本内容作为**一次新的编辑**写入，版本号继续递增，旧修订永不被物理修改或覆盖。

这是「不建权限模型」得以成立的前提 —— AI 改错了，回滚即可。

### 4.3 归档与定期清理

直接回应「不好定期清理和整理」这一诉求。P0 已落 `archived_at` 字段，P1 交付策略与界面。

| 能力 | 设计 |
|---|---|
| 清理建议 | 扫描长期未使用（基于 `last_used` 与 `created_at`）、来源文件已不存在、内容重复的资料条目，聚合为待清理清单 |
| 归档而非删除 | 归档后检索默认排除，可一键恢复；不进回收站二级机制 |
| 批量操作 | 待清理清单支持批量归档、批量删除、批量移动分类 |
| 来源失效检测 | 资料条目记录了内容哈希与路径，可检测源文件被删或被改，提示用户处理 |
| 重复检测 | 基于内容哈希的精确重复；不在此阶段做语义近似重复（属 P2 向量能力） |

删除语义：删除页面时二次确认并显示受影响反链数，链接索引级联清理，其他页正文中的 `[[...]]` 文本保留为未解析。删除资料条目时解绑关联，**不级联删除引用它的页面**，页面仅失去来源标注。不做软删除回收站 —— 修订历史与数据库备份已是双重兜底。

### 4.4 多媒体附件嵌入

补齐多媒体的第二重角色：

- 编辑器支持拖拽上传图片与媒体文件，自动登记为附件并插入引用语法。
- 页面附件关联表记录页面、可选的资料条目、文件路径、媒体类型与展示名。
- 预览渲染将引用语法渲染为图片查看器或媒体播放器。
- 附件与资料条目可关联（同一文件既是资料源又被页面引用时不重复存储文件）。

### 4.5 概念页与实体页

启用 `concepts/` 与 `entities/` 两类分类，AI 可在满足复现门槛时建页：

- 门槛设计：同一概念或实体需在多份资料中复现方可建页，具体阈值需依实际数据调优，且必须可配置。
- 建页后，相关资料摘要页自动链接到概念或实体页，形成导航网络。
- 概念与实体页涉及跨资料合并语义，出错代价高于摘要页，因此**此类写入需用户确认**（与 `sources/`、`media/` 的全自动区别对待）。

### 4.6 Markdown 批量导出

- 按页面路径结构导出为标准 Markdown 文件，可选附带资料原文与多媒体附件。
- 路径规范化：拒绝空段、`..`、绝对路径与分隔符逃逸。
- 逐页返回失败清单，不静默跳过。
- 写入导出清单文件，记录导出范围与时间。
- 目标：导出结果在无 Lumii 环境下可正常阅读，且与 Obsidian 等工具的链接语法兼容。

### 4.7 P1 界面增量

- 恢复第三栏：反链列表与修订历史（窄窗口折叠到正文下方）。
- 新增「清理」视图：待清理清单、批量操作、归档项浏览与恢复。
- 编辑器增强：拖拽上传、链接补全提示、路径选择器。
- 顶部新增导出与重建索引命令，进行中与结果态明确，不后台静默执行。

### 4.8 P1 验收标准

- 链接与反链正确建立，歧义与未解析场景均不破坏正文。
- 每次保存版本递增，任意历史版本可预览、可对比、可回滚，回滚后旧修订完好。
- 清理清单能识别长期未用、来源失效与重复资料；归档后检索排除、可恢复。
- 附件可拖拽上传、正确渲染、导出时一并带出。
- 概念与实体页在达到门槛时生成候选并经用户确认后落库。
- 导出产物在无 Lumii 环境可阅读，失败项有明确清单。

## 5. P2：知识合成 + 图谱 + 智能检索

P2 把 Wiki 从「资料整理」推进到「知识积累」。三项能力相互独立，可按实际痛点分别决策，不必捆绑发布。

### 5.1 综述合成（`syntheses/`）

启用 `syntheses/` 分类。这是 AI 唯一承担真正知识合成的场景。

- **仅用户显式触发**，AI 不自动创建综述。
- 输入为用户选定的一组资料或页面（或某个分类下的全部页面）。
- 产出为候选而非直接写入：用户查看后逐项接受或拒绝，接受后写为新修订。
- 综述页记录其依据的页面与资料，保证可溯源。
- 引用保真：综述中的数字、日期、引述必须能在来源资料中验证。

**为何不自动化**：综述需要跨资料判断与取舍，错误不是「放错位置」而是「结论错误」，且难以被用户察觉。全自动生成会污染知识库的可信度。

### 5.2 页面状态与矛盾提示

给页面增加状态：活跃、过期、存疑、已归档。

- 状态变更不由 AI 静默批量执行，只能生成候选由用户确认。
- 矛盾处理语义为**标记而非删除**：保留双方原文，标注存疑，不替用户判定真伪。
- 矛盾检测分层：先用低成本规则扫描（否定表述、明显极性冲突），语义层面的漂移检测依赖 §5.4 的向量能力。

### 5.3 ERO 图谱

**发布门槛**：用户已积累足量页面，且「反链不足以发现跨页关系」成为可观察的真实痛点。在此之前不启动。

最小模型为实体、观察、关系三者：

- **实体**：具名事物（人、项目、工具、概念），含名称与类型。
- **观察**：附着于实体的原子事实，可独立增删；过期时以退役标记保留演变轨迹，不物理删除。
- **关系**：有向、带类型、带强度的边，采用主动语态命名；重复出现同一关系时以概率并集强化既有边而非新建，这是图谱自动去重的关键。

此阶段**不引入**完整双时态建模、实体模糊合并与多跳问答。

图谱可视化不与 ERO 绑定发布：先让检索、实体详情与反链产生价值，确有需要时再以受限子图形式呈现（限制节点数，复用既有图形依赖）。

### 5.4 向量检索

**发布门槛**：先建立中文与中英混合的金标集，证明全文检索的召回确实不足，再引入模型。不以「向量更先进」为理由启动。

- 引入本地嵌入运行时与多语言小模型（须支持中文）；已核实 MemPalace 的向量能力不可复用。
- 向量层**可关闭**；关闭或失败时退化为全文检索，并在界面显式提示，**无静默降级**。
- 融合策略采用倒数排名融合，将全文检索与向量检索的排名合并。
- 实施路径：从少量页面的线性相似度计算开始，证明存在性能瓶颈后再引入向量索引扩展。
- 新增向量派生表并纳入 §3.2 的派生索引重建骨架。

**不做跨域全局混合检索**（Wiki、记忆、MemPalace 三域合并检索）：三域的语义、归属与可解释性不同，混列结果会先损失可控性。

### 5.5 遗忘曲线排序

P0 已记录使用次数与末次使用时间，P2 将其纳入排序：重要度与新近度加权，衰减速率随使用次数增长（用得越多衰减越慢）。同一公式可同时服务检索排序、相关页面推荐与 §4.3 的清理建议。

### 5.6 P2 发布门槛汇总

| 能力 | 门槛 |
|---|---|
| 综述合成 | 用户已有足量分类资料，且提出跨资料总结需求 |
| 页面状态与矛盾提示 | 出现真实的知识过期与冲突场景 |
| ERO 图谱 | 反链不足以支撑关系导航，且可被观察到 |
| 向量检索 | 金标集证明全文召回不足，且接受模型下载与存储成本 |

## 6. 系统边界

| 系统 | 职责 | 与 Wiki 的关系 |
|---|---|---|
| `agent_memories` | AI 对话中抽取的用户画像与工作上下文 | 独立。不自动互相回写；Wiki 存「知识」，记忆存「画像与短上下文」 |
| `user-memory.md` | 个人记忆的可读载体 | 独立 |
| 上传目录与产物目录 | 原始文件与执行输出的落盘位置 | 保持原流程不变；Wiki 仅在其完成点挂摄入钩子，**只引用路径不搬移文件** |
| MemPalace 插件 | 插件形态的向量记忆 | 不依赖、不调用、不共享向量索引；已核实其向量能力不可复用 |

这条边界的意义在于避免把「用户主动维护的知识」与「模型应何时注入的短期记忆」混库。未来若需打通，应以用户主动操作的形式（从某页生成记忆候选、在对话中引用某页），不做自动闭环，直到交互形态与质量评估都确定。

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| FTS5 在两条 SQLite 路径行为不一致（项目无先例） | 检索能力不稳定 | bigram 方案已规避版本特性依赖；P0 以单测覆盖双路径行为一致性 |
| bigram 检索精度不足 | 检索质量不达标 | 以中文与中英混合样本实测；分词逻辑变更只需重建派生索引，无需迁移主表 |
| vision 槽未配置 | 图片不可检索 | 降级为元数据 + 来源上下文，UI 明示，配置后可重新提取 |
| 全自动分类准确率不足 | 页面分类混乱，用户失去信任 | 落点规则将 AI 自由度压到最小；运行日志可追溯；页面路径可改 |
| LLM 成本超预期 | 用户体验受损 | 批量合并调用；分类提示词保持精简；串行队列限流 |
| 音视频不可检索 | 用户误以为资料未入库 | UI 明示限制；来源上下文兜底；转录能力可后续加入 |
| 对话提取产生噪音 | Wiki 塞满低价值页 | 仅显式信号触发；落点限于 `inbox/` 待用户处理 |
| 自动摄入使库快速膨胀 | 检索精度与浏览体验下降 | P1 清理能力；归档默认排除检索 |
