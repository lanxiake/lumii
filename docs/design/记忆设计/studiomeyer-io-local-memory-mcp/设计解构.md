# local-memory-mcp 设计解构与 Lumii 参考建议

## 1. 结论

`studiomeyer-io/local-memory-mcp` 是一个 MIT 许可、单用户、本地 SQLite 的 MCP 记忆服务。它的特点是将会话、学习、决策、实体观察和关系拆为不同表，再通过一个统一 FTS5 索引和可选向量表进行跨类型检索。

对 Lumii 最有价值的参考有五点：**结构化决策记录、原子实体观察、可回退的混合检索、事实 supersede 的 tombstone 语义，以及无 LLM 的运营/反思指标**。相较于 `mcp-memory-graph`，它更克制、依赖更少，尤其适合 Lumii 先完成 P0/P1；但其 MCP 工具集合、单用户假设和自动索引触发器都不能直接照搬。

## 2. 调研边界与证据

分析基于 `main` 的提交 `2d3600634c0f95b13fd956013d9794c4187af014`（2026-08-21）。源码位置与许可证见 [`源码/README.md`](源码/README.md)。

“已验证”来自源码或测试；“建议”是基于 Lumii 当前架构的推导，不代表已实现功能。注意项目文档使用“bi-temporal”一词，但其白皮书明确实现的是**仅有效时间可查询**：`created_at` 只被保留，未作为独立事务时间轴查询。

## 3. 架构与数据流

```text
会话 / learning / decision / entity observation
                    |
                    +--> 业务表 -> FTS5 触发器 -> search_fts
                    |
                    +--> 可选本地 embedding -> sqlite-vec embeddings

查询
  |
  +--> BM25/FTS5 -----------------+
  +--> cosine/sqlite-vec（可关闭）+--> RRF(k=60) -> 轻量排序增强 -> 结果

事实演变
  |
  +--> 无 LLM 矛盾候选扫描 -> 人/客户端确认 -> valid_to tombstone
```

### 3.1 领域数据模型

**已验证。** `src/db/schema.sql` 定义：

- `sessions`：会话时间、项目、摘要和任务；
- `learnings`：十种类别、内容、项目、标签、置信度、使用次数、归档/生命周期、语义或情节类型；
- `decisions`：标题、决定、理由、备选项、来源、置信度和验证状态；
- `entities`、`entity_observations`、`entity_relations`：标准 ERO 风格的实体、原子事实和有向关系；
- `search_fts`：将 learning、decision、entity、observation 统一为 `content_id + content_type + title + body`；
- `meta`：schema 元数据。

`entity_observations` 使用半开有效期 `[valid_from, valid_to)`。`entity_open({ asOf })` 的下界包含、上界排除，相关测试覆盖了两个边界。`memory_observation_supersede` 不删除旧行，只设置 `valid_to`；指定替代事实时，终止时间取新事实的 `valid_from`，同实体和自替代都被拒绝，重复调用幂等。

**对 Lumii 的建议。**

- P0 的 Wiki 页面保留 `raw/wiki/note` 和用户可编辑 Markdown，不应先拆成全部 ERO 表。
- P1 可引入结构化 `decision` 记录，因为“结论 + 理由 + alternatives”比普通文本记忆更可解释。
- P2 再创建 `wiki_entities`、`wiki_observations` 和 `wiki_relations`。时间字段应只属于会变化的观察事实，不应强加到每个文档页。
- 对事实采用半开区间并在 API/测试中固定边界，可避免“valid_to 当日是否有效”的歧义。

### 3.2 FTS5 和索引一致性

**已验证。** `search_fts` 使用 `unicode61 remove_diacritics 2` tokenizer。对 learnings、decisions、observations、entities 定义了 insert/update/delete 触发器：写业务表即可维护索引，更新先删旧 FTS 行再写新行。实时检索明确排除 `archived = 1` 的 learning 和 `valid_to IS NOT NULL` 的 observation。

**对 Lumii 的建议。** 统一 FTS 表是跨类型检索的实用模式，但 Lumii 的 Wiki 索引应可完整重建，不能只依赖触发器维持正确性。推荐：业务表或 Markdown 是真相源；提供显式 `rebuildWikiSearchIndex()`；写入路径可使用事务内增量更新；损坏恢复和导入后统一走重建。FTS tokenizer 必须对中文样本实测，不能从英语/德语项目直接推断效果。

### 3.3 本地 embedding 与混合检索

**已验证。** `src/db/migrations/002_vector.sql` 增加 sqlite-vec 的 384 维 `embeddings` 表；`src/lib/embed.ts` 以 Transformers.js 懒加载 `Xenova/multilingual-e5-small`，默认 q8，支持缓存目录、模型和量化类型覆盖。`MEMORY_EMBED_DISABLED=1` 会完全关闭该层。

`src/tools/search.ts` 提供 `fts`、`vector`、`hybrid` 三种模式：

1. FTS5 通过 BM25 取得关键词候选；
2. sqlite-vec 通过余弦距离取得语义候选；
3. hybrid 用 RRF，`score = Σ 1 / (60 + rank)` 融合；
4. 融合后应用不超过 40% 的保守乘数：时效指数衰减（默认半衰期 30 天）、`usage / (usage + 5)` 与 importance；
5. 向量扩展未加载或 query embedding 失败时，返回明确 notice 并回退 FTS，而非让搜索失败。

向量路径会过取候选后再按类型、项目、标签、归档和 supersede 状态过滤，原因是 sqlite-vec KNN 查询不能同时承载所有辅助列过滤条件。

**对 Lumii 的建议。** P0 只做 FTS；P3 才评估该模型或 MemPalace 可复用能力。届时保留 `fts/vector/hybrid` 诊断模式和显式降级状态，使用户与调试工具能区分“无结果”和“向量不可用”。对于按 `agentId/userId/path/status` 的过滤，要在候选过取后验证召回损失，并设置上限，避免大量不相关向量挤出有效结果。

### 3.4 矛盾、去重和生命周期

**已验证。** learning 的去重是确定性的完全相同内容门控：命中时增加使用次数而不是新增。`src/tools/contradictions.ts` 只扫描仍有效的 observations，通过 `vec_distance_cosine` 找出高相似度对；只有“否定词 XOR”或置信度漂移超过阈值才报告候选。它覆盖英语、德语、西班牙语等若干语种的否定正则，但不做自动判断或修改。supersede 是独立的显式工具。

`memory_learn_archive` 是软删除，search/recall/去重均排除已归档行。`memory_learn_update` 在内容变化时采用“事务外计算 embedding，事务内写业务数据与向量”的顺序；若向量写入失败，清除旧向量，防止语义索引继续指向过时文本。

**对 Lumii 的建议。**

- 对用户资料和 Wiki，使用 `active/outdated/disputed/archived` 状态，不做无提示自动覆盖。
- P1 先采用“发现并标记，用户确认后 supersede”；不要将多语言否定词正则当作中文矛盾检测方案。
- 向量索引写入必须与内容版本绑定：新向量未能提交时，旧向量应不可再被检索。
- `archive` 用于内容生命周期，`supersede` 只用于被新事实替代，两个动作不能混为一谈。

### 3.5 反思与产品可见性

**已验证。** `src/tools/reflect.ts` 不调用 LLM，而是按 SQL 聚合近期最常用 learning、从未召回的陈旧 learning、近期活跃实体和未验证的旧 decision，同时输出结构化字段和 Markdown 摘要。它是按需调用，不含常驻后台进程。

**对 Lumii 的建议。** 可将这种“先记录指标，再生成操作候选”的方法用于 P1 的 Wiki 管理页：显示待确认争议、长期未复查的资料、未解决的决策和零结果搜索词。不要把“少用”直接视为删除理由；每个候选应有来源、最后访问时间和可撤销操作。

## 4. 可迁移性决策

| 技术/模式 | Lumii 阶段 | 结论 | 说明 |
| --- | --- | --- |
| Session / learning / decision 分域 | P1 | 部分采用 | `decision` 可独立建模；不要复制 MCP 工具模型。 |
| 统一 FTS5 跨类型索引 | P0 | 采用 | 支撑 Wiki、raw 资料和笔记检索；需提供可重建路径。 |
| FTS 触发器 | P0 | 谨慎采用 | 适合增量一致性，但必须配索引重建与导入恢复。 |
| ERO + 关系权重 | P2 | 有条件采用 | 先由 wikilink/backlinks 验证关系需求。 |
| 有效时间 + tombstone supersede | P2 | 采用 | 只用于 observation；先以用户确认触发。 |
| LLM-free 矛盾候选 | P2 | 有条件采用 | 需要中文规则和真实误报率验证。 |
| multilingual-e5-small + sqlite-vec + RRF | P3 | 有条件采用 | 需验证中文质量、Windows 首次下载、性能和包体。 |
| 时效/使用/importance 轻量重排 | P1/P3 | 采用 | P1 可用于纯标量排序，P3 再叠加到 RRF。 |
| FTS-only 明确降级 | P0/P3 | 采用 | 应作为离线和模型失败时的稳定基础。 |
| MCP stdio、客户端 hooks、MCPB 包 | 不纳入 | 不采用 | Lumii 应通过现有 Electron IPC 提供能力。 |
| 单用户、无权限模型 | 不纳入 | 不采用 | Lumii 仍需遵守用户/Agent 数据边界。 |

## 5. 对 Lumii 的实施启示

1. **先建立可重建的搜索索引。** 将页面/原始资料写入和 FTS 索引更新定义为一个清晰的 repository 事务，并提供全量重建。
2. **再为事实建立时间语义。** `wiki_observations` 采用 `[valid_from, valid_to)` 和 `supersedes_id`；历史查询与实时查询必须走不同 predicate。
3. **将自动化保持在候选层。** 重复、冲突、陈旧内容和缺失知识只能生成建议或状态，用户资料绝不被隐式替换。
4. **把向量视为可拔插加速层。** 搜索产品必须在没有模型、没有网络或扩展加载失败时可用；SQLite/FTS 是基础服务等级。
5. **为每个排名策略建立 Lumii 自有测试集。** 至少覆盖中文、混合语言、路径过滤、过期事实、同义表达、错误召回和无结果查询。

## 6. 约束与风险

- **时间模型命名。** 该项目的可查询语义是 valid-time，不是完整的 valid-time × transaction-time；Lumii 文档不得把两者混称。
- **向量过滤。** sqlite-vec 的 KNN 辅助列限制迫使后过滤和候选过取；数据隔离或多条件筛选场景必须测试召回损失。
- **中文矛盾检测。** 上游的否定正则没有覆盖中文语义、反问、程度词或上下文，不能直接复用为规则。
- **索引真相源。** 触发器保证正常写入的一致性，但不能代替损坏恢复、批量导入和 schema 迁移中的显式重建。
- **范围控制。** 25 个 MCP 工具是外部集成接口，不是 Lumii 记忆 UI 的需求清单；优先实现页面、编辑、搜索、来源和状态闭环。

## 7. 后续待验证项

1. Lumii 的 node:sqlite/better-sqlite3 运行时在目标 Windows 构建中对 FTS5、JSON1 的具体可用性和 tokenizer 效果。
2. 文档/资料导入时的原始内容、chunk、页面和 FTS 行之间应如何定义原子性与失败恢复。
3. `wiki_observations` 是否要支持手动编辑历史，或统一采用“创建新 observation + supersede 旧 observation”的不可变策略。
4. P3 选择 embedding 运行时前，完成中文及中英混合检索的金标集、离线回退与首启性能测量。
