# mcp-memory-graph 设计解构与 Lumii 参考建议

## 1. 结论

`YonasValentin/mcp-memory-graph` 是一个面向 MCP 客户端的本地优先记忆服务。其最值得 Lumii 借鉴的不是 51 个 MCP 工具，而是四项可拆开的基础能力：

1. 单库 SQLite 中并置业务记录、FTS5 和向量索引；
2. 写入前识别重复、疑似替代与矛盾，并把“是否替代旧事实”做成显式策略；
3. 以向量、关键词和图谱排序作为可独立启用的检索层；
4. 把访问、搜索空结果和版本/时间状态保存为数据，供后续整理和审计使用。

Lumii 当前已有 `agent_memories`、`AgentMemoryRepo`、SQLite 迁移及热记忆排序。这意味着 P0 应聚焦用户可见的 Wiki/资料库和 FTS5 检索；图谱、向量、NLI 与自动整理均应是后续可选层，而非把参考项目的服务端/MCP 编排整体移植进来。

## 2. 调研边界与证据

本结论基于 `main` 的提交 `6dd8aea43a022f380b9764cf5e468171360802f1`（2026-07-06）。源码位置和许可证见 [`源码/README.md`](源码/README.md)。

下文“已验证”均可在该源码快照中定位；“建议”是针对 Lumii 的设计推导，尚非已实现承诺。

## 3. 系统分层

```text
写入请求 / 导入 / 会话学习
        |
        v
输入规范化 -> embedding -> 近邻候选 -> 写入门控 -> 单事务持久化
                                             |              |
                                             |              +-> memories / 版本 / FTS / vec / 访问与冲突记录
                                             v
                                      可选 NLI 矛盾检测

检索请求
   |
   +-> FTS5 (BM25) ---------+
   +-> sqlite-vec (语义近邻) +-> RRF -> importance/时效调整 -> 可选 rerank
   +-> 图谱 PPR（可选） -----+
```

### 3.1 存储与索引

**已验证。** `src/db/schema.ts` 的主表是 `memories`，携带内容、scope/namespace、文档分类、标签、来源、访问次数、重要度、置信度、失效时间、版本与来源证明。它使用：

- `memories_fts`：对标题、正文、标签、作者、部门创建 FTS5 虚拟表；
- `memories_vec`：以 `vec0(embedding float[dimensions], scope, namespace)` 保存嵌入；默认维度 384；
- `memory_versions`：保存更新前版本；
- `memory_access_log` 和 `search_log`：记录被访问内容及零结果查询；
- `entities`、`memory_entities`、`memory_links`：实体、实体-记忆归属和记忆链接；
- `schema_meta`：保存 schema 版本、嵌入维度和模型身份，拒绝不匹配的既有库。

同一逻辑保留显式迁移版本，当前上游为 V19。建库时先校验既有表的最低列集，再按版本迁移，避免把不完整旧库错误标记为最新。

**对 Lumii 的建议。** 复用 `LocalDatabase` 的迁移机制，在独立的 Wiki 表域落地 `wiki_pages` 和 `wiki_pages_fts`；不要改造 `agent_memories` 为万能文档表。索引必须由原始 Markdown 或页面数据重建，而不是成为唯一真相。向量表应等 P3 再引入，届时将模型 ID、维度、索引版本写入元数据，避免模型升级导致混合向量静默失真。

### 3.2 检索

**已验证。** `src/search/hybrid.ts` 分别运行向量与 FTS5 查询，并使用 RRF 合并。常量 `k=60`；若启用图谱，则将 Personalized PageRank 排名作为第三个 RRF 列表。RRF 后再乘以 `1 + importance * 0.5`，并按过期、有效时间、分区和访问级别过滤。结果给出 vector/keyword/hybrid/graph 的匹配类型以及 `high`、`medium`、`low` 置信度。

可选的 `CrossEncoderReranker` 使用本地交叉编码器重排候选。上游公开基准显示：10,000 向量时纯混合检索 p95 约 9.1ms；重排增加约 200ms。该结论不能直接外推到 Lumii 的 Windows 硬件、中文资料或新的数据模型。

**对 Lumii 的建议。**

- P0：只实现 FTS5 + `bm25()` 排序、路径/状态/标签过滤和 backlinks；这是零新模型依赖且面向用户可见的闭环。
- P3：在嵌入层可用且中文测集达标后，再接入向量候选和 RRF。必须支持关闭向量层，确保模型首次下载失败、离线或硬件性能不足时仍可用。
- 重排不是默认前置需求。其固定延迟会直接影响桌面交互；只有在 Lumii 自己的查询集证明收益稳定时才启用。

### 3.3 写入门控与矛盾

**已验证。** 写入主流程位于 `src/tools/store.ts`：先生成嵌入并在同一 `scope + namespace` 中寻找近邻，然后由 `src/graph/conflict-resolver.ts` 根据词项重叠和向量候选产生 `duplicate`、`superseded`、`contradicted`。`src/graph/write-gate.ts` 将调用者策略映射为：

| `on_conflict` | 处理 |
| --- | --- |
| `add` | 新增，同时记录冲突，不静默使旧事实失效 |
| `update` | 对可合并替代项更新现有记录 |
| `supersede` | 新增后将已匹配的替代/矛盾旧事实标记失效 |

可选 NLI 采用本地 `Xenova/nli-deberta-v3-xsmall`。源码要求正反两个方向都以足够分数判为矛盾，才认定为冲突；且只有显式 `supersede` 时才退役旧事实。模型加载失败时，写入继续，只跳过本次 NLI 检查。

**对 Lumii 的建议。** 把“标记而非删除”作为 P1 的产品语义：`active`、`outdated`、`disputed` 和可追溯 source。第一版不应自动让 AI 覆盖用户资料；编译流程只能创建候选或标记争议，用户确认后才 supersede。NLI 模型约有冷启动、下载和误判成本，不适合 MVP。

### 3.4 时间、版本与遗忘

**已验证。** 主记录和 `memory_links` 有 `valid_from`、`valid_to`、`tx_expired`；当前查询过滤已经失效的事实，部分图谱查询可按历史时刻检索。旧内容不被物理覆盖：`memory_versions` 记录版本，supersede 则写有效期终点。项目也记录 `access_count`、`last_accessed_at`、`stability` 与 `importance_score`，并提供 consolidate/dream-cycle 类型的整理入口。

**对 Lumii 的建议。** P0 保留 `created_at`、`updated_at`、`last_used`、`use_count`；P1 增加页面状态和编译日志；P2 才需要 observation 的 `valid_from/valid_to`。不能把“低访问”直接等同于可删除，尤其是用户上传资料和手工笔记，应默认归档或降权而非清除。

### 3.5 图谱

**已验证。** 图谱分两层：`memory_links` 表直接表达记忆间链接，包含 relation、来源类型、置信度和证据计数；实体表将名称归一化并按 namespace 唯一。`src/graph/graph-query.ts` 对相邻节点按置信度限宽遍历，避免高连接度节点吞没上下文。`src/graph/pagerank.ts` 将实体关系的 `evidence_count * strength` 作为边权，执行 Personalized PageRank，再映射回有效记忆。

**对 Lumii 的建议。** MVP 只做 Markdown `[[wikilinks]]` 和反链；这是可解释、可编辑、可导出的关系层。P2 再引入 ERO（Entity/Relation/Observation）表，图谱检索必须是 `useGraph` 开关，而不是替代 FTS 搜索。可视化放在有足够实体和边之后，否则会制造没有检索价值的装饰界面。

## 4. 可迁移性决策

| 技术/模式 | Lumii 阶段 | 结论 | 原因 |
| --- | --- | --- |
| SQLite 迁移 + 元数据校验 | P0 | 采用 | 已有 `LocalDatabase`，只需扩展迁移与备份覆盖范围。 |
| FTS5 与可重建索引 | P0 | 采用 | 零模型依赖，适合 Markdown/Wiki 搜索。 |
| `[[wikilinks]]` + backlinks | P0 | 采用 | 用户可见、可解释，是最低成本关系模型。 |
| 写入冲突状态与审计日志 | P1 | 采用但人审优先 | 防止 AI 静默覆写原始资料。 |
| LLM 编译管线 | P1 | 采用但显式触发 | 使用 triage/compile/cascade/log，不复制 MCP 工具接口。 |
| 双时态 Observation | P2 | 有条件采用 | 仅在事实演变和历史查询成为真实需求时引入。 |
| ERO 与图谱检索 | P2 | 有条件采用 | 必须先证明 Wiki 链接与 FTS 无法覆盖的多跳场景。 |
| 本地 embedding + sqlite-vec + RRF | P3 | 有条件采用 | 需先确认 MemPalace 复用性、中文效果、包体和 Windows 性能。 |
| 交叉编码重排 / NLI | P3 或不做 | 暂缓 | 模型体积、冷启动和延迟明显，且会放大误判风险。 |
| MCP 工具、Claude hooks、Web 服务、团队 RBAC | 不纳入 | 不采用 | 与 Lumii 的 Electron 主进程/IPC 边界和单用户产品方向不匹配。 |

## 5. 建议的 Lumii 演进顺序

1. **P0，用户可见闭环**：`wiki_pages`/FTS5、CRUD、目录树、Markdown 编辑、wikilink 解析、backlinks、导出和 IPC 三层闭环。
2. **P1，可信编译**：原始资料不可变引用、手动触发的 triage/compile/cascade、`outdated`/`disputed`、可查看的 compile log。
3. **P2，事实和关系**：按需要增加实体、观察、关系与时间字段；先提供搜索结果中的关系解释，再评估图谱视图。
4. **P3，智能检索**：以 Lumii 自有中文查询集验证 embedding、RRF、候选重排和衰减策略；记录延迟、离线失败回退和索引重建行为。

## 6. 落地约束与风险

- **许可证**：该项目为 PolyForm Noncommercial，不应复制实现、模型组合或将其作为 Lumii 商业发行的直接依赖；本文件只提取思想和可公开验证的架构模式。
- **SQLite 向量规模**：上游明确 sqlite-vec 当前近邻查询与写入近邻扫描含 O(n) 路径。个人资料库可接受，但不可把其基准当作百万级数据承诺。
- **中文与本地模型**：上游默认 MiniLM、MS MARCO 重排和 NLI 的效果不代表中文。必须建立 Lumii 的中文/中英混合测试集再作决策。
- **数据所有权**：Lumii 的 raw 资料、用户笔记和 AI 编译页必须可区分、可回溯；AI 不得把索引或推断结果写回原文。
- **IPC 边界**：后续新增 Wiki 能力须同步定义 `agent-runtime` repo、Electron main handler、preload `ElectronAPI` 和 renderer 调用方，不能把数据库直接暴露给 renderer。

## 7. 后续需验证的问题

1. Lumii 当前的 SQLite 构建是否已包含可直接启用 FTS5 的运行时能力，以及索引重建和备份策略是否覆盖新表。
2. MemPalace 的 embedding 能力能否从插件边界稳定复用；若不能，P3 的模型、缓存位置、下载提示和离线回退如何设计。
3. Wiki Markdown 的真实来源应使用文件系统、SQLite，还是“Markdown 真相源 + SQLite 索引”的混合形态；该选择决定导出/同步/损坏恢复的边界。
4. 哪些写入可自动编译，哪些必须用户确认；这一策略应在 P1 前通过产品交互设计确定。
