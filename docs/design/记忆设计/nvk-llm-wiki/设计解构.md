# nvk/llm-wiki 设计解构与 Lumii 参考建议

## 1. 结论

`nvk/llm-wiki` 将知识库实现为 Git/Obsidian 兼容的 Markdown 文件树，并将 AI 的写入过程约束为“采集原始资料 -> 编译派生知识 -> 更新目录和日志 -> lint/audit”的受治理工作流。它最值得借鉴的是**可读的原始证据、显式索引和可自动验证的文件约定**，不是其围绕 Claude、Codex、OpenCode 的大量技能与命令包装。

## 2. 调研边界与证据

本分析基于上游提交 `d78e119e3f63368730b2893317a7d773a86f0364`，MIT 许可证和检出位置见[源码/README.md](源码/README.md)。下文“已验证”均来自该快照中的实现说明、fixture 或测试；“对 Lumii 的建议”是设计推导，并非现有功能。

## 3. 架构与数据流

```text
URL/笔记/研究输出
  -> raw/{articles,papers,repos,notes,data}/ Markdown 原始资料
  -> LLM 编译（概念、主题、参考、论题）
  -> wiki/ 派生知识页 + [[链接]]
  -> _index.md、log.md、inventory/、datasets/
  -> 结构校验、链接/来源校验、审计与只读查询
```

### 3.1 文件即真相，目录即显式导航

**已验证：**`tests/test-structure.sh` 对 golden wiki 强制要求根 `_index.md`、`config.md`、`schema.md`，以及 `raw/`、`wiki/`、`inventory/` 等每个受管理目录的 `_index.md`。原始资料按 articles/papers/repos/notes/data 分类；编译后的页按 concepts/topics/references/theses 分类。测试同时检查 frontmatter 的必填字段、允许枚举、路径与类型的一致性、索引条目和实际文件的双向一致性、正文链接可解析性及来源引用存在性。

**对 Lumii 的建议：**P0 采用“Markdown 页面/原始附件为真相，SQLite 仅为可重建索引”的边界。目录导航不应依赖模型记忆；可维护 `wiki_pages` 物化树或生成目录页，但必须提供全量重建。把页面类型、状态、来源、创建/更新时间作为可验证 frontmatter/字段，而非自由文本提示。

### 3.2 原始资料与派生知识分层

**已验证：**该项目分别保存 `raw/` 来源、`wiki/` 编译页和 `inventory/` 操作记录。fixture 与结构测试要求 raw 页至少具备 `title/source/type/ingested/tags/summary`，wiki 页具备 `title/category/tags/summary/confidence`；inventory 又有 `kind/status/priority` 等独立枚举。工作流文档将 ingest、compile、retract、audit 拆成不同命令语义，且会检查被撤回来源标记和悬空 source reference。

**对 Lumii 的建议：**保留 `source`、`note/wiki page`、`AI 编译候选` 三种不同所有权。AI 可以从来源产出候选页和引用清单，但不得静默覆盖用户手写页；撤回、过时和争议应成为显式状态及审计记录。P0 只需 source/page/link，P1 再引入 compile run 与候选审批。

### 3.3 链接、索引与质量门控

**已验证：**项目使用 Markdown 及链接表达关系，并把 `_index.md` 视为可核验的导航产物。`test-structure.sh` 以缺索引、过期索引、断链、悬空来源、非法 frontmatter 等缺陷 fixture 来验证 lint 能力；还检查 retracted-source 标记不得残留。可见其可靠性策略是“写入后验证并修复”，而非靠一次 LLM 输出正确。

**对 Lumii 的建议：**解析 `[[wikilink]]` 到独立的 `wiki_links` 关系表，生成 backlinks；页面改动、导入和恢复后统一执行链接/索引校验。链接必须支持唯一、稳定的页标识或完整路径，不能像纯 stem 匹配那样允许歧义。质量检查应返回可定位错误，不能由 renderer 直接碰数据库自行猜测。

### 3.4 多运行时封装

**已验证：**README 将 Claude 插件行为层作为源头，再用同步脚本生成 Codex/OpenCode 包装；`tests/test-codex-sync.sh`、`test-opencode-sync.sh` 检查生成树漂移。查询精简配置是只读，完整配置才允许 research/ingest/compile 等写入；会话捕获另有 hook 和测试。

**对 Lumii 的建议：**可借鉴“读路径与写路径权限不同”的产品语义：聊天中的检索可默认只读，写 Wiki 或应用编译建议需要明确动作和可见预览。但不应移植插件生成、agent hook 或外部目录权限协议；Lumii 应用现有 Electron main/preload/renderer IPC 边界。

## 4. 可迁移性决策

| 模式 | Lumii 阶段 | 结论 |
| --- | --- | --- |
| Markdown/附件为真相，索引可重建 | P0 | 采用 |
| 强约束元数据、目录/链接/来源 lint | P0 | 采用 |
| `[[wikilink]]` 与 backlinks | P0 | 采用，使用无歧义页 ID/路径 |
| raw 与编译页分层 | P1 | 采用，编译结果必须可审阅 |
| inventory、审计、撤回传播 | P1 | 条件采用，先做最小状态机 |
| 多 Agent 研究编排、session hook | 不纳入 | 不采用，属于外部客户端工作流 |
| 为每个运行时生成技能包 | 不纳入 | 不采用，和 Electron 产品边界不符 |

## 5. 分阶段落地建议

1. **P0：**页面 CRUD、原始资料引用、类型/状态字段、wikilink/backlink、FTS5 和全量索引重建；为断链、重复 slug、非法状态和删除后的索引建立单测。
2. **P1：**编译任务保存输入来源、输出候选、批准人/时间和替代关系；提供来源失效后可复查的影响清单。
3. **P2：**根据真实使用量评估专题、论题和 inventory 视图，避免过早把目录分类固化成很多页面类型。

## 6. 约束与风险

- `_index.md` 是可读却会重复的数据；若用它作真相而没有重建程序，必然产生漂移。
- Markdown frontmatter 很适合作为导出格式，但 GUI 内编辑仍需结构化校验和冲突处理。
- 上游测试验证的是其协议与 fixture，不代表 Lumii 的中文、Windows 文件系统或并发编辑已被覆盖。
- MIT 允许复用，但本调研仅提取设计；Lumii 应按自身 TypeScript 架构独立实现。
