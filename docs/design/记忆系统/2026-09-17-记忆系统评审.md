## 1. 结论摘要

| 项 | 结论 |
|---|---|
| **主目标** | 把记忆系统的重心从「写得进」挪到「读得到」——补齐 Agent 侧的检索通道与写入纪律，让已沉淀的 229 条可达记忆真正可达、可信、可追溯 |
| **根本判断** | 写入侧已相当完备（规则 + 段落管线 + 主动工具 + 后台源），**断裂点几乎全在读路径**；教程第 2 章的主线判断「不是存得不够多，而是写得不可寻、读了没通道」逐字成立 |
| **技术路线** | 读侧三路合并检索 + 曝光/效用信号分离 + 写入侧 schema 门 + 非破坏失效语义；不引入向量库、不引入 ML 框架、不改 `agent_memories` 的既有列语义 |
| **规模** | P0 五项（约 4.5 人日，含 V47 一个纯加列迁移）；P1 五项（约 6 人日，含 V48 迁移）；P2 三项（宫殿自建不依赖评测集，详见 §4.6.5）。实施计划：[`2026-09-17-记忆系统整改实施计划.md`](../../plans/记忆系统/2026-09-17-记忆系统整改实施计划.md) |
| **最大风险** | 读路径接通后，沉淀已久的低质条目会同时暴露给 Agent 主动检索。**P0-3 的写入 schema 门必须与 P0-1 同批上线**，否则等于把垃圾从"偶尔注入"升级成"随时可查" |
| **明确不做** | 不上向量检索栈（可达集 6.39 万字符、`assistant` 单 Agent 5.98 万字符，正好卡在 Letta「<50k 字符不必上检索栈」判据的边界；且 BM25 已就绪，缺的只是读者）；不启用两套 Learning-to-Rank 代码；不恢复轮数触发的 LLM 提取 |

## 2. 背景与代码事实核查

### 2.1 现状：四层架构与五条管道

代码内显式建模了四层记忆（`memory/memory-architecture.ts:23-65`）：

| 层 | 存储形态 | 类别 | 写入方 | 读取方 |
|---|---|---|---|---|
| 个人记忆 | Markdown `~/.lumii/data/user-memory.md` | `user` / `feedback` | `profile_memory` 工具、提取回调、定时整理 | 每轮全量注入 |
| 场景记忆 | Markdown `<项目>/.lumii/memory.md` 或 `~/.lumii/data/scene-memory/*.md` | 项目约定 / 渠道偏好 | `scene_memory` 工具 | 命中场景时注入 |
| 工作记忆 | SQLite `agent_memories` | `project` / `reference` / `general` | 规则提取、段落管线、`memory_manage`、若干后台源 | 每轮择优注入 6 条 |
| 记忆宫殿 | 外部 MemPalace（Python MCP） | 对话原文 | 段落管线归档 | `memory_search` / `memory_read` |

写入侧共 **5 条活跃管道**（本次核查修正了此前的一处误判）：

| # | 写入管道 | 触发方式 | 状态 |
|---|---|---|---|
| 1 | 规则提取（6 条高置信正则） | 每轮 `onTurnComplete` | ✅ 活跃（`bridge-instance-factory.ts:613`） |
| 2 | 段落总结管线 | **事件驱动**：段关闭即总结 | ✅ 默认开启（`segment-memory-service.ts:54-55`，`MTBOT_SEGMENT_MEMORY !== '0'`） |
| 3 | 模型主动工具 | `memory_manage` / `profile_memory` / `scene_memory` / `news_preference` | ✅ 活跃 |
| 4 | 客户端后台源 | 学习产出、开发转交、定时整理 | ✅ 活跃 |
| 5 | LLM 轮数提取 | `turnCount % extractEvery === 0` | ❌ **已停用**（`agent-instance.ts:442-443`、`:467-468` 注释掉，原文「停用：自动记忆提取方案待重新设计」） |

**这条停用是个正面结论**：教程纪律 #9 要求「写入触发器是事件不是轮数」，代码已经主动做到了这件事。代价是工作记忆的产出**收敛成段落管线单一来源**（见 §5 风险 R3）。

### 2.4 五个根因（按严重度）

#### 2.4.1 读路径断裂：整条 FTS 链路没有 Agent 侧消费者

```
agent_memories (229 条可达)
      │
      ▼
agent_memories_fts  ← bigram 预分词 + BM25（memory-index.ts:25-38）
      │
      ▼
AgentMemoryRepo.search()          memory-repo.ts:569
      │
      ▼
handleAgentMemoriesSearch()       ipc/agent-runtime/agent-commands.ts:135
      │
      ▼
【终点】UI 记忆管理页

【另一条路】Agent 的 memory_search 工具   bridge-tool-registrar-integration.ts:164
      ├─ 优先 MemPalace 语义搜索
      └─ 失败降级 → grep user-memory.md + 场景记忆文件（:214-249，分数硬编码 0.8/0.75）
      → 返回模型
      ✗ 全程不碰 agent_memories
```

后果：**229 条可达工作记忆里，模型每轮只能看见 6 条，想主动找第 7 条没有任何通道。** 这正是教程引用的 UIST'23 论文摘要级结论——检索失败是记忆系统的头号死因。

这是一次典型的「先建存储、后缺读者」：FTS5 + 中文 bigram 分词的工程做得很完整，但只服务了 UI。

#### 2.4.2 曝光冒充效用，形成自激循环

- `use_count` 在**注入时** +1（`memory-repo.ts:186-197`），记录的是「被展示」而非「被使用」。
- `last_used` 同样在注入时刷新，而 `scoreMemory` 的 recencyBonus 吃 `lastUsedAt`（`scorer.ts:40-43`）→ **注入即刷新 = 恒满额加分**。
- `scorer.ts:22-27` 的注释已识别该陷阱，并用 `created_at` 做年龄衰减对冲；但 recencyBonus 这条通道未改，**自激只堵了一半**。

实测：9 条记忆吃掉 54% 的注入席位。抽查其内容，多为「现行有效口径」类记忆（如某话题的最终结论、某个交付的当前状态），**并不全是噪音**——所以这一条要精确表述为：

> **自激是机制层面确定存在的缺陷**（注入刷新 `last_used` → recencyBonus 恒满额 → 更容易再被注入），**但其造成的实际损害未测量**。要测量需要知道"每轮 6 个席位里有多少是与当前话题无关的"，这要靠 P2 的评测集或人工抽查，当前的 `use_count` 数据回答不了。

按教程纪律 #4，可信度应由 UPVOTE/DOWNVOTE 这类**判定信号**管理，而不是曝光量——这一点与损害大小无关，是设计层面的对错。

设计好的判定通道就在仓库里但从未接线：`autonomous/memory-evolution.ts` 的 `recordFeedback()` 会写 `memory_usage_feedback`（含 `was_used_in_response` / `contribution_score`），但全仓无 `new MemoryEvolution(...)` 实例化点，表 0 行。

#### 2.4.3 写入无门：垃圾入库 + 证据链断裂

**（a）垃圾根因已定位到具体正则。** 5 条含 JSON 残片的行全部满足 `importance = 0.95` + `category = general`，精确对应 `memory-extractor.ts:32-41` 的 `RULE_PATTERNS[0]`：

```js
regex: /(?:请?记住|...)\s*[:：]?\s*(.{2,200})/i,
category: "general",
importance: 0.95,
```

该正则按 **200 字符贪婪捕获**，用户输入中的 JSON 模板尾部（`"}]` 之类）被一并吞入。原始形态示意：

```
记住它：……（正文被贪婪吃满 200 字符）……"}]      ← 连同残片入库，且 importance 0.95
```

即：触发词路径本应交给语义判断，现在由一条贪婪正则兜底，且给垃圾发了最高优先级。

**（b）写入侧 schema 校验形同虚设。** `parseCandidatesJson`（`memory-extractor.ts:286-320`）只校验 `content` / `category` 是字符串，其余仅做 `importance` clamp 与 `tags` 过滤。无长度上下限、无完整性校验、无 JSON 残片检测。

**（c）证据链覆盖不足。** 50% 的条目没有任何来源锚点，无法回答「当初为什么这么记」。

#### 2.4.4 幽灵命名空间与幽灵工具

- **幽灵命名空间**：24 行记忆的 `user_id = 'local'`，而读写路径一律用 `local-user`（`bridge-instance-factory.ts:613`、`segment-memory-service.ts`）。这批行既不被注入也不被检索。**写入方已修复**（`planner-landing.ts:40`），24 行全部产生于 2026-09-15 修复前的最后 90 分钟——属于清理脚本漏跑，不是持续泄漏。
- **幽灵工具**：`prompt/guides/memory-guide.ts:34` 与 `memory-architecture.ts:62` 均告知模型「记忆宫殿的写入方式：`memory_store` 工具」，但全仓库无此工具定义、MemPalace MCP 客户端也未暴露。模型被引导去调用一个不存在的工具。

这两条是教程「纪律交给代码而不是交给模型」的镜像问题——**提示词许了愿，代码没兑现**。

#### 2.4.5 失效语义只做了一半

- `deleted_at` 是 V38 为云同步软删除加的墓碑列（`schema.ts:1337-1341`），同步器会传播它（`sync-importer.ts:544-553`），`asset-checkup.ts:249` 也认它——**唯独 `AgentMemoryRepo` 的每条读路径都不认**。
- 但更根本的是：**全仓没有任何一处对 `agent_memories` 写 `deleted_at`**（只有 exporter 导出、importer 合并时传播、asset-checkup 过滤三处读）。本地删除走 `removeById` **硬删**（`memory-repo.ts:639`）。也就是说 V38 的设计意图从未落地：墓碑列存在、传播逻辑存在、过滤逻辑部分存在，**唯独没有生产者**。这是一条完整的、但断在起点的链路。
- 归档无时间戳、无原因，无法回放「当时为什么那么认为」（教程纪律 #5）。

### 2.5 有效性预验证（整改前的三次实测）

本设计的三项关键假设在上线前先做了验证，结论直接改写了方案。

#### 2.5.1 FTS5 通道能否解决真实失败？——能（5/5）

把 09-17 日志里的真实 `memory_search` 查询，按 `AgentMemoryRepo.search()` 的原样逻辑重放到既有 `agent_memories_fts`：

| 查询 | top-1 命中 |
|---|---|
| `未知任务 工具为0 默认分 0.76 观察 评估` | ✅ 正是当时检索不到的那条（`use_count=91`） |
| `ODS 同步 卡点` | ✅ 相关（目标记忆排第 2） |
| `会话评分 效率 反馈 总分 0.44 评分链路` | ✅ |
| `贴标签 原因 排查 检查` | ✅ |
| `效率异常 原因 归类 逐条 标记` | ✅ |

**结论：索引、中文 bigram 分词、BM25 排序三样都已就绪且质量达标，缺的只是接线。** P0-1 因此是低风险高确定性改动，不需要向量、不需要宫殿。

#### 2.5.2 本地向量检索能否显著强于 BM25？——不能（打平）

本机已有 `~/.lumii/models/wiki-embeddings/Xenova/multilingual-e5-small`（134MB，量化 ONNX，`LUMII_WIKI_VECTOR` 默认开启）。直接加载并对 178 条真实记忆做语义改写查询对比：

| 指标 | 实测值 |
|---|---|
| 模型加载 | 912 ms（一次性） |
| 索引 178 条 | 4099 ms（平均 23 ms/条，一次性） |
| 单次查询嵌入 | **4.8 ms** |
| top-1 余弦分布 | 0.873 – 0.893（**区分度极低**） |

4 组语义改写查询的人为对照：e5 与 bigram 重叠**打平 2 组、e5 胜 1 组、e5 负 1 组**。

**结论：本地向量可用、够快，但在本语料上没有碾压 BM25；且余弦绝对值高度聚集，不能靠阈值判别，必须与 BM25 做 RRF 融合。** 这印证了教程 §4.3 的分治判断——不是"谁赢"，而是按查询类型分工。详见 §4.6。

#### 2.5.3 `archiveOldProjectSnapshots` 的取代检测器在工作吗？——没在工作

`manager.ts:233-253` 依据 `extractProjectTheme()`（`manager.ts:463-482`）识别同主题快照并归档旧条目，这是全系统唯一的"新事实取代旧事实"机制。用真实数据实测：

| 指标 | 实测值 |
|---|---|
| `project` 类记忆 | 72 条 |
| 主题识别成功 | **13 条（18%）** |
| 识别出的重复主题（≥2 条同主题） | **0 组** |
| 归零原因 | 检测器要求 `项目：XXX` 格式，真实内容是 `XXX：项目当前状态为…`——**方向反了** |

实测样例（同属「当前程序使用指南」主题，检测器一条未识别）：

```
当前程序使用指南任务：用户要求为当前程序编写一份 Markdown 使用指南…
当前程序使用指南新增任务：根据上述使用指南文档，使用录屏功能录制一个视频教程…
当前程序使用指南文档图片渲染问题：部分图片可展示，chat 渲染正常…
```

**结论：这是 251 条记忆 0 归档的直接原因，也是 §4.4「加 `superseded_at` 字段」必须附条件的原因——检测器不修，字段就是死字段（违反教程纪律 #10）。** 更深一层的教训：内容格式由模型自由生成，而检测器是硬编码正则，两者必然脱节。正确解法是把解释工作**搬到写路径**（写入时产出结构化键），而不是在读路径堆正则——这正是教程 §2.2 引 Schema-Grounded Memory「less like search, more like a system of record」的落点。

## 3. 方案对比与选型

### 3.1 读路径如何接通

| 方案 | 做法 | 优点 | 缺点 | 选择 |
|---|---|---|---|---|
| **A. 三路合并 + provider 字段** | `memory_search` 同时查 `agent_memories`(FTS5) / MemPalace / Markdown 文件，结果带 `provider` | 改动最小（复用现成 `MemoryManager.searchMemories`）；三条通道优势互补；对模型透明 | 需统一打分口径（BM25 与相似度量纲不同） | ✅ **采用** |
| B. 用 SQLite FTS5 取代 MemPalace | 全部检索走 BM25 | 去掉外部 Python 依赖 | 丧失语义召回；原文归档仍需宫殿；与既有 `memory_read` 链路冲突 | ✗ |
| C. 只加 `work-memory` provider | 在现有 MemPalace 分支后再追加一路 | 改动最小 | 模型无法按来源选择；排序语义含糊 | ✗ |

**选 A 的理由**：FTS5 索引与中文 bigram 分词已经写好且经过实测（`memory-index.ts:1-14` 记录了 unicode61 不支持 2 字中文词的验证过程），**接通成本接近零**；不接通才是浪费。

### 3.2 个人记忆的存储形态

| 方案 | 做法 | 优点 | 缺点 | 选择 |
|---|---|---|---|---|
| **A. 迁入 SQLite 条目化** | `user`/`feedback` 类落 `agent_memories`（表结构已支持），Markdown 降级为**派生视图** | 一次到位满足纪律 #1/#2/#3/#5；条目级状态与时间戳天然可得；与工作记忆共用检索栈 | 迁移成本最高；需处理 34 行存量与 `.bak` 语义 | ⏸ **P1 目标形态** |
| B. 保留 Markdown 但条目化 | 保持文件，但每条带 `id`/时间戳，harness 独占结构字段，模型只能改 `text` | 人可读可编辑的优点保留；迁移成本中等 | 仍是 Markdown（纪律 #1 反对）；并发写与去重仍需自建 | ✅ **P1 过渡形态** |
| C. 维持现状 | 继续 LLM 全量重写 | 零成本 | 纪律 #1/#3/#5 全部不满足；`.bak` 只有一层，丢失不可回放 | ✗ |

**分两步走的理由**：B 能立刻满足「模型只能改状态字段」这条最关键的纪律（教程把它列为「把纪律交给代码」的三个范例之一），而 A 的价值主要在统一检索栈——那是 P2 的事。先 B 后 A，避免一次性大改。

### 3.3 效用信号如何采集

| 方案 | 做法 | 优点 | 缺点 | 选择 |
|---|---|---|---|---|
| **A. 接线既有 `memory_usage_feedback`** | 注入快照已持有本轮记忆（`memory-integration.ts:65`），`agent_end` 时写一条反馈 | 表与代码都现成；一次同时兑现纪律 #4 与 #10；为 Learning-to-Rank 供数 | 需要设计 `contribution_score` 的廉价算法 | ✅ **采用** |
| B. 新增 upvote/downvote 列 | `agent_memories` 加两列计数 | 简单直观 | 与既有表重复；仍需算法判定"什么算一票" | ✗ |
| C. 不做 | 继续用 `use_count` | 零成本 | 自激循环不解决 | ✗ |

**A 的 `contribution_score` 采用廉价代理**：回复文本与记忆 `content` 的 bigram 重叠度（复用 `segmentation.ts:53` 的 `overlapCoefficient`），分档 0 / 0.5 / 1 三值。**先让表有数据，再谈学习排序**——教程 §五.1 反模式「上来就上更复杂的机制」在效用信号上的翻版：没有数据的排序模型只会学出噪音。

## 4. 核心设计

### 4.1 读路径三路合并

```
memory_search(query)
  ├─ 通道 1: work-memory     AgentMemoryRepo.search()          provider="work-memory"
  │                          FTS5 + bm25()，中文 bigram
  ├─ 通道 2: palace          MemPalace 语义搜索                 provider="mempalace"
  │                          （不可用时跳过，不降级为文件 grep）
  └─ 通道 3: profile/scene   user-memory.md + 场景记忆文件行匹配  provider="profile"/"scene:<name>"
       │
       ▼
  合并 → 按通道内归一化分数排序 → 截断 limit
```

要点：

1. **排序策略：FTS 优先，不加权融合。** 通道内分数（BM25 负分 / 余弦 / 硬编码分）量纲不可比，做跨通道归一化只会引入无依据的权重。改为**按通道分段返回**：先给 `work-memory` 的 top-N（N 由 `limit` 决定），余量再给 `palace`，最后是文件通道。实测（见 §2.5）FTS 单通道已能把真实查询的目标记忆排进 top-5，不需要靠融合去救。
2. **`sessionKey` 过滤保留**：现有的会话级 drawer 过滤（`bridge-tool-registrar-integration.ts:170-180`）继续作用于 palace 通道。
3. **降级语义变更**：MemPalace 不可用时不再用文件 grep 冒充"语义搜索"，而是三条通道各自独立返回——`work-memory` 通道在 MemPalace 缺席时**照常工作**，这正是本次整改的核心收益。
4. **返回结构**每条带 `{ provider, id | drawer_id, content, score, category?, updatedAt? }`，工作记忆条目额外带 `id` 以便模型接 `memory_manage` 读取/修正。

> **有效性预验证（2026-09-17 实测）**：把日志中 5 条真实 `memory_search` 查询按 `AgentMemoryRepo.search()` 的原样逻辑（同一套 bigram 分词 + FTS5 MATCH + `bm25()` 排序）重放到 `agent_memories_fts`，**5/5 全部命中相关记忆**。其中 09:14:34 那次失败查询 `未知任务 工具为0 默认分 0.76 观察 评估`，top-1 正是当时已在库中、却检索不到的 `【工具为0/效率0/未知任务/默认0.76话题·静默挂起…】`。**索引、分词、排序三样都已就绪且质量达标，缺的只是接线。**

### 4.2 写入侧 schema 门

在 `parseCandidatesJson`（`memory-extractor.ts:286`）后插入一道 `validateCandidate()`，规则如下：

| 规则 | 判定 | 处置 | 依据 |
|---|---|---|---|
| JSON 残片 | `content` 含 `"}]` / `"]` / 未闭合引号 | 拒绝 | §2.4.3(a) |
| 长度下限 | `content.length < 5` | 拒绝 | 防碎片（阈值取 5 而非 8：见实施计划差异 #5） |
| 长度上限 | `content.length > 600` | 拒绝并告警 | 防整段总结灌入 |
| ~~重复~~ | — | **不做** | 去重归 `mergeCandidates`；在此拦掉会连带丢失 tags 并集与来源回填（实施计划差异 #4） |
| importance 缺失 | **不拒绝**，按类别给保守默认值 | 接受并告警 | 见下方说明 |

同时修正源头正则（`memory-extractor.ts:32-41`）：

- `. {2,200}` 改为**按句读边界截断**：`[^。！？!?\n]{2,200}`，避免吞入后续模板文本。
- `importance: 0.95` 固定值改为**按内容长度与是否含结构化信号**给分，不再给所有命中项发最高优先级。

拒绝的候选记录 `console.warn`（含拒绝原因与 content 前 40 字），供后续统计「写入拒绝率」——这是写入侧质量的可观测指标。

> **为什么不把 `importance` 设为必填并拒绝缺失**：丢一条好记忆的代价高于存一条默认重要度的记忆。真正的病根是**这个字段没有锚点示例**——模型在拿不准时倾向给 0.7（实测 0.5–0.8 占 88%，0.7 为众数），而 `general` 类在提取提示里连示例都没有（设计正本 §7.4 已识别）。解法是照 Generative Agents 的做法给**分档锚点**：把 1–10 分写成带具体例子的量纲（"日常琐事=2 / 重要的用户偏好=8"），而不是靠拒绝来逼模型给值。这属于提示词工程，在 P0-3 里与正则修正同批做。

### 4.3 曝光 / 效用信号分离

新增迁移 **V47**：

```sql
ALTER TABLE agent_memories ADD COLUMN last_injected_at TEXT;   -- 注入时间（原 last_used 的语义）
ALTER TABLE agent_memories ADD COLUMN exposure_count INTEGER NOT NULL DEFAULT 0;  -- 曝光次数
ALTER TABLE agent_memories ADD COLUMN utility_count  INTEGER NOT NULL DEFAULT 0;  -- 有效使用次数
```

- `use_count` 保留为历史累积值，**不再写入**（避免破坏既有 UI 与统计）。
- **迁移时回填**：`exposure_count = use_count`、`last_injected_at = last_used`。否则新列全 0 会让 `passesInjectionGates` 把 155 条「其实用过」的记忆误判成「从未用过」而集体跳过。
- **分两步上线**（见实施计划 §附表中的差异 #1）：P0-4 先只**记录** `utility_count` 与 `memory_usage_feedback`，**不进入打分**；等 P1-5 抽样验证效用代理（bigram 重叠近似）的命中率 ≥70% 后，才决定 `useCountBonus` 是否切到 `utility_count`。代理噪声未知时接线等于污染排序。
- `loadTopMemories` 注入时改刷 `last_injected_at` / `exposure_count`（`memory-repo.ts:186-197`）。
- `scoreMemory` 的 recencyBonus 输入从 `lastUsedAt` 改为 `createdAt`（消除自激）；`useCountBonus` 的输入从 `useCount` 改为 `utilityCount`（效用而非曝光）。
- 效用回写路径：`MemoryIntegration` 在 `agent_end` 时用本轮 `_injectedSnapshot` + 回复文本计算重叠度，写 `memory_usage_feedback`，并递增对应条目的 `utility_count`。

打分公式变更对照：

```
改前: importance × weight × ageFactor(created_at)
      + recencyWeight × f(lastUsedAt)        ← 注入即刷新，恒满额
      + relevanceBonus × relevance
      + min(0.15, w × ln(1 + use_count))     ← 曝光量

改后: importance × weight × ageFactor(created_at)
      + recencyWeight × f(createdAt)         ← 与注入解耦（P0-4 落地）
      + relevanceBonus × relevance
      + min(0.15, w × ln(1 + utility_count)) ← 效用（P1-5 抽样达标后才切）
```

> **⚠ 连带改动：`last_used` / `use_count` 的所有下游消费者必须同批切换**，否则会静默失准。已核出的消费点：
> - `passesInjectionGates`（`memory-repo.ts:262-267`）的「从未被用过且已过期」判定 → 改读 `exposure_count`
> - `archiveCold`（`memory-repo.ts:510-521`）的冷记忆判定 → 改读 `last_injected_at`
> - `prune`（`memory-repo.ts:535-558`）的排序键 → 改读 `last_injected_at`
> - `countByTemperature`（`memory-repo.ts:719-750`）与 `computeTemperature`（`temperature.ts:44-63`）的输入 → 改读 `last_injected_at`
> - `listByWindow` 的 `field: 'last_used'` 分支（`memory-repo.ts:307`）→ 保留兼容，但文档标注语义已变更
> - 云同步 `mergeMemory` 的时间戳比较键（`sync-importer.ts:509`、`:526`）→ 改读 `last_injected_at`，否则跨设备冲突判定失准

### 4.4 非破坏失效

新增迁移 **V48**：

```sql
ALTER TABLE agent_memories ADD COLUMN superseded_at TEXT;    -- 被取代的时间
ALTER TABLE agent_memories ADD COLUMN superseded_by TEXT;    -- 取代者的 id（可空，跨 agent 时为空）
ALTER TABLE agent_memories ADD COLUMN archive_reason TEXT;   -- 'cold' | 'superseded' | 'pruned' | 'user'
```

规则：

1. `archive(memoryId)` 与 `archiveCold` / `archiveBatch` / `prune` 一律写入 `archive_reason`。
2. **`superseded_at` 必须先修检测器才有意义**。`archiveOldProjectSnapshots`（`manager.ts:233-253`）是唯一的取代检测机制，但实测只识别 18% 的 project 记忆、零重复主题、251 条零归档（见 §2.5.3）——根因是 `extractProjectTheme` 的正则方向与真实内容格式相反。**只加字段不修检测器 = 死字段（违反纪律 #10）。**
   修法分两步，且顺序不可颠倒：
   - **第一步（P1，提示词侧）**：提取提示词要求输出结构化 `project_key` 字段（写入时解释），落 `agent_memories` 新列。这一步把解释工作从读路径搬到写路径，是 Schema-Grounded Memory 的落点。
   - **第二步（P1，代码侧）**：检测器改为比对 `project_key`（代码可判定），命中同 key 的旧条目写 `superseded_at` + `superseded_by`，指向新快照。
   - 弃用 `extractProjectTheme` 的正则路线——自由文本 + 硬编码正则注定脱节，实测 18% 识别率就是证据。
3. `deleted_at` 补齐读侧过滤：`loadCandidates`（`:216`、`:232`）、`listByWindow`（`:324`）、`search`/`searchByLike`（`:581`、`:602`）、`listActive`（`:613`）、`listActiveAllAgents`（`:625`）、`countByTemperature`（`:727`）全部加 `AND deleted_at IS NULL`。
4. 本地 `removeById` 从硬删改为写 `deleted_at`（保留行）——**这是给墓碑列补上缺失的生产者**（§2.4.5），删除才能跨设备传播；同时清理 FTS 索引行使其不可检索。
   > 顺序要求：**先补生产者，再加读过滤**。反过来做（只加 `AND deleted_at IS NULL`）没有任何可观测效果——列永远为 NULL，行为与现在完全一致。若决定不做生产者，则应当**把列删掉**，而不是留一个永远为空的墓碑。
5. 读路径默认**排除** `superseded_at IS NOT NULL` 的行（与 `is_archived` 同级过滤）；`memory_manage` 的查询动作可显式包含已失效条目。

### 4.6 记忆宫殿自建（不依赖 Python / MemPalace）

#### 4.6.1 结论：可行，且零件全部已在仓库里跑着

MemPalace 当前的真实依赖链是：**捆绑 Python 运行时**（`getMemPalaceRuntimeDir()` / `getMemPalacePythonExe()`）+ `mempalace` + `chromadb` 两个包 + 30 秒超时的 import 健康检查（`plugin-ipc.ts:131-148`）。本机实测：`~/.lumii/runtimes/` 下只有通用的 `python-embed`，**无 mempalace 运行时** → `checkMemPalaceInstalled()` 恒为 false → 每次 `memory_search` 都走文件 grep 降级（这解释了 1.4–2.4s 的调用耗时与 2% 的 drawer 覆盖率）。

要替换掉的能力只有三件，且接口边界**已经定义好**（宿主只需换实现，runtime 不用改）：

而实现它所需的零件，**每一样都已经在生产环境跑着**：

#### 4.6.3 设计（分两阶段）

> **实施细节见 [`../../plans/记忆系统/2026-09-17-自建记忆宫殿实施计划.md`](../../plans/记忆系统/2026-09-17-自建记忆宫殿实施计划.md)**，本节只锁设计决策。

| 阶段 | 内容 | 启动条件 |
|---|---|---|
| **Phase 1** | SQLite + FTS5（BM25）承载段原文，替换 MemPalace | 立即（工程收益确定） |
| **Phase 2** | 向量通道 + RRF 融合，开关默认关 | **必须由 P2-1 评测集数据显示正收益才启动**（§2.5.2 实测向量未强于 BM25） |

Phase 1 的表结构：

```sql
-- V49
CREATE TABLE palace_drawers (
  drawer_id       TEXT PRIMARY KEY,        -- contentAddressId([wing, room, content])[:16]，与现有一致
  agent_id        TEXT NOT NULL,
  user_id         TEXT NOT NULL,
  conversation_id TEXT,
  segment_id      TEXT REFERENCES memory_segments(id) ON DELETE SET NULL,
  wing            TEXT NOT NULL,
  room            TEXT NOT NULL,
  content         TEXT NOT NULL,           -- 段原文（最长实测 94473 字符）
  char_count      INTEGER NOT NULL,
  created_at      TEXT NOT NULL,
  deleted_at      TEXT
);
CREATE INDEX idx_palace_drawers_scope   ON palace_drawers (agent_id, user_id, deleted_at);
CREATE INDEX idx_palace_drawers_segment ON palace_drawers (segment_id);

-- 独立虚表 + 应用层维护（与 agent_memories_fts 同构，不用 external-content 表）
CREATE VIRTUAL TABLE palace_drawers_fts USING fts5(content, content_bigram);
```

检索流程：

```
Phase 1:  FTS5 BM25 → top-N → 返回 { drawer_id, text, score, wing, room }
                                  ↑ 与 MemPalaceSearchItem 同形，调用方零改动

Phase 2:  FTS5 BM25 top-30  ∪  暴力余弦 top-30  →  RRF(60)  →  返回
```

Phase 2 的关键取舍（照抄 Wiki 侧已验证的结论，`wiki-source-vector.ts:23-32`）：

- **不把整段原文压成单向量**。段原文平均 6790 字符、最长 94473，单向量会把语义平均掉并吸入噪声。语料取 `summary + topic_tokens` 截断 300 字，**长文精确匹配继续交给 FTS（BM25 本就强于单向量）**。
- **不做 chunk**。分块向量是 `content-address.ts:8-9` 提到的阶段二形态，当前语料量下收益不明，按教程反模式 #1 不上。
- **余弦不能用于阈值判定**。实测 top-1 余弦全落在 0.873–0.893，绝对值无区分度——只做排序信号，经 RRF 融合。

#### 4.6.4 迁移路径与退出标准

宿主侧把三个回调从 MemPalace MCP 换成自建实现即可，**runtime 零改动**（`archivePalace` / `ArchivePalaceMeta` 契约不变）。`palace_drawer_id` 生成规则不变（`deterministicDrawerId(wing, room, content)`）；已有 4 条由 Python 侧生成的旧 id 需在回填时重算覆盖（见计划 R1）。

| 步骤 | 内容 |
|---|---|
| 1 | V49 建表 + `PalaceRepo` + `PalaceIndexRepo`（Phase 1 不含向量） |
| 2 | 宿主三回调切换到 `LUMII_PALACE_BACKEND=builtin`；MemPalace 客户端保留一个版本周期作回退 |
| 3 | 回填：遍历 `memory_segments` 中 `char_count >= 50` 的 **98 段 / 66.5 万字符 / 47 会话**，逐段归档并回填 id |
| 4 | **退出标准**：`palace_drawer_id` 覆盖率 > 90%；`memory_search` P95 < 150 ms；`memory_read` 可按 id 读回原文；移走 `~/.lumii/runtimes/` 后功能不降级 |

#### 4.6.5 但它应当排在 P0-1 之后

§2.5.2 的实测结论必须如实反映到优先级上：**本地向量在 Lumii 的真实语料上并没有强过 BM25，4 组对照打平 2 组、各胜 1 组**。所以自建宫殿的正当理由是工程性的，不是检索质量：

| 理由 | 强度 |
|---|---|
| 去掉 Python + chromadb 依赖（本机 chromadb 写入会崩，见环境笔记） | **强** |
| 延迟从 1.4–2.4s 降到 <150ms | **强** |
| 与主库同源，可 JOIN、可测试、可观测（现在是黑盒） | **强** |
| 承载 FTS 覆盖不到的原始段原文（66.6 万字符） | 中 |
| 检索质量提升 | **弱**（实测未碾压 BM25） |

因此：**P0-1（接通 FTS5）先做，它已经解决日志里那次真实失败；自建宫殿排在其后**，其价值主张写清楚是"替换依赖、降延迟"，不是"更聪明"。实施计划（[`2026-09-17-自建记忆宫殿实施计划.md`](../../plans/记忆系统/2026-09-17-自建记忆宫殿实施计划.md)，5 人日）已提前写好，P0-1 落地后即可启动，不必等排队。
