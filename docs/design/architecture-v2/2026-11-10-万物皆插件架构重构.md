## 0. 判断：抄什么，不抄什么

**要抄的是三条生命周期语义**，不是整套框架：

1. **依赖驱动激活（PENDING）**——插件缺服务时等待，不是失败；服务出现后自动激活。
2. **级联停用与重激活**——服务消失时，依赖它的插件一起停；服务恢复后自动回来。
3. **可嵌套的作用域（effect / 子作用域）**——一个插件可以按实体（会话、窗口、Agent 实例）开子作用域，
   父作用域销毁时整棵子树按 LIFO 清理。

这三条是 Cordis 在 Koishi 4000+ 插件规模下被验证的部分（见 `设计解构.md` §2）。

**不引入 Cordis 本体的理由**：

- 它解决的是「4000 个第三方插件互不认识、必须靠服务可用性协商顺序」的问题；
  Lumii 是自用客户端，插件来源是自己与 Agent，**不存在互不认识的第三方生态**。
- 它的 API 是 `ctx.xxx` 代理形态，与 Lumii 现有 `ctx.get(S.xxx)` 不同；
  引入意味着 31 个插件全部重写 `apply`，换来的能力 90% 用不上（isolate / intercept / schema 配置）。
- 上游是 `4.0.0-rc.12`，DSH 自己维护了 V1–V24 共 20 多条本地补丁。
  绑定它等于把核心的稳定性押在一个 rc 版本上——**与「核心必须稳」正好相反**。

结论：**内核语义对齐，实现保持自研且极小**（目标 ≤ 1200 行，含类型与错误）。

## 1. 现状诊断

### 1.1 内核缺一半状态机

| 语义 | Cordis | Lumii 现在 | 后果 |
|---|---|---|---|
| 缺依赖 | `PENDING`，服务出现后自动激活 | 直接 `failed`（`loader.ts:118`） | 启动顺序全靠手工排序；动态启用时依赖可能还没就绪 |
| 服务消失 | 依赖方一起卸载，服务恢复后重激活 | 只 `container.remove` | 停用一个插件后，依赖它的插件拿着已经失效的引用继续跑 |
| 子作用域 | `ctx.plugin()` / `ctx.effect(generator)` | 只有插件级 scope | 按会话/窗口注册的资源没法归到实体上，只能全局登记再手工清理 |
| 激活超时 | 无（同步部分有 vm 超时） | 无 | Agent 写坏的 `apply` 可以卡死主进程 |
| 状态可见 | `internal/status` 事件 | 1 秒轮询 + 渲染层上报 | 事件式的即时性做不到 |

### 1.2 真正的“核心”没有住进插件系统

主进程 101,985 行里，`agent-runtime/` 占 38,320 行，其中 `bridge.ts` 单文件 5,266 行。
它同时管：实例工厂、工具注册、提示词组装、上下文压缩、记忆注入、MCP、权限闸门、流水线、宠物、渠道事件、cron。

判据只有一条：**关掉这个能力，App 还完整吗？**
现在关掉工具注册 → 不能说话；关掉提示词组装 → 不认识自己；关掉记忆 → 丢上下文。
这三块是“核心”，不是插件——所以当前是「**自带能力做成了插件，产品骨架留在了核心**」。

### 1.3 能力贡献点是特例，不是契约

- 插件注册模型工具：只有 `bridge.createPipelineExecutor().registerTool(config, factory?)` 一条内部路径
  （`bridge.ts:4124`），要求完整 typebox 配置，外部扩展还得自带构造器避免打进 5MB。
- 插件贡献提示词：两个硬编码特例（`getPipelineHints`、`renderVirtualHumanPromptSection`）。
- `manifest.contributes` / `configSchema`：类型有，**全仓库零消费**。
- 斜杠命令：渲染层本地表，插件没有入口。

## 2. 目标架构

四层，边界靠**服务 key** 表达，不靠 import。

```
┌────────────────────────────────────────────────────────┐
│ apps/windows（壳）                                       │
│  窗口 / 托盘 / IPC 路由 / 渠道适配 —— 不含业务            │
├────────────────────────────────────────────────────────┤
│ 产品插件（可关闭，关闭后 App 仍可启动）                    │
│  agent-loop  tools  prompt  memory  mcp  sessions       │
│  channel-*  pet  voice  ocr  vcs  ...                   │
├────────────────────────────────────────────────────────┤
│ 能力契约（kernel/*-contract.ts）                          │
│  ToolRegistry  PromptAssembler  CommandRegistry         │
│  ChannelHub  MemoryStore  SessionStore                  │
├────────────────────────────────────────────────────────┤
│ 内核 packages/plugin-core（不依赖 electron / DOM）        │
│  ServiceContainer  PluginScope  EventBus  PluginHost     │
└────────────────────────────────────────────────────────┘
```

**内核只认“服务”，不认“工具/提示词/渠道”这些业务概念。**
业务概念以契约形式声明在 `kernel/`，插件实现它，核心按服务 key 取用。

### 2.1 为什么“最小核心”不是指行数

DSH 的核心是 99 行 bundle patch —— 它的“小”来自**每个子系统都能被替换**，不是代码少。
Lumii 的目标同样不是把 10 万行压到 1 万行，而是：

> 任何一块业务能力停止后，App 仍能启动、仍能对话（降级而非崩溃）；
> 换掉任意一块（换 agent loop、换提示词装配器），产品还在。

## 3. 内核 v2 契约

### 3.1 状态机

```
registered ──┐
             ▼
          pending ──(依赖就绪)──► activating ──► active
             ▲                      │              │
             │                   (apply 抛错)   (依赖消失/停用)
             │                      ▼              ▼
             └────────────────── failed ◄────── stopped
```

| 状态 | 含义 | UI 文案 |
|---|---|---|
| `registered` | 已注册，等待启动 | 待激活 |
| `pending` | 缺必需服务，等待中 | 等待依赖 |
| `activating` | `apply` 执行中 | 激活中 |
| `active` | 运行中 | 运行中 |
| `failed` | `apply` 抛错或激活超时 | 失败 |
| `stopped` | 被停用（可再激活） | 已停止 |

**关键变化**：缺依赖从 `failed` 改为 `pending`。这是动态启停的前提——
用户在设置页打开一个插件时，它依赖的服务可能还没就绪，此时应等待而不是报错。

### 3.2 依赖驱动

```
provide(key)        → 通知宿主 → 重新评估所有 pending 插件
remove(key)         → 依赖该 key 的 active 插件级联 stop，回到 pending
unregister(provider)→ 同上，再移除 provider
```

评估规则：`pending` 插件所需的 `inject` 全部存在 → 激活。
`injectOptional` 缺失不阻塞。

### 3.3 作用域与嵌套

```ts
ctx.effect(fn)                    // fn 返回 disposer
ctx.effect(function* () {         // generator：每个 yield 是一个 disposer
  yield () => closeA()
  yield () => closeB()
})
ctx.fork(name, (subCtx) => { ... }) // 子作用域：随父作用域销毁
```

子作用域用于按实体登记资源：每个会话的工具、每个窗口的监听器。
父作用域 dispose 时，子树按 LIFO 逆序清理，任一 disposer 抛错不中断其余。

### 3.4 激活看门狗

`apply` 的超时上限（默认 10s，可按插件配置）。超时 → 标 `failed` → 清理已登记的作用域 → 记录错误。
理由：Agent 自举写的插件里一个 `while(true)` 会卡死主进程；没有看门狗，自举就是“让 Agent 随时能把 App 弄死”。

### 3.5 生命周期事件

```ts
host.onStateChange(({ id, from, to, activationMs, error }) => ...)
```

替代轮询：控制面（设置页、`plugin_dev status`、客户端插件宿主）订阅它，
而不是每秒 stat 一次文件。

## 4. 能力契约（kernel/）

内核不认业务，业务能力以契约声明的形式挂在服务 key 上：

| 契约 | 服务 key | 插件能做什么 |
|---|---|---|
| `ToolRegistry` | `S.tools` | `registerTool({name, description, parameters, execute})` |
| `PromptAssembler` | `S.prompt` | `registerSection({ id, render, order })` |
| `CommandRegistry` | `S.commands` | `registerCommand({ name, description, execute })` |
| `ChannelHub` | `S.channelHub` | 注册出站 Provider（已有） |
| `MemoryStore` | `S.memory` | 读写记忆（已有，待契约化） |
| `SessionStore` | `S.sessions` | 会话生命周期（已有，待契约化） |

每条契约只包含**插件需要的那部分**，不暴露内部状态。
契约文件在 `apps/windows/src/main/kernel/*-contract.ts`，核心与插件都只 import 类型。

## 5. 迁移路径

每一阶段独立可验收；任何阶段停下，产品都是可用的。

### 阶段 0：内核 v2（本分支先做）

| 内容 | 验收 |
|---|---|
| PENDING + 依赖驱动 + 级联 stop | 单测：缺依赖 → pending；provide 后自动 active；provider stop 后 dependents 回 pending |
| effect 嵌套 + generator | 单测：父 scope dispose 后子树全部清理；异步串行；失败不中断 |
| 激活看门狗 | 单测：`apply` 永不 resolve → 超时判 failed，已登记 effect 被清理 |
| 生命周期事件 | 单测：状态迁移序列正确 |
| 现有 API 不变 | `pnpm --filter @mtbot/plugin-core test` 全绿；31 个插件无需改动 |

### 阶段 1：能力契约

| 内容 | 验收 |
|---|---|
| `S.tools` 契约 + `registerTool` | 外部插件不用碰 `bridge` 就能注册工具；禁用后工具从 `tools:list` 消失 |
| `S.prompt` 契约 + `registerSection` | 插件注册的段出现在系统提示词里；禁用后消失 |
| `S.commands` 契约 | 插件注册的斜杠命令出现在输入框；禁用后消失 |
| `plugin_dev guide` 重写 | 槽位表从代码生成；含工具/提示词/命令三个可复制示例 |

### 阶段 2：桥拆解（按子系统切，一次一个）

顺序按依赖最少优先：

| 批次 | 从 `bridge.ts` 拆出 | 目标服务 |
|---|---|---|
| 2a | MCP 管理（已是独立文件 533 行） | `S.mcp` |
| 2b | 工具注册 / loadout / 权限闸门 | `S.tools` |
| 2c | 提示词组装 / 分区 / 压缩 | `S.prompt` |
| 2d | 记忆（宫殿 / 工作记忆 / 注入） | `S.memory` |
| 2e | 会话 / 实例生命周期 | `S.sessions` |

每批验收：**停用该插件后，对应能力从工具表 / 提示词 / 事件里整条消失，其余插件正常工作，App 仍能对话。**

### 阶段 3：Agent 运行时自举

| 内容 | 验收 |
|---|---|
| `plugin_dev run { kind, id }` | 在 vm 里试跑 `apply`，带 5s 超时与假 ctx，记录注册了什么，不落盘 |
| `plugin_dev apply` | 试跑通过后落盘 + 激活 + 回读状态 |
| 回滚 | 新版本激活失败 → 旧版本继续服务（加载器已有此语义，补齐到 `apply` 阶段） |

## 6. 明确不做

| 不做 | 原因 |
|---|---|
| 引入 Cordis 本体 | 见 §0：换不来能力，换来一个 rc 版本的稳定性押注 |
| isolate / intercept 服务隔离 | 自用客户端，无多租户诉求 |
| 把主进程 10 万行拆成 99 个插件 | 按子系统切 8~10 个即可；拆细只增加认知成本 |
| 追 DSH 的 55 个 waterfall 事件 | 没有消费方的事件是文档债 |
| 沙箱 / 权限体系 | 决策 D1/D2 不变：插件与主进程同权限，靠审批不靠隔离 |

## 7. 风险与判据

| 风险 | 判据 / 对策 |
|---|---|
| 内核改动破坏 31 个插件 | 现有 API 保持兼容；loader.test 全部保留并补充新语义用例 |
| PENDING 让“配错依赖”静默 | `pending` 必须带 `missingServices` 并在 UI 显示“等待：xxx” |
| 级联 stop 导致意外连锁 | 只在**服务消失**时级联；用户手动 stop 不级联（与 Cordis 一致） |
| 看门狗误杀慢插件 | 默认 10s，按 manifest 可配；超时日志带阶段名 |

**最终判据**：`grep -c "ctx.get(S.agentRuntime)" apps/windows/src/plugins` 应当趋近于 0——
插件不该通过“拿到整个 bridge”来做它那一点点事。
