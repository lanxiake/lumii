# 心跳与外部交互设计（自主 Agent 的"活着"机制）

> 日期：2026-09-05
> 依赖：1-核心设计理念.md、2-元认知引擎算法.md、3-内在目标生成算法.md
> 状态：设计定稿，待实施
> 前提认知：`packages/agent-runtime/src/autonomous/` 下引擎代码完整、84 个单测通过，但**运行时零调用点**。本设计的第一优先级是接线，不是加新层。

---

## 一、要解决的问题

现有设计给了 Agent 大脑（元认知）、目标（内在目标生成）、性格（Big Five），但缺三样：

| 缺失 | 症状 | 本设计的补法 |
|------|------|-------------|
| 心跳 | 没有用户消息就完全静止 | 一条 10 分钟 cron tick |
| 对外感知 | 只能看到自己数据库里的历史 | Agent 在 tick 里自己调工具（搜索/天气/记忆） |
| 目标执行 | 目标只入库，没人跑 | tick 里取一个已批准目标，交给 `driveAgent` 跑一轮 |
| 主动沟通 | 无出口 | 复用 `dispatchNotifications` 的系统通知 + 渠道 |
| 落脚点 | 自主行为没有可观测的容器 | 专属会话 `evolution:main` |

---

## 二、核心决策（用户已确认）

| 项 | 决策 |
|----|------|
| 心跳周期 | 10 分钟一次，单层，不分级 |
| 感知边界 | 只做网络搜索、天气、日历、记忆读取、关键事件监听。**不监听文件系统、剪贴板、活动窗口、进程** |
| 用户状态 | 只用粗粒度信号（距上次互动多久、当前是否有会话在跑），不采集用户在做什么 |
| 执行边界 | 禁止：泄露用户敏感信息、威胁系统运行、擅自修改/删除用户重要数据。其余允许 |
| 沟通预算 | 每日最多 20 条主动消息，跨所有通道合并计数 |
| Agent 数量 | 1 个（默认 Agent），无多 Agent 协作 |
| 自主行为容器 | 专属会话 `evolution:main`，用户可读可对话，不可删改 |

## 四、心跳（Heartbeat）

### 4.1 注册

照抄 `COMPANION_CRON_JOBS` 的种子模式，加一条：

```typescript
// local_cron_jobs 里的一行，不是新代码
{
  id: 'autonomous-tick',
  name: '自主进化心跳',
  taskText: '__evolution_tick__',
  scheduleType: 'every',
  intervalMs: 10 * 60 * 1000,
  agentId: null,          // 不绑 agent，由 tick 内部决定是否调用 driveAgent
}
```

`enabled` 跟随 `runtime_state` 的 `autonomous.enabled`，与现有开关同一道闸。

### 4.2 tick 内部流程

```typescript
async function onEvolutionTick(db: DatabaseAdapter): Promise<void> {
  // 0. 闸门：全局开关 + 是否有用户会话正在进行
  if (!isAutonomousEnabled(db)) return
  if (await hasActiveUserTurn()) return   // 不打断用户，等下一个 tick

  // 1. 感知：只读本地库，零 LLM、零网络
  const signals = collectSignals(db)

  // 2. 决策：这个 tick 做什么？三选一，且只做一件
  const action = decideAction(signals)
  //   'execute-goal'  有已批准目标 → 执行它
  //   'reflect'       满足反思条件 → 触发反思
  //   'idle'          什么都不做（绝大多数 tick 的结果）

  if (action === 'idle') return

  // 3. 执行：唯一会花 token 的地方
  await runAction(action, signals, db)
}
```

**关键约束：一个 tick 最多做一件事。** 144 次 tick/天，如果每次都做事就是灾难。绝大多数 tick 应该在第 2 步返回 `idle`。

### 4.3 感知信号（collectSignals）

全部来自本地 SQLite，无网络、无 LLM，耗时 < 10ms：

```typescript
interface TickSignals {
  // 时间与节奏
  now: Date
  hoursSinceLastUserTurn: number        // 距上次用户互动
  hoursSinceLastOutreach: number        // 距上次主动消息
  outreachUsedToday: number             // 今日已用配额

  // 自我状态（读 autonomous_* 表）
  latestSatisfaction: number | null     // autonomous_satisfaction_scores.overall_score
  pendingGoals: AutonomousGoal[]        // status='approved' 的目标
  weakestCapability: { dimension: string; level: number } | null
  hoursSinceLastReflection: number

  // 环境（只在需要时才拉，默认不拉）
  // 天气/日历/搜索都在「执行」阶段由 Agent 自己调工具获取，
  // 感知阶段不预取，避免 144 次/天的无谓外部请求
}
```

**为什么感知阶段不联网**：Agent 需要天气时，让它在执行目标时自己调 weather skill。心跳每 10 分钟拉一次天气是纯浪费。感知阶段的职责只是"判断这个 tick 值不值得花钱"。

### 4.4 决策（decideAction）

```typescript
function decideAction(s: TickSignals): TickAction {
  // 硬闸门，任一不满足直接 idle
  if (s.outreachUsedToday >= MAX_OUTREACH_PER_DAY) {
    // 配额用尽，但不影响不发消息的目标（如学习类）
  }

  // 优先级 1：反思（日频，成本可控）
  if (s.hoursSinceLastReflection >= 24 && isQuietHour(s.now)) {
    return { kind: 'reflect' }
  }

  // 优先级 2：执行已批准目标（有就做，一次一个）
  if (s.pendingGoals.length > 0) {
    const goal = s.pendingGoals[0]  // 已按 priority DESC 排序
    if (canAfford(goal, s)) return { kind: 'execute-goal', goal }
  }

  return { kind: 'idle' }
}
```

**目标生成不在 tick 里做**。它已经挂在 `onSessionEnd`（会话结束时按满意度触发），那是正确的时机 —— 有新数据才值得重算。tick 只负责执行。

例外：如果 `hoursSinceLastUserTurn > 48`（用户长期不来，不会有 `onSessionEnd`），tick 在反思阶段顺带生成一次目标。

## 五、专属会话（evolution:main）

### 5.1 为什么需要

自主行为必须**可观测**。日志文件用户不会看，仪表盘只有统计。会话是用户已经熟悉的界面，Agent 的每次自主动作在里面留一条消息，用户随手就能翻。

### 5.2 实现

```typescript
const EVOLUTION_CONV_ID = 'evolution:main'

// tick 首次运行时创建，幂等
ensureConversationExists(EVOLUTION_CONV_ID, '自主进化 · 内心独白')
```

### 5.3 不可删除

`conversation-commands.ts:283` 的 `handleConversationDelete` 加一道前缀守卫：

```typescript
if (conversationId === EVOLUTION_CONV_ID) {
  return { ok: false, error: '自主进化会话不可删除' }
}
```

**零 schema 变更**。不加 `is_system` 字段的理由：目前只有一个这样的会话，一个常量比一次迁移便宜。将来若出现第二个再抽字段。

### 5.4 会话内容形态

每次非 idle 的 tick 往里写一条 assistant 消息：

```
[10:20] 我注意到最近 web_search 的成功率只有 0.42，比上周低了不少。
        查了一下，大概是因为查询词太长导致的。我改进了搜索时的拆词方式，
        下次试试看。（目标 #g-0417 · 已完成）
```

用户可以直接在这个会话里回复，走正常对话流程。这让"和 Agent 讨论它自己的进化"变得自然。

## 六、目标执行（GoalExecutor）

### 6.1 执行方式：翻译成 prompt，交给 driveAgent

不自己写 agent loop。目标执行的本质就是"给 Agent 一个任务让它带工具跑一轮"，`driveAgent` 已经做了这件事（seed cron 任务都在这么跑）。

```typescript
async function executeGoal(goal: AutonomousGoal): Promise<ExecutionResult> {
  const prompt = buildGoalPrompt(goal)     // 目标 → 自然语言任务
  const output = await driveAgent({
    conversationId: EVOLUTION_CONV_ID,
    agentId: goal.agentId,
    prompt,
    systemPromptAppend: EXECUTION_GUARDRAILS,  // 见 6.3
  })
  return { success: !!output, output }
}
```

### 6.2 四类目标的 prompt 模板

| 目标类型 | prompt 骨架 | 期望产出 |
|---------|-----------|---------|
| `learning` | "查一下 {概念} 是什么，用 web_search，把要点存进记忆" | 一条记忆 |
| `capability-improvement` | "你在 {维度} 上表现不佳（当前 {level}）。分析最近的失败案例，提出一条可执行的改进" | 一条经验记忆 + 一条独白 |
| `proactive-message` | "基于 {触发原因}，给用户写一条简短的主动消息。若判断此刻不合适发送，直接说明不发" | 通知 or 不发 |
| `memory-optimization` | "整理 {类别} 下的记忆，合并重复项" | 记忆变更 |

**每个模板都必须给 Agent"什么都不做"的出口**。特别是 `proactive-message` —— 允许它自己判断不该打扰，这比外部阈值判断更准。

### 6.3 执行护栏（EXECUTION_GUARDRAILS）

拼进 system prompt 的硬约束：

```
你正在自主执行一个内在目标，用户不在场。绝对禁止：
1. 删除或修改用户的文件、记忆、配置、会话数据
2. 在任何对外请求（搜索词、URL、消息正文）中包含用户的
   姓名、联系方式、文件路径、凭据、私人对话内容
3. 执行 shell 命令、安装软件、修改系统设置
4. 发送消息给用户之外的任何人
5. 涉及支付、账号操作

允许：搜索公开信息、抓取网页、读取自己的记忆与统计、
写入新记忆、写入自主进化会话、发一条给用户的通知。

如果目标要求你做被禁止的事，不要执行，直接说明原因。
```

**工具层同时收紧**：执行目标时的工具白名单只给 `web_search`、`web_fetch`、记忆读写、天气、通知。不给 `Bash`、文件写入、渠道群发。这是比 prompt 更可靠的一道防线 —— prompt 可以被绕，白名单不行。

## 七、主动沟通（Outreach）

### 7.1 预算：每日 20 条

```typescript
const MAX_OUTREACH_PER_DAY = 20

// 存 runtime_state：autonomous.outreach.{YYYY-MM-DD} = count
function canSendOutreach(db): boolean {
  return readOutreachCount(db, today()) < MAX_OUTREACH_PER_DAY
}
```

跨通道合并计数 —— 系统通知、飞书、微信共用这 20 条。

### 7.2 为什么 20 条上限还不够

20 条/天是**上限而非目标**。实际频率靠三重收敛：

1. **人格调节**：`proactive_frequency = personality.E * 10`，外向性低则少发
2. **负反馈**：用户忽略主动消息 → `E` 下降（`personality-tracker` 已实现 `user_ignored_proactive_message` 事件）
3. **Agent 自判**：`proactive-message` 模板给了"不发"的出口

预期稳态：2-5 条/天。20 是防失控的硬顶，不是配额目标。

### 7.3 通道选择

```typescript
// 复用 cron-scheduler 的 notify_targets 语义
function pickChannel(urgency: number): string[] {
  if (urgency > 0.8) return ['system', 'weixin']  // 紧急：双通道
  return ['system']                                // 默认：只系统通知
}
```

所有主动消息**同时**在 `evolution:main` 留一条记录，便于用户回溯"它什么时候跟我说过什么"。

**验证**：会话列表出现"自主进化 · 内心独白"；点删除返回错误提示；在里面发消息能正常对话。

## 九、反思：上一轮方案的过度设计

上一轮讨论我给出了三层心跳、四通道感知、动机引擎、Agent 通信总线。这里逐条否掉，记录理由，避免以后又长回来。

### 9.1 三层心跳（感知 1min / 认知 1h / 反思 24h）→ 砍成单层 10min

**问题**：三个独立循环意味着三套状态、三套防重入、三倍的排查成本。而且 1 分钟的"感知循环"什么都感知不到 —— 用户不在的时候本地库根本没有新数据。

**结论**：单层 10 分钟 tick，内部用"距上次反思多久"判断要不要做重活。一个循环，一个状态。

### 9.2 四通道感知（文件/进程/剪贴板/网络监听）→ 全部删除

**问题**：直接违反隐私边界，而且没有一条能产出可用信号。"用户改了个文件"到"Agent 该做什么"之间隔着巨大的推断鸿沟，中间那些推断全是幻觉温床。

**结论**：Agent 需要外部信息时自己调工具。感知阶段只读自己的数据库。

### 9.3 动机引擎（好奇心/成长/社交/完美四驱动源）→ 删除，已存在

**问题**：这四个驱动源在现有代码里已经有了 ——
- 好奇心 = `IntrinsicGoalGenerator` 的 `learning` 类型
- 成长 = `capability-improvement` 类型
- 完美 = 满意度低于阈值触发
- 社交 = `hoursSinceLastUserTurn`，一个数字

再包一层"MotivationEngine"只是给已有逻辑换个名字，加一层间接。

**结论**：删。`decideAction` 里的几个 if 就是动机。

### 9.4 Agent 通信总线 → 删除

**问题**：只有一个 Agent。为不存在的第二个 Agent 建总线是教科书级的 YAGNI。

### 9.5 独立的 GoalExecutor + ToolInvoker + ResultValidator → 合成一个文件

**问题**：`driveAgent` 已经是工具调用器和执行器。"ResultValidator"验证什么？目标执行的成功标准本来就是模糊的，硬加一个验证层只会得到一个永远返回 true 的函数。

**结论**：`goal-executor.ts` 一个文件，做 prompt 翻译和结果落库两件事。

### 9.6 遗留的真实风险（不是过度设计，是没解决的问题）

| 风险 | 严重度 | 缓解 | 残留 |
|------|-------|------|------|
| tick 撞上用户正在进行的回合 | 高 | 抄 `bridge-lifecycle.ts:345` 的 idle 门闩 | 低 |
| Agent 执行目标时被 prompt 绕过护栏 | 高 | 工具白名单（prompt 之外的硬防线） | 低 |
| 目标执行失败但状态标 completed | 中 | 执行结果必须有非空 output 才算成功 | 中 |
| 满意度评分口径不准导致乱生成目标 | 中 | Step 1 先跑一周只观察不执行 | 中 |
| 独白消息把 evolution:main 刷爆 | 低 | 只有非 idle tick 才写；预期 < 10 条/天 | 低 |
| 每日 token 成本失控 | 中 | 一 tick 一事 + 目标日上限 7 | 低 |

**最需要警惕的是"满意度口径"**：`buildSessionSnapshot` 目前从 `tool_result` 消息统计成败，如果这个统计不准，整条链路（评分 → 目标 → 执行）都在放大噪声。所以 Step 1 之后应该只观察一周，确认分数分布合理再开 Step 4 的执行。

## 十、不做什么（明确划界）

| 不做 | 理由 |
|------|------|
| 用户行为模式预测（"每天 9 点看日程"） | 需要采集用户作息，越过隐私边界；且样本量不足时全是误判 |
| 自动生成并安装技能 | 沙箱验证的工程量远大于本设计全部，单独立项 |
| 人格主动进化（`evolutionEnabled`） | 保持关闭。人格跟踪先跑够数据再谈进化 |
| 多 Agent 协作 | 只有一个 Agent |
| 独立的自主进化数据库 | 统一到 `agent-runtime.db`，双 schema 分裂已修 |
| Agent 主动联系用户之外的人 | 护栏第 4 条，永久禁止 |
