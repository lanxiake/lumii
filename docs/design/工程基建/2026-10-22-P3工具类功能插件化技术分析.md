# P3 工具类功能插件化技术分析

> 创建日期：2026-10-22  
> 分析范围：ACP / VCS / Usage / Dashboard Feed / File Preview 五个工具类功能  
> 目的：评估插件化可行性、识别技术难点、提出改造方案

## 0. 背景与问题

P1（桌宠/语音/代聊/浏览器）和 P2（四个渠道适配器）都遵循**声明式包装**原则：
- 功能在 `index.ts` 中集中构造（服务类或适配器）
- 插件只做声明（`definePlugin` + 注释），不移动初始化点
- 禁用插件 = 代码不加载，但服务照旧运行

P3 工具类功能的**核心问题**：
1. **没有统一的初始化点**（不像渠道适配器在 index.ts 中集中构造）
2. **多为函数式 API**（usage-store / tool-usage-store）而非服务类
3. **与核心运行时深度耦合**（ACP 后端在 bridge 构造期注入，VCS 快照在回合末尾调用）

这些特征表明 **P3 不适合简单的 P1 式声明式包装**，需要评估每个功能的插件化方案。

## 1. 功能清单与代码结构

### 1.1 ACP 编码后端（`com.lumii.acp`）

**代码文件**（约 20+ 个文件）:
- `coding-dev-*.ts`：ACP 运行器、消息解析、CLI 检测、版本管理、项目管理等
- `coding-dev-backends-stub/`：ACP 后端存根（`run-coding-dev-acp-prompt.ts`）

**依赖关系**:
- 微信渠道的 `AcpBackendManager`（L1631）：微信独有的后端路由
- 渠道适配器的后端切换命令（`/backend` / `/lumii`）
- Agent Runtime 的工具注册（ACP 相关工具）

**初始化模式**:
- `AcpBackendManager` 在微信适配器构造时创建（L1631）
- **只有微信渠道支持 ACP 后端路由**（其他渠道无此功能）

**插件化难点**:
- ACP 后端管理器与微信适配器强耦合
- ACP 工具注册分散在多处（需要梳理 `bridge-tool-registrar.ts`）
- 配置存储分散（`getCodingDevConfig` / `resolveDevContext`）

### 1.2 VCS / Git 集成（`com.lumii.vcs`）

**代码文件**（18 个文件）:
- `workspace-vcs/`：Git 操作、快照、diff、ignore 等
- `project-git/`：项目级 Git 状态、CLI 封装

**依赖关系**:
- Agent Runtime 的回合结束事件（快照触发时机）
- Bridge 的 `workspace` 路径（Git 仓库位置）
- 工具注册（`git_*` 系列工具）

**初始化模式**:
- **函数式 API**（`vcs-repo.ts` / `workspace-turn-snapshot.ts`）
- 回合结束时调用 `captureWorkspaceTurnSnapshot`（在 bridge-agent-instance-events.ts）

**插件化难点**:
- VCS 快照与 Agent 回合生命周期深度耦合
- Git 工具注册分散在 `bridge-tool-registrar.ts`
- 快照触发时机在 bridge 内部（`agent:turn-end` 事件）

### 1.3 用量统计（`com.lumii.usage`）

**代码文件**（4 个文件）:
- `usage-store.ts`：LLM 调用用量记录（JSONL 追加写）
- `tool-usage-store.ts`：工具调用统计

**依赖关系**:
- Agent Runtime 的回合事件（`llm:response-complete` 时调用 `recordUsage`）
- Bridge 的工具调用事件（工具结束时记录用量）

**初始化模式**:
- **函数式 API**（`recordUsage` / `queryUsage`）
- 在 `bridge-agent-instance-events.ts` L873 调用 `recordUsage`
- 在工具调用结束事件中记录工具用量

**插件化难点**:
- 用量记录与 Agent 回合事件耦合
- 函数式 API 无显式初始化点（按需调用）
- 禁用用量统计需要在事件监听层做条件判断

### 1.4 首页信息流（`com.lumii.dashboard-feed`）

**代码文件**（4 个文件）:
- `dashboard-feed-store.ts`：信息流数据存储（SQLite）
- `agent-runtime/dashboard-feed-tool.test.ts`：工具测试

**依赖关系**:
- Agent Runtime 的工具注册（`dashboard_*` 系列工具）
- 渲染层的首页组件（读取信息流数据）

**初始化模式**:
- **可能有懒初始化**（首次调用时创建 SQLite 表）
- 工具注册在 `bridge-tool-registrar.ts`

**插件化难点**:
- 首页信息流与渲染层耦合
- 工具注册分散

### 1.5 文件预览（`com.lumii.file-preview`）

**代码文件**（2 个文件）:
- `file-preview/preview-window-ipc.ts`：预览窗口 IPC
- `file-preview/preview-window-manager.ts`：预览窗口管理

**依赖关系**:
- Electron 窗口管理
- 渲染层的预览组件

**初始化模式**:
- **可能有懒初始化**（首次预览时创建窗口）
- IPC 注册在主进程启动阶段

**插件化难点**:
- 预览窗口管理与主窗口耦合
- IPC 注册时机

## 2. 插件化方案评估

> **评审结论（2026-10-22，见实施计划 §10）**：P3-C（ACP）**判定不做**。
> 本节的「只有微信渠道用 ACP」已过期——飞书适配器在构造函数里自己 `new AcpBackendManager()`
> （`feishu-channel-adapter.ts:116`），微信那个由 `index.ts` 注入，是两条所有权路径。
> 提取全局服务的收益只是少注册几个本来就 no-op 的 IPC；触发条件是出现第三个 ACP 渠道
> 或 ACP 改成独立安装包。下文保留原分析，作决策留档。

### 2.1 ACP 编码后端

**方案 A：P1 声明式包装**（不推荐）
- ✅ 可以创建 `extensions/acp.ts` 声明插件
- ❌ 但 ACP 后端管理器只在微信渠道初始化，其他渠道无此功能
- ❌ 禁用插件不影响微信渠道的 ACP 功能（因为管理器在微信适配器构造时创建）

**方案 B：重构后插件化**（推荐）
1. 将 `AcpBackendManager` 从微信适配器中解耦
2. 创建全局 ACP 后端服务（所有渠道共享）
3. 微信适配器通过服务容器获取 ACP 服务
4. ACP 插件提供全局 ACP 服务（`ctx.provide(ACP_SERVICE)`）
5. 禁用插件 = ACP 服务不初始化，相关工具不注册

**改造工作量**：中等（需要重构微信适配器的 ACP 后端管理）

### 2.2 VCS / Git 集成

**方案 A：P1 声明式包装**（不推荐）
- ✅ 可以创建 `extensions/vcs.ts` 声明插件
- ❌ 但 VCS 快照在 `bridge-agent-instance-events.ts` 中调用，无法通过插件控制
- ❌ 禁用插件不影响 VCS 快照功能

**方案 B：事件订阅式插件化**（推荐）
1. VCS 快照逻辑从 `bridge-agent-instance-events.ts` 移到插件内
2. 插件订阅 `agent:turn-end` 事件，在事件回调中触发快照
3. Git 工具注册从 `bridge-tool-registrar.ts` 移到插件内
4. 禁用插件 = 不订阅事件，VCS 快照不触发，Git 工具不注册

**改造工作量**：中等（需要重构 bridge 的 VCS 快照逻辑）

### 2.3 用量统计

**方案 A：P1 声明式包装**（不推荐）
- ✅ 可以创建 `extensions/usage.ts` 声明插件
- ❌ 但用量记录在 `bridge-agent-instance-events.ts` L873 调用，无法通过插件控制
- ❌ 禁用插件不影响用量记录功能

**方案 B：事件订阅式插件化**（推荐）
1. 用量记录逻辑从 `bridge-agent-instance-events.ts` 移到插件内
2. 插件订阅 `llm:response-complete` 事件，在事件回调中调用 `recordUsage`
3. 工具用量记录同样移到插件内
4. 禁用插件 = 不订阅事件，用量记录不触发

**改造工作量**：小（函数式 API，只需移动调用点）

### 2.4 首页信息流

**方案 A：P1 声明式包装**（可行）
- ✅ 可以创建 `extensions/dashboard-feed.ts` 声明插件
- ✅ 信息流工具注册可以在插件内完成
- ⚠️ 但首页组件读取信息流数据的逻辑需要做容错（插件禁用时数据不可用）

**方案 B：完全插件化**（推荐）
1. 信息流工具注册移到插件内
2. 渲染层首页组件做容错（插件禁用时不显示信息流）
3. 禁用插件 = 工具不注册，首页不显示信息流

**改造工作量**：小（主要是工具注册迁移 + 渲染层容错）

### 2.5 文件预览

**方案 A：P1 声明式包装**（可行）
- ✅ 可以创建 `extensions/file-preview.ts` 声明插件
- ✅ 预览窗口管理可以在插件内完成
- ⚠️ 但预览入口（IPC / 菜单项）需要做容错（插件禁用时预览不可用）

**方案 B：完全插件化**（推荐）
1. 预览窗口管理移到插件内
2. IPC 注册移到插件内
3. 渲染层预览入口做容错（插件禁用时隐藏预览按钮）
4. 禁用插件 = 预览窗口不创建，IPC 不注册

**改造工作量**：小（预览窗口管理相对独立）

## 3. 总体建议

### 3.1 P3 功能的插件化难度分级

| 功能 | 难度 | P1 可行性 | 推荐方案 |
|------|------|-----------|----------|
| 用量统计 | ⭐ 低 | ❌ 不可行 | 事件订阅式插件化 |
| 首页信息流 | ⭐ 低 | ✅ 可行 | P1 声明式包装 + P2 完全插件化 |
| 文件预览 | ⭐⭐ 中 | ✅ 可行 | P1 声明式包装 + P2 完全插件化 |
| VCS / Git 集成 | ⭐⭐⭐ 高 | ❌ 不可行 | 事件订阅式插件化 |
| ACP 编码后端 | ⭐⭐⭐ 高 | ❌ 不可行 | 重构 + 插件化 |

### 3.2 建议的实施策略

**阶段 1：P3-A 低难度功能**（立即可开始）
1. 首页信息流：P1 声明式包装（创建插件文件 + 注释）
2. 文件预览：P1 声明式包装（创建插件文件 + 注释）

**阶段 2：P3-B 中等难度功能**（需要设计评审）
1. 用量统计：事件订阅式插件化（需要重构 bridge 的事件监听逻辑）
2. VCS / Git 集成：事件订阅式插件化（需要重构 bridge 的 VCS 快照逻辑）

**阶段 3：P3-C 高难度功能**（需要架构评审）
1. ACP 编码后端：重构微信适配器的 ACP 后端管理（涉及多个渠道的兼容性）

### 3.3 当前阶段的行动建议

**立即执行**（2026-10-22）:
1. 完成 P3-A：首页信息流 + 文件预览的 P1 声明式包装
2. 输出 P3-B / P3-C 的技术设计文档（事件订阅式插件化的具体方案）
3. 提交代码 + 文档，等待评审

**待评审决策**:
1. P3-B 的事件订阅式插件化是否立即推进？
   - 需要重构 bridge 的事件监听逻辑（影响核心运行时）
   - 建议先完成 P3-A，验证插件系统的可用性后再推进
2. P3-C 的 ACP 编码后端是否需要插件化？
   - ACP 后端管理器只在微信渠道使用（其他渠道无此功能）
   - 是否值得为单一渠道的功能做全局重构？
3. P4 实验性功能（skill-evolution / selection）是否优先级更高？
   - skill-evolution 已停用，插件化收益不明确
   - selection（划词动作）可能比 P3-C 更容易插件化

## 4. 风险与缓解

### 4.1 主要风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 事件订阅式插件化破坏核心运行时 | 高 | 先完成 P3-A，验证插件系统的可用性 |
| ACP 后端重构影响微信渠道稳定性 | 中 | 保留旧代码路径，通过环境变量切换 |
| P3 功能插件化收益不明确 | 低 | 优先插件化用户可感知的功能（首页信息流 / 文件预览） |
