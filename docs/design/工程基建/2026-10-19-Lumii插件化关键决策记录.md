# 关键决策重新分析：自用客户端的激进方案

> 基于"自用客户端、内部迭代、接近原生能力"的前提重新评估五个决策
> 
> **核心改变**：性能 & 开发体验优先 >> 安全隔离 & 第三方审核

---

## 核心论点

**Lumii 是自用客户端，不是开放平台**。因此：
- ❌ 不需要"第三方安全隔离"（都是自己人）
- ❌ 不需要"复杂的审核流程"（自己维护）
- ❌ 不需要"权限声明与降级"（信任内部）
- ✅ 需要"最快的开发迭代"（秒级热更新）
- ✅ 需要"接近原生的能力"（无沙箱限制）
- ✅ 需要"最小的性能开销"（没有 iframe 通信成本）

---

## D1：是否支持第三方代码插件？

### 激进方案：内部团队可以自由开发插件

**定义**：
- ✅ 完全支持代码插件（即 P0 就支持）
- ✅ 没有权限检查或隐藏（都是自己人）
- ✅ 本地 `~/.lumii/plugins/` 即可开发与测试
- ✅ npm 可选（方便内部分享），但不必要

#### 为什么激进

| 原因 | 说明 |
|---|---|
| **信任简单** | 所有代码都是自己或信任的人写的，不需要审核 |
| **开发速度** | 少了审核流程，改完即可推送 |
| **灵活性** | 想试验什么功能就快速加一个插件，验证后决定合并到核心 |
| **解耦效果** | 大量功能以插件形式开发，核心保持精简 |

#### 实际方案

```
P0–P1: 只支持"内置插件"（Lumii 官方维护）
P2: 支持"本地开发者插件"（~/.lumii/plugins/）
  → 这些都是内部团队开发的，无需审核
  → 开发者可以快速迭代、测试
P3: 可选：支持"内部 npm 包"分发（方便跨项目共享）
  → 不必要，但如果多个项目都要用 Lumii，可以这样管理
```

#### 关键优势

- ✅ **P2 立即可用** — 内部团队可以快速在 `~/.lumii/plugins/` 开发新功能
- ✅ **验证快速** — 改代码 → 热更新 → 看效果，一分钟内
- ✅ **零审核成本** — 少了"谁审核"、"什么标准"的问题
- ✅ **解耦效果显著** — 可以用插件形式开发新功能，而不是直接改核心

#### 注意事项

- ⚠️ 内部约定：插件作者自己负责质量（代码审查、测试等）
- ⚠️ 不能因为是插件就"不管质量"，反而要更严格
- ⚠️ 定期评估"哪些插件功能应该合并回核心"

## D2：第三方渲染层如何隔离？

### 激进方案：完全不隔离，同一 JS 上下文

**定义**：
- ✅ 所有插件的 React 组件在同一 JS 上下文中执行
- ✅ 可以直接 `import` Lumii 的任何内部模块
- ✅ 可以直接访问 `window.electronAPI`
- ✅ 没有任何 postMessage 通信开销

#### 为什么激进

| 原因 | 说明 |
|---|---|
| **性能最优** | 零通信开销，直接函数调用 |
| **开发体验最好** | 像开发 Lumii 本身一样开发插件 |
| **功能完整** | 插件可以访问所有 Electron API，做任何事 |
| **调试简单** | 用 DevTools 直接断点，和调试 Lumii 一样 |
| **迭代快速** | 改代码 → 热更新 → 完全生效，无限制 |

#### 实际方案

```typescript
// 插件代码（完全和 Lumii 本身无区别）
import React from 'react'
import { useChatContext } from '@lumii/internal-hooks'  // 直接用内部 hook
import { invoke } from '@lumii/internal-utils'         // 直接调用内部函数
import { electronAPI } from 'window'                   // 直接访问

export function MyPlugin() {
  const { messages, sendMessage } = useChatContext()
  
  // 完全可以做任何事
  return (
    <div>
      {/* 组件代码 */}
    </div>
  )
}
```

#### 关键优势

- ✅ **SDK 最小** — 不需要繁琐的导出，插件就是 Lumii 代码的一部分
- ✅ **性能最好** — 没有通信开销
- ✅ **调试最快** — Chrome DevTools 直接断点
- ✅ **功能无限制** — 插件可以直接调用任何内部 API

#### 注意事项

- ⚠️ **约定**：插件代码必须遵守 Lumii 的设计约定（不能乱改全局状态）
- ⚠️ **测试**：插件要自己写单测（可以崩溃就是自己的责任）
- ⚠️ **code review**：PR 要严格 review，就像核心代码一样

## D3：插件代码放哪里？

### 激进方案：一开始就分散，便于独立开发

**定义**：
```
内置插件: apps/windows/src/plugins/<id>/     (打包进 asar)
用户装的插件: ~/.lumii/plugins/<id>/         (运行时动态加载)
  ├─ 内部团队开发的: 可以直接在本地开发
  └─ 从 npm 安装的: 可选（不必要，但支持）
```

#### 为什么激进

| 原因 | 说明 |
|---|---|
| **独立开发** | 一个插件=一个目录，开发者可以独立工作 |
| **快速测试** | 在 `~/.lumii/plugins/<id>/` 改代码，秒级热更新 |
| **模块化** | 功能清晰分离，容易理解谁维护什么 |
| **灵活迁移** | 功能成熟后可以随时合并回核心 |

#### 实际方案

```
第一天开发新功能时:
  1. 在 ~/.lumii/plugins/com.internal.my-feature/ 下创建代码
  2. 在 Lumii 中启用这个插件
  3. 改代码 → 热更新 → 看效果（秒级）
  4. 开发完成，决定是否合并到核心或保持为插件

长期维护时:
  - 如果是通用功能 (如云同步) → 内置在 apps/windows/src/plugins/
  - 如果是可选功能 (如个人的小工具) → 保持在 ~/.lumii/plugins/
```

#### 关键优势

- ✅ **开发最灵活** — 新功能可以快速原型化
- ✅ **迭代最快** — 热更新秒级响应
- ✅ **协作友好** — 多人开发不同插件时不互相干扰
- ✅ **测试简单** — 禁用插件就能测试"核心是否运行正常"

#### 实施细节

**首次启动时**：
```typescript
// 如果插件不在用户目录，从 asar 解包
if (!fs.existsSync(path.join(userPluginsDir, 'com.lumii.cloud-sync'))) {
  fs.copySync(
    path.join(builtinPluginsDir, 'cloud-sync'),
    path.join(userPluginsDir, 'com.lumii.cloud-sync')
  )
}
```

**开发时**：
```bash
# 直接在用户目录开发
~/.lumii/plugins/com.internal.my-feature/
  ├── src/
  │   └── index.ts
  └── package.json

# pnpm dev 时自动检测并热更新
# 改 src/index.ts → 秒级重新加载
```

## D4：UI 文案"插件"还是"扩展"？

### 激进方案：简单清晰，统一叫"扩展"

**定义**：
- 所有东西统一叫"扩展"，不区分类型
- 如果真的需要区分，用小标签或 icon（不需要分栏）
- UI 简单、扁平、快速

#### 为什么激进

| 原因 | 说明 |
|---|---|
| **用户简单** | 内部团队对产品很熟悉，不需要"教学" |
| **UI 简洁** | 一个列表，快速查看和管理 |
| **实现快** | 不需要设计分栏、标签的复杂 UI |
| **扩展性好** | 未来想加新类型时，直接加标签即可 |

#### 实际方案

```
扩展中心

扩展列表
├─ ☁️  云同步 (builtin)      ✅ 启用      🔧 设置  ⚙️
├─ 🎤 语音 (builtin)         ✅ 启用      🔧 设置  ⚙️
├─ 🎬 录屏 (builtin)         ⏸️ 禁用      🔧 设置  ⚙️
├─ 🐱 桌宠 (builtin)         ✅ 启用      🔧 设置  ⚙️
├─ 📦 ffmpeg (asset)         ⬇️ 已装      🔧 设置  ✕ (卸载)
├─ 📦 微信 MCP (asset)       ⬇️ 已装      🔧 设置  ✕ (卸载)
└─ 🔧 我的工具 (local dev)   ✅ 启用      🔧 设置  ⚙️
```

**标签说明**：
- `(builtin)` — 内置插件
- `(asset)` — 资源包
- `(local dev)` — 本地开发

#### 关键优势

- ✅ **UI 实现快** — 一个列表，配个搜索框，完事
- ✅ **易于扩展** — 想加新类型，直接加标签
- ✅ **用户清晰** — 标签一眼看清楚

#### 注意事项

- ⚠️ 标签要选择好，让用户能快速理解区别

## D5：热更新默认开启吗？

### 激进方案：全局自动热更新，完全无感

**定义**：
- ✅ 所有模式（dev 与 prod）都自动热更新
- ✅ 改代码 → 秒级加载，无需任何操作
- ✅ 用户无法关闭（因为都是自己人，这就是好事）
- ✅ Native 模块也支持热更新（通过包装）

#### 为什么激进

| 原因 | 说明 |
|---|---|
| **开发最快** | 改代码即时反馈，零等待 |
| **用户体验最好** | 完全无感更新，不需要重启 |
| **迭代快速** | 能以秒为单位验证想法 |
| **都是信任代码** | 不需要担心"无感更新被破坏" |

#### 实际方案

```
开发模式 (pnpm dev):
  ✅ 自动热更新（所有插件）

生产模式 (App):
  ✅ 自动热更新（所有插件）
    内置插件: 运行时直接重加载
    用户插件: 检测到文件变化立即重加载
  
  内部开发者在生产环境修改时:
    1. 改代码 (在 ~/.lumii/plugins/<id>/)
    2. 几秒钟内自动加载
    3. 无需重启 App，无需任何操作
    4. 实时看到效果
```

#### 关键优势

- ✅ **迭代最快** — 秒级反馈，日常开发体验最好
- ✅ **验证最快** — 修复 bug 或试验新想法时立即看到效果
- ✅ **无感更新** — 用户不需要做任何事

#### 如何处理失败

**如果热更新失败**：
```typescript
// 1. 记录错误日志
logger.error('Plugin hot reload failed:', error)

// 2. 保持旧版本运行
// (回滚到上个成功的版本)

// 3. UI 提示用户有问题（开发者看日志）
// 或者自动重启一次试试

// 4. 开发者看到错误，立即修复
```

**Native 模块的处理**：
```
如果插件用了 .node 文件:
  1. 改代码 → 自动重编
  2. .node 文件也重新加载
  3. 或者 fallback: 如果加载失败，则提示"需要重启"
```

#### 注意事项

- ⚠️ 开发者要确保热更新时的状态一致性（不能丢用户数据）
- ⚠️ 如果有长时间运行的异步任务，要能安全中断

## 四个激进方案的组合

如果全部采用激进方案：

```
D1: ✅ 完全支持代码插件（P0 即支持）
    内置 + 本地开发，无审核，无限制

D2: ✅ 完全不隔离（同一 JS 上下文）
    插件可以访问所有 Electron API
    SDK 最小，性能最优

D3: ✅ 分散位置，便于独立开发
    内置: apps/windows/src/plugins/
    用户: ~/.lumii/plugins/

D4: ✅ 统一叫"扩展"，简单清晰
    一个列表，按标签区分

D5: ✅ 自动热更新，完全无感
    改代码 → 秒级反馈
    dev 与 prod 统一
```

### 优点

- ✅ **开发体验最好** — 秒级反馈，无限制
- ✅ **性能最优** — 没有通信开销，没有隔离成本
- ✅ **迭代最快** — 可以以秒为单位试验
- ✅ **功能完整** — 插件可以做任何 Lumii 能做的事
- ✅ **实现最简** — 代码最少，逻辑最清晰
- ✅ **协作友好** — 多人开发不同功能时互不干扰

### 缺点

- ⚠️ **信任前提** — 必须所有代码都来自信任的源
- ⚠️ **质量责任** — 每个开发者要对自己的代码负责
- ⚠️ **无法恢复** — 热更新失败时需要有回滚机制
- ⚠️ **状态管理** — 要注意热更新时的状态转移

## 风险与应对

### 风险 1：热更新失败导致 App 卡住

**症状**：改了代码，热更新失败，App 在某个状态卡住

**应对**：
- 实现"如果热更新 5 次失败就重启 App"的自动兜底
- 开发者看到重启时的日志就知道问题在哪
- 或者提供"一键重新加载"按钮

### 风险 2：插件 bug 导致 App 崩溃

**症状**：某个开发者改的插件有 bug，导致整个 App 崩溃

**应对**：
- 这是正常的开发过程（测试代码时经常会崩溃）
- 关键是"崩溃后能快速恢复"
- 实现"上次启动失败，禁用最后更改的插件，重新启动"

### 风险 3：多个插件的加载顺序问题

**症状**：插件 A 依赖插件 B，但 B 加载失败

**应对**：
- 在激进方案中做好"依赖声明"
- manifest 中明确 `requires` 与 `optional`
- 加载时检查依赖，如果缺失则禁用该插件

### 风险 4：状态不一致（热更新时）

**症状**：热更新时用户正在输入，热更新后状态丢失

**应对**：
- 这是设计问题，不是激进方案的问题
- 应该在"热更新前暂停 UI"的方式处理
- 或者在插件中实现"onSuspend/onResume"保存状态

## 与保守方案的比较

| 视角 | 保守方案 | 激进方案 |
|---|---|---|
| **适用场景** | 开放平台（如 VS Code、Obsidian） | 自用客户端（如 Cursor、Copilot） |
| **第一年重点** | 框架稳定、安全可靠 | 开发迭代、快速验证 |
| **社区参与** | 第三方开发者 | 内部团队 |
| **用户体验** | 安全、隐私 | 快、流畅 |
| **维护成本** | 高（审核、隔离、文档） | 低（信任代码） |
| **长期可扩展** | 易于开放 | 需要加限制后才能开放 |

**关键区别**：
- 保守方案是"从不开放到可开放"（+=限制）
- 激进方案是"从完全开放到有限制"（−=限制）

两条路都能到达"可以开放给第三方"的状态，只是**出发点不同**。
