# Lumii 插件化改造实施计划

> 创建日期：2026-10-21  
> 目标：将核心功能插件化，实现代码解耦、降低安装包体积、支持热拔插和快速迭代

## 0. 改造原则

1. **按收益排序** — 优先改造体积大、变更频繁、故障半径小的模块
2. **增量交付** — 每个插件独立验收，可随时回滚
3. **保持兼容** — 改造期间应用正常运行，不影响用户
4. **验证充分** — 每个插件完成后验证：可禁用、可重载、无残留、启动时间不增

## 2. P1-A：桌宠插件化

### 2.1 现状分析

**主进程：**
- `main/pet/` — 11 个文件，2726 行
  - `pet-window-manager.ts` — 窗口管理
  - `pet-mode-ipc.ts` — 模式切换 IPC
  - `pet-subject.ts` — 状态管理
  - `pet-model-resolver.ts` — 资产解析
  - `virtual-human-*.ts` — 虚拟人激活

**渲染层：**
- `renderer/pet/` — 37 个文件，13142 行
  - 桌宠渲染引擎
  - 动作编排
  - 物理模拟

**资产：**
- `resources/pet-assets/` — 约 15.9MB

**耦合点：**
- 依赖 bridge（宠物目标、性格）
- 主窗口/托盘联动
- agent-runtime 的 pet-goal-runner

### 2.2 改造方案

**主进程插件：**
```typescript
// apps/windows/src/main/extensions/pet.ts
export const petExtension = {
  manifest: {
    id: 'com.lumii.pet',
    name: '桌面宠物',
    version: '0.1.0',
    engines: { lumii: '>=0.1.0' },
    kind: 'code',
    assets: ['pet-assets'], // 声明依赖的资产
  },
  definition: definePlugin<MainEvents>({
    id: 'com.lumii.pet',
    activationEvents: ['on-demand'], // 首次打开设置或主动启用时激活
    provides: ['pet-window', 'pet-mode'],
    apply(ctx) {
      // 注册 IPC
      ctx.registerIpc('pet:getMode', handleGetMode)
      ctx.registerIpc('pet:setMode', handleSetMode)
      
      // 订阅事件
      ctx.on('agent:turn-end', onTurnEnd)
      
      // 提供服务
      ctx.provide(PET_SERVICE, createPetService())
      
      // 清理
      ctx.effect(() => {
        petWindowManager.closeAll()
      })
    },
  }),
}
```

**渲染层视图：**
- 独立路由 `/pet`（已存在）
- 通过 `app.view` slot 贡献设置区

**验收标准：**
- ✅ 禁用后桌宠窗口关闭，IPC 注销
- ✅ 重新启用后恢复
- ✅ 资产未安装时显示引导
- ✅ 主进程代码从 bundle 移除，体积减少 ~50KB
- ✅ 资产可选下载，节省 15.9MB

### 2.3 实施步骤

1. ✅ 将桌宠包装为内建插件（`extensions/pet.ts` 已存在）
2. ✅ 通过服务容器获取依赖（`ctx.get(S.mainWindow)` / `S.tray`）
3. ✅ 用 `ctx.effect()` 注册清理逻辑（`disposePetModeIpc`）
4. ✅ 完善插件注释（架构定位、依赖、资产）
5. 🔲 验证禁用/启用（设置页添加开关，测试禁用后 IPC 不注册）

7. 🔲 P2: IPC 改用 `ctx.registerIpc`（渐进式迁移，20+ handlers）

**当前状态（2026-10-21）**:
- ✅ 桌宠已是真正的插件（通过 `definePlugin` 定义，注册到 `BUILTIN_EXTENSIONS`）
- ✅ 可通过 `disabledIds` 禁用（PluginHost 初始化时跳过）

- ASR（语音识别）、TTS（文本转语音）、来电

**资产：**
- ONNX 模型 ~200MB
- 模型下载与管理

**耦合点：**
- 全局单例 `voiceService`
- ONNX 顺序闸（同时只能一个模型加载）
- 桌宠虚拟人集成

### 3.2 改造方案

**插件结构：**
```
com.lumii.voice
├── 激活条件：首次使用语音功能或设置中启用
├── 提供服务：ASR_SERVICE、TTS_SERVICE
├── 资产依赖：onnx-runtime、voice-models
└── IPC：voice:*
```

**关键改造点：**
- ONNX 顺序闸改为服务内部管理（不暴露给全局）
- 模型下载进度通过事件发射
- 与桌宠的耦合改为服务依赖（桌宠 `ctx.require(TTS_SERVICE)`）

### 3.3 验收标准

- ✅ 未启用时不加载 ONNX
- ✅ 模型按需下载
- ✅ 禁用后释放资源

## 4. P1-C：代聊插件化

### 4.1 现状分析

代聊逻辑散落在：
- `channel/adapters/` 中各适配器的代聊处理

**核心能力：**
- 监听入站消息
- 判断是否需要代聊
- 调用 Agent 生成回复
- 发送出站消息

### 4.2 改造方案

**插件架构：**
```
com.lumii.channel-relay
├── 订阅事件：channel:message-received
├── 调用服务：AGENT_SERVICE、CHANNEL_SERVICE
├── 配置：代聊规则、响应延迟、Agent 参数
└── 设置区：启用/禁用、规则配置
```

**关键点：**
- 通过事件订阅而非硬编码在适配器中
- 配置独立存储（`relay-config.json`）
- 失败不影响其他渠道功能

### 4.3 验收标准

## 7. 风险与缓解

### 7.1 主要风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 改造破坏现有功能 | 高 | 每个插件独立验收，保留旧代码路径 |
| 启动时间增加 | 中 | 懒激活 + 性能监控 |
| 资产下载失败 | 中 | 降级提示 + 重试机制 |
| 插件间依赖复杂 | 低 | 服务容器 + 依赖注入 |

### 7.2 回滚策略

每个插件改造时：
1. 保留原代码（通过环境变量 `LUMII_LEGACY_<MODULE>=1` 启用）
2. 插件激活失败时自动回退
3. 用户可在设置中禁用单个插件
4. 保留至少一个版本的回滚路径

**P2 第一阶段特点**（延续 P1 原则）：
- 插件文件：`extensions/channel-*.ts`（4 个）
- 已注册到 `BUILTIN_EXTENSIONS`
- 适配器仍在 `index.ts` 构造，在构造函数末尾自注册到全局注册表（`registerChannelAdapter(this)`）
- **2026-10-22 补**：构造段已包进 `isExtensionActive('com.lumii.channel-*')`，
  禁用时登录服务与适配器都不装配（P2 第一阶段当时「禁用不影响渠道」的问题已修）

**为什么仍然不是运行期热插拔**：
1. 适配器依赖多个服务（LoginService / Bridge / AcpBackendManager / ReplyContextStore），都在 `index.ts` 中初始化
2. 适配器在构造函数末尾自注册（`registerChannelAdapter(this)`），调用时机与 app:ready 时序耦合
3. `registerChannelAdapter` 无对应的 `unregister` API（全局注册表不支持动态注销）
4. LoginService 的事件（`statusChange` / `qrcode`）需转发到渲染层，事件订阅与取消订阅需重构

P1 + P2 第一阶段证明了插件系统对适配器的包装能力，P2 第二阶段才做真正的解耦与按需加载。

### P2 接线门补齐（2026-10-22）

**问题**：P2 迁移只把注册逻辑搬进了插件文件，调用点却仍**无条件**调用 `registerXxxIpc()`。
`disabledIds` 只让 `PluginHost` 跳过 `register()`，功能照旧接线——文档里的
「禁用插件 = 功能不可用」此前并不成立。

**改法**：新增 `main/extensions/active.ts`，`startExtensions()` 在外部扩展加载完后把
`host.list()` 写成快照；调用点按 `isExtensionActive(id)` 决定接不接线。

| 调用点 | 插件 |
|--------|------|
| `ipc/ipc-handlers-registry.ts` | `com.lumii.vcs`、`com.lumii.selection` |
| `main/index.ts`（文件预览） | `com.lumii.file-preview` |
| `agent-runtime/bridge-tool-registrar.ts` | `com.lumii.dashboard-feed`、`com.lumii.browser`（工具） |
| `kernel/stages/post-ready.ts`（`browserPluginEnabled`） | `com.lumii.browser`（服务启动） |
| `main/index.ts`（`initChannelServices`） | `com.lumii.channel-{weixin,wecom,feishu,qbot}` |
| `agent-runtime/bridge.ts`（`ensureWechatWatchCronJobSeeded`） | `com.lumii.relay` |

仍待端到端验证：在 `~/.lumii/state/extensions.json` 的 `disabled` 里加 id → 重启 →
对应 IPC 通道应报 no handler。`usage` 插件无需门（它在 `apply()` 里订阅事件，天然随禁用移除）。

**禁用已真实生效**（2026-10-22 复核）：`pet`（IPC 就在 `apply()` 里注册）、`voice`（服务由容器获取）、
`browser`（上面两处门）、`vcs`/`selection`/`file-preview`/`dashboard-feed`（接线门）、
`relay`（`ensureWechatWatchCronJobSeeded` 的 `pluginEnabled`：禁用时把已播种的盯梢任务也停掉）、
四个渠道适配器（`initChannelServices` 里整段按插件状态跳过，登录服务也不建）。

**渠道的 Hub 契约已放宽**：`ChannelHubDeps` 的 `feishu`/`wecom` 改为可选，
`wecomProvider` 可为 null；缺省渠道只是不进 registry，出站得到稳定的
`CHANNEL_NOT_CONNECTED`（`channel-hub-bootstrap.test.ts` 钉住）。

### 运行期启停（2026-10-22 落地）

设置页的开关**不再一律要求重启**：接线全在 `apply(ctx)` 里的插件，关掉即摘、开回来即装。

**做法**（每迁移一个插件 = 把接线搬进 apply + 加进 `HOT_SWAPPABLE_BUILTINS`）：
1. `PluginHost.start({ exclude })`：禁用的插件仍**登记**在宿主里，只是不激活
   （以前是压根不 register，那样运行期就没有可 activate 的条目）
2. 通道用 `ctx.registerIpc` 注册——作用域一拆，`ipcMain.removeHandler` 跟着走
3. 需要 bridge 的接线（工具、盯梢 cron）等 `agent:runtime-ready` 事件后补上
   （该事件此前只在类型表里声明，**没有发射点**）
4. `extension-control.setEnabled` 返回 `restartRequired`，UI 据此提示「已生效 / 需重启」

| 插件 | 启停 | 观测到的判据 |
|------|------|--------------|
| vcs / selection / file-preview | ✅ 即时 | 通道 `No handler registered` ↔ 正常返回 |
| dashboard-feed | ✅ 即时 | `tools:list` 里 feed 工具 2→0→2 |
| browser | ✅ 即时 | `browser_*` 10→0→10；服务随之停/起 |
| pet | ✅ 即时 | `pet:get-mode` 无 handler ↔ `ok:desktop`；窗口与快捷键随 dispose 收干净 |
| relay | ✅ 即时 | 「代聊插件已禁用，暂停 job id=wechat-watch」↔ 恢复 |
| voice | ✅ 即时 | 通道 handler ↔ 无 ↔ handler；停用时释放 VAD/ASR/TTS。**例外**：启动时就被禁用、且 E5 已跑过的进程不能再启用（ONNX 运行时已绑定），此时如实报错要求重启 |
| 四个渠道适配器 | ✅ 即时 | `channelService.list()` 里该渠道消失 ↔ 恢复；适配器 `stopListening` 只摘监听，**不登出**，重新启用不必重新扫码 |

**外部扩展（`~/.lumii/extensions/`）仍要重启**：它们的服务句柄（`S.perf` / `S.cloudSync` /
`S.syncScheduler`）在启动期被 `index.ts` 取走并缓存，卸载扩展只拆掉它自己的作用域，
已经分发出去的调度器照旧在跑——「关掉了但还在工作」比要求重启更糟。
要做需先让核心改成每次现取（与语音的 `currentVoiceService()` 同一做法）。

`isExtensionActive` 现在优先走**实时解析器**（宿主的 `state === 'active'`）：
运行期开关之后，启动快照会过期（插件已经停了，快照还说它开着）。

**端到端实测（2026-10-22）**：`~/.lumii/extensions.json` 禁用
`com.lumii.channel-feishu` / `com.lumii.vcs` / `com.lumii.browser` 后重启——
日志出现 `扩展已按配置禁用: …`、`浏览器插件已禁用：跳过控制服务启动`、
`飞书插件已禁用：跳过登录服务与适配器`；渲染层 `electronAPI.vcs.log()` 得到
`No handler registered for 'vcs:log'`。恢复配置重启后同一调用返回真实提交列表。

**第三轮（2026-10-22，禁用 voice / pet）**：语音引擎完全没有初始化（日志里
`初始化语音引擎` 0 次）、`voice:command` 报 no handler；`pet:get-mode` 报 no handler。
至此 15 个内置插件逐一验过「禁用 = 功能真的不在」。

**第二轮（2026-10-22，禁用 relay / dashboard-feed / file-preview / selection）**：
日志 `代聊插件已禁用，暂停 job id=wechat-watch`、`无头模式或插件已禁用：跳过文件预览窗口 IPC 注册`；
渲染层 `selection:run` / `file-preview:open` 均 `No handler registered`；
`tools:list` 从 162 项降到 160 项、feed 工具消失（恢复配置后回到 162 项）。
后者暴露了设计问题：`dashboard_feed_*` 在内置总表里留了 stub，插件禁用后工具照样被
advertise，模型会白调一次拿到 `not_implemented`——已从 `ALL_BUILT_IN_TOOL_CONFIGS` 删除，
真实现仍由插件覆盖注册。

**顺带修掉一个只有真启动才看得见的坑**：P2 迁移时用的是
`const { registerVcsIpc } = require('../extensions/vcs')`——`require` 会被原样打进
`out/main/index.js`，运行时按**产物目录**解析成 `out/extensions/vcs`（不存在），
`tsc` 与 vitest 都绿、一启动就 `Cannot find module`。四处已改成静态 import。
`verify/pet-plugin-disable-test.mjs` 也把配置路径从 `~/.lumii/state/` 改正到
`~/.lumii/`（主进程根本不读 state 那份，所以以前「禁用没生效」是写错了文件）。

**快照的 fail-open**：`isExtensionActive()` 在快照未写入时一律返回 true。
若按「不在集合=禁用」处理，任何在 `startExtensions()` 之前跑的消费方（单测直接构造 bridge）
都会悄悄把功能关掉，症状是「功能没了」，比「禁用了没关」难查得多。
