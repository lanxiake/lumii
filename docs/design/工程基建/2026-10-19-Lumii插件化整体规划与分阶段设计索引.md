## 核心决策框架（激进方案）

### 问题定义

Lumii 插件化的真实目标是解决**三个具体的工程问题**，**并为内部快速迭代优化**：

| 问题 | 症状 | 激进方案 |
|---|---|---|
| **一切都在启动期** | `main/index.ts` 1999 行，线性 590 行 bootstrap | 分离启动阶段，秒级热更新 |
| **上帝对象** | `bridge.ts` 4484 行/134 方法，211 个 IPC 无归属 | 按领域拆服务，完全不隔离 |
| **无法独立启停** | 新增功能要改 3–5 个文件，无法禁用 | 用 manifest + Context，秒级反馈 |

### 设计原则（激进优化）

| 原则 | 说明 | 体现 |
|---|---|---|
| **性能优先** | 零通信开销，直接函数调用，接近原生 | D2：完全不隔离，同一 JS 上下文 |
| **开发速度优先** | 秒级迭代循环，5 倍加速 | D5：秒级热更新，完全无感 |
| **内核最小化** | 内核只保留窗口/IPC/Agent 循环 | 大量功能以插件形式，核心精简 |
| **完全信任** | 所有代码来自内部团队，无审核成本 | D1：P0 即支持，无权限限制 |

## 阶段规划详表（激进方案）

### P0：内核与清单（8–12 周）

**目标**：实现插件框架，不改变任何现有功能行为。关键差异：**完全不隔离，秒级热更新框架**

| 子目标 | 交付物 | 验收 | 风险 |
|---|---|---|---|
| `packages/plugin-core` 实现 | Context / Service / Effect / Event 内核（**无权限隔离**） | 单测全绿；effect 严格 LIFO；依赖环检测 | 低 |
| Manifest 类型与校验 | `shared/plugin-manifest.ts` + JSON Schema | Schema 与代码同步；load-time 校验；冲突检测 | 低 |
| Plugin SDK 骨架 | `@mtbot/plugin-sdk` 包与构建预设（**完整 API 访问**） | Exports 类型 + 示例用法；TypeScript 检查通过 | 低 |
| IPC 元数据补全 | 211 个通道加 owner/schema/risk（**激进：直接使用，无权限检查**） | 无重复；每个通道有 owner；不改行为 | 中 |
| Bootstrap 分阶段 | `index.ts` 拆成 `kernel/bootstrap.ts` + 阶段文件 | 内部可读性提升；App 行为 100% 相同 | 中 |
| 热更新基础 | 秒级模块重加载机制（**开发模式秒级响应**） | 改代码 → 秒级加载；失败自动回滚 | 中 |
| 内置 hello 插件 | 演示示例（**完全没有隔离**，可直接访问内部 API） | 可启停不崩；显示在日志里 | 低 |
| 门禁 + 文档 | Wiring 守卫、typecheck、manifest 校验脚本 | CI 全绿；无新 typecheck 错误 | 低 |

**关键变化**：
- ❌ 不需要"权限声明"框架（内部用，完全信任）
- ❌ 不需要"隔离机制"（同一上下文，性能最优）
- ✅ 需要"秒级热更新框架"（激进优化）
- ✅ SDK 完整暴露（插件可以访问所有内部 API）

**时间线**：
- W1–2：`plugin-core` + manifest（并行单测）
- W3–4：Plugin SDK + 构建预设
- W5–6：IPC 元数据补全 + bootstrap 分阶段
- W7–8：内置示例 + 门禁 + 文档
- W9–12：缓冲 & 准备 P1

### P1：主进程 PluginHost + 快速迭代开发（12–16 周）

**目标**：实现主进程 PluginHost，启用内部团队快速开发插件。关键差异：**完全激进，秒级验证**

| 子目标 | 交付物 | 验收 | 风险 |
|---|---|---|---|
| PluginHost 框架 | discovery / validate / load / activate / monitor（**无权限检查**） | 可激活/停用/重载；不崩；秒级反馈 | 中 |
| 秒级热更新 | 文件变化检测 + 模块重加载（**dev 与 prod 统一**） | 改代码 → 秒级加载；失败自动回滚 | 中 |
| 低风险迁移（性能监控） | `perf/` → 内建插件（**直接访问内部状态**） | 禁用后 metrics 不采集；App 正常 | 低 |
| 低风险迁移（云同步） | `cloud-sync/` → 内建插件（**全栈样例，完全信任**） | 禁用后云同步停止；数据无损 | 中 |
| 低风险迁移（更新检查） | `updater-service/` → 内建插件 | 禁用后不检查；已激活 App 无异常 | 低 |
| 低风险迁移（控制口） | `app-ui-control/` 路由→插件贡献（**无额外权限检查**） | 白名单从 manifest 聚合；控制面仍可用 | 中 |
| 本地开发支持 | `~/.lumii/plugins/<id>/` 开发流程文档 | 开发者可在本地快速原型化 | 低 |
| 监测与反馈 | 插件激活耗时、错误日志聚合 | `plugin:list` 可查状态；错误清晰 | 低 |

**关键变化**：
- ✅ **秒级热更新全局启用**（dev & prod 统一）
- ✅ **本地开发完全支持**（在 `~/.lumii/plugins/` 改代码即反馈）
- ❌ 不需要权限检查（都是内部代码）
- ✅ 激进优化：插件可以直接访问任何 API，改代码秒级看效果

**验收**：
- `pnpm test:all` 全绿
- 改代码 → 秒级反馈（不超过 2 秒）
- 启动耗时不增加 > 50ms
- 内部团队可以在 `~/.lumii/plugins/` 快速原型化新功能

**时间线**：
- W13–16：PluginHost 框架 + 秒级热更新
- W17–22：5 个低风险插件迁移 + 本地开发验证
- W23–24：内部团队开始试验（日常开发中使用）

## 分阶段风险与依赖关系

```
P0 (plugin-core + 元数据补全)
  ├─ P0.2 (启动分阶段 + IPC 治理)
  └─> P1 (主进程 PluginHost + 低风险)
        ├─ 依赖 P0.2 完成
        └─> P2 (服务分解)
            ├─ 不阻塞 P1 的后续迭代
            ├─ 可与 P3 并行
            └─> P3 (中等风险迁移)
            
P1 完成后，可并行：
  ├─ P3 (中等风险)
  ├─ P4 (渲染层)
  └─ P2 (服务分解 — 复杂，先做准备)

最后：P5 (中心 UI + 开发工具)
```

**关键约束**：
- P0 必须完成且验收通过，P1 才能开始
- P1 初版（PluginHost 框架）与 P3 初版（一个中等风险插件）可同时推进
- P4 依赖 P1 PluginHost 框架，但不依赖 P2 或 P3（可独立完成卡片系统）
- P5 需要至少一个 P3 或 P4 的示例插件验证完整流程
