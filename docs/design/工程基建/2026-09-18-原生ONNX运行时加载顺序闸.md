# 原生 ONNX 运行时冲突与加载顺序闸

> 2026-09-18 · 起因：打开 `LUMII_PALACE_VECTOR=1` 后**连续 3 次启动崩溃**
> 代码正本：[`apps/windows/src/main/onnx-runtime-gate.ts`](../../../apps/windows/src/main/onnx-runtime-gate.ts)
> 复现脚本：`scripts/repro-vad-crash.mjs`（顺序） / `scripts/repro-vad-concurrent.mjs`（并发）

## 1. 崩溃现场

开启宫殿向量后，每次启动都在同一指纹处死掉：

```
[VadEngine] [initialize] 加载 Silero VAD 模型: ...\silero_vad.onnx
The given version [27] is not supported, only version 1 to 14 is supported in this build.
Exit status 4294930435
```

`4294930435` = `0xC0000005`（访问冲突）——**原生层崩溃**，不是 JS 异常，
所以 try/catch 兜不住，整个进程直接没了。

## 2. 根因：两个同名不同版本的 `onnxruntime.dll`

进程里同时存在两份 ONNX Runtime：

| 来源 | 版本 | 支持的 opset |
| --- | --- | --- |
| `sherpa-onnx-win-x64/onnxruntime.dll`（VAD 用） | **1.27.0** | 到 27 ✅ |
| `onnxruntime-node/bin/napi-v3/win32/x64/onnxruntime.dll`（E5 嵌入用） | **1.14.20230209** | 到 14 ❌ |

报错文案中"only version 1 to 14"精确对应 **1.14**。而 `sherpa-onnx-c-api.dll`
的导入表里只有**裸文件名 `onnxruntime.dll`**（二进制字符串表确认，**没有路径**）。

Windows 的 DLL 解析规则是：**先按基名在「已加载模块」里找**。于是：

1. 宫殿向量回填启动 → 创建 E5 流水线 → 把 **1.14** 加载进进程
2. 约 3 秒后 VAD 预热 → sherpa 绑定的不是它自带的 1.27，而是**已在进程里的 1.14**
3. 1.14 去加载 opset **27** 的 VAD 模型 → 版本不支持 → 原生崩溃

### 隔离复现

| 场景 | 结果 |
| --- | --- |
| VAD 先加载，再跑 E5（30 轮交替） | 全过 ✅ |
| E5 先跑，VAD 1.5 秒后加载 | 卡死在原生调用里（153 秒 CPU 仅 0.09 秒）❌ |

## 3. 为什么之前没炸

地雷是**既有的**，不是这次引入的——只要有任何 E5 初始化早于 VAD 就会踩。

之前没暴露，是因为 wiki 向量是**查询时懒加载**（必然发生在启动后的 VAD 之后）。
宫殿回填是**第一个"启动即跑 E5"的路径**，把它顶到了前面。

**推论**：不能靠"关掉宫殿向量"躲过去。将来任何新的启动期嵌入需求都会再踩一次。

## 4. 修法：进程级加载顺序闸

`onnx-runtime-gate.ts` 用一个三态状态机表达"VAD 必须排在所有 E5 之前"这个
**进程级约束**——而不是靠"两个模块各自记得排序"（那正是会漂移的东西）。

```
idle ──sherpaFirst()──> sherpaHolding ──sherpaDone()──> sherpaDone
  │                                                        ▲
  └──waitForSherpa()──> e5Running ──────────────────────────┘（不可逆）
```

| 调用点 | 动作 |
| --- | --- |
| `voice/vad-engine.ts` `initialize()` | 第一个 `await` **之前**同步 `sherpaFirst()`；`finally` 里 `sherpaDone()` |
| `voice/voice-service.ts` `ensureInitialized()` | 同上（**同步**，不能放在 `await getModelPaths()` 之后） |
| `agent-runtime/bridge.ts` 宫殿回填 | `await waitForSherpa()` 后再 `setupPalaceVector` |
| `wiki-transformers-embedder.ts` | 首次 `await` 前 `await waitForSherpa()` |
| `index.ts` | 语音服务创建与预热**移到** `bridge.initialize()` **之前** |

进入 `e5Running` 后 `sherpaFirst()` 会**拒绝**并让 VAD 抛错——那时再加载 sherpa
已经晚了，**如实报错好过在原生层崩掉**（沿用本仓「禁止静默降级」纪律）。

### 一个容易写错的地方

`voice-service.ts` 里的 `sherpaFirst()` 必须在**第一个 `await` 之前**同步调用。
最初写成 `await getModelPaths()` 之后，于是 `waitForSherpa()` 可能先把状态推到
`e5Running`，VAD 反过来被拒——闸门的存在反而制造了故障。

## 5. 验证

修复后启动实序（此前三次都崩在 VAD 那一行）：

```
20:35:31.978 加载 Silero VAD 模型
20:35:32.094 VAD 初始化完成          ← 此前 3 次都崩在这
20:35:47.977 语音引擎预热完成
20:35:48.610 嵌入器已加载             ← E5 在 VAD 之后
20:37:00.798 后台补齐完成：518 条
```

单测 `onnx-runtime-gate.test.ts` 锁的是**状态机契约**（崩溃本身由上面两个
复现脚本在真实原生层覆盖）：VAD 抢救机会只有一次、E5 永远等它、
VAD 失败也要放行 E5（不能一起拖死）。

## 6. 遗留

- **依赖层没有根治**：只要 `sherpa-onnx` 与 `onnxruntime-node` 仍然各自捆绑
  ONNX Runtime，这个约束就一直在。上游若能统一版本（或让 sherpa 用带路径导入），
  本闸可以删除。
- 闸门是**进程级单例**，多窗口/多实例共用一个进程时共享状态——当前架构是单主进程，
  符合预期；若将来拆多进程，每个进程都要各自走一遍这个顺序。
