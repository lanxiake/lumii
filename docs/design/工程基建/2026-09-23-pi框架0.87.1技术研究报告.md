## 一、结论速览

### 1.1 五条核心判断

1. **框架的价值分布是"底层零件成熟、上层集成未完成"**。compaction / truncate / messages / frame 这些**纯函数层**是可直接取用的稳定资产；harness 集成层设计优秀但**按切片交付**（`watchSession` 未实现、`drive` 与取消的公共出口"guarded until M8"），且同一包里已有第二套自称 experimental 的内核（pico3）。
2. **durable 是本轮最核心的"净增"能力**（重启续跑、崩溃恢复、效果去重），但它的收益场景是**无人值守的长任务**，不是普通问答。本仓最匹配的落点是 cron/自主任务——那里现在是"每次新建实例、跑完销毁、中途崩了全丢"。（另一项净增是会话树/分支，见第 4 条。）
3. **迁移的真正成本在数据模型，不在 API**。本仓 SQLite 是"最终态 + 原地覆盖"（流式行被反复覆盖），而 durable/session 树要求 append-only 事件与 `parentId` 树形结构；这一条决定了"整体迁移"不是几十小时的活。
4. **产品价值最高的一项是会话树/fork/navigation**（编辑历史重来、对话分支），它同时也是迁移面最大的一项。当前仓里只有 `forkConversation` 这个"从这条重开"的按钮级原语。
5. **`/compat` 有外部期限**：`pi-ai` 的兼容入口已全量标 `@deprecated`，删除绑定在"coding-agent 的 ModelManager 迁移"之后。本仓 **18 个源码文件依赖它（14 个生产文件 + 4 个测试）**，**这是必须排期、且不由我们控制时间表的一件事**。

### 1.2 建议分档

| 档 | 内容 | 理由 |
| --- | --- | --- |
| **A · 立即（零迁移成本）** | 借鉴 compaction 的三个细节（**增量摘要**、按轮切分、文件操作记忆）；截断诊断字段对齐。（~~token 估算替换~~ 经核对我们已具备且更准，见 §7.1） | 纯函数，无架构耦合；我们刚做完压缩，正好对照 |
| **B · 中期（局部试点）** | ① 自主任务（cron）的 durable 试点；② 会话树/navigation 立项时评估借 session 层；③ 多端协议等 M8 | 收益真实但需要设计；不宜与主对话链路耦合 |
| **C · 暂不** | 整体迁移到 harness / pico3；telemetry | 成本高、成熟度不足、可能白做（见 7.3） |
| **⚠️ 必办** | `/compat` → `createModels()` 迁移排期 | 外部期限，非我们掌控 |

> 详细论证见第七章；全部事实依据与行号见第二~六章。

## 二、框架全景

### 2.1 四个包的分工

0.87.1 不再是"一个包 + 一个 patch"，而是四个包的组合：

| 包 | 职责 | 与我们的关系 |
| --- | --- | --- |
| `pi-ai` | 模型调用层：provider 适配、模型目录（Models registry）、流式事件、工具调用协议、图像生成 | 直接使用（`streamSimple` 走 `/compat`） |
| `pi-agent-core` | Agent 内核：裸 `Agent`、harness、session、durable runtime、compaction、tools | **只用了裸 `Agent`**，其余未用 |
| `chord` | `Context` / `ContextKey` / `withCancel` / `JsonValue` 等基础抽象 | 间接（经 pi-agent-core 的类型） |
| `pi-telemetry` | 结构化遥测：span schema、`TelemetryContext` | 未用 |

`pi-agent-core` 的子路径导出（`package.json` → `exports`）：

```
.                        → dist/index.js（导出 harness 全量 + 裸 Agent + compaction 工具函数）
./node                   → Node 入口
./harness/context        → Context 相关
./harness/env/nodejs     → NodeExecutionEnv
./harness/runtime/reducer→ reduceLaneSnapshot（多端协议用）
./harness/session        → Session 存储
./harness/session/testing→ 存储一致性测试套件（conformance）
./experimental/pico3     → 第二套内核（见 2.2）
```

注意两点：**harness 不是"内部实现"，而是主入口公开导出的能力**（`dist/index.d.ts:6` `export * from "./harness/agent-harness.ts"`）；而 pico3 的路径里带 `experimental` 字样。

### 2.2 pi-agent-core 里并存着两套内核栈

这是本次研究最需要先讲清楚的事实——同一个包里有两个互相独立、都带 durable 语义的 agent 内核：

| | 裸 Agent（我们在用） | harness 旧栈 | pico3 新栈 |
| --- | --- | --- | --- |
| 入口 | `dist/agent.js`、`agent-loop.js` | `dist/harness/agent-harness.js` | `dist/harness/pico3/index.js` |
| 状态 | 进程内 `AgentState`（`agent.d.ts:80`） | Session + Lane，13 个持久化状态叶子 | 四表三文档（注释见 `pico3/types.d.ts:1-10`） |
| 持久化 | **无**（`sessionId` 只是给 provider 做缓存亲和） | `Storage` 契约 + JsonlStorage / InMemory | 自定义 JSONL |
| 对外状态 | 事件流 | Hook（11 个）+ Event（~30 种）+ Watch/reducer | `ViewEvent`（~25 种）+ Watch |
| 成熟度标记 | 稳定 | 公开但**部分切片未完成**（见 4.7） | 注释自称 "Experimental"，路径在 `./experimental/` |

pico3 的头部注释原文（`harness/pico3/index.d.ts:1-6`）：

> ```
> Experimental Pico3 kernel API.
> This subpath is intentionally separate from the package root while the kernel
> and its Chord integration are being validated.
> ```

其内核注释（`harness/pico3/types.d.ts:1-10`）进一步说明数据模型：

> ```
> harness-v3 — records, documents, storage, kinds, transactions, runtime, tools, hooks.
> Durable model: four tables (conversations, entries, tasks, inputs) and three documents
> (session, per-conversation rewindable, per-conversation sticky). Every durable position
> is strict JSON (`JsonValue`); nothing durable is `unknown`.
> Single process. A storage path has one owning process and one owning Session at a time.
> Two processes opening the same JSONL directory is unsupported.
> ```

**判断**：pico3 是官方对 harness 旧栈的**重写/收敛方向**（作者自称 harness-v3，旧栈可视为 v2）。我们在选型时应把它当作"未来形态"观察，而不是今天的集成目标——它连入口都还挂在 `experimental` 下。

### 2.3 裸 Agent 面（现状对照的基线）

我们现在用的是 `Agent` 类（`agent.d.ts:35-127`），其能力面为：

- **构造参数**（`agent.d.ts:7-28`）：`initialState` / `convertToLlm` / `transformContext` / `streamFn` / `beforeToolCall` / `afterToolCall` / `finishTurn` / `prepareRequest` / `prepareNextTurn(WithContext)` / `steeringMode` / `followUpMode` / `toolExecution` / `sessionId` / `thinkingBudgets` / `transport` / `maxRetryDelayMs`
- **运行时 API**：`subscribe` / `state` / `steer` / `followUp` / `clearXxxQueue` / `hasQueuedMessages` / `peekQueuedMessages` / `abort` / `waitForIdle` / `reset` / `prompt` / `continue`
- **明确没有**：持久化、会话树、压缩、hint 钩子体系、多端协议

关于 `subscribe` 的语义有一条关键注释（`agent.d.ts:64-73`）——它解释了本仓此前"心跳误判"一类的现象：

> ```
> Listener promises are awaited in subscription order and are included in
> the current run's settlement. Listeners also receive the active abort
> signal for the current run.
> `agent_end` is the final emitted event for a run, but the agent does not
> become idle until all awaited listeners for that event have settled.
> ```

即：**run 的"空闲"取决于订阅者回调的完成**，回调慢则 run 迟迟不结束。

### 2.4 pi-ai 0.87.1 的增量（相对 0.50.x）

> 说明：pnpm store 中留存的旧版是 `@mariozechner/pi-ai@0.50.7`，下文的"旧版"指它。

| 增量 | 事实依据 | 对我们的意义 |

| **Models collection 取代全局 registry** | `dist/models.d.ts:159-201` 的 `createModels()` / `createProvider()` / `hasApi()`；分发改由 `Provider.stream` 承担 | 多 provider 与按模型路由是我们的既有需求，新架构更干净 |

| **流式帧编解码** | `utils/assistant-message-frame`（19.7 KB）：`AssistantMessageFrameEncoder` + `reduceAssistantMessageFrames()` | **正是 durable 恢复所需的"已提交帧前缀"**（见 4.4） |

**流式事件模型有三条硬约束**（README:659-682），写消费代码时必须遵守：

1. 事件序列是 `start → updates* → done`（失败为 `… → error`；生成前失败则流中只有 `error`）
2. **非终态事件带的 `partial` 是 live 引用而非快照**——provider 会原地 mutate，消费者必须立即拷走需要的字段
3. **不同 content block 的事件不保证连续**，必须用 `contentIndex` 关联

### 2.5 `/compat` 是定时炸弹：删除时机已写死但无日期

`pi-ai/dist/compat.d.ts:1-11` 原文：

> ```
> Temporary compatibility entrypoint preserving the old global pi-ai API surface: api-dispatch `stream()`/`complete()`

### 2.6 chord 与 pi-telemetry 的定位（澄清两个易误判的包）

- **chord 不是 agent 编排库**。其 README:3-7 原文："Chord is an application-composition runtime for systems assembled from plugins/extensions. It provides facets, services, replicated state, and a pluggable remote-service boundary… **it is not a Pi package: it does not depend on any other Pi workspace package**"。它解决的是"插件拆包、跨进程投放、服务绑定、复制状态同步"，服务于"同一功能同时跑在 agent worker / TUI / 远端 WebUI"这类诉求。对我们是**传递依赖**（我们 import 的 `Context` 类就来自它，见 3.3），无需直接使用。
- **pi-telemetry 是契约包，且默认全关**。README:3 称其为 "Vendor-neutral telemetry contracts"；它**没有任何网络能力**（对 `dist/` 全目录 grep `fetch(`/`http`/`endpoint`/`OTEL_` 零命中），默认上下文是 `NOOP_TELEMETRY_CONTEXT`（"does not inspect or retain names, attributes, events, or statuses"），且规定 instrumentation "should **avoid prompts, completions, tool arguments or output, file contents, provider payloads, headers, credentials**"。**结论：不存在隐私风险**（默认零采集、零上报），我们也确实未启用（全仓 `telemetryContext` 零命中）。

## 三、harness 深潜

### 3.1 心智模型：Session → Lane → Operation → Entry 树

四个概念层层嵌套（类型见 `harness/session/types.d.ts`、`harness/agent-harness.d.ts`）：

```
Session（会话容器：元数据 + 值存储 + 多条 Lane）
 └─ Lane（泳道：一条独立对话线 = transcript 树 + 配置 + 收件箱 + 当前操作）
     └─ Operation（操作：run / compaction / navigation 三类，各自有 id 与持久化状态）
         └─ Entry（条目：树的节点，parentId 串成链）
```

- **Entry 是树不是数组**：`EntryBase { id, parentId, seq, timestamp, type }`（`session/types.d.ts:14-21`），`type` 取四种：`message` / `compaction` / `branch_summary` / `custom`（`:13`）。
- **`CustomEntry` + `EntryProjector`** 是留给宿主的扩展点：宿主自定义条目的 `customType` 与 `data`，再注册一个投影器告诉框架"这类条目该以什么消息形态进入模型上下文"（`session/types.d.ts:44-50`）。**我们的记忆、场景、注入内容都可以挂在这里，而不是塞进 messages[0]**。
- **Lane 单飞**：一个 lane 同时只能跑一个 operation，冲突时返回 `LaneBusy`（`harness/result.d.ts:34-41`）。
- **会话级并发由多 lane 承担**：`lanes()` / `lane(name)`（`agent-harness.d.ts:679-682`）。`Session` 是容器、`Lane` 才是对话线——这与我们"一个会话一个实例"的模型不同（见 6.2）。

### 3.2 钩子体系：11 个钩子，四类聚合语义

`HookMap`（`harness/agent-harness.d.ts:485-604`）定义全部钩子：

| 钩子 | 时机 | 能改什么 | 聚合语义（实现见 `harness/hooks.js`） |
| --- | --- | --- | --- |
| `before_run` | 运行开始 | 追加 messages | **累积**：每个 handler 的 messages 都追加（`hooks.js:91-107`） |
| `before_drive` | 每个操作推进前 | 无（纯通知） | **fail-closed**：任一 handler 抛错则整个操作失败（`hooks.js:282-293`） |
| `before_run_end` | 运行将结束时 | 返回 `followUp` 自动续跑 | 累积（`hooks.js:64-72`） |
| `transform_context` | 构建请求前 | messages + systemPrompt | **链式覆盖**：后者收到前者的输出（`hooks.js:133-153`） |
| `before_request` | 发请求前 | streamOptions patch | 链式（`hooks.js:154-170`） |
| `before_payload` | 序列化后 | 原始 payload | 链式（`hooks.js:171-184`） |
| `after_response` | 收到响应 | assistant message | 链式（`hooks.js:185-198`） |
| `before_tool` | 工具执行前 | 改参 / **block 并可选 terminate** | **首个 block 生效即止**，args 链式（`hooks.js:108-132`） |
| `after_tool` | 工具执行后 | 结果 / isError / terminate | 链式 + 聚合（`hooks.js:199-234`） |
| `before_compaction` | 压缩决策时 | `decline` 或自定义结果 | **首个非空结果生效**（`hooks.js:235-254`） |
| `before_navigation` | 分支跳转时 | 同上 | 同上 |

三点值得注意：

1. **错误策略是分级的**：绝大多数钩子出错只 `reportError` 然后继续（框架容错），唯独 `before_drive` 是 fail-closed。这体现了"推进操作"被视为不可带病前进的临界点。
2. **钩子执行要过"效果闸门"**：`runWithGate` / `runToolWithGate` 通过 `Gate.admit()` 后才执行，并注入 `abortSignal`（`hooks.js:31-47`）。取消优先于效果发生——`effect-gate.d.ts:1-9` 定义 `AbortRequested` 与 `Gate`/`GateControl` 的分离视图。
3. **每个工具钩子一个遥测 span**，属性含 lane / operationId / hook 名 / registration id / outcome（`hooks.js:255-278`）。

`before_run_end` 值得单独说：它可以在运行"本来要结束"时返回 `followUp` 让 agent **自我延续**（`agent-harness.d.ts:501-509`；实现见 `hooks.js:64-72`）。这是框架版的"自主性"落脚点——与我们的心跳/自主进化方向属于同一问题域，但框架把它做成了运行循环的内建语义，而不是外部 cron 驱动的重新 prompt。

`streamOptions` 的 patch 面（`hooks.js:305-352`）暴露了 provider 侧的新能力：`transport` / `timeoutMs` / `maxRetries` / `maxRetryDelayMs` / **`cacheRetention`** / **`deferred`** / `headers` / `metadata`。

### 3.3 能力抽象：把"环境"变成注入的接口

harness 不直接碰 `fs`，而是要求宿主注入两类能力（`harness/types.d.ts:182-304`）：

- **`FileSystem`**：20 个方法（读写、行读取、原子改名、列目录、canonical path、临时文件……），契约有三条硬约束：
  - **绝不 throw**，一切失败编码进 `Result`（`:178-181`）
  - 路径分"addressed"与"canonical"两套语义，**不自动跟随 symlink**（`:150-160`、`:209-210`）
  - 错误码是 backend-independent 的稳定枚举（`:115`）
- **`Shell`**：`exec(command, options)`，options 含 `cwd` / `env` / `timeout` / `capture`（源侧限流）/ `onUpdate`（流式增量）。
- **`ExecutionEnv extends FileSystem, Shell`**（`:303`）——官方 Node 实现是 `NodeExecutionEnv`（`harness/env/nodejs.d.ts:3-42`），带 `activeChildPids` 做子进程清理。

`Context`（来自 `chord`，见 `harness/context.d.ts:1-8`）是贯穿所有 API 的隐式环境：取消信号（`withAbortSignal`）、取消（`withCancel`）、值注入（`withContextValue`）、遥测父级（`getTelemetryContext`）。**每个 harness API 都要求传 `context`**——这不是样板代码，而是取消传播与遥测串联的载体。

### 3.4 工具契约：比裸 Agent 多了三样东西

`AgentHarnessTool`（`harness/types.d.ts:78-81`）的 execute 签名是：

```ts
execute(toolCallId, params, onUpdate, toolContext, invocation, context)
```

比裸 `AgentTool` 多了：

1. **`invocation: AgentHarnessToolInvocation`**（`:66-76`）——稳定的调用身份（"unchanged during safe replay"），提供 **`getMemo` / `setMemo`**：工具自己可以存取持久化备忘，跨崩溃复用。
2. **`onUpdate(partialResult, { checkpoint?: true })`**（`:60-65`）——流式进度，且工具可**主动请求"替换本次调用的恢复检查点"**。
3. **`toolContext`**——由 `toolContext` 选项解析的宿主上下文（`AgentHarnessOptions.toolContext`，`agent-harness.d.ts:624`），每个 turn 快照解析一次。

官方内置工具只有 4 个工厂函数（`harness/tools/index.d.ts`）：`createReadTool` / `createWriteTool` / `createEditTool` / `createBashTool`。它们同样**把能力做成可注入**——例如 read 的 `ReadToolProcessor`（图片处理）是注入项（`harness/tools/read.d.ts:24-32`）。

### 3.5 事件与多端协议：watch / snapshot / reducer

harness 的事件面有约 30 种（`agent-harness.d.ts:206-420`），覆盖 run / turn / retry / message / tool / queue / config / compaction / navigation / lane / usage。

更有价值的是**为"远程消费者"准备的一整套协议**：

- `LaneSnapshot`（`:174-201`）——一条 lane 的完整快照（transcript、tip、配置、统计、当前操作、队列、故障标记）
- `LaneTranscriptSnapshot = JsonRepresentation<LaneSnapshot>`（`:472-473`）——严格 JSON 表示
- `LaneWatchEvent`（`:474-475`）——"Reducer-relevant strict-JSON Harness events published to remote transcript consumers"
- `reduceLaneSnapshot(snapshot, event)`（`harness/runtime/reducer.d.ts:3-4`）——把事件应用到快照，返回 `"rebase"` 时需重新取快照
- `WatchHandle<T>`（`:130-135`）——`snapshot` + `start(listener)` + `resnapshot(context)` + `unsubscribe`

**这套协议正好对应 Electron 的主进程/渲染进程分居结构**：主进程是 durable owner，渲染进程是 transcript consumer。目前我们是手写桥接（`bridge-agent-instance-events.ts`），框架则给出了标准形态。

⚠️ 但要注意成熟度：`Harness.watchSession` **尚未实现**——`harness/runtime/harness.js:229` 直接 `throw new SliceNotImplemented("watchSession")`，`agent-harness.d.ts:701` 仍保留该 API 签名。单 lane 的 `lane.watch()` 是实现了的（`lane.d.ts:88`），会话级 watch 要等"M8 切片"。

## 四、durable 深潜

这一章是本报告的重点：durable execution 是 harness 相对裸 `Agent` 最本质的增量，也是"能不能给我们的自主任务用"的关键判据。

### 4.1 问题定义

裸 `Agent` 的问题在长任务上暴露得最清楚：一次运行跨越几十次 provider 请求与工具调用，进程一挂，**"做到哪了"只存在于内存里**。重放全部会重复副作用（重发消息、重跑命令），不重放则丢失进展。

harness 的答案是：**把运行的每个推进边界都变成持久化状态**，进程重启后从最后状态继续，且区分"可重放"与"不可重放"的效果。

### 4.2 十三个状态叶子

`OperationState` 是一个显式的扁平状态机——注释原文（`session/types.d.ts:278-279`）：

> ```
> Flat durable operation state: exactly 13 family-neutral dispatcher leaves.
> ```

13 个状态（`:226-279`）：

```
starting → checkpoint → assistant.ready → assistant.effect_pending → assistant.retry_wait
        → tools → deferred.suspended → deferred.effect_pending
        → summary.deciding → summary.ready → summary.effect_pending → summary.retry_wait
        → navigation.ready_to_commit
```

四个族：**assistant**（生成）、**tools**（工具批）、**summary**（压缩/分支摘要）、**deferred**（异步响应），外加 checkpoint / navigation。每个状态都是 `at: "..."` 判别式联合，可独立持久化与恢复。

### 4.3 意图先写、结果 memo：崩溃安全的核心

durable 的键空间定义在 `harness/session/values.ts:75-93`，逐个看非常说明问题：

| 键 | 含义 | 为什么需要 |
| --- | --- | --- |
| `operationToolArgs(opId, stepId, sourceIndex)` | **工具参数在执行前就落库** | 崩溃后知道"打算做什么" |
| `operationToolMemo(opId, invocationId, name)` | 工具结果备忘 | 恢复时直接复用，不重复副作用 |
| `pendingToolOutput(opId, invocationId)` | 进行中的输出 | 中断时的部分结果 |
| `pendingAssistantFrames(opId, responseEntryId)` | assistant 流式帧 | 见 4.4 |
| `operationState(opId)` / `operationMeta(opId)` / `operationResult(opId)` | 状态/元数据/结果三件套 | 状态机的持久载体 |
| `operationPreparation(opId, taskId)` | 压缩/摘要的准备数据 | 摘要任务的输入也持久化 |
| `laneConfig(lane)` / `laneState(lane)` / `branchTip(branch)` | lane 与分支 | 恢复时重建 lane |

工具调用的生命周期因此变成一个小状态机（`session/types.d.ts:139-150`）：

```ts
export type ToolCall = { status: "planned" }
  | { status: "effect_pending"; replay: "never" | "safe" }
  | { status: "outcome_ready"; terminate: boolean }
  | { status: "completed"; terminate: boolean }
```

**`replay: "never" | "safe"` 是整个设计里最实用的一处**：工具在"效果发生前"声明自己能否重放。`never`（发消息、扣款、 spawn 一个已存在的子任务）在崩溃后不会被盲目重跑；`safe`（读文件、查询）可以。

### 4.4 崩溃恢复的三条路径

`harness/runtime/drive/` 下的模块就是恢复逻辑的分解：

| 路径 | 函数 | 注释（原文） |
| --- | --- | --- |
| 孤立的 assistant 请求 | `recoverAssistantGeneration`（`drive/recovery.d.ts:5`） | "Settle an orphaned assistant request from its bounded committed frame prefix **without another provider call**" |
| 已取消的孤立效果 | `recoverCancelledAssistantEffect`（`:7`） | "Synthetically settle one cancelled orphaned assistant or deferred effect under its reserved ids" |
| 取消后的推进 | `reconcileOperation`（`drive/reconcile.d.ts:4`） | "Advance one cancelled durable leaf **without starting new ordinary work**" |

第一条尤其值得注意：**它用已提交的流式帧前缀把请求"结算"掉，而不是重新发一次 provider 请求**。对于按 token 计费的场景，这避免了崩溃重试导致的重复计费与重复输出。

deferred（异步长生成）的重试语义更细（`drive/deferred.d.ts:9-11`）：`recoverDeferredPoll` 的注释是 "Replace one orphaned **unknown-outcome** poll under fresh ids"——一次 poll 的结果未知（进程死了）时，用**新 id** 重发，避免与可能已生效的旧 poll 冲突。

### 4.5 提交模型：决策与效果分离

运行时层的核心抽象是"命令"（`harness/runtime/types.d.ts:36-74`）：

```ts
export type LaneCommand<TResult> = (CommitDecision<TResult> & { next: LaneState })
  | { kind: "return"; result: TResult }
  | { kind: "reject"; error: Error }
```

即：**先算出一个纯决策（"effect-free decision"，`:42` 注释），再由框架配 commit 与 materialize**。配套约束：

- `SessionMutation.commit`："**Exactly zero or one commit attempt. A second attempt rejects.**"（`session/types.d.ts:428-433`）——一次突变事务至多提交一次
- `Lane.settleOperation`："The capability narrows the planner's state type; the Drive continuation remains **the sole top-level state writer**"（`runtime/lane.d.ts:37-42`）
- `Lane.continueOperation`："Returns `cancel_requested` without invoking the planner once cancellation is requested"（`:44-47`）——**取消后不再启动新钩子/效果/前进**
- 边界推进"at most one commit"：`runCheckpoint` 的注释是 "Advance one durable run boundary with **at most one commit**"（`drive/checkpoint.d.ts:7`）

这套"单写者 + 至多一次提交 + 决策与效果分离"的组合，是它敢声称 durable 的机制基础。

### 4.6 存储契约：官方明确指路"数据库后端"

`Storage` 接口 11 个方法（`session/types.d.ts:387-399`）：`commit` / `getEntries` / `getValue` / `scanValues` / `readList` / `scanBranch` / `scanBranchStructure` / `scanEntries` / `scanUsage` / `getStats` / `close`。

官方给的三条实现路线：

1. **`JsonlStorage`**（`session/jsonl/storage.js`）——append-only 的 JSONL：首行 header，之后每行一个 transaction（一个或多个 write 的 JSON 数组，`jsonl/io.js:51-63`）；写入串行化（`commitQueue`，`storage.js:23-24`）；整文件发布走"临时文件 + rename"原子替换（`io.js:65-78`）。
2. **`InMemoryStorageState`**——内存态。它的注释直接给出了**给数据库后端的设计指导**（`session/in-memory-storage-state.d.ts:5-10`）：

   > ```
   > This is intentionally unsuitable for database backends and long-running sessions that may not fit in memory.
   > Those backends should query indexed durable state and update durable aggregates within each commit transaction.
   > ```
3. **自实现** —— 有官方一致性测试套件可验：`./harness/session/testing` 子路径导出 conformance 测试（`harness/session/testing/conformance/storage.js` 33.5KB、`session-repo.js` 46.2KB），另有**性能基准场景集**（`testing/benchmark/storage.d.ts:20-23` 的读写场景）。

**对我们的直接含义**：本仓已有 SQLite。若走 harness，正确姿势是**实现一个 SQLite 版 `Storage`**（把 commit 做成一个事务），而不是迁到 JSONL 或内存态——而且官方给了 conformance 套件与基准，迁移不是"裸奔"。

### 4.7 成熟度与成本边界（必须先看清）

**成熟度证据**：

- `SliceNotImplemented` 异常类存在且被抛出：`harness/runtime/types.js:3-7`（消息为 `"${operation} is not implemented until its later AgentHarness slice"`），当前唯一抛出点是 `watchSession`（`harness/runtime/harness.js:229`）
- `SuspendedRun` 的注释：**"Convenience-only suspended run observation, constructed when M8 exposes public drive."**（`agent-harness.d.ts:13`）
- `Lane.requestOperationAbort` 的注释：**"Package-private durable cancellation primitive. Public exposure remains guarded until M8."**（`runtime/lane.d.ts:53`）
- 第二套内核 pico3 自称 Experimental（见 2.2）

即：**框架正在按切片（slice）交付，M8 之前 `drive` 与取消的部分公共出口还没开**。这解释了为什么它的 API 面里有一批"签了名但还没通电"的方法。

**成本与代价**：

- **写放大（推断，未实测）**：从 13 状态机与 `values.ts` 键空间推断，每个 durable 边界至少一次 commit（工具参数、工具结果、状态推进、消息落库各算），相比我们"流式结束写一次 + 100ms 节流"的做法，写次数显著增加。**此条是根据设计的推断，不是测量**——B1 试点时应实测任务耗时与 IO。
- **耐久性边界**：`JsonlStorage.applyCommit` 是普通 `appendFile`（`storage.js:97`），**没有 fsync**。因此它防的是"进程崩溃"（数据已进 OS 页缓存），不承诺"断电不丢最后几条"。这是合理取舍，但要理解它的边界。
- **内存态不适用长会话**：官方明说 `InMemoryStorageState` 不适合"可能装不进内存的长会话"（4.6 引文）。
- **单进程单写者**：pico3 注释明说 "A storage path has one owning process and one owning Session at a time"（`pico3/types.d.ts:8-9`）。我们的多窗口/多实例场景要落在这一约束内设计。

## 五、配套子系统

### 5.1 compaction：三段式产物与增量摘要

**配置极简**（`harness/compaction/compaction.d.ts:31-40`）：

```ts
{ enabled: true, reserveTokens: 16384, keepRecentTokens: 20000 }   // 默认值
```

**触发**：`shouldCompact(tokens, window, settings)` → `tokens > window - reserveTokens`（`compaction.js:144-148`）。触发原因有三条：`manual` / `threshold` / `overflow`（`agent-harness.d.ts:376`）。

**切点算法**（`compaction.js:205-294`）：
1. 收集"合法切点"——**toolResult 不是合法切点**（`:221-222`），避免把 assistant 的 tool call 与它的结果切散
2. 从尾部往前累加 token 直到超过 `keepRecentTokens`，取最近的合法切点
3. 若切点落在轮中间，回退到该轮起点（`findTurnStartIndex`，`:237-251`），并标记 `isSplitTurn`

**产物是三段，不是一段**（`CompactionPreparation`，`compaction.d.ts:96-113`）：

| 段 | 内容 | 去向 |
| --- | --- | --- |
| `messagesToSummarize` | 历史消息 | 生成摘要 |
| `turnPrefixMessages` | 被切断那一轮的头部 | 单独摘要（专用提示词 `TURN_PREFIX_SUMMARIZATION_PROMPT`，`compaction.js:480-493`） |
| `retainedTail` | 近期消息 | **原样保留**，存在 compaction entry 上 |

**增量摘要**（重点）：已有摘要时不重新摘要全部历史，而是让模型**更新**旧摘要。提示词原文（`compaction.js:330-339`）：

> ```
> The messages above are NEW conversation messages to incorporate into the existing summary provided in <previous-summary> tags.
> Update the existing structured summary with new information. RULES:
> - PRESERVE all existing information from the previous summary
> - ADD new progress, decisions, and context from the new messages
> - UPDATE the Progress section: move items from "In Progress" to "Done" when completed
> - PRESERVE exact file paths, function names, and error messages
> ```

摘要格式要求固定六节：`## Goal / ## Constraints & Preferences / ## Progress(Done·In Progress·Blocked) / ## Key Decisions / ## Next Steps / ## Critical Context`，并明确 "Keep each section concise. **Preserve exact file paths, function names, and error messages.**"（`compaction.js:298-329`）。

**文件操作记忆**：摘要生成时同步提取 `<read-files>` / `<modified-files>`（从 tool call 的 `path` 参数，工具名 read/write/edit 三选一，`compaction/utils.js:11-61`），随压缩详情一起持久化，且**上次的列表会被继承**（`compaction.js:16-41`）。

**可逆性**：原始消息**不删除**，压缩只是追加一条 `CompactionEntry { summary, retainedTail, tokensBefore, ... }`（`session/types.d.ts:27-35`）。pico3 侧同思路但更清晰——用 `head` 指针折叠逻辑视图（`pico3/kinds/entries.d.ts:50-57` 的 `SummaryEntry { data: { through }, head }`，配合 `pico3/harness.d.ts:134-138` 的"active transcript = H + head 之后的全部"定义）。

**token 估算的巧处**（`compaction.js:117-143`）：若历史里有 assistant 的 usage，则**以真实 usage 为锚**，只对 usage 之后的消息做启发式估算（`char/4`）。既准确又便宜。

**压缩本身也是 durable 操作**：它不是"顺手做一下"的辅助逻辑，而是与 `run` / `navigation` 并列的一等操作（`kind: "compaction"`），拥有自己的四个持久化状态叶子——`summary.deciding` → `summary.ready` → `summary.effect_pending` → `summary.retry_wait`（`session/types.d.ts:259-271`）。含义：压缩过程中的 provider 调用、重试、中断都可以崩溃恢复；且 `recoverStructuralGeneration` 专门处理"孤立的摘要生成尝试"（`drive/structural.d.ts:19`）。这套设计回答了我们压缩实现里最麻烦的一类问题：**压缩中途失败/被打断时，状态怎么办**。

### 5.2 会话树、fork 与 navigation

- **导航**：`navigateTree(targetId)` 回到树中任意历史节点（`agent-harness.d.ts:655`），离开的分支可用 `summarize: true` 生成 `BranchSummaryEntry`（`NavigateOptions`，`:43-47`）。这是一等公民操作（`kind: "navigation"`），有独立的 durable 状态 `navigation.ready_to_commit`。
- **fork**：`SessionRepo.fork(source, options)`（`session/types.d.ts:502-511`）两种粒度——
  - `scope: "branch"`：复制一条分支路径（可选 `entryId` 定位、`position: "before" | "at"`）
  - `scope: "tree"`：复制整棵会话树与所有分支
  实现上是构造目的地快照 `{ entries, scalarValues, nextSeq }`（`session/fork.d.ts:9-15`）。
- 还有一层 `fork-policy`（`harness/session/fork-policy.d.ts`）规定哪些历史可继承、哪些要重跑。

对我们而言这是**产品级能力的来源**：编辑历史消息后重新分支、会话分叉、以及"回到某个节点重来"的体验，框架里已经是数据模型的一部分，而不是 UI 层 hack。

### 5.3 skills 与 prompt templates

- **Skill**（`harness/types.d.ts:25-42`）：`{ name, description, content, filePath, disableModelInvocation? }`，从 `SKILL.md` 加载。注入分两处（`harness/skills.js:8-11`、`system-prompt.js:1-21`）：系统提示词里只放 `<available_skills>` 清单（name + description + location，XML 转义），显式调用时把全文包进 `<skill name=... location=...>` 块。`disableModelInvocation` 只影响模型可见性，不影响应用显式调用。
- **目录扫描约定**（`harness/skills.js:12-18`）：递归找 `SKILL.md`、根目录 `.md` 带 frontmatter 也算、尊重 `.gitignore/.ignore/.fdignore`；元数据有硬校验（name ≤ 64 且 `^[a-z0-9-]+$` 且与父目录同名，description ≤ 1024）。
- **PromptTemplate**（`harness/types.d.ts:43-51`）：`{ name, description?, content }`，支持 `$1` / `$@` / `$ARGUMENTS` / `${@:N:L}` 参数替换（`prompt-templates.d.ts:45-48`），从目录或文件加载并返回 diagnostics。

这层与我们仓库里已有的 skills/命令体系是**同构**的：对照价值大于替换价值——可以直接借用它的 XML 清单格式与元数据校验规则。

### 5.4 telemetry（pi-telemetry）

`pi-telemetry` 提供**类型化**的遥测能力：`defineTelemetrySchema` / `createTypedSpanStarter` / `InMemoryTelemetryContext` / `NOOP_TELEMETRY_CONTEXT`（`pi-agent-core/dist/index.d.ts:2-3`）。harness 内部已埋好 span（如钩子 span、`AI_TELEMETRY_SCHEMA` / `HARNESS_TELEMETRY_SCHEMA`，`index.d.ts:17-18`）。

关键性质：**默认 no-op**（`NOOP_TELEMETRY_CONTEXT`），不注入实现就不采集；schema 在先、属性强类型。对我们现有的中文日志体系而言，它是"结构化追踪"的可选补充，不是替代。

### 5.5 内置工具与截断

- 工具只有 4 个工厂（read/write/edit/bash），全部可配置、依赖可注入（见 3.4）。
- **截断工具**（`harness/utils/truncate.d.ts:1-42`）：双限（默认 2000 行 / 50KB），谁先命中算谁；**绝不返回半行**（tail 边界除外）；返回 12 字段的 `TruncationResult` 完整诊断（`truncatedBy` / `totalLines` / `outputLines` / `lastLinePartial` / `firstLineExceedsLimit` …）。
- **shell 输出的增量协议**（`harness/types.d.ts:260-275`）：`ShellOutputUpdate = replace | append | slide | metadata`——`slide` 是"窗口滑动丢弃前 N 字符"，专门服务长输出流式展示。

## 六、与 Lumii 现状的对照

### 6.1 三个已踩过的坑，框架里都已有正解

本次升级实测中查出的三个问题（详见升级评估 §8.2），恰好都对应 harness 里的一等公民机制——这说明**这些坑不是我们笨，而是裸 Agent 层的固有缺口**：

| 我们踩的坑 | 根因 | harness 里的正解 |
| --- | --- | --- |
| **system 消息被静默滤掉**（提示词与工具声明一起消失，inputTokens 掉到两位数） | `defaultConvertToLlm` 只放行 user/assistant/toolResult | `AgentHarnessOptions.toProviderMessages` 是显式的转换出口（`agent-harness.d.ts:633`）；另外 **pi-ai 提供了处理 system 消息收敛/保留的官方工具**——`resolveTranscript` / `collapseSystemMessages` / `getCurrentSystemMessage` / `getCurrentSystemPrompt`（`pi-ai/dist/utils/transcript.d.ts:32-41`），它们**不在 harness 里，在 pi-ai 的 `utils/transcript`，裸 Agent 用法也能直接取用** |
| **steering 退化**（工具批整批跑完才看插话；并行路径下 `beforeToolCall` 拦不住） | 裸 `Agent` 的 steering 轮询时机 + 批内并发 | `before_tool` 钩子返回 `{ block: { reason, terminate } }`（`agent-harness.d.ts:556-562`）是**受支持的语义**；且 harness 的 inbox 是持久化的（`InboxItem`），插话跨重启不丢 |
| **`edit-and-resend` 幽灵消息**（改了不存在的消息，仍无条件发给模型） | 自研链路缺存在性校验 | durable 的 `OperationMismatch` / `InvalidMessage`（`harness/result.d.ts:42-81`）把"操作与当前状态不匹配"变成**类型化的显式失败**，而不是静默通过 |

### 6.2 关键能力逐项对照

> 现状列来自本仓源码与升级实测；框架列见本文第二~五章。

### 6.3 一个必须点明的结构性差异

框架的并发模型是"**一个 Session 容器 + 多条 Lane**"，而本仓是"一个会话 = 一个 Agent 实例 = 一条对话线"。如果将来迁移，需要先决定映射方式：

- **方案 A**：一个 Lumii 会话 = 一个 Session + 一条 lane（如 `"main"`）——改动最小，但浪费多 lane 能力（子 Agent 仍走我们自己的 `spawn_agent`）
- **方案 B**：一个 Lumii 会话 = 一个 Session，主助手与团队成员各占一条 lane——能直接吃到框架的并发/隔离能力，但要重做会话 UI 的数据模型

另外，pico3 明说 "A storage path has one owning process and one owning Session at a time"（`pico3/types.d.ts:8-9`），**本仓的多窗口/多实例场景需要显式设计在这一约束内**（例如按会话分文件、由单一进程独占）。

### 6.4 若真要迁移，四个必须先解决的硬约束

梳理项目侧实现时发现的、会直接卡住迁移的四处（按难度排序）：

1. **存储模型冲突**：`messages` 表是"原地覆盖"（流式行被 `updateMessageContent` 反复覆盖），而 entry 树要求 append-only + `parentId`。要么新增一套 entry 表与现有表并存（双写，复杂），要么改造现有表（风险面大）。
2. **压缩口径要收口**：本仓有三条压缩路径（钩子内不落库 / 发消息前同步兜底 / idle 后台落库），注释里已明确要求三者共用 `getSessionContextUsage().triggerThreshold`。引入框架 compaction 就是**第四条**——迁移前必须先决定谁归谁。
3. **实例映射是分布式状态**：`sessionToInstance` 在 IPC 层，各渠道适配器又各维护一份；框架的"单写者 + 单 Session owner"要求集中化，这属于重构而非替换。
4. **自主任务的实例生命周期**：cron 现在是"新建 → prompt → 等空闲 → 销毁"。durable 化意味着实例要能被"挂起后由另一次进程启动恢复"，`resume()` 的调用点（谁在什么时候恢复）需要在新架构里明确。

> 这四条的共同点：**都不是 API 适配问题，而是数据与生命周期归属问题**。这解释了为什么升级评估里"把 `AgentInstance` 换成 `AgentHarness`"被估为架构大改。

### 7.2 B 档：中期候选（需局部试点或产品立项）

**B1 · durable 用于自主任务（最值得试点的落点）**

依据：cron 现在是 `cron:<jobId>` 新建实例 → `prompt` + `waitForInstanceIdle` → finally `destroy`。这意味着**任务跑到一半 App 退出/崩溃，这次任务的所有进展都丢失**，而自主任务（无人值守、可能长跑）恰恰是最需要续跑的场景（§6.2、§4.3）。

试点设计（隔离，不碰主链路）：
- 给 cron 任务单开一条 harness lane，存储先用官方 `JsonlStorage`（按任务分文件，天然满足"单文件单 owner"约束），不必立刻实现 SQLite Storage
- 验证点：① 任务跑到一半 kill 进程 → 重启 → 任务续跑；② 已完成的工具**不重跑**（`replay: "never"`）；③ provider 不重复计费（`recoverAssistantGeneration` 不重发请求）
- 退出条件：若写放大导致 cron 明显变慢，或恢复语义与我们的心跳/预算机制冲突，则记录结论后回退

**B2 · 会话树 / navigation（产品价值最高，迁移面最大）**

依据：NavigationResult / `navigateTree` / `fork`（branch/tree 两粒度）是框架一等公民（§5.2），而我们只有 `forkConversation` 这个"按锚点复制行"的按钮级原语。

两条路线，建议**先走轻量自研**：
- **轻量自研**：在 `messages` 表加 `parent_id`，把"编辑历史后重来"做成真正的分支——不引入框架，成本可控，且直接服务产品
- **借框架**：只有在 B1 的 durable 落地、且确认要长期走 harness 时才有意义（navigation 的完整语义依赖 durable operation）

**B3 · 多端协议（等 M8）**

依据：`LaneSnapshot` + `LaneWatchEvent` + `reduceLaneSnapshot` 正是主进程/渲染进程分居的标准形态，但 `watchSession` 目前直接抛 `SliceNotImplemented`（§3.5）。**现在能做的**是把我们 IPC 事件的形状与 `LaneWatchEvent` 的"严格 JSON + reducer 可归约"精神对齐，为将来铺路。

**B4 · 工具 invocation memo 的思路**

依据：`AgentHarnessToolInvocation.getMemo/setMemo` 让工具自己管理"跨重放复用的结果"（§3.4）。我们不必引框架，但这条思路可以用于我们已有的缓存类工具（如 web 缓存的命中/失效语义）。

### 7.3 C 档：暂不建议，及理由

| 项 | 不建议的理由 |
| --- | --- |
| **整体迁移到 harness** | ① 四条硬约束（§6.4）都要先解决，是重构不是替换；② 收益项（durable / 会话树 / 多端）已可由 B1/B2 局部获得；③ **风险：M8 未到 + pico3 可能取代旧栈**——现在投入的迁移可能白做 |

| **接入 pi-telemetry** | 默认 NOOP、零网络能力、无隐私风险，但也**没有现成收益**：它只是契约包，要自己写 adapter；我们的中文日志已满足当前诊断需求 |

### 7.6 专项：改造重构对"稳定性"与"架构"到底有多少提升

> 本节回答一个比"值不值得迁移"更根本的问题：**我们现在遇到的麻烦，框架是不是真的能解决？** 结论比前面的分档更保守。

#### 7.6.1 先说稳定性：我们的痛点不是"崩溃"，是"静默错误"

把本次升级与近期实测发现的缺陷列出来，模式立刻显现：

| 事故 | 表现 | 发现方式 |
| --- | --- | --- |
| `convertToLlm` 滤掉 system | 提示词 + 工具声明一起消失，对话"照常" | 靠端点的 inputTokens 掉到两位数，**人肉发现** |
| steering 语义退化 | 插话要等整批工具跑完才生效 | 构造场景实测 |
| `edit-and-resend` 幽灵消息 | 文本进了模型上下文，**库中完全不存在** | 用户复核时发现，排查中误导过一次判断 |
| `hasActiveUserTurn` 误判后台 cron | 心跳瘫痪 | 实验复盘 |
| 工作记忆注入时序失败 | 旧注入永不到达模型 | 实测对比 |

**五条没有一条是"崩溃"，全是"运行时不报错、功能静默失效"。** 这才是我们稳定性的真实病灶。

这个判断会**改变对 durable 的估值**：durable 最擅长的"进程崩溃后精确恢复"，对桌面应用是**中等价值**（崩溃不常发，且用户在场、重试成本低）；它真正能帮到我们的，是另外三件不那么显眼的事：

| 框架机制 | 对着我们的哪个病 |
| --- | --- |
| **显式失败**（`OperationMismatch` / `InvalidMessage` / `LaneBusy` 等 TaggedError） | 幽灵消息的本质就是"命中 0 行静默通过"。框架把"操作与状态不匹配"变成**类型化的失败**，而不是沉默 |
| **状态机穷举**（13 个叶子里没有"未知态"） | 我们崩溃/中断时那行 `is_streaming=1` 的占位处于什么语义？没有定义。框架不存在这个中间态 |
| **append-only 可回放**（entry 树 + 不可变的 `OperationResultRecord`） | 排查幽灵消息时"库里什么都没有"——**没有历史就没有取证**。这是我们最缺的一件东西 |

⚠️ **但必须点明**：这三条**不是迁移就自动获得**。框架提供的是"能做显式失败/能记历史"的机制，**要用起来仍得我们在自研层逐个接线**。指望"换个 runtime 就变稳"是不成立的。

**代价一侧**：迁移期本身是稳定性风险（双跑、回归），成熟度不足（M8 未到）是新的不确定性，范式从"命令式 + 补丁"转成"状态机 + 纯决策 + commit"后**写错状态机比写错 if 更难发现**。

#### 7.6.2 三条不依赖迁移、也不依赖框架的稳定性改进

顺着上面的诊断，有三件事**现在就能做，且直接对症**——它们比"迁移"更早、更便宜、更低风险：

1. **把"存在性 + 影响行数"校验从个例推广成规范**。幽灵消息的修复已开了头（`messageExists()` + `updateMessageContent` 返回行数 + 调用方双处拒绝）。同类隐患还有多少处"静默通过"的写入？值得做一次排查。
2. **给流式落库留不可变痕迹**。现在 `updateMessageContent` 反复覆盖同一行，出事后无法回放"当时写进去的是什么"。哪怕只加一张只追加的审计表，也能把"幽灵消息"这类问题的排查从"靠日志猜"变成"能对账"。
3. **压缩三路径的口径收口成代码而非注释**。现在"三者共用 `triggerThreshold`"写在注释里——这说明它是靠人守纪律。抽成一个函数/常量并加断言，成本极低。

> 这三条的 ROI 高于任何迁移动作，且**与将来是否迁移无关**——迁移了它们依然成立。

#### 7.6.3 再说架构：内核层是提升，系统层不是

要回答"架构上是否有较大提升"，必须先分清是哪一层：

**在内核层（单个 agent 运行时内部）——是真提升**：

| 我们现在的问题 | 框架的答案 |
| --- | --- |
| 职责边界靠约定（压缩 3 条路径、`MemoryIntegration` 名不副实、`setSystemPrompt` 实则改 `messages[0]`） | Session / Lane / Operation / Entry 四层各有明确契约与持久化边界；compaction 与 navigation 是**一等操作**，不是散落的工具函数 |
| 状态分散（pi 内存 / SQLite / 渲染层，靠 1241 行桥接同步） | **单一事实来源**：session 是唯一真相，UI 从 snapshot + events 派生 |
| 平台耦合 | 能力注入（`FileSystem` / `Shell` / `ExecutionEnv` / `Context`） |

**在系统层（我们真正的复杂度所在）——框架帮不上，甚至要我们让步**：

我们的领域形态是：多 Agent 实例、多渠道适配器、桌面 UI 富交互、定时自主任务、桌宠。而框架的模型是"**一个 Session 一个属主进程 + 若干 Lane**"——它没有为"多实例 + 多渠道 + 多入口"设计。强行映射的两种方案（§6.3）都不理想：方案 A 浪费 Lane 能力，方案 B 要重做会话数据模型。

更值得警惕的是**演进风险**：pico3 自称 harness-v3，等于官方认为现 harness（v2）的架构**还要改**。在它成型前投入迁移，是拿我们的稳定期去赌它的成熟期。

#### 7.6.4 结论：提升是"分层的"，且不来自整体迁移

| 问题 | 判断 |
| --- | --- |
| 稳定性会有较大提升吗？ | **上限显著，当下不会**。框架给出了治"静默错误"的机制，但要我们逐个接线；整体迁移期内反而下降。**三条不依赖迁移的改进能立即拿到大部分收益**（§7.6.2） |
| 架构会有较大提升吗？ | **内核层是，系统层不是**。分层与单一事实来源是真升级，但收益集中在 agent 内核；我们的主要复杂度（多实例/多渠道/UI 同步）不在它的射程内 |
| 那还迁移吗？ | **内核层值得借，整体不值得换**。若将来要换，合理窗口是"pico3 定型" + "我们做客户端解耦/平台移植"同时成立时 |

**一句话**：这个框架能治好我们一半的病（静默错误），但那一半的药**不用等迁移就能先吃起来**；另一半病（系统层复杂度）它本来就不治。

### 8.2 术语表

| 术语 | 含义 |
| --- | --- |
| **Lane** | 泳道：一条独立对话线（transcript 树 + 配置 + 收件箱 + 当前操作）；一个 Session 可有多条 |
| **Operation** | 操作：`run` / `compaction` / `navigation` 三类，各有 operationId 与 13 态持久化状态机 |
| **Entry** | 条目：transcript 树的节点（`message` / `compaction` / `branch_summary` / `custom`），靠 `parentId` 成树 |
| **durable** | 可持久化执行：每个推进边界落库，崩溃后可续跑；核心手段是"意图先写 + 结果 memo + 状态机" |
| **steering / followUp / nextRun** | 三种排队输入：插话（当前轮注入）、轮后追加、下次运行前注入 |
| **deferred** | 异步长生成：provider 后台生成，用 `DeferredHandle` 轮询取回 |
| **conformance 套件** | 官方为自定义 `Storage` / `SessionRepo` 提供的一致性测试（`./harness/session/testing`） |
