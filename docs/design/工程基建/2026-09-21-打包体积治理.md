> 日期：2026-09-21
> 范围：`apps/windows` 的 electron-builder 打包链路（Windows 为主，Linux 侧同步受益）
> 状态：已实施并验收（提交 `13908728` / `5d79cf44` / `e981537f` / `98d3b260`）
> 起因：跑「Windows 门槛 3」时发现产物不可用（electron-builder 缺陷，见
> [`../../plans/Linux客户端移植/2026-09-19-Linux桌面客户端第一期实施计划.md`](../../plans/Linux客户端移植/2026-09-19-Linux桌面客户端第一期实施计划.md) §9），
> 顺着查出「包体比记忆中的 ~170 MB 大了 80 MB」。**膨胀是静默的**——命令退出码 0、没有任何报错。

## 1. 结论摘要

| 指标 | 治理前 | 治理后 |
| --- | --- | --- |
| 安装包 `Lumii-Setup-*.exe` | 253.9 MiB | **162.3 MiB**（−36%） |
| `app.asar` 数据区 | 595.2 MB | **131 MB** |
| `release/win-unpacked` | — | 598 → 561 MB |

功能逐项实测无回退（判据见 §4）：asar 内 package.json 全可解析、启动四条就绪标记齐、
**Wiki/记忆嵌入仍走真 ONNX**（`backend:"transformers"`）、PDF 文本提取正常（118 页中文）。

## 3. electron-builder 的三条配置真相（都实测过，反直觉）

### 真相 1：`files` 的**顶层**模式只作用于 node_modules，**平台段**才作用于 app 目录

`release/builder-debug.yml` 里两套模式分得很清楚：

- `firstOrDefaultFilePatterns`（app 目录文件集）= `**/*` + `!**/node_modules/**` + 输出目录 + **平台段 `files` 的排除项**
- `nodeModuleFilePatterns`（node_modules 集）= `**/*` + **顶层 `files` 的全部模式**

踩过的坑：`!.mtbot/**` 写在顶层，重建后 asar 里 `.mtbot` 纹丝不动 —— 必须写进
`win.files` / `linux.files`。

### 真相 2：`asarUnpack` 是**第二套白名单**，`files` 的排除管不到它

`@xenova/transformers/dist/ort-wasm*.wasm` 三条路都试过：

| 配置 | 结果 |
| --- | --- |
| `files` 里 `!...dist/*.wasm` | **不生效** |
| 加上 `asarUnpack: node_modules/@xenova/transformers/**/*` | 被解包到 `app.asar.unpacked`（`@xenova` 共 45 MB） |
| 去掉那条 asarUnpack | 又整个塞进 `app.asar`（130 → 176 MB）——**安装包大小一模一样** |

即：`asarUnpack` 的模式同时充当「包含」规则，与 `files` 的排除是两套，压不到一起。
另外实测：`asarUnpack` 里写 `!` 取反只改变「解包与否」，不改变「是否进包」。

**顺带确认**：wasm 留在 asar 里由 Node 原生读没问题（Linux 那轮已验）。真正需要「真文件」的
只有 `node_modules/silk-wasm/lib/silk.wasm`（232 KB），所以顶层 asarUnpack 已从 `**/*.wasm`
收窄成它。

### 真相 3：只自动排除**当前**输出目录，兜底目录会把上一轮产物打进下一轮

`package-app.js` 在 `release/` 被占用时会兜底输出到 `release-build-<时间戳>/`，此时陈旧的
`release/` 不再被排除 → 被当 app 内容整包打进去（实测一次 **864 MB**）。已在平台段用
`!release*{,/**/*}` 统一覆盖（含 `release`、`release-build-*`、自建的 `release-trim` 等）。

## 4. 判据（可复跑）

`apps/windows/scripts/verify-win-package.mjs`（npm script `verify:win-package`，子命令
`asar` / `launch` / `all`，可用 `--release-dir` 指向兜底目录）：

| 子命令 | 判据 | 能抓到的缺陷 |
| --- | --- | --- |
| `asar` | 逐个 `package.json` 可解析；条目声明不超数据区；**体积护栏**（出现 `out/`、`node_modules/`、`package.json`、`config/` 之外的顶层项，或数据区 > 250 MB 即报错）；打印体积构成前 8 名 | asar 损坏（内容错位）、产物目录/开发文件混入、包体异常膨胀 |
| `launch` | 隔离数据根起 `win-unpacked/Lumii.exe`，等四条就绪标记（`日志系统已初始化`/`React 应用已挂载`/`窗口准备就绪`/`创建系统托盘`）、`Cannot find module` 计数 0、控制口就绪 | 打包产物根本起不来（今天真实发生过：只弹一个标题为 `Error` 的对话框） |

功能级判据（本轮新增的两条，用来证明「排掉的东西真的没人用」）：

- **嵌入**：`lumii-ui wiki vector rebuild` 必须返回 `backend:"transformers"`（不是 `bigram-hash`），
  日志出现 `[wiki-embedder] 已加载`
- **PDF**：用产物内的 pdf-parse 解析一份真实 PDF（走应用实际用的 esm 路径），页数与文本正确

> 判据本身也要拿已知反例试一遍：`asar` 用 ① 那份坏 asar 跑过，两条判据都拦下（退出码 1）。

| 项 | 体积 | 依据 |

| `@ffmpeg-installer/win32-x64` | 62 MB | ffmpeg.exe 本体（只装了 win32-x64，无跨平台浪费） |
| `sherpa-onnx-win-x64` | 22 MB | 语音 VAD/ASR |
| `onnxruntime-node` | 19 MB | 嵌入用的原生 ONNX（注意与 sherpa 的同名 DLL 顺序闸，见[同目录另一篇](2026-09-18-原生ONNX运行时加载顺序闸.md)） |
| `@img/sharp-win32-x64` | 19 MB | 图像处理 |
| `better-sqlite3` | 12 MB | 主数据库 |
| `@esbuild` | 12 MB | `src/main/ts-runner.ts` 运行时转译 TS 技能 |
| `out/` | 28.5 MB | 应用本体（含渲染层 chunk） |
| `@larksuiteoapi/node-sdk` / `playwright-core` / `pdf-parse` | 8.4 / 7.2 / 6.5 MB | 渠道、浏览器控制、文档解析 |

更激进的压缩要换策略（例如把 onnxruntime-web 的静态 import 从 transformers 里彻底摘掉、
或把嵌入模型改成纯按需下载），不是配置层面能做的。

## 6. 复发风险

- **`.mtbot/tool-results` 会继续长**：每次 dev 跑 agent 都往里写（单个结果可达 47 MB）。
  现在已排除出包，但它仍会占仓库磁盘；根治要让它默认落到客户端数据根（`.lumii`），属
  `packages/agent-runtime` 的改动，未做。
- **各种产物目录**：`release/`、`release-build-*/`、临时自建的 `release-*/` 都可能残留，
  已用 `!release*{,/**/*}` 兜住，但**新增别的名字的产物目录要记得加**。
- **新增依赖时**：先按 §2 第 3 条的「三条判据」判断它是否只在渲染层用；平台二进制注意
  §3 真相 2 的白名单语义。
