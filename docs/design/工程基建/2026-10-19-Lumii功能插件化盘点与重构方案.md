## 0. 结论先行

**这份文档回答的不是「插件系统怎么造」**（那是架构设计文档），而是三个更实际的问题：

1. 现有 30 多个功能模块里，**哪些真的值得插件化**；
2. 按什么顺序拆，才能**每一步都能独立验收、随时可回滚**；
3. 拆完之后靠什么**阻止它长回去**。

核心结论：

- **值得插件化的不是「大部分代码」，而是「有独立生命周期和独立故障半径的那部分」。** 按 2026-10-19 口径盘点，主进程约 **11.0 万行**非测试代码中，真正适合做成插件的约 **2.7 万行（25%）**；其余是核心服务或内核，做成插件只会增加间接层。
- **最大的收益不是「支持第三方插件」，而是把三个上帝对象拆开**：
  - `main/index.ts` 1999 行、直接 import 83 个模块、初始化顺序靠注释维护；
  - `agent-runtime/bridge.ts` 4484 行、134 个公开方法、被 37 个文件依赖；
  - IPC 共 **211 个通道 / 33 个命名空间**，没有「归属」元数据，新增功能只能继续往 `ipc-handlers-registry.ts` 里塞。
- **先接线，后搬家。** 不要求第一轮就移动几万个文件；先用 manifest + 生命周期把现有模块包起来，证明「可启停、可观测、可回滚」，再按收益迁移物理目录。
- **明确不做的事**：不引入 Cordis；不把 Agent 主循环、权限门、存储 schema、窗口创建做成插件；不为只有一个实现的接口造抽象。

三个量化目标（P5 验收）：

| 指标 | 现状 | 目标 |
| --- | --- | --- |
| `main/index.ts` | 1999 行 / 83 imports | ≤ 200 行，只保留阶段编排 |
| `bridge.ts` 公开方法 | 134 | 门面 ≤ 25，其余下沉到 6–8 个服务 |
| IPC 无归属通道 | 211 / 211 | 0（每个通道声明 owner + schema + 风险级） |
| >800 行文件 | 49 个 | 只降不升，拆一个收紧一格 |
| 冷启动到主窗口可交互 | 已有分阶段埋点 | 不回退；插件激活耗时单列预算 |

## 1. 盘点方法与判定标准

### 1.1 六条判据

一个模块是否值得插件化，不看它「像不像插件」，看这六条：

| 判据 | 问题 | 偏向插件 | 偏向内核/服务 |
| --- | --- | --- | --- |
| **状态所有权** | 它是否独占一份持久状态？ | 独占（如云同步游标、宠物注册表） | 共享（会话库、配置） |
| **可选性** | 用户能否不用它而应用仍完整？ | 能（录屏、语音、桌宠） | 不能（Agent 循环、模型调用） |
| **故障半径** | 它崩了会带走谁？ | 只带走自己（渠道适配器、外部进程） | 带走全应用（窗口、IPC 路由） |
| **外部依赖** | 是否依赖可选二进制/模型/网络服务？ | 是（ffmpeg、微信 exe、ONNX 模型） | 否 |
| **变更频率** | 是否经常独立迭代？ | 是（渠道协议、宠物、技能市场） | 否（存储 schema、安全策略） |
| **UI 面** | 是否拥有独立页面/卡片/设置区？ | 是（记忆页、设置分区） | 否（全局壳） |

**四条中三条命中 → 插件；两条以下 → 核心服务或内核。**

### 1.2 四档分类

本文统一使用四档，避免「插件」一词被滥用：

| 档位 | 定义 | 生命周期 | 能否禁用 | 示例 |
| --- | --- | --- | --- | --- |
| **内核（kernel）** | 应用存在的前提，启动顺序固定 | 与进程同生共死 | 否 | 窗口、配置、日志、IPC 路由、协议注册 |
| **核心服务（core service）** | 必需能力，但有明确接口与状态边界 | 常驻，可独立启动/停止 | 否（可配置） | Agent Runtime、工具注册表、技能运行时、渠道 Hub |
| **内建插件（built-in plugin）** | 随包分发、可禁用、有 manifest | 可激活/停用/重载 | 是 | 云同步、语音、录屏、桌宠、渠道适配器 |
| **资产组件（asset）** | 不执行代码的外部文件/模型/二进制 | 按需安装/卸载 | 是 | ffmpeg、CloakBrowser、微信 MCP exe、宠物模型 |

> 现有「插件中心」实际管理的是**资产组件**。代码插件落地后，UI 文案建议改为「扩展中心」，分「功能扩展 / 组件资源」两栏；否则两个「插件」概念会在支持与文档上长期打架（见 §12 待决策 D4）。

## 3. 现状耦合：五个「病灶」与证据

### 3.1 `main/index.ts` 是隐式状态机

- 1999 行，直接 import **83 个模块**；
- 全局单例集中声明在 224–272 行；
- `initialize()` 从 1195 行到约 1786 行，**约 590 行线性脚本**，顺序只靠注释保证；
- `setupIpcHandlers()`（1069）把 **13 个 getter + 6 个回调/缓存注入**手工塞给注册器；
- 初始化顺序错误会导致「注册时依赖还没建好」，只能靠 getter 延迟取值兜底（如渠道登录服务）。

这不是「文件大」的问题，是**没有阶段与依赖声明**的问题。拆文件但不拆顺序，只是把 1999 行摊到 6 个文件里。

### 3.2 `bridge.ts` 是上帝门面

- 4484 行、**134 个公开方法**，被 **37 个文件** import；
- `bridge-utils.ts` 被 **47 个文件** import——工具函数已经变成事实上的全局层；
- 方法横跨：会话、模型上下文、压缩、工具注册、提示词、渠道分发、微信回放、宠物目标、Wiki、图片生成、数据库备份、技能进化。

结论：**不能直接把它「插件化」**。正确做法是先做门面（Facade）+ 领域服务拆分，让外部依赖从 134 个方法降到个位数接口。

### 3.3 IPC 无归属

- 211 个通道散落在 41 个文件；
- `ipc-handlers-registry.ts` 只集中了一部分，Coding Dev、SkillNet 等仍是各自注册；
- preload `index.ts` **1325 行**，手写扁平 API，新增通道要改三处（主进程、preload、类型）；
- 当前实测**无重复通道**（0 条），但没有守卫：`handle` 重复会在启动时抛错、`on` 重复会静默叠加监听器；
- 无 sender 校验统一口、无 schema 校验。

### 3.4 一个功能横跨五六个面，但没有「一次注册」的地方

以云同步为例，它同时拥有：

1. `CloudSyncManager` + `SyncScheduler`（服务）
2. 11 个 IPC 通道
3. 10+ 条 `app-ui-control` HTTP 路由
4. 设置页 `CloudSyncSection`
5. 冲突回调直接写在 `index.ts` 里，反向依赖 `agentRuntimeBridge`

现在「删掉云同步」需要改 5 个地方，且没有清单。插件化的真正价值是让这 5 个面**在一个 manifest 里声明、一次启停**。

### 3.5 拆分后回涨，是已经发生过的事实

`docs/plans/代码重构/README.md` 的结论：

> 拆分方案不是瓶颈，「拆完没有东西阻止它长回去」才是。
> `bridge.ts` 在 3 周内从 1483 行涨到 2717 行；当前 4484 行。

当前门禁：`check:large-files` 棘轮（阈值 800，允许 +20）、`check:wiring`、`knip`、`typecheck`。**本文的所有拆分动作必须同步收紧棘轮基线**，否则 P5 时会回到今天的数字。

## 4. 目标架构

### 4.1 分层与依赖方向

```
┌──────────────────────────────────────────────────────────────┐
│ apps/windows/src/renderer                                     │
│  Shell(App/Router/SettingsHub/Chat)  SlotRegistry  CardRegistry│
│  Plugin views / settings sections / chat parts                 │
└───────────────▲───────────────────────────┬──────────────────┘
                │ preload（由 contribution 生成） │
┌───────────────┴───────────────────────────▼──────────────────┐
│ main: kernel（内核）                                           │
│  bootstrap 阶段 / window / tray / config / log / protocols    │
│  IpcRouter / ContributionRegistry / PermissionGate / Perf     │
└───────────────▲───────────────────────────┬──────────────────┘
                │ 只依赖 plugin-sdk 契约       │
┌───────────────┴───────────────────────────▼──────────────────┐
│ services（核心服务，常驻）                                      │
│  AgentRuntime / Conversation / Llm / ToolRegistry / Skill     │
│  ChannelHub / Usage / Mcp / Updater                           │
└───────────────▲───────────────────────────┬──────────────────┘
                │                            │
┌───────────────┴───────────────────────────▼──────────────────┐
│ plugins（内建插件，可启停）                                     │
│  cloud-sync / voice / screen-record / pet / channels adapters │
│  coding-dev / vcs / browser / dashboard-feed / skill-evolution │
└───────────────▲──────────────────────────────────────────────┘
                │
┌───────────────┴──────────────────────────────────────────────┐
│ adapters / assets（外部世界）                                   │
│  微信/企微/飞书/QQ 协议 · MCP 子进程 · ffmpeg · Chromium · 模型   │
└──────────────────────────────────────────────────────────────┘
```

**硬规则（用守卫强制，不靠自觉）：**

1. 依赖只能**向下**：plugin → sdk/core，service → sdk/core，kernel → 什么都不依赖（除 Electron/Node）。
2. **插件之间不互相 import。** 需要协作走事件或服务接口；两个插件强耦合 → 合并或上提为服务。
3. **一个状态只有一个所有者。** 其他模块只能通过接口读写，禁止直接碰数据库/文件。
4. 插件不得 import `apps/windows/src/main/**` 的内部实现，只能 import `@lumii/plugin-sdk`。
5. 内核不 import 插件；插件在 manifest 中声明激活条件，由宿主拉起。

### 4.2 包布局（目标，非一次到位）

```
packages/
  plugin-core/          # Context / Service / EffectScope / EventBus / Manifest 校验
  plugin-sdk/           # 主进程与渲染层共享的契约、类型、贡献定义
  plugin-host-main/     # 主进程 PluginHost（加载、激活、重载、观测）
  plugin-host-renderer/ # 渲染层 SlotRegistry / CardRegistry / 懒加载工厂
  agent-runtime/        # 已有，逐步变成 service 层实现
  pet-core/ pet-asset/  # 已有，保持
  protocol/ client-sdk/ # 已有
apps/windows/src/main/
  kernel/               # bootstrap、window、tray、config、log、protocol、ipc-router
  services/             # 领域服务（bridge 拆出来的）
  plugins/              # 内建插件，一目录一插件
  adapters/             # 渠道协议、外部进程
```

**但 P0/P1 不移动任何大目录。** 先在原地加 `plugin.json` 与 `activate(ctx)` 包装，验证契约；P2 起只迁“拆完确实变小、依赖确实变少”的部分。

### 5.2 生命周期与激活时机

不是所有插件都在启动时激活。三类激活条件：

| 类型 | 触发 | 例子 |
| --- | --- | --- |
| `startup` | 应用启动 | 云同步（要在窗口前建立状态）、渠道 Hub 适配器（用户已登录时） |
| `on-demand` | 首次使用/首次打开页面 | 语音、录屏、桌宠、VCS、编码后端 |
| `event` | 事件/命令触发 | 划词、文件预览、SkillNet 安装后刷新 |

宿主必须提供：**激活超时（默认 10s）、失败标记、UI 可见的降级提示、重试入口**。激活失败不得阻塞启动。

## 6. 逐模块重构方案

### 6.1 `main/index.ts`：从线性脚本到阶段编排

**目标结构：**

```
main/kernel/
  bootstrap.ts        # app 事件、单实例、scheme、whenReady、AppUserModelId
  lifecycle.ts        # 阶段注册与依赖拓扑、ready gate、cleanup 栈
  ipc-router.ts       # 统一 handle/on、sender 校验、schema、owner 元数据
  protocols.ts        # lumii-local / lumii-pet
  observability.ts    # logger + PerformanceMonitor 装配
main/services/*/bootstrap.ts   # 每个服务导出 { start(ctx), stop() }
main/plugins/registry.ts       # 读取 manifest，按激活条件拉起
main/index.ts                  # ≤200 行：调用 lifecycle.run(stages)
```

**阶段与依赖（显式声明，不再靠注释）：**

```
S0 pre-ready   : 单实例、scheme、命令行开关
S1 foundation  : logger → config/directory → perf
S2 kernel-io   : ipc-router → protocol handlers → ready gate
S3 core        : agent-runtime(bridge) → tool/skill → channel hub
S4 plugins     : (并行，失败隔离) cloud-sync / voice / screen-record / pet / vcs / coding-dev
S5 ui          : window → tray → app-ui-control → pet window
S6 post-ready  : updater check、后台预取、维护任务
```

**关键改动：**

- 去掉 `initialize()` 里的全局单例赋值，改成 `ctx.services` 注册；
- 每个阶段返回结果，`lifecycle` 记录耗时并写入现有 `recordStartupPhase`；
- 清理逻辑进 LIFO 栈（与插件 effect 同一套），替换 `performCleanup` 的手写顺序；
- 渲染进程早于 S3 的调用继续返回 `NOT_READY`（现有做法正确，保留为内核能力）。

**验收：** `index.ts` ≤ 200 行；阶段依赖图可导出为 JSON；断掉任一可选插件仍能启动。

### 6.2 `AgentRuntimeBridge`：门面 + 领域服务

按现有 134 个方法聚类，拆成 8 个服务（方法数按粗分，落地时逐条对账）：

| 服务 | 职责 | 约方法数 |
| --- | --- | --- |
| `ConversationService` | 会话、消息、压缩、上下文用量 | 25 |
| `ModelService` | provider 选择、模型目录、思考档位、图片识别/生成 | 20 |
| `ToolService` | 工具注册、进化工具、权限门、调用统计 | 20 |
| `PromptService` | system prompt 组装、记忆注入、风格 | 15 |
| `ChannelDispatchService` | 入站/出站、微信回放、渠道上下文 | 20 |
| `AutonomousService` | 自主目标、心跳、宠物目标 | 15 |
| `KnowledgeService` | Wiki、记忆、导出、嵌入 | 10 |
| `MaintenanceService` | 备份/恢复、数据清理、迁移 | 10 |

**做法：**

1. P2-1：先定义 8 个接口，`AgentRuntimeBridge` 变成**只做转发的门面**（Facade），方法体逐个搬走，外部调用点零改动；
2. P2-2：把 `bridge-utils.ts`（fan-in 47）按领域拆成 3–4 个模块，禁止继续堆通用函数；
3. P2-3：IPC / 渲染层逐步从 `bridge.xxx` 改调具体服务接口，门面方法标记 deprecated；
4. P2-4：门面稳定后，删除无消费者的转发方法（用 `check:wiring` 的无消费者清单）。

**风险控制：** 这是全仓最高风险改动。每个服务迁移单独 PR + 现有测试全绿 + 至少一条实测（`lumii-ui` 驱动真实回合）验证。

### 6.3 IPC：从 211 个通道到「有主的 211 个通道」

**P0 只做元数据，不改通道名：**

```ts
interface IpcContribution {
  channel: string                 // 保留现有命名，先不重命名
  owner: string                   // 插件 id / service id
  kind: 'invoke' | 'send' | 'on'
  schema?: ZodType                // 入参校验
  risk: 'read' | 'write' | 'control' | 'destructive'
  exposeToControlPlane?: boolean  // 默认 false
  handler: (event, ...args) => unknown
}
```

**四项守卫：**

1. 注册前检测重复通道 → 给出「通道 + 两个 owner」的明确错误（当前实测 0 条重复：`handle` 重复会由 Electron 抛错、`on` 重复则静默叠加监听器）；
2. 所有 `ipcMain.handle/on` 只能经 `ipc-router`，禁止直接调用（AST 守卫）；
3. sender 校验集中一处（window id + URL 白名单），不再各 handler 自行判断；
4. 控制面（`app-ui-control` / `lumii-ui`）只暴露 `exposeToControlPlane: true` 且 `risk` 允许的通道；现有 `command-allowlist.ts` 保持默认拒绝，插件贡献不能自行放开。

**preload 生成：** P4 起，从 contribution 清单生成 `preload/api/<namespace>.ts`，消灭 1325 行手写。生成前保留手写文件作为对照，逐 namespace 切换，避免一次性全量替换。

### 6.4 渠道：Hub 核心 + 四个适配器插件

**保留在 `ChannelHub`（核心服务）：**

- 会话/peer 映射、入站归一化事件、出站队列、回复路由、能力协商；
- `peers` 请求时快照语义不变；
- 「省略 channel/to 必须回来源渠道，能力不足如实报错」的兜底放在 Hub，而不是各适配器。

**迁移为插件：**

| 插件 | 现有代码 | 说明 |
| --- | --- | --- |
| `channel-weixin` | `weixin-*-service.ts`、`channel/adapters/weixin-*`、`wechat-watch-tick.ts`（1800 行）、`weixin-media-reply` | 微信盯梢/回放整体归属该插件 |
| `channel-wecom` | `wecom-*` | 登录、适配器 |
| `channel-feishu` | `feishu-*` | 登录、应用注册、适配器 |
| `channel-qbot` | `qbot-*` | 登录、适配器 |

**适配器接口（能力声明）：**

```ts
interface ChannelAdapter {
  id: string
  capabilities: { text: true; image?: boolean; file?: boolean; voice?: boolean; quote?: boolean }
  login(): Promise<LoginState>
  send(msg: OutboundMessage): Promise<SendResult>

```

**验收：** 禁用任一渠道插件后，其余渠道、聊天主流程、设置页均正常；出错只影响该渠道，不产生未处理 rejection。

### 6.5 `app-ui-control`：宿主 + 路由贡献

现状：一个 1116 行 server 文件里混装 skills、pet、cloudSync、channel、provider、settings、screenshot/act 等路由。

**拆分：**

```
app-ui-control/
  server.ts          # 鉴权、端口、runtime.json、错误信封、路由分发
  routes/system.ts   # status/health
  routes/ui.ts       # screenshot/act（保持 allowlist）
  routes/skills.ts
  routes/pet.ts
  routes/cloud-sync.ts
  routes/channel.ts
  routes/provider.ts
  routes/settings.ts
```

每个路由模块导出 `ControlRoute[]`，由宿主注册。**控制面安全策略不下放**：`ACT_ACTIONS`、字段 denylist、默认拒绝仍在内核；插件只能声明「允许被控制」，不能声明「绕过校验」。

### 6.6 云同步：第一个全栈样例（P1）

选它做样例的原因：它同时覆盖服务、任务、IPC、HTTP、设置页、事件六种接缝，但故障半径小、可禁用、状态独立。

**manifest 草案：**

```json
{
  "id": "cloud-sync",
  "kind": "code",
  "activation": "startup",
  "contributes": {
    "services": ["cloudSync"],
    "ipc": ["cloudSync:*"],
    "controlRoutes": ["cloud-sync/*"],
    "settingsSections": ["cloud-sync"],
    "jobs": ["sync-scheduler"]
  }
}
```

**解耦动作：**

- 冲突回调不再在 `index.ts` 里直接调 `agentRuntimeBridge`；
- 改为 `ctx.emit('cloud-sync:conflict', conflict)`，由 Agent Runtime 侧订阅并创建维护目标；
- 若订阅方缺席，事件只记录不报错（插件不得假设别人在）。

**验收：** 禁用云同步 → 无 IPC 残留、无定时器残留、设置页不显示该分区；重新启用无需重启。

### 6.7 语音 / 录屏：懒激活 + 资产依赖

两者共同点：可选、依赖大件、启动时不必要。

- 激活条件：首次打开对应设置区或首次调用工具；
- manifest 声明 `requires.assets: ['ffmpeg']`；宿主解析不到时插件进入 `DEGRADED`，UI 显示「缺少组件」并提供安装入口；
- ONNX 加载顺序闸（`onnx-runtime-gate.ts`）**留在内核**：它是进程级约束，不是某个插件的私事；
- 录屏的窗口捕获能力探测放插件内，但「窗口创建/媒体协议」仍在内核；
- 若实测某个操作阻塞主线程 >50ms（模型加载、ffmpeg 探测），迁到 `utilityProcess`；**先测再迁**，不预先上进程隔离。

### 6.8 桌宠：独立窗口插件

- 已有 `pet-core` / `pet-asset` 包，边界最好，迁移成本最低；
- 插件持有：注册表读取、窗口管理、`lumii-pet://` 协议的**使用方**（协议注册仍在核内）、模式状态、托盘联动命令；
- 注意既有约束：`registry.json` 每进程只读一次；点击映射 `tapMotions` 为空则静默无效——插件重载必须提供显式 `reloadRegistry()`，不能靠重启应用；
- 激活条件：用户开启桌宠模式；关闭时释放窗口与定时器，但保留设置。

### 6.9 技能与自进化

区分三件事：

| 能力 | 归属 | 理由 |
| --- | --- | --- |
| 技能解析、加载、注入提示词 | **核心服务** | Agent 主流程依赖 |
| 技能商店 / 外部安装 / 导入导出 | **内建插件** | 可选、网络依赖 |
| 技能自进化（`skill-evolution/`） | **内建插件（默认 disabled）** | 当前已停用但保留 |

`skill-evolution` 不要再以「不可达的 9 个文件」形式存在——manifest 中显式 `disabled: true`，守卫据此豁免，启用时走正常激活路径。

## 7. 设计模式映射（只映射真实接缝）

| 模式 | 落点 | 现状 | 重构后 |
| --- | --- | --- | --- |
| 微内核 | 主进程 | `index.ts` 隐式承担 | kernel + host + plugins |
| 依赖倒置 | 插件 → 宿主 | 直接 import 内部模块 | 只依赖 `@lumii/plugin-sdk` |
| 门面 | `AgentRuntimeBridge` | 上帝对象 | 薄门面 + 领域服务 |
| 策略 | provider、渠道、捕获后端 | 已有分支 | 统一接口 + 注册 |
| 适配器 | 微信/企微/飞书/QQ、外部二进制 | 各自实现 | `ChannelAdapter` / asset resolver |
| 注册表 | ToolRegistry、IPC、卡片、Slot | 部分存在 | 全部统一为 contribution |
| 责任链 | `ToolHook` before/after | 已存在 | 扩展到 IPC/控制面中间件 |
| 观察者 | runtime events、渠道事件 | 已有 EventEmitter | 类型化事件总线 + effect 反注册 |
| 模板方法 | 插件生命周期 | 无 | `activate/deactivate` 由宿主模板化调用 |
| 状态机 | Fiber、宠物模式、同步状态 | 分散 | 统一 `PENDING/ACTIVE/FAILED/DEGRADED/DISPOSED` |
| 仓库 | 会话/记忆/Wiki | 已有 repo | 保持；插件不得直连数据库 |
| 工厂 | `assembleAgent`、`host-kit` | 已存在 | 保持，作为服务组装点 |
| 惰性代理 | 重模块加载 | 部分 dynamic import | 激活时加载，启动不 import |
| 断路器 | 渠道健康、provider 探测 | 分散 | 统一 health/backoff，失败隔离 |

**反模式红线：**

- 不为单一实现造接口（如「只有一个 provider 的 provider 接口」可以等第二个实现出现）；
- 不把事件总线当万能胶：跨插件协作超过两跳，改为显式服务接口；
- 不用 service locator 满天飞：`ctx.get()` 只允许在激活阶段，运行期持有注入的依赖；
- 不为了「插件化」把同步调用改成异步：IPC/控制面的行为变化必须有独立收益。

## 8. 五个目标的对应措施

### 8.1 更精简

- 删除重复注册：IPC、控制面路由、设置分区各收敛为一处；
- 删除「停用但保留」的不可达代码，改为 manifest `disabled`；
- 删除无消费者 IPC（`check:wiring` 已报 38 条待决策）；
- 不新增抽象层：插件包装优先「原地」，不为分层而搬文件。

### 8.2 更稳定

- **失败边界**：激活/调用 per-plugin try/catch，插件失败 → `FAILED`，应用继续；
- **两阶段启动**：注册（同步、快）与激活（异步、可失败）分离；
- **effect 作用域**：所有注册可逆，LIFO 清理，重载不泄漏；
- **降级可见**：UI 上明确显示「某扩展不可用」，而不是静默少一块功能（已有教训：配置读一次、tapMotions 为空静默无效）；
- **超时与熔断**：外部进程（MCP/微信）健康检查 + backoff，不因外部故障拖死主进程；
- **不可插件化清单**：权限门、路径 ACL、sender 校验、存储 schema 迁移——这些出错是安全问题或数据丢失。

### 8.3 更解耦

- 依赖方向守卫（§10）；
- 状态所有权表；
- 插件间禁 import；
- 事件只承载「通知」，不承载「请求」；请求走接口。
- 控制面/渲染层通过生成的 preload 契约访问，不再手写三处。

### 8.4 更高性能

- **懒激活**：语音、录屏、桌宠、编码后端不在启动路径；
- **启动预算**：每阶段与每插件记录耗时，超过预算告警（现有 `PerformanceMonitor` 扩展）；
- **IPC 批处理**：高频事件（流式 part、性能采样）合并发送，避免每 token 一次 IPC；
- **渲染**：插件视图懒加载 + 现有消息窗口化；卡片注册表避免整棵子树重渲染；
- **进程隔离**：只对实测阻塞 >50ms 或会崩溃的任务（模型、ffmpeg、浏览器）用 `utilityProcess`；
- **缓存**：manifest 与注册表读一次并缓存，提供显式 reload（不要每次调用重读磁盘）。

### 8.5 更易扩展

- 新增一个功能 = 一个目录 + manifest + `activate`；
- 新增 IPC = 一条 contribution，preload 自动生成；
- 新增设置区/页面/卡片 = 声明式贡献，不改壳；
- 新增渠道 = 实现 `ChannelAdapter`，不改 Hub；
- 新增资产 = `kind: 'asset'`，复用现有安装器。

## 11. 风险与不做什么

### 11.1 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 插件在主进程内 = 完全信任 | 恶意/有 bug 的插件可读密钥、写文件 | 内建插件才允许同进程；第三方需 D1 决策 + 进程隔离 |
| 拆分 bridge 引入回归 | 聊天/渠道/工具全受影响 | 门面兼容 + 分批 + 每批实测 + 可回滚 |
| 插件激活顺序错误 | 注册缺失/重复 | 显式依赖 + 拓扑排序 + 启动自检 |
| 事件总线滥用 | 难以追踪的隐式耦合 | 事件只通知；跨插件请求走接口 |
| 插件数量膨胀 | 启动变慢、维护成本上升 | 内建插件默认随包但懒激活；每个插件必须有 owner 与测试 |
| 拆分后回涨 | 3 周回到今天 | 棘轮 + 文件归属规范 + PR 检查 |

### 11.2 明确不插件化

- Agent 主循环与工具执行核心（`packages/agent-runtime`）；
- 权限门、路径 ACL、控制面 allowlist；
- 配置与凭据管理；
- 存储 schema 与迁移；
- 窗口创建、单实例、协议注册；
- 日志与性能监控的下限能力。

**理由：** 它们要么是安全边界，要么是全局不变量，要么被所有插件依赖。把它们做成插件，只会得到「一个必须永远启用、但多了一层间接调用的插件」。

### 11.3 不做的事

- 不引入 Cordis 作为第三套内核；
- 不为「未来可能有第二个实现」预造接口；
- 不在 P0/P1 移动大目录；
- 不把资产安装器改造成代码插件；
- 不追求「所有功能都能热更新」：主进程代码热重载的收益远小于风险，先做启停与重载。
