# Lumii 插件化架构设计方案

> 状态：**设计待评审**
> 日期：2026-10-19
> 范围：`packages/plugin-core`（新增）、`apps/windows` 主进程与渲染层、插件中心
> 目标：内核稳定、前后端能力可插件化、前端卡片化动态加载 + 热更新、后端可扩展/可控制/可监测
> 前置研究：[`../../reference/开源项目解构/deepseek-harness/设计解构.md`](../../reference/开源项目解构/deepseek-harness/设计解构.md)

## 0. 结论摘要

**推荐路线：借 Cordis 的契约，不引入 Cordis 本体。**

Lumii 已经有两套底层：Electron 主/渲染双进程，以及 `@earendil-works/pi-agent-core` 的 Agent 循环。再引入一套 Cordis loader/HMR，会让启动、构建、类型、调试都变成三套。正确的做法是：

1. 新建 `packages/plugin-core`，实现 **Context / Service / Effect / Event** 四个最小契约；
2. 主进程与渲染层各有一个 **PluginHost**，共用同一份 manifest 类型；
3. 现有功能按"低风险 → 高风险"逐步迁移为内置插件；
4. 前端复用现有 **A2UI 卡片渲染器**，把固定 `switch` 改成可扩展注册表，再加 slot 与插件模块加载；
5. 插件中心从"资产下载器"升级为"代码插件 + 资产插件"的统一管理面。

分四期：

| 期 | 内容 | 风险 | 可独立验收 |
|---|---|---|---|
| **P0** | `plugin-core` 内核 + manifest + 注册表 + 单测；不改变任何现有行为 | 低 | 内核测试全绿、App 行为不变 |
| **P1** | 主进程 PluginHost，迁移低风险功能（性能监控、云同步、录屏、控制口） | 中 | 禁用某插件后功能消失、进程不崩 |
| **P2** | 渲染层 PluginHost：slot、卡片注册表、模块懒加载、设置页/视图迁移 | 中高 | 示例插件可装/可卸/可热更 |
| **P3** | 插件中心统一、代码插件安装/升级、开发者工具与监测面板 | 中 | 端到端安装一个外部插件 |

## 1. 现状与问题

### 1.1 现在的"插件"是什么

`apps/windows/src/main/plugins/plugin-manager.ts` 的 `PluginHandler` 只做三件事：

```ts
interface PluginHandler {
  id: string
  status(): Promise<PluginInstalledStatus>
  install(onProgress, signal): Promise<void>
  uninstall(): Promise<void>
}
```

它解决的是**大体积可选资产**的下载/落盘/卸载（CloakBrowser、ffmpeg、wechat-mcp、宠物包），见 [`2026-10-11-可选组件插件化设计.md`](2026-10-11-可选组件插件化设计.md)。这层机制值得保留，但它不是"代码插件"。

同时，渲染层 `PluginCenterPage/plugins-registry.ts` 有一份硬编码清单，主进程 `builtins.ts` 有另一份；注释明确要求"两边按 id 保持同步"。这是典型的**清单双写**，也说明当前模型承载不了动态插件。

### 1.2 主进程的接线痛点

`apps/windows/src/main/index.ts` 约 2000 行，把窗口、托盘、系统服务、Agent 运行时、渠道、语音、录屏、技能、云同步、性能监控、控制口、插件 IPC、MCP 配置全部串在一个 bootstrap 里。`ipc/ipc-handlers-registry.ts` 又用 `IpcHandlersDeps` 把十几组 getter 传给各模块。

结果是：

- 加一个可选功能要改 3–5 个文件，且顺序敏感；
- 无法按用户配置启用/禁用；
- 无法热卸载，出问题只能重启；
- 无法回答"这个功能是谁注册的、占了多少资源"。

### 1.3 已经具备的底座

| 能力 | 现状 | 对插件化的价值 |
|---|---|---|
| Agent 装配 | `packages/agent-runtime/src/host-kit/` 已有 `assembleTools` / `assembleSystemPrompt` / `assembleAgent` / `createPermissionGateHook` | 工具与权限插件天然有落点 |
| 工具注册 | `ToolRegistry.register/unregister` + `ToolRunner` + `ToolHook` | 已有可逆注册与横切钩子的雏形 |
| 事件 | 主进程 → 渲染层的 `subscribeMainEvent`、Agent 事件流、`app-ui-control` | 可收敛为类型化事件总线 |
| 卡片渲染 | `A2UIRenderer` + `parseA2UIBlocks`，12 种组件 | **前端卡片化的现成底座** |
| 消息时间线 | `AssistantPart`（text/thinking/tool...）+ `ChatContainer` | 天然节点模型，可加 part 渲染注册表 |
| 技能 | `SkillRuntime` + `SkillWatcher` + `SKILL.md` | 已经是"文件系统插件"，可作为 manifest 的一类来源 |
| 控制面 | `app-ui-control` + `lumii-ui` CLI + 命令白名单 | 可升级为插件命令总线 |
| 监测 | `PerformanceMonitor`、tool telemetry、文件日志 | 可扩展为插件健康面板 |

### 1.4 设计约束

- **不重写 Agent 循环**。`pi-agent-core` 是稳定的；插件只能通过工具、钩子、提示词 section、事件接入。
- **不把主进程拆成多个进程**（本期）。插件的失败隔离先靠 try/catch 与作用域，不靠进程沙箱。
- **不在热路径上做全量扫描**。消息渲染、token 流、工具执行保持现有性能基线。
- **不制造第二份清单**。manifest 是唯一真源。

## 2. 目标与边界

### 2.1 目标

1. **内核稳定**：窗口/托盘/IPC 信任边界/Agent 循环/持久化/模型流属于内核，不随插件变化。
2. **前后端功能插件化**：可选功能、第三方能力、UI 区块都用同一套 manifest 声明。
3. **前端卡片化动态渲染**：卡片 = 数据 + 类型 + 组件；首次出现时才加载组件；可热替换。
4. **后端可扩展**：工具、LLM provider、渠道、命令、IPC、服务、任务、存储适配器。
5. **可控制**：控制面能从 manifest 自动发现命令，而不是维护一份硬编码白名单。
6. **可监测**：每个插件的激活耗时、effect 数、事件数、工具调用、错误率可查。
7. **可回滚**：卸载插件必须撤销它注册的一切；失败要如实报告。

### 2.2 非目标（本期）

- 不把不可信第三方代码做成安全沙箱。同进程渲染插件 = 受信任代码。
- 不做插件市场、签名、付费、远程分发（先支持本地目录 + 内置 + 后续 npm）。
- 不做跨设备插件同步。
- 不把 Agent 循环、消息存储、模型流、窗口生命周期插件化。

### 2.3 什么不该插件化

判断标准：**每个回合都依赖、失败即全站不可用、或属于信任边界的东西，留在内核。**

明确留在内核：

- Electron 窗口/托盘/单实例/深链；
- preload 与 IPC 信任边界；
- `AgentRuntimeBridge` 与 `pi-agent-core` 装配骨架；
- 会话持久化、消息排序、上下文压缩主流程；
- 设置存储、凭据、日志、崩溃处理；
- 基础 IPC 路由与权限门。

```
│  │  ├─ RendererPluginHost  module loader / hot swap       │  │

│  │ Kernel: window / tray / ipc trust / agent bridge / log │  │
│  │  ├─ MainPluginHost   discovery → validate → activate    │  │
│  │  ├─ ServiceContainer ctx.tools / ctx.llm / ctx.channels│  │
│  │  ├─ EventBus         emit / waterfall / serial / ...   │  │
│  │  ├─ CommandBus       control plane / lumii-ui          │  │
│  │  ├─ PluginMonitor    activation / effects / errors     │  │
│  │  └─ AssetPlugins     install / uninstall / status      │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
                           │
        ┌──────────────────┴──────────────────┐
        │ @lumii/plugin-core（共享类型与内核） │
        │ Context / Service / Effect / Event   │
        │ Manifest / Registry / Errors         │
        └─────────────────────────────────────┘
```

三条不变量：

1. **插件只能通过 `ctx` 拿能力**，不能直接 import 具体实现（避免静态耦合）。
2. **每个注册返回 disposer**，PluginHost 统一持有作用域。
3. **跨进程只走窄桥**：渲染层不能直接拿主进程对象；主进程不能信任渲染层传来的 manifest/权限。

## 4. 内核：`packages/plugin-core`

### 4.1 设计原则

- 只做四件事：服务容器、作用域、事件、注册表；
- 不含任何 Lumii 业务逻辑；
- 依赖注入用声明式 `inject`，加载顺序由依赖图决定；
- 失败默认 **fail loud**：缺依赖、重复注册、循环依赖、manifest 非法，都在加载期抛错。

### 4.2 Context 与 Service

```ts
// packages/plugin-core/src/context.ts
export type ServiceKey<T> = string & { readonly __service?: T }

export interface PluginContext {
  readonly pluginId: string

  /** 注册服务；随插件卸载自动移除 */
  provide<T>(key: ServiceKey<T>, value: T | (() => T)): T

  /** 取服务；缺失返回 undefined */
  get<T>(key: ServiceKey<T>): T | undefined

  /** 取服务；缺失抛 MissingServiceError */
  require<T>(key: ServiceKey<T>): T

  /** 注册可逆副作用；dispose 按 LIFO 执行 */
  effect(dispose: () => void | Promise<void>): void

  /** 事件总线 */
  on<K extends keyof LumiiEvents>(name: K, listener: EventListener<LumiiEvents[K]>): void
  emit<K extends keyof LumiiEvents>(name: K, payload: LumiiEvents[K]): void
  waterfall<K extends keyof LumiiEvents>(name: K, payload: LumiiEvents[K]): Promise<LumiiEvents[K]>
  serial<K extends keyof LumiiEvents>(name: K, payload: LumiiEvents[K]): Promise<LumiiEvents[K]>
  parallel<K extends keyof LumiiEvents>(name: K, payload: LumiiEvents[K]): Promise<void>

  /** 日志带 pluginId 前缀 */
  log: PluginLogger
}
```

服务 key 用字符串 + TypeScript declaration merging：

```ts
declare module '@lumii/plugin-core' {
  interface LumiiServices {
    tools: ToolRegistry
    llm: LlmRegistry
    channels: ChannelRegistry
    ipc: IpcRegistry
    commands: CommandRegistry
    metrics: MetricsRegistry
    storage: StorageService
  }
}
```

**为什么不用 Symbol**：跨 bundle 的 `Symbol.for` 虽然能共享，但调试、日志、manifest 声明都不友好；字符串更适合跨进程与配置文件。运行期另外维护 `SERVICE_TOKENS` 做冲突检测。

### 4.3 Effect 作用域

```ts
export class PluginScope {
  private disposers: Array<() => void | Promise<void>> = []
  private disposed = false

  effect(dispose: () => void | Promise<void>): void {
    if (this.disposed) throw new Error('scope already disposed')
    this.disposers.push(dispose)
  }

  async dispose(): Promise<void> {
    if (this.disposed) return
    this.disposed = true

    const errors: unknown[] = []
    // 严格 LIFO；异步 disposer 串行 await，避免并发清理互相踩状态
    for (let i = this.disposers.length - 1; i >= 0; i--) {
      try {
        await this.disposers[i]()
      } catch (err) {
        errors.push(err)
      }
    }
    this.disposers.length = 0

    if (errors.length > 0) {
      throw new AggregateError(errors, `plugin ${this.pluginId} dispose failed`)
    }
  }
}
```

注意两点（Cordis 的实践教训）：

- **异步清理必须串行**。多个异步 disposer 并发跑，容易出现"依赖先于提供者销毁"。
- **清理失败要继续清理完**，最后用 `AggregateError` 一次性抛出；不能因为第一个错误就停，留下半卸载状态。

### 4.4 事件总线

事件分五种模式，模式是声明的一部分：

```ts
export interface EventMeta {
  mode: 'emit' | 'waterfall' | 'serial' | 'parallel' | 'bail'
}

export interface LumiiEvents {
  'app/ready': { at: number }
  'agent/pre-step': EventMeta & { messages: unknown[] }
  'tools/pre-execute': EventMeta & { toolName: string; params: unknown }
  'plugin/activated': { pluginId: string; durationMs: number }
  'plugin/deactivated': { pluginId: string; reason: string }
  'plugin/error': { pluginId: string; error: unknown }
}
```

实现要点：

- `emit` / `parallel` 不返回值；
- `waterfall` 是**环绕中间件**：监听器拿到 `(payload, next)`，调 `next()` 继续，返回新值则替换；
- `serial` 按注册顺序 `await`，返回最后一个监听器的值；
- `bail` 遇到第一个非 `undefined` 返回值即停止；
- 监听器注册走 `ctx.on`，卸载自动移除；
- 某个监听器抛错时：`emit`/`parallel` 记录错误并继续；`waterfall`/`serial` 向上抛（由调用方决定是否降级）。

### 4.5 依赖解析

插件声明：

```ts
export interface PluginDefinition {
  id: string
  inject?: string[]          // 必需服务
  injectOptional?: string[]  // 可选服务
  provides?: string[]        // 本插件提供的服务
  apply(ctx: PluginContext): void | Promise<void>
}
```

加载器：

1. 校验 id 唯一；
2. 建图：`plugin.provides -> plugin.inject`；
3. 拓扑排序；发现环 → `PluginDependencyCycleError`，列出环上的 id；
4. 按序激活；缺服务 → `MissingServiceError`，不激活；
5. 每个插件激活后记录 `durationMs` 与 effect 数；
6. 卸载按**逆拓扑序**。

### 4.6 与 host-kit 的关系

`packages/agent-runtime/src/host-kit/` 已经是宿主装配层，不替换它。插件通过它拿到的能力：

```ts
ctx.require<AgentRuntimeService>('agentRuntime').assemble({
  tools,
  promptSections,
  hooks,
})
```

也就是说，**host-kit 是内核的一部分**；插件在内核之上做"贡献"，不直接改 `assembleAgent` 的实现。

## 5. 插件清单与组合

### 5.1 Manifest v1

唯一真源放在 `apps/windows/src/shared/plugin-manifest.ts`（主进程、渲染层、CLI 共用）。

```ts
export interface LumiiPluginManifest {
  /** 全局唯一，建议反向域名：com.example.weather */
  id: string
  name: string
  version: string
  description?: string
  icon?: string

  /** 宿主版本范围，semver */
  engines: { lumii: string }

  /** code = 可执行插件；asset = 只提供文件/二进制（复用现有插件中心） */
  kind: 'code' | 'asset'

  /** 主进程入口，相对插件根目录 */
  main?: string

  /** 渲染层入口 */
  client?: {
    entry: string
    styles?: string[]
    /** 非基线共享模块，必须精确声明 */
    external?: string[]
  }

  /** 懒激活事件；省略 = onStartup */
  activation?: ActivationEvent[]

  /** 权限声明；主进程强制执行 */
  permissions?: PluginPermission[]

  /** 贡献点 */
  contributes?: PluginContributions

  /** 配置 schema（JSON Schema 子集） */
  configSchema?: Record<string, unknown>
}

export type ActivationEvent =
  | 'onStartup'
  | `onView:${string}`
  | `onCommand:${string}`
  | `onTool:${string}`
  | `onChannel:${string}`

export type PluginPermission =
  | 'fs:workspace'
  | 'fs:user-data'
  | 'net:http'
  | 'process:spawn'
  | 'clipboard:read'
  | 'clipboard:write'
  | 'secrets:read'
  | 'shell:execute'

export interface PluginContributions {
  services?: ServiceContribution[]
  tools?: ToolContribution[]
  llm?: LlmContribution[]
  channels?: ChannelContribution[]
  ipc?: IpcContribution[]
  commands?: CommandContribution[]
  events?: EventContribution[]
  views?: ViewContribution[]
  settings?: SettingsSectionContribution[]
  cards?: CardContribution[]
  slots?: SlotContribution[]
  jobs?: JobContribution[]
}
```

清单可以写在 `package.json` 的 `lumii` 字段里，也可以单独 `plugin.json`。**两者只能有一个**，同时存在时启动报错。

### 5.2 贡献点清单

| 贡献点 | 运行位置 | 注册 API | 卸载行为 |
|---|---|---|---|
| `services` | 主进程 | `ctx.provide` | 移除服务；依赖者逆序卸载 |
| `tools` | 主进程 | `ctx.tools.register` | 从 ToolRegistry 移除 |
| `llm` | 主进程 | `ctx.llm.registerProvider` | 移除 provider |
| `channels` | 主进程 | `ctx.channels.register` | 断开并移除适配器 |
| `ipc` | 主进程 | `ctx.ipc.handle(namespace, method)` | 移除 handler |
| `commands` | 主进程 | `ctx.commands.register` | 从控制面移除 |
| `events` | 主进程 | `ctx.on` | 移除监听器 |
| `jobs` | 主进程 | `ctx.jobs.register` | 取消并移除 |
| `views` | 渲染层 | `ctx.slots.register('app.view', ...)` | 移除导航项 |
| `settings` | 渲染层 | `ctx.slots.register('settings.section', ...)` | 移除设置分区 |
| `cards` | 渲染层 | `ctx.cards.register({ type, schema, component })` | 移除组件；已有卡片显示 fallback |
| `slots` | 渲染层 | `ctx.slots.register(slot, entry)` | 移除条目 |

### 5.3 Profile 分层

不照搬 dsh 的 pnpm/YAML patch（对桌面端太重），先用三层 JSON：

```
内置 bundle（随包）
  → 用户 profile（~/.lumii/profiles/default.json）
    → 工作区覆盖（<workspace>/.lumii/profile.json）
```

```json
{
  "version": 1,
  "bundles": ["@lumii/bundle-base", "@lumii/bundle-desktop"],
  "plugins": {
    "com.lumii.performance-monitor": { "enabled": true },
    "com.lumii.cloud-sync": { "enabled": false },
    "com.example.weather": {
      "enabled": true,
      "config": { "city": "成都" }
    }
  }
}
```

规则：

- 只记录**与内置默认不同的偏离**；
- `enabled` 与 `config` 整体替换，不做深合并（避免"我以为关了某个子项"）；
- 未知插件 id 保留但标记 `missing`，不静默删除；
- 工作区覆盖只允许 `enabled`，不允许改权限。

### 5.4 资产插件

现有 `PluginHandler` 保留，作为 `kind: 'asset'` 的实现：

```ts
interface AssetPluginManifest extends LumiiPluginManifest {
  kind: 'asset'
  asset: {
    source: { npmPackage?: string; files?: { url: string; sha256: string }[] }
    target: { dir: string; entry: string }
    provides?: string[]   // 'mcp:wechat-local' | 'pet:demo_cartoon_cat'
  }
}
```

这样插件中心只有一套列表，`kind` 决定是"加载代码"还是"下载文件"。

## 6. 主进程 PluginHost

### 6.1 启动顺序（两阶段）

```
discover
  → validate manifest（schema + engines + 权限合法性）
  → resolve dependencies（拓扑排序）
  → register phase：只注册贡献，不执行副作用
  → activate phase：按拓扑序 apply(ctx)
  → publish ready：通知渲染层可用的插件/贡献
```

两阶段的好处：插件 A 在 `register` 阶段就能看到插件 B 声明的命令/工具名，不必猜加载顺序。停止时反向：

```
deactivate（逆拓扑序）
  → 每个插件 scope.dispose()（LIFO）
  → 等待异步清理
  → 从注册表移除
```

### 6.2 服务目录

首批只开放这些 `ctx` key（宁少勿多）：

| key | 类型 | 说明 |
|---|---|---|
| `tools` | `ToolRegistry` | 注册 `MtBotTool` |
| `llm` | `LlmRegistry` | 注册 provider 或模型适配器 |
| `channels` | `ChannelRegistry` | 注册渠道适配器 |
| `ipc` | `IpcRegistry` | 命名空间化 IPC |
| `commands` | `CommandRegistry` | 控制面命令 |
| `jobs` | `JobRegistry` | 定时/后台任务 |
| `metrics` | `MetricsRegistry` | 计数器/直方图 |
| `net` | `NetService` | 受限 HTTP 客户端（域名/体积记录，受 `net:http` 权限约束） |
| `storage` | `StorageService` | 插件私有 KV/目录，不直接碰主库 |
| `agentRuntime` | `AgentRuntimeService` | 访问 host-kit 装配与当前 bridge |
| `log` | `PluginLogger` | 带 pluginId 的日志 |

**不开放**：`BrowserWindow`、`ipcMain`、`safeStorage`、主数据库连接、`child_process`。需要这些能力时，走 `permissions` + 主进程封装的服务。

### 6.3 IPC 贡献

问题：如果每个插件都往 preload 里加 API，装一个插件就要改 preload，不可行。

方案：**一个通用通道 + manifest 白名单**。

```ts
export interface IpcContribution {
  /** 方法名，插件内唯一；完整调用名是 pluginId + method */
  method: string
  description?: string
  /** 请求/响应 JSON Schema；主进程校验 */
  schema?: Record<string, unknown>
}
```

```ts
// preload
contextBridge.exposeInMainWorld('lumiiPlugins', {
  invoke: (pluginId: string, method: string, payload?: unknown) =>
    ipcRenderer.invoke('plugins:invoke', { pluginId, method, payload }),
  onEvent: (cb: (event: PluginEvent) => void) => { /* 订阅 plugins:event */ },
})
```

主进程：

```ts
ipcMain.handle('plugins:invoke', async (event, req) => {
  assertSenderIsMainWindow(event)              // 只认主窗口 webContents
  const plugin = host.get(req.pluginId)
  if (!plugin) throw new PluginNotFoundError(req.pluginId)

  const method = plugin.manifest.contributes?.ipc?.find(m => m.method === req.method)
  if (!method) throw new PluginIpcDeniedError(req.pluginId, req.method)

  validatePayload(method.schema, req.payload)  // 失败即拒
  return plugin.invoke(method.method, req.payload)
})
```

规则：

- 插件不能注册任意 channel 名；manifest 的 `ipc[].method` 是唯一白名单；
- payload 必须过 JSON Schema；
- 主进程校验 `event.sender`，拒绝外来 webContents；
- 单向事件走 `plugins:event`，同样按 manifest 声明过滤。

### 6.4 控制面与命令

`apps/windows/src/main/app-ui-control/command-allowlist.ts` 目前是硬编码 Set，扩一条命令要改代码并评审。插件化后：

```ts
interface CommandContribution {
  command: string              // 'weather:refresh'
  description: string
  risk: 'read' | 'write' | 'sensitive'
  /** 是否允许外部控制口调用；默认 false */
  exposeToControlPlane?: boolean
  schema?: Record<string, unknown>
}
```

- 内置插件可以在 manifest 里声明 `exposeToControlPlane: true`；
- 外部插件默认 `false`，必须在设置页显式授权；
- 控制口启动时**从已激活插件聚合白名单**，仍然保留"默认拒绝"；
- `lumii-ui commands` 能列出插件命令及其风险等级；
- 高危字段拒绝清单（`COMMAND_FIELD_DENYLIST`）继续保留，不能由插件绕过。

### 6.5 监测与健康

每个插件记录：

```ts
interface PluginRuntimeState {
  id: string
  state: 'discovered' | 'activated' | 'failed' | 'disabled'
  activatedAt?: number
  activationMs?: number
  effectCount: number
  eventListenerCount: number
  toolCallCount: number
  lastError?: { message: string; at: number; stack?: string }
}
```

暴露：

- `plugin:list` 返回 manifest + runtime state；
- `metrics` 服务记录 `plugin.activation_ms`、`plugin.errors`、`plugin.tool_calls`；
- 日志统一加 `[plugin:<id>]` 前缀；
- 插件抛错不拖垮宿主：`apply` 失败标记 `failed`；事件监听器失败按模式记录或上抛；工具执行失败走现有 `ToolRunner` 错误路径。

### 6.6 热更新

```ts
async function reload(plugin: LoadedPlugin): Promise<ReloadResult> {
  // 1. 先加载新模块，不执行副作用
  const nextModule = await import(`${pathToFileURL(plugin.main)}?v=${++revision}`)

  // 2. 卸载旧作用域（逆拓扑序，等待异步清理）
  await plugin.scope.dispose()

  // 3. 用新模块激活
  try {
    const next = await activate(plugin.manifest, nextModule)
    return { ok: true, plugin: next }
  } catch (err) {
    // 4. 回滚：旧模块仍在 ESM 缓存中，可重新激活
    try {
      await activate(plugin.manifest, plugin.module)
      return { ok: false, rolledBack: true, error: err }
    } catch (rollbackErr) {
      return { ok: false, rolledBack: false, error: err, rollbackError: rollbackErr }
    }
  }
}
```

已知限制（要写进文档，不要让用户以为是无损热更）：

- ESM 模块无法真正卸载；旧模块对象会留在内存，直到进程重启；
- 插件状态默认**不迁移**；需要保留时由插件实现 `onSuspend(): unknown` / `onResume(state)`；
- 正在执行的工具调用不打断；等它结束后再切换；
- 主进程 Native 模块（`.node`）不能热替换，标记 `restart-required`。

### 6.7 权限模型

两级信任：

| 级别 | 来源 | 默认权限 | 用户提示 |
|---|---|---|---|
| `builtin` | 随包内置 | manifest 声明即授予 | 不提示 |
| `trusted` | 本地目录 / 用户显式安装 | 逐项授权 | 首次启用时列出权限 |
| `untrusted` | 未来远程安装 | 只允许声明式 A2UI，不执行 JS | 默认不启用 |

主进程强制：

- `fs:*`：所有文件访问走 `StorageService` / `WorkspaceFsService`，插件拿不到裸 `fs`；
- `process:spawn`：只能通过 `ctx.process.spawn(spec)`，spec 由主进程校验；
- `net:http`：走 `ctx.net.fetch`，记录域名与体积；
- `secrets:read`：只能读 manifest 声明的 secret key，且返回值脱敏日志；
- `shell:execute`：默认不开放；需要时单独审批。

**明确写死**：插件代码与主进程同权限，权限声明是"减少误用 + 用户知情"，不是安全沙箱。真正不可信的插件只能通过 iframe/Worker + 消息协议运行（本期不做）。

## 7. 渲染层 PluginHost

### 7.1 模块加载协议

复用 dsh 的 lazy-CJS 思路，但按 Lumii 的构建现实简化：

- 插件包由 SDK 的构建预设产出**单文件工厂**：

```js
// dist/client.js
globalThis.__LUMII_REGISTER_PLUGIN__('com.example.weather', function (require) {
  const React = require('react')
  const { defineCard } = require('@lumii/plugin-sdk')

  return {
    activate(ctx) {
      ctx.cards.register(defineCard({
        type: 'weather.forecast',
        schema: { /* JSON Schema */ },
        component: function WeatherCard(props) { /* ... */ },
      }))
      ctx.slots.register('dashboard.card', {
        id: 'weather.today',
        title: '今日天气',
        component: function WeatherWidget() { /* ... */ },
      })
    }
  }
})
```

- 宿主提供冻结的共享模块表：

```ts
const SHARED_MODULES = {
  react: React,
  'react-dom': ReactDOM,
  'react/jsx-runtime': jsxRuntime,
  '@lumii/plugin-sdk': pluginSdk,
}
```

- 加载流程：

```
manifest.client.entry
  → main 通过 lumii-plugin://<id>/client.js?rev=<mtime> 提供文件
  → renderer 注入 <script>（或动态 import 包装）
  → 工厂注册到 globalThis.__LUMII_REGISTER_PLUGIN__
  → RendererPluginHost 取出 factory，首次 activate 时传入 require
  → 模块体副作用此时才执行
```

- 如果用 `<script>` 注入，需在 CSP 中允许 `lumii-plugin:`；如果更愿意用 ESM，可让工厂文件 `export default factory`，再 `import(url)`。**推荐 `<script>` + 全局注册**：避免 ESM 缓存导致热更新不生效，也避免 import map 处理共享模块。

### 7.2 Slot 系统

先实现四种 slot，但只开放少量位置：

```ts
type SlotKind = 'single' | 'list' | 'keyed' | 'chain'

interface SlotEntry<P = unknown> {
  id: string
  component: React.ComponentType<P>
  order?: number
  when?: (ctx: SlotContext) => boolean
}
```

首批 slot：

| slot | 类型 | 位置 | 用途 |
|---|---|---|---|
| `app.view` | `keyed` | Router | 整页视图（dashboard / autonomous / 新页面） |
| `app.nav` | `list` | 侧边栏 | 导航入口 |
| `settings.section` | `list` | SettingsHub | 设置分区 |
| `dashboard.card` | `list` | DashboardPage | 概览卡片 |
| `chat.part` | `keyed` | ChatMessage | 消息时间线里的自定义 part/卡片 |
| `chat.node` | `keyed` | ChatContainer | 独立节点（后续） |
| `composer.action` | `list` | Composer | 输入框旁动作 |
| `sidebar.panel` | `list` | 右侧栏 | 工具面板 |

规则：

- 注册返回 disposer；
- 同名 keyed 冲突在**加载期**抛错，不允许后注册覆盖（除非显式 `replace: true`）；
- `order` 相同按注册顺序；
- slot 声明与渲染授权绑定：未声明的 slot 不能注册；
- 每个 entry 带 `pluginId`，便于监测与调试。

`Router.tsx` 的 `ViewType` 从联合类型改成 `string`，但保留内置视图常量；未知视图渲染 `NotFoundView`，不白屏。

### 7.3 A2UI 卡片注册表

现状：`A2UIRenderer/index.tsx` 是固定 `switch`，`parseA2UIBlocks.ts` 里有固定 `KNOWN_A2UI_COMPONENT_TYPES`。

改造：

```ts
// packages/plugin-sdk/src/cards.ts
export interface CardDefinition<T = unknown> {
  type: string
  schema: JsonSchema
  component: React.ComponentType<CardProps<T>>
  /** 允许出现的 slot；默认全部 */
  slots?: string[]
}

export interface CardProps<T> {
  data: T
  actions: {
    emit(action: string, payload?: unknown): Promise<unknown>
  }
}
```

渲染器：

```tsx
function ComponentDispatch({ component, onAction }) {
  const def = cardRegistry.get(component.type)
  if (def) {
    const parsed = validateOrNull(def.schema, component)
    if (!parsed) return <InvalidCard type={component.type} />
    return <def.component data={parsed} actions={makeActions(def, onAction)} />
  }
  switch (component.type) {
    case 'Text': ...
    // 保留内置 12 种作为兼容
    default: return <FallbackComponent type={component.type} />
  }
}
```

要点：

- 内置组件仍走内置实现，插件只能**新增** type，不能覆盖内置 type（防止劫持）；
- 卡片数据必须过 schema；校验失败显示错误卡片，不渲染半成品；
- 卡片动作走 `actions.emit` → 渲染层事件总线 → 主进程 `plugins:invoke`；**卡片组件不能直接访问 `window.electronAPI`**（SDK 不暴露，lint 守卫检查）；
- 卡片组件可以是任意 React 组件，但只能通过 SDK 的 hooks 拿数据与动作。

### 7.4 消息时间线里的卡片

`AssistantPart` 目前是联合类型。新增一种：

```ts
interface CardPart {
  type: 'card'
  cardType: string      // 对应 CardDefinition.type
  id: string            // 稳定实例 id
  data: unknown
  status?: 'streaming' | 'done' | 'error'
}
```

渲染：

- `ChatMessage` 的 part 循环遇到 `type: 'card'` → `cardRegistry` 查找 → 渲染；
- 流式更新按 `id` 原地更新数据，不重建组件；
- 历史回放直接读落库的 part，不依赖实时事件；
- 卡片加载失败显示 `CardErrorBoundary`，不影响整条消息。

后续再引入 dsh 式的 `ConversationNodeDefinition`：用 durable session event + 稳定 `(kind, id)` 做可回放节点。**P2 先不做**，避免一次性改消息模型。

### 7.5 热更新

```ts
async function reloadClientPlugin(id: string) {
  const entry = registry.get(id)
  const rev = await host.getRevision(id)      // mtime + size
  if (rev === entry.rev) return

  const factory = await loadFactory(`${url(id)}?rev=${rev}`)
  const next = await materialize(factory)     // activate 到临时 scope
  // 激活成功后再替换：先停旧 scope，再提交新贡献
  await entry.scope.dispose()
  registry.replace(id, { ...next, rev })
  bus.emit('client-plugin-updated', { id, rev })
}
```

- React 组件按 `pluginId@rev` 作为 key 的一部分，强制重挂载；
- 正在显示的卡片在重挂载前保留旧组件，避免闪烁；
- 加载/激活失败保留旧版本，并显示"插件更新失败"提示；
- 样式：每个插件注入的 `<style>` 打 `data-plugin-id`，卸载时移除。

### 7.6 安全边界（必须写进插件开发文档）

- 渲染层插件与宿主同源、同 JS 上下文：**它可以访问 `window`、DOM、localStorage**；
- SDK 不暴露 `electronAPI`，但恶意代码可以绕过 SDK 直接访问 `window.electronAPI`；
- 因此：**只安装受信任插件**；外部插件安装页必须显示权限与来源；
- 不可信内容（模型生成的 A2UI、远程主题）只能走**声明式卡片**（无代码）或 iframe 沙箱；
- preload 只暴露窄 API，主进程校验 sender 与 manifest，不能因为"渲染层是自家的"就省略校验。

| 风险 | 说明 | 缓解 |
|---|---|---|
| **过度插件化** | 每个小功能都走 manifest/slot，调试与类型成本上升 | 严守"什么不该插件化"清单；内核保持无业务 |
| **热更新状态丢失** | 组件重挂载、插件重激活会丢内存状态 | 明确 `onSuspend/onResume`；关键状态落 SQLite/插件 KV |
| **同进程无隔离** | 插件崩溃可能拖垮主进程/渲染层 | `apply` 与事件监听 try/catch；工具走 ToolRunner；UI 用 ErrorBoundary；未来可选 Worker/iframe |
| **性能** | 启动时扫描全部插件、渲染时查注册表 | 懒激活；注册表用 Map；卡片按 type 缓存；启动只读 manifest 不执行代码 |
| **类型复杂度** | 跨包 declaration merging 难追踪 | 核心事件/服务集中在一个 `LumiiEvents`/`LumiiServices`；插件只 augment 这两个接口 |
| **清单双写回潮** | 主进程与渲染层各维护一份 | manifest 唯一真源；构建期生成类型；守卫测试扫描重复清单 |
| **安全** | 插件可访问全部 Electron API | 信任分级；安装提示；主进程 sender 校验；不可信内容只走声明式卡片 |
| **向 pi-agent-core 渗透** | 插件直接改 Agent 循环 | 只开放 host-kit 的装配接口；`assembleAgent` 不暴露给插件 |
| **迁移期间双轨** | 旧硬编码与插件注册并存 | 每个功能迁移时删除旧路径；守卫测试禁止两处注册同一能力 |

`main.ts`：

```ts
import { definePlugin } from '@lumii/plugin-sdk'

export default definePlugin({
  id: 'com.lumii.demo.weather',
  inject: ['tools', 'commands', 'net', 'storage'],
  provides: ['weather'],
  apply(ctx) {
    const cache = ctx.require('storage').namespace('weather')

    ctx.require('tools').register({
      name: 'weather_query',
      label: '查询天气',
      description: '查询指定城市当前天气',
      category: 'network',
      isReadOnly: true,
      needsPermission: false,
      parameters: { type: 'object', properties: { city: { type: 'string' } } },
      async execute(_id, params) {
        const city = String(params.city ?? '成都')
        const cached = await cache.get(city)
        if (cached) return { content: [{ type: 'text', text: cached }] }
        const res = await ctx.require('net').fetch(
          `https://api.example.com/weather?city=${encodeURIComponent(city)}`
        )
        const text = await res.text()
        await cache.set(city, text, { ttlMs: 10 * 60_000 })
        return { content: [{ type: 'text', text }] }
      },
    })

    ctx.require('commands').register('weather:refresh', async () => {
      await cache.clear()
      return { ok: true }
    })
  },
})
```


## 12. 开放问题（需要拍板）

1. **是否引入 Cordis 本体？**
   **建议：不引入。** 用它的四条契约在 `plugin-core` 里做最小实现。理由：Lumii 已有 pi-agent-core 与 Electron 双进程；Cordis 的 loader/HMR/pnpm 集成会带来第三套构建与生命周期。P2 结束后如果发现内核能力不足，再评估把 Cordis 作为可选依赖引入。
2. **插件分发渠道**
   建议：P0–P2 只支持内置 + 本地目录；P3 再评估 npm 包或 GitHub Release。不要一上来做市场。
3. **插件代码写入仓库还是独立目录**
   建议：内置插件放 `apps/windows/src/plugins/<id>/`，随构建打包；外部插件放 `~/.lumii/plugins/<id>/`。两者 manifest 相同。
4. **热更新是否默认开启**
   建议：开发模式默认开启；生产模式默认只对内置插件开启，外部插件需在设置页打开。Native 模块永远 `restart-required`。
5. **插件能否修改系统提示词**
   建议：只能通过 `ctx.prompt.section({ id, content, order })` 注册 section；不允许直接替换完整 systemPrompt。用户自定义内容优先级高于插件。
6. **插件能否注册 IPC 给渲染层**
   建议：可以，但必须走 `contributes.ipc` 白名单 + schema，不允许任意 channel。渲染层插件优先通过 `ctx` 的渲染层 API，而不是自己开 IPC。
7. **不可信插件的隔离**
   建议：本期不做；在插件中心明确标注"插件代码与 Lumii 同权限"。未来需要时，用 iframe/Worker + 受限消息协议，而不是同进程 `eval`。
