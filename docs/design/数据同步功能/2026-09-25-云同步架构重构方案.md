# 云同步架构重构方案

- 日期：2026-09-25
- 状态：设计中
- 背景：单一 Git 仓库方案已触达 GitCode 1GiB 硬上限，日常同步持续失败（aborted/timeout）

---

## 1. 问题诊断

### 1.1 当前架构（v3）的根本性限制

| 问题 | 现象 | 根因 |
|------|------|------|
| **仓库体积爆炸** | sync 仓库 1.0 GiB（已触顶）+ .git 966 MB | 所有数据（DB jsonl + 用户文件 + outputs）塞进单一 Git 仓库 |
| **同步失败** | aborted / Request timed out | GitCode 服务器处理大仓库超时/限流 |
| **传输慢** | 一次同步 5-10 分钟（fetch 100s） | isomorphic-git 每次 fetch 都增量下载 pack，累积体积大 |
| **gc 无效** | pack 504 MB ≈ 工作区 500 MB | 历史大文件已被 delta 压缩，无水分可挤 |
| **分级传输治标不治本** | 阶段一 18s，但阶段二仍会推高总体积 | 分级只改传输顺序，不改"全部进 Git"的架构 |

### 1.2 单一 Git 仓库的结构性矛盾

Git 是**版本控制系统**，设计目标是追踪代码变更历史，而不是：
- **大文件存储**：outputs 中的视频（152 MB）、图片每次修改都会留历史副本
- **高频同步**：30 分钟定时 + 文件监听，每次都要 stage/commit/push 整个工作区
- **多设备协调**：Git 的三方合并对"谁先推谁赢"敏感，不适合多设备并发写

**结论**：继续在 Git 上打补丁（如 git-lfs）只会增加复杂度，不解决根本矛盾。

---

## 2. 架构重构方向（三选一）

### 方案 A：混合架构（元数据 Git + 大文件对象存储）⭐ 推荐

**思路**：
- **小文件（元数据类）** 继续用 Git：DB jsonl、profile、skills、workspace/files（md/json）
- **大文件（产出类）** 改用对象存储：outputs 中的图片/视频/文档，走 S3/OSS/COS API

**架构图**：
```
┌─────────────────────────────────────────────────────┐
│  本地 Lumii                                          │
│  ├── data/                                           │
│  │   ├── agent-runtime.db ────┐                     │
│  │   └── profile/             │                     │
│  │       └── user-memory.md ──┤                     │
│  └── workspace/                │                     │
│      ├── files/    ────────────┤─→ Git 仓库（轻量）  │
│      │   └── notes.md         │   ↓                 │
│      └── outputs/              │   push/pull        │
│          ├── image.png ────────┼→ 对象存储（S3/OSS） │
│          └── video.mp4 ────────┘   ↓                │
│                                    上传/下载（并发） │
└─────────────────────────────────────────────────────┘
```

**优势**：
1. **解决体积问题**：Git 仓库只含元数据（<50 MB），永不触顶
2. **大文件高效**：并发上传/下载，支持断点续传，CDN 加速
3. **成本可控**：OSS 标准存储 ¥0.12/GB/月（阿里云），远低于 Git LFS
4. **渐进迁移**：先迁移 outputs，Git 部分保持不变

**技术栈**：
- Git 仓库：保持现有 gitcode-provider
- 对象存储：`@aws-sdk/client-s3`（兼容 S3 协议的 OSS/COS/MinIO）
- 清单文件：outputs/.sync-manifest.json（记录文件名 → object key 映射）

**实施路径**（Phase 1-3，约 2-3 周）：
- **Phase 1**：outputs 只读对接（下载功能先通）
- **Phase 2**：outputs 上传与增量同步
- **Phase 3**：冲突处理与多设备协调

---

### 方案 B：完全 API 化（自建/托管后端）

**思路**：抛弃 Git，全部走 RESTful API + 关系型数据库。

**架构**：
```
客户端 ←→ HTTPS API ←→ 后端服务（Node.js/Go）
                      ├── PostgreSQL（元数据 + 版本）
                      └── S3/OSS（大文件）
```

**优势**：
- 灵活性最高：冲突解决、权限控制、增量同步全部可定制
- 性能最好：按需查询，不用每次 fetch 整个仓库

**劣势**：
- **开发成本高**：需要实现整套后端服务（认证、存储、版本控制）
- **运维负担**：自建需要服务器维护；托管（如 Supabase）有供应商锁定
- **迁移成本**：现有 Git 仓库数据需要全量导入

**评估**：除非计划长期商业化（SaaS 服务），否则投入产出比不划算。

---

### 方案 C：多仓库拆分（Git Only）

**思路**：将单一仓库按数据类型拆分成多个独立仓库。

**拆分方案**：
```
lumii-sync-db/        # DB jsonl（wiki + memory + autonomous）
lumii-sync-profile/   # 用户配置
lumii-sync-outputs/   # workspace 产出（仍会触顶）
```

**评估**：
- ❌ **outputs 仍会触顶**：视频/图片积累后单仓库仍会超限
- ❌ **协调复杂**：三个仓库的原子性同步需要额外逻辑
- ❌ **治标不治本**：没解决"大文件进 Git"的根本问题

**结论**：不推荐。

## 3. 方案 A 详细设计（推荐实施）

### 3.1 数据分类与存储策略

| 数据类型 | 示例 | 存储方式 | 理由 |
|---------|------|---------|------|
| **元数据** | wiki/*.jsonl, memory/*.jsonl | Git 仓库 | 小、频繁变更、需要版本历史 |
| **配置** | profile/soul.md, user-memory.md | Git 仓库 | 同上 |
| **技能** | skills/*.ts | Git 仓库 | 同上 |
| **小文件** | workspace/files/*.md | Git 仓库 | 同上 |
| **大文件** | workspace/outputs/*.{png,jpg,mp4,pdf} | 对象存储 | 大、低频变更、不需要 diff |

### 3.2 对象存储选型

| 方案 | 优势 | 劣势 | 成本 |
|------|------|------|------|
| **阿里云 OSS** | 国内速度快，CDN 成熟 | 需要实名认证 | 标准存储 ¥0.12/GB/月 |
| **腾讯云 COS** | 同上 | 同上 | 类似 |
| **AWS S3** | 全球通用，生态最好 | 国内访问慢（需配置加速） | 标准存储 $0.023/GB/月 |
| **MinIO（自建）** | 完全自主，兼容 S3 API | 需要自己维护服务器 | 服务器成本 |
| **Cloudflare R2** | 零出口流量费，S3 兼容 | 相对新，生态较少 | $0.015/GB/月 |

**推荐**：
- **个人用户**：Cloudflare R2（性价比最高，10 GB 免费额度）
- **国内用户**：阿里云 OSS（速度优先）
- **开源部署**：MinIO（自主可控）

### 3.3 核心流程设计

#### 3.3.1 同步流程（混合架构）

```typescript
async function sync() {
  // 阶段一：元数据同步（Git）
  await gitSync({
    include: ['wiki/', 'memory/', 'profile/', 'workspace/files/'],
    exclude: ['workspace/outputs/']
  })
  
  // 阶段二：大文件同步（对象存储）
  const manifest = await loadManifest('workspace/outputs/.sync-manifest.json')
  const localFiles = await scanOutputs('workspace/outputs/')
  
  // 并发上传新增/变更文件
  const uploads = localFiles.filter(f => needsUpload(f, manifest))
  await Promise.all(uploads.map(f => s3.upload(f)))
  
  // 下载远端新增文件
  const remoteManifest = await s3.getObject('.sync-manifest.json')
  const downloads = diffManifests(manifest, remoteManifest)
  await Promise.all(downloads.map(f => s3.download(f)))
  
  // 更新本地清单
  await saveManifest(mergedManifest)
}
```

#### 3.3.2 清单文件格式

```json
{
  "version": "1.0",
  "files": {
    "image.png": {
      "key": "outputs/2026/09/image-abc123.png",
      "size": 102400,
      "mtime": 1726934400000,
      "etag": "abc123def456",
      "device": "device-001"
    }
  }
}
```

#### 3.3.3 冲突处理策略

| 场景 | 策略 |
|------|------|
| **同名文件不同内容** | 重命名保留两份（`file.png` + `file-conflict-device2.png`） |
| **清单冲突** | 合并两侧清单（union），按 mtime 最新者为准 |
| **删除传播** | 清单中标记 `deleted: true`，不立即删物理文件（30 天后 GC） |

### 3.4 配置模型

```typescript
interface CloudSyncConfigV4 {
  // Git 部分（保持兼容）
  git: {
    enabled: boolean
    provider: 'gitcode' | 'github' | 'gitee'
    repoUrl: string
    branch: string
    tokenEnc: string
  }
  
  // 对象存储部分（新增）
  objectStorage: {
    enabled: boolean
    provider: 's3' | 'oss' | 'cos' | 'minio' | 'r2'
    endpoint: string       // 例如 'https://s3.amazonaws.com'
    region: string         // 例如 'us-east-1'
    bucket: string
    accessKeyId: string
    secretAccessKey: string
    pathPrefix?: string    // 例如 'lumii-sync/'
  }
  
  // 同步范围
  syncScope: {
    enableGit: boolean
    enableObjectStorage: boolean
    outputsPatterns: string[]  // 例如 ['**/*.{png,jpg,mp4,pdf}']
  }
}
```

## 4. 迁移路径

### 4.1 向后兼容策略

- **Phase 0**：现有 Git 仓库继续服役，只读不写
- **Phase 1**：outputs 新增文件走对象存储，旧文件保持在 Git
- **Phase 2**：清空 Git 仓库中的 outputs/（force push 新历史），旧文件迁移到对象存储
- **Phase 3**：完全切换到混合架构

### 4.2 数据完整性保障

1. **迁移前备份**：
   ```bash
   cp -r ~/.lumii/sync ~/.lumii/sync-backup-20260925
   ```

2. **双写验证期**（1-2 周）：
   - 新文件同时写 Git 和对象存储
   - 下载时优先对象存储，失败回退 Git
   - 验证无误后关闭 Git 双写

3. **迁移后校验**：
   - 清单文件 checksum 校验
   - 随机抽样文件对比 hash

## 5. 风险评估与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| **对象存储服务商故障** | 大文件暂时无法同步 | 支持多 provider 热切换（S3 → R2） |
| **访问密钥泄露** | 数据被非法访问 | 密钥加密存储（safeStorage）+ bucket policy 限制 |
| **清单文件冲突** | 两设备同时上传同名文件 | 冲突重命名策略 + mtime 仲裁 |
| **迁移失败** | 数据丢失 | 迁移前完整备份 + 双写验证期 |
| **成本超预期** | OSS 账单高 | 设置月度预算告警 + 生命周期策略（30 天后归档） |

## 6. 性能对比预估

| 指标 | 当前（Git Only） | 混合架构 | 提升 |
|------|----------------|---------|------|
| 仓库体积 | 1.0 GB（触顶） | <50 MB | 20x ↓ |
| 首次同步 | 5-10 分钟 | 30-60 秒（元数据） + 按需下载大文件 | 10x ↑ |
| 增量同步 | 1-2 分钟 | 5-10 秒（元数据） + 并发上传 | 10x ↑ |
| 大文件传输 | 阶段二队列 50 MB/批 | 并发上传，无批次限制 | 5x ↑ |
| 多设备冲突 | Git merge，Agent 介入 | 清单合并 + 重命名 | 无需 Agent |

## 7. 成本估算

### 7.1 存储成本（以 Cloudflare R2 为例）

```
当前 outputs 体积: 643.8 MB
月增长（按 100 MB 估算）
年度体积: 643.8 + 100*12 = 1843.8 MB ≈ 1.8 GB

R2 费用:
- 存储: $0.015/GB/月 × 1.8 GB = $0.027/月 ≈ ¥0.2/月
- 操作: Class A（上传）1000 次免费/月，超出 $4.50/百万次
- 出口: 零费用

年度成本: ~¥2.4（vs GitCode 免费但不可用）
```

### 7.2 开发成本

- **Phase 1**（只读下载）: 3-5 天
- **Phase 2**（上传与增量）: 5-7 天
- **Phase 3**（冲突与多设备）: 3-5 天
- **总计**: 2-3 周（一人全职）
