## 1. 结论摘要

| 项 | 结论 |
| --- | --- |
| **主目标** | Agent 侧不再因慢同步阻塞；小文件快速到位、大文件可靠传输；同类死循环不再发生 |
| **范围** | 超时语义、任务形态、传输分级、同步范围管理；**不改** v3 数据层 |
| **技术路线** | 移植同仓已验证的 `ProgressFence` 滑动续期 + 1 MB 阈值分级传输（大文件走独立低优先级队列，50 MB/批）+ Agent 工具秒回 jobId 异步回填 |
| **最大风险** | **① 数据完整性**：2026-09-16 远端被第二台设备清空（§2.5），本地是唯一完整副本，**任何一次落决成功都会触发本地 863 个文件被删除**；**②** isomorphic-git 无法注入细粒度进度，单步超时靠 50 MB 分批压小来规避 |
| **明确不做** | 重写 git 历史、git-lfs、收窄同步范围（用户要求视频/图片/文档全同步）、限速 |

## 2. 背景与代码事实核查

### 2.1 一次仍在发生的死循环

2026-09-17 上午，用户工作空间的云同步陷入无限重试，日志（`~/.lumii/config/cloud-sync-log.json`）实录：

```
09:58:58  Agent 正在处理 6 个冲突文件…
10:04:38  ✗ 解决冲突超时（300000ms）。落决仍在后台继续…
10:04:53  Agent 文字总结：「决定：6 个冲突文件统一 keep-local」
10:08:34  Agent 正在处理 6 个冲突文件…     ← 重来
10:14:13  ✗ 又超时
10:18:34  Agent 正在处理 6 个冲突文件…     ← 再来
10:24:20  ✗ 又超时
10:28:34  Agent 正在处理 6 个冲突文件…     ← 第四轮
```

每一轮里，Agent 都做出了**正确**的判断（keep-local，依据是本地为 09-17 最新版、远端为 09-16 被取代的旧版），但决定传不出去 —— `resolve_sync_conflict` 调用 5 分钟零返回（`durationMs=300004`，`mtbot-2026-09-17.log` `ToolTelemetry`），Agent 只好用文字总结收场（`task_complete` 在当前环境还不可用），系统判定"处理失败"后重建目标重试。

### 2.3 四层根因

**L1 触发器 —— 仓库体积让每一步都慢。**
`sync-manager.ts` 的每次同步都做全量操作：`stageAllChanges` 等价 `add -A`（遍历整个 sync 目录做 hash）；`computeFileChanges` 全量 tree diff；`exportUserFiles`（`sync-exporter.ts:432-469`）对 `workspace/{files,outputs}` 完整递归复制，**无 mtime/内容短路** —— 改一个文件也要重拷 500 MB。

**L2 超时是墙钟一刀切。**
全部超时共用一个原语 `withTimeout`（`sync-manager.ts:100-110`）= 纯 `Promise.race`，无进度感知、无续期、不可取消。且预算嵌套不成立：外层 `RESOLVE_TIMEOUT_MS=300s`，而内部 push 单项允许 240s、其后的 refresh-fetch 又允许 300s —— 内层预算之和必然大于外层。

**L3 超时语义错误 —— 循环的直接原因。**
超时后 `resolveInner` **不会停**：`enqueueWorkspace` 排的是 `resolveInner` 本身而非加过超时的外层（`sync-manager.ts:958-980` 注释明确写了这是刻意设计），后台继续跑到底。但调用方（Agent）收到的是 `isError: true`。而调度器的冲突重试冷却 `CONFLICT_RETRY_COOLDOWN_MS = 2min` **小于** 5 分钟超时 —— 每一轮都必然重入：Agent 重新读文件、重新决策、重新发起落决，排到还在跑的那一轮后面。

**L4 反馈缺失。**
Agent 拿不到任何 job id，只能靠 `cloud_sync_git` 只读轮询猜后台状态。雪上加霜：`cloud_sync_read_file` 读 remote 侧在当轮 4 次全部失败（`无法读取 remote/...（无冲突或文件不存在）`，日志 10:18:41 / 10:18:42 / 10:18:53 / 10:18:54），Agent 每轮都要多绕数圈才敢下结论。

## 3. 方案对比与选型

### 3.1 慢操作超时问题

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A. 简单加大超时值 | 把 300s 改成 1800s | 治标。慢的原因没解决，且真卡死时要多等 30 分钟；预算嵌套矛盾依旧 |
| B. 滑动续期 | 移植 `ProgressFence` 双预算，超时语义改为「多久没动静」 | 治本之一。同仓已有验证实现（`compact/progress-fence.ts`），风险低 |
| C. 完全异步化 | 慢操作秒回 jobId，后台跑完回填 | 治本之二。Agent 侧从根上不再有"等待"这个状态 |

**选型：B + C。** B 解决"正常但慢"被误杀，C 解决"Agent 干等"的结构性问题。两者互补而非重复 —— C 之后 B 仍需要，因为后台任务自身也需要判死（真卡死时不能无限等）。

### 3.2 大文件传输

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A. 收窄同步范围 | outputs 的大文件不同步 | 用户明确否决：视频、图片、文档都需要同步 |
| B. git-lfs | 大文件走 LFS 通道 | GitCode 支持情况未知；引入新依赖与新故障面；分级传输已解决主要矛盾 |
| C. 分级传输 | 1 MB 阈值分流，大文件走独立低优先级队列分批传 | 数据支撑充分（见 §4.1）；复用现有 git 通道，无新依赖 |

**选型：C。**

| 方案 | 收益 | 代价 | 评价 |
| --- | --- | --- | --- |
| A. 只做 GC | 966 MB → ~508 MB | 无 | **选** |
| B. `git filter-repo` 重写历史 | 收益很小 | force push + 其他设备重克隆 | 否 |

## 4. 核心设计

### 4.1 分级传输（Tiered Sync）

**阈值 1 MB**（用户拍板，配置项 `smallFileThresholdBytes`）。依据实测分布：

| 阈值 | 小文件 | 大文件 |
| --- | --- | --- |
| 100 KB | 669 个 / 10.5 MB | 309 个 / 633 MB |
| **1 MB** | **812 个 / 71 MB** | **166 个 / 573 MB** |
| 5 MB（现状硬上限） | 972 个 / 491 MB | 6 个 / 152 MB |

**68% 的文件只占 1.6% 的体积** —— 分级的意义在此：阶段一仅 71 MB，一两分钟可完成，覆盖 83% 的文件（全部 md / json / 小图）。

```
sync 任务
 ├─ fetch → import                    （一次）
 ├─ 阶段一：≤1MB 文件 + DB jsonl + profile + skills
 │    → export → commit → push        ← 完成即置 idle，对外是"同步完成"
 └─ 阶段二：>1MB 文件，独立低优先级队列
      → 每批 ≤50MB → export → commit → push → 报进度
      → 批次间让路：sync / watcher 需要仓库时，当前批次传完即暂停
```

**三个关键约束：**

1. **阶段二按批切片（50 MB/批）**。git push 失败会丢弃 quarantine 对象，一次性传 573 MB 等于每次失败从头再来；切片后已成功的批次不重传。批次大小同样受限于 §4.3 的单步粒度问题 —— 批次必须小到能被续期机制覆盖。

2. **`stageAllChanges` 必须加排除集**（`sync-manager.ts:771-783` 现存缺陷）：

   ```ts
   for (const [filepath, head, workdir] of status) {
     if (head !== 0 && workdir === 0) await git.remove({ ...p, filepath })
   }
   ```

   `HEAD 有 + 工作区没有 = 删除`。分级后，阶段一 export 用 1 MB 过滤，大文件**不在** sync 工作区 → 被判为删除并提交推走 —— **阶段一每跑一次就删一次阶段二的成果**。修法：`stageAllChanges` 接受排除路径集，这些路径不参与 `hasChanges` 判定、不 `remove`；`git.add` 从目录遍历，不在目录里的文件本就不会被加入，只需堵住 remove 一侧。

   > 该缺陷在当前 5 MB 上限下已经存在（"曾经 <5MB 同步过、后来长过 5MB"的文件旧版本会被静默删除），只是本机恰好没有此类文件（6 个视频生成时就超标，从未进入仓库）。

3. **镜像删除安全阀语义保持**（`sync-copy.ts:168-175`）。现行为"跳过大文件时名字留在 `srcNames` 里，目标侧同名旧版本不删，避免『跳过』被误当成『删除』"—— 分级后阶段一"看不到"大文件，这条语义必须原样保留，否则会误删远端已有的旧版本。

### 4.2 异步任务化

慢操作的工具调用**秒回 `{ jobId, phase }`**，后台执行，完成 / 失败 / 进度一律走回填。

复用 `spawn_agent` async 的既有机制：父 Agent idle 时 `prompt` 唤醒，running 时 `followUp` 排队（`bridge-lifecycle.ts:298-346` `handleAsyncSubagentComplete`）。**这是仓库里已验证的"后台跑完回填上下文"实现，不需要新造轮子。**

`resolve_sync_conflict` 一并改造 —— 当前"超时了但后台还在跑"的薛定谔状态是 L3 循环的直接来源，异步化后该状态从根上消失。

### 4.3 滑动续期（ProgressFence 移植）

移植 `packages/agent-runtime/src/compact/progress-fence.ts` 的 `ProgressFence` + `withProgressTimeout`：

- **双预算**：`idleTimeoutMs`（默认 120s，距上次进度多久判死）+ `totalCeilingMs`（绝对封顶，防死等）
- **语义**：从"总共等了多久"变为"多久没动静了"。正常推进 → 自动续命；真卡死 → 在 idle 预算内判失败
- 触点打在步骤之间（export 完成、fetch 回来、import 完成、push 开始/结束 —— `sync-manager.ts` 已有 `[sync] N. ...` 日志点，可直接挂）

**必须诚实标注的限制**：isomorphic-git 是纯 JS 库，单次 push / add 内部无法注入进度信号，触点只能到**步骤级**。若某一步自身就超过 idle 预算，滑动窗救不了它。这正是 §4.1 分批的第二个理由 —— **分批既是减少传输量，也是让"单步"足够小到能被续期覆盖**。

配套：`isPushTimeout()`（`sync-manager.ts:133-135`）现靠**错误消息字符串匹配**，随本次改造一并类型化。

### 4.4 死循环根治

- **重入守卫（实际驱动源已查明，见实施计划 Phase 1 T1.1）**：真正的驱动链是 `autonomous-tick` cron（默认每 10 分钟）→ `handleEvolutionTick` → `driveConflictGoal` → `executeSyncConflictGoal`，且该调用位于 `isAutonomousEnabled()` 检查**之前**（无条件驱动）。落决外层超时 5 分钟 < 心跳间隔 10 分钟，**数学上必然重入**。修法：`resolveConflict` 维护 `resolveInFlight` 标志（含失效保护），`executeSyncConflictGoal` 驱动前先查 `isResolveInFlight()`。
- **超时 ≠ 失败**：区分"排队中 / 执行中"与"已失败"，前者对 Agent 报"进行中，勿重复决策"。异步化（§4.2）后此区分变得自然。
- **`massDeleteConfirmed` 语义修复（事故根因，见 §2.5）**：当前"第一次挡下 → 置位 → 第二次自动放行"在自动化流程中等同于无确认。改为：超阈值的批量删除必须由**显式用户确认**放行，确认绑定到具体的待删集合（快照 hash），集合变化即失效；**自动触发的同步永不自动放行**。此项是重新启用云同步的前置条件。

### 4.5 同步范围管理（三项全要，按需触发为主）

| 能力 | 形态 | 语义 |
| --- | --- | --- |
| **排除规则** | 配置 `syncExcludePatterns`（glob），设置页 + Agent 工具均可改 | 永不参与同步（含阶段二）。与硬编码的 `SYNC_SKIP_DIR_NAMES` 并存，后者不动 |
| **强制包含** | 配置 `syncForceIncludePatterns` | 无视 1 MB 阈值，直接走**阶段一**（立即同步） |
| **按需触发** | Agent 工具参数 `cloud_sync_push({ paths })` | 单次生效：指定路径立即同步，不走等待队列 |

用户场景原话："我在 A 机器上生成的绘本，想在 B 机器上直接看" —— 按需触发即此路径。

### 4.6 配置模型

```jsonc
  "enabled": true,
  "provider": "gitcode",
  "repoUrl": "...",
  "branch": "main",
  "intervalMinutes": 30,
  "smallFileThresholdBytes": 1048576,   // 新增：阶段一阈值
```

## 6. 安全 / 隐私 / 风险与缓解

### 6.1 安全

| 项 | 风险 | 缓解 |
| --- | --- | --- |
| Agent 自主 push | Agent 可写远端仓库（数据外发不可逆） | push 类工具加入 `WRITE_TOOL_NAMES` 触发用户确认；**注意 `needsPermission: true` 只是声明，不入列则 `default` 模式静默放行** |
| 自主目标放行 | system-maintenance 目标可能自主调用写型工具 | `GOAL_EXECUTION_TOOLS` 倾向**先不放**写型云同步工具（该列表有 T1/T2/T3 风险分级约定） |
| token | 已由 `safeStorage` 加密 | 不变；日志中 token 已有 `split(token).join('***')` 脱敏（`sync-manager.ts:1190`） |
| 排除规则被 Agent 篡改 | Agent 改配置把敏感目录纳入同步 | 规则变更走配置写入路径，属可审计的显式操作；如需更强约束可后续加规则变更确认 |

### 6.2 隐私

同步内容已是用户选定范围（Wiki / 记忆 / 用户配置 / 自主进化数据 / 技能 / workspace 产出），不含对话历史与工具缓存。本次改动**不扩大**同步范围。

### 6.3 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 单步超时无法续期 | 某批 push 仍可能超时 | 50 MB 分批把单步压到续期机制可覆盖的范围；超时批次下轮重试 |
| 阶段一/阶段二之间的中间态 | 远端短暂缺少大文件 | 可接受：小文件是元数据与文档主体，大文件是产物 |
| 阶段二队列持久化 | 重启丢失待传列表 | 队列状态从"工作区与 HEAD 的差异"重建（大文件仍在本地，天然幂等），无需额外持久化 |
| `cloud_sync_read_file` 读 remote 侧失败 | Agent 决策效率低 | 独立排查（实施计划 Phase 1） |
| 分级后阶段一频繁 commit | 历史提交数增长 | 阶段一批次不单独成史，与 sync 提交合并 |
| 改动落在主流程超时语义 | 回归面广 | 必须跑 `test:all` 全量；`refreshConflictFromRemote` 四种返回值全覆盖 |

## 8. 测试与验收

1. **死循环消除**：构造冲突场景，后台任务在跑时不再发起新一轮 Agent 处理；日志中不再出现连续"超时 → 重试"序列。
2. **分级生效**：新增一个大文件，阶段一在 1 分钟内完成并置 idle，大文件在阶段二队列中出现且最终推送成功。
3. **误删修复**：阶段一执行后，阶段二已提交的大文件在 HEAD 中保持不变（当前实现会删除）。
4. **续期生效**：人为拖慢网络，只要步骤在推进，任务不被判超时；真正卡死时在 idle 预算内失败。
5. **按需触发**：`cloud_sync_push({ paths: [...] })` 指定一个 >1MB 文件，秒回 jobId，完成后回填。
6. **零回归**：`pnpm --filter ./apps/windows test:all` 全绿。
