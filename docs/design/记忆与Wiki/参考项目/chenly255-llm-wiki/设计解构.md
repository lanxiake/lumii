# chenly255/llm-wiki 设计解构与 Lumii 参考

## 结论

`chenly255/llm-wiki` 是一个以 Markdown 目录为核心、由 Claude Code Skill 编排的个人知识库工作流，而不是常驻数据库服务。最有价值的部分是：原始资料、AI 编译产物与人工信任内容分区；任何写入均由显式操作触发；索引和关系图可从 Markdown 重新生成。它适合为 Lumii 的内容所有权与审核流提供参考，不适合作为桌面端存储或检索实现直接复用。

## 已验证：架构与数据流

```text
原始文件或 URL -> raw/inbox 与 raw/sources
                      |
                      v
              Agent digest / compile
                      |
                      +-> wiki/concepts, entities, sources
                      |       |
                      |       +-> [[wikilink]] -> index.py -> _index.md / _graph.md
                      |
                      +-> output/（报告等衍生物）
                      |
                      +-> 人工确认 trust -> trusted/
```

- `README.md` 定义 `raw/inbox`、`raw/sources`、`wiki`、`output`、`trusted` 和 `log.md` 的目录职责，并将 Obsidian 兼容的 `[[wikilink]]` 作为关系表达。
- `SKILL.md` 明确“获取不等于入库”：链接默认只获取并展示，只有用户显式要求保存/入库时才创建 wiki 内容；`trust` 是从 AI 产物到可信内容的人工审核动作。
- `scripts/index.py` 全量扫描 `.md`，解析首个 H1、摘要和 `[[...]]`；生成反链、断链、孤岛列表，并限制 Mermaid 图为最多 50 个概念/实体节点。它是可重建的派生视图，不保存独立的关系真相源。
- `scripts/search.py` 每次查询重新读取 Markdown，在内存建立简单 BM25 索引（`k1=1.5`、`b=0.75`），返回路径、标题、分数和邻近行摘要。其 tokenizer 以空白和标点切词，未提供持久索引、增量更新或中文分词策略。

## 对 Lumii 的建议

1. P0 将 `raw`、用户可编辑 Wiki、AI 草稿和已确认知识分为可见状态或独立来源类型；AI 不得覆盖用户原文。
2. P0 支持 Markdown `[[wikilink]]` 与 backlinks，并提供从页面源数据重建索引的能力；将图谱视图延后到链接密度足够时。
3. P1 将“编译/归纳/发现断链”设计成可审阅候选和操作日志，`publish` 或 `trust` 必须由用户确认。
4. P0 搜索使用 SQLite FTS5 而不是每次扫描全部文件；同时保留路径、标题、命中片段和来源以解释结果。

## 不可直接采用项与风险

- 不采用 Claude Code Skill、MCP 获取工具或其全局配置路径；Lumii 应通过 `agent-runtime -> Electron main -> preload -> renderer` 建立边界。
- 不采用其简单 tokenization 作为中文检索方案，也不把约 100 篇文档的 README 经验外推到大规模库。
- `README` 声明 MIT 但根目录缺少许可证文件；在复制代码、文案或脚本前必须先确认上游许可证状态。
- Mermaid 自动图只能作为浏览产物；不能替代可查询、可追溯的链接数据。

## 分阶段采用

| 阶段 | 范围 |
| --- | --- |
| P0 | 页面来源标识、Markdown/Wikilink、FTS5、反链与可重建索引 |
| P1 | AI 编译草稿、人工信任动作、操作日志、断链/孤岛检查 |
| P2 | 页面关系统计和受限图谱视图 |
| 不纳入 | Claude Skill 命令、依赖外部 Agent 工具的摄入实现 |
