## 0. 结论摘要

| 问题 | 结论 |
|------|------|
| 第一期做什么 | **只做 Ubuntu 图形界面（形态 A）**：出包 → 能启动 → 核心功能可用。终端/无头形态（形态 B）整体推到第二期 |
| 第一期的三个硬骨头 | ① **构建环境不可用**（无 pnpm、无 node_modules、Node v26 高于仓库基线 22）② **打包链路只有 Windows 段**（`electron-builder.json` 无 `linux`）③ **平台抽象层缺失**（`taskkill` 8 处、策略混排、数据根双实现） |
| 桌宠怎么办 | **屏蔽入口 + 文案说明**（决策见 §1）。`packages/pet-core` 与 `src/renderer/pet/**` 一行不改——将来用精灵图重写时它们仍是资产 |
| 屏蔽机制怎么建 | 新增**统一的 `FEATURES` 矩阵**（`main`/`renderer` 同源读取），桌宠以它作为首个使用者。以后录屏、系统音频等屏蔽项都挂这里，不再散落 `if (platform)` |
| 第一期验收 | AppImage 双击能启动 → 完成一轮含工具调用的对话 → 记忆/Wiki/渠道/定时任务可用 → 被舍弃功能的入口明确置灰且有说明。**不含桌宠、录屏、无头** |
| 主要风险 | Linux 上首次全量安装/编译原生模块（better-sqlite3、onnxruntime-node、sherpa-onnx、sharp）能否跑通；Node v26 的兼容性；`silk-wasm` 打包后是否随包分发（存量缺陷 2） |

**与调查文档的关系**：调查文档 §4 的 P0/P1/P2/P3 是**完整移植**的优先级；本文的「批次」是**第一期**内的实施顺序，两者不是同一套编号，不应混用。

## 3. 构建与运行环境（M0，风险最高，最先做）

| 步骤 | 内容 | 退出标准 |
|------|------|---------|
| M0.1 | 安装 pnpm 10.23.0（`corepack` 或官方脚本；仓库 `packageManager` 已钉版本），把构建 shell 切到 Node 22 | `pnpm -v` = 10.23.0，`node -v` = 22.x |
| M0.2 | `pnpm install`（`.npmrc` 已配 npmmirror 镜像与 `allow-build-scripts`）。**风险点**：`shamefully-hoist=true` + Linux 平台 optional 包自动安装；`.npmrc` 的 `allow-build-scripts` 列表**不含 `onnxruntime-node`**（尽管 `pnpm-workspace.yaml:15` 的 `onlyBuiltDependencies` 列了它），需确认它是否需要编译、以及 pnpm 版本对两个配置的优先级 | 安装无报错；`node_modules/better-sqlite3`、`onnxruntime-node`、`sharp`、`sherpa-onnx-node` 的 Linux 产物存在 |
| M0.3 | `postinstall` 的 `@electron/rebuild --only better-sqlite3,sharp` 在 Linux 上成功 | `pnpm --filter ./apps/windows exec node -e "require('better-sqlite3')"` 不报 ABI 错 |
| M0.4 | `pnpm dev` 起 Electron（X11） | 出现主窗口；主进程日志写入 `~/.lumii/logs/` |
| M0.5 | `pnpm --filter ./apps/windows typecheck` 与 `test:all` 基线 | 记录**当前**失败集合（作为后续改动对比基线） |

**不做的事**：不在 Windows 上交叉打包（原生模块必须在目标平台 rebuild）；不使用 Ubuntu 26.04+ 的新包名假设。

**平台探测（M0 产出）**：写一个只读探测脚本（`scripts/probe-linux.mjs`，第二期无头形态可复用），报告：

1. 会话类型：`XDG_SESSION_TYPE` / `WAYLAND_DISPLAY` / `DISPLAY`；
2. 透明合成器：`_NET_WM_CM_S0` 是否被选中（无该 atom 则透明窗不可用，主窗口仍可用）；
3. `screen.getCursorScreenPoint()` 在真实 X11 下是否返回期望坐标（第二期桌宠用，第一期只记录）。

## 5. 批次二：平台抽象层 + 目标分层结构

### 5.0 目标分层结构（D19）

> 本节回答「改完之后的代码长什么样」，也是「便于后续其他客户端移植」的可度量判据。**批次划分（§6–§8）是实施顺序，本节是结构**——两者是正交的两条轴，不要混用。

```
packages/agent-runtime/           零 Electron（已成立，边界必须守住；第二期解耦时加 CI 守卫）
  └─ shell/                       ShellProvider 等抽象已在此
apps/windows/src/
  ├─ shared/                      跨进程契约（含新增 feature-availability.ts）
  ├─ main/platform/               ← 新增：平台实现层（唯一的「判断平台」的地方）
  │     ├─ capabilities.ts        平台能力探测（会话类型、合成器、Python…）
  │     ├─ process-kill.ts        win32: taskkill /T /F      linux: 进程组 SIGTERM→SIGKILL
  │     ├─ shell-env.ts           win32: 现有白名单         linux: +XDG/DISPLAY/DBUS
  │     ├─ system-info.ts         win32: WMI/Get-Process    linux: df/ps
  │     ├─ security-policy.ts     win32: 现有策略（不动）    linux: 独立策略表
  │     ├─ cli-paths.ts           win32: 现有候选           linux: ~/.local/bin…
  │     └─ autostart.ts           win32: 现有 API           linux: XDG .desktop
  ├─ main/<业务模块>              只调 platform/ 的原语，不再出现 process.platform
  └─ renderer/                    只读能力快照（FEATURES 矩阵）
```

> **关于未纳入本期收敛的存量平台分支**：本期**只收敛会被重写的部分**（`process-kill`、`shell-env`、`system-info`、`security-policy`、`cli-paths`、`autostart`）。以下几类**明确不动**，它们已是正确的跨平台实现，且不属于本期的风险面：
>
> - `skill-md-frontmatter.ts:174`（`where`/`which` 分支）、`cloak-browser-downloader.ts:237/260/566/689`（三平台资源矩阵）、`wecom-login-service.ts:29`（`linux=3` 映射）、`model-manager.ts:1129`（tar 分支）；
> - `voice/model-manager.ts` 的 torch wheel、`updater-service.ts` 等**已判定第二期处理**的点。
>
> 因此 §5.0 规则 1 的验收判据**只对本期的六个原语生效**，不是「一次扫清 `src/main` 里所有 `process.platform`」。`src/main/cloak-browser-downloader.ts` 等文件里保留的分支是**有意的**，不是遗漏。

**三条硬规则**：

1. **平台判断只发生在 `platform/` 内部**。业务模块调用原语，不自己写 `if (process.platform)`。这是可度量的验收判据：`grep -rn "process\.platform" src/main --include=*.ts | grep -v platform/` 的残留收敛到接近 0（`index.ts:1173,1188` 这类进程级开关允许保留，需逐条备注理由）。
2. **`platform/` 是「宿主实现细节」，不提前抽象成跨仓接口**。将来随宿主一起搬进 host 包是机械搬运（调查文档 §7.6 已判定返工成本低）。现在为它设计跨仓接口，属于「没有真实需求的设计抽象」。
3. **`shared/` 的能力矩阵是渲染层与未来客户端的契约**。第二期的无头形态、将来的精灵图桌宠、系统 Python，都往同一张表扩展，不各自发明一套。

> **不做的事**：不在 `packages/` 下新建平台包。`platform/` 原语依赖 Electron/主进程上下文，放 `packages/agent-runtime` 会违反 `AGENTS.md:3` 的边界约定。

### 5.1 进程树终止（8 处收敛为 1 处）

已核实的重复实现：

| 位置 | 现状 |
|------|------|
| `shell-runner.ts:273-296`（`forceKillProcess`，类方法） | win32 走 `taskkill /pid <pid> /T /F` |
| `ts-runner.ts:248-261`（同类方法） | 同上 |
| `python-runner.ts:269-287`（模块函数） | 同上 |
| `local-bash.ts:20-38`（模块函数） | 同上；注释已指出非 win32 分支只杀 shell 本身、孙进程变孤儿 |
| `browser-service.ts:122` | 直接 `spawn('taskkill', ...)` |
| `system-service.ts:784` | `execAsync('taskkill /PID ... /F')` |

目标 API：

```ts
export function spawnChildInGroup(command, args, options): ChildProcess  // POSIX: detached=true 使其成为进程组长
export function killProcessTree(child, signal = 'SIGTERM'): void
  // win32: taskkill /pid <pid> /T /F（SIGTERM 对 cmd/powershell 子进程树无效）
  // posix: process.kill(-pid, signal) → 2s → SIGKILL；进程组不可用时回退单进程 kill
export function killPidTree(pid: number): void  // 外部进程（浏览器残留等）
```

**行为变更提示**：POSIX 下 `detached: true` 才会形成独立进程组；随之需要在应用退出钩子统一清理子进程，避免「Electron 退出后孤儿存活」。这是本次移植引入的行为变化，需在实施计划里显式列出并测试退出清理。

### 5.4 安全策略（`security-utils.ts:38-68`）

现状把两套平台规则混在一起：`allowedCommands: ['powershell','cmd','tasklist','taskkill','systeminfo','wmic']` 是 Windows 命令；路径黑名单混了 `/etc`、`/var` 与 `C:\Windows`；长度上限硬编码 260。

设计要点：

- 按平台返回**完整策略对象**（允许根 / 禁止模式 / 命令白名单 / 最大长度 / 最大深度）；
- **允许根优先于禁止模式**：命中 `allowedBasePaths` 即通过，避免 `os.tmpdir()` 的平台差异被 `/^\/var/i` 误伤；
- POSIX 侧移除过宽的 `/^\/var/i`，改为 `/^\/var\/lib`、`/^\/var\/spool`；补齐 `/usr`、`/boot`、`/proc`、`/sys`、`/dev`、`/root`；
- 长度上限从 260 改为策略字段（POSIX 常用 `PATH_MAX` 4096），但**不改 Windows 侧行为**——这是越权防护，直接删除会引入安全回归；
- 命令白名单按平台给：POSIX 侧给 `bash`、`sh`、`ps`、`kill`、`df`、`free` 等。

### 5.5 CLI 路径探测

`cli-user-path.ts:21-29` 与 `coding-dev-cli-detect.ts:179-189` 补 Linux 候选：`~/.local/bin`（已无条件包含）、`~/.cargo/bin`、`~/.npm-global/bin`、`/usr/local/bin`、`~/.bun/bin`。`where.exe`/`which` 分支已存在，直接检查文件存在而非依赖 PATH。

### 5.6 剪贴板

`ipc/dialog-clipboard-ipc.ts` 的 win32 走 PowerShell 写 CF_HDROP、darwin 走 `osascript`，Linux 落到 Electron `clipboard` → 第一期**只复制路径文本**并在 UI 提示。
