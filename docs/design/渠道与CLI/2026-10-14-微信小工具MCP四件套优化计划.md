## 0. 一页结论

四件套现在的完成度不低：零注入、只读、失败信封统一、安装/技能包/有效期都商品化过一轮。
本次调研的结论不是「要大改」，而是**三个结构性缺口 + 一批低风险高收益的补丁**：

| # | 缺口 | 归属 | 证据强度 |
|---|---|---|---|
| 0 | **⚠️ 生态风险**：官方点名"破解数据库"与"模拟按键"，腾讯已 DMCA 下架 30+ 同类项目 | 全 | 官方公告 + 多家媒体（**§2.5，先读**） |
| 1 | **合并转发（聊天记录）只导出一行摘要，正文全丢**——竞品明确做了 | B | 实测定死（§3.1） |
| 2 | **引用消息没带出被引用的原文**——设计文档的示例承诺了，实现没做；竞品已做 | B | 实测 + 代码对照 |
| 3 | **群成员只有全局显示名，"群里那个人叫什么"查不到**——`contact_fts.db` 里其实有 | C | 实测（§3.3） |
| 4 | **沉默客户只有排序、没有分层**——而这是四家 SCRM 的标配需求 | C | 调研（§2.3） |
| 5 | 视频谁都不管：A 明确不做、B 没有实现 | A/B | 代码对照 |
| 6 | 撤回后**媒体本体**还原不了（归档只存了消息 XML）——调研点名"只存文字不存文件"是行业通病 | D | 代码对照 + §3.5 |
| 7 | 导出的 HTML 是**相对路径 assets**，换台机器全红叉；行业公认"没人做到单文件可翻阅" | B | 代码对照 + §2.2 |
| 8 | 共享底座两处隐患：`_plain` 的镜像占用竞态、`describe_nontext` 的**失效注释** | 全 | 实测踩到（§3.7） |

外部调研（§2）给了两个值得写进定位的事实：
**同类工具全部要求你 patch 客户端或扫码登录第三方**，而我们在做的是"不碰微信进程、原生读 4.x 库"
——这不是功能竞赛，是生态位差异；以及 **§2.5 的生态与合规风险**，它决定发布形态，不是功能问题。

> ⚠️ **先读 §2.5**。微信 2026-01 的安全公告逐字点名了两类行为，而四件套的两条主线
> （读本地库解密、模拟按键发送）**在形态上分别落在里面**。这不否定技术本身只读/零注入，
> 但它影响"怎么发、怎么命名、README 怎么写、能不能商用"——是立项级前提，不是文案问题。

## 2. 外部需求调研

### 2.1 A · 文件归档

**市场痛点（强，且官方已经定过调）**

- 微信团队 2025-12-29 公开回应：**文件过期 = 没下载到本地或已被清理，服务端也拿不回来**，
  网上流传的"找回过期文件攻略"同样无效。过期时限官方从未公布。
- 一个死结被反复提到：**关掉"自动下载"省空间 ⟺ 更多文件在手机端过期**，等于主动放弃唯一留存机会。
- 官方自己给的数据：**占用 40GB 以上的用户里，聊天记录平均占 70%**；用户"一键清理原图原视频"能释放 10+G。

**同类工具做了什么**

| 工具 | 形态 | 关键能力 | 现状 |
|---|---|---|---|
| 微信文件采集助手 V2.22（52pojie） | GUI | **通配符 + 日期批量挑文件**——"对接几十家店收报表，一下把今天的文件导出来" | **作者已宣布停更**，仅 Win10+ |
| wechat_file_manager（macOS，开源） | CLI | MD5 哈希去重 + 集中存储 + 符号链接保持原结构 | — |
| wechat-file-organizer（Windows，开源） | CLI | 按「月份+类型」归档、`--since`、dry-run、移回收站 | **去重是"比大小"不是哈希 ⇒ 会误判** |
| 时间猎犬 / 归所 / 雷神 / WxCleaner | GUI/CLI | 归类或去重 | **只管本地已有文件，不解决"谁发的、哪个群的"**，也不管过期 |

**用户原话（痛点）**

- 「近日需翻起陈年旧账，发现以前聊天记录里的文件已经失效了」（V2EX）——**用户总是发现得太晚**
- 「图片都在文件夹里缓存了」→「这种方式还是挺不方便的，得再做筛选」（52pojie）
- 「对接几十家店，收集报表…一下子把今天要的文件导出来，不用再翻聊天记录」（工具作者）
- WeChatMsg PR：**「把视频/音频/图片的修改时间改为其发送时间，方便本地筛选」**

**对我们的含义（差异化收敛成一句）**

调研的原话是：**没有任何工具同时做到「只读本地 + 文件归档 + 真哈希去重 + 来源归属 + 不出网」**。
A 现在的形态（copy-only / 不覆盖 / 按会话布局 / dry-run）已经覆盖了两个开源工具的大半，
真正的差距只有两条：**内容级去重与空间账**、**来源归属（哪个会话、谁发的、什么时候）**——
后者我们**天生有数据**（本来就读消息库），别人没有。
"过期文件救援"官方已定调不可能，不做是对的。

**不值做**（调研结论，与我方判断一致）：**zip 一键打包**（调研中没有任何用户提）、云同步（让别人做）、
PDF/Word 内容提取与全文检索（扫描件还要 OCR，公认效果差，与"小工具"定位冲突）。

### 2.2 B · 记录导出

**同类工具**（调研给出的功能矩阵，横向对照我们缺什么）：

| 工具 | 平台 | 图片 | 语音 | 视频 | **引用** | **合并转发** | 转账 | 名片/位置/小程序/视频号 | 输出 |
|---|---|---|---|---|---|---|---|---|---|
| **留痕 MemoTrace / WeChatMsg** | Win（仅 3.x，2025-04 删库停更） | ✅ | ✅ | ✅ | ✅ **可定位原文** | ✅ **可展开** | ✅ | ✅ | HTML/Word/CSV/TXT/SQLite |
| chatlog | Win/mac，3.x+4.x（2025-10-20 收函删库） | ✅ | ✅ | ✅ | 未证实 | 未证实 | 未证实 | — | json/csv/文本 + **MCP** |
| wechatDataBackup | Win（**不支持 4.0**） | ✅ | ✅ | ✅ | 未证实 | 未证实 | ✅ | ✅ 全类型 | **界面还原微信** |
| WechatExporter(93857536) | macOS 13+ / Win | ✅ | ✅ **本地转写** | ✅ | 未证实 | 未证实 | ✅ | 未证实 | **单文件 HTML（媒体全内嵌）**、EPUB、加密包、水印 |
| **四件套（B）** | Win，**微信 4.x** | ✅ | ✅（±转写） | ❌ | ❌ | ❌ | ❌ | ❌ | md/html/json |

**行业公认的缺口（原话）**：**没人同时做到「4.x 兼容 + 消息全类型 + 单文件可直接翻阅 + 本地转写」**。

**用户原话（痛点）**

- 「**能用的工具一个接一个被腾讯搞掉**」——「先有 MemoTrace，后有 wechatbackup，再是 chatlog，没一个逃过」
- 换机助手导致 8 年记录全无；「弄丢了好多记录，真的太可惜了」
- **图片打不开**："电脑端没点开过，只加载了预览图"（官方 FAQ）——**我们已知的同一个坑**
- 语音只剩 `[语音]` 占位、归属难
- 留痕"前一天还能导，隔天就废"
- **喂 AI 卡上下文**：MCP 默认 `limit=100` 导致"只能取到少部分消息"（chatlog issue #17）

**对我们的含义**

- **必须补**：合并转发展开（B1）、引用原文（B2）——**竞品明确做了而我们没做**，且这正是
  "用户转发聊天记录的主要形式"，现在被压成一行摘要 = 内容整体丢失。
- **补上就构成差异化**：**单文件自包含 HTML（媒体内嵌、目录锚点，"双击像微信一样翻"）** +
  `manifest.json`（条数/起止时间/SHA-256）。前者直击"没人做到"，后者回答"证据效力弱"。
  注意：现在 `media="images"` 出的是**相对路径的 assets 目录**，换台机器就全是红叉——自包含是实质改进。
- **别踩的坑**：`limit` 默认值（read_history 也有）；图片"电脑端没点开过就只有预览图"要**显式计数报缺**。
- **不做**：分析可视化（词云/年报/性格画像——竞品扎堆，且偏离"只读取数"）、企微会话存档接入。

### 2.3 C · 客户分析

**同类工具全是企业微信 SCRM**：OpenSCRM(Apache-2.0)、MoChat(GPL-3.0)、CRMUU、LinkWeChat、
powerxadmin、yshop-crm、微小擎。它们的共同功能面：**客户标签、客户群标签、客户群列表、
自动拉群、群 SOP、群发、成员统计、会话存档**。

**关键事实：它们全部依赖企业微信官方 API**。个人微信没有任何官方接口，所以这个赛道对个人号是空的——
我们不是在和它们竞争，是在补它们覆盖不到的生态位。

**需求映射**（它们有的 → 我们的对应物）：

| SCRM 能力 | 四件套现状 | 差距 |
|---|---|---|
| 客户标签 | **做不到**（本地无好友↔标签映射表） | 仍 backlog |
| 客户群列表 / 成员统计 | `list_contacts(scope=group/room)` | **群内昵称缺失**（见 C1） |
| 会话存档 | D 的归档 | 已覆盖，比 SCRM 更前置 |
| 客户画像 | `wechat_profile_get/save`（主产品） | 已覆盖 |
| 群 SOP / 自动拉群 / 群发 | `send_batch`（主产品，逐目标校验） | 已覆盖 |
| **沉默客户清单（30/60/90 天分层）** | `interaction_rank(sort=recent)` | 缺分层与原始时间戳口径（见 C3） |
| **通讯录全量导出** | `list_contacts`（默认 200 条 + offset） | 缺"导出"形态（见 C7） |
| 互动频次 / 首响时延 | `contact_stats` 部分覆盖 | 缺响应时延口径（见 C8） |

**⭐ 本次调研最有力的发现（支撑 §6.1 那条"只出取数、不出判断"的线）**

厂商都在卖**判断**（微盛自称标签 90%+、一维助手 85–95%、腾讯企点 85%+，全是自述无第三方验证），
但一线的反应是——

- 「销售对 AI 打分的第一反应：**凭什么这条是高价值、那条是低价值**」，最后分级"变成后台没人维护的数字"
- 「**最怕的不是分级不准，而是没法反驳。不能被反驳的分级本质是黑箱**」
- 从业者给的验收方法：抽 30 条让两个资深销售独立分级对比 AI，「人工之间一致率往往也只有七成」
- 「AI 能分析互动频率，但**看不到客户内部谁在失势**」，结果 AI 高分却丢单

⇒ **我们"不出判断"不是缺功能，而是恰好避开了市场最被诟病的一环**。
可以反过来讲成卖点：**别人给你一个不可反驳的分数，我们给你能自己验算的原始数字。**

**另外两条边界（来自调研，必须遵守）**

- **不要声称"官方禁止个人微信客户管理"**——官方禁的是**手段**（见 §2.5），没找到针对品类的说明。
- 「个人微信 200 个标签 / 单好友 20 个标签」是第三方经验值，**官方从未公开确认**，别当事实引用。

### 2.4 D · 撤回防护

**同类工具的路线，一条比一条更"脏"**：

| 路线 | 代表 | 代价 |
|---|---|---|
| 二进制补丁 | RevokeMsgPatcher（把 `JE/JZ` 改成 `JMP`，绕过撤回逻辑） | 版本一升级就失效；改客户端内存 |
| 网页版协议 | itchat / wxpy | 网页版已基本停用，协议频繁变更，**有封号风险**；只缓存最近 200 条 |
| 内存取证 | pmdump 转储 + 分析 | 面向取证，重 |
| 安卓通知监听 | 各类 App | 只拿到通知文本，要授权+常驻 |
| 企业终端监控 | 安企神类 | 合规侧部署，非个人 |

**行业调研里被点名的常见坑**：「**只存文字不存文件**」「只盯微信漏企微」「纯 API 方案遇端到端加密失明」。
第一条正好命中我们的缺口（D 归档只有消息 XML，没有媒体本体，见 D1）。

**⭐ 调研的关键发现：需求是"追溯"，不是"拦截"**

> **没有找到任何一条「我装了防撤回工具就为了实时拦截」的正面诉求原话**。
> 找到的诉求几乎全是**「东西没了想找回来」「怕对方赖账」「想永久留住」**。

而所有补丁类工具的 README 都自己写明：**「装上那一刻起生效，之前撤回的拿不回」「它不是时光机」**
——**用户真正想要的那件事，恰好是补丁给不了的**。D 走的是"事前留档"，正好接住这个空缺。

**用户原话**

- 「老板承诺的奖金截图、客户确认的方案记录，如果都能被对方无时限撤回，那**弱势一方连自证的底牌都没了**」
- 「消息已读 127 次，**撤回根本没用**」
- 「**导出亲人去世后的聊天记录永久保存**」（V2EX 求 4.0 版备份工具）
- ⚖️ **山东巨野 2026 借贷案：被告用已撤回的片段截图主张赠与，法院认定"截图不完整、还原不了完整沟通过程，不予采信"**
  ⇒ **碎片截图 ≠ 证据**。这是"常驻归档"相对"截图/补丁"的最强论据，直接写进 README。

**同类方案的能力与代价**

| 方案 | 能拿回已撤回？ | 代价 |
|---|---|---|
| PC 补丁（RevokeMsgPatcher / BetterWX） | ❌ 只是让**后续**撤回失效 | 改官方 DLL；微信一更新即失效；杀软报毒 |
| RevokeHook（运行期注入） | ❌ 同上 | 注入比改文件更易触发完整性校验 |
| 手机 Xposed/LSPosed | ⚠️ 拦后续 | **微信官方明令违规**（封号警告里点名"消息防撤回"）；实测有人 24h 内收预警 |
| **企业微信「会话内容存档」（官方）** | ✅ **含被撤回、被删除消息** | 需认证企业 + 开发能力 + **400~1800 元/人/年**；**不能回溯开通前** |
| 取证设备（美亚柏科/盘古等） | ✅ 碎片级恢复 | 需专业设备与鉴定机构 |
| **D（常驻只读留档 + 事后对差）** | ✅（归档期内的） | 零门槛；**不碰微信进程** |

**两个行业公认的硬伤，我们的处境**

1. **关机/守护没跑那段时间的撤回永久丢失，无人解决**——官方 SDK 也"不能回溯开通前"。
   ⇒ D 的 `archive_gap` **如实暴露漏抓区间**，在调研里被标为"无同类先例的设计"——这不是缺点，是可信度来源。
2. **「可提交的证据」（哈希/可信时间戳）与导出工具断层**——导出工具只管出 txt/html，
   存证是另一批工具（权利卫士/e签宝/铭印）。⇒ D2 导出时**顺手带上哈希与时间线**，就把断层接上了。

**对我们最该做的一条**：把「**无封号风险的撤回追溯**」讲成主打——
需求侧（用户要"找回来"）与供给侧（补丁做不到、hook 会被封）之间的空缺最大，
而 D 的能力（只读 + 常驻 + 不注入）恰好严丝合缝。这条要写进 README/技能包。

**明确不做**：不做防撤回补丁/注入（法律与封号双风险，与现有能力零复用）
✱ v1 不做区块链存证上链（哈希 + 导出日志已够内部追溯，上链是独立生意）。

**A. 微信官方 2026-01 公告点名了两类行为**（原话摘录）：

> 违规获取聊天记录、联系人信息等敏感数据；
> **外挂类工具**：利用**模拟按键、自动化脚本操控微信**，实现"自动回复""管理聊天记录"

> —— 官方原话：**「不要安装或使用任何访问本地聊天记录的第三方工具」**
> 处置阶梯：功能限制 → 登录异常验证 → 临时限制 → **账号冻结，严重者永久封禁**

**这几句要如实写进 README 与技能包，不能承诺"绝对安全"。**

## 3. 本轮新证据（只读实测）

### 3.1 合并转发的内容是**可完整还原**的 ✅（B1 的前提）

`local_type=49` + `appmsg <type>19</type>` 的消息，`<recorditem>` 的 **CDATA 里嵌了一段完整的
`<recordinfo>` XML**，`<datalist>` 逐条列出被转发的消息：

```
本机 8 条合并转发，dataitem datatype 分布：{1: 19, 2: 15, 8: 5, 17: 1}
  datatype=1（文本）→ <datadesc>正文</datadesc>
                      <sourcename>谁说的</sourcename>
                      <sourcetime>2026-09-06 15:57:22</sourcetime>
  datatype=2（图片）→ cdnthumburl / fullmd5 / datasize / datafmt
```

节选（真实数据，已脱敏掉无关字段）：

```xml
<dataitem datatype="1" ...>
  <datadesc>你如果有自己的意识，你希望我称呼你什么</datadesc>
  <sourcename>TOOLAN</sourcename>
  <sourcetime>2026-09-06 15:57:22</sourcetime>
</dataitem>
```

**这意味着**：合并转发**不是一个"摘要行"，而是一段结构化数据**——发送者、时间、正文都在。
现在 B 把它压成 `[聊天记录] 时遇的聊天记录`，等于**把最常被转发的那类内容整体丢掉**。

### 3.2 客户端自带的 FTS **不能直接换用**（关掉 §9.4 的一个选项）❌

- `message_fts.db` 的 `message_fts_v4_*` 用的是微信私有 `MMFtsTokenizer`，系统 SQLite 打不开；
- 覆盖率实测 **73.4%**（3625 / 4942 条）——直接换过去会**静默漏结果**，这是最坏的一类失败。

⇒ 结论不变：检索要走**自建 FTS5(trigram) 索引 + `local_id` 水位增量**。
但它的 `_content` 表是**普通可读表**，可以当"文本快照"用（例如给自建索引做首轮灌数据）。

### 3.3 群内昵称**可解**，不在 protobuf 里 ✅（关掉 §8 backlog 的一半）

原设计说"在 `chat_room.ext_buffer` 里，字段语义未知"。**实测另有其表**：

```
contact_fts.db
  chatroom_member_fts_v3_content   行=1980
    c0 = 群内昵称        （如「何建辰」「魏雷」这类群里称呼）
    c1 = room_id   ─┐
    c2 = member_id ─┴─→ contact_fts.db.name2id.rowid  →  username
```

- 同一个人在不同群的名字**确实不同**（`group by member_id having count>1` 有大量样例）；
- 存在 c0 为空的行 → 必须回落全局显示名（备注 > 昵称）并标注来源。

**更正（2026-10-14 切片 2 实测）**："行=1980"是**行数**，不是**有名字的人数**——
1980 行里 **c0 非空的只有 191 行（9.6%）**。而且分布极不均：自己的办公群多（27/32 有名字），
外部大群几乎没有（1/159、8/444）。所以群内昵称**只对一部分人存在**，`name_in_room` 为空串
= "这个群里没设过"，**不是查询失败**，也不许拿全局名顶上。（`chat_room.ext_buffer` 是 ~12 字节
的 blob，不是名字表——原设计的猜测方向是错的，但结论"不在 protobuf 里"侥幸对了。）

### 3.4 `hardlink.db` 能定位磁盘文件，但消息侧的 md5 是空的 ⚠️（B3 的止损依据）

```
hardlink.db
  file_hardlink_info_v4   153 行   (md5, file_name, file_size, modify_time, dir1, dir2)
  video_hardlink_info_v4   33 行   → 磁盘命中 33/33
  image_hardlink_info_v4  481 行

msg/video 磁盘实况：59 个 .jpg（缩略图） vs 18 个 .mp4  ← 缩略图远多于视频 ⇒ 多数视频没下载
```

- **视频**：33/33 都能在磁盘上找到（`msg/video/<月>/<32hex>.mp4` + `.jpg` + `_thumb.jpg`）；

**⚠️ 本条的"只能近似配对"结论已被推翻（2026-10-14 复查）**：`videomsg` **自己身上**的 `md5`
就是这份**正片**的 md5，接 `hardlink.db.video_hardlink_info_v4` 就能拿到确切的磁盘文件名——
**这条路是精确的，不用猜**（`wechat_core._video_meta` / `_video_hardlink` / `video_file_path`，
只认正片、排除 `_raw.mp4` 与 `_thumb.jpg`，混进来就是"给错文件"）。
当初说"md5 是空的"，是**找错了位置**（试的是 `rawmd5`/`newmd5`/`originsourcemd5`，那几版实测都对不上）。

实测覆盖（本机 2026-10-14）：48 条视频消息 → **精确命中 8 条**；`hardlink` 里可用正片 12 个，
磁盘正片 15 个（`msg/video` 里 18 个 mp4，3 个是 `_raw`）。**落空 40 条的根因是视频压根没下载**
（微信只缓存看过的），不是"配对算法不够好"——近似配对**猜不出没下载的东西**，
只会把别的会话的视频按到这条消息上，那是张冠李戴，比没有更糟。

**近似配对到底值不值：拿那 8 条精确命中当标尺量过了（2026-10-14，`verify/wechat-mcp/probe_video_approx.py`）。**

盲配 = 完全不用 md5，只用「消息时间邻近 + 消息 `length` == 磁盘字节数」。结果：

| 时间窗 | 48 条里给出**唯一候选** | 在那 8 条标尺上 对/错 |
|---|---|---|
| ±60 s | 2 | 2 / 0 |
| ±10 min | 3 | 3 / 0 |
| ±1 h | 6 | 3 / 0 |
| ±24 h | 7 | 4 / 0 |

两条读法：

1. **近似救不回覆盖率**——磁盘上总共就 15 个正片，精确路已经拿到 8 条；窗口放到整整一天，
   唯一候选也只有 7 条，**比精确的 8 条还少**（另 4 条标尺消息落进"多候选"里没选中）。
   上限不是算法，是磁盘上只有那么多文件。
2. **时间窗不是可靠的键**——8 条真值里 6 条消息时间与文件 mtime 相差 ±500 s 内，
   另 2 条差 **55000 s / 498605 s**（转发、或之后才重新下载）。窗口开小漏、开大撞。

所以 B4 的**近似配对不做**（用户 2026-10-14 提出"主要用来搜索"，实测后改按"搜索侧给准"落地，见 §8 切片 4d）。
真正缺的不是配对，是**检索这条路没挂 `attach_video`**：实测搜「视频」命中 48 条、
带 `video_path` 的 **0 条**（`history`/`poll_new` 都挂了，唯独最该挂的没挂）——
用户搜到了却是一条点不开的消息。补上后 0 → 8。


图片那侧是另一回事：`wechat_image.image_file()` 已经有两条路（hardlink + `packed_info_data` 里的本地文件名），
实测 464/465 命中——**图片是可精确还原的**。

### 3.5 媒体占位与磁盘占用（A2 与 D1 的数据面）

```
<用户目录> = ...\xwechat_files\wxid_xxx_9c2d
  msg/            1321.9 MB  1289 文件   ← 真正的媒体
    file/          896.1 MB  （A 现在唯一覆盖的）
    video/         269.5 MB  （没人管）
    attach/        156.3 MB  （1049 个 .dat，图片加密本体 + History 目录）
  db_storage/       66.5 MB
  cache/            65.5 MB
```

`msg/attach/<会话hash>/<月>/Img/*.dat` = **图片加密本体**（magic `07085632`），
`describe_nontext` 注释里说的"V4 加密解不开"**已经过时**——`wechat_image.py` 解出来了（见 §3.7）。

### 3.6 扫描成本（D3 与 C/B 共用）

| 操作 | 实测 |
|---|---|
| `poll()` 一拍 | **90–131 ms** |
| `sessions()` | 321 ms |
| 首次 `_refresh()` | 1524 ms |
| 全量打底（D） | 4637 条 / **4.8 s** |

`Msg_*` 的索引是 `local_id` / `real_sender_id` / `server_id` / `sort_seq` / `(local_type, sort_seq)`，
**没有 `create_time`** ⇒ 所有按时间过滤的查询都是 `SCAN`。D 的守护每 30s 一拍、拍的都是全表扫，
随会话变大会持续变慢。

### 3.7 两处底座问题（实测踩到）

1. **`wechat_core.describe_nontext` 的 docstring 已经失效**：
   它写着「要拿图片内容得先逆向 V4，是研究任务，不是顺手能做的」，
   而 `wechat_image.py` 早把 V2 容器解开了（`aes_size` / XOR 尾巴 / 账号级 AES key，实测 464/465）。
   这段字**刚刚误导了一次本计划的作者**——属于必须改的一行。
2. **`_plain` 的镜像占用竞态**：若同一进程里还开着该库的 sqlite 连接，
   `os.replace(tmp, out)` 会 `PermissionError`（Windows 不能替换被打开的文件）。
   探针里靠"先 close 再解密"绕开，但**调用方忘关就炸**。
   设计 §6.6 记过 C 的同类问题（那里是"刷新调用必须在开连接前"）——同一个坑的第二现场。

### 切片 1 ✅ 已完成（2026-10-14）：非文本消息渲染补齐（B1 / B2 底座 + X1）

范围：`wechat_core.py`（共享层）+ `wechat-export-mcp/exportcore.py`（B 的渲染层）。
选它做第一刀的理由：一个文件一件事，同时喂**主产品的代聊上下文**（模型看到的是标签而不是 XML）
和 B 的导出，且 `test_render_labels.py` 现成在那里。

落地内容：

| 项 | 内容 |
|---|---|
| B1 | 合并转发（`appmsg type=19`）逐条展开：`merged_forward()` 解析 `<recorditem>` 的 CDATA，出 `{sender, time, ts, kind, text}` |
| B2 | 引用（`type=57`）取出被引原文：`refer_text()`，一行摘要接成 `[引用] 回复正文 ← 谁: 被引原文` |
| — | 导出层：md 排成引用块、html 排成 `.fw` 嵌套框、json 出 `forward` 数组 |
| X1 | `describe_nontext` 的过时 docstring 改掉（旧文说"图片要逆向 V4，是研究任务"，实际 `wechat_image.py` 早已解出 464/465） |

**顺带挖出并修掉两个真 bug**（都不在计划里，是写判据时撞出来的）：

1. **`_attr("type")` 命中 `datatype="2"`** —— `<type>19</type>` 是**元素**、不匹配 `type="`，
   而它后面的 `<dataitem datatype="2">` 是全串第一个 `type="` ⇒ 合并转发被读成 type=2，
   整条渲染成 `[链接] 标题 (support.weixin.qq.com…)`。修法：属性名卡左边界 `(?<![\w-])`。
2. **`_attr("length")` 命中 `cdnthumblength="`** —— 图片大小按**120px 缩略图**报，
   实测同一条：旧 2716 B（缩略图）vs 真值 32171 B（31KB）。同一根棍子。

真机取证（`verify/wechat-mcp/probe_forward_export.py`，只读 + 临时目录）：

```
会话 杨冬（wxid_bmr50soxlyen22）：613 条 ｜ md 含「转发的聊天记录」= True ｜ html 含 class=fw = True
> **转发的聊天记录（8 条）**
> lucky pig 2026-08-28 13:58:20：Miku: 查了你的key都只用了一点点
> Miku: 只看你的，本月一共268，挺少的
...
[引用] 你这个是走的你那边渠道 ← 地图鱼: [图片 694KB]     ← 被引内容本身是图片，已压成摘要
```

判据：`test_render_labels.py`（+10 项）与 `test_exportcore.py`（+1 组）全绿；
五个工具包 16 个 `test_*.py` 全绿。

**第三个 bug（切片 2 结束后跑全量扫描才浮出来，同属本次改动）**：
`test_automation.py` 的"全类型扫一遍，渲染结果里不许再出现 XML 痕迹"报了 **589 条里 2 条漏**
（`[引用] 你这也不是codex ← wxid_jnt7kck7di1622: <?xml version="1.0"?> …`）。
根因：**群里的**引用，被引原文自带「发送者: 」前缀；而 `_render` 早就把换行压成空格，
那个前缀长成 `: ` 而不是 `:\n` ⇒ `_nested_text` 判"这不是 XML"就原样放行。
修法：在 `_nested_text` 里**复用现成的 `_PREFIX_RE`** 剥一道再判（剥完还是 XML 才解析，
真是人话就原样留着）；`test_render_labels.py` ⑧ 钉住这个形态。
教训记一笔：这条**只在全量扫描里可见**，`test_render_labels.py` 的合成样本当时没覆盖"带前缀"——
合成样本要照**真身**抄，别照"看着顺眼"的写法抄。

已知天花板（记录，不修）：转发块里的**图片导不出来**（没有 `local_id`，落不到 `image_message()`）；
`datatype=17`（嵌套转发）用自带的 `<datadesc>` 多行预览，没有递归进它自己的 `<recordxml>`。

### 切片 2 ✅ 已完成（2026-10-14）：C 侧两件（C1 群内昵称 + C2 沉默客户分层）

纯读库、无新依赖。改动只在 `wechat-crm-mcp`：`contactscore.py`（`room_nicknames` /

真机判据（全绿）：

- **C2**：共 2515 人，`30 天内有互动 113` / `never 2348`；两个口径都出现

**顺带逮到一个真 bug + 一处口径澄清**（不是推出来的，是测试逐条对账逼出来的）：
1. **第一桶漏人**：`silent_days` 是 `round(x,1)`，刚说过话的人是 `0.0`，而第一桶下界是**开**的

   `_bucket_labels` 一份。测试的走查天数列里补上 `0.0` 与 `-0.3`——**原来正是因为没测 0 才漏网的**。
   （我的第一版探针没能复现它：探针算的是**未取整**的 sd，自然都是正数。判据要跟**实现同一条路径**。）
2. **口径分开报**（不是 bug，是别让人误会）：C2 把"私聊最后一条"（`last_msg_*`）与
   "TA 在任何会话最后发言"（`last_spoke_*`）**分开给**，因为两者的差本身就是信息
   （本机 2515 好友里只有 45 个有 1:1 会话，而 166 个发过言）。

**摊牌（写进 README/SKILL，别让接入方误会）**：`silence_ladder` 只**列清单与原始时间戳**，
不打分、不判意向；`never` 桶里那 2348 人正是"别的工具完全看不见"的那批。

**先量后定**（探针 `verify/wechat-mcp/probe_html_size.py`，只读、不写导出文件，按 base64 的
4/3 折算）：本机 42 个会话带图，**500 条带图的会话 = 原图 30 MB ⇒ base64 后 40 MB**，
而同样的会话只出文字是 **17 KB**——体积**全在图上**。按同比例 5000 条就是 400 MB 单文件。

于是按"先量"的结论落地（改动只在 `wechat-export-mcp`）：

- **`format=html` + `media` ⇒ 媒体内嵌成 `data:` URI**（md/json 仍旧落 `assets/`——md 里塞 base64 没人要）。
- **上限 `inline_max_mb`（默认 20，0 = 不限）**：超出的媒体**退回落盘**（一样不少），
  页首黄条 + 返回里 `media_report.inline_fallback` 都写明"这份不再自包含"——降级必须留痕。
- **跨天的 html 给日期目录 + 锚点**（一天的会话不给：那是噪音）。
- 顺手修：相对路径一律用 `/`（Windows 的 `assets\img.jpg` 写进 `src`/markdown 是坏路径，
  这也正是"换台机器全是红叉"的一半原因）。

真机取证（`test_exportcore.py` 里钉住；同一次运行里跑了三遍）：

| 会话 | 条数 | 内嵌 | 退回落盘 | 单文件 | 目录总量 | 页首提示 |
|---|---|---|---|---|---|---|
| 微信ClawBot | 497 | 21 张 | 0 | 11.6 MB | 11.6 MB | 无 |
| 严子云。、杨冬（默认 20 MB） | 511 | 47 张 | 14 张 | 28.0 MB | 37.5 MB | **有** |
| 严子云。、杨冬（`inline_max_mb=0`） | 511 | 61 张 | 0 | 40.6 MB | 40.6 MB | 无 |

**顺带逮到一个真 bug（本次改动才让它显形）**：`_export_media` 把**没解析过的** `talker` 喂给
`image_message` / `voice_file`，而 `tbl_of` 是拿字符串算 md5 的——**传会话显示名时表根本不存在**，
于是每张图都定位不到、导出文件里一张图没有，却仍然 `ok:true`（只有 `image_missing` 在涨）。
而"用显示名"正是工具说明里推荐的用法（`list_sessions` 返回的就是 name）。
修法：沿用 `build_records` 已解析出的 `data["talker"]`。
回归钉：`test_real_media_by_display_name()`（用显示名导一个带图的会话，断言 `image_exported >= 1`
且 html 里是 `data:image/`、没有 `assets/`）——**这条如果用 wxid 测就永远发现不了**。

**已知天花板（记录，不修）**：转发块里的图片仍出不来（见切片 1）；内嵌是原图，没做缩略图
（本机没有能用的缩略图落点，要缩得引图像库）。

### 切片 4 ✅ 已完成（2026-10-14）：B6 附件落盘 + B8 非文本补全

用户给的用途是「**分享聊天 / 分析解析记录 / 提取文字、图片、文件**」——按这条排序，B6+B8 比
A 侧（§8 原切片 4）更贴，于是先做这两件。

**先量**（探针 `verify/wechat-mcp/probe_appmsg_kinds.py` / `probe_type1.py`，只读全库）：

| 事实 | 实测值 |
|---|---|
| 全库 `appmsg` 子类型计数 | `{1: 305, 6: 157, 57: 120, 5: 118, 2000: 20, 62: 15, 87: 9, …}` |
| 文件消息可定位率 | 157 条 → 145 条（92%）；9 条 `missing`（未下载/已过期）、3 条大小不符 |
| 视频号（44/51/63）的 `<title>` | 「当前版本不支持展示该内容，请升级至最新版本。」+ 一条 `support.weixin.qq.com/...upgrade` 的升级链接 —— **是微信的升级话术，不是内容** |
| 转账（2000）金额 | 在 `<wcpayinfo><feedesc>`（`￥1000.00`）；`<des>` 的后半句同样是升级话术 |
| 「引用」的判据 | **不是 `type=57`**：`type=1` 带 `<refermsg>` 的也是引用（本机 2 条）。判据改成「有没有 `refermsg`」 |

**B8（`wechat_core.describe_nontext`）**：视频号改出 `_finder_text`（`<nickname>`/`<desc>`）；
转账出 `_pay_text`（`feedesc` 优先，`<des>` 兜底）；引用按 `refermsg` 判、不再按 57；
`_NAG_URL` 把升级链接滤掉。**`_pay_text` 必须只在 `<wcpayinfo` 存在（或 type∈2000/2002/2003）时兜底**——
第一版没加这个门，合并转发里的 `<des>时遇: [图片]</des>` 让整条渲染成 `[转账] 时遇: [图片]`（被 ⑥ 抓住）。

**B6（导出侧收附件）**：`media` 增 `files`（`all` = 图片+文件+语音）；
「消息 → 磁盘文件」这段读原语**上移到共享层 `wechat_core`**（`parse_file_msg` / `files_root` /
`build_index` / `match_file`），`filecore.py` 只留同名引用——**不留第二份实现**（这就是 §7-3 的答案）。
同名同大小视作同一份只收一次（`file_dup`），大小不符计入 `file_mismatch`，定位不到计入
`file_missing`（**不伪造空文件**）。附件**从不内嵌**（一个附件几十上百 MB，内嵌进 HTML 就打不开了）。
顺带把 `media_report` 拆出 `image_no_key`：图片密钥没抓过（在微信里点开任意一张图就有）与
图本地永久缺失（`image_missing`）**用户要做的事完全不同**，混在一起就分不清该去干什么。

真机取证（`文件传输助手`，375 条）：

| 调用 | 附件 | 图片 | 语音 | 备注 |
|---|---|---|---|---|
| `media=files`（md） | 18 收 / 2 去重 / 0 缺 | — | — | `chat.md` 里有 `](files/…)` 链接 |
| `media=all`（html） | 18 收 / 2 去重 | 12 内嵌 1.3 MB | 2 wav | 附件仍落 `files/`，页首有"要一起打包"提示 |

**顺手逮到的一次跨会话回归**：`core.image_message` 被（另一个会话）改成返回
`(msg, 失败原因)` 元组，而导出侧还按 dict 用 ⇒ `AttributeError: 'tuple' object has no attribute 'get'`，
**整条媒体流程炸掉**。这条正是"共享层改签名、调用点没跟"的典型，靠全量扫描才发现——
所以**共享层动过之后必须重跑全量 16 个测试文件**，单跑自己那几个永远是绿的。

### 切片 4b ✅ A2 已完成（2026-10-14）：占用分析 `disk_usage`

**先量**（探针 `verify/wechat-mcp/probe_disk_usage.py`，只读、1.7 s）：三条结论各自改了设计。

| 实测 | 对设计的影响 |
|---|---|
| 账号目录 **1503 MB**，其中 `msg/` 1322 MB（file 896 / video 270 / attach 157），而 `db_storage` 只有 **67 MB** | 「为什么这么大」只能在磁盘上答，读库那套（会话条数）答不了 ⇒ 工具建在磁盘事实层 |
| 磁盘文件**只有 74% 被消息引用到**（149 → 110） | 剩下 26% 记 `file_unattributed` **单独一档**。不单列，各会话加起来就对不上总量，用户会以为工具漏了 |
| **同一份文件会被多个会话引用**（91 独占 / 15 双主 / 4 三主）⇒「按会话求和」= **1039 MB > 磁盘 896 MB** | 独占 `own_*` 与共享 `shared_*` **分开报**。否则"删了这个会话能省 X"是假话——那正是 A1 说竞品"比大小去重会误判"的同一类错 |

落地：`filecore.disk_usage()`（一次 walk 出前 N 层小计 + 按会话/年月/扩展名聚合）+ 第三个工具
`disk_usage(session_limit=20)`。**视频/attach 只报小计、不做会话归属**——video 靠消息配对只有
9/48 能唯一定位（§3.4），attach 是 md5 目录名 + 加密 `.dat`。**配不出来就别编。**

真机取证（`test_filecore.py` 里钉住不变式）：账号 1503 MB / file 896 MB
= **独占 455 + 共享 281 + 无主 160**，22 个会话有文件。

**一次自己的 bug 也是设计缺口**：测试第一版拿 `sum(sessions[].own_bytes)` 验账，真机差 **9.6 KB**
——因为 `sessions[]` 被 `session_limit` 截断（本机 22 个会话，默认只回 20）。
于是在返回里**单独给三个总量**（`file_own_bytes` / `shared_bytes` / `file_unattributed`），
并在工具说明里写「要验账用这三个数，别拿截断后的榜单求和」——**能被截断的字段不能兼作对账基准**。

### 切片 4d ✅ 已完成（2026-10-14）：检索命中挂 `video_path`（B4 的替代落法）

**改了什么**：`wechat_core.search_messages` 返回前加一句 `attach_video(hits[:limit])`。
（`history` / `poll_new` 早就挂了，**唯独检索没挂**——而检索是用户"找那段视频"的唯一入口。）

**判据**：

- 单测 `test_watch.py::o3_search_hits_carry_video_path`（假库 + 假 hardlink，断言命中带路径）。
- 真机取证：`verify/wechat-mcp/probe_video_search.py` —— 搜「视频」命中 48 条，
  带 `video_path` 的 **0 条 → 8 条**。
- 近似配对的取舍量测：`verify/wechat-mcp/probe_video_approx.py`（结论见 §3.4，**不做**）。
- **五个 exe 全部重打包并部署**（2026-10-14 14:10）：改的是共享层 `wechat_core`，
  四件套的产物各自**内嵌**一份它——即使只有 local 会调 `search_messages`，也让五份产物
  与源码同版，免得下次发版对不上。部署后逐个起真 exe 手验（`initialize` + `tools/list`）：
  local pro 19 / file 3 / export 2 / crm 4 / recall 4。

**为什么不做近似配对**（用户原话"近似吧，主要用来搜索哇"）：实测下来"搜索"这个目的
**根本不需要配对**——48 条视频消息的会话/发送者/时间/时长本来就在库里，搜「视频」全都搜得到；
配对只决定"点开能不能播"。而近似配对连这一栏也加不动：磁盘只有 15 个正片，
24 小时窗口的唯一候选 7 条 < 精确的 8 条（§3.4 的表）。**上限在磁盘，不在算法。**

**顺带修正的口径**：搜索结果里没有 `video_path` **不等于**这段视频不存在——
消息在、时长在，就是本地没那份字节。在微信里点开一次就会下载，之后再搜就有了
（与图片 `no_key` 同构：缺的是**一次用户动作**，不是数据）。这条已写进 `_MEDIA_PRO` 引导词。

## 附：本计划**没有**建议做的事（明确记录，防止下次再议）

- ❌ 换用微信客户端自带的 FTS（覆盖率 73.4%，会静默漏结果，§3.2）
- ❌ 下载/救援已过期文件（微信官方已定调服务端也拿不回来）
- ❌ patch 客户端 / 注入内存来"防撤回"（有封号与稳定性代价，且违背零注入红线）
- ❌ docx / PDF 导出（竞品的付费墙功能，要引依赖）
- ❌ 朋友圈导出（不在本四件套的数据面）
- ❌ 好友↔标签映射（本地确实没有这张表，需逆向，仍在 backlog）
- ❌ 出"客户意向/情绪/关系质量"这类判断（§6.1 划死的线，判断归 LLM 与技能包；且调研证明这正是市场最被诟病的一环）
- ❌ **自动打标签 / 批量改备注**（写操作，落在微信点名的"批量操控"里；本地也没有映射表）
- ❌ **zip 一键打包**（调研中没有任何用户提出，属功能想象）
- ❌ **分析可视化**：词云 / 年度报告图 / 性格画像（竞品扎堆、多为个人玩具，偏离"只读取数"定位）
- ❌ **任何云端上传 / 分享链接 / 把聊天内容交给第三方 AI**（PIPL 红线，且摧毁唯一差异点）
- ❌ **区块链存证上链**（哈希 + 导出日志已够内部追溯，上链是另一门生意）
- ❌ **接入企业微信会话存档**（官方 400~1800 元/人/年且要自建解密，个人工具路径未证实）
- ❌ **对外宣称"能替代企业微信 SCRM"**（提高被投诉概率，§2.5B）
