## 0. 一句话与三条不变量

本机微信 MCP 是**一双以用户身份操作本机微信的手**：读走「只读解密 SQLCipher + 内存扫密钥」，写走「GUI 自动化（UIA 树定位 + 窗口消息投递）」，全程**不注入微信进程**。灵栖的「代聊」是这双手之上的一个定时回路：每 15 秒看一次新消息，按渠道策略决定「提醒我 / 起草 / 直接回」，回信仍从这双手发出去。

先立三条不变量，文档其余部分都是它们的推论：

1. **不可撤回**（对面是真人）⇒ 出站一律**失败闭合**：拿不到明确确认就报 `ok:false`，绝不把「可能发出去了」写成「已发出」（`pcwechat-outbound-provider.ts:20-29`）。
2. **不打扰用户**：发送不移光标、不劫持剪贴板；**窗口已经在屏上时不抢前台**。两个例外：窗口收在托盘/最小化时必须经「微信自己显示+激活」才能真正可用（会顶一次前台，见 §5.1），引用回复要前台（见 §5.6）。
3. **名单即白名单**：`channel_send` 只能发给渠道策略里配过的人——不是提示词里的君子协定，是真的发不出去（`pcwechat-outbound-provider.ts:11-19`）。

## 1. 分层全景

```
        ┌───────────────────────────────┐
        │  Weixin.exe（Qt，用户自己的） │
        └───────────────────────────────┘
            ▲ UIA 树 / WM_* 投递 / PrintWindow        ▼ 只读解密
            │                                            db_storage/*.db（SQLCipher + WAL）
┌──────────────────────────────────────────────────────────────────┐
│ wechat-mcp.exe（PyInstaller onefile，pro / lite 两档）            │
│   server.py        协议面：JSON-RPC、19 个工具、统一失败信封       │
│   wechat_core.py   读：定位 db_storage、扫密钥、解密、查询、水位   │
│   wechat_sender.py 写：窗口态机、UIA 定位、投递、读库确认          │
│   wechat_image.py  图片 V2 .dat 解密（pro）                        │
│   wechat_asr.py    SILK → PCM → Paraformer 转写（pro）             │
│   licensing.py     离线授权（pro 打包版才校验）                    │
└──────────────────────────────────────────────────────────────────┘
            ▲ tools/call（stdio JSON-RPC，MCP）
┌──────────────────────────────────────────────────────────────────┐
│ Electron 主进程                                                    │
│   plugins/builtin.ts      插件安装（从 GitHub Release 下 exe）     │
│   bundled-mcp-exe.ts      部署到 ~/.lumii/mcp/<name>/<name>.exe    │
│   mcp-manager.ts          连/装/调 MCP 子进程                      │
│   channel/providers/pcwechat-outbound-provider.ts  channel_send    │
│   agent-runtime/wechat-watch-tick.ts  15s 一拍的代聊回路           │
│   agent-runtime/bridge.ts             把回路接到真实 Agent 回合     │
└──────────────────────────────────────────────────────────────────┘
```

**脑手分离**是这套设计的核心：MCP 只是手（无状态、无策略、无记忆），一切「该不该回、回什么、给谁回」都在客户端。两边的契约面因此被压到最小：**19 个工具 + 一份统一的失败信封 + 一份 instructions**。任何一侧单独升级都不会破坏另一侧。

## 3. 协议面

- **传输**：stdio 上的 JSON-RPC 2.0（MCP）。`initialize` 协商版本、返回 `serverInfo`（含档位标签）与 **`instructions`**（`server.py:1056`）。
- **instructions 不是装饰**：它是提示词的唯一载体，客户端拿它拼进系统提示词的 `## MCP Servers` 段；改错地方（例如写进 `mcp-presets.ts`）不会有任何报错，只是 Agent 一个字都收不到。
- **工具清单**（19 个，`server.py:783`）：读——`list_sessions` / `read_history` / `search_messages` / `list_unread` / `poll_new` / `check_env` / `locate_db`；写——`send_text` / `send_file` / `send_batch` / `reply_to`；pro 专属——`read_image` / `transcribe_voice` / `wechat_digest` / `wechat_distill_state` / `wechat_distill_clear` / `wechat_profile_save` / `wechat_profile_get`（共 7 个，`PRO_ONLY_TOOLS:983`）。
- **每个工具都带 annotations**（`readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint`，`_annotate_tools:981`），客户端据此决定要不要用户确认。
- **统一失败信封**：所有失败都走 `_fail(error_code, message, **extra)`，形状固定为 `{ok:false, detail, error_code, stage, suggestion}`（`server.py:156`）。收敛的原因：曾经的 13 处「参数校验不过就提前返回」各写各的形状，Agent 拿到的形状随「错在哪一步」而变，一份提示词覆盖不了。**新增错误码要给 `stage` 与 `suggestion`**。
- **重试**：`_send_with_retry(max_retries=2)` 包住发送（`server.py:239`）。这也是客户端把 `timeoutMs` 调到 300s 的原因——单次 MCP 调用尾巴可能到 60s+。
- **可观测**：每次关键操作往 `%TEMP%/lumii-wechat-mcp/metrics.jsonl` 写一行 `{ts, op, ms, ok, tag, detail}`（`_metric:1925`）。诊断「现在哪个操作在慢/在失败」看它。
- **服务端没有工具级超时，靠两道串行化兜底**：stdio 主循环是**逐行读 stdin、处理完才读下一行**（`server.py:1193-1200`），所以一个长调用会挡住后面所有请求——客户端的 `timeoutMs` 才是唯一的超时；而真正会互相打架的只有 UI（同一台微信只容一个操作），由**跨进程文件锁** `_acquire_ui(timeout=90)` 管住（`wechat_sender.py:1972`，锁文件在 WORK 根下共享，拿不到就返回 `busy`）。两个 MCP 进程（客户端一个、别的会话一个）同时发消息时，看到的就是这条：一个在发、另一个等最多 90s。

### 3.1 双档位与授权

- 档位是**构建期注入**的：源码拷进临时目录后写一个 `edition.py`，`server.py:69` 读 `_licensing.effective_edition(_BUILT_EDITION)`。工作区不落这个文件，因此**跑源码 = pro**。
- lite 少 7 个工具（上面那批）与 ASR 重依赖，体积约 11.8MB vs pro 约 37.7MB。**两处都要拦**：`tools/list` 里不列，`handle_tools_call` 里也要挡（只从列表删，模型照样能按名字直接调）。
- **lite 还在返回处剥媒体路径**：`_strip_media`（`server.py:1010`）把 `image_path`/`voice_path` 摘掉，消息只剩 `[图片 17KB]` 这类摘要。**裁在 server 层、不动 `wechat_core`**——core 的职责是挂上解密后的路径，「给不给模型看」是档位策略，不该渗进读取层。
- **授权只对打包 exe 生效**（源码运行不校验）：载体是**环境变量 `WECHAT_MCP_LICENSE_KEY`**（形如 `WMK1.<载荷>.<RSA 签名>`），**不绑机器**——发行方一次签一批，用户无需提供任何信息。另有 `.state.json` 防时钟回拨。
- **旧的 `license.json` 文件式授权（含三项机器指纹校验）已整体移除**（2026-10-13）：留着不只多余，还有害——用户既配密钥又有旧文件时，**密钥写错会被旧文件悄悄兜住**。现在没配 = `missing`、配了但解不出来 = `bad_key`，两种提示不同。
- **随包/插件安装的 exe 免授权**：`bundled_exempt()` 认 `.lumii-bundled` 标记（`licensing.py:214`），由客户端安装时写下（`markLumiiDeployed`，`bundled-mcp-exe.ts:105`）。

## 4. 读：入站是怎么拿到的

### 4.1 定位与解密

1. **找 db_storage**：先读微信 ini / 注册表，找不到再扫固定盘（`wechat_core.py:108/132/189`），最终 `db_root:335`。`locate_db` 工具把这段过程与结论报给用户。
2. **拿密钥**：`wxkey4.py` **只读扫描微信进程内存里的 `Config.Cipher`**（`PROCESS_VM_READ | PROCESS_QUERY_INFORMATION`，不注入、不重启微信），验证方式是用候选 key 解 `page1` 的 `enc_key` 槽。
3. **解库**：微信 4.1+ 是 SQLCipher —— page=4096、reserve=80、HMAC-SHA512；内存里取到的就是最终 AES key，`mac_key = PBKDF2-HMAC-SHA512(encKey, salt^0x3a, 2, 32)`（`wxread4.py:31`）。**WAL 必须重放**，且只认「帧 salt == 头 salt」的帧——`-wal` 不截断复用、混着历史残留帧，认错 salt 会读到别人的旧页。
4. **镜像**：解密结果落到 `%TEMP%/lumii-wechat-mcp/mirror-<pid>/`（`_ShardMirror:532`），后续查询都打在镜像上，**绝不碰用户的原库**。镜像连接**不可缓存**：`refresh()` 会重写镜像，缓存住的连接会读到旧页。

### 4.2 新消息与水位的判据

- `poll(since_ts, per)`（`wechat_core.py:1323`）按 `create_time` 增量取，带上会话名与发送者。
- **`from_me` 是判据而不是提示**：`from_me = (sender == me)`。自聊（文件传输助手 / 本人 wxid）里**恒为真**——这正是 2026-10-09 把 `filehelper` 从黑名单里拿出来的原因（见 §6.3）。
- 消息类型的描述（`describe_nontext:901`）：图片/语音/文件/链接各有元数据；**语音的音频不在磁盘上**，在 `media_*.db` 的 `VoiceInfo.voice_data`（明文 SILK_V3），必须用 `local_id` 对（同一秒能有多条）。图片的 md5 指的是**原图**，本地落盘文件名在 `packed_info_data` 里，`download_status` 不是判据。

### 4.3 媒体可达性（现状）

| 类型 | 现在能不能拿到 | 怎么拿 |
| --- | --- | --- |
| 文本 | ✅ | 直接解 XML |
| 语音 | ✅ | `VoiceInfo` → SILK 落文件 → 客户端 `transcribeVoice`（pro 也可在 MCP 侧转写） |
| 图片 | ⚠️ 需 AES key | `V2 .dat` 的 XOR 尾段自解；AES 段要「用户看图的瞬间」在内存里的 key，拿到即缓存复用 |
| 视频 / 文件 | ✅ 明文 | `msg/video/`、`msg/file/`（视频与 XML 的 md5 映射尚未对上） |
| 表情 / 转账 / 系统消息 | ❌ 不解 | 只报类型 |

## 5. 写：一条消息是怎么发出去的

### 5.1 窗口态机（发送前的门）

`check_env`（`wechat_sender.py:969`）吐一份**环境快照**：`weixin_running / pids / hwnd / visible / minimized / onscreen / locked / rect / dpi / ratio / db_ok / can_send / reason / hint / deps`。发送前的门是 `preflight:1102` → `env_gate:1074`，`wake_window:1026` 负责把不可用态救回来：

| 态 | 判据 | 救法（`wake_window:1026`） |
| --- | --- | --- |
| 收进托盘 | `visible=False`，句柄还在 | **经微信自己的托盘图标 `InvokePattern` 拉起**（`_unfreeze_ui:943`） |
| 最小化 | `IsIconic=1` | 同上 |
| **被搬到桌面外** | `rect` 是 `-32000` 哨兵或整窗落在虚拟屏外 | `MoveWindow` 到 `60,40`（`_bring_onscreen:349`）。**绝不点托盘** |
| 锁屏 | `session_locked()` | 默认放行（`allow_locked`），发送链在锁屏下实测全通 |

**托盘/最小化为什么不是 `ShowWindow`**：`SW_SHOWNOACTIVATE` / `SW_RESTORE` 拉出来的窗口**只渲染、不收输入**——帧看着完全正常（左列、聊天区、表头都在），但投递点击与真实点击全无反应，切不了会话也投不进正文（2026-10-11 实测，两种态一样）；只有经微信自己的「显示 + 激活」才真正可用。所以 `ShowWindow(…, 4)` 现在只是托盘图标用不了时的**退路**（`wechat_sender.py:1067-1068`）。代价是这一步会顶前台——用户本来就没在用（收在托盘/最小化），可以接受。

**桌面外是最阴的一种**：`IsWindowVisible=1 / IsIconic=0 / showCmd=1 / rcNormalPosition 也是 -32000`——常规三条判据全绿，而**微信自己的托盘图标是按可见性 toggle 的**，方向正好反了，于是用户点托盘、点任务栏都叫不出来（2026-10-12 用户报障的现场）。
两条根因叠加：① `check_env` 曾只看 `visible/minimized`，桌面外被判「可用」；② `_restore_geometry:2096` 与 `Win.__exit__:1145` 会**照抄读到的 rect**，把哨兵坐标原样写回去 ⇒ 每代回一次钉得更死。
**现在的三道守卫**：`_offscreen:331`（判据）+ `_bring_onscreen`（搬回）+ 两个写入口拒绝还原桌面外窗口；`repair_env:2200`（面板「修复环境」）同时负责搬回与规范化尺寸。

### 5.2 目标会话定位（fail-closed 的核心）

按优先级：

1. **UIA 树**（首选，`read_uia:632` / `uia_find_session:725` / `uia_header_is:747`）：投递点击用树里**活的 `BoundingRectangle`**，目标确认用表头 `current_chat_name_label`。为什么弃用「截图帧」：`PrintWindow` 给的是窗口**最后一次绘制**的表面，窗口被盖住/最小化时 Qt 不重绘，那层表面冻在几分钟前——会话顺序、预览、坐标全是旧的（由此产生过 4 次 `target_unconfirmed`），而 UIA 树一直是新的。
2. **目标掉出可视区** ⇒ 投 `WM_MOUSEWHEEL` 滚动会话列表再点（`_scroll_find_session:1781`，每屏拿帧指纹自证，没变就放弃并滚回顶部）。**搜索切会话是最后手段且要前台**：搜索面板只在窗口「激活」时渲染，走了就得用真键鼠 + 剪贴板（`open_chat_via_search_posted:1744`，锁屏直接放弃、用完还原剪贴板/光标/前台）。投递路（`open_chat_post`）里那条搜索兜底**已经撤掉**——投递的搜索词微信只收下不渲染。
3. **确认不下来就一个字都不输入**：`target_unconfirmed` 是 fail-closed 兜底，所以补发**绝不会重复发**。
4. UIA 空树（微信 4.x 的既有状态，不是 bug）⇒ 退回帧 + OCR 判据（`_uia_tree_blank:701` 认它并记 `uia_blank` 指标）。

### 5.3 投递

- 文本用**窗口消息投递**（`post_text:505`，逐字符 `WM_CHAR`），不是 `SendInput`：不抢前台、不用真键盘钩子。
- **非 BMP 字符（emoji）投不进去**：整投会静默变成另一个私用区字符，拆代理对则整个丢掉。所以 `post_text` 主动跳过并记进 `_LAST_DROPPED`，`send_text` 如实写进 detail（「已发送（注意：N 个 emoji/生僻字符无法投递，已略去）」）——**宁可少发几个字并如实说，也绝不静默发错字**。
- **「读—清—回读」**：回车前读输入框（UIA `chat_input_field` 的 ValuePattern）→ 按实读长度退格 → 回读确认清空（`clear_input:568`）→ 投递正文 → 回读校验。判据是「框里的字都在正文里」= **子序列**（容忍投递丢字），**不容忍正文之外的残留**（`_residue:587`；探测残留真跟着附件发出去过）。读不到就退化为盲退格、且不拦——别把「读不到」变成「发不出去」。
- **跨进程互斥**：一次只允许一个 UI 操作（`_acquire_ui:1972`）。两个回合同时抢微信窗口会互相破坏。

### 5.4 确认

发送成功不是「投递没报错」，而是**读库确认**：`_wait_new_message:2409` / `_talker_latest_ts:2401` 等到那条消息真落库才算数。确认不到就按失败处理。

### 5.5 发送上下文与还原

`_send_locked_body:2113` 在目标不对时**按需**搬窗口（`_repair_geometry_for_send:2069` 规范化到 `1280×820`），`finally` 里 `_restore_geometry` 还原；`reply_to` 走 `Win` 上下文管理器（`__enter__` 记 rect，`__exit__` 还原）。**还原的守卫就是 §5.1 那条**：桌面外的 rect 不还原。

### 5.6 附件与引用回复

- **附件**（`send_attachment:2423`）：点工具栏「发送文件」（**按几何定位**，那个图标没有名字）→ 微信自己弹标准 `#32770` 对话框 → UIA 读控件句柄 → `WM_SETTEXT` 写路径 + `BM_CLICK` 点「打开」。这两个系统消息会跨进程编组，不用注入、不用碰剪贴板、不用移光标。文件名框 id 会一次命中好几个控件，**以回读为准**。
- **不按扩展名分流**：图片、视频、音频、文档走的是**同一条**投递路（都是「发送文件」），代码里没有任何扩展名分支——最终渲染成图片气泡还是文件卡片由微信自己决定。工具描述里一度写着「按扩展名自动区分：图片内联发送」，那是老路径（剪贴板粘贴）的残留文案，2026-10-12 已修（`server.py` 的 `send_file` 描述 + `instructions`、`wechat_sender.py` 的 `env_gate` docstring、`README.md`）；**模型的工具描述会直接决定它怎么向用户承诺能力**，这类过期描述比代码里的过期注释更贵。
- **引用回复**（`reply_text:2585`）：右键目标消息 → 引用 → 输入 → 发送。这条路历史上用过 `bring_to_front`（`SW_RESTORE` + 反复抢前台 + `AttachThreadInput` + 模拟 Alt），**是「微信 UI 卡死」的原始诱因**；现已改为 `SW_SHOWNOACTIVATE`，但这条路径仍是潜在风险点，卡死先看它。

## 6. 客户端侧：代聊回路

### 6.1 一拍做什么

`wechat-watch` 是**本地 cron 任务**（id 固定 `wechat-watch`，`every 15s`，`wechat-watch-tick.ts:56-58`），由 `ensureWechatWatchCronJobSeeded:1746` 播种/自愈：MCP 没配就自动暂停并落标记，MCP 回来再自动恢复（用户手停的不碰）。main 里只认 `taskText === '__wechat_watch__'` 这一条指令。

一拍的主流程 `runWechatWatch:1411`：

```
poll_new（或回放口注入） → selectNewMessages（水位 + 身份去重）
  → 逐 peer：档位（ignore/notify/draft/auto）× 冷却 × pendingByPeer 合并
  → 转写语音 / 识别图片（缺部件就只留元数据，绝不断链）
  → 拼提示词 → driveTurn（真实 Agent 回合）→ 落库 pcwechat:<talker>
  → Agent 用 channel_send 回信 → Provider → MCP send_text → 读库复核
  → detectSentTo 复核落库 → 打 AGENT_REPLY_MARKER
```

### 6.2 档位与「名单即白名单」

档位四档（`shared/channel-policy.ts:33`）：`ignore`（连提醒都不发）/ `notify`（只提醒，不叫模型）/ `draft`（叫醒模型起草，草稿落在那个 peer 的会话里等点头）/ `auto`（直接代回）。
真源是**渠道策略**（`~/.lumii/channel/channel-policies.json`，设置页 → 渠道 → 本机微信），名单外的 `defaultMode` 会被**收敛到非 agent 档**（`NON_AGENT_MODES:101`）——老配置里手写的 `draft/auto` 一律退回 `notify`，只有一道口子等于没有口子。Router 拿这份 peers 当**出站白名单**：名单外的人连 `channel_list` 里都不出现，`channel_send` 报 `PEER_NOT_FOUND`。

### 6.3 自聊会话（主人渠道）

用户给自己发（文件传输助手 / 本人 wxid）的会话里 `from_me` **恒为真**，但要当**入站**处理——它等价于飞书/企微里的 owner 渠道，用户在这里指挥助手。判据是 `isSelfChatPeer:139`（`filehelper` + 本人 wxid 列表，后者由 `locate_db/check_env` 拿、带缓存），配套 `withSelfPeers:153` 把它们自动补进名单，冷却单列 `SELF_PEER_COOLDOWN_S = 20s`（要盖过「一拍 15s + 发送延迟」，免得助手刚回的那条又被当成新消息）。

**区分「Agent 回的」与「用户自己发的」**靠零宽标记 `AGENT_REPLY_MARKER`（`​‌​`，`wechat-watch-tick.ts:235`）：出站前 `withAgentMarker` 打上、读回来 `hasAgentMarker` 认得出、进提示词前 `stripAgentMarker` 抹掉。**同一串字符在 Python 侧也有常量**（`wechat_core.AGENT_MARK:1142`）：`poll`/`msg_dict` 据此给每条消息打 `agent_sent`（`wechat_core.py:1161`，截断前先剥标记），客户端 `selectNewMessages:556` 直接跳过它。另有 `wasSelfSent:262`（用 `rememberSelfSends` 记下**读库实测**发出的原话）兜住「没有标记的老回复」。**别用 `from_me` 判「是不是我回的」**——它分不出代回与本人发言。

### 6.4 提示词的三段分工

| 段 | 住哪 | 变化频率 |
| --- | --- | --- |
| 约定与护栏（能做什么、不许做什么、发送只能走 `channel_send`） | 「灵栖代聊」Agent 的 systemPrompt（程序维护分区 `relayOwnedSection()`） | 极少变；**重生成 systemPrompt 会静默抹掉用户改动** |
| 本轮事实（谁、说了什么、转写/识别结果、画像、冷却是谁） | 每轮现拼（`buildAutoPrompt:710` / `buildDraftPrompt:669` / `buildOwnerPrompt:754`） | 每轮 |
| 用户手册（兜底口径） | `instructionsFile` | 用户自己改 |

**Agent 不在**（删了/禁用了）时回落成「把程序分区注入本轮提示词」——护栏绝不能因为少了一个 Agent 就静默消失（`WechatWatchDeps.getRelayAgent`）。画像注入上限 1500 字符（`WECHAT_PROFILE_MAX_CHARS:980`）。

### 6.5 出站与补发队列

`PcwechatChannelProvider.sendText:97` → `callMcpTool('send_text', {dry_run:false})` → **必须确认为 `dry_run === false`**（工具默认是演练，不确认就等于没发）。失败按两类处理（`UNDELIVERABLE_CODES`，`pcwechat-outbound-provider.ts:37`）：

| 错误码 | 含义 | 处理 |
| --- | --- | --- |
| `env_not_ready` | 微信没跑 / 收在托盘 / 切不过去 | **重试就能成功** ⇒ 进待补发队列 `wechat_watch_outbox` 等门开 |
| `target_unconfirmed` | 目标会话没确认下来，**一个字都没输入** | 同上；不排它的话那条回复就**静默没了** |
| 其余（`PEER_NOT_FOUND` 等） | 重试一万次也没用 | 不进队列，直接报错 |

⚠️ **慢失败比快失败更糟**：MCP 客户端超时（30s）**不是错误码**，归不出 `env_not_ready` ⇒ 不进队列 ⇒ 静默丢回复。所以预设给了 `timeoutMs: 300_000`（`src/shared/mcp-presets.ts`），服务端还叠了 ×2 重试。

**队列本身**（`wechat-watch-tick.ts:1177-1350`）：上限 20 条（超了丢最老）、TTL 30 分钟（过期**弹「已放弃」通知**，不静默丢）、重试节流 60s、只在**空闲拍**消费；消费前先 `read_history(limit=1)` 复核「末条是 `from_me` 且不早于入队时刻」，本人已经回过话了就直接作废（比时间不比文本，因为对面可能改了措辞）。工具侧回给模型的是 `{status:'queued', delivered:false, …}`——**刻意既不报 `ok:false`**（会推着 Agent 改内容/重发/转人工）**也不报 `ok:true`**。

### 6.6 落库与会话身份

代聊回合的会话 id 是 `pcwechat:<talker>`（`watchConversationIdFor:1035`）——**一个好友一条线**，历史按人聚合、点通知直达那个人（早先是所有人共用 `wechat:watch` 单例，用户会在一个没有对方的线程里看到所有人的代回记录）。入站渲染与落库**用同一个函数** `formatIncomingForHistory:968`，否则复盘时提示词与记录对不上。

## 7. 失败语义速查

| 现象 | 判据 | 去哪看 |
| --- | --- | --- |
| 回信没出去 | `ToolTelemetry ... success=false` + `MCP request timeout`（≈30s） | 客户端日志；这类**不进队列**，是真丢 |
| 回信排队等门开 | `wechat_watch_outbox` 非空；`error_code ∈ {env_not_ready, target_unconfirmed}` | 库表 + 日志 `flushWechatOutbox:1258` |
| 目标确认不下来 | `target_unconfirmed`，**没有一个字被输入** | `metrics.jsonl` 的 `uia_blank` / `_target_unconfirmed_detail:1878` |
| 界面「没变化」 | ⚠️ 窗口被盖住 / UI 卡死时 `PrintWindow` 给**冻结旧帧**，「没变化」**不构成证据** | `_ui_alive:871`（点别的会话行，前后两帧像素级比对） |
| 微信叫不出来 | `check_env.reason` 会直说是哪一态（托盘 / 最小化 / **被搬到桌面外**） | `check_env`；修复用 `repair_env` 或面板「修复环境」 |

## 8. 部署、版本与一致性

- **构建**：`node apps/windows/scripts/build-wechat-mcp.mjs [--edition pro|lite|both]`（默认两档）。产物 `dist/wechat-mcp.exe`（名字固定，客户端写死它）与 `dist/wechat-mcp-<version>.exe`（供人眼区分）。
- **版本号唯一来源**是 `server.py` 的 `SERVER_VERSION`（现 0.8.0），同时写进 exe 的 Windows 版本资源；TS 镜像在 `src/shared/mcp-presets.ts`（`WECHAT_MCP_VERSION`），由 `mcp-presets.test.ts` 对账。**不实读 exe 的 `--version`**：onefile 冷启动要 1–3 秒，不值当。
- **客户端怎么拿到 exe**：插件化（`plugins/builtin.ts:133`）——从 GitHub Release `v<App版本>` 下 `wechat-mcp.exe` 到 `~/.lumii/mcp/wechat-mcp/wechat-mcp.exe`（`getDeployedMcpExePath:42`），写 `.lumii-bundled` 免授权标记。**wechat-mcp 已不再走随包同步**——`deployBundledExecutables` 里有一行显式跳过（`mcp-manager.ts:105`：`if (preset.bundledExe === 'wechat-mcp') continue`，理由是不让 dev 启动时把仓库里的源同步回部署路径、与打包版行为不一致）；`syncMcpExecutable:121` 仍在，只服务别的内置 exe。所以「改了源码 → dev 重启」不会自动更新部署里的 exe：**必须重新构建 + 覆盖部署路径，再重启客户端**（被占用的 exe 要「改名让位」再覆盖，旧文件留 `.old-*` 等下次清理）。
- 打包链上的一个坑：`ownerOf()` 曾只按 `<档名>-` 判前缀，`wechat-mcp-lite.exe` 会掉进 pro 的前缀被判成 pro 的历史副本 —— **单打 pro 会顺手删掉 lite 的固定名产物**（2026-10-12 修，同处循环也要显式排除本档固定名）。

## 9. 已知限制（不做的事）

- **图片画面要 AES key**：只做「key 已在内存里（用户看过图）」的解密与缓存，**不扫内存找 key**、不注入微信。
- **不用搜索切会话**：会强迫微信到前台（见 §5.2 第 2 条）。
- **不做「滚动到任意历史」**：只滚会话列表，不滚聊天记录。
- **不提权**：只读 `PROCESS_VM_READ | PROCESS_QUERY_INFORMATION`，不要管理员，不注入。
- **MCP 侧不存策略**：名单、档位、冷却、画像归属全在客户端；换客户端即换脑。
- **`search_skipped` 是死分支**（待清理）：`_code_of`/`_stage_of`/`_get_fix_suggestion`（`server.py:136/201/223`）与测试 `test_watch.py:1907` 都还在，配套诊断 `search_skipped_restored` 在 `_record_diagnostics` 的调用点**只被置成 None**、从无写入方——因为投递路里的「搜索兜底」已撤（`open_chat_post:1853` 那段注释自陈「已撤」）。测试测的是纯映射函数，所以**测试全绿但功能是死的**，属典型「绿测试掩盖死代码」。
