## 〇、结论速览

### 客户端侧

1. **`Weixin.exe` 只是引导壳**（2.9MB，只导入 `KERNEL32.dll`），真正的应用是 `Weixin.dll`（201MB）导出的 `WeChatMain`。同一个 `{GetHandleVerifier, WeChatMain}` 导出模式在 `wxpublic.dll` / `wxutility.dll` / `wxocr.dll` 上重复出现 —— **"一个壳跑多个脸"是 4.x 的基本结构**。
2. **底座是自研运行时 `owl`（`owl::v9`）**：事件循环（`looper`）、协程（`coroutine`/`co_scope`/`co_job`）、`promise`/`deferred`/`co_channel`、事件总线（`grouped_eventbus`）、日志（`zlog::v9`）、内嵌 `fmt` 与 `moodycamel` 无锁队列。**3000+ 导出，无外部依赖**（只导 WS2_32/KERNEL32/ADVAPI32）。**4.x 的并发模型与 3.x 完全不同**，任何按 3.x 线程模型做的假设都会走偏。
3. **网络是双栈**：自研 `ilink`（`ilink2.dll` + `ilink_stream.dll` + `ilink_wrapper.dll`，基于 **mmtls/mars**，`zidl` IDL 生成对象接口）与 Chromium 系 `mmcronet`（Cronet，QUIC/HTTP2/WebSocket，BoringSSL）+ `shared_andromeda`（`HttpWithCronet` 封装层）。
4. **进程间通信用 Chromium Mojo**（`mmmojo_64.dll`，版本 `109.0.5414.76` → Chromium 109），不是自己写的 IPC。
5. **UI 是 Qt 5.15.14 + 自研控件库 `mmui`**（`Weixin.dll` 带 `.qtmetad`/`.qtmimed` 区段，窗口类 `Qt51514QWindowIcon`，UIA 里是 `mmui::*` 类名），渲染走 Skia + ANGLE。**"UIA 树稀疏"是架构性的，不是版本 bug** —— 这决定了 MCP 读界面这条路的天然上限。
6. **多媒体全套自研或内嵌**：语音 SILK（`VoipEngine.dll` 导出 `SKP_Silk_SDK_*`）、视频编解码 `VCodec2/VCodec3`（`libwxcodec.dll`）、播放器 `XPlayer`（Chromium + FFmpeg + D3D12/Vulkan/SwiftShader）、编辑器 `XEditor`（Skia + V8 + Node 原生插件）、直播 `liteav`。
7. **小程序/小游戏是独立的一套 Chromium**：`RadiumWMPF.bin`（432MB ZIP），主体是 **`flue.dll` 237MB**（XWeb 内核）+ `WeChatAppEx.exe` 宿主 + `AndrowsInstaller.exe`（Android 兼容层）。
8. **机器学习是自研推理引擎 `XNet`**：`XNet.dll` 导出 1000+ `xnet::`/`dnn::` 张量算子符号，模型是私有 `.xnet` 格式。**onnxruntime / ncnn / tensorflow 全部零命中**。**客户端自带 OCR**（`wxocr.dll` + `text_det/text_rec/paragraph_det` 等 8 个 `.xnet` 模型，中文 13562 字表）—— 但**它没有可调用的 C 接口**（见 §4.7），只能"走它的界面"用。
9. **有主动防篡改**：`wcprobe.dll`（7.6MB）段表是 **VMProtect（`.vmp0/.vmp1`）+ Microsoft Detours（`.detourc/.detourd`）**，导入 `WINTRUST/CRYPT32/WTSAPI32`，**无导出、无 PDB**；组件包各带 `file_component.xml`（**RSA 签名 + MD5 清单 + `ComponentVerification.dll`**）。这既是纪律也是技术边界（§5、§9.11）。
10. **数据层**：`db_storage` 下 21 个 `.db`，**20 个 SQLCipher 加密**，唯一明文的是 `all_users\login\<wxid>\key_info.db`。**其中 `message_fts.db` / `contact_fts.db` / `favorite_fts.db` 三个名字表明微信自己建了 FTS 索引** —— 这是"复用客户端已有能力"最直接的一条线索。

### MCP 侧（一句话）

现有两条腿（内存扫密钥 + SQLCipher 直读；UIA 定位 + 窗口消息零注入投递）在 4.x 上**路线正确、已被证明可行，且完全没有碰客户端的防篡改面**。按"稳定 / 可靠 / 简单 / 用客户端已有的"这四条看，改进集中在三类：

- **可直接换成"用客户端已有能力"的有 4 处**（对照表见 §9.0）：全文检索（客户端有 `*_fts.db`）、输入框写入（客户端暴露 UIA `ValuePattern`）、图片识文与语音转写（客户端自带「提取文字」「转文字」）、消息到达（客户端写 `xlog`）。
- **可靠性的两个具体抓手**：① 发送重试用**幂等判据**（读库看最近几分钟有没有同内容、同标记的消息）替掉"超时了到底发没发"的人工判断；② 接收侧给 `local_id` 高水位加一条**周期对账**兜底。
- **"简单"的入口只有一个**：先定 `chat_input_field` 的 UIA 可见性/可写性（§9.1 / E0）。它决定发送路径是能压成"一次 `SetValue`"，还是必须保留现在这套逐字投递 + 子序列容错的复杂度。

> **⚠️ 上面这套读完的结论，实测后大部分不成立（2026-10-14，详见 §9.12）**——留在这里是为了看清"推理与实际差多远"：
> - "用客户端已有的 4 处" ⇒ **两处不成立**：客户端 FTS 只有 **73.3% 覆盖**且虚表要**私有分词器**（查不了）；
>   客户端的图片文字索引在本机**全是 0 行**。剩下两处（UIA `ValuePattern`、`xlog`）**本机要么判不了、要么没验**。
> - "用幂等判据替掉人工判断" ⇒ **方向对了、病根找错了**：真凶是**落地校验判据本身**会假成功
>   （对方回话顶包），修判据即可，**幂等重试那套不用做**。
> - "先定 UIA 可写性" ⇒ 本机 **E0 判不了**（前台锁拒绝激活），且代码里**早就**按"可能不暴露"设计了。
> - **真正值钱的那条不在原报告里**：接收侧**满量截断会静默丢消息**（本机 71 张表 39 张满量）——

## 三、启动与进程架构

**实测链**：

```
Weixin.exe  (2.9MB, 只导入 KERNEL32.dll；导出 GetHandleVerifier)
   │  .rdata 内嵌模块名清单（加载顺序）：
   │  Weixin.dll / wxpublic.dll / mmcronet.dll / shared_andromeda.dll / ilink2.dll /
   │  ilink_stream.dll / ilink_wrapper.dll / mmmojo_64.dll / VoipEngine.dll / ConfSdk.dll /
   │  XNet.dll / roam_server.dll / roam_migration.dll / wcprobe.dll /
   │  libEGL.dll / libGLESv2.dll / crashpad_handler.exe
   │  以及符号名：WeChatMain / SetWeixinCallbackFunc
   └─ LoadLibrary + GetProcAddress → WeChatMain
        ↑
   Weixin.dll (201MB) 导出：WeChatMain / SetWeixinCallbackFunc / SetUseUserCA /
                            HostStartupExceptionReport / GetHandleVerifier
                            + 112 个 mmcronet:: 类
   wxpublic.dll  导出：{GetHandleVerifier, WeChatMain}      ← 同一个口
   wxutility.dll 导出：{GetHandleVerifier, WeChatMain}      ← 同一个口
   wxocr.dll     导出：{GetHandleVerifier, GetMergeOffsetInner, WeChatMain}
```

**推断**：`Weixin.exe` 是 Chromium 风格的通用加载器（`GetHandleVerifier` 是 Chromium 的沙箱/校验特征符号），**按参数决定加载哪个模块的 `WeChatMain`** —— 这解释了同目录下为什么有好几个导出同名入口的 DLL：宿主进程可以复用同一个壳去跑 OCR、跑工具、跑公开接口等不同"脸"。

**进程拓朴（实测自 `tasklist`）**：

```

WeChatAppEx.exe ×8   （小程序宿主，每个小程序一个）
wechat-*-mcp.exe ×6  （本项目的四件套 MCP，2 进程/个）
```

### 4.1 `owl` —— 自研基础运行时（最被低估的一块）

**实测**（`owl.dll`，1.5MB，x64，**3000+ 导出**，只导入 `WS2_32/KERNEL32/ADVAPI32`），符号里可见：

| 能力 | 证据符号（节选） |
|---|---|
| 事件循环 | `owl::v9::looper`、`owl::v9::task_type` |
| 协程 | `owl::v9::coroutine`、`co_scope`、`co_job_base`、`co_job_impl` |
| 异步原语 | `owl::v9::promise`、`promise_impl`、`deferred`、`co_channel` |
| 事件总线 | `owl::v9::grouped_eventbus`、`eventbus_node`、`subscriber_t`、`bind_strategy` |
| 内存/容器 | `owl::v9::allocator`、`Storage<>`、`MemoryBlock` |
| 日志 | `owl::v9::zlog`：`async_log_writer`、`log_appender`、`log_object`、`log_level`、`log_mode` |
| 内嵌三方 | `owl::fmt`（{fmt}）、`moodycamel::`（无锁 MPMC 队列） |

**含义**：4.x 有一套自己的跨平台协程运行时，`ilink`/`ilink_stream`/`Weixin.dll` 全都链接它（`ilink2.dll` 的导入表第一项就是 `owl.dll`）。

### 4.2 通讯栈：双栈并存

#### A) `ilink`（自研，长连接）

| 观测 | 值 |
|---|---|
| 字符串计数（`ilink2.dll`） | `ilink`=2278、`zidl`=1161、`mars::`=800、`mmtls`=225、`mtls`=228、`quic`=25、`protobuf`=42、`WebSocket`=4 |
| 导出总数 | **523**，其中 521 个是 `zidl` 模板符号（`zidl::CallerTemplate<...>`、`zidl_export::...`） |
| 少数 C 口导出 | `CreateIlinkNetwork`、`DeleteIlinkNetwork`、`GetIlinkContext`、`GetIlinkDeviceInterface`、`GetIlinkLogManager`、`GetIlinkXlogInterface`、`GetIlinkWifiInfoCallback`、`CreateTdiManager` |
| 依赖 | `owl.dll`、`WS2_32`、`CRYPT32`、`bcrypt`、`IPHLPAPI`、`WININET` |

- **`zidl`** 是腾讯自研的接口 IDL：会话按 `AppSession` / `AppDeviceSession` / `CloudSession` / `DeviceSession` 分四类，每类都有 `*Dispatcher` + `*Events` + `*NoPBEvents` 三件套（`NoPB` = 非 protobuf 变体）。
- `ilink_stream.dll` 是在其上的**流复用层**：`IlinkStreamChannel::CreateUpStream/CreateDownStream/CreateStream`、`SendStreamFragment`、`OnReceiveStreamFragment`、`ForegroundChanged`、`GetCurrentNetworkTypeAsync`（返回 `owl::v9::promise2`）。典型的大文件/媒体上传下载通道。
- `ilink_wrapper.dll` 是**唯一一个好用的 C 口**（8 个导出全是 C 风格）：`GetContextNoPB` / `CreateNetworkManagerNoPB` / `GetIlinkStreamContext` … 名字直说是"给非 protobuf 调用方准备的包装"。

#### B) `mmcronet` + `shared_andromeda`（Chromium 系）

| 观测 | 值 |
|---|---|
| `mmcronet.dll` | 导出 435 个，全 `Cronet_*`；字符串 `quic`=707、`websocket`=102、`http2`=22、`boringssl`=87、`chromium`；PDB 在 `E:\chromium\src\out\release\` |
| `shared_andromeda.dll` | 导出 185 个；C++ 类名 `HttpWithCronet`、`HttpCronetContextBuilder`、`CronetFileTaskRunnerWrapper`、`NetWorkEstimateCallback`、`AddForceQuicOn`、`AddHostMap` |
| `mmmojo_64.dll` | 版本资源 **`109.0.5414.76`** → Chromium **109**；导出 26 个 `MMMojo*`：`CreateMMMojoEnvironment`、`SendMMMojoWriteInfo`、`SetMMMojoWriteInfoMessagePipe`、`StartMMMojoEnvironment` |
| Weixin.dll 侧 | 导出 112 个 `mmcronet::` 类，说明主程序**直接嵌了 Cronet 的 C++ 门面** |

**含义**：微信 4.x 是**"两个网络世界"**：自研 ilink 走 mmtls（长连接、收发消息、信令），Cronet 走标准 TLS/QUIC（CDN、图片、文章、小程序）。这不是过渡状态，是长期分工。

### 4.7 推理：`XNet`（自研，非 onnxruntime/ncnn）

- `XNet.dll`（7.3MB，x64）**导出 1000+ 符号**，全是 C++ mangled 的 `xnet::` / `xnet::dnn::`：`CopyTensor<>`、`Device<>`、`DnnDeviceImpl<>`、`DnnOperatorVisitor<>`、`Storage<>`、`Bfloat16`/`Float16`、`CRC32Calculator`、`DnnCompilation`。
- 只导入 `KERNEL32/ADVAPI32/imagehlp` → **纯 CPU 推理**（无 CUDA/DirectML 依赖）。
- PDB 路径 `E:\data\landun\workspace\win-891\CompileXNetScript\XNet\` → 有**独立的模型编译工具链**。
- `WeChatOcr.bin` 里的模型（实测文件清单）：

```

- **`onnxruntime`/`ncnn`/`tensorflow`/`paddle`/`openvino` 在 `WeChatOcr.bin` 上零命中**（只有 `opencv`=174、`MNN`=73、`TNN`=38 的少量第三方标记）。

**对 MCP 的含义（一个否定结论 + 一个正向线索）**：

- ⛔ **不能"复用"这份 OCR 当库调**：实测 `wxocr.dll` 只有 3 个导出（`GetHandleVerifier`/`GetMergeOffsetInner`/`WeChatMain`），走的是"壳加载 `WeChatMain`"模式，**没有可调用的 C 接口**；`.xnet` 是私有格式，`XNet.dll` 的导出全是 C++ 模板，从 Python 侧用不了。**所以 `ocr4.ps1` 继续用 `Windows.Media.Ocr` 是当前唯一可行解，不是将就。**
- 💡 **但可以"走它的界面"用**：既然客户端自己有 OCR，那么**界面上就一定有一个入口**（右键图片 → 提取文字），而**走界面正是本项目既有的技术路线**（零注入 + UIA + 投递）。详见 §9.3。

### 4.8 迁移与备份

`roam_server.dll`（导出 88 个）+ `roam_migration.dll`（21 个）+ `libusb-1.0.dll`（197 个 `libusb_*`）+ `backup_drivers.bin`：

- 类名证据：`RoamServer`、`RoamSmcManager`、`MmAoaWrapper`（**AOA = Android Open Accessory**）、`GetBindQrCode`、`GetDeviceId`、`CDNDownload`、`GetBackupPackageList`、`DeleteBackupPackage`、`RoamMigrationManagerCoAgent`。
- `backup_drivers.bin` 解包后是 `backup_drivers/{x64,ARM64}/WeChatAOAFilter/{*.sys,*.inf,*.cat}` —— **内核态 USB 过滤驱动**。

**含义**：手机↔PC 的聊天记录迁移走 **USB（AOA）+ CDN** 双通道，且会动系统驱动。这条与 MCP 无关，但解释了 `libusb` 与 `backup_drivers.bin` 的存在，也说明**微信对"数据离开设备"有自己的既有通道**（如果哪天要做"全量导出"，这是客户端已有的功能，比我们手搓导出更合规）。

## 五、防篡改与安全（对 MCP 最有约束力的一节）

### 5.1 实测证据

| 层 | 证据 |
|---|---|
| **VMProtect 保护** | `wcprobe.dll` 段表含 `.vmp0`(3.2MB) / `.vmp1`(1.8MB)。全目录**只有它有** |
| **API Hook 框架** | 同文件段表含 `.detourc` / `.detourd` → **Microsoft Detours** |
| **完整性/会话感知** | 导入 `WINTRUST.dll`（验签）、`CRYPT32`、`WTSAPI32`（查会话/锁屏）、`IPHLPAPI` + `WS2_32`（联网上报） |
| **刻意隐藏** | `wcprobe.dll` **无导出表、无 PDB、字符串几乎零命中**（其余文件全都留着 PDB 路径） |
| **组件签名** | 每个 `.bin` 包内 `file_component.xml` = `checkvalue`(MD5) + `signature`(RSA) + `appClientId="UniWeChatWin"` + `sdkMin` + `runtimeAbis="x64"` |
| **组件校验器** | `RadiumWMPF.bin` 内含 `ComponentVerification.dll` |
| **崩溃上报** | `crashpad_handler.exe` + 命名管道 `\\.\pipe\crashpad_%lu_` + 环境变量 `XWECHAT_MM_CRASHPAD_PIPE` |

### 5.2 结论

> **微信 4.x 对"进程内被注入 / 被改"这件事是有主动防线的**：一个 VMProtect 加密、用 Detours 挂钩、能验签、能查会话、能联网上报的常驻模块（`wcprobe.dll`），加上**每个组件包的 RSA 签名 + MD5 清单 + 独立校验 DLL**。

**这就是本 MCP 坚持"零注入"的技术理由**（而不只是道德理由）：注入/hook 微信不但有账号风险，还直接撞在这套机制上。**§9.11 的"不要做的"清单大半由这一节支撑。**

## 七、本 MCP 现状基线

（来源：[微信MCP工作流程与技术原理](2026-10-12-微信MCP工作流程与技术原理.md) 与源码实测；此处只留与优化有关的部分。）

### 7.1 读层

```

  ↓

### 7.2 写层（零注入）

```

```

### 9.1 P0-A　发送路径能不能压成"一次 `SetValue`"？（简化与稳定的总入口）

**现象（实测自源码，两个观测互斥）**：

- `wechat_sender.py:568 clear_input()` 依赖 `read_uia(h, "clr")["input"]` 读到框里原文 —— `uia_read.ps1:121` 是通过 **`chat_input_field` 的 `ValuePattern`** 读的。**说明这个控件在 UIA 树里有 AutomationId、而且暴露 ValuePattern。**
- 但 `wechat_sender.py:770 uia_input_pt()` 的注释写：**"输入框不在 UIA 树里（实测整棵树只有一个 Edit，就是左上角那个搜索框）"**，所以它只能靠"发送"按钮的几何反推输入框位置。

**推断（已修正，2026-10-14）**：原文把这写成"两个观测互斥"，**是错的**。读代码可知这是**两套环境**，作者早就写明了：`wechat_sender.py:978` —— **"微信 4.x 可能整条生命周期都不向 UIA 暴露控件树"**，并配了 `read_uia()` 返回 `None` 的降级路、`_uia_tree_blank()` 判定、以及 `check_env()` 里的 `uia_tree: "blank" | "unknown"` 字段。也就是说：**有的机器暴露、有的机器不暴露，MCP 早就按"可能不暴露"设计了**。本机实测正是**不暴露**那一类（E0 见下），一直跑的是几何反推 + 盲退格的降级路。

**做法（先测，别先改）**：写一个**只读**探针，在 4 种窗口态（前台 / 后台 / 最小化 / 锁屏）各枚举一次 UIA 树，记录：
1. `chat_input_field` 在不在树里；
2. 它的 `ValuePattern.Current.IsReadOnly` 是什么；
3. `TrySetValue()` 是否成功（用**空串或无害短串**试，试完立刻恢复原值）。

**若 `IsReadOnly == false` 且 `SetValue` 生效** → 发送路径可以变成：

```
SetValue(正文) → 回读校验 → PostMessageW(VK_RETURN) → 读库确认
```

一次性解决四个问题：**天然支持 emoji/非 BMP**（不再有"整投变成私用区字符"）、**不再丢字**（不需要 `_residue()` 子序列容错）、**清空变成一次 `SetValue("")`**（不再逐字退格 ≤2000 次）、**代码短一大截**。

**若只读** → 现状保持，但把"逐字符"的复杂度**收进一处**并写明为什么不能简化（避免后人再试一遍）。

**风险**：低。只读 UIA + 一次 `SetValue`（可逆）。**注意**：`SetValue` 会覆盖用户草稿 —— 与既有路径口径一致（现有清空路径本来就会删草稿），但要在文档里写清。
**验收**：探针产出四种窗口态的可见性/可写性矩阵；`send_text` 在现代码路径下不再出现 `_residue` 容错分支。

> **E0 实测结论（2026-10-14，两轮）**
>
> **第一轮（作废）**：`probe_composer_uia.ps1` 报"三种窗口态下都只有 2 个后代"。
> **这一轮无效**：它用 `SetWindowPos(HWND_TOP, SWP_NOACTIVATE)` 当"还原"，而那**根本不会还原
> 最小化窗口**（只改 z 序），所以"三种态"其实**都是最小化的同一态**；想进"真前台"那格又被
> Windows 前台锁拒绝。**结论被撤回。**
>
> **第二轮（受控，`probe_uia_gate.ps1`，纯 ASCII）**：先 `IsIconic` 记录真实态，再用
> `ShowWindow(SW_SHOWNOACTIVATE)` **真还原**（`rect` 从 `-32000,-32000 160x28` 变
> `775,208 1280x820`，且 `GetForegroundWindow` 前后不变 ⇒ **确认没抢前台**），测完把窗口
> **还原成最小化**（用户窗口归用户）。结果：
>
> | 格 | 后代数 | 内容 |
> |---|---|---|
> | 还原前 | 2 | `Pane 'Weixin'` + `Pane 'MMUIRenderSubWindowHW'` |
> | 还原后 | 2 | 同上 |
> | 显式 `WM_GETOBJECT(OBJID_CLIENT)` 握手后 | 2 | 同上；**握手返回值 = 0** |
> | `chat_input_field` | — | **找不到** |
>
> 所以**不是"窗口没还原所以没树"，是这版客户端根本不提供 IAccessible**：握手返回 0，剩下的
> `MMUIRenderSubWindowHW` 正是 mmui 那层**自绘渲染子窗口**（与 §4.4 的架构判断互证）。
> 网络检索到的旁证也指向同一件事：微信 4.0/4.1 起是**按需暴露**（默认只给极小 Content View），
> 且 pywechat 明文记载**讲述人方案已失效**、微信对"从未用过无障碍模式的账号"直接不给树——
> 而社区给出的"恢复"手段里，热补丁 `Weixin.dll` 一个字节属于**改客户端，本方案的红线**。
>
> **不改代码**：`SetValue` 这条路要有"暴露"的机器才谈得上，而代码里已经有 `_uia_tree_blank` 分支
> 处理"不暴露"。**P0-A 对本机收益为零**，等遇到暴露的机器再复用这份探针。
> **剩下没试过的**：`TreeWalker.RawViewWalker` 遍历、以及 UIA 自己的 `UiaRootObjectId(-25)`
> 握手（探针发的是 MSAA 的 `OBJID_CLIENT(-4)`）。但 `WM_GETOBJECT` 返回 0 意味着 provider 层
> 根本没起来，walker 无树可走——所以这条路**判为不通**，除非换一台"暴露"的机器。

### 9.2 P0-B　发送重试的**幂等判据**（把"超时了到底发没发"变成可判）

**现状（文档原文）**：

> `send_not_confirmed` —— 回车已按、库里没看到。可能真发出去了。先 `read_history` 看，或问用户。
> **超时 ≠ 失败**：真发生超时时消息很可能已经发出去了……这时**不要重发**。

也就是说：**最危险的失败模式（可能已发出）现在靠"人判断"**。这既不稳也不简单。

**做法（完全在读者侧，用客户端已有的数据）**：发送前先写一个**幂等指纹**，重试前用它查库：

- 现有的 `AGENT_MARK`（零宽字符 `\u200b\u200c\u200b`，`wechat_core.py:1177`）已经是天然标记 —— **但它贴在"我们自己发出去的"消息上，是事后判据**。
- 补一步：重试**之前**，读该 talker 最近 N 分钟（比如 10 分钟）的消息，若存在一条**带 `AGENT_MARK` 且正文与待发内容相同**的消息 → **判定"已发出"，直接销账**，不再重试。
- 再补一步：拿一个**本次发送的短随机 nonce** 一起写进正文尾部（或作为 mark 的一部分），则"这一条"与"上一次同内容的合法发送"可区分开。

**收益**：`send_not_confirmed` / 超时这两条路**从"问用户"变成"自己判"**；重试队列可以安全地自动补发，不会再出现"重发就是给对方发第二遍"的恐惧。

**风险**：低（纯读 + 纯本地标记）。
**验收**：构造"发送成功但读库确认超时"的场景，重试判据给出"已发出"而不是"再发一次"。

> **已实施（2026-10-14），但真凶不是"重试"，是**判据本身**。**
> 顺着这条去读代码，发现根因在**落地校验**（`_wait_new_message`）而不在重试策略：它原先只问
> **"有没有比基线更新的消息"**，于是有**假成功**——发送窗口里对方恰好回一句，就判「已发送」，
> 而我们那条可能压根没出去。**消息静默丢失比报错危险得多**，而这恰恰是这道闸门存在的唯一理由
> （防"看着发出去了、其实发到别处"）。
> 改成认**我们自己发的那条**：① `agent_sent`（正文末尾的零宽标记，所有文本出口统一打）是
> "这串字是 AI 代发的"唯一指纹，对方伪造不来（实测本机 200 条样例里 36 条带它）；② 标记被
> 客户端吞掉时退回 `from_me` + 正文一致（`msg_dict` 截到 400 字 ⇒ 比前 400）；③ 附件没有正文
> 可打标记，只用 `from_me`；连 `from_me` 都解析不出来时退回原时间戳判据（**不因判据升级把发送
> 能力降级**）。判不了就继续等（fail-closed），宁可报 `send_not_confirmed` 让人去 `read_history`。
> **结论**：**"幂等重试"那套（nonce / 重试前对账）不用做了**——误报才是病根，修掉它之后
> `send_not_confirmed` 就是一个可信信号（"确实没看到我们那条"），而**不自动重试仍是对的**
> （可能真发出去了、只是落库慢）。回归锁：`test_send_confirm.py`（12 例，含"对方回话不算我们
> 发成功"这条核心）；已接进 CI。

### 9.3 P0-C　图片识文 / 语音转写：**能用客户端的就用客户端的**

**依据**：客户端自带 OCR（`wxocr.dll` + `text_rec_zh13562_fp16_v2.xnet` 等 8 个模型，含**段落检测**与 **13562 字中文表**）+ 自带语音转文字（`VoipEngine` 侧）。且 **4.x 界面上有对应入口**（右键图片「提取文字」、右键语音「转文字」）—— **推断**，需实验 E8/E9 确认菜单项文案。

**为什么这条路对**：

1. **本项目既有技术路线就是"读界面 + 投递"**，走客户端入口不需要任何新机制。
2. **绕开 MCP 目前最贵的两步**：图片的 AES key 扫描（**~50s**，且只在"用户看过图之后"才有效）；语音要自备 78MB 模型 + `pilk` + sherpa-onnx 依赖链。
3. **识别质量由客户端负责** —— 它训练的就是微信里的图（截图、表情包、文档照片）和微信的语音编码。

**做法**：
- 给 `read_image` 加一条**降级路**：AES key 未就绪 / 图片解不开时，不再硬等 50s，而是**投递右键 → 点「提取文字」→ 读弹层文本**，返回文本并标注 `"via": "client_ocr"`。
- 给 `transcribe_voice` 加一条**降级路**：本地模型未装 / 转写失败时，走客户端「转文字」，**并把联网这件事如实告诉用户**（客户端转文字要联网，本地方案不需要 —— 这是显式的隐私取舍，必须让用户选）。
- **同时**把 50s 的 AES key 扫描**移出请求路径**：`read_image` 在 key 缺失时**立即返回可用的缩略图**（`_t.dat` 是 XOR-only 的 JPEG，不需要 AES key），后台任务再去补原图。

**风险**：中。UI 路径依赖菜单文案与弹层；客户端 OCR 需要联网（要如实告知）。
**验收**：无 AES key 时 `read_image` P50 < 200ms（返回缩略图）；「提取文字」路径在真实图片上返回非空文本。

> **E8 部分否掉（2026-10-14）：客户端**没有**在这台机器上索引图片文字。**
> 解密后的 `ImgFtsAux*V0` / `ImgFtsV0` / `ImgRangeV0` 三张表**全是 0 行** ⇒ 客户端自己的图片
> OCR 结果并没有落到可读的索引里。**"读客户端已有的图片文字索引"这条路不存在**；
> 想用客户端的 OCR 只能走"投递右键 → 点「提取文字」→ 读弹层"那条 UI 路（未经实测）。

> **上面第三小点的"无 key 时返回缩略图"也否掉（2026-10-14）：缩略图同样需要 AES key。**
> 那半句的前提是"`_t.dat` 是 XOR-only 的 JPEG"，实测**不成立**：抽样本机 400 个 `_t.dat`，
> `aes_size` **全部 > 64**、`aes_size==0` 的 0 个 ⇒ 缩略图也带 AES 段（`decrypt` 在
> `aes_size<=0` 时直接返回 None，纯 XOR 那支一个都走不到）。
> 复现：`verify/wechat-mcp/probe_thumb_needs_key.py`（只读文件头）。
> ⇒ **没抓过图片密钥时，一张图都拿不到**（连缩略图也不行），key 的抓取入口成了硬前置 ——
> 见 §9.12 的 ⑫-3：这个入口原先**根本不存在**，现已补上 `wechat-mcp.exe --image-key`。

### 9.4 P0-D　检索改走客户端自己的 FTS，别再做全量 Python 扫描

**现状**：`wechat_core.search_messages()`（`wechat_core.py:1608`）对每个会话取 `scan=3000` 行，再对每行跑 `_render()` 做 Python 侧解码匹配。

**依据**：`message_fts.db` / `contact_fts.db` / `favorite_fts.db` 存在（§6.3）。

**做法（两步，先验证后替换）**：
1. 跑 E1，解密 `message_fts.db` 读 `sqlite_master`。
2. 若可用 → 直接 `MATCH` 查询，结果集与现在对齐；
   若不可用（比如只是给微信界面用的粗索引）→ **用同一份明文镜像自建 FTS5**，`tokenize='trigram'`（CJK 必须 trigram，`unicode61` 会按单字切；见 `docs/reference/sqlite-fts5-fulltext-search.md`），用现有 `local_id` 高水位做增量写入。

**风险**：低。自建索引等价于多一个 `%TEMP%` 下的明文缓存，与现有镜像同生命周期。
**验收**：同一批 keyword 的结果集与旧实现一致（对拍）；P50 从秒级降到 <100ms。
**注意**：本机 SQLite 3.53.3 忽略 `bm25(k1,b)` 参数（见记忆 `bm25-params-ignored-on-this-sqlite`），排序要靠查询侧裁剪。

> **E1 + E6 实测结论（2026-10-14）：整条否掉，**两条路都不划算**。**
>
> **① 直接查客户端的 FTS —— 不行。** 两个独立的拦路虎：
> - **虚表查不了**：`message_fts_v4_*` 用微信私有的 `MMFtsTokenizer`，外部 Python 的 SQLite
>   报 `no such tokenizer: MMFtsTokenizer`；配套的 `_idx` 里存的是私有编码 BLOB。**没有可用的接口。**
> - **覆盖不全**：`message_fts_v4_*_content` 有明文正文 + `(session_id, message_local_id,
>   create_time)` 元数据，但对账下来**只覆盖 3608/4923 = 73.3%** 的消息。**直接换过去会静默漏
>   掉四分之一**——那正是本项目最忌讳的失败形态。
>
> **② 自建 FTS —— 收益不够。** E6 把 `search_messages` 拆开量了：
> | 项 | 实测 |
> |---|---|
> | `search_messages` 全库 | **363ms**（其中 `_rows_full` 读行 93% / `_render` 逐条解码 7%） |
> | 假想"渲染后文本 + 纯 LIKE"全表扫 | ~20ms |
> ⇒ 上限只有 **363ms → 20ms**，而代价是**多一份明文缓存 + 增量写入 + 与镜像同生命周期的失效管理**。
> 按"这件事真的有痛到需要吗"这一关，**不划算**：363ms 对一个 Agent 回合来说根本不是瓶颈。
> **收手**。真要做，先量用户的库大到什么程度再说。

### 9.6 P1-A　把 `reply_to` 从"前台 + OCR + SendInput"里救出来

**现状**：引用回复是唯一需要微信窗口可见且在前台的路径，也是文档里"微信 UI 卡死"的历史诱因。卡点是"聊天区没有逐条消息的 UIA 元素，按消息定位只能靠实时帧 OCR"。

**依据**：UI 是 Qt + `mmui` 自绘（§4.4），UIA 稀疏是**架构性的**。但 `mmui` 确实在别的区域暴露了 AutomationId（`mmui::SearchContentCellView`）—— **自绘不等于零 UIA**。

**做法**（两步，都可独立否掉）：
1. **枚举度实验（E3）**：对主窗口做一次**完整** UIA 后代枚举（含 `-All` 的 NativeWindowHandle），统计 `chat_message_list` 下到底有没有元素、有多少、有没有 `Name`/`Value`/`LegacyIAccessible`。若**有** → `reply_to` 改成 UIA 定位 + `PostMessage` 点击，**彻底去掉前台与 SendInput**。
2. **菜单窗口实验**：微信右键菜单是**独立弹窗**（文档已记：常超出主窗口矩形）。向主窗口投 `WM_CONTEXTMENU`，用 `EnumWindows` 找新出现的顶级窗口，读它的 UIA 树找「引用」。若是 UIA 元素 → 同样可以不出前台就点。

**风险**：中（要真机试，但只读 UIA / 只投消息，不注入）。
**验收**：`reply_to` 在**微信最小化且非前台**时成功，且不产生前台抖动。
**若两条都失败**：维持现状，但把 `reply_to` 明确标成"需要前台"的降级路径，并在文档里写死原因（避免后人再试一遍）。

> **E3 已跑（2026-10-14）：不可判，而且和 E0 是**同一个根因**。**
> 本机这个微信进程**根本不向 UIA 暴露控件树**：枚举了它**全部 8 个顶级窗口 + 主窗口的 2 个子窗口**
> （`probe_e3_uia_scope.ps1`），除了主窗口那两个 Win32 Pane（`Weixin` / `MMUIRenderSubWindowHW`）
> 之外**全是 0 个后代**，MSAA 桥（`AccessibleObjectFromWindow`）也拿不到 `IAccessible`。
> 所以"`chat_message_list` 下有没有逐条消息"这个问题**在本机问不出来** —— 不是"没试"，是**没有树可问**。
>
> 这三条是**同一个事实**的不同侧面：E0（composer 不在树里）、E3（消息列表不在树里）、
> 以及 `wechat_sender._uia_tree_blank` 的注释（"2026-10-09 19:44 微信重启后整棵树只剩两个
> Win32 Pane，连读多次、设读屏标志、挂 UIA 事件监听都唤不醒"）。
> 社区记录的触发条件是**微信启动前**就在跑读屏器 ⇒ **要么重启一次微信再试，要么放弃**。
> 重启用户的微信不在本项目的授权范围内，所以 E3 就此**封存**：等哪天真的要动 `reply_to`，
> 先让用户重启微信、再跑 `probe_e3_uia_scope.ps1` 看一眼——**判据是那一天有没有 `CTL` 行**。

### 9.7 P1-B　`send_batch` 改成"一次切会话发多条"

文档 §3.1 已列。同 talker 连续多条时，现在每条都独立走一遍"校验→切会话→清框→投递→确认"。**切会话是 36s 那个最坏值的主要来源。** 一次切、多条发、逐条确认，把 N 条的 `36s + (N−1)×7s` 变成 `36s + (N−1)×7s` → 实际上等于把 N 次 36s 降成 1 次 36s。

### 9.9 P1-D　接收侧的可靠性：版本门 + 高水位对账

**现状**：`VERIFIED_VERSION_PREFIXES = ("4.1.15",)`；`wxkey4` 的快路径偏移（`node+0x28 → +0x88 → {+0x8,+0x10}`）是**硬绑定 4.1.15 布局**的，靠"无偏移兜底"兜；`poll_new` 用 `local_id` 高水位取增量。

3. 把 `wxkey4` 的无偏移兜底路径**在第二个微信版本上真验一次**（现在注释自己承认没验过）。

**验收**：升级到任意新版本后，首次工具调用会明确带 `version_unverified`；人为制造"表重建"场景后周期对账能补回消息。

> **版本门**落在 `handle_tools_call` 里**唯一**那一处（`core.version_warning()` → 结果的

### 9.10 P2-A　用 `xlog` 换掉/增强轮询，以及更便宜的延迟改进

**依据**：`%APPDATA%\Tencent\xwechat\log\mm_YYYYMMDD.xlog` 每天 40–55MB；`radium\ilink_*.xlog` 是长连接日志；`radium\net-export\` 是 Chromium net-export 格式。

**想法**：如果消息到达在 `mm_*.xlog` 里有稳定事件行，那么"尾随日志"可以把入站延迟从一个轮询周期降到一条日志的 flush 延迟。

**风险 / 前提**：
- `xlog` 是 Tencent 私有格式（有公开解码工具），需先跑 E5 确认**是否有消息级事件**；
- 日志体积大（每天 50MB），要做偏移量跟踪而不是全读；
- 发布版日志可能**只在 debug 级别才写消息**。

**更便宜的中间改进（先做这个）**：现在 15s 一拍。实测**全量解密 30ms、WAL 增量 2ms**，所以一拍的真实成本主要是几次 `stat`（镜像只在主库/`-wal` 变化时刷新）。**先量（E6）**：在 `devcli watch` 上打点，看一拍的实际耗时分布与 CPU；若一拍 < 20ms，把 tick 降到 1–3s，入站延迟 P50 就能从 ~7.5s（15s 周期均值）降到 <1.5s —— **这是本题里性价比最高的延迟改进**。

> **E6 实测结论（2026-10-14）：这一段**被自己的数据否掉了**。**
> - 一拍实测 **29–33ms**（不是 <20ms），且**没变差**——修复满量截断后仍是这个数。
> - 更关键的是：**这个节拍不是成本逼出来的**，是**产品决策**。`wechat-watch-tick.ts:28` 原文：
>   "节拍 15 秒：读取成本可忽略，而「当场感」值得（用户在等对方回话时，15 秒才出现是
>   '它盯着呢'，几分钟才出现是'它刚才在忙别的'）。"同文件 :16 还算过：
>   "15 秒一拍 ≈ 每秒 0.2% 的时间在干活。"
> ⇒ **降到 1–3s 买到的是 0.2% → 1% 的 CPU，代价是改掉一个刻意为之的产品行为。不值。收手。**

### 9.12 实施记录（2026-10-14）——做了什么、量到了什么

> 本节是**实测记录**，不是建议。上面各节里与本记录冲突的结论，以本节为准（已在各节就地标注）。

#### ① 接收侧：满量截断会**静默丢消息**（本轮最值钱的一条，报告原文没有）

**发现**：`poll()` 的水位 `next_since_ts` 是**全局单条 ts**（所有返回消息里最大的那个），
而 `per` 是**每会话**上限。旧实现每会话取的是**最新** `per` 条 ⇒ 某会话在这段时间来了
30 条时，返回的是第 11–30 条、水位直接推到第 30 条，**第 1–10 条再也不会被取到**
（`create_time > 水位` 永远为假），**而且没有任何迹象**。群里刷屏就是这个量级。

**实测规模**：`per=20` 时本机 **71 张表里 39 张满量**——不是罕见分支。

**修法**：满量的会话**整批放大重取一次**（`per * _POLL_BURST` = 500，同一批的超集：同 `since`、
同升序、只是 limit 更大 ⇒ 只多不少、**绝不重复**），一拍把它读全、水位照旧推；放大到上限
仍满才放弃，并置 `truncated` 如实上报。取的是**最早**的那批，所以万一真放弃，丢的也是最新的、
不是中间的（`_rows_full_conn` 由降序改为升序——它**只有 `poll` 一个调用方**，改序是安全的）。

**验证**（真机，选一个 60 条历史的群，水位退到 40 条之前，故意用 `per=5` 逼出满量）：

| | 修复前 | 修复后 |
|---|---|---|
| 走完 40 条得到 | 5 条，**漏 35 条** | **39/39，无漏**（2 拍） |

回归锁：`test_watch.py` B 层新增 `b5_burst_not_lost`（夹具驱动，用 `per=3` + 12 条消息，
旧实现在这条用例上必挂）。

**代价（如实记）**：`since_ts=0`（要全量历史）时逐表放大 ⇒ **2.5s → 6.8s**。**产品路径不会走它**
（盯梢首拍用"现在"，水位只有 `>0` 才落库），所以没为此加复杂度。稳态一拍仍是 **29–33ms**，
"隔一天"（水位 −86400）**180ms**，都没变差。

#### ② 发送侧：落地校验从"有新消息"改成"认我们自己发的那条"

见 §9.2 的标注。根因是**假成功**（对方回话顶包），不是"重试不安全"。`test_send_confirm.py` 12 例。

#### ③ 性能：`unread()` 149× 

`unread()` 原先对每个未读会话各调一次 `history(u, 1)` 再渲染 ⇒ 本机 **128 个未读会话 / 1784ms**，
**比全库检索一次还慢 5 倍**。而这一整块信息客户端早就算好、躺在 `SessionTable` 同一行里
（`summary` 就是会话列表上显示的那句）。改成一次 SQL 读 ⇒ **12ms**。预览覆盖率 127/128。

#### ④ 简化：删掉 `search_skipped` 死链（见 §9.5 的标注）

#### ⑤ 可靠：版本门跟着每个结果走（见 §9.9 的标注）

#### ⑥ 各热路径的实测成本（本机，供后来人做取舍）

#### ⑦ 发送路径：**硬的不是 sleep，是"每次白 spawn 一个 PowerShell"**（2026-10-14 追加）

**方法**：先量再改。`time.sleep` 字面量加起来只有 ~5.5s，而实测一句要 7–15s，差额必须先定位。

**量出来的三处浪费**（同一份 `send_text` 快路径，本机 UIA 树为空）：

1. **`read_uia` 每次 1183ms，而空树下它必然返回 `None`**——一次发送读 3 次
   （目标确认 / 清空回读 / 正文回读），**3.0s 纯废**。修法：空树判据**按窗口**记
   （`_UIA_BLANK_HWNDS`），命中就**不 spawn**（实测 1183ms → **0.0ms**）。
   ⚠️ **必须按窗口、不能按进程**：`send_attachment` 读的是微信弹出的文件对话框
   （`#32770`），那是原生 Win32 窗口、控件树好得很——进程级短路会把附件路径一起掐死
   （这一点被 `test_watch.py` 的 `d4b` 用例逮住，其夹具原本两个窗口共用 `hwnd=1`，
   已改成不同句柄并补上"别的窗口照样要读"的断言）。
2. **`_wait_new_message` 首轮无条件硬等 2.5s**，而落库通常在 1s 内。改成
   **首轮立刻读 + `_POLL_BACKOFF` 退避**（0 / 0.25 / 0.4 / 0.7 / 1.1 / 1.6 / 2.5 循环）。
   读库实测 14.5ms/次，密着打毫无压力。送后那次 `time.sleep(1.0)` 同理降为 0.35s
   （只留微信"自激活"0.1–0.3s 的窗口，前台归还才不会赶在它前面）。
3. **`post_text` 每字 `sleep(0.05)`**：200 字就是 **10s**，而 PostMessage 只是入队、不阻塞。

#### ⑧ ⚠️ 过程中**自己引入并抓到**的静默丢字（记下来，因为它差点溜过去）

`read_uia` 短路之后，**每句的首字被静默吃掉**，而 `ok` 照样是 `True`、`detail` 是「已发送」。

- **根因**：`clear_input` 投递 200 次退格（400 条入队消息）之后，输入框要一拍才吃得住第一个
  `WM_CHAR`。原先那一拍**不是显式写的**——是 `clear_input` 里那次 `read_uia` 每次都 spawn
  PowerShell 磨掉 ~1.0s，**顺手当了刹车**。短路把它抽走，刹车就没了。
- **为什么没人发现**：`post_text` 只看 PostMessage 返回值（恒真）；`_wait_new_message` 认的是
  `agent_sent` 指纹（**指纹在、正文少一个字照样算成功**）。整条链没有任何一道会报错。
  只有**读库回读正文逐字比对**看得见。
- **修法**：显式常量 `_COMPOSER_SETTLE = 0.4`，两个 `clear_input` 调用点都加，并在
  `post_text` 的 docstring 里点名这个前提。实测阈值在 0～0.15s 之间（0 稳定丢字，
  0.15/0.25/0.6 均正常），取 0.4 留余量。
- **固化判据**：新增 `verify/wechat-mcp/probe_send_roundtrip.py`——真发 + **读库逐字对账** +
  计时，不一致时打印首个不同字符的位置（首字丢失 vs 中间丢字是两种不同故障）。
  默认只打文件传输助手，打真人要显式加 `--allow-real-talker`。
  验证：200 字 × 4 句、154 字 × 3 句、94 字 × 3 句，**零丢字**。

**没有做的（明确记下来，免得后人再来一遍）**：§9.4 换 FTS（两条路都不划算，见 §9.4 标注）、
§9.3 读客户端图片文字索引（本机 0 行，见 §9.3 标注）、§9.1 `SetValue`（本机判不了，见 §9.1 标注）、
§9.10 降 tick（见下）。**2026-10-14 追加两条否掉的**：§9.7「`send_batch` 一次切会话发多条」——
它的收益只对**交错目标**（A,B,A）成立，而文档里的用法是群发（每个目标各一条），那时收益为 **0**；
更要紧的是同一目标的两条之间**不能**省掉目标确认（用户可能就在这两秒里点了别的会话，省掉即发错人），
省掉的那点时间买不到；§9.6「把 `reply_to` 从"前台+OCR"里解放出来」——本机**没有 UIA 树**（见 §9.1），
重建它没有立足点，而另一条路（粘贴）本来就要前台，故**卡住**，不是没做。

#### ⑨ 切会话路径：白跑的不是"切换"，是**切换前那次注定同答案的复核**（2026-10-14 追加）

这是所有优化里最贵的一条路——MCP 文档写着「目标会话不在当前打开的那个时最长 36 秒」。
用 `send_text` 自己的 `_progress` 回调量它（`dry_run` 打文件传输助手，**真发零条**）：

```
0.00s  正在检查微信环境
0.04s  正在确认目标会话
4.64s  窗口尺寸漂移，正在把微信窗口规范化     ← 疑点
7.29s  目标不在当前会话，正在切换
总计  12.58s  ok=True  dry-run：已验证目标会话，未输入未发送
```

**① 白跑的是那次"修窗口 + 复核"，实测 2.65s（0.80s 修 + 2.04s 重读）**，而且它给出的答案
**必然和第一次一样**。逻辑上：目标没确认上的时候，先「规范化窗口尺寸」再复核一遍的意义只有两种——
帧**压根没读到**（可能是旧帧没重绘，`ShowWindow` 加那一拍有机会让它重画出来），或尺寸**真漂移了**
（帧 OCR 的布局常量按 1280×820 标定，坐标会错位）。而最常见的那种是**第三种**：帧读得好好的、
表头明明白白写着别的会话——目标就是没开着，修完再读必然是同一个答案，紧接着就是切会话，
**切完那次核对才是真判据**。

**② 更要紧的是：那 0.80s 的"修复"会搬动用户的窗口。** `_repair_geometry_for_send` 的判据是
「位置**或**尺寸」偏离 `(60,40,1280,820)`，而渲染的布局用的是**窗口相对**坐标——窗口摆哪儿
都不影响读数。这与 `preflight` 用的 `_size_canonical`（**只看尺寸**）自相矛盾。本机实测：
窗口在 `(775,208,1280,820)`、尺寸合规，照样花掉 0.80s 并返回原 rect ⇒ 每次这种循环都是
**一次可见的窗口跳动**，纯粹为了满足一个没有依据的位置判据。

**③ 顺带修掉一个对称性 bug**：`send_attachment` 的目标确认原先硬写
`ok = uia_header_is(d, name) if d else False`——在本机这种**空 UIA 树**上，目标**永远确认不上**
⇒ **每次发附件都白切一次会话**，而且会把搜索兜底那条「抢剪贴板 + 真鼠标 + 抢前台」的路一起
带起来。文本路径的同一处早已判为 bug 并改成帧判据，**附件路径漏改了**。现已对称。

修法：新增 `_needs_geometry_repair(uia, frame_lines, h)`，两个调用点共用——
UIA 读到表头就不修（那是**精确文本**，说了不是就不是）；帧读到且**尺寸合规**就不修（位置偏移不算）；
只有「帧空」或「尺寸真漂移」才修。判据固化为 `test_watch.py::d8_geometry_repair_gate`（四个分支全钉）。

**量到的收益**：非当前会话的发送省 **2.84s**，外加**不再有一次可见的窗口跳动**。
⚠️ **没有做的**：完整的"切会话"端到端**没有重跑**——本机当时目标就是当前打开的会话，
不切会话就造不出「非当前目标」的现场，切了就会翻动用户正在看的窗口。所以 36s 那个上界
**至今未重新测量**，这里只记"省掉了 2.84s 的确定白跑"，不外推。

**顺带否掉一个猜想**：`verify_target` 一度被读成花了 1.45s（纯 Python，且在两条路径上都跑），
像是下一个目标。实测 **40ms**（`_usable_anchors` 16ms + 命中判定；单锚点 `anchor_lcs` ~18ms，
且只在 `anchor_exact` 落空时才跑）。那个 1.45s 是探针里的错记，**不动它**。

#### ⑩ 正文里的换行被**静默吞掉**——`ok=True`、内容却变了（2026-10-14 追加）

**现象**：`send_text("第一段。\n第二段。")` 返回 `ok=True`、`detail="已发送"`，而落库的正文是
`第一段。第二段。`——**换行没了，两段连成一串**。整条链没有任何一道会报错。

**实测三轮**（都是发给自己，文件传输助手）：`\n`(0x0A)、`\r\n`、单独 `\r`(0x0D) **全被吞**，
且**都没有误触发发送**（每条都只落一条消息——最坏的那条路「一条多段消息被拆成好几条发出去」
不存在）。对照：同批次的 `\t` 反倒**留得住**（落库有真制表符）⇒ 不是"所有控制字符都被过滤"。

**为什么修不出去——四条路都试过或推掉了**（记下来，免得后人再来一遍）：

| 路 | 为什么不成立 |
|---|---|
| 找输入框的 hwnd 直接 `EM_REPLACESEL`/`WM_SETTEXT` | **微信 4.x 是 Qt 应用**（主窗口类名 `Qt51514QWindowIcon`），输入框**不是独立子窗口**：`EnumChildWindows` 只有 2 个（`MMUIRenderSubWindowHW` + 一个 1×1 的 Qt 窗口）。**没有一个 hwnd 可以写** |
| 投 `WM_CHAR` 0x0D（CR） | 也吞。Windows 编辑控件的通用约定是"认 CR 不认 LF"，**这条在 Qt 上不成立** |
| Shift+Enter / Ctrl+V | 都要读 `GetKeyState`（**真实键盘消息队列**）——PostMessage 造不出来 |
| 粘贴（`reply_to` 就是这么发的） | 要**抢用户的剪贴板 + 前台**。为一个边缘情形把主发送路径变回前台依赖，不划算 |

**修法**：`post_text` 是唯一的收口处，在那里把 `\r\n|\r|\n` 压成**一个空格**并计数
（`folded_newlines()`）；`_send_locked_body` 在 detail 里如实交代
「N 处换行微信输入框收不下，已压成空格（要分段请分多次发送）」；`send_text`/`send_batch`
的工具描述里写明这条契约（模型调用时读到的就是它）。

**为什么压成空格**：`line one\nline two` 压成 `line oneline two` 是**破坏**，空格至少读得通；
中文段落在全角标点后多一个空格，可读性损失最小。**不选"拒绝发送"**——LLM 输出常带尾随换行，
为此把热路径变成失败会显得工具很脆。

**验证**：真机落库正文与期望**逐字一致**，detail 报了「2 处换行」。离线固化为
`test_watch.py::d9_newline_folded`（抓 `PostMessageW` 的 wParam，不需要真窗口，CRLF 只算一处）。

**顺带记一条不对称（未改，属既有行为）**：`reply_text` 走的是**剪贴板粘贴**、**不经过 `post_text`**，
所以它既不受这条限制、也不受 emoji 跳过的影响；但它同样**不在 detail 里报**丢了什么。

#### ⑪ 接收侧：水位是**秒级**的，同一秒里晚到的那批整批关在门外（2026-10-14 追加）

**这是 `①`（满量截断）的**时间版**——同一个根因：水位越过了还没送达的消息。**

`next_since_ts` 取"本拍见过的最大 ts"，而 `create_time` **只到秒**。轮询只要**落在某个活跃秒的
中间**，水位就已经是那一秒；同一秒后面到达的消息用 `create_time > 水位` **永远取不到**，且毫无迹象。
群聊一个爆发秒里几十条正是这个形态。文档里那句"**别传墙上时钟的 now，同秒会漏**"只堵了一半：
`next_since_ts` **自己就可能是当前这一秒的 ts**，于是"照文档说的做"照样漏。

**取证三层**（都不是推理）：

| 层 | 做了什么 | 结果 |
|---|---|---|
| 真机历史量化 | `probe_watermark_loss.py`：只读解密镜像，按两套语义对推（每次 poll 扫一批，见下） | 旧语义真丢 **195 条 / 5067 = 3.85%**（上界：每插入一次一拍）；轮询越稀越少——每 5 次一拍 **51** 条、每 20 次 **7** 条、每 50 次 **0** 条。新语义 **0 条、0 重复** |
| 直接 SQL | 拿同秒行最多的那张真表，`cut` 设在第二个同秒行之前 | `Msg_1710f7ff1c36` 有一秒里 **9 条**：纯 `>` 返回 **0**，补集返回 **8** |
| 离线回归锁 | `test_watch.py::b6`（真 `poll` + 真 SQLite）：同秒两批、中间夹一次 poll；旧实现必挂 | 通过。**固定 5 轮不提前 break**，让"重复投递"也能被抓到 |

丢的那批全落在"**差 0s**"这一档；≤1天/>1天 那两档两套语义**完全一样**——那是**历史回填**
（ts 落后水位几分钟到几天，`_rows_full_conn` 刻意不送，因为把 5 天前的消息当"新消息"送上去
会让代聊去回一条古早消息）。所以补集只动"同一秒"这一类，别的一律不碰。

**修法**：`_rows_full_conn(..., min_lids=…)` 多认一个 **`create_time = 水位 且 local_id > 上次扫描时的
最大 local_id`**；分界线直接取 `poll` 里 memo 已有的那条逐分片 `max(local_id)`（它本来就是"这张表
变没变"的探针，白捡）。**为什么这条补集既不重复也不遗漏**：`local_id` 是
`INTEGER PRIMARY KEY AUTOINCREMENT`（逐分片单调递增），分界线恰好把集合切成两半——
**扫描前就存在的（必然已送达）**与**之后插入的（必然是新的）**。复用快路径不必带它：
复用要求 `ids` 没变 = 扫描之后**一次插入都没有**，也就没有边界行要补。

**明确的取舍**：拿不到分界线时（本进程**第一次**扫这张表）退回纯 `>`——
**宁可漏掉这一秒的尾巴，也不冒重复投递的险**。重复会让代聊把同一条消息回两遍，比漏更难查；
这与本模块别处（`send_not_confirmed` 绝不重发）同一套价值排序。

⚠️ **一个必须记住的坑**：`_query_rows` 的 `except Exception: continue`（为"缺列就退化"而设）
会把**SQL 写错**也一起吞掉 ⇒ 轮询静默变聋。所以新加的 `OR` 子句特意在**真库**上验过一整条路
（冷 `poll(0)` 4961 条 → 暖 `poll` 正常返回边界行、再来一次不重复），不是只跑夹具。

⚠️ **建模方式本身会造出结果**：这个探针第一版按"每插入一行就判定一次"写，`--every 20` 报出
**53 条假丢失**——真实 `poll` 是**一次扫描**对当时已有的一批施加**同一条**规则（用扫描**前**的水位、
扫完才推），逐行判定会把"水位在这一批里自己涨了"算成漏判。改成按批建模后曲线才单调。
**先怀疑模型，再怀疑被测对象。**

#### ⑫ 接收侧媒体：三处"给不出正确结果"，外加一个**装完就没有的入口**（2026-10-14 追加）

这一轮换到 `attach_image` / `attach_voice`（把媒体挂到消息上那两条路）。先回答原先的疑问
**「会不会错配」：不会**——两条路的键都取自**该行自己**的列，不存在跨行按时间找：
图片用本行 `content` 里的 `md5` + 本行 `packed_info_data` 里的本地文件名，语音用本行的
`local_id`（`voice_file` 的 docstring 已记着为什么不能用 `create_time`：同一秒两条语音
lid 41 是 3.4 秒、lid 42 是 34.8 秒，按时间取会**转写出另一个人说的另一段话**）。
**但顺着这条线量出四个真问题**：

**⑫-1 语音等待是"逐条 6s"，一批会累乘拖穿一拍。**
`_VOICE_FRESH_S=180` / `_VOICE_WAIT_S=6.0` 是为"SILK 异步下载、刚到的语音要等一拍"设的，
但额度是**每一条**给的，而 `attach_voice` 逐条调用它。实测（只读，全库合并流）真机
**任一 180s 窗口内最多 6 条语音** ⇒ 一趟 `poll_new` 最坏 **36s**，而盯梢一拍是 **15s**
（`WECHAT_WATCH_INTERVAL_MS`），正好被拖穿。代码旁边那句注释写的是"封顶 6s 不会把节拍拖垮"
——**意图是对的，实现不是**。
**不是丢消息**（这点要写清楚）：水位在 attach **之前**就已提交，而复用是按调用方给的 `since_ts`
过滤的，所以调用方超时后用同一游标重试会**拿回同一批**——是**延迟几十秒**，不是丢。
**修法**：`voice_file(..., deadline=)` 改成收**绝对截止时刻**，`attach_voice` **一批共用一个额度**
（把它们**同时**在下载这件事用上：等第一条就把整批都等到了）；老语音仍只看一眼（`deadline=0`）。
上限从 N×6s 变成 6s。

**⑫-2 `read_image` 取不到图时，四种原因压成一句错话，而最该说的那条不在里面。**
`image_message` 把「找不到这条 / 不是图片 / **图片 AES key 还没抓** / 原图与中图都没落到本地」
全压成一个 `None`，调用方只能报「不是图片 / 图没落到本地 / 原始图与中图都缺」——
而真正常见的那个（**key 没抓**）症状与"图没落本地"**一模一样**，用户会去查根本不存在的文件缺失。
**修法**：`image_message` → `(m, why)`，四种原因各给各的话（含"下一步做什么"），并锁在
`test_watch.py::m7`（顺带断言四句话两两不同，防以后又被合并）。

**⑫-3 `read_image` 的前置**在装好的 exe 上**没有任何入口**。
图片是加密落盘的，key **不在消息里、也不在配置文件里**，只能从微信进程内存只读扫出来。
而：MCP 工具表里没有抓 key 的工具；exe 的 argv 里没有（对照 pro 的语音模型有
`--download-asr-model`）；宿主 App 里**没有这个界面**（全仓 grep 无 image-key UI）；
`wechat_core` 那句注释写的「设置页的按钮 / devcli」里，**按钮是假的**，devcli 只在源码树里。
⇒ **新装的 pro exe 永远读不出图**，而且报错把锅推给"文件缺失"（见 ⑫-2）。
（本机 key 早已缓存，所以**本机**能用——这正是它没被发现的原因。）
**没有"退一步"的路**：§9.3 设想的"没 key 就返回缩略图"已实测否掉——抽样本机 400 个 `_t.dat`，
`aes_size` **全部 > 64**，缩略图同样要 key（`verify/wechat-mcp/probe_thumb_needs_key.py`）。
**修法**：加 `wechat-mcp.exe --image-key`（`--refresh` 重抓），与 `--download-asr-model` 同形；
`check_env`（pro）多报一栏 `image_key.cached`；README/PUBLISHING/pro-SKILL 各补一行。
`test_watch.py::m6` 钉住"没扫到 ⇒ 非零码 + 教先点开一张图"与 `--refresh` 的透传。

**⑫-4 陈旧的图片 key 会**静默给出坏图**，而且缓存会把这个错误**固化**。
`attach_image` 走的是 `cached_aes_key()`——**不过 `_verify_key`**。账号换过 / key 陈旧时，
AES-ECB 解出来是**随机字节**；随机字节既不是 WXGF 也不是 PNG，旧代码于是把它当原图写成
`.jpg` 返回。这正是 `_verify_key` 注释里说的「**安静地给出错误的图，比报错糟得多**」。
更要命的是缓存命中发生在解密**之前**：那段窗口里写坏的图，在换回好 key 之后**还会被永远命中**
——修好的代码一样吐坏图（**不自愈就是个死结**）。
**修法**：写入前用现成的 `looks_like_image()` 拦掉不像图的；缓存命中时也验 4 字节头
（`_head_ok`），不像图就**就地删掉**重解。`test_watch.py::n1`（新 N 层）锁两条：
坏缓存既不能返回、也要被清掉；好缓存照旧走快路（不重新解密）。

**顺带记下"没做"的一条**：lite 档不做媒体——`_strip_media` 会在返回前把 `image_path`/`voice_path`
**剥掉**，而 `read_image`/`transcribe_voice` 本身也是 pro 独占 ⇒ lite 为每条新图**解密并落盘**、
为每条到货语音**等满 6s**，全是为了随后被删掉的字段。不做的理由：`_strip_media` 的 docstring
明确写过「**在 server 层裁、不动 wechat_core**——core 的职责是把路径挂上，"给不给模型看"是档位
策略，不该渗进读取层」，加 `media=` 开关正是那句话拒绝的事；而且 ⑫-1 修完之后 lite 的剩余成本是
"每批 ≤6s、且只在真有到货语音时"，量级不大。**要做就得先把刀口落在 server 层**（例如 lite 的
`_strip_media` 之外再给 core 一个"我不会消费媒体"的显式入参），那就等于改分层约定，不该顺手做。

**这一轮的取证卫生**：`test_watch.py` 97 通过 / 0 失败（新增 b7、m6、m7、n1 四例，都是**合同级**

#### ⑬ 视频路径落地 + 检索命中可寻址（E2 的实现面）

#### ⑭ `read_history` 翻页也会**静默丢同秒消息**（和 ① 同一类，这次在**读取侧**）

**发现**：页是按**条数**切的（`limit`），而游标是**秒**（`cursor` = 本页最老一条的 `ts`），下一页用
`create_time < cursor`。一秒里挤了 5 条、页只装得下 3 条时，**同秒更早的那 2 条**既 `> 本页`
又 `< 下一页` —— **两边都够不着，永久取不到**。修 `poll` 时用的 `local_id` 补集只补了轮询那条路，
读取/翻页这条**没跟着改**。（`wechat-export-mcp` 不受影响：它一次性取全量、不翻页。）

**实测规模**（`probe_history_cursor_gap.py`，真库 72 张表、`limit=10`= 默认值，逐表**模拟翻页**
再与全量对账）：**17 张表丢，共 76/4973 条（1.53%）**，最坏一张 **19/87（22%）**。
前面提的"导出/统计看着少了几条"就是这个。

**修法**：`_pad_page` —— 页切在秒中间时，把**那一秒的整秒**补齐（`create_time = bts` 精确取，
用已有的 `local_id` 去重），`cursor` **仍是单个 int**，调用方（含 Agent、`devcli`）**一个字都不用改**。
代价：页可能比 `limit` 略多几条（本机最挤的一秒 17 条）。
**同一秒条数无上限** ⇒ 没给补齐设上限：设了就等于在更大的突发下重新引入这个 bug。

**前后对照**（同一份真数据、同一套翻页算法）：**76 → 0**。
代价实测：**2.56 → 2.99 ms/条**（+17%，含媒体挂载；多的是那一趟"取整秒"的查询）。
回归锁：`test_watch.py` P 层 `p1`（假库按 `_rows_full` 的真语义过滤，确定性复现：
旧码上此例必挂——实测报 `缺 [7, 8]`）。

**这一轮的取证卫生**：`test_watch.py` **100 通过 / 0 失败**。
真机端到端：拿真实会话翻两页，**两页零重叠**且第 2 页最老秒 < 第 1 页最老秒（无缝）。
`py_compile` 通过。

#### ⑮ `search_messages`：时间范围被扫描窗口吃掉 + 截断不报

顺着 ⑭ 复查"还有哪些地方拿秒/条数当窗口"，`search_messages` 里两条：

1. **时间范围是"事后过滤"**：先取**最新 `scan`(3000) 条**，再在内存里筛 `since`/`until`。
   查一个**老的时间段**时，扫描窗口早被更新的消息占满 ⇒ **恒返回 0 条，而且不报错**
   ——"这段确实没有"和"根本没扫到"长得一模一样。（本机没超过 3000 条的会话，所以这是
   **机制可证、现场不可复现**的一处；夹具上旧码 0 命中 vs 新码 3 命中。）
2. **撞上 `scan` 上限不报**：`scanned_per_talker` 在场，但没人会从它推出"还有更老的没扫"。

**修法**：把 `since`/`until` **下推进 SQL**（`_rows_full` 本来就支持，且语义一致：
`create_time > since` / `< until`，与原来的内存过滤逐字等价）⇒ 窗口落在**时间段内**；
再多取一条来判断是否截断，结果里加 **`truncated`** 如实上报。检索的**总**结果数不变。

回归锁：`test_watch.py` P 层 `p2`（夹具上旧码 0 命中、新码 3）、`p3`（撞上限必须报 `true`，
没撞必须报 `false`）。

#### ⑯ `wechat_digest`：写着"统计永远是全量的"，实际每个会话只扫最新 500 条

同一个复查扫出来的第三条，而且是**当下就在错**的一条：

**现状**：`limit` 默认 **500**（每个会话最多扫多少条），而返回里写着
`stats_scope: "all"`，schema/提示词里三处写着"**统计（`self`/`contacts`/`top_words`/`style`）
永远是全量的**"。超过 500 条的会话给出的 `self.total` / `hour_hist` / `contacts` / `style`
**全是切片**——而画像卡是**整体覆盖**写的，切片会被当成事实落盘，再喂回去让代聊照着演。

**实测（本机，就是现在）**：默认全量 `self.total=4822`、被截断 0 个会话；
旧的默认 500 给 **4697**（少 **125 条 / 2.6%**）并静默截断 **2 个会话**

**修法**：`limit` 默认改 **0 = 全量**（多取一条只为*知道*被截断），并在结果里加
**`capped_talkers`**：显式设了 `limit` 就点名是哪几个会话被截断——**别拿它当真值**。
`stats_scope` 语义不动（它本来就是"不被 `since` 收窄"的意思，且 `test_automation.py` 断言了它）。

代价：**0.36s → 1.69s**（5096 行全量解码 + 风格统计；蒸馏是显式、低频的操作，这个量级可以接受）。

回归锁：`test_watch.py` P 层 `p4`（默认要扫满 6 条、`self.total==6`、`capped_talkers==[]`；
`limit=2` 时要如实点名）。旧码上此例必挂（没有 `capped_talkers` 字段）。

#### ⑰ 复查 `poll` 的截断路径：语义成立，剩一个刻意的残余

⑭⑮⑯ 修完回看 §9.12 ①（满量截断改"整批放大重取"）时，原实现里那句
"取的是**最早**的那批，所以万一真放弃，丢的也是最新的、不是中间的"**只是注释，没被验过**。
这轮把它当命题核了一遍（读码 + 与 `_rows_full_conn` 的语义对齐，无新实验）：

**成立的部分**：`_rows_full_conn` 合并后按 `create_time` 升序、`out[:limit]` ⇒ 放弃时留下的是
**最新的那条尾巴**；而 `next_since_ts` 只取**本批返回行**的最大 ts ⇒ 水位停在尾巴**之前**，
下一拍 `create_time > 水位` 会把它们接着读回来。**不是中间开洞**。

**残余（真丢，且是静默的）**：放弃点若**恰好切在某一秒中间**，那一秒剩下的那些既够不着
`> 水位`（同秒），又够不着 `= 水位 且 local_id > 上次表尾`——因为"上次表尾"记的是**本拍扫描时的表尾**
（`_poll_memo[tbl]["ids"]`，已经越过它们）。这一秒的尾巴就找不回来了。**同一类"秒级切点"的第 4 处**。

**为什么刻意不修**：修法要 `_rows_full_conn` 按分片回传"已投递的最大 `local_id`"（现在回的行里
没有分片），签名波及 `history` / `_pad_page` / `search_messages` / `digest` 四个调用方；而触发它要
**单表 500 条（`per × _POLL_BURST` = 20×25）新消息挤进同一个 15 秒窗口**，且那一拍已经带
`truncated: true` 上报。备选方案（"整秒留到下一拍"）会在"整批都是同一秒"时**死循环**——一拍读不到、
水位不动、下一拍还是同一幕，比丢一小截更糟。**代价与概率都不支持为它加复杂度**，于是把结论
写进 `poll` 的 docstring（改成准确表述，不再只说"丢的是最新的"），代码不动。

#### ⑱ `msg_dict` 的 400 字硬截断**不留痕**：1.4% 的消息，读的人拿到半句还以为是全文

同一轮复查往"输出侧的静默窗口"方向扫到的：`d["text"] = text[:400]`——截了**不标记、不补省略号**。

**实测（`verify/wechat-mcp/probe_text_truncation.py`，只读真库）**：5101 条里 **73 条（1.43%）**
渲染后 > 400 字，最长 **3069 字**；样本形态是**粘进来的日志/终端回显**（`lt=1`）与
**长段落**（`lt=49`）。也就是说"某条消息比 400 字长"在本机**不是罕见分支**，而这个接口的读者是
要**据此回话**的 Agent：拿到前 400 字当成全文去总结，正是本报告反复强调的
「看不到就编」（§六 硬约束）——只不过这次的"看不到"发生在**读取侧**，不报错、不置空。

**修法**（`wechat_core.msg_dict`，全部消息路径共用）：超 400 字时**额外**给两个字段——
`text_len`（全文长度，判据）与 `text_more`（后一截，最多到全文第 4000 字，免得一条长消息撑爆
工具输出）。`text` 本身**不动**（保持前 400 字、不加省略号），因为 `reply_to` 的 `quote` 是要拿去
和**界面里可见的原文**做比对的，往 `text` 里塞字符只会让它更难匹配。两者相加仍短于 `text_len`
⇒ 读的人知道**还没给全**。

回归锁：`test_watch.py` P 层 `p5`（1200 字要能原样拼回、5000 字要如实报长度且只给到第 4000 字、
短消息**不能**多出这两个键）。

> 文档（`README.md` / `server.py` 的工具描述 / 两版 `SKILL.md`）本轮**没动**：这三个文件正被
> **并行会话**改着（未提交），按提交卫生不往别人的工作区里塞东西，留给下一轮补一句话。

#### ⑲ 两处"看着像同一类、量完决定不修"的（一并记下，免得下一轮再扫一遍）

- **`decode()` 的 zstd 兜底会把压缩字节当正文**（`except: pass` 之后 `decode("utf-8", "replace")`
  ⇒ 乱码冒充内容，比截断更难发现）。量了：本机 5101 条里 1837 条是 zstd，**解压失败 0**，
  解压后最大 **12KB**，而上限是 1MB——**87 倍余量**（`verify/wechat-mcp/probe_decode_failures.py`）。
  要真踩到得有一条解压后 >1MB 的消息。**不修**：这是"要一条 1MB 消息"才可能发生的路径。
- **`_rows_full_conn` 里 `except: continue`**（某个分片查不出来就静默少一批消息）。判定为
  **不可达**：镜像路径自带双重护栏（`_plain` / `apply_wal` 的帧 HMAC + `quick_check`），
  坏的镜像在**构建时**就抛错上抛成工具错误，读到"构建成功但读不出"的镜像需要磁盘级损坏。
  **不修**：加"读不了的分片"信号要穿 4 个返回字典，而这条路的概率与代价不成比例。
