## 1. 背景与目标

现有 `wechat-mcp` 是一个「读本机微信 + 以本人身份发消息」的通用 MCP。实测发现，同一套读取技术还能支撑**四类高频痛点**，且每一类都值得做成**独立小工具产品**（独立安装 / 发版 / 技能包 / 授权）。

目标：把四类痛点各做成一个独立 MCP，**共享底层、业务独立**。

四个产品：

| | 产品 | 一句话 | 形态 |
|---|---|---|---|
| **A** | 文件归档 | 把助手/群/好友的文件收出来、防过期 | 无状态 |
| **B** | 记录导出 | 聊天记录导出成 md/html（带图/语音） | 无状态 |
| **C** | 客户分析 | 好友/群/成员清单 + 会话统计 | 无状态 |
| **D** | 撤回防护 | 撤回/删除消息可回溯 | **守护 + 前台** |

---

## 2. 共享基础层（唯一的分界）

**分界线**：基础设施共享，业务独立。

```
共享（基础设施）—— 4 个产品都 import
  wxkey4.py      进程内存只读扫密钥
  wxread4.py     SQLCipher4 解密
  wechat_core.py 多分片合并 / WAL 增量镜像 / 路径自动发现 / 会话发现 / _render

独立（业务）—— 各自一套，互不影响
  A 归档逻辑    B 导出逻辑    C 统计逻辑    D 守护与归档库
```

**为什么**：基础层是最脏最硬的骨头（实测堆出来的）；复制四份 = 微信改一次 DB 格式改四遍，且四份会各自漂移出不同的 bug。业务层则必须独立——四个产品的演进节奏不同，耦合只会互相拖累。

对外仍是**四个独立产品**：独立 exe、独立 npm 包、独立 skill、各自单档（**不保留 lite/pro 双档机制**）。

## 3. 本轮实测结论（设计依据，非推测）

本轮在真机（`db_storage` 本机账号）上实测，得出三条决定性事实：

### 3.1 文件本体可直接定位（A 的可行性前提）✅

- 文件本体落 `msg/file/<YYYY-MM>/<文件名>`（按月分目录）。本机 133 个文件 / 896MB。
- 消息（`local_type=49` 且 appmsg `type=6`）的 `<title>` **与磁盘文件名直接同名**；同名用 `<totallen>` 对大小消歧。
- **实测命中率：140 条文件消息 → 129 条 title+大小双命中（92%）**。
- 剩余 8%（如 182MB 的 `Lumii-Setup-0.1.4-x64.exe`、`tianshu.zip`）= **未下载 / 已过期**——这本身就是 A 的卖点。
- 坑：微信给重名文件加 `(1)`/`(3)` 后缀；同名不同版本靠大小区分；同一磁盘文件可被多条消息引用（只拷一次）。

### 3.2 撤回后原消息从库里消失（D 的形态前提）⚠️

- 扫本机 114 条 `local_type=10000` 系统消息，全是 `revokemsg`。
- **local_id 连续无空洞** → 被撤回的原消息行被删除/替换成 sysmsg，**原内容不在当前快照里**。
- revokemsg XML **只有** `<content>"某人" 撤回了一条消息</content>` + `<revoketime>0</revoketime>`，**没有 `newmsgid`** → 连"撤回的是哪条"都指不出来。
- **结论：撤回查看只能靠事前留存**（常驻守护 + 本地归档），不是"读库翻历史"。

### 3.3 通讯录表齐全，但标签映射缺失（C 的缺口）⚠️

| 表 | 实测 |
|---|---|
| `contact` | 2793 行，含 `remark`/`nick_name`/`alias`/`description`/`delete_flag` |
| `chat_room` | 34 群，含 `owner` |
| `chatroom_member` | 1984 条成员关系 |
| `contact_label` | 5 个标签**名**，**无好友↔标签映射表** |
| 标签映射 | 全库无此表，疑似埋在 `contact.extra_buffer`（protobuf）→ **需逆向** |

## 4. A · 文件归档 MCP

### 4.1 用户故事
1. 文件传输助手堆了几百个文件，一次性导到 `D:\wechat-files\助手\`
2. 客户群的文件怕过期，先存下来
3. 想知道**哪些文件已经下不动了**（过期预警）
4. 按 会话/类型/时间 理成目录

### 4.2 工具面（2 个）
```python
list_files(talker?, since?, until?, types?, keyword?, only_missing?)
  → [{name, size, ext, ts, talker, sender, local_path|null, status: "ok"|"missing"}]

archive_files(out_dir, talker?, since?, until?, types?, layout="by_session", dry_run=True)
  → {copied, skipped, missing, files[], out_dir}
```
- **预警 = `list_files(only_missing=true)`**，不单开工具。
- `dry_run=true` 默认，与现有发送工具同一纪律。

### 4.3 锁定决策

| 决策 | 取法 | 理由 |
|---|---|---|
| 拷贝 vs 移动 | **只 copy** | move 让微信「打开文件」失效，且动 `msg/file` 属改微信数据 |
| 默认布局 | `by_session` | 最贴「整理某会话文件」的心智 |
| 重复文件 | 同一磁盘文件只拷一次，清单标注引用数 | |
| 同名不同版本 | 输出名加时间戳后缀 | |
| 过期文件 | **只报告，不下载** | 服务器端拿不到 |
| 媒体范围 | **先只做 type=49.6 文件** | 图片/视频归 B |
| 输出落点 | `out_dir` 参数，否则读 `LUMII_WECHAT_ARCHIVE` | 复用现有配置约定 |

### 4.4 明确不做
不改微信数据 ✱ 不删原文件 ✱ 不下载已过期文件 ✱ 不做文件内容分析 ✱ 不管图片/视频

### 4.5 实现要点
- 复用：`wechat_core` 的 `_mirror`/`db_root`/会话发现/多分片合并/`_render`；密钥层不动。
- 新增：文件消息解析器（appmsg type=6 → title/totallen/fileext）、磁盘映射器、拷贝器。约 200–300 行。
- 测试：纯函数测（映射/消歧/layout 路径生成）秒级；真机只读测 `list_files`。

## 5. B · 记录导出 MCP

### 5.1 定位
核心只读原语从共享层来，B 只加「导出」这一层：把消息流变成**能读、能分享、能归档**的文件。

### 5.2 工具面（1 个）
```python
export_chat(talker, out_dir, format="md",            # md | html | json
            since?, until?, media="none",            # none | images | all
            transcribe_voice=false, split="none")    # none | month
  → {out_dir, messages, files_written, bytes}
```

### 5.3 输出形态（一个会话 = 一个目录）
```
D:\export\客户群A\
  chat.md              ← 正文
  assets\img_001.jpg   ← media=images
  assets\voice_003.wav ← media=all
```
`split=month` 时拆成 `2026-08/`、`2026-09/`… 每段一份 md。

正文（群聊标发送人）：
```markdown
### 2026-08-12 14:30 · 张三
晚上一起吃饭？

### 2026-08-12 14:31 · 我
好，几点？
> [引用] 晚上一起吃饭？
```

### 5.4 锁定决策
- 默认 **md**（html/json 可选）；默认**不带媒体**；体量按**时间分段成目录**。

### 5.5 技术点
- 跨分片全量：复用共享层合并，不漏历史。
- 图片：复用 `wechat_image.image_file()`（已解密）。
- 语音音频：`pilk.decode` → stdlib `wave` 写 wav。
- 语音转写：复用 `wechat_asr.transcribe`（默认关，0.5s/条 + 模型 78MB）。

### 5.6 明确不做
不导出到云端 ✱ 不自动发出去（导出≠发送，发送是另一个 MCP 的事）✱ 不做消息编辑

## 7. D · 撤回防护 MCP

### 7.1 形态：一写一读两个进程
```
   微信 ──写库──▶  守护进程 (常驻)  poll_new 增量 → 归档库
                          │
                          ▼
        ~/.lumii/wechat-archive/archive.db   (SQLite)
                          ▲
                   MCP 前台 (stdio，随客户端)  只读
```
**为什么拆开**：MCP 是 stdio、随客户端生死，**不能常驻**。拆开后 MCP 只读归档库，守护不在跑也能查历史归档；守护只写，互不干扰。

### 7.2 工具面（4 个）
```python
daemon_status()                        # 守护在不在跑 / 水位 / 归档条数
list_recalls(talker?, since?, until?)  # 归档里有、当前库已没的 = 被撤回/删除
read_recall(talker, msg_id)            # 取一条被撤回消息的完整内容
archive_gap(talker?)                   # 守护没覆盖到的时间段（关机期）
```
**核心机制**：`归档库 ∩ 当前微信库` 的**差集**——归档里有、库里没了 → 被撤回。同一机制顺带能抓**被本地删除的消息**。

### 7.3 锁定决策

| 决策 | 取法 |
|---|---|
| 守护范围 | 全部会话（poll_new 本就是一次扫全部） |
| 归档内容 | **原始 content**（撤回后能完整还原图/文件/引用元数据） |
| 守护启动 | **开机自启（注册表 Run）+ 手动开关**，提供 `daemon install/uninstall/status` |

### 7.4 关键技术点
- **首次打底**：守护首次启动做一次「全量对齐」（当前库全灌进归档库），之后 poll 增量 → 至少能回溯到守护启用那一刻。
- poll 间隔：微信撤回窗口 2 分钟，**≤30s** 就够。
- **断电缺口**：关机期间漏的归档不了 → `archive_gap` 如实报告，**不假装全覆盖**。
- 存储：全量原始 content + 索引；膨胀靠定期修剪。

### 7.5 明确不做
不改微信数据 ✱ 不阻止撤回（只事后查看）✱ 不保证关机期不漏 ✱ 不替 A 备份文件本体

## 12. 商品化第一批：失败信封与环境提示（2026-10-13 → 0.3.0）

按"这东西要卖"的门槛过一遍，第一批只做**用户看不见就会骂人**的两件：出错时说不说得清、
出了环境问题要不要用户自己猜。四个 exe 已重打包 v0.3.0。

### 12.1 失败信封收敛到主产品的形状

四件套原先的失败是 `{"error": ..., "error_code": ...}`，而主产品 `wechat-mcp/server.py` 的
`_fail()` 早就是 `{ok: false, detail, error_code, stage, suggestion}`。同一套产品线两种形状 =
一份提示词覆盖不了，而"形状随错在哪一步而变"正是主产品自己踩过并收敛过一次的坑（见其 `_fail`
的 docstring）。**对齐主产品**，字段名照抄（`detail` 而不是 `error`）。

统一入口 `mcp_stdio.tool_error(code, message, **extra)`；码表只有四件套真会发的那些：

| 码 | stage | 谁发 |
|---|---|---|
| `env_not_ready` | `env` | `EnvError`（读取层环境失败，见 §12.2） |
| `target_not_found` | `target` | `UnknownTalker`（会话名没对上） |
| `bad_args` | `args` | 各 `server.py` 的参数校验 |
| `not_archived` | `data` | D 的 `read_recall` 查不到 |
| `internal_error` | `internal` | 兜底（**只有它**置 `isError=true`） |

`isError` 的取舍写进了 `TOOL_CONVENTIONS`：业务性失败**不置** `isError`——它们是要模型读了照做的
结构化结果，置了 `isError` 反而会被某些客户端当成协议层故障打断；只有工具内部真炸了才是
`isError=true`。这条必须同时写在**引导词**里和**代码**里，两边不一致等于没写。

### 12.2 `EnvError`：环境失败要分类，且 `__str__` 必须带 hint

读取层的三处环境失败（找不到数据目录 / `LUMII_WECHAT_ACCOUNT` 没匹配 / 密钥扫不到）原先抛
裸 `RuntimeError`，文案混在一起。现在抛 `wechat_core.EnvError(message, hint)`，由 `mcp_stdio`
统一翻成 `env_not_ready` + 独立的 `hint` 字段（给用户的**动手步骤**）。

> **踩到的坑（值得记住）**：一开始把原来的"已扫描路径清单 / 修复建议"整段搬进 `hint`，只留一句
> 短 message。结果全仓大量 `except Exception as e: ... str(e)` 的路径（主产品读类工具是
> `ERROR: {e}`、`check_env` 是 `db_hint=str(e)`）**一个字都看不到 hint**——等于把给用户的修复建议
> 弄丢了，比不分类还糟。修法：`EnvError.__str__` 把 message 和 hint **一起**带出来；
> 结构化出口单取 `e.message` 免得重复。**加了个字段不是加了个能力，必须验证所有既有的取用路径。**

### 12.3 "找不到"要可操作：带上近似候选

`wechat_core.suggest_talkers()`（把名字相近的会话列出来）**早就在仓库里**，只是没接到错误上。
现在 `talker_of()` 在失败路径上把它塞进 `UnknownTalker.candidates`，`mcp_stdio` 既组装成
一句话进 `detail`、又作为 `candidates` 字段原样给出。本机真有三个 `loop` 这类歧义，靠这句
一次问清，而不是卡在"没有这个会话"。

### 12.4 启动时**不做**阻塞式前置检查

"启动时检测环境"没有按字面实现，理由写进了 `log_env_status` 的 docstring：MCP 随客户端启动，
用户完全可能**先开客户端、后开微信**，启动就拦 = 自找假失败；完整探测（找数据目录会扫盘）也不该
卡在握手上。改成**两件都不贵的事**：启动时把最便宜的那条事实（微信进程在不在）打进 stderr 撑支持，
真正的判断留在**调用时**（那时失败会被归类成 `env_not_ready` 并带上动手步骤）。

### 12.5 验收

## 13. 商品化第二批：进度反馈与守护管理（2026-10-13 → 0.4.0）

### 13.1 进度反馈（A/B）

几百个文件的归档、几千条消息的导出要跑几十秒，期间界面上什么都不动——用户只会以为卡死了。
主产品早就有这套接线（`wechat_sender._progress` + `server._emit_progress`，`test_watch.py` M 层
4 例守着），**照抄，没有另发明**：

- 槽位放 `mcp_stdio`（`set_progress` / `progress`）：worker 持有、协议层注入、**调用结束必须还原**
  （finally）——不还原就会把上一条请求的 `progressToken` 泄漏给下一次调用。
- 只在客户端**主动带了** `_meta.progressToken` 时才发；不带 token 的上报是无主的，规范不允许。
- **单调性由协议层兜底**：`_PROGRESS["n"] = max(上次+1, n)`。一次调用里可能有多个阶段各报各的
  （先"读记录"再"导媒体"），让每个调用点自己维护递增序列既啰嗦又容易错。
- A 按「每 20 条 **或** 距上次 2 秒」报——单个文件可能上百 MB，只按条数报会长时间静默；
  且播报放在循环**最前面**，后面的 `continue`（dedup/exists/出错）会跳过循环尾部。

### 13.2 D 的守护管理

**先纠正一处立项时的误判**：原计划要"托盘图标"给用户可见性。真去看代码，D 更贵的洞在别处——

> `log()` 只写 stderr。而开机自启拉起的进程（HKCU Run）**没有控制台**，stderr 是黑洞；
> 且 `archive.connect()` 在 try 之外，启动失败会**静默死掉**。
> 也就是说：守护半夜挂了，用户与排查者都看不到任何痕迹，而**那段时间的撤回永久查不到**
> （原文只在库里活到撤回那一刻）。这是"静默且不可逆"，比"看不见图标"严重一个量级。

所以这批做的是：

| 项 | 做法 |
|---|---|
| 日志落盘 | `log()` 同时写 `~/.lumii/wechat-recall/daemon.log`（512KB 滚动一代）。写日志失败**不能**影响守护本身 |
| 自愈 | 外层 `_supervise` 兜住**一切**异常，退避重启（5s→300s 封顶）；`_loop` 里原有的"单拍失败继续"保留 |
| 优雅收工 | 停止信号用 **Windows 命名事件**（`Local\LumiiWechatRecallStop`），`--stop` 发信号、守护在 `finally` 里记完停机时间才退 |
| 防双开 | `CreateEventW` 同名会返回已有句柄，靠 `GetLastError()==ERROR_ALREADY_EXISTS` 当场认出"已经在跑"，第二个自己退出 |
| 卸载真的卸载 | `--uninstall-autostart` 摘 Run 项**并停掉正在跑的守护**（只摘 Run 项的话，用户说"我关了"而进程还在） |
| 判活两口径 | `running`（进程，按事件句柄，即时）/ `alive`（心跳，按周期）——刚崩时心跳没过期，两个一起看才分得清"没跑"和"跑着但卡住了" |

**为什么不用 pid 文件 + 杀进程**：pid 会复用，判定"这个 pid 现在是不是我的守护"判错的代价是
**杀掉用户别的进程**；而且硬杀会把正在写的库截断。命名事件让守护自己收工，`--stop` 只负责喊一声。

**托盘图标没做**，理由：本产品的界面本来就是 AI 客户端（`daemon_status` 工具就报得清清楚楚），
而托盘要给的是一个 `pystray` + `Pillow` 依赖、一个 GUI 线程和一份图标资源（onefile 体积 +10~20MB）。
**如果用户要一个不经过 AI 的可见入口，这是个明确的待办**，不是遗漏。

### 13.3 验收

  停止事件（判活 / 防双开 / 优雅收工，用**测试专有的事件名**，不碰真守护的事件）。

  （正是 §13.2 那两口径要分开的理由）→ `daemon.log` 里全程有痕。

## 15. 商品化第三批：一键安装（2026-10-13 → 0.5.0）

§14 把安装器列为"上手门槛最高的一环"，本轮做掉。目标就一句：**用户拿到 exe，跑一个 `--install` 就能用**，
不用找路径、不用手写 `mcpServers` JSON、不用另外下载技能包。

### 15.1 形态：**不引入安装器工具链**，让 exe 自己会装

三条路可选：NSIS/Inno（真安装器）、独立安装脚本、**exe 自带 `--install`**。选了第三条：

- 零新构建依赖、零新增分发产物——还是那一个单文件 exe，和 D 的 `--install-autostart` 是同一种语汇；
- **可无头测试**（GUI 安装器没法在 CI 里验）；
- 产物与"四个独立产品、各自单档"的定位一致：每个产品自己管自己。

`mcp_stdio.serve()` 里拦下三个开关（**必须在这里拦**，否则会被当成"没有参数"而进 MCP 循环挂住），
共享实现在新模块 `wechat-mcp/mcp_install.py`。

### 15.2 客户端：**能用 CLI 就用 CLI，别碰别人的状态文件**

| 客户端 | 做法 |
|---|---|
| **Claude Code** | 调它自己的 `claude mcp add/remove -s user`。**不手改 `~/.claude.json`**——实测那是它的状态库（60 个顶级键，混着 projects/pluginUsage/tipsHistory），我们读写之间它自己也在写，竞态下丢的是用户的项目状态 |
| **Claude Desktop** | 合并进 `%APPDATA%\Claude\claude_desktop_config.json`（文件在才动） |
| **Cursor** | 合并进 `~/.cursor/mcp.json`（文件在才动） |

写 JSON 客户端配置的三条纪律，每条都对应一种真实的翻车方式：

1. **只改已经存在的配置文件**——不去给没装的客户端造目录（造出来会让用户以为装了）。
2. **读不出来就拒绝**（非法 JSON / 顶层不是对象）⇒ **一个字节都不动**，只报告。
   宁可不装，也不能洗掉用户手写的配置。
3. **只增删我们自己的那个键**，改前备份 `<文件>.bak`，写回走 tmp + `os.replace`。

### 15.3 部署与技能包

- **部署目录在哪儿已经有约定**：`%USERPROFILE%\.lumii\mcp\<产品>\<产品>.exe`（主产品 wechat-mcp 由
  `src/main/bundled-mcp-exe.ts` 的 `getDeployedMcpExePath()` 放在那儿）——沿用，不另开一处。
  覆盖旧版必须用**「旧文件改名让位」**：Windows 下运行中的 exe **可以改名、不能覆盖**（直接覆盖是 `WinError 5`），
  主产品同一处理，留下的 `*.old-*` 只留最近两个（否则每次升级涨一份 10MB）。
- **技能包打进 exe**（构建脚本加 `--add-data`），`--install` 时从 `sys._MEIPASS/skills/` 取。
  单文件产品不该要求"技能包得跟 exe 放一起"。
- ⚠️ **技能 id ≠ MCP 服务名**：目录是 `skills/wechat-file-mcp/`（技能 id），而服务名是 `wechat-file`。
  第一次真装就栽在这儿——拿服务名去找 `_MEIPASS/skills/wechat-file` 找不到，**技能包静默没装上而其余步骤全绿**。
  修法：技能包一律用 `spec["product"]`；且**冻结模式下源找不到要报 `fail`（构建漏了 `--add-data`），
  不能用 `skip` 蒙混**——用户会以为装好了，实际客户端里没这个技能。

### 15.4 卸载的语义

- 摘注册 + 删技能包 + 删部署的 exe（正在跑的就是它自己时 `MoveFileEx(..., MOVEFILE_DELAY_UNTIL_REBOOT)`
  安排重启后删——比"再起个进程等几秒"稳）；
- **用户数据一律不动**，但**要说清留在哪**（D 的归档库、A/B 的 `out_dir`），免得用户以为卸载没干净；
- 结尾有 `_footer()`：**有 `fail` 就不是"装好了"**。装了一半的安装器比失败的更坑——后者至少会去查。

### 15.5 本轮**不做**的

- **Codex**（TOML 形状不同，本轮不做）。**Cursor / Codex 的技能目录**也不写：
  `.cursor/skills-cursor/` 旁边有个 `.sync-manifest.json`，看着是**别人在管**的目录，
  往一个自己看不懂其管理方式的目录里写，比不写更糟。

### 15.6 验收

- 新 `test_mcp_install.py` **10 例**（全在临时目录，**不碰任何真实客户端配置**，所以 CI 上也能真跑）：
  增删幂等且不动别人的键、非法配置拒改且字节不变、技能包往返、部署源码模式、`*.old-*` 修剪、
  卸载连残留一起清（且不误删别人的文件）、**子进程参数必须是 Python 写法**、开关路由
  （没命中必须返回 `None`）、**摘失败不许挡住挂**、**技能 id ≠ 服务名**。
- **真机端到端**（真 exe）：跑 `--install` → 部署到 `~/.lumii/mcp/<产品>/`、Claude Code 重指到
  稳定路径、Cursor 合并、技能包落 `~/.claude/skills/`；`claude mcp list` 四个全 **✔ Connected**；
  跑 `--uninstall` → 注册/技能包/部署目录全清，**D 的归档库字节数不变**（1945600）；再装一遍。
- 活体探针 53 → **57/57 PASS**（每个 exe 加一条 `--install-status` 退出码检查——验"开关被
  `serve()` 拦下并立即退出"，**不跑 `--install`**：探针不该改用户的客户端配置）。
- 已挂 CI（`test_mcp_install.py`）。

### 15.7 两个只有"真跑一次"才会暴露的 bug（打桩单测全绿）

## 16. 商品化第四批：版本对账与更新检查（2026-10-13 → 0.6.0）

> ⚠️ **本节的一半已在 0.10.0 摘掉**：**本地版本对账留着**（它不联网、天天有用），
> **联网的 `--check-update` 连同发布清单生成器删了**——用户明确不做对外发布 ⇒ 没有发布通道
> ⇒ 那个开关永远只能返回 404。理由与判据见 §16.7。下面是当时的完整设计（要恢复照着捞）。

### 16.1 拆成两半，因为一半能守红线、另一半不能

| | 做什么 | 要不要联网 |
|---|---|---|
| **本地版本对账** | 「你现在跑的这份」vs「装在客户端里那份」不一致 ⇒ 报「重跑 `--install`」 | **不联网** |
| **`--check-update`** | 查远端有没有新版 | 联网，但**必须由用户显式触发** |

**为什么联网那半不能自动跑**：本产品的红线是「全部本地处理、**不外传**」（§10）。自动联网检查
虽然不传用户数据，但那也**是一次对外请求**——跟卖点直接冲突，用户会问"你不是说本地吗"。所以默认
一次网络都不发，只有 `--check-update` 才发。这条同时写进了测试（断言 `do_install` / `do_status`
的函数体里**不出现** `fetch_latest_version`）。

### 16.2 版本对账为什么要落一个 `installed.json`

`wechat-*-mcp.exe --version` 是 PyInstaller **onefile**——连打印版本都要先解包，**冷启动 1–3 秒**
（主产品 `wechat-mcp.exe` 已实测过，TS 侧因此留了版本常量镜像）。`--install-status` 若去问部署
副本，状态查询就变秒级。所以安装时把 `{version, exe, installed_at}` 落进
`~/.lumii/mcp/<产品>/installed.json`，查状态读它。**卸载时连同它一起清**（`_clean_install_dir`
的"我的文件"清单里必须带上它，否则目录永远 rmdir 不掉）。

### 16.3 「拿不到」不许说成「已是最新」

`--check-update` 失败时输出的是**「拿不到版本清单（原因）——不代表是最新版」**。清单没发布、
没网、被墙，这三种情况用户看到的都该是"没法确认"，而不是一个让人安心但错误的结论——
后者会让用户**停在旧版上还以为自己是最新的**。测试里专门钉了这一条。

### 16.4 清单（缺了这一半，更新检查就是个摆设）

远端要有个东西可查。四个产品版本各自独立（不像 App 有统一的 `v<App版本>` tag），从 release 的
tag 推不出产品版本，所以在 release 里放一份小清单：

```json
{ "wechat-file-mcp": {"version": "0.6.0", "asset": "wechat-file-mcp.exe", "bytes": 12095947}, ... }
```

- 生成：`pnpm --filter ./apps/windows build:wechat-toolkits-manifest` →
  `resources/dist/wechat-toolkits.json`（根 `.gitignore` 覆盖 `dist/`）。
  版本号唯一来源仍是各产品 `server.py` 的 `SERVER_VERSION`；**缺 exe 就拒绝生成**（指向不存在
  产物的清单等于骗人）。
- 取：`releases/latest/download/wechat-toolkits.json`（挂在 App 的 release 上，与
  `wechat-mcp.exe` 同一个地方，沿用现成通道，不新开）。
- **发布是两步**：跑脚本 + 把四个 exe 和这份 json 一起挂到 release 的 assets 上。
  只做第一步的话 `--check-update` 会如实说拿不到——**不会假绿**。

> **现状**：四个产品**还没有发布过**（没有 tag、没有 release）。所以今天跑 `--check-update`
> 会得到"拿不到版本清单"，这是**正确**的诚实输出，不是 bug。发布通道一旦建起来，这一半自动就通了。

### 16.5 验收

- `test_mcp_install.py` 10 → **13 例**：版本比较（段数不同/非数字段/`0.10 > 0.9` 别按字符串比）、
  登记往返与"装的是旧版要报出来"、**联网检查永不谎报**（含"自动路径里不许出现取远端调用"）。
- 真机：`--install-status` 的版本对账三种状态各验一次；`--check-update` 在**没有发布通道**时
  必须输出"拿不到"，且退出码 0（那不是错误）。

### 16.7 摘掉联网那一半（2026-10-13 → 0.10.0）

用户明确"**不需要对外发布**"。那 `--check-update` 就**永远只能返回 404**——它是个
**注定失败的按钮**，比没有这个功能更糟：后来的人看见它会以为"是不是坏了/网络有问题"，
而真相是这个产品根本没有发布通道。

**删掉的**：`do_check_update` / `fetch_latest_version` / `MANIFEST_URL` /
`scripts/build-wechat-toolkits-manifest.mjs` / `package.json` 里那条 script /
两个测试 / 四个 README 的开关行 / `resources/dist/` 产物。
**留着的**：本地版本对账（`installed.json` + `--install-status` 那行）——它不联网、天天有用，
"你现在跑的这份 vs 装的那份"不一致照样得报出来。

**顺手把它变成一条结构性守卫**（`test_no_network_code_in_install_or_license`）：
断言 `mcp_install.py` 与 `mcp_license.py` 里**不出现** `urllib` / `urlopen` / `requests.` /
`socket.` / `http://` / `https://`。产品红线是「本地处理、**不外传**」（§10），联网代码一旦
混进来，机器码或会话内容就有被带出去的可能——而那是不可逆的。今天两个文件里**一条网络代码都没有**。

## 17. 商品化第五批：Codex 客户端（2026-10-13 → 0.7.0）

装上后 §14 里"只做 JSON 类的客户端"那一格清掉。

### 17.1 它是 TOML，而且这份 TOML 里有**明文 API key**

`~/.codex/config.toml`（实测本机那份就带着 `experimental_bearer_token = "sk-…"`），条目形状：

```toml
[mcp_servers.<名>]
type = "stdio"
command = "C:\\…\\wechat-file-mcp.exe"
args = []
transport = "stdio"
```

标准库只有 `tomllib`（**只读**）。为这一件事引一个写 TOML 的依赖不划算，所以**手工拼段**——
但只在"**追加一个还不存在的段**"和"**整段删掉**"这两件事上手工拼是安全的，那就**只做这两件**，
不动任何既有行。三条纪律比 JSON 那两家更硬：

1. **反斜杠必须转义**。TOML 的基本字符串里 `\` 是转义符，Windows 路径全是反斜杠——不转就是
   **非法 TOML**（第一版测试夹具自己栽在另一个类似点上：`[mcp_servers.别人]`，裸键只允许 ASCII）。
2. **写完立刻 `tomllib` 读回来验**，读不回来就**放弃改动**（原文一个字节没动）。
3. **整段删除**要连子表一起（`[mcp_servers.x.args]`），且不碰紧邻的下一段。

### 17.2 技能包变成**多目标**

`SKILL_TARGETS` 列出各客户端的技能根（Claude Code `~/.claude/skills/`、Codex `~/.codex/skills/`），
**判据是客户端目录在不在**（不是技能目录在不在：装了客户端、还没放过技能时，技能目录往往不存在，
那时我们**该**建它）。Cursor 仍不在列——`.cursor/skills-cursor/` 旁边有个 `.sync-manifest.json`，
看着是别人在管的目录，往一个自己看不懂其管理方式的目录里写比不写更糟。

### 17.3 事故与它换来的结构性守卫

`test_remove_failure_does_not_block_add` 最初**没打桩 `codex_apply`**，而 `do_install` 里 Codex 那步
在 `skill_apply` **之前**——于是那一轮测试**真把一段 `[mcp_servers.wechat-file]`（`command = "C:\fake\x.exe"`）
写进了用户的 `~/.codex/config.toml`**（那里面有明文 API key）。已用 `config.toml.bak` 还原并核对
（888 字节、TOML 可读、key 完好、`.bak` 已清）。

**教训不是"记得打桩"**（逐点防会漏），而是**面上防**：新增
`test_all_client_paths_under_home_or_appdata` —— 把 `USERPROFILE`/`HOME`/`APPDATA` 都指到临时目录，
然后断言**每一条**客户端路径都落在这些根之下。任何一条绕过 `~`/`%APPDATA%` 的硬编码路径都会当场露出来。
"改配置"这类函数的测试，光靠 `monkeypatch` 是不够的，得有一条证明**根是可改的**。

### 17.4 验收

- `test_mcp_install.py` 14 → **17 例**：新增 Codex TOML 往返（含**反斜杠转义**、`tomllib` 读回、
  别人的段与 API key 一字节不碰）、`[mcp_servers.x]` 整段删除（含子表、不碰邻段）、
  上面那条**结构性路径守卫**。
- 真机：四个产品都写进真实 `~/.codex/config.toml`（TOML 可解析、`ynote`/`langfuse-docs` 与
  API key 完好）；卸 `wechat-crm` → 段消失、其余段与 key 完好 → 装回来。技能包两家各一份。
- 探针 57/57；四个 exe 重打包 v0.7.0；清单重新生成。

## 18. 商品化第六批：授权门禁（2026-10-13 → 0.8.0）

**这推翻 §11.3 里"四件套不接授权门禁"的结论**（那条是当时按代码现状记的，现在按产品化要求补上）。

### 18.1 复用 `licensing.py`，只补它没有的三件

主产品那套（验签 / 机器指纹 / 到期 / 防时钟回拨 / 内置豁免）已被 `test_licensing.py` 钉过，
直接复用；`mcp_license.py` 只加：

1. **按产品分 scope**。主产品是「pro/lite 双档，授权把 lite 升成 pro」，**降级总还能用**；
   四件套是**单档要卖**，语义不同：**未授权就是不给用**。一份授权覆盖一个产品
   （`--scope wechat-file-mcp`）或打包覆盖四个（`--scope wechat-toolkits`）。
2. **落点分开**：四件套读 `~/.lumii/wechat-toolkits/license.json`。走的是 `licensing` 自己留下的
   `LUMII_WECHAT_LICENSE_DIR` 覆盖口（它的注释写的就是"测试与**多份授权并存**的场景要用"），
   所以 **`licensing.py` 一行没改**。
3. **给用户看的出口**：`--license-status` / `--machine-id`，以及 MCP 侧的 `not_licensed`。

### 18.2 拦在**工具调用**，不是拒绝启动

服务器连不上，用户和 Agent 看到的只是"这个 MCP 挂了"，**没有任何可操作信息**；而结构化地拒绝
每一次工具调用，Agent 能把「授权文件该放哪、机器码怎么拿」原话转达给用户。所以：

- `initialize` **照常完成**（连接是通的），但未授权时 `instructions` 里已写明；
- 每次 `tools/call` 返回 `{"ok": false, "error_code": "not_licensed", "hint": ...}`；
- **每次调用都重新查**（不是启动时缓存）——用户放好授权文件后**不必重启**，下一拍就生效。

引导词那一条是关键：Agent 是**先读引导词、后调工具**的。只靠工具报错，它会白调一次、
甚至把 `not_licensed` 误判成别的问题。

### 18.3 D 的守护也要拦

它守着本产品**最核心的价值**（持续留存、撤回可查），不拦等于白送；而且守护是**持续**跑的，
跑到一半才发现没授权等于白跑一场。`license_gate()` **fail-closed**：授权模块读不出来也算不放行
（模块是打进 exe 的，缺了就是构建出了问题，该报出来而不是放行）。

### 18.4 一个被实测推翻的假设（值得记）

补门禁前我按构建脚本的 `stagePyDir`（把共享层所有非 `test_` 的 `.py` 拷进 staged）推断
"`licensing.py` 一直在四个 exe 里"，还准备据此改 §11.3。**实测搜不到它的任何特征串**，
说明它此前确实不在（PyInstaller 只打包**实际被 import 的**模块——文件放进搜索路径**不等于**打包）。

## 19. 商品化第七批：双击即安装（2026-10-13 → 0.9.0）

用户的原话是"**直接运行 exe 就是一个黑窗口**，应该不需要托盘吧"——那句话点出的其实不是托盘
（托盘已明确不做），而是**双击之后一个黑窗口什么都不干**。对一个卖给非技术用户的工具，
这是最直观的"坏了"。

### 19.1 判据不能是 `isatty()`——`NUL` 是字符设备

"双击（控制台）" 与 "被 MCP 客户端拉起（管道）" 要能分开。第一直觉是 `sys.stdin.isatty()`。
**实测三行把它否了**（真机跑出来的表）：

| 启动方式 | `isatty()` | `GetConsoleMode` |
|---|---|---|
| 新控制台（等价双击） | True | **True** |
| `stdin=NUL` | **True** ← 误判 | **False** |
| 真管道（等价客户端） | False | False |

Windows 上 `NUL` 是**字符设备**，所以 `isatty()` 对它返回真。客户端若拿 `NUL` 当 stdin 拉起
服务器，服务器会被弹成一个**安装向导**——然后 stdio 传输**彻底堵死**（服务器在等回车，
客户端在等 JSON）。改用 **`GetConsoleMode(STD_INPUT_HANDLE)`**：它只对**真正的控制台**成功。

**判不出来一律当客户端**（安全侧）：宁可双击时显得没反应（用户会再点一次或看文档），
也不能让服务器在客户端里弹向导。

### 19.2 向导本身

`interactive()`：讲清楚**这是什么**（给 AI 客户端用的 MCP 插件，不是双击就干活的程序）→
列出**接下来会动的三处** → **勾选要注册到哪些客户端** → 问一句 → 装 →
需要常驻的产品（D）顺口问一句要不要开机自启 → **`input("按回车关闭")` 停住**
（双击来的窗口，输出还没看就没了等于没装）。

**勾选客户端**（用户明确要的）：检测到哪些就列哪些，**回车 = 全勾**，输入序号切换
（`2 3` / `2,3` 都认），没装的显示「（未安装）」且点了不生效——

```
检测到你装了这些 AI 客户端，要注册到哪些？
  1. [✓] Claude Code
  2. [ ] Claude Desktop   （未安装）
  3. [✓] Cursor
  4. [✓] Codex
  输入序号切换（空格/逗号分开），直接回车 = 就这些：
```

- **为什么要问**：它要写 Claude Code / Cursor / Codex **三个别的应用**的配置。下载目录里
  误双击一下就把三份配置改了、且窗口关掉就看不出来了。一次回车换掉这一整类投诉，值。
- **卸载不问**：装的时候能挑是因为那是**加法**；摘干净是**减法**，留一半更糟。
- **为什么要问自启**：D 的价值全在"守护常驻"，不问的话用户装完发现"什么都查不到"，
  会以为产品坏了。
- `ask` / `ask_raw` / `_pause` 都做成了可注入：测试里不会被 `input()` 卡住，也不会真去开自启。

**顺手收敛的一件事**：四家客户端原先在装/卸/看状态三个地方**各写了一遍循环**。现在统一成
`clients()`（一份"本机有哪些、装没装"的清单）+ `register_client`/`unregister_client`
（按 `kind` 分派到 CLI / JSON / TOML 三条路）+ `_registered_line`。三个动作只遍历这一份，
新加客户端只改一处。

### 19.2b 装到一半崩掉比装不上更糟：`_say` 不许抛

真机撞见：控制台是 GBK 时 `✓` 抛 `UnicodeEncodeError`——而那时 exe 已经拷完、客户端还没注册。
**装到一半的现场比纯失败难查得多。** 所以 `_say` 编不出来就降级成可编码的近似字符把流程走完
（正常双击路径上 `serve()` 已先 `force_utf8_stdio()`，基本不会触发）。

### 19.3 验收

- `test_mcp_install.py` 17 → **22 例**：`is_interactive` 用**真子进程 + `stdin=NUL`** 钉死
  （并顺带钉住"只靠 isatty 会误判"这个前提——前提没了这条测试就该重写）、勾选菜单
  （回车=全勾/序号切换/没装点不动/越界乱输入忽略/EOF 不卡）、向导的确认/拒绝/常驻分支、
  `_ask`/`_pause` 在 EOF 与 Ctrl-C 下**不抛不卡**、`_say` 编不出来时**降级不抛**。
- **真机**：`echo '{...initialize...}' | exe` → 出的是 JSON 握手（**没被向导劫持**，这是最要紧
  的安全性质）；`Start-Process` 开新控制台 → `GetConsoleMode=True`；向导渲染人工过目一遍。
- 探针 67/67；四个 exe 重打包 v0.9.0。
- 四个 README 的「一键装」改成以**双击**开头。

> **测试自己也会死循环**：勾选菜单的测试最初写成 `ask_raw=lambda p: "2"`——每轮都把第 2 项
