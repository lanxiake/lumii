# 上下文压缩 · 复杂度反思（2026-09-20）

> **怎么来的**：排查主进程冻结时定位到 token 估算（见
> [`docs/fix/2026-09-20-主进程冻结调查与修复.md`](../../fix/2026-09-20-主进程冻结调查与修复.md) §6.9）。
> 我先优化了**单次估算的实现**（逐字符正则 → 码点比较，5.6×），但读
> `strategies/hard-trim.ts` 时发现**真正的规模问题在调用次数**，于是回来反思方案本身。
>
> **一句话结论**：单次估算我已经优化了，但**架构层面的重复全量计算一点没动** ——
> 一次压缩实测仍是 **1714ms**，而它可以做到约 60ms。

## 一、实测：一次压缩要多久

`scripts/probe-hard-trim-cost.mjs`（取 live DB 里最大的会话、真实消息、
**已优化过的**单次估算实现）：

| 项 | 值 |
| --- | --- |
| 会话规模 | 134 条消息，`content_json` 合计 **7.6 MB** |
| 估算 token | **286 万** |
| `estimateTokenCount` 调用次数 | **31 次** |
| 总耗时 | **1714 ms** |
| 平均每次估算 | 55.3 ms |

**⇒ 单次压缩 1.7 秒**，而它跑在主进程主线程上 —— 这已经够触发冻结阈值。

---

## 二、问题：复杂度是 O(n × k)

`strategies/hard-trim.ts` 的 `iterativeDropUntilUnder` 把 `estimateTokenCount`
写在**循环条件**里 —— 每删一条消息就**重算整个消息列表**：

| 位置 | 形式 | 上限次数 |
| --- | --- | --- |
| `hard-trim.ts:98` | `for (i < 48 && estimateTokenCount(m) > max)` | 48 |
| `hard-trim.ts:107` | `for (i < 16 && …)`，**循环体内再算一次** | 32 |
| `hard-trim.ts:115` | `for (i < 8 && estimateTokenCount(m) > max)` | 8 |
| `hard-trim.ts:50-60` | `while (groups.length > 1)` 每轮一次 | 轮数 |
| `hard-trim.ts:138-147` | `trimHistoryHeadUntilUnderBudget` 的**二分**：每次比较都全量估算 | log n |
| `hard-trim.ts:80 / 85 / 92` | 三道防线各一次 | 3 |

**最坏约 90~100 次全量估算**，每次是 O(全部消息字符数) ⇒ **总计 O(n × k)**，k 可达近百。

**这也解释了修复收益为什么有限**：把单次估算加速 5.6× 之后，最坏情况仍有 ~1.7 秒。
（反过来说，**如果不优化单次实现，这里会是 ~10 秒**。）

---

## 三、可以做到 O(n)

```
1. 一次性算出每条消息的 token     O(n)   ← 一次遍历
2. 其余用「总和 − 已丢弃前缀和」   O(1)   ← 丢弃区间不再需要重算
3. 循环里只做比较                O(1)
```

关键性质：**「丢掉前 k 条之后的剩余 token」= 总和 − 前 k 条的 token** ——
根本不需要重新遍历。

**⇒ 1.7 秒 → 约 60 ms**（一次遍历的量级），且与循环次数无关。

## 四、更深层的三个问题

### 4.1 286 万 token 的会话，该不该走这条路

实测最大会话估算 **286 万 token**，是常见上下文窗口（128K）的 **20 倍以上** ——
它**永远不可能完整进模型**，每次都要走完整压缩流程。

这类会话（渠道归档）**是不是应该在更上游被隔离或截断**？
现在的形态是"一路带到压缩阶段才处理"。

### 4.2 估算精度与成本不匹配

现在用**逐字符精确统计**（中文 0.6 / 英文 0.3），而它的用途只是**判断是否超阈值** ——
精度要求并不高，成本却是 O(全部字符)。

**采样式估算**（取前 N 字符按比例外推）能到 O(1)。本次**没这么做**，
因为误差会影响阈值判断（尤其临近阈值时）。

但值得记下这个取舍：**如果 O(n) 之后仍不够，采样是下一个可用的杠杆。**

### 4.3 服务商的真实值没有被用上

`providerPromptTokens(usage)` 已经解析了**服务商返回的真实 prompt token**
（含 cacheRead / cacheWrite）。那是**真实值**，而估算只是**预测**。

理想形态是**增量估算**：

```
上一轮真实 token（服务商给的）
  ＋ 本轮新增消息的估算
  ＝ 当前 token
```

**⇒ O(新增) 而非 O(全部)**，且精度**更高**（锚在真实值上）。

代价是要维护状态（上轮 token、消息边界），改动面比第三节的 O(n) 方案大。

## 五、建议（按性价比排序）

| 方案 | 复杂度 | 改动面 | 评价 |
| --- | --- | --- | --- |
| 现状 | O(n × k)，k ≤ ~100 | — | 实测 1714 ms / 次压缩 |
| **一次算完 + 前缀和** | **O(n)** | 局部（`hard-trim.ts` 的循环） | **推荐**：收益明确、风险可控 |
| 增量估算（锚服务商真实值） | O(新增) | 中（需状态管理） | 更优，但要动接口 |
| 采样式估算 | O(1) | 小 | 精度换速度，暂不建议 |

**本轮只做了单次实现的优化**（5.6×，已提交 `c6b28d4b`）。
上表后三行**都没做** —— 它们是方案层面的改动，需要单独决策。
