## 1. 结论摘要

| 项 | 结论 |
| --- | --- |
| 主目标 | 为客户端提供**轻量本地 OCR**：效果够用中英印刷体，CPU 默认可跑，有 GPU 时可选加速，不绑架 CUDA |
| 范围（首版） | **A** 聊天附件 `ocrText`、**B** Agent 截图后抽字、**D** 扫描文档/无文字层 PDF；**先 Windows**，Linux 二期 |
| 不做 | 微信 UI OCR 替换（继续 `ocr4.ps1`）、手写专项、版面还原/表格重建、server 大模型档、首版 Linux GPU |
| 技术路线 | Electron **utilityProcess** 隔离推理 + **PP-OCR mobile ONNX**；EP：`DirectML → CPU`；模型按需下载 |
| 与云端关系 | **双轨**：本地负责 `ocrText`，云端 vision 继续负责 `description`；本地失败/低置信再云端补 OCR |
| 最大风险 | 再引入第三份 `onnxruntime.dll` 污染主进程；缓解：**推理永不进主进程** |

## 2. 背景与代码事实

### 2.1 现状

| 能力 | 实现 | 路径要点 |
| --- | --- | --- |
| 产品级「OCR」 | 云端多模态 vision，prompt 要求返回 JSON `ocrText` | `bridge-image-services.ts` → `recognizeImage` |
| 本地 OCR | 仅微信：`Windows.Media.Ocr` | `apps/windows/assets/wechat/ocr4.ps1` |
| 文档文字 | PDF/Office **解析**，非 OCR | `document-parser.ts` |
| 截图工具 | 落盘 `imagePath`，本身不抽字 | `app_screenshot` / `screen_screenshot` / `browser_screenshot` |
| 本地 ONNX | sherpa **1.27** + `onnxruntime-node` **1.14**（E5），主进程内有 DLL 顺序闸 | `onnx-runtime-gate.ts` |

微信客户端自带 `wxocr.dll` / `.xnet` **无可调用 C API**，不能复用（见渠道逆向调研）。仓库计划曾写明微信路径「本轮不做 RapidOCR」——本设计针对**通用客户端 OCR**，不替代微信专用链路。

### 2.2 产品诉求（已对齐）

1. 不受「必须有 GPU」限制；有 GPU 可用，无 GPU 用 CPU  
2. 效果不错，但**不能太占资源** → 固定 **mobile** 档，不自动升 server  
3. 场景：聊天附件 + Agent 截图 + 扫描文档  
4. 云端分工：本地 `ocrText` + 云端 `description`；本地失败云端补 OCR  

## 3. 方案对比与选型

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A. Utility 进程 + PP-OCR mobile ONNX** | 独立进程自带 ORT；CPU + DirectML | 与 sherpa/E5 隔离；无 Python；包体可控；EP 回退清晰 | 需薄封装 det/cls/rec 或引入成熟小封装 | **采用** |
| B. Python venv + RapidOCR | 对齐 Qwen3-TTS 子进程 | 生态成熟 | 依赖 Python 就绪；冷启动重；与「轻量」拧 | 不采用（可作极端兜底，不进首版） |
| C. 主进程复用 `onnxruntime-node@1.14` | 与 E5 同 ORT | 少一个运行时 | 卡旧版、DirectML 弱、加重主进程、缠顺序闸 | **否决** |

**选型理由**：主进程已有两份同名 ORT 冲突史；OCR 必须进程外。mobile ONNX（det≈4.7MB + rec≈11MB 量级）满足资源红线；Windows 上 DirectML 覆盖核显/独显且不强制 CUDA 工具链。业界对 OCR 小模型用 CUDA EP 常因动态 shape **反而不如 CPU**——故 GPU 定位为「可选加速 + 可关」，不是正确性前提。

## 4. 核心设计

### 4.1 架构

```
Chat 附件 / Agent 截图 / 扫描 PDF 页图
              │
              ▼
     OcrService（主进程，无 ORT）
     · 懒启动 utility · 排队 · 超时 · 空闲退出
     · 模型下载与校验 · 平台开关
              │  IPC / MessagePort
              ▼
     OCR Utility Process
     · PP-OCR mobile：det + cls + rec
     · executionProviders: ['DML', 'CPU']（可配置强制 CPU）
     · enableCpuMemArena=false（避免 RSS 暴涨）
              │
              ▼
     { text, lines[], confidence, backend: 'dml'|'cpu' }
              │
     失败 / 低置信 ──► 云端 vision 补 ocrText
     同时 云端 vision ──► description（双轨，prompt 可不再要求列字）
```

**硬边界**

- Utility **禁止**加载进 Electron 主进程的任何 `onnxruntime*.dll`  
- 主进程 **禁止** `require('onnxruntime-node')` 用于 OCR  
- 模型与 ORT 二进制不进默认安装包；按需落到 `LUMII_CLIENT_DATA_DIR`（默认 `~/.lumii`）下约定目录，例如 `runtimes/ocr/`、`models/ocr/ppocr-v4-mobile-zh-en/`

### 4.2 对外 API（主进程）

```ts
/** 本地 OCR 一次识别请求 */
type OcrRecognizeRequest = {
  path: string
  /** 长边上限，默认 1600；截图/扫描控内存 */
  maxSide?: number
  timeoutMs?: number
  /** 强制 CPU，跳过 DirectML */
  forceCpu?: boolean
}

type OcrLine = {
  text: string
  score: number
  /** 四点或轴对齐框，实现选定一种并在类型里固定 */
  box: number[]
}

type OcrRecognizeResult = {
  text: string
  lines: OcrLine[]
  /** 行均分或几何平均，用于是否触发云端补 OCR */
  confidence: number
  backend: 'dml' | 'cpu'
  source: 'local'
  durationMs: number
}
```

`OcrService` 另提供：`ensureReady()`（下载+拉起进程）、`getStatus()`、`shutdown()`、`setPreferredBackend('auto'|'dml'|'cpu')`。

### 4.3 接线点

#### A. 聊天附件

改 `BridgeImageServices.recognizeImage`（及 IPC `image:recognize` 契约）：

1. `includeOcr !== false` 时先 `OcrService.recognize`  
2. 云端 vision prompt：**默认只要 description**；仅当本地失败或 `confidence < 阈值`（建议 0.5，可配置）时，再带「补 OCR」或单独一次补抽  
3. 返回增加 `ocrSource: 'local' | 'cloud' | 'mixed' | 'none'`，前端附件策略可展示来源，不破坏现有「描述 + OCR」展示  

#### B. Agent 截图

在截图工具成功写出 `imagePath` 后：

- 默认跑本地 OCR（可用工具参数 `ocr?: boolean`，默认 `true`）  
- 工具结果增加 `ocrText`（及可选 `ocrConfidence`）  
- 超大图先按 `maxSide` 缩放再送 utility  
- OCR 失败不导致截图工具失败：返回图路径 + `ocrError`，由 Agent 自行决定是否再调识图  

涉及：`bridge-screen-record-tools` / `bridge-browser-tools` / `bridge-app-ui-tools`（或统一后处理钩子，避免三处复制）。

#### D. 扫描文档

| 输入 | 策略 |
| --- | --- |
| jpg/png/webp/bmp | 直接 `OcrService` |
| PDF | 先走现有文字层解析；若页文本极少（阈值：字符数 / 页面积或绝对字符数，需定一个可测阈值）→ 渲染该页为图再 OCR |
| 多页 | 并发度 **1～2**；按页拼接，页间空行分隔；单页超时不阻断整文档（记失败页） |

不在首版做：版面阅读顺序精修、表格结构、双栏复杂还原（mobile 行框拼接按检测顺序即可）。

### 4.4 资源、模型与生命周期

| 项 | 约定 |
| --- | --- |
| 模型档 | **仅** PP-OCR mobile（中英）；不自动下载 server 权重 |
| 下载 | 对齐语音 `model-manager`：校验 hash、可取消、进度事件；国内源优先策略与现有模型下载一致（可复用镜像列表模式） |
| 进程 | 首次 OCR 懒启动；空闲 **N 分钟**（建议 5）退出 utility，释放 RSS |
| 队列 | 主进程单队列；同时只跑 1 个推理任务进 utility（截图连发也不打爆） |
| 内存 | ORT `enable_cpu_mem_arena=false`；输入长边默认 ≤1600 |
| GPU | `auto`：尝试 DirectML，创建 session 失败则 CPU；用户可设置强制 CPU |
| 包体 | OCR ORT / 模型 **不**写入 `electron-builder` 默认 `files`；若必须带 stub 启动器，体积护栏按打包文档审计 |

### 4.5 错误处理与降级

| 情况 | 行为 |
| --- | --- |
| 模型未下载 | `ensureReady` 触发下载；聊天路径可提示「正在准备本地 OCR」；超时则云端补 |
| Utility 崩溃 | 主进程标记 unhealthy，重启最多 K 次（建议 2），仍失败走云端 |
| DirectML 失败 | 静默回退 CPU，日志记 `backend=cpu reason=dml_fail`（OCR 路径允许 EP 降级；与「业务结果禁止静默伪造」不冲突） |
| 低置信 | 保留本地 `ocrText`，同时请求云端补；合并策略：云端非空则优先云端，或按字段 `ocrSource=mixed` 保留两者供调试（产品默认：**云端覆盖**本地） |
| 无 vision 槽 | 仅本地 OCR；失败则 `ocrText=''` + 明确错误码，不假装成功 |

### 4.6 平台分期

| 期 | 平台 | 算力 |
| --- | --- | --- |
| **P0（本设计）** | Windows | CPU + DirectML |
| P1 | Linux | **仅 CPU**（EP 后续再开） |
| P2+ | 按需 | 评估 WinML / 更新 ORT；仍禁止主进程混载 |

微信 `ocr4.ps1`：**不改**。

## 5. 模块划分与文件落点（预期）

| 模块 | 建议落点 | 职责 |
| --- | --- | --- |
| `OcrService` | `apps/windows/src/main/ocr/ocr-service.ts` | 生命周期、队列、降级编排 |
| Model manager | `apps/windows/src/main/ocr/ocr-model-manager.ts` | 下载、校验、路径 |
| Utility 入口 | `apps/windows/src/main/ocr/ocr-utility.ts`（或独立打包脚本入口） | 加载 ORT、跑 pipeline |
| Pipeline | `apps/windows/src/main/ocr/ppocr-pipeline.ts` 或小依赖封装 | det/cls/rec + 后处理 |
| IPC | `image:ocr` / 扩展 `image:recognize`；preload `ElectronAPI` 同步 | 渲染层可选直接调本地 OCR |
| Bridge 接线 | `bridge-image-services.ts` + 截图 tools + document 路径 | A/B/D |
| 配置 | provider/设置页或实验开关：启用本地 OCR、backend、置信阈值 | 可先主进程配置 + 后续 UI |

原生 ORT for utility：与主进程 `onnxruntime-node@1.14` **版本解耦**；以 utility 目录私有二进制加载（绝对路径 / 旁路 DLL 搜索），避免基名污染。

## 6. 安全 / 隐私 / 风险

| 风险 | 缓解 |
| --- | --- |
| 用户图片出域 | 本地 OCR 默认不上网；仅降级云端时走现有 vision 通道与用户已配密钥 |
| ORT DLL 再次冲突 | 进程隔离 + 加载路径隔离；回归：sherpa VAD + E5 + OCR 交错压测 |
| 包体膨胀 | 模型与 ORT 按需下载；`verify:win-package` / 体积审计 |
| DirectML 驱动差异 | 失败回退 CPU；设置项强制 CPU |
| 资源占用 | 空闲退出、单飞队列、maxSide、关 mem arena |
| Prompt 注入（截图 OCR 进 Agent） | OCR 文本按工具结果普通字段处理，沿用现有工具输出消毒策略 |

## 7. 分期与退出标准

### P0 — Windows 可用（本设计范围）

退出标准：

- [ ] 聊天附件：本地产出 `ocrText`，云端仍出 `description`；本地失败可云端补  
- [ ] 至少一种 Agent 截图工具结果带 `ocrText`  
- [ ] 无文字层 PDF 单页 / 图片扫描件可抽字  
- [ ] 无独显机器纯 CPU 可完成上述路径  
- [ ] 有 DirectML 时 `backend` 可为 `dml`，失败自动 `cpu`  
- [ ] 启动后仅跑 VAD+E5、不跑 OCR 时，行为与现网一致（无新崩溃）  
- [ ] 安装包体积不因 OCR 模型显著增加（模型不进包）  

### P1 — Linux CPU

- 同 API；utility 仅 CPU EP；接入 `test:all` Linux 口径差异说明  

### P2 — 体验与可观测

- 设置页开关、下载进度、置信阈值；诊断页展示 backend / 耗时  

## 8. 测试与验收

### 单测

- `OcrService` 队列、超时、崩溃重启、空闲退出（mock utility）  
- 置信降级与 `ocrSource` 合并策略  
- PDF「有文字层跳过 OCR / 无文字层触发」阈值逻辑  
- `/** @vitest-environment node */` 凡 mock 子进程处  

### 集成 / 手测

- 中英 UI 截图、聊天泡图、扫描件照片各若干张，抽检正确率与耗时  
- 与语音 VAD 同时开启、触发 Wiki/宫殿 E5 后仍可 OCR  
- 强制 CPU / auto DML 切换  
- 断网：仅本地；未下模型：下载或降级云端  

### 性能目标（P0 参考，实测定标）

| 场景 | 目标（Windows 常见办公机 CPU） |
| --- | --- |
| 1080p 截图、文字区域中等 | 端到端 P50 &lt; 1.5s（含进程已热） |
| 冷启动（含拉起 utility，模型已在盘） | P50 &lt; 3s |
| 空闲退出后 RSS | OCR 相关进程退出，主进程无明显长期泄漏 |
