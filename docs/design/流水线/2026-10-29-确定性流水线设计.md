## 0. 结论摘要

| 项 | 结论 |
|------|------|
| 主目标 | 把"长且步骤可枚举"的自动化从"模型自由循环"降级为"确定性执行器跑一份声明式 spec"，消除字幕/配音/实操三者的错位 |
| 范围 | 一个执行引擎（工具 `pipeline_run` + 4 种 step kind）+ N 份数据化 spec；**不做**可视化编排器、不做 DSL、不做分布式（§1.4） |
| 技术路线 | spec 引用**已注册的工具名**（不新造动作词表）；执行器逐步派发、逐步落 journal、逐步打点；录制与旁白从同一条 step 记录派生 |
| 交付形态 | 引擎是**一个热插拔插件**（`com.lumii.pipeline`）；流水线是**数据**（`{workspace}/pipelines/<id>/spec.json`），加一条流水线 = 加一个 JSON（§6.4） |
| 数据落点 | `{workspace}/pipelines/`（与 `skills/` 同根）+ 云同步映射，**换设备可直接用**；`runs/` 进 VCS 忽略清单（§5.2） |
| 最大风险 | 变成"只有一条流水线的框架"——本仓库已有四处"声明了但没人消费"的先例（§2.3），故 P0 退出标准是**两条不同流水线跑通**（§8） |

## 1. 背景与目标

### 1.1 用户陈述的问题

客户端能很好地完成大部分琐碎复杂任务，但**长且复杂的自动化**不稳定。具体现场：让客户端录制一段"自动回复微信消息"的演示视频，它做了大量测试、规划、录制、实际操练，但这些环节是**割裂**的——录出来的视频里，字幕、配音、真实操作内容对不上。把它"做成固化技能"效果不明显。

要求：做一条**专用流水线**，比 skill 更稳定；复杂度和使用难度**不高于** skill；易于搭建、修改、使用。从架构和组织上根本解决。

### 1.2 代码事实核查

以下每条都在本仓库代码里核实过，是本次设计的事实基础。

**(a) 技能是提示词，不是执行单元。**

- `skill_invoke` 只做三件事：读 SKILL.md 全文、列资源清单、记一次使用次数，**不执行任何东西**（`packages/agent-runtime/src/tools/built-in/skill-tools.ts:146-240`）。
- 技能确有可执行通道，但窄到无法承载流程：`detectClaudeCodeEntry` 在根目录与 `scripts/` 下按 `.py → .ts/.js → .ps1 → .sh` **只挑第一个文件**当入口（`apps/windows/src/main/skill-external-loader.ts:83-158`），一次同步调用、**120s 硬超时**（`:182`）、无沙箱（`apps/windows/src/main/index.ts:345` 传 `enableSandbox=false`）、无状态、无重试、**没有"第 N 步"这个概念**。
- 结论：「固化技能效果不明显」是结构性结果。技能只改变"模型倾向于怎么做"，不改变"运行时保证怎么做"。继续加长提示词无法解决——本仓库的两份录屏设计文档已经量化过失败：一次教程任务 70 次思考、25+ 次截图、30~45 分钟推理，**有效画面 15~25 秒**（`docs/design/录屏与教程/2026-08-16-Agent录屏教程效率优化设计.md` §1.1）。

**(b) 收窄到"必须一次工具调用跑完"。**

`maxTurns` 在 `turn_end` 直接 `abort()`，**不先收尾**（`packages/agent-runtime/src/agent/agent-instance.ts:588-598`）。内置 Agent 上限 30–80（`packages/agent-runtime/src/agent/builtin/definitions.ts:94/126/145/165/212/247/289`），宠物与代聊 20。

结论：**不能设计成"模型逐步调用 pipeline_step"**——一条 20 步的流水线自己就撞天花板。整条链必须在一个工具调用内跑完。这不是妥协，这恰好逼出正确形态：执行器必须是纯代码。

**(c) 融合层已经是确定性的，误差全在时间轴来源。**

`narrate-service.ts:355-400` 已做到：探测 TTS 实际时长、冲突时压到下一段前 200ms、`atrim` 物理截断防重叠。**融合不该再改。**

误差出在源头：`screen_record_mark` 的 `atMs` 是**模型觉得"该打点了"那一刻**的活跃时钟（`screen-record-service.ts:532-565`），而真实操作发生在 `app_act` 返回之前。两份时间各写各的，靠模型事后缝合。并且 `app_act` 与 `screen_record_mark` 之间**没有任何联动**——`2026-08-16-Agent录屏教程效率优化设计.md` 的非目标里明确写了"不把 app_act 强绑自动 mark"。

**(d) 剧本已经存在，但只是输出物。**

`bundled-skills/视频创作/screen-tutorial-pipeline/SKILL.md:76-145` 定义了 `TutorialNavSpec v1`：`steps[] / action.kind 白名单 / verify / pauseAfterMs / postCleanup`，并写了硬性禁令「MUST 用 steps[i] 作为唯一操作输入」。

但执行者仍是 LLM——它读这段 JSON，然后逐条自己调工具。spec 只约束"该干什么"，不约束"干了没有、什么时候干的、结果对不对"。

**(e) 仓库里唯一被真机验证过的端到端编排，是录屏链。**

`start → mark → stop(timeline) → narrate(cues) → inspect`。它能跑通靠的不是模型记忆，而是 **timeline / cues 两个数据类型的契约**（`apps/windows/src/shared/screen-record.ts:106`、`apps/windows/src/main/kernel/screen-record-contract.ts:44`）。这是本设计要照抄的形态。

**(f) 工具可以被程序按名找到，但直接 execute 会绕过权限闸门。**

`ToolRegistry.get(name)` 存在（`packages/agent-runtime/src/tools/tool-registry.ts:44`）。但注册进 registry 的是**未包装**的 `MtBotTool`；权限闸门、审计、日志是 `assembleTools` 在**每个 Agent 实例装配时**包上去的（`packages/agent-runtime/src/host-kit/tool-assembly.ts:138-175`，`new ToolRunner` 在 `:142`）。

结论：执行器不能直接 `toolRegistry.get(n).execute()` 了事——那会静默跳过权限。处理方式见 §7.1。

**(g) 插件能注册工具，但目前只有一个窄口。**

只有三个 `bridge.install*Tools()` 方法：`installDashboardFeedTools`（`bridge.ts:3702`）、`installBrowserTools`（`:3715`）、`installWechatTools`（`:3730`）。插件形态可行，但要先加第四个 install 方法。这是一次性成本，§6.4 会说明为什么仍然值得。

**(h) 四处「声明了但没人消费」——本次设计必须绕开的坑。**

| 声明处 | 现状 |
|---|---|
| `PluginContributions.contributes`（`packages/plugin-core/src/manifest.ts:70`） | 全仓 grep `.contributes` 为空，**无任何读取点** |
| `contributes.jobs` | 无调度器消费 |
| `todo_write` 的 `parallel` / `dependsOnIndex`（`task-tools.ts:58-68`） | 写进了表，**无调度器消费** |
| `skill-execution-logger` 的执行日志 | `queryExecutionLogs` 全仓仅出现在自身与 IPC 委托里，**无消费者** → 因此"这条技能成功率多少"至今不可答 |

后两条是本次设计最直接的教训：**不可度量的编排，等于没有编排。**

### 1.3 目标

| 维度 | 目标态 | 度量 |
|---|---|---|
| 稳定性 | 同一 spec 重复跑，步数与结果一致 | 10 次连跑，步数差异 0 |
| 对齐 | 字幕时间与本步骤操作**同源** | 无人工校正即对齐 |
| 成本 | 一条 N 步流水线的 LLM 往返 | 作者态 1 次，运行态 **0** 次 |
| 搭建 | 新增一条流水线 | 一个 JSON 文件，零代码 |
| 可诊断 | 失败时能指出第几步、期望什么、实际什么 | journal 可读 |

### 1.4 明确不做（Non-Goals）

- **不做可视化拖拽编排器**。Spec 是给人改的文本文件；有了 GUI 就要维护两套模型。
- **不做新 DSL / 不做编译器**。用 JSON，键名照抄已有的 `TutorialNavSpec`。
- **不做自动重试 / 自动修复**。失败即停并报因——重试正是非确定性的入口。
- **不做分布式 / 多机 / 任务队列**。单用户单机，串行。
- **不改采编底层**：`screen-record-service` 状态机、`narrate-service` 融合逻辑、`controller` 动作实现一律不动。
- **不替换 skill 体系**。skill 降级为"作者态"工具（§5.5）。

## 2. 问题定位

### 2.1 根因：长任务被表达成了"自由循环"

每一步"下一步做什么"都是一次采样。设单步正确率 p，N 步成功率 ≈ p^N。上文 70 次思考里，每次都要重新推断"我在哪页、这个 ref 是不是它、该滚还是该点"——p 撑不到 0.95，20 步就退到三成。

这是**概率结构**，与提示词质量无关。

### 2.2 三种媒介的约束力对比

| 媒介 | 谁能违反 | 能否保存状态 | 事实来源 | 单次成本 |
|---|---|---|---|---|
| SKILL.md | 模型可以合理地不照做 | 否，断了只能重来 | 模型自述 | 全文进上下文 |
| 声明式 spec + 确定性执行器 | 执行器不会违反 | 每步落盘 | 系统时钟 + 视图回读 | 零 token |
| 模型自由循环 | —— | 内存态，重启即丢（`background-task-manager.ts:14`） | 模型推理 | 每步一次往返 |

### 2.3 组织上的根因：一人分饰五角

现状里 Agent 同时是导演、演员、摄影、剪辑、质检，共用一个采样器。拆开后每个角色的失败模式独立、可单独定位：

| 角色 | 执行者 | 失败模式 |
|---|---|---|
| 编剧 | LLM（一次） | spec 写错 |
| 执行 | 代码 | 某步平台不一致 |
| 合成 | 代码（narrate 已有） | 无（已确定性） |
| 质检 | 代码断言 | 断言写漏 |

## 3. 方案对比与选型

### 3.1 四个候选

**方案 A：继续加强 skill（更多禁令、更结构化输出）**
否决。§1.2(a) 已证：技能没有步骤边界、没有状态、没有失败点。本仓库已经写过两轮"禁令 + JSON 手册"，实测仍是 70 次思考。

**方案 B：专用 Agent（复用 `专项Agent` 的「一等公民」概念）**
否决。专用 Agent 仍是采样循环，上限 30–80 回合（§1.2(b)），且它解决的是"职责归属"，不是"路径确定性"。可以并行存在，但解决不了本次问题。

**方案 C：确定性执行器 + 声明式 spec**（选定）
把 `TutorialNavSpec` 从"输出物"翻成"输入物"，由代码逐条执行。一步错就停，改了重跑。

**方案 D：引入 Temporal / LangGraph / Inngest**
否决。理由三条：① 要带一个新运行时与部署面；② 拿不到本应用的工具上下文（`ToolExecutionContext` 绑在进程内窗口与 controller 上，无法跨进程重放）；③ 我们的问题不是"崩溃后恢复"，是"路径不该由模型决定"。持久化只到"步骤 journal"这一层，用目录 + JSONL 就够（§5.2）。

### 3.2 选型理由一句话

不要把这件事做得更"智能"，要把它做得更"不像 AI"。剧本给 LLM，执行给代码，时间戳给系统，LLM 只在出错时被叫回来一次。

### 3.3 与 SKILL.md 的复杂度对比（回应"不能高于 skill"）

| 维度 | 现状（skill） | 本设计 |
|---|---|---|
| 搭建 | 写 272 行 prose 教模型怎么做 | 写一份 ~30 行的 JSON steps 表 |
| 修改 | 改文档 + 祈祷模型读到并照做 | 改一行，重跑 |
| 使用 | 对话里说一句话，赌它走对 | 聊天里一句"跑 wechat-reply-demo"，或页面点一下 |
| 调试 | 读 70 段思考文本 | 读 journal，看 `failedAt` |
| 失败后 | 从头发散 | 从断点续跑 |

## 4. 核心设计

### 4.1 架构

```
① 编剧（LLM，仅作者态，一次）
    探路 → 写 {workspace}/pipelines/<id>/spec.json
              │
              ▼
② 执行器（纯代码，零 LLM）
    pipeline_run(specId)
      ├─ 校验 spec（工具名必须已注册，否则拒绝启动）
      ├─ 一次性权限审批（§7.1）
      ├─ 若 record.enabled → screen_record_start
      └─ for step of steps:
           ├─ run     : toolRegistry 派发（§4.4）
           ├─ mark    : 若 record 且 step 有 narration → mark(label)   ← 同源
           ├─ hold    : holdMs 停留（画面停在该步结果上）
           ├─ assert  : 视图回读 / 工具返回断言（§4.5）
           └─ journal : 追加一行到 journal.jsonl
      ├─ 若 record.enabled → screen_record_stop → narrate(cues) → inspect
              │
              ▼
③ 合成器（既有代码，不改）
    narrate-service：TTS 时长探测 + 冲突压缩 + atrim 截断
              │
              ▼
④ 质检器（纯代码断言）
    产物存在 / 时长 / 字幕条数 / 静音段；不过才叫 LLM 一次
```

关键：**`mark` 与 `cue` 来自同一个 step 对象**。`atMs` 由执行器在动作返回后立刻取系统活跃时钟，`text` 就是 `step.narration`。二者不可能错位——不是"对齐"，是**同源**。

### 4.2 修订记录（相对 2026-10-29 口头方案）

| 项 | 口头方案 | 本文 | 理由 |
|---|---|---|---|
| 数据落点 | 抄 cron 建两张 sqlite 表 | **不建表，用目录 + JSONL** | 引擎是**可选插件**，核心 schema（`SCHEMA_VERSION = 54`）不该为它加表；journal 是只追加、可读、单次读一个 run，目录扫描足够。若将来要跑统计再看要不要 SQL |
| step 词表 | 沿用 `TutorialNavSpec` 的 7 个 `action.kind` | **只留 `tool` 一种动作**，直接写工具名 | 那 7 个 kind 全是对现有工具的语法糖。让引擎自带词表 = 第二次维护（工具改名/新增时 spec 与引擎漂移）。写工具名则永不过期 |

### 4.3 Spec 数据模型

```jsonc
{
  "specVersion": "1.0",
  "id": "wechat-reply-demo",
  "name": "微信自动回复演示",
  "description": "演示代聊如何读取并回复一条消息",
  "risk": "sensitive",                  // read | write | sensitive（决定审批强度，§7.1）

  "record": {                            // 可选；缺省 = 不录
    "enabled": true,
    "sourceHint": "auto",                // auto | 具体 sourceId
    "includeMic": false,
    "narrate": { "dub": true, "subtitleMode": "burn", "exportMp4": true }
  },

  "preconditions": [                     // 启动前断言，不满足直接拒绝且不录
    { "kind": "toolOk", "tool": "wechat_check_env" },
    { "kind": "toolOk", "tool": "relay_status", "expect": { "running": false },
      "hint": "先停代聊，否则会抢占同一会话" }
  ],

  "steps": [
    {
      "id": "open-chat",
      "label": "打开会话",
      "narration": "首先打开与客户的会话。",
      "tool": "wechat_list_sessions",
      "params": { "query": "客服" },
      "holdMs": 1200,
      "expect": { "fields": { "ok": true } }
    },
    {
      "id": "read",
      "label": "读取最近一条",
      "narration": "读取最近一条消息的内容。",
      "tool": "wechat_read_history",
      "params": { "talker": "{{open-chat.sessions[0].talker}}", "limit": 1 },
      "holdMs": 2000,
      "expect": { "fields": { "ok": true } }
    },
    {
      "id": "fill",
      "label": "填入回复（不发送）",
      "narration": "把生成的回复填进输入框。",
      "tool": "app_fill_form",
      "params": { "fields": [{ "slotHeading": "输入框", "label": "消息", "text": "您好，已收到" }] },
      "holdMs": 1500
    }
  ],

  "postCleanup": [
    { "tool": "app_act", "params": { "kind": "clearInput" } }
  ]
}
```

**约定（写死，不做可选）：**

| 键 | 语义 |
|---|---|
| `steps[].tool` | 必须是启动时 `toolRegistry.get(name)` 存在的工具名。**不存在 → 加载即拒**，不允许跑到第 7 步才发现 |
| `steps[].expect` | 断言，见 §4.5。缺省 = 只断言工具返回 `isError !== true` |
| `steps[].holdMs` | 动作返回后停留时长，供观众看清结果；缺省 800 |
| `steps[].narration` | 有它才在录制里打点。**没有旁白就不该有画面停留**，反之亦然 |
| `{{stepId.path}}` | 引用先前步骤返回值（JSONPath 极简子集：`a.b[0].c`）。**引用只能向后**，循环检测在加载期做 |
| `postCleanup` | 无论成败都跑；失败也要尽力执行，只记日志不抛出 |

**不做的事情**：不做条件分支、不做循环、不做并发。需要分支说明路径不能枚举——那就不该做成流水线（§7.4 判据）。

### 4.4 执行器

```
pipeline_run(specId, { mode: "record" | "rehearsal", resumeRunId? })
```

| 阶段 | 行为 |
|---|---|
| 加载 | 读 spec → schema 校验 → 工具名存在性校验 → 引用完整性校验（含向后引用 + 无环）→ `specHash = sha256(spec 归一化文本)` |
| 审批 | 按 `risk` 与涉及工具的 `needsPermission` 汇总**一次**审批（§7.1） |
| 预备 | `record.enabled` → `screen_record_start`（失败则整条拒绝，不降级成"不录但继续"） |
| 预条件 | 跑 `preconditions`，任一不满足 → 停，返回 `{ stage: "precondition", failedId, observed }`，**且不 start 录制**（顺序：预条件在录制开始之前） |
| 主循环 | `run → mark(若record) → hold → assert → journal`，任一步失败即停 |
| 收尾 | `postCleanup`（尽力） → `screen_record_stop` → `narrate(cues, …)` → `inspect` |
| 返回 | `{ ok, runId, journalPath, failedAt?, steps: [{id, ok, ms, observed}], artifact?: {mp4Path, burned, dubbed, durationMs, cueCount} }` |

**rehearsal 模式规则（三条，其余完全同 record）：**

1. `needsPermission === true` 的工具**不执行**，记 `skipped: "rehearsal"`，并按 schema 造一个"最小可用的假返回"供后续 `{{}}` 引用（无 schema 可用时填空对象）。
2. **不 start 录制**。
3. `assert` 仍执行——rehearsal 的价值就在"确认每一段的选择器都还命中"。

**resume 规则**：读 `journal.jsonl`，跳过已 `ok` 的 step；但先校验 `specHash` 一致，不一致拒绝（否则续跑是在撒谎）。

**mark 的时机**：在工具返回**之后**、`hold` **之前**。原因：观众该看到的是"动作完成后的界面"，而那一刻正是画面变化可见的帧。活跃时钟由 `screen_record_mark` 自己从服务取，执行器不传时间——**执行器不拥有时钟**。

### 4.5 断言（expect）

三类，全部确定性、零 LLM：

| kind | 依据 | 例 |
|---|---|---|
| `fields` | 工具返回的 JSON 字段 | `{"fields": {"ok": true, "sessions.0.talker": "wxid_x"}}` |
| `viewState` | 复用 `app_goto` 已有的视图回读通道（`VIEW_STATE_SCRIPT` → `{view, hub:{open,tab,category}}`，`controller.ts:53`，`App.tsx:224-236`） | `{"viewState": {"view": "chat", "hub.open": false}}` |
| `exists` | 文件/路径存在（含产物） | `{"exists": "{{open-chat.exportPath}}"}` |

匹配语义：`fields` 为**子集匹配 + 路径寻址**（不要求全等，避免工具多加字段就判失败）；`viewState` 为全等匹配。失败返回 `{expected, observed}`，两个值都进 journal。

**不得**用"截图 + 视觉比对"做断言——那是把不确定性搬回执行器。

### 4.6 与录屏/旁白的耦合点

只有一个：`record` 块与 `steps[].narration`。执行器内部：

```
cues = steps.filter(s => s.narration)
            .map(s => ({ startMs: journal[s.id].markAtMs, text: s.narration }))
```

`endMs` 交给 `narrate-service` 自己按"下一段起点 − 200ms"算（已有逻辑，`:386-400`）。执行器**不重算**融合规则。

由此得到一条硬保证：**只要 step 有旁白，就必然有一个真实操作时刻与之对应**；只要旁白时间对不上画面，那一定是 spec 写错了，而不是运行时漂移了。

**必须知道的两个事实（否则会以为已经能跨设备）**

**所以，跨设备需要两处小改动**

**(a) 忽略 runs/，不污染快照** —— `apps/windows/src/plugins/builtin/vcs/vcs-ignore.ts` 的 `DEFAULT_VCS_IGNORE_RULES` 增加：

### 6.4 插件形态：能做，且该做——但只有引擎做插件

**回答原问题：可以使用插件形式来扩展这个功能。**

| 对象 | 是否做成插件 | 理由 |
|---|---|---|
| **执行引擎** | ✅ 是，`com.lumii.pipeline` | 三个真实收益：① `hot: true` 即时启停（`registry.ts` 16 个内置插件已标 hot），停用后工具与页面同时消失 —— 这正是本仓库插件化的既定形态；② UI 走槽位，不改核心页面（`app.nav`/`app.view`/`registerTimelineCard` 全是现成口子）；③ **spec 在 `{workspace}/pipelines/`，不归插件所有**——卸载/重装插件不碰用户数据，换设备也带得走 |
| **每条流水线** | ❌ 不是 | 若一条流水线 = 一个插件，就要 manifest + `apply` + `renderer` + 构建 + 激活时机 + 设置页条目。**这会直接击穿"搭建难度不高于 skill"**——skill 只是一份 md。流水线必须是**数据**：一个 JSON 文件放进目录就被发现 |
| **step 执行器扩展** | 暂不做（P3） | 若将来出现 `tool` 之外的 step 类型（如"等某个事件"），可由别的插件提供 executor 并注册到 `S.pipeline`。现在**没有第二种 step**，先不做 seam（YAGNI） |

**一次性成本（诚实披露）**：需要在 `bridge.ts` 加第 4 个 `installPipelineTools()`。这是当前插件注册工具的唯一通路（§1.2(g)）。之后**加流水线永不再动 bridge**。

### 6.5 插件启停后的行为（必须明确，否则会假绿）

| 状态 | 行为 |
|---|---|
| 引擎禁用 | `pipeline_*` 工具不注册；`app.nav` 条目不出现（`renderer.tsx` 的 `setup` 清理函数生效，`RendererPlugin.setup` 返回 disposer，见 `plugins/api/renderer.ts`）；**已有 spec 文件保留**；已有 run 的 journal 保留（只读） |
| 运行中禁用 | 先 `screen_record_stop`（尽力），journal 标 `aborted: "extension_disabled"`，产物按已录部分交付并标注"被中止" |

## 7. 安全 / 隐私 / 风险与缓解

### 7.1 权限：审批"整条计划"，不审批"每一步"

**问题**：执行器直接 `toolRegistry.get(n).execute()` 会绕过 `assembleTools` 包的权限闸门（§1.2(f)）。若改成每步都问用户，一条 8 步流水线会弹 8 次——这是通知疲劳，用户最终会全点允许，比不审批更糟。

**设计**：

1. `pipeline_run` 工具自身 `needsPermission: true`。
2. 加载后、执行前，把涉及 `needsPermission === true` 的工具**汇总成一份清单**，随审批一并呈现（复用现有 permission provider，不新造 UI）。
3. `spec.risk === "sensitive"` 时**强制**要求审批，不得被"允许并记住"跳过——绕过方式是显式改 spec，不是点一次按钮。
4. rehearsal 模式下 `needsPermission` 工具一律不执行（§4.4），因此 rehearsal **不需要**审批。

审批对象是"这份 spec 会点哪些有副作用的工具"，一次给全。

### 7.2 微信场景的两条硬约束

真实发送**不可撤回**，比录 Lumii 截图严格一档。

1. **rehearsal 必跑**：`risk: "sensitive"` 的 spec 首次运行若为 `mode: "record"`，执行器先跑一遍 rehearsal（不录不发送），全绿才允许 record。判据来自工具自身的 `needsPermission`（侧车已从 `_DESTRUCTIVE_TOOLS` / `_OPEN_WORLD_TOOLS` 推导，`apps/windows/assets/wechat/app.py:1748/1751`；桥接层落到 `needsPermission`，`bridge-wechat-tools.ts:62` 附近）——**不新造分类**。
2. **前置条件是断言，不是散文**。"测微信要先停代聊"这条现在活在记忆里的人话，在 spec 里写成 `preconditions`（如 `relay_status.running === false`），不满足即拒绝启动。否则会产出一条"看起来跑完了，其实抢了代聊会话"的视频。

### 7.3 其他风险

| 风险 | 缓解 |
|---|---|
| 界面改版导致 spec 失效 | `expect` 失败即停并报 `{expected, observed}`；工具名不存在在**加载期**就拒。失败可见、可定位，不静默 |
| `{{}}` 引用把 typo 变成空值 | 引用路径在加载期校验（键存在性无法静态验，但格式与向后性可验）；运行时解析失败 = 判该步失败 |
| spec 漂移（跑了 6 步才发现） | 加载期三道校验（工具名 / 引用 / 无环）+ 每步断言 |
| 录制没起来但流程照跑 | `record.enabled` 时 `screen_record_start` 失败 → **整条拒绝**，不降级 |
| 变成"写死不能用的脚本" | §7.4 判据；P0 用两条不同流水线验证通用性 |
| journal 无限增长 | 每次 run 一个目录，`meta.json` 记时间；P2 加清理（保留最近 N 次 + 被标记的），**默认不删** |
| 滥用成通用队列 | `pipeline_run` 只接受 spec 文件路径/specId，不接受任意工具序列。任意序列请直接调工具 |

### 7.4 什么时候**不该**做流水线（写进工具描述与页面空态）

三条全中才做：① 路径能预先枚举；② 每步有可断言的结果；③ 会重复跑。
不满足就留在 Agent 里。硬套会变成"写死的不够用的脚本"，**比 agent 更糟**。

## 8. 分期与退出标准

### P0 — 引擎 + 一条真流水线（约 2 人日）

| 内容 | 验收 |
|---|---|
| `spec.ts` / `runner.ts` / `journal.ts` / `store.ts` | 单测覆盖：校验三关、rehearsal 跳过、resume 跳步、specHash 不符拒绝 |
| `pipeline_run` + `pipeline_list` 工具 | 一次调用跑完 N 步；失败返回 `{failedAt, expected, observed, journalPath}` |
| `bridge.installPipelineTools()` + registry 一行 | 启停即时生效 |
| `resolvePipelinesDir()`（`workspace-paths.ts`）+ `vcs-ignore.ts` 加 `pipelines/**/runs/` | 新建工作区 `git status` 不出现 runs/ |
| 云同步映射 `workspace/pipelines/`（§5.2(b)） | 设备 A 新建 spec → 同步 → 设备 B 上流水线页可见且可跑 |
| 时间线卡（运行中/成功/失败三态） | 真机截图，对照 `prototype/pipeline-ui.html` 第二节 |
| `wechat-reply-demo` spec（rehearsal 可跑） | rehearsal 全绿 |

**退出标准（硬）**：同一 spec 连跑 3 次，步数与每步 `observed` 一致；产物 MP4 的 `cueCount === 有 narration 的 step 数`。

### P1 — 断点续跑 + 页面 + 第二条流水线（约 2 人日）

| 内容 | 验收 |
|---|---|
| `pipeline resume <runId>` | 第 5 步失败 → 改 spec → 续跑只跑第 5 步起 |
| `{workspace}/pipelines/` 扫描 + 流水线页（清单/详情/历史） | 按原型实现两栏布局；禁用插件后条目消失 |
| 已有工作区的 `.gitignore` 迁移（补 `pipelines/**/runs/`） | 老库升级后 `runs/` 不被跟踪 |
| `pipeline_inspect` | 返回 journal 摘要 + 产物校验 |
| **第二条流水线**（如 `model-config-tutorial`，复用既有 NavSpec 内容） | 不写新代码即可跑通 |

**退出标准（硬）**：**两条不同流水线**跑通。这是本次设计最关键的验收——若只有一条能跑，说明它是单用例包装而不是框架（§1.2(h) 的教训）。

### P2 — record 模式 + 合成闭环 + 可度量（约 2 人日）

## 9. 测试与验收

### 9.1 单测点（TDD，先写失败测试）

| 模块 | 用例 |
|---|---|
| `spec.ts` | 未知工具名 → 拒；前向引用 → 拒；循环引用 → 拒；`steps` 空 → 拒；缺 `id`/重复 `id` → 拒 |
| `runner.ts` | 步序正确；失败即停且后续步不执行；`holdMs` 生效；`postCleanup` 在失败时仍尽力执行；rehearsal 跳过 `needsPermission`；断言 `fields` 子集匹配语义；`viewState` 全等匹配 |
| `journal.ts` | append 顺序；resume 计算跳过集；`specHash` 不符拒绝；半行损坏容忍（读时跳过并记 `corrupt`） |
| `tools.ts` | `pipeline_run` 参数校验；返回结构；失败时 `isError` 与 `content` 内容（遵守 `types/tool.ts` 的失败语义契约——**模型需要的信息必须写在 content 里**，`details` 会被清空） |

### 9.2 手测点（真机，`lumii-ui` CLI）

1. 引擎禁用 → `tools list` 无 `pipeline_*`；侧栏无"流水线"；spec 文件仍在。
2. 启用 → 条目出现，无需重启。
3. 跑 `wechat-reply-demo` rehearsal → 卡显示三态正常；journal 有 N 行。
4. 中途 `user:abort` → journal 标 aborted，`screen_record_stop` 被调用（`inspect` 有产物）。
5. 改 spec 的 `specHash` 后 `resume` → 拒绝并说明原因。

### 9.3 性能目标

- 单步额外开销（journal 写盘 + mark + 断言）：**< 20ms**
- 8 步 spec（不含 hold 与录制）：总耗时 < 1s
- 不影响 Agent 回合：`pipeline_run` 为单次工具调用，不增加往返

### 9.4 回归门禁

`pnpm -C apps/windows test:all` 全绿（基线已清零）；`pnpm tsc` 0 错误（vitest 不做类型检查）。

现行 skill 里的 NavSpec 可作为**作者态的草稿格式**，转换规则：

| NavSpec | spec |
|---|---|
| `steps[].id/label/narrationZh` | `id/label/narration` |
| `action.kind: goto` | `tool: "app_goto"` |
| `action.kind: scroll_to_heading` | `tool: "app_scroll_to_text"` |

转换是机械的，可先手写一份。**不做自动转换器**（一次性工作，做完就过期）。
